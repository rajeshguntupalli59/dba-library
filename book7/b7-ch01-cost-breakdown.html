Chapter 1 of 30 Stop Overpaying for SQL Server

Chapter 1: Where Your Cloud Database Bill Actually Comes From

Most teams migrating to cloud databases expect their bills to be lower than their on-premises costs, or at least predictable. Instead, they open the first full month's invoice and find a number that is 40–60% higher than anyone budgeted. The engineering team points at the DBAs, the DBAs point at the architects, and the finance team points at everyone. This chapter stops the finger-pointing by mapping exactly where cloud database spend originates, how each cost component grows, and which levers move the needle fastest. The techniques in this chapter alone — primarily tagging, right-sizing, and storage class migration — routinely save teams between $8,000 and $40,000 per month on mid-sized deployments before any architectural changes are required.

---

1.1 The Anatomy of a Cloud Database Bill

Cloud database pricing is not a single line item. It is a stack of at least seven distinct charges, and most teams are only watching one or two of them. Understanding each layer is the prerequisite to cutting any of them.

Compute (instance hours) is usually the largest single charge, but it is also the most visible. An db.r6g.2xlarge on AWS RDS costs $0.48 per hour on-demand, or $4,204.80 annualized. The equivalent on Azure SQL (Business Critical, 8 vCores) runs approximately $1.13 per vCore-hour. On GCP Cloud SQL, a db-custom-8-32768 instance costs roughly $0.4465 per hour for the VM component alone. Teams that provision for peak traffic and never revisit those sizes pay full rate around the clock.

Storage is the second-largest charge and the most underappreciated growth driver. On AWS RDS, gp2 storage costs $0.115 per GB-month. gp3 costs $0.092 per GB-month for the first 3,000 IOPS and 125 MB/s throughput, which are included. A 1 TB database on gp2 costs $117.76/month. The same workload on gp3 costs $94.21/month — a saving of $23.55/month, or $282.60/year, for a single database instance with zero performance change. Multiply that across 20 instances and you have saved $5,652 annually by changing a storage type flag.

I/O charges on RDS for SQL Server take two forms. gp2 and magnetic volumes bill per million I/O requests, while io1/io2 volumes bill per provisioned IOPS-month — roughly $0.10–$0.125 per IOPS-month whether the IOPS are used or not. A SQL Server instance provisioned with 10,000 io1 IOPS pays $1,000–$1,250/month for I/O capacity alone, before storage costs. Moving a workload that averages 2,500 IOPS from io1 to gp3 (3,000 IOPS included in the base price) eliminates the provisioned-IOPS charge entirely — a saving of over $1,000/month per instance with no performance change for most OLTP patterns. Chapter 14 runs the full break-even analysis.

Backup storage defaults to retaining 7 days of automated backups. AWS includes backup storage equal to 100% of your provisioned database storage at no charge. Anything beyond that costs $0.095/GB-month. If your database is 2 TB and you have a 35-day retention window, you are paying for approximately 9 TB of backup storage above the free tier: $855/month in backup costs alone.

Data transfer charges catch teams off guard when analytics pipelines, application servers, or cross-region replicas are added. Intra-region transfer from RDS to EC2 in the same Availability Zone is free. Moving data to a different AZ costs $0.01/GB in each direction. Transferring data out to the internet costs $0.09/GB (for the first 10 TB/month on AWS). A 500 GB monthly export to an external analytics platform costs $45/month in transfer fees, before compute.

Licensing is the dominant cost dimension for SQL Server in the cloud. It is either included in the per-hour rate (at a significant premium) or managed through License Included vs. BYOL (Bring Your Own License) pricing. An db.r6i.4xlarge running SQL Server Enterprise Edition with License Included costs $6.656/hour, or $58,306.56/year. The same instance running BYOL SQL Server costs $1.008/hour, or $8,830.08/year — a saving of $49,476.48/year if you have an existing SA agreement.

Multi-AZ and read replica charges double or multiply your compute costs. Every Multi-AZ instance provisions a synchronous standby in a second AZ, billed at the same rate as the primary. Teams that enable Multi-AZ on every instance, including development and test environments, are paying double for uptime guarantees that non-production workloads do not require.

Your bill is not one number — it is seven separate meters. Compute and storage get all the attention, but I/O charges, backup retention, cross-AZ data transfer, SQL Server licensing, and Multi-AZ replicas quietly compound. The arrows fan out from the bill to show that each component is metered independently, which is why a single optimization (like downsizing an instance) rarely moves the total the way you expect.

The following query, run against the AWS Cost and Usage Report data that has been exported to S3 and queried via Athena, gives you a breakdown of spend by these service components for any date range:

-- Run in Amazon Athena against your Cost and Usage Report (CUR) table
-- Replace 'your_cur_database.your_cur_table' with your actual table name
-- and adjust the date range as needed

SELECT
    line_item_product_code,
    product_volume_type,
    line_item_usage_type,
    SUM(line_item_unblended_cost)   AS total_cost_usd,
    SUM(line_item_usage_amount)     AS total_usage_units,
    COUNT(DISTINCT resource_tags_user_environment) AS environment_count
FROM your_cur_database.your_cur_table
WHERE
    line_item_product_code = 'AmazonRDS'
    AND line_item_line_item_type IN ('Usage', 'Tax')
    AND line_item_usage_start_date >= DATE '2024-01-01'
    AND line_item_usage_start_date <  DATE '2024-04-01'
GROUP BY
    line_item_product_code,
    product_volume_type,
    line_item_usage_type
ORDER BY
    total_cost_usd DESC;

This query surfaces the split between RDS:Multi-AZUsage, RDS:InstanceUsage, RDS:GP2-Storage, RDS:GP3-Storage, RDS:BackupUsage, and RDS:DataTransfer — typically revealing that two or three line items you were not tracking account for 25–35% of your total spend.

1.2 Tagging: The Foundation of Cost Accountability

You cannot optimize what you cannot attribute. Before any cost reduction work is meaningful, every database resource must carry tags that map it to a business owner, environment, and application. Without tags, cost reports are noise. With tags, they become a governance tool.

AWS, Azure, and GCP all support resource tagging, but the tag schemas differ. The following schema works across all three platforms and integrates cleanly with most finance and ITSM systems:

| Tag Key | Example Value | Purpose |

|---|---|---|

| environment | production, staging, dev | Separates prod costs from non-prod |

| application | payments-api, user-service | Maps cost to application |

| team | platform-engineering | Owner for chargeback |

| cost-center | CC-4821 | Finance integration |

| tier | tier-1, tier-2 | SLA tier for right-sizing policy |

| auto-shutdown | true | Enables scheduled stop/start automation |

The following script enforces this tag schema across all RDS instances in an AWS account. It is designed to run on a schedule via AWS Lambda or a CI/CD pipeline, not as a one-time task. Instances missing required tags are flagged to a Slack channel for remediation.

#!/usr/bin/env bash
# enforce_rds_tags.sh
# Run via cron, AWS Lambda (using aws-cli layer), or CI/CD
# Required environment variables: SLACK_WEBHOOK_URL, AWS_REGION

set -euo pipefail

REQUIRED_TAGS=("environment" "application" "team" "cost-center")
REGION="${AWS_REGION:-us-east-1}"
SLACK_WEBHOOK_URL="${SLACK_WEBHOOK_URL:?SLACK_WEBHOOK_URL is required}"
NON_COMPLIANT=()

# Retrieve all RDS instance ARNs in the region
INSTANCE_ARNS=$(aws rds describe-db-instances \
    --region "$REGION" \
    --query 'DBInstances[*].DBInstanceArn' \
    --output text)

for ARN in $INSTANCE_ARNS; do
    # Fetch tags for this instance
    TAGS_JSON=$(aws rds list-tags-for-resource \
        --region "$REGION" \
        --resource-name "$ARN" \
        --query 'TagList' \
        --output json)

    # Extract tag keys into a space-separated list
    EXISTING_KEYS=$(echo "$TAGS_JSON" | \
        python3 -c "import sys,json; \
        tags=json.load(sys.stdin); \
        print(' '.join(t['Key'] for t in tags))")

    MISSING=""
    for TAG in "${REQUIRED_TAGS[@]}"; do
        if ! echo "$EXISTING_KEYS" | grep -qw "$TAG"; then
            MISSING="$MISSING $TAG"
        fi
    done

    if [[ -n "$MISSING" ]]; then
        INSTANCE_ID=$(echo "$ARN" | awk -F: '{print $NF}')
        NON_COMPLIANT+=("$INSTANCE_ID: missing[$MISSING]")
    fi
done

# Report non-compliant instances to Slack
if [[ ${#NON_COMPLIANT[@]} -gt 0 ]]; then
    MESSAGE="*RDS Tag Compliance Alert* (${REGION})\n"
    MESSAGE+="${#NON_COMPLIANT[@]} instance(s) missing required tags:\n"
    for ITEM in "${NON_COMPLIANT[@]}"; do
        MESSAGE+="> $ITEM\n"
    done

    curl -s -X POST "$SLACK_WEBHOOK_URL" \
        -H 'Content-type: application/json' \
        --data "{\"text\": \"${MESSAGE}\"}"

    echo "Alert sent: ${#NON_COMPLIANT[@]} non-compliant instances"
else
    echo "All RDS instances are tag-compliant in ${REGION}"
fi

On Azure, the equivalent enforcement is done through Azure Policy. The following Azure CLI command creates a deny policy that prevents any Azure SQL instance from being deployed without the environment and team tags:

# Create a custom policy definition that denies SQL deployments without required tags
# Run once per subscription; policy evaluates on every new resource creation

az policy definition create \
    --name "require-sql-tags" \
    --display-name "Require environment and team tags on Azure SQL" \
    --description "Denies creation of Azure SQL servers and managed instances without required tags" \
    --mode "Indexed" \
    --rules '{
        "if": {
            "allOf": [
                {
                    "field": "type",
                    "in": [
                        "Microsoft.Sql/servers",
                        "Microsoft.Sql/managedInstances"
                    ]
                },
                {
                    "anyOf": [
                        {
                            "field": "tags[environment]",
                            "exists": false
                        },
                        {
                            "field": "tags[team]",
                            "exists": false
                        }
                    ]
                }
            ]
        },
        "then": {
            "effect": "deny"
        }
    }' \
    --params '{}'

# Assign the policy to your subscription
SUBSCRIPTION_ID=$(az account show --query id -o tsv)

az policy assignment create \
    --name "require-sql-tags-assignment" \
    --policy "require-sql-tags" \
    --scope "/subscriptions/${SUBSCRIPTION_ID}"

Once tagging is enforced, AWS Cost Explorer can group costs by tag in the console, and the Athena CUR query shown in section 1.1 can be extended with GROUP BY resource_tags_user_team to produce per-team chargeback reports automatically.

1.3 Finding the Waste: Right-Sizing Analysis at Scale

The single most common source of overspend in cloud databases is over-provisioning. The engineering team asked for db.r6g.4xlarge for a service that peaked at 12% CPU utilization six months later. No one revisited the size. This is not negligence — it is the expected outcome of an environment where resizing requires a maintenance window and no one is watching the utilization data systematically.

AWS Compute Optimizer analyzes CloudWatch metrics over a 14-day window and produces right-sizing recommendations for RDS instances. It considers CPU, memory, storage, and network throughput. The following Python script pulls these recommendations programmatically and calculates the projected monthly savings for each instance:

#!/usr/bin/env python3
"""
rds_rightsizing_report.py

Pulls AWS Compute Optimizer recommendations for RDS instances,
calculates projected monthly savings, and writes a CSV report.

Schedule: Run weekly via EventBridge + Lambda or cron.
Requirements: boto3, csv (stdlib)
IAM permissions: compute-optimizer:GetRDSDatabaseRecommendations,
                 pricing:GetProducts
"""

import boto3
import csv
import json
import sys
from datetime import datetime

REGION = "us-east-1"
OUTPUT_FILE = f"rds_rightsizing_{datetime.now().strftime('%Y%m%d')}.csv"

def get_rds_recommendations(region: str) -> list:
    client = boto3.client("compute-optimizer", region_name=region)
    recommendations = []
    paginator = client.get_paginator("get_rds_database_recommendations")

    for page in paginator.paginate():
        recommendations.extend(page.get("rdsDBRecommendations", []))

    return recommendations

def calculate_monthly_savings(current_price_hr: float, recommended_price_hr: float) -> float:
    """Assumes 730 hours per month (average)."""
    return (current_price_hr - recommended_price_hr) * 730

def parse_recommendations(recommendations: list) -> list:
    rows = []
    for rec in recommendations:
        instance_id = rec.get("resourceArn", "").split(":")[-1]
        finding = rec.get("finding", "")

        if finding not in ("OVERPROVISIONED", "UNDERPROVISIONED"):
            continue

        current = rec.get("currentDBInstanceClass", "N/A")
        options = rec.get("recommendationOptions", [])

        if not options:
            continue

        # Take the top-ranked recommendation
        best = options[0]
        recommended = best.get("dbInstanceClass", "N/A")

        # Savings currency info from Compute Optimizer
        savings_opportunity = best.get("savingsOpportunity", {})
        estimated_monthly_savings = savings_opportunity.get(
            "estimatedMonthlySavings", {}
        ).get("value", 0.0)

        estimated_savings_pct = savings_opportunity.get(
            "savingsOpportunityPercentage", 0.0
        )

        utilization = rec.get("utilizationMetrics", [])
        max_cpu = next(
            (m["value"] for m in utilization
             if m["name"] == "CPU" and m["statistic"] == "MAXIMUM"),
            None
        )
        avg_cpu = next(
            (m["value"] for m in utilization
             if m["name"] == "CPU" and m["statistic"] == "AVERAGE"),
            None
        )

        rows.append({
            "instance_id": instance_id,
            "finding": finding,
            "current_class": current,
            "recommended_class": recommended,
            "avg_cpu_pct": f"{avg_cpu:.1f}" if avg_cpu else "N/A",
            "max_cpu_pct": f"{max_cpu:.1f}" if max_cpu else "N/A",
            "estimated_monthly_savings_usd": f"{estimated_monthly_savings:.2f}",
            "savings_opportunity_pct": f"{estimated_savings_pct:.1f}",
        })

    return rows

def write_csv(rows: list, output_file: str):
    if not rows:
        print("No actionable recommendations found.")
        return

    fieldnames = rows[0].keys()
    with open(output_file, "w", newline="") as f:
        writer = csv.DictWriter(f, fieldnames=fieldnames)
        writer.writeheader()
        writer.writerows(rows)

    total_savings = sum(float(r["estimated_monthly_savings_usd"]) for r in rows)
    print(f"Report written: {output_file}")
    print(f"Instances with recommendations: {len(rows)}")
    print(f"Total estimated monthly savings: ${total_savings:,.2f}")

if __name__ == "__main__":
    print(f"Fetching RDS recommendations for region: {REGION}")
    recommendations = get_rds_recommendations(REGION)
    print(f"Total recommendations retrieved: {len(recommendations)}")

    rows = parse_recommendations(recommendations)
    write_csv(rows, OUTPUT_FILE)

Running this script against a typical environment with 15–30 RDS instances reveals that 30–50% of instances are over-provisioned by at least one instance family size. The savings add up quickly. Moving from db.r6g.4xlarge ($0.96/hr) to db.r6g.2xlarge ($0.48/hr) for a single instance saves $350.40/month. Across ten such instances, that is $3,504/month, or $42,048/year.

TOTAL=$(python3 -c "

print(f'Recommendations: {len(data)}, Estimated monthly savings: \${total_impact:,.2f}')

echo "Full report written to: ${OUTPUT_FILE}"

1.4 Storage Costs: The Silent Accumulator

Storage is the cost that compounds invisibly. Databases grow, old tables are never cleaned up, and backup retention windows are set conservatively once and never revisited. The following T-SQL query identifies tables that have not been accessed in the past 90 days and calculates their size contribution — information that directly translates to storage cost savings when the data is archived or deleted.

-- Identify unused or rarely accessed tables for potential archival
-- Run against each SQL Server instance (RDS for SQL Server, Azure SQL, Cloud SQL)
-- Requires: sys.dm_db_index_usage_stats (resets on service restart: pair with uptime check)

SELECT TOP 50
    OBJECT_SCHEMA_NAME(i.object_id) AS schema_name,
    OBJECT_NAME(i.object_id)         AS table_name,
    SUM(a.total_pages) * 8 / 1024   AS total_mb,
    SUM(a.used_pages)  * 8 / 1024   AS used_mb,
    MAX(us.last_user_seek)          AS last_seek,
    MAX(us.last_user_scan)          AS last_scan,
    MAX(us.last_user_lookup)        AS last_lookup,
    MAX(us.last_user_update)        AS last_update,
    CASE
        WHEN MAX(COALESCE(us.last_user_seek, us.last_user_scan,
                          us.last_user_lookup, us.last_user_update)) IS NULL
            THEN 'NEVER ACCESSED (since restart)'
        WHEN MAX(COALESCE(us.last_user_seek, us.last_user_scan,
                          us.last_user_lookup, us.last_user_update))
             < DATEADD(day, -90, SYSDATETIME())
            THEN 'IDLE > 90 DAYS'
        WHEN MAX(COALESCE(us.last_user_seek, us.last_user_scan,
                          us.last_user_lookup, us.last_user_update))
             < DATEADD(day, -30, SYSDATETIME())
            THEN 'IDLE > 30 DAYS'
        ELSE 'ACTIVE'
    END AS access_status,
    -- Estimated monthly storage cost at gp3 pricing ($0.092/GB-month)
    CAST(SUM(a.total_pages) * 8 / 1048576.0 * 0.092 AS DECIMAL(10,4))
        AS est_monthly_cost_usd
FROM sys.indexes i
JOIN sys.partitions pt ON i.object_id = pt.object_id AND i.index_id = pt.index_id
JOIN sys.allocation_units a ON pt.partition_id = a.container_id
LEFT JOIN sys.dm_db_index_usage_stats us
  ON us.object_id = i.object_id AND us.index_id = i.index_id
     AND us.database_id = DB_ID()
WHERE i.object_id > 100
  AND pt.rows > 0
GROUP BY i.object_id
HAVING SUM(a.total_pages) * 8 / 1024 > 100   -- Tables larger than 100 MB only
ORDER BY total_mb DESC;

Running this query on a production SQL Server instance is frequently surprising. Teams discover event log tables from deprecated features consuming 400 GB, audit tables that are never queried consuming 200 GB, and staging tables from ETL jobs that were never cleaned up consuming another 150 GB. At gp3 pricing on AWS, that 750 GB of unused data costs $69/month. Archived to S3 Standard-IA, the same data costs $6.25/month — a saving of $62.75/month. Moved to S3 Glacier Instant Retrieval, it costs $2.50/month.

For SQL Server on RDS or Azure SQL, the equivalent analysis runs against sys.dm_db_index_usage_stats and sys.allocation_units:

-- SQL Server: Identify large tables with no reads in the current uptime period
-- Run in the context of the target database

SELECT
    OBJECT_SCHEMA_NAME(t.object_id)                          AS schema_name,
    t.name                                                  AS table_name,
    p.rows                                                  AS row_count,
    CAST(
        SUM(a.total_pages) * 8.0 / 1024 / 1024
        AS DECIMAL(18, 2)
    )                                                       AS size_gb,
    ROUND(
        SUM(a.total_pages) * 8.0 / 1024 / 1024 * 0.092,
        4
    )                                                       AS est_monthly_cost_gp3_usd,
    SUM(ISNULL(ius.user_seeks,  0))                         AS total_seeks,
    SUM(ISNULL(ius.user_scans,  0))                         AS total_scans,
    SUM(ISNULL(ius.user_lookups,0))                         AS total_lookups,
    SUM(ISNULL(ius.user_seeks,  0))
        + SUM(ISNULL(ius.user_scans,  0))
        + SUM(ISNULL(ius.user_lookups,0))                   AS total_reads,
    MAX(ius.last_user_seek)                                 AS last_user_seek,
    MAX(ius.last_user_scan)                                 AS last_user_scan,
    CASE
        WHEN SUM(ISNULL(ius.user_seeks,  0))
           + SUM(ISNULL(ius.user_scans,  0))
           + SUM(ISNULL(ius.user_lookups,0)) = 0
            THEN 'NO READS SINCE STARTUP'
        ELSE 'HAS READS'
    END                                                     AS read_status
FROM
    sys.tables                  t
    JOIN sys.partitions          p  ON  p.object_id = t.object_id
                                    AND p.index_id  IN (0, 1)
    JOIN sys.allocation_units    a  ON  a.container_id = p.partition_id
    LEFT JOIN sys.dm_db_index_usage_stats ius
                                    ON  ius.object_id   = t.object_id
                                    AND ius.database_id = DB_ID()
WHERE
    t.is_ms_shipped = 0
GROUP BY
    t.object_id,
    t.name,
    p.rows
HAVING
    SUM(a.total_pages) * 8.0 / 1024 / 1024 > 0.1   -- Tables larger than 100 MB
ORDER BY
    size_gb DESC;

One important caveat with the SQL Server version: sys.dm_db_index_usage_stats is reset every time the SQL Server service restarts, which on RDS happens during maintenance windows and failover events. A table with total_reads = 0 is suspicious but not conclusive unless the instance has been running continuously for at least 30 days. Cross-reference the last_user_seek and last_user_scan columns with your maintenance window schedule before scheduling any archival.

#### Backup Retention Tuning

Backup retention is one of the fastest wins available. Most teams accept the default 7-day retention window or, worse, extend it to 35 days "just in case" without a documented recovery scenario that requires more than 7 days of history. The cost math is straightforward:

  • → A 500 GB database with 7-day retention and 5% daily change rate generates roughly 175 GB of incremental backup storage per week above the free-tier baseline on AWS (the first 100% of provisioned storage is free).
  • → The same database with 35-day retention generates approximately 875 GB above the free tier.
  • → At $0.095/GB-month, the difference is $66.50/month per database.

    • Across 15 databases, that is $997.50/month saved simply by reducing retention from 35 days to 7 days — assuming your recovery point objective genuinely requires only 7 days of history.

    The following AWS CLI command audits every RDS instance in a region and outputs any instance with a backup retention period greater than 14 days:

    #!/usr/bin/env bash
# audit_backup_retention.sh
# Flags RDS instances with retention > threshold (default 14 days)
# Usage: ./audit_backup_retention.sh [retention_threshold_days]

REGION="${AWS_REGION:-us-east-1}"
THRESHOLD="${1:-14}"

echo "Auditing RDS backup retention in region: ${REGION}"
echo "Flagging instances with retention > ${THRESHOLD} days"
echo "---"

aws rds describe-db-instances \
    --region "$REGION" \
    --query "DBInstances[?BackupRetentionPeriod > \`${THRESHOLD}\`].{
        ID:DBInstanceIdentifier,
        Class:DBInstanceClass,
        Engine:Engine,
        RetentionDays:BackupRetentionPeriod,
        StorageGB:AllocatedStorage,
        Environment:TagList[?Key=='environment'].Value | [0]
    }" \
    --output table

    Run this monthly. In organizations where developers can self-service RDS instances through Terraform modules, retention creep is common — a module default of 30 propagates across dozens of instances without anyone noticing the cumulative cost.

    1.5 Reserved Instances, Savings Plans, and Committed Use Discounts

    On-demand pricing is the highest rate you can pay for cloud database compute. Every major cloud provider offers a lower rate in exchange for a usage commitment, and for any database instance that has been running continuously for more than three months, a commitment discount is almost always justified.

    AWS Reserved Instances (RIs) for RDS offer up to 72% savings versus on-demand pricing for a one-year, all-upfront commitment. The mechanics are:

    | Payment Option | 1-Year Discount | 3-Year Discount |

    |---|---|---|

    | All Upfront | ~42% | ~62% |

    | Partial Upfront | ~38% | ~58% |

    | No Upfront | ~35% | ~52% |

    A db.r6g.2xlarge Multi-AZ costs $1.344/hr on-demand, or $11,773.44/year. The same instance reserved for one year all-upfront costs approximately $6,861 — a saving of $4,912.44 per instance per year. Reserved Instances apply at the instance-family level: a db.r6g.2xlarge RI also applies to two db.r6g.xlarge instances or one db.r6g.2xlarge, giving you flexibility when right-sizing.

    The key risk with RIs is committing to an instance family that you subsequently right-size away from. If you purchase a db.r6g.4xlarge RI and later downsize the instance to db.r6g.2xlarge, the RI converts to cover two db.r6g.2xlarge instance-equivalents automatically — but only if you stay within the same instance family and region. Crossing to a different family or region means the RI is idle and you are paying for it without benefit.

    The correct process is:

    1. Run the right-sizing analysis from section 1.3 first.

    2. Apply right-sizing changes.

    3. Observe the correctly-sized instance under real workload for at least 30 days.

    4. Purchase RIs only for instances that have been stable at their current size for 30+ days.

    Azure Reserved Capacity for Azure SQL Database and SQL Managed Instance works similarly, with 1-year and 3-year commitment tiers. Savings versus pay-as-you-go pricing are in the same range as AWS. Azure reservations are scoped to a subscription or a management group, and they apply to the vCore count — so a reservation for 8 vCores applies to one 8-vCore instance or two 4-vCore instances in the same subscription.

    GCP Committed Use Discounts (CUDs) for Cloud SQL function differently. Rather than purchasing a specific instance reservation, you commit to a minimum spend on Cloud SQL resources in a region for one or three years. GCP then applies a discount to all Cloud SQL usage in that region up to the committed amount. This is administratively simpler than AWS RIs but requires you to estimate future spend rather than future instance count.

    The following Python script calculates the break-even point for purchasing an AWS RDS Reserved Instance versus continuing on-demand, accounting for the probability that the instance is terminated early:

    #!/usr/bin/env python3
"""
ri_breakeven.py

Calculates the break-even month for an RDS Reserved Instance purchase
versus continuing on-demand pricing.

Inputs (edit the CONFIG dict below or pass as environment variables):
  - on_demand_hourly: On-demand price per hour (USD)
  - ri_upfront:       All-upfront RI cost for 1 year (USD)
  - ri_monthly:       Monthly charge for RI (0 for all-upfront)
  - hours_per_month:  Assumed hours of operation per month (default 730)
"""

CONFIG = {
    "on_demand_hourly": 1.344,    # db.r6g.2xlarge Multi-AZ, us-east-1
    "ri_upfront":       6861.00,  # 1-year all-upfront RI cost
    "ri_monthly":       0.00,     # 0 for all-upfront
    "hours_per_month":  730,
}

def calculate_breakeven(cfg: dict) -> None:
    on_demand_monthly = cfg["on_demand_hourly"] * cfg["hours_per_month"]
    ri_first_month    = cfg["ri_upfront"] + cfg["ri_monthly"]
    ri_subsequent     = cfg["ri_monthly"]

    print(f"On-demand monthly cost:        ${on_demand_monthly:>10,.2f}")
    print(f"RI upfront cost:               ${cfg['ri_upfront']:>10,.2f}")
    print(f"RI monthly charge:             ${cfg['ri_monthly']:>10,.2f}")
    print()
    print(f"{'Month':<8} {'On-Demand Cumul':>16} {'RI Cumul':>12} {'Delta':>12} {'Status'}")
    print("-" * 60)

    cumul_on_demand = 0.0
    cumul_ri        = cfg["ri_upfront"]   # paid at month 0
    breakeven_month = None

    for month in range(1, 13):
        cumul_on_demand += on_demand_monthly
        cumul_ri        += cfg["ri_monthly"]
        delta            = cumul_on_demand - cumul_ri

        status = ""
        if delta > 0 and breakeven_month is None:
            breakeven_month = month
            status = "<-- BREAK-EVEN"

        print(
            f"{month:<8} "
            f"${cumul_on_demand:>14,.2f}  "
            f"${cumul_ri:>10,.2f}  "
            f"${delta:>10,.2f}  "
            f"{status}"
        )

    annual_savings = cumul_on_demand - cumul_ri
    print()
    if breakeven_month:
        print(f"Break-even month: {breakeven_month}")
    print(f"Annual savings:   ${annual_savings:,.2f}")
    print(
        f"Savings %:        "
        f"{(annual_savings / cumul_on_demand * 100):.1f}%"
    )

if __name__ == "__main__":
    calculate_breakeven(CONFIG)

    1.6 Bringing It Together: A Monthly FinOps Cadence

    Individual optimizations — tagging, right-sizing, storage cleanup, RI purchases — are valuable once. They become a sustainable practice only when embedded in a repeatable review cycle. The following monthly cadence covers the four highest-leverage activities and can be run by a single engineer in approximately two hours per month once the scripts are in place.

    Week 1 of the month: Spend attribution review

    Run the Athena CUR query from section 1.1 against the previous month's data. Group by resource_tags_user_team and resource_tags_user_environment. Identify any team whose database costs increased by more than 15% month-over-month. Send that team a cost report with the specific line items driving the increase. Do not escalate; inform. Most engineers will self-correct when they can see the specific numbers.

    Week 2: Right-sizing sweep

    Run the Compute Optimizer script from section 1.3. Filter for instances that have been over-provisioned for two consecutive months — these are safe candidates for resizing because the pattern is established, not a temporary dip in load. Schedule the resize during the next maintenance window. On RDS, a resize requires a brief outage of a few minutes for Single-AZ instances, or an automatic failover for Multi-AZ instances, which is near-zero downtime.

    Week 3: Storage and backup audit

    Run the SQL Server table size query from section 1.4 on any database that grew by more than 50 GB in the past month. Identify the tables driving the growth. Check whether backup retention is still aligned with each database's recovery requirements. For any non-production database where the retention is set above 7 days without a documented reason, reduce it.

    Week 4: Commitment coverage check

    Calculate your RI and CUD coverage ratio: the percentage of your on-demand database compute that is covered by a commitment discount. A healthy target for mature environments is 70–80% coverage, leaving 20–30% on-demand to absorb unpredictable spikes. If coverage is below 60%, identify the longest-running on-demand instances and purchase RIs for the ones that passed the 30-day stability check.

    This cadence, executed consistently, compounds over time. Teams that run it for six consecutive months typically find that their month-12 database bill is 30–45% lower than month 1, without any architectural changes — purely through the continuous application of the techniques in this chapter.

    Key Takeaways

  • → **Cloud database bills are a stack of at least seven distinct cost components** — compute, storage, I/O, backup, data transfer, licensing, and replication — and most teams are only monitoring one or two of them. Visibility across all components is the prerequisite to any meaningful reduction.
  • → **Tagging is not an administrative task; it is a cost control mechanism.** Enforcing a consistent tag schema across all database resources with automated compliance checks converts cost reports from noise into actionable chargeback data, and it takes less than a day to implement with the scripts in this chapter.
  • → **Over-provisioning is the default outcome of cloud migrations**, not an exception. Right-sizing analysis run against real utilization data — using AWS Compute Optimizer, Azure Advisor, or GCP Recommender — routinely surfaces 30–50% of instances as candidates for downsizing, with no performance impact on the workloads involved.
  • → **Storage costs compound silently.** Unused tables, over-retained backups, and the wrong storage class type are each individually small but collectively significant. A single query against `sys.dm_db_index_usage_stats` run monthly surfaces archival candidates that can be moved to object storage at a fraction of block storage pricing.
  • → **Reserved Instances and Committed Use Discounts should follow right-sizing, not precede it.** Committing to the wrong instance size locks in inefficiency for one to three years. The correct sequence is: right-size first, observe for 30 days, then purchase commitments for stable instances — at which point the discounts compound the savings already achieved through right-sizing.
