Chapter 22: Separating Analytics from OLTP: The Financial Case

Organizations that run analytical queries directly against their production OLTP databases routinely overpay for compute by 40–70%. A single poorly-timed BI report hitting an db.r6g.2xlarge RDS instance at peak transaction hours can cost the same as running a dedicated analytics cluster for an entire month — and that assumes the report finishes without triggering a CPU alarm or degrading customer-facing latency. This chapter quantifies the financial damage of mixed workloads, shows you how to measure the exact cost of analytics queries running on OLTP infrastructure, and builds the business case for routing those workloads to purpose-built, cheaper infrastructure. Done right, workload separation typically reduces the primary OLTP instance tier by one to two sizes, cuts storage IOPS costs by 30–50%, and moves analytics to infrastructure that costs 60–80% less per query-hour.

---

The Hidden Cost of Shared Infrastructure

The fundamental problem with running analytics on OLTP instances is a pricing mismatch. OLTP databases are sized for memory and IOPS — you pay premium prices for fast, consistent transaction throughput. Analytics workloads need CPU and sequential scan throughput, which is exactly what columnar stores and MPP engines provide at a fraction of the row-store cost.

Consider a production setup on AWS: a db.r5.4xlarge RDS for SQL Server instance running in Multi-AZ. At US East pricing (License Included, illustrative), that is roughly $2,800 per month for the pair. Now consider what actually runs on that instance. Performance Insights might reveal that 35% of active session time belongs to reporting queries — dashboard aggregations, month-end rollups, data export jobs. That 35% equates to roughly $769 per month in compute cost attributed purely to analytics.

The same queries on Amazon Redshift Serverless, priced at $0.375 per RPU-hour, would consume perhaps 8–12 RPU-hours for a typical daily analytics batch. Monthly cost: $90–$135. The math alone closes the case before you have written a single line of migration code.

On Azure, the picture is similar. An GP_Gen5_8 Azure SQL Database at around $1,150 per month shared with Power BI DirectQuery connections sees the same compression ratio when workloads move to Azure Synapse Analytics serverless SQL pools, billed at $5 per TB scanned.

The first step is measuring your current baseline with precision.

-- SQL Server: identify analytics queries consuming disproportionate resources
-- Run on RDS for SQL Server with Query Store enabled
WITH query_totals AS (
    SELECT
        q.query_id,
        LEFT(qt.query_sql_text, 120)                        AS query_snippet,
        SUM(rs.count_executions)                             AS calls,
        SUM(rs.avg_duration * rs.count_executions)
            / 1000000.0                                      AS total_exec_sec,
        AVG(rs.avg_duration) / 1000.0                        AS mean_exec_ms,
        SUM(rs.avg_rowcount * rs.count_executions)           AS total_rows,
        SUM(rs.avg_logical_io_reads * rs.count_executions)   AS total_blocks_accessed
    FROM sys.query_store_query q
    JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
    JOIN sys.query_store_plan pl       ON pl.query_id = q.query_id
    JOIN sys.query_store_runtime_stats rs ON rs.plan_id = pl.plan_id
    WHERE rs.last_execution_time >= DATEADD(DAY, -7, SYSDATETIME())
    GROUP BY q.query_id, qt.query_sql_text
    HAVING SUM(rs.count_executions) > 10
)
SELECT TOP 40
    query_snippet,
    calls,
    ROUND(total_exec_sec, 2)                              AS total_exec_sec,
    ROUND(mean_exec_ms / 1000.0, 4)                       AS mean_exec_sec,
    ROUND(100.0 * total_exec_sec
          / NULLIF(SUM(total_exec_sec) OVER (), 0), 2)    AS pct_total_time,
    ROUND(CAST(total_rows AS FLOAT) / NULLIF(calls, 0), 0) AS avg_rows_returned,
    total_blocks_accessed,
    -- High rows returned + long execution = likely analytics, not OLTP
    CASE
        WHEN mean_exec_ms > 5000
         AND CAST(total_rows AS FLOAT) / NULLIF(calls, 0) > 10000
            THEN 'ANALYTICS_CANDIDATE'
        WHEN mean_exec_ms > 1000
         AND CAST(total_rows AS FLOAT) / NULLIF(calls, 0) > 1000
            THEN 'REVIEW_NEEDED'
        ELSE 'OLTP'
    END                                                   AS workload_classification
FROM query_totals
ORDER BY total_exec_sec DESC;

This query gives you the classification foundation. Any query returning more than 10,000 rows on average or running longer than 5 seconds mean execution time is an analytics candidate that does not belong on an OLTP instance. Export this result set. It becomes the financial exhibit in your executive presentation.

For SQL Server on Azure SQL or AWS RDS SQL Server, the equivalent pull from sys.dm_exec_query_stats is:

-- SQL Server: Classify workloads by execution profile
SELECT TOP 50
    SUBSTRING(st.text, (qs.statement_start_offset / 2) + 1,
              ((CASE qs.statement_end_offset
                    WHEN -1 THEN DATALENGTH(st.text)
                    ELSE qs.statement_end_offset
               END - qs.statement_start_offset) / 2) + 1)  AS query_text,
    qs.execution_count,
    ROUND(qs.total_elapsed_time / 1e6, 2)                   AS total_elapsed_sec,
    ROUND(qs.total_elapsed_time / qs.execution_count / 1e6,
          4)                                                AS avg_elapsed_sec,
    ROUND(CAST(qs.total_elapsed_time AS FLOAT)
          / SUM(qs.total_elapsed_time) OVER () * 100, 2)   AS pct_total_elapsed,
    qs.total_logical_reads / qs.execution_count             AS avg_logical_reads,
    qs.total_rows / qs.execution_count                      AS avg_rows,
    CASE
        WHEN qs.total_elapsed_time / qs.execution_count > 5000000
             AND qs.total_rows / qs.execution_count > 10000 THEN 'ANALYTICS_CANDIDATE'
        WHEN qs.total_logical_reads / qs.execution_count > 100000 THEN 'HEAVY_SCAN'
        ELSE 'OLTP'
    END                                                     AS workload_type
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
WHERE qs.execution_count > 5
ORDER BY qs.total_elapsed_time DESC;

Quantifying the Dollar Value of Separation

Having identified analytics candidates, the next step is attaching a dollar figure to each. This requires combining query execution data with instance cost data. The Python script below pulls Performance Insights metrics from CloudWatch and maps CPU consumption per query group to hourly instance cost.

#!/usr/bin/env python3
"""
analytics_cost_attribution.py

Pulls RDS Performance Insights data and attributes hourly compute cost
to OLTP vs. analytics query workloads.

Requires: boto3, pyodbc, pandas
Schedule: Daily via EventBridge + Lambda or cron
"""

import boto3
import pandas as pd
from datetime import datetime, timedelta, timezone
from dataclasses import dataclass
from typing import Dict, List

# ── Configuration ────────────────────────────────────────────────────────────
DB_INSTANCE_ID  = "prod-sqlserver-01"
REGION          = "us-east-1"
INSTANCE_TYPE   = "db.r6g.4xlarge"
MULTI_AZ        = True

# On-demand hourly pricing (update from AWS pricing page quarterly)
HOURLY_RATES: Dict[str, float] = {
    "db.r6g.xlarge":  0.384,
    "db.r6g.2xlarge": 0.768,
    "db.r6g.4xlarge": 1.536,
    "db.r6g.8xlarge": 3.072,
}

LOOKBACK_HOURS = 24

# ── Helpers ──────────────────────────────────────────────────────────────────
@dataclass
class WorkloadCostSummary:
    period_hours: int
    total_instance_cost_usd: float
    analytics_cost_usd: float
    oltp_cost_usd: float
    analytics_pct: float
    projected_monthly_analytics_cost: float


def get_pi_metrics(client, db_id: str, hours: int = 24) -> pd.DataFrame:
    """Fetch DBLoad by sql digest from Performance Insights."""
    end_time   = datetime.now(timezone.utc)
    start_time = end_time - timedelta(hours=hours)

    response = client.get_resource_metrics(
        ServiceType="RDS",
        Identifier=db_id,
        MetricQueries=[
            {
                "Metric": "db.load.avg",
                "GroupBy": {
                    "Group": "db.sql",
                    "Dimensions": ["db.sql.statement"],
                    "Limit": 25,
                },
            }
        ],
        StartTime=start_time,
        EndTime=end_time,
        PeriodInSeconds=3600,
    )

    records = []
    for metric_list in response.get("MetricList", []):
        sql_text = (
            metric_list.get("Key", {})
            .get("Dimensions", {})
            .get("db.sql.statement", "unknown")
        )
        for dp in metric_list.get("DataPoints", []):
            records.append(
                {
                    "timestamp": dp["Timestamp"],
                    "db_load":   dp.get("Value", 0.0),
                    "sql_text":  sql_text[:200],
                }
            )
    return pd.DataFrame(records)


def classify_query(sql: str) -> str:
    """
    Heuristic classification. Replace with Query Store
    integration for production use.
    """
    sql_upper = sql.upper()
    analytics_signals = [
        "GROUP BY", "HAVING", "ROLLUP", "CUBE",
        "WINDOW", "PARTITION BY", "PERCENTILE",
        "EXTRACT(", "DATE_TRUNC",
    ]
    if any(sig in sql_upper for sig in analytics_signals):
        return "ANALYTICS"
    return "OLTP"


def compute_cost_attribution(df: pd.DataFrame,
                              instance_type: str,
                              multi_az: bool,
                              lookback_hours: int) -> WorkloadCostSummary:
    base_rate   = HOURLY_RATES.get(instance_type, 1.536)
    effective_rate = base_rate * (2 if multi_az else 1)
    total_cost  = effective_rate * lookback_hours

    df["workload"] = df["sql_text"].apply(classify_query)

    total_load    = df["db_load"].sum() or 1.0
    analytics_load = df.loc[df["workload"] == "ANALYTICS", "db_load"].sum()
    analytics_pct  = (analytics_load / total_load) * 100

    analytics_cost = total_cost * (analytics_pct / 100)
    oltp_cost      = total_cost - analytics_cost

    # Project to 30 days
    hourly_analytics_cost   = analytics_cost / lookback_hours
    monthly_analytics_cost  = hourly_analytics_cost * 730

    return WorkloadCostSummary(
        period_hours=lookback_hours,
        total_instance_cost_usd=round(total_cost, 2),
        analytics_cost_usd=round(analytics_cost, 2),
        oltp_cost_usd=round(oltp_cost, 2),
        analytics_pct=round(analytics_pct, 1),
        projected_monthly_analytics_cost=round(monthly_analytics_cost, 2),
    )


def main():
    pi_client = boto3.client("pi",  region_name=REGION)

    print(f"Fetching Performance Insights for {DB_INSTANCE_ID} "
          f"over last {LOOKBACK_HOURS}h …\n")

    df = get_pi_metrics(pi_client, DB_INSTANCE_ID, LOOKBACK_HOURS)

    if df.empty:
        print("No PI data returned. Verify PI is enabled and the instance ID is correct.")
        return

    summary = compute_cost_attribution(
        df, INSTANCE_TYPE, MULTI_AZ, LOOKBACK_HOURS
    )

    print("=" * 60)
    print(f"  Instance:                 {DB_INSTANCE_ID} ({INSTANCE_TYPE})")
    print(f"  Analysis window:          {LOOKBACK_HOURS} hours")
    print(f"  Total compute cost:       ${summary.total_instance_cost_usd:>8.2f}")
    print(f"  OLTP cost:                ${summary.oltp_cost_usd:>8.2f}")
    print(f"  Analytics cost:           ${summary.analytics_cost_usd:>8.2f}  "
          f"({summary.analytics_pct}%)")
    print(f"  Projected monthly waste:  ${summary.projected_monthly_analytics_cost:>8.2f}")
    print("=" * 60)

    if summary.analytics_pct > 20:
        print("\n⚠  RECOMMENDATION: Analytics load exceeds 20% of total DB load.")
        print("   Consider offloading to Redshift Serverless, Athena, or a")
        print("   read replica sized for analytics workloads.")


if __name__ == "__main__":
    main()

Run this daily via a scheduled Lambda or cron job. When projected_monthly_analytics_cost exceeds $500 consistently, you have your financial justification. When it exceeds $2,000, the conversation with your CTO writes itself.

Choosing the Right Analytics Target Infrastructure

Workload separation is not a single architecture. The correct target depends on query patterns, data freshness requirements, and the volume of data scanned. Getting this wrong means you trade one cost problem for another.

Scenario 1 — Latency-tolerant batch analytics, large data volumes: Amazon Redshift Serverless (AWS), Azure Synapse Analytics serverless SQL pools (Azure), or BigQuery (GCP). These are columnar MPP engines billed per query or per RPU-hour. A query scanning 500 GB of Parquet in BigQuery costs $2.50 flat. The same query on an r6g.4xlarge RDS instance spending 45 minutes of CPU time costs roughly $1.15 in compute plus weeks of DBA time managing contention. Over a month of daily runs, BigQuery at $2.50 per day is $75; the RDS share is $840.

Scenario 2 — Near-real-time dashboards against production data, sub-minute lag tolerance: readable Always On secondaries or Azure SQL geo-replicas. The secondary runs on a smaller instance — you do not need the same IOPS tier as primary. An RDS for SQL Server readable secondary on a smaller instance class costs a fraction of the primary while dashboard queries stay off the primary; primary stays clean for writes. On Azure SQL, a readable geo-secondary billed at its own vCore size serves the same role.

Scenario 3 — Ad-hoc analyst queries against recent data already exported: Amazon Athena over S3. Export a daily snapshot of your OLTP tables to S3 in Parquet format. Athena charges $5 per TB scanned, and column pruning plus Parquet compression typically means analysts scan 90–95% less data than the raw row size. A 100 GB Parquet file holding 1 TB of logical data costs $0.50 per full scan instead of $5.00.

The following script sets up a daily export from RDS for SQL Server to S3 using native backup to S3 (or bcp for table extracts) via AWS CLI, enabling Athena queries without touching production:

#!/usr/bin/env bash
# daily_analytics_export.sh
# Exports selected analytical tables from RDS for SQL Server to S3 as CSV,
# convertible to Parquet via AWS Glue or Athena CTAS.
# Schedule: cron 0 2 * * * (02:00 UTC daily)
# Requires: sqlcmd (ODBC Driver 18 for SQL Server)

set -euo pipefail

DB_HOST="prod-sqlserver-01.xyz.us-east-1.rds.amazonaws.com"
DB_NAME="appdb"
DB_USER="readonly_analytics"
DB_PASS="<redacted>"
S3_BUCKET="s3://my-company-analytics-lake"
DATE_PREFIX=$(date +%Y/%m/%d)

TABLES=(
  "orders"
  "order_items"
  "customers"
  "products"
  "events"
)

echo "[$(date -u +%FT%T)] Starting analytics export ..."

for TABLE in "${TABLES[@]}"; do
  LOCAL_FILE="/tmp/${TABLE}_$(date +%Y%m%d).csv"

  echo "  Exporting ${TABLE} ..."
  sqlcmd -S "${DB_HOST},1433" -U "${DB_USER}" -P "${DB_PASS}" -d "${DB_NAME}" \
    -Q "SET NOCOUNT ON; SELECT * FROM dbo.${TABLE} WHERE updated_at >= DATEADD(DAY, -1, SYSDATETIME())" \
    -s"," -W -k1 > "${LOCAL_FILE}"

  # Upload to date-partitioned S3 prefix
  aws s3 cp "${LOCAL_FILE}" \
    "${S3_BUCKET}/raw/${TABLE}/${DATE_PREFIX}/${TABLE}.csv" \
    --storage-class INTELLIGENT_TIERING \
    --sse aws:kms

  rm -f "${LOCAL_FILE}"
done

echo "[$(date -u +%FT%T)] Export complete."

The --storage-class INTELLIGENT_TIERING flag is intentional. Analytics data accessed heavily the day after export and rarely thereafter fits the Intelligent-Tiering pattern, which automatically moves objects to lower-cost tiers after 30 and 90 days of inactivity. For a 500 GB dataset, this can reduce S3 storage cost from $11.50/month (Standard) to $6.00/month within two months.

Right-Sizing OLTP After Workload Removal

The separation is only half the saving. The other half comes from downsizing the OLTP instance once analytics load is removed. This is where DBAs often leave money on the table — they successfully move the analytics workload but never revisit the instance type because "production changes are scary."

Use AWS Compute Optimizer and RDS recommendations to make the case with data rather than intuition.

#!/usr/bin/env bash
# get_rds_rightsizing_recommendations.sh
# Pulls Compute Optimizer recommendations for all RDS instances in account.
# Prerequisites: AWS CLI configured, Compute Optimizer enabled.

set -euo pipefail

REGION="us-east-1"
OUTPUT_FILE="rds_rightsizing_$(date +%Y%m%d).json"

echo "Fetching Compute Optimizer recommendations for RDS …"

aws compute-optimizer get-rds-database-recommendations \
  --region "${REGION}" \
  --filters name=Finding,values=Overprovisioned \
  --query 'rdsDBRecommendations[*].{
      Instance:resourceArn,
      CurrentType:currentDBInstanceClass,
      RecommendedType:recommendationOptions[0].dbInstanceClass,
      CurrentMonthlyPrice:currentMonthlyPrice.value,
      RecommendedMonthlyPrice:recommendationOptions[0].monthlyPrice.value,
      SavingsMonthly:currentMonthlyPrice.value
          - recommendationOptions[0].monthlyPrice.value,
      CPUUtilizationP99:utilizationMetrics[?name==`CPU`].value | [0],
      MemoryUtilizationP99:utilizationMetrics[?name==`Memory`].value | [0]
  }' \
  --output json \
  | tee "${OUTPUT_FILE}"

# Summarize total potential savings
echo ""
echo "Summary of potential monthly savings:"
python3 - <<PYEOF
import json, sys

with open("${OUTPUT_FILE}") as f:
    recs = json.load(f)

if not recs:
    print("  No overprovisioned instances found — or Compute Optimizer needs more data.")
    sys.exit(0)

total_current     = sum(r.get("CurrentMonthlyPrice",     0) or 0 for r in recs)
total_recommended = sum(r.get("RecommendedMonthlyPrice", 0) or 0 for r in recs)
total_savings     = total_current - total_recommended

print(f"  Instances reviewed:       {len(recs)}")
print(f"  Current monthly spend:    \${total_current:>10,.2f}")
print(f"  Optimized monthly spend:  \${total_recommended:>10,.2f}")
print(f"  Potential monthly saving: \${total_savings:>10,.2f}")
print(f"  Annualized saving:        \${total_savings * 12:>10,.2f}")
PYEOF

In practice, after removing analytics load from an db.r6g.4xlarge, Compute Optimizer frequently recommends dropping to db.r6g.2xlarge. At US East Multi-AZ pricing, that is a reduction from $2,196/month to $1,098/month — $1,098/month saved on the OLTP instance alone. Combined with the analytics migration to a cheaper target, total monthly savings often land between $1,200 and $1,800 for a single database cluster.

The instance downsize also has a compounding effect on reserved instance pricing. A 1-year no-upfront Reserved Instance for db.r6g.2xlarge costs approximately $686/month versus $1,098 on-demand — a further 37% reduction. When presenting the business case, the three-layer stack of savings (analytics offload + instance downsize + RI purchase) often produces a number that immediately gets CTO approval.

Automation: Continuous Workload Classification and Alerting

One-time separation is not enough. New features ship, developers run queries, and analytics workload creeps back onto the OLTP instance within weeks if nobody is watching. The following automation runs as a scheduled Lambda (or GitHub Actions workflow for non-AWS shops) and posts an alert when analytics load on the primary instance exceeds a configured threshold.

#!/usr/bin/env python3
"""
workload_drift_monitor.py

Monitors Query Store on RDS for SQL Server via a read-only connection
and alerts via SNS when analytics query load exceeds threshold.

Intended deployment: AWS Lambda, triggered every 15 minutes via EventBridge.
Environment variables:
  DB_SECRET_ARN   - Secrets Manager ARN with {host, port, dbname, username, password}
  SNS_TOPIC_ARN   - SNS topic for alerts
  ALERT_THRESHOLD - Analytics share of total exec time that triggers alert (default 0.25)
"""

import json
import os
import boto3
import pyodbc
from datetime import datetime, timezone

sns     = boto3.client("sns")
secrets = boto3.client("secretsmanager")

ALERT_THRESHOLD = float(os.environ.get("ALERT_THRESHOLD", "0.25"))
SNS_TOPIC_ARN   = os.environ["SNS_TOPIC_ARN"]
DB_SECRET_ARN   = os.environ["DB_SECRET_ARN"]

ANALYTICS_CLASSIFICATION_QUERY = """
WITH stmt_stats AS (
    SELECT
        q.query_id,
        LEFT(qt.query_sql_text, 200)                        AS query_snippet,
        SUM(rs.avg_duration * rs.count_executions)
            / 1000.0                                        AS total_exec_time_ms,
        SUM(rs.count_executions)                            AS calls,
        SUM(rs.avg_rowcount * rs.count_executions)          AS rows,
        AVG(rs.avg_duration) / 1000.0                       AS mean_exec_time_ms,
        SUM(rs.avg_rowcount * rs.count_executions)
            / NULLIF(SUM(rs.count_executions), 0)           AS avg_rows_per_call,
        -- Classify heuristically; tune thresholds for your workload
        CASE
            WHEN AVG(rs.avg_duration) / 1000.0 > 3000
                 AND SUM(rs.avg_rowcount * rs.count_executions)
                     / NULLIF(SUM(rs.count_executions), 0) > 5000
                                                              THEN 'ANALYTICS'
            WHEN qt.query_sql_text LIKE '%GROUP BY%'
                 AND AVG(rs.avg_duration) / 1000.0 > 1000  THEN 'ANALYTICS'
            WHEN qt.query_sql_text LIKE '%OVER(%'          THEN 'ANALYTICS'
            WHEN qt.query_sql_text LIKE '%DATEADD%'
                 AND SUM(rs.avg_rowcount * rs.count_executions)
                     / NULLIF(SUM(rs.count_executions), 0) > 500
                                                              THEN 'ANALYTICS'
            ELSE 'OLTP'
        END                                                 AS workload_class
    FROM sys.query_store_query q
    JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
    JOIN sys.query_store_plan pl       ON pl.query_id = q.query_id
    JOIN sys.query_store_runtime_stats rs ON rs.plan_id = pl.plan_id
    WHERE rs.last_execution_time >= DATEADD(HOUR, -1, SYSDATETIME())
    GROUP BY q.query_id, qt.query_sql_text
    HAVING SUM(rs.count_executions) > 5
),
totals AS (
    SELECT
        workload_class,
        SUM(total_exec_time_ms)                             AS class_exec_time,
        COUNT(*)                                            AS query_count
    FROM stmt_stats
    GROUP BY workload_class
)
SELECT
    workload_class,
    class_exec_time,
    query_count,
    ROUND(
        class_exec_time / SUM(class_exec_time) OVER () * 100,
        2
    )                                                       AS pct_of_total_time
FROM totals
ORDER BY class_exec_time DESC;
"""


def get_db_credentials(secret_arn: str) -> dict:
    resp = secrets.get_secret_value(SecretId=secret_arn)
    return json.loads(resp["SecretString"])


def query_workload_distribution(creds: dict) -> list[dict]:
    conn_str = (
        "DRIVER={ODBC Driver 18 for SQL Server};"
        f"SERVER={creds['host']},{creds.get('port', 1433)};"
        f"DATABASE={creds['dbname']};UID={creds['username']};PWD={creds['password']};"
        "Encrypt=yes;TrustServerCertificate=no;Connection Timeout=10;"
    )
    conn = pyodbc.connect(conn_str)
    try:
        cur = conn.cursor()
        cur.execute(ANALYTICS_CLASSIFICATION_QUERY)
        cols = [d[0] for d in cur.description]
        return [dict(zip(cols, row)) for row in cur.fetchall()]
    finally:
        conn.close()


def build_alert_message(rows: list[dict], analytics_pct: float) -> str:
    lines = [
        f"⚠  WORKLOAD DRIFT ALERT — {datetime.now(timezone.utc).strftime('%Y-%m-%d %H:%M UTC')}",
        f"Analytics queries consume {analytics_pct:.1f}% of total execution time",
        f"(threshold: {ALERT_THRESHOLD * 100:.0f}%)",
        "",
        "Breakdown by workload class:",
    ]
    for row in rows:
        lines.append(
            f"  {row['workload_class']:<12} "
            f"{row['pct_of_total_time']:>6}%  "
            f"({row['query_count']} queries)"
        )
    lines += [
        "",
        "Action: Review Query Store on the OLTP instance and confirm",
        "analytical queries have not been re-routed to the primary.",
        "Runbook: https://wiki.internal/db-finops/workload-separation-runbook",
    ]
    return "\n".join(lines)


def lambda_handler(event, context):
    creds = get_db_credentials(DB_SECRET_ARN)
    rows  = query_workload_distribution(creds)

    if not rows:
        return {"status": "no_data"}

    analytics_row = next(
        (r for r in rows if r["workload_class"] == "ANALYTICS"), None
    )
    analytics_pct = float(analytics_row["pct_of_total_time"]) / 100 if analytics_row else 0.0

    result = {
        "timestamp": datetime.now(timezone.utc).isoformat(),
        "analytics_fraction": analytics_pct,
        "alert_fired": False,
        "distribution": rows,
    }

    if analytics_pct >= ALERT_THRESHOLD:
        message = build_alert_message(rows, analytics_pct * 100)
        sns.publish(
            TopicArn=SNS_TOPIC_ARN,
            Subject=f"[DB FinOps] Analytics workload drift detected — {analytics_pct * 100:.1f}%",
            Message=message,
        )
        result["alert_fired"] = True

    return result

Deploy this Lambda with a 128 MB memory allocation — the function itself is lightweight; all the work happens inside the database. At 15-minute intervals, the Lambda invocation cost is negligible (approximately 2,880 invocations per month, well within the free tier). Set the EventBridge rule to disable itself if the Lambda errors three consecutive times to avoid alert fatigue from transient network issues.

The equivalent for SQL Server environments uses a stored procedure that writes to a monitoring table, queried by an Azure Monitor workbook or CloudWatch custom metric:

-- SQL Server: Stored procedure to log workload distribution to a monitoring table
-- Schedule via SQL Server Agent or Azure Elastic Jobs every 15 minutes

IF OBJECT_ID('dbo.LogWorkloadDistribution', 'P') IS NOT NULL
    DROP PROCEDURE dbo.LogWorkloadDistribution;
GO

CREATE PROCEDURE dbo.LogWorkloadDistribution
AS
BEGIN
    SET NOCOUNT ON;

    -- Ensure monitoring table exists
    IF OBJECT_ID('dbo.WorkloadDistributionLog', 'U') IS NULL
    BEGIN
        CREATE TABLE dbo.WorkloadDistributionLog (
            log_id              INT IDENTITY(1,1) PRIMARY KEY,
            captured_at         DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
            workload_class      NVARCHAR(20) NOT NULL,
            total_elapsed_sec   DECIMAL(18,2) NOT NULL,
            query_count         INT NOT NULL,
            pct_of_total        DECIMAL(6,2) NOT NULL
        );
        CREATE INDEX IX_WorkloadLog_CapturedAt
            ON dbo.WorkloadDistributionLog (captured_at DESC);
    END;

    WITH classified AS (
        SELECT
            CASE
                WHEN qs.total_elapsed_time / NULLIF(qs.execution_count, 0) > 3000000
                     AND qs.total_rows / NULLIF(qs.execution_count, 0) > 5000
                                                        THEN 'ANALYTICS'
                WHEN qs.total_logical_reads
                     / NULLIF(qs.execution_count, 0)  > 50000
                                                        THEN 'ANALYTICS'
                ELSE 'OLTP'
            END                                         AS workload_class,
            qs.total_elapsed_time                       AS elapsed_us,
            1                                           AS query_count
        FROM sys.dm_exec_query_stats qs
        WHERE qs.execution_count > 5
    ),
    aggregated AS (
        SELECT
            workload_class,
            SUM(elapsed_us)                             AS class_elapsed_us,
            SUM(query_count)                            AS query_count
        FROM classified
        GROUP BY workload_class
    ),
    with_pct AS (
        SELECT
            workload_class,
            class_elapsed_us,
            query_count,
            ROUND(
                CAST(class_elapsed_us AS FLOAT)
                / NULLIF(SUM(class_elapsed_us) OVER (), 0) * 100,
                2
            )                                           AS pct_of_total
        FROM aggregated
    )
    INSERT INTO dbo.WorkloadDistributionLog
        (workload_class, total_elapsed_sec, query_count, pct_of_total)
    SELECT
        workload_class,
        ROUND(class_elapsed_us / 1e6, 2),
        query_count,
        pct_of_total
    FROM with_pct;

    -- Raise an alert event if analytics load exceeds 25%
    IF EXISTS (
        SELECT 1
        FROM dbo.WorkloadDistributionLog
        WHERE captured_at >= DATEADD(MINUTE, -16, SYSUTCDATETIME())
          AND workload_class = 'ANALYTICS'
          AND pct_of_total   > 25.0
    )
    BEGIN
        RAISERROR(
            'WORKLOAD DRIFT: Analytics queries exceed 25%% of total elapsed time. Review sys.dm_exec_query_stats.',
            10, -- severity (informational; raise to 16+ to break jobs)
            1
        ) WITH LOG;  -- writes to SQL Server error log, picked up by Azure Monitor / CloudWatch
    END;

    -- Prune log older than 90 days
    DELETE FROM dbo.WorkloadDistributionLog
    WHERE captured_at < DATEADD(DAY, -90, SYSUTCDATETIME());
END;
GO

Wire the RAISERROR ... WITH LOG output to an Azure Monitor alert rule (for Azure SQL Managed Instance) or a CloudWatch Logs metric filter (for RDS SQL Server) that pages on-call when triggered outside business hours. This closes the feedback loop: the team migrates analytics, the monitor watches for drift, and any re-introduction of analytical load triggers a ticket before it accumulates into a billing surprise.

Implementation Sequencing

Sequence the work to capture savings quickly while minimizing risk. Do not attempt a big-bang cutover.

Week 1–2: Run the classification queries and cost attribution script. Produce the financial exhibit. Identify the top five analytics queries by total execution time. Get buy-in.

Week 3–4: Provision the analytics target infrastructure (read replica, Redshift Serverless workspace, or Athena data lake). Run the daily export script. Validate that query results on the analytics target match the OLTP source within acceptable tolerance.

Week 5–6: Redirect one non-critical BI tool or report to the analytics target. Monitor for latency regressions and data freshness complaints. Keep the OLTP route as fallback.

Week 7–8: Migrate remaining analytics workloads. Confirm with Performance Insights that analytics load on the primary has dropped. Request a Compute Optimizer recommendation pull.

Week 9–10: Resize the OLTP instance during a low-traffic maintenance window. For RDS, this is a Multi-AZ failover-based resize — downtime is typically under 60 seconds when done correctly. Verify application connection pool behavior post-resize.

Week 11–12: Purchase Reserved Instances for the new, smaller OLTP tier. Enable the workload drift monitor Lambda. Document the runbook.

Each phase has a clear deliverable and a defined rollback path. The two-week cadence allows teams with normal sprint rhythms to absorb the work without dedicated project staffing.

Key Takeaways

  • → **Mixed workloads are a billing multiplier.** Analytics queries running on OLTP infrastructure force you to pay row-store prices for column-store workloads. Measuring the split with Query Store or `sys.dm_exec_query_stats` is the necessary first step before any cost conversation.
  • → **The financial case has three compounding layers**: offloading analytics reduces attributed compute cost, lower sustained load allows an instance downsize, and a smaller instance purchases at a lower Reserved Instance tier. Each layer multiplies the previous saving.
  • → **Choose the analytics target by query pattern, not by vendor familiarity.** Near-real-time dashboards belong on a read replica. Batch aggregations over large historical data belong on a columnar MPP engine. Ad-hoc analyst queries against exported snapshots belong on Athena or BigQuery. Routing everything to a single alternative is a common mistake that recreates the original cost problem.
  • → **Separation without monitoring drifts back.** Workload classification alerts — whether a Lambda querying Query Store or a SQL Server Agent job writing to a log table — are the operational control that prevents analytics load from silently re-accumulating on the primary over subsequent release cycles.
  • → **Sequence implementation over 10–12 weeks with explicit rollback paths.** Instance resizes and RI purchases are irreversible commitments. Validate workload behavior at each phase before proceeding to the next, and keep the original routing available as fallback until query results and latency have been confirmed stable on the new target.
