Chapter 15: Automated Storage Cleanup: Snapshots, Temp Tables, and Bloat

Storage is the silent budget drain that most engineering teams discover too late. A typical production RDS for SQL Server instance that has been running for 18 months accumulates between 40% and 70% of its total storage bill in artifacts that provide zero ongoing business value: orphaned snapshots from deprecated environments, fragmented indexes and data files grown far beyond the live data they hold, temporary tables that survived a connection restart, and transaction log backups that retention policies never cleaned up. Organizations running mid-scale database fleets on AWS, Azure, or GCP routinely find $8,000 to $25,000 per month in recoverable storage spend once they instrument and automate cleanup properly. This chapter gives you the diagnostic queries, the cleanup logic, and the scheduled automation to capture that money — and keep capturing it every month without manual intervention.

---

15.1 Diagnosing Where Storage Money Is Actually Going

Before automating anything, you need an accurate map of what you are paying for. Cloud providers bill storage across several independent dimensions: provisioned IOPS volume capacity, automated backup retention windows, manual snapshots, cross-region snapshot copies, and transaction log storage. Each line item has a different unit price, and the cost composition varies significantly between AWS, Azure, and GCP.

On AWS RDS, storage billing breaks down into four categories:

  • → **Provisioned volume**: gp2 at $0.115/GB-month or gp3 at $0.092/GB-month (us-east-1, 2024 pricing)
  • → **Automated backups**: free up to 100% of provisioned storage; each GB beyond that billed at $0.095/GB-month
  • → **Manual snapshots**: $0.095/GB-month, charged from creation date, never expire automatically
  • → **Cross-region snapshot copies**: source region egress ($0.02–$0.09/GB depending on region pair) plus destination snapshot storage

    • The manual snapshot line item is where teams consistently hemorrhage money. An automated snapshot taken at day 30 of a 30-day retention window gets deleted automatically. A manual snapshot taken on the same day to "preserve a known-good state before a migration" — and then forgotten — costs $0.095/GB-month indefinitely. A 2 TB database snapshot costs $194/month. If your team has been running for three years with ad hoc snapshot practices, multiply that figure by however many forgotten snapshots exist across however many accounts.

    The following query runs against AWS Cost Explorer via CLI and breaks down your RDS storage costs by usage type, giving you the exact composition of what you are paying:

    #!/bin/bash

# Requires aws cli v2 and Cost Explorer access (us-east-1)

AWS_ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)

echo "Fetching RDS storage cost breakdown for account: $AWS_ACCOUNT_ID"

aws ce get-cost-and-usage \
  --time-period Start=$(date -d '90 days ago' +%Y-%m-%d),End=$(date +%Y-%m-%d) \
  --granularity MONTHLY \
  --filter '{
    "And": [
      {
        "Dimensions": {
          "Key": "SERVICE",
          "Values": ["Amazon Relational Database Service"]
        }
      },
      {
        "Dimensions": {
          "Key": "USAGE_TYPE_GROUP",
          "Values": [
            "RDS: Storage",
            "RDS: Backup",
            "RDS: Snapshot Export"
          ]
        }
      }
    ]
  }' \
  --group-by Type=DIMENSION,Key=USAGE_TYPE \
  --metrics BlendedCost UnblendedCost UsageQuantity \
  --output json | jq -r '
    .ResultsByTime[] |
    .TimePeriod.Start as $period |
    .Groups[] |
    [$period, .Keys[0],
     (.Metrics.UnblendedCost.Amount | tonumber | . * 100 | round / 100),
     (.Metrics.UsageQuantity.Amount | tonumber | . * 100 | round / 100),
     .Metrics.UsageQuantity.Unit
    ] | @tsv
  ' | column -t -s $'\t' -N "Period,UsageType,Cost_USD,Quantity,Unit"

    On Azure SQL, the equivalent breakdown lives in Cost Management. Filter by resource type microsoft.sql/servers/databases and group by meter subcategory. You will find separate line items for LRS backup storage, RA-GRS backup storage, and provisioned database storage. The RA-GRS backup storage meter frequently surprises teams — it bills at 1.5x the LRS rate and gets applied to databases configured with geo-redundant backup storage even when the secondary region is never actually used for recovery.

    On GCP Cloud SQL, run this against the billing export table in BigQuery to isolate storage costs by type:

    15.2 Snapshot Lifecycle Automation

    A manual snapshot costs money from the moment it is created to the moment it is explicitly deleted. There is no built-in expiration mechanism on RDS manual snapshots, Azure SQL long-term retention backups, or Cloud SQL on-demand backups. Every team that does not have enforcement automation accumulates snapshots indefinitely.

    The standard approach is to implement a tagging convention at snapshot creation time, then run a scheduled Lambda (or Azure Function or Cloud Run job) that evaluates tags and deletes snapshots past their intended retention date.

    The tagging convention requires two tags on every manual snapshot:

  • → `RetentionDays`: integer, e.g., `30`, `90`, `365`, or `permanent`
  • → `CreatedBy`: the team or automation that created it
  • → `Purpose`: `pre-migration`, `pre-upgrade`, `compliance`, `ad-hoc`

    • Snapshots tagged permanent are exempt from automated deletion. Everything else gets evaluated. The following Python Lambda function implements this logic for AWS RDS:

    """
rds_snapshot_cleanup.py
Lambda function for automated RDS snapshot lifecycle management.
Deploy with EventBridge rule on daily schedule (cron: 0 2 * * ? *)
Required IAM permissions:
  - rds:DescribeDBSnapshots
  - rds:DeleteDBSnapshot
  - rds:ListTagsForResource
  - sns:Publish (for alerting)
Environment variables:
  SNS_TOPIC_ARN : ARN of SNS topic for deletion reports
  DRY_RUN       : "true" to log without deleting (default: "false")
  MAX_AGE_DAYS  : Hard cap — delete any untagged snapshot older than this (default: 90)
"""

import boto3
import json
import os
from datetime import datetime, timezone, timedelta

rds_client   = boto3.client('rds')
sns_client   = boto3.client('sns')

DRY_RUN      = os.environ.get('DRY_RUN', 'false').lower() == 'true'
MAX_AGE_DAYS = int(os.environ.get('MAX_AGE_DAYS', '90'))
SNS_TOPIC    = os.environ.get('SNS_TOPIC_ARN', '')

def get_tag_value(tags: list, key: str) -> str | None:
    for tag in tags:
        if tag['Key'] == key:
            return tag['Value']
    return None

def evaluate_snapshot(snapshot: dict, tags: list) -> dict:
    """
    Returns a dict describing what action to take and why.
    """
    snap_id        = snapshot['DBSnapshotIdentifier']
    snap_type      = snapshot['SnapshotType']
    created_time   = snapshot['SnapshotCreateTime']
    now            = datetime.now(timezone.utc)
    age_days       = (now - created_time).days
    allocated_gb   = snapshot.get('AllocatedStorage', 0)
    cost_per_month = round(allocated_gb * 0.095, 2)  # us-east-1 snapshot pricing

    # Never touch automated snapshots — RDS manages their lifecycle
    if snap_type == 'automated':
        return {'action': 'skip', 'reason': 'automated snapshot'}

    # Check for permanent exemption
    retention_tag = get_tag_value(tags, 'RetentionDays')
    if retention_tag and retention_tag.lower() == 'permanent':
        return {
            'action'        : 'skip',
            'reason'        : 'tagged permanent',
            'age_days'      : age_days,
            'cost_per_month': cost_per_month
        }

    # If RetentionDays tag is present and not expired, skip
    if retention_tag and retention_tag.isdigit():
        retention_days = int(retention_tag)
        if age_days <= retention_days:
            return {
                'action'        : 'skip',
                'reason'        : f'within retention ({age_days}/{retention_days} days)',
                'age_days'      : age_days,
                'cost_per_month': cost_per_month
            }
        else:
            return {
                'action'        : 'delete',
                'reason'        : f'retention expired ({age_days} days > {retention_days} day policy)',
                'snap_id'       : snap_id,
                'age_days'      : age_days,
                'size_gb'       : allocated_gb,
                'cost_per_month': cost_per_month
            }

    # No retention tag — apply hard cap
    if age_days > MAX_AGE_DAYS:
        return {
            'action'        : 'delete',
            'reason'        : f'no retention tag, exceeded hard cap ({age_days} days > {MAX_AGE_DAYS})',
            'snap_id'       : snap_id,
            'age_days'      : age_days,
            'size_gb'       : allocated_gb,
            'cost_per_month': cost_per_month
        }

    return {
        'action'        : 'skip',
        'reason'        : 'no tag but within hard cap',
        'age_days'      : age_days,
        'cost_per_month': cost_per_month
    }

def lambda_handler(event, context):
    paginator         = rds_client.get_paginator('describe_db_snapshots')
    deleted           = []
    skipped           = []
    total_savings_usd = 0.0

    for page in paginator.paginate(SnapshotType='manual'):
        for snapshot in page['DBSnapshots']:
            if snapshot['Status'] != 'available':
                continue

            snap_id  = snapshot['DBSnapshotIdentifier']
            snap_arn = snapshot['DBSnapshotArn']

            tag_response = rds_client.list_tags_for_resource(ResourceName=snap_arn)
            tags         = tag_response.get('TagList', [])
            decision     = evaluate_snapshot(snapshot, tags)

            if decision['action'] == 'delete':
                total_savings_usd += decision.get('cost_per_month', 0)
                if not DRY_RUN:
                    try:
                        rds_client.delete_db_snapshot(DBSnapshotIdentifier=snap_id)
                        decision['status'] = 'deleted'
                    except Exception as e:
                        decision['status'] = f'error: {str(e)}'
                else:
                    decision['status'] = 'dry_run_would_delete'
                deleted.append(decision)
            else:
                skipped.append(decision)

    report = {
        'dry_run'              : DRY_RUN,
        'snapshots_deleted'    : len(deleted),
        'snapshots_skipped'    : len(skipped),
        'estimated_savings_usd': round(total_savings_usd, 2),
        'deleted_details'      : deleted[:50],   # cap report size
    }

    print(json.dumps(report, indent=2, default=str))

    if SNS_TOPIC and (deleted or not DRY_RUN):
        sns_client.publish(
            TopicArn = SNS_TOPIC,
            Subject  = f"RDS Snapshot Cleanup: {len(deleted)} deleted, ${total_savings_usd:.2f}/mo recovered",
            Message  = json.dumps(report, indent=2, default=str)
        )

    return report

    Deploy this Lambda with an EventBridge rule on a daily schedule at 02:00 UTC. First week, run with DRY_RUN=true and review the SNS report. After confirming the deletion list looks correct, flip to DRY_RUN=false. In most environments, the first live run recovers between 15% and 35% of the total RDS storage bill within 24 hours.

    For Azure, the equivalent is a PowerShell Azure Function that evaluates long-term retention backup policies. The key lever there is adjusting the LTR (Long-Term Retention) weekly, monthly, and yearly backup retention values via the Set-AzSqlDatabaseBackupLongTermRetentionPolicy cmdlet. The default values on many older Azure SQL databases are set to maximums during initial setup and never revisited. Dropping weekly retention from 12 weeks to 4 weeks on a 500 GB database reduces RA-GRS backup storage from approximately 6 TB to 2 TB — a saving of roughly $180/month at $0.05/GB-month for RA-GRS.

    15.3 Identifying and Reclaiming Index Fragmentation and File Growth in SQL Server

    SQL Server's storage fragmentation problem manifests at the page and extent level inside B-tree index structures. Fragmentation occurs at the page and extent level inside B-tree index structures. A heavily modified table with a clustered index will develop internal fragmentation (pages that are partially filled) and external fragmentation (pages out of logical order). Both consume storage and degrade query performance.

    The key measurement is avg_fragmentation_in_percent from sys.dm_db_index_physical_stats. An index with 80% fragmentation means that on average, each allocated page is only 20% full — you are paying for 5x more storage than the data actually requires.

    -- SQL Server: Identify index fragmentation and estimate storage waste
-- Use SAMPLED mode for large databases — LIMITED mode is faster but less accurate
-- DETAILED mode is most accurate but scans every page; use only in maintenance windows

SELECT
  OBJECT_SCHEMA_NAME(ips.object_id)                     AS schema_name,
  OBJECT_NAME(ips.object_id)                             AS table_name,
  i.name                                                 AS index_name,
  ips.index_type_desc,
  ips.index_level,
  ROUND(ips.avg_fragmentation_in_percent, 1)             AS fragmentation_pct,
  ips.page_count,
  ips.record_count,
  ROUND(ips.avg_page_space_used_in_percent, 1)           AS avg_page_fullness_pct,
  -- Estimate wasted pages: pages that should be freed if fully packed
  CAST(
    ips.page_count * (1.0 - ips.avg_page_space_used_in_percent / 100.0)
    AS INT
  )                                                      AS wasted_pages,
  -- Estimate wasted MB (8 KB per page)
  ROUND(
    ips.page_count * (1.0 - ips.avg_page_space_used_in_percent / 100.0) * 8.0 / 1024.0,
    2
  )                                                      AS wasted_mb,
  -- Monthly cost estimate at Azure SQL GP storage pricing ($0.115/GB-month)
  ROUND(
    ips.page_count * (1.0 - ips.avg_page_space_used_in_percent / 100.0)
      * 8.0 / 1024.0 / 1024.0 * 0.115,
    4
  )                                                      AS monthly_waste_usd,
  CASE
    WHEN ips.avg_fragmentation_in_percent >= 30 THEN 'REBUILD INDEX'
    WHEN ips.avg_fragmentation_in_percent >= 10 THEN 'REORGANIZE INDEX'
    ELSE 'MONITOR'
  END                                                    AS recommended_action
FROM
  sys.dm_db_index_physical_stats(
    DB_ID(),         -- current database
    NULL,            -- all tables
    NULL,            -- all indexes
    NULL,            -- all partitions
    'SAMPLED'        -- sampling mode
  ) AS ips
INNER JOIN sys.indexes AS i
  ON  i.object_id = ips.object_id
  AND i.index_id  = ips.index_id
WHERE
  ips.index_level    = 0           -- leaf level only
  AND ips.page_count > 1000        -- skip tiny indexes (< ~8 MB)
  AND ips.avg_fragmentation_in_percent > 10
ORDER BY
  wasted_mb DESC;

    For indexes with fragmentation above 30%, REBUILD is the appropriate action. REBUILD reallocates the entire index, producing a completely clean B-tree with pages filled to the configured FILLFACTOR. For fragmentation between 10% and 30%, REORGANIZE performs an online defragmentation of the leaf level without rebuilding the entire structure. The key operational difference: REBUILD can be done WITH (ONLINE = ON) on SQL Server Enterprise Edition (and on Azure SQL), which avoids blocking DML during the operation.

    The following stored procedure automates adaptive index maintenance based on fragmentation thresholds:

    -- SQL Server / Azure SQL: Adaptive index maintenance procedure
-- Rebuilds high-fragmentation indexes, reorganizes medium-fragmentation indexes
-- Skips indexes on tables with active long-running transactions

CREATE OR ALTER PROCEDURE dbo.usp_AdaptiveIndexMaintenance
  @MinPageCount        INT           = 1000,      -- Skip indexes smaller than this
  @RebuildThreshold    FLOAT         = 30.0,      -- Fragmentation % threshold for REBUILD
  @ReorganizeThreshold FLOAT         = 10.0,      -- Fragmentation % threshold for REORGANIZE
  @MaxDurationMinutes  INT           = 120,        -- Stop after this many minutes
  @FillFactor          TINYINT       = 85,         -- Fill factor for rebuilds
  @PrintOnly           BIT           = 0           -- 1 = print commands, don't execute
AS
BEGIN
  SET NOCOUNT ON;

  DECLARE
    @StartTime         DATETIME2     = SYSUTCDATETIME(),
    @SchemaName        NVARCHAR(128),
    @TableName         NVARCHAR(128),
    @IndexName         NVARCHAR(128),
    @FragPct           FLOAT,
    @PageCount         BIGINT,
    @SQL               NVARCHAR(MAX),
    @Action            NVARCHAR(20),
    @RowsProcessed     INT           = 0,
    @ErrorMessage      NVARCHAR(MAX);

  -- Staging table for fragmentation data
  CREATE TABLE #IndexWork (
    RowID          INT IDENTITY PRIMARY KEY,
    SchemaName     NVARCHAR(128),
    TableName      NVARCHAR(128),
    IndexName      NVARCHAR(128),
    FragPct        FLOAT,
    PageCount      BIGINT,
    Action         NVARCHAR(20),
    Processed      BIT DEFAULT 0,
    ErrorMsg       NVARCHAR(MAX)
  );

  INSERT INTO #IndexWork (SchemaName, TableName, IndexName, FragPct, PageCount, Action)
  SELECT
    OBJECT_SCHEMA_NAME(ips.object_id),
    OBJECT_NAME(ips.object_id),
    i.name,
    ips.avg_fragmentation_in_percent,
    ips.page_count,
    CASE
      WHEN ips.avg_fragmentation_in_percent >= @RebuildThreshold    THEN 'REBUILD'
      WHEN ips.avg_fragmentation_in_percent >= @ReorganizeThreshold THEN 'REORGANIZE'
    END
  FROM
    sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'SAMPLED') AS ips
  INNER JOIN sys.indexes AS i
    ON  i.object_id = ips.object_id
    AND i.index_id  = ips.index_id
  WHERE
    ips.index_level                    = 0
    AND ips.page_count                 >= @MinPageCount
    AND ips.avg_fragmentation_in_percent >= @ReorganizeThreshold
    AND i.name                         IS NOT NULL   -- exclude heap
  ORDER BY
    ips.avg_fragmentation_in_percent DESC;

  DECLARE index_cursor CURSOR LOCAL FAST_FORWARD FOR
    SELECT RowID, SchemaName, TableName, IndexName, FragPct, PageCount, Action
    FROM   #IndexWork
    ORDER  BY FragPct DESC;

  OPEN index_cursor;
  FETCH NEXT FROM index_cursor
    INTO @RowsProcessed, @SchemaName, @TableName, @IndexName,
         @FragPct, @PageCount, @Action;

  WHILE @@FETCH_STATUS = 0
  BEGIN
    -- Enforce time budget
    IF DATEDIFF(MINUTE, @StartTime, SYSUTCDATETIME()) >= @MaxDurationMinutes
    BEGIN
      PRINT 'Time budget exceeded. Stopping maintenance.';
      BREAK;
    END;

    SET @SQL = CASE @Action
      WHEN 'REBUILD'
        THEN N'ALTER INDEX ' + QUOTENAME(@IndexName)
             + N' ON ' + QUOTENAME(@SchemaName) + N'.' + QUOTENAME(@TableName)
             + N' REBUILD WITH (ONLINE = ON, FILLFACTOR = '
             + CAST(@FillFactor AS NVARCHAR(3)) + N', SORT_IN_TEMPDB = ON);'
      WHEN 'REORGANIZE'
        THEN N'ALTER INDEX ' + QUOTENAME(@IndexName)
             + N' ON ' + QUOTENAME(@SchemaName) + N'.' + QUOTENAME(@TableName)
             + N' REORGANIZE;'
    END;

    IF @PrintOnly = 1
    BEGIN
      PRINT @SQL;
    END
    ELSE
    BEGIN
      BEGIN TRY
        EXEC sp_executesql @SQL;
        UPDATE #IndexWork SET Processed = 1 WHERE RowID = @RowsProcessed;
      END TRY
      BEGIN CATCH
        SET @ErrorMessage = ERROR_MESSAGE();
        UPDATE #IndexWork
          SET ErrorMsg = @ErrorMessage
        WHERE RowID = @RowsProcessed;
        PRINT 'Error on ' + @IndexName + ': ' + @ErrorMessage;
      END CATCH;
    END;

    FETCH NEXT FROM index_cursor
      INTO @RowsProcessed, @SchemaName, @TableName, @IndexName,
           @FragPct, @PageCount, @Action;
  END;

  CLOSE index_cursor;
  DEALLOCATE index_cursor;

  -- Summary report
  SELECT
    Action,
    COUNT(*)                          AS IndexCount,
    SUM(PageCount * 8 / 1024)         AS TotalMB,
    SUM(CASE WHEN Processed = 1 THEN PageCount * 8 / 1024 ELSE 0 END)
                                      AS ProcessedMB,
    COUNT(CASE WHEN ErrorMsg IS NOT NULL THEN 1 END)
                                      AS Errors,
    DATEDIFF(MINUTE, @StartTime, SYSUTCDATETIME())
                                      AS ElapsedMinutes
  FROM
    #IndexWork
  GROUP BY
    Action;

  DROP TABLE #IndexWork;
END;
GO

-- Execute in report-only mode first
EXEC dbo.usp_AdaptiveIndexMaintenance @PrintOnly = 1;

-- Schedule in a SQL Agent job during maintenance window:
-- EXEC dbo.usp_AdaptiveIndexMaintenance @MaxDurationMinutes = 180;

    One important nuance for Azure SQL specifically: the storage reduction from index rebuilds becomes meaningful only if you are on a DTU-based pricing model where total database size determines the pricing tier, or if you are tracking total database size against the maximum size allocation for your service tier. On vCore pricing, the provisioned storage allocation is independent of actual usage, so the FinOps benefit of defragmentation on Azure SQL is primarily performance-driven rather than directly storage-cost-driven — unless you then reduce the provisioned max storage size via an ALTER DATABASE operation after reclaiming space.

    15.4 Temporary Table and Temp Space Management

    Temporary storage is a category that engineering teams almost universally underestimate until it causes either a production incident (temp space exhaustion) or a cost anomaly (unexpected storage tier upgrade). Understanding where temp data lives in each cloud database platform is the prerequisite for managing its cost.

    SQL Server on Azure SQL / RDS SQL Server: SQL Server uses tempdb for temporary tables, table variables, sort spills, row versioning, and online index operations. On RDS SQL Server, tempdb lives on a separate NVMe SSD that is not billed as part of your storage allocation — it is sized based on instance class and reset on every restart. On Azure SQL, tempdb is managed by Microsoft and does not count toward your database size allocation. This means temporary table cost in SQL Server is primarily an instance-size concern (whether you need a larger instance due to tempdb pressure) rather than a direct storage billing concern.

    However, excessive tempdb usage still creates FinOps problems through a different mechanism: it causes PAGELATCH contention on tempdb allocation pages, which degrades performance and can force an instance size upgrade. Monitor tempdb usage with this query:

    -- SQL Server: tempdb space usage by session
SELECT
  r.session_id,
  r.status,
  r.command,
  r.total_elapsed_time / 1000                      AS elapsed_sec,
  tsu.user_objects_alloc_page_count * 8 / 1024     AS user_obj_mb,
  tsu.internal_objects_alloc_page_count * 8 / 1024 AS internal_obj_mb,
  (tsu.user_objects_alloc_page_count
   + tsu.internal_objects_alloc_page_count) * 8 / 1024
                                                   AS total_tempdb_mb,
  LEFT(t.text, 120)                                AS query_snippet
FROM
  sys.dm_exec_requests              AS r
JOIN sys.dm_db_task_space_usage     AS tsu
  ON  r.session_id = tsu.session_id
  AND r.request_id = tsu.request_id
CROSS APPLY
  sys.dm_exec_sql_text(r.sql_handle) AS t
WHERE
  (tsu.user_objects_alloc_page_count
   + tsu.internal_objects_alloc_page_count) > 12800  -- > 100 MB
ORDER BY
  total_tempdb_mb DESC;

    A commonly overlooked tempdb cost driver in SQL Server is excessive use of #temp tables instead of table variables or CTEs for small result sets. Each #temp table creation generates metadata writes to tempdb system tables. At scale, a stored procedure that creates and drops a #temp table inside a high-frequency loop (tens of thousands of executions per minute) creates measurable allocation contention. The fix is to replace #temp tables with @table variables for small sets, or to use TRUNCATE TABLE #temp inside loops rather than DROP and re-CREATE.

    15.5 Automated Transaction Log File Management

    Transaction logs are another category where retention policies frequently drift from intent. The right approach differs significantly across the three platforms.

    SQL Server Transaction Logs on RDS / Azure SQL: SQL Server transaction log bloat is a classic operational problem. The log file grows during a long-running transaction and then cannot be reused (even after a log backup) until the transaction commits or rolls back. On RDS SQL Server, log files live on the EBS data volume and count toward your storage billing. On Azure SQL, log files are included within the max database size allocation.

    Monitor log space usage and identify what is blocking log truncation:

    -- SQL Server: Transaction log space usage and truncation blockers

-- Current log space usage
DBCC SQLPERF(LOGSPACE);

-- More detailed log reuse wait reason per database
SELECT
  name                              AS database_name,
  log_reuse_wait_desc               AS truncation_blocked_by,
  -- log_reuse_wait_desc values:
  --   NOTHING        : log can be reused (healthy)
  --   LOG_BACKUP     : waiting for log backup (most common in FULL recovery)
  --   ACTIVE_TRANSACTION : long-running transaction blocking truncation
  --   DATABASE_MIRRORING / AVAILABILITY_GROUP : replica lag blocking truncation
  --   CHECKPOINT     : waiting for checkpoint (SIMPLE recovery model)
  recovery_model_desc,
  log_size_mb = (
    SELECT SUM(size) * 8.0 / 1024
    FROM sys.master_files
    WHERE database_id = databases.database_id
      AND type_desc = 'LOG'
  )
FROM
  sys.databases
WHERE
  state_desc = 'ONLINE'
ORDER BY
  log_size_mb DESC;

-- Find the active transaction blocking log truncation (if log_reuse_wait_desc = ACTIVE_TRANSACTION)
SELECT TOP 10
  tran_begin_time,
  DATEDIFF(MINUTE, tran_begin_time, GETDATE())   AS age_minutes,
  s.session_id,
  s.login_name,
  s.program_name,
  t.log_bytes_used / 1024 / 1024                 AS log_mb_used,
  LEFT(st.text, 200)                             AS current_sql
FROM
  sys.dm_tran_active_transactions   AS t
JOIN sys.dm_exec_sessions           AS s  ON s.session_id = t.session_id
CROSS APPLY
  sys.dm_exec_sql_text(s.sql_handle) AS st
WHERE
  t.transaction_type IN (1, 2)   -- read-write and read-only transactions
ORDER BY
  t.log_bytes_used DESC;

    When log_reuse_wait_desc shows LOG_BACKUP, the fix is to ensure your SQL Agent (or Azure SQL elastic job) is running log backups at a frequency consistent with your RPO. For a database generating significant log volume, running log backups every 15 minutes instead of every 60 minutes keeps the log file from growing to accommodate an hour's worth of unflushed log records.

    15.6 Building the Storage Cleanup Automation Pipeline

    The previous sections delivered individual diagnostic queries and cleanup scripts. This section assembles them into a coordinated pipeline that runs on schedule, reports results, and integrates with your FinOps cost tracking.

    The architecture has three components:

    1. Daily snapshot cleanup (Lambda / Azure Function / Cloud Run) — runs at 02:00 UTC

    2. Weekly bloat analysis and repack (cron job on bastion host or ECS Fargate task) — runs Sunday at 01:00 UTC

    3. Monthly storage cost report (scheduled query against billing API) — runs first day of month

    B[Weekly: bloat analysis + repack\nSunday 01:00 UTC] --> D
    C[Monthly: storage cost report\n1st of month] --> D
    D --> E[DynamoDB / Cosmos DB / Firestore\nsavings ledger]

    *The three-component cleanup pipeline — each runs independently but feeds the same savings ledger for FinOps reporting.*

    Here is the DynamoDB schema and a boto3 writer function you can drop into the Lambda from Section 15.2:

    # Add to rds_snapshot_cleanup.py after the cleanup report is generated

import hashlib

def write_run_record_to_dynamodb(report: dict, table_name: str = 'storage-cleanup-runs'):
    """
    Persist cleanup run results to DynamoDB for historical tracking.
    Table schema:
      PK: run_date (YYYY-MM-DD)
      SK: run_id (timestamp + type)
    """
    dynamodb = boto3.resource('dynamodb')
    table    = dynamodb.Table(table_name)

    run_id = f"{datetime.now(timezone.utc).strftime('%Y%m%dT%H%M%SZ')}-snapshot"

    item = {
        'run_date'                    : datetime.now(timezone.utc).strftime('%Y-%m-%d'),
        'run_id'                      : run_id,
        'platform'                    : 'aws-rds',
        'run_type'                    : 'snapshot_cleanup',
        'dry_run'                     : report.get('dry_run', True),
        'snapshots_deleted'           : report.get('snapshots_deleted', 0),
        'snapshots_skipped'           : report.get('snapshots_skipped', 0),
        'estimated_savings_usd'       : str(report.get('estimated_savings_usd', 0)),
        'ttl'                         : int(
            (datetime.now(timezone.utc) + timedelta(days=365)).timestamp()
        ),  # Auto-expire records after 1 year
    }

    try:
        table.put_item(Item=item)
        print(f"Run record written to DynamoDB: {run_id}")
    except Exception as e:
        print(f"Failed to write DynamoDB record: {e}")
        # Non-fatal — cleanup still succeeded

    To query historical savings from DynamoDB, use a GSI on run_date or export the table to S3 and query it with Athena:

    -- Athena: Monthly savings summary from storage cleanup runs
-- Table created from DynamoDB export to S3

SELECT
  DATE_FORMAT(DATE_PARSE(run_date, '%Y-%m-%d'), '%Y-%m') AS billing_month,
  run_type,
  SUM(snapshots_deleted)                                  AS total_deleted,
  SUM(CAST(estimated_savings_usd AS DOUBLE))              AS total_savings_usd,
  COUNT(*)                                                AS run_count,
  MAX(CAST(estimated_savings_usd AS DOUBLE))              AS largest_single_run_usd
FROM
  storage_cleanup_runs
WHERE
  dry_run = false
GROUP BY
  DATE_FORMAT(DATE_PARSE(run_date, '%Y-%m-%d'), '%Y-%m'),
  run_type
ORDER BY
  billing_month DESC,
  total_savings_usd DESC;

    15.7 Setting Storage Budgets and Anomaly Alerts

    Automation that cleans up storage is only half the solution. You also need alerting that tells you when storage spend is growing faster than your application's legitimate data growth — which usually signals a new source of waste you have not yet automated away.

    On AWS, CloudWatch has a built-in metric FreeStorageSpace per RDS instance. Combine this with a Billing Alarm on the Cost Explorer anomaly detection to get two independent signals: one that fires when an individual instance is filling up (operational signal), and one that fires when the aggregate RDS storage spend grows unexpectedly across the account (FinOps signal).

    The following CloudWatch alarm fires when free storage drops below 20% of provisioned capacity on any monitored instance:

    #!/bin/bash
# create_storage_alarms.sh
# Creates CloudWatch alarms for RDS storage utilization across all instances
# Requires: aws cli with CloudWatch and RDS permissions

SNS_ARN="${1:?Usage: $0 <sns-topic-arn>}"

# Get all RDS instance identifiers and their allocated storage
aws rds describe-db-instances \
  --query 'DBInstances[*].[DBInstanceIdentifier,AllocatedStorage]' \
  --output text | \
while IFS=$'\t' read -r instance_id allocated_gb; do

  # Threshold: alert when free space < 20% of provisioned
  threshold_bytes=$(echo "$allocated_gb * 1073741824 * 0.20" | bc | cut -d'.' -f1)

  echo "Creating alarm for $instance_id (${allocated_gb} GB provisioned, threshold: ${threshold_bytes} bytes)"

  aws cloudwatch put-metric-alarm \
    --alarm-name "RDS-LowStorage-${instance_id}" \
    --alarm-description "RDS instance ${instance_id} free storage below 20%" \
    --metric-name FreeStorageSpace \
    --namespace AWS/RDS \
    --dimensions Name=DBInstanceIdentifier,Value="$instance_id" \
    --statistic Minimum \
    --period 300 \
    --evaluation-periods 3 \
    --threshold "$threshold_bytes" \
    --comparison-operator LessThanThreshold \
    --alarm-actions "$SNS_ARN" \
    --ok-actions    "$SNS_ARN" \
    --treat-missing-data notBreaching

done

echo "Done. Alarms created for all RDS instances."

    For the FinOps-layer alert, use Cost Explorer Anomaly Detection. This is more effective than a fixed budget alert because it learns your seasonal baseline and fires only when the growth pattern deviates from what it has learned to expect:

    # Create a Cost Explorer anomaly monitor for RDS storage
aws ce create-anomaly-monitor \
  --anomaly-monitor '{
    "MonitorName": "RDS-Storage-Anomaly-Monitor",
    "MonitorType": "DIMENSIONAL",
    "MonitorDimension": "SERVICE"
  }'

# After creating the monitor, capture its MonitorArn from the response
# Then create a subscription for the alert

aws ce create-anomaly-subscription \
  --anomaly-subscription '{
    "SubscriptionName": "RDS-Storage-Anomaly-Alert",
    "MonitorArnList": ["<MonitorArn-from-above>"],
    "Subscribers": [
      {
        "Address": "<your-sns-topic-arn>",
        "Type": "SNS"
      }
    ],
    "Threshold": 50,
    "Frequency": "DAILY"
  }'

    The Threshold: 50 value means the alert fires when Cost Explorer detects an anomaly with an estimated impact above $50. Adjust this to a value that is meaningful for your fleet size — lower for smaller deployments, higher for large multi-account organizations where $50 might be normal variance.

    On Azure, the equivalent is an Azure Cost Management Budget with an alert action group. Set the budget scope to your resource group or subscription, filter to the SQL meter category, and configure an alert at 80% and 100% of the monthly budget. Wire the alert to an Action Group that sends email and triggers an Azure Function that runs the diagnostic queries from Section 15.1 automatically, so the person receiving the alert immediately gets a breakdown of what changed.

    On GCP, use Budget Alerts in the Billing console filtered to the Cloud SQL service, and configure a Pub/Sub topic as the notification channel. A Cloud Function subscribed to that topic can then run the BigQuery cost breakdown query from Section 15.1 and publish the results to a Slack channel or incident management system.

    15.8 Right-Sizing Provisioned Storage After Cleanup

    After running the cleanup automation for several weeks, you will have recovered storage at the physical layer — table files are smaller, snapshots are gone, log files are trimmed. However, on RDS, the provisioned storage allocation does not decrease automatically. You are still paying for the full provisioned volume size regardless of how much space is now free.

    The path to reducing provisioned storage on RDS requires creating a snapshot of the current instance, restoring it to a new instance with a lower storage allocation, and then cutting over application connections. This is not a live resize — it is a migration. The steps are:

    1. Confirm that actual used storage is well below your target new allocation. Leave at minimum 30% headroom.

    2. Take a final snapshot of the current instance.

    3. Restore the snapshot to a new instance, specifying the lower --allocated-storage value.

    4. Validate the restored instance thoroughly (run your integration test suite against it).

    5. Update the DNS CNAME or Route 53 record to point to the new instance endpoint.

    6. Monitor for 24 hours, then delete the old instance.

    The restore command with reduced storage:

    # Restore RDS snapshot to a new instance with reduced provisioned storage
# Assumes the snapshot has been taken and physical used space supports the reduction

SOURCE_SNAPSHOT="rds:prod-sqlserver-2024-03-01-02-00"
NEW_INSTANCE_ID="prod-sqlserver-resized"
NEW_STORAGE_GB=300     # Must be >= actual used space + 30% headroom
INSTANCE_CLASS="db.r6g.2xlarge"
SUBNET_GROUP="prod-db-subnet-group"
SECURITY_GROUPS="sg-0abc123def456789"

aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier "$NEW_INSTANCE_ID" \
  --db-snapshot-identifier "$SOURCE_SNAPSHOT" \
  --db-instance-class      "$INSTANCE_CLASS" \
  --allocated-storage       "$NEW_STORAGE_GB" \
  --storage-type            gp3 \
  --db-subnet-group-name    "$SUBNET_GROUP" \
  --vpc-security-group-ids  "$SECURITY_GROUPS" \
  --no-publicly-accessible \
  --enable-performance-insights \
  --performance-insights-retention-period 7 \
  --tags Key=Environment,Value=production \
         Key=ManagedBy,Value=finops-automation

echo "Restore initiated. Monitor progress:"
echo "aws rds describe-db-instances --db-instance-identifier $NEW_INSTANCE_ID \\"
echo "  --query 'DBInstances[0].DBInstanceStatus'"

    For Azure SQL Database, reducing the max size allocation is simpler — it does not require a restore. You can issue an ALTER DATABASE statement directly, as long as the actual data size is below the new target:

    -- Azure SQL: Reduce max size allocation after reclaiming space
-- Check current usage first
SELECT
  DB_NAME()                                               AS database_name,
  SUM(size) * 8 / 1024                                    AS allocated_mb,
  SUM(FILEPROPERTY(name, 'SpaceUsed')) * 8 / 1024         AS used_mb,
  (SUM(size) - SUM(FILEPROPERTY(name, 'SpaceUsed'))) * 8 / 1024
                                                          AS free_mb
FROM
  sys.database_files
WHERE
  type_desc = 'ROWS';

-- If used_mb is sufficiently below your target, reduce the max size
-- Example: reduce from 1 TB to 500 GB after bloat reclamation
ALTER DATABASE CURRENT MODIFY (MAXSIZE = 500 GB);

    On GCP Cloud SQL, storage capacity is managed differently: it auto-increases but does not auto-decrease, and you cannot reduce the provisioned disk size on a running instance. The path to reduction on Cloud SQL is similar to RDS — export the data, delete the instance, and create a new one with a smaller disk. For most GCP deployments, the practical approach is to focus cleanup energy on preventing autoscale events rather than on reducing already-provisioned capacity.

    Key Takeaways

  • → **Manual snapshots are the highest-leverage cleanup target**: They accumulate indefinitely, carry per-GB monthly costs, and have no built-in expiration. A tagging convention (`RetentionDays`, `Purpose`) combined with a daily enforcement Lambda recovers storage budget within days of deployment, with no application impact.
  • → **Index fragmentation requires both immediate remediation and root-cause treatment**: Use `ALTER INDEX ... REBUILD` (online on Enterprise) for severely fragmented indexes, and simultaneously fix the fill-factor and maintenance schedule that let fragmentation recur. Treating only one side of this problem means running the rebuild operation repeatedly on the same indexes.
  • → **SQL Server fragmentation savings on cloud platforms are context-dependent**: On RDS SQL Server, index rebuilds directly reduce storage billing because log and data files share the provisioned EBS volume. On Azure SQL vCore, the benefit is primarily performance-driven unless you follow the rebuild with an `ALTER DATABASE MODIFY (MAXSIZE = ...)` to reduce the provisioned maximum.
  • → **Temporary storage mismanagement triggers permanent cost increases**: On RDS, tempdb spills that push the data volume can trigger autoscale events that are irreversible without a snapshot restore. Monitor tempdb allocation continuously, and fix the queries and statistics that cause spills rather than growing storage to absorb them.
  • → **Automation without measurement is incomplete**: Each cleanup run should emit a structured result record — items deleted, storage reclaimed, estimated monthly savings — to a queryable store such as DynamoDB or BigQuery. This creates a savings ledger that makes the FinOps ROI of cleanup automation visible to finance and engineering leadership, and makes it straightforward to detect when a new source of waste has appeared that the existing automation does not yet address.
