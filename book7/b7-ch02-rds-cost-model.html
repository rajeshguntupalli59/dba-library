Chapter 2 of 30 Stop Overpaying for SQL Server

Chapter 2: RDS for SQL Server Cost Model: Compute, Storage, Licensing, and Transfer

Organizations running AWS RDS at scale routinely overpay by 40–60% — not because the pricing is opaque, but because most teams accept the default configuration and never revisit it. A single db.r6i.2xlarge running SQL Server Standard Edition with License Included, gp2 storage, Multi-AZ enabled, and no Reserved Instance commitment can cost over $2,600/month — and more than half of that is the SQL Server license embedded in the hourly rate. That same workload, rightsized to a db.r6i.xlarge on gp3 storage with a one-year Reserved Instance (or converted to BYOL if you hold licenses), costs closer to $900/month. That is $1,700/month saved on a single instance — before touching I/O fees, snapshot retention, or data transfer charges. This chapter dismantles the RDS for SQL Server cost model component by component, shows you exactly where the money goes, and gives you the queries, scripts, and automation to recover it systematically.

---

2.1 Understanding the RDS Billing Anatomy

AWS bills RDS across five distinct cost dimensions. Most teams only see the monthly total and treat it as a single line item. That is a mistake. To optimize, you need to decompose the bill into its components and assign each one a remediation strategy.

The five RDS cost dimensions:

| Dimension | Typical Share of Bill | Primary Lever |

|---|---|---|

| Compute (instance hours) | 50–65% | Reserved Instances, rightsizing, stop/start |

| Storage (EBS volumes) | 15–25% | gp2 → gp3 migration, size right-sizing |

| I/O requests | 5–20% | gp3 eliminates per-I/O charges entirely |

| Data transfer | 3–10% | Same-AZ reads, VPC endpoints, caching |

| Snapshots and backups | 2–8% | Retention period tuning, export cleanup |

The critical insight here is that gp2 storage charges per I/O request beyond the baseline throughput, which scales at 3 IOPS per GB. A 500 GB gp2 volume provides 1,500 baseline IOPS. Any database workload that regularly exceeds this baseline incurs per-request charges that accumulate invisibly. A busy OLTP workload on a 500 GB gp2 volume can easily pay $200–$400/month in I/O alone. gp3 provides 3,000 IOPS and 125 MB/s throughput at no per-I/O charge, and costs $0.08/GB/month compared to gp2's $0.115/GB/month. The math on a 1 TB volume is straightforward:

  • → **gp2, 1 TB**: $0.115 × 1,024 GB = **$117.76/month** (plus I/O charges)
  • → **gp3, 1 TB**: $0.08 × 1,024 GB = **$81.92/month** (no I/O charges)
  • → **Storage savings**: $35.84/month, approximately 30%
  • → **I/O savings**: varies, but commonly $50–$200/month on active workloads

    • That is the storage dimension alone. Compute is where the larger numbers live.

    Retrieving your current RDS cost breakdown using AWS Cost Explorer:

    Run this script every Monday morning as part of a cost review cadence. The output tells you immediately whether I/O charges are appearing as RDS:StorageIOUsage line items — a clear signal that affected instances should move to gp3.

    2.2 Compute Cost Analysis: Finding the Right Instance

    Compute is the largest single cost driver in RDS. The instance family, size, and purchase option together determine whether you are paying market rate or overpaying substantially. AWS offers three purchase options for RDS compute:

  • → **On-Demand**: Full price, no commitment, billed per second (minimum 10 minutes)
  • → **Reserved Instances (RI)**: 1-year or 3-year commitment, 30–60% discount
  • → **Savings Plans**: More flexible than RIs, applies across instance families

    • A db.r6i.2xlarge running SQL Server Standard Edition (License Included) on-demand costs approximately $1.75/hour in us-east-1, or $1,277.50/month — roughly $0.96/hour of which is the embedded SQL Server license. The same instance on a one-year Reserved Instance (no upfront) costs about $1.14/hour, or $832/month — a 35% reduction with zero architectural changes. Note that Reserved Instances discount the whole hourly rate including the license portion, which makes them disproportionately valuable for SQL Server compared to open-source engines.

    The instance family choice matters as much as the size — with a SQL Server-specific constraint: RDS for SQL Server runs on Intel and AMD instance families only. Graviton (r6g, m6g) instances, which offer the best price-performance on RDS for open-source engines, cannot run SQL Server at all. Within the supported families, the current-generation r6i/m6i instances provide 10–20% better price-performance than the previous-generation r5/m5. Teams still running r5 or r4 instances have low-hanging savings available with a simple instance class modification — and any fleet inventory that lists Graviton classes next to SQL Server engines has a data quality problem worth fixing.

    Query to identify compute sizing opportunities using CloudWatch metrics:

    #!/usr/bin/env python3
"""
rds_compute_rightsizing.py

Analyzes CPU and memory utilization across all RDS instances over
the last 14 days. Flags instances with consistently low CPU for
downsizing and instances at saturation for upsizing.

Schedule: Weekly via EventBridge + Lambda or cron
"""

import boto3
from datetime import datetime, timedelta
from collections import defaultdict

def get_cloudwatch_metric_stats(cw_client, instance_id, metric_name, days=14):
    """Retrieve average, max, and p95 for a given CloudWatch RDS metric."""
    end_time = datetime.utcnow()
    start_time = end_time - timedelta(days=days)

    response = cw_client.get_metric_statistics(
        Namespace='AWS/RDS',
        MetricName=metric_name,
        Dimensions=[{'Name': 'DBInstanceIdentifier', 'Value': instance_id}],
        StartTime=start_time,
        EndTime=end_time,
        Period=3600,  # 1-hour granularity
        Statistics=['Average', 'Maximum'],
        ExtendedStatistics=['p95']
    )

    datapoints = response.get('Datapoints', [])
    if not datapoints:
        return None

    averages = [dp['Average'] for dp in datapoints]
    maximums = [dp['Maximum'] for dp in datapoints]
    p95_values = [dp['ExtendedStatistics'].get('p95', 0) for dp in datapoints]

    return {
        'avg': sum(averages) / len(averages),
        'max': max(maximums),
        'p95': sum(p95_values) / len(p95_values) if p95_values else 0,
        'datapoint_count': len(datapoints)
    }

def estimate_monthly_cost(instance_class, engine, region='us-east-1'):
    """
    Approximate on-demand hourly rates for common instance types.
    In production, replace with AWS Price List API calls.
    """
    # Approximate on-demand rates, us-east-1, SQL Server Standard Edition License Included
    # SQL Server cannot run on Graviton (r6g/m6g) or burstable Graviton (t4g) classes: Intel/AMD only
    rates = {
        'db.r6i.large':   0.46,
        'db.r6i.xlarge':  0.92,
        'db.r6i.2xlarge': 1.75,
        'db.r6i.4xlarge': 3.50,
        'db.r6i.8xlarge': 7.00,
        'db.r5.large':    0.48,
        'db.r5.xlarge':   0.96,
        'db.r5.2xlarge':  1.92,
        'db.r5.4xlarge':  3.84,
        'db.m6i.large':   0.45,
        'db.m6i.xlarge':  0.90,
        'db.m6i.2xlarge': 1.72,
        'db.m5.large':    0.47,
        'db.m5.xlarge':   0.94,
        'db.m5.2xlarge':  1.88,
    }
    hourly = rates.get(instance_class, 0)
    return hourly * 730  # approximate monthly hours

def analyze_rds_rightsizing():
    rds_client = boto3.client('rds')
    cw_client = boto3.client('cloudwatch')

    instances = rds_client.describe_db_instances()['DBInstances']

    print(f"{'Instance ID':<35} {'Class':<20} {'CPU Avg':>8} {'CPU P95':>8} "
          f"{'CPU Max':>8} {'Est. Monthly':>13} {'Recommendation'}")
    print("-" * 120)

    total_potential_savings = 0.0

    for inst in instances:
        if inst['DBInstanceStatus'] != 'available':
            continue

        instance_id = inst['DBInstanceIdentifier']
        instance_class = inst['DBInstanceClass']
        engine = inst['Engine']

        cpu_stats = get_cloudwatch_metric_stats(cw_client, instance_id, 'CPUUtilization')

        if not cpu_stats or cpu_stats['datapoint_count'] < 50:
            recommendation = "INSUFFICIENT DATA"
            monthly_cost = estimate_monthly_cost(instance_class, engine)
            savings = 0.0
        else:
            monthly_cost = estimate_monthly_cost(instance_class, engine)
            cpu_avg = cpu_stats['avg']
            cpu_p95 = cpu_stats['p95']
            cpu_max = cpu_stats['max']

            if cpu_p95 < 20 and cpu_max < 50:
                recommendation = "DOWNSIZE CANDIDATE"
                savings = monthly_cost * 0.40  # approximate 40% savings one size down
                total_potential_savings += savings
            elif cpu_p95 < 40 and cpu_max < 70:
                recommendation = "RESERVE (RI opportunity)"
                savings = monthly_cost * 0.38
                total_potential_savings += savings
            elif cpu_avg > 75:
                recommendation = "UPSIZE or OPTIMIZE QUERIES"
                savings = 0.0
            else:
                recommendation = "OK"
                savings = 0.0

            print(f"{instance_id:<35} {instance_class:<20} "
                  f"{cpu_avg:>7.1f}% {cpu_p95:>7.1f}% {cpu_max:>7.1f}% "
                  f"${monthly_cost:>11.2f}  {recommendation}"
                  + (f" (save ~${savings:.0f}/mo)" if savings > 0 else ""))
            continue

        print(f"{instance_id:<35} {instance_class:<20} "
              f"{'N/A':>8} {'N/A':>8} {'N/A':>8} "
              f"${monthly_cost:>11.2f}  {recommendation}")

    print("-" * 120)
    print(f"Total estimated monthly savings opportunity: ${total_potential_savings:,.2f}")
    print(f"Annual savings opportunity: ${total_potential_savings * 12:,.2f}")

if __name__ == '__main__':
    analyze_rds_rightsizing()

    Run this weekly. Any instance showing DOWNSIZE CANDIDATE where P95 CPU stays below 20% for two consecutive weeks is a legitimate rightsizing target. For production databases, validate against peak traffic periods — holiday seasons, month-end close, batch jobs — before committing to a smaller instance class.

    2.3 Storage Cost Deep Dive: gp2 to gp3 Migration

    The storage billing story in RDS changed significantly when AWS introduced gp3 in 2022. Despite gp3 being strictly superior for most workloads — cheaper per GB, higher baseline IOPS, no per-I/O charges, and independently scalable IOPS and throughput — a large fraction of RDS instances in production today still run on gp2. This is a pure cost problem with a well-defined solution.

    gp2 vs gp3 economics (us-east-1, February 2025):

    | Storage Type | Price/GB/Month | Baseline IOPS | Max IOPS | Throughput | I/O Charges |

    |---|---|---|---|---|---|

    | gp2 | $0.115 | 3 × GB (min 100) | 16,000 | 250 MB/s | Yes, above baseline |

    | gp3 | $0.080 | 3,000 (fixed) | 16,000 (+$0.02/IOPS) | 125 MB/s (+$0.04/MB/s) | Never |

    | io1 | $0.125 | Provisioned | 64,000 | 4,000 MB/s | Never |

    | io2 | $0.125 | Provisioned | 256,000 | 4,000 MB/s | Never |

    For the vast majority of RDS workloads, gp3 at base configuration (3,000 IOPS, 125 MB/s) is sufficient. For high-IOPS workloads that were previously on gp2 with large volumes to get more IOPS, the math is even more compelling: you can right-size the storage volume down and provision exactly the IOPS needed on gp3.

    Example: A team running a 2 TB gp2 volume to get 6,000 IOPS:

  • → gp2 cost: 2,048 GB × $0.115 = **$235.52/month** (plus I/O charges)
  • → gp3 equivalent: 500 GB × $0.080 + (6,000 - 3,000) IOPS × $0.02 = $40 + $60 = **$100/month**
  • → **Monthly savings: $135.52 + eliminated I/O charges**

    • The following query identifies all RDS instances still on gp2 and calculates the projected savings:

    -- Run this against an Amazon Athena table built from AWS Cost and Usage Reports,
-- or adapt for your cost data warehouse.
-- This example uses the standard CUR schema.

SELECT
    line_item_resource_id                           AS instance_arn,
    resource_tags_user_environment                  AS environment,
    resource_tags_user_team                         AS team,
    product_volume_type                             AS storage_type,
    SUM(line_item_usage_amount)                     AS total_gb_hours,
    SUM(line_item_unblended_cost)                   AS total_storage_cost,
    -- Estimate gp3 equivalent cost
    ROUND(
        (SUM(line_item_usage_amount) / 730.0)       -- convert GB-hours to GB
        * 0.080, 2
    )                                               AS gp3_estimated_cost,
    -- Savings potential
    ROUND(
        SUM(line_item_unblended_cost)
        - (SUM(line_item_usage_amount) / 730.0 * 0.080),
        2
    )                                               AS estimated_monthly_savings
FROM
    cost_and_usage_report
WHERE
    line_item_service_code    = 'AmazonRDS'
    AND product_volume_type   = 'General Purpose'   -- this is gp2 in CUR
    AND line_item_usage_type  LIKE '%StorageUsage%'
    AND year = '2025'
    AND month = '2'
GROUP BY
    line_item_resource_id,
    resource_tags_user_environment,
    resource_tags_user_team,
    product_volume_type
HAVING
    SUM(line_item_unblended_cost) > 10.00           -- ignore trivially small volumes
ORDER BY
    estimated_monthly_savings DESC;

    To execute the gp2 → gp3 migration itself, AWS allows you to modify storage type without downtime for most instance classes. The modification applies immediately and the volume conversion happens in the background:

    #!/bin/bash
# migrate_gp2_to_gp3.sh
# Migrates a single RDS instance from gp2 to gp3 storage.
# Run during low-traffic periods. No downtime required for most engines.
# Validate: check Performance Insights for I/O latency before and after.

INSTANCE_ID="${1:-}"
DRY_RUN="${2:-true}"   # Set to "false" to execute

if [[ -z "$INSTANCE_ID" ]]; then
    echo "Usage: $0 <instance-id> [true|false]"
    echo "  Second argument: dry-run mode (default: true)"
    exit 1
fi

echo "=== Checking current storage configuration ==="
CURRENT_CONFIG=$(aws rds describe-db-instances \
    --db-instance-identifier "$INSTANCE_ID" \
    --query 'DBInstances[0].{
        StorageType:StorageType,
        AllocatedStorage:AllocatedStorage,
        Iops:Iops,
        StorageThroughput:StorageThroughput,
        MultiAZ:MultiAZ,
        InstanceClass:DBInstanceClass
    }' \
    --output json)

echo "$CURRENT_CONFIG" | python3 -c "
import json, sys
config = json.load(sys.stdin)
storage_type = config.get('StorageType', 'unknown')
allocated_gb = config.get('AllocatedStorage', 0)
iops = config.get('Iops', 'N/A')
multi_az = config.get('MultiAZ', False)
instance_class = config.get('InstanceClass', 'unknown')

print(f'Instance class:    {instance_class}')
print(f'Storage type:      {storage_type}')
print(f'Allocated storage: {allocated_gb} GB')
print(f'Current IOPS:      {iops}')
print(f'Multi-AZ:          {multi_az}')

if storage_type == 'gp3':
    print('Already on gp3. No migration needed.')
    sys.exit(0)

# Cost calculations
gp2_monthly = allocated_gb * 0.115
gp3_monthly = allocated_gb * 0.080
savings = gp2_monthly - gp3_monthly
multiplier = 2 if multi_az else 1  # Multi-AZ doubles storage cost

print()
print('=== Cost Impact (excluding I/O charges) ===')
print(f'gp2 monthly cost:  \${gp2_monthly * multiplier:.2f}')
print(f'gp3 monthly cost:  \${gp3_monthly * multiplier:.2f}')
print(f'Monthly savings:   \${savings * multiplier:.2f}')
print(f'Annual savings:    \${savings * multiplier * 12:.2f}')
print(f'(Multi-AZ multiplier of {multiplier} applied)')
"

STORAGE_TYPE=$(aws rds describe-db-instances \
    --db-instance-identifier "$INSTANCE_ID" \
    --query 'DBInstances[0].StorageType' \
    --output text)

if [[ "$STORAGE_TYPE" == "gp3" ]]; then
    echo "Instance is already on gp3. Exiting."
    exit 0
fi

if [[ "$DRY_RUN" == "true" ]]; then
    echo ""
    echo "DRY RUN: Would execute the following modification:"
    echo "aws rds modify-db-instance \\"
    echo "    --db-instance-identifier $INSTANCE_ID \\"
    echo "    --storage-type gp3 \\"
    echo "    --apply-immediately"
    echo ""
    echo "Set second argument to 'false' to execute."
else
    echo ""
    echo "=== Executing gp2 to gp3 migration ==="
    aws rds modify-db-instance \
        --db-instance-identifier "$INSTANCE_ID" \
        --storage-type gp3 \
        --apply-immediately

    echo "Migration initiated. Monitor status with:"
    echo "  aws rds describe-db-instances \\"
    echo "      --db-instance-identifier $INSTANCE_ID \\"
    echo "      --query 'DBInstances[0].PendingModifiedValues'"
fi

    For a fleet migration, run this script in aloop across all instances identified by the Athena query, validating each before proceeding to the next:

    #!/bin/bash
# fleet_gp2_to_gp3_migration.sh
# Iterates all gp2 RDS instances and migrates them to gp3.
# Pauses between each instance to allow background conversion to stabilize.

SLEEP_BETWEEN=30  # seconds to wait between instance modifications
DRY_RUN="${1:-true}"

echo "=== Fleet gp2 → gp3 Migration ==="
echo "Dry run: $DRY_RUN"
echo ""

# Retrieve all available instances on gp2
GP2_INSTANCES=$(aws rds describe-db-instances \
    --query 'DBInstances[?StorageType==`gp2` && DBInstanceStatus==`available`].DBInstanceIdentifier' \
    --output text)

if [[ -z "$GP2_INSTANCES" ]]; then
    echo "No gp2 instances found. Nothing to do."
    exit 0
fi

COUNT=$(echo "$GP2_INSTANCES" | wc -w | tr -d ' ')
echo "Found $COUNT instance(s) on gp2:"
echo "$GP2_INSTANCES" | tr '\t' '\n' | sed 's/^/  - /'
echo ""

for INSTANCE_ID in $GP2_INSTANCES; do
    echo "--- Processing: $INSTANCE_ID ---"
    bash migrate_gp2_to_gp3.sh "$INSTANCE_ID" "$DRY_RUN"
    echo ""
    if [[ "$DRY_RUN" == "false" ]]; then
        echo "Waiting ${SLEEP_BETWEEN}s before next instance..."
        sleep "$SLEEP_BETWEEN"
    fi
done

echo "=== Fleet migration complete ==="

    One important operational note: after migrating to gp3, monitor ReadLatency and WriteLatency in CloudWatch for 48 hours. In rare cases involving very small volumes (under 20 GB) that relied on gp2's burst credit model, I/O latency can increase because gp2 burst credits allowed short spikes above the baseline IOPS tier. gp3's fixed 3,000 IOPS baseline is more consistent but has no burst headroom unless you provision additional IOPS explicitly.

    2.4 I/O Cost Analysis and Elimination

    The least visible component of the RDS bill is often I/O charges, because they do not appear as a separate instance cost — they accumulate as RDS:StorageIOUsage charges and only become obvious when you decompose the bill by usage type, as shown in Section 2.1. On a gp2 volume, every I/O request beyond the baseline IOPS allocation costs $0.10 per million requests.

    That sounds trivially small. It is not. A moderately busy SQL Server instance executing 500 read IOPS and 200 write IOPS continuously against a 200 GB gp2 volume (baseline: 600 IOPS) will stay near but can intermittently exceed baseline during query bursts. An instance that regularly exceeds baseline by even 200 IOPS for 12 hours per day generates approximately 260 million excess I/O requests per month — a $26/month charge that appears invisible until you look for it. Multiply across a fleet of 20 instances and you are looking at potentially $500+/month in charges that vanish entirely by moving to gp3.

    Identifying I/O charges in the Cost and Usage Report:

    -- Athena query: find instances generating the highest I/O charges
-- These are your highest-priority gp3 migration targets

SELECT
    line_item_resource_id                           AS instance_id,
    resource_tags_user_environment                  AS environment,
    resource_tags_user_name                         AS owner,
    SUM(line_item_unblended_cost)                   AS io_charges_usd,
    SUM(line_item_usage_amount) / 1e6               AS billions_of_requests,
    -- Annualize to make the business case clear
    SUM(line_item_unblended_cost) * 12              AS annualized_io_cost
FROM
    cost_and_usage_report
WHERE
    line_item_service_code = 'AmazonRDS'
    AND line_item_usage_type LIKE '%StorageIOUsage%'
    AND year = '2025'
    AND month = '2'
GROUP BY
    line_item_resource_id,
    resource_tags_user_environment,
    resource_tags_user_name
HAVING
    SUM(line_item_unblended_cost) > 5.00
ORDER BY
    io_charges_usd DESC
LIMIT 25;

    Beyond the storage type migration, a second lever for I/O cost reduction is query-level optimization. Many I/O charges trace back to a small number of queries executing full sequential scans on large tables. The following T-SQL query identifies the highest I/O-consuming queries using sys.dm_exec_query_stats:

    The avg_logical_reads column is your primary signal. Queries with high logical reads per execution are churning the buffer pool and driving physical I/O. The remediation path is typically one of three options:

    1. Add an index to eliminate a scan — check sys.dm_db_missing_index_details for what the engine already recommends

    2. Increase the buffer pool via the max server memory setting (RDS parameter group) to cache more data in memory

    3. Increase instance memory by upsizing the instance class — weighed against the licensing cost of larger instances

    The T-SQL equivalent using sys.dm_exec_query_stats:

    -- SQL Server: top queries by logical reads (I/O proxy)
-- Run against the target RDS SQL Server instance

SELECT TOP 20
    qs.execution_count,
    qs.total_logical_reads,
    qs.total_logical_reads / qs.execution_count       AS avg_logical_reads,
    qs.total_elapsed_time / qs.execution_count / 1000 AS avg_elapsed_ms,
    SUBSTRING(
        qt.text,
        (qs.statement_start_offset / 2) + 1,
        (
            CASE qs.statement_end_offset
                WHEN -1 THEN DATALENGTH(qt.text)
                ELSE qs.statement_end_offset
            END - qs.statement_start_offset
        ) / 2 + 1
    )                                                 AS query_text
FROM
    sys.dm_exec_query_stats qs
    CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS qt
WHERE
    qs.execution_count > 50
    AND qs.total_logical_reads > 100000
ORDER BY
    qs.total_logical_reads DESC;

    High logical read counts on SQL Server translate directly to I/O pressure. Each logical read that misses the buffer cache becomes a physical read from the EBS volume, incrementing the I/O counter that AWS bills on gp2. On gp3, these physical reads still consume IOPS against your provisioned allocation, but they do not generate additional charges unless you exceed your provisioned IOPS limit — which you control explicitly.

    2.5 Data Transfer Cost Analysis

    Data transfer charges are the most unpredictable dimension of the RDS bill. AWS charges for data leaving a region, for data crossing Availability Zone boundaries within a region, and for data exiting to the internet. The rules are nuanced enough that many teams discover transfer charges only after a large unexpected bill.

    The data transfer pricing rules that matter most for RDS:

    | Transfer Type | Cost (us-east-1) | Common Cause |

    |---|---|---|

    | RDS → Internet | $0.09/GB | Direct public endpoint access |

    | RDS → Different AZ (same region) | $0.01/GB each direction | App in AZ-a, DB in AZ-b |

    | RDS → Same AZ | Free | Requires explicit AZ-aware placement |

    | RDS → CloudFront | Free | Edge caching of DB-backed APIs |

    | RDS → S3 (same region) | Free | Snapshot exports, ETL |

    | RDS → Another AWS Region | $0.02–$0.08/GB | Cross-region replicas |

    The cross-AZ transfer cost is the most commonly overlooked. If your application servers are in us-east-1a and your RDS primary is in us-east-1b, every query result crosses an AZ boundary. At $0.01/GB in each direction, a database serving 1 TB of query results per month incurs $10.24/month in cross-AZ transfer charges — charges that appear on the EC2 transfer line, not the RDS line, which is why they are easy to miss.

    Identifying cross-AZ transfer costs using VPC Flow Logs:

    #!/usr/bin/env python3
"""
analyze_rds_transfer_costs.py

Queries CloudWatch Logs Insights against VPC Flow Logs to identify
data flows involving RDS endpoints. Requires VPC Flow Logs enabled
and delivered to CloudWatch Logs.

This is a read-only diagnostic script — it does not modify anything.
"""

import boto3
import time
from datetime import datetime, timedelta

def get_rds_private_ips(region='us-east-1'):
    """Retrieve the private IP addresses of all RDS instances."""
    rds_client = boto3.client('rds', region_name=region)
    ec2_client = boto3.client('ec2', region_name=region)

    rds_ips = {}
    instances = rds_client.describe_db_instances()['DBInstances']

    for inst in instances:
        endpoint = inst.get('Endpoint', {})
        hostname = endpoint.get('Address', '')
        if not hostname:
            continue

        # Resolve hostname to IP via EC2 network interfaces
        try:
            import socket
            ip = socket.gethostbyname(hostname)
            rds_ips[ip] = {
                'id': inst['DBInstanceIdentifier'],
                'az': inst.get('AvailabilityZone', 'unknown'),
                'class': inst['DBInstanceClass']
            }
        except Exception:
            continue

    return rds_ips

def query_flow_logs_for_rds_traffic(log_group, rds_ip, hours=24):
    """
    Query VPC Flow Logs for bytes transferred to/from a specific RDS IP.
    Returns total bytes separated by direction.
    """
    logs_client = boto3.client('logs')

    query = f"""
    fields @timestamp, srcAddr, dstAddr, bytes, action
    | filter (srcAddr = '{rds_ip}' or dstAddr = '{rds_ip}')
    | filter action = 'ACCEPT'
    | stats sum(bytes) as total_bytes by srcAddr, dstAddr
    | sort total_bytes desc
    | limit 50
    """

    end_time = int(datetime.utcnow().timestamp())
    start_time = int((datetime.utcnow() - timedelta(hours=hours)).timestamp())

    response = logs_client.start_query(
        logGroupName=log_group,
        startTime=start_time,
        endTime=end_time,
        queryString=query
    )
    query_id = response['queryId']

    # Poll for completion
    for _ in range(30):
        time.sleep(2)
        result = logs_client.get_query_results(queryId=query_id)
        if result['status'] in ('Complete', 'Failed', 'Cancelled'):
            break

    if result['status'] != 'Complete':
        return []

    rows = []
    for record in result['results']:
        row = {field['field']: field['value'] for field in record}
        rows.append(row)
    return rows

def estimate_transfer_cost(bytes_transferred, transfer_type='cross_az'):
    """Estimate cost for a given number of bytes based on transfer type."""
    gb = bytes_transferred / (1024 ** 3)
    rates = {
        'cross_az': 0.01,      # per GB, each direction
        'internet':  0.09,
        'cross_region': 0.02,
    }
    return gb * rates.get(transfer_type, 0.01)

def main():
    LOG_GROUP = '/aws/vpc/flowlogs'   # adjust to your VPC Flow Log group name
    HOURS = 24

    print("=== RDS Data Transfer Cost Analysis ===")
    print(f"Analyzing last {HOURS} hours of VPC Flow Logs\n")

    rds_ips = get_rds_private_ips()
    if not rds_ips:
        print("No RDS instances found or could not resolve IPs.")
        return

    total_estimated_daily_cost = 0.0

    for ip, metadata in rds_ips.items():
        print(f"Instance: {metadata['id']} ({metadata['class']}, AZ: {metadata['az']})")
        print(f"  Private IP: {ip}")

        flows = query_flow_logs_for_rds_traffic(LOG_GROUP, ip, HOURS)
        if not flows:
            print("  No flow log data available.\n")
            continue

        total_bytes = sum(int(row.get('total_bytes', 0)) for row in flows)
        total_gb = total_bytes / (1024 ** 3)
        daily_cost = estimate_transfer_cost(total_bytes, 'cross_az')
        monthly_cost = daily_cost * 30

        print(f"  Total data transferred (24h): {total_gb:.2f} GB")
        print(f"  Estimated daily transfer cost: ${daily_cost:.4f}")
        print(f"  Estimated monthly transfer cost: ${monthly_cost:.2f}")
        total_estimated_daily_cost += daily_cost
        print()

    print(f"Total estimated monthly transfer cost across all RDS: "
          f"${total_estimated_daily_cost * 30:.2f}")

if __name__ == '__main__':
    main()

    The primary remediation for cross-AZ transfer costs is AZ-aware deployment: ensure application servers and the RDS primary endpoint are colocated in the same Availability Zone. This requires either:

    1. Querying the RDS endpoint's current AZ and placing Auto Scaling groups to prefer that AZ

    2. Using Amazon RDS Proxy with connection pooling that routes to the same-AZ replica

    For Multi-AZ deployments, the standby is in a different AZ by design — but only reads and writes to the primary endpoint incur transfer costs. The standby receives replication traffic that AWS does not charge for between the primary and standby RDS nodes.

    2.6 Snapshot and Backup Cost Management

    Automated backups and manual snapshots represent the quietest cost dimension on the RDS bill. AWS provides free automated backup storage up to the size of your provisioned database storage. Beyond that threshold, automated backup storage costs $0.095/GB/month. Manual snapshots are charged at $0.095/GB/month from the first byte.

    Teams that leave the default retention period (7 days), keep manual snapshots indefinitely, and never prune exported snapshots from S3 accumulate backup storage costs that can rival their storage volume costs within a year.

    The snapshot cost scenarios that quietly compound:

    | Scenario | Monthly Cost Impact |

    |---|---|

    | 1 TB database, 7-day retention, daily change rate 10% | Approximately free (within allocation) |

    | 1 TB database, 35-day retention, daily change rate 10% | ~$28.50/month in excess backup storage |

    | 50 manual snapshots from testing, never deleted | Potentially $50–$200/month |

    | Snapshot exported to S3, S3 storage not cleaned up | S3 Standard charges at $0.023/GB/month |

    2.7 Multi-AZ Cost Considerations and When to Reconsider

    Multi-AZ deployments double the compute and storage cost of an RDS instance by maintaining a synchronous standby replica in a second Availability Zone. For production workloads that require high availability and automatic failover, this is money well spent. For non-production environments, it is frequently unnecessary spending.

    The cost of Multi-AZ is precisely the cost of the primary instance, repeated:

  • → A db.r6i.xlarge Multi-AZ costs **twice** what the single-AZ configuration costs
  • → The standby incurs compute charges at the same rate as the primary
  • → Storage is replicated and billed twice

    • Teams often enable Multi-AZ on staging, QA, and development environments "because it matches production." This is a category error. Multi-AZ for a staging environment that receives traffic for 8 hours per day and sits idle the rest of the time provides no meaningful availability benefit — and costs the same as a 24/7 production instance.

    Identifying Multi-AZ instances in non-production environments:

    #!/usr/bin/env python3
"""
multiaz_audit.py

Identifies Multi-AZ RDS instances in non-production environments
based on naming conventions or tags. Calculates potential savings
from disabling Multi-AZ or replacing with single-AZ + read replica.
"""

import boto3

# Patterns in instance names that suggest non-production
NON_PROD_PATTERNS = ['dev', 'staging', 'stage', 'qa', 'test', 'uat', 'sandbox', 'demo']

def is_non_production(instance_id, tags):
    """Determine if instance is non-production by name or tags."""
    name_lower = instance_id.lower()
    if any(pattern in name_lower for pattern in NON_PROD_PATTERNS):
        return True

    for tag in tags:
        key = tag.get('Key', '').lower()
        value = tag.get('Value', '').lower()
        if key in ('environment', 'env') and any(p in value for p in NON_PROD_PATTERNS):
            return True
    return False

# Approximate on-demand hourly rates, SQL Server Standard License Included (us-east-1)
# SQL Server cannot run on Graviton (r6g/m6g) or burstable Graviton (t4g): Intel/AMD only
HOURLY_RATES = {
    'db.r6i.large':   0.46,
    'db.r6i.xlarge':  0.92,
    'db.r6i.2xlarge': 1.75,
    'db.r5.large':    0.48,
    'db.r5.xlarge':   0.96,
    'db.r5.2xlarge':  1.92,
    'db.m6i.large':   0.45,
    'db.m6i.xlarge':  0.90,
    'db.m5.large':    0.47,
    'db.m5.xlarge':   0.94,
}

def main():
    rds = boto3.client('rds')
    instances = rds.describe_db_instances()['DBInstances']

    print("=== Multi-AZ Non-Production Audit ===\n")
    print(f"{'Instance ID':<35} {'Class':<20} {'MultiAZ':>7} "
          f"{'Monthly Waste':>14} {'Recommendation'}")
    print("-" * 105)

    total_recoverable = 0.0

    for inst in instances:
        if inst['DBInstanceStatus'] != 'available':
            continue

        instance_id = inst['DBInstanceIdentifier']
        instance_class = inst['DBInstanceClass']
        multi_az = inst.get('MultiAZ', False)

        tags_response = rds.list_tags_for_resource(
            ResourceName=inst['DBInstanceArn']
        )
        tags = tags_response.get('TagList', [])

        non_prod = is_non_production(instance_id, tags)
        hourly = HOURLY_RATES.get(instance_class, 0)
        # Multi-AZ standby cost = same as primary compute
        standby_monthly = hourly * 730

        if multi_az and non_prod:
            recommendation = "DISABLE Multi-AZ"
            recoverable = standby_monthly
            total_recoverable += recoverable
            print(f"{instance_id:<35} {instance_class:<20} {'Yes':>7} "
                  f"${recoverable:>12.2f}  {recommendation}")
        elif multi_az and not non_prod:
            print(f"{instance_id:<35} {instance_class:<20} {'Yes':>7} "
                  f"{'(production)':>14}  OK — keep Multi-AZ")
        else:
            print(f"{instance_id:<35} {instance_class:<20} {'No':>7} "
                  f"{'—':>14}  OK — single-AZ")

    print("-" * 105)
    print(f"Estimated monthly savings from disabling non-production Multi-AZ: "
          f"${total_recoverable:,.2f}")
    print(f"Annual savings: ${total_recoverable * 12:,.2f}")

if __name__ == '__main__':
    main()

    For non-production databases that genuinely need availability during business hours, consider the stop/start schedule pattern instead: keep single-AZ, and use EventBridge scheduled rules to stop the instance overnight and on weekends. An instance that runs only 50 hours per week instead of 168 hours reduces compute costs by approximately 70%.

aws events put-rule \
    --name "stop-dev-rds-evening" \
    --schedule-expression "cron(0 19 ? * MON-FRI *)" \
    --state ENABLED

# EventBridge rule to start it at 7 AM weekdays
aws events put-rule \
    --name "start-dev-rds-morning" \
    --schedule-expression "cron(0 7 ? * MON-FRI *)" \

For a db.r6i.xlarge running SQL Server Standard (License Included) at $0.92/hour, running 50 hours/week instead of 168 hours/week saves approximately $471/month on that single dev instance — the license portion of the hourly rate makes start/stop schedules dramatically more valuable for SQL Server than for open-source engines.

    2.8 Building an RDS Cost Dashboard

    Visibility precedes optimization. A team that cannot see its RDS cost breakdown by instance, by dimension, and over time will always be reactive rather than proactive. This section builds a CloudWatch dashboard that surfaces all five cost dimensions in a single view, backed by a Lambda function that populates custom metrics from Cost Explorer data.

    Architecture:

  • → EventBridge triggers a Lambda function daily at 6 AM UTC
  • → Lambda queries Cost Explorer for yesterday's RDS costs grouped by usage type and resource
  • → Lambda publishes custom CloudWatch metrics under the `RDS/FinOps` namespace
  • → A CloudWatch dashboard displays 30-day trends for each cost dimension
    • #!/usr/bin/env python3
"""
rds_cost_metrics_publisher.py

Lambda handler that reads RDS Cost Explorer data and publishes
custom CloudWatch metrics. Deploy this as a Lambda function with
Cost Explorer and CloudWatch permissions.

IAM permissions required:
  - ce:GetCostAndUsage
  - cloudwatch:PutMetricData
"""

import boto3
import json
from datetime import datetime, timedelta

METRIC_NAMESPACE = 'RDS/FinOps'

# Maps CUR usage type keywords to human-readable dimension names
USAGE_TYPE_MAP = {
    'InstanceUsage':    'Compute',
    'Multi-AZUsage':    'Compute_MultiAZ',
    'StorageUsage':     'Storage',
    'StorageIOUsage':   'IO_Requests',
    'DataTransfer':     'DataTransfer',
    'BackupUsage':      'Backup',
}

def lambda_handler(event, context):
    ce = boto3.client('ce')
    cw = boto3.client('cloudwatch')

    end_date = datetime.utcnow().date()
    start_date = end_date - timedelta(days=1)

    response = ce.get_cost_and_usage(
        TimePeriod={
            'Start': str(start_date),
            'End':   str(end_date),
        },
        Granularity='DAILY',
        Filter={
            'Dimensions': {
                'Key':    'SERVICE',
                'Values': ['Amazon Relational Database Service']
            }
        },
        GroupBy=[
            {'Type': 'DIMENSION', 'Key': 'USAGE_TYPE'},],
        Metrics=['UnblendedCost', 'UsageQuantity']
    )

    metric_data = []
    timestamp = datetime.utcnow()

    for group in response['ResultsByTime'][0].get('Groups', []):
        usage_type_full = group['Keys'][0]
        cost = float(group['Metrics']['UnblendedCost']['Amount'])

        if cost < 0.001:
            continue

        # Map to a clean dimension name
        dimension_name = 'Other'
        for keyword, label in USAGE_TYPE_MAP.items():
            if keyword in usage_type_full:
                dimension_name = label
                break

        metric_data.append({
            'MetricName': 'DailyCost',
            'Dimensions': [
                {'Name': 'CostDimension', 'Value': dimension_name},
            ],
            'Timestamp': timestamp,
            'Value':     cost,
            'Unit':      'None',   # CloudWatch has no USD unit; use None
        })

    # Publish in batches of 20 (CloudWatch limit)
    for i in range(0, len(metric_data), 20):
        batch = metric_data[i:i + 20]
        cw.put_metric_data(
            Namespace=METRIC_NAMESPACE,
            MetricData=batch
        )

    total_cost = sum(m['Value'] for m in metric_data)
    print(f"Published {len(metric_data)} metrics. Total RDS cost yesterday: ${total_cost:.4f}")

    return {
        'statusCode': 200,
        'body': json.dumps({
            'metrics_published': len(metric_data),
            'total_cost_usd': round(total_cost, 4)
        })
    }

    2.9 Putting It All Together: An RDS Cost Optimization Runbook

    The preceding sections each address one cost dimension in isolation. In practice, optimization happens as a coordinated sequence of changes. The following runbook consolidates the actions into a repeatable process that a team can execute monthly.

    Cost optimization is a cycle, not a project. Discovery surfaces waste each month, Prioritization ranks fixes by ROI so you work the biggest wins first, Execution applies the changes, and Validation proves the savings landed on the bill. The dashed loop back to Discovery is the point: drift returns within weeks, so the runbook repeats every month.

    Phase 1 — Discovery (Week 1)

    1. Run the Cost Explorer breakdown script from Section 2.1. Record the split across compute, storage, I/O, transfer, and backup.

    2. Run the compute rightsizing script from Section 2.2. Flag all instances with P95 CPU below 20%.

    3. Run the gp2 identification Athena query from Section 2.3. List all gp2 instances ordered by storage size.

    4. Run the snapshot audit script from Section 2.6. List all manual snapshots older than 90 days.

    5. Run the Multi-AZ audit script from Section 2.7. List non-production Multi-AZ instances.

    Phase 2 — Prioritization (Week 1)

    Rank findings by annualized savings potential. A representative priority stack typically looks like:

    | Rank | Action | Typical Annual Savings |

    |---|---|---|

    | 1 | Reserved Instance purchases for stable production instances | Largest absolute value |

    | 2 | gp2 → gp3 migration for high-I/O instances | High, zero risk |

    | 3 | Downsize overprovisioned dev/staging instances | Moderate |

    | 4 | Disable Multi-AZ on non-production | Moderate |

    | 5 | Delete orphaned snapshots | Smaller but immediate |

    | 6 | Stop/start schedules for dev instances | Moderate, ongoing |

    Phase 3 — Execution (Weeks 2–3)

    Execute changes in order of risk, lowest first:

  • → Snapshot deletion requires only CLI access and carries no availability risk
  • → Multi-AZ disablement on non-production is safe during low-traffic periods
  • → gp2 → gp3 migration can be done live with no downtime
  • → Instance class changes require a maintenance window (minutes of downtime)
  • → Reserved Instance purchases are commitment decisions requiring finance approval

    • Phase 4 — Validation (Week 4)

    After changes are applied, validate using the cost dashboard from Section 2.8:

  • → I/O charges should drop to zero for migrated instances
  • → Storage charges should decrease by approximately 30% per migrated volume
  • → Compute charges should reflect the new instance classes within the billing period
  • → Snapshot charges should decrease within 24 hours of deletion

    • Establish a monthly cost review cadence using the runbook. Teams that run this process consistently across a fleet of 30 or more RDS instances typically identify recoverable spending equivalent to several months of engineering time in the first cycle alone.

    2.10 SQL Server Licensing: License-Included vs BYOL — The 70% Line Item

    Every section of this chapter so far has dealt with the smaller half of the RDS for SQL Server bill. On License-Included instances, the SQL Server license embedded in the hourly rate typically represents 50–70% of total instance cost — which means the licensing model decision dwarfs every other optimization in this chapter combined.

    License Included (LI) bundles the SQL Server license into the hourly rate. It is simple — no license tracking, no compliance paperwork — and it is the right choice when you do not own SQL Server licenses, when the workload is short-lived, or when you need an edition (like Enterprise) that you have not licensed. The premium is steep: a db.r6i.2xlarge running SQL Server Standard LI costs roughly $1.75/hour versus about $0.96/hour for the same hardware without the license.

    Bring Your Own License (BYOL) lets you apply existing SQL Server licenses with active Software Assurance (SA) to RDS instances, paying only the underlying compute rate. The same db.r6i.2xlarge drops to roughly $0.96/hour — a saving of about $0.79/hour, or $577/month per instance. Across a fleet of 20 instances, that is $138,000/year in avoided license spend. BYOL requires License Mobility through SA and proper license tracking, but for any organization that already owns SQL Server licenses, it is the single highest-value FinOps action available on AWS.

    The decision framework:

    1. Own licenses with SA and running steady-state workloads? BYOL, always. The payback period on the SA is measured in weeks.

    2. No licenses, or elastic/burst workloads? License Included. The hourly premium is cheaper than buying licenses for capacity you use 30% of the time.

    3. Enterprise Edition features needed? Price both. Enterprise LI carries an enormous premium (often 3–4x Standard); if you own Enterprise licenses with SA, BYOL Enterprise is one of the largest single savings available in cloud FinOps. If you do not, verify the workload genuinely needs Enterprise features — most do not, and Standard LI or BYOL Standard is the answer.

    Two traps to avoid. First, mixing models without tracking: a fleet with some LI and some BYOL instances needs a license position report, or you will either over-buy SA or drift into non-compliance. Tag every instance with license-model (LI or BYOL) and reconcile quarterly against your Microsoft license statement. Second, Reserved Instances on the wrong model: an RI purchased for an LI instance does not transfer cleanly if you later convert to BYOL. Settle the licensing model first, then commit — the same sequencing rule as right-sizing in Chapter 8.

    Key Takeaways

  • → **AWS RDS billing has five independent cost dimensions** — compute, storage, I/O, data transfer, and snapshots — and each requires a distinct optimization strategy. Treating the monthly total as a single opaque number prevents systematic reduction.
  • → **Migrating from gp2 to gp3 storage is the lowest-risk, highest-return action available for most RDS fleets.** gp3 costs approximately 30% less per GB, eliminates all per-I/O charges, and provides higher baseline IOPS. The migration requires no downtime and can be scripted for fleet-wide execution in a single afternoon.
  • → **Reserved Instances applied to stable production workloads typically reduce compute costs by 38–60%** compared to on-demand pricing. For any instance that has run continuously for more than three months, the RI commitment pays for itself within the first few months and the savings compound for the remainder of the term.
  • → **Non-production Multi-AZ and idle-hours compute are the two most common sources of unrecognized waste.** Disabling Multi-AZ on development and staging environments and applying stop/start schedules to instances that run only during business hours can reduce non-production RDS spend by 50–70% without affecting any production workload.
  • → **Cost visibility through a daily metrics pipeline and CloudWatch dashboard converts FinOps from a monthly retrospective into a continuous signal.** An I/O charge alarm that fires the day a gp2 instance starts accumulating excess charges enables same-day remediation rather than a month-end surprise.
