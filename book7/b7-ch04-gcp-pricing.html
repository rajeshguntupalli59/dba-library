Chapter 4: Cloud SQL for SQL Server Pricing Deep Dive

Cloud SQL for SQL Server is the only fully managed SQL Server option on Google Cloud — and it has the most deceptive pricing of any managed SQL Server service. The compute rates look modest until you discover the licensing layer sitting on top of them: SQL Server licensing is billed per vCPU-hour, cannot be covered by committed use discounts, and carries a four-vCPU minimum per instance. A team running three modest Cloud SQL for SQL Server instances — a db-custom-8-32768 production primary, a read replica, and a dev instance — can easily accumulate $9,000/month before anyone realizes that licensing, not compute, is 70–80% of the bill. This chapter breaks down every pricing dimension, the licensing traps that catch teams migrating from other clouds, and how to systematically eliminate waste.

---

4.1 How Cloud SQL for SQL Server Pricing Actually Works

Cloud SQL bills across six independent dimensions. Miss any one of them in your cost model and your forecast will be wrong by a wide margin:

1. Compute (vCPU + RAM) — billed per second with a 10-minute minimum, based on the custom machine type (db-custom-N-MMMM). For Enterprise edition in us-central1, published rates are approximately $0.0706 per vCPU-hour and $0.0118 per GB-hour of memory.

2. SQL Server licensing — billed per core-hour on top of compute: Enterprise $0.47, Standard $0.13, Web $0.01134, Express $0 per core-hour. This is the dimension that dominates the bill.

3. Storage — billed per GB-month on provisioned capacity, SSD or HDD, separate from compute.

4. Backups — automated backup and point-in-time recovery storage beyond the included allowance, approximately $0.11/GB-month.

5. Networking — egress to other regions, other Google products, or the internet.

6. IP address — a small per-hour charge for a public IPv4 address while the instance runs.

Work the math for a db-custom-8-32768 instance (8 vCPU, 32 GB RAM) running SQL Server Enterprise in us-central1 with 500 GB of SSD storage:

Compute:   8 vCPU × $0.0706 × 730h  =   $412/month
Memory:   32 GB   × $0.0118 × 730h  =   $276/month
Licensing: 8 vCPU × $0.47   × 730h  = $2,745/month   ← 78% of the bill
Storage:  500 GB × $0.17/GB-month   =    $85/month
                                          ──────────
Total:                                   ≈ $3,518/month per instance

Read that again: licensing is 78% of the monthly cost. Every FinOps decision on Cloud SQL for SQL Server is primarily a licensing decision wearing a compute costume. Teams that optimize vCPU and memory while ignoring the licensing layer are rearranging deck chairs.

4.2 The Licensing Layer: License-Included Only, and What That Means

Here is the single most important fact about Cloud SQL for SQL Server pricing: it is license-included only — there is no Bring Your Own License (BYOL) option. Unlike Azure (Azure Hybrid Benefit) or AWS EC2 self-managed deployments (License Mobility through Software Assurance), you cannot apply your existing SQL Server licenses to Cloud SQL. If your organization holds Enterprise Agreement licenses with Software Assurance, those licenses sit idle while you pay Google's per-core-hour license rate. This alone can make Cloud SQL for SQL Server the wrong economic choice for license-heavy enterprises — the correct comparison is not Cloud SQL vs RDS license-included, but Cloud SQL license-included vs self-managed SQL Server on Compute Engine where your existing licenses apply.

The four-vCPU minimum. SQL Server licensing requires a core license per vCPU with a four-core minimum per instance. An instance with 2 vCPUs is billed licensing at 4 vCPUs. Run the math on a small dev instance: db-custom-2-7680 on Enterprise is billed $0.47 × 4 × 730 = $1,372/month in licensing alone — before a single byte of compute or storage. Small instances have the worst licensing-to-compute ratio on the platform. This has a direct consequence for right-sizing (Section 4.4): downsizing a 4-vCPU instance to 2 vCPU saves compute but saves zero licensing dollars.

The SMT trick. Disabling simultaneous multithreading (SMT) halves the vCPUs that licensing is calculated against, while compute billing stays on the configured vCPUs. An 8-vCPU instance with SMT disabled is licensed as 4 vCPUs — cutting the Enterprise licensing line from $2,745/month to $1,372/month in the example above, at the cost of some throughput on heavily parallel workloads. For OLTP workloads that rarely saturate all threads, this is close to free money. Test before and after; if P95 query latency is unchanged, keep it.

Edition selection is a pricing decision. Most instances are created on Enterprise by default, and nobody revisits the choice. The per-core-hour rates tell the story: Enterprise $0.47 vs Standard $0.13 vs Web $0.01134 vs Express $0. Moving a workload from Enterprise to Standard cuts the licensing line by 72% — $2,745/month becomes $759/month on the 8-vCPU example. Audit every instance against actual feature usage: if nothing in the workload uses Enterprise-only features (partitioning, online index rebuilds at scale, Always On availability groups beyond basic HA, data compression at scale), downgrade. Web edition at $0.01134/core-hour is purpose-built for public-facing web workloads and is dramatically cheaper than Standard for eligible use.

HA licensing. Regional high-availability instances incur licensing only for the active node — the standby's license is not double-billed. This is one of the few places Cloud SQL for SQL Server is generous, and it makes HA relatively cheaper here than the naive "double everything" mental model suggests.

Committed use discounts do not apply to licensing. CUDs discount vCPU and memory only. A 3-year commitment that cuts compute 52% leaves the $2,745/month licensing line completely untouched. Always model commitments against the compute portion alone — the headline "up to 52% off" applies to roughly a fifth of your actual bill.

4.3 Diagnosing Where Your Money Is Going

Before optimizing, build the diagnostic view. Cloud SQL costs surface in Cloud Billing under several SKUs that do not obviously belong together — compute, license, and storage SKUs for the same instance appear as separate line items. Enable BigQuery billing export, then break the bill down by SKU and label:

-- Monthly cost by SKU group for Cloud SQL for SQL Server
SELECT
  sku.description                              AS sku,
  SUM(cost)                                    AS total_cost,
  SUM(IF(REGEXP_CONTAINS(LOWER(sku.description), r'licen'), cost, 0))
    / SUM(cost)                                AS license_share
FROM `YOUR_PROJECT.billing.gcp_billing_export_v1_XXXXXX`
WHERE service.description = 'Cloud SQL'
  AND usage_start_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
GROUP BY sku.description
ORDER BY total_cost DESC
LIMIT 25;

The license_share column is the diagnostic that matters. If licensing is under 50% of a SQL Server instance's cost, something is unusual — either the instance is massively over-provisioned on compute, or you are looking at Express/Web edition. For Enterprise fleets, expect 65–80%.

Enforce labels at creation time — environment, team, sql-edition — because SKU-level data tells you what is expensive but only labels tell you whose it is. The sql-edition label is worth adding even though edition is technically derivable from the SKU: it makes the "which Enterprise instances could be Standard?" report a one-line query instead of a SKU-mapping exercise.

4.4 Right-Sizing Cloud SQL for SQL Server Instances

Right-sizing on Cloud SQL for SQL Server follows the standard methodology — 30 days of Cloud Monitoring CPU and memory utilization, targeting the 90th percentile rather than the peak — with two SQL Server-specific twists.

Twist one: the licensing floor breaks the usual math. On most platforms, halving vCPUs roughly halves cost. Here, downsizing from 4 vCPU to 2 vCPU saves about $200/month in compute and $0 in licensing — the licensing floor eats the win. The downsizing steps that actually move the licensing line are 8→4 (with SMT disabled, 8→4 licensed cores) and any step that crosses an edition boundary. Always compute the licensing delta of a resize, not just the compute delta, before scheduling the maintenance window.

Twist two: memory deserves respect. SQL Server performance is buffer-pool-bound for most OLTP workloads. An instance showing 15% CPU but 90% memory utilization is not oversized — it is correctly sized, and cutting memory will convert a cheap RAM bill into an expensive I/O and licensing-inefficiency problem. Use Query Store and sys.dm_os_wait_stats to check whether the workload is actually memory-pressured before touching the memory allocation:

-- Top wait types since last restart: is this instance memory- or CPU-bound?
SELECT TOP 10
    wait_type,
    wait_time_ms / 1000.0 AS wait_time_sec,
    100.0 * wait_time_ms / SUM(wait_time_ms) OVER() AS pct
FROM sys.dm_os_wait_stats
WHERE wait_type NOT IN (
  'CLR_SEMAPHORE','LAZYWRITER_SLEEP','RESOURCE_QUEUE','SLEEP_TASK',
  'SLEEP_SYSTEMTASK','SQLTRACE_BUFFER_FLUSH','WAITFOR','XE_DISPATCHER_WAIT')
ORDER BY wait_time_ms DESC;

If PAGEIOLATCH_* and RESOURCE_SEMAPHORE dominate, the instance is starved of memory relative to its working set — downsizing memory will hurt. If SOS_SCHEDULER_YIELD is absent and CPU sits at 12%, the vCPUs (and their $0.47/hour licenses) are the target.

4.5 Storage Optimization: Provisioned Capacity, Backups, and Log Growth

Cloud SQL storage is provisioned-capacity billing: you pay for what you allocate, not what you use, and automatic storage increase only ever grows the allocation. Three storage-side optimizations matter most for SQL Server.

SSD vs HDD. SSD is the default and the right choice for virtually all production SQL Server workloads. HDD exists for archival and rarely-touched instances — but remember that a slow disk on SQL Server converts directly into longer query runtimes, which on a per-second-billed compute model with per-core licensing is the most expensive kind of savings. Only move to HDD when the instance is genuinely cold.

Backup storage beyond the free allowance. Automated backups run daily, and point-in-time recovery retains transaction log backups on top. Backup storage is approximately $0.11/GB-month beyond the included allowance, and PITR log retention typically adds 20–40% on top of the snapshot volume. A 30-day retention policy on a 500 GB database with moderate churn can accumulate 2–3 TB of backup data at $220–$330/month. Right-size the retention window to the actual RPO: if the business RPO is 24 hours, a 30-day backup retention is not a recovery strategy, it is a storage donation.

Transaction log growth is a storage cost. SQL Server's transaction log grows with uncommitted and unreplicated transactions, long-running open transactions, and infrequent log backups. On Cloud SQL, log backups for PITR run frequently, but a single runaway transaction — an ETL job that opens a transaction and then waits on an external API for six hours — can balloon the log and trigger automatic storage increase, permanently raising the provisioned capacity. Monitor log_reuse_wait_desc in sys.databases and alert on anything other than LOG_BACKUP persisting for more than an hour.

4.6 Reducing I/O Costs Through Query Optimization

Cloud SQL for SQL Server does not charge per I/O the way some storage architectures do — but I/O inefficiency still bills you, laundered through compute. Every missing index that forces a full scan burns vCPU-seconds at $0.0706/hour plus $0.47/hour in licensing on Enterprise. Query tuning is licensing optimization.

Enable Query Store (it is on by default for Cloud SQL for SQL Server) and pull the top resource consumers weekly:

-- Top 20 queries by total CPU: the licensing-burn leaderboard
SELECT TOP 20
    q.query_id,
    SUM(rs.count_executions)                       AS executions,
    SUM(rs.avg_cpu_time * rs.count_executions)/1e6 AS total_cpu_sec,
    MAX(t.query_sql_text)                          AS sample_text
FROM sys.query_store_query q
JOIN sys.query_store_plan p   ON q.query_id = p.query_id
JOIN sys.query_store_runtime_stats rs ON p.plan_id = rs.plan_id
JOIN sys.query_store_query_text t ON q.query_text_id = t.query_text_id
WHERE rs.last_execution_time > DATEADD(day, -7, SYSUTCDATETIME())
GROUP BY q.query_id
ORDER BY total_cpu_sec DESC;

The standard hits apply: add the missing indexes the engine is already recommending (sys.dm_db_missing_index_details), rewrite non-SARGable predicates that defeat index seeks, and parameterize the ad-hoc query storms that bloat the plan cache. Each query you take off this leaderboard reduces the vCPU-hours — and therefore the licensed vCPU-hours — the workload needs.

4.7 Network Egress Cost Reduction

Egress from Cloud SQL follows standard Google Cloud networking rates: free within the same zone/region to Compute Engine in most configurations, $0.12/GB between regions in North America, and $0.19/GB to the internet. Two patterns drive most of the egress bill.

Cross-region application placement. An application tier in us-east1 chatting with a database in us-central1 pays $0.12/GB on every result set. At 500 GB/month of query traffic, that is $60/month of pure placement tax — and it adds latency that makes the application open more connections, which increases memory pressure, which pushes you toward a larger instance. Co-locate the app tier with the database; it is the rare optimization that improves both cost and latency.

Cross-region read replicas. A read replica in another region pays the full instance cost plus the replication egress. Before deploying one for "reporting," check whether the reporting workload can run against a scheduled export to BigQuery instead — BigQuery storage is an order of magnitude cheaper than a running replica, and the replica's licensing line ($0.47/core-hour on Enterprise) does not pause when the report is not running.

4.8 Committed Use Discounts: Strategy and Gotchas

Committed use discounts for Cloud SQL cover vCPU and memory: roughly 25% off for a 1-year commitment and up to 52% for 3 years on Enterprise compute. The strategy is straightforward; the gotchas are where teams lose money.

Gotcha one: commitments are resource-based, not instance-based. A commitment for 16 vCPUs in us-central1 covers any combination of Cloud SQL instances in that project and region summing to 16 vCPU — two 8-vCPU instances, four 4-vCPU instances, or one 16-vCPU instance. This flexibility is your friend: commit to the aggregate steady-state vCPU count across the fleet, not per instance, and let instances scale within the envelope.

Gotcha two: commit after right-sizing, never before. A commitment locks the compute baseline for 1–3 years. Committing to the pre-right-sizing footprint bakes the waste into a contract. Sequence: right-size (Section 4.4), run one full billing cycle to validate, then commit to the validated baseline.

Gotcha three: the licensing exclusion changes the ROI math. Because CUDs do not touch the licensing line — 65–80% of the bill — a "52% discount" on a Cloud SQL for SQL Server Enterprise instance is roughly a 10–15% discount on the total bill. Model commitments against compute-only spend, and compare the committed total against the alternative of moving the workload to a platform where your existing licenses apply (Compute Engine with License Mobility, or Azure with Hybrid Benefit). For license-heavy estates, the platform decision dwarfs the commitment decision.

4.9 Terraform Patterns and Ongoing Cost Control

Point-in-time optimizations erode without guardrails. Encode the cost policy in the provisioning path so the next instance is born optimized:

resource "google_sql_database_instance" "orders" {
  name             = "orders-prod"
  database_version = "SQLSERVER_2019_ENTERPRISE"
  region           = "us-central1"
  deletion_protection = true

  settings {
    tier              = "db-custom-8-32768"   # approved tier for prod OLTP
    edition           = "ENTERPRISE"
    availability_type = "REGIONAL"            # HA: standby license not billed

    backup_configuration {
      enabled                        = true
      point_in_time_recovery_enabled = true
      backup_retention_settings {
        retained_backups = 7               # match the 7-day RPO, not 30
      }
    }

    insights_config {
      query_insights_enabled = true         # Query Store-backed diagnostics
    }

    user_labels = {
      environment  = "prod"
      team         = "orders"
      sql-edition  = "enterprise"          # feeds the edition-downgrade report
      cost-center  = "cc-1042"
    }
  }
}

Layer three ongoing controls on top. First, a Cloud Billing budget alert at 50%, 90%, and 100% of expected monthly spend, routed to the team channel — not to an unread distribution list. Second, a weekly scheduled query against the BigQuery billing export that recomputes the license-share diagnostic from Section 4.3 and flags any instance whose edition label says enterprise while its Query Store shows no Enterprise-feature usage. Third, a quarterly edition-and-tier review: workloads change, and the Enterprise instance that was justified eighteen months ago may be a Standard workload today. The review takes an hour; the downgrade saves thousands per month per instance.

---

Key Takeaways

  • → **Licensing is the bill**: On Cloud SQL for SQL Server Enterprise, per-core-hour licensing ($0.47) typically represents 65–80% of total instance cost. Every optimization should be evaluated on its licensing delta first and its compute delta second — including right-sizing, where the four-vCPU licensing floor means small downsizes can save nothing at all.
  • → **There is no BYOL on Cloud SQL**: License-included is the only option, so existing SQL Server licenses with Software Assurance cannot be applied. For license-heavy estates, compare Cloud SQL against Compute Engine self-managed (License Mobility) or Azure Hybrid Benefit before committing — the platform decision dwarfs any discount.
  • → **Edition selection is the highest-leverage single change**: Moving a workload from Enterprise ($0.47/core-hour) to Standard ($0.13) cuts the licensing line by 72%. Audit every instance against actual Enterprise feature usage; most Standard-eligible workloads are sitting on Enterprise by historical accident.
  • → **Committed use discounts cover compute only**: The headline 52% three-year discount applies to roughly a fifth of a SQL Server bill. Commit to the aggregate right-sized vCPU footprint after validation, and model the ROI against compute-only spend — never the total bill.
  • → **Guardrails beat one-time cleanups**: Approved tiers, mandatory cost labels, backup retention matched to the real RPO, and a weekly license-share report keep the savings permanent. Without them, the next provisioned instance quietly reintroduces every inefficiency you just removed.
