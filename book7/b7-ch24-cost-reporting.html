Chapter 24: Per-Team, Per-App, Per-Feature Cost Reporting

Organizations that implement granular cost reporting—breaking cloud database spend down to the team, application, and feature level—consistently identify 20–35% in previously invisible waste within the first 90 days. The mechanism is straightforward: when a team can see that their recommendation engine's nightly batch job costs $4,200/month while the feature drives less than $800/month in attributed revenue, the conversation about optimization practically has itself. This chapter covers how to build that attribution layer from scratch across AWS RDS, Azure SQL, and Google Cloud SQL, including the tagging taxonomy, the cost allocation queries, the dashboard pipelines, and the automated weekly reports that land in engineering leads' inboxes without anyone having to run a manual export.

---

24.1 Building a Tagging Taxonomy That Actually Works

The failure mode for most tagging initiatives is starting with too many tags and enforcing none of them. Production environments end up with 40% of resources untagged, and the cost attribution reports are immediately discredited because the numbers don't add up.

A workable minimum taxonomy for database cost attribution uses exactly five tags:

| Tag Key | Example Values | Purpose |

|---|---|---|

| team | payments, ml-platform, core-api | Charge back to engineering team |

| app | checkout-service, fraud-detector | Charge back to application |

| environment | prod, staging, dev | Separate production from non-production spend |

| feature | recommendations, search, auth | Feature-level attribution |

| cost-center | cc-1042, cc-2017 | Finance system integration |

The feature tag is optional for initial rollout. Add it when teams are ready to instrument individual workloads. Forcing feature-level tagging prematurely creates inconsistent data that undermines trust in the entire system.

Enforcing tags at resource creation is non-negotiable. Resources that exist without tags accumulate cost in an unattributed bucket that grows until someone gets angry about it in a budget review.

Handling the untagged backlog is a common stumbling block. The pragmatic approach is to run a quarterly tagging sprint. Pull all untagged resources, assign them to account owners based on VPC or subnet membership, and have those owners tag within 30 days or face a chargeback to a shared pool. The shared pool penalty is the behavioral incentive that makes the tagging sprint work.

24.2 Extracting Per-Team Cost Data from Each Cloud Provider

Once tags are in place, the next step is extracting cost data in a form that can be joined, aggregated, and reported. Each cloud provider exposes this differently, and the approach that works across all three is to land the data in a common schema in your data warehouse or an S3/GCS/Azure Blob bucket.

AWS Cost Explorer with Tag Filtering

#!/usr/bin/env python3
"""
Pull per-team RDS costs from AWS Cost Explorer and write to a SQL Server
reporting database. Designed to run on a weekly schedule via Lambda or cron.

Requirements: boto3, pyodbc, python-dateutil
"""

import boto3
import pyodbc
import json
from datetime import datetime, timedelta, timezone
from dateutil.relativedelta import relativedelta
import logging

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)

# Configuration
REPORTING_DB_CONN = (
    "DRIVER={ODBC Driver 18 for SQL Server};"
    "SERVER=reporting-db.internal,1433;DATABASE=finops;"
    "UID=finops_writer;PWD=REPLACE;"
    "Encrypt=yes;TrustServerCertificate=no;"
)
AWS_ACCOUNT_ID = "123456789012"
REGION = "us-east-1"

def get_rds_costs_by_team(start_date: str, end_date: str) -> list[dict]:
    """
    Query Cost Explorer for RDS costs grouped by team tag.
    Returns list of dicts with team, service, cost, and usage_type.
    """
    client = boto3.client("ce", region_name="us-east-1")
    
    response = client.get_cost_and_usage(
        TimePeriod={
            "Start": start_date,
            "End": end_date
        },
        Granularity="MONTHLY",
        Filter={
            "And": [
                {
                    "Dimensions": {
                        "Key": "SERVICE",
                        "Values": [
                            "Amazon Relational Database Service"
                        ]
                    }
                },
                {
                    "Not": {
                        "Dimensions": {
                            "Key": "RECORD_TYPE",
                            "Values": ["Credit", "Refund"]
                        }
                    }
                }
            ]
        },
        GroupBy=[
            {"Type": "TAG", "Key": "team"},
            {"Type": "TAG", "Key": "app"},
            {"Type": "DIMENSION", "Key": "USAGE_TYPE"}
        ],
        Metrics=["UnblendedCost", "UsageQuantity"]
    )
    
    results = []
    for time_period in response["ResultsByTime"]:
        period_start = time_period["TimePeriod"]["Start"]
        for group in time_period["Groups"]:
            keys = group["Keys"]
            # Keys order: team tag, app tag, usage_type
            team_raw = keys[0] if len(keys) > 0 else ""
            app_raw = keys[1] if len(keys) > 1 else ""
            usage_type = keys[2] if len(keys) > 2 else ""
            
            # Strip the tag key prefix that Cost Explorer adds
            team = team_raw.replace("team$", "") or "untagged"
            app = app_raw.replace("app$", "") or "untagged"
            
            cost = float(group["Metrics"]["UnblendedCost"]["Amount"])
            usage = float(group["Metrics"]["UsageQuantity"]["Amount"])
            unit = group["Metrics"]["UsageQuantity"]["Unit"]
            
            if cost > 0:
                results.append({
                    "period_start": period_start,
                    "team": team,
                    "app": app,
                    "usage_type": usage_type,
                    "cost_usd": round(cost, 4),
                    "usage_quantity": round(usage, 4),
                    "usage_unit": unit,
                    "account_id": AWS_ACCOUNT_ID,
                    "extracted_at": datetime.now(timezone.utc).isoformat()
                })
    
    logger.info(f"Extracted {len(results)} cost records for period {start_date} to {end_date}")
    return results


def get_rds_costs_by_feature(start_date: str, end_date: str) -> list[dict]:
    """
    Query Cost Explorer for RDS costs grouped by feature tag.
    Use this for feature-level attribution where teams have instrumented
    their workloads with the 'feature' tag.
    """
    client = boto3.client("ce", region_name="us-east-1")
    
    response = client.get_cost_and_usage(
        TimePeriod={"Start": start_date, "End": end_date},
        Granularity="MONTHLY",
        Filter={
            "Dimensions": {
                "Key": "SERVICE",
                "Values": ["Amazon Relational Database Service"]
            }
        },
        GroupBy=[
            {"Type": "TAG", "Key": "team"},
            {"Type": "TAG", "Key": "feature"},
        ],
        Metrics=["UnblendedCost"]
    )
    
    results = []
    for time_period in response["ResultsByTime"]:
        period_start = time_period["TimePeriod"]["Start"]
        for group in time_period["Groups"]:
            keys = group["Keys"]
            team = keys[0].replace("team$", "") or "untagged"
            feature = keys[1].replace("feature$", "") or "untagged"
            cost = float(group["Metrics"]["UnblendedCost"]["Amount"])
            
            if cost > 0:
                results.append({
                    "period_start": period_start,
                    "team": team,
                    "feature": feature,
                    "cost_usd": round(cost, 4),
                    "account_id": AWS_ACCOUNT_ID
                })
    
    return results


def upsert_team_costs(records: list[dict]) -> None:
    """Write team cost records to the reporting database."""
    if not records:
        logger.warning("No records to write")
        return
    
    conn = pyodbc.connect(REPORTING_DB_CONN)
    cur = conn.cursor()

    # Ensure the table exists
    cur.execute("""
        IF OBJECT_ID('dbo.db_team_costs', 'U') IS NULL
        CREATE TABLE dbo.db_team_costs (
            id             INT IDENTITY(1,1) PRIMARY KEY,
            period_start   DATE NOT NULL,
            team           NVARCHAR(128) NOT NULL,
            app            NVARCHAR(128) NOT NULL,
            usage_type     NVARCHAR(256) NOT NULL,
            cost_usd       NUMERIC(12,4) NOT NULL,
            usage_quantity NUMERIC(16,4),
            usage_unit     NVARCHAR(64),
            account_id     NVARCHAR(32),
            extracted_at   DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
            CONSTRAINT uq_db_team_costs UNIQUE (period_start, team, app, usage_type, account_id)
        )
    """)
    
    upsert_sql = """
        MERGE dbo.db_team_costs AS tgt
        USING (SELECT ? AS period_start, ? AS team, ? AS app,
                      ? AS usage_type, ? AS cost_usd, ? AS usage_quantity,
                      ? AS usage_unit, ? AS account_id, ? AS extracted_at) AS src
        ON tgt.period_start = src.period_start
           AND tgt.team = src.team
           AND tgt.app = src.app
           AND tgt.usage_type = src.usage_type
           AND tgt.account_id = src.account_id
        WHEN MATCHED THEN
            UPDATE SET cost_usd = src.cost_usd,
                       usage_quantity = src.usage_quantity,
                       extracted_at = src.extracted_at
        WHEN NOT MATCHED THEN
            INSERT (period_start, team, app, usage_type, cost_usd,
                    usage_quantity, usage_unit, account_id, extracted_at)
            VALUES (src.period_start, src.team, src.app, src.usage_type,
                    src.cost_usd, src.usage_quantity, src.usage_unit,
                    src.account_id, src.extracted_at);
    """

    rows = [(r["period_start"], r["team"], r["app"], r["usage_type"],
             r["cost_usd"], r["usage_quantity"], r["usage_unit"],
             r["account_id"], r["extracted_at"]) for r in records]
    cur.executemany(upsert_sql, rows)
    conn.commit()
    cur.close()
    conn.close()
    logger.info(f"Upserted {len(records)} records into db_team_costs")


if __name__ == "__main__":
    # Pull the previous full month
    today = datetime.today()
    first_of_this_month = today.replace(day=1)
    first_of_last_month = first_of_this_month - relativedelta(months=1)
    
    start = first_of_last_month.strftime("%Y-%m-%d")
    end = first_of_this_month.strftime("%Y-%m-%d")
    
    logger.info(f"Pulling RDS costs from {start} to {end}")
    
    team_records = get_rds_costs_by_team(start, end)
    upsert_team_costs(team_records)
    
    feature_records = get_rds_costs_by_feature(start, end)
    # Feature costs go into a separate table with the same pattern
    logger.info(f"Feature-level records: {len(feature_records)}")

24.3 Database-Level Attribution with Query Store

Tags cover the infrastructure cost—instance hours, storage, I/O. But they cannot tell you which feature's queries are consuming 60% of your RDS for SQL Server instance's CPU. For that, you need query-level attribution using Query Store or sys.dm_exec_query_stats on SQL Server. This is the layer that connects infrastructure cost to application behavior.

The pattern is to add a comment to every query at the application layer that embeds team and feature metadata. Query Store captures the full query text including comments in sys.query_store_query_text, so they can be parsed out.

Application code wraps queries like this:

-- Pattern: prefix queries with a structured comment
-- /* app:checkout-service team:payments feature:cart-totals */
SELECT p.product_id, p.price, i.quantity
FROM products p
JOIN inventory i ON p.product_id = i.product_id
/* app:checkout-service team:payments feature:cart-totals */
WHERE p.product_id = ANY($1);

With that convention in place, extract per-feature query costs from SQL Server:

The equivalent attribution query for SQL Server uses sys.dm_exec_query_stats paired with sys.dm_exec_sql_text to retrieve the query text, then parses the embedded comment:

-- SQL Server: Per-team query cost attribution using dm_exec_query_stats
-- Works on RDS for SQL Server, Azure SQL Database, and SQL Server on GCE

WITH query_text AS (
    SELECT
        qs.sql_handle,
        qs.query_hash,
        qs.total_elapsed_time,         -- microseconds
        qs.execution_count,
        qs.total_logical_reads,
        qs.total_logical_writes,
        qs.total_worker_time,          -- CPU microseconds
        qs.total_rows,
        SUBSTRING(
            st.text,
            (qs.statement_start_offset / 2) + 1,
            ((CASE qs.statement_end_offset
                WHEN -1 THEN DATALENGTH(st.text)
                ELSE qs.statement_end_offset
              END - qs.statement_start_offset) / 2) + 1
        ) AS statement_text
    FROM sys.dm_exec_query_stats AS qs
    CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS st
    WHERE st.text NOT LIKE '%dm_exec%'
),
parsed AS (
    SELECT
        query_hash,
        total_elapsed_time,
        execution_count,
        total_logical_reads,
        total_worker_time,
        -- Extract team tag from comment pattern /* team:X */
        COALESCE(
            (SELECT TOP 1 m.match
             FROM (
                 SELECT value AS match
                 FROM STRING_SPLIT(statement_text, ' ')
             ) m
             WHERE m.match LIKE 'team:%'
            ),
            'untagged'
        ) AS team_raw,
        -- Simpler pattern: use PATINDEX + SUBSTRING for SQL Server compatibility
        CASE
            WHEN statement_text LIKE '%team:%'
            THEN SUBSTRING(
                    statement_text,
                    PATINDEX('%team:%', statement_text) + 5,
                    CHARINDEX(' ', statement_text + ' ',
                        PATINDEX('%team:%', statement_text) + 5)
                    - PATINDEX('%team:%', statement_text) - 5
                 )
            ELSE 'untagged'
        END AS team,
        CASE
            WHEN statement_text LIKE '%feature:%'
            THEN SUBSTRING(
                    statement_text,
                    PATINDEX('%feature:%', statement_text) + 8,
                    CHARINDEX(' ', statement_text + ' ',
                        PATINDEX('%feature:%', statement_text) + 8)
                    - PATINDEX('%feature:%', statement_text) - 8
                 )
            ELSE 'untagged'
        END AS feature,
        CASE
            WHEN statement_text LIKE '%app:%'
            THEN SUBSTRING(
                    statement_text,
                    PATINDEX('%app:%', statement_text) + 4,
                    CHARINDEX(' ', statement_text + ' ',
                        PATINDEX('%app:%', statement_text) + 4)
                    - PATINDEX('%app:%', statement_text) - 4
                 )
            ELSE 'untagged'
        END AS app,
        -- Cost proxy: CPU time + weighted logical reads
        (total_worker_time + (total_logical_reads * 8.0)) AS cost_proxy,
        LEFT(LTRIM(RTRIM(REPLACE(statement_text, CHAR(10), ' '))), 120) AS query_fingerprint
    FROM query_text
),
totals AS (
    SELECT SUM(cost_proxy) AS total_proxy FROM parsed
),
attribution AS (
    SELECT
        team,
        app,
        feature,
        COUNT(DISTINCT query_hash)          AS distinct_queries,
        SUM(execution_count)                AS total_executions,
        ROUND(SUM(total_elapsed_time) / 1e6, 2) AS total_elapsed_seconds,
        ROUND(SUM(total_worker_time) / 1e6, 2)  AS total_cpu_seconds,
        SUM(total_logical_reads)            AS total_logical_reads,
        ROUND(SUM(cost_proxy), 2)           AS team_cost_proxy,
        ROUND(
            SUM(cost_proxy) / NULLIF((SELECT total_proxy FROM totals), 0) * 100,
            2
        ) AS pct_of_total
    FROM parsed
    GROUP BY team, app, feature
)
SELECT
    team,
    app,
    feature,
    distinct_queries,
    total_executions,
    total_elapsed_seconds,
    total_cpu_seconds,
    total_logical_reads,
    team_cost_proxy,
    pct_of_total,
    -- Replace 4800.00 with actual monthly cost of this SQL Server instance
    ROUND(pct_of_total / 100.0 * 4800.00, 2) AS estimated_monthly_usd
FROM attribution
ORDER BY pct_of_total DESC;

The estimated_monthly_usd column is only as accurate as the base cost you supply. Pull the actual monthly instance cost from the billing extraction scripts in section 24.2 and substitute it here. When you join both layers—infrastructure billing data from the cloud provider and query-level attribution from Query Store or sys.dm_exec_query_stats—you get a complete picture: the team's total database spend, and which of their features and queries are responsible for it.

24.4 Building the Cost Attribution Schema

The billing extracts and query attribution data both need to land somewhere before they can feed a dashboard. A simple star schema in SQL Server handles this well and works whether your reporting database is on RDS, Azure SQL, Cloud SQL, or a self-managed instance.

-- SQL Server: create the cost attribution reporting schema
-- This schema stores both infrastructure costs (from billing APIs)
-- and query-level costs (from Query Store snapshots)

IF SCHEMA_ID('finops') IS NULL EXEC('CREATE SCHEMA finops');

-- Dimension: teams
IF OBJECT_ID('finops.dim_teams', 'U') IS NULL
CREATE TABLE finops.dim_teams (
    team_id     INT IDENTITY(1,1) PRIMARY KEY,
    team_slug   NVARCHAR(100) NOT NULL UNIQUE,  -- e.g. 'payments', 'ml-platform'
    team_name   NVARCHAR(200) NOT NULL,
    cost_center NVARCHAR(50),
    lead_email  NVARCHAR(200),
    created_at  DATETIME2 DEFAULT SYSDATETIME()
);

-- Dimension: applications
IF OBJECT_ID('finops.dim_apps', 'U') IS NULL
CREATE TABLE finops.dim_apps (
    app_id      INT IDENTITY(1,1) PRIMARY KEY,
    app_slug    NVARCHAR(100) NOT NULL UNIQUE,  -- e.g. 'checkout-service'
    app_name    NVARCHAR(200) NOT NULL,
    team_id     INT REFERENCES finops.dim_teams(team_id),
    repo_url    NVARCHAR(500),
    created_at  DATETIME2 DEFAULT SYSDATETIME()
);

-- Dimension: features
IF OBJECT_ID('finops.dim_features', 'U') IS NULL
CREATE TABLE finops.dim_features (
    feature_id   INT IDENTITY(1,1) PRIMARY KEY,
    feature_slug NVARCHAR(100) NOT NULL,
    app_id       INT REFERENCES finops.dim_apps(app_id),
    description  NVARCHAR(500),
    created_at   DATETIME2 DEFAULT SYSDATETIME(),
    UNIQUE (feature_slug, app_id)
);

-- Dimension: database instances
IF OBJECT_ID('finops.dim_db_instances', 'U') IS NULL
CREATE TABLE finops.dim_db_instances (
    instance_id      INT IDENTITY(1,1) PRIMARY KEY,
    provider         NVARCHAR(20) NOT NULL CHECK (provider IN ('aws', 'azure', 'gcp')),
    account_id       NVARCHAR(100),        -- AWS account, Azure subscription, GCP project
    region           NVARCHAR(50),
    instance_identifier NVARCHAR(200) NOT NULL,
    engine           NVARCHAR(50),        -- sqlserver
    instance_class   NVARCHAR(50),        -- db.r5.2xlarge, etc.
    environment      NVARCHAR(20),        -- prod, staging, dev
    team_id          INT REFERENCES finops.dim_teams(team_id),
    app_id           INT REFERENCES finops.dim_apps(app_id),
    monthly_base_cost_usd NUMERIC(12,2),  -- updated monthly from billing extract
    created_at       DATETIME2 DEFAULT SYSDATETIME(),
    UNIQUE (provider, account_id, instance_identifier)
);

-- Fact: infrastructure costs by team/app from cloud billing APIs
IF OBJECT_ID('finops.fact_infra_costs', 'U') IS NULL
CREATE TABLE finops.fact_infra_costs (
    id              BIGINT IDENTITY(1,1) PRIMARY KEY,
    period_start    DATE NOT NULL,
    period_end      DATE NOT NULL,
    provider        NVARCHAR(20) NOT NULL CHECK (provider IN ('aws', 'azure', 'gcp')),
    account_id      NVARCHAR(100),
    team_id         INT REFERENCES finops.dim_teams(team_id),
    app_id          INT REFERENCES finops.dim_apps(app_id),
    instance_id     INT REFERENCES finops.dim_db_instances(instance_id),
    cost_category   NVARCHAR(50),  -- ComputeUsage, StorageUsage, IOUsage, DataTransfer, Backup
    cost_usd        NUMERIC(14,4) NOT NULL,
    usage_quantity  NUMERIC(16,4),
    usage_unit      NVARCHAR(50),
    extracted_at    DATETIME2 DEFAULT SYSDATETIME(),
    UNIQUE (period_start, provider, account_id, team_id, app_id, cost_category)
);

-- Fact: query-level cost attribution from Query Store snapshots

-- SQL Server: Monthly infrastructure cost rollup per team with MoM trend
-- Run against the finops reporting database

WITH monthly_costs AS (
    SELECT
        DATETRUNC(month, fic.period_start) AS month,
        dt.team_slug,
        dt.team_name,
        dt.lead_email,
        SUM(fic.cost_usd) AS total_cost_usd
    FROM finops.fact_infra_costs fic
    JOIN finops.dim_teams dt ON fic.team_id = dt.team_id
    WHERE fic.period_start >= DATETRUNC(month, DATEADD(month, -3, SYSDATETIME()))
    GROUP BY DATETRUNC(month, fic.period_start), dt.team_slug, dt.team_name, dt.lead_email
),
with_trend AS (
    SELECT
        month,
        team_slug,
        team_name,
        lead_email,
        total_cost_usd,
        LAG(total_cost_usd) OVER (
            PARTITION BY team_slug ORDER BY month
        ) AS prior_month_cost_usd
    FROM monthly_costs
)
SELECT
    month,
    team_slug,
    team_name,
    lead_email,
    ROUND(total_cost_usd, 2)        AS total_cost_usd,
    ROUND(prior_month_cost_usd, 2)  AS prior_month_cost_usd,
    ROUND(
        CASE
            WHEN prior_month_cost_usd IS NULL OR prior_month_cost_usd = 0 THEN NULL
            ELSE ((total_cost_usd - prior_month_cost_usd) / prior_month_cost_usd) * 100
        END, 1
    )                               AS mom_change_pct
FROM with_trend
ORDER BY month DESC, total_cost_usd DESC;

24.5 Automated Weekly Cost Digest Emails

The most effective forcing function for cost awareness is a weekly email that lands in an engineering lead's inbox without requiring any action on their part. The email answers three questions: what did my team spend on databases this week, how does that compare to last week, and which specific queries or instances are driving the biggest costs. The goal is to surface the information at the moment it is most actionable—before it becomes a budget overrun problem at the end of the month.

Requirements: pyodbc, boto3 (for SES), jinja2

def send_ses_email(to_address: str, subject: str, html_body: str) -> None:
    client = boto3.client("ses", region_name=SES_REGION)
    client.send_email(
        Source=FROM_EMAIL,
        Destination={"ToAddresses": [to_address]},
        Message={
            "Subject": {"Data": subject, "Charset": "UTF-8"},
            "Body": {"Html": {"Data": html_body, "Charset": "UTF-8"}}
        }
    )
    logger.info(f"Email sent to {to_address}")


def run_weekly_digest() -> None:
    today = datetime.now(timezone.utc).date()
    # Week runs Mon–Sun; send on Monday covering the prior Mon–Sun
    week_end = today - timedelta(days=today.weekday())          # this Monday
    week_start = week_end - timedelta(days=7)                   # last Monday
    prior_week_start = week_start - timedelta(days=7)
    prior_week_end = week_start

    params = {
        "week_start": week_start.isoformat(),
        "week_end": week_end.isoformat(),
        "prior_week_start": prior_week_start.isoformat(),
        "prior_week_end": prior_week_end.isoformat(),
    }

    conn = pyodbc.connect(REPORTING_DB_CONN)
    cur = conn.cursor()

    def _rows_as_dicts(cursor):
        cols = [d[0] for d in cursor.description]
        return [dict(zip(cols, row)) for row in cursor.fetchall()]

    cur.execute(TEAM_WEEKLY_SQL, (
        params["week_start"], params["week_end"],
        params["prior_week_start"], params["prior_week_end"],
    ))
    teams = _rows_as_dicts(cur)
    logger.info(f"Sending digests to {len(teams)} team leads")

    template = Template(EMAIL_TEMPLATE)
    generated_at = datetime.now(timezone.utc).strftime("%Y-%m-%d %H:%M UTC")

    for team in teams:
        # Fetch top instances for this team
        cur.execute(TOP_INSTANCES_SQL, (
            team["team_slug"],
            week_start.isoformat(),
            week_end.isoformat(),
        ))
        top_instances = _rows_as_dicts(cur)

        # Fetch top queries for this team
        cur.execute(TOP_QUERIES_SQL, (
            team["team_slug"],
            week_start.isoformat(),
            week_end.isoformat(),
        ))
        top_queries = _rows_as_dicts(cur)

        html_body = template.render(
            team_name=team["team_name"],
            team_slug=team["team_slug"],
            week_start=week_start.isoformat(),
            generated_at=generated_at,
            week_cost=team["week_cost"],
            wow_change_pct=team["wow_change_pct"],
            top_instances=top_instances,
            top_queries=top_queries,
            currency=CURRENCY_SYMBOL,
        )

        subject = (
            f"DB Cost Digest – {team['team_name']} – "
            f"${team['week_cost']} this week"
        )
        send_ses_email(team["lead_email"], subject, html_body)

    cur.close()
    conn.close()
    logger.info("Weekly digest run complete")


if __name__ == "__main__":
    run_weekly_digest()

24.6 Grafana Dashboard for Per-Team Cost Visibility

The weekly email is the push mechanism. The Grafana dashboard is the pull mechanism—what engineering leads open when they want to investigate a spike or prepare for a budget conversation. The dashboard should answer five questions without clicking through multiple panels: how much is my team spending this month, what is the trend over the past 90 days, which instances are consuming most of the budget, which features are the most expensive at the query level, and which queries have degraded in performance or cost since last week.

The following panel definitions assume the finops SQL Server reporting database defined in section 24.4 as a Grafana data source named finops-db.

-- Grafana Panel 1: Total monthly spend by team (bar chart, last 6 months)
-- Variable: $team (multi-value, populated from dim_teams.team_slug)

SELECT

-- Grafana Panel 3: Top 10 most expensive instances for this team (table panel)

OFFSET 0 ROWS FETCH NEXT 10 ROWS ONLY;


-- Grafana Panel 4: Feature-level query cost breakdown (pie chart or bar)

SELECT
    COALESCE(df.feature_slug, 'untagged') AS feature,
    ROUND(SUM(fqc.estimated_cost_usd), 2) AS estimated_cost_usd
FROM finops.fact_query_costs fqc

-- Grafana Panel 5: Week-over-week query cost change (table with threshold coloring)
-- Highlight queries that have increased cost by more than 20%

WITH this_week AS (
    SELECT
        fqc.queryid,
        fqc.query_fingerprint,
        COALESCE(df.feature_slug, 'untagged') AS feature,
        SUM(fqc.estimated_cost_usd) AS cost_this_week,
        AVG(fqc.mean_exec_ms)       AS avg_exec_ms_this_week
    FROM finops.fact_query_costs fqc
    JOIN finops.dim_teams dt ON fqc.team_id = dt.team_id
    LEFT JOIN finops.dim_features df ON fqc.feature_id = df.feature_id
    WHERE dt.team_slug = '$team'
      AND fqc.snapshot_ts >= DATEADD(day, -7, SYSDATETIME())
    GROUP BY fqc.queryid, fqc.query_fingerprint, COALESCE(df.feature_slug, 'untagged')
),
last_week AS (
    SELECT
        fqc.queryid,
        SUM(fqc.estimated_cost_usd) AS cost_last_week,
        AVG(fqc.mean_exec_ms)       AS avg_exec_ms_last_week
    FROM finops.fact_query_costs fqc
    JOIN finops.dim_teams dt ON fqc.team_id = dt.team_id
    WHERE dt.team_slug = '$team'
      AND fqc.snapshot_ts >= DATEADD(day, -14, SYSDATETIME())
      AND fqc.snapshot_ts <  DATEADD(day, -7, SYSDATETIME())
    GROUP BY fqc.queryid
)
SELECT
    tw.feature,
    tw.query_fingerprint,
    ROUND(tw.cost_this_week, 4)                 AS cost_this_week_usd,
    ROUND(lw.cost_last_week, 4)                 AS cost_last_week_usd,
    ROUND(tw.avg_exec_ms_this_week, 2) AS avg_ms_this_week,
    ROUND(lw.avg_exec_ms_last_week, 2) AS avg_ms_last_week,
    ROUND(
        CASE
            WHEN lw.cost_last_week = 0 OR lw.cost_last_week IS NULL THEN NULL
            ELSE ((tw.cost_this_week - lw.cost_last_week) / lw.cost_last_week * 100)
        END, 1
    ) AS wow_cost_change_pct
FROM this_week tw
LEFT JOIN last_week lw ON tw.queryid = lw.queryid
ORDER BY cost_this_week_usd DESC
LIMIT 20;

For the week-over-week panel, set a Grafana threshold on wow_cost_change_pct: green below 10, yellow between 10 and 25, red above 25. This turns the table into a quick triage view—engineering leads can scan for red rows and immediately see which queries to hand to their team for optimization.

Dashboard variable configuration worth noting: the $team variable should be backed by this query against the finops database:

-- Grafana variable query: populate $team dropdown
SELECT DISTINCT team_slug AS __value, team_name AS __text
FROM finops.dim_teams

24.7 Handling Shared Infrastructure and Allocation Splits

Not all database costs map cleanly to a single team. A shared RDS for SQL Server instance used by three services, a central ElastiCache cluster, or a data warehouse instance accessed by both the analytics team and the product team all present the same challenge: the billing tag can only carry one value, but the cost needs to be split.

There are three approaches, in order of increasing accuracy and implementation complexity:

1. Even split: Divide the shared instance cost equally among all teams that use it. Easy to implement, defensible in team budget conversations, and almost certainly wrong—but consistently wrong in a way that teams can predict and plan around.

2. Weighted split by query execution time: Use the query attribution data from section 24.3 to calculate what fraction of total database CPU each team consumed, then apply that fraction to the infrastructure cost. This requires the query comment tagging convention to be in place on the shared instance.

3. Weighted split by row access: For workloads where CPU time is not a reliable proxy for cost (for example, large sequential scans that are cheap on CPU but expensive on storage I/O), weight by total_logical_reads from Query Store instead.

The following query implements option 2 (query-time weighted split) for a shared instance:

-- SQL Server: compute the cost allocation split for a shared database instance
-- Replace 'shared-sqlserver-01' with your instance identifier
-- Replace 4200.00 with the actual monthly cost of the shared instance

WITH instance_query_costs AS (
    SELECT
        dt.team_slug,
        SUM(fqc.total_exec_seconds)   AS team_exec_seconds,
        SUM(fqc.total_logical_reads)  AS team_logical_reads
    FROM finops.fact_query_costs fqc
    JOIN finops.dim_teams dt ON fqc.team_id = dt.team_id
    JOIN finops.dim_db_instances ddi ON fqc.instance_id = ddi.instance_id
    WHERE ddi.instance_identifier = 'shared-sqlserver-01'
      AND fqc.snapshot_ts >= DATEFROMPARTS(YEAR(SYSDATETIME()), MONTH(SYSDATETIME()), 1)
      AND fqc.snapshot_ts <  DATEADD(MONTH, 1, DATEFROMPARTS(YEAR(SYSDATETIME()), MONTH(SYSDATETIME()), 1))
    GROUP BY dt.team_slug
),
totals AS (
    SELECT
        SUM(team_exec_seconds)  AS total_exec_seconds,
        SUM(team_logical_reads) AS total_logical_reads
    FROM instance_query_costs
)
SELECT
    iqc.team_slug,
    ROUND(iqc.team_exec_seconds, 2)                    AS exec_seconds,
    ROUND(
        iqc.team_exec_seconds / NULLIF(t.total_exec_seconds, 0) * 100, 2
    )                                                 AS pct_by_cpu,
    ROUND(
        iqc.team_exec_seconds / NULLIF(t.total_exec_seconds, 0) * 4200.00, 2
    )                                                 AS allocated_cost_usd,
    ROUND(CAST(iqc.team_logical_reads AS FLOAT), 0)   AS logical_reads,
    ROUND(
        CAST(iqc.team_logical_reads AS FLOAT)
            / NULLIF(CAST(t.total_logical_reads AS FLOAT), 0) * 100, 2
    )                                                 AS pct_by_io
FROM instance_query_costs iqc
CROSS JOIN totals t
ORDER BY allocated_cost_usd DESC;

Store the allocation results in a finops.fact_shared_allocations table alongside the direct costs in finops.fact_infra_costs, and union them in your reporting queries. Teams that work primarily on shared infrastructure will see their allocated share rather than a zero on the dashboard—which is exactly the behavioral nudge that motivates them to optimize their query patterns and eventually request dedicated infrastructure when the economics justify it.

24.8 Escalation Thresholds and Budget Alerts

Automated reports are most useful when they are quiet until something needs attention. A weekly digest that always says "costs are flat" trains leads to stop reading it. The same digest with a clear escalation signal—"your team's database spend increased 40% this week, here are the three queries driving it"—gets read every time.

The threshold logic below runs as part of the weekly digest pipeline and determines the email subject line, the opening paragraph emphasis, and whether a Slack notification fires in addition to the email.

#!/usr/bin/env python3
"""
Escalation threshold evaluator for the weekly database cost digest.
Called from run_weekly_digest() before sending emails.
Sends a Slack alert in addition to email when thresholds are breached.

Thresholds (tune to your organization's norms):
  - wow_increase_pct > 20: yellow alert (noted in email subject)
  - wow_increase_pct > 40: red alert (Slack notification + email)
  - absolute_week_cost > team_budget_weekly: budget breach alert
"""

import json
import urllib.request
import logging

logger = logging.getLogger(__name__)

SLACK_WEBHOOK_URL = "https://hooks.slack.com/services/YOUR/WEBHOOK/URL"
ALERT_CHANNEL = "#finops-alerts"


def evaluate_thresholds(team: dict, top_queries: list) -> dict:
    """
    Evaluate cost thresholds for a team's weekly report.
    Returns a dict with alert_level ('ok', 'warn', 'critical'),
    alert_reason, and email_subject_prefix.
    """
    wow = team.get("wow_change_pct")
    week_cost = float(team.get("week_cost", 0))
    team_name = team["team_name"]

    alert_level = "ok"
    alert_reason = None

    if wow is not None:
        if wow > 40:
            alert_level = "critical"
            alert_reason = f"Database spend increased {wow}% week-over-week"
        elif wow > 20:
            alert_level = "warn"
            alert_reason = f"Database spend increased {wow}% week-over-week"

    # Check if any single query accounts for more than 30% of the team's weekly cost
    if top_queries:
        top_query_cost = float(top_queries[0].get("est_cost_usd", 0))
        if week_cost > 0 and (top_query_cost / week_cost) > 0.30:
            if alert_level != "critical":
                alert_level = "warn"
            alert_reason = (
                (alert_reason or "") +
                f". Single query accounts for "
                f"{round(top_query_cost / week_cost * 100, 1)}% of team spend"
            ).strip(". ")

    subject_prefix = {
        "ok": "✅",
        "warn": "⚠️",
        "critical": "🚨"
    }.get(alert_level, "")

    return {
        "alert_level": alert_level,
        "alert_reason": alert_reason,
        "subject_prefix": subject_prefix
    }


def send_slack_alert(team: dict, threshold_result: dict, top_queries: list) -> None:
    """Send a Slack notification for critical or warn-level cost events."""
    if threshold_result["alert_level"] == "ok":
        return

    wow = team.get("wow_change_pct", "N/A")
    week_cost = team.get("week_cost", 0)
    color = "#ff0000" if threshold_result["alert_level"] == "critical" else "#ffaa00"

    top_query_text = ""
    if top_queries:
        q = top_queries[0]
        top_query_text = (
            f"\n*Top query ({q.get('feature_slug', 'untagged')})* — "
            f"est. ${q.get('est_cost_usd', 0)} | "
            f"{q.get('total_calls', 0):,} calls | "
            f"avg {q.get('avg_exec_ms', 0)}ms\n"
            f"```{q.get('query_fingerprint', '')[:100]}```"
        )

    payload = {
        "channel": ALERT_CHANNEL,
        "attachments": [
            {
                "color": color,
                "title": f"Database Cost Alert — {team['team_name']}",
                "text": (
                    f"{threshold_result['alert_reason']}\n"
                    f"*This week:* ${week_cost} | "
                    f"*WoW change:* {wow}%"
                    f"{top_query_text}"
                ),
                "footer": "FinOps Platform",
                "actions": [
                    {
                        "type": "button",
                        "text": "View Dashboard",
                        "url": f"https://finops.yourcompany.internal/dashboard?team={team['team_slug']}"
                    }
                ]
            }
        ]
    }

    try:
        data = json.dumps(payload).encode("utf-8")
        req = urllib.request.Request(
            SLACK_WEBHOOK_URL,
            data=data,
            headers={"Content-Type": "application/json"}
        )
        urllib.request.urlopen(req, timeout=5)
        logger.info(f"Slack alert sent for team {team['team_name']} (level: {threshold_result['alert_level']})")
    except Exception as e:
        logger.error(f"Failed to send Slack alert: {e}")

Integrate this into run_weekly_digest() by calling evaluate_thresholds() before rendering the email template, passing the result into the template context to conditionally render an alert banner, and calling send_slack_alert() for any team at warn or critical level. The Slack message links directly to the Grafana dashboard pre-filtered for that team, so whoever picks it up in the channel can go straight to the data without logging into the FinOps portal first.

Key Takeaways

  • → **A five-tag taxonomy applied consistently outperforms a twenty-tag taxonomy applied inconsistently.** Start with `team`, `app`, `environment`, `feature`, and `cost-center`. Enforce them at resource creation using SCPs (AWS), Azure Policy, or GCP Organization Policy. Untagged resources must have a consequence—a shared pool chargeback—to close the behavioral loop.
  • → **Infrastructure billing data and query-level attribution serve different purposes and must be combined.** Cloud billing APIs tell you what each team spends on instance hours, storage, and I/O. Query Store and `sys.dm_exec_query_stats` tell you which features and queries within a team are consuming the infrastructure. Neither layer alone is sufficient to drive optimization conversations.
  • → **Embedding team and feature metadata directly in SQL comments is the lowest-friction path to query-level attribution.** Query planners ignore comments, so there is no performance cost. The metadata is captured by Query Store and `sys.dm_exec_query_stats` automatically, requiring no changes to monitoring infrastructure once the comment convention is adopted in application code.
  • → **The weekly cost digest email is the primary behavioral intervention.** Dashboards are consulted reactively; emails arrive proactively. When an engineering lead sees their team's database spend alongside the specific queries driving cost every Monday morning, optimization decisions become self-motivating rather than requiring top-down pressure from a FinOps team.
  • → **Shared infrastructure requires explicit allocation logic, not ignored cost.** Splitting a shared instance's cost by query execution time or logical reads—using the same Query Store data already collected—produces defensible, team-visible allocations that motivate teams to reduce their share rather than treating shared resources as free.
