Chapter 6: Building Your First Database Cost Dashboard

Organizations that build a centralized database cost dashboard reduce their monthly cloud spend by an average of 23% within the first 90 days — not because the dashboard itself saves money, but because visibility forces accountability. Before a dashboard exists, cost anomalies hide for weeks inside undifferentiated billing line items. After one exists, a $14,000 spike in RDS storage costs gets caught on day two. This chapter walks through building a production-ready database cost dashboard from scratch, covering data collection across AWS, Azure, and GCP, metric normalization, automated alerting, and the specific queries that surface actionable cost intelligence. By the end, you will have a working system that your DBAs can monitor daily and your CTO can review weekly without needing a cloud billing certification to interpret the numbers.

---

6.1 Understanding What Your Database Bill Actually Contains

Most engineers look at a cloud database bill and see a single number. The actual bill is a composition of six to twelve distinct cost dimensions, each of which responds to different optimization levers. Before building any dashboard, you need a precise accounting of what you are measuring.

For AWS RDS, the billable dimensions are:

  • → **Instance hours** — the per-hour rate for your DB instance class, multiplied by uptime
  • → **Multi-AZ surcharge** — typically 2× the single-AZ instance rate
  • → **Storage** — per GB-month for gp2, gp3, or io1/io2 storage
  • → **I/O requests** — charged separately on gp2 and io1/io2 (not gp3)
  • → **Backup storage** — free up to 100% of provisioned storage, then $0.095/GB-month
  • → **Data transfer** — egress charges when data leaves the AWS region or crosses AZ boundaries
  • → **Snapshot storage** — manual snapshots billed at the same rate as backup storage
  • → **Proxy hours** — RDS Proxy billed per vCPU of the associated instance

    • For Azure SQL, the dimensions are:

  • → **vCore or DTU hours** — General Purpose, Business Critical, or Hyperscale tier
  • → **Storage** — $0.115/GB-month for General Purpose, included up to 32 GB
  • → **Backup storage LRS/GRS** — $0.05–$0.10/GB-month depending on redundancy tier
  • → **Long-term retention** — separate pricing for blobs in Azure Backup vault
  • → **Elastic Pool overhead** — pool-level eDTUs or vCores shared across databases

    • For Cloud SQL for SQL Server, the dimensions are:

  • → **Instance vCPU and memory** — billed per second with sustained use discounts applied automatically
  • → **SSD storage** — $0.17/GB-month for Cloud SQL for SQL Server (illustrative — verify current pricing)
  • → **HDD storage** — $0.09/GB-month for Cloud SQL for SQL Server (illustrative — verify current pricing)
  • → **Egress** — billed when data crosses regions or exits Google's network
  • → **Backup storage** — $0.08/GB-month for Cloud SQL automated backups

    • The math that surprises most teams: a db.r6g.2xlarge RDS instance in us-east-1 running 24/7 on-demand costs $0.48/hour × 730 hours = $350.40/month for the instance alone. Multi-AZ doubles that to $700.80/month; add 1TB gp2 storage ($115), backup retention across 7 days (~$95), and a conservative data transfer estimate ($40), and a single "medium" database costs approximately $950/month before you have written a single query against it. A reserved instance purchase for that same class drops the hourly rate to roughly $0.286 for a 1-year no-upfront commitment — saving $140/month per instance. With ten such instances, that is $16,800/year in savings from one configuration change.

    Your dashboard must expose all of these dimensions independently. An aggregated "database cost" number is not actionable. A breakdown that shows backup storage growing 15% month-over-month while instance costs remain flat tells a DBA to look at retention policy configuration immediately.

    6.2 Collecting Cost Data: AWS, Azure, and GCP APIs

    A database cost dashboard is only as good as the data feeding it. This section covers the exact API calls, queries, and export configurations needed to pull granular cost data from each cloud provider into a centralized store — in practice, a SQL Server table works well for this, and the irony of using a database to track database costs is not lost on anyone who has done it.

    #### AWS Cost Explorer via CLI and API

    AWS Cost Explorer exposes a rich API that returns cost breakdowns by service, usage type, tag, and linked account. The following bash script pulls the last 30 days of RDS costs grouped by usage type and writes them to a local JSON file for ingestion.

    #!/bin/bash
# collect_aws_rds_costs.sh
# Pulls RDS cost breakdown from AWS Cost Explorer for the trailing 30 days
# Schedule: daily via cron or EventBridge Scheduler
# Requirements: AWS CLI v2, IAM permissions for ce:GetCostAndUsage

START_DATE=$(date -d "30 days ago" +%Y-%m-%d 2>/dev/null || date -v-30d +%Y-%m-%d)
END_DATE=$(date +%Y-%m-%d)
OUTPUT_FILE="/var/log/dbfinops/rds_costs_$(date +%Y%m%d).json"

mkdir -p /var/log/dbfinops

echo "Collecting RDS costs from $START_DATE to $END_DATE"

aws ce get-cost-and-usage \
  --time-period Start="$START_DATE",End="$END_DATE" \
  --granularity DAILY \
  --filter '{
    "Dimensions": {
      "Key": "SERVICE",
      "Values": ["Amazon Relational Database Service"],
      "MatchOptions": ["EQUALS"]
    }
  }' \
  --group-by '[
    {"Type": "DIMENSION", "Key": "USAGE_TYPE"},
    {"Type": "TAG", "Key": "Environment"},
    {"Type": "TAG", "Key": "Team"}
  ]' \
  --metrics "BlendedCost" "UnblendedCost" "UsageQuantity" \
  --output json > "$OUTPUT_FILE"

echo "Cost data written to $OUTPUT_FILE"

# Also collect Reserved Instance utilization
aws ce get-reservation-utilization \
  --time-period Start="$START_DATE",End="$END_DATE" \
  --granularity MONTHLY \
  --filter '{
    "Dimensions": {
      "Key": "SERVICE",
      "Values": ["Amazon Relational Database Service"],
      "MatchOptions": ["EQUALS"]
    }
  }' \
  --output json > "/var/log/dbfinops/ri_utilization_$(date +%Y%m%d).json"

echo "RI utilization data collected"

# Collect Savings Plans coverage
aws ce get-savings-plans-coverage \
  --time-period Start="$START_DATE",End="$END_DATE" \
  --granularity MONTHLY \
  --output json > "/var/log/dbfinops/sp_coverage_$(date +%Y%m%d).json"

echo "Collection complete. Files in /var/log/dbfinops/"

    #### Azure Cost Management Export

    Azure requires a slightly different approach. The Cost Management API is powerful but verbose. The recommended production pattern is to configure a scheduled export from Azure Cost Management to a Storage Account blob, then process the CSV from there.

    #!/bin/bash
# configure_azure_cost_export.sh
# Creates a recurring Azure Cost Management export for SQL database costs
# Requires: az CLI, Contributor role on subscription or resource group

SUBSCRIPTION_ID="your-subscription-id"
RESOURCE_GROUP="rg-finops-monitoring"
STORAGE_ACCOUNT="sadbfinops$(echo $RANDOM | md5sum | head -c 8)"
CONTAINER_NAME="cost-exports"
EXPORT_NAME="SQLDatabaseDailyCosts"
LOCATION="eastus"

echo "Creating storage account for cost exports..."
az storage account create \
  --name "$STORAGE_ACCOUNT" \
  --resource-group "$RESOURCE_GROUP" \
  --location "$LOCATION" \
  --sku Standard_LRS \
  --kind StorageV2

az storage container create \
  --name "$CONTAINER_NAME" \
  --account-name "$STORAGE_ACCOUNT"

STORAGE_ID=$(az storage account show \
  --name "$STORAGE_ACCOUNT" \
  --resource-group "$RESOURCE_GROUP" \
  --query id --output tsv)

echo "Creating daily cost export..."
az costmanagement export create \
  --name "$EXPORT_NAME" \
  --type ActualCost \
  --scope "subscriptions/$SUBSCRIPTION_ID" \
  --storage-account-id "$STORAGE_ID" \
  --storage-container "$CONTAINER_NAME" \
  --storage-directory "sql-costs" \
  --recurrence Daily \
  --recurrence-period \
    from="$(date +%Y-%m-%dT00:00:00Z)" \
    to="$(date -d '+1 year' +%Y-%m-%dT00:00:00Z 2>/dev/null || date -v+1y +%Y-%m-%dT00:00:00Z)" \
  --dataset-configuration columns="Date,SubscriptionId,ResourceId,ResourceType,ResourceGroup,MeterCategory,MeterSubCategory,Quantity,UnitPrice,Cost,Tags"

echo "Export configured. Data will appear in blob storage daily."
echo "Storage account: $STORAGE_ACCOUNT"
echo "Container: $CONTAINER_NAME"

# Trigger an immediate export run
az costmanagement export run \
  --name "$EXPORT_NAME" \
  --scope "subscriptions/$SUBSCRIPTION_ID"

echo "Immediate export triggered."

    #### GCP BigQuery Billing Export

    GCP's billing export to BigQuery is the most analysis-friendly of the three providers. Once enabled in the Console under Billing → Budget & Alerts → Billing Export, you can query cost data with standard SQL. The following query extracts Cloud SQL for SQL Server costs by project and label, normalized to a per-day grain.

    -- GCP BigQuery: daily Cloud SQL for SQL Server cost breakdown
-- Run in BigQuery against your billing export dataset
-- Replace 'your-project.billing_export.gcp_billing_export_v1_XXXXXX'
-- with your actual billing export table name

SELECT
  DATE(usage_start_time) AS cost_date,
  project.name AS project_name,
  service.description AS service_name,
  sku.description AS sku_description,
  labels.value AS environment_label,
  resource.name AS resource_name,
  SUM(usage.amount) AS usage_amount,
  usage.unit AS usage_unit,
  SUM(cost) AS total_cost,
  SUM(
    IFNULL(
      (SELECT SUM(c.amount)
       FROM UNNEST(credits) c
       WHERE c.type IN ('SUSTAINED_USE_DISCOUNT', 'COMMITTED_USE_DISCOUNT')),
      0
    )
  ) AS total_credits,
  SUM(cost) + SUM(
    IFNULL(
      (SELECT SUM(c.amount)
       FROM UNNEST(credits) c),
      0
    )
  ) AS net_cost
FROM
  `your-project.billing_export.gcp_billing_export_v1_XXXXXX`,
  UNNEST(labels) AS labels
WHERE
  service.description IN ('Cloud SQL')
  AND labels.key = 'environment'
  AND DATE(usage_start_time) >= DATE_SUB(CURRENT_DATE(), INTERVAL 30 DAY)
GROUP BY
  1, 2, 3, 4, 5, 6, 8
ORDER BY
  cost_date DESC,
  total_cost DESC;

    6.3 Building the Cost Metrics Store

    Rather than building a separate analytics platform for database costs, the most pragmatic approach for a team that already manages SQL Server is to create a dedicated schema within an existing monitoring database. This keeps the tooling familiar and allows you to join cost data with performance metrics from Query Store, SQL Server error logs, and CloudWatch exports.

    The following schema creates the tables needed to store normalized cost data across providers, along with the performance correlation tables that make the dashboard genuinely useful rather than decorative.

    -- Database Cost Metrics Schema (T-SQL)
-- Apply to a dedicated monitoring SQL Server instance
-- or a separate schema in your existing monitoring database

IF NOT EXISTS (SELECT 1 FROM sys.schemas WHERE name = 'dbfinops')
    EXEC('CREATE SCHEMA dbfinops');
GO

-- Normalized cost fact table (all providers, all dimensions)
CREATE TABLE dbfinops.daily_costs (
    id                  BIGINT IDENTITY(1,1) PRIMARY KEY,
    cost_date           DATE NOT NULL,
    provider            NVARCHAR(20) NOT NULL CHECK (provider IN ('aws', 'azure', 'gcp')),
    account_id          NVARCHAR(100) NOT NULL,   -- AWS account, Azure subscription, GCP project
    region              NVARCHAR(50) NOT NULL,
    database_identifier NVARCHAR(255) NOT NULL,   -- instance/cluster/pool name
    engine              NVARCHAR(50),             -- sqlserver
    instance_class      NVARCHAR(100),            -- db.r6i.2xlarge, GP_Gen5_4, etc.
    environment         NVARCHAR(50),             -- from tag/label: prod, staging, dev
    team                NVARCHAR(100),            -- from tag/label: payments, analytics, etc.
    cost_dimension      NVARCHAR(50) NOT NULL,    -- instance, storage, io, backup, transfer, license
    usage_quantity      DECIMAL(18, 6),
    usage_unit          NVARCHAR(50),
    unblended_cost      DECIMAL(18, 6) NOT NULL,
    blended_cost        DECIMAL(18, 6),
    credits_applied     DECIMAL(18, 6) DEFAULT 0,
    net_cost            AS (unblended_cost + ISNULL(credits_applied, 0)) PERSISTED,
    currency            CHAR(3) DEFAULT 'USD',
    loaded_at           DATETIME2 DEFAULT SYSUTCDATETIME()
);

CREATE INDEX idx_daily_costs_date
    ON dbfinops.daily_costs (cost_date DESC);

CREATE INDEX idx_daily_costs_provider_db
    ON dbfinops.daily_costs (provider, database_identifier, cost_date DESC);

CREATE INDEX idx_daily_costs_environment_team
    ON dbfinops.daily_costs (environment, team, cost_date DESC);

-- Unique constraint to prevent duplicate loads
CREATE UNIQUE INDEX idx_daily_costs_unique
    ON dbfinops.daily_costs (
        cost_date, provider, account_id, database_identifier,
        cost_dimension, region, environment
    );

-- Month-to-date cost summary view (refresh via job, or convert to an indexed view)
CREATE OR ALTER VIEW dbfinops.mtd_cost_summary AS
SELECT
    DATEFROMPARTS(YEAR(cost_date), MONTH(cost_date), 1) AS month_start,
    provider,
    database_identifier,
    environment,
    team,
    instance_class,
    engine,
    SUM(unblended_cost)  AS mtd_cost,
    SUM(credits_applied) AS mtd_credits,
    SUM(net_cost)        AS mtd_net_cost,
    MAX(cost_date)       AS last_updated
FROM
    dbfinops.daily_costs
WHERE
    cost_date >= DATEFROMPARTS(YEAR(SYSDATETIME()), MONTH(SYSDATETIME()), 1)
GROUP BY
    DATEFROMPARTS(YEAR(cost_date), MONTH(cost_date), 1),
    provider, database_identifier, environment, team, instance_class, engine;
GO

-- Cost anomaly detection table
CREATE TABLE dbfinops.cost_anomalies (
    id                  BIGINT IDENTITY(1,1) PRIMARY KEY,
    detected_at         DATETIME2 DEFAULT SYSUTCDATETIME(),
    cost_date           DATE NOT NULL,
    provider            NVARCHAR(20) NOT NULL,
    database_identifier NVARCHAR(255) NOT NULL,
    cost_dimension      NVARCHAR(50) NOT NULL,
    expected_cost       DECIMAL(18, 6),
    actual_cost         DECIMAL(18, 6),
    deviation_pct       DECIMAL(8, 2),
    severity            NVARCHAR(20) CHECK (severity IN ('low', 'medium', 'high', 'critical')),
    acknowledged        BIT DEFAULT 0,
    acknowledged_by     NVARCHAR(100),
    notes               NVARCHAR(MAX)
);

-- Reserved instance and commitment tracking
CREATE TABLE dbfinops.commitments (
    id                  BIGINT IDENTITY(1,1) PRIMARY KEY,
    provider            NVARCHAR(20) NOT NULL,
    account_id          NVARCHAR(100) NOT NULL,
    commitment_type     NVARCHAR(50) NOT NULL,   -- reserved_instance, savings_plan, committed_use
    instance_class      NVARCHAR(100),
    region              NVARCHAR(50),
    term_months         INT,
    start_date          DATE NOT NULL,
    end_date            DATE NOT NULL,
    hourly_commitment   DECIMAL(18, 6),
    monthly_cost        DECIMAL(18, 6),
    utilization_pct     DECIMAL(6, 2),
    break_even_date     DATE,
    notes               NVARCHAR(MAX),
    created_at          DATETIME2 DEFAULT SYSUTCDATETIME()
);

-- Cost-per-query correlation (joins with sys.dm_exec_query_stats data)
CREATE TABLE dbfinops.query_cost_attribution (
    id                  BIGINT IDENTITY(1,1) PRIMARY KEY,
    sample_date         DATE NOT NULL,
    database_identifier NVARCHAR(255) NOT NULL,
    query_hash          BINARY(8),        -- from sys.dm_exec_query_stats
    query_fingerprint   NVARCHAR(MAX),
    execution_count     BIGINT,
    total_elapsed_ms    DECIMAL(18, 3),
    avg_elapsed_ms      DECIMAL(18, 3),
    total_logical_reads BIGINT,
    total_physical_reads BIGINT,
    estimated_io_cost   DECIMAL(18, 6),  -- physical_reads x storage_cost_per_gb
    pct_of_instance_cpu DECIMAL(6, 2),
    attributed_cost_usd DECIMAL(18, 6)   -- (pct_cpu / 100) x daily_instance_cost
);

    With this schema in place, you have a foundation that supports both operational alerting and executive reporting. The query_cost_attribution table is particularly valuable for the conversations that no one wants to have but every engineering team needs: "This ETL job costs us approximately $380/month in compute attribution. Is that acceptable for what it produces?"

    6.4 Connecting Performance Data to Cost Data

    A cost dashboard that shows only spend is a finance tool. A cost dashboard that shows spend alongside performance metrics — query latency, connection counts, CPU utilization, I/O wait — is an engineering tool that finance can also read. This section builds the queries and automation that populate that correlation layer.

    The following Python script pulls query statistics from sys.dm_exec_query_stats on a SQL Server instance, calculates a cost attribution per query based on its CPU share, and writes the results to the query_cost_attribution table.

    #!/usr/bin/env python3
"""
query_cost_attribution.py

Connects to a SQL Server database, pulls sys.dm_exec_query_stats metrics,
fetches the daily instance cost from dbfinops.daily_costs,
calculates per-query cost attribution, and stores results.

Schedule: daily at 01:00 UTC via cron, SQL Agent, or EventBridge

Dependencies:
    pip install pyodbc python-dotenv

Environment variables (via .env or Secrets Manager):
    DB_SERVER, DB_NAME, DB_USER, DB_PASSWORD
    MONITORING_DB_SERVER, MONITORING_DB_NAME, MONITORING_DB_USER, MONITORING_DB_PASSWORD
"""

import os
import logging
from datetime import date, timedelta
from decimal import Decimal

import pyodbc
from dotenv import load_dotenv

load_dotenv()

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s"
)
log = logging.getLogger(__name__)

# -- Connection helpers -------------------------------------------------------

def _conn_str(server, database, user, password):
    return (
        "DRIVER={ODBC Driver 18 for SQL Server};"
        f"SERVER={server};DATABASE={database};"
        f"UID={user};PWD={password};"
        "Encrypt=yes;TrustServerCertificate=no;Connection Timeout=30;"
    )

def get_source_conn():
    """Connect to the database being analyzed."""
    return pyodbc.connect(_conn_str(
        os.environ["DB_SERVER"], os.environ["DB_NAME"],
        os.environ["DB_USER"], os.environ["DB_PASSWORD"]))

def get_monitoring_conn():
    """Connect to the monitoring database where dbfinops schema lives."""
    return pyodbc.connect(_conn_str(
        os.environ["MONITORING_DB_SERVER"],
        os.environ.get("MONITORING_DB_NAME", "dbfinops"),
        os.environ["MONITORING_DB_USER"],
        os.environ["MONITORING_DB_PASSWORD"]))

# -- Query stats collection ---------------------------------------------------

QUERY_STATS_SQL = """
SELECT TOP 100
    qs.query_hash,
    LEFT(qt.text, 200) AS query_fingerprint,
    qs.execution_count,
    qs.total_elapsed_time / 1000.0 AS total_elapsed_ms,
    (qs.total_elapsed_time / 1000.0) / NULLIF(qs.execution_count, 0) AS avg_elapsed_ms,
    qs.total_logical_reads,
    qs.total_physical_reads,
    -- CPU share: this query's worker time as % of all queries' worker time
    100.0 * qs.total_worker_time
        / NULLIF(SUM(qs.total_worker_time) OVER (), 0) AS pct_of_total_cpu
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS qt
WHERE qs.execution_count > 10
  AND qs.total_elapsed_time > 1000000   -- more than 1 second total (microseconds)
  AND qt.text NOT LIKE '%dm_exec_query_stats%'  -- exclude monitoring queries
ORDER BY qs.total_worker_time DESC;
"""

def fetch_query_stats(conn):
    """Pull top query stats from sys.dm_exec_query_stats."""
    cur = conn.cursor()
    cur.execute(QUERY_STATS_SQL)
    cols = [c[0] for c in cur.description]
    rows = [dict(zip(cols, r)) for r in cur.fetchall()]
    log.info("Fetched %d query stats rows", len(rows))
    return rows

# -- Daily cost lookup --------------------------------------------------------

def fetch_daily_cost(monitoring_conn, db_identifier: str,
                     target_date: date, dimension: str) -> Decimal:
    """Look up yesterday's cost for a database and cost dimension."""
    cur = monitoring_conn.cursor()
    cur.execute(
        """
        SELECT COALESCE(SUM(unblended_cost), 0)
        FROM   dbfinops.daily_costs
        WHERE  database_identifier = ?
          AND  cost_date            = ?
          AND  cost_dimension       = ?
        """,
        db_identifier, target_date, dimension,
    )
    row = cur.fetchone()
    cost = Decimal(str(row[0])) if row else Decimal("0")
    log.info("Daily %s cost for %s on %s: $%s", dimension, db_identifier, target_date, cost)
    return cost

# -- Cost attribution calculation ----------------------------------------------

def attribute_costs(query_stats, daily_instance_cost: Decimal,
                    daily_storage_cost: Decimal):
    """Merge query stats with cost data to produce per-query cost attribution."""
    attributed = []
    for row in query_stats:
        pct = Decimal(str(row["pct_of_total_cpu"] or 0))
        instance_share = (pct / Decimal("100")) * daily_instance_cost
        # Physical reads (8KB pages) as a proxy for I/O pressure on the storage bill
        gb_read = (Decimal(str(row["total_physical_reads"] or 0))
                   * Decimal("8192") / Decimal("1073741824"))
        io_cost = (gb_read * daily_storage_cost).quantize(Decimal("0.000001"))
        attributed.append({
            "query_hash":           row["query_hash"],
            "query_fingerprint":    row["query_fingerprint"],
            "execution_count":      int(row["execution_count"] or 0),
            "total_elapsed_ms":     float(row["total_elapsed_ms"] or 0),
            "avg_elapsed_ms":       float(row["avg_elapsed_ms"] or 0),
            "total_logical_reads":  int(row["total_logical_reads"] or 0),
            "total_physical_reads": int(row["total_physical_reads"] or 0),
            "estimated_io_cost":    float(io_cost),
            "pct_of_instance_cpu":  float(pct),
            "attributed_cost_usd":  float(instance_share + io_cost),
        })
    return attributed

# -- Write results to monitoring DB --------------------------------------------

INSERT_SQL = """
INSERT INTO dbfinops.query_cost_attribution (
    sample_date, database_identifier, query_hash, query_fingerprint,
    execution_count, total_elapsed_ms, avg_elapsed_ms,
    total_logical_reads, total_physical_reads,
    estimated_io_cost, pct_of_instance_cpu, attributed_cost_usd
)
SELECT ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?
WHERE NOT EXISTS (
    SELECT 1 FROM dbfinops.query_cost_attribution
    WHERE sample_date = ? AND database_identifier = ? AND query_hash = ?
);
"""

def write_attributions(monitoring_conn, db_identifier: str,
                       sample_date: date, rows) -> int:
    written = 0
    cur = monitoring_conn.cursor()
    for row in rows:
        cur.execute(INSERT_SQL,
                    sample_date, db_identifier, row["query_hash"],
                    row["query_fingerprint"], row["execution_count"],
                    row["total_elapsed_ms"], row["avg_elapsed_ms"],
                    row["total_logical_reads"], row["total_physical_reads"],
                    row["estimated_io_cost"], row["pct_of_instance_cpu"],
                    row["attributed_cost_usd"],
                    sample_date, db_identifier, row["query_hash"])
        written += cur.rowcount
    monitoring_conn.commit()
    log.info("Wrote %d attribution rows for %s", written, db_identifier)
    return written

# -- Main entry point -----------------------------------------------------------

def main():
    db_identifier = os.environ.get("DB_IDENTIFIER",
                                   os.environ["DB_SERVER"].split(".")[0])
    target_date   = date.today() - timedelta(days=1)

    source_conn     = get_source_conn()
    monitoring_conn = get_monitoring_conn()

    try:
        query_stats = fetch_query_stats(source_conn)
        if not query_stats:
            log.warning("No query stats available - skipping attribution run.")
            return

        daily_instance_cost = fetch_daily_cost(
            monitoring_conn, db_identifier, target_date, "instance")
        daily_storage_cost = fetch_daily_cost(
            monitoring_conn, db_identifier, target_date, "storage")

        attributed = attribute_costs(query_stats, daily_instance_cost,
                                    daily_storage_cost)
        write_attributions(monitoring_conn, db_identifier, target_date,
                           attributed)
    finally:
        source_conn.close()
        monitoring_conn.close()


if __name__ == "__main__":
    main()

    With this script running nightly, the query_cost_attribution table accumulates a rolling history that makes two previously invisible patterns visible: which queries are becoming more expensive over time as data volume grows, and which teams own the workloads driving the largest share of the monthly bill.

    6.5 The Core Dashboard Queries

    The queries in this section are designed to be dropped directly into Grafana, Metabase, or any SQL-capable BI tool. Each answers a specific question that a DBA or an engineering manager will actually ask. They are written in T-SQL against the dbfinops schema defined earlier.

    #### Query 1: Month-over-Month Cost Change by Database

    This is the first panel any database cost dashboard should show: are costs going up or down, and by how much, for each database.

    -- T-SQL: Month-over-Month cost change per database
-- Dashboard variables: @provider (aws | azure | gcp | all)
-- Dashboard variables: @environment (prod | staging | dev | all)

DECLARE @provider NVARCHAR(20) = 'all';
DECLARE @environment NVARCHAR(50) = 'all';
DECLARE @month_start DATE =
    DATEFROMPARTS(YEAR(CAST(GETUTCDATE() AS DATE)), MONTH(CAST(GETUTCDATE() AS DATE)), 1);

WITH monthly_costs AS (
    SELECT
        DATEFROMPARTS(YEAR(cost_date), MONTH(cost_date), 1) AS month,
        provider,
        database_identifier,
        environment,
        team,
        SUM(unblended_cost)                  AS total_cost
    FROM
        dbfinops.daily_costs
    WHERE
        cost_date >= DATEADD(MONTH, -2, @month_start)
        AND (@provider = 'all' OR provider = @provider)
        AND (@environment = 'all' OR environment = @environment)
    GROUP BY
        DATEFROMPARTS(YEAR(cost_date), MONTH(cost_date), 1),
        provider, database_identifier, environment, team
),
with_lag AS (
    SELECT
        month,
        provider,
        database_identifier,
        environment,
        team,
        total_cost,
        LAG(total_cost) OVER (
            PARTITION BY provider, database_identifier
            ORDER BY month
        )                                    AS prior_month_cost
    FROM monthly_costs
)
SELECT
    month,
    provider,
    database_identifier,
    environment,
    team,
    CAST(ROUND(total_cost, 2) AS DECIMAL(18,2))        AS current_month_cost,
    CAST(ROUND(prior_month_cost, 2) AS DECIMAL(18,2))  AS prior_month_cost,
    CAST(ROUND(total_cost - prior_month_cost, 2) AS DECIMAL(18,2)) AS cost_delta,
    CAST(ROUND(
        CASE
            WHEN prior_month_cost > 0
            THEN (total_cost - prior_month_cost) / prior_month_cost * 100.0
            ELSE NULL
        END, 1) AS DECIMAL(18,1))                     AS pct_change
FROM
    with_lag
WHERE
    month = @month_start
ORDER BY
    CASE WHEN total_cost - prior_month_cost IS NULL THEN 1 ELSE 0 END,
    total_cost - prior_month_cost DESC;

    #### Query 2: Cost Dimension Breakdown for a Single Database

    When a database's total cost spikes, this query reveals which dimension is responsible.

    -- T-SQL: Cost breakdown by dimension for a specific database
-- Dashboard variables: @db_identifier, @num_days (default 30)

DECLARE @db_identifier NVARCHAR(255) = 'my-prod-db';
DECLARE @num_days INT = 30;

SELECT
    cost_date,
    cost_dimension,
    CAST(ROUND(SUM(unblended_cost), 4) AS DECIMAL(18,4))   AS daily_cost,
    CAST(ROUND(
        SUM(SUM(unblended_cost)) OVER (
            PARTITION BY cost_dimension
            ORDER BY cost_date
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ), 4) AS DECIMAL(18,4))                            AS cumulative_cost
FROM
    dbfinops.daily_costs
WHERE
    database_identifier = @db_identifier
    AND cost_date >= DATEADD(DAY, -@num_days, CAST(GETUTCDATE() AS DATE))
GROUP BY
    cost_date, cost_dimension
ORDER BY
    cost_date DESC, SUM(unblended_cost) DESC;

    #### Query 3: Reserved Instance / Commitment Coverage Gap

    This query surfaces databases running entirely on on-demand pricing — the highest priority targets for commitment purchases.

    -- T-SQL: Identify databases with no commitment coverage
-- Compares actual spend against commitment records

DECLARE @month_start DATE =
    DATEFROMPARTS(YEAR(CAST(GETUTCDATE() AS DATE)), MONTH(CAST(GETUTCDATE() AS DATE)), 1);

WITH daily_spend AS (
    SELECT
        provider,
        account_id,
        database_identifier,
        instance_class,
        environment,
        SUM(unblended_cost)                  AS monthly_spend
    FROM
        dbfinops.daily_costs
    WHERE
        cost_date >= @month_start
        AND cost_dimension = 'instance'
    GROUP BY
        provider, account_id, database_identifier, instance_class, environment
),
covered AS (
    SELECT DISTINCT
        provider,
        account_id,
        instance_class
    FROM
        dbfinops.commitments
    WHERE
        end_date >= CAST(GETUTCDATE() AS DATE)
        AND utilization_pct > 0
)
SELECT
    ds.provider,
    ds.database_identifier,
    ds.instance_class,
    ds.environment,
    CAST(ROUND(ds.monthly_spend, 2) AS DECIMAL(18,2))       AS mtd_on_demand_spend,
    CAST(ROUND(ds.monthly_spend * 12, 2) AS DECIMAL(18,2))  AS projected_annual_spend,
    CASE
        WHEN c.instance_class IS NOT NULL THEN 'Partially Covered'
        ELSE 'No Coverage'
    END                                                     AS coverage_status,
    -- Rough savings estimate for a 1-year no-upfront RI (approximately 30-35% discount)
    CAST(ROUND(ds.monthly_spend * 12 * 0.32, 2) AS DECIMAL(18,2)) AS est_annual_ri_savings
FROM
    daily_spend ds
LEFT JOIN covered c
    ON  ds.provider       = c.provider
    AND ds.account_id     = c.account_id
    AND ds.instance_class = c.instance_class
WHERE
    ds.environment = 'prod'                  -- focus RI analysis on production
ORDER BY
    ds.monthly_spend DESC;

    #### Query 4: Storage Growth Rate and Projected Overage

    Storage costs tend to grow silently. This query computes a linear trend and projects when storage costs will breach a defined threshold.

    -- T-SQL: Storage cost growth trend and projection
-- Uses least-squares linear regression over the past 60 days to project forward 30 days
-- (T-SQL has no REGR_* aggregates, so slope/intercept/R-squared are computed manually)

WITH daily_storage AS (
    SELECT
        database_identifier,
        provider,
        cost_date,
        SUM(unblended_cost)                                  AS storage_cost,
        CAST(DATEDIFF(DAY, '2000-01-01', cost_date) AS FLOAT) AS x_day
    FROM
        dbfinops.daily_costs
    WHERE
        cost_dimension = 'storage'
        AND cost_date >= DATEADD(DAY, -60, CAST(GETUTCDATE() AS DATE))
    GROUP BY
        database_identifier, provider, cost_date
),
regression AS (
    SELECT
        database_identifier,
        provider,
        COUNT(*)                                             AS n,
        SUM(x_day)                                           AS sum_x,
        SUM(storage_cost)                                    AS sum_y,
        SUM(x_day * x_day)                                   AS sum_xx,
        SUM(x_day * storage_cost)                            AS sum_xy,
        SUM(storage_cost * storage_cost)                     AS sum_yy,
        MAX(storage_cost)                                    AS latest_daily_cost
    FROM
        daily_storage
    GROUP BY
        database_identifier, provider
),
fitted AS (
    SELECT
        database_identifier,
        provider,
        latest_daily_cost,
        -- slope = (n*sum_xy - sum_x*sum_y) / (n*sum_xx - sum_x^2)
        CASE WHEN n * sum_xx - sum_x * sum_x = 0 THEN 0.0
             ELSE (n * sum_xy - sum_x * sum_y) / (n * sum_xx - sum_x * sum_x)
        END                                                  AS slope_per_day,
        -- R-squared
        CASE WHEN (n * sum_xx - sum_x * sum_x) = 0
               OR (n * sum_yy - sum_y * sum_y) = 0 THEN 0.0
             ELSE POWER(n * sum_xy - sum_x * sum_y, 2)
                / ((n * sum_xx - sum_x * sum_x) * (n * sum_yy - sum_y * sum_y))
        END                                                  AS r_squared
    FROM
        regression
)
SELECT
    database_identifier,
    provider,
    CAST(ROUND(latest_daily_cost, 4) AS DECIMAL(18,4))        AS current_daily_storage_cost,
    CAST(ROUND(latest_daily_cost * 30, 2) AS DECIMAL(18,2))  AS current_monthly_projection,
    -- Project 30 days forward using the regression slope
    CAST(ROUND(latest_daily_cost + slope_per_day * 30, 2) AS DECIMAL(18,2))
                                                            AS projected_monthly_30d,
    CAST(ROUND(r_squared, 3) AS DECIMAL(18,3))               AS trend_confidence,
    CASE
        WHEN r_squared > 0.85 AND slope_per_day > 0
        THEN 'Consistent upward trend - review retention policy'
        WHEN r_squared > 0.85 AND slope_per_day < -0.001
        THEN 'Declining - verify expected'
        ELSE 'Variable - insufficient trend confidence'
    END                                                     AS recommendation
FROM
    fitted
ORDER BY
    latest_daily_cost + slope_per_day * 30 DESC;

    #### Query 5: Top Cost-Attributing Queries

    This query surfaces the queries responsible for the largest share of daily compute cost — the starting point for any query optimization effort tied directly to a cost outcome.

    -- T-SQL: Top queries by attributed cost, past 7 days
-- Requires query_cost_attribution table populated by nightly script

SELECT TOP 20
    query_fingerprint,
    database_identifier,
    SUM(execution_count)                                   AS total_executions,
    CAST(ROUND(SUM(total_elapsed_ms) / 1000.0 / 60.0, 1) AS DECIMAL(18,1))
                                                          AS total_exec_minutes,
    CAST(ROUND(AVG(avg_elapsed_ms), 1) AS DECIMAL(18,1))   AS avg_exec_ms,
    CAST(ROUND(SUM(attributed_cost_usd), 4) AS DECIMAL(18,4))
                                                          AS total_attributed_cost,
    CAST(ROUND(
        SUM(attributed_cost_usd) / NULLIF(
            SUM(SUM(attributed_cost_usd)) OVER (), 0
        ) * 100.0, 2) AS DECIMAL(18,2))                    AS pct_of_total_cost,
    CAST(ROUND(SUM(estimated_io_cost), 4) AS DECIMAL(18,4))
                                                          AS total_io_cost,
    MAX(sample_date)                                      AS last_seen
FROM
    dbfinops.query_cost_attribution
WHERE
    sample_date >= DATEADD(DAY, -7, CAST(GETUTCDATE() AS DATE))
GROUP BY
    query_fingerprint, database_identifier
ORDER BY
    SUM(attributed_cost_usd) DESC;

    6.6 Automated Anomaly Detection

    A dashboard that requires someone to look at it to catch a problem is only half a system. The anomaly detection layer fires alerts automatically when costs deviate from expected ranges, reducing the mean time to detect (MTTD) from days to hours.

    The following function implements a statistical anomaly detector using a 14-day rolling mean and standard deviation. It is designed to run nightly as a SQL Server stored procedure, populating the cost_anomalies table, which then drives alert rules in Grafana or PagerDuty.

    The following T-SQL stored procedure implements the detector using temp tables and set-based inserts. Schedule it nightly with SQL Agent or an Elastic Job: EXEC dbfinops.DetectCostAnomalies;

    -- SQL Server / Azure SQL: Cost anomaly detection stored procedure
-- Nightly anomaly detection — run after the cost ETL finishes

CREATE OR ALTER PROCEDURE dbfinops.DetectCostAnomalies
    @LookbackDays    INT  = 14,
    @ZThresholdMed   FLOAT = 2.0,
    @ZThresholdHigh  FLOAT = 3.0,
    @ZThresholdCrit  FLOAT = 4.0
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @TargetDate DATE = DATEADD(DAY, -1, CAST(GETUTCDATE() AS DATE));
    DECLARE @BaselineStart DATE = DATEADD(DAY, -@LookbackDays, @TargetDate);

    -- Remove unacknowledged anomalies for target date (idempotent re-runs)
    DELETE FROM dbfinops.cost_anomalies
    WHERE  CostDate    = @TargetDate
      AND  Acknowledged = 0;

    -- Compute baseline statistics
    DROP TABLE IF EXISTS #Baseline;
    SELECT
        Provider,
        DatabaseIdentifier,
        CostDimension,
        AVG(UnblendedCost)                          AS MeanCost,
        STDEV(UnblendedCost)                        AS StddevCost,
        COUNT(*)                                    AS DayCount
    INTO #Baseline
    FROM dbfinops.daily_costs
    WHERE CostDate BETWEEN @BaselineStart AND DATEADD(DAY, -1, @TargetDate)
    GROUP BY Provider, DatabaseIdentifier, CostDimension
    HAVING COUNT(*) >= 7;

    -- Compute yesterday's actuals
    DROP TABLE IF EXISTS #Yesterday;
    SELECT
        Provider,
        DatabaseIdentifier,
        CostDimension,
        SUM(UnblendedCost)                          AS ActualCost
    INTO #Yesterday
    FROM dbfinops.daily_costs
    WHERE CostDate = @TargetDate
    GROUP BY Provider, DatabaseIdentifier, CostDimension;

    -- Insert anomalies
    INSERT INTO dbfinops.cost_anomalies (
        CostDate, Provider, DatabaseIdentifier, CostDimension,
        ExpectedCost, ActualCost, DeviationPct, Severity
    )
    SELECT
        @TargetDate,
        y.Provider,
        y.DatabaseIdentifier,
        y.CostDimension,
        ROUND(b.MeanCost, 6)                        AS ExpectedCost,
        ROUND(y.ActualCost, 6)                      AS ActualCost,
        ROUND(
            CASE WHEN b.MeanCost > 0
                 THEN (y.ActualCost - b.MeanCost) / b.MeanCost * 100.0
                 ELSE NULL
            END,
            2
        )                                           AS DeviationPct,
        CASE
            WHEN b.StddevCost = 0 OR b.StddevCost IS NULL
                THEN 'low'
            WHEN (y.ActualCost - b.MeanCost) / NULLIF(b.StddevCost, 0) >= @ZThresholdCrit
                THEN 'critical'
            WHEN (y.ActualCost - b.MeanCost) / NULLIF(b.StddevCost, 0) >= @ZThresholdHigh
                THEN 'high'
            WHEN (y.ActualCost - b.MeanCost) / NULLIF(b.StddevCost, 0) >= @ZThresholdMed
                THEN 'medium'
            ELSE 'low'
        END                                         AS Severity
    FROM #Yesterday y
    JOIN #Baseline  b
        ON  y.Provider             = b.Provider
        AND y.DatabaseIdentifier   = b.DatabaseIdentifier
        AND y.CostDimension        = b.CostDimension
    WHERE
        y.ActualCost > b.MeanCost
        AND y.ActualCost > 1.0
        AND (
            b.StddevCost IS NULL
            OR b.StddevCost = 0
            OR (y.ActualCost - b.MeanCost) / NULLIF(b.StddevCost, 0) >= @ZThresholdMed
        );

    SELECT @@ROWCOUNT AS AnomaliesInserted;
END;
GO

    6.7 Wiring Alerts to Grafana and PagerDuty

    Anomalies sitting in a database table help no one. The final integration step connects the cost_anomalies table to an alerting pipeline. The recommended pattern uses Grafana's built-in alerting engine, which can query SQL Server directly and route alerts to Slack, PagerDuty, or email based on severity.

    The following Grafana alert rule definition (in Terraform format for reproducibility) creates a high-severity alert that fires when the cost_anomalies table contains any unacknowledged critical or high anomalies detected in the last two hours.

    # grafana_cost_alert.tf
# Requires: Grafana Terraform provider, Grafana 9.x or later
# grafana datasource must point to the dbfinops SQL Server instance

resource "grafana_alert_rule" "db_cost_anomaly_critical" {
  name            = "Database Cost Anomaly — High/Critical"
  folder_uid      = grafana_folder.finops.uid
  group_name      = "DatabaseCostAlerts"
  for             = "5m"     # must be firing for 5 minutes before alert triggers
  condition       = "threshold"
  no_data_state   = "OK"
  exec_err_state  = "Alerting"

  data {
    ref_id = "A"
    query_type = ""
    relative_time_range {
      from = 7200   # 2 hours in seconds
      to   = 0
    }
    datasource_uid = var.grafana_mssql_datasource_uid
    model = jsonencode({
      rawSql = <<-SQL
        SELECT
          COUNT(*)                          AS anomaly_count,
          NOW()                             AS "time",
          MAX(deviation_pct)                AS max_deviation_pct,
          STRING_AGG(
            database_identifier || ' (' || cost_dimension || '): '
            || ROUND(deviation_pct::NUMERIC, 1) || '% above expected',
            E'\n' ORDER BY deviation_pct DESC
          )                                 AS anomaly_summary
        FROM dbfinops.cost_anomalies
        WHERE
          severity IN ('critical', 'high')
          AND acknowledged = FALSE
          AND detected_at >= NOW() - INTERVAL '2 hours'
      SQL
      format = "table"
    })
  }

  data {
    ref_id     = "threshold"
    query_type = "expression"
    datasource_uid = "-100"
    model = jsonencode({
      type       = "threshold"
      refId      = "threshold"
      expression = "A"
      conditions = [{
        evaluator = {
          params = [0]
          type   = "gt"
        }
        operator  = { type = "and" }
        query     = { params = ["A"] }
        reducer   = {
          params = []
          type   = "last"
        }
        type = "query"
      }]
    })
  }

  annotations = {
    description = "One or more database cost anomalies at high or critical severity detected in the last 2 hours. Review the dbfinops.cost_anomalies table for details."
    runbook_url = "https://wiki.internal/runbooks/db-cost-anomaly"
    summary     = "Database cost anomaly detected — immediate review required"
  }

  labels = {
    severity = "high"
    team     = "platform"
    category = "finops"
  }

  notification_settings {
    contact_point   = "pagerduty-platform-oncall"
    group_wait      = "30s"
    group_interval  = "5m"
    repeat_interval = "4h"
    group_by        = ["database_identifier"]
  }
}

resource "grafana_alert_rule" "db_cost_anomaly_medium" {
  name            = "Database Cost Anomaly — Medium"
  folder_uid      = grafana_folder.finops.uid

    With this Terraform applied, critical anomalies page the on-call engineer within five minutes of detection, while medium anomalies post a Slack notification that the team can triage the following morning.     6.8 The Weekly Executive Report Query

    The dashboard is a daily operational tool. Once a week, a different audience — engineering leadership, finance, or the CTO — needs a summary that does not require reading raw SQL output. The following query produces a weekly summary formatted for direct paste into a Markdown-friendly report or a simple HTML email template.

    -- T-SQL: Weekly database cost executive summary
-- Run every Monday covering the prior calendar week (Mon-Sun)
-- Produces one row per provider with key metrics

DECLARE @today DATE = CAST(GETUTCDATE() AS DATE);
-- 1900-01-01 was a Monday, so this Monday-of-current-week math is DATEFIRST-independent
DECLARE @monday_this_week DATE =
    DATEADD(DAY, -((DATEDIFF(DAY, '1900-01-01', @today)) % 7), @today);
DECLARE @week_start DATE = DATEADD(DAY, -7, @monday_this_week);
DECLARE @week_end   DATE = DATEADD(DAY, -1, @monday_this_week);

WITH this_week AS (
    SELECT
        provider,
        SUM(unblended_cost)                     AS week_cost,
        COUNT(DISTINCT database_identifier)     AS db_count
    FROM dbfinops.daily_costs
    WHERE cost_date BETWEEN @week_start AND @week_end
    GROUP BY provider
),
prior_week AS (
    SELECT
        provider,
        SUM(unblended_cost)                     AS week_cost
    FROM dbfinops.daily_costs
    WHERE cost_date BETWEEN DATEADD(DAY, -7, @week_start)
                        AND DATEADD(DAY, -7, @week_end)
    GROUP BY provider
),
anomaly_count AS (
    SELECT
        provider,
        COUNT(*)                                AS unacked_anomalies,
        SUM(CASE WHEN severity = 'critical' THEN 1 ELSE 0 END) AS critical_count
    FROM dbfinops.cost_anomalies
    WHERE CAST(detected_at AS DATE) BETWEEN @week_start AND @week_end
      AND acknowledged = 0
    GROUP BY provider
),
top_spender AS (
    SELECT
        provider,
        database_identifier                     AS top_db,
        SUM(unblended_cost)                     AS db_cost,
        ROW_NUMBER() OVER (
            PARTITION BY provider
            ORDER BY SUM(unblended_cost) DESC
        )                                       AS rn
    FROM dbfinops.daily_costs
    WHERE cost_date BETWEEN @week_start AND @week_end
    GROUP BY provider, database_identifier
)
SELECT
    tw.provider,
    tw.db_count                                                AS databases_tracked,
    CAST(ROUND(tw.week_cost, 2) AS DECIMAL(18,2))              AS total_week_cost,
    CAST(ROUND(pw.week_cost, 2) AS DECIMAL(18,2))              AS prior_week_cost,
    CAST(ROUND(tw.week_cost - pw.week_cost, 2) AS DECIMAL(18,2)) AS week_delta,
    CAST(ROUND(
        CASE WHEN pw.week_cost > 0
             THEN (tw.week_cost - pw.week_cost) / pw.week_cost * 100.0
             ELSE NULL
        END, 1) AS DECIMAL(18,1))                               AS pct_change,
    COALESCE(ac.unacked_anomalies, 0)                          AS open_anomalies,
    COALESCE(ac.critical_count, 0)                             AS critical_anomalies,
    ts.top_db                                                  AS highest_cost_database,
    CAST(ROUND(ts.db_cost, 2) AS DECIMAL(18,2))                AS highest_cost_db_spend
FROM
    this_week tw
    LEFT JOIN prior_week pw    ON pw.provider = tw.provider
    LEFT JOIN anomaly_count ac ON ac.provider = tw.provider
    LEFT JOIN top_spender ts   ON ts.provider = tw.provider AND ts.rn = 1
ORDER BY
    tw.week_cost DESC;

    Pair this with a simple Python script that runs the query and sends the output via AWS SES, SendGrid, or an internal SMTP relay, and the weekly report becomes zero-effort for the people who need it most. The structure — total spend, week-over-week delta, open anomalies, top spender — answers the three questions leadership asks every week: "Are we spending more than last week?", "Is anything on fire?", and "What's our biggest database cost right now?"

    6.9 Putting It All Together: The Dashboard Layout

    The individual queries from section 6.5 compose into a dashboard with a clear visual hierarchy. The recommended layout for Grafana follows a three-row structure:

    graph TD
    A[Row 1: Executive Summary\nMTD spend, WoW change, anomalies, RI coverage] --> B[Row 2: Provider & Database Breakdown\nMoM cost table + dimension drilldown]
    B --> C[Row 3: Engineering Detail\nStorage trend, top cost queries, RI gap]
    C --> D[Row 4: Anomaly Log\nfull cost_anomalies table with Acknowledge action]

    *The dashboard's visual hierarchy: each row narrows from a glanceable executive number down to the raw, actionable anomaly log.*

    Row 1 — Executive Summary (4 stat panels)

  • → Total MTD spend across all providers (single number, colored red/amber/green against budget threshold)
  • → Week-over-week percentage change (sparkline + delta badge)
  • → Open unacknowledged anomalies (count, red if any critical)
  • → Reserved Instance / Commitment utilization percentage

    • Row 2 — Provider and Database Breakdown (2 panels)

  • → Month-over-month cost change table (Query 1 from section 6.5), filterable by provider and environment
  • → Cost dimension breakdown time series (Query 2), drilldown activated by clicking a database row in the adjacent table

    • Row 3 — Engineering Detail (3 panels)

  • → Storage growth trend with 30-day projection (Query 4), one line per database
  • → Top cost-attributing queries table (Query 5), sortable by attributed cost or execution time
  • → RI/commitment coverage gap table (Query 3), sorted by on-demand spend descending

    • Row 4 — Anomaly Log (1 full-width panel)

  • → Raw table view of `cost_anomalies` with filters for severity, provider, and acknowledged status
  • → Includes an "Acknowledge" button wired to a Grafana panel action that sets `acknowledged = TRUE` and records the acknowledging user

    • This layout works equally well as a static Metabase dashboard, a Tableau workbook, or a simple HTML page generated from cron-scheduled SQL queries — the choice of visualization tool matters less than the discipline of reviewing the dashboard consistently.

    Key Takeaways

  • → **Visibility creates accountability**: a database cost dashboard does not save money directly, but it eliminates the weeks-long lag between a cost anomaly occurring and someone noticing it, which is where most avoidable cloud spend accumulates.
  • → **Normalize cost data across providers**: storing AWS, Azure, and GCP costs in a single `dbfinops.daily_costs` schema with consistent dimensions (provider, database_identifier, cost_dimension, environment, team) enables cross-cloud comparison and prevents costs from hiding in provider-specific abstractions.
  • → **Connect cost to workload**: populating `query_cost_attribution` with per-query cost estimates transforms a finance dashboard into an engineering tool — it lets a DBA point to a specific query and say "optimizing this saves us a measurable amount per month."
  • → **Automate anomaly detection, not just reporting**: a rolling z-score function running nightly against the cost table catches unexpected spikes within 24 hours; without automation, the same spike might hide for a billing cycle.
  • → **Tailor alert routing to severity**: critical anomalies warrant immediate on-call paging; medium anomalies warrant a next-morning Slack notification; routing both to PagerDuty guarantees alert fatigue and guarantees the alerts get ignored.
