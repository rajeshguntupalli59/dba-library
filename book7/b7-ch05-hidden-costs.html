Chapter 5: The Hidden Costs: Data Transfer, Snapshots, and Logs

Most engineering teams can recite their RDS instance cost to within a few dollars. Almost none can tell you what they spent on data transfer last month. That gap between what teams track and what actually appears on the bill is where database budgets quietly hemorrhage. Across AWS, Azure, and GCP, data egress fees, automated snapshot accumulation, and unmanaged log retention collectively account for 18–35% of total database spend for organizations running production workloads at scale — and the majority of that cost is entirely recoverable with targeted intervention. This chapter shows you exactly where to find these charges in your bill, how to calculate their true cost, and how to automate the controls that eliminate them. Organizations that complete the optimizations in this chapter typically recover $2,000 to $40,000 per month depending on data volumes, with the largest savings coming from cross-region replication patterns that were designed for resilience without any cost accounting applied to them.

---

5.1 Understanding Data Transfer Pricing: The Billing Model Nobody Reads

Data transfer pricing is intentionally complex. Cloud providers publish egress rates buried in footnotes, vary them by region pair, and charge differently depending on whether traffic crosses availability zones, regions, or the open internet. Understanding the layered model before you optimize is not optional — misreading it leads to architectural changes that save nothing.

AWS Data Transfer Tiers (2024 pricing, us-east-1 baseline)

| Traffic Type | Cost |

|---|---|

| Inbound (ingress) | $0.00 |

| Same-AZ, same-region (private IP) | $0.00 |

| Cross-AZ within same region | $0.02/GB each direction |

| Cross-region | $0.02–$0.09/GB depending on destination |

| Internet egress (first 10TB/month) | $0.09/GB |

| Internet egress (next 40TB/month) | $0.085/GB |

| RDS to EC2 in same AZ (public IP) | $0.02/GB |

The last row deserves a second read. An application server connecting to an RDS instance in the same availability zone over the instance's public DNS endpoint incurs cross-AZ charges even though both resources are physically in the same building. This single misconfiguration — using the public endpoint instead of the private endpoint — generates measurable egress charges on databases processing more than a few hundred gigabytes per month.

Azure Data Transfer Tiers (2024 pricing, East US baseline)

| Traffic Type | Cost |

|---|---|

| Inbound | $0.00 |

| Same-region, same VNet | $0.00 |

| Cross-region (within continent) | $0.02–$0.05/GB |

| Cross-continent | $0.05–$0.08/GB |

| Internet egress (first 5GB/month) | $0.00 |

| Internet egress (over 5GB) | $0.087/GB |

GCP Data Transfer Tiers (2024 pricing, us-central1 baseline)

| Traffic Type | Cost |

|---|---|

| Inbound | $0.00 |

| Same-zone | $0.00 |

| Cross-zone, same region | $0.01/GB |

| Cross-region (North America) | $0.01/GB |

| Cross-region (other) | $0.02–$0.08/GB |

| Internet egress | $0.085–$0.23/GB |

GCP's cross-zone pricing is lower than AWS — $0.01/GB vs $0.02/GB — making the cost of Multi-AZ equivalent patterns roughly half the AWS price. This is a relevant consideration when comparing total cost of ownership across providers for read-heavy workloads with multiple replicas.

5.2 Cross-AZ and Cross-Region Traffic: Finding and Fixing the Expensive Flows

The most common source of unexpected data transfer costs is cross-AZ traffic generated by Multi-AZ RDS configurations combined with application servers spread across availability zones. In a standard production setup, you have three application servers distributed across three AZs for high availability, and an RDS Multi-AZ instance whose primary is in one of those AZs. Every application server not co-located with the RDS primary is paying $0.02/GB in each direction for every byte they exchange.

For a database processing 10TB of query results per month to application servers (a moderate OLTP workload), this costs:

  • → 10TB × $0.02/GB = 10,000GB × $0.02 = **$200/month cross-AZ egress**
  • → Plus return traffic: another **$200/month**
  • → Total cross-AZ penalty: **$400/month for a single database**

    • This compounds with read replicas. An RDS instance with three read replicas spread across AZs for distribution generates replication traffic costs on top of application traffic costs.

    Identifying Cross-AZ Traffic Sources

    On AWS, VPC Flow Logs capture the source and destination of all traffic including AZ origins. The following query, run against Flow Logs exported to CloudWatch Logs Insights, identifies the largest cross-AZ flows involving database ports.

    -- CloudWatch Logs Insights query (not SQL — uses Logs Insights syntax)
-- Run this in the CloudWatch console under Logs Insights against your VPC Flow Log group
-- Paste this directly into the query editor:
-- fields @timestamp, srcAddr, dstAddr, dstPort, bytes, azId
-- | filter dstPort in [1433]
-- | filter srcAddr not like /^10\.0\.1\./   -- replace with your primary AZ subnet
-- | stats sum(bytes) as total_bytes by srcAddr, dstAddr, dstPort
-- | sort total_bytes desc
-- | limit 20

-- For SQL Server: query sys.dm_exec_connections to see connection origins
-- Run this on your RDS for SQL Server instance to identify which client IPs are connecting
SELECT
    c.client_net_address AS client_ip,
    COUNT(*) AS connection_count,
    s.program_name AS application_name,
    s.login_name
FROM sys.dm_exec_connections c
JOIN sys.dm_exec_sessions s ON c.session_id = s.session_id
WHERE c.client_net_address IS NOT NULL
GROUP BY c.client_net_address, s.program_name, s.login_name
ORDER BY connection_count DESC;

    Cross-reference the client_addr values against your AWS subnet map. Any connection coming from a subnet in a different AZ than your RDS primary is generating cross-AZ charges.

    Fixing Cross-AZ Traffic: Three Approaches

    *Option 1: Subnet-Aware Connection Routing*

    Configure your application's database connection pool to prefer the endpoint nearest to its own AZ. For applications using a service mesh or a proxy layer like SQL Server Always On routing or a proxy layer, configure topology-aware routing. This is the lowest-risk change.

    *Option 2: Read Replica Placement*

    If your workload is read-heavy, place one read replica in each AZ where application servers run. Configure read traffic to route to the local replica. For a three-AZ setup processing 5TB of reads per month per AZ, this eliminates cross-AZ read traffic entirely. The cost of an additional read replica (for example, an db.r6i.large at approximately $146/month) is offset immediately if cross-AZ read traffic exceeds 7,300GB/month per AZ.

    *Option 3: Private Endpoint Enforcement*

    Audit all connection strings and ensure every application is connecting to the private DNS endpoint, not the public endpoint. This single change eliminates the class of cross-AZ charges that arise from public-IP routing.

    #!/usr/bin/env python3
"""
cross_az_detector.py
Scans RDS instances and their connecting EC2 instances,
flags mismatched AZ combinations that generate cross-AZ traffic costs.
Run on a schedule (daily recommended) via Lambda or cron.
"""

import boto3
import json
from datetime import datetime, timedelta
from collections import defaultdict

def get_rds_primary_az(rds_client, db_instance_id):
    """Return the AZ of the primary RDS instance."""
    response = rds_client.describe_db_instances(DBInstanceIdentifier=db_instance_id)
    return response['DBInstances'][0]['AvailabilityZone']

def get_ec2_instances_by_az(ec2_client):
    """Return dict mapping AZ to list of instance IDs and private IPs."""
    az_map = defaultdict(list)
    paginator = ec2_client.get_paginator('describe_instances')
    for page in paginator.paginate(Filters=[{'Name': 'instance-state-name', 'Values': ['running']}]):
        for reservation in page['Reservations']:
            for instance in reservation['Instances']:
                az = instance['Placement']['AvailabilityZone']
                az_map[az].append({
                    'id': instance['InstanceId'],
                    'private_ip': instance.get('PrivateIpAddress', 'unknown'),
                    'tags': {t['Key']: t['Value'] for t in instance.get('Tags', [])}
                })
    return az_map

def estimate_cross_az_cost(cloudwatch_client, rds_instance_id, days=30):
    """
    Estimate data transfer cost by looking at NetworkReceiveThroughput
    and NetworkTransmitThroughput on the RDS instance.
    Returns estimated GB transferred.
    """
    end_time = datetime.utcnow()
    start_time = end_time - timedelta(days=days)
    
    total_gb = 0
    for metric in ['NetworkReceiveThroughput', 'NetworkTransmitThroughput']:
        response = cloudwatch_client.get_metric_statistics(
            Namespace='AWS/RDS',
            MetricName=metric,
            Dimensions=[{'Name': 'DBInstanceIdentifier', 'Value': rds_instance_id}],
            StartTime=start_time,
            EndTime=end_time,
            Period=86400,  # daily datapoints
            Statistics=['Average']
        )
        
        # Average bytes/sec * seconds_per_day * days = total bytes
        for dp in response['Datapoints']:
            bytes_per_day = dp['Average'] * 86400
            total_gb += bytes_per_day / (1024**3)
    
    return round(total_gb, 2)

def main():
    region = 'us-east-1'
    rds_client = boto3.client('rds', region_name=region)
    ec2_client = boto3.client('ec2', region_name=region)
    cw_client = boto3.client('cloudwatch', region_name=region)
    
    report = {
        'generated_at': datetime.utcnow().isoformat(),
        'region': region,
        'findings': []
    }
    
    # Get all RDS instances
    paginator = rds_client.get_paginator('describe_db_instances')
    ec2_by_az = get_ec2_instances_by_az(ec2_client)
    
    for page in paginator.paginate():
        for db in page['DBInstances']:
            db_id = db['DBInstanceIdentifier']
            db_az = db['AvailabilityZone']
            db_endpoint = db.get('Endpoint', {}).get('Address', '')
            is_multi_az = db.get('MultiAZ', False)
            
            # Count EC2 instances in other AZs
            cross_az_instances = []
            for az, instances in ec2_by_az.items():
                if az != db_az:
                    cross_az_instances.extend(instances)
            
            total_gb_30d = estimate_cross_az_cost(cw_client, db_id)
            # Assume 50% of traffic crosses AZ (conservative estimate)
            estimated_cross_az_gb = total_gb_30d * 0.5
            estimated_monthly_cost = estimated_cross_az_gb * 0.02 * 2  # both directions
            
            if estimated_monthly_cost > 10:  # Only report if > $10/month
                finding = {
                    'db_instance': db_id,
                    'db_az': db_az,
                    'is_multi_az': is_multi_az,
                    'total_network_gb_30d': total_gb_30d,
                    'estimated_cross_az_gb_30d': estimated_cross_az_gb,
                    'estimated_monthly_cost_usd': round(estimated_monthly_cost, 2),
                    'ec2_instances_in_other_azs': len(cross_az_instances),
                    'recommendation': (
                        'Place read replica in each application AZ, '
                        'or configure topology-aware routing. '
                        f'Estimated savings: ${round(estimated_monthly_cost * 0.7, 2)}/month'
                    )
                }
                report['findings'].append(finding)
    
    # Sort by cost impact
    report['findings'].sort(key=lambda x: x['estimated_monthly_cost_usd'], reverse=True)
    
    total_recoverable = sum(f['estimated_monthly_cost_usd'] for f in report['findings'])
    report['total_estimated_recoverable_usd_monthly'] = round(total_recoverable, 2)
    
    print(json.dumps(report, indent=2))
    
    # In production: push to S3, SNS, or Slack webhook
    # s3_client.put_object(Bucket='finops-reports', Key=f'cross-az/{datetime.utcnow().date()}.json', Body=json.dumps(report))

if __name__ == '__main__':
    main()

    5.3 Snapshot Economics: Retention Policies That Cost Fortunes

    Automated snapshots are not free storage. They feel free because most cloud providers offer a limited window at no charge — AWS gives you free snapshot storage equal to the size of your database — but that boundary erodes almost immediately in practice.

    AWS Snapshot Pricing

    AWS charges $0.095/GB-month for snapshots stored in gp2/gp3 format beyond the provisioned database storage size. A 500GB database with 35 automated snapshots (the result of setting a 35-day retention period for a compliance requirement) stores approximately:

  • → First 500GB: **free** (offset by provisioned storage payment)
  • → Remaining ~17,000GB (34 snapshots × 500GB): 17,000 × $0.095 = **$1,615.00/month**

    • The relationship between retention period and cost is linear. Moving from a 35-day to a 7-day retention window for development databases reduces snapshot storage by 80%.

    Azure SQL Backup Pricing

    Azure charges for backup storage beyond the provisioned database size in the LRS tier at $0.0375/GB-month for locally redundant storage and $0.115/GB-month for geo-redundant storage. Point-in-time restore relies on full, differential, and log backups — the log backup volume grows proportionally with write throughput, making high-write databases disproportionately expensive to back up.

    GCP Cloud SQL Backup Pricing

    GCP charges $0.08/GB-month for automated backups. Unlike AWS, there is no free tier equivalent; you pay for the full snapshot volume from the first byte.

    Finding Your Current Snapshot Footprint

    Snapshot Optimization Strategy by Environment

    Blanket retention policies applied uniformly across production, staging, and development databases are the most expensive snapshot mistake. A tiered approach based on environment and compliance requirement cuts snapshot spend by 40–70% in most organizations:

    | Environment | Recommended Retention | Rationale |

    |---|---|---|

    | Production (regulated) | 35 days automated + 12 monthly manual | Compliance baseline |

    | Production (standard) | 7 days automated + 4 weekly manual | Covers most restore scenarios |

    | Staging | 3 days | Rarely restored, easily recreated |

    | Development | 1 day or snapshot-on-demand only | No production data, no restore need |

    | Data warehouse | Weekly only | Full rebuilds cheaper than snapshots |

    Manual snapshots that are never deleted are the second largest snapshot cost driver. Teams create manual snapshots before schema migrations, forget to delete them, and those snapshots accumulate for years. The following script audits and remediates orphaned manual snapshots.

    #!/usr/bin/env python3
"""
snapshot_cost_auditor.py
Identifies overdue manual snapshots, orphaned snapshots from deleted databases,
and databases with excessive automated retention.
Designed to run weekly via EventBridge + Lambda.
"""

import boto3
import json
from datetime import datetime, timedelta, timezone
from dataclasses import dataclass, asdict
from typing import List

@dataclass
class SnapshotFinding:
    snapshot_id: str
    db_instance: str
    snapshot_type: str
    age_days: int
    size_gb: int
    monthly_cost_usd: float
    issue: str
    action: str

def calculate_monthly_cost(size_gb: int) -> float:
    """AWS snapshot pricing: $0.095/GB-month."""
    return round(size_gb * 0.095, 2)

def get_active_db_instances(rds_client) -> set:
    """Return set of currently active DB instance identifiers."""
    active = set()
    paginator = rds_client.get_paginator('describe_db_instances')
    for page in paginator.paginate():
        for db in page['DBInstances']:
            active.add(db['DBInstanceIdentifier'])
    return active

def audit_snapshots(rds_client, max_manual_age_days=90, dev_patterns=None) -> List[SnapshotFinding]:
    """
    Audit all RDS snapshots for cost issues.
    dev_patterns: list of substrings that identify dev/staging instances (e.g., ['dev', 'staging', 'test'])
    """
    if dev_patterns is None:
        dev_patterns = ['dev', 'staging', 'test', 'sandbox', 'qa']

    active_instances = get_active_db_instances(rds_client)
    findings = []
    now = datetime.now(timezone.utc)

    paginator = rds_client.get_paginator('describe_db-snapshots')
    # Note: actual boto3 method is describe_db_snapshots
    paginator = rds_client.get_paginator('describe_db_snapshots')

    for page in paginator.paginate():
        for snap in page['DBSnapshots']:
            snap_id = snap['DBSnapshotIdentifier']
            db_id = snap['DBInstanceIdentifier']
            snap_type = snap['SnapshotType']
            size_gb = snap.get('AllocatedStorage', 0)
            status = snap['Status']
            created_raw = snap.get('SnapshotCreateTime')

            if status != 'available':
                continue

            age_days = 0
            if created_raw:
                age_days = (now - created_raw).days

            monthly_cost = calculate_monthly_cost(size_gb)

            # 1. Orphaned snapshot: source DB no longer exists
            if db_id not in active_instances and snap_type == 'manual':
                findings.append(SnapshotFinding(
                    snapshot_id=snap_id,
                    db_instance=db_id,
                    snapshot_type=snap_type,
                    age_days=age_days,
                    size_gb=size_gb,
                    monthly_cost_usd=monthly_cost,
                    issue='orphaned_snapshot',
                    action=f'Delete immediately — source instance no longer exists. Saves ${monthly_cost}/month.'
                ))
                continue

            # 2. Ancient manual snapshot
            if snap_type == 'manual' and age_days > max_manual_age_days:
                findings.append(SnapshotFinding(
                    snapshot_id=snap_id,
                    db_instance=db_id,
                    snapshot_type=snap_type,
                    age_days=age_days,
                    size_gb=size_gb,
                    monthly_cost_usd=monthly_cost,
                    issue='stale_manual_snapshot',
                    action=(
                        f'Manual snapshot is {age_days} days old. '
                        f'Review and delete if no longer needed for migration/compliance. '
                        f'Saves ${monthly_cost}/month.'
                    )
                ))

            # 3. Dev/staging instance with automated snapshots older than 3 days
            is_dev = any(p.lower() in db_id.lower() for p in dev_patterns)
            if is_dev and snap_type == 'automated' and age_days > 3:
                findings.append(SnapshotFinding(
                    snapshot_id=snap_id,
                    db_instance=db_id,
                    snapshot_type=snap_type,
                    age_days=age_days,
                    size_gb=size_gb,
                    monthly_cost_usd=monthly_cost,
                    issue='excessive_dev_retention',
                    action=(
                        f'Dev/staging instance retaining automated snapshots for {age_days} days. '
                        f'Reduce BackupRetentionPeriod to 1. '
                        f'Estimated savings: ${monthly_cost}/month per excess snapshot.'
                    )
                ))

    return sorted(findings, key=lambda f: f.monthly_cost_usd, reverse=True)


def apply_retention_policy(rds_client, db_instance_id: str, retention_days: int, dry_run=True):
    """Modify automated backup retention for a DB instance."""
    if dry_run:
        print(f'[DRY RUN] Would set BackupRetentionPeriod={retention_days} on {db_instance_id}')
        return
    rds_client.modify_db_instance(
        DBInstanceIdentifier=db_instance_id,
        BackupRetentionPeriod=retention_days,
        ApplyImmediately=False  # Apply during next maintenance window
    )
    print(f'Updated retention to {retention_days} days for {db_instance_id}')


def delete_snapshot(rds_client, snapshot_id: str, dry_run=True):
    """Delete a manual snapshot after confirmation."""
    if dry_run:
        print(f'[DRY RUN] Would delete snapshot: {snapshot_id}')
        return
    rds_client.delete_db_snapshot(DBSnapshotIdentifier=snapshot_id)
    print(f'Deleted snapshot: {snapshot_id}')


def main():
    rds_client = boto3.client('rds', region_name='us-east-1')

    findings = audit_snapshots(rds_client, max_manual_age_days=90)

    total_recoverable = sum(f.monthly_cost_usd for f in findings)

    report = {
        'generated_at': datetime.utcnow().isoformat(),
        'total_findings': len(findings),
        'total_recoverable_monthly_usd': round(total_recoverable, 2),
        'findings': [asdict(f) for f in findings]
    }

    print(json.dumps(report, indent=2))

    # Categorize findings
    orphaned = [f for f in findings if f.issue == 'orphaned_snapshot']
    stale_manual = [f for f in findings if f.issue == 'stale_manual_snapshot']
    dev_excess = [f for f in findings if f.issue == 'excessive_dev_retention']

    print(f'\n=== SUMMARY ===')
    print(f'Orphaned snapshots (auto-deletable):     {len(orphaned)}, '
          f'${sum(f.monthly_cost_usd for f in orphaned):.2f}/month')
    print(f'Stale manual snapshots (review required): {len(stale_manual)}, '
          f'${sum(f.monthly_cost_usd for f in stale_manual):.2f}/month')
    print(f'Dev/staging over-retention:               {len(dev_excess)}, '
          f'${sum(f.monthly_cost_usd for f in dev_excess):.2f}/month')
    print(f'Total recoverable:                        ${total_recoverable:.2f}/month')

    # Uncomment to execute remediations (start with dry_run=True)
    # for f in orphaned:
    #     delete_snapshot(rds_client, f.snapshot_id, dry_run=True)

if __name__ == '__main__':
    main()

    Cross-Region Snapshot Replication Costs

    Snapshot replication to a second region for disaster recovery doubles your snapshot storage costs in the destination region and adds a one-time data transfer charge per replication. For a 1TB database snapshot:

  • → Source region storage: 1TB × $0.095 = **$97.50/month**
  • → Destination region storage: 1TB × $0.095 = **$97.50/month**
  • → Transfer cost for initial replication: 1TB × $0.02 = **$20.48 one-time**

    • The storage cost in the destination region is often missed entirely. Teams account for the transfer charge during architecture review but forget that the replicated snapshot occupies equal storage in the destination region at the same per-GB rate. This doubles the effective snapshot storage cost for any database using cross-region replication for DR.

    The alternative: For databases where the DR requirement is "restore within hours, not minutes," evaluate whether cross-region snapshot replication is necessary, or whether recreating the database from application-level backups (SQL Server BACPAC exports or native backup files stored in S3/Blob Storage) achieves the same RTO at a fraction of the cost. Application-level exports stored as compressed files in object storage typically reduce DR storage costs by 70–90% versus binary snapshot replication.

    5.4 Log Retention and the Bill Nobody Expected

    Database logs are generated constantly and, left unmanaged, grow without limit. The costs accumulate across three dimensions: log storage on the database instance itself, log export to cloud monitoring services, and log retention in those monitoring services. Each dimension has a different pricing model and a different remediation approach.

    CloudWatch Logs: The Silent Cost Multiplier

    AWS RDS for SQL Server can export log types to CloudWatch Logs — primarily the SQL Server error log and the SQL Agent log. Each log type enabled multiplies CloudWatch Logs ingestion costs ($0.50/GB ingested) and storage costs ($0.03/GB-month) against the volume of logs generated.

    The most expensive single configuration is enabling general query logging on a high-throughput OLTP database. A database handling 5,000 queries per second generates approximately 1–3GB of query log data per hour. At $0.50/GB ingestion:

  • → 2GB/hour × 24 hours × 30 days = 1,440GB/month
  • → 1,440GB × $0.50 = **$720/month in CloudWatch ingestion alone**
  • → Plus 1,440GB × $0.03 retention = **$43.20/month**
  • → **Total: $763.20/month for general query logging on a single database**

    SQL Server Query Store deserves special attention. It is the single highest-value observability mechanism for production SQL Server because it aggregates query performance data inside the database engine itself, with no per-query log write overhead and no CloudWatch cost. Everything verbose logging tells you (which queries ran, how long, how often) is available from Query Store and sys.dm_exec_query_stats at a fraction of the infrastructure cost.

    -- SQL Server equivalent: sys.dm_exec_query_stats for top queries
SELECT TOP 20
    SUBSTRING(qt.text, (qs.statement_start_offset/2)+1,
        ((CASE qs.statement_end_offset
          WHEN -1 THEN DATALENGTH(qt.text)
          ELSE qs.statement_end_offset END
          - qs.statement_start_offset)/2)+1) AS query_text,
    qs.execution_count,
    ROUND(qs.total_elapsed_time / 1000.0, 2) AS total_elapsed_ms,
    ROUND(qs.total_elapsed_time / qs.execution_count / 1000.0, 2) AS avg_elapsed_ms,
    ROUND(100.0 * qs.total_elapsed_time /
          SUM(qs.total_elapsed_time) OVER (), 2) AS pct_total_time,
    qs.total_logical_reads,
    qs.total_logical_writes
FROM sys.dm_exec_query_stats AS qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS qt
WHERE qs.execution_count > 10
ORDER BY qs.total_elapsed_time DESC;

    Automating Log Retention Policies

    Log groups without retention policies are a debt that compounds monthly. The following script enforces retention policies across all RDS-related CloudWatch Log groups in an account.

    #!/usr/bin/env python3
"""
log_retention_enforcer.py
Sets retention policies on all /aws/rds log groups that lack them.
Maps log group types to appropriate retention windows.
Safe to run repeatedly (idempotent).
"""

import boto3
import re
from typing import Dict, Optional

# Define retention policy by log type (in days)
RETENTION_POLICY: Dict[str, int] = {
    'slowquery':       30,   # Slow query logs: 30 days for trend analysis
    'error':           90,   # Error logs: 90 days for incident investigation
    'general':         7,    # General query logs: if enabled, keep minimal window
    'audit':           365,  # Audit logs: 1 year (common compliance baseline)
    'agent':           30,   # SQL Agent logs: short retention
    'upgrade':         30,   # Upgrade logs: short retention
    'default':         30,   # Fallback for unrecognized log types
}

def infer_log_type(log_group_name: str) -> str:
    """Infer the log type from the log group name."""
    lower = log_group_name.lower()
    for log_type in RETENTION_POLICY:
        if log_type in lower:
            return log_type
    return 'default'

def enforce_retention(region: str = 'us-east-1', dry_run: bool = True):
    logs_client = boto3.client('logs', region_name=region)

    paginator = logs_client.get_paginator('describe_log_groups')
    updated = []
    already_set = []
    skipped = []

    for page in paginator.paginate(logGroupNamePrefix='/aws/rds'):
        for group in page['logGroups']:
            name = group['logGroupName']
            current_retention = group.get('retentionInDays')
            stored_bytes = group.get('storedBytes', 0)
            stored_gb = stored_bytes / (1024 ** 3)

            log_type = infer_log_type(name)
            target_retention = RETENTION_POLICY[log_type]

            if current_retention is None:
                action = 'SET_RETENTION'
            elif current_retention > target_retention * 2:
                action = 'REDUCE_RETENTION'
            else:
                action = 'OK'

            if action in ('SET_RETENTION', 'REDUCE_RETENTION'):
                monthly_cost_usd = stored_gb * 0.03
                record = {
                    'log_group': name,
                    'log_type': log_type,
                    'current_retention': current_retention,
                    'target_retention': target_retention,
                    'stored_gb': round(stored_gb, 3),
                    'monthly_storage_cost_usd': round(monthly_cost_usd, 4),
                    'action': action
                }
                updated.append(record)
                print(f"{'[DRY RUN] ' if dry_run else ''}Setting retention={target_retention}d "
                      f"on {name} (was: {current_retention}, type: {log_type}, "
                      f"stored: {stored_gb:.2f}GB, ${monthly_cost_usd:.4f}/mo)")

                if not dry_run:
                    logs_client.put_retention_policy(
                        logGroupName=name,
                        retentionInDays=target_retention
                    )
            else:
                already_set.append(name)

    print(f'\n=== RETENTION ENFORCEMENT SUMMARY ===')
    print(f'Log groups updated/to update:  {len(updated)}')
    print(f'Log groups already compliant:  {len(already_set)}')
    total_monthly_cost = sum(r['monthly_storage_cost_usd'] for r in updated)
    print(f'Storage cost affected:         ${total_monthly_cost:.2f}/month')
    print(f'Dry run:                       {dry_run}')

    return updated

if __name__ == '__main__':
    # Start with dry_run=True to review before applying
    enforce_retention(region='us-east-1', dry_run=True)

    5.5 Multi-Region Replication: Calculating the True Cost of Global Architectures

    The blue Primary region (us-east-1) ships log to the green Secondary region (us-west-2) — the thick ‘sync GB’ arrow with its dollar badge is the data-transfer charge, the single largest line item at $120. Two quieter costs hide below: cross-AZ traffic inside the primary and snapshot storage at $45, plus $80 in replication operations. The $245/month total is an estimate, but the shape of the bill is the lesson: the replica is never free, and multi-region designs should budget transfer before compute.

    Cross-region replication is where the largest single-source cost surprises live. Engineers designing multi-region database architectures focus on latency and failover characteristics; the data transfer cost of keeping the secondary region synchronized is rarely modeled during the design phase.

    AWS RDS Cross-Region Read Replicas

    An RDS cross-region read replica receives a continuous stream of transaction log records from the primary. The replication traffic volume equals the database's write throughput. For a database writing 500MB/hour:

  • → Replication data per month: 500MB × 24 × 30 = 360GB/month
  • → Cross-region transfer at $0.02/GB (us-east-1 to us-west-2): **$7.20/month** on replication alone
  • → For a write-heavy database at 5GB/hour: 3,600GB × $0.02 = **$72/month**

    • These numbers are manageable. The expensive scenario is when application servers in the secondary region also read from the replica — adding application read traffic to the replication traffic in the same region, and requiring careful accounting of whether reads are served locally or pulled cross-region.

    Cross-Region Replication Pricing for SQL Server

    Cross-region replication for SQL Server adds a distinct cost tier that surprises teams coming from single-region deployments. In addition to full instance costs in the secondary region, every gigabyte of replication traffic crossing regions is billed at inter-region transfer rates (approximately $0.02/GB on AWS). For a write-heavy SQL Server workload with a cross-region read replica:

  • → 500 GB/day of transaction log replication traffic (a moderate OLTP workload)
  • → Replication transfer: 15,000 GB/month × $0.02 = **$300/month in transfer**
  • → Plus the full secondary-region instance cost — a replica is billed at the same hourly rate as the primary, including the SQL Server license portion

    • This replication transfer charge does not appear on most single-region cost models because it is a separate line item from the instance cost, storage cost, and snapshot cost. Run the following commands to estimate your cross-region replication transfer volume from CloudWatch network metrics:

    # CloudWatch: estimate cross-region replication transfer for the last 30 days
# NetworkTransmitThroughput is bytes/sec leaving the primary instance
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name NetworkTransmitThroughput \
  --dimensions Name=DBInstanceIdentifier,Value=YOUR_PRIMARY_ID \
  --start-time $(date -u -d '30 days ago' '+%Y-%m-%dT%H:%M:%SZ') \
  --end-time $(date -u '+%Y-%m-%dT%H:%M:%SZ') \
  --period 86400 \
  --statistics Average \
  --query 'sort_by(Datapoints, &Timestamp)[*].[Timestamp, Average]' \
  --output table

# Monthly GB transferred ~= Average bytes/sec x 2,592,000 sec / 1e9
# Multiply by $0.02/GB for the cross-region transfer estimate
# Then add the full secondary-region instance cost (same rate as primary, license included)

    Google Cloud SQL Cross-Region Replicas

    GCP Cloud SQL cross-region replicas transfer replication data at $0.01/GB within North America and $0.02–$0.08/GB for other region pairs — roughly half the AWS equivalent cost for North America regions. However, unlike AWS, GCP charges for the replica instance at full price regardless of whether it is actively serving reads. An idle cross-region replica on GCP costs as much as an active one.

    Modeling Total Multi-Region Cost

    #!/usr/bin/env python3
"""
multiregion_cost_model.py
Calculates the true monthly cost of a multi-region database architecture.
Accounts for instance costs, storage, replication transfer, and snapshot replication.
Adjust the parameters below for your specific workload.
"""

from dataclasses import dataclass
from typing import List

@dataclass
class RegionConfig:
    name: str
    instance_type: str
    instance_monthly_usd: float
    storage_gb: int
    storage_cost_per_gb: float = 0.115   # gp3 pricing
    is_primary: bool = False
    serves_reads: bool = True
    replica_count: int = 0               # read replicas within this region

@dataclass
class ReplicationConfig:
    write_throughput_gb_per_hour: float
    transfer_cost_per_gb: float          # cross-region rate

def calculate_total_cost(
    regions: List[RegionConfig],
    replication: ReplicationConfig,
    snapshot_gb: int,
    snapshot_transfer_cost_per_gb: float = 0.02,
    secondary_snapshot_regions: int = 1,
) -> dict:

    breakdown = {}
    total = 0.0

    # Instance costs
    instance_total = sum(r.instance_monthly_usd * (1 + r.replica_count) for r in regions)
    breakdown['instance_costs_usd'] = round(instance_total, 2)
    total += instance_total

    # Storage costs
    storage_total = sum(r.storage_gb * r.storage_cost_per_gb for r in regions)
    breakdown['storage_costs_usd'] = round(storage_total, 2)
    total += storage_total

    # Replication transfer cost (write throughput × hours × days × rate)
    replication_gb_per_month = replication.write_throughput_gb_per_hour * 24 * 30
    secondary_regions = [r for r in regions if not r.is_primary]
    replication_transfer_total = (
        replication_gb_per_month
        * len(secondary_regions)
        * replication.transfer_cost_per_gb
    )
    breakdown['replication_transfer_usd'] = round(replication_transfer_total, 2)
    total += replication_transfer_total

    # Snapshot costs: primary region
    primary_snapshot_cost = snapshot_gb * 0.095
    breakdown['snapshot_primary_region_usd'] = round(primary_snapshot_cost, 2)
    total += primary_snapshot_cost

    # Snapshot replication to secondary regions (storage + one-time transfer)
    snapshot_secondary_storage = snapshot_gb * 0.095 * secondary_snapshot_regions
    snapshot_transfer_onetime = snapshot_gb * snapshot_transfer_cost_per_gb
    breakdown['snapshot_secondary_regions_usd'] = round(snapshot_secondary_storage, 2)
    breakdown['snapshot_replication_transfer_usd'] = round(snapshot_transfer_onetime, 2)
    total += snapshot_secondary_storage
    # Transfer is one-time but amortize over 12 months for monthly comparison
    total += snapshot_transfer_onetime / 12

    breakdown['total_monthly_usd'] = round(total, 2)
    return breakdown


if __name__ == '__main__':
    # Example: two-region SQL Server setup with a cross-region read replica
    regions = [
        RegionConfig(
            name='us-east-1 (primary)',
            instance_type='db.r6i.2xlarge',
            instance_monthly_usd=730,
            storage_gb=1000,
            is_primary=True,
            replica_count=2   # two read replicas in primary region
        ),
        RegionConfig(
            name='eu-west-1 (secondary)',
            instance_type='db.r6g.xlarge',
            instance_monthly_usd=365,
            storage_gb=1000,
            is_primary=False,
            replica_count=1
        ),
    ]

    replication = ReplicationConfig(
        write_throughput_gb_per_hour=2.0,       # 2 GB/hour write throughput
        transfer_cost_per_gb=0.02,               # us-east-1 to eu-west-1
        write_throughput_gb_per_hour=20.8,   # ~500 GB/day of log replication
        transfer_cost_per_gb=0.02,
    )

    result = calculate_total_cost(
        regions=regions,
        replication=replication,
        snapshot_gb=1000,
        secondary_snapshot_regions=1,
    )

    print('\n=== Multi-Region Database Cost Model ===')
    for key, value in result.items():
        label = key.replace('_', ' ').title()
        if key == 'total_monthly_usd':
            print(f'\n{"TOTAL MONTHLY COST":40} ${value:>10,.2f}')
        else:
            print(f'  {label:38} ${value:>10,.2f}')

    5.6 Practical Remediation Playbook: Sequencing the Work

    With the measurement tools established across the previous sections, this section provides a prioritized sequence for remediation. The ordering reflects both cost impact and implementation risk — changes with the highest return and lowest operational risk come first.

    Sequencing matters more than speed. Week 1 audits and baselines so you can measure; Week 2 takes zero-risk wins that need no approval; Week 3 tackles log export costs once you know the volumes; Week 4 reroutes traffic last, because it carries the most blast radius. Each week's arrow flows into the next — never skip ahead to the risky changes before the baseline exists.

    Week 1: Audit and Baseline (No Changes)

    1. Run the Cost Explorer queries from §5.1 for all three providers used in your organization. Document current transfer, snapshot, and log spend in a shared tracking sheet.

    2. Run snapshot_cost_auditor.py in dry-run mode. Record total orphaned snapshot cost and stale manual snapshot cost.

    3. Run log_retention_enforcer.py in dry-run mode. Record log groups without retention policies and their current storage cost.

    4. Run cross_az_detector.py. Record estimated cross-AZ traffic cost per database.

    5. Run multiregion_cost_model.py with your actual region configurations and write throughput numbers. Compare model output against actual Cost Explorer data to validate assumptions.

    At the end of Week 1, you have a complete picture of recoverable costs with no changes made to production systems. This baseline serves two purposes: it directs your effort toward the highest-impact items, and it provides the before-measurement against which you will demonstrate savings.

    Week 2: Zero-Risk Remediations

    These changes carry no operational risk because they affect storage retention and log policies, not active query paths.

    1. Delete orphaned snapshots. Any snapshot whose source instance no longer exists has zero operational value. Run snapshot_cost_auditor.py with dry_run=False for the orphaned snapshot category only. Validate the list manually before executing — confirm that the source instance truly no longer exists and that no compliance hold requires the snapshot.

    2. Set retention policies on log groups without them. Run log_retention_enforcer.py with dry_run=False. This change takes effect immediately and begins reducing log storage costs within the next billing cycle. It does not affect log ingestion rates, only how long logs are kept.

    3. Reduce development database snapshot retention. For any database whose name matches your dev/staging patterns and currently has a BackupRetentionPeriod greater than 3, reduce it to 1. Apply during business hours so the maintenance window applies immediately.

    # Bulk-reduce retention for dev/staging RDS instances
# Adjust the name filter to match your naming convention
aws rds describe-db-instances \
  --query 'DBInstances[?contains(DBInstanceIdentifier, `dev`) || contains(DBInstanceIdentifier, `staging`) || contains(DBInstanceIdentifier, `test`)].DBInstanceIdentifier' \
  --output text | tr '\t' '\n' | while read db_id; do
    current=$(aws rds describe-db-instances \
      --db-instance-identifier "$db_id" \
      --query 'DBInstances[0].BackupRetentionPeriod' \
      --output text)
    if [ "$current" -gt 3 ]; then
      echo "Reducing $db_id from ${current}d to 1d"
      aws rds modify-db-instance \
        --db-instance-identifier "$db_id" \
        --backup-retention-period 1 \
        --apply-immediately
    else
      echo "$db_id already at ${current}d, skipping"
    fi
  done

    Week 3: Log Export and Diagnostic Setting Changes

    1. Disable verbose statement-level logging on production databases. This is the single highest-impact log change. On RDS for SQL Server, a SQL Server Audit specification capturing every statement — plus error/agent log exports to CloudWatch — is the equivalent cost driver. Audit what is actually exported: keep only failed-logon and error-severity events in the audit specification, and export the SQL Server error log to CloudWatch only for production instances where you actively alert on it. Statement-level auditing belongs on the instances where compliance requires it, not on every database in the fleet.

aws rds describe-db-instances \
  --db-instance-identifier your-instance \
  --query 'DBInstances[0].EnabledCloudwatchLogsExports' \
  --output table

# Disable log exports that are not actively used (error/agent logs
# generate the most volume on busy instances)
aws rds modify-db-instance \
  --db-instance-identifier your-instance \
  --cloudwatch-logs-export-configuration '{"DisableLogTypes":["agent","error"]}' \
  --apply-immediately

-- generating high log volume, and scope them down
SELECT s.name AS audit_spec,
       d.audit_action_name,
       d.class_desc
FROM sys.server_audit_specifications s

  ON s.server_specification_id = d.server_specification_id
WHERE d.audit_action_name LIKE '%STATEMENT%'
  AND s.is_state_enabled = 1;

    2. Disable high-volume Azure SQL diagnostic categories. Run the Azure CLI diagnostic settings commands from §5.4 to disable SQLInsights and AutomaticTuning on databases not under active investigation.

    3. Enable Query Store on SQL Server databases where it is absent. This provides query performance visibility through the database engine rather than log files, removing the operational justification for keeping verbose statement-level logging enabled:
    ALTER DATABASE [YourDB] SET QUERY_STORE = ON (OPERATION_MODE = READ_WRITE);

    Week 4: Traffic Routing Changes

    Traffic routing changes carry higher operational risk than retention and logging changes and require coordination with application teams.

    1. Audit all connection strings for public endpoint usage. For every RDS instance, compare the endpoint used in application configuration against the private DNS endpoint. Any application using the public endpoint incurs unnecessary charges and an avoidable security exposure.

aws rds describe-db-instances \
  --query 'DBInstances[*].{
    ID:DBInstanceIdentifier,
    PrivateEndpoint:Endpoint.Address,
    Port:Endpoint.Port,
    AZ:AvailabilityZone,
    VPC:DBSubnetGroup.VpcId
  }' \
  --output table

# Search for public endpoint patterns in common config file locations
# (Run on each application server or in your config management system)
grep -rn "\.rds\.amazonaws\.com" /etc/app/ /opt/app/ ~/.env 2>/dev/null | \
  grep -v ".cluster-ro-" | \
  grep -v "private" | \
  head -50

    2. Implement AZ-aware connection routing for the top two databases by cross-AZ cost. Do not attempt to change connection routing for all databases simultaneously. Start with the two highest-cost instances identified in Week 1. Configure your connection pool to prefer connections within the same AZ. Validate that connection counts and query latency remain stable for 48 hours before expanding to additional databases.

    3. Review cross-region replica necessity. For each cross-region read replica or secondary, answer three questions: What is the current RTO/RPO requirement? When was this replica last used for actual reads? Is the DR requirement met by cross-region snapshots at lower cost? If the replica is serving zero application reads and exists purely for DR, evaluate replacing it with automated cross-region snapshot replication — which typically satisfies RTO requirements measured in hours at a fraction of the active-replica cost.

    Tracking and Reporting Progress

    Two weeks after completing Week 4 changes, re-run the baseline queries from Week 1 and compare against the recorded baseline. Calculate realized savings as the difference between before and after monthly costs. Document the changes made and their financial impact in your organization's FinOps tracking system.

    The most common pattern is that Week 2 changes (orphaned snapshots, log retention, dev retention) deliver 30–40% of total recoverable savings with the least effort. Week 3 (log export changes) delivers another 30–40%. Week 4 (traffic routing) delivers the remaining value but requires the most coordination. Teams that implement all four weeks typically recover 70–85% of the opportunity identified in the Week 1 baseline.

    5.7 Preventing Future Accumulation: Infrastructure Controls

    Remediating existing costs is the first phase. The second phase is preventing the same costs from accumulating again as new databases, log groups, and snapshots are created. Infrastructure controls — policy guardrails applied at provisioning time — are more reliable than periodic manual audits.

    AWS Service Control Policies for Snapshot Retention

    AWS Organizations Service Control Policies (SCPs) cannot directly enforce RDS backup retention values, but they can deny the creation of RDS instances that do not include appropriate tags, which your provisioning pipeline then uses to validate configuration compliance.

    A more direct control is an AWS Config rule that evaluates RDS backup retention against a required minimum and maximum.

    #!/usr/bin/env python3
"""
config_rds_retention_rule.py
AWS Config custom rule that flags RDS instances with:
- BackupRetentionPeriod > MAX_RETENTION for non-production
- BackupRetentionPeriod < MIN_RETENTION for production
Deploy via CloudFormation or AWS Config console as a Lambda-backed custom rule.
"""

import json
import boto3

COMPLIANCE_RULES = {
    'production': {'min_retention': 7, 'max_retention': 35},
    'staging':    {'min_retention': 1, 'max_retention': 7},
    'dev':        {'min_retention': 0, 'max_retention': 3},
    'test':       {'min_retention': 0, 'max_retention': 3},
}

DEFAULT_RULE = {'min_retention': 1, 'max_retention': 14}


def get_environment_tag(db_instance: dict) -> str:
    """Extract environment from RDS tags."""
    tags = {t['Key'].lower(): t['Value'].lower()
            for t in db_instance.get('TagList', [])}
    return tags.get('environment', tags.get('env', 'unknown'))


def evaluate_compliance(db_instance: dict) -> tuple:
    """
    Returns (compliance_type, annotation) where compliance_type is
    'COMPLIANT', 'NON_COMPLIANT', or 'NOT_APPLICABLE'.
    """
    db_id = db_instance['DBInstanceIdentifier']
    retention = db_instance.get('BackupRetentionPeriod', 0)
    env = get_environment_tag(db_instance)

    # Find applicable rule
    rule = DEFAULT_RULE
    for env_key, env_rule in COMPLIANCE_RULES.items():
        if env_key in env or env_key in db_id.lower():
            rule = env_rule
            break

    if retention < rule['min_retention']:
        return (
            'NON_COMPLIANT',
            f'BackupRetentionPeriod={retention} is below minimum={rule["min_retention"]} '
            f'for environment={env}. Risk: insufficient backup coverage.'
        )

    if retention > rule['max_retention']:
        return (
            'NON_COMPLIANT',
            f'BackupRetentionPeriod={retention} exceeds maximum={rule["max_retention"]} '
            f'for environment={env}. '
            f'Estimated excess monthly cost: '
            f'${(retention - rule["max_retention"]) * db_instance.get("AllocatedStorage", 0) * 0.095:.2f}'
        )

    return (
        'COMPLIANT',
        f'BackupRetentionPeriod={retention} within [{rule["min_retention"]}, {rule["max_retention"]}] '
        f'for environment={env}.'
    )


def lambda_handler(event, context):
    """AWS Config rule Lambda entry point."""
    invoking_event = json.loads(event['invokingEvent'])
    configuration_item = invoking_event.get('configurationItem', {})

    if configuration_item.get('resourceType') != 'AWS::RDS::DBInstance':
        return

    config_client = boto3.client('config')
    rds_client = boto3.client('rds')

    db_id = configuration_item['resourceName']

    try:
        response = rds_client.describe_db_instances(DBInstanceIdentifier=db_id)
        db_instance = response['DBInstances'][0]
    except Exception as e:
        print(f'Could not describe {db_id}: {e}')
        return

    compliance_type, annotation = evaluate_compliance(db_instance)

    config_client.put_evaluations(
        Evaluations=[{
            'ComplianceResourceType': 'AWS::RDS::DBInstance',
            'ComplianceResourceId': db_id,
            'ComplianceType': compliance_type,
            'Annotation': annotation[:255],  # Config has a 255-char limit
            'OrderingTimestamp': configuration_item['configurationItemCaptureTime']
        }],
        ResultToken=event['resultToken']
    )

    print(f'{db_id}: {compliance_type} — {annotation}')

    EventBridge Rules for Snapshot Lifecycle

    For manual snapshots created outside of Terraform (during migrations, for instance), an EventBridge rule can trigger a Lambda function that tags the snapshot with a TTL and a scheduled cleanup rule that deletes it when the TTL expires.

    #!/usr/bin/env python3
"""
snapshot_ttl_tagger.py
Lambda function triggered by EventBridge on RDS snapshot creation events.
Tags every new manual snapshot with a deletion date (default 30 days).
A companion cleanup Lambda runs daily and deletes expired snapshots.
"""

import boto3
import json
from datetime import datetime, timedelta, timezone


DEFAULT_TTL_DAYS = 30
TTL_TAG_KEY = 'SnapshotExpiryDate'
CREATED_BY_TAG_KEY = 'CreatedBy'


def lambda_handler(event, context):
    """
    Triggered by EventBridge rule:
    source: ["aws.rds"]
    detail-type: ["RDS DB Snapshot Event"]
    detail.EventID: ["RDS-EVENT-0042"]  (manual snapshot created)
    """
    rds_client = boto3.client('rds')

    detail = event.get('detail', {})
    source_arn = detail.get('SourceArn', '')
    
    # Extract snapshot identifier from ARN
    # ARN format: arn:aws:rds:region:account:snapshot:snapshot-id
    if ':snapshot:' not in source_arn:
        print(f'Not a snapshot event, skipping: {source_arn}')
        return

    snapshot_id = source_arn.split(':snapshot:')[-1]
    expiry_date = (datetime.now(timezone.utc) + timedelta(days=DEFAULT_TTL_DAYS)).strftime('%Y-%m-%d')

    try:
        rds_client.add_tags_to_resource(
            ResourceName=source_arn,
            Tags=[
                {'Key': TTL_TAG_KEY, 'Value': expiry_date},
                {'Key': 'AutoCreatedAt', 'Value': datetime.now(timezone.utc).isoformat()},
                {'Key': 'ManagedBy', 'Value': 'snapshot-ttl-enforcer'},
            ]
        )
        print(f'Tagged {snapshot_id} with expiry {expiry_date}')
    except Exception as e:
        print(f'Failed to tag {snapshot_id}: {e}')
        raise


def cleanup_expired_snapshots(event, context):
    """
    Companion Lambda: triggered daily by EventBridge schedule.
    Deletes manual snapshots past their SnapshotExpiryDate tag.
    """
    rds_client = boto3.client('rds')
    today = datetime.now(timezone.utc).strftime('%Y-%m-%d')
    deleted = []
    skipped = []

    paginator = rds_client.get_paginator('describe_db_snapshots')
    for page in paginator.paginate(SnapshotType='manual'):
        for snap in page['DBSnapshots']:
            if snap['Status'] != 'available':
                continue

            snap_id = snap['DBSnapshotIdentifier']
            snap_arn = snap['DBSnapshotArn']

            # Get tags for this snapshot
            tag_response = rds_client.list_tags_for_resource(ResourceName=snap_arn)
            tags = {t['Key']: t['Value'] for t in tag_response.get('TagList', [])}

            expiry = tags.get(TTL_TAG_KEY)
            if not expiry:
                skipped.append(snap_id)
                continue

            if expiry <= today:
                size_gb = snap.get('AllocatedStorage', 0)
                print(f'Deleting expired snapshot {snap_id} (expired {expiry}, {size_gb}GB)')
                try:
                    rds_client.delete_db_snapshot(DBSnapshotIdentifier=snap_id)
                    deleted.append({'id': snap_id, 'size_gb': size_gb, 'expired': expiry})
                except Exception as e:
                    print(f'Failed to delete {snap_id}: {e}')
            else:
                skipped.append(snap_id)

    total_gb_freed = sum(d['size_gb'] for d in deleted)
    monthly_cost_freed = total_gb_freed * 0.095

    print(f'\nCleanup complete: deleted={len(deleted)}, skipped={len(skipped)}')
    print(f'Storage freed: {total_gb_freed}GB (~${monthly_cost_freed:.2f}/month savings)')

    return {
        'deleted_count': len(deleted),
        'skipped_count': len(skipped),
        'total_gb_freed': total_gb_freed,
        'estimated_monthly_savings_usd': round(monthly_cost_freed, 2),
        'deleted_snapshots': deleted
    }

    This TTL pattern eliminates the manual snapshot accumulation problem at its source. Rather than relying on periodic audits to identify stale snapshots, every new manual snapshot automatically carries a deletion date. Engineers who need a snapshot to persist beyond the default TTL update the tag explicitly — making the retention decision conscious rather than accidental.

    Key Takeaways

  • → **Data transfer, snapshots, and logs collectively account for 18–35% of total database spend in production environments, yet most teams track none of these costs with the same rigor they apply to instance sizing.** Establishing a baseline measurement using the CLI queries in §5.1 before making any changes is not optional — without it, you cannot demonstrate savings or prioritize effort.
  • → **Cross-AZ traffic is generated invisibly by common architectural patterns.** Application servers distributed across availability zones connecting to a single-AZ RDS primary, or using public endpoints instead of private DNS, produce continuous egress charges that compound with every read and write. Topology-aware connection routing and private endpoint enforcement are the highest-return, lowest-risk changes available for databases processing more than a few hundred gigabytes per month.
  • → **Snapshot costs scale linearly with retention period and are frequently doubled by cross-region replication storage that teams forget to account for.** A tiered retention policy — 35 days for regulated production, 7 days for standard production, 1–3 days for non-production — combined with automated TTL tagging for manual snapshots eliminates 40–70% of snapshot spend without reducing actual restore capability for any environment.
  • → **General query logging on high-throughput OLTP databases is the single most expensive logging misconfiguration, and it is almost always unnecessary.** Query Store and `sys.dm_exec_query_stats` provide complete query performance visibility at less than 1% of the CloudWatch ingestion cost of verbose statement-level logging. Keeping statement-level audit logging scoped to compliance requirements — not left capturing every batch — is a zero-risk, high-return remediation.
  • → **Prevention through infrastructure guardrails is more reliable than periodic remediation.** Terraform variable validations that reject non-compliant retention and logging configurations at plan time, AWS Config custom rules that flag drift, and EventBridge-triggered TTL tagging for manual snapshots together ensure that the costs eliminated during the remediation phase do not silently return as new databases and log groups are provisioned.
