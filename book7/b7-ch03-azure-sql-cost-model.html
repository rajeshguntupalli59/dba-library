Chapter 3: Azure SQL Cost Model: DTU vs vCore vs Serverless

Organizations running workloads on Azure SQL Database routinely overspend by 40–60% because they inherited a DTU tier chosen during initial migration, never revisited it, and now pay for capacity that sits idle 70% of the day. This chapter breaks down all three Azure SQL purchasing models — DTU-based, vCore-based, and Serverless — explains exactly when each one saves or costs you money, and gives you the queries, CLI commands, and Python automation to identify mismatches and fix them on a schedule. A team running a 250 DTU Premium (P2) database that migrates to a General Purpose 8 vCore with a reserved instance and the Azure Hybrid Benefit can realistically reduce that single database's monthly bill from roughly $930 to $310 — a saving of $620/month without touching a line of application code.

---

3.1 Understanding the Three Purchasing Models

Before optimizing, you need a precise mental model of what you are actually buying. Azure SQL charges you differently depending on which of its three cost models you choose, and conflating them is the primary reason teams make poor sizing decisions.

#### DTU-Based Purchasing

DTU stands for Database Transaction Unit — a blended measure of CPU, memory, and I/O that Microsoft bundles into a single number. You cannot see or control the individual components. A 100 DTU Standard database costs roughly $150/month; a 500 DTU Premium database costs around $465/month. The tiers are:

| Tier | DTU Range | Max Storage | Approximate Monthly Cost |

|------|-----------|-------------|--------------------------|

| Basic | 5 | 2 GB | $5 |

| Standard (S0–S9) | 10–3,000 | 1 TB | $15–$450 |

| Premium (P1–P15) | 125–4,000 | 4 TB | $465–$14,000+ |

The DTU model's core problem is opacity. You cannot correlate DTU consumption to actual CPU or memory utilization. If a query is I/O bound and you're buying a CPU-heavy DTU tier, you're paying a bundled price for resources you don't consume. DTU databases also do not support the Azure Hybrid Benefit for SQL Server licenses, which alone eliminates 30% of the vCore price.

#### vCore-Based Purchasing

The vCore model lets you choose cores and memory independently (within hardware tiers), apply your own SQL Server licenses, and see actual CPU and memory metrics. There are three hardware families:

  • → **General Purpose (Fsv2 or Gen5)** — balanced compute and storage, good for most OLTP workloads.
  • → **Business Critical** — local SSD, built-in read replica, high memory-to-core ratio. Equivalent to a local Premium SSD RAID; suited for latency-sensitive OLTP.
  • → **Hyperscale** — distributed storage that scales to 100 TB, with rapid snapshot-based backups.

    • A General Purpose 4 vCore (Gen5) runs approximately $368/month pay-as-you-go. Apply the Azure Hybrid Benefit if you have existing SQL Server Enterprise licenses with Software Assurance, and the cost drops to roughly $186/month. Buy a 1-year reserved instance on top of that and you reach approximately $155/month. Buy a 3-year reserved instance and you reach approximately $115/month. The math on that last number versus a 500 DTU Premium ($465/month) tells the whole story for moderately sized OLTP databases.

    #### Serverless

    Serverless is a vCore-based sub-model where you define a minimum and maximum vCore count and pay only for the compute you use, billed per second. When the database sits idle for a configurable period (the auto-pause delay, minimum 1 hour), Azure pauses it entirely and you pay only for storage. When the next connection arrives, the database resumes — the cold-start latency typically runs 30–90 seconds.

    Serverless pricing for General Purpose: approximately $0.000145 per vCore-second. A database running at 2 vCores for 8 hours/day costs roughly $250.56/month in compute, versus the always-on General Purpose 2 vCore at approximately $762/month. That is a 67% compute saving for a development database used only during business hours, assuming it auto-pauses for the remaining 16 hours.

    The break-even point between Serverless and provisioned vCore is roughly 50% average utilization across a 730-hour month. Workloads above that threshold are cheaper on provisioned; workloads below it are cheaper on Serverless.

    3.2 Diagnosing Your Current Spend and Utilization

    The first step is understanding what you are actually paying for versus what your databases actually consume. Azure provides this data in two places: Azure Cost Management and the database's own DMVs.

    #### Pulling Cost Data with Azure CLI

    The following command exports the last 30 days of Azure SQL spend by resource, broken down to the database level:

    #!/bin/bash
# Pull Azure SQL cost breakdown for the last 30 days
# Requires: Azure CLI authenticated, correct subscription set

SUBSCRIPTION_ID="your-subscription-id"
RESOURCE_GROUP="your-rg"
START_DATE=$(date -d "30 days ago" '+%Y-%m-%d')
END_DATE=$(date '+%Y-%m-%d')

az consumption usage list \
  --start-date "$START_DATE" \
  --end-date "$END_DATE" \
  --query "[?contains(instanceName, 'sql')].{
    Resource:instanceName,
    Cost:pretaxCost,
    Currency:currency,
    UsageDate:usageStart
  }" \
  --output table \
  --subscription "$SUBSCRIPTION_ID"

# For more granular breakdown by SKU (DTU tier, vCore family)
az costmanagement query \
  --type Usage \
  --timeframe Custom \
  --time-period from="$START_DATE" to="$END_DATE" \
  --dataset-configuration columns='["SubscriptionId","ResourceGroup","ResourceId","MeterCategory","MeterSubCategory","MeterName","Quantity","Unit","PreTaxCost","UsageDate"]' \
  --dataset-filter '{
    "and": [
      {
        "dimensions": {
          "name": "MeterCategory",
          "operator": "In",
          "values": ["SQL Database"]
        }
      }
    ]
  }' \
  --scope "subscriptions/$SUBSCRIPTION_ID" \
  --output json | jq '.properties.rows[] | {
    resource: .[2],
    meter: .[4],
    sku: .[5],
    quantity: .[6],
    cost: .[8],
    date: .[9]
  }'

    #### Reading Utilization from the Database DMVs

    Once you know what you're paying, you need to know what you're using. The following query runs inside Azure SQL and returns the 15-day average DTU (or CPU) consumption alongside the tier you're paying for — giving you the utilization percentage that drives every sizing decision:

    -- Run this inside the Azure SQL database (not master)
-- Returns: 15-day average resource utilization vs. purchased tier
-- Works for both DTU and vCore databases

SELECT
    database_name                                               AS [Database],
    service_objective                                           AS [Current_SKU],
    elastic_pool_name                                           AS [Elastic_Pool],
    -- DTU utilization (NULL for vCore databases)
    AVG(avg_cpu_percent)                                        AS [Avg_CPU_Pct_15Day],
    MAX(avg_cpu_percent)                                        AS [Max_CPU_Pct_15Day],
    AVG(avg_data_io_percent)                                    AS [Avg_DataIO_Pct_15Day],
    MAX(avg_data_io_percent)                                    AS [Max_DataIO_Pct_15Day],
    AVG(avg_log_write_percent)                                  AS [Avg_LogWrite_Pct_15Day],
    MAX(avg_log_write_percent)                                  AS [Max_LogWrite_Pct_15Day],
    AVG(avg_memory_usage_percent)                               AS [Avg_Mem_Pct_15Day],
    MAX(avg_memory_usage_percent)                               AS [Max_Mem_Pct_15Day],
    -- Derived overall DTU utilization (highest of the four dimensions)
    AVG(GREATEST(
        avg_cpu_percent,
        avg_data_io_percent,
        avg_log_write_percent
    ))                                                          AS [Avg_Effective_DTU_Pct],
    MAX(GREATEST(
        avg_cpu_percent,
        avg_data_io_percent,
        avg_log_write_percent
    ))                                                          AS [Max_Effective_DTU_Pct],
    MIN(end_time)                                               AS [Oldest_Sample],
    MAX(end_time)                                               AS [Newest_Sample],
    COUNT(*)                                                    AS [Sample_Count]
FROM sys.dm_db_resource_stats
CROSS JOIN (
    SELECT
        d.name                  AS database_name,
        d.service_objective     AS service_objective,
        d.elastic_pool_name     AS elastic_pool_name
    FROM sys.database_service_objectives d
    WHERE d.database_id = DB_ID()
) meta
GROUP BY
    database_name,
    service_objective,
    elastic_pool_name;

    > Reading the output: If Avg_Effective_DTU_Pct is below 40% and Max_Effective_DTU_Pct is below 75%, you are a candidate for downsizing. If Avg_Effective_DTU_Pct is above 70% consistently, downsizing will cause performance degradation — address query efficiency first.

    For longer historical windows (up to 14 days) from the master database, use sys.resource_stats instead:

    -- Run this in the MASTER database on a logical server
-- 14-day utilization view across all databases on the server

SELECT
    database_name,
    sku,
    -- 5-minute granularity samples
    COUNT(*)                                        AS sample_count,
    AVG(avg_cpu_percent)                            AS avg_cpu_pct,
    PERCENTILE_CONT(0.95) WITHIN GROUP
        (ORDER BY avg_cpu_percent)                  AS p95_cpu_pct,
    AVG(avg_data_io_percent)                        AS avg_io_pct,
    PERCENTILE_CONT(0.95) WITHIN GROUP
        (ORDER BY avg_data_io_percent)              AS p95_io_pct,
    -- Cost signal: hours where utilization < 20% (idle capacity)
    SUM(CASE WHEN avg_cpu_percent < 20
             AND avg_data_io_percent < 20
             THEN 1 ELSE 0 END) * 5.0 / 60         AS idle_hours_approx,
    SUM(CASE WHEN avg_cpu_percent > 80
             THEN 1 ELSE 0 END) * 5.0 / 60         AS saturated_hours_approx
FROM sys.resource_stats
WHERE start_time >= DATEADD(DAY, -14, GETUTCDATE())
GROUP BY database_name, sku
ORDER BY avg_cpu_pct DESC;

    3.3 Choosing the Right Tier: Decision Framework

    Given utilization data, you can now apply a structured decision process. The following flowchart captures the logic:

    graph TD
    A[Start: new or existing DB] --> B{Used < 12 hrs/day and\ntolerates cold start?}
    B -->|Yes| C[Serverless]
    B -->|No| D{Predictable load\n> 12 hrs/day?}
    D -->|Yes| E[Provisioned vCore General Purpose\n+ Hybrid Benefit + Reserved Capacity]
    D -->|No| F{Needs < 5ms latency,\nlocal SSD, or free read replica?}
    F -->|Yes| G[Business Critical vCore]
    F -->|No| H{DTU tier, shared load\nwith other databases?}
    H -->|Yes| I[Elastic Pool]
    H -->|No| J{Needs > 4 TB or\nfast backup/restore?}
    J -->|Yes| K[Hyperscale]

    *The Azure SQL tier decision framework, expressed as the actual flowchart the prose logic below describes.*

    1. Is the database used fewer than 12 hours per day on average, and can it tolerate a 30–90 second cold-start? → Serverless. Set min_capacity = 0.5 vCores, max_capacity to your peak requirement, and set auto_pause_delay_minutes = 60 for dev/test or 120 for lightly used production databases.

    2. Is the database used more than 12 hours per day with predictable load? → Provisioned vCore General Purpose. Apply Hybrid Benefit if you own licenses. Buy reserved capacity.

    3. Does the workload require < 5 ms read latency, local SSD, or a free read replica for reporting? → Business Critical vCore. This tier is significantly more expensive (~3× General Purpose) but eliminates the need for a separate read replica or Premium storage.

    4. Is the database in a DTU tier and used inconsistently across a shared pool of multiple databases? → Elastic Pool (vCore or DTU-based), covered in Chapter 4. Do not optimize a single database in isolation if it shares load patterns with ten others.

    5. Does the database need to grow beyond 4 TB or requires fast, large-scale backup/restore? → Hyperscale. Cost is separate from the above tiers; storage is billed at $0.115/GB/month for Hyperscale versus $0.115/GB/month for General Purpose remote storage — similar per-GB pricing but Hyperscale adds compute cost for its page servers.

    #### Translating DTU to vCore (The Conversion Table)

    Microsoft's rough conversion guideline: 100 DTUs ≈ 1 vCore for Standard/General Purpose. For Premium/Business Critical, it's closer to 125 DTUs ≈ 1 vCore. However, these are approximations. The utilization percentages matter more than the raw numbers.

    | Current Tier | Approx. Monthly Cost | vCore Equivalent | vCore Pay-as-Go | With Hybrid Benefit | With 1-Yr RI + HB |

    |---|---|---|---|---|---|

    | S3 (100 DTU) | $150 | GP 1 vCore | $184 | $93 | $77 |

    | P1 (125 DTU) | $465 | GP 4 vCore | $368 | $186 | $155 |

    | P2 (250 DTU) | $930 | GP 8 vCore | $736 | $372 | $310 |

    | P4 (500 DTU) | $1,860 | GP 16 vCore | $1,471 | $743 | $619 |

    The P2→GP8 + HB + 1-Yr RI move illustrated here is where the $310/month number in the chapter opener comes from. The P4 → GP16 equivalent at 3-year RI with HB reaches approximately $490/month versus $1,860 — a $1,370/month saving on a single database.

    3.4 Activating Azure Hybrid Benefit and Reserved Instances

    The Azure Hybrid Benefit (AHB) and reserved instances are the two highest-leverage levers that require zero application change. Yet many organizations leave both on the table because no one on the database team owns the licensing conversation.

    #### Enabling Hybrid Benefit via Azure CLI

    #!/bin/bash
# Enable Azure Hybrid Benefit on an existing Azure SQL Database (vCore model)
# Prerequisites: SQL Server license with Software Assurance

RESOURCE_GROUP="prod-databases-rg"
SERVER_NAME="prod-sqlserver-eastus"
DATABASE_NAME="orders-db"

# Check current license type
az sql db show \
  --resource-group "$RESOURCE_GROUP" \
  --server "$SERVER_NAME" \
  --name "$DATABASE_NAME" \
  --query "{name:name, licenseType:licenseType, sku:sku}" \
  --output table

# Apply Hybrid Benefit (change licenseType from LicenseIncluded to BasePrice)
az sql db update \
  --resource-group "$RESOURCE_GROUP" \
  --server "$SERVER_NAME" \
  --name "$DATABASE_NAME" \
  --license-type BasePrice

# Verify the change
az sql db show \
  --resource-group "$RESOURCE_GROUP" \
  --server "$SERVER_NAME" \
  --name "$DATABASE_NAME" \
  --query "{name:name, licenseType:licenseType, edition:edition, capacity:currentServiceObjectiveName}" \
  --output table

# Apply to all databases on a server in bulk
echo "Applying Hybrid Benefit to all vCore databases on $SERVER_NAME..."
az sql db list \
  --resource-group "$RESOURCE_GROUP" \
  --server "$SERVER_NAME" \
  --query "[?licenseType=='LicenseIncluded'].name" \
  --output tsv | while read db_name; do
    echo "Updating: $db_name"
    az sql db update \
      --resource-group "$RESOURCE_GROUP" \
      --server "$SERVER_NAME" \
      --name "$db_name" \
      --license-type BasePrice
done

echo "Done. Verify in Azure Portal under Cost Management."

    #### Purchasing Reserved Instances

    Reserved instances for Azure SQL are purchased through the Azure Portal under Reservations, not through the SQL Database blade itself. You reserve at the vCore family and region level, not at the individual database level. A 4-vCore General Purpose East US reservation covers any General Purpose 4-vCore database in East US, regardless of the server name. This means you can replace databases, rename them, or move workloads between databases, and the reservation continues applying.

    Reservation calculation before purchasing:

    Before committing, verify utilization will remain stable. A 1-year commitment on compute that you later delete runs to waste. The break-even for a 1-year RI versus pay-as-you-go is approximately 5–6 months of continuous operation. For databases you know will run for 12+ months, the 1-year RI is always the right choice unless the team plans a migration to a different service within the year.

    3.5 Automating Serverless Right-Sizing with Python

    The following Python script connects to Azure Monitor metrics and the Azure Cost Management API, evaluates each Azure SQL database in a subscription against Serverless break-even criteria, and outputs a prioritized recommendation report. Designed to run as a weekly Azure Function or a cron job on any Linux host.

    #!/usr/bin/env python3
"""
azure_sql_rightsizing.py

Weekly right-sizing analysis for Azure SQL databases.
Compares current provisioned cost against Serverless equivalent.
Outputs a CSV report and optionally sends to Azure Blob Storage.

Requirements:
    pip install azure-identity azure-mgmt-sql azure-mgmt-monitor \
                azure-mgmt-costmanagement pandas

Usage:
    python azure_sql_rightsizing.py \
        --subscription-id <sub-id> \
        --output-path ./reports/sql_rightsizing.csv
"""

import argparse
import datetime
import json
import csv
import sys
from dataclasses import dataclass, field, asdict
from typing import Optional

from azure.identity import DefaultAzureCredential
from azure.mgmt.sql import SqlManagementClient
from azure.mgmt.monitor import MonitorManagementClient
from azure.mgmt.costmanagement import CostManagementClient
from azure.mgmt.costmanagement.models import (
    QueryDefinition, QueryTimePeriod, QueryDataset,
    QueryAggregation, QueryGrouping, TimeframeType
)


# ------------------------------------------------------------------
# Pricing constants (East US, USD, as of 2024 — verify current rates)
# ------------------------------------------------------------------
GP_VCORE_PAYG_HOURLY = 0.5042          # General Purpose per vCore per hour
GP_VCORE_HB_HOURLY = 0.2546           # With Hybrid Benefit
GP_VCORE_RI1YR_HB_HOURLY = 0.2121    # 1-Year RI + Hybrid Benefit
SERVERLESS_PER_VCORE_SECOND = 0.000145
STORAGE_PER_GB_MONTH = 0.115
AUTO_PAUSE_THRESHOLD_HOURS_PER_DAY = 12  # Serverless is cheaper if DB active < this


@dataclass
class DatabaseAnalysis:
    server_name: str
    database_name: str
    resource_group: str
    current_sku: str
    current_vcores: int
    license_type: str
    avg_cpu_pct: float
    p95_cpu_pct: float
    avg_active_hours_per_day: float
    storage_gb: float
    monthly_cost_current: float
    monthly_cost_serverless: float
    monthly_cost_provisioned_rib_hb: float
    recommendation: str
    monthly_savings: float
    annual_savings: float


def get_databases(sql_client: SqlManagementClient, subscription_id: str) -> list:
    """Return all Azure SQL databases (excluding system DBs) across all servers."""
    databases = []
    servers = list(sql_client.servers.list())

    for server in servers:
        rg = server.id.split("/")[4]
        try:
            dbs = sql_client.databases.list_by_server(rg, server.name)
            for db in dbs:
                if db.name in ("master",) or db.kind == "system":
                    continue
                databases.append((rg, server.name, db))
        except Exception as e:
            print(f"  Warning: Could not list databases on {server.name}: {e}",
                  file=sys.stderr)

    return databases


def get_cpu_metrics(
    monitor_client: MonitorManagementClient,
    resource_id: str,
    days: int = 14
) -> dict:
    """Pull CPU utilization metrics from Azure Monitor for a database."""
    end_time = datetime.datetime.utcnow()
    start_time = end_time - datetime.timedelta(days=days)

    metrics = monitor_client.metrics.list(
        resource_uri=resource_id,
        timespan=f"{start_time.isoformat()}Z/{end_time.isoformat()}Z",
        interval="PT1H",
        metricnames="cpu_percent",
        aggregation="Average,Maximum",
    )

    hourly_values = []
    for metric in metrics.value:
        for ts in metric.timeseries:
            for point in ts.data:
                if point.average is not None:
                    hourly_values.append(point.average)

    if not hourly_values:
        return {
            "avg_cpu_pct": 0.0,
            "p95_cpu_pct": 0.0,
            "avg_active_hours_per_day": 0.0,
        }

    hourly_values.sort()
    p95_index = int(len(hourly_values) * 0.95)
    active_hours = sum(1 for v in hourly_values if v > 5.0)  # > 5% = "active"

    return {
        "avg_cpu_pct": sum(hourly_values) / len(hourly_values),
        "p95_cpu_pct": hourly_values[p95_index],
        "avg_active_hours_per_day": active_hours / days,
    }


def estimate_monthly_cost_provisioned(
    vcores: int,
    license_type: str,
    storage_gb: float,
    use_ri_hb: bool = False,
) -> float:
    """Estimate monthly cost for a provisioned vCore database."""
    hours_per_month = 730.0

    if use_ri_hb:
        compute_hourly = vcores * GP_VCORE_RI1YR_HB_HOURLY
    elif license_type == "BasePrice":
        compute_hourly = vcores * GP_VCORE_HB_HOURLY
    else:
        compute_hourly = vcores * GP_VCORE_PAYG_HOURLY

    compute_monthly = compute_hourly * hours_per_month
    storage_monthly = max(storage_gb, 32) * STORAGE_PER_GB_MONTH  # 32 GB minimum
    return compute_monthly + storage_monthly


def estimate_monthly_cost_serverless(
    vcores_max: int,
    avg_active_hours_per_day: float,
    storage_gb: float,
) -> float:
    """
    Estimate Serverless monthly cost assuming the database auto-pauses during idle hours.
    Uses max_vcores as the estimate for active compute (conservative).
    """
    seconds_per_month = 730 * 3600
    active_fraction = min(avg_active_hours_per_day / 24.0, 1.0)
    active_seconds_per_month = seconds_per_month * active_fraction

    compute_monthly = vcores_max * SERVERLESS_PER_VCORE_SECOND * active_seconds_per_month
    storage_monthly = max(storage_gb, 32) * STORAGE_PER_GB_MONTH
    return compute_monthly + storage_monthly


def make_recommendation(analysis_data: dict) -> tuple[str, float]:
    """
    Return (recommendation_string, monthly_savings).
    Priority order:
      1. Switch to Serverless (large idle period, tolerable cold start)
      2. Apply Hybrid Benefit (vCore, license not yet BasePrice)
      3. Apply 1-Year Reserved Instance + Hybrid Benefit
      4. No change needed
    """
    current_cost = analysis_data["monthly_cost_current"]
    serverless_cost = analysis_data["monthly_cost_serverless"]
    ri_hb_cost = analysis_data["monthly_cost_provisioned_rib_hb"]
    active_hours = analysis_data["avg_active_hours_per_day"]
    license_type = analysis_data["license_type"]
    sku = analysis_data["current_sku"]

    # Cannot apply Serverless to elastic pool members or Hyperscale
    is_serverless_eligible = (
        "GP" in sku or "GeneralPurpose" in sku
    ) and active_hours < AUTO_PAUSE_THRESHOLD_HOURS_PER_DAY

    if is_serverless_eligible and serverless_cost < current_cost * 0.7:
        savings = current_cost - serverless_cost
        return (
            f"MIGRATE_TO_SERVERLESS: estimated ${serverless_cost:.2f}/mo "
            f"(save ${savings:.2f}/mo)",
            savings,
        )

    if ri_hb_cost < current_cost * 0.75:
        savings = current_cost - ri_hb_cost
        action = []
        if license_type != "BasePrice":
            action.append("APPLY_HYBRID_BENEFIT")
        action.append("BUY_1YR_RESERVED_INSTANCE")
        return (
            f"{'+'.join(action)}: estimated ${ri_hb_cost:.2f}/mo "
            f"(save ${savings:.2f}/mo)",
            savings,
        )

    if license_type != "BasePrice" and "vCore" in sku.lower():
        hb_cost = estimate_monthly_cost_provisioned(
            analysis_data["current_vcores"],
            "BasePrice",
            analysis_data["storage_gb"],
            use_ri_hb=False,
        )
        if hb_cost < current_cost * 0.85:
            savings = current_cost - hb_cost
            return (
                f"APPLY_HYBRID_BENEFIT: estimated ${hb_cost:.2f}/mo "
                f"(save ${savings:.2f}/mo)",
                savings,
            )

    return "NO_CHANGE_RECOMMENDED", 0.0


def analyze_subscription(subscription_id: str, output_path: str) -> None:
    credential = DefaultAzureCredential()
    sql_client = SqlManagementClient(credential, subscription_id)
    monitor_client = MonitorManagementClient(credential, subscription_id)

    print(f"Fetching databases in subscription {subscription_id}...")
    databases = get_databases(sql_client, subscription_id)
    print(f"  Found {len(databases)} user databases.")

    results: list[DatabaseAnalysis] = []

    for rg, server_name, db in databases:
        print(f"  Analyzing: {server_name}/{db.name} ({db.sku.name if db.sku else 'unknown SKU'})")

        # Extract current vCore count and license type
        vcores = db.sku.capacity if db.sku and db.sku.capacity else 2
        license_type = getattr(db, "license_type", "LicenseIncluded") or "LicenseIncluded"
        storage_gb = (db.max_size_bytes or 32 * 1024**3) / (1024**3)
        sku_name = db.sku.name if db.sku else "Unknown"

        # Fetch CPU metrics from Azure Monitor
        metrics = get_cpu_metrics(monitor_client, db.id, days=14)

        # Estimate costs
        current_cost = estimate_monthly_cost_provisioned(
            vcores, license_type, storage_gb, use_ri_hb=False
        )
        serverless_cost = estimate_monthly_cost_serverless(
            vcores, metrics["avg_active_hours_per_day"], storage_gb
        )
        ri_hb_cost = estimate_monthly_cost_provisioned(
            vcores, "BasePrice", storage_gb, use_ri_hb=True
        )

        analysis_input = {
            "monthly_cost_current": current_cost,
            "monthly_cost_serverless": serverless_cost,
            "monthly_cost_provisioned_rib_hb": ri_hb_cost,
            "avg_active_hours_per_day": metrics["avg_active_hours_per_day"],
            "license_type": license_type,
            "current_sku": sku_name,
            "current_vcores": vcores,
            "storage_gb": storage_gb,
        }

        recommendation, monthly_savings = make_recommendation(analysis_input)

        results.append(DatabaseAnalysis(
            server_name=server_name,
            database_name=db.name,
            resource_group=rg,
            current_sku=sku_name,
            current_vcores=vcores,
            license_type=license_type,
            avg_cpu_pct=round(metrics["avg_cpu_pct"], 2),
            p95_cpu_pct=round(metrics["p95_cpu_pct"], 2),
            avg_active_hours_per_day=round(metrics["avg_active_hours_per_day"], 2),
            storage_gb=round(storage_gb, 2),
            monthly_cost_current=round(current_cost, 2),
            monthly_cost_serverless=round(serverless_cost, 2),
            monthly_cost_provisioned_rib_hb=round(ri_hb_cost, 2),
            recommendation=recommendation,
            monthly_savings=round(monthly_savings, 2),
            annual_savings=round(monthly_savings * 12, 2),
        ))

    # Sort by annual savings descending
    results.sort(key=lambda x: x.annual_savings, reverse=True)

    # Write CSV report
    with open(output_path, "w", newline="") as f:
        writer = csv.DictWriter(f, fieldnames=list(asdict(results[0]).keys()) if results else [])
        writer.writeheader()
        for row in results:
            writer.writerow(asdict(row))

    total_monthly = sum(r.monthly_savings for r in results)
    total_annual = sum(r.annual_savings for r in results)
    actionable = sum(1 for r in results if r.monthly_savings > 0)

    print(f"\n{'='*60}")
    print(f"  Analysis complete. {len(results)} databases evaluated.")
    print(f"  Actionable recommendations: {actionable}")
    print(f"  Total potential monthly savings: ${total_monthly:,.2f}")
    print(f"  Total potential annual savings:  ${total_annual:,.2f}")
    print(f"  Report written to: {output_path}")
    print(f"{'='*60}\n")


if __name__ == "__main__":
    parser = argparse.ArgumentParser(description="Azure SQL right-sizing analysis")
    parser.add_argument("--subscription-id", required=True)
    parser.add_argument("--output-path", default="./sql_rightsizing.csv")
    args = parser.parse_args()
    analyze_subscription(args.subscription_id, args.output_path)

    > Operational note: The pricing constants at the top of the script are point-in-time estimates for East US. Pull current rates from the [Azure Pricing Calculator](https://azure.microsoft.com/en-us/pricing/calculator/) or the Azure Retail Prices API (https://prices.azure.com/api/retail/prices) before running this in production. The script's structure separates pricing constants from logic precisely so they can be updated without touching the analysis code.

    3.6 Migrating from DTU to vCore Without Downtime

    The migration from DTU to vCore in Azure SQL is a metadata operation — it does not move data. Azure performs the migration online, and the database remains available throughout. The observable effect is a brief failover (typically under 30 seconds) at the end of the operation as connections are routed to the new compute tier.

    #### Pre-Migration Checklist

    Before initiating the tier change:

    1. Confirm the vCore count meets your workload requirement. Run the utilization queries in Section 3.2. If P95 CPU utilization on a P1 (125 DTU) is 40%, a 2-vCore General Purpose is adequate; 4 vCores gives headroom.

    2. Check storage. vCore General Purpose databases include storage billed separately at $0.115/GB/month with a 32 GB minimum. Ensure the max size you set equals your actual data volume, not the inherited DTU default (which may be over-provisioned).

    3. Notify application teams of the failover window. 30 seconds is brief but will drop active connections. Schedule during low-traffic periods or ensure your application uses retry logic (ADO.NET connection resiliency, SqlRetryLogicBaseProvider, or equivalent).

    4. Verify feature compatibility. DTU Premium supports In-Memory OLTP (memory-optimized tables). vCore General Purpose does not. If your database uses MEMORY_OPTIMIZED = ON tables, migrate to Business Critical, not General Purpose.

    #### Executing the Migration

    #!/bin/bash
# Migrate a single Azure SQL database from DTU (Premium) to vCore General Purpose
# with Hybrid Benefit applied in a single operation.

RESOURCE_GROUP="prod-databases-rg"
SERVER_NAME="prod-sqlserver-eastus"
DATABASE_NAME="orders-db"

echo "Current configuration:"
az sql db show \
  --resource-group "$RESOURCE_GROUP" \
  --server "$SERVER_NAME" \
  --name "$DATABASE_NAME" \
  --query "{name:name, edition:edition, objective:currentServiceObjectiveName, licenseType:licenseType, maxSizeGb:maxSizeBytes}" \
  --output table

echo ""
echo "Initiating migration to vCore General Purpose 4 with Hybrid Benefit..."
echo "Note: A brief failover (~30 seconds) will occur during the transition."

az sql db update \
  --resource-group "$RESOURCE_GROUP" \
  --server "$SERVER_NAME" \
  --name "$DATABASE_NAME" \
  --edition "GeneralPurpose" \
  --family "Gen5" \
  --capacity 4 \
  --license-type "BasePrice" \
  --max-size "250GB"

echo ""
echo "Migration complete. Verifying new configuration:"
az sql db show \
  --resource-group "$RESOURCE_GROUP" \
  --server "$SERVER_NAME" \
  --name "$DATABASE_NAME" \
  --query "{name:name, edition:edition, objective:currentServiceObjectiveName, licenseType:licenseType, vcores:currentSku.capacity}" \
  --output table

    For Managed Instance migrations (which are more complex and involve compute tier changes at the instance level), the pattern is similar but uses az sql mi update with --service-principal-type and --tier flags. Managed Instance migrations are covered in Chapter 6.

    #### Post-Migration Validation

    After migration, run the following query to confirm the database is operating on the new tier and that performance is acceptable:

    -- Post-migration health check
-- Run immediately after migration and again 24 hours later

SELECT
    DB_NAME()                                           AS [Database],
    DATABASEPROPERTYEX(DB_NAME(), 'ServiceObjective')  AS [Current_SKU],
    DATABASEPROPERTYEX(DB_NAME(), 'Edition')            AS [Edition],
    -- Check for any resource waits that indicate underpowering
    wait_type,
    waiting_tasks_count,
    wait_time_ms / 1000.0                               AS wait_time_sec,
    signal_wait_time_ms / 1000.0                        AS signal_wait_sec,
    (wait_time_ms - signal_wait_time_ms) / 1000.0       AS resource_wait_sec
FROM sys.dm_os_wait_stats
WHERE wait_type NOT IN (
    -- Filter out benign wait types
    'SLEEP_TASK', 'BROKER_TO_FLUSH', 'BROKER_TASK_STOP',
    'CLR_AUTO_EVENT', 'DISPATCHER_QUEUE_SEMAPHORE',
    'FT_IFTS_SCHEDULER_IDLE_WAIT', 'HADR_FILESTREAM_IOMGR_IOCOMPLETION',
    'HADR_WORK_QUEUE', 'LAZYWRITER_SLEEP', 'LOGMGR_QUEUE',
    'ONDEMAND_TASK_QUEUE', 'REQUEST_FOR_DEADLOCK_SEARCH',
    'RESOURCE_QUEUE', 'SERVER_IDLE_CHECK', 'SLEEP_DBSTARTUP',
    'SLEEP_DBRECOVER', 'SLEEP_DBTASK', 'SLEEP_MASTERDBREADY',
    'SLEEP_MASTERMDREADY', 'SLEEP_MASTERUPGRADED', 'SLEEP_MSDBSTARTUP',
    'SLEEP_SYSTEMTASK', 'SLEEP_TEMPDBSTARTUP', 'SNI_HTTP_ACCEPT',
    'SP_SERVER_DIAGNOSTICS_SLEEP', 'SQLTRACE_BUFFER_FLUSH',
    'SQLTRACE_INCREMENTAL_FLUSH_SLEEP', 'WAIT_XTP_OFFLINE_CKPT_NEW_LOG',
    'WAITFOR', 'XE_DISPATCHER_WAIT', 'XE_TIMER_EVENT',
    'BROKER_EVENTHANDLER', 'CHECKPOINT_QUEUE', 'DBMIRROR_EVENTS_QUEUE',
    'SQLTRACE_WAIT_ENTRIES'
)
AND waiting_tasks_count > 0
ORDER BY wait_time_ms DESC;

    High RESOURCE_SEMAPHORE or PAGEIOLATCH_SH waits after migration indicate memory or I/O pressure and should trigger an upsize or a query tuning review before concluding the migration is cost-optimal.

    3.7 Configuring Serverless Auto-Pause for Non-Production Databases

    Development, staging, and integration test databases are the most reliable candidates for Serverless. They typically follow strict business-hours usage patterns, developers tolerate cold-start latency, and they accumulate cost around the clock despite sitting idle nights and weekends.

    #### Setting Up Serverless via Azure CLI

    #!/bin/bash
# Convert a provisioned General Purpose database to Serverless
# Best suited for dev/test databases with predictable idle windows

RESOURCE_GROUP="dev-databases-rg"
SERVER_NAME="dev-sqlserver-eastus"
DATABASE_NAME="integration-test-db"

# Step 1: Confirm current configuration
echo "Current configuration:"
az sql db show \
  --resource-group "$RESOURCE_GROUP" \
  --server "$SERVER_NAME" \
  --name "$DATABASE_NAME" \
  --query "{edition:edition, objective:currentServiceObjectiveName, minCapacity:minCapacity, autoPauseDelay:autoPauseDelay}" \
  --output table

# Step 2: Convert to Serverless
# --auto-pause-delay: minutes before auto-pause (-1 = disabled, 60 minimum when enabled)
# --min-capacity: minimum vCores when active (0.5 is the lowest)
# --capacity: maximum vCores

az sql db update \
  --resource-group "$RESOURCE_GROUP" \
  --server "$SERVER_NAME" \
  --name "$DATABASE_NAME" \
  --edition "GeneralPurpose" \
  --family "Gen5" \
  --compute-model Serverless \
  --min-capacity 0.5 \
  --capacity 4 \
  --auto-pause-delay 60

echo ""
echo "Serverless configuration applied."

# Step 3: For production-adjacent staging environments, use a longer pause delay
# to prevent cold starts during occasional off-hours test runs

DATABASE_NAME_STAGING="staging-db"
az sql db update \
  --resource-group "$RESOURCE_GROUP" \
  --server "$SERVER_NAME" \
  --name "$DATABASE_NAME_STAGING" \
  --edition "GeneralPurpose" \
  --family "Gen5" \
  --compute-model Serverless \
  --min-capacity 1 \
  --capacity 8 \
  --auto-pause-delay 120

echo "Staging Serverless configuration applied (120-minute auto-pause delay)."

# Step 4: Verify both databases
az sql db list \
  --resource-group "$RESOURCE_GROUP" \
  --server "$SERVER_NAME" \
  --query "[?computeModel=='Serverless'].{name:name, minCap:minCapacity, maxCap:currentSku.capacity, pauseDelay:autoPauseDelay}" \
  --output table

    #### Monitoring Serverless Pause State

    A database in the paused state does not appear in sys.dm_db_resource_stats because the compute is not running. Use Azure Monitor or the management API to determine pause state:

    # Check whether a Serverless database is currently paused
az sql db show \
  --resource-group "dev-databases-rg" \
  --server "dev-sqlserver-eastus" \
  --name "integration-test-db" \
  --query "{name:name, status:status, pausedDate:pausedDate}" \
  --output table

    The status field returns Online, Paused, or Pausing. Track the proportion of time a database spends in Paused state over a month to validate your Serverless savings assumption — if it never pauses, the auto-pause delay may be set too long or the database is receiving constant low-level connections (health checks, monitoring agents) that prevent pausing. Identify and suppress those connections, or accept that this database is not a good Serverless candidate.

    3.8 Elastic Pools as a Cost Alternative to Individual Sizing

    When you have multiple databases with complementary usage patterns — some busy while others are idle — an Elastic Pool lets them share a vCore (or DTU) budget, smoothing out peaks through aggregation. A pool of 20 databases that individually require 4 vCores at peak but whose peaks do not overlap can often run on a 16-vCore pool, producing a 20% reduction in total compute cost.

    Elastic Pool sizing and management is covered in depth in Chapter 4. However, one question is worth answering here: should you migrate individual databases to vCore first, then pool them, or pool them before the DTU-to-vCore migration?

    The answer depends on operational complexity. If more than five databases are involved and they already share a logical server, migrate them into a vCore Elastic Pool in a single operation — it avoids the intermediate step. For databases spread across multiple logical servers, migrate to standalone vCore first (as described in Section 3.6), then consolidate servers and add the pool. Attempting both moves simultaneously increases rollback complexity.

    Key Takeaways

  • → **DTU opacity is a cost trap.** The bundled DTU metric prevents you from knowing whether your bottleneck is CPU, memory, or I/O — and therefore whether you're buying the right resources. Moving to vCore gives you observable dimensions, Hybrid Benefit eligibility, and reserved instance pricing, all of which the DTU model blocks.
  • → **Azure Hybrid Benefit and reserved instances are independent, stackable discounts that require no code changes.** Applied together on a 1-year commitment, they typically reduce vCore compute cost by 55–60% compared to DTU pay-as-you-go. Every vCore database that carries `LicenseIncluded` without a justification is burning money.
  • → **Serverless is the default choice for development and test databases.** Any database that sits idle for more than 12 hours per day — and can tolerate a 30–90 second cold start — will cost less on Serverless than on the smallest provisioned vCore tier. The break-even is roughly 50% average utilization over a full month.
  • → **DTU-to-vCore migration is online and takes under 30 seconds of failover.** The operational risk is low when retry logic is in place. The utilization queries in Section 3.2 provide the data you need to right-size the vCore count before migrating rather than after.
  • → **The Python right-sizing script in Section 3.5 turns a manual audit into a repeatable weekly process.** Run it as an Azure Function on a Monday morning cadence, write the CSV to Blob Storage, and route high-savings recommendations to a Teams or Slack channel. The compounding effect of catching new databases early — before they run for 12 months at the wrong tier — is where most of the annual savings accumulates.
