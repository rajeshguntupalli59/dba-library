Chapter 21: Caching Layer Economics: ElastiCache vs Database Direct

Organizations that add a properly sized Redis caching layer in front of their RDS for SQL Server instances typically see database costs drop by 30–60% within the first billing cycle. A mid-size SaaS company running a db.r5.2xlarge RDS for SQL Server instance at roughly $1,400/month (License Included) can often drop to a db.r5.xlarge at roughly $700/month after offloading read traffic to ElastiCache for Redis — a cache.r6g.large at $104/month — netting around $600/month in savings. This chapter walks through the economics of caching layer decisions: when adding cache actually saves money, when it just adds complexity and cost, how to right-size ElastiCache clusters, and how to automate cache hit rate monitoring so you catch degradation before it shows up on your AWS bill.

21.1 The Caching Economics Baseline: When Cache Pays for Itself

Before spending a dollar on ElastiCache or Memorystore, you need to establish whether your workload actually benefits from caching. The economics break down into three scenarios, and only two of them favor adding a cache tier.

Scenario A — High read ratio, repetitive queries: Your database serves 90% reads, and a meaningful percentage of those reads fetch the same rows repeatedly. Product catalogs, user profiles, session data, configuration tables. Cache wins overwhelmingly here.

Scenario B — Write-heavy transactional workload: Your database is processing orders, logging events, or updating financial ledgers. Reads are largely unique. Cache adds cost without meaningful throughput benefit.

Scenario C — Mixed workload with hot data concentration: 80% of reads hit 20% of rows. This is the most common production pattern and the most nuanced to optimize.

The first diagnostic step is measuring your current read/write ratio and query repetition rate directly from the database engine. This query runs against SQL Server Query Store and gives you the data needed to build the business case:

-- SQL Server: read/write ratio and query repetition from Query Store
-- Run on the database with Query Store enabled
WITH query_agg AS (
    SELECT
        q.query_id,
        LEFT(qt.query_sql_text, 80)                     AS query_preview,
        SUM(rs.count_executions)                        AS calls,
        SUM(rs.avg_duration * rs.count_executions)
            / 1000.0                                    AS total_exec_ms,
        SUM(rs.avg_rowcount * rs.count_executions)      AS total_rows,
        SUM(rs.avg_logical_io_reads * rs.count_executions)
                                                        AS total_logical_reads
    FROM sys.query_store_query q
    JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
    JOIN sys.query_store_plan pl       ON pl.query_id = q.query_id
    JOIN sys.query_store_runtime_stats rs ON rs.plan_id = pl.plan_id
    WHERE rs.last_execution_time >= DATEADD(DAY, -7, SYSDATETIME())
    GROUP BY q.query_id, qt.query_sql_text
    HAVING SUM(rs.count_executions) > 100
)
SELECT TOP 50
    query_preview,
    calls,
    ROUND(total_exec_ms / NULLIF(calls, 0), 2)          AS avg_ms,
    ROUND(total_exec_ms / 1000.0, 2)                    AS total_exec_sec,
    total_rows,
    ROUND(CAST(total_rows AS FLOAT) / NULLIF(calls, 0), 1)
                                                        AS avg_rows_returned,
    total_logical_reads,
    -- Queries returning a stable small row set are cache candidates
    CASE
        WHEN calls > 1000
         AND CAST(total_rows AS FLOAT) / NULLIF(calls, 0) BETWEEN 1 AND 50
            THEN 'HIGH cache candidate'
        WHEN calls > 500
         AND CAST(total_rows AS FLOAT) / NULLIF(calls, 0) < 100
            THEN 'MEDIUM cache candidate'
        ELSE 'LOW cache value'
    END                                                 AS cache_recommendation
FROM query_agg
ORDER BY calls DESC;

For SQL Server on RDS or Azure SQL, the equivalent analysis pulls from sys.dm_exec_query_stats:

-- SQL Server: Identify repetitive read queries suitable for caching
SELECT TOP 40
    LEFT(qt.text, 100)                                          AS query_preview,
    qs.execution_count,
    qs.total_logical_reads / qs.execution_count                 AS avg_logical_reads,
    qs.total_elapsed_time / qs.execution_count / 1000          AS avg_elapsed_ms,
    qs.total_rows / qs.execution_count                         AS avg_rows,
    qs.total_logical_reads                                      AS total_logical_reads,
    -- Estimate I/O cost: each logical read = ~8KB page
    -- At 50,000 IOPS provisioned IOPS cost on io1, each read has a cost
    CAST(qs.total_logical_reads * 8.0 / 1024 / 1024 AS DECIMAL(10,2)) AS total_data_gb_read,
    CASE
        WHEN qs.execution_count > 1000
         AND qs.total_rows / qs.execution_count < 100
        THEN 'CACHE NOW'
        WHEN qs.execution_count > 500
        THEN 'EVALUATE'
        ELSE 'SKIP'
    END                                                         AS cache_action
FROM
    sys.dm_exec_query_stats qs
    CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) qt
WHERE
    qt.text NOT LIKE '%sys.dm%'
    AND qs.total_logical_reads > 0
ORDER BY
    qs.execution_count DESC;

21.2 ElastiCache Sizing and Configuration for Maximum Cost Efficiency

The single most common ElastiCache mistake is over-provisioning. Teams spin up cache.r6g.2xlarge nodes because their database is large, when the working set of frequently accessed data is often a fraction of total database size. A 500GB database might have a hot working set of only 8–12GB.

Measuring your actual working set size in SQL Server:

-- SQL Server: estimate hot data working set from index usage and table sizes
-- Tables with heavy user seeks/scans but low buffer-pool residency are cache candidates
SELECT TOP 30
    OBJECT_SCHEMA_NAME(i.object_id)                       AS schema_name,
    OBJECT_NAME(i.object_id)                               AS table_name,
    i.name                                                 AS index_name,
    ius.user_seeks + ius.user_scans                        AS read_operations,
    ius.user_updates                                       AS write_operations,
    CAST(SUM(a.total_pages) * 8.0 / 1024 AS DECIMAL(12,2)) AS table_size_mb,
    -- High reads with low buffer residency = cache opportunity
    CASE
        WHEN ius.user_seeks + ius.user_scans > 10000
         AND ius.user_updates < (ius.user_seeks + ius.user_scans) / 10
            THEN 'HIGH cache candidate'
        ELSE 'LOW cache value'
    END                                                    AS cache_recommendation
FROM sys.indexes i
JOIN sys.dm_db_index_usage_stats ius
    ON ius.object_id = i.object_id AND ius.index_id = i.index_id
    AND ius.database_id = DB_ID()
JOIN sys.partitions p ON p.object_id = i.object_id AND p.index_id = i.index_id
JOIN sys.allocation_units a ON a.container_id = p.hobt_id
WHERE ius.user_seeks + ius.user_scans > 1000
GROUP BY i.object_id, i.name, ius.user_seeks, ius.user_scans, ius.user_updates
ORDER BY read_operations DESC;

-- Total estimated cache requirement: sum of hot-table data sizes
WITH hot_tables AS (
    SELECT DISTINCT i.object_id
    FROM sys.indexes i
    JOIN sys.dm_db_index_usage_stats ius
        ON ius.object_id = i.object_id AND ius.index_id = i.index_id
        AND ius.database_id = DB_ID()
    WHERE ius.user_seeks + ius.user_scans > 10000
)
SELECT
    CAST(SUM(a.total_pages) * 8.0 / 1024 / 1024 AS DECIMAL(12,2))
                                                       AS estimated_cache_requirement_gb
FROM hot_tables ht
JOIN sys.partitions p ON p.object_id = ht.object_id
JOIN sys.allocation_units a ON a.container_id = p.hobt_id;

The Python script below automates cluster sizing recommendations by pulling CloudWatch metrics and comparing against current node specifications:

#!/usr/bin/env python3
"""
ElastiCache Sizing Analyzer
Pulls CloudWatch metrics for existing clusters and recommends right-sizing.
Schedule via CloudWatch Events or GitHub Actions weekly.
"""

import boto3
import json
from datetime import datetime, timedelta
from dataclasses import dataclass
from typing import Optional


@dataclass
class ClusterSizingRecommendation:
    cluster_id: str
    current_node_type: str
    current_monthly_cost: float
    avg_memory_utilization_pct: float
    max_memory_utilization_pct: float
    avg_cpu_utilization_pct: float
    avg_cache_hit_rate_pct: float
    recommended_node_type: Optional[str]
    recommended_monthly_cost: Optional[float]
    monthly_savings: float
    action: str
    reasoning: str


# Current on-demand hourly pricing (us-east-1, update as needed)
ELASTICACHE_PRICING = {
    "cache.t4g.micro":    {"memory_gb": 0.5,   "hourly": 0.008},
    "cache.t4g.small":    {"memory_gb": 1.37,  "hourly": 0.016},
    "cache.t4g.medium":   {"memory_gb": 3.09,  "hourly": 0.032},
    "cache.r6g.large":    {"memory_gb": 13.07, "hourly": 0.145},
    "cache.r6g.xlarge":   {"memory_gb": 26.32, "hourly": 0.290},
    "cache.r6g.2xlarge":  {"memory_gb": 52.82, "hourly": 0.580},
    "cache.r6g.4xlarge":  {"memory_gb": 105.81,"hourly": 1.160},
    "cache.r6g.8xlarge":  {"memory_gb": 209.55,"hourly": 2.320},
}

HOURS_PER_MONTH = 730


def get_cloudwatch_metric_stats(cw_client, cluster_id, metric_name,
                                 namespace, dimension_name, days=14):
    """Retrieve average and max for a CloudWatch metric over the past N days."""
    end_time = datetime.utcnow()
    start_time = end_time - timedelta(days=days)

    response = cw_client.get_metric_statistics(
        Namespace=namespace,
        MetricName=metric_name,
        Dimensions=[{"Name": dimension_name, "Value": cluster_id}],
        StartTime=start_time,
        EndTime=end_time,
        Period=3600,  # 1-hour granularity
        Statistics=["Average", "Maximum"]
    )

    datapoints = response.get("Datapoints", [])
    if not datapoints:
        return 0.0, 0.0

    avg_vals = [dp["Average"] for dp in datapoints]
    max_vals = [dp["Maximum"] for dp in datapoints]
    return sum(avg_vals) / len(avg_vals), max(max_vals)


def analyze_cluster(ec_client, cw_client, cluster_id: str,
                    node_type: str) -> ClusterSizingRecommendation:
    """Analyze a single ElastiCache cluster and generate sizing recommendation."""

    current_pricing = ELASTICACHE_PRICING.get(node_type, {})
    current_hourly = current_pricing.get("hourly", 0.0)
    current_monthly = current_hourly * HOURS_PER_MONTH

    # Pull key metrics from CloudWatch
    avg_mem, max_mem = get_cloudwatch_metric_stats(
        cw_client, cluster_id, "DatabaseMemoryUsagePercentage",
        "AWS/ElastiCache", "CacheClusterId"
    )
    avg_cpu, max_cpu = get_cloudwatch_metric_stats(
        cw_client, cluster_id, "CPUUtilization",
        "AWS/ElastiCache", "CacheClusterId"
    )
    avg_hits, _ = get_cloudwatch_metric_stats(
        cw_client, cluster_id, "CacheHits",
        "AWS/ElastiCache", "CacheClusterId"
    )
    avg_misses, _ = get_cloudwatch_metric_stats(
        cw_client, cluster_id, "CacheMisses",
        "AWS/ElastiCache", "CacheClusterId"
    )

    # Calculate cache hit rate
    total_ops = avg_hits + avg_misses
    cache_hit_rate = (avg_hits / total_ops * 100) if total_ops > 0 else 0.0

    recommended_node = None
    recommended_monthly = None
    action = "KEEP"
    reasoning = ""

    # Sizing decision logic
    if avg_mem < 30 and max_mem < 45:
        # Memory significantly underutilized — downsize candidate
        node_types_sorted = sorted(
            ELASTICACHE_PRICING.items(),
            key=lambda x: x[1]["memory_gb"]
        )
        current_memory = current_pricing.get("memory_gb", 0)
        target_memory = current_memory * (max_mem / 100) * 1.5  # 50% headroom

        for node_name, node_specs in node_types_sorted:
            if node_specs["memory_gb"] >= target_memory:
                if node_specs["hourly"] < current_hourly:
                    recommended_node = node_name
                    recommended_monthly = node_specs["hourly"] * HOURS_PER_MONTH
                    action = "DOWNSIZE"
                    reasoning = (
                        f"Avg memory {avg_mem:.1f}%, max {max_mem:.1f}%. "
                        f"Node is oversized. Target memory: {target_memory:.1f}GB."
                    )
                break

    elif max_mem > 85:
        # Memory pressure — upsize required
        node_types_sorted = sorted(
            ELASTICACHE_PRICING.items(),
            key=lambda x: x[1]["memory_gb"]
        )
        current_memory = current_pricing.get("memory_gb", 0)
        target_memory = current_memory * 1.5

        for node_name, node_specs in node_types_sorted:
            if node_specs["memory_gb"] >= target_memory:
                recommended_node = node_name
                recommended_monthly = node_specs["hourly"] * HOURS_PER_MONTH
                action = "UPSIZE"
                reasoning = (
                    f"Max memory utilization {max_mem:.1f}% indicates eviction risk. "
                    f"Recommend node with {target_memory:.1f}GB+ memory."
                )
                break

    if cache_hit_rate < 80 and action == "KEEP":
        action = "INVESTIGATE"
        reasoning = (
            f"Cache hit rate {cache_hit_rate:.1f}% is below 80% threshold. "
            f"Cache may not be providing adequate value — review TTL and key strategy."
        )

    if action == "KEEP" and not reasoning:
        reasoning = (
            f"Memory utilization healthy at avg {avg_mem:.1f}%, max {max_mem:.1f}%. "
            f"Cache hit rate {cache_hit_rate:.1f}% is acceptable."
        )

    monthly_savings = 0.0
    if recommended_monthly and action == "DOWNSIZE":
        monthly_savings = current_monthly - recommended_monthly
    elif recommended_monthly and action == "UPSIZE":
        monthly_savings = -(recommended_monthly - current_monthly)  # negative = cost increase

    return ClusterSizingRecommendation(
        cluster_id=cluster_id,
        current_node_type=node_type,
        current_monthly_cost=round(current_monthly, 2),
        avg_memory_utilization_pct=round(avg_mem, 1),
        max_memory_utilization_pct=round(max_mem, 1),
        avg_cpu_utilization_pct=round(avg_cpu, 1),
        avg_cache_hit_rate_pct=round(cache_hit_rate, 1),
        recommended_node_type=recommended_node,
        recommended_monthly_cost=round(recommended_monthly, 2) if recommended_monthly else None,
        monthly_savings=round(monthly_savings, 2),
        action=action,
        reasoning=reasoning
    )


def main():
    session = boto3.Session()
    ec_client = session.client("elasticache", region_name="us-east-1")
    cw_client = session.client("cloudwatch", region_name="us-east-1")

    # Get all Redis clusters
    paginator = ec_client.get_paginator("describe_cache_clusters")
    all_clusters = []
    for page in paginator.paginate(ShowCacheNodeInfo=True):
        all_clusters.extend(page["CacheClusters"])

    recommendations = []
    total_current_monthly = 0.0
    total_potential_savings = 0.0

    print(f"\n{'='*80}")
    print(f"ElastiCache Sizing Report — {datetime.utcnow().strftime('%Y-%m-%d %H:%M UTC')}")
    print(f"{'='*80}\n")

    for cluster in all_clusters:
        cluster_id = cluster["CacheClusterId"]
        node_type = cluster["CacheNodeType"]
        engine = cluster.get("Engine", "unknown")

        if engine != "redis":
            continue

        rec = analyze_cluster(ec_client, cw_client, cluster_id, node_type)
        recommendations.append(rec)

        total_current_monthly += rec.current_monthly_cost
        if rec.monthly_savings > 0:
            total_potential_savings += rec.monthly_savings

        print(f"Cluster: {rec.cluster_id}")
        print(f"  Current Node:       {rec.current_node_type} (${rec.current_monthly_cost:.2f}/mo)")
        print(f"  Memory Util:        avg {rec.avg_memory_utilization_pct}% / max {rec.max_memory_utilization_pct}%")
        print(f"  CPU Util:           avg {rec.avg_cpu_utilization_pct}%")
        print(f"  Cache Hit Rate:     {rec.avg_cache_hit_rate_pct}%")
        print(f"  Action:             {rec.action}")
        print(f"  Reasoning:          {rec.reasoning}")
        if rec.recommended_node_type:
            print(f"  Recommended Node:   {rec.recommended_node_type} (${rec.recommended_monthly_cost:.2f}/mo)")
            print(f"  Monthly Savings:    ${rec.monthly_savings:.2f}")
        print()

    print(f"{'='*80}")
    print(f"SUMMARY")
    print(f"  Total Current Monthly Cost:     ${total_current_monthly:.2f}")
    print(f"  Total Potential Monthly Savings: ${total_potential_savings:.2f}")
    print(f"  Annual Savings Opportunity:      ${total_potential_savings * 12:.2f}")
    print(f"{'='*80}\n")

    # Write JSON output for downstream processing or ticketing
    output = {
        "generated_at": datetime.utcnow().isoformat(),
        "total_current_monthly_cost": round(total_current_monthly, 2),
        "total_potential_monthly_savings": round(total_potential_savings, 2),
        "recommendations": [
            {
                "cluster_id": r.cluster_id,
                "current_node_type": r.current_node_type,
                "current_monthly_cost": r.current_monthly_cost,
                "action": r.action,
                "recommended_node_type": r.recommended_node_type,
                "monthly_savings": r.monthly_savings,
                "reasoning": r.reasoning
            }
            for r in recommendations
        ]
    }

    with open("/tmp/elasticache_sizing_report.json", "w") as f:
        json.dump(output, f, indent=2)
    print("Report written to /tmp/elasticache_sizing_report.json")


if __name__ == "__main__":
    main()

21.3 Cache Hit Rate Monitoring and the Cost of Cache Misses

A cache that isn't hitting is worse than no cache at all — you've added infrastructure cost and latency on cache misses without reducing database load. The break-even cache hit rate for most workloads is approximately 60–70%, but the economic sweet spot is 85% or higher.

Here is the math on why cache hit rate matters so much to your bill. Consider an application serving 10,000 requests/minute:

  • → At **50% hit rate**: 5,000 requests/minute still hit the database. Database must be sized for full concurrent load.
  • → At **80% hit rate**: 2,000 requests/minute hit the database. Database can be one tier smaller.
  • → At **95% hit rate**: 500 requests/minute hit the database. Database can often drop two tiers.

    • For a db.r5.4xlarge RDS for SQL Server Multi-AZ (roughly $5,600/month License Included, illustrative) that can be right-sized based on cache effectiveness:

  • → 80% hit rate → `r6g.2xlarge` ($1,752/month) + `cache.r6g.xlarge` ($208/month) = **$1,544/month savings**
  • → 95% hit rate → `r6g.xlarge` ($876/month) + `cache.r6g.xlarge` ($208/month) = **$2,420/month savings**

    • The difference between 80% and 95% cache effectiveness is worth nearly $900/month on that single instance. Monitoring hit rate and acting on degradation is not optional — it's the financial control mechanism for the entire caching strategy.

    CloudWatch Metrics for ElastiCache Redis hit rate monitoring:

    The two primary metrics are CacheHits and CacheMisses. AWS does not publish a pre-computed hit rate metric, so you need to derive it using metric math. The CloudWatch alarm below triggers when the rolling hit rate drops below your threshold:

    #!/usr/bin/env python3
"""
ElastiCache Cache Hit Rate Alarm Setup
Creates CloudWatch metric math alarms for cache hit rate monitoring.
Run once per cluster to establish monitoring baseline.
"""

import boto3
import json


def create_cache_hit_rate_alarm(
    cluster_id: str,
    threshold_pct: float = 80.0,
    evaluation_periods: int = 3,
    period_seconds: int = 300,
    sns_topic_arn: str = None,
    region: str = "us-east-1"
):
    """
    Create a CloudWatch alarm that fires when cache hit rate drops below threshold.
    Uses metric math to compute HitRate = Hits / (Hits + Misses) * 100.
    """
    cw_client = boto3.client("cloudwatch", region_name=region)

    alarm_name = f"elasticache-hit-rate-low-{cluster_id}"
    alarm_description = (
        f"Cache hit rate for {cluster_id} has dropped below {threshold_pct}% "
        f"over {evaluation_periods} consecutive {period_seconds//60}-minute periods. "
        f"Database load may be increasing. Review TTL settings and key eviction policy."
    )

    alarm_actions = []
    if sns_topic_arn:
        alarm_actions.append(sns_topic_arn)

    # Metric math: HitRate = (Hits / (Hits + Misses)) * 100
    # CloudWatch metric math requires FILL to handle zero-division gracefully
    metrics = [
        {
            "Id": "hits",
            "MetricStat": {
                "Metric": {
                    "Namespace": "AWS/ElastiCache",
                    "MetricName": "CacheHits",
                    "Dimensions": [
                        {"Name": "CacheClusterId", "Value": cluster_id}
                    ]
                },
                "Period": period_seconds,
                "Stat": "Sum"
            },
            "ReturnData": False
        },
        {
            "Id": "misses",
            "MetricStat": {
                "Metric": {
                    "Namespace": "AWS/ElastiCache",
                    "MetricName": "CacheMisses",
                    "Dimensions": [
                        {"Name": "CacheClusterId", "Value": cluster_id}
                    ]
                },
                "Period": period_seconds,
                "Stat": "Sum"
            },
            "ReturnData": False
        },
        {
            "Id": "hit_rate",
            "Expression": "IF(hits+misses > 0, (hits/(hits+misses))*100, 100)",
            "Label": "CacheHitRatePct",
            "ReturnData": True
        }
    ]

    cw_client.put_metric_alarm(
        AlarmName=alarm_name,
        AlarmDescription=alarm_description,
        Metrics=metrics,
        ComparisonOperator="LessThanThreshold",
        Threshold=threshold_pct,
        EvaluationPeriods=evaluation_periods,
        DatapointsToAlarm=evaluation_periods,
        TreatMissingData="notBreaching",
        AlarmActions=alarm_actions,
        OKActions=alarm_actions
    )

    print(f"Created alarm: {alarm_name}")
    print(f"  Threshold:           Hit rate < {threshold_pct}%")
    print(f"  Evaluation window:   {evaluation_periods * period_seconds // 60} minutes")
    print(f"  SNS notification:    {sns_topic_arn or 'none configured'}")
    return alarm_name


def create_evictions_alarm(
    cluster_id: str,
    evictions_threshold: int = 1000,
    period_seconds: int = 300,
    sns_topic_arn: str = None,
    region: str = "us-east-1"
):
    """
    Create alarm for cache evictions — a leading indicator of memory pressure
    that precedes hit rate degradation.
    """
    cw_client = boto3.client("cloudwatch", region_name=region)

    alarm_name = f"elasticache-evictions-high-{cluster_id}"

    cw_client.put_metric_alarm(
        AlarmName=alarm_name,
        AlarmDescription=(
            f"High eviction rate on {cluster_id}. Memory pressure is causing "
            f"key evictions, which will degrade cache hit rate and increase "
            f"database load. Consider upsizing or reviewing maxmemory-policy."
        ),
        Namespace="AWS/ElastiCache",
        MetricName="Evictions",
        Dimensions=[{"Name": "CacheClusterId", "Value": cluster_id}],
        Period=period_seconds,
        Statistic="Sum",
        ComparisonOperator="GreaterThanThreshold",
        Threshold=evictions_threshold,
        EvaluationPeriods=2,
        DatapointsToAlarm=2,

    Diagnosing hit rate degradation — what actually causes it:

    When your cache hit rate drops, the cause is almost always one of four things:

    1. TTL too short — Keys expire before they can be reused. Check your application's cache TTL settings against actual query repetition frequency. A user profile queried once every 15 minutes with a 5-minute TTL will never hit cache.

    2. Key space explosion — Query parameters are being included in cache keys without normalization. user_profile:12345:v2:en-US and user_profile:12345:v2:en-GB might be the same data but generate separate keys, doubling your key count and halving effective hit rates.

    3. Memory pressure causing eviction — Check the Evictions CloudWatch metric. Non-zero evictions mean keys are being forced out before they naturally expire. The maxmemory-policy setting (allkeys-lru vs volatile-lru vs noeviction) determines what gets evicted first. For caching workloads, allkeys-lru is typically correct.

    4. Deployment or code push flushed the cache — A common pattern where cache warming hasn't completed post-deployment. Hit rates will recover organically within minutes to hours, but the database spike during that window can trigger auto-scaling events or performance alerts.

    The following SQL Server query, run after a cache hit rate drop, helps identify which tables have suddenly started generating high physical read volume — a direct signal that previously cached data is now bypassing cache:

    -- SQL Server: which tables lost cache coverage (physical reads spiking)
SELECT TOP 30
    OBJECT_SCHEMA_NAME(i.object_id)                       AS schema_name,
    OBJECT_NAME(i.object_id)                               AS table_name,
    SUM(ius.user_seeks + ius.user_scans + ius.user_lookups) AS read_ops,
    CAST(SUM(a.total_pages) * 8.0 / 1024 AS DECIMAL(12,2)) AS table_size_mb,
    -- Sudden read-op growth on a table that "should" be cached
    -- signals cache misses on that key pattern — compare to last week's baseline
    ius.last_user_seek,
    ius.last_user_scan
FROM sys.indexes i
JOIN sys.dm_db_index_usage_stats ius
    ON ius.object_id = i.object_id AND ius.index_id = i.index_id
    AND ius.database_id = DB_ID()
JOIN sys.partitions p ON p.object_id = i.object_id AND p.index_id = i.index_id
JOIN sys.allocation_units a ON a.container_id = p.hobt_id
GROUP BY i.object_id, ius.last_user_seek, ius.last_user_scan
HAVING SUM(ius.user_seeks + ius.user_scans + ius.user_lookups) > 500
ORDER BY read_ops DESC;

    21.4 Multi-Tier Caching: When a Second Cache Layer Changes the Math

    For workloads with very high throughput — above roughly 50,000 requests per second to a single cache cluster — a second caching tier becomes both a performance and a cost optimization. The pattern is:

    1. Application-level in-memory cache (e.g., a 256MB Python functools.lru_cache or a Go sync.Map) absorbs the top 5–10% of the hottest keys with zero network overhead.

    2. ElastiCache Redis absorbs the next tier — high-frequency data with moderate working set size.

    3. RDS for SQL Server handles only cache misses from both layers above.

    The economics shift materially: the application-level cache costs nothing in AWS infrastructure dollars (it runs in your existing application server memory), so every request it absorbs is pure savings against both ElastiCache and RDS.

    flowchart LR
    A[Request] --> B{"L1: in-process
    cache hit?"}
    B -->|"Yes — ~free"| Z[Response]
    B -->|No| C{"L2: Redis
    cache hit?"}
    C -->|"Yes — ElastiCache cost"| Z
    C -->|No| D["L3: RDS SQL Server
    (most expensive tier)"]
    D --> Z

    *Each layer above the database absorbs load at a lower marginal cost than the one below it — L1 is free, L2 is metered, L3 is the most expensive tier to hit.*

    The gotcha with application-level caches in auto-scaling environments is consistency. When you have 20 application server instances each holding their own in-memory cache, you get 20 independent cache warming events after any deployment and 20 separate TTL clocks. The standard solution is short TTLs at the application layer (30–120 seconds) combined with longer TTLs in Redis, accepting brief inconsistency windows in exchange for the compute savings.

    This Python module demonstrates the two-tier caching pattern with explicit cost attribution logging — letting your FinOps tooling see exactly where each tier is absorbing load:

    """
Two-tier cache implementation with FinOps cost attribution.
Tier 1: Local in-process LRU cache (zero AWS cost)
Tier 2: ElastiCache Redis (metered AWS cost)
Tier 3: RDS for SQL Server (most expensive tier — minimize hits here)
"""

import time
import json
import hashlib
import logging
from functools import lru_cache
from collections import Counter
from threading import Lock
from typing import Any, Optional, Callable
import redis
import pyodbc

logger = logging.getLogger(__name__)


class TieredCacheMetrics:
    """Thread-safe counters for cost attribution across cache tiers."""

    def __init__(self):
        self._lock = Lock()
        self._counters = Counter()

    def record(self, tier: str, outcome: str):
        with self._lock:
            self._counters[f"{tier}:{outcome}"] += 1

    def report(self) -> dict:
        with self._lock:
            counters = dict(self._counters)

        l1_hits   = counters.get("l1:hit", 0)
        l2_hits   = counters.get("l2:hit", 0)
        l3_hits   = counters.get("l3:hit", 0)  # database hits
        l2_misses = counters.get("l2:miss", 0)

        total = l1_hits + l2_hits + l3_hits
        if total == 0:
            return {"total_requests": 0}

        return {
            "total_requests": total,
            "l1_hit_rate_pct": round(l1_hits / total * 100, 2),
            "l2_hit_rate_pct": round(l2_hits / total * 100, 2),
            "db_hit_rate_pct": round(l3_hits / total * 100, 2),
            "l1_hits": l1_hits,
            "l2_hits": l2_hits,
            "db_hits": l3_hits,
            # Cost attribution: only l3 hits have meaningful DB cost
            # l2 hits have ElastiCache cost (network + compute)
            # l1 hits are essentially free
            "estimated_db_queries_avoided": l1_hits + l2_hits,
            "cost_pressure_score": round(l3_hits / total * 100, 2)
        }


class TieredCache:
    """
    Two-tier cache: in-process dict (L1) + Redis (L2) + DB fallback (L3).
    L1 TTL is intentionally short to limit stale data exposure in
    horizontally scaled deployments.
    """

    def __init__(
        self,
        redis_client: redis.Redis,
        l1_max_size: int = 1000,
        l1_ttl_seconds: int = 60,
        l2_ttl_seconds: int = 3600
    ):
        self.redis = redis_client
        self.l1_ttl = l1_ttl_seconds
        self.l2_ttl = l2_ttl_seconds
        self.metrics = TieredCacheMetrics()

        # L1: simple dict with expiry timestamps
        self._l1: dict[str, tuple[Any, float]] = {}
        self._l1_max = l1_max_size
        self._l1_lock = Lock()

    def _make_key(self, namespace: str, identifier: str) -> str:
        """Produce a consistent, safe Redis key."""
        safe_id = hashlib.md5(identifier.encode()).hexdigest()
        return f"tc:{namespace}:{safe_id}"

    def _l1_get(self, key: str) -> tuple[bool, Any]:
        with self._l1_lock:
            entry = self._l1.get(key)
            if entry is None:
                return False, None
            value, expiry = entry
            if time.monotonic() > expiry:
                del self._l1[key]
                return False, None
            return True, value

    def _l1_set(self, key: str, value: Any):
        with self._l1_lock:
            # Evict oldest entry if at capacity (simple FIFO eviction)
            if len(self._l1) >= self._l1_max:
                oldest_key = next(iter(self._l1))
                del self._l1[oldest_key]
            self._l1[key] = (value, time.monotonic() + self.l1_ttl)

    def get_or_fetch(
        self,
        namespace: str,
        identifier: str,
        fetch_fn: Callable[[], Any],
        skip_l1: bool = False
    ) -> Any:
        """
        Retrieve value from L1 → L2 → L3 (fetch_fn) with metrics tracking.

        Args:
            namespace:    Cache namespace (e.g., 'user_profile', 'product_catalog')
            identifier:   Unique key within namespace (e.g., user_id as string)
            fetch_fn:     Callable that hits the database if both cache tiers miss
            skip_l1:      Force bypass of L1 (useful for write-through invalidation)
        """
        cache_key = self._make_key(namespace, identifier)

        # L1 check
        if not skip_l1:
            found, value = self._l1_get(cache_key)
            if found:
                self.metrics.record("l1", "hit")
                return value

        # L2 check (Redis)
        try:
            raw = self.redis.get(cache_key)
            if raw is not None:
                self.metrics.record("l2", "hit")
                value = json.loads(raw)
                if not skip_l1:
                    self._l1_set(cache_key, value)
                return value
            else:
                self.metrics.record("l2", "miss")
        except redis.RedisError as e:
            logger.warning(f"Redis error on GET {cache_key}: {e}. Falling through to DB.")
            self.metrics.record("l2", "error")

        # L3: database fetch
        self.metrics.record("l3", "hit")
        value = fetch_fn()

        if value is not None:
            # Populate both cache tiers on DB hit
            try:
                self.redis.setex(cache_key, self.l2_ttl, json.dumps(value))
            except redis.RedisError as e:
                logger.warning(f"Redis error on SET {cache_key}: {e}")
            self._l1_set(cache_key, value)

        return value

    def invalidate(self, namespace: str, identifier: str):
        """Remove a key from both cache tiers (use on write operations)."""
        cache_key = self._make_key(namespace, identifier)
        with self._l1_lock:
            self._l1.pop(cache_key, None)
        try:
            self.redis.delete(cache_key)
        except redis.RedisError as e:
            logger.warning(f"Redis error on DELETE {cache_key}: {e}")

    def get_metrics_report(self) -> dict:
        return self.metrics.report()

    Emitting the get_metrics_report() output every 5 minutes to CloudWatch custom metrics gives your FinOps dashboard a direct window into what percentage of traffic is reaching the database. When db_hit_rate_pct trends upward, the cost implication is immediate and quantifiable.

    21.5 Google Cloud Memorystore vs Cloud SQL: The GCP Equivalent Analysis

    The economic principles are identical on GCP, but the pricing structure and tooling differ enough to warrant explicit treatment. Google Cloud Memorystore for Redis is the managed caching layer that offloads Cloud SQL for SQL Server workloads.

    Memorystore for Redis pricing is capacity-based rather than node-type-based: you pay per GB of provisioned capacity per hour. As of this writing, the Standard Tier (with replication and automatic failover) runs approximately $0.049/GB/hour in us-central1, and the Basic Tier (no replication) runs approximately $0.016/GB/hour. A 10GB Standard Tier instance therefore costs roughly $0.49/hour or $357/month — comparable to an ElastiCache cache.r6g.xlarge for similar memory capacity.

def analyze_memorystore_instance(project_id: str, instance) -> dict:
    """Generate sizing recommendation for a single Memorystore instance."""
    instance_id = instance.name.split("/")[-1]
    memory_size_gb = instance.memory_size_gb
    tier = "STANDARD" if instance.tier == redis_v1.Instance.Tier.STANDARD_HA else "BASIC"
    cost_per_gb_hour = (
        MEMORYSTORE_STANDARD_COST_PER_GB_HOUR if tier == "STANDARD"
        else MEMORYSTORE_BASIC_COST_PER_GB_HOUR
    )
    current_monthly_cost = memory_size_gb * cost_per_gb_hour * HOURS_PER_MONTH

    # Memory usage ratio (0–1 scale in Cloud Monitoring)
    mem_usage_values = get_metric_timeseries(
        project_id, instance_id,
        "redis.googleapis.com/stats/memory/usage_ratio"
    )
    # Cache hit ratio (0–1)
    hit_ratio_values = get_metric_timeseries(
        project_id, instance_id,
        "redis.googleapis.com/stats/keyspace_hits_ratio"
    )

    avg_mem_pct  = (sum(mem_usage_values) / len(mem_usage_values) * 100) if mem_usage_values else 0
    max_mem_pct  = (max(mem_usage_values) * 100) if mem_usage_values else 0
    avg_hit_rate = (sum(hit_ratio_values) / len(hit_ratio_values) * 100) if hit_ratio_values else 0

    action = "KEEP"
    recommended_gb = None
    reasoning = ""

    if avg_mem_pct < 30 and max_mem_pct < 45:
        # Overprovisioned — calculate minimum safe size
        min_required_gb = math.ceil(memory_size_gb * (max_mem_pct / 100) * 1.5)
        # Round up to nearest valid Memorystore size
        valid_sizes = [1, 2, 4, 5, 6, 8, 10, 12, 14, 16, 18, 20,
                       25, 30, 35, 40, 45, 50, 60, 70, 80, 90, 100]
        recommended_gb = next((s for s in valid_sizes if s >= min_required_gb), memory_size_gb)
        if recommended_gb < memory_size_gb:
            action = "DOWNSIZE"
            reasoning = (
                f"Avg memory {avg_mem_pct:.1f}%, max {max_mem_pct:.1f}%. "
                f"Reduce from {memory_size_gb}GB to {recommended_gb}GB."
            )
    elif max_mem_pct > 85:
        action = "UPSIZE"
        recommended_gb = math.ceil(memory_size_gb * 1.5)
        reasoning = f"Max memory {max_mem_pct:.1f}% — eviction risk. Upsize to {recommended_gb}GB."

    if avg_hit_rate < 80 and action == "KEEP":
        action = "INVESTIGATE"
        reasoning = f"Cache hit rate {avg_hit_rate:.1f}% below 80% threshold."

    recommended_monthly = (
        recommended_gb * cost_per_gb_hour * HOURS_PER_MONTH
        if recommended_gb else current_monthly_cost
    )
    monthly_savings = (
        current_monthly_cost - recommended_monthly if action == "DOWNSIZE" else 0.0
    )

    return {
        "instance_id": instance_id,
        "tier": tier,
        "memory_size_gb": memory_size_gb,
        "current_monthly_cost": round(current_monthly_cost, 2),
        "avg_memory_pct": round(avg_mem_pct, 1),
        "max_memory_pct": round(max_mem_pct, 1),
        "avg_hit_rate_pct": round(avg_hit_rate, 1),
        "action": action,
        "recommended_gb": recommended_gb,
        "recommended_monthly_cost": round(recommended_monthly, 2),
        "monthly_savings": round(monthly_savings, 2),
        "reasoning": reasoning
    }

    Azure SQL–specific diagnostic: identifying cacheable query patterns via Query Store

    Azure SQL Database and SQL Server on Azure VMs have Query Store enabled by default, providing a persistent record of query execution history that survives restarts — unlike sys.dm_exec_query_stats, which resets on restart or plan cache eviction. For identifying caching candidates on Azure SQL, Query Store is the authoritative source:

    -- Azure SQL / SQL Server: Identify top cache candidates using Query Store
-- Query Store persists execution history across restarts, making it
-- more reliable than dm_exec_query_stats for long-term trend analysis
SELECT TOP 30
    qsq.query_id,
    LEFT(qsqt.query_sql_text, 120)                              AS query_preview,
    qsrs.count_executions,
    CAST(qsrs.avg_logical_io_reads AS BIGINT)                   AS avg_logical_reads,
    CAST(qsrs.avg_duration / 1000.0 AS DECIMAL(10, 2))         AS avg_duration_ms,
    CAST(qsrs.avg_rowcount AS BIGINT)                           AS avg_rows_returned,
    -- High execution count + low row count = strong cache candidate
    CASE
        WHEN qsrs.count_executions > 5000
         AND qsrs.avg_rowcount < 50
        THEN 'CACHE NOW'
        WHEN qsrs.count_executions > 1000
         AND qsrs.avg_rowcount < 200
        THEN 'EVALUATE'
        WHEN qsrs.count_executions > 500
        THEN 'MONITOR'
        ELSE 'SKIP'
    END                                                         AS cache_recommendation,
    qsrs.count_executions * qsrs.avg_logical_io_reads           AS total_logical_reads_estimated,
    -- Translate logical reads to cost pressure:
    -- each read page is 8KB; high values on DTU-based databases
    -- directly drive DTU consumption and potential tier upgrades
    CAST(
        qsrs.count_executions * qsrs.avg_logical_io_reads * 8.0 / 1024 / 1024
        AS DECIMAL(12, 2)
    )                                                           AS total_data_gb_read
FROM
    sys.query_store_query                   qsq
    JOIN sys.query_store_query_text         qsqt ON qsq.query_text_id = qsqt.query_text_id
    JOIN sys.query_store_plan               qsp  ON qsq.query_id       = qsp.query_id
    JOIN sys.query_store_runtime_stats      qsrs ON qsp.plan_id        = qsrs.plan_id
    JOIN sys.query_store_runtime_stats_interval qsrsi
        ON qsrs.runtime_stats_interval_id = qsrsi.runtime_stats_interval_id
WHERE
    qsrsi.start_time >= DATEADD(DAY, -14, GETUTCDATE())
    AND qsq.is_internal_query = 0
    AND qsqt.query_sql_text NOT LIKE '%query_store%'
ORDER BY
    qsrs.count_executions DESC;

    The total_logical_reads_estimated column is particularly useful when your Azure SQL database is on a DTU-based pricing model. DTU consumption is heavily influenced by I/O, and high-frequency read queries that can be cached represent a direct path to dropping a DTU tier — which often yields larger savings than any other single optimization on Azure SQL.

    21.7 Cache Invalidation Economics: The Hidden Cost of Getting It Wrong

    Cache invalidation is routinely called one of the hardest problems in computer science, but its financial dimension is less often discussed. Getting cache invalidation wrong costs money in two distinct directions:

    Over-invalidation: Flushing too aggressively (short TTLs, broad key patterns, flush-on-any-write) keeps your cache cold and routes traffic back to the database. You pay for the cache infrastructure without capturing the savings. This is the more common failure mode.

    Under-invalidation: Serving stale data reduces database load but can cause correctness issues that lead to incident response, customer credits, or in regulated industries, compliance failures. The remediation cost can dwarf months of cache savings.

    The optimal TTL strategy balances these two failure modes by aligning TTL to the business tolerance for stale data, not to technical convenience. Different data classes have fundamentally different staleness tolerances:

    | Data Class | Staleness Tolerance | Recommended TTL | Cache Strategy |

    |---|---|---|---|

    | User session tokens | None — must be current | Session lifetime only | Authoritative store, not cache |

    | User profile / preferences | Minutes acceptable | 5–15 minutes | Cache with explicit invalidation on update |

    | Product catalog / pricing | Minutes to hours | 30–60 minutes | Cache with TTL; invalidate on CMS publish |

    | Configuration tables | Hours acceptable | 4–24 hours | Cache aggressively; invalidate on admin change |

    | Reference / lookup data | Days acceptable | 24 hours+ | Cache very aggressively; invalidate on release |

    | Analytics aggregates | Hours to days | 1–12 hours depending on freshness SLA | Read-through with long TTL |

    The financial impact of TTL misconfiguration is measurable. A product catalog with a 2-minute TTL instead of a 30-minute TTL will have its entire keyspace invalidated 30 times per hour instead of twice — 15x more often. If your catalog has 50,000 active keys and your database serves each miss in 10ms average, each full invalidation cycle generates 500 seconds of database query time. At 30 cycles per hour, that's 15,000 seconds of database load per hour from the 2-minute TTL, versus 1,000 seconds/hour at 30 minutes — often enough to push you into the next RDS instance tier.

    The following SQL Server query helps audit which tables are generating write volume that may be triggering over-eager cache invalidation:

    For SQL Server and Azure SQL, the same write audit against the Query Store and DMVs:

    -- SQL Server / Azure SQL: Audit write operations that drive cache invalidation
SELECT TOP 30
    OBJECT_SCHEMA_NAME(object_id)                               AS schema_name,
    OBJECT_NAME(object_id)                                      AS table_name,
    SUM(ios.leaf_insert_count)                                  AS leaf_inserts,
    SUM(ios.leaf_update_count)                                  AS leaf_updates,
    SUM(ios.leaf_delete_count)                                  AS leaf_deletes,
    SUM(ios.leaf_insert_count
        + ios.leaf_update_count
        + ios.leaf_delete_count)                                AS total_write_ops,
    SUM(p.rows)                                                 AS approx_row_count,
    -- Write operations per 1000 rows — higher values mean
    -- this table triggers cache invalidation very frequently
    CASE
        WHEN SUM(p.rows) > 0
        THEN CAST(
            SUM(ios.leaf_insert_count + ios.leaf_update_count + ios.leaf_delete_count)
            * 1000.0 / SUM(p.rows) AS DECIMAL(12, 2))
        ELSE 0
    END                                                         AS writes_per_1k_rows
FROM
    sys.dm_db_index_operational_stats(DB_ID(), NULL, NULL, NULL) ios
    JOIN sys.indexes i
        ON ios.object_id = i.object_id AND ios.index_id = i.index_id
    JOIN sys.partitions p
        ON i.object_id = p.object_id AND i.index_id = p.index_id
WHERE
    OBJECT_NAME(ios.object_id) IS NOT NULL
    AND i.object_id > 100
GROUP BY
    ios.object_id
ORDER BY
    total_write_ops DESC;

    Tables surfacing at the top of this query with high writes_per_1k_rows ratios are the ones where broad cache invalidation on every write causes the most damage. The remediation pattern is row-level cache key invalidation — invalidating only the specific cache key for the modified row (user_profile:{user_id}) rather than flushing the entire namespace (user_profile:*). Namespace-level flushes are operationally convenient but financially expensive at any meaningful scale.

    21.8 Building the Cache ROI Dashboard

    All of the individual metrics — hit rate, eviction count, memory utilization, L1/L2/L3 distribution, TTL effectiveness — only create accountability when they are visible as a unified cost story. A cache ROI dashboard translates these operational metrics into dollars, making the business case for cache investment self-evident and surfacing degradation before it erodes savings.

    Establishing a weekly cache review cadence

    The monitoring infrastructure is only valuable if someone reviews it on a cadence tied to billing cycles. A lightweight weekly review covers four questions:

    1. Is the average hit rate above the threshold (typically 85%) across all production clusters?

    2. Are eviction counts trending up — a leading indicator of memory pressure before hit rate degrades?

    3. Have any clusters been running at under 40% average memory utilization for more than two consecutive weeks? If so, they are candidates for the next right-sizing run.

    4. Are any new query patterns visible in Query Store that are high-frequency but not yet cached?

    Answering all four questions takes under 15 minutes when the dashboards are in place. The cumulative effect of this cadence — catching hit rate degradation early, right-sizing overprovisioned nodes quarterly, identifying new caching candidates as applications evolve — compounds over time into savings that substantially exceed the initial cache deployment benefit.

    Key Takeaways

  • → **Cache ROI is measurable before you deploy**: Query the Query Store or `sys.dm_exec_query_stats` (SQL Server/Azure SQL) to identify high-frequency, low-row-count queries that are strong caching candidates. Build the savings case with actual execution counts before provisioning any cache infrastructure.
  • → **Working set size, not total database size, determines cache node selection**: A 500GB database may have a hot working set of 8–12GB. Use `sys.dm_db_index_usage_stats` and table-size DMVs to measure the actual data being read frequently, then size ElastiCache, Memorystore, or Azure Cache for Redis to cover that working set at 75–80% utilization — not the full database footprint.
  • → **Cache hit rate is the single most important financial control metric**: The difference between an 80% and 95% hit rate on a mid-tier RDS instance can represent hundreds of dollars per month in database sizing savings. Automate CloudWatch or Azure Monitor alarms on hit rate and evictions so degradation triggers notification within minutes, not after your next billing statement.
  • → **TTL misconfiguration is a hidden cost multiplier**: Over-eager invalidation (short TTLs or broad namespace flushes on writes) keeps caches cold and routes traffic back to the database, eliminating the savings that justified the cache investment. Align TTLs to business staleness tolerance by data class, and use row-level key invalidation rather than namespace flushes for write-heavy tables.
  • → **Reserved instances and committed-use discounts apply to cache tiers too**: ElastiCache 1-year reserved pricing cuts on-demand costs by 40–45%; GCP Memorystore committed-use discounts provide comparable reductions. For any cache cluster you expect to run for more than six months, converting to reserved or committed pricing is the fastest single action to improve cache tier economics — and it compounds on top of all right-sizing work done at the node level.
