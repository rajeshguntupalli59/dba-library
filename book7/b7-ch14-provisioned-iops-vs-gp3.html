Chapter 14: Provisioned IOPS vs gp3: The Break-Even Analysis for I/O-Heavy SQL Server

Storage is the quietest line on the RDS for SQL Server bill — and for I/O-heavy workloads, the most mispriced. Teams choose gp3 because it is the default, then discover their workload sustains 12,000 IOPS against a volume provisioned for 3,000. Or they choose io2 "for performance" and pay for 20,000 provisioned IOPS while the workload averages 2,500. Both mistakes cost thousands per month, and both come from the same root cause: nobody ran the break-even math between pay-per-GB burstable storage and pay-per-IOPS provisioned storage. This chapter runs that math properly for SQL Server, shows you how to measure what your workload actually needs, and builds the automation that keeps the decision current as workloads evolve.

---

14.1 The Two Storage Pricing Models for SQL Server on RDS

RDS for SQL Server offers two fundamentally different storage economics:

gp3: burstable, pay-per-GB. Every gp3 volume includes a baseline of 3,000 IOPS and 125 MiB/s throughput free with the per-GB-month storage charge. Need more? You can provision additional IOPS (up to 16,000) at roughly $0.005 per provisioned IOPS-month, and additional throughput up to 1,000 MiB/s. Below the baseline, I/O is effectively free; above it, you pay a small premium per IOPS. gp3 is the right default for workloads whose I/O is bursty — the classic OLTP pattern of quiet stretches punctuated by checkpoint flushes and batch jobs.

io1/io2: provisioned IOPS, pay-per-IOPS. You declare an IOPS number (io1 up to 64,000; io2 Block Express up to 256,000 on supported instances) and pay per provisioned IOPS-month — roughly $0.10–$0.125 per IOPS-month depending on region — plus the per-GB storage charge. Provision 20,000 IOPS and use 2,000, and you still pay for 20,000. io2 adds higher durability (99.999%) and lower latency than io1. This model wins for workloads with sustained, predictable high IOPS where the gp3 baseline is structurally insufficient.

The SQL Server wrinkle: SQL Server I/O is spikier than most engines'. Checkpoint flushes, lazy writer activity, tempdb spills from hash joins and sorts, and transaction log writes all create I/O bursts that can be 5–10x the average. A workload averaging 2,000 IOPS but bursting to 15,000 during checkpoints looks like an io2 candidate on the peak and a gp3 candidate on the average. Section 14.3 shows how to resolve that tension with real numbers instead of gut feel.

14.2 Measuring Actual I/O Consumption — and Attributing It

CloudWatch gives you the volume-level truth: ReadIOPS, WriteIOPS, and BurstBalance on the RDS instance. Pull 30 days at 5-minute granularity and compute three numbers: the average, the 95th percentile, and the 99.9th percentile of total IOPS. The average tells you what provisioned IOPS would mostly cover; the P99.9 tells you what gp3's burst model must absorb.

But volume-level metrics cannot tell you which database files generate the I/O — and that attribution determines the fix. A workload whose IOPS are 70% transaction log writes has a different answer than one whose IOPS are 70% tempdb. SQL Server exposes per-file I/O statistics directly:

-- I/O attribution by database file: data vs log vs tempdb
SELECT
    DB_NAME(vfs.database_id) AS db,
    mf.type_desc             AS file_type,
    mf.physical_name        AS file_path,
    vfs.num_of_reads,
    vfs.num_of_writes,
    CAST(vfs.num_of_bytes_read  / 1048576.0 AS DECIMAL(12,1)) AS read_mb,
    CAST(vfs.num_of_bytes_written / 1048576.0 AS DECIMAL(12,1)) AS written_mb,
    vfs.io_stall_read_ms,
    vfs.io_stall_write_ms
FROM sys.dm_io_virtual_file_stats(NULL, NULL) vfs
JOIN sys.master_files mf
  ON vfs.database_id = mf.database_id AND vfs.file_id = mf.file_id
ORDER BY (vfs.num_of_reads + vfs.num_of_writes) DESC;

Run this weekly and snapshot the output. The pattern to look for: if tempdb dominates writes, the cheapest fix is often query tuning (eliminate the spills) rather than faster storage — a sort spill fixed by an index removes the IOPS entirely instead of making them cheaper. If the transaction log dominates, check log backup frequency and long-running transactions before buying IOPS. Only the residual I/O — the I/O that remains after tuning — should drive the gp3 vs io2 decision.

14.3 Running the Break-Even Calculation

The break-even formula is straightforward. For a given workload with measured IOPS requirement I and storage size S GB:

gp3 monthly  = S × $0.115  +  max(0, I - 3000) × $0.005
io2 monthly  = S × $0.125  +  I × $0.125        (illustrative us-east-1 rates)

Worked example: 1 TB volume, workload needs sustained 12,000 IOPS
  gp3: 1000 × $0.115 + 9000 × $0.005  = $115 + $45  = $160/month
  io2: 1000 × $0.125 + 12000 × $0.125 = $125 + $1500 = $1,625/month
  → gp3 wins by 10x. Provisioned IOPS is wildly overpriced here.

Worked example: 1 TB volume, workload needs sustained 40,000 IOPS
  gp3: maxes at 16,000 IOPS — cannot serve this workload at all
  io2: 1000 × $0.125 + 40000 × $0.125 = $125 + $5000 = $5,125/month
  → io2 is the only option; the question becomes whether the workload
     can be tuned below 16,000 IOPS to unlock gp3.

Three insights fall out of the math. First, gp3's extra-IOPS pricing ($0.005/IOPS-month) is roughly 25x cheaper than io2's ($0.125) — so any workload under 16,000 IOPS should be on gp3 unless latency requirements demand io2's lower tail latency. Second, the break-even is not a single number but a band: between ~3,000 and 16,000 IOPS, gp3 with extra provisioned IOPS almost always wins on cost. Third, the workloads that genuinely need io2 are rare — sustained 20,000+ IOPS with sub-millisecond latency requirements — and they are exactly the workloads where a tuning pass (Section 14.2) has the highest ROI, because every 1,000 IOPS eliminated saves ~$125/month permanently.

One more consideration: io2 volumes carry a durability and latency advantage (99.999% durability, lower P99 latency) that matters for the most demanding OLTP systems. If your SLA is written in P99 latency terms, model io2 as an insurance cost rather than a capacity cost — and make sure the SLA actually requires it before paying the premium.

14.4 Workload Pattern Considerations

Steady high IOPS. Data warehouse loading docks, high-throughput OLTP with constant write rates. If the P50 and P95 IOPS are close together and both above 10,000, provisioned IOPS (or a tuned-down gp3 with extra IOPS) is the honest choice. These workloads are also the best candidates for Reserved Instance coverage on the compute side — steady I/O usually means steady CPU.

Bursty IOPS (the SQL Server default). Checkpoint flushes every minute, hourly batch jobs, nightly index maintenance. gp3's burst model absorbs these naturally: the baseline covers the average, and short bursts above baseline ride the burst balance or the cheap extra-IOPS tier. Putting a bursty workload on io2 means paying the peak rate for the valleys — the single most common storage overspend on RDS for SQL Server.

Log-heavy vs tempdb-heavy. Transaction log I/O is sequential and latency-sensitive; tempdb I/O is random and throughput-sensitive. If log writes are the driver, consider that RDS for SQL Server on io2 gives the log the latency it wants — but first check whether the log volume is inflated by overly frequent log backups or by FULL recovery on databases that only need SIMPLE. If tempdb is the driver, the fix is almost never storage: it is indexing, statistics, and memory grants (see Chapter 12).

Multi-AZ note. In a Multi-AZ deployment, storage I/O patterns are mirrored to the standby. Size provisioned IOPS for the primary's workload — the standby replays the same writes — and remember that a failover does not change the storage bill, only which instance serves the I/O.

14.5 The Azure SQL Angle: Hyperscale vs General Purpose

For completeness, the same break-even thinking applies on Azure SQL, where the choice is between General Purpose (remote storage, 5–10ms latency) and Hyperscale or Business Critical (faster local/distributed storage at a premium). Hyperscale's value proposition for SQL Server FinOps is different from io2's: it is not just faster I/O, it is rapidly scalable storage up to 100 TB with near-instant backups. The break-even question becomes: does the workload need Hyperscale's scale and snapshot agility, or would General Purpose with adequate vCores serve at half the price? Run the same measurement discipline — P50/P95/P99.9 of I/O latency and throughput from sys.dm_io_virtual_file_stats — before accepting the Hyperscale premium. Many workloads moved to Hyperscale for "performance" are actually vCore-starved on General Purpose, and the cheaper fix is scaling compute, not upgrading the storage architecture.

14.6 Automating the Ongoing Decision

Workload I/O profiles drift: the application grows, the batch window moves, the new feature doubles write volume. A break-even analysis run once is a snapshot; run it monthly as automation. The pipeline is simple: a scheduled Lambda (or Azure Function for Azure SQL) pulls the last 30 days of ReadIOPS/WriteIOPS from CloudWatch, computes P50/P95/P99.9, plugs them into the Section 14.3 formula for both storage types, and posts a recommendation to the team channel when the cheaper option would save more than a threshold (say, $200/month).

Keep a human in the loop for the actual switch. Changing storage type on RDS requires a modification that can involve downtime or performance impact depending on the volume size, and the recommendation engine cannot see the latency SLA. The automation proposes; the DBA disposes. What the automation can do unattended is the tuning side: when tempdb I/O crosses a threshold, open a ticket with the top spill queries attached. Storage-type changes are monthly decisions; query tuning is continuous.

14.7 Validating the Decision Post-Switch

After any storage change, validate against the bill — not just the metrics. Confirm the provisioned-IOPS line items disappear (or appear, if you moved to io2) in Cost Explorer within one billing cycle, and confirm the total storage line moved in the predicted direction. Then confirm performance: compare P99 read/write latency from sys.dm_io_virtual_file_stats snapshots before and after, and check that checkpoint durations and tempdb spill rates did not regress. A storage "optimization" that saves $300/month while doubling P99 latency during the nightly batch is not an optimization — it is a deferred incident.

---

Key Takeaways

  • → **gp3 wins on cost for almost everything under 16,000 IOPS**: Extra gp3 IOPS at ~$0.005/IOPS-month are roughly 25x cheaper than io2 provisioned IOPS. Only workloads with sustained 20,000+ IOPS or hard sub-millisecond latency SLAs justify io2 — and those workloads deserve a tuning pass first, because every 1,000 IOPS eliminated saves ~$125/month permanently.
  • → **Attribute I/O before buying IOPS**: `sys.dm_io_virtual_file_stats` tells you whether the I/O is data, log, or tempdb. Tempdb-dominated I/O is a query-tuning problem, log-dominated I/O is often a recovery-model or backup-frequency problem — only residual I/O after tuning should drive the storage-type decision.
  • → **Bursty SQL Server I/O belongs on gp3**: Checkpoints, batch jobs, and index maintenance create 5–10x bursts over the average. Provisioned IOPS charges the peak rate for the valleys; gp3's burst model absorbs the peaks at a fraction of the cost.
  • → **Automate the analysis, not the switch**: A monthly job that recomputes the break-even from CloudWatch data and proposes changes keeps the decision current as workloads drift. Keep the actual storage-type change human-approved — the automation cannot see latency SLAs or maintenance windows.
  • → **Validate against the bill and the latency**: After switching, confirm the Cost Explorer line items moved as predicted and that P99 latency did not regress. A cheaper storage tier that doubles tail latency during batch windows is a deferred incident, not a saving.
