Chapter 18: Query Cost Attribution: Which Queries Are Burning Money

Organizations running cloud databases routinely overpay by 30–60% not because their infrastructure is wrong, but because a handful of queries are consuming disproportionate compute, I/O, and memory resources that translate directly into larger instance sizes, higher storage throughput costs, and ballooning read replica bills. This chapter shows you how to identify exactly which queries are responsible for those costs, assign dollar values to each one, and build an automated attribution pipeline that surfaces the worst offenders before they hit your monthly bill. Teams that implement structured query cost attribution typically find that the top 5% of queries account for 70–80% of database compute spend—and that fixing three to five of them can cut monthly RDS or Cloud SQL bills by $2,000–$15,000 without touching a single infrastructure knob.

---

18.1 The Attribution Problem: Connecting Query Execution to Dollar Costs

Most DBAs know which queries are slow. Far fewer know which queries are *expensive*. The distinction matters enormously for FinOps work. A query that runs in 50 milliseconds but executes 2 million times per day is doing more damage to your bill than a query that takes 10 seconds and runs once an hour. Cloud costs accumulate through three primary mechanisms at the database layer:

Compute costs arise when queries hold CPU longer than necessary, forcing you onto a larger instance class. Moving from an db.r6g.2xlarge ($0.528/hour on-demand, us-east-1) to a db.r6g.4xlarge ($1.056/hour) costs an additional $382/month—a cost that is entirely invisible unless you connect it to the queries driving CPU saturation.

I/O costs hit you in two ways. For RDS with gp2 storage, provisioned IOPS above the baseline incur per-IOPS charges of $0.10/IOPS-month. For gp3, you pay $0.02/GB-month for storage plus $0.08 per provisioned IOPS beyond 3,000. Queries doing full table scans on large tables are the most common driver of unexpected IOPS bills.

Network and replication costs surface when poorly written queries return massive result sets or trigger excessive binary log events that replicate to read replicas or cross-region standby instances. Data transfer between Availability Zones costs $0.01/GB on AWS, which becomes significant when a single analytics query pulls 500GB across the wire nightly.

The framework this chapter builds assigns three cost components to every query: compute cost, I/O cost, and network cost. These roll up into a single monthly dollar figure per query, giving you a ranked list to work from.

18.2 Extracting Query Cost Data: Query Store, Performance Insights, and sys.dm_exec_query_stats

#### SQL Server: sys.dm_exec_query_stats

For Azure SQL Database and SQL Server on RDS, the equivalent attribution lives in sys.dm_exec_query_stats:

-- Query cost attribution for SQL Server / Azure SQL Database
-- Adjust @instance_cost_per_hour to match your DTU/vCore pricing
-- Azure SQL Business Critical 8 vCores = ~$1.13/hr
DECLARE @instance_cost_per_hour  FLOAT = 1.13;
DECLARE @vcpu_count              INT   = 8;
DECLARE @observation_hours       FLOAT = 168.0; -- 7 days
DECLARE @cost_per_cpu_second     FLOAT = @instance_cost_per_hour / @vcpu_count / 3600.0;

SELECT TOP 25
    qs.total_worker_time / 1000000.0                        AS total_cpu_seconds,
    qs.total_elapsed_time / 1000000.0                       AS total_elapsed_seconds,
    qs.total_logical_reads                                  AS logical_reads,
    qs.total_physical_reads                                 AS physical_reads,
    qs.total_logical_writes                                 AS logical_writes,
    qs.execution_count,
    qs.total_rows,
    SUBSTRING(qt.text, (qs.statement_start_offset / 2) + 1,
        ((CASE qs.statement_end_offset
            WHEN -1 THEN DATALENGTH(qt.text)
            ELSE qs.statement_end_offset
          END - qs.statement_start_offset) / 2) + 1)       AS query_text,
    qp.query_plan,
    -- Compute cost estimate
    ROUND(qs.total_worker_time / 1000000.0
          * @cost_per_cpu_second, 4)                        AS compute_cost_usd,
    -- I/O cost: physical reads * 8KB pages, approximate $0.115/GB for Azure Premium SSD
    ROUND(qs.total_physical_reads * 8.0 / 1048576.0
          * 0.115, 4)                                       AS io_cost_usd,
    -- Projected monthly (scale from observation window to 30 days)
    ROUND((qs.total_worker_time / 1000000.0 * @cost_per_cpu_second
          + qs.total_physical_reads * 8.0 / 1048576.0 * 0.115)
          * (720.0 / @observation_hours), 2)                AS est_monthly_cost_usd
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) qt
OUTER APPLY sys.dm_exec_query_plan(qs.plan_handle) qp
WHERE qs.execution_count > 50
ORDER BY est_monthly_cost_usd DESC;

18.3 AWS Performance Insights and Cost Explorer Integration

Performance Insights provides the bridge between database-level metrics and the infrastructure cost data in Cost Explorer. The combination is powerful: Performance Insights shows you which SQL is consuming DB time, while Cost Explorer shows you what that DB time is costing in dollars.

#### Pulling Performance Insights Data via AWS CLI

#!/bin/bash
# Retrieve top SQL queries by DB load from Performance Insights
# Requires: aws cli v2, jq, Performance Insights enabled on the RDS instance
# Run this daily via cron or EventBridge to populate a cost attribution table

DB_INSTANCE_ID="prod-sqlserver-01"
REGION="us-east-1"
ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)

# Performance Insights uses a resource ARN
PI_RESOURCE_ID=$(aws rds describe-db-instances \
    --db-instance-identifier "$DB_INSTANCE_ID" \
    --region "$REGION" \
    --query 'DBInstances[0].DbiResourceId' \
    --output text)

# Fetch top 25 SQL digests for the past 7 days
# Metric: db.load.avg (average active sessions)
START_TIME=$(date -u -d '7 days ago' '+%Y-%m-%dT%H:%M:%SZ')
END_TIME=$(date -u '+%Y-%m-%dT%H:%M:%SZ')

aws pi get-resource-metrics \
    --service-type RDS \
    --identifier "$PI_RESOURCE_ID" \
    --metric-queries '[
        {
            "Metric": "db.load.avg",
            "GroupBy": {
                "Group": "db.sql",
                "Dimensions": ["db.sql.tokenized_id"],
                "Limit": 25
            }
        }
    ]' \
    --start-time "$START_TIME" \
    --end-time "$END_TIME" \
    --period-in-seconds 3600 \
    --region "$REGION" \
    --output json \
    | jq '.MetricList[] | {
        metric: .Key.Metric,
        sql_id: .Key.Dimensions["db.sql.tokenized_id"],
        avg_load: (.DataPoints | map(.Value) | add / length)
      }' \
    | jq -s 'sort_by(-.avg_load)' \
    > /tmp/pi_top_queries_$(date +%Y%m%d).json

echo "Performance Insights data saved to /tmp/pi_top_queries_$(date +%Y%m%d).json"

# Fetch instance cost from Cost Explorer for the same period
aws ce get-cost-and-usage \
    --time-period "Start=$(date -u -d '7 days ago' '+%Y-%m-%d'),End=$(date -u '+%Y-%m-%d')" \
    --granularity DAILY \
    --filter '{
        "And": [
            {
                "Dimensions": {
                    "Key": "SERVICE",
                    "Values": ["Amazon Relational Database Service"]
                }
            },
            {
                "Tags": {
                    "Key": "db-instance",
                    "Values": ["prod-sqlserver-01"]
                }
            }
        ]
    }' \
    --metrics "BlendedCost" "UsageQuantity" \
    --group-by Type=DIMENSION,Key=USAGE_TYPE \
    --output json \
    > /tmp/rds_cost_$(date +%Y%m%d).json

echo "Cost Explorer data saved to /tmp/rds_cost_$(date +%Y%m%d).json"

# Combine: total DB cost / total DB load = cost per AAS unit
TOTAL_COST=$(cat /tmp/rds_cost_$(date +%Y%m%d).json \
    | jq '[.ResultsByTime[].Groups[].Metrics.BlendedCost.Amount | tonumber] | add')

echo "Total RDS cost (7 days): \$$TOTAL_COST"
echo "Cost attribution file ready for Python enrichment step"

#### GCP: Pulling BigQuery Cost Data for Cloud SQL

#!/bin/bash
# GCP cost attribution for Cloud SQL queries
# Requires: gcloud CLI, BigQuery billing export enabled
# Billing export dataset: billing_export.gcp_billing_export_v1_XXXXXX

PROJECT_ID="your-project-id"
BILLING_DATASET="billing_export"
BILLING_TABLE="gcp_billing_export_v1_XXXXXXXX"  # replace with your export table

# Query BigQuery for Cloud SQL costs broken down by resource labels
bq query \
    --use_legacy_sql=false \
    --project_id="$PROJECT_ID" \
    --format=json \
    "
    SELECT
        DATE(usage_start_time)                              AS usage_date,
        labels.value                                        AS instance_label,
        service.description                                 AS service,
        sku.description                                     AS sku,
        SUM(cost)                                           AS total_cost_usd,
        SUM(usage.amount)                                   AS usage_amount,
        usage.unit                                          AS unit
    FROM \`${PROJECT_ID}.${BILLING_DATASET}.${BILLING_TABLE}\`
    CROSS JOIN UNNEST(labels) AS labels
    WHERE
        service.description = 'Cloud SQL'
        AND labels.key = 'db-instance'
        AND DATE(usage_start_time) >= DATE_SUB(CURRENT_DATE(), INTERVAL 7 DAY)
    GROUP BY 1, 2, 3, 4, 7
    ORDER BY total_cost_usd DESC
    LIMIT 100
    " > /tmp/cloudsql_cost_$(date +%Y%m%d).json

echo "Cloud SQL cost data exported to /tmp/cloudsql_cost_$(date +%Y%m%d).json"

# Retrieve slow query log from Cloud SQL via Cloud Logging
gcloud logging read \
    'resource.type="cloudsql_database" 
     jsonPayload.message=~"Query_time"
     severity>=DEFAULT' \
    --project="$PROJECT_ID" \
    --limit=1000 \
    --format=json \
    --freshness=7d \
    > /tmp/cloudsql_slow_queries_$(date +%Y%m%d).json

echo "Slow query log exported. Lines: $(wc -l < /tmp/cloudsql_slow_queries_$(date +%Y%m%d).json)"

18.4 Building an Automated Query Cost Attribution Pipeline

Manual query analysis is a one-time exercise. The organizations that consistently control costs automate the attribution process and integrate it into their observability stack. The following Python pipeline runs on a daily schedule (via AWS Lambda, Cloud Functions, or a cron job on an EC2 instance) and writes results to a SQL Server tracking table and optionally to Slack or PagerDuty.

#!/usr/bin/env python3
"""
query_cost_attribution.py

Automated query cost attribution pipeline.
Runs daily via EventBridge Scheduler or cron.
Writes results to a SQL Server attribution table.
Sends Slack alerts when a query's estimated monthly cost exceeds threshold.

Requirements:
    pip install pyodbc boto3 requests python-dotenv

Environment variables:
    DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD
    TRACKING_DB_HOST, TRACKING_DB_NAME (can be same as above)
    AWS_REGION
    PI_RESOURCE_ID        (from aws rds describe-db-instances)
    SLACK_WEBHOOK_URL     (optional)
    INSTANCE_COST_PER_HOUR
    VCPU_COUNT
    COST_ALERT_THRESHOLD  (default: 500 USD/month per query)
"""

import os
import json
import logging
import datetime
import pyodbc
import boto3
import requests
from decimal import Decimal

logging.basicConfig(
    level=logging.INFO,
    format='%(asctime)s %(levelname)s %(message)s'
)
log = logging.getLogger(__name__)

# ─── Configuration ────────────────────────────────────────────────────────────

def _conn_str(host, port, dbname, user, password):
    return (
        "DRIVER={ODBC Driver 18 for SQL Server};"
        f"SERVER={host},{port};DATABASE={dbname};"
        f"UID={user};PWD={password};"
        "Encrypt=yes;TrustServerCertificate=yes;Connection Timeout=30;"
    )

DB_CONN_STR = _conn_str(
    os.environ["DB_HOST"],
    int(os.environ.get("DB_PORT", 1433)),
    os.environ["DB_NAME"],
    os.environ["DB_USER"],
    os.environ["DB_PASSWORD"],
)
TRACKING_CONN_STR = _conn_str(
    os.environ.get("TRACKING_DB_HOST", os.environ["DB_HOST"]),
    int(os.environ.get("TRACKING_DB_PORT", 1433)),
    os.environ.get("TRACKING_DB_NAME", "finops_tracking"),
    os.environ["DB_USER"],
    os.environ["DB_PASSWORD"],
)

INSTANCE_COST_PER_HOUR = float(os.environ.get("INSTANCE_COST_PER_HOUR", "1.056"))
VCPU_COUNT             = int(os.environ.get("VCPU_COUNT", "16"))
COST_PER_CPU_SECOND    = INSTANCE_COST_PER_HOUR / VCPU_COUNT / 3600.0
IOPS_COST_PER_BLOCK    = 0.08 / 1_000_000  # gp3 I/O approximation per 8KB block
OBSERVATION_DAYS       = 7
SCALE_TO_MONTHLY       = 30.0 / OBSERVATION_DAYS

SLACK_WEBHOOK_URL      = os.environ.get("SLACK_WEBHOOK_URL")
ALERT_THRESHOLD_USD    = float(os.environ.get("COST_ALERT_THRESHOLD", "500"))

AWS_REGION             = os.environ.get("AWS_REGION", "us-east-1")
PI_RESOURCE_ID         = os.environ.get("PI_RESOURCE_ID", "")

# ─── DDL for tracking table ────────────────────────────────────────────────────

TRACKING_TABLE_DDL = """
IF OBJECT_ID('dbo.query_cost_attribution', 'U') IS NULL
CREATE TABLE dbo.query_cost_attribution (
    id                      BIGINT IDENTITY(1,1) PRIMARY KEY,
    captured_at             DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
    observation_window_days INT         NOT NULL,
    query_id                BIGINT,
    query_preview           NVARCHAR(4000),
    calls                   BIGINT,
    total_exec_seconds      NUMERIC(18,4),
    avg_exec_ms             NUMERIC(18,4),
    disk_blocks_read        BIGINT,
    total_rows_returned     BIGINT,
    compute_cost_usd        NUMERIC(12,4),
    io_cost_usd             NUMERIC(12,4),
    est_monthly_cost_usd    NUMERIC(12,2),
    pct_of_total_cost       NUMERIC(6,2),
    alerted                 BIT NOT NULL DEFAULT 0
);

IF NOT EXISTS (SELECT 1 FROM sys.indexes WHERE name = 'idx_qca_captured_at')
    CREATE INDEX idx_qca_captured_at ON dbo.query_cost_attribution (captured_at DESC);

IF NOT EXISTS (SELECT 1 FROM sys.indexes WHERE name = 'idx_qca_monthly_cost')
    CREATE INDEX idx_qca_monthly_cost ON dbo.query_cost_attribution (est_monthly_cost_usd DESC);
"""

ATTRIBUTION_SQL = """
-- Query Store must be enabled on the source database
WITH query_stats AS (
    SELECT
        q.query_id,
        LEFT(qt.query_sql_text, 200)                       AS query_preview,
        SUM(rs.count_executions)                           AS calls,
        SUM(rs.avg_cpu_time * rs.count_executions)
            / 1000000.0                                    AS total_exec_seconds,
        AVG(rs.avg_duration) / 1000.0                      AS avg_exec_ms,
        SUM(rs.avg_physical_io_reads * rs.count_executions) AS disk_blocks_read,
        SUM(rs.avg_rowcount * rs.count_executions)         AS total_rows_returned
    FROM sys.query_store_query q
    JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
    JOIN sys.query_store_plan pl       ON pl.query_id = q.query_id
    JOIN sys.query_store_runtime_stats rs ON rs.plan_id = pl.plan_id
    WHERE rs.last_execution_time >= DATEADD(DAY, -7, SYSDATETIME())
    GROUP BY q.query_id, qt.query_sql_text
    HAVING SUM(rs.count_executions) > 50
),
cost_calc AS (
    SELECT
        qs.*,
        ROUND(qs.total_exec_seconds * ? , 6)                AS compute_cost_usd,
        ROUND(qs.disk_blocks_read * ? , 6)                 AS io_cost_usd,
        ROUND((qs.total_exec_seconds * ?
             + qs.disk_blocks_read * ?) * ?, 2)             AS est_monthly_cost_usd
    FROM query_stats qs
)
SELECT TOP 50
    query_id,
    query_preview,
    calls,
    ROUND(total_exec_seconds, 4)                           AS total_exec_seconds,
    ROUND(avg_exec_ms, 4)                                  AS avg_exec_ms,
    disk_blocks_read,
    total_rows_returned,
    compute_cost_usd,
    io_cost_usd,
    est_monthly_cost_usd,
    ROUND(100.0 * est_monthly_cost_usd
          / NULLIF(SUM(est_monthly_cost_usd) OVER (), 0), 2) AS pct_of_total_cost
FROM cost_calc
ORDER BY est_monthly_cost_usd DESC;
"""


# ─── Functions ────────────────────────────────────────────────────────────────

def get_attribution_rows(conn) -> list[dict]:
    """Pull ranked query cost attribution from Query Store."""
    params = (COST_PER_CPU_SECOND, IOPS_COST_PER_BLOCK,
              COST_PER_CPU_SECOND, IOPS_COST_PER_BLOCK, SCALE_TO_MONTHLY)
    cur = conn.cursor()
    cur.execute(ATTRIBUTION_SQL, params)
    cols = [c[0] for c in cur.description]
    rows = [dict(zip(cols, row)) for row in cur.fetchall()]
    cur.close()
    log.info("Retrieved %d attribution rows from Query Store", len(rows))
    return rows


def ensure_tracking_table(tracking_conn) -> None:
    """Create the tracking table if it does not exist."""
    cur = tracking_conn.cursor()
    cur.execute(TRACKING_TABLE_DDL)
    cur.close()
    tracking_conn.commit()
    log.info("Tracking table verified / created")


def write_attribution_rows(tracking_conn, rows: list[dict]) -> None:
    """Insert attribution rows into the tracking table."""
    insert_sql = """
        INSERT INTO dbo.query_cost_attribution (
            observation_window_days,
            query_id,
            query_preview,
            calls,
            total_exec_seconds,
            avg_exec_ms,
            disk_blocks_read,
            total_rows_returned,
            compute_cost_usd,
            io_cost_usd,
            est_monthly_cost_usd,
            pct_of_total_cost
        ) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)
    """
    params = [
        (OBSERVATION_DAYS, row["query_id"], row["query_preview"][:4000],
         row["calls"], row["total_exec_seconds"], row["avg_exec_ms"],
         row["disk_blocks_read"], row["total_rows_returned"],
         row["compute_cost_usd"], row["io_cost_usd"],
         row["est_monthly_cost_usd"], row["pct_of_total_cost"])
        for row in rows
    ]
    cur = tracking_conn.cursor()
    cur.executemany(insert_sql, params)
    cur.close()
    tracking_conn.commit()
    log.info("Wrote %d rows to query_cost_attribution", len(rows))


def send_slack_alert(row: dict) -> None:
    """Post a Slack message for a query exceeding the cost threshold."""
    if not SLACK_WEBHOOK_URL:
        return
    message = {
        "text": (
            f":money_with_wings: *Query Cost Alert* "
            f"— estimated monthly cost: *${row['est_monthly_cost_usd']:,.2f}*\n"
            f"```{row['query_preview'][:300]}```\n"
            f"Calls: {row['calls']:,} | "
            f"Avg: {row['avg_exec_ms']:.1f} ms | "
            f"Disk blocks read: {row['disk_blocks_read']:,} | "
            f"Share of total cost: {row['pct_of_total_cost']:.1f}%"
        )
    }
    try:
        resp = requests.post(SLACK_WEBHOOK_URL, json=message, timeout=10)
        resp.raise_for_status()
        log.info("Slack alert sent for query_id=%s", row.get("query_id"))
    except requests.RequestException as exc:
        log.warning("Failed to send Slack alert: %s", exc)


def check_and_alert(tracking_conn, rows: list[dict]) -> None:
    """
    Alert on any query whose estimated monthly cost exceeds ALERT_THRESHOLD_USD
    and has not already been alerted today.
    """
    today = datetime.date.today()
    check_sql = """
        SELECT TOP 1 1
        FROM dbo.query_cost_attribution
        WHERE query_id = ?
          AND CAST(captured_at AS DATE) = ?
          AND alerted = 1
    """
    mark_sql = """
        UPDATE dbo.query_cost_attribution
        SET alerted = 1
        WHERE query_id = ?
          AND CAST(captured_at AS DATE) = ?
          AND alerted = 0
    """
    for row in rows:
        if float(row.get("est_monthly_cost_usd") or 0) < ALERT_THRESHOLD_USD:
            continue
        cur = tracking_conn.cursor()
        cur.execute(check_sql, (row["query_id"], today))
        already_alerted = cur.fetchone() is not None
        cur.close()
        if not already_alerted:
            send_slack_alert(row)
            cur = tracking_conn.cursor()
            cur.execute(mark_sql, (row["query_id"], today))
            cur.close()
            tracking_conn.commit()


def lambda_handler(event: dict, context) -> dict:
    """
    AWS Lambda entry point.
    Also callable as a plain Python script main().
    """
    log.info("Starting query cost attribution run at %s", datetime.datetime.now(datetime.timezone.utc))

    src_conn = pyodbc.connect(DB_CONN_STR, autocommit=True)
    trk_conn = pyodbc.connect(TRACKING_CONN_STR, autocommit=True)
    try:
        ensure_tracking_table(trk_conn)
        rows = get_attribution_rows(src_conn)
        write_attribution_rows(trk_conn, rows)
        check_and_alert(trk_conn, rows)
    finally:
        src_conn.close()
        trk_conn.close()

    top = rows[0] if rows else {}
    log.info(
        "Run complete. Top query: query_id=%s, est_monthly=$%s",
        top.get("query_id"), top.get("est_monthly_cost_usd")
    )
    return {
        "statusCode": 200,
        "queries_analyzed": len(rows),
        "top_query_monthly_cost_usd": str(top.get("est_monthly_cost_usd", 0)),
    }


if __name__ == "__main__":
    lambda_handler({}, None)

Deploy this as a Lambda function with a 15-minute timeout, 512 MB memory, and an EventBridge rule triggering it at cron(0 6 * * ? *) (06:00 UTC daily). The function needs a VPC configuration that places it in the same subnet as the RDS instance, and a security group rule allowing port 5432 outbound to the database security group.

18.5 Reading the Attribution Output: Patterns That Indicate Wasted Spend

Raw numbers only go so far. The value is in recognizing the cost patterns that map to specific optimization actions. The following patterns appear repeatedly across production systems and each has a well-defined remediation path.

#### Pattern 1: High Disk Blocks Read, Low Row Efficiency

query_preview:  SELECT * FROM orders WHERE customer_id = $1 AND status = $2
calls:          1,842,000
avg_exec_ms:    12.4
disk_blocks_read: 94,000,000
total_rows:     1,842,000
row_efficiency: 0.019    (roughly 53 rows examined per row returned)
est_monthly:    $2,847

A row efficiency below 0.10 combined with high disk block reads is the signature of a missing or ineffective index. The fix is almost always a composite index on (customer_id, status). For this query, adding that index would reduce disk_blocks_read from 94 million to roughly 1.8 million—a 98% reduction in I/O cost, dropping the monthly estimate from $2,847 to under $60.

-- SQL Server equivalent
-- Check missing index DMV first
SELECT
    mid.statement                                           AS table_name,
    migs.avg_total_user_cost * migs.avg_user_impact
        * (migs.user_seeks + migs.user_scans)              AS improvement_measure,
    'CREATE INDEX ix_' + OBJECT_NAME(mid.object_id)
        + '_' + REPLACE(ISNULL(mid.equality_columns,''), ', ', '_')
        + ' ON ' + mid.statement
        + ' (' + ISNULL(mid.equality_columns,'')
        + CASE WHEN mid.inequality_columns IS NOT NULL
               THEN ',' + mid.inequality_columns ELSE '' END + ')'
        + CASE WHEN mid.included_columns IS NOT NULL
               THEN ' INCLUDE (' + mid.included_columns + ')' ELSE '' END
                                                            AS create_index_statement
FROM sys.dm_db_missing_index_details mid
JOIN sys.dm_db_missing_index_groups mig
    ON mid.index_handle = mig.index_handle
JOIN sys.dm_db_missing_index_group_stats migs
    ON mig.index_group_handle = migs.group_handle
ORDER BY improvement_measure DESC;

#### Pattern 2: High Call Count, Trivial Individual Cost — But Large Aggregate

query_preview:  SELECT id, name, email FROM users WHERE id = $1
calls:          28,000,000
avg_exec_ms:    0.3
disk_blocks_read: 2,800,000
est_monthly:    $1,140

This pattern—often called a "chatty query"—is common in ORM-heavy applications that issue individual lookups inside loops. The query is fast and well-indexed, but the sheer call volume adds up. The fix is application-side: batch the lookups using WHERE id IN (...) or a table-valued parameter, or introduce an application-level cache for frequently-requested user records.

-- SQL Server equivalent using a table-valued parameter
-- Define the TVP type once:
CREATE TYPE dbo.BigIntList AS TABLE (id BIGINT NOT NULL PRIMARY KEY);

-- In the application, pass a DataTable and use:
SELECT u.id, u.name, u.email
FROM dbo.users u
JOIN @user_ids_tvp t ON u.id = t.id;

#### Pattern 3: High CPU Seconds, Modest I/O — Computation-Heavy Query

query_preview:  SELECT customer_id, SUM(amount), COUNT(*), AVG(amount)
                FROM transactions
                WHERE created_at BETWEEN $1 AND $2
                GROUP BY customer_id
                ORDER BY SUM(amount) DESC
calls:          12,000
avg_exec_ms:    8,400
cpu_seconds:    100,800
compute_cost:   $6,650
est_monthly:    $28,500

A high CPU-to-I/O ratio with long execution time points to a query that touches many rows but reads them efficiently (possibly from shared buffers). For aggregation queries like this, the options are:

1. Materialized views or pre-aggregation tables refreshed on a schedule

2. Partial indexes that restrict the scan to recent data

3. Read replica offloading if the query is analytical and can tolerate slight staleness

-- SQL Server: indexed view equivalent
CREATE VIEW dbo.vw_customer_tx_daily
WITH SCHEMABINDING AS
SELECT
    customer_id,
    CAST(created_at AS DATE)        AS summary_date,
    SUM(amount)                     AS total_amount,
    COUNT_BIG(*)                    AS tx_count
FROM dbo.transactions
GROUP BY customer_id, CAST(created_at AS DATE);

CREATE UNIQUE CLUSTERED INDEX ucx_customer_tx_daily
    ON dbo.vw_customer_tx_daily (customer_id, summary_date);
-- SQL Server will use this indexed view automatically when the optimizer
-- recognizes it covers the query; or reference it directly with NOEXPAND hint

#### Pattern 4: N+1 Query Signature

An N+1 pattern shows up in the attribution table as two queries with a suspicious relationship: one query has call counts that are an exact multiple of another's.

queryid: 8734  calls: 45,000   query: SELECT * FROM products WHERE id = $1
queryid: 8201  calls: 45,000   query: SELECT * FROM categories WHERE id = $1
queryid: 9012  calls: 1,500    query: SELECT * FROM products WHERE page = $1 LIMIT 30

The 1,500 page queries each trigger 30 product lookups (45,000 total) which each trigger a category lookup—the classic ORM N+1. The fix is to rewrite the page-level query with JOINs or to configure eager loading in the ORM.

-- SQL Server equivalent
SELECT
    p.id,
    p.name,
    p.price,
    c.id            AS category_id,
    c.name          AS category_name
FROM dbo.products p
JOIN dbo.categories c ON c.id = p.category_id
WHERE p.page = @page
ORDER BY p.sort_order
OFFSET 0 ROWS FETCH NEXT 30 ROWS ONLY;

18.6 Trending Attribution Data: Catching Cost Regressions Before They Hit Your Bill

A single snapshot of query costs is useful. A time-series of snapshots is how you catch regressions before they appear as billing surprises. The query_cost_attribution tracking table written by the pipeline in section 18.4 supports trend analysis directly.

-- SQL Server: week-over-week cost trend for top queries
-- Detects queries whose monthly cost estimate has grown by more than 20%
WITH this_week AS (
    SELECT
        query_id,
        query_preview,
        AVG(est_monthly_cost_usd)       AS avg_cost
    FROM dbo.query_cost_attribution
    WHERE captured_at >= DATEADD(DAY, -7, SYSDATETIME())
    GROUP BY query_id, query_preview
),
last_week AS (
    SELECT
        query_id,
        AVG(est_monthly_cost_usd)       AS avg_cost
    FROM dbo.query_cost_attribution
    WHERE captured_at >= DATEADD(DAY, -14, SYSDATETIME())
      AND captured_at <  DATEADD(DAY, -7, SYSDATETIME())
    GROUP BY query_id
)
SELECT
    tw.query_id,
    tw.query_preview,
    ROUND(lw.avg_cost, 2)               AS last_week_usd,
    ROUND(tw.avg_cost, 2)               AS this_week_usd,
    ROUND((tw.avg_cost - lw.avg_cost)
           / NULLIF(lw.avg_cost, 0) * 100, 1)
                                        AS pct_change,
    CASE
        WHEN tw.avg_cost - lw.avg_cost > 200  THEN 'HIGH'
        WHEN tw.avg_cost - lw.avg_cost > 50   THEN 'MEDIUM'
        ELSE 'LOW'
    END                                 AS regression_severity
FROM this_week tw
JOIN last_week lw ON lw.query_id = tw.query_id
WHERE tw.avg_cost > lw.avg_cost * 1.20  -- 20% cost increase
ORDER BY (tw.avg_cost - lw.avg_cost) DESC;
-- SQL Server: equivalent trend query against the same tracking table
-- (Assumes tracking table is mirrored to SQL Server or queried via linked server)
WITH this_week AS (
    SELECT
        queryid,
        query_preview,
        AVG(est_monthly_cost_usd)       AS avg_cost
    FROM query_cost_attribution
    WHERE captured_at >= DATEADD(DAY, -7, GETUTCDATE())
    GROUP BY queryid, query_preview
),
last_week AS (
    SELECT
        queryid,
        AVG(est_monthly_cost_usd)       AS avg_cost
    FROM query_cost_attribution
    WHERE captured_at >= DATEADD(DAY, -14, GETUTCDATE())
      AND captured_at <  DATEADD(DAY, -7,  GETUTCDATE())
    GROUP BY queryid
)
SELECT
    tw.queryid,
    tw.query_preview,
    ROUND(lw.avg_cost, 2)               AS last_week_usd,
    ROUND(tw.avg_cost, 2)               AS this_week_usd,
    ROUND((tw.avg_cost - lw.avg_cost)
          / NULLIF(lw.avg_cost, 0) * 100, 1)
                                        AS pct_change,
    CASE
        WHEN tw.avg_cost - lw.avg_cost > 200  THEN 'HIGH'
        WHEN tw.avg_cost - lw.avg_cost > 50   THEN 'MEDIUM'
        ELSE 'LOW'
    END                                 AS regression_severity
FROM this_week tw
JOIN last_week lw ON tw.queryid = lw.queryid
WHERE tw.avg_cost > lw.avg_cost * 1.20
ORDER BY (tw.avg_cost - lw.avg_cost) DESC;

Wire this trend query into your daily pipeline and route HIGH severity regressions to Slack or PagerDuty. A deploy that ships a new code path introducing a full table scan will appear as a HIGH regression within 24 hours—long before the end-of-month bill.

#### Grafana Dashboard Integration

If your organization uses Grafana, the tracking table makes a natural data source. The following Grafana panel query renders a stacked area chart of the top 10 queries by estimated monthly cost over the past 30 days:

-- Grafana: top 10 queries by cost over time (SQL Server / MSSQL data source)
-- Use $__timeFilter(captured_at) for the Grafana time range variable
SELECT
    CAST(captured_at AS DATE)           AS time,
    LEFT(query_preview, 60)             AS metric,
    AVG(est_monthly_cost_usd)           AS value
FROM dbo.query_cost_attribution
WHERE captured_at IN (
    SELECT DISTINCT CAST(captured_at AS DATE)
    FROM dbo.query_cost_attribution
    WHERE $__timeFilter(captured_at)
)
AND query_id IN (
    SELECT TOP 10 query_id
    FROM dbo.query_cost_attribution
    WHERE $__timeFilter(captured_at)
    GROUP BY query_id
    ORDER BY SUM(est_monthly_cost_usd) DESC
)
GROUP BY CAST(captured_at AS DATE), LEFT(query_preview, 60)
ORDER BY 1, 3 DESC;

Set the panel type to Time series, enable stacking, and label it "Estimated Monthly Query Cost by Query (USD)". Over time this chart becomes a visual changelog: deploy-induced cost spikes appear as step changes in specific query series, and optimization work shows up as a visible drop.

18.7 Connecting Attribution to Reserved Instance and Savings Plan Decisions

Query cost attribution data also informs infrastructure purchasing decisions. Here is the chain of reasoning:

1. Identify the top three compute-heavy queries from the attribution table.

2. Estimate the CPU headroom needed if those queries were optimized (typically a 40–70% CPU reduction for index additions or query rewrites).

3. Model the instance downgrade path: if optimizing two queries allows you to move from db.r6g.4xlarge to db.r6g.2xlarge, you save approximately $382/month before any Reserved Instance discount.

4. Apply the RI discount on the smaller instance: a 1-year no-upfront RI on db.r6g.2xlarge in us-east-1 runs roughly 30% below on-demand, meaning you pay for a smaller box at a further discount.

The mistake most teams make is purchasing Reserved Instances before optimizing queries. They lock in a commitment at an inflated instance size, then optimize queries, and find themselves over-provisioned and unable to recover the cost difference. The correct sequence is:

1. Run query attribution for 30 days.

2. Fix the top five to ten queries.

3. Observe CPU and I/O metrics for two weeks post-optimization.

4. Right-size the instance.

5. Purchase the RI or Savings Plan on the right-sized instance.

*The correct sequence: optimize and right-size before committing — reversing this order locks in spend at an inflated instance size.*

-- SQL Server: estimate post-optimization compute savings
-- Assumes you have identified which query_ids to fix and their expected improvement
WITH optimization_scenarios AS (
    SELECT TOP 10
        query_id,
        query_preview,
        est_monthly_cost_usd                            AS current_monthly_cost,
        -- Conservative: assume 70% reduction in compute cost for an index fix
        -- Adjust improvement_factor per query based on plan analysis
        CASE
            WHEN query_preview LIKE '%WHERE%AND%'
             AND query_preview NOT LIKE '%JOIN%'
             THEN 0.70   -- likely missing composite index
            WHEN query_preview LIKE '%GROUP BY%'
             AND query_preview LIKE '%SUM%'
             THEN 0.60   -- aggregation, indexed view candidate
            ELSE 0.40    -- conservative default
        END                                             AS improvement_factor
    FROM dbo.query_cost_attribution
    WHERE captured_at >= DATEADD(DAY, -7, SYSDATETIME())
    ORDER BY est_monthly_cost_usd DESC
)
SELECT
    query_id,
    LEFT(query_preview, 80)                             AS query_preview,
    ROUND(current_monthly_cost, 2)                       AS current_usd,
    ROUND(current_monthly_cost * improvement_factor, 2) AS projected_savings_usd,
    ROUND(current_monthly_cost * (1 - improvement_factor), 2)
                                                        AS post_opt_cost_usd
FROM optimization_scenarios
UNION ALL
SELECT
    NULL,
    '=== TOTAL ===',
    ROUND(SUM(current_monthly_cost), 2),
    ROUND(SUM(current_monthly_cost * improvement_factor), 2),
    ROUND(SUM(current_monthly_cost * (1 - improvement_factor)), 2)
FROM optimization_scenarios;

The output of this query gives you the business case document for optimization work: total projected savings, per-query savings, and the residual cost after optimization. Pair it with the instance right-sizing model from Chapter 12 and you have a full cost reduction roadmap that connects query-level work to infrastructure spend.

18.8 Special Considerations for Azure SQL Serverless, Elastic Pools, and Managed Instance

The attribution model described above assumes a provisioned instance where compute cost is primarily a function of time and CPU utilization. Three Azure SQL deployment options have different billing models that require adjusted attribution logic.

#### Azure SQL Database serverless

Serverless bills in vCore-seconds: each second the database is unpaused, you pay for the vCores actually used (between the configured minimum and maximum), and a paused database bills nothing for compute. Attribution for serverless should therefore track two things per query: its share of vCore-seconds, and whether its execution pattern is what keeps the database from auto-pausing.

-- Azure SQL serverless: attribute vCore-second cost per query
-- Query Store must be enabled; pull billed vCore-seconds from Azure Cost Management
-- for the same window and pass it in as @billed_vcore_seconds and @total_cost_usd

DECLARE @billed_vcore_seconds FLOAT = 1296000;  -- e.g. 15 vCore-hours in the window
DECLARE @total_cost_usd       FLOAT = 84.50;    -- billed compute cost for the window

WITH query_cpu AS (
    SELECT
        q.query_id,
        LEFT(qt.query_sql_text, 120)              AS query_preview,
        SUM(rs.count_executions)                  AS calls,
        SUM(rs.avg_cpu_time * rs.count_executions)
            / 1000000.0                           AS cpu_seconds
    FROM sys.query_store_query q
    JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
    JOIN sys.query_store_plan pl       ON pl.query_id = q.query_id
    JOIN sys.query_store_runtime_stats rs ON rs.plan_id = pl.plan_id
    WHERE rs.last_execution_time >= DATEADD(DAY, -7, SYSDATETIME())
    GROUP BY q.query_id, qt.query_sql_text
)
SELECT TOP 25
    query_id,
    query_preview,
    calls,
    ROUND(cpu_seconds, 2)                         AS cpu_seconds,
    ROUND(cpu_seconds / NULLIF(SUM(cpu_seconds) OVER (), 0) * 100, 2)
                                                  AS pct_of_cpu,
    -- Pro-rata share of the billed vCore-second cost
    ROUND(cpu_seconds / NULLIF(SUM(cpu_seconds) OVER (), 0)
          * @total_cost_usd, 2)                    AS attributed_cost_usd
FROM query_cpu
ORDER BY attributed_cost_usd DESC;

Separately, check whether scheduled jobs or keep-alive probes are preventing auto-pause: any query that executes at least once inside every auto-pause delay window (commonly one hour to seven days) keeps the database awake and converts a near-zero compute bill into a 24/7 one. Those queries deserve attribution for the entire unpaused cost, not just their own vCore-seconds.

#### Azure SQL elastic pools

In an elastic pool, vCores (or eDTUs) are shared across databases and billed at the pool level. Attribute the pool's cost to individual databases first — using per-database CPU percent from sys.elastic_pool_resource_stats (logical server master) or Azure Metrics — then run the standard per-query attribution inside each database. A database that consistently uses 2% of the pool should carry roughly 2% of the pool's bill, which often reveals that one noisy database is subsidized by nineteen quiet ones.

-- Elastic pool: per-database share of pool CPU (run on the logical server master)
SELECT
    database_name,
    AVG(avg_cpu_percent)                          AS avg_cpu_pct,
    MAX(avg_cpu_percent)                          AS max_cpu_pct,
    -- Multiply avg_cpu_pct / 100 by the pool's monthly cost for a dollar share
    ROUND(AVG(avg_cpu_percent), 2)                AS pool_share_pct
FROM sys.elastic_pool_resource_stats
WHERE end_time >= DATEADD(DAY, -7, SYSDATETIME())
GROUP BY database_name
ORDER BY avg_cpu_pct DESC;

#### Azure SQL Managed Instance

Managed Instance bills like a provisioned instance (vCores per hour plus storage), so the standard attribution model applies directly. The one adjustment: Query Store is available per database, and cross-database queries are common on Managed Instance. Aggregate query_id values are only unique per database, so include DB_NAME() in the attribution extract when consolidating across databases on the same instance.

18.9 Presenting Attribution Data to Engineering and Finance Teams

The most technically complete cost attribution system fails if its outputs don't drive action. Engineering teams and finance teams have different relationships with the data, and the pipeline you build should produce artifacts for both audiences.

For engineering teams, the actionable artifact is a ranked list of queries with specific optimization recommendations attached. The pipeline from section 18.4 can be extended to generate a Markdown or HTML report:

def generate_engineering_report(rows: list[dict]) -> str:
    """
    Generate a Markdown report suitable for a GitHub issue or Confluence page.
    """
    lines = [
        "# Query Cost Attribution Report",
        f"Generated: {datetime.datetime.now(datetime.timezone.utc).strftime('%Y-%m-%d %H:%M UTC')}",
        f"Observation window: {OBSERVATION_DAYS} days | Scaled to 30-day estimate",
        "",
        "## Top Queries by Estimated Monthly Cost",
        "",
        "| Rank | Est. Monthly Cost | % of Total | Calls | Avg ms | Query Preview |",
        "|------|-------------------|------------|-------|--------|---------------|",
    ]
    for i, row in enumerate(rows[:15], 1):
        cost   = row.get("est_monthly_cost_usd") or 0
        pct    = row.get("pct_of_total_cost") or 0
        calls  = row.get("calls") or 0
        avg_ms = row.get("avg_exec_ms") or 0
        qtext  = (row.get("query_preview") or "")[:80].replace("|", "\\|")
        lines.append(
            f"| {i} | ${float(cost):,.2f} | {float(pct):.1f}% "
            f"| {int(calls):,} | {float(avg_ms):.1f} | `{qtext}` |"
        )
    total = sum(float(r.get("est_monthly_cost_usd") or 0) for r in rows)
    lines += [
        "",
        f"**Total estimated monthly database query cost: ${total:,.2f}**",
        "",
        "## Recommended Actions",
        "",
        "1. Review queries with `disk_blocks_read > 1,000,000` for missing indexes.",
        "2. Investigate queries with `calls > 1,000,000` for batching opportunities.",
        "3. Evaluate materialized views for queries with `avg_exec_ms > 5,000`.",
        "4. Check N+1 patterns where two queries share identical call counts.",
    ]
    return "\n".join(lines)

For finance teams, the artifact is a cost allocation summary that maps query costs to engineering teams or product features. This requires tagging—either via application-level query comments or by maintaining a mapping table from queryid to team:

-- SQL Server equivalent
SELECT
    COALESCE(qtm.team_name, 'unattributed')     AS team,
    COALESCE(qtm.feature_area, 'unknown')        AS feature_area,
    COUNT(DISTINCT qca.queryid)                  AS unique_queries,
    ROUND(SUM(qca.est_monthly_cost_usd), 2)      AS total_monthly_cost_usd,
    ROUND(100.0 * SUM(qca.est_monthly_cost_usd)
          / NULLIF(SUM(SUM(qca.est_monthly_cost_usd)) OVER (), 0), 2)
                                                 AS pct_of_total
FROM query_cost_attribution qca
LEFT JOIN query_team_mapping qtm ON qca.queryid = qtm.queryid
WHERE qca.captured_at >= DATEADD(DAY, 1 - DAY(GETUTCDATE()), CAST(GETUTCDATE() AS DATE))
GROUP BY qtm.team_name, qtm.feature_area
ORDER BY total_monthly_cost_usd DESC;

This team-level rollup turns query attribution into a chargeback or showback model. When the payments team sees that their batch reconciliation job owns 38% of the database compute bill, the conversation about optimization priority changes fundamentally—it becomes a feature team's budget problem, not an invisible infrastructure overhead.

---

Key Takeaways

  • → **Query attribution quantifies invisible costs**: most cloud database overspend is driven by a small number of queries whose individual costs are invisible until converted to a per-query monthly dollar figure; Query Store and `sys.dm_exec_query_stats` provide the raw data needed to build that figure.
  • → **Three cost signals matter most**: disk blocks read (I/O cost), CPU seconds consumed (compute cost), and call count (aggregate cost from individually cheap queries); ranking queries on the combination of these three rather than on latency alone surfaces the true budget drivers.
  • → **Automate daily attribution and trend detection**: a single attribution snapshot is a debugging tool; a daily time series written to a tracking table becomes a regression detector that surfaces new full-table scans or N+1 patterns within 24 hours of a problematic deploy, long before they appear on the monthly bill.
  • → **Different billing models require adjusted attribution logic**: Azure SQL serverless attributes cost via vCore-seconds weighted by query CPU share, elastic pools via per-database CPU share of pool cost, and Managed Instance via the standard provisioned model—the correct cost formula depends on the billing model of the service, not a generic CPU/IOPS proxy.
  • → **Sequence matters for RI and Savings Plan purchases**: committing to Reserved Instances before optimizing queries locks in spend at an inflated instance size; the correct order is attribute, optimize, observe, right-size, then commit—turning query-level engineering work directly into durable infrastructure savings.
