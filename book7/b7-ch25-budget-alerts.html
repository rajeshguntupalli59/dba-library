Chapter 25: Budget Alerts and Anomaly Detection

Organizations that implement proactive budget alerts and anomaly detection catch runaway database costs an average of 11 days earlier than those relying on monthly billing reviews — translating to savings of $3,000 to $50,000 per incident depending on workload size. This chapter covers building a layered alerting system across AWS, Azure, and GCP that notifies the right people at the right thresholds, pairs those alerts with automated anomaly detection to distinguish genuine cost spikes from expected growth, and wires everything into the scheduling and remediation systems introduced in earlier chapters. By the end, your team will move from reactive bill shock to a posture where no database cost anomaly survives more than 24 hours undetected.

---

25.1 Understanding the Cost Signal Landscape

Before configuring a single alert, it pays to understand what signals are actually available and what each one measures. Budget alerts and anomaly detection are often treated as synonyms, but they serve different purposes. A budget alert fires when spending crosses a predefined dollar threshold. An anomaly detector fires when spending deviates from a predicted baseline — even if the absolute number is still within budget. Both matter.

The three major clouds each expose cost data through distinct APIs, and those APIs have different latency characteristics that directly affect how quickly you can detect a problem.

AWS publishes cost data to Cost Explorer with roughly 8–24 hours of lag. The Cost Anomaly Detection service processes that same data and sends SNS notifications within the lag window. CloudWatch metrics for RDS — CPU, storage, IOPS, connections — are near real-time (60-second granularity on most instance types) and serve as the leading indicator that a cost spike is about to appear in billing data.

Azure Cost Management data carries a lag of 8–24 hours for Pay-As-You-Go resources. Azure Monitor metrics for SQL Database are near real-time. The Azure Cost Management anomaly detection feature (in preview as of 2024) applies machine learning against the daily cost feed.

GCP BigQuery billing export is the most flexible of the three: once enabled, data appears in your dataset within hours and you can query it with SQL. The Cloud Billing Budget API supports percentage-based and absolute threshold alerts. Cloud Monitoring catches database-level signals in near real-time.

The architecture that works across all three clouds looks like this:

Real-time DB metrics (CloudWatch / Azure Monitor / Cloud Monitoring)
        ↓ [leading indicators: connections, IOPS, CPU]
Hourly cost feed (Cost Explorer API / Cost Management API / BQ billing export)
        ↓ [lagging indicators: actual spend]
Anomaly detection layer (AWS Cost Anomaly Detection / custom Python / BQ ML)
        ↓
Alert routing (SNS / Action Groups / PagerDuty / Slack)
        ↓
Automated remediation (Lambda / Automation Runbooks / Cloud Functions)

*Real-time database metrics give a 6-12 hour head start over lagging billing data.*

The key insight is that by the time billing data shows an anomaly, the underlying cause — a runaway query, an unexpected replica count, a forgotten snapshot — has already been running for hours. Wiring real-time DB metrics into the alert pipeline gives you the 6–12 hour head start that billing data alone cannot provide.

25.2 Configuring Budget Alerts on AWS, Azure, and GCP

#### AWS Budget Alerts

AWS Budgets support four budget types: Cost, Usage, Savings Plans coverage, and Reserved Instance utilization. For database FinOps, all four are relevant. A team running RDS for SQL Server on Reserved Instances needs both a cost budget and an RI utilization alert — the first catches overspend, the second catches underutilized reservations that represent sunk cost without benefit.

The following script creates a complete budget configuration for an RDS workload using the AWS CLI. It establishes three alert thresholds: 70% (early warning), 90% (action required), and 100% (breach). The forecasted-spend alert at 80% gives finance teams roughly a week of lead time before the billing period closes.

#!/bin/bash
# create_rds_budget.sh
# Creates a monthly RDS cost budget with tiered alerts
# Requires: AWS CLI configured, SNS topic ARN for notifications

ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
SNS_TOPIC_ARN="arn:aws:sns:us-east-1:${ACCOUNT_ID}:database-cost-alerts"
BUDGET_LIMIT="5000.00"  # Adjust to your monthly RDS spend baseline
CURRENCY="USD"

aws budgets create-budget \
  --account-id "${ACCOUNT_ID}" \
  --budget '{
    "BudgetName": "RDS-Monthly-Cost-Budget",
    "BudgetLimit": {
      "Amount": "'"${BUDGET_LIMIT}"'",
      "Unit": "'"${CURRENCY}"'"
    },
    "TimeUnit": "MONTHLY",
    "BudgetType": "COST",
    "CostFilters": {
      "Service": ["Amazon Relational Database Service"]
    },
    "CostTypes": {
      "IncludeTax": true,
      "IncludeSubscription": true,
      "UseBlended": false,
      "IncludeRefund": false,
      "IncludeCredit": false,
      "IncludeUpfront": true,
      "IncludeRecurring": true,
      "IncludeOtherSubscription": true,
      "IncludeSupport": false,
      "IncludeDiscount": true,
      "UseAmortized": false
    }
  }' \
  --notifications-with-subscribers '[
    {
      "Notification": {
        "NotificationType": "ACTUAL",
        "ComparisonOperator": "GREATER_THAN",
        "Threshold": 70,
        "ThresholdType": "PERCENTAGE"
      },
      "Subscribers": [
        {"SubscriptionType": "SNS", "Address": "'"${SNS_TOPIC_ARN}"'"},
        {"SubscriptionType": "EMAIL", "Address": "dba-team@company.com"}
      ]
    },
    {
      "Notification": {
        "NotificationType": "ACTUAL",
        "ComparisonOperator": "GREATER_THAN",
        "Threshold": 90,
        "ThresholdType": "PERCENTAGE"
      },
      "Subscribers": [
        {"SubscriptionType": "SNS", "Address": "'"${SNS_TOPIC_ARN}"'"},
        {"SubscriptionType": "EMAIL", "Address": "cto@company.com"}
      ]
    },
    {
      "Notification": {
        "NotificationType": "ACTUAL",
        "ComparisonOperator": "GREATER_THAN",
        "Threshold": 100,
        "ThresholdType": "PERCENTAGE"
      },
      "Subscribers": [
        {"SubscriptionType": "SNS", "Address": "'"${SNS_TOPIC_ARN}"'"},
        {"SubscriptionType": "EMAIL", "Address": "finance@company.com"}
      ]
    },
    {
      "Notification": {
        "NotificationType": "FORECASTED",
        "ComparisonOperator": "GREATER_THAN",
        "Threshold": 80,
        "ThresholdType": "PERCENTAGE"
      },
      "Subscribers": [
        {"SubscriptionType": "SNS", "Address": "'"${SNS_TOPIC_ARN}"'"},
        {"SubscriptionType": "EMAIL", "Address": "dba-team@company.com"}
      ]

  ]'

echo "Budget created. Verifying..."

  --query 'Budgets[?BudgetName==`RDS-Monthly-Cost-Budget`].{Name:BudgetName,Limit:BudgetLimit.Amount,Type:BudgetType}' \
  --output table

# Create RI utilization alert separately — fires when utilization drops below 80%
aws budgets create-budget \
  --account-id "${ACCOUNT_ID}" \
  --budget '{
    "BudgetName": "RDS-RI-Utilization-Alert",
    "BudgetLimit": {
      "Amount": "80",
      "Unit": "PERCENTAGE"
    },
    "TimeUnit": "MONTHLY",
    "BudgetType": "RI_UTILIZATION",
    "CostFilters": {
      "Service": ["Amazon Relational Database Service"]
    }
  }' \
  --notifications-with-subscribers '[
    {
      "Notification": {
        "NotificationType": "ACTUAL",
        "ComparisonOperator": "LESS_THAN",
        "Threshold": 80,
        "ThresholdType": "PERCENTAGE"
      },
      "Subscribers": [
        {"SubscriptionType": "EMAIL", "Address": "dba-team@company.com"}
      ]
    }
  ]'

echo "RI utilization budget created."

#### Azure Cost Management Budget Alerts

Azure budget alerts are configured per subscription or resource group. For database teams, creating a budget scoped to the resource group containing your Azure SQL instances isolates the signal from unrelated compute costs.

#!/bin/bash
# create_azure_sql_budget.sh
# Creates a monthly Azure SQL budget with alert rules
# Requires: Azure CLI logged in, resource group name

SUBSCRIPTION_ID=$(az account show --query id -o tsv)
RESOURCE_GROUP="rg-databases-prod"
BUDGET_NAME="AzureSQL-Monthly-Budget"
BUDGET_AMOUNT=4000
START_DATE=$(date +%Y-%m-01)
END_DATE="2030-12-31"
ALERT_EMAIL="dba-team@company.com"
ACTION_GROUP_ID="/subscriptions/${SUBSCRIPTION_ID}/resourceGroups/${RESOURCE_GROUP}/providers/microsoft.insights/actionGroups/DatabaseCostAlerts"

# Create action group first (email + webhook to Slack or PagerDuty)

  --name "DatabaseCostAlerts" \
  --resource-group "${RESOURCE_GROUP}" \
  --short-name "DBCostAlert" \
  --action email dba-primary "${ALERT_EMAIL}"

# Create the budget scoped to the database resource group
az consumption budget create \
  --budget-name "${BUDGET_NAME}" \
  --amount "${BUDGET_AMOUNT}" \
  --time-grain Monthly \
  --start-date "${START_DATE}" \
  --end-date "${END_DATE}" \
  --resource-group "${RESOURCE_GROUP}" \
  --notifications '[
    {
      "enabled": true,
      "operator": "GreaterThan",
      "threshold": 75,
      "contactEmails": ["'"${ALERT_EMAIL}"'"],
      "contactRoles": ["Owner"],
      "thresholdType": "Actual"
    },
    {
      "enabled": true,
      "operator": "GreaterThan",
      "threshold": 90,
      "contactEmails": ["'"${ALERT_EMAIL}"'", "cto@company.com"],
      "contactRoles": ["Owner", "Contributor"],
      "thresholdType": "Actual"
    },
    {
      "enabled": true,
      "operator": "GreaterThan",
      "threshold": 90,
      "contactEmails": ["'"${ALERT_EMAIL}"'"],
      "contactRoles": ["Owner"],
      "thresholdType": "Forecasted"
    }
  ]'

echo "Azure SQL budget ${BUDGET_NAME} created for resource group ${RESOURCE_GROUP}"
az consumption budget show --budget-name "${BUDGET_NAME}" \
  --resource-group "${RESOURCE_GROUP}" \
  --query '{Name:name, Amount:properties.amount, TimeGrain:properties.timeGrain}' \
  -o table

#### GCP Cloud Billing Budget Alerts

GCP billing budgets are managed at the billing account level and support programmatic notification via Pub/Sub, which enables automated remediation workflows far more cleanly than email-only alerts.

#!/bin/bash
# create_gcp_cloudsql_budget.sh
# Creates a Cloud SQL budget with Pub/Sub notification for automation
# Requires: gcloud CLI authenticated, billing account ID

BILLING_ACCOUNT_ID="XXXXXX-XXXXXX-XXXXXX"  # Replace with your billing account
PROJECT_ID="your-project-id"
PUBSUB_TOPIC="projects/${PROJECT_ID}/topics/billing-alerts"
BUDGET_AMOUNT=3500

# Create Pub/Sub topic for programmatic alerts
gcloud pubsub topics create billing-alerts --project="${PROJECT_ID}"

# Grant billing account permission to publish to the topic
gcloud pubsub topics add-iam-policy-binding billing-alerts \
  --member="serviceAccount:billing-alerts@system.gserviceaccount.com" \
  --role="roles/pubsub.publisher" \
  --project="${PROJECT_ID}"

# Create budget with tiered thresholds
gcloud billing budgets create \
  --billing-account="${BILLING_ACCOUNT_ID}" \
  --display-name="CloudSQL-Monthly-Budget" \
  --budget-amount="${BUDGET_AMOUNT}USD" \
  --threshold-rule=percent=0.75,basis=current-spend \
  --threshold-rule=percent=0.90,basis=current-spend \
  --threshold-rule=percent=1.00,basis=current-spend \
  --threshold-rule=percent=0.90,basis=forecasted-spend \
  --filter-services="services/95FF-2EF5-5EA1" \
  --notifications-rule-pubsub-topic="${PUBSUB_TOPIC}" \
  --notifications-rule-disable-default-iam-recipients=false \
  --all-updates-rule-monitoring-notification-channels=""

# Verify creation
gcloud billing budgets list \
  --billing-account="${BILLING_ACCOUNT_ID}" \
  --format="table(displayName, budgetFilter.services, amount.specifiedAmount.units)"

25.3 Enabling and Tuning AWS Cost Anomaly Detection

AWS Cost Anomaly Detection uses machine learning trained on your specific historical spend patterns. Unlike a simple threshold alert, it accounts for seasonal variation — it will not fire an alert on the last day of the month simply because billing is cumulative. This makes it substantially more precise than budget alerts for detecting genuine anomalies in the $200–$2,000 range that budget thresholds miss.

The service operates on monitors (what to watch) and subscriptions (how to be notified). For RDS-specific detection, creating a service-level monitor scoped to RDS gives the ML model a cleaner signal than an account-wide monitor that mixes RDS costs with EC2 and S3 noise.

#!/bin/bash
# setup_cost_anomaly_detection.sh
# Configures AWS Cost Anomaly Detection for RDS workloads
# Monitors: service-level RDS, plus per-tag monitor for prod vs. non-prod isolation

ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
SNS_TOPIC_ARN="arn:aws:sns:us-east-1:${ACCOUNT_ID}:database-cost-alerts"

# Monitor 1: Service-level monitor for all RDS costs
RDS_MONITOR_ARN=$(aws ce create-anomaly-monitor \
  --anomaly-monitor '{
    "MonitorName": "RDS-Service-Monitor",
    "MonitorType": "DIMENSIONAL",
    "MonitorDimension": "SERVICE"
  }' \
  --query AnomalyMonitorArn --output text)

echo "RDS service monitor created: ${RDS_MONITOR_ARN}"

# Monitor 2: Tag-based monitor to isolate production database costs
# This prevents a dev environment spike from masking a prod anomaly
PROD_MONITOR_ARN=$(aws ce create-anomaly-monitor \
  --anomaly-monitor '{
    "MonitorName": "RDS-Production-Tag-Monitor",
    "MonitorType": "CUSTOM",
    "MonitorSpecification": {
      "Tags": {
        "Key": "Environment",
        "Values": ["production", "prod"]
      }
    }
  }' \
  --query AnomalyMonitorArn --output text)

echo "Production tag monitor created: ${PROD_MONITOR_ARN}"

# Subscription for RDS service monitor
# Alert threshold: $50 individual anomaly OR $200 cumulative in rolling 7-day window
aws ce create-anomaly-subscription \
  --anomaly-subscription '{
    "SubscriptionName": "RDS-Anomaly-Alerts-Primary",
    "MonitorArnList": ["'"${RDS_MONITOR_ARN}"'"],
    "Subscribers": [
      {
        "Address": "'"${SNS_TOPIC_ARN}"'",
        "Type": "SNS"
      },
      {
        "Address": "dba-team@company.com",
        "Type": "EMAIL"
      }
    ],
    "Threshold": 50,
    "Frequency": "DAILY",
    "ThresholdExpression": {
      "Or": [
        {
          "Dimensions": {
            "Key": "ANOMALY_TOTAL_IMPACT_ABSOLUTE",
            "Values": ["50"],
            "MatchOptions": ["GREATER_THAN_OR_EQUAL"]
          }
        },
        {
          "Dimensions": {
            "Key": "ANOMALY_TOTAL_IMPACT_PERCENTAGE",
            "Values": ["20"],
            "MatchOptions": ["GREATER_THAN_OR_EQUAL"]
          }
        }
      ]
    }
  }'

# High-severity subscription for production monitor — immediate notification
aws ce create-anomaly-subscription \
  --anomaly-subscription '{
    "SubscriptionName": "RDS-Production-Critical-Alerts",
    "MonitorArnList": ["'"${PROD_MONITOR_ARN}"'"],
    "Subscribers": [
      {
        "Address": "'"${SNS_TOPIC_ARN}"'",
        "Type": "SNS"
      },
      {
        "Address": "cto@company.com",
        "Type": "EMAIL"
      }
    ],
    "Threshold": 200,
    "Frequency": "IMMEDIATE"
  }'

# List all configured anomaly subscriptions to confirm setup
echo "Configured anomaly subscriptions:"
aws ce list-anomaly-subscriptions \
  --query 'AnomalySubscriptions[].{Name:SubscriptionName,Threshold:Threshold,Frequency:Frequency}' \
  --output table

# Query recent anomalies detected in last 90 days (useful for baseline calibration)
echo "Recent RDS cost anomalies:"
aws ce get-anomalies \
  --monitor-arn "${RDS_MONITOR_ARN}" \
  --date-interval '{
    "StartDate": "'$(date -d '90 days ago' +%Y-%m-%d)'",
    "EndDate": "'$(date +%Y-%m-%d)'"
  }' \
  --query 'Anomalies[].{
    Start:AnomalyStartDate,
    End:AnomalyEndDate,
    ImpactUSD:Impact.TotalActualSpend,
    ExpectedUSD:Impact.TotalExpectedSpend
  }' \
  --output table

One tuning decision deserves attention: the threshold values of $50 (absolute) and 20% (percentage). Teams with predictable workloads and tight budgets should lower these — $25 and 15% — to catch small anomalies early. Teams with noisy, variable workloads (many batch jobs, development databases with irregular usage) should raise them to reduce alert fatigue. Review the anomaly history query above after 30 days and recalibrate.

25.4 Custom Anomaly Detection Using Database and Cost Metrics

The built-in anomaly detection on all three clouds works well for billing-level anomalies but misses the pattern where a cost spike is caused by a specific query, connection pool explosion, or unexpected autoscaling event. Building a custom detection layer that correlates database-level metrics with cost data closes this gap. When an alert fires, you want to know not just *that* costs spiked but *why*.

The following Python script runs on a schedule (recommended: every 6 hours via AWS Lambda, Azure Functions, or Cloud Run) and performs three checks: it queries Query Store for query-level cost drivers, it pulls CloudWatch RDS metrics to detect resource anomalies, and it compares the current day's Cost Explorer spend against the 30-day rolling average. If any of the three checks exceed their thresholds, it posts a structured alert to a Slack webhook with enough context to act immediately.

#!/usr/bin/env python3
"""
db_cost_anomaly_detector.py
Correlates database metrics with cost data to identify anomaly root causes.
Runs on a 6-hour schedule via Lambda/Cloud Run/Azure Functions.
Requires: pyodbc, boto3, requests
Environment variables: DB_HOST, DB_NAME, DB_USER, DB_PASSWORD,
                       SLACK_WEBHOOK_URL, AWS_DEFAULT_REGION
"""

import os
import json
import statistics
from datetime import datetime, timedelta, timezone
from typing import Optional

import boto3
import pyodbc
import requests

# ── Configuration ──────────────────────────────────────────────────────────────
def build_conn_str() -> str:
    return (
        "DRIVER={ODBC Driver 18 for SQL Server};"
        f"SERVER={os.environ['DB_HOST']},{os.environ.get('DB_PORT', '1433')};"
        f"DATABASE={os.environ['DB_NAME']};"
        f"UID={os.environ['DB_USER']};PWD={os.environ['DB_PASSWORD']};"
        "Encrypt=yes;TrustServerCertificate=no;Connection Timeout=10;"
    )

SLACK_WEBHOOK = os.environ.get("SLACK_WEBHOOK_URL")
REGION = os.environ.get("AWS_DEFAULT_REGION", "us-east-1")
RDS_INSTANCE_ID = os.environ.get("RDS_INSTANCE_ID", "prod-sqlserver-01")

# Anomaly thresholds
COST_SPIKE_THRESHOLD_PCT = 25.0      # Alert if today's spend > 30-day avg by this %
QUERY_COST_THRESHOLD_MS = 5000.0     # Alert if mean query time exceeds this (ms)
CONNECTION_SPIKE_THRESHOLD = 1.5     # Alert if connections > 1.5x recent average
IOPS_SPIKE_THRESHOLD_PCT = 40.0      # Alert if IOPS > 40% above recent average


def get_cost_anomaly(ce_client, days_back: int = 30) -> dict:
    """
    Compares today's RDS spend against the rolling 30-day daily average.
    Returns anomaly data including current spend, expected spend, and % deviation.
    """
    end_date = datetime.now(timezone.utc).date()
    start_date = end_date - timedelta(days=days_back)
    today = end_date

    response = ce_client.get_cost_and_usage(
        TimePeriod={
            "Start": start_date.isoformat(),
            "End": end_date.isoformat(),
        },
        Granularity="DAILY",
        Filter={
            "Dimensions": {
                "Key": "SERVICE",
                "Values": ["Amazon Relational Database Service"],
            }
        },
        Metrics=["UnblendedCost"],
    )

    daily_costs = []
    today_cost = 0.0

    for result in response["ResultsByTime"]:
        amount = float(result["Total"]["UnblendedCost"]["Amount"])
        date_str = result["TimePeriod"]["Start"]
        if date_str == today.isoformat():
            today_cost = amount
        else:
            if amount > 0:  # Exclude zero-cost days (weekends on dev environments)
                daily_costs.append(amount)

    if not daily_costs:
        return {"status": "insufficient_data"}

    avg_daily = statistics.mean(daily_costs)
    stddev_daily = statistics.stdev(daily_costs) if len(daily_costs) > 1 else 0.0
    deviation_pct = ((today_cost - avg_daily) / avg_daily * 100) if avg_daily > 0 else 0.0

    return {
        "status": "anomaly" if deviation_pct > COST_SPIKE_THRESHOLD_PCT else "normal",
        "today_cost_usd": round(today_cost, 2),
        "avg_daily_cost_usd": round(avg_daily, 2),
        "stddev_usd": round(stddev_daily, 2),
        "deviation_pct": round(deviation_pct, 1),
        "threshold_pct": COST_SPIKE_THRESHOLD_PCT,
        "sample_days": len(daily_costs),
    }


def get_cloudwatch_anomalies(cw_client, instance_id: str) -> list:
    """
    Checks CloudWatch RDS metrics for resource-level spikes.
    Covers: DatabaseConnections, ReadIOPS, WriteIOPS, CPUUtilization.
    """
    anomalies = []
    now = datetime.now(timezone.utc)
    period_hours = 6
    baseline_hours = 72  # Compare against 3-day baseline

    metrics_to_check = [
        {
            "name": "DatabaseConnections",
            "namespace": "AWS/RDS",
            "stat": "Maximum",
            "threshold_multiplier": CONNECTION_SPIKE_THRESHOLD,
            "unit": "connections",
        },
        {
            "name": "ReadIOPS",
            "namespace": "AWS/RDS",
            "stat": "Average",
            "threshold_pct": IOPS_SPIKE_THRESHOLD_PCT,
            "unit": "IOPS",
        },
        {
            "name": "WriteIOPS",
            "namespace": "AWS/RDS",
            "stat": "Average",
            "threshold_pct": IOPS_SPIKE_THRESHOLD_PCT,
            "unit": "IOPS",
        },
        {
            "name": "CPUUtilization",
            "namespace": "AWS/RDS",
            "stat": "Average",
            "threshold_pct": 30.0,  # Alert if CPU spikes 30% above baseline
            "unit": "percent",
        },
    ]

    for metric in metrics_to_check:
        response = cw_client.get_metric_statistics(
            Namespace=metric["namespace"],
            MetricName=metric["name"],
            Dimensions=[{"Name": "DBInstanceIdentifier", "Value": instance_id}],
            StartTime=now - timedelta(hours=baseline_hours),
            EndTime=now,
            Period=3600,  # 1-hour granularity
            Statistics=[metric["stat"]],
        )

        if not response["Datapoints"]:
            continue

        datapoints = sorted(response["Datapoints"], key=lambda x: x["Timestamp"])
        recent_values = [dp[metric["stat"]] for dp in datapoints[-period_hours:]]
        baseline_values = [dp[metric["stat"]] for dp in datapoints[:-period_hours]]

        if not recent_values or not baseline_values:
            continue

        recent_avg = statistics.mean(recent_values)
        baseline_avg = statistics.mean(baseline_values)

        if baseline_avg == 0:
            continue

        deviation_pct = (recent_avg - baseline_avg) / baseline_avg * 100
        threshold = metric.get("threshold_pct", (metric.get("threshold_multiplier", 1.5) - 1) * 100)

        if deviation_pct > threshold:
            anomalies.append({
                "metric": metric["name"],
                "recent_avg": round(recent_avg, 2),
                "baseline_avg": round(baseline_avg, 2),
                "deviation_pct": round(deviation_pct, 1),
                "unit": metric["unit"],
            })

    return anomalies


def get_expensive_queries(conn) -> list:
    """
    Queries Query Store for queries with mean execution time
    above the configured threshold, which directly maps to I/O cost.
    Read-only — no state is reset here.
    """
    query = """
        SELECT TOP 10
            LEFT(qt.query_sql_text, 120)              AS query_snippet,
            SUM(rs.count_executions)                  AS calls,
            ROUND(AVG(rs.avg_duration) / 1000.0, 2)   AS mean_ms,
            ROUND(SUM(rs.avg_duration
                      * rs.count_executions) / 1000000.0, 2) AS total_sec,
            ROUND(CAST(SUM(rs.avg_rowcount * rs.count_executions) AS FLOAT)
                  / NULLIF(SUM(rs.count_executions), 0), 1) AS rows_per_call,
            ROUND(CAST(SUM(rs.avg_logical_io_reads * rs.count_executions) AS FLOAT)
                  / NULLIF(SUM(rs.count_executions), 0), 0) AS logical_reads_per_call
        FROM sys.query_store_query q
        JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
        JOIN sys.query_store_plan pl       ON pl.query_id = q.query_id
        JOIN sys.query_store_runtime_stats rs ON rs.plan_id = pl.plan_id
        WHERE rs.last_execution_time >= DATEADD(DAY, -1, SYSDATETIME())
        GROUP BY qt.query_sql_text
        HAVING AVG(rs.avg_duration) / 1000.0 > ?
           AND SUM(rs.count_executions) > 50
        ORDER BY SUM(rs.avg_duration * rs.count_executions) DESC;
    """
    cur = conn.cursor()
    cur.execute(query, (QUERY_COST_THRESHOLD_MS,))
    cols = [d[0] for d in cur.description]
    return [dict(zip(cols, row)) for row in cur.fetchall()]


def format_slack_alert(cost_data: dict, cw_anomalies: list, query_data: list) -> dict:
    """Formats a structured Slack message with all anomaly findings."""
    blocks = [
        {
            "type": "header",
            "text": {
                "type": "plain_text",

def post_to_slack(payload: dict) -> None:
    """Posts the formatted alert to Slack via webhook."""
    if not SLACK_WEBHOOK:
        print("SLACK_WEBHOOK_URL not set — printing alert to stdout.")
        print(json.dumps(payload, indent=2))
        return

    response = requests.post(
        SLACK_WEBHOOK,
        json=payload,
        headers={"Content-Type": "application/json"},
        timeout=10,
    )
    if response.status_code != 200:
        raise RuntimeError(f"Slack webhook failed: {response.status_code} {response.text}")

    """Entry point for AWS Lambda. Also callable directly for local testing."""

    try:
        conn = pyodbc.connect(build_conn_str(), autocommit=True)
        expensive_queries = get_expensive_queries(conn)

    except pyodbc.Error as exc:

    return {
        "statusCode": 200,
        "body": json.dumps({"findings": [], "alerted": False}),

25.5 Query-Level Cost Attribution Using Query Store and sys.dm_exec_query_stats

Budget alerts tell you that money is leaving the account. Query-level attribution tells you exactly which SQL statement is responsible. This is where FinOps crosses back into DBA territory, and it is where database professionals have a decisive advantage over generic cloud cost teams.

On SQL Server (RDS, Azure SQL, Cloud SQL), Query Store is the primary instrument. The following query correlates execution statistics with an estimated I/O cost model. It does not produce exact dollar figures — those live in the billing feed — but it ranks queries by their share of total I/O load, which maps directly to IOPS spend on gp2/gp3/io1 volumes.

-- ============================================================
-- Azure SQL: Query Cost Attribution by Logical Reads
-- Covers: Azure SQL Database, SQL Managed Instance
-- Run in the context of the target database
-- ============================================================

SELECT TOP 20
    qs.execution_count,
    qs.total_logical_reads,
    ROUND(qs.total_logical_reads * 1.0 / qs.execution_count, 0)
                                        AS avg_logical_reads,
    qs.total_elapsed_time / 1000        AS total_elapsed_ms,
    ROUND(qs.total_elapsed_time * 1.0
        / qs.execution_count / 1000, 2) AS avg_elapsed_ms,
    qs.total_worker_time / 1000         AS total_cpu_ms,
    ROUND(qs.total_worker_time * 1.0
        / qs.execution_count / 1000, 2) AS avg_cpu_ms,
    qs.total_physical_reads,
    ROUND(qs.total_physical_reads * 1.0
        / qs.execution_count, 1)        AS avg_physical_reads,
    -- DTU cost proxy: logical reads / 1M * execution_count
    -- On a Business Critical 8 vCore (~$1,100/mo), each logical read costs roughly $0.0000004
    ROUND(qs.total_logical_reads * 1.0
        / 1e6 * 0.0004, 4)             AS est_cost_proxy_usd,
    qs.creation_time                    AS plan_compiled_at,
    DB_NAME(qt.dbid)                    AS database_name,
    qt.objectid,
    SUBSTRING(
        qt.text,
        (qs.statement_start_offset / 2) + 1,
        (CASE qs.statement_end_offset
            WHEN -1 THEN DATALENGTH(qt.text)
            ELSE qs.statement_end_offset
         END - qs.statement_start_offset) / 2 + 1
    )                                   AS query_text
FROM
    sys.dm_exec_query_stats AS qs
    CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS qt
WHERE
    qs.execution_count > 5
    AND qt.text NOT LIKE '%sys.dm_exec%'
ORDER BY
    qs.total_logical_reads DESC;

For GCP Cloud SQL for SQL Server, the Query Store query above works directly against the Cloud SQL instance. For analytical spillover, attribute cost by bytes scanned in your analytics platform's job history instead:

-- BigQuery: Cloud SQL for SQL Server cost attribution from the billing export
-- Replace 'your-project.billing_export.gcp_billing_export_v1_XXXXXX'
-- with your actual billing export table name
SELECT
    project.name                                     AS project_name,
    labels.value                                     AS team_label,
    sku.description                                  AS sku_description,
    COUNT(DISTINCT DATE(usage_start_time))            AS active_days,
    SUM(cost)                                        AS total_cost_usd,
    SUM(cost) / NULLIF(COUNT(DISTINCT DATE(usage_start_time)), 0)
                                                     AS avg_daily_cost_usd
FROM
    `your-project.billing_export.gcp_billing_export_v1_XXXXXX`,
    UNNEST(labels) AS labels
WHERE
    service.description = 'Cloud SQL'
    AND labels.key = 'team'
    AND usage_start_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
GROUP BY
    project_name,
    team_label,
    sku_description
ORDER BY
    total_cost_usd DESC
LIMIT 30;

These three queries together cover the full multi-cloud estate. The pattern is consistent: find the queries consuming the most I/O or bytes processed, calculate their share of total load, and prioritize optimization work accordingly. A single query responsible for 35% of instance I/O that can be rewritten to use an index represents not just a performance win but a direct reduction in IOPS charges — particularly significant on io1 volumes at $0.065/GB-month compared to gp3 at $0.02/GB-month.

25.6 Automating Alert Response and Cost Runbook Execution

Receiving an alert is only half the system. The other half is what happens next. Organizations that automate initial triage steps — not full remediation, but data collection and scoping — reduce mean time to resolution by 60–70% compared to teams that start each incident by manually pulling metrics.

The following approach wires an SNS topic (populated by budget alerts and anomaly detection) to a Lambda function that executes a structured response runbook: it identifies the top cost drivers, snapshots current CloudWatch metrics, estimates the dollar impact, and posts a pre-filled incident ticket summary to Slack. A human still makes the remediation decision, but they receive a briefing rather than a blank screen.

#!/usr/bin/env python3
"""
cost_alert_responder.py
SNS-triggered Lambda that executes an automated cost incident runbook.
Triggered by: AWS Budget alerts, Cost Anomaly Detection, or CloudWatch alarms.
Posts a structured incident brief to Slack with recommended actions.
"""

import json
import os
import urllib.request
from datetime import datetime, timedelta, timezone

import boto3

SLACK_WEBHOOK = os.environ["SLACK_WEBHOOK_URL"]
REGION = os.environ.get("AWS_DEFAULT_REGION", "us-east-1")

# Pre-defined remediation playbooks keyed by anomaly type
PLAYBOOKS = {
    "storage_spike": {
        "title": "Unexpected Storage Growth",
        "likely_causes": [
            "Uncontrolled transaction log growth / backup accumulation",
            "Forgotten large table without TTL or partition pruning",
            "Snapshot retention policy changed or missing",
        ],
        "immediate_actions": [
            "Check RDS storage metrics in CloudWatch (FreeStorageSpace)",
            "Query sys.master_files and file sizes for growth",
            "Review automated backup retention period (target: 7 days for prod)",
            "Identify largest tables: SELECT TOP 20 OBJECT_SCHEMA_NAME(object_id), OBJECT_NAME(object_id) FROM sys.tables ORDER BY (SELECT SUM(reserved_page_count) FROM sys.dm_db_partition_stats WHERE object_id = t.object_id) DESC;",
        ],
        "automation_available": True,
        "runbook_url": "https://wiki.internal/runbooks/rds-storage-spike",
    },
    "iops_spike": {
        "title": "IOPS Spike Detected",
        "likely_causes": [
            "New or changed query missing an index",
            "Index rebuild / reorg running on large table",
            "Bulk insert / ETL job without rate limiting",
            "gp2 IOPS burst bucket depleted",
        ],
        "immediate_actions": [
            "Pull Query Store top resource consumers sorted by logical reads",
            "Check sys.dm_exec_requests for long-running queries",
            "Verify maintenance window scheduling for large tables",
            "If on gp2: evaluate migration to gp3 (3,000 baseline IOPS free)",
        ],
        "automation_available": True,
        "runbook_url": "https://wiki.internal/runbooks/rds-iops-spike",
    },
    "connection_spike": {
        "title": "Connection Count Anomaly",
        "likely_causes": [
            "Application connection pool misconfigured after deploy",
            "Client-side pooling misconfigured (Max Pool Size / connection string sprawl)",
            "Connection leak in application code",
            "Sudden traffic spike without connection pool scaling",
        ],
        "immediate_actions": [
            "SELECT status, wait_type, COUNT(*) FROM sys.dm_exec_requests GROUP BY status, wait_type;",
            "Check sys.dm_exec_sessions for idle session counts per host/program;",
            "Verify user connections against max worker threads (sys.dm_os_sys_info)",
            "Consider client-side pooling fixes before upsizing (see Chapter 20)",
        ],
        "automation_available": False,
        "runbook_url": "https://wiki.internal/runbooks/rds-connection-spike",
    },
    "cost_budget_breach": {
        "title": "Budget Threshold Breached",
        "likely_causes": [
            "Instance class upsized without cost review",
            "Read replica added without budget approval",
            "Multi-AZ enabled on non-production instance",
            "Reserved Instance expired and not renewed",
        ],
        "immediate_actions": [
            "Review Cost Explorer by usage type (InstanceUsage vs StorageUsage vs DataTransfer)",
            "Check for untagged resources: aws resourcegroupstaggingapi get-resources --resource-type-filters rds",
            "Verify RI coverage report for RDS in Cost Explorer",
            "Check for idle instances: CPU < 5% for 7+ days via Compute Optimizer",
        ],
        "automation_available": False,
        "runbook_url": "https://wiki.internal/runbooks/rds-budget-breach",
    },
}


def classify_alert(sns_message: dict) -> str:
    """
    Classifies the incoming alert type based on SNS message content.
    Returns a key matching the PLAYBOOKS dictionary.
    """
    message_str = json.dumps(sns_message).lower()

    if any(term in message_str for term in ["storage", "freestorage", "disk"]):
        return "storage_spike"
    if any(term in message_str for term in ["iops", "readiops", "writeiops", "throughput"]):
        return "iops_spike"
    if any(term in message_str for term in ["connection", "databaseconnections"]):
        return "connection_spike"
    if any(term in message_str for term in ["budget", "anomaly", "threshold", "cost"]):
        return "cost_budget_breach"

    return "cost_budget_breach"  # Default fallback


def get_rds_cost_breakdown(ce_client) -> list:
    """
    Pulls a 7-day RDS cost breakdown by usage type.
    Identifies whether the spike is compute, storage, I/O, or data transfer.
    """
    end = datetime.now(timezone.utc).date()
    start = end - timedelta(days=7)

    response = ce_client.get_cost_and_usage(
        TimePeriod={"Start": start.isoformat(), "End": end.isoformat()},
        Granularity="DAILY",
        Filter={
            "Dimensions": {
                "Key": "SERVICE",
                "Values": ["Amazon Relational Database Service"],
            }
        },
        GroupBy=[{"Type": "DIMENSION", "Key": "USAGE_TYPE"}],
        Metrics=["UnblendedCost"],
    )

    usage_totals = {}
    for day in response["ResultsByTime"]:
        for group in day["Groups"]:
            usage_type = group["Keys"][0]
            cost = float(group["Metrics"]["UnblendedCost"]["Amount"])
            usage_totals[usage_type] = usage_totals.get(usage_type, 0.0) + cost

    # Return sorted by cost descending, top 8 usage types
    sorted_usage = sorted(usage_totals.items(), key=lambda x: x[1], reverse=True)[:8]
    return [{"usage_type": k, "cost_usd": round(v, 2)} for k, v in sorted_usage]


def format_incident_brief(alert_type: str, cost_breakdown: list, sns_message: dict) -> dict:
    """Builds a Slack message with the full incident brief."""
    playbook = PLAYBOOKS[alert_type]
    timestamp = datetime.now(timezone.utc).strftime("%Y-%m-%d %H:%M UTC")

    causes_text = "\n".join([f"  • {c}" for c in playbook["likely_causes"]])
    actions_text = "\n".join([f"  {i+1}. {a}" for i, a in enumerate(playbook["immediate_actions"])])

    cost_lines = "\n".join([
        f"  • `{item['usage_type']}`: ${item['cost_usd']}"
        for item in cost_breakdown[:5]
    ])

    return {
        "blocks": [
            {
                "type": "header",
                "text": {
                    "type": "plain_text",
                    "text": f"📋 Cost Incident Brief: {playbook['title']}",
                },
            },
            {
                "type": "section",
                "fields": [
                    {"type": "mrkdwn", "text": f"*Detected:*\n{timestamp}"},
                    {"type": "mrkdwn", "text": f"*Category:*\n{alert_type.replace('_', ' ').title()}"},
                    {"type": "mrkdwn", "text": f"*Automation Available:*\n{'✅ Yes' if playbook['automation_available'] else '🔴 Manual'}"},
                    {"type": "mrkdwn", "text": f"*Runbook:*\n<{playbook['runbook_url']}|Open Runbook>"},
                ],
            },
            {
                "type": "section",
                "text": {
                    "type": "mrkdwn",
                    "text": f"*7-Day RDS Cost by Usage Type:*\n{cost_lines}",
                },
            },
            {
                "type": "section",
                "text": {
                    "type": "mrkdwn",
                    "text": f"*Likely Causes:*\n{causes_text}",
                },
            },
            {
                "type": "section",
                "text": {
                    "type": "mrkdwn",
                    "text": f"*Immediate Actions:*\n{actions_text}",
                },
            },
            {"type": "divider"},
            {
                "type": "context",
                "elements": [
                    {
                        "type": "mrkdwn",
                        "text": "This brief was generated automatically. "
                                "Escalate to on-call DBA if spend is not explained within 2 hours.",
                    }
                ],
            },
        ]
    }


def lambda_handler(event, context):
    """Entry point. Processes SNS records from budget/anomaly alerts."""
    ce_client = boto3.client("ce", region_name="us-east-1")

    for record in event.get("Records", []):
        if record.get("EventSource") != "aws:sns":
            continue

        try:
            sns_message = json.loads(record["Sns"]["Message"])
        except (json.JSONDecodeError, KeyError):
            sns_message = {"raw": record["Sns"].get("Message", "")}

        alert_type = classify_alert(sns_message)
        cost_breakdown = get_rds_cost_breakdown(ce_client)
        payload = format_incident_brief(alert_type, cost_breakdown, sns_message)

        req = urllib.request.Request(
            SLACK_WEBHOOK,
            data=json.dumps(payload).encode("utf-8"),
            headers={"Content-Type": "application/json"},
            method="POST",
        )
        with urllib.request.urlopen(req, timeout=10) as resp:
            if resp.status != 200:
                raise RuntimeError(f"Slack post failed with status {resp.status}")

        print(f"Incident brief posted for alert type: {alert_type}")

    return {"statusCode": 200, "body": "Runbook executed"}

Wire this Lambda to the same SNS topic used in the budget alert setup in section 25.2. Every alert — whether from a budget threshold, Cost Anomaly Detection, or a CloudWatch alarm — will now trigger both a human notification and an automated briefing with context, cost breakdown, and ranked remediation steps.

The dollar value of this automation is found in response time. An on-call DBA receiving a structured briefing at 2:00 AM can scope and begin resolving a cost incident in 15 minutes rather than 45. At an average RDS cost of $3–$8 per instance-hour for db.r6g.2xlarge, a 30-minute reduction in detection-to-action time on a 5-instance fleet saves $7.50–$20 per incident. More significantly, the incidents where a runaway workload runs for 8 hours instead of 1 — the $300 mistake rather than the $35 mistake — become structurally harder to miss.

Key Takeaways

  • → **Layer alerts, do not rely on a single threshold.** Budget alerts catch absolute spend; anomaly detection catches deviation from baseline; CloudWatch alarms catch the resource signals that precede billing anomalies by 6–12 hours. All three layers working together reduce detection lag from days to hours.
  • → **Tune anomaly detection thresholds after 30 days of data.** The default AWS Cost Anomaly Detection thresholds and the custom Python script's percentage values are starting points. Review the anomaly history, count false positives and missed events, and recalibrate. A threshold set too low creates alert fatigue that causes engineers to ignore real incidents.
  • → **Query-level attribution is where billing data meets database expertise.** Query Store and `sys.dm_exec_query_stats` translate abstract cost spikes into specific SQL statements. The DBA who can deliver a root-cause query within 30 minutes of an alert firing is providing $10,000-equivalent value compared to a team that spends two days correlating metrics manually.
  • → **Automate the triage brief, not the remediation.** Automated remediation of cost anomalies risks making systems worse — killing a query that was intentional, scaling down an instance during a legitimate traffic spike. The safe automation boundary is data collection, classification, and briefing. Let humans make the remediation call but give them everything they need to make it in under 10 minutes.
  • → **GCP's BigQuery billing export is the most flexible cost data source across all three clouds.** Enabling it costs nothing beyond storage and unlocks SQL-based anomaly detection, custom dashboards, and cross-project cost attribution that neither native GCP alerts nor the console can match. If your organization uses GCP, activating the billing export to BigQuery should be the first step in any FinOps program — before configuring a single budget alert.
