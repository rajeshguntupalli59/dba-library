Chapter 7: Right-Sizing Instances: The Methodology

Organizations running cloud databases consistently overpay by 30–40% on compute alone. The root cause is almost always the same: instances were sized for peak load at launch, workloads evolved, and nobody went back to revisit the original choices. A single db.r6g.4xlarge on AWS RDS running at 12% average CPU costs roughly $700.80/month on-demand. Downsizing to db.r6g.xlarge with a one-year Reserved Instance brings that to $108.62/month — a saving of $592.18 per month, per instance, without touching a line of application code. This chapter gives you the complete methodology: how to collect the right metrics, how to analyze them without being fooled by outliers, how to build the business case, and how to automate the entire process so right-sizing becomes a continuous operational discipline rather than a quarterly fire drill.

---

7.1 Why Instances Stay Oversized (And Why That's Not Stupidity)

Before reaching for the resize button, it is worth understanding why oversizing is so persistent. The forces that created it are rational, even if the outcome is wasteful.

The provisioning bias. When a database is first deployed, the team responsible for it has no production workload data. They extrapolate from development benchmarks, add a safety margin, round up to the next instance tier, and ship. This is not negligence — it is risk management under uncertainty. The problem is that the uncertainty resolves after go-live, but the safety margin never gets reclaimed.

The fear of the resize operation. On AWS RDS, resizing a Multi-AZ instance causes a failover. On Azure SQL, changing a service tier can trigger minutes of reduced connectivity. These are real concerns, especially for teams that have been burned by a botched maintenance window. The organizational response is to defer the operation indefinitely.

Ownership fragmentation. The DBA knows the CPU numbers. The finance team sees the invoice. The application team owns the deployment pipeline. Nobody owns the intersection of all three. FinOps as a discipline exists precisely to close this gap.

The right-sizing window. Practical experience shows that the best time to right-size is 8–12 weeks after a workload goes live. By then, you have enough data to identify true peak patterns but the team is still close enough to the original architecture to make confident changes. If that window passes, the next best opportunity is a quarterly review cycle anchored to billing data.

7.2 Collecting the Right Metrics

Right-sizing decisions made on CPU alone are dangerous. A database can run at 8% CPU while holding 95% of its RAM in buffer pool — shrink the instance and you blow the cache, triggering a cascade of disk I/O that destroys query latency. Collect all four dimensions before drawing any conclusions.

The four dimensions:

| Dimension | What to Measure | Safe Threshold for Downsizing |

|---|---|---|

| CPU | Average and P95 utilization | P95 < 40%, average < 20% |

| Memory | Buffer pool hit ratio, freeable memory | Freeable memory consistently > 20% of total |

| I/O | Read/write IOPS, throughput MB/s | Sustained utilization < 50% of provisioned |

| Connections | Active vs. max connections | Peak active < 40% of max\_connections |

Collecting from AWS CloudWatch

The following script pulls 30 days of RDS metrics for a given instance and outputs a summary. Schedule this with EventBridge to run on the first of every month.

#!/bin/bash
# collect_rds_metrics.sh
# Usage: ./collect_rds_metrics.sh <db-instance-identifier> <region>
# Schedule: AWS EventBridge, 1st of each month, 06:00 UTC

DB_INSTANCE="${1:-mydb-prod}"
REGION="${2:-us-east-1}"
END_DATE=$(date -u +"%Y-%m-%dT%H:%M:%SZ")
START_DATE=$(date -u -d "30 days ago" +"%Y-%m-%dT%H:%M:%SZ")

echo "=== RDS Right-Sizing Report: $DB_INSTANCE ==="
echo "Period: $START_DATE to $END_DATE"
echo ""

# CPU Utilization - Average and P95
echo "--- CPU Utilization ---"
aws cloudwatch get-metric-statistics \
  --region "$REGION" \
  --namespace AWS/RDS \
  --metric-name CPUUtilization \
  --dimensions Name=DBInstanceIdentifier,Value="$DB_INSTANCE" \
  --start-time "$START_DATE" \
  --end-time "$END_DATE" \
  --period 86400 \
  --statistics Average Maximum \
  --output table

# Freeable Memory (bytes)
echo ""
echo "--- Freeable Memory (GB) ---"
aws cloudwatch get-metric-statistics \
  --region "$REGION" \
  --namespace AWS/RDS \
  --metric-name FreeableMemory \
  --dimensions Name=DBInstanceIdentifier,Value="$DB_INSTANCE" \
  --start-time "$START_DATE" \
  --end-time "$END_DATE" \
  --period 86400 \
  --statistics Average Minimum \
  --query 'Datapoints[*].{Date:Timestamp,AvgGB:to_number(Average)/1073741824,MinGB:to_number(Minimum)/1073741824}' \
  --output table

# Database Connections
echo ""
echo "--- Database Connections ---"
aws cloudwatch get-metric-statistics \

# Read/Write IOPS

  --start-time "$START_DATE" \

Querying workload behavior from inside SQL Server

CloudWatch tells you about resource consumption. sys.dm_exec_query_stats tells you *why*. These two sources must be read together. A database showing 15% CPU might have one query consuming 14% of it — downsize the instance and that query becomes a latency problem.

Top queries and memory pressure on RDS for SQL Server or Azure SQL

-- SQL Server: top queries by CPU consumption (last execution plan cache)
-- Run on RDS SQL Server or Azure SQL Database
SELECT TOP 20
    qs.total_worker_time / 1000000.0               AS total_cpu_sec,
    qs.execution_count,
    qs.total_worker_time / qs.execution_count / 1000.0
                                                    AS avg_cpu_ms,
    qs.total_elapsed_time / qs.execution_count / 1000.0
                                                    AS avg_elapsed_ms,
    qs.total_logical_reads / qs.execution_count     AS avg_logical_reads,
    SUBSTRING(
        qt.text,
        (qs.statement_start_offset / 2) + 1,
        ((CASE qs.statement_end_offset
            WHEN -1 THEN DATALENGTH(qt.text)
            ELSE qs.statement_end_offset
          END - qs.statement_start_offset) / 2) + 1
    )                                               AS query_text
FROM
    sys.dm_exec_query_stats AS qs
    CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS qt
ORDER BY
    qs.total_worker_time DESC;

-- Memory pressure: page life expectancy
-- PLE < 300 seconds is a warning; < 100 seconds means the buffer pool is too small
SELECT
    object_name,
    counter_name,
    cntr_value AS page_life_expectancy_seconds
FROM
    sys.dm_os_performance_counters
WHERE
    counter_name = 'Page life expectancy'
    AND object_name LIKE '%Buffer Manager%';

7.3 Reading the Data Without Being Fooled

Raw metric averages mislead. A database that runs at 5% CPU for 23 hours and 95% CPU for one hour shows an average of 8.75% — and that one-hour burst is your month-end payroll batch or your nightly ETL. Right-size to remove that headroom and you break payroll.

The three-tier analysis framework

The three tiers answer different questions: P50 sets the sizing floor you never go below, P95 defines the ceiling your instance must sustain, and P99 captures bursts. The Schedulable diamond is the key decision — periodic bursts get offloaded to a read replica or scheduled scaling (green), while unpredictable bursts mean you keep true headroom in the primary (gray). Conflating the tiers is how teams end up both oversized and slow.

Tier 1 — Baseline: What does the instance look like during normal business hours on a typical weekday? Use the 50th percentile (median) across a 30-day window. This is the floor for sizing.

Tier 2 — Sustained peak: What is the P95 over the same window? This is the target utilization ceiling. If P95 CPU is 35%, the instance should be sized so that 35% CPU represents roughly 70% of its actual capacity, leaving a 2× headroom buffer.

Tier 3 — Burst events: What is the P99 or absolute maximum? These are the events that would cause customer-facing impact if the instance were undersized. Identify whether they are periodic and schedulable (ETL jobs, month-end reports) or unpredictable (traffic spikes from marketing campaigns). Periodic bursts can be handled with scheduled scaling or by moving those jobs to a read replica. Unpredictable bursts require true headroom in the primary.

The headroom formula

Required vCPUs = ceil(P95_CPU_utilization_pct / 0.70 × current_vCPUs)
Required RAM   = ceil(working_set_GB / 0.75)

Where working_set_GB is estimated as: total_database_size_GB × active_data_ratio. The active data ratio is typically 0.15–0.30 for OLTP workloads (only a fraction of tables are hot at any given time). If your buffer cache hit ratio is above 99%, your working set already fits in RAM. If it is between 95% and 99%, you are cache-constrained and should not reduce memory even if the instance appears to have freeable memory — freeable memory in RDS often reflects OS-level cache that SQL Server will use immediately under load.

Instance family selection

AWS RDS for SQL Server offers multiple instance families (note: SQL Server cannot run on Graviton/ARM classes, so the eligible families are Intel/AMD-based), and the price difference between them is substantial. Relative costs below are illustrative license-included ratios — verify current prices in the AWS pricing calculator:

| Family | vCPU:RAM Ratio | Best For | Example (4 vCPU) | On-Demand/mo |

|---|---|---|---|---|

| db.t3 | 1:2 (burstable) | Dev/test, low-traffic | db.t3.xlarge | lowest |

| db.m6i | 1:4 (general) | Balanced OLTP | db.m6i.xlarge | ~2.4x t3 |

| db.r6i | 1:8 (memory) | Large buffer pools | db.r6i.xlarge | ~3.6x t3 |

| db.x2iedn | 1:16 (memory) | In-memory analytics | db.x2iedn.xlarge | ~8x t3 |

Moving a workload from db.r6i.2xlarge to db.m6i.2xlarge saves roughly a third of the instance cost if the workload is CPU-bound rather than memory-bound — and that saving compounds over a one- or three-year reserved term.

7.4 Building the Right-Sizing Recommendation Engine

Manual monthly reviews do not scale across a portfolio of dozens of databases. The following Python script connects to AWS Cost Explorer and CloudWatch, pulls 30 days of data for all RDS instances in an account, applies the headroom formula, and outputs a prioritized recommendation report with estimated monthly savings. Run it on a schedule using AWS Lambda or a cron job.

#!/usr/bin/env python3
"""
rds_rightsizing_advisor.py

Automated right-sizing recommendations for AWS RDS instances.
Pulls 30 days of CloudWatch metrics, applies headroom formula,
and cross-references current instance pricing.

Requirements: boto3, pandas
Schedule: AWS Lambda (EventBridge trigger, 1st of month) or cron

Usage:
    python rds_rightsizing_advisor.py --region us-east-1 --output recommendations.csv
"""

import argparse
import json
import math
from datetime import datetime, timedelta, timezone
from typing import Optional

import boto3
import pandas as pd

# ---------------------------------------------------------------------------
# Instance pricing map: RDS for SQL Server, Standard edition, license-included,
# on-demand, us-east-1, single-AZ, USD/hour.
# NOTE: SQL Server cannot run on Graviton (t4g/m7g/r7g) classes — only Intel/AMD.
# Rates below are ILLUSTRATIVE. Replace with current rates from the
# AWS RDS for SQL Server pricing page before relying on the output.
# ---------------------------------------------------------------------------
RDS_PRICING = {
    "db.t3.micro":     0.12,   "db.t3.small":     0.24,
    "db.t3.medium":    0.48,   "db.t3.large":     0.96,
    "db.t3.xlarge":    1.92,   "db.t3.2xlarge":   3.84,
    "db.m6i.large":    1.15,   "db.m6i.xlarge":   2.30,
    "db.m6i.2xlarge":  4.60,   "db.m6i.4xlarge":  9.20,
    "db.m6i.8xlarge":  18.40,  "db.m6i.12xlarge": 27.60,
    "db.r6i.large":    1.60,   "db.r6i.xlarge":   3.20,
    "db.r6i.2xlarge":  6.40,   "db.r6i.4xlarge":  12.80,
    "db.r6i.8xlarge":  25.60,  "db.r6i.12xlarge": 38.40,
}

# Instance specs: vCPUs and RAM (GB)
INSTANCE_SPECS = {
    "db.t3.micro":     (2,  1),   "db.t3.small":     (2,  2),
    "db.t3.medium":    (2,  4),   "db.t3.large":     (2,  8),
    "db.t3.xlarge":    (4,  16),  "db.t3.2xlarge":   (8,  32),
    "db.m6i.large":    (2,  8),   "db.m6i.xlarge":   (4,  16),
    "db.m6i.2xlarge":  (8,  32),  "db.m6i.4xlarge":  (16, 64),
    "db.m6i.8xlarge":  (32, 128), "db.m6i.12xlarge": (48, 192),
    "db.r6i.large":    (2,  16),  "db.r6i.xlarge":   (4,  32),
    "db.r6i.2xlarge":  (8,  64),  "db.r6i.4xlarge":  (16, 128),
    "db.r6i.8xlarge":  (32, 256), "db.r6i.12xlarge": (48, 384),
}

HOURS_PER_MONTH = 730
LOOKBACK_DAYS   = 30
CPU_HEADROOM    = 0.70   # target: P95 CPU uses no more than 70% of capacity
MEM_HEADROOM    = 0.75   # target: working set uses no more than 75% of RAM


def get_metric_statistics(
    cw_client,
    instance_id: str,
    metric_name: str,
    stat: str,
    period: int = 3600,
) -> list[float]:
    """Fetch hourly metric values for a given RDS instance over LOOKBACK_DAYS."""
    end   = datetime.now(timezone.utc)
    start = end - timedelta(days=LOOKBACK_DAYS)

    response = cw_client.get_metric_statistics(
        Namespace="AWS/RDS",
        MetricName=metric_name,
        Dimensions=[{"Name": "DBInstanceIdentifier", "Value": instance_id}],
        StartTime=start,
        EndTime=end,
        Period=period,
        Statistics=[stat],
    )
    return [dp[stat] for dp in response.get("Datapoints", [])]


def percentile(values: list[float], pct: float) -> float:
    if not values:
        return 0.0
    sorted_vals = sorted(values)
    idx = int(math.ceil(pct / 100.0 * len(sorted_vals))) - 1
    return sorted_vals[max(idx, 0)]


def recommend_instance(
    current_class: str,
    p95_cpu: float,
    min_freeable_gb: float,
    family_preference: str = "same",
) -> Optional[str]:
    """
    Return the smallest instance that satisfies the headroom constraints,
    or None if the current instance is already right-sized.
    """
    if current_class not in INSTANCE_SPECS:
        return None

    current_vcpu, current_ram = INSTANCE_SPECS[current_class]

    # Determine required capacity
    required_vcpu = math.ceil(p95_cpu / 100.0 / CPU_HEADROOM * current_vcpu)
    required_vcpu = max(required_vcpu, 2)  # floor at 2 vCPU

    # Estimate working set from freeable memory
    # freeable = RAM not used by buffer pool; working set ≈ RAM - freeable
    working_set_gb = max(current_ram - min_freeable_gb, 4)
    required_ram   = math.ceil(working_set_gb / MEM_HEADROOM)

    # Find candidate instances smaller than current that meet requirements
    current_price = RDS_PRICING.get(current_class, 0)
    best_candidate = None
    best_price     = current_price

    for inst, (vcpu, ram) in INSTANCE_SPECS.items():
        price = RDS_PRICING.get(inst, 0)
        if price >= current_price:
            continue  # not cheaper, skip
        if vcpu < required_vcpu:
            continue
        if ram < required_ram:
            continue
        if price < best_price:
            best_price     = price
            best_candidate = inst

    return best_candidate


def analyze_account(region: str) -> pd.DataFrame:
    rds = boto3.client("rds",        region_name=region)
    cw  = boto3.client("cloudwatch", region_name=region)

    paginator = rds.get_paginator("describe_db_instances")
    instances = []
    for page in paginator.paginate():
        instances.extend(page["DBInstances"])

    rows = []
    for db in instances:
        iid   = db["DBInstanceIdentifier"]
        itype = db["DBInstanceClass"]
        print(f"  Analyzing {iid} ({itype}) ...")

        cpu_values = get_metric_statistics(cw, iid, "CPUUtilization",  "Average")
        mem_values = get_metric_statistics(cw, iid, "FreeableMemory",  "Minimum")

        if not cpu_values:
            print(f"    No metrics found for {iid}, skipping.")
            continue

        avg_cpu    = sum(cpu_values) / len(cpu_values)
        p95_cpu    = percentile(cpu_values, 95)
        min_mem_gb = (min(mem_values) / 1_073_741_824) if mem_values else 0.0

        current_price   = RDS_PRICING.get(itype, 0)
        current_monthly = current_price * HOURS_PER_MONTH

        recommendation  = recommend_instance(itype, p95_cpu, min_mem_gb)
        rec_price       = RDS_PRICING.get(recommendation, current_price) if recommendation else current_price
        rec_monthly     = rec_price * HOURS_PER_MONTH
        monthly_saving  = current_monthly - rec_monthly

        rows.append({
            "instance_id":       iid,
            "current_class":     itype,
            "avg_cpu_pct":       round(avg_cpu, 1),
            "p95_cpu_pct":       round(p95_cpu, 1),
            "min_freeable_gb":   round(min_mem_gb, 1),
            "current_monthly":   round(current_monthly, 2),
            "recommended_class": recommendation or "no change",
            "rec_monthly":       round(rec_monthly, 2),
            "monthly_saving":    round(monthly_saving, 2),
            "annual_saving":     round(monthly_saving * 12, 2),
        })

    df = pd.DataFrame(rows).sort_values("monthly_saving", ascending=False)
    return df


def main():
    parser = argparse.ArgumentParser(description="RDS Right-Sizing Advisor")
    parser.add_argument("--region", default="us-east-1", help="AWS region")
    parser.add_argument("--output", default="recommendations.csv", help="Output CSV path")
    args = parser.parse_args()

    print(f"RDS Right-Sizing Advisor")
    print(f"Region: {args.region}")
    print(f"Lookback: {LOOKBACK_DAYS} days")
    print(f"{'='*60}")

    df = analyze_account(args.region)

    if df.empty:
        print("No instances with sufficient metric data found.")
        return

    # Summary
    total_current  = df["current_monthly"].sum()
    total_rec      = df["rec_monthly"].sum()
    total_saving   = df["monthly_saving"].sum()
    candidates     = df[df["monthly_saving"] > 0]

    print(f"\n{'='*60}")
    print(f"SUMMARY")
    print(f"{'='*60}")
    print(f"Total instances analyzed : {len(df)}")
    print(f"Instances with savings   : {len(candidates)}")
    print(f"Current monthly spend    : ${total_current:,.2f}")
    print(f"Optimized monthly spend  : ${total_rec:,.2f}")
    print(f"Monthly saving           : ${total_saving:,.2f}")
    print(f"Annual saving            : ${total_saving * 12:,.2f}")
    print(f"\nTop 10 opportunities:")
    print(
        candidates.head(10)[
            ["instance_id", "current_class", "p95_cpu_pct",
             "min_freeable_gb", "recommended_class", "monthly_saving"]
        ].to_string(index=False)
    )

    df.to_csv(args.output, index=False)
    print(f"\nFull report written to {args.output}")


if __name__ == "__main__":
    main()

Adapting the engine for Azure SQL

Azure SQL exposes equivalent metrics through Azure Monitor. The pattern is the same — pull DTU or vCore utilization, memory pressure, and connection counts — but the SDK and metric names differ.

# azure_sql_rightsizing.py (excerpt)
# Full script follows the same structure as the AWS version above.
# Requires: azure-mgmt-monitor, azure-mgmt-sql, azure-identity

from azure.identity import DefaultAzureCredential
from azure.mgmt.monitor import MonitorManagementClient
from azure.mgmt.sql import SqlManagementClient
from datetime import datetime, timedelta, timezone

LOOKBACK_DAYS = 30

def get_azure_sql_metrics(
    subscription_id: str,
    resource_group: str,
    server_name: str,
    database_name: str,
) -> dict:
    credential    = DefaultAzureCredential()
    monitor_client = MonitorManagementClient(credential, subscription_id)

    resource_uri = (
        f"/subscriptions/{subscription_id}/resourceGroups/{resource_group}"
        f"/providers/Microsoft.Sql/servers/{server_name}"
        f"/databases/{database_name}"
    )

    end   = datetime.now(timezone.utc)
    start = end - timedelta(days=LOOKBACK_DAYS)

    # Metrics available: cpu_percent, dtu_consumption_percent,
    # memory_usage_percent, connection_successful, storage_percent
    metrics_response = monitor_client.metrics.list(
        resource_uri=resource_uri,
        timespan=f"{start.isoformat()}/{end.isoformat()}",
        interval="PT1H",
        metricnames="cpu_percent,memory_usage_percent,connection_successful",
        aggregation="Average,Maximum",
    )

    result = {}
    for metric in metrics_response.value:
        values = []
        for ts in metric.timeseries:
            for dp in ts.data:
                if dp.average is not None:
                    values.append(dp.average)
        result[metric.name.value] = values

    return result

For Azure SQL, the right-sizing logic maps to service tier selection rather than instance class. The General Purpose tier offers 1:5.1 vCore-to-RAM ratio; Business Critical offers 1:5.1 with local SSD and higher IOPS. A workload running at low DTU consumption with modest storage throughput is a candidate for dropping from Business Critical to General Purpose, which typically reduces the compute cost by 40–50% for the same vCore count.

7.5 The Resize Operation: Executing Safely

Collecting recommendations is the easy part. Executing the resize without causing an incident requires a structured runbook.

Pre-resize checklist

1. Confirm the metric window covers at least one full business cycle. For most workloads that is four weeks. For quarterly-reporting businesses (finance, healthcare) it may be 13 weeks.

2. Check for scheduled jobs that run at non-business hours. Nightly ETL, weekly statistics updates, and monthly purges can all create CPU or I/O spikes that appear in P99 but are invisible in daily averages. Query the job scheduler directly.

```sql

```sql

-- SQL Server: list SQL Agent jobs and their last run duration

SELECT

j.name AS job_name,

ja.run_requested_date,

ja.stop_execution_date,

DATEDIFF(SECOND, ja.run_requested_date,

ja.stop_execution_date) AS duration_sec,

ja.last_executed_step_id

FROM

msdb.dbo.sysjobs AS j

JOIN msdb.dbo.sysjobactivity AS ja

ON j.job_id = ja.job_id

WHERE

ja.run_requested_date IS NOT NULL

ORDER BY

ja.run_requested_date DESC;

```

3. Take a manual snapshot before the resize. Even though RDS takes an automated snapshot at resize time, a manual snapshot with a descriptive name (pre-rightsize-2024-11-01) is faster to locate under pressure.

4. Notify stakeholders. A right-sizing operation on a Multi-AZ RDS instance triggers a failover, which causes roughly 30–60 seconds of interrupted connections. Application teams need to verify their connection retry logic handles this gracefully. If they do not have retry logic, the resize window becomes a deployment event, not just a DBA task.

5. Plan the rollback. Resizing back up is always possible but takes the same time as the original resize. Set a rollback decision deadline — typically 24 hours post-resize. If any key performance metric degrades beyond an agreed threshold within that window, resize back without debate.

Executing the resize on AWS RDS

# Step 1: Modify the instance class (change takes effect at next maintenance window

Post-resize validation queries

Run these in the first 15 minutes after the resize and again at the 24-hour mark.

-- SQL Server: post-resize health check
-- Confirm PLE has recovered and there is no memory pressure
SELECT
    'PLE'                                           AS metric,
    cntr_value                                      AS value,
    CASE
        WHEN cntr_value > 300  THEN 'OK'
        WHEN cntr_value > 100  THEN 'WARNING'
        ELSE 'CRITICAL'
    END                                             AS status
FROM
    sys.dm_os_performance_counters
WHERE
    counter_name = 'Page life expectancy'
    AND object_name LIKE '%Buffer Manager%'

UNION ALL

-- Confirm no runaway waits have appeared
SELECT TOP 10
    wait_type                                       AS metric,
    wait_time_ms                                    AS value,
    'CHECK'                                         AS status
FROM
    sys.dm_os_wait_stats
WHERE
    wait_type NOT IN (
        'SLEEP_TASK', 'BROKER_TO_FLUSH', 'BROKER_TASK_STOP',
        'CLR_AUTO_EVENT', 'DISPATCHER_QUEUE_SEMAPHORE',
        'FT_IFTS_SCHEDULER_IDLE_WAIT', 'HADR_WORK_QUEUE',

7.6 Handling Edge Cases

No methodology survives contact with a real production estate without encountering anomalies. The following cases are the most common.

The bursty dev/test instance that looks like prod

Development and test databases often have low average utilization but periodic spikes caused by CI/CD pipelines running integration tests. These spikes are real but they are not customer-facing. The right response is to move the instance to a db.t3 burstable family and let it accumulate CPU credits during idle periods to spend during test runs. For a db.m6i.xlarge running CI workloads, switching to db.t3.xlarge reduces cost by roughly a quarter with no performance degradation in practice.

The connection-saturated instance with low CPU

An instance at 8% CPU and 95% connection utilization is not oversized — it is under-pooled. Before recommending a downsize, check whether the application is using a connection pooler. On SQL Server, the standard answer is client-side connection pooling (ADO.NET / ODBC pooling, enabled by default in most drivers) plus right-sizing Max Pool Size per application tier. Fixing the pool configuration can reduce the effective connection count by 10x without changing the instance class, and it unblocks the downsize decision by removing the false constraint.

-- SQL Server: diagnose connection waste
-- "sleeping" sessions holding connections but doing no work
SELECT
    COUNT(*)                                            AS sleeping_sessions,
    MIN(DATEDIFF(SECOND, s.last_request_end_time, SYSDATETIME()))
                                                        AS shortest_idle_sec,
    MAX(DATEDIFF(SECOND, s.last_request_end_time, SYSDATETIME()))
                                                        AS longest_idle_sec,
    AVG(CAST(DATEDIFF(SECOND, s.last_request_end_time, SYSDATETIME()) AS FLOAT))
                                                        AS avg_idle_sec,
    s.program_name
FROM
    sys.dm_exec_sessions s
WHERE
    s.is_user_process = 1
    AND s.status = 'sleeping'
GROUP BY
    s.program_name
ORDER BY
    sleeping_sessions DESC;

The instance with high I/O and low CPU

This pattern indicates either a missing index causing full table scans, or a workload that is genuinely I/O-bound (large analytical queries, bulk exports). Before concluding the instance needs more I/O-optimized storage, check whether adding an index eliminates the scans.

-- SQL Server: missing index recommendations from the DMV
SELECT TOP 20
    migs.avg_total_user_cost *
    migs.avg_user_impact *
    (migs.user_seeks + migs.user_scans)             AS improvement_measure,
    mid.statement                                   AS table_name,
    mid.equality_columns,
    mid.inequality_columns,
    mid.included_columns,
    migs.user_seeks,
    migs.user_scans,
    round(migs.avg_total_user_cost, 2)              AS avg_query_cost,
    round(migs.avg_user_impact, 2)                  AS estimated_improvement_pct
FROM
    sys.dm_db_missing_index_group_stats AS migs
    JOIN sys.dm_db_missing_index_groups AS mig
        ON migs.group_handle = mig.index_group_handle
    JOIN sys.dm_db_missing_index_details AS mid
        ON mig.index_handle = mid.index_handle
ORDER BY
    improvement_measure DESC;

The read replica that mirrors primary sizing

Read replicas are frequently cloned from the primary at the same instance class and then left unchanged. Many analytical queries that drive a replica's load are selective and cache-friendly once the working set is established. Replicas are often candidates for smaller instance classes than the primary, or for a different family (memory-optimized for analytics vs. balanced for OLTP). Profile the replica independently — do not assume it needs the same resources as the primary.

7.7 Embedding Right-Sizing into the Operating Model

One-time right-sizing captures immediate savings but does not prevent the problem from recurring. The goal is a continuous process.

Monthly automated scan. The Python script from Section 7.4 should run on the first of every month and post results to a Slack channel or Teams webhook, tagged to the owning team. Visibility changes behavior — when teams see their instance in a "no change needed" status, they understand why. When they see it flagged, they have the data to act.

Tagging discipline. Every RDS instance should carry tags for environment (prod/staging/dev/test), owner (team or squad name), workload-type (oltp/analytics/reporting/batch), and rightsizing-reviewed (date of last review). The monthly scan should filter by environment=prod for immediate savings focus and log all others for weekly review.

Change freeze windows. Define a calendar of blackout periods when right-sizing operations cannot be executed — typically the last two weeks of a fiscal quarter, major product release dates, and the period around public holidays. The recommendation engine should flag instances as "eligible" or "frozen" based on this calendar.

Linking to Reserved Instance purchases. Right-sizing must precede RI commitments. An organization that buys a three-year RI for db.r6i.4xlarge and then discovers six months later that the workload fits on db.r6i.xlarge has locked in the savings of neither. The workflow should be:

1. Right-size the instance on-demand.

2. Observe for 30 days.

3. Purchase the RI at the right-sized tier.

This sequencing is easy to describe and often ignored under budget deadline pressure. Building it into the process as a gate — the RI purchase form requires a field for "last right-sizing review date" — enforces the discipline without relying on individual vigilance.

Feedback loop to architecture. Right-sizing data is valuable beyond cost optimization. An instance that cannot be downsized despite low utilization often reveals an architectural constraint: a schema with no partitioning that requires a full-table scan during purges, a connection count problem that points to missing pooling infrastructure, or a buffer cache sensitivity that signals data model inefficiency. Feed these findings back to the architecture review process. The right-sizing program pays for itself twice: once in direct savings, and once in the architectural improvements it surfaces.

Key Takeaways

  • → **Right-sizing requires four dimensions, not one.** CPU alone misleads. Collect P95 CPU, buffer cache hit ratio, minimum freeable memory, and peak connection count before making any resize decision. An instance with low CPU but a 99% buffer hit ratio will suffer a serious performance regression if its RAM is reduced.
  • → **The headroom formula prevents under-sizing.** Size the instance so that P95 CPU represents no more than 70% of its capacity, and so that the estimated working set occupies no more than 75% of available RAM. This 30% and 25% headroom absorbs legitimate burst traffic without requiring the instance to be oversized for average load.
  • → **Burst classification determines the right response.** Periodic, schedulable bursts (ETL, month-end reports) do not require headroom in the primary instance — they can be offloaded to a read replica or accommodated by temporary scaling. Unpredictable bursts require true headroom. Conflating the two leads to either chronic oversizing or preventable incidents.
  • → **Automate the scan, humanize the decision.** The recommendation engine in Section 7.4 can identify and quantify every right-sizing opportunity in an account in minutes. The actual resize decision still requires human review — checking the business calendar, validating the metric window, and confirming rollback readiness. Automation handles the tedious data collection; judgment handles the risk assessment.
  • → **Right-sizing must precede Reserved Instance purchases.** Committing to a three-year RI at the wrong instance class eliminates the flexibility to capture compute savings later. The correct sequence is: resize on-demand, observe for 30 days, then purchase the commitment. Building this sequence into the procurement workflow as a required step prevents the most common FinOps mistake in the database cost domain.
