Chapter 30: FinOps for AI Workloads on SQL Server

FinOps fundamentals — tagging, showback, budget alerts — are Book 7's subject. This chapter assumes you have them and focuses on what is genuinely new: the cost drivers that appear only when you run AI workloads on SQL Server. Vector index builds that burn a weekend of compute. Embedding API calls metered per token through sp_invoke_external_rest_endpoint. ML Services sessions consuming memory outside the buffer pool. A copilot whose per-question cost is invisible until the invoice arrives. Each of these is metered differently, attributed differently, and controlled differently — and if you do not instrument them deliberately, the first person to notice the spend will be finance, not you.

---

Mapping the AI Cost Surface

AI workloads on SQL Server create four distinct cost streams, and they land in different invoices. Compute for vector indexes: building and rebuilding DiskANN indexes over large embedding tables is CPU- and I/O-intensive, and on Azure SQL Database that is DTU/vCore time billed by the second. External model calls: every sp_invoke_external_rest_endpoint invocation that hits Azure OpenAI is metered per token on the Azure OpenAI side, plus the SQL compute spent waiting on the call. ML Services compute: in-database R and Python (Machine Learning Services) run in external processes with their own memory allocation — invisible in buffer pool metrics, very visible on the host. Copilot and agent traffic: LLM API spend driven by your Chapter 26 copilot, proportional to questions asked and tool-call rounds per question.

The first step is attribution: tag every AI workload so its consumption is separable. Set a distinct Application Name in the connection strings of your ingestion jobs, copilot services, and ML Services sessions. Query Store then attributes CPU, duration, and I/O per query, and you filter by program name. Without that tag, AI spend dissolves into the general workload and you are arguing about invoices with no data.

-- AI workload cost attribution: Query Store resource consumption by program
SELECT
    s.program_name,
    COUNT(DISTINCT qsq.query_id) AS distinct_queries,
    SUM(rs.count_executions) AS total_executions,
    SUM(rs.avg_cpu_time * rs.count_executions) / 1000000.0 AS total_cpu_seconds,
    SUM(rs.avg_duration * rs.count_executions) / 1000000.0 AS total_duration_seconds,
    SUM(rs.avg_logical_io_reads * rs.count_executions) / 1000.0 AS total_logical_reads_k,
    SUM(rs.avg_logical_io_writes * rs.count_executions) / 1000.0 AS total_logical_writes_k
FROM sys.query_store_query qsq
JOIN sys.query_store_plan qsp ON qsp.query_id = qsq.query_id
JOIN sys.query_store_runtime_stats rs ON rs.plan_id = qsp.plan_id
JOIN sys.query_store_runtime_stats_interval i
  ON i.runtime_stats_interval_id = rs.runtime_stats_interval_id
CROSS APPLY (
    SELECT TOP (1) s2.program_name
    FROM sys.dm_exec_query_stats qs
    JOIN sys.dm_exec_sessions s2 ON s2.session_id = qs.last_execution_time -- placeholder join
    WHERE 0 = 1
) s
WHERE i.start_time >= DATEADD(DAY, -30, GETUTCDATE())
GROUP BY s.program_name
ORDER BY total_cpu_seconds DESC;

In practice, join Query Store data against your own execution log instead of DMVs: have every AI job (embedding ingestion, vector index maintenance, copilot service) write its runs — start, end, rows processed, tokens consumed — to a dbo.ai_workload_runs table. Query Store gives you per-query compute; your runs table gives you per-job business context (tokens, documents, questions answered). Cost per embedding, cost per copilot answer, cost per index rebuild — those ratios are what you manage.

Vector Index Build and Maintenance Costs

Vector search is cheap at query time and expensive at build time. Creating a DiskANN index over a million-row embedding table is a heavyweight operation — sustained CPU, large sorts, significant transaction log generation — and every bulk reload of the knowledge base (Chapter 28's ingestion pipeline) that invalidates the index repeats it. On Azure SQL Database, that build time is metered vCore compute; on managed instances and RDS, it is IOPS and CPU that contend with production workload.

Three controls keep this cost bounded. First, incremental ingestion over bulk reload: hash source documents and embed only what changed (Chapter 28's pipeline already does this), so the index absorbs trickle inserts instead of full rebuilds. Second, schedule builds in low-cost windows: on serverless Azure SQL, auto-pause means an index build can wake the database and hold it awake — run maintenance during windows when the database is already active, or accept the wake cost explicitly. Third, measure build cost per run: capture CPU time and duration around index maintenance in your runs table, and alert when a build's cost deviates from its baseline — a sudden 3x build cost usually means the embedding table grew without anyone noticing.

-- Track vector index maintenance cost per run in dbo.ai_workload_runs
DECLARE @start_cpu BIGINT, @start_time DATETIME2;
SELECT @start_cpu = SUM(cpu_time) FROM sys.dm_exec_requests WHERE session_id = @@SPID;
SET @start_time = SYSUTCDATETIME();

-- ... vector index maintenance: CREATE VECTOR INDEX / rebuild ...

INSERT INTO dbo.ai_workload_runs
    (run_start, run_end, workload, operation, rows_processed,
     cpu_ms, duration_seconds, notes)
SELECT
    @start_time, SYSUTCDATETIME(), 'knowledge_base', 'vector_index_rebuild',
    (SELECT COUNT(*) FROM dbo.dba_knowledge_chunks),
    SUM(cpu_time) - @start_cpu,
    DATEDIFF(SECOND, @start_time, SYSUTCDATETIME()),
    'post-ingestion index maintenance'
FROM sys.dm_exec_requests WHERE session_id = @@SPID;

Metering Azure OpenAI Calls via sp_invoke_external_rest_endpoint

When SQL Server calls Azure OpenAI directly through sp_invoke_external_rest_endpoint — for embedding generation, classification, or summarization inside T-SQL — the cost has two components: the Azure OpenAI token metering on the model side, and the SQL compute burned while the session waits on the HTTP call. The token side is invisible to SQL Server; the wait side shows up as elapsed time with no CPU, which makes these calls look cheap in Query Store CPU reports while they hold sessions, workers, and (on Azure SQL) billable time.

Instrument both sides. On the SQL side, wrap every external call with timing and payload-size logging into dbo.ai_external_calls: endpoint, model, prompt tokens, completion tokens (returned in the response metadata), duration. On the Azure side, reconcile weekly against the Azure OpenAI usage metrics — the token counts in your log should match the metered usage within a few percent. Any gap is calls happening outside your logging, which is itself a finding.

-- Logged wrapper pattern for sp_invoke_external_rest_endpoint calls
DECLARE @payload NVARCHAR(MAX) = JSON_OBJECT(
    'input': @text_to_embed,
    'model': 'text-embedding-3-small');
DECLARE @t0 DATETIME2 = SYSUTCDATETIME();
DECLARE @response NVARCHAR(MAX);

EXEC @response = sp_invoke_external_rest_endpoint
    @url = 'https://my-openai.openai.azure.com/openai/deployments/embed/embeddings?api-version=2024-02-01',
    @method = 'POST',
    @credential = [https://my-openai.openai.azure.com],
    @payload = @payload;

-- Log: tokens from the response metadata, duration, payload size
INSERT INTO dbo.ai_external_calls
    (call_time, endpoint, model, prompt_chars,
     prompt_tokens, completion_tokens, duration_ms)
SELECT
    SYSUTCDATETIME(), 'embeddings', 'text-embedding-3-small',
    LEN(@payload),
    JSON_VALUE(@response, '$.usage.prompt_tokens'),
    JSON_VALUE(@response, '$.usage.completion_tokens'),
    DATEDIFF(MILLISECOND, @t0, SYSUTCDATETIME());

The cost controls for external calls are batching, caching, and model tiering. Batch embedding inputs to the API's maximum per-request limit instead of one call per row — Chapter 28's ingestion already batches, and the savings are roughly linear in batch size. Cache embeddings by content hash so re-ingestion never re-pays for unchanged text. And tier your models deliberately: text-embedding-3-small costs a fraction of the large variant and is sufficient for runbook retrieval; reserve expensive models for the copilot's reasoning calls where quality differences actually matter. A monthly review of dbo.ai_external_calls grouped by model and endpoint tells you exactly where the token budget goes.

ML Services Compute: The Invisible Spender

Machine Learning Services runs R and Python in external processes outside the SQL Server engine. That isolation is a feature for stability and a hazard for cost accounting: the memory and CPU consumed by sp_execute_external_script sessions do not appear in buffer pool or Query Store CPU metrics the way T-SQL does. On a boxed SQL Server, a runaway training job starves the engine of memory; on Azure, the external compute is part of what you are paying for in the vCore model.

Contain it with Resource Governor: create a dedicated workload group for external script sessions with REQUEST_MAX_MEMORY_GRANT_PERCENT and CPU caps, and classify ML Services logins into it. Then monitor sys.dm_external_script_requests and sys.dm_resource_governor_workload_groups for actual consumption versus the cap. The decision this data informs is architectural: training jobs that consistently hit the governor belong on a dedicated ML compute (Azure ML, a separate VM) with SQL Server holding only inference-time scoring — which is cheaper per run and stops training from contending with production queries.

Budgeting the Copilot: Cost per Answered Question

The Chapter 26 copilot's cost is fully variable: every question burns tokens on the initial prompt, every tool-call round burns more, and a curious user base asks a lot of questions. The metric that matters is cost per answered question, computed from the audit log: tokens consumed (log per-turn usage from the API response) divided by questions resolved. Track it weekly, segmented by question class — diagnostic questions that trigger three tool rounds cost 3–4x a simple lookup.

Three levers control it. Cap tool rounds (Chapter 26's max_tool_rounds) — each round is a full model call, so a cap of 4 versus 8 roughly halves worst-case cost. Cache ruthlessly: wait-stat snapshots and runbook excerpts change slowly, so cache tool results for minutes and retrieved excerpts for hours; repeated "is the server slow right now" questions should not re-run the world. Route by difficulty: answer simple lookups ("show me top waits") with a small fast model and reserve the large reasoning model for multi-tool diagnostic sessions. Set a monthly token budget with an alert at 80% — when it fires, the decision is explicit (raise the budget, tighten caps, or restrict access) instead of a surprise invoice.

---

Key Takeaways

  • → **AI workloads create four cost streams metered in different places.** Vector index compute, Azure OpenAI tokens via sp_invoke_external_rest_endpoint, ML Services external-process compute, and copilot LLM traffic — tag every one with a distinct Application Name so Query Store and your own runs table can attribute each.
  • → **Vector indexes are cheap to query and expensive to build.** Favor incremental ingestion over bulk reloads, schedule builds when the database is already active on serverless tiers, and alert when a build's CPU cost deviates from baseline.
  • → **Log every external model call with its token usage.** Wrap sp_invoke_external_rest_endpoint with timing and usage-metadata logging into dbo.ai_external_calls, reconcile weekly against Azure OpenAI metering, and cut costs through batching, content-hash caching, and deliberate model tiering.
  • → **Govern ML Services with Resource Governor.** External script sessions consume memory and CPU outside the engine's normal accounting — cap them in a dedicated workload group and move chronic training workloads to dedicated ML compute.
  • → **Manage the copilot on cost per answered question.** Cap tool rounds, cache tool results and runbook excerpts, route simple lookups to small models, and put a monthly token budget with an 80% alert in front of the invoice.
