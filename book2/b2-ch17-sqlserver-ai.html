Chapter 17: AI in the SQL Server Ecosystem

SQL Server's AI story is not a cloud-only story. Long before Azure SQL offered embedding generation and DiskANN indexes, the on-premises engine was already learning from your workload: Intelligent Query Processing feedback loops that adjust memory grants and parallelism from one execution to the next, in-database R and Python through Machine Learning Services, and native ONNX model scoring with the PREDICT function. Chapter 15 covered the Azure SQL side of the AI picture — vector search, external models, and REST-based enrichment. This chapter covers the other half: the AI capabilities that live inside the SQL Server engine itself, on hardware you own, with no API calls leaving your data center. If you run SQL Server on-premises and want to embed intelligence directly into your database operations, this chapter shows you how that actually works.

---

SQL Server Machine Learning Services: R and Python In-Database

SQL Server Machine Learning Services (2017+) and its successor, the Language Extensions framework (2019+), let you execute R and Python scripts inside the database engine via sp_execute_external_script. The script runs in an external process (Launchpad) that the engine manages, data flows between T-SQL and the script as data frames, and results come back as result sets your application consumes like any other query. The operational significance: your feature engineering and model scoring run where the data lives, eliminating the extract-to-Python round trip for batch analytics.

Enablement is a conscious choice — external scripts are off by default, and turning them on has resource implications you should plan for:

-- Enable external script execution (requires a service restart to take effect)
EXEC sp_configure 'external scripts enabled', 1;
RECONFIGURE;
GO

-- Constrain the external runtime with a dedicated resource pool so
-- a runaway Python script cannot starve the relational engine
CREATE EXTERNAL RESOURCE POOL ml_pool
WITH (MAX_CPU_PERCENT = 40, MAX_MEMORY_PERCENT = 40);
ALTER RESOURCE GOVERNOR RECONFIGURE;
GO

-- Verify the Launchpad service is running
EXEC sp_execute_external_script
    @language = N'Python',
    @script = N'print("ML Services is operational")';
GO

The canonical pattern is scoring or enriching a batch of rows and returning the result as a table. Here a Python script computes a simple demand forecast per product category and returns it alongside the input rows:

-- In-database Python: forecast next month's demand per category
EXEC sp_execute_external_script
    @language = N'Python',
    @script = N'
import pandas as pd
from sklearn.linear_model import LinearRegression
import numpy as np

# InputDataSet arrives from the @input_data_1 query below
df = InputDataSet.copy()
df["month_idx"] = np.arange(len(df))

results = []
for category, grp in df.groupby("category_name"):
    X = grp[["month_idx"]].values
    y = grp["units_sold"].values
    model = LinearRegression().fit(X, y)
    next_month = model.predict([[len(grp)]])[0]
    results.append((category, float(max(next_month, 0))))

OutputDataSet = pd.DataFrame(results, columns=["category_name", "forecast_units"])
',
    @input_data_1 = N'
        SELECT c.category_name,
               DATEPART(MONTH, o.order_date) AS month_num,
               SUM(oi.quantity) AS units_sold
        FROM dbo.orders o
        JOIN dbo.order_items oi ON oi.order_id = o.order_id
        JOIN dbo.products p ON p.product_id = oi.product_id
        JOIN dbo.categories c ON c.category_id = p.category_id
        WHERE o.order_date >= DATEADD(YEAR, -1, GETUTCDATE())
        GROUP BY c.category_name, DATEPART(MONTH, o.order_date)
    ',
    @output_data_1_name = N'OutputDataSet'
WITH RESULT SETS ((
    category_name NVARCHAR(100),
    forecast_units FLOAT
));
GO

Three operational realities to internalize before you put this in production. First, the Python and R runtimes are versioned with the SQL Server release — you cannot pip-install an arbitrary new scikit-learn into the in-database runtime without matching the supported package set, so keep training in your data science environment and deploy only scoring code in-database. Second, sp_execute_external_script is a batch operation: it is excellent for nightly scoring jobs and enrichment ETL, and terrible for per-row invocation from a trigger. Third, external scripts run outside the SQL Server memory manager — that is why the external resource pool matters. An unconstrained Python process doing a large in-memory join can push the OS into paging and take the whole instance down with it.

Intelligent Query Processing: The Engine That Learns

Intelligent Query Processing (IQP) is the set of engine features where SQL Server observes its own mistakes and corrects them on subsequent executions. Unlike a recommendation you review and apply, IQP feedback loops are automatic, persisted in Query Store, and reversible. Understanding them is no longer optional for a DBA: when a plan changes at 2 AM with no deployment and no statistics update, IQP feedback is the first suspect.

The feedback family, and what each one does:

Memory grant feedback. When a query spills to tempdb because its memory grant was too small — or wastes memory because the grant was far too large — the engine records the discrepancy and adjusts the grant for the next compilation of the same plan shape. Persisted memory grant feedback (2022+) survives restarts and plan cache evictions because it lives in Query Store. Diagnose it here:

-- Which queries had their memory grants adjusted by feedback?
SELECT
    qsq.query_id,
    OBJECT_NAME(qsq.object_id) AS object_name,
    qsp.plan_id,
    mgf.feature_desc,
    mgf.state_desc,
    CAST(qrs.avg_query_max_used_memory / 1024.0 AS DECIMAL(12,1)) AS avg_used_memory_mb
FROM sys.query_store_query qsq
JOIN sys.query_store_plan qsp
    ON qsp.query_id = qsq.query_id
JOIN sys.query_store_runtime_stats qrs
    ON qrs.plan_id = qsp.plan_id
CROSS APPLY (
    SELECT feature_desc, state_desc
    FROM sys.query_store_plan_feedback
    WHERE plan_id = qsp.plan_id
) mgf
WHERE mgf.feature_desc LIKE '%memory grant%'
ORDER BY qsq.last_execution_time DESC;

Cardinality estimation (CE) feedback. When the optimizer's row estimates are badly wrong and a better plan exists, CE feedback learns a correction model for the query and applies it at optimization time. Degree of parallelism (DOP) feedback. When a parallel plan underperforms because of excessive parallelism overhead on the instance's hardware, DOP feedback dials the effective DOP down for that plan shape. Parameter sensitive plan (PSP) optimization. For parameter-sensitive queries that flip between good plans based on the parameter value, the engine can cache multiple plans per query — one per parameter sensitivity bucket — instead of forcing a single plan to serve all values badly.

The failure mode you must know about is feedback oscillation: memory grant feedback increases a grant, which changes the plan choice, which invalidates the feedback, which then re-learns from the new plan, and the cycle repeats. Symptoms are a query whose plan and grant size flap every few hours with no workload change. The fix is to stabilize one side: force the known-good plan in Query Store, or disable the specific feedback at the database or query level while you investigate:

-- Stabilize a flapping query: force the last-known-good plan
EXEC sp_query_store_force_plan @query_id = 42, @plan_id = 118;
GO

-- Or disable one feedback mechanism at the database scope while investigating
ALTER DATABASE SCOPED CONFIGURATION
    SET MEMORY_GRANT_FEEDBACK_PERCENTILE_GRANT = OFF;
GO

IQP is also where AI-assisted operations get leverage for free: because every feedback action is recorded in Query Store, your monitoring pipeline can treat feedback events as labeled training data. A query that needed CE feedback three times in a month is telling you its statistics or its parameterization need attention — that is a far better prioritization signal than raw duration alone.

PREDICT: Scoring ONNX Models Directly in T-SQL

The PREDICT function (SQL Server 2017+) scores a pre-trained ONNX model inline in a T-SQL query — no external script, no Launchpad process, no Python runtime. The model is stored as VARBINARY(MAX) in a table, loaded once per query execution, and applied row by row. Train wherever you like — Azure Machine Learning, a data scientist's laptop, scikit-learn converted with skl2onnx — and deploy the resulting .onnx file into the database.

-- Model registry table: versioned ONNX models deployed to the database
CREATE TABLE dbo.ml_models (
    model_id      INT IDENTITY(1,1) PRIMARY KEY,
    model_name    NVARCHAR(200) NOT NULL,
    model_version NVARCHAR(50)  NOT NULL,
    model_data    VARBINARY(MAX) NOT NULL,   -- the .onnx file bytes
    deployed_at   DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    is_active     BIT NOT NULL DEFAULT 0,
    CONSTRAINT UQ_ml_models_name_version UNIQUE (model_name, model_version)
);
GO

-- Deploy a model (load the .onnx bytes from a file share the engine can read)
INSERT INTO dbo.ml_models (model_name, model_version, model_data, is_active)
SELECT 'churn_predictor', 'v3',
       BulkColumn, 1
FROM OPENROWSET(BULK 'D:\Models\churn_predictor_v3.onnx', SINGLE_BLOB) AS m;
GO

-- Score customers inline: PREDICT applies the ONNX model per row
DECLARE @model VARBINARY(MAX) = (
    SELECT TOP 1 model_data
    FROM dbo.ml_models
    WHERE model_name = 'churn_predictor' AND is_active = 1
    ORDER BY deployed_at DESC
);

SELECT TOP 100
    c.customer_id,
    c.company_name,
    p.churn_probability
FROM dbo.customers c
CROSS APPLY (
    SELECT churn_probability
    FROM PREDICT(
        MODEL = @model,
        DATA = (
            SELECT c2.tenure_months, c2.monthly_charges,
                   c2.total_charges, c2.contract_type
            FROM dbo.customers c2
            WHERE c2.customer_id = c.customer_id
        ) AS model_input
    ) WITH (churn_probability FLOAT)
) p
WHERE c.segment = 'enterprise'
ORDER BY p.churn_probability DESC;
GO

The operational contract of PREDICT is simple and worth respecting. The model runs on every row the query touches, so filter before you score — put the WHERE clause on the driving table, not after the CROSS APPLY. ONNX models are CPU-bound; scoring millions of rows inline will saturate schedulers, so for large batches prefer the Lambda-style pre-compute pattern from Chapter 16 and reserve PREDICT for interactive or near-real-time scoring of filtered sets. And version your models in the registry table — when v4 behaves differently from v3, you want deployed_at and is_active flags to tell you exactly when the behavior changed, not a mystery file on a share.

AI-Driven Index Recommendations from Query Store Workload Data

Query Store is the richest workload signal SQL Server has ever produced: every query's text, plans, runtime statistics, and wait categories, retained across restarts. It is also the ideal input for AI-driven index recommendations, because the signal set is structured and the action space — CREATE INDEX, DROP INDEX, rebuild — is finite and verifiable. The pipeline: extract the top regressed or expensive queries with their plans from Query Store, pass them to a language model with the existing index definitions as context, and get back executable T-SQL.

-- Workload extraction: top queries by total duration with plan and index context
SELECT TOP 20
    qsq.query_id,
    SUM(qrs.count_executions)                       AS total_executions,
    CAST(SUM(qrs.avg_duration * qrs.count_executions) / 1000000.0
         AS DECIMAL(18,2))                           AS total_duration_sec,
    MAX(qtxt.query_sql_text)                        AS query_text,
    MAX(CAST(qsp.query_plan AS NVARCHAR(MAX)))      AS plan_xml
FROM sys.query_store_query qsq
JOIN sys.query_store_query_text qtxt
    ON qtxt.query_text_id = qsq.query_text_id
JOIN sys.query_store_plan qsp
    ON qsp.query_id = qsq.query_id
JOIN sys.query_store_runtime_stats qrs
    ON qrs.plan_id = qsp.plan_id
WHERE qsq.last_execution_time > DATEADD(DAY, -7, GETUTCDATE())
GROUP BY qsq.query_id
HAVING SUM(qrs.count_executions) > 100
ORDER BY total_duration_sec DESC;
GO

-- Existing index context for the tables those queries touch
SELECT
    SCHEMA_NAME(t.schema_id) + '.' + t.name AS table_name,
    i.name AS index_name,
    i.type_desc,
    STRING_AGG(c.name, ', ') WITHIN GROUP (ORDER BY ic.key_ordinal) AS key_columns
FROM sys.indexes i
JOIN sys.tables t ON t.object_id = i.object_id
JOIN sys.index_columns ic
    ON ic.object_id = i.object_id AND ic.index_id = i.index_id
JOIN sys.columns c
    ON c.object_id = ic.object_id AND c.column_id = ic.column_id
WHERE t.name IN ('orders', 'customers', 'order_items')
GROUP BY t.schema_id, t.name, i.name, i.type_desc;
GO

Feed both result sets to the model with a prompt that demands executable T-SQL, one justification sentence per index, and an explicit statement when the query is already optimal. The governance rules from later in this chapter apply in full: validate the DDL with SET NOEXEC ON before it reaches a human reviewer, confirm the target columns are not already indexed via sys.dm_db_index_usage_stats, and build with WITH (ONLINE = ON) so production traffic is not blocked.

Calling LLM APIs from In-Database Python

Machine Learning Services can also host the generative side of your operations: a Python script inside sp_execute_external_script that calls a language model API for batch enrichment — ticket sentiment classification, alert summarization, runbook tagging. The pattern keeps the orchestration in T-SQL (a SQL Agent job, a stored procedure) while the script handles HTTP, batching, and retries. The tradeoff is latency: every LLM call adds hundreds of milliseconds, so the viable shapes are batch operations and scheduled jobs, never per-row calls on an interactive path.

-- Batch enrichment: classify ticket sentiment with an LLM, in-database Python
EXEC sp_execute_external_script
    @language = N'Python',
    @script = N'
import pandas as pd
import urllib.request, json, time

# Batch the API calls: 20 tickets per request keeps latency manageable
def classify_batch(texts):
    payload = json.dumps({
        "model": "your-llm-deployment",
        "messages": [{
            "role": "user",
            "content": "Classify each ticket as positive, neutral, or negative. "
                       "Return only a JSON array of labels, in order."
        }, {
            "role": "user",
            "content": json.dumps(texts)
        }],
        "max_tokens": 200
    }).encode()

    req = urllib.request.Request(
        LLM_ENDPOINT,
        data=payload,
        headers={"Content-Type": "application/json",
                 "api-key": LLM_API_KEY})
    for attempt in range(3):
        try:
            with urllib.request.urlopen(req, timeout=60) as resp:
                return json.loads(resp.read())["choices"][0]["message"]["content"]
        except Exception:
            time.sleep(2 ** attempt)
    return None

df = InputDataSet.copy()
labels = []
for i in range(0, len(df), 20):
    batch = df["ticket_body"].iloc[i:i+20].tolist()
    raw = classify_batch(batch)
    try:
        parsed = json.loads(raw)
    except Exception:
        parsed = ["unknown"] * len(batch)
    labels.extend(parsed[:len(batch)])

df["sentiment"] = labels
OutputDataSet = df[["ticket_id", "sentiment"]]
',
    @input_data_1 = N'
        SELECT TOP 500 ticket_id, ticket_body
        FROM dbo.support_tickets
        WHERE sentiment IS NULL
    ',
    @params = N'@LLM_ENDPOINT NVARCHAR(500), @LLM_API_KEY NVARCHAR(200)',
    @LLM_ENDPOINT = N'https://your-llm-endpoint/openai/deployments/your-llm-deployment/chat/completions?api-version=2024-02-01',
    @LLM_API_KEY = N' stored-in-a-credential-not-inline '
WITH RESULT SETS ((
    ticket_id INT,
    sentiment NVARCHAR(20)
));
GO

-- Land the classifications (reviewed, then applied by a separate step)
MERGE dbo.support_tickets AS t
USING #ticket_sentiment AS s
    ON t.ticket_id = s.ticket_id
WHEN MATCHED THEN UPDATE SET t.sentiment = s.sentiment;
GO

Keep the API key out of the procedure text — pass it from a database-scoped credential or retrieve it from your secrets store in the calling job step. Keep the batch narrow: constrained prompts, validated output labels, and never direct insertion of raw LLM text into a production table without the MERGE landing in a staging table first.

Embedding AI Governance Into SQL Server Workflows

Using AI to assist with database operations introduces a category of risk that is different from traditional automation: the outputs are probabilistic, not deterministic. A SQL Agent job that rebuilds an index either succeeds or fails. An LLM that recommends an index might recommend a correct index, a redundant one, a harmful one, or an index that is correct but would take a four-hour blocking build on a hot table. Managing this requires governance structures built into your workflows — not as an afterthought.

The practical governance patterns for SQL Server AI workflows are:

1. Capture every AI recommendation with its full context.

Before any AI-generated DDL reaches production, log both the input context and the output recommendation to a dedicated audit table:

CREATE TABLE dbo.ai_recommendations (
    recommendation_id INT IDENTITY(1,1) PRIMARY KEY,
    created_at        DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    source_workflow   NVARCHAR(100) NOT NULL,   -- e.g. 'index_advisor', 'iqp_review'
    input_context     NVARCHAR(MAX) NOT NULL,   -- the prompt / snapshot sent
    recommendation    NVARCHAR(MAX) NOT NULL,   -- the model output
    status            NVARCHAR(30) NOT NULL DEFAULT 'pending',
    reviewed_by       NVARCHAR(128) NULL,
    reviewed_at       DATETIME2 NULL,
    outcome_notes     NVARCHAR(MAX) NULL
);
GO

2. Enforce a dry-run / review gate before application.

No AI output should directly trigger CREATE INDEX, DROP INDEX, ALTER INDEX, or any destructive DML. Even when the recommendation is correct, the build may need WITH (ONLINE = ON), and the model has no knowledge of your maintenance windows or current blocking chains. A simple gating procedure:

CREATE PROCEDURE dbo.usp_apply_ai_recommendation
    @recommendation_id INT,
    @reviewer          NVARCHAR(128)
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @ddl NVARCHAR(MAX), @status NVARCHAR(30);

    SELECT @ddl = recommendation, @status = status
    FROM dbo.ai_recommendations
    WHERE recommendation_id = @recommendation_id;

    IF @status <> 'approved'
    BEGIN;
        RAISERROR('Recommendation %d is not approved (status=%s).',
                  16, 1, @recommendation_id, @status);
        RETURN;
    END;

    -- Parse check only: validates syntax without executing
    SET NOEXEC ON;
    EXEC sp_executesql @ddl;
    SET NOEXEC OFF;

    -- Syntax valid: execute for real, then record the outcome
    EXEC sp_executesql @ddl;

    UPDATE dbo.ai_recommendations
    SET status = 'applied',
        reviewed_by = @reviewer,
        reviewed_at = SYSUTCDATETIME()
    WHERE recommendation_id = @recommendation_id;
END;
GO

3. Validate AI-generated DDL programmatically before review.

Catch obvious errors — wrong table names, nonexistent columns, duplicate index definitions — before wasting review time. Query sys.indexes and sys.columns to confirm every referenced object exists, and check sys.dm_db_index_usage_stats for redundancy with existing indexes.

Practical Deployment Patterns

Several deployment topologies have emerged as reliable for AI-augmented SQL Server operations on-premises. Understanding the tradeoffs helps you choose the right architecture rather than over-engineering from the start.

Pattern 1: Sidecar AI Agent

A separate process (a scheduled PowerShell or Python job on a utility server) reads Query Store and DMVs through pyodbc, calls a language model API for analysis, and writes recommendations to dbo.ai_recommendations. The database itself makes no outbound network calls. This is the lowest-risk topology — SQL Server remains unmodified, and the AI process can be restarted, upgraded, or replaced without touching the database.

Pattern 1, Sidecar AI Agent: SQL Server makes no outbound calls itself — a separate job reads Query Store and DMVs, calls the LLM, and writes recommendations back as ordinary rows behind a review gate.

Pattern 2: In-Database Python via ML Services

AI calls happen inside sp_execute_external_script — appropriate for batch classification, enrichment, and scoring workloads where the AI operation is tightly coupled to the data. Requires a dedicated external resource pool and strict batching; never call per-row from a trigger.

Pattern 3: SQL Agent Orchestration

For batch workloads — nightly index analysis, weekly Query Store review, monthly capacity forecasting — SQL Agent jobs collect DMV and Query Store data, invoke the sidecar or in-database scoring step, and route recommendations through dbo.ai_recommendations for DBA review. You get retry logic, history, and alerting from infrastructure you already operate.

The right pattern depends on latency requirements, your existing infrastructure, and how tightly coupled the AI analysis needs to be to the data path. Most teams start with Pattern 1 (sidecar), add Pattern 3 (SQL Agent orchestration) for batch jobs, and adopt Pattern 2 (in-database Python) only for specific workloads like batch enrichment where moving data out adds unacceptable overhead.

Key Takeaways

  • → **Machine Learning Services brings R and Python inside the engine** for batch scoring and enrichment without data movement. Constrain the external runtime with a dedicated resource pool, keep training outside the database, and never invoke sp_execute_external_script per-row on a hot path.
  • → **Intelligent Query Processing is a closed-loop learning system you must understand operationally.** Memory grant, CE, and DOP feedback persist in Query Store and change plans without deployments. Watch for feedback oscillation, stabilize with plan forcing, and treat feedback events as labeled signals for your own AI-assisted tuning.
  • → **PREDICT scores ONNX models inline in T-SQL** with no external runtime. Filter before you score, version models in a registry table, and reserve inline scoring for filtered interactive sets — large batches belong in a pre-compute job.
  • → **Query Store is the ideal input for AI-driven index recommendations**: structured workload data with plans, runtime stats, and wait categories. Demand executable T-SQL from the model, validate with SET NOEXEC ON, and build online.
  • → **Governance is not optional for AI database operations.** Log every recommendation with its input context, enforce a DBA review gate before applying any AI-generated DDL, validate statements programmatically before review, and track outcomes to tighten prompts over time.
