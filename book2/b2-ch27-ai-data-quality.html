Chapter 27: AI for Data Quality and Master Data

DBAs own the storage, the backups, and the performance — but the data itself increasingly lands on their desk too. Duplicate customers breaking unique constraints, NULL rates creeping up after a vendor feed change, product codes that drifted out of the reference list months ago: these are data quality failures, and they surface as database incidents. Traditional data quality work is rule-based: hand-written checks, threshold alerts, periodic profiling reports nobody reads. AI changes the economics of this work. Statistical profiling catches drift without anyone writing a rule for it, ML-based entity resolution finds duplicates that exact matching misses, and anomaly detection on data distributions flags the vendor feed change the day it happens. This chapter builds an AI-assisted data quality practice on SQL Server, from profiling to master data governance.

---

Profiling at Scale with T-SQL

Every data quality program starts with profiling: what does this column actually contain? A profile is the statistical fingerprint of a column — NULL rate, distinct count, min/max, value distribution, pattern breakdown. On SQL Server, a single dynamic query can profile every column of a table and store the fingerprint in a history table. That history is the foundation everything else in this chapter builds on.

-- Column profile snapshot: run nightly, store in dbo.dq_column_profile_history
DECLARE @schema sysname = 'dbo', @table sysname = 'Customers';
DECLARE @sql NVARCHAR(MAX) = N'';

SELECT @sql += N'
INSERT INTO dbo.dq_column_profile_history
    (profile_date, schema_name, table_name, column_name,
     row_count, null_count, null_pct, distinct_count,
     min_value, max_value, avg_length)
SELECT
    CAST(GETUTCDATE() AS DATE),
    ''' + @schema + ''', ''' + @table + ''', ''' + c.name + ''',
    COUNT(*),
    SUM(CASE WHEN [' + c.name + '] IS NULL THEN 1 ELSE 0 END),
    SUM(CASE WHEN [' + c.name + '] IS NULL THEN 1.0 ELSE 0 END) / COUNT(*),
    COUNT(DISTINCT [' + c.name + ']),
    CAST(MIN(CAST([' + c.name + '] AS NVARCHAR(4000))) AS NVARCHAR(4000)),
    CAST(MAX(CAST([' + c.name + '] AS NVARCHAR(4000))) AS NVARCHAR(4000)),
    AVG(CAST(LEN(CAST([' + c.name + '] AS NVARCHAR(4000))) AS FLOAT))
FROM [' + @schema + '].[' + @table + '];'
FROM sys.columns c
JOIN sys.types t ON t.user_type_id = c.user_type_id
WHERE c.object_id = OBJECT_ID(QUOTENAME(@schema) + '.' + QUOTENAME(@table))
  AND t.name NOT IN ('image','varbinary','xml','geography','geometry');

EXEC sp_executesql @sql;

Store every run. The profile of a single day is trivia; the time series of profiles is a quality signal. When the NULL rate on EmailAddress jumps from 2% to 18% overnight, you do not need a business rule to know something broke — the distribution itself tells you. The next section turns that time series into automated detection.

Detecting Data Drift Without Hand-Written Rules

Rule-based checks fail the same way rule-based monitoring fails: someone has to anticipate every failure mode. Statistical drift detection inverts the problem. Instead of asserting "NULL rate must stay under 5%," you model each profiled metric's normal behavior and flag statistically significant deviations. A z-score over a rolling baseline catches the EmailAddress NULL spike, the sudden appearance of a new product code, or a value distribution that quietly shifted after a deployment — without a single threshold anyone had to guess.

import pandas as pd
import numpy as np
import pyodbc

def detect_profile_drift(conn_string: str, baseline_days: int = 30,
                         z_threshold: float = 4.0) -> pd.DataFrame:
    """
    Compare the latest column profile snapshot against a rolling baseline.
    Flags metrics whose z-score exceeds the threshold.
    """
    conn = pyodbc.connect(conn_string)
    df = pd.read_sql("""
        SELECT schema_name, table_name, column_name, profile_date,
               null_pct, distinct_count, avg_length
        FROM dbo.dq_column_profile_history
        WHERE profile_date >= DATEADD(DAY, -%d, CAST(GETUTCDATE() AS DATE))
    """ % (baseline_days + 1), conn)
    conn.close()

    alerts = []
    for (schema, table, col), g in df.groupby(['schema_name','table_name','column_name']):
        g = g.sort_values('profile_date')
        if len(g) < 7:
            continue  # need a week of history before judging
        latest, baseline = g.iloc[-1], g.iloc[:-1]
        for metric in ['null_pct', 'distinct_count', 'avg_length']:
            mu, sigma = baseline[metric].mean(), baseline[metric].std()
            if sigma == 0 or np.isnan(sigma):
                continue
            z = abs(latest[metric] - mu) / sigma
            if z >= z_threshold:
                alerts.append({
                    'table': f"{schema}.{table}",
                    'column': col,
                    'metric': metric,
                    'baseline_mean': round(mu, 4),
                    'latest_value': round(latest[metric], 4),
                    'z_score': round(z, 2),
                })
    return pd.DataFrame(alerts).sort_values('z_score', ascending=False)

Run this as a SQL Agent job step every morning and write the alerts to a dbo.dq_drift_alerts table. The z-score threshold of 4.0 is deliberately conservative — profile metrics are noisy, and you want the first weeks of alerting to build trust, not fatigue. Tune it down once the team sees that every alert so far was a genuine data event. For categorical columns, extend the same idea to value-distribution drift: compare today's top-20 value frequencies against the baseline with a chi-squared test, and flag columns whose distribution shifted.

ML-Based Deduplication and Entity Resolution

Duplicates are the data quality problem that exact matching cannot solve. "Acme Corp", "ACME Corporation", and "Acme Corp." are the same customer; no unique constraint catches that. SQL Server's built-in fuzzy functions — SOUNDEX() and DIFFERENCE() — handle phonetic similarity, but real entity resolution needs more: string distance across multiple fields, weighted by field importance, with a learned decision boundary instead of a guessed threshold.

The practical architecture is blocking plus scoring. Blocking narrows the candidate pairs cheaply in T-SQL (same postal code, same SOUNDEX of last name) so you never compare every row to every other row. Scoring then computes similarity features per pair in Python and classifies them with a model trained on a few hundred hand-labeled pairs.

import pandas as pd
import pyodbc
from sklearn.ensemble import RandomForestClassifier
from rapidfuzz import fuzz

def candidate_pairs(conn) -> pd.DataFrame:
    """Blocking in T-SQL: only compare rows sharing a blocking key."""
    return pd.read_sql("""
        SELECT a.CustomerID AS id_a, b.CustomerID AS id_b,
               a.CompanyName AS name_a, b.CompanyName AS name_b,
               a.Email AS email_a, b.Email AS email_b,
               a.PostalCode AS zip_a, b.PostalCode AS zip_b,
               a.Phone AS phone_a, b.Phone AS phone_b
        FROM dbo.Customers a
        JOIN dbo.Customers b
          ON a.CustomerID < b.CustomerID
         AND (
               LEFT(a.PostalCode, 3) = LEFT(b.PostalCode, 3)   -- same zip prefix
            OR SOUNDEX(a.CompanyName) = SOUNDEX(b.CompanyName) -- phonetic match
         )
    """, conn)

def featurize(pairs: pd.DataFrame) -> pd.DataFrame:
    """Similarity features per candidate pair."""
    f = pd.DataFrame()
    f['name_ratio']  = pairs.apply(lambda r: fuzz.ratio(str(r.name_a), str(r.name_b)), axis=1) / 100
    f['name_token']  = pairs.apply(lambda r: fuzz.token_set_ratio(str(r.name_a), str(r.name_b)), axis=1) / 100
    f['email_exact'] = (pairs.email_a.str.lower() == pairs.email_b.str.lower()).astype(int)
    f['email_ratio'] = pairs.apply(lambda r: fuzz.ratio(str(r.email_a), str(r.email_b)), axis=1) / 100
    f['zip_exact']   = (pairs.zip_a == pairs.zip_b).astype(int)
    f['phone_exact'] = (pairs.phone_a == pairs.phone_b).astype(int)
    return f

# Train once on hand-labeled pairs (1 = same entity, 0 = different)
# labels.csv: id_a, id_b, is_duplicate  — 300-500 rows labeled by a data steward
model = RandomForestClassifier(n_estimators=200, random_state=42, class_weight='balanced')
train_pairs = pd.read_csv('labels.csv').merge(candidate_pairs(conn), on=['id_a','id_b'])
model.fit(featurize(train_pairs), train_pairs['is_duplicate'])

# Score all candidates; review band 0.4-0.7 goes to a steward, >0.7 auto-flags
pairs = candidate_pairs(conn)
pairs['dup_probability'] = model.predict_proba(featurize(pairs))[:, 1]
review = pairs[(pairs.dup_probability >= 0.4) & (pairs.dup_probability < 0.7)]
auto_flag = pairs[pairs.dup_probability >= 0.7]

The review band is the key operational detail. Pairs scoring above 0.7 are high-confidence duplicates — flag them for merge automatically or queue them for fast steward approval. Pairs in the 0.4–0.7 band go to a human data steward, and every steward decision becomes new training data. Retrain monthly; the model gets smarter exactly where your data is ambiguous, which is precisely where hand-written rules stay dumb forever.

Master Data Management with SQL Server MDS

Deduplication cleans up the past; Master Data Services (MDS) prevents the mess from recurring. MDS gives you a governed hub for reference and master entities — product codes, customer hierarchies, chart of accounts — with versioning, business rules, and steward workflows. The AI angle is using the drift detection and entity resolution from the previous sections as feeds into MDS rather than standalone tools.

The pattern: your profiling pipeline flags a new, unseen product code appearing in the orders feed. Instead of just alerting, the pipeline stages the candidate value into an MDS staging table, where a business rule validates its format and a steward approves or rejects it. Approved values flow into the published master entity; subscribing systems pull the golden record instead of maintaining their own copies. The duplicate detector's high-confidence pairs feed the same staging flow as merge candidates. MDS becomes the system of record, and the ML pipelines become its intake sensors.

For shops not running MDS, the same hub-and-spoke pattern works with a governed schema: a mdm schema holding golden-record tables, a mdm_staging schema for candidate intake, and stored procedures enforcing the approve/publish workflow. The tooling matters less than the discipline: one write path, one approval path, full history.

The Data Quality Scorecard

Executives do not read drift alert tables. They read scorecards. Roll your profiling history, drift alerts, and duplicate counts into a single per-table DQ score, refreshed daily, and publish it where the business can see it. A useful score blends four dimensions: completeness (1 − NULL rate on business-critical columns), validity (share of values passing format/domain rules), uniqueness (1 − duplicate rate), and stability (1 − normalized drift alert count over 30 days).

-- Daily DQ scorecard per table: 0-100 per dimension, weighted composite
WITH latest_profiles AS (
    SELECT schema_name, table_name,
           AVG(null_pct) AS avg_null_pct,
           SUM(CASE WHEN null_pct > 0.05 THEN 1 ELSE 0 END) AS cols_high_null
    FROM dbo.dq_column_profile_history
    WHERE profile_date = CAST(GETUTCDATE() AS DATE)
    GROUP BY schema_name, table_name
),
drift_30d AS (
    SELECT table_name, COUNT(*) AS drift_alerts
    FROM dbo.dq_drift_alerts
    WHERE alert_date >= DATEADD(DAY, -30, CAST(GETUTCDATE() AS DATE))
    GROUP BY table_name
),
dup_rates AS (
    SELECT 'dbo.Customers' AS table_name,
           COUNT(*) * 1.0 / NULLIF((SELECT COUNT(*) FROM dbo.Customers), 0) AS dup_rate
    FROM dbo.dq_duplicate_flags
    WHERE flag_date = CAST(GETUTCDATE() AS DATE) AND status = 'confirmed'
)
SELECT
    p.schema_name + '.' + p.table_name AS table_name,
    CAST(100 * (1 - p.avg_null_pct) AS DECIMAL(5,1)) AS completeness_score,
    CAST(100 * (1 - ISNULL(d.drift_alerts, 0) / 30.0) AS DECIMAL(5,1)) AS stability_score,
    CAST(100 * (1 - ISNULL(u.dup_rate, 0)) AS DECIMAL(5,1)) AS uniqueness_score,
    CAST(100 * (0.4 * (1 - p.avg_null_pct)
              + 0.3 * (1 - ISNULL(d.drift_alerts, 0) / 30.0)
              + 0.3 * (1 - ISNULL(u.dup_rate, 0))) AS DECIMAL(5,1)) AS dq_score
FROM latest_profiles p
LEFT JOIN drift_30d d ON d.table_name = p.schema_name + '.' + p.table_name
LEFT JOIN dup_rates u ON u.table_name = p.schema_name + '.' + p.table_name
ORDER BY dq_score;

Publish the scorecard to a dashboard and set one alert: any table dropping more than 10 points week over week pages the data owner. That single alert, backed by the drill-down from score to drift alert to profile history, is what turns data quality from a quarterly audit exercise into a daily operational metric — owned, measured, and improving.

---

Key Takeaways

  • → **Profile everything, store every run.** A nightly T-SQL column-profile snapshot written to a history table is cheap, and the time series of profiles is the raw material for every detection technique in this chapter.
  • → **Statistical drift detection replaces guessed thresholds.** A z-score against a rolling baseline flags NULL spikes, new codes, and distribution shifts without anyone writing a rule for each failure mode — start conservative at z ≥ 4.0 and tune down as trust builds.
  • → **Entity resolution is blocking plus learned scoring.** Cheap T-SQL blocking (zip prefix, SOUNDEX) narrows candidate pairs; a classifier trained on a few hundred steward-labeled pairs scores them, with a human review band in the middle that becomes retraining data.
  • → **Feed ML detections into your master data hub, not around it.** Drift alerts and duplicate candidates should stage into MDS (or a governed mdm schema) as intake — one write path, one approval path, full history.
  • → **Roll it up into a DQ scorecard the business reads.** Completeness, validity, uniqueness, and stability per table, one composite score, one alert on a 10-point weekly drop — that is what makes data quality an operational metric instead of an audit artifact.
