Chapter 16: AI Features in AWS RDS for SQL Server

AWS has quietly assembled one of the most complete stacks for AI-augmented database operations available to any DBA today. For SQL Server workloads on Amazon RDS, the surrounding ecosystem — Bedrock, Performance Insights ML, DevOps Guru for RDS, Lambda-driven automation, and OpenSearch-backed vector search — gives you building blocks that were either unavailable or required significant custom engineering just three years ago. This chapter cuts through the marketing and focuses on what these services actually do for RDS for SQL Server, where they fall short, and how to wire them together into production-grade systems that reduce operational toil and surface intelligence you can act on.

---

What AWS Actually Gives You: The AI/ML Layer Mapped to RDS for SQL Server

Before writing a single line of code or enabling a single feature, it pays to understand exactly which services belong to which layer of the stack. AWS tends to announce AI features at re:Invent and then roll them out unevenly across engine versions, regions, and instance types. Knowing the landscape prevents you from designing an architecture that breaks because a feature you assumed was available on db.t3.medium is actually restricted to db.r6g.large and above.

The AI/ML capabilities around RDS for SQL Server fall into four broad layers:

Layer 1: ML inference wired into the SQL workflow. RDS for SQL Server has no in-engine ML invocation feature. The production pattern is to pre-compute predictions with SageMaker or Lambda and land them in a dedicated predictions table that T-SQL queries JOIN against — or to call a REST inference endpoint from the application tier. It is less elegant than in-database scoring, but it is operationally predictable and keeps the database engine focused on query execution.

Layer 2: Performance observability with ML-based anomaly detection. Performance Insights includes a Counter Metrics ML model that flags unusual deviations in wait events and DB load. DevOps Guru for RDS sits above this layer and correlates anomalies across metrics, logs, and events to surface what AWS calls "insights" — essentially root cause hypotheses generated by an ML model trained on AWS operational data.

Layer 3: Vector search alongside the database. RDS for SQL Server does not ship a native vector type or ANN index, so production RAG pipelines pair the instance with a managed vector store — Amazon OpenSearch Serverless or a Bedrock Knowledge Base — while SQL Server remains the system of record for structured data. Embeddings are generated by Bedrock models and the retrieval tier handles semantic search; a Python application tier joins vector results with relational rows.

Layer 4: External AI model integration via Bedrock. AWS Bedrock gives you managed access to foundation models — Anthropic Claude, Amazon Titan, Meta Llama, Cohere, and others — via a single API. When you need generative reasoning about your database (query rewriting, schema summarization, anomaly explanation), you call Bedrock. There is no native Bedrock-to-RDS integration today; you build that bridge yourself.

Understanding these layers matters because a common mistake is treating DevOps Guru as a replacement for a proper observability pipeline, or treating pre-computed prediction tables as a replacement for an external feature store. They complement each other, and the production architectures that work are the ones that use each layer for what it does well.

ML Inference for RDS for SQL Server: Pre-Computed Predictions and Lambda Scoring

RDS for SQL Server does not offer in-engine ML invocation, and SQL Server Machine Learning Services (in-database Python and R) is not available on RDS. The production pattern is to score outside the engine and bring predictions back into the relational world. The most robust variant: a scheduled Lambda function pulls feature rows from RDS, invokes a SageMaker endpoint, and writes predictions to a dedicated table that T-SQL queries JOIN against.

import boto3
import json
import pyodbc

sagemaker = boto3.client('sagemaker-runtime', region_name='us-east-1')

CONN_STR = (
    "DRIVER={ODBC Driver 18 for SQL Server};"
    "SERVER=prod-sql01.cluster-xyz.us-east-1.rds.amazonaws.com;"
    "DATABASE=AppDB;UID=scoring_svc;PWD=${SCORING_PASSWORD};"
    "Encrypt=yes;TrustServerCertificate=yes;"
)

def score_churn_batch(batch_size: int = 500) -> int:
    """Score unscored customers and land predictions in dbo.churn_predictions."""
    conn = pyodbc.connect(CONN_STR)
    cur = conn.cursor()
    cur.execute("""
        SELECT TOP (?) customer_id, tenure_months, monthly_charges,
               total_charges, contract_type
        FROM dbo.customer_features
        WHERE segment = 'enterprise'
          AND last_activity_date > DATEADD(DAY, -90, CAST(GETUTCDATE() AS DATE))
          AND NOT EXISTS (
              SELECT 1 FROM dbo.churn_predictions p
              WHERE p.customer_id = customer_features.customer_id
          )
    """, batch_size)
    rows = cur.fetchall()

    scored = 0
    for customer_id, tenure, monthly, total, contract in rows:
        payload = json.dumps({
            'tenure_months': tenure,
            'monthly_charges': float(monthly),
            'total_charges': float(total),
            'contract_type': contract
        })
        resp = sagemaker.invoke_endpoint(
            EndpointName='churn-prediction-endpoint-v2',
            ContentType='application/json',
            Body=payload
        )
        prob = json.loads(resp['Body'].read())['churn_probability']
        cur.execute("""
            MERGE dbo.churn_predictions AS t
            USING (SELECT ? AS customer_id) AS s
              ON t.customer_id = s.customer_id
            WHEN MATCHED THEN UPDATE SET
                churn_probability = ?, scored_at = SYSUTCDATETIME()
            WHEN NOT MATCHED THEN INSERT
                (customer_id, churn_probability, scored_at)
                VALUES (?, ?, SYSUTCDATETIME());
        """, customer_id, prob, customer_id, prob)
        scored += 1

    conn.commit()
    conn.close()
    return scored


if __name__ == "__main__":
    print(f"Scored {score_churn_batch()} customers")

Consuming the predictions from T-SQL is then trivial — a JOIN against the predictions table, no HTTP calls in the query path:

-- Churn-risk report: relational data enriched with pre-computed ML scores
SELECT TOP 100
    c.customer_id,
    c.company_name,
    c.lifetime_value_usd,
    p.churn_probability,
    p.scored_at
FROM dbo.customers c
JOIN dbo.churn_predictions p ON p.customer_id = c.customer_id
WHERE p.churn_probability > 0.70
ORDER BY p.churn_probability DESC;

One anti-pattern to avoid: calling a SageMaker or Comprehend endpoint synchronously from the application write path or from a trigger. Inference API calls add 50–200ms of latency under normal conditions. That is acceptable for a scheduled Lambda batch scoring job; it is not acceptable on an OLTP write path that needs sub-10ms response times. Keep scoring asynchronous, keep the predictions table fresh with a schedule (EventBridge on a 15-minute cadence is typical), and let T-SQL read pre-computed scores.

Performance Insights ML and DevOps Guru: Reading What the Model Tells You

Performance Insights is the most underused tool in the RDS toolkit. Most DBAs enable it, look at the DB Load chart when something is on fire, and ignore it the rest of the time. The ML layer on top of Performance Insights changes that calculus because it can surface anomalies you were not watching for.

Performance Insights ML operates on the DB load time series per wait event. It builds a baseline model for each metric using approximately two weeks of historical data and then flags deviations using a threshold derived from that baseline — not a static threshold you configure, but a learned one. When io/file/read wait time spikes 8x its normal value at 3:47 AM on a Tuesday, the model flags it even if the absolute value is still within the range your static alarm would not trigger.

You surface these programmatically using the Performance Insights API:

import boto3
import json
from datetime import datetime, timedelta, timezone

pi_client = boto3.client('pi', region_name='us-east-1')

resource_id = 'db-ABCDEFGHIJKLMNOPQRSTUVWXYZ'  # DbiResourceId from RDS describe-db-instances

end_time = datetime.now(timezone.utc)
start_time = end_time - timedelta(hours=6)

response = pi_client.get_resource_metrics(
    ServiceType='RDS',
    Identifier=resource_id,
    StartTime=start_time,
    EndTime=end_time,
    PeriodInSeconds=60,
    MetricQueries=[
        {
            'Metric': 'db.load.avg',
            'GroupBy': {
                'Group': 'db.wait_event',
                'Dimensions': ['db.wait_event.name'],
                'Limit': 10
            }
        }
    ]
)

# Extract anomalous periods — look for data points flagged by the ML layer
# The API returns MeanSquaredError and other anomaly metadata in AlignedStartTime
for metric_key in response.get('MetricList', []):
    key_dimensions = metric_key['Key'].get('Dimensions', {})
    wait_event = key_dimensions.get('db.wait_event.name', 'unknown')
    
    for point in metric_key.get('DataPoints', []):
        if point.get('Value', 0) > 5.0:  # DB load > 5 vCPUs on this wait event
            print(json.dumps({
                'wait_event': wait_event,
                'timestamp': point['Timestamp'].isoformat(),
                'db_load': round(point['Value'], 2)
            }))

DevOps Guru for RDS sits above this and uses a broader ML model trained on AWS operational data across a large fleet of RDS instances. It correlates Performance Insights anomalies with CloudWatch metrics, database logs, and RDS events to generate insights. An insight might look like: "High proportion of CPU time spent in lock:relation wait events correlates with a recent increase in connection count and a schema change detected in the audit log. This pattern is consistent with a missing index on a table that is being scanned under lock contention."

That is a real example of what DevOps Guru produces. It is not always right, and it sometimes surfaces insights that are obvious to any experienced DBA. But the value is not in replacing your judgment — it is in reducing the time from anomaly to hypothesis. When you are on call at 2 AM and your pager fires, getting a formatted hypothesis in your DevOps Guru console is faster than starting from scratch with sys.dm_exec_sessions and wait event histograms.

To pull DevOps Guru insights programmatically and route them into your incident management workflow:

import boto3

dg_client = boto3.client('devops-guru', region_name='us-east-1')
sns_client = boto3.client('sns', region_name='us-east-1')

INSIGHT_TOPIC_ARN = 'arn:aws:sns:us-east-1:123456789012:rds-critical-insights'

paginator = dg_client.get_paginator('list_insights')
pages = paginator.paginate(
    StatusFilter={
        'Any': {
            'StartTimeRange': {
                'FromTime': __import__('datetime').datetime.utcnow() - __import__('datetime').timedelta(hours=1),
                'ToTime': __import__('datetime').datetime.utcnow()
            },
            'Type': 'REACTIVE'
        }
    }
)

for page in pages:
    for insight in page.get('ReactiveInsights', []):
        severity = insight.get('Severity', 'LOW')
        if severity in ('HIGH', 'MEDIUM'):
            description = insight.get('Name', 'No description')
            insight_id = insight['Id']
            
            # Fetch the full insight for recommendations
            detail = dg_client.describe_insight(Id=insight_id)
            recommendations = detail.get('Insight', {}).get('Description', '')
            
            sns_client.publish(
                TopicArn=INSIGHT_TOPIC_ARN,
                Subject=f'[DevOpsGuru][{severity}] RDS Insight Detected',
                Message=f"Insight: {description}\n\nRecommendations:\n{recommendations}\n\nInsight ID: {insight_id}"
            )

The gap between Performance Insights ML and DevOps Guru is worth understanding. Performance Insights ML tells you *what* metric is anomalous. DevOps Guru attempts to tell you *why* and *what to do*. Neither replaces the need for a human-readable diagnostic workflow, but together they shorten the diagnostic cycle for the most common RDS failure patterns.

Building RAG Pipelines with RDS for SQL Server

RDS for SQL Server ships no native vector type or approximate nearest neighbor index, so production retrieval-augmented generation (RAG) pipelines pair the instance with a managed vector store while SQL Server remains the system of record for structured data. This is where the most active engineering work is happening in the database AI space today: the ability to keep operational runbooks, incident post-mortems, and schema documentation searchable by meaning — and to join those semantic results with live relational data.

The practical architecture on AWS has three parts. First, a Bedrock Knowledge Base (backed by Amazon OpenSearch Serverless as its vector store) holds chunked, embedded runbooks and documentation. Second, SQL Server holds the structured operational data — incident records, schema inventory, performance history. Third, a Python application tier performs retrieval from the Knowledge Base and joins the semantic results with relational rows before calling the language model.

The ingestion side is simple: runbooks live as documents in S3, and the Bedrock Knowledge Base syncs, chunks, and embeds them automatically. What the DBA owns is the structured side — the incident catalog in SQL Server that lets you correlate a retrieved runbook with actual system state:

-- Operational runbook catalog: structured metadata in SQL Server,
-- semantic content in the Bedrock Knowledge Base
CREATE TABLE dbo.runbook_catalog (
    runbook_id      INT IDENTITY(1,1) PRIMARY KEY,
    runbook_name    NVARCHAR(200) NOT NULL,
    section_title   NVARCHAR(300) NOT NULL,
    s3_document_key NVARCHAR(1000) NOT NULL,  -- source doc in the KB's S3 bucket
    owner_team      NVARCHAR(100),
    last_reviewed   DATE,
    kb_sync_status  NVARCHAR(30) DEFAULT 'pending'
);

-- Retrieval joins semantic search results with live incident context
CREATE PROCEDURE dbo.usp_get_incident_context
    @incident_type NVARCHAR(100)
AS
BEGIN
    SET NOCOUNT ON;
    -- Recent similar incidents from the relational store
    SELECT TOP 5
        i.incident_id,
        i.started_at,
        i.root_cause_summary,
        i.resolution_minutes
    FROM dbo.incident_history i
    WHERE i.incident_type = @incident_type
    ORDER BY i.started_at DESC;
END;

The retrieval side queries the Bedrock Knowledge Base for the top-k most semantically similar runbook chunks, pulls live incident context from SQL Server with pyodbc, and passes both to the language model:

import boto3
import json
import pyodbc

bedrock_agent = boto3.client('bedrock-agent-runtime', region_name='us-east-1')
bedrock_rt = boto3.client('bedrock-runtime', region_name='us-east-1')

KB_ID = 'YOUR_KNOWLEDGE_BASE_ID'  # Bedrock Knowledge Base with ops runbooks
CONN_STR = (
    "DRIVER={ODBC Driver 18 for SQL Server};"
    "SERVER=prod-sql01.cluster-xyz.us-east-1.rds.amazonaws.com;"
    "DATABASE=AppDB;UID=ops_reader;PWD=${OPS_READER_PASSWORD};"
    "Encrypt=yes;TrustServerCertificate=yes;"
)

def retrieve_runbook_context(question: str, incident_type: str, top_k: int = 5) -> dict:
    # Step 1: semantic retrieval from the Bedrock Knowledge Base
    kb_resp = bedrock_agent.retrieve(
        knowledgeBaseId=KB_ID,
        retrievalQuery={'text': question},
        retrievalConfiguration={
            'vectorSearchConfiguration': {'numberOfResults': top_k}
        }
    )
    chunks = [
        r['content']['text']
        for r in kb_resp.get('retrievalResults', [])
    ]

    # Step 2: structured incident context from RDS for SQL Server
    conn = pyodbc.connect(CONN_STR)
    cur = conn.cursor()
    cur.execute("EXEC dbo.usp_get_incident_context @incident_type = ?", incident_type)
    incidents = [
        {'incident_id': r[0], 'started_at': str(r[1]),
         'root_cause': r[2], 'resolution_minutes': r[3]}
        for r in cur.fetchall()
    ]
    conn.close()

    return {'runbook_chunks': chunks, 'recent_incidents': incidents}


def answer_ops_question(question: str, incident_type: str) -> str:
    ctx = retrieve_runbook_context(question, incident_type)
    prompt = (
        "You are an expert SQL Server DBA on Amazon RDS. "
        "Answer the operations question using the runbook excerpts and "
        "recent incident history below.

"
        f"RUNBOOK EXCERPTS:
" + "
---
".join(ctx['runbook_chunks']) +
        f"

RECENT SIMILAR INCIDENTS:
{json.dumps(ctx['recent_incidents'], indent=2)}"
        f"

QUESTION: {question}"
    )
    resp = bedrock_rt.invoke_model(
        modelId='anthropic.claude-3-5-sonnet-20241022-v2:0',
        body=json.dumps({
            'anthropic_version': 'bedrock-2023-05-31',
            'max_tokens': 1024,
            'messages': [{'role': 'user', 'content': prompt}]
        }),
        contentType='application/json',
        accept='application/json'
    )
    return json.loads(resp['body'].read())['content'][0]['text']


print(answer_ops_question(
    "What are the steps to safely fail over a Multi-AZ RDS for SQL Server instance?",
    incident_type="failover"
))

The most important operational consideration for this architecture is keeping the two stores in sync. When a runbook is updated in S3, the Knowledge Base re-sync must complete before on-call engineers see the new version — monitor the sync job status and alert on failures. On the SQL Server side, the runbook_catalog table's kb_sync_status column gives you a relational view of which documents are current.

Wiring Bedrock into Your RDS Operations Workflow

Performance Insights and DevOps Guru tell you what is wrong with your database. Bedrock is where you build the generative layer that translates raw diagnostic signals into actionable operational intelligence. The architecture pattern that works in production is: collect structured signals from AWS APIs, pass them as structured context to a Bedrock-hosted Claude or Titan model, and get back a reasoning chain that your on-call team can act on.

The most immediate use case is autonomous wait event diagnosis. Your monitoring pipeline collects the top-10 wait events from Performance Insights and the current request distribution from sys.dm_exec_requests and sys.dm_os_wait_stats. You pass this as a structured prompt to Bedrock and get back a hypothesis with recommended actions.

Python (SQL Server via pyodbc):

import pyodbc
import json
import boto3

bedrock_client = boto3.client('bedrock-runtime', region_name='us-east-1')

def collect_sqlserver_snapshot(sql_conn) -> dict:
    """Collect equivalent diagnostic data from SQL Server DMVs."""
    cursor = sql_conn.cursor()
    
    # Active requests with wait info
    cursor.execute("""
        SELECT TOP 10
            r.session_id,
            r.status,
            r.wait_type,
            r.wait_time / 1000.0          AS wait_time_seconds,
            r.cpu_time / 1000.0           AS cpu_time_seconds,
            r.total_elapsed_time / 1000.0 AS elapsed_seconds,
            LEFT(st.text, 200)            AS query_snippet,
            DB_NAME(r.database_id)        AS database_name
        FROM sys.dm_exec_requests r
        CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) st
        WHERE r.session_id != @@SPID
          AND r.total_elapsed_time > 5000
        ORDER BY r.total_elapsed_time DESC
    """)
    
    columns = [col[0] for col in cursor.description]
    active_requests = [dict(zip(columns, row)) for row in cursor.fetchall()]
    
    # Top wait types over recent history from sys.dm_os_wait_stats
    cursor.execute("""
        SELECT TOP 10
            wait_type,
            waiting_tasks_count,
            wait_time_ms,
            signal_wait_time_ms,
            wait_time_ms - signal_wait_time_ms AS resource_wait_time_ms
        FROM sys.dm_os_wait_stats
        WHERE wait_type NOT IN (
            'SLEEP_TASK','BROKER_TO_FLUSH','BROKER_TASK_STOP','CLR_AUTO_EVENT',
            'DISPATCHER_QUEUE_SEMAPHORE','FT_IFTS_SCHEDULER_IDLE_WAIT',
            'HADR_FILESTREAM_IOMGR_IOCOMPLETION','HADR_WORK_QUEUE',
            'LAZYWRITER_SLEEP','LOGMGR_QUEUE','ONDEMAND_TASK_QUEUE',
            'REQUEST_FOR_DEADLOCK_MONITOR','RESOURCE_QUEUE','SERVER_IDLE_CHECK',
            'SLEEP_DBSTARTUP','SLEEP_DCOMSTARTUP','SLEEP_MASTERDBREADY',
            'SLEEP_MASTERMDREADY','SLEEP_MASTERUPGRADED','SLEEP_MSDBSTARTUP',
            'SLEEP_TEMPDBSTARTUP','SNI_HTTP_ACCEPT','SP_SERVER_DIAGNOSTICS_SLEEP',
            'SQLTRACE_BUFFER_FLUSH','WAITFOR','XE_DISPATCHER_WAIT',
            'XE_TIMER_EVENT'
        )
        ORDER BY wait_time_ms DESC
    """)
    
    columns = [col[0] for col in cursor.description]
    wait_stats = [dict(zip(columns, row)) for row in cursor.fetchall()]
    
    return {
        'engine': 'SQL Server',
        'active_requests': active_requests,
        'cumulative_wait_stats': wait_stats
    }

def diagnose_sqlserver_with_bedrock(snapshot: dict) -> str:
    snapshot_json = json.dumps(snapshot, indent=2, default=str)
    
    prompt = f"""You are an expert SQL Server DBA analyzing a live performance snapshot from Amazon RDS for SQL Server.

Analyze the diagnostic snapshot below and provide:
1. The most likely root cause of any performance issue visible in the data.
2. Immediate T-SQL or configuration steps the on-call DBA should take right now.
3. Any index, statistics, or configuration changes to prevent recurrence.

Reference specific wait types and query snippets from the data. Do not speculate beyond what the data shows.

DIAGNOSTIC SNAPSHOT:
{snapshot_json}

ANALYSIS:"""

    response = bedrock_client.invoke_model(
        modelId="anthropic.claude-3-5-sonnet-20241022-v2:0",
        body=json.dumps({
            "anthropic_version": "bedrock-2023-05-31",
            "max_tokens": 2048,
            "messages": [{"role": "user", "content": prompt}]
        }),
        contentType="application/json",
        accept="application/json"
    )
    
    result = json.loads(response['body'].read())
    return result['content'][0]['text']

# Usage
sql_conn = pyodbc.connect(
    "DRIVER={ODBC Driver 18 for SQL Server};"
    "SERVER=your-rds-sqlserver.xyz.us-east-1.rds.amazonaws.com,1433;"
    "DATABASE=prod_db;"
    "UID=monitoring_user;"
    "PWD=...;"
    "Encrypt=yes;"
    "TrustServerCertificate=no;"
)

snapshot  = collect_sqlserver_snapshot(sql_conn)
diagnosis = diagnose_sqlserver_with_bedrock(snapshot)
print(diagnosis)

The key discipline in both cases is context quality. Bedrock models are only as useful as the context you give them. Passing a raw CloudWatch metrics dump or a filtered sys.dm_exec_requests output with hundreds of idle sessions produces vague, unhelpful responses. The collection functions above are opinionated about filtering: they exclude idle sessions, they cap query snippets to 200 characters, they exclude benign wait types from SQL Server. That specificity is what allows the model to reason precisely rather than narrate.

Automated Index Recommendations Using AWS and Bedrock

Index management is one of the highest-leverage areas for AI assistance because the signal set — slow query logs, execution plans, table statistics — is well-structured and the action space — CREATE INDEX, DROP INDEX, rebuild — is finite and verifiable. AWS provides some native tooling here (Performance Insights top queries), but it stops short of generating DDL. Bedrock fills that gap.

The pattern is a three-stage pipeline:

1. Collect candidate slow queries from the Performance Insights API or from the slow query log via CloudWatch Logs Insights.

2. For each candidate query, retrieve the execution plan from the database.

3. Pass the slow query and its plan to Bedrock with a prompt that requests index recommendations in the form of executable DDL.

T-SQL (SQL Server):

-- Step 1: Retrieve execution plan for a slow query
SET SHOWPLAN_XML ON;
GO

SELECT
    o.order_id,
    o.customer_id,
    o.total_amount,
    c.email
FROM dbo.orders o
JOIN dbo.customers c ON c.customer_id = o.customer_id
WHERE o.status = 'pending'
  AND o.created_at > DATEADD(DAY, -7, GETUTCDATE())
ORDER BY o.total_amount DESC;
GO

SET SHOWPLAN_XML OFF;
GO

With the plan captured, the Bedrock call generates actionable DDL:

import boto3
import json
import pyodbc

bedrock_client = boto3.client('bedrock-runtime', region_name='us-east-1')

def get_showplan_xml(conn, query: str) -> str:
    """Return the estimated plan as SHOWPLAN_XML text."""
    cur = conn.cursor()
    cur.execute("SET SHOWPLAN_XML ON")
    cur.execute(query)
    plan_xml = cur.fetchall()[0][0]
    cur.execute("SET SHOWPLAN_XML OFF")
    conn.commit()
    return plan_xml

def recommend_indexes(query: str, plan_xml: str) -> str:
    prompt = f"""You are a senior SQL Server DBA and query optimization expert.

A slow query has been identified in production. Your task is to recommend the minimum set of indexes needed to improve its performance. Follow these rules:
- Recommend only indexes that are directly evidenced by the execution plan (MissingIndex hints, table scans on large tables, sort operations that could be eliminated).
- Write complete, executable T-SQL CREATE INDEX statements with ONLINE = ON.
- For each index, write one sentence explaining which part of the plan it addresses.
- Do not recommend dropping existing indexes without evidence they are unused.
- If the plan shows the query is already optimal, say so explicitly.

SLOW QUERY:

{query}


EXECUTION PLAN (SHOWPLAN_XML):

{plan_xml}


INDEX RECOMMENDATIONS (as executable T-SQL DDL with explanations):"""

    response = bedrock_client.invoke_model(
        modelId="anthropic.claude-3-5-sonnet-20241022-v2:0",
        body=json.dumps({
            "anthropic_version": "bedrock-2023-05-31",
            "max_tokens": 1024,
            "messages": [{"role": "user", "content": prompt}]
        }),
        contentType="application/json",
        accept="application/json"
    )

    result = json.loads(response['body'].read())
    return result['content'][0]['text']

# Usage — RDS for SQL Server
sql_conn = pyodbc.connect(
    "DRIVER={ODBC Driver 18 for SQL Server};"
    "SERVER=your-rds-sqlserver.xyz.us-east-1.rds.amazonaws.com,1433;"
    "DATABASE=prod_db;UID=monitoring_user;PWD=${MONITORING_PASSWORD};"
    "Encrypt=yes;TrustServerCertificate=yes;"
)

slow_query = """
SELECT o.order_id, o.customer_id, o.total_amount, c.email
FROM dbo.orders o
JOIN dbo.customers c ON c.customer_id = o.customer_id
WHERE o.status = 'pending'
  AND o.created_at > DATEADD(DAY, -7, GETUTCDATE())
ORDER BY o.total_amount DESC
"""

plan = get_showplan_xml(sql_conn, slow_query)
recommendations = recommend_indexes(slow_query, plan)
print(recommendations)

A typical response from the model for the orders query above would identify that (status, created_at, total_amount) is a strong composite index candidate because the plan shows a MissingIndex hint or clustered index scan filtered on status and created_at followed by an in-memory sort on total_amount. It would generate:

-- Addresses the clustered index scan on dbo.orders filtered by status and
-- created_at; includes total_amount as a key column to eliminate the sort.
CREATE NONCLUSTERED INDEX IX_orders_pending_recent
    ON dbo.orders (status, created_at DESC, total_amount DESC)
    WHERE status = 'pending'
    WITH (ONLINE = ON);

The filtered index on status = 'pending' is the kind of nuance a good model picks up on because the WHERE clause makes the selectivity obvious. It is not universal — you would not use a partial index if pending orders represent 80% of the table — but the model's reasoning about the plan structure is sound and the T-SQL it generates is executable.

What you should not do is apply model-generated index recommendations without review. The model does not know your table sizes, your existing index set, your write amplification tolerance, or your storage budget on the RDS instance class. Treat the output as a starting point: validate the recommended index against sys.dm_db_index_usage_stats to confirm the target columns are not already indexed, then build it with WITH (ONLINE = ON) so the build does not block production traffic on RDS.

Automatic Tuning and Index Maintenance with AI Assistance

On RDS for SQL Server, the maintenance concern that benefits most from AI assistance is index fragmentation and statistics staleness. Automatic Tuning can correct plan regressions by forcing last-known-good plans, but index maintenance remains a DBA-owned job — and on RDS you run it from a scheduled Lambda or an external SQL Agent-style scheduler rather than in-engine jobs. The AI-assisted approach uses the same pattern as index recommendations: collect the signal, pass it to Bedrock, get back a prioritized maintenance script with targeted REBUILD or REORGANIZE statements and UPDATE STATISTICS calls.

First, confirm Automatic Tuning is doing its part — it is the closed-loop learning system that catches plan regressions between maintenance windows:

-- Automatic Tuning state and recent plan corrections on RDS for SQL Server
SELECT
    name,
    desired_state_desc,
    actual_state_desc,
    reason_desc
FROM sys.database_automatic_tuning_options;

-- Plans forced by Automatic Tuning in the last 7 days
SELECT
    qsq.query_id,
    OBJECT_NAME(qsq.object_id) AS object_name,
    qsq.last_execution_time,
    qrs.count_executions,
    CAST(qrs.avg_duration / 1000.0 AS DECIMAL(12,2)) AS avg_duration_ms
FROM sys.query_store_query qsq
JOIN sys.query_store_plan qsp
    ON qsp.query_id = qsq.query_id
JOIN sys.query_store_runtime_stats qrs
    ON qrs.plan_id = qsp.plan_id
WHERE qsp.is_forced_plan = 1
  AND qsq.last_execution_time > DATEADD(DAY, -7, GETUTCDATE())
ORDER BY qsq.last_execution_time DESC;

Then collect fragmentation and statistics age from the catalog views and let Bedrock prioritize the maintenance work:

import boto3
import json
import pyodbc

bedrock_client = boto3.client('bedrock-runtime', region_name='us-east-1')

MAINTENANCE_QUERY = """
SELECT
    DB_NAME()                                AS database_name,
    OBJECT_NAME(ips.object_id)               AS table_name,
    i.name                                   AS index_name,
    ips.index_type_desc,
    ips.avg_fragmentation_in_percent,
    ips.page_count,
    DATEDIFF(DAY,
        STATS_DATE(ips.object_id, ips.index_id),
        GETUTCDATE())                         AS stats_age_days
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') ips
JOIN sys.indexes i
    ON i.object_id = ips.object_id
    AND i.index_id = ips.index_id
WHERE ips.page_count > 1000
  AND ips.avg_fragmentation_in_percent > 5
ORDER BY ips.avg_fragmentation_in_percent DESC
"""

def recommend_maintenance(conn) -> str:
    cur = conn.cursor()
    cur.execute(MAINTENANCE_QUERY)
    columns = [c[0] for c in cur.description]
    frag_data = [dict(zip(columns, r)) for r in cur.fetchall()]

    prompt = f"""You are an expert SQL Server DBA planning index maintenance for an Amazon RDS for SQL Server instance.

INDEX FRAGMENTATION AND STATISTICS AGE REPORT:
{json.dumps(frag_data, indent=2, default=str)}

For each index, recommend REBUILD (fragmentation >= 30% and page_count > 5000) or REORGANIZE (5-30%), and add UPDATE STATISTICS where stats_age_days > 7. Rules:
- Write executable T-SQL with WITH (ONLINE = ON) for rebuilds.
- Order the statements by expected impact (largest, most fragmented first).
- Skip indexes under 1000 pages — rebuilding them wastes log space.
- Keep the whole script runnable inside a single maintenance window.

Write only the T-SQL statements and one-line justifications."""

    response = bedrock_client.invoke_model(
        modelId="anthropic.claude-3-5-sonnet-20241022-v2:0",
        body=json.dumps({
            "anthropic_version": "bedrock-2023-05-31",
            "max_tokens": 1536,
            "messages": [{"role": "user", "content": prompt}]
        }),
        contentType="application/json",
        accept="application/json"
    )
    return json.loads(response['body'].read())['content'][0]['text']

The model reliably generates output like this for a fragmented orders table:

-- dbo.orders.IX_orders_pending_recent: 47% fragmented, 82,400 pages,
-- stats 11 days old. Rebuild online, then refresh statistics.
ALTER INDEX IX_orders_pending_recent ON dbo.orders
    REBUILD WITH (ONLINE = ON, MAXDOP = 4);
UPDATE STATISTICS dbo.orders IX_orders_pending_recent WITH FULLSCAN;

Integrating AWS Secrets Manager and IAM for Secure AI Pipelines

Every AI pipeline in this chapter involves credentials: database passwords, API keys, IAM role ARNs. On RDS, the correct pattern is to store database credentials in AWS Secrets Manager, rotate them automatically using the RDS Secrets Manager integration, and have your application code retrieve credentials at runtime rather than baking them into configuration files or environment variables.

The RDS Secrets Manager integration supports automatic rotation for RDS for SQL Server. Enable it when you create the instance or attach it afterward:

import boto3
import json
import pyodbc

secrets_client = boto3.client('secretsmanager', region_name='us-east-1')

def get_db_credentials(secret_name: str) -> dict:
    """Retrieve database credentials from Secrets Manager."""
    response = secrets_client.get_secret_value(SecretId=secret_name)
    return json.loads(response['SecretString'])

def get_connection(secret_name: str) -> pyodbc.Connection:
    """Return a pyodbc connection using credentials from Secrets Manager."""
    creds = get_db_credentials(secret_name)
    conn_str = (
        "DRIVER={ODBC Driver 18 for SQL Server};"
        f"SERVER={creds['host']},{creds.get('port', 1433)};"
        f"DATABASE={creds['dbname']};"
        f"UID={creds['username']};PWD={creds['password']};"
        "Encrypt=yes;TrustServerCertificate=yes;"
    )
    return pyodbc.connect(conn_str)

# Usage — no hardcoded credentials anywhere in the codebase
conn = get_connection('prod/rds-sqlserver/app-user')

For Bedrock calls, use IAM role-based authentication rather than API keys. When your Lambda function or EC2 instance has an IAM role with bedrock:InvokeModel permission scoped to the specific model ARNs you need, the boto3 client picks up credentials automatically from the instance metadata service. You never need to store a Bedrock API key.

The principle of least privilege applies to the scoring Lambda as well. The IAM role used for SageMaker invocation should be scoped to specific endpoint ARNs:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "sagemaker:InvokeEndpoint",
      "Resource": [
        "arn:aws:sagemaker:us-east-1:123456789012:endpoint/churn-prediction-endpoint-v2"
      ]
    }
  ]
}

Do not use "Resource": "*" for SageMaker invocation. A misconfigured or compromised Lambda execution role with wildcard IAM permissions could invoke arbitrary SageMaker endpoints, which has both security and cost implications.

Monitoring Your AI Pipelines: CloudWatch, Costs, and Guardrails

AI-augmented database operations introduce a new category of operational risk: a runaway enrichment job that calls Comprehend on every row in a 50-million-row table, a Lambda function that enters a retry loop calling Bedrock at maximum rate, or a Knowledge Base retrieval that degrades because the S3 sync job has been failing silently. These are real failure modes, and you need monitoring to catch them before they produce a surprise AWS bill.

For SageMaker invocations from the scoring Lambda, the call volume is visible in CloudWatch under the AWS/SageMaker and AWS/Comprehend namespaces. Set an alarm on InvocationCount and Throttles:

import boto3

cw_client = boto3.client('cloudwatch', region_name='us-east-1')

cw_client.put_metric_alarm(
    AlarmName='ScoringLambda-SageMaker-InvocationSpike',
    AlarmDescription='SageMaker invocations from scoring Lambda exceeded expected rate',
    Namespace='AWS/SageMaker',
    MetricName='InvocationsPerInstance',
    Dimensions=[{'Name': 'EndpointName', 'Value': 'churn-prediction-endpoint-v2'}],
    Statistic='Sum',
    Period=300,
    EvaluationPeriods=2,
    Threshold=50000,          # Tune to your expected batch size
    ComparisonOperator='GreaterThanThreshold',
    AlarmActions=['arn:aws:sns:us-east-1:123456789012:rds-ops-alerts'],
    TreatMissingData='notBreaching'
)

For Bedrock calls, AWS bills per input and output token. The CloudWatch namespace AWS/Bedrock exposes InputTokenCount and OutputTokenCount metrics per model ID. Build a Cost Explorer budget alert scoped to the Bedrock service alongside your operational CloudWatch alarms so that a cost anomaly surfaces at the billing layer as well as the metrics layer.

For Knowledge Base retrieval quality, the risk is a sync job that fails silently and leaves the vector store stale — on-call engineers get answers from last month's runbooks. Monitor the Bedrock Knowledge Base ingestion jobs with a CloudWatch alarm on failed syncs, and reconcile against dbo.runbook_catalog.kb_sync_status in SQL Server so a stale document is visible in the same place DBAs already look.

*The reference architecture's four planes: data and observability feed the AI plane, every AI-generated recommendation lands in front of a human reviewer, and the security plane underlies every call.*

Data plane:

  • → RDS for SQL Server as the primary OLTP store and system of record for structured operational data.
  • → A Bedrock Knowledge Base (OpenSearch Serverless vector store) holding embedded runbooks and documentation.
  • → A scheduled scoring Lambda that invokes SageMaker endpoints and lands predictions in a dedicated SQL Server predictions table.

    • Observability plane:

  • → Performance Insights enabled on all instances, with Enhanced Monitoring at 15-second granularity.
  • → DevOps Guru for RDS enabled and routing HIGH and MEDIUM insights to an SNS topic.
  • → CloudWatch Logs Insights queries scheduled hourly against the slow query log, feeding a DynamoDB table of candidate slow queries.

    • AI plane:

  • → A Step Functions state machine that runs on a configurable schedule (or triggered by a DevOps Guru SNS notification) to: collect a diagnostic snapshot → call Bedrock for diagnosis → write the result to a DynamoDB table → post a summary to a Slack channel via a Lambda webhook.
  • → A separate Step Functions workflow for the index recommendation pipeline: pull top-10 slow queries from DynamoDB → get SHOWPLAN_XML plans from RDS for SQL Server → call Bedrock → write DDL recommendations to an S3 bucket with a timestamp prefix → notify the DBA team for review.
  • → A nightly Lambda function that collects index fragmentation and statistics age from the catalog views, calls Bedrock for a prioritized maintenance plan, and writes the T-SQL script to S3 for next-day review.

    • Security plane:

  • → All database credentials in Secrets Manager with 30-day automatic rotation.
  • → Bedrock access via IAM roles scoped to specific model ARNs.
  • → Scoring Lambda IAM role scoped to specific SageMaker endpoint ARNs.
  • → VPC endpoints for Bedrock, Secrets Manager, and Comprehend so that API traffic does not traverse the public internet.

    • This architecture is deliberately conservative about automation. Recommendations from Bedrock are written to S3 and reviewed by a human before any DDL runs. The only autonomous actions are: posting a diagnosis to Slack (read-only), enabling a CloudWatch alarm (configuration change only), and publishing to SNS (notification only). The reason for this conservatism is not distrust of the models — the models are often correct — but accountability. When a CREATE INDEX statement causes a production incident because it was built on the wrong table due to a name collision, you need a human in that decision chain.

    As your team builds confidence in the pipeline's recommendations over time, you can move specific action categories to autonomous execution. A reasonable progression is:

    1. Month 1–3: All recommendations reviewed manually. Track the accept/reject rate and the accuracy of diagnoses.

    2. Month 4–6: Statistics updates and index reorganizes applied automatically after a 2-hour human review window, since they are low-risk and easily reverted.

    3. Month 7+: Index creation via CREATE INDEX ... WITH (ONLINE = ON) executed automatically during off-peak windows for indexes on tables under a threshold size, with automatic rollback if the index build fails.

    The progression matters because it builds institutional knowledge about where the model's recommendations are reliable and where they need qualification. That knowledge is what separates a durable AI-augmented operations practice from a demo that impresses at a conference and causes a P1 incident three months later.

    ---

    Key Takeaways

  • → **AWS AI capabilities around RDS for SQL Server span four distinct layers** — Lambda-driven ML scoring with SageMaker, Performance Insights ML and DevOps Guru for anomaly detection and root cause hypothesis, Bedrock Knowledge Bases for vector search and RAG pipelines, and Bedrock for generative reasoning — and each layer is suited to a different operational task. Conflating them leads to architectures that are both over-engineered and under-performing.
  • → **ML scoring belongs in batch jobs, not in the query path.** Calling SageMaker from a Lambda scorer adds network latency that has no place in an OLTP transaction. Pre-compute predictions on a schedule, land them in a predictions table, and let T-SQL JOIN against pre-computed scores.
  • → **Pair RDS for SQL Server with a Bedrock Knowledge Base for RAG.** SQL Server stays the system of record for structured data while the Knowledge Base handles semantic search over runbooks and documentation. Monitor the KB sync jobs — a silently stale vector store serves last month's runbooks to tonight's on-call engineer.
  • → **Bedrock-powered diagnosis and index recommendation pipelines are most valuable when context quality is high.** Filter your diagnostic snapshots aggressively — exclude idle sessions, cap query snippets, remove benign wait types — before passing data to the model. Garbage context produces garbage hypotheses, regardless of model capability.
  • → **Automate conservatively and progressively.** Start with Bedrock recommendations flowing to human reviewers, track accuracy, and expand the automation boundary only for action categories where model reliability is demonstrated. The goal is a feedback loop that builds institutional trust in the AI pipeline, not a system that acts autonomously from day one and erodes trust the first time it makes a consequential mistake.
