Chapter 32: Prompt Engineering for DBA Workflows

The prompt is the API contract between your database context and the model's reasoning. Same model, same telemetry, same incident — a well-engineered prompt produces a correct, evidence-grounded diagnosis in a parseable schema; a sloppy one produces confident fiction in freeform prose that your executor cannot safely consume. In DBA automation, prompt quality is not a soft skill. It is the difference between a triage assistant your on-call team trusts and one they mute.

This chapter is the DBA's prompt engineering playbook — not generic prompting advice, but the patterns that matter when the model is reasoning about SQL Server internals: how to pack DMV context so the model sees what a senior DBA would see, how to write system prompts that function as enforceable policy, how to teach T-SQL judgment with few-shot examples, how to demand structured output, and how to build guardrails so the model can never talk its way into running something destructive.

---

Context Packing: Feed the Model What a Senior DBA Would Look At

Model quality in DBA workflows is dominated by context quality. A senior DBA diagnosing slow queries does not stare at a single counter — they check wait deltas, active requests, blocking chains, memory grants, and recent plan changes, in that order. Your prompt context should mirror that investigation, pre-assembled. The rules for packing it:

Most-recent-first, capped rows. TOP 10–20 per section. A 400-row active-request dump wastes tokens and buries the one session that matters. Rank by wait time, age, or resource consumption before truncating.

Deltas, not absolutes. Cumulative sys.dm_os_wait_stats counters since last restart tell the model almost nothing. Capture two snapshots 60 seconds apart and send the delta — that is the signal.

Include baselines and units. "PLE is 42" is meaningless without "typical for this hour is 3,800" and the knowledge that the unit is seconds. Baselines turn numbers into deviations, and deviations are what the model reasons about.

Strip PII and literals. Parameterize query text before it enters the prompt. The model needs query shapes and wait profiles, not customer email addresses from a string literal.

-- Compact triage snapshot: the core of every DBA prompt context
-- Run twice, 60s apart, and send the DELTA to the model
WITH wait_delta AS (
    SELECT
        wait_type,
        SUM(wait_time_ms) AS wait_ms,
        SUM(waiting_tasks_count) AS waits
    FROM sys.dm_os_wait_stats
    WHERE wait_type NOT IN (
        'SLEEP_TASK','BROKER_TO_FLUSH','BROKER_EVENTHANDLER','CHECKPOINT_QUEUE',
        'DBMIRROR_EVENTS_QUEUE','SQLTRACE_BUFFER_FLUSH','CLR_AUTO_EVENT',
        'DISPATCHER_QUEUE_SEMAPHORE','REQUEST_FOR_DEADLOCK_SEARCH','XE_TIMER_EVENT'
    )
    GROUP BY wait_type
),
top_requests AS (
    SELECT TOP 10
        r.session_id,
        r.wait_type,
        r.wait_time / 1000.0 AS wait_sec,
        r.cpu_time,
        r.logical_reads,
        DATEDIFF(SECOND, r.start_time, GETUTCDATE()) AS age_sec,
        LEFT(st.text, 250) AS query_shape
    FROM sys.dm_exec_requests r
    CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) st
    WHERE r.session_id <> @@SPID
    ORDER BY r.wait_time DESC
),
memory_pressure AS (
    SELECT
        cntr_value AS memory_grants_pending
    FROM sys.dm_os_performance_counters
    WHERE object_name LIKE '%Memory Manager%'
      AND counter_name = 'Memory Grants Pending'
)
SELECT
    (SELECT wait_type, wait_ms, waits FROM wait_delta
     ORDER BY wait_ms DESC FOR JSON PATH) AS wait_stats,
    (SELECT * FROM top_requests FOR JSON PATH) AS top_waits,
    (SELECT memory_grants_pending FROM memory_pressure
     FOR JSON PATH, WITHOUT_ARRAY_WRAPPER) AS memory,
    (SELECT cpu_count, physical_memory_kb / 1048576.0 AS memory_gb
     FROM sys.dm_os_sys_info
     FOR JSON PATH, WITHOUT_ARRAY_WRAPPER) AS instance;

Assemble this in Python, compute the wait delta between the two snapshots, attach the baseline ("PLE typical for this hour: 3,800; current: 42"), and you have a context payload the model can actually reason from. Every prompt in your automation should start from a builder like this — never from ad-hoc string concatenation scattered across scripts.

System Prompts Are Policy, Not Suggestions

The system prompt is the one part of the prompt the end user (or the calling code) does not change per incident. Treat it as policy: role definition, platform constraints, output schema, the allowed action vocabulary, and explicit prohibitions. Here is a production-grade system prompt for a SQL Server triage assistant:

TRIAGE_SYSTEM_PROMPT = """
You are a SQL Server database reliability engineer performing incident triage.
You diagnose; you do not execute. No action you recommend will run without
a separate, human-approved execution step.

PLATFORM CONSTRAINTS:
- The database is Microsoft SQL Server. Reference only real SQL Server DMVs,
  catalog views, and stored procedures. Never invent object names.
- All T-SQL you quote must be valid T-SQL syntax.

OUTPUT CONTRACT:
- Respond with exactly one JSON object. No prose outside the JSON.
- Schema:
  {
    "diagnosis": "<one sentence: what is happening>",
    "evidence": ["<metric or observation supporting the diagnosis>", "..."],
    "confidence": <0.0-1.0>,
    "recommended_action": "<one of the allowed actions below>",
    "action_parameters": {},
    "next_diagnostic": "<single query or check to confirm>"
  }

ALLOWED ACTIONS:
- KILL_IDLE_TRANSACTIONS, CANCEL_LONG_QUERIES, CHECKPOINT_IMMEDIATE,
  UPDATE_STATISTICS_TABLE, FORCE_QUERY_STORE_PLAN, ALERT_HUMAN, NO_ACTION

PROHIBITIONS:
- Never recommend DROP, TRUNCATE, ALTER DATABASE, or DBCC SHRINK*.
- Never recommend an action with confidence below 0.6; use ALERT_HUMAN instead.
- Every claim in "evidence" must cite a value present in the input context.
  If the context does not support a diagnosis, say so and use ALERT_HUMAN.
"""

Notice what this prompt does not contain: no pleasantries, no "you are a helpful assistant," no open-ended invitation to be creative. Every line either constrains the output shape, restricts the action space, or demands evidence grounding. The prohibitions section is the most important part — it converts "the model probably won't suggest dropping things" into "the model has an explicit rule against it," which your eval harness (Chapter 31) then verifies.

Few-Shot Examples That Teach T-SQL Judgment

System prompts set the rules; few-shot examples teach judgment. One or two worked examples in the prompt — input snapshot, correct JSON output — calibrate the model's sense of how confident to be, how specific the evidence should be, and which action fits which signature. Keep examples short and representative of your actual workload:

FEW_SHOT_EXAMPLE = """
EXAMPLE 1 — memory grant pressure:
Input context:
{
  "wait_stats": [{"wait_type": "RESOURCE_SEMAPHORE", "wait_ms": 482000, "waits": 310}],
  "memory": {"memory_grants_pending": 14},
  "instance": {"memory_gb": 64.0},
  "top_waits": [{"session_id": 87, "wait_type": "RESOURCE_SEMAPHORE",
                 "wait_sec": 212.0, "query_shape": "SELECT ... GROUP BY ..."}]
}
Correct output:
{
  "diagnosis": "Memory grant pressure: 14 queries waiting for workspace memory, dominated by RESOURCE_SEMAPHORE waits.",
  "evidence": ["RESOURCE_SEMAPHORE wait_ms=482000 over 60s (top wait by far)",
               "memory_grants_pending=14 (baseline for this hour: 0)",
               "session 87 waiting 212s on RESOURCE_SEMAPHORE"],
  "confidence": 0.85,
  "recommended_action": "ALERT_HUMAN",
  "action_parameters": {"suspect_session": 87},
  "next_diagnostic": "SELECT * FROM sys.dm_exec_query_memory_grants WHERE session_id = 87"
}

Note the judgment being taught: the model does NOT recommend killing session 87
(a hash spill victim, not the cause) — it escalates with the right next diagnostic.
"""

The annotation at the end is deliberate: examples should teach not just the format but the restraint. Your few-shot set should include at least one case where the correct output is ALERT_HUMAN or NO_ACTION. If every example ends in decisive action, the model learns that decisiveness is the pattern — and you get a trigger-happy triage bot.

Structured Output or It Didn't Happen

Freeform prose from a model cannot be safely consumed by automation. Every operational prompt must demand a machine-parseable contract — JSON with a fixed schema — and your code must validate the response against that schema before doing anything with it. The validation pattern:

import json

REQUIRED_KEYS = {"diagnosis", "evidence", "confidence",
                 "recommended_action", "action_parameters", "next_diagnostic"}
ALLOWED_ACTIONS = {"KILL_IDLE_TRANSACTIONS", "CANCEL_LONG_QUERIES",
                   "CHECKPOINT_IMMEDIATE", "UPDATE_STATISTICS_TABLE",
                   "FORCE_QUERY_STORE_PLAN", "ALERT_HUMAN", "NO_ACTION"}

def parse_triage_response(raw: str) -> dict:
    """
    Parse and validate a triage model response. Raises on any contract
    violation — the caller treats violations as ALERT_HUMAN.
    """
    try:
        obj = json.loads(raw.strip())
    except json.JSONDecodeError as e:
        raise ValueError(f"triage response is not valid JSON: {e}")

    missing = REQUIRED_KEYS - set(obj.keys())
    if missing:
        raise ValueError(f"triage response missing keys: {missing}")

    if obj["recommended_action"] not in ALLOWED_ACTIONS:
        raise ValueError(
            f"action '{obj['recommended_action']}' not in allowed vocabulary"
        )

    conf = obj["confidence"]
    if not isinstance(conf, (int, float)) or not 0.0 <= conf <= 1.0:
        raise ValueError(f"confidence out of range: {conf}")

Set temperature low — 0.0 to 0.2 — for every operational prompt. Temperature controls randomness, and you want none of it when the output selects remediation actions. Higher temperatures are for brainstorming runbook prose, never for triage. And on parse failure, retry exactly once with a "your previous response was invalid JSON; respond with valid JSON only" nudge, then escalate to ALERT_HUMAN. Never regex-scrape prose into a KILL command — if the contract is broken, the output is unusable, full stop.

Guardrails: The Model Proposes, the Executor Disposes



Prompt engineering controls what the model says. Guardrails control what the system does with what the model says. Both are required; neither substitutes for the other. The guardrail set for DBA workflows:



Identifier allowlist validation. Any schema, table, index, or session ID the model names must be verified against the live catalog — sys.tables, sys.indexes, sys.dm_exec_sessions — before execution. A hallucinated object name must fail closed at the executor, even if it slipped past the prompt.



Read-only versus write prompt separation. Diagnosis prompts and action prompts are different prompts with different system instructions. A diagnosis prompt should never contain action vocabulary at all — it outputs findings, and a separate, stricter planning prompt converts findings into actions. This separation means a compromised or confused diagnosis step cannot directly emit an executable command.



Destructive actions always require an approval token. No prompt, however well engineered, authorizes a DROP, TRUNCATE, failover, or configuration change. Those actions route through the human approval flow from Chapter 10 regardless of model confidence. The prompt can recommend; only a human approves.



Query text is data, never instructions. State this explicitly in the system prompt, and enforce it in the harness with adversarial cases (Chapter 31). Captured SQL containing "ignore previous instructions" must be treated as a string to analyze, not a command to obey.

Versioning and Regression-Testing Your Prompts



Prompts are code. Store them in version control, review changes like code, and run the Chapter 31 evaluation harness against the golden dataset on every prompt change. A one-word change to a system prompt ("recommend" to "execute") can silently alter model behavior across every incident — the eval suite is what catches that before production does.



Log the prompt version alongside every model call in your audit trail. When a bad recommendation ships, the first question is "which prompt version produced this?" — and you need the answer in seconds, not after digging through deployment logs. Tag prompt versions semantically (triage-v3.2) and keep a changelog: what changed, what the eval delta was, who approved it.



---



Decomposing Multi-Step Workflows



The final pattern: never ask one prompt to diagnose, plan, and execute. Decompose multi-step DBA workflows into separate prompts with verification between steps. A query-regression workflow becomes three prompts — diagnose (is this a real regression? what changed?), plan (which corrective action, with what parameters?), verify (did the action resolve it?) — each with its own system prompt, its own output schema, and its own validation.



Decomposition buys you three things. First, each step is independently evaluable — you can measure diagnosis accuracy separately from planning quality. Second, verification steps between prompts catch compounding errors: if the diagnosis prompt hallucinates, the planning prompt receives structured findings it can sanity-check rather than raw prose it must trust. Third, different steps can use different models — a cheap, fast model for the initial triage classification and a stronger model for the final planning step — optimizing the cost curve from Chapter 31.



The orchestrator pattern is simple: each step's validated output becomes the next step's context, and any validation failure anywhere in the chain collapses to ALERT_HUMAN with the partial results attached. Partial automation that fails loudly beats full automation that fails silently.
