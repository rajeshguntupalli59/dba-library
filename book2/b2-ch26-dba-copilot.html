Chapter 26: Building a Conversational DBA Copilot

Every DBA team has the same bottleneck: a handful of senior engineers who hold the institutional knowledge of how the systems actually behave, and a growing queue of developers, analysts, and junior DBAs asking them questions. "Why is this query slow?" "Can I add this index?" "What happened at 3 AM?" A conversational DBA copilot — a chat interface backed by a language model with tools that can inspect your SQL Server environment — turns that queue into a self-service surface. This chapter builds one: a chat agent that answers DBA questions using live DMV data, Query Store history, and your runbook library, with the safety boundaries that keep a helpful assistant from becoming a destructive one.

---

The Tool-Using Agent Architecture

Reading the diagram left to right: the DBA User (blue) types into the Chat UI. The Copilot Service (purple) is the orchestrator — the Intent Router classifies the request (diagnosis, change, question) and the Context Builder assembles the evidence pack. The LLM Reasoning Engine (violet) never works from memory alone: it pulls downward from two sources — the Vector Knowledge Base (green: runbooks, ticket history, embeddings index) for "how we fixed this before," and SQL Server (teal: DMVs, Query Store, live telemetry) for "what is happening right now." The LLM's proposed answer or action then flows right into Guardrails (amber): a Policy Check (is this action class allowed?), a Human Approval Gate for anything that writes, and a Risk Score. Only validated, approved actions reach Safe Execution (green) — parameterized T-SQL, never string-concatenated — and every action lands in the Audit Log. The single most important arrow in the whole diagram is the one between Guardrails and Safe Execution: nothing the model dreams up touches production without passing through it.

A DBA copilot is an operator console in chat form. The operator asks in plain language; the copilot answers from two evidence sources: live telemetry pulled through read-only tools, and your own runbooks and incident history retrieved as quoted excerpts. Model memory and generic SQL Server advice are allowed only when explicitly labeled as such. That evidence contract is the whole product — the chat UI and the model API are commodity plumbing this chapter does not dwell on. What this chapter covers is the DBA-specific part: which tools the copilot needs, how runbook excerpts ground its answers, and the guardrails that keep a helpful assistant from executing a destructive action.

The single most important design decision: the LLM never writes free-form SQL. Every database interaction goes through a predefined tool with a fixed query template and validated parameters. The model decides which tool to call and what parameters to pass — it never concatenates its own T-SQL. This is the same boundary established in Chapter 10's runbook executor, and it matters even more here because the input is unconstrained natural language from users of varying skill levels.

---

Designing the Read-Only Tool Layer

Start with the questions DBAs actually get asked, and build one tool per question class. Five tools cover roughly eighty percent of copilot traffic: top wait stats, currently running queries, blocking chains, Query Store regression lookup, and index usage. Each tool is a Python function with a fixed T-SQL template, input validation, and a result-size cap so a single question cannot dump a million rows into the model's context window.

import pyodbc
import json
from dataclasses import dataclass

@dataclass
class CopilotTool:
    name: str
    description: str
    sql_template: str
    max_rows: int = 20

# Tool 1: top wait stats over a window — the "what is the server doing" tool
TOOL_WAIT_STATS = CopilotTool(
    name="get_top_waits",
    description="Returns the top wait types by total wait time. Use when diagnosing slowness.",
    sql_template="""
        SELECT TOP (?)
            wait_type,
            SUM(wait_time_ms) / 1000.0 AS total_wait_seconds,
            SUM(waiting_tasks_count) AS waiting_tasks,
            SUM(wait_time_ms) * 1.0 / NULLIF(SUM(waiting_tasks_count), 0) AS avg_wait_ms
        FROM sys.dm_os_wait_stats
        WHERE wait_type NOT IN (
            'SLEEP_TASK','BROKER_TO_FLUSH','BROKER_EVENTHANDLER','CHECKPOINT_QUEUE',
            'DBMIRROR_EVENTS_QUEUE','SQLTRACE_BUFFER_FLUSH','CLR_AUTO_EVENT',
            'DISPATCHER_QUEUE_SEMAPHORE','LAZYWRITER_SLEEP','XE_TIMER_EVENT'
        )
        GROUP BY wait_type
        ORDER BY total_wait_seconds DESC;
    """,
    max_rows=10,
)

# Tool 2: currently executing requests with blocking info
TOOL_ACTIVE_REQUESTS = CopilotTool(
    name="get_active_requests",
    description="Returns currently executing requests, their wait types, blocking sessions, and query text excerpts.",
    sql_template="""
        SELECT TOP (?)
            r.session_id,
            s.login_name,
            s.program_name,
            r.status,
            r.wait_type,
            r.wait_time / 1000.0 AS wait_seconds,
            r.blocking_session_id,
            DATEDIFF(SECOND, r.start_time, GETUTCDATE()) AS age_seconds,
            r.cpu_time,
            r.logical_reads,
            LEFT(st.text, 400) AS query_excerpt
        FROM sys.dm_exec_requests r
        JOIN sys.dm_exec_sessions s ON s.session_id = r.session_id
        CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) st
        WHERE r.session_id <> @@SPID
        ORDER BY age_seconds DESC;
    """,
    max_rows=15,
)

# Tool 3: Query Store regression lookup for a query text fragment
TOOL_QS_REGRESSION = CopilotTool(
    name="find_query_regressions",
    description="Finds queries in Query Store whose recent average duration is at least 50% worse than their best historical plan. Optional text filter.",
    sql_template="""
        SELECT TOP (?)
            qsq.query_id,
            LEFT(qsqt.query_sql_text, 300) AS query_text,
            qsrs.avg_duration / 1000.0 AS recent_avg_ms,
            qsrs_best.avg_duration / 1000.0 AS best_avg_ms,
            qsrs.count_executions
        FROM sys.query_store_query qsq
        JOIN sys.query_store_query_text qsqt ON qsqt.query_text_id = qsq.query_text_id
        JOIN sys.query_store_plan qsp ON qsp.query_id = qsq.query_id
        JOIN sys.query_store_runtime_stats qsrs ON qsrs.plan_id = qsp.plan_id
        JOIN sys.query_store_runtime_stats_interval qsrsi
            ON qsrsi.runtime_stats_interval_id = qsrs.runtime_stats_interval_id
        JOIN (
            SELECT qsp2.query_id, MIN(qsrs2.avg_duration) AS avg_duration
            FROM sys.query_store_plan qsp2
            JOIN sys.query_store_runtime_stats qsrs2 ON qsrs2.plan_id = qsp2.plan_id
            WHERE qsrs2.count_executions > 50
            GROUP BY qsp2.query_id
        ) qsrs_best ON qsrs_best.query_id = qsq.query_id
        WHERE qsrsi.start_time > DATEADD(HOUR, -4, GETUTCDATE())
          AND qsrs.count_executions > 10
          AND qsrs.avg_duration > qsrs_best.avg_duration * 1.5
          AND (? = '' OR qsqt.query_sql_text LIKE '%' + ? + '%')
        ORDER BY qsrs.avg_duration DESC;
    """,
    max_rows=10,
)

def run_tool(conn, tool: CopilotTool, *params) -> str:
    """Execute a copilot tool with validated parameters; returns JSON for the LLM."""
    with conn.cursor() as cur:
        cur.execute(tool.sql_template, params)
        cols = [c[0] for c in cur.description]
        rows = [dict(zip(cols, r)) for r in cur.fetchmany(tool.max_rows)]
    # Truncate long text fields so one tool call cannot flood the context
    for row in rows:
        for k, v in row.items():
            if isinstance(v, str) and len(v) > 600:
                row[k] = v[:600] + "…"
    return json.dumps(rows, default=str)

Notice the guardrails baked into the tool definitions: result caps, truncated text fields, a benign-wait filter on sys.dm_os_wait_stats, and parameter binding rather than string interpolation. The connection the tools use should run under a dedicated login granted only VIEW SERVER STATE and VIEW DATABASE STATE — no data access, no DDL, nothing the model can escalate.

Grounding Answers in Runbooks

Telemetry tells the copilot what is happening; runbooks tell it what your team does about it. When a question concerns an operational procedure — failing over an availability group, responding to corruption, clearing a blocking chain — the copilot must retrieve the relevant runbook excerpt and quote it, citing the document ID. It never improvises procedures from model memory. Operational answers without a runbook citation are treated as drafts, not guidance. The retrieval mechanics live in Chapter 28; the rule that matters here is the evidence contract: no cited runbook, no procedure.

COPILOT_SYSTEM_PROMPT = """
You are a senior SQL Server DBA assistant. You answer questions about the SQL Server
environment using ONLY data returned by your tools. Rules:

1. Never invent wait stats, query text, or performance numbers. If a tool returns
   no rows, say so explicitly.
2. When diagnosing slowness, always check get_top_waits AND get_active_requests
   before concluding. Correlate the two: a top wait of CXPACKET with no active
   parallel queries means the waits are historical, not current.
3. Explain your reasoning in plain language, then cite the specific tool output
   that supports each claim.
4. For operational procedures (failover, corruption response, blocking remediation),
   you MUST quote the relevant runbook excerpt supplied in context and cite its
   document ID. If no runbook excerpt was retrieved, say so and decline to give
   procedural guidance — never improvise a procedure from memory.
5. You may suggest remediation (e.g., "consider updating statistics on dbo.Orders"),
   but you may NOT execute any write operation. State that writes require a DBA.
6. If the question is about schema design, T-SQL syntax, or general SQL Server
   knowledge, answer from your training but label it as general guidance, not
   observations about this environment.
7. Keep answers under 250 words unless the user asks for detail.
"""

def copilot_answer(user_question: str, conn, llm_client, tools: list[CopilotTool],
                   max_tool_rounds: int = 4) -> str:
    """Run the tool-use loop for one user question."""
    tool_schemas = [{
        "name": t.name,
        "description": t.description,
        "input_schema": {
            "type": "object",
            "properties": {
                "limit": {"type": "integer", "description": "max rows, capped at tool max_rows"},
                "text_filter": {"type": "string", "description": "optional query text fragment"}
            }
        }
    } for t in tools]

    messages = [{"role": "user", "content": user_question}]

    for _ in range(max_tool_rounds):
        response = llm_client.messages.create(
            model="claude-opus-4-5",
            max_tokens=1500,
            system=COPILOT_SYSTEM_PROMPT,
            tools=tool_schemas,
            messages=messages,
        )

        # If the model stopped calling tools, return its final text
        tool_uses = [b for b in response.content if b.type == "tool_use"]
        if not tool_uses:
            return "".join(b.text for b in response.content if b.type == "text")

        messages.append({"role": "assistant", "content": response.content})

        tool_results = []
        for tu in tool_uses:
            tool = next(t for t in tools if t.name == tu.name)
            args = tu.input or {}
            limit = min(int(args.get("limit", tool.max_rows)), tool.max_rows)
            text_filter = str(args.get("text_filter", ""))[:100]
            try:
                if tool.name == "find_query_regressions":
                    result = run_tool(conn, tool, limit, text_filter, text_filter)
                else:
                    result = run_tool(conn, tool, limit)
            except Exception as e:
                result = json.dumps({"error": f"tool failed: {type(e).__name__}"})
            tool_results.append({
                "type": "tool_result",
                "tool_use_id": tu.id,
                "content": result,
            })
        messages.append({"role": "user", "content": tool_results})

    return "I hit my tool-call limit before reaching an answer. A DBA should take a look."

The max_tool_rounds cap is a cost and safety control — it bounds both API spend per question and the blast radius of a model stuck in a tool-call loop. The text filter is length-capped before it reaches the query so a hostile or accidental input cannot smuggle anything meaningful past parameter binding. And the fallback message at the end is intentional: when the agent cannot converge, it says so rather than guessing.

Prompt Design for Accurate T-SQL Guidance

A copilot that only reads DMVs is useful; one that also helps developers write better T-SQL is indispensable. But this is where hallucination risk is highest — the model generating OPTION hints, index DDL, or query rewrites from memory. The mitigation is grounding: whenever the user asks for a rewrite or an index recommendation, the orchestrator first pulls the actual query plan and statistics, then asks the model to reason from that concrete evidence.

The practical pattern is a "show your work" system-prompt addendum for tuning questions: the model must (1) state what the plan shows, (2) identify the specific operator or estimate problem, and (3) propose the change with the expected mechanism ("this converts the scan to a seek because…"). Recommendations that cannot name a mechanism are rejected by reviewers — and you should have reviewers. Route every index or hint recommendation the copilot makes into a review queue (a table or a Teams channel) where a DBA approves before anything touches production. Chapter 4's AI query tuning patterns plug in here directly.

One more prompt-design lesson from production deployments: give the copilot a sense of your environment's conventions. A few lines in the system prompt — "this shop uses Ola Hallengren's maintenance solution, Query Store is enabled on all user databases, AGs run in synchronous commit" — dramatically improve answer relevance. Maintain this as a short environment brief, versioned in source control, injected into every conversation.

Approval-Gated Write Actions

Read-only answers cover most questions, but the real productivity unlock is letting the copilot perform safe, reversible writes: killing a blocked session that everyone agrees is stuck, updating statistics on a table, forcing a known-good Query Store plan. Each of these maps to a parameterized action tool behind the same gating pattern from Chapter 10 — auto-execute for the low-risk reversible set, approval-required for the rest, escalate for everything else.

# Write-action tool: kill a session, with pre-flight validation
KILL_SESSION_SQL = """
    -- Pre-flight: confirm the session exists and is not a system session
    SELECT session_id, login_name, program_name, status,
           open_transaction_count,
           DATEDIFF(SECOND, last_request_start_time, GETUTCDATE()) AS last_batch_age_s
    FROM sys.dm_exec_sessions
    WHERE session_id = ?
      AND session_id > 50
      AND is_user_process = 1;
"""

def request_kill_session(conn, session_id: int) -> dict:
    with conn.cursor() as cur:
        cur.execute(KILL_SESSION_SQL, (session_id,))
        row = cur.fetchone()
        if not row:
            return {"approved": False, "reason": "session not found or is a system session"}
        cols = [c[0] for c in cur.description]
        info = dict(zip(cols, row))
    # Never auto-kill a session holding an open transaction without approval
    if info["open_transaction_count"] > 0:
        return {"approved": False, "reason": "session holds open transactions; needs DBA approval",
                "session": info}
    return {"approved": True, "session": info}

The kill path shows the principle: even "approved" actions run pre-flight checks in T-SQL first. The tool validates the session is a user process, checks for open transactions, and returns structured data the orchestrator uses to decide whether to proceed or route to a human. Every executed write — who asked, what was validated, what ran, what happened — goes into the audit table from Chapter 10. Over time, that audit log becomes training data for tightening the approval policy: actions with a 100% clean record graduate to auto-execute; anything with a single bad outcome stays gated.

Evaluating the Copilot Before Rollout

Do not roll out a copilot on vibes. Build a golden question set: 30–50 real questions your team has answered in the past, each paired with the correct answer or the correct diagnostic conclusion, drawn from actual incidents. Run the copilot against the set in a staging environment with a restored copy of production telemetry, and score it: did it call the right tools, did it cite real data, did it reach the right conclusion, did it refuse appropriately when data was missing?

Track three metrics per question: tool precision (did it call the tools a senior DBA would call, no more), grounding rate (what fraction of factual claims trace to tool output), and abstention quality (when the data was insufficient, did it say so). A copilot that scores 90% on tool precision but 60% on abstention quality is dangerous — it confidently answers questions it should decline. Set your rollout bar on the weakest metric, not the average.

Re-run the golden set weekly after rollout. Copilot quality drifts: models get updated, your environment brief goes stale, new wait types appear. The golden set is your regression suite. When a score drops, the fix is usually in the system prompt or the tool definitions, not the model — add the missing tool, tighten the instruction, update the environment brief.

---

Key Takeaways

  • → **The LLM never writes free-form SQL.** A DBA copilot is a tool-using agent: the model reasons in language and selects tools, but every database interaction goes through a fixed, parameterized template executed under a least-privilege login.
  • → **Build one tool per question class, with result caps and input validation.** Top waits, active requests, blocking chains, and Query Store regressions cover most traffic; cap rows, truncate long text, and length-limit every parameter before it reaches the query.
  • → **The system prompt encodes DBA judgment — including the runbook rule.** Rules like "check both waits and active requests before diagnosing" and "quote the runbook excerpt and cite its document ID, or decline procedural guidance" are what separate a useful copilot from a confident guesser.
  • → **Write actions need pre-flight validation plus the Chapter 10 gating pattern.** Even approved kills validate the session in T-SQL first; audit every execution and let clean audit history graduate actions to auto-execute.
  • → **Evaluate with a golden question set before rollout and re-run it weekly.** Score tool precision, grounding rate, and abstention quality — and set your rollout bar on the weakest metric, because confident wrong answers are the failure mode that matters.
