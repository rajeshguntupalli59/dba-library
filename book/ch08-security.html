Chapter 8: Security Foundations

Security is the layer of your database infrastructure that, when done right, nobody notices — and when done wrong, becomes the headline. Whether you're managing a healthcare system bound by HIPAA requirements, a financial platform subject to PCI-DSS audits, or a startup that just doesn't want its customer data on Pastebin, the principles are the same: control who gets in, control what they can do once they're inside, and know what happened after the fact. This chapter walks through the foundational security model of SQL Server — from authentication and authorization through privilege management, row-level security, auditing, and encryption at rest and in transit. The goal is to give you the mental model and the practical tools to build a defensible database environment, not just one that passes a checkbox audit.

---

How Authentication Works — and Where It Can Go Wrong

Authentication answers a single question: are you who you claim to be? SQL Server answers it with two authentication modes and a layered login system — and misconfiguring that layer is one of the most common findings in security audits.

SQL Server's authentication is controlled by the server's authentication mode: Windows Authentication mode (only Windows/AD identities) or Mixed Mode (Windows plus SQL Server logins). It's set at install time and changeable under Server Properties → Security in SSMS, requiring a restart. The mode is the first thing to check when a login fails that "should" work — a SQL login cannot authenticate at all against a Windows-only instance, and the error log won't always make that obvious.

For SQL logins, enforce password policy with CHECK_POLICY=ON and CHECK_EXPIRATION=ON so domain complexity and expiry rules apply to database passwords too. Prefer Windows/AD authentication wherever possible — it delegates credential management to the domain, supports Kerberos (verify with the auth_scheme column in sys.dm_exec_connections), removes passwords from connection strings, and makes deprovisioning a matter of disabling one AD account instead of hunting logins across instances.

SQL Server takes a different approach with two authentication modes: Windows Authentication (also called Integrated Security) and SQL Server Authentication (username and password stored in SQL Server itself). Mixed Mode enables both. In domain-joined environments, Windows Authentication is the stronger choice — credentials are managed by Active Directory, password policies are enforced by Group Policy, and Kerberos or NTLM handles the handshake without passwords appearing in connection strings. SQL Server Authentication has its place — cloud environments, cross-domain connections, application service accounts that can't use Kerberos — but it puts the burden of credential management back on the DBA.

A common production mistake is leaving the highest-privileged accounts reachable from the network. The sa login should be disabled outright in most production environments — and renamed as well, so attackers can't target a known account name. AD service accounts and application logins should carry only the privileges they need. If sa must exist for break-glass, give it a long random password stored in a vault, and alert on any use of it.

You can inspect active authentication configuration in both systems:

SQL Server exposes login metadata through sys.server_principals and sys.sql_logins — you can audit which logins exist, which are disabled, whether password policy is enforced, and when passwords were last changed. sys.dm_exec_connections shows the auth scheme (NTLM, Kerberos, or SQL) per live session, which is how you confirm Kerberos is actually being used rather than assumed.

-- Check the server authentication mode (1 = Windows only, 2 = Mixed)
SELECT SERVERPROPERTY('IsIntegratedSecurityOnly') AS windows_auth_only;

-- Review all logins, their type, and whether they are enabled
SELECT name,
       type_desc,
       is_disabled,
       create_date,
       modify_date
FROM sys.server_principals
WHERE type IN ('S', 'U', 'G')  -- SQL login, Windows user, Windows group
ORDER BY type_desc, name;

One trap worth calling out explicitly: SQL logins created with CHECK_POLICY=OFF and a weak password, or applications connecting as sa "temporarily" and never being fixed. Another is the service account running as a domain admin because the installer needed it once. The principle is defense in depth — every layer (network, login, database, object) should independently require proof, because attackers only need one layer to fail.

Users, Roles, and the Principle of Least Privilege

Once a connection is authenticated, the database needs to know what that identity is allowed to do. SQL Server uses a two-tier role-based model — server-level logins and roles, database-level users and roles — and the mechanics repay precise understanding, because this is where least privilege is actually implemented.

In SQL Server, the hierarchy is: login (the server-level identity, Windows or SQL) → user (the database-level identity mapped to a login) → role membership (fixed server roles like sysadmin, fixed database roles like db_owner, and user-defined database roles you create). Permissions are granted to roles, and roles are granted to users — never grant permissions directly to individual users if you want access changes to stay auditable and reversible. Contained databases collapse the two tiers: the user authenticates directly at the database level with no server login, which simplifies Availability Group failovers and migrations because there's no SID to orphan.

SQL Server separates server-level principals (logins) from database-level principals (users). A login authenticates at the server. A database user maps to a login (or is a contained user, or maps to a certificate or asymmetric key) and holds permissions within a specific database. This two-tier model gives you granular control — a login can exist at the server level without having access to any individual database, or can be mapped to a guest account, or can be given different database-level identities in different databases.

The practical implication is that SQL Server requires two steps to give someone database access: create the login, then create the user in the target database and map it to that login. The classic failure is the orphaned user — a database user whose login no longer exists (different SID) after a restore or migration. ALTER USER ... WITH LOGIN repairs the mapping, and auditing for orphaned users should be part of every restore validation.

-- Step 1: Create a server-level login
CREATE LOGIN app_user WITH PASSWORD = 'use_a_strong_password_here';

-- Step 2: In the target database, create a user mapped to that login
USE OrdersDB;
CREATE USER app_user FOR LOGIN app_user;

-- Create a database role to hold permissions
CREATE ROLE app_readonly;

-- Assign the user to the role
ALTER ROLE app_readonly ADD MEMBER app_user;

-- Grant the role read access to a schema
GRANT SELECT ON SCHEMA::orders TO app_readonly;

The principle of least privilege is not just a compliance checkbox — it's practical defense. An application that only reads data from a reporting schema should not hold INSERT, UPDATE, or DELETE on that schema, and it certainly should not hold schema ownership or DDL privileges. In practice, DBAs often find that developers were given db_owner during development and that role was never narrowed before production deployment. Auditing existing privileges is the first step to correcting this.

In SQL Server, sys.database_permissions, sys.server_permissions, and fn_my_permissions are your tools for auditing who can do what — run them before every compliance review, not after the auditor asks.

-- List all explicit permissions in the current database
SELECT dp.name         AS principal,
       dp.type_desc    AS principal_type,
       perm.class_desc AS object_class,
       perm.permission_name,
       perm.state_desc AS grant_state,
       OBJECT_NAME(perm.major_id) AS object_name
FROM sys.database_permissions perm
JOIN sys.database_principals dp
  ON dp.principal_id = perm.grantee_principal_id
WHERE dp.name NOT IN ('public', 'sys', 'INFORMATION_SCHEMA')
ORDER BY dp.name, perm.class_desc, object_name;

One pattern worth institutionalizing: never grant permissions directly to individual users. Always grant to roles, and assign users to roles. This makes permission management auditable and maintainable — when an employee changes teams or leaves, you change role membership, not dozens of individual permission grants scattered across dozens of objects.

Row-Level Security — Controlling What Data Each User Sees

Privilege grants at the table level are coarse instruments. They answer the question "can this role access this table?" but they can't answer "can this role access *these rows* in this table?" Row-Level Security (RLS) answers that second question, and it does so in a way that is enforced by the database engine itself — not by application code, which can be bypassed.

SQL Server supports Row-Level Security on a simple conceptual model: you define a policy that adds a filter expression to queries against a table. When a user queries the table, the engine automatically appends that filter condition, as though the user had written it in their WHERE clause — except they can't remove it.

In SQL Server, RLS is implemented with a predicate function — an inline table-valued function returning 1 for allowed rows — bound to the table via CREATE SECURITY POLICY. The filter predicate applies to reads; block predicates can reject writes that would violate the policy. Members of db_owner bypass RLS predicates by default, so design your ETL and service accounts with that in mind rather than discovering it during a test.

A canonical example: a multi-tenant SaaS platform where one table stores orders for all tenants. Each tenant's application authenticates as a dedicated database role, and you want to guarantee at the database level that Tenant A can never read Tenant B's rows.

-- Create a schema to hold the security predicate function
CREATE SCHEMA Security;
GO

-- The predicate function returns 1 (allow) or 0 (deny)
CREATE FUNCTION Security.fn_tenant_predicate (@tenant_id NVARCHAR(100))
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN SELECT 1 AS fn_result
       WHERE @tenant_id = USER_NAME();
GO

-- Create a security policy binding the predicate to the table
CREATE SECURITY POLICY TenantIsolationPolicy
  ADD FILTER PREDICATE Security.fn_tenant_predicate(tenant_id)
    ON orders.line_items,
  ADD BLOCK PREDICATE Security.fn_tenant_predicate(tenant_id)
    ON orders.line_items AFTER INSERT
WITH (STATE = ON);
GO

SQL Server's approach separates the predicate logic (an inline table-valued function) from the policy binding, which gives you more flexibility — you can update the function without recreating the policy — but it also means you have an additional object to manage and secure. The function itself must be protected from modification by anyone other than the security administrator.

A nuance: if a role needs to bypass RLS for administrative purposes (running ETL, batch updates, producing audit reports), it must be db_owner or the policy must explicitly exempt it — grant that sparingly, and document why. For application roles, the policy is always enforced. Test RLS with EXECUTE AS to verify each role sees exactly its rows before you declare the feature done.

Performance is a legitimate concern with RLS. Every query against a protected table gets the predicate joined in, and if the predicate column isn't indexed, you're doing full table scans on every single row access. Index the columns referenced in your RLS predicates. In a multi-tenant scenario, a composite index on (tenant_id, created_at) or similar is not optional — it's required for acceptable performance at scale.

Auditing — Building a Trail You Can Actually Use

Knowing what's happening in your database right now is important. Knowing what happened three weeks ago when a data anomaly is discovered is irreplaceable. Auditing is the discipline of recording who did what, to which objects, at what time — and storing that record in a way that can't be quietly altered.

SQL Server ships a built-in audit framework: SQL Server Audit. Server audits write to the Security log, the Application log, or files; database audit specifications capture statement-level and object-level events with proper session context. Unlike text logs, audit output is structured and queryable via sys.fn_get_audit_file. Write audit output to a volume the DBAs don't casually browse, and ship it off the database server — an audit trail the audited party can edit is theater, not compliance.

You configure SQL Server Audit with CREATE SERVER AUDIT (where output goes, and what happens on audit failure — shut the server down or keep running), then CREATE DATABASE AUDIT SPECIFICATION for the events you care about: SELECT/INSERT/UPDATE/DELETE on sensitive tables, failed logins, permission and role changes. Audit at the granularity your compliance regime requires; auditing everything is how you fill a disk at 3 a.m.:

-- SQL Server has a built-in Server Audit mechanism

-- Step 1: Create a server audit (writes to Windows Event Log here,
--         but file destination is common for compliance)
CREATE SERVER AUDIT OrdersDBAudit
  TO APPLICATION_LOG
  WITH (QUEUE_DELAY = 1000, ON_FAILURE = CONTINUE);
GO

-- Step 2: Create a database audit specification
USE OrdersDB;
CREATE DATABASE AUDIT SPECIFICATION AuditLineItemAccess
  FOR SERVER AUDIT OrdersDBAudit
  ADD (SELECT, INSERT, UPDATE, DELETE
       ON orders.line_items BY public)
WITH (STATE = ON);
GO

-- Step 3: Enable the server audit
ALTER SERVER AUDIT OrdersDBAudit WITH (STATE = ON);
GO

-- Query the audit log
SELECT event_time, action_id, succeeded,
       server_principal_name, database_name,
       object_name, statement
FROM sys.fn_get_audit_file
  ('C:\AuditLogs\OrdersDBAudit_*.sqlaudit', DEFAULT, DEFAULT)
ORDER BY event_time DESC;

SQL Server's audit system is more fully integrated — it ships in the box, writes structured records to queryable files, supports both server-level and database-level specifications, and can write to Windows Event Log, Security Log, or binary files. The binary file format is tamper-evident by design: SQL Server uses a hash chain across audit records so any deletion or modification of records is detectable.

Several things are worth being deliberate about when designing an audit strategy. First, audit data should not live on the same server as the database it's auditing — an attacker who compromises the database server should not be able to silently wipe the evidence. Ship audit logs to a centralized SIEM or append-only log store. Second, be thoughtful about what you audit — logging every SELECT in a high-throughput OLTP system can generate enough volume to degrade performance and to make the logs themselves unmanageable. Audit writes and DDL universally; audit reads selectively based on data sensitivity classification. Third, establish a retention policy that meets your regulatory requirements before you need it — discovering during an incident response that logs only go back 14 days when the breach started 30 days ago is a particularly unpleasant experience.

Encryption — Protecting Data in Transit and at Rest

Authentication tells you who is connecting. Auditing tells you what they did. Encryption protects the data itself — from eavesdropping on the wire, from being read if storage media is stolen, and from unauthorized access to backup files. These are three distinct problems that require three distinct mechanisms.

Encryption in Transit

SQL Server encrypts connections with TLS using a certificate installed in the machine certificate store, configured via SQL Server Configuration Manager. Enable the Force Encryption flag so unencrypted connections are refused, and on the client use Encrypt=yes with TrustServerCertificate=no so the certificate chain is actually validated. In production, full verification is the right choice — encryption without certificate verification is susceptible to man-in-the-middle attacks.

In SQL Server, TLS is enabled by obtaining a certificate, binding it to the SQL Server service via SQL Server Configuration Manager, and setting "Force Encryption" to Yes. Applications connect with Encrypt=True;TrustServerCertificate=False in the connection string — the TrustServerCertificate=False portion forces certificate validation, which is the difference between actual protection and theater.

Encryption at Rest

SQL Server's Transparent Data Encryption (TDE) encrypts the data files, log files, and backups at the storage level using a database encryption key (DEK) protected by a certificate or asymmetric key stored in the master database (or, in enterprise deployments, in Azure Key Vault or an HSM via Extensible Key Management). The application sees nothing different — all encryption and decryption happens in the buffer pool, transparent to queries.

-- Check TDE status across all databases
SELECT db.name,
       dek.encryption_state,
       dek.encryption_state_desc,
       dek.key_algorithm,
       dek.key_length,
       dek.percent_complete
FROM sys.dm_database_encryption_keys dek
JOIN sys.databases db ON db.database_id = dek.database_id
ORDER BY db.name;

-- Enable TDE on a database (certificate must already exist in master)
USE master;
CREATE MASTER KEY ENCRYPTION BY PASSWORD = 'StrongPassphraseHere!';
CREATE CERTIFICATE TDECert WITH SUBJECT = 'TDE Certificate for OrdersDB';

USE OrdersDB;
CREATE DATABASE ENCRYPTION KEY
  WITH ALGORITHM = AES_256
  ENCRYPTION BY SERVER CERTIFICATE TDECert;
ALTER DATABASE OrdersDB SET ENCRYPTION ON;

SQL Server's Transparent Data Encryption encrypts data files, log files, and backups at the storage engine level via a database encryption key protected by a certificate in master. Enable it with CREATE DATABASE ENCRYPTION KEY followed by ALTER DATABASE ... SET ENCRYPTION ON — then immediately back up the certificate and private key and store them off-server, because without them your backups are unrecoverable. TDE protects against physical media theft; it does not protect against a compromised sysadmin, which is what auditing and Always Encrypted are for.

Column-Level Encryption

For highly sensitive fields — Social Security numbers, credit card numbers, medical identifiers — you may want encryption that is visible at the column level, so that even users with table access can't read the plaintext values unless they hold the key. Both systems support this, but the operational complexity is significantly higher.

For column-level protection, SQL Server offers Always Encrypted: the column encryption keys live on the client side — the database server itself never sees the plaintext, which protects against a compromised DBA or backup theft. The tradeoff is limited query capability on encrypted columns (deterministic encryption supports equality, randomized does not) and driver requirements on every client. Use it for specific high-sensitivity fields like SSNs or card numbers, not whole tables.

The trade-off is functionality: encrypted columns cannot be indexed in the normal sense, can't be used in WHERE clause comparisons without decrypting first (unless using randomized versus deterministic encryption carefully), and require application-level key management. These are real constraints that affect schema design, query patterns, and operational procedures. Column-level encryption is the right choice for specific high-value fields, not a blanket approach for entire tables.

Hardening a Database in a Real Production Environment

Understanding individual security mechanisms is necessary but not sufficient. A hardened production database is a system where all these mechanisms work together and where the configuration has been deliberately reviewed rather than left at defaults.

The defaults in SQL Server are designed for broad compatibility and ease of getting started, not for security. The public role has EXECUTE permission on a set of system stored procedures by default, which is a larger attack surface than most organizations realize — audit public-role grants and revoke what applications don't need. Also review the guest user in each database and disable it where it isn't required.

A useful starting exercise is enumerating what's listening and who can reach it. The SQL Server port (1433 by default) should be reachable only from application servers, not from developer laptops, not from the general office network, and certainly not from the internet. Network-level controls and database-level authentication are separate layers — having both means an attacker must defeat two independent controls rather than one.

sa-level accounts deserve special treatment. Their use should be exceptional, logged, and ideally require a break-glass procedure. sa should be disabled and renamed; all routine administrative tasks should be performed as AD service accounts or application logins carrying only the necessary privileges.

Object ownership is another overlooked surface. In SQL Server, the schema owner (often dbo) controls the objects — application roles should not own production schemas. And beware ownership chaining: when a stored procedure and the tables it touches share the same owner, the procedure can access those tables without explicit grants on them. That's convenient, but it means a compromised procedure account inherits broad read access — review chained access paths, not just direct grants.

-- Identify server-level roles and their members
SELECT r.name AS server_role,
       m.name AS member_name,
       m.type_desc
FROM sys.server_role_members rm
JOIN sys.server_principals r ON r.principal_id = rm.role_principal_id
JOIN sys.server_principals m ON m.principal_id = rm.member_principal_id
WHERE r.name IN ('sysadmin', 'securityadmin', 'serveradmin')
ORDER BY r.name, m.name;

-- Check whether sa is disabled (it should be)
SELECT name, is_disabled
FROM sys.server_principals
WHERE name = 'sa';

Periodic privilege reviews should be formalized, not left to "we'll do it eventually." A recurring review that produces a report of all roles, members, and permission grants — compared against the previous review — catches privilege creep before it becomes a liability. Privilege creep is the natural byproduct of normal operations: a developer gets temporary elevated access to debug a production incident, and the access is never revoked; a role is granted broad permissions because narrowing them correctly would have taken longer than the deadline allowed. None of these grants look dangerous in isolation. Reviewed as a whole, on a schedule, they are how a well-designed permission model quietly turns into an open one.

Finally, security hardening is not a project with an end date. New objects get created without the right ownership, new roles get added without the right memberships, and new features (a new API endpoint, a new reporting tool) create new access patterns that the original security review never considered. Treat hardening as a continuous practice tied to your change management process — every schema change, every new service account, and every new integration is an opportunity to either maintain the security posture you built or quietly erode it.

---

Key Takeaways

  • → Authentication configuration lives in the server's authentication mode setting and in the login inventory (`sys.server_principals`, `sys.sql_logins`); audit for weak methods (`CHECK_POLICY=OFF`, `sa` left enabled, NTLM where Kerberos was intended) rather than trusting it was configured correctly once and left alone.
  • → SQL Server's two-tier login/user model exists to serve least-privilege access; grant permissions to roles, not individual users, so access changes are auditable and reversible — and hunt orphaned users after every restore or migration.
  • → Row-Level Security, enforced by the database engine itself, is the right tool when access needs to be restricted by row content (like tenant isolation) rather than by table — but predicate columns must be indexed or performance suffers badly at scale, and always verify with `EXECUTE AS` before shipping.
  • → Auditing requires a real strategy, not just default logging: SQL Server Audit gives you a structured, queryable, object-level audit trail built in — but audit logs must be shipped off the database server itself, or they protect no one.
  • → Encryption is three separate problems — in transit (TLS with full certificate verification), at rest (TDE, with the certificate backed up off-server or your backups are worthless), and at the column level for specific high-sensitivity fields (Always Encrypted) — and hardening a production database is an ongoing discipline tied to change management, not a one-time checklist.
