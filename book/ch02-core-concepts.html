Chapter 2: Understanding the Core Concepts

Before you can write efficient queries, design reliable schemas, or troubleshoot production issues, you need a firm grip on how relational databases actually think. SQL Server is built on decades of relational theory, and this chapter walks through the core concepts that every DBA and developer must internalize — from how relational data is organized, to how transactions protect your data, to how the engine's architecture shapes everyday behavior. Understanding these building blocks will make everything else in this book click into place.

---

How Relational Databases Organize Data

At its heart, a relational database stores data in tables — structured grids of rows and columns. Each table represents a single entity type: customers, orders, products. Each row is one instance of that entity, and each column holds a specific attribute of that entity. This sounds simple, and it is. The elegance of the relational model lies in what you can do with that simplicity.

The concept was formalized by Edgar F. Codd in 1970, and the rules he established — known as Codd's relational rules — are still the theoretical backbone of every major relational database today. The most important practical idea from that work is that data should be stored without redundancy and that relationships between entities should be expressed through keys, not through embedding one table's data inside another.

A primary key is a column or set of columns that uniquely identifies every row in a table. No two rows can share the same primary key value. In practice, most tables use either a surrogate key — an auto-generated integer or UUID with no business meaning — or a natural key, which is a value that already exists in the real world and is inherently unique, like a tax identification number.

A foreign key enforces a relationship between two tables. It says: the value in this column must exist as a primary key in that other table. When you have an orders table with a customer_id column, the foreign key constraint ensures you can never create an order that points to a nonexistent customer. This referential integrity is one of the most valuable guarantees a relational database provides — and one of the most commonly disabled by developers who don't understand the cost of losing it.

Normalization is the process of structuring tables to eliminate data redundancy and dependency anomalies. First Normal Form (1NF) requires that every column holds atomic values — no lists, no repeating groups. Second Normal Form (2NF) requires that every non-key column depends on the entire primary key, not just part of it. Third Normal Form (3NF) requires that non-key columns depend only on the primary key, not on each other. In practice, most production schemas target 3NF as a baseline, with strategic denormalization applied in specific places for performance reasons.

Data Types: Choosing the Right Tool for the Column

Every column in a relational table has a data type, and that choice matters more than most developers initially appreciate. The right data type enforces correctness at the storage level, reduces storage overhead, and enables the query engine to process data more efficiently.

SQL Server's data types each carry specific storage, behavior, and performance characteristics — and choosing well at design time prevents expensive migrations later.

Integers are the most common data type for identifiers and counts. Both databases offer small, regular, and large integer variants.

-- Integer variants in SQL Server
CREATE TABLE product_catalog (
    product_id    INT IDENTITY(1,1) PRIMARY KEY,  -- auto-incrementing 4-byte integer
    sku_code      SMALLINT,                        -- 2-byte integer
    warehouse_id  INT,                             -- 4-byte integer
    total_units   BIGINT                           -- 8-byte integer for large counts
);

One of the most consequential data type choices you will make is how to store text. In SQL Server, VARCHAR(n) and NVARCHAR(n) are the standard choices. NVARCHAR stores Unicode data using two bytes per character and should be used whenever you store multilingual content — or data that may one day become multilingual. A common production mistake is using NVARCHAR(MAX) for every text column — this disables certain indexing optimizations, inflates storage, and pushes large values off-row into LOB allocation units. Size your text columns deliberately: VARCHAR(100) for a name, NVARCHAR(4000) for a description, and (MAX) only when the data genuinely has no bound.

Dates and timestamps deserve deliberate choice. SQL Server's DATETIMEOFFSET carries the UTC offset with the value itself, making it the right type for any application that runs across multiple time zones or stores audit records — a timestamp without its offset is ambiguous the moment it leaves the server that wrote it. For date-and-time values where the zone is fixed by convention, DATETIME2 offers better precision and range than the legacy DATETIME type and should be your default. Avoid DATETIME in new schemas: its 3.33-millisecond rounding and narrower range are historical baggage.

JSON storage is a first-class concern in modern SQL Server. There is no native JSON column type; instead, JSON documents live in NVARCHAR columns and the engine provides a rich function library — OPENJSON to shred documents into rows, JSON_VALUE and JSON_QUERY to extract scalars and fragments, FOR JSON to serialize query results — plus the ability to index frequently-queried JSON properties through computed columns. This keeps semi-structured data inside the relational engine with full transactional guarantees, but it rewards discipline: validate JSON with ISJSON() check constraints, index the properties you filter on, and never let a JSON column become an excuse to skip schema design.

Choosing NUMERIC(precision, scale) or DECIMAL for financial figures is non-negotiable. Floating-point types (FLOAT, REAL, DOUBLE PRECISION) are approximations — they cannot exactly represent many decimal fractions, and you will eventually see rounding errors in financial calculations if you use them.

NULL: The Three-Valued Logic Problem

NULL is the most misunderstood concept in SQL, and it causes real production bugs. NULL does not mean zero, empty string, or unknown-but-similar. NULL means the absence of a value. And because of this, SQL operates under three-valued logic: a comparison can be TRUE, FALSE, or UNKNOWN.

When you compare any value to NULL using an equality operator, the result is UNKNOWN — not FALSE. This is why WHERE column = NULL never returns rows. The correct test is WHERE column IS NULL. This behavior catches developers off guard most often in WHERE clause filters and JOIN conditions.

Consider what happens with an outer join:

-- Finding customers with no orders using LEFT JOIN and NULL check
SELECT
    c.customer_id,
    c.customer_name,
    o.order_id
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;

The query is identical here, but the underlying behavior differs when NULL propagation enters aggregate functions. Both databases correctly ignore NULLs in SUM(), AVG(), MIN(), and MAX(). But COUNT(column) counts only non-NULL values, while COUNT(*) counts all rows. This distinction has tripped up many a reporting query.

NULL also interacts with NOT IN in a particularly dangerous way. If a subquery used with NOT IN returns even one NULL value, the entire NOT IN expression evaluates to UNKNOWN for every row, and the outer query returns zero results. In production, this manifests as a query that silently returns no data and no error. The safest pattern when using subquery exclusions is NOT EXISTS.

SQL Server's COALESCE function returns the first non-NULL value in a list — the standard, portable way to substitute a default for a NULL. SQL Server also has ISNULL(value, replacement), a two-argument shortcut, but COALESCE is preferred: it is part of the SQL standard, accepts more than two arguments, and follows standard data-type precedence rules that ISNULL does not.

Transactions, ACID, and What They Actually Mean in Practice

A transaction is a unit of work that either completes entirely or does not happen at all. The ACID properties — Atomicity, Consistency, Isolation, and Durability — define what guarantees a transaction must provide. These are not aspirational goals; they are contractual obligations that the database engine upholds at the cost of significant engineering complexity.

Atomicity means all operations in a transaction succeed, or all are rolled back. If you are transferring funds between two bank accounts — debiting one and crediting the other — atomicity ensures you can never debit without also crediting. A crash between the two operations leaves neither change in the database.

Consistency means the database moves from one valid state to another. Constraint checking — primary keys, foreign keys, check constraints — happens within the transaction boundary and ensures that a committed transaction never violates the schema's rules.

Isolation determines how concurrent transactions interact with each other. SQL defines four isolation levels: Read Uncommitted, Read Committed, Repeatable Read, and Serializable. Most production systems run at Read Committed, which prevents dirty reads but allows non-repeatable reads and phantom reads. SQL Server implements Read Committed using locking by default — readers can block writers, and writers can block readers. Enabling Read Committed Snapshot Isolation (RCSI) switches the engine to row versioning for reads: readers see a consistent snapshot served from tempdb and never block writers. RCSI is one of the highest-impact configuration decisions you will make, and most OLTP systems run better with it on — at the cost of tempdb capacity you must plan for.

Durability means once a transaction is committed, it survives even a power failure. SQL Server accomplishes this through the transaction log: every change is written to the log before it is applied to the data files (write-ahead logging), so the log can be replayed after a crash. The transaction log is the single most important file in your SQL Server deployment — it is what makes point-in-time recovery possible, what availability groups ship to secondaries, and what fills up and halts all writes when nobody is backing it up.

Explicit transaction control is straightforward in both systems:

-- Explicit transaction with error handling in SQL Server (T-SQL)
BEGIN TRANSACTION;

BEGIN TRY
    UPDATE accounts SET balance = balance - 500.00 WHERE account_id = 101;
    UPDATE accounts SET balance = balance + 500.00 WHERE account_id = 202;
    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    ROLLBACK TRANSACTION;
    THROW;  -- re-raise the original error to the caller
END CATCH;

Error handling inside transactions deserves your full attention. By default, SQL Server does not abort an entire transaction when a single statement raises an error — the transaction stays open, locks stay held, and a subsequent COMMIT will happily commit partial work. This is why SET XACT_ABORT ON is a recommended practice in stored procedures: it makes any statement error terminate the batch and roll back the transaction, which is the behavior most developers expect. Pair it with TRY...CATCH blocks and check XACT_STATE() in the catch handler to decide whether the transaction is committable, doomed, or already gone — that distinction determines whether your catch block should commit, roll back, or simply log and re-throw.

Savepoints allow a transaction to establish intermediate rollback points without abandoning the entire transaction. This is useful in long-running batch operations where a single record failure should not roll back hours of work.

Schemas, Databases, and the Object Hierarchy

SQL Server organizes objects into a hierarchy — server, database, schema, object — and misunderstanding any level of it causes genuine confusion in production.

In SQL Server, the hierarchy is: Server → Database → Schema → Object. A single SQL Server instance can host many databases, and each database is fully isolated — cross-database queries require three-part naming (database.schema.table) and cross-database transactions have significant limitations. Within a database, schemas are namespaces for grouping objects. The default schema is dbo. Schemas in SQL Server are primarily an organizational and permission-management tool.

Cross-database access in SQL Server deserves a closer look, because it is both powerful and easy to misuse. Three-part naming (database.schema.table) lets a query span databases on the same instance, but cross-database ownership chaining is off by default — a user needs permissions in both databases, which surprises teams that assume access flows downhill. When databases move between servers — Availability Group failovers, log-shipped restores, migrations — the login-to-user mapping breaks and you get orphaned users. Partially contained databases, which authenticate at the database level with no server login at all, eliminate this entire class of problem. Choose containment deliberately for any database with a mobile lifestyle.

Querying the system catalog tells you a great deal about how your database is structured:

-- List all tables in the current database with their schemas and row counts
SELECT
    s.name              AS schema_name,
    t.name              AS table_name,
    p.rows              AS estimated_rows,
    SUM(a.total_pages) * 8 / 1024.0 AS total_size_mb
FROM sys.tables t
JOIN sys.schemas s ON t.schema_id = s.schema_id
JOIN sys.indexes i ON t.object_id = i.object_id AND i.index_id IN (0, 1)
JOIN sys.partitions p ON i.object_id = p.object_id AND i.index_id = p.index_id
JOIN sys.allocation_units a ON p.partition_id = a.container_id
GROUP BY s.name, t.name, p.rows
ORDER BY total_size_mb DESC;

Understanding the object hierarchy matters particularly for permission management. In SQL Server, granting SELECT on a schema grants access to all current and future objects within it — a powerful pattern for role-based access control that avoids the per-table grant treadmill. Design your schemas as security boundaries from the start: an app schema for application tables, a reporting schema for views, a staging schema for ETL — then grant at the schema level and let new objects inherit the right permissions automatically.

SQL Server separates logins (server-level identities) from users (database-level identities) — a login maps to a user within each database, and a user who exists in one database has no automatic presence in another. Internalize this split early: revoking a login's CONNECT permission is not the same as dropping its database users, and orphaned users — database users whose login no longer exists, common after restores to a different server — are a classic production gotcha that ALTER USER ... WITH LOGIN exists to fix. Contained databases, which authenticate users without any server-level login at all, are the modern answer for databases that move between servers.

Key Takeaways

  • → Relational databases express entity relationships through primary and foreign keys, and referential integrity enforced by foreign key constraints is one of the most valuable correctness guarantees the database provides — disabling it trades short-term convenience for long-term data quality problems.
  • → Data type selection is a design decision with lasting consequences: use `NUMERIC`/`DECIMAL` for financial data, `DATETIMEOFFSET` for any timestamp that crosses time zones, size `VARCHAR`/`NVARCHAR` deliberately instead of defaulting to `(MAX)`, and use the JSON function library with indexed computed columns when semi-structured data must live in the relational engine.
  • → NULL represents the absence of a value and participates in three-valued logic — comparisons involving NULL produce UNKNOWN, not FALSE, which causes silent failures in `WHERE` filters and especially in `NOT IN` subqueries.
  • → ACID transactions in SQL Server rest on the transaction log for durability and on your isolation choice for concurrency: locking-based Read Committed by default, or row-versioned Read Committed Snapshot Isolation when readers must not block writers; pair every explicit transaction with `SET XACT_ABORT ON` and `TRY...CATCH` so a statement error can never leave partial work committed.
  • → The object hierarchy — server, database, schema, table — is a security and organization tool, not just naming: design schemas as permission boundaries, grant at the schema level so future objects inherit correctly, and master the login-versus-user split (including orphaned users after restores) before it bites you in production.
