Chapter 21: Advanced Architecture Patterns

Architecture is where database administration meets systems engineering. You can tune queries all day and optimize indexes until they're perfect, but if the underlying architecture is wrong, you're building on sand. This chapter covers the high-level structural patterns that determine how databases are deployed, scaled, and made resilient — from the foundational decision of how data gets distributed across nodes, to the operational complexities of running multi-region deployments that survive datacenter failures. These patterns show up in every serious production environment, and understanding them deeply changes how you think about every other decision you make as a DBA.

---

How Data Gets Distributed: Sharding, Partitioning, and Replication

Before any advanced architecture can be understood, you need a precise mental model of the three fundamental ways data gets spread across infrastructure. These concepts are often conflated in conversation, but confusing them in practice leads to catastrophic design mistakes.

Partitioning splits a single logical table into multiple physical segments, usually on the same server or cluster. The application sees one table; the database engine routes reads and writes to the correct partition behind the scenes. Partitioning primarily solves performance problems — queries that touch only recent data don't scan years of history, and maintenance operations like archival and index rebuilds can target individual partitions. SQL Server's declarative partitioning (partition functions and schemes) is mature and production-proven.

Replication creates copies of data across multiple servers. It solves availability and read scalability. The primary accepts writes; replicas follow behind and serve reads. Replication doesn't reduce the data volume on any single node — every replica holds the full dataset. It buys you redundancy and read throughput, not horizontal write scaling.

Sharding distributes different rows of a table to different servers based on a shard key. A user table sharded by user_id might put users 1–1,000,000 on shard A and users 1,000,001–2,000,000 on shard B. Each shard holds a fraction of the total data. Sharding is the only pattern that scales write throughput horizontally, because writes go to different machines. It also dramatically complicates queries that span shard boundaries, cross-shard joins, and distributed transactions.

Understanding which problem you actually have determines which tool you reach for. A 500GB table with slow queries from full scans probably needs partitioning. A reporting workload overwhelming the primary needs a read replica. A write-heavy application that has outgrown any single server's I/O capacity needs sharding.

SQL Server's partitioning model uses a partition function (mapping ranges to partition numbers) and a partition scheme (mapping partitions to filegroups). Partition-aligned indexes let you switch partitions in and out as metadata-only operations — the workhorse pattern for sliding-window archival of time-series data.

-- Create a partition function mapping date ranges to partitions
CREATE PARTITION FUNCTION pf_events_monthly (DATETIME2)
AS RANGE RIGHT FOR VALUES (
    '2024-01-01',
    '2024-02-01',
    '2024-03-01'
);

-- Create a partition scheme mapping partitions to filegroups
CREATE PARTITION SCHEME ps_events_monthly
AS PARTITION pf_events_monthly
ALL TO ([PRIMARY]);  -- In production, map to separate filegroups

-- Create the partitioned table
CREATE TABLE events (
    event_id    BIGINT IDENTITY(1,1),
    occurred_at DATETIME2       NOT NULL,
    user_id     BIGINT,
    event_type  NVARCHAR(100),
    payload     NVARCHAR(MAX)
) ON ps_events_monthly(occurred_at);

-- Check partition row counts
SELECT
    p.partition_number,
    p.rows,
    rv.value AS boundary_value
FROM sys.partitions p
JOIN sys.tables t ON p.object_id = t.object_id
LEFT JOIN sys.partition_range_values rv
    ON rv.function_id = (
        SELECT ps.function_id
        FROM sys.partition_schemes ps
        JOIN sys.indexes i ON i.data_space_id = ps.data_space_id
        WHERE i.object_id = t.object_id AND i.index_id IN (0,1)
    )
    AND rv.boundary_id = p.partition_number - 1
WHERE t.name = 'events';

The key architectural insight here is that partitioning and sharding exist at different layers of abstraction. Partitioning is a storage optimization within a single logical database. Sharding requires application-layer awareness or a routing proxy that knows which physical node to contact. Many teams reach for sharding prematurely when partitioning would have solved their problem with far less operational complexity.

CQRS and Read/Write Splitting in Practice

Command Query Responsibility Segregation — CQRS — is an application architecture pattern with deep database implications. The core idea is that the data model optimized for writing is often poorly suited for reading, and vice versa. Writes need normalized data to avoid anomalies. Reads, especially for reporting and analytics, need denormalized, pre-aggregated, or differently indexed data to return fast results.

At the database level, CQRS typically manifests as two distinct data stores or schemas: a write-optimized transactional store and a read-optimized query store. In practice, DBAs implement this spectrum several ways:

Physical read replicas are the simplest form. The application routes all writes to the primary and all reads to one or more replicas. SQL Server's Always On Availability Groups support this pattern, with readable secondaries taking the read load via ApplicationIntent=ReadOnly routing. The tradeoff is replication lag — a secondary might be milliseconds to seconds behind the primary, so reads that require the absolute latest data must still go to the primary.

Materialized views represent a middle path. You write to normalized tables, and a materialized view or indexed view pre-computes the denormalized form for reads. This keeps the read and write paths in the same database instance while giving each path an optimized physical structure.

Separate OLAP stores complete the spectrum. The write store is a normalized OLTP database. An ETL or CDC pipeline continuously feeds a separate analytical store — often a columnar data warehouse — that's optimized for aggregation-heavy queries. The OLAP store might be minutes or hours behind, which is acceptable for reporting but not for operational lookups.

Deciding where on this spectrum to operate requires understanding your read/write ratio and your read latency tolerance. A system with 95% reads, a few seconds of acceptable lag, and complex aggregate queries is a strong candidate for a replica plus materialized views. A system where every read must reflect the latest write must stay on the primary.

-- SQL Server uses indexed views (schema-bound) for similar functionality
-- Note: SQL Server indexed views have stricter requirements than pg materialized views
CREATE VIEW vw_daily_sales_summary
WITH SCHEMABINDING
AS
SELECT
    CAST(o.created_at AS DATE)    AS sale_date,
    p.category,
    COUNT_BIG(DISTINCT o.order_id) AS order_count,
    SUM(oi.quantity)               AS units_sold,
    SUM(oi.quantity * oi.unit_price) AS gross_revenue
FROM dbo.orders o
JOIN dbo.order_items oi ON oi.order_id = o.order_id
JOIN dbo.products p ON p.product_id = oi.product_id
WHERE o.status = 'completed'
GROUP BY CAST(o.created_at AS DATE), p.category;
GO

-- Create clustered index to materialize the view on disk
CREATE UNIQUE CLUSTERED INDEX cidx_daily_sales_summary
    ON vw_daily_sales_summary (sale_date, category);

-- Create additional non-clustered index
CREATE NONCLUSTERED INDEX idx_daily_sales_category
    ON vw_daily_sales_summary (category, sale_date DESC)
    INCLUDE (order_count, units_sold, gross_revenue);

One operational pitfall worth addressing explicitly: when you introduce read replicas, your application developers need to think carefully about read-after-write consistency. A user creates an order and immediately navigates to their order history. If that read goes to a replica that hasn't caught up yet, the order they just placed won't appear — which looks like a bug to the user even though the data is technically correct. The solution is to route reads to the primary for a brief window after any write, or to accept that certain reads are always primary-bound.

Event Sourcing, CDC, and Keeping Systems in Sync

Traditional systems store current state — the users table holds the current email address, the accounts table holds the current balance. Event sourcing stores the sequence of events that led to that state instead. The balance isn't stored; it's computed by replaying deposits and withdrawals. This pattern has profound database architecture implications.

In an event-sourced system, the database becomes an append-only event log. Updates and deletes, in the traditional sense, largely disappear. Instead, you append new events. The "current state" is a projection — a view computed from the event stream and often cached in a separate read model for query performance. The database DBA role shifts from managing mutable state to managing a growing immutable log and the projections built on top of it.

Even if your application doesn't fully adopt event sourcing, Change Data Capture (CDC) brings many of the same benefits at the infrastructure level. CDC reads the database transaction log and publishes a stream of change events — inserts, updates, deletes — to downstream consumers. Those consumers might update a search index, populate a data warehouse, invalidate a cache, or trigger business workflows.

SQL Server implements CDC by reading the transaction log: the capture job harvests row changes into change tables, one per tracked table. ETL jobs poll the change tables, or Debezium's SQL Server connector streams them into Kafka, from which any number of consumers can read independently at their own pace.

SQL Server's equivalent is SQL Server Change Data Capture, a built-in feature that captures changes into shadow tables within the same database. Downstream systems query these capture tables to read changes since a given LSN (Log Sequence Number).

-- Enable CDC on the database
EXEC sys.sp_cdc_enable_db;

-- Enable CDC on a specific table
EXEC sys.sp_cdc_enable_table
    @source_schema = N'dbo',
    @source_name   = N'orders',
    @role_name     = NULL,          -- NULL means no role restriction
    @supports_net_changes = 1;      -- Enable net changes queries

-- Query changes in a time range
DECLARE @from_lsn BINARY(10) = sys.fn_cdc_map_time_to_lsn(
    'smallest greater than or equal',
    DATEADD(HOUR, -1, GETUTCDATE())
);
DECLARE @to_lsn BINARY(10) = sys.fn_cdc_get_max_lsn();

SELECT
    __$operation,       -- 1=delete, 2=insert, 3=before-update, 4=after-update
    __$commit_time,
    order_id,
    customer_id,
    status,
    total_amount
FROM cdc.fn_cdc_get_all_changes_dbo_orders(
    @from_lsn,
    @to_lsn,
    N'all with merge'
)
ORDER BY __$seqval;

The operational concern with CDC that catches teams off guard is backpressure management. A CDC consumer that falls behind creates a situation where the source database must retain ever-growing amounts of transaction log or CDC data. An unconsumed change feed will cause the change tables to grow until the disk fills up — a silent, creeping disaster. The CDC cleanup jobs handle retention automatically, but you need to verify those jobs are running and that their retention window matches your consumers' recovery time expectations. Monitor capture latency as the primary health signal of the whole pipeline.

Multi-Region and High Availability Architecture

Running a single-datacenter database is operationally simple compared to running across regions, but single-datacenter deployments carry existential risk: a datacenter failure takes down your entire system. Multi-region architectures trade operational complexity for resilience and sometimes latency improvements for globally distributed users.

The foundational challenge in multi-region database architecture is the CAP theorem's practical implications. During a network partition between regions — which is the failure mode you're designing for — you cannot simultaneously guarantee consistency (every read sees the most recent write) and availability (every request receives a response). You must choose which to sacrifice.

Active-passive setups have one primary region accepting writes and one or more secondary regions running replicas. In a failure, you promote a secondary to primary, accepting some data loss (the replication lag at the time of failure) and some downtime (the time to detect the failure and complete promotion). This is the most common pattern for OLTP databases because it preserves strong consistency during normal operations. Always On Availability Groups implement it well, with automatic failover inside a cluster and manual or forced failover across regions.

Active-active setups allow writes to multiple regions simultaneously. This eliminates the promotion step during failover but introduces the hardest problem in distributed systems: conflict resolution. If a user updates their email in region A and region B simultaneously, which write wins? Multi-master replication systems handle this through last-write-wins policies, vector clocks, or application-defined merge logic — none of which is simple. SQL Server has no native multi-master: the supported patterns are conflict-avoidance designs — shard-per-region (each region owns its writes), or distributed availability groups with a single global primary. True active-active with conflict resolution belongs in the application layer, not the database.

The practical middle ground most production systems land on is active-passive with fast failover and read-local routing. Writes always go to the primary region. Reads are served from the nearest replica. Replication is synchronous (or semi-synchronous) to at least one replica to bound data loss in a failover. This balances consistency, availability, and operational complexity reasonably well.

A topic that becomes urgent at multi-region scale is connection management. Connections to a database carry state — open transactions, session settings, prepared statements. When a failover occurs, those connections become invalid. Applications must handle connection pool invalidation and reconnection gracefully. SQL Server's AG listener abstracts the connection endpoint — a single virtual network name that always resolves to the current primary — so applications don't need to know which server holds the role. Pair it with retry logic: during failover, in-flight connections break and pools must drain and reconnect.

Monitoring in multi-region setups requires watching replication lag from multiple vantage points. A replica that's 5 seconds behind the primary is fine under normal load. A replica that's 5 minutes behind because network conditions degraded undetected is a problem you want to know about before a failover forces you to discover it.

-- Monitor Always On AG replica synchronization health
SELECT
    ag.name                             AS availability_group,
    ar.replica_server_name,
    ar.availability_mode_desc,
    ar.failover_mode_desc,
    ars.role_desc,
    ars.synchronization_health_desc,
    ars.connected_state_desc,
    ars.last_connect_error_description,
    adbrs.synchronization_state_desc,
    adbrs.log_send_queue_size          AS log_send_queue_kb,
    adbrs.redo_queue_size              AS redo_queue_kb,
    adbrs.log_send_rate                AS log_send_rate_kb_sec,
    adbrs.redo_rate                    AS redo_rate_kb_sec,
    adbrs.estimated_data_loss_seconds,
    adbrs.estimated_recovery_time_seconds
FROM sys.availability_groups ag
JOIN sys.availability_replicas ar
    ON ar.group_id = ag.group_id
JOIN sys.dm_hadr_availability_replica_states ars
    ON ars.replica_id = ar.replica_id
JOIN sys.dm_hadr_database_replica_states adbrs
    ON adbrs.replica_id = ar.replica_id
ORDER BY ag.name, ar.replica_server_name;

Recovery time objective (RTO) and recovery point objective (RPO) are the two numbers that should drive every high availability decision. RTO is how long the system can be down. RPO is how much data loss is acceptable. If RPO is zero, synchronous replication to at least one replica is mandatory — you confirm a commit only after at least one replica has acknowledged it. If RTO is under 30 seconds, automated failover must be configured and tested. Every architectural decision flows from these two numbers. If you don't have explicit SLAs for RTO and RPO from your business stakeholders, getting them is the most valuable thing you can do before designing your HA topology.

Connection Pooling Architecture and the Problem It Solves

Every database connection consumes real resources. SQL Server assigns a worker thread per connection — an idle connection still holds memory and a thread, and thousands of active connections cause scheduler contention. At scale, the number of application instances multiplied by the threads per instance quickly exceeds what a database can handle directly, which is why pooling is architectural, not optional.

A connection pool sits between the application and the database. The application thinks it has a dedicated connection; the pool maintains a smaller set of actual database connections and multiplexes application requests across them. This decouples the number of application threads (which can be in the thousands across a fleet of servers) from the number of database connections (which ideally stays in the dozens to low hundreds).

SqlClient connection pooling is the standard pooling mechanism for SQL Server, and it lives in the driver rather than as an external tier. The pool is keyed by the exact connection string: Open() checks out a pooled connection, Close()/Dispose returns it, and the driver issues sp_reset_connection to clean session state between checkouts. The knobs that matter:

  • → Min Pool Size / Max Pool Size: the floor the pool keeps warm and the ceiling per application process. Size the ceiling from measured concurrency across your whole app fleet — 50 app servers × 100 is 5,000 database connections.
  • → Connection Lifetime: how long a pooled connection lives before being recycled; recycling bounds the damage from leaked session state.
  • → Identical connection strings: any difference — even whitespace — creates a separate pool. Build connection strings once, centrally, never per user or per request.

    • The catch mirrors every pooler: pooled connections must be stateless. Temp tables, session SET options, and open transactions don't reliably survive a checkout — sp_reset_connection clears most of it, and anything it misses becomes an intermittent bug. Keep pooled work short and stateless, and never hold a pooled connection across user think time.

    SQL Server doesn't need an external pooler tier because the driver pools in-process — but at very high scale, with hundreds of microservices, a centralized middle-tier pool becomes relevant to cap total database connections. The AG listener with ApplicationIntent routing covers the read/write split; the middle tier covers connection-count fan-in.

    The architectural question that matters most is where pooling lives. Driver-level pooling is per process — simple, no extra tier, but the database sees the sum of every app server's pool. A middle-tier pool consolidates that fan-in at the cost of another component to operate and a network hop. In Kubernetes environments, a sidecar pooler per application pod is increasingly common, but this defeats the purpose for the database — you want pooling consolidated close to the database, not fragmented across pods.

    Sizing the pool correctly requires understanding your workload. The rule of thumb — rooted in research and widely tested in production — is that the optimal number of active database connections is approximately 2 × num_cores + num_disks. Beyond that number, connections queue behind each other and throughput actually decreases due to lock contention and context switching. A 32-core server with fast NVMe storage might perform optimally at 70 active connections even if it could technically accept 500. Size Max Pool Size so the fleet's total stays near that optimum — queuing in the pool is far cheaper than 500 active workers fighting over schedulers.

    Designing for Observability: Metrics, Tracing, and the Feedback Loop

    Architecture isn't complete at design time — it evolves as you learn how it actually behaves under real load. Observability is what gives you that learning loop. A system you can't observe is a system you can't improve, and architecture decisions made without feedback from production tend to calcify into technical debt.

    Database observability has three layers that work together:

    Metrics tell you what's happening numerically over time. Connection count, cache hit rate, transaction throughput, replication lag, lock wait time, I/O utilization — these are time-series numbers you collect on a fixed interval and chart or alert against. SQL Server ships with a DMV-based metrics infrastructure (sys.dm_os_performance_counters and friends) that integrates naturally with SQL Server Management Studio, Azure Monitor, and third-party tools like Datadog or SolarWinds; Prometheus exporters exist for shops standardizing on that stack.

    Logs tell you what happened in narrative form. Error logs, XEvent captures, Query Store history, Agent job history — these are discrete events with context you can query after the fact. Structured logging (JSON output rather than free-form text) makes logs far more useful because they become queryable data rather than strings to grep through.

    Traces tell you how a request moved through your system. A distributed trace follows a single request from the application through the connection pool through the database query and back, with timing at each hop. This is where you find latency problems that don't show up in aggregate metrics — a query that's fast on average but occasionally spikes because it's waiting for a lock, or a request that's slow because it's making 200 individual database roundtrips instead of one well-constructed query.

    Wiring these three layers together creates an actionable observability stack. When an alert fires on a metrics threshold (average query latency exceeded 100ms for 5 minutes), you pivot to logs to identify the slow queries responsible, then use traces to understand which application paths are generating those queries and why.

    -- Top queries by total CPU time using Query Store
-- (Query Store must be enabled on the database)
SELECT TOP 20
    SUBSTRING(qt.query_sql_text, 1, 100)    AS query_preview,
    rs.count_executions,
    ROUND(rs.avg_duration / 1000.0, 2)      AS avg_duration_ms,
    ROUND(rs.max_duration / 1000.0, 2)      AS max_duration_ms,
    ROUND(rs.avg_cpu_time / 1000.0, 2)      AS avg_cpu_ms,
    ROUND(rs.avg_logical_io_reads, 0)       AS avg_logical_reads,
    ROUND(rs.avg_rowcount, 0)               AS avg_rows,
    rs.last_execution_time
FROM sys.query_store_runtime_stats rs
JOIN sys.query_store_plan qp
    ON qp.plan_id = rs.plan_id
JOIN sys.query_store_query q
    ON q.query_id = qp.query_id
JOIN sys.query_store_query_text qt
    ON qt.query_text_id = q.query_text_id
WHERE rs.last_execution_time > DATEADD(HOUR, -24, GETUTCDATE())
ORDER BY rs.avg_cpu_time * rs.count_executions DESC;

-- Queries with high execution time variance (spike candidates)
SELECT TOP 20
    SUBSTRING(qt.query_sql_text, 1, 100)    AS query_preview,
    rs.count_executions,
    ROUND(rs.avg_duration / 1000.0, 2)      AS avg_duration_ms,
    ROUND(rs.stdev_duration / 1000.0, 2)    AS stddev_duration_ms,
    ROUND(rs.max_duration / 1000.0, 2)      AS max_duration_ms,
    ROUND(
        rs.stdev_duration / NULLIF(rs.avg_duration, 0),
        2
    )                                       AS coefficient_of_variation
FROM sys.query_store_runtime_stats rs
JOIN sys.query_store_plan qp ON qp.plan_id = rs.plan_id
JOIN sys.query_store_query q ON q.query_id = qp.query_id
JOIN sys.query_store_query_text qt
    ON qt.query_text_id = q.query_text_id
WHERE rs.count_executions > 50
  AND rs.avg_duration > 5000   -- more than 5ms average
ORDER BY coefficient_of_variation DESC;

    The feedback loop observability enables is what makes architecture durable. You design based on your best understanding of the workload, deploy, observe what actually happens, and revise. Partitioning strategies that looked good on paper may need adjustment when real access patterns emerge. Materialized view refresh intervals that seemed conservative may turn out to be too aggressive or not aggressive enough. Connection pool sizes set at deployment may need tuning as the application fleet grows.

    Building observability in from the start — not bolting it on after performance problems surface — is the difference between an architecture you control and one that surprises you.

    ---

    Key Takeaways

  • → **Partitioning, replication, and sharding solve different problems** — storage performance, read scale, and write scale respectively. Match the tool to the actual bottleneck before adding architectural complexity you don't need.
  • → **CQRS and read/write splitting exist on a spectrum**: from simple read replicas all the way to separate OLAP stores. The right point on that spectrum depends on your read/write ratio, acceptable replication lag, and the analytical complexity of your read workload.
  • → **CDC and event sourcing make your database a first-class event producer**: CDC change tables give downstream systems a reliable change stream, but they require active monitoring of capture latency and cleanup-job health to avoid runaway change-table growth.
  • → **Multi-region HA design must start with explicit RTO and RPO targets**: synchronous replication is required for zero RPO, automated failover is required for aggressive RTO, and every architectural tradeoff — active-passive vs. active-active, connection pooling topology, DNS failover strategy — should be evaluated against those two numbers.
  • → **Observability is a first-class architectural component**, not an afterthought: wiring together metrics (Query Store, Extended Events), structured logs, and distributed traces creates the feedback loop that lets you validate architectural decisions against real production behavior and evolve the design over time.
