Chapter 39: Maintenance Playbooks

Databases don't maintain themselves. Behind every stable, high-performing production system is a DBA who has thought carefully about what needs to happen regularly, under what conditions, and in what order. This chapter brings together the recurring tasks that keep SQL Server healthy—statistics gathering, index maintenance, integrity checks, log management, and scheduled job coordination—and organizes them into actionable playbooks you can adapt for your own environment. Rather than treating these tasks in isolation, we'll look at how they interact, how to sequence them intelligently, and how to handle the edge cases that surface only after systems have been running for months or years.

---

Understanding the Maintenance Landscape

Before writing a single maintenance script, it's worth stepping back and asking what "maintenance" actually means for a database system. At the highest level, maintenance is the set of activities that prevent gradual degradation. Databases accumulate dead rows, statistics drift away from reality, indexes fragment, transaction ID counters advance toward dangerous limits, and log files grow without bound. None of these problems are dramatic on day one—they're slow burns that become crises six months later when nobody has been watching.

SQL Server's maintenance concerns center on page fragmentation inside the B-tree structures it calls clustered and nonclustered indexes, statistics staleness that causes the query optimizer to make poor plan choices, and transaction log growth that can fill a disk when backups and log management are not disciplined. These three areas shape the playbooks you will build.

SQL Server has auto-update statistics built in, but it should not be treated as a complete solution on its own. Automatic statistics updates fire based on a row-modification threshold that doesn't scale linearly with table size; a billion-row table needs a change to twenty percent of rows before an automatic update triggers, which almost never happens. Manual maintenance jobs fill in the gaps that automation leaves.

The maintenance landscape also includes tasks that no automatic mechanism handles at all: validating physical data integrity with DBCC CHECKDB, archiving or rotating transaction logs, purging old audit data, refreshing materialized views, and validating foreign key constraints that may have been temporarily suspended during bulk loads. A mature maintenance playbook covers all of these, with clear ownership, documented schedules, and alerting when something fails to run or runs longer than expected.

Building the Statistics Playbook

In SQL Server, the optimizer's statistics are the maintenance item most DBAs underestimate. Statistics tell the optimizer how many rows to expect at each step of a plan; stale statistics produce bad estimates, and bad estimates produce bad plans. The AUTO_UPDATE_STATISTICS option keeps most statistics current, but the update is synchronous by default—a plan compilation can stall while statistics refresh on a huge table. Enabling AUTO_UPDATE_STATISTICS_ASYNC decouples the refresh from plan compilation: the optimizer uses the existing statistics for the current query while the refresh happens in the background.

The first sign of stale statistics is usually plan regression: a query that was fast starts doing far more I/O than expected. You can observe this by comparing the estimated row counts in an execution plan to the actual row counts—a large gap points at statistics that no longer describe the data.

When you find a table where STATS_DATE shows statistics weeks old while the row count has changed dramatically, auto-update should have already addressed it—if it hasn't, the first question is whether auto-update statistics is enabled at all, and the second is whether the table's change pattern falls below the auto-update threshold. Large tables that change a little at a time often need scheduled manual statistics updates.

For the manual statistics playbook, the key distinction is between UPDATE STATISTICS with sampling and WITH FULLSCAN. The default update samples the table, which is fast but can misrepresent skewed distributions. UPDATE STATISTICS ... WITH FULLSCAN scans every row—accurate but I/O-heavy on large tables. In practice, the sampling default is fine for most tables; reserve full scans for tables where plan regressions have been traced to sampling error.

A safer alternative to blocking plan compilation during a statistics refresh is AUTO_UPDATE_STATISTICS_ASYNC: the refresh happens in the background and queries proceed with the existing statistics instead of waiting. The tradeoff is a brief window of suboptimal plans, which is usually cheaper than blocking.

Transaction log growth deserves its own attention in any SQL Server maintenance playbook. Every modification is logged, and in the full recovery model the log is not truncated until a log backup occurs. If log backups stop—or never existed—the log grows until the disk fills and the database goes read-only. The DBA's job is to make sure this never becomes an emergency: monitor log size, verify that log backup jobs are succeeding, and know which databases legitimately run in simple recovery.

A transaction log above seventy percent of its allocated space with no recent log backup should be a monitored alert. At ninety percent, you should be taking a log backup immediately and investigating why the regular job stopped.

For statistics, the maintenance playbook should include a scheduled UPDATE STATISTICS run after any significant batch load or ETL job, because the auto-update threshold may not fire quickly enough for the optimizer to produce good plans for the next batch of work. A simple approach is to update statistics on the tables that were modified as part of the batch job script itself, immediately after the data load completes.

Index Maintenance Playbook

Index maintenance serves two purposes: removing fragmentation that forces the engine to read more pages than necessary, and identifying indexes that are either missing or have stopped being used so resources aren't wasted maintaining them. The mechanics differ between clustered and nonclustered indexes, so it's worth treating each case separately before looking at the combined strategy.

In SQL Server, index fragmentation is measured as the percentage of pages in the index that are out of logical order relative to their physical location on disk. This matters most for range scans, where the engine benefits from physically sequential reads. SQL Server provides two remediation operations: ALTER INDEX ... REORGANIZE, which defragments in place with minimal locking and can be interrupted and restarted, and ALTER INDEX ... REBUILD, which reconstructs the index from scratch. REBUILD is more thorough and also updates statistics as a side effect, but it takes an exclusive lock on the index unless you specify ONLINE = ON (available in Enterprise Edition).

The conventional guidance is to use REORGANIZE for fragmentation between fifteen and thirty percent, and REBUILD for fragmentation above thirty percent, though these thresholds should be treated as starting points rather than rules. For very small indexes, fragmentation numbers are statistically meaningless—rebuilding a 10-page index every week wastes more I/O than the fragmentation would ever cost.

-- Identify index fragmentation across a database
SELECT
    OBJECT_SCHEMA_NAME(ips.object_id) AS schema_name,
    OBJECT_NAME(ips.object_id) AS table_name,
    i.name AS index_name,
    ips.index_type_desc,
    ROUND(ips.avg_fragmentation_in_percent, 2) AS fragmentation_pct,
    ips.page_count,
    ips.record_count
FROM sys.dm_db_index_physical_stats(
    DB_ID(), NULL, NULL, NULL, 'LIMITED') AS ips
JOIN sys.indexes i
    ON ips.object_id = i.object_id
    AND ips.index_id = i.index_id
WHERE ips.avg_fragmentation_in_percent > 10
  AND ips.page_count > 100
ORDER BY ips.avg_fragmentation_in_percent DESC;

In SQL Server, fragmentation is measured at the page level. sys.dm_db_index_physical_stats reports average fragmentation and page density; the standard playbook reorganizes lightly fragmented indexes (REORGANIZE compacts pages online) and rebuilds heavily fragmented ones (REBUILD creates a fresh index structure). The main tool for reclaiming index space is ALTER INDEX, which rebuilds the index from scratch and requires an ACCESS EXCLUSIVE lock unless you use the CONCURRENTLY option, which avoids blocking but takes longer and cannot run inside a transaction block.

In practice, most indexes don't need rebuilds on a fixed schedule if fragmentation is monitored and addressed adaptively. The cases where rebuilds help are heavily updated indexes where page splits accumulate faster than reorganization can tidy them, or indexes that have grown significantly through one-time bulk inserts and now have structural imbalance.

Identifying unused indexes deserves its own place in the maintenance playbook. SQL Server maintains index usage statistics in sys.dm_db_index_usage_stats, but there's an important caveat: the stats reset when the service restarts. Before removing an index based on usage stats, verify that the collection window is long enough to cover all workload patterns—including month-end reports, quarterly batch jobs, and infrequent operational queries that might run only a few times a year. A safe practice is to mark candidate indexes for removal, communicate the intent to application owners, and observe for at least one full business cycle before dropping.

The index maintenance playbook should also include a step to check for duplicate indexes—multiple indexes on the same columns in the same order, or indexes that are strict prefixes of other indexes and therefore redundant for most query patterns. In SQL Server, duplicate indexes increase write overhead and consume storage without providing additional query acceleration.

Database Integrity Checks and Corruption Prevention

The most expensive database problem is one that goes undetected for months—a storage-level corruption that slowly propagates into backups, making recovery impossible. Integrity checks are the insurance policy against this scenario. Running them consistently and acting on failures immediately is not optional in any production environment.

SQL Server provides DBCC CHECKDB as its primary integrity validation tool. It verifies the structural integrity of all objects in the database: allocation structures, B-tree consistency, row data against index data, and cross-page linkages. A full CHECKDB on a large database can take hours and consumes significant I/O bandwidth, which is why many shops run it during off-peak maintenance windows or use the PHYSICAL_ONLY option during frequent checks and reserve full logical consistency checks for weekly runs.

-- Run a full integrity check with informational output
DBCC CHECKDB (N'YourDatabaseName')
    WITH NO_INFOMSGS, ALL_ERRORMSGS;

-- Faster physical-only check suitable for nightly runs on large databases
DBCC CHECKDB (N'YourDatabaseName')
    WITH PHYSICAL_ONLY, NO_INFOMSGS;

When CHECKDB reports errors, the severity determines the response. Allocation errors and B-tree consistency failures often indicate hardware or storage problems and may require restoring from backup. Never run CHECKDB repair options (REPAIR_ALLOW_DATA_LOSS) without exhausting restore options first—the repair commands sacrifice data to restore structural consistency, which is sometimes necessary but should never be the first response.

DBCC CHECKDB is the built-in integrity validator for SQL Server. It checks page allocation, index linkage, and data-page consistency across the whole database. Run it on a regular schedule—weekly for critical databases—and understand that it is I/O-heavy: on very large databases, splitting CHECKDB across a longer window or running it against a restored backup copy are the standard adaptations.

SQL Server can also detect block-level corruption through page checksums: the PAGE_VERIFY option (CHECKSUM is the default) stores a checksum on every page and verifies it on read. Verify that PAGE_VERIFY is set to CHECKSUM on all databases—a database upgraded long ago may still carry TORN_PAGE_DETECTION or NONE, which leave corruption undetectable until something reads the bad page.

The integrity check playbook should document expected runtimes for each check so that you have a baseline. When a check starts taking significantly longer than its baseline, it can indicate either growing database size (expected and acceptable) or an underlying storage performance issue (needs investigation). Capturing check runtimes in a logging table alongside the completion status gives you a historical record that makes anomaly detection straightforward.

A complete integrity playbook also includes verifying backup integrity. A CHECKDB that passes on the live database is necessary but not sufficient—you also need to know that your backups are restorable. This means periodically restoring a backup to a test server and running CHECKDB against the restored copy. The backup that has never been tested is not a backup—it's a hope.

Scheduling, Logging, and Operational Hygiene

A maintenance task that runs unreliably is only marginally better than one that doesn't run at all. The operational infrastructure around your maintenance jobs—how they're scheduled, how their outcomes are recorded, how failures are surfaced—is as important as the maintenance tasks themselves.

SQL Server Agent is the standard scheduler for SQL Server environments, with job steps, schedules, alerts, and notifications built in. In containerized or cloud environments, Kubernetes CronJobs or cloud-native schedulers such as Azure Elastic Jobs often take over this role.

Regardless of what technology handles scheduling, every maintenance job should follow the same operational pattern:

1. Record the start time and the job name to a maintenance log table.

2. Execute the maintenance work.

3. Record the completion time, row count affected (where applicable), and success or failure status.

4. If the job fails, write the error detail and raise an alert.

This pattern makes the maintenance log table a first-class operational artifact. When someone asks why a query is suddenly slow, you can check whether the most recent statistics refresh ran on schedule. When a developer asks why index fragmentation is high on a specific table, you can check whether the index maintenance job ran successfully and whether that table has unusually high write volume.

-- Create a maintenance log table and record job execution
CREATE TABLE dba_maintenance.maintenance_log (
    log_id          INT IDENTITY(1,1) PRIMARY KEY,
    job_name        NVARCHAR(200) NOT NULL,
    target_object   NVARCHAR(500) NULL,
    started_at      DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
    completed_at    DATETIME2 NULL,
    rows_affected   BIGINT NULL,
    status          NVARCHAR(20) NOT NULL DEFAULT 'RUNNING',
    error_message   NVARCHAR(MAX) NULL
);

-- At the start of a maintenance step:
DECLARE @log_id INT;
INSERT INTO dba_maintenance.maintenance_log (job_name, target_object)
VALUES ('IndexRebuild', 'Sales.Orders');
SET @log_id = SCOPE_IDENTITY();

-- At completion:
UPDATE dba_maintenance.maintenance_log
SET completed_at  = SYSDATETIME(),
    status        = 'SUCCESS',
    rows_affected = @@ROWCOUNT
WHERE log_id = @log_id;

Maintenance windows deserve explicit planning rather than implicit assumptions. The question "when can we run this?" has different answers for different tasks. A statistics update on a non-critical table might run during business hours with minimal impact. An offline index rebuild that holds locks for forty minutes needs a maintenance window agreement with application owners. CHECKDB on a 2 TB database will saturate I/O for several hours and should run during the deepest off-peak period available.

Documenting maintenance windows—not just the schedules, but the rationale and the stakeholders who agreed to them—prevents the frustrating situation where a maintenance job that's been running successfully for two years suddenly becomes "causing problems" because a new application team didn't know it existed. The maintenance playbook should be a document that other teams can read, not just a collection of SQL Agent jobs.

Finally, maintenance jobs need to be protected against overlap. If a nightly index rebuild is still running when the next night's job starts, you'll end up with concurrent rebuilds competing for resources and potentially deadlocking. SQL Server Agent will happily start a second instance of a job that is already running, so guard against overlap by checking msdb.dbo.sysjobactivity in the first job step and exiting if the job is already active. Verifying that this protection is in place—rather than assuming it is—is part of good operational hygiene.

Tuning Maintenance for Large-Scale and High-Availability Environments

At a certain scale, the maintenance playbooks that work for a 500 GB single-server deployment start to create their own problems. A CHECKDB that takes forty minutes on a 200 GB database takes four hours on a 2 TB database and fourteen hours on a 10 TB database. An index rebuild job that cycles through fifty tables in twenty minutes needs to cycle through five hundred tables without blowing past the maintenance window. And in high-availability environments—Always On Availability Groups with readable secondaries—maintenance activities on the primary can have unexpected effects on secondaries.

For SQL Server at scale, the standard approach to index maintenance is to move from blanket rebuild/reorganize jobs to smart, adaptive scripts that query fragmentation levels at runtime and only perform work above meaningful thresholds. The Ola Hallengren maintenance solution is the industry-standard implementation of this approach, handling index fragmentation, statistics updates, and integrity checks with configurable thresholds, parallelism controls, and detailed logging. Rather than rebuilding every index nightly, it rebuilds only those that need it, which dramatically reduces the total work and makes the maintenance window predictable regardless of how many tables the database contains.

For SQL Server at scale, the strategy is adaptive fragmentation maintenance: query sys.dm_db_index_physical_stats at runtime and rebuild only indexes above a meaningful fragmentation threshold. Cycling rebuilds across every table uniformly wastes resources and can blow past the maintenance window.

-- SQL Server: adaptive index maintenance based on live fragmentation
SELECT
    OBJECT_SCHEMA_NAME(ips.object_id) AS schema_name,
    OBJECT_NAME(ips.object_id) AS table_name,
    i.name AS index_name,
    ips.avg_fragmentation_in_percent,
    ips.page_count,
    CASE
        WHEN ips.avg_fragmentation_in_percent >= 30 THEN N'REBUILD'
        WHEN ips.avg_fragmentation_in_percent >= 5  THEN N'REORGANIZE'
        ELSE N'SKIP'
    END AS recommended_action
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') ips
JOIN sys.indexes i ON ips.object_id = i.object_id AND ips.index_id = i.index_id
WHERE ips.page_count > 1000   -- fragmentation stats are meaningless on tiny indexes
  AND ips.avg_fragmentation_in_percent >= 5;

In SQL Server Always On Availability Groups, index rebuilds on the primary generate redo log that must be applied on secondary replicas. For a large index rebuild, this can cause the secondary to lag behind the primary, which matters if read workloads are routed to the secondary. ONLINE index rebuilds, while they avoid blocking the primary, still generate substantial log volume. Strategies to manage this include performing rebuilds in smaller batches (one partition at a time on partitioned tables), scheduling them during windows when secondary read workloads are low, and monitoring secondary redo queue during maintenance to detect and pause if lag grows too large.

Availability group secondaries are similarly affected by heavy write operations during maintenance. An offline index rebuild generates transaction log that must be shipped and replayed on secondaries. Monitoring the redo queue before and during maintenance operations is good practice, with documented thresholds at which the DBA should pause or throttle maintenance work.

For integrity checks at scale, SQL Server Enterprise Edition's CHECKDB supports parallel execution across multiple CPUs, and the WITH PHYSICAL_ONLY option dramatically reduces runtime by skipping logical consistency checks. A practical approach for very large databases is to run physical checks nightly and full logical checks weekly, potentially using a secondary replica as the target for CHECKDB to avoid impacting the primary (SQL Server allows running CHECKDB against a database snapshot, which can be taken from a secondary in some configurations).

A final consideration for large environments is maintenance of the maintenance system itself. Log tables accumulate rows. Statistics on the maintenance log table itself can go stale. Jobs that ran once while a database was 100 GB may need their timeout parameters revisited now that the database is 2 TB. Building a quarterly review of maintenance configurations into the DBA calendar—reviewing runtimes, adjusting thresholds, removing jobs for objects that no longer exist, and adding jobs for new high-volume tables—is what separates a maintenance system that drifts toward failure from one that continues to serve the database well over time.

---

Key Takeaways

  • → **Auto-update statistics is a starting point, not a complete solution.** SQL Server provides background automation for statistics maintenance, but manual playbooks are required to handle batch loads, high-volume tables, and workloads that exceed what the background process can keep up with.
  • → **Transaction log management in the full recovery model is non-negotiable.** Monitoring log size and verifying that log backup jobs succeed is a non-negotiable part of any SQL Server maintenance playbook—without log backups, the log grows until the disk fills.
  • → **SQL Server index maintenance should be adaptive, not uniform.** Rebuilding every index on a fixed schedule wastes resources and can extend maintenance windows past acceptable limits. Query fragmentation levels at runtime, act only above meaningful thresholds, and skip small indexes where fragmentation statistics are not statistically meaningful.
  • → **Integrity checks are only useful if failures are acted upon immediately.** Running CHECKDB or amcheck regularly is valuable, but the playbook must also specify what happens when a check fails—who is notified, what the escalation path is, and when a restore from backup takes precedence over attempting repair.
  • → **Maintenance operations in high-availability environments must account for replication effects.** Index rebuilds and CHECKDB all generate I/O and log volume that affects secondaries. Monitor the redo queue and replication lag during maintenance windows and have documented thresholds at which work should be paused or throttled to protect secondary availability.
