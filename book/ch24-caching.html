Chapter 24: Caching Strategies

Database performance is rarely just about writing better queries or adding the right indexes. At a certain scale, the bottleneck shifts from execution logic to how efficiently the system avoids doing work it has already done. Caching sits at the center of that idea. This chapter covers how SQL Server approaches caching internally, how you as a DBA can observe and influence those mechanisms, and how application-layer and query-result caching strategies complement what the database engine provides. By the end of this chapter, you will have a clear picture of how data moves from disk to buffer to application, where the opportunities for optimization lie, and what can go wrong when caching is mismanaged.

---

How Databases Use Memory to Avoid Disk I/O

Every modern database engine operates on a fundamental principle: disk access is expensive, and memory access is cheap. When a query needs a page of data — whether a heap page, index page, or internal metadata — the engine first checks whether that page already lives in memory. If it does, the access is served immediately. If it does not, the engine reads it from disk, stores a copy in its in-memory buffer pool, and then serves the query. This buffer pool is the beating heart of database caching.

In SQL Server, this memory region is the buffer pool. Every query that reads a page goes through it: when SQL Server reads a page from disk, it loads it into the buffer pool, and subsequent requests for the same page are served from memory. SQL Server manages this memory dynamically — by default it will take nearly all available RAM — so the critical DBA decision is the max server memory setting: cap it explicitly and leave headroom for the OS, the thread stacks, and anything else on the box. On a dedicated database server, reserving 4-8 GB (or roughly ten percent) for the OS and giving the rest to SQL Server is the standard starting point.

In SQL Server, the equivalent structure is the Buffer Pool, managed by the Buffer Manager component. SQL Server is more aggressive by default — it claims as much RAM as the operating system allows (up to max server memory) and does not readily return it. SQL Server's buffer pool handles not just data pages but also index pages, execution plan caches, and connection memory. The two engines differ meaningfully in how they manage memory pressure and eviction, but the underlying goal is the same: keep frequently needed pages in memory.

SQL Server uses an LRU-K style algorithm to decide which pages to evict when the buffer pool fills up — weighing how recently and how frequently each page was touched, plus system memory pressure signals. Hot pages — those accessed frequently — tend to stay in memory, while cold pages get pushed out as new data enters. When Windows signals memory pressure, SQL Server trims the buffer pool cooperatively rather than fighting the OS for pages.

Understanding this behavior matters operationally. When you restart a database server, the buffer pool is cold — empty. Queries that were fast before the restart will suddenly be slow because every page access now requires a disk read. This is called a cold cache, and it explains why performance benchmarks should never be taken immediately after a server restart, and why production deployments use warm-up scripts or delayed traffic ramp-ups after maintenance windows.

Observing Buffer Cache Hit Rates

Before you can optimize caching, you need to measure it. SQL Server exposes the buffer cache hit ratio through both the Buffer cache hit ratio performance counter and sys.dm_os_performance_counters, and this metric tells you how often your workload is being served from memory versus disk.

The sys.dm_os_buffer_descriptors DMV shows how many buffer pool pages each database currently holds, which tells you where your memory is actually going. A database whose working set doesn't fit will show a depressed cache hit ratio and elevated page reads/sec / page writes/sec counters — the signature of a buffer pool under pressure.

-- Buffer cache hit ratio from performance counters
SELECT
    object_name,
    counter_name,
    cntr_value AS hit_ratio
FROM sys.dm_os_performance_counters
WHERE counter_name IN (
    'Buffer cache hit ratio',
    'Buffer cache hit ratio base'
)
AND object_name LIKE '%Buffer Manager%';

A healthy OLTP system typically shows buffer cache hit ratios above 95%, and most well-configured production databases run at 98–99%. If you are seeing ratios significantly below 95%, the first question is whether shared buffers (or SQL Server's max server memory) is sized appropriately for the working set of data your queries access regularly.

You can also look at which databases and objects are generating the most physical reads, which helps prioritize tuning efforts. A persistently low buffer cache hit ratio usually means one of two things: the buffer pool is undersized for the working set (raise max server memory), or large scans are polluting it with data that is only needed once — in which case the fix is routing that workload to a readable secondary or a columnstore, not more memory.

-- Pages in buffer pool per database
SELECT
    DB_NAME(database_id) AS database_name,
    COUNT(*) AS pages_in_buffer,
    COUNT(*) * 8 / 1024 AS size_mb
FROM sys.dm_os_buffer_descriptors
WHERE database_id > 4  -- exclude system databases
GROUP BY database_id
ORDER BY pages_in_buffer DESC;

In SQL Server, examining sys.dm_os_buffer_descriptors lets you see exactly how much of the buffer pool each database is consuming, which is valuable on shared instances. You can extend that query to the object level by joining through allocation units to find which tables are consuming the most buffer space — a table that holds a large fraction of the buffer pool but serves infrequent queries may be a candidate for moving to a separate filegroup or partitioning strategy.

The Operating System Page Cache and Its Role

There is a layer of caching that many DBAs overlook: the operating system's own page cache. On Linux, when SQL Server reads a page from disk, it passes through the kernel page cache — so a page can effectively live in two places. On Windows, SQL Server opens database files with FILE_FLAG_NO_BUFFERING, bypassing the OS cache for database I/O; the buffer pool is the cache, full stop. Either way, the practical rule is the same: size the OS headroom first, then give SQL Server the rest via max server memory.

graph TD
    App["Application"] --> AppCache["Application Cache\n(Redis / Memcached)"]
    AppCache -->|miss| Query["Database Query"]
    Query --> Buffer["Buffer Pool /\nShared Buffers"]
    Buffer -->|miss| OSCache["OS Page Cache"]
    OSCache -->|miss| Disk[("Physical Disk")]

*Figure: The layered read path from application to disk — each tier is checked in order, and a hit at any layer avoids the cost of the tiers below it.*

SQL Server's query optimizer needs no such hint — its cost model accounts for cached versus physical I/O internally, driven by statistics and the actual buffer pool state. There is no planner knob to tune here; the lever is the buffer pool size itself and keeping statistics current so the optimizer's cost estimates reflect reality.

SQL Server takes a different approach on Windows through its Large Pages and Lock Pages in Memory features. When configured, SQL Server can lock its buffer pool pages in physical RAM, preventing the operating system from paging them out under memory pressure. This eliminates OS-level eviction but requires specific Windows privileges and is typically enabled only on dedicated database servers where memory contention with other processes is not a concern.

Because SQL Server bypasses the OS cache for database files on Windows, the buffer pool is genuinely the single tier of database caching — which is exactly why max server memory is the most consequential memory setting on the instance. Backup and bulk-load paths may still use the OS cache, but ordinary query I/O lives and dies by the buffer pool.

The practical implication is that tuning a database server means thinking about total memory holistically. On a 64 GB dedicated SQL Server box, setting max server memory to around 56 GB and leaving the rest for the OS is the standard starting point. There is no second-tier overflow cache for database pages on Windows — data that doesn't fit in the buffer pool goes to disk, period — so getting this number right matters more than any other memory decision you'll make.

Query Plan Caching and Prepared Statements

Parsing, optimizing, and compiling a query takes CPU time. For a simple lookup query that executes thousands of times per second, re-compiling on every execution is wasteful. SQL Server maintains a plan cache — an in-memory store of compiled query plans — that allows previously seen queries to skip the optimization phase entirely, keyed by the query text hash.

In SQL Server, the Procedure Cache (also called the Plan Cache) stores execution plans for ad-hoc queries, stored procedures, and prepared statements. SQL Server uses parameterization to recognize when two queries differ only in their literal values and can share a plan. You can inspect the plan cache through sys.dm_exec_cached_plans and related DMVs.

-- Top cached plans by execution count and CPU cost
SELECT TOP 20
    qs.execution_count,
    qs.total_worker_time / 1000 AS total_cpu_ms,
    qs.total_worker_time / qs.execution_count / 1000 AS avg_cpu_ms,
    SUBSTRING(st.text, 1, 200) AS query_text,
    qp.query_plan
FROM sys.dm_exec_query_stats AS qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS st
CROSS APPLY sys.dm_exec_query_plan(qs.plan_handle) AS qp
ORDER BY qs.execution_count DESC;

SQL Server caches plans for ad-hoc batches, sp_executesql calls, and stored procedures alike. Ad-hoc SQL benefits from simple parameterization — the engine automatically parameterizes trivial queries so that SELECT * FROM Orders WHERE OrderId = 1 and SELECT * FROM Orders WHERE OrderId = 2 share one cached plan. For complex queries, parameterization doesn't happen automatically; that's what sp_executesql is for. If your workload is dominated by non-parameterized ad-hoc SQL, the plan cache fills with single-use plans — watch the Cache Hit Ratio counter, and consider forced parameterization at the database level before reaching for trace flags.

This matters because the optimal plan for WHERE customer_id = 1 can differ wildly from WHERE customer_id = 99999 depending on data distribution — the classic setup for parameter sniffing, covered next. When the plan cache is polluted with single-use ad-hoc plans, the blunt instrument is DBCC FREEPROCCACHE, but that evicts every plan on the instance and causes a compile storm; prefer targeted fixes like forced parameterization or plan guides.

SQL Server's signature plan-cache problem is parameter sniffing. When SQL Server first compiles a plan for a stored procedure, it uses the actual parameter values at that moment to estimate cardinality, and the resulting plan is cached. If those initial values were unusual — either very selective or very broad — the cached plan may perform poorly for typical parameter values. This is one of the most common performance problems in SQL Server, and solutions range from OPTION (RECOMPILE) on the query, to OPTIMIZE FOR hints, to breaking procedures into smaller pieces. For plan instability that comes and goes, Query Store is the diagnostic tool: it captures the plan history per query so you can see exactly when the plan flipped and force the good one back.

Application-Layer Caching Strategies

The database buffer pool and plan cache are internal, automatic mechanisms. But at scale, even a perfectly tuned database will struggle if the application sends the same expensive queries repeatedly for data that does not change frequently. This is where application-layer caching strategies enter the picture, and DBAs need to understand them — not necessarily to implement them, but to design the database tier so that caching at higher layers works effectively.

The most common pattern is a read-through cache using a system like Redis or Memcached. The application checks the cache first; on a miss, it queries the database, stores the result in the cache with a TTL (time-to-live), and returns the result. Subsequent requests for the same data hit the cache and never reach the database. From the DBA's perspective, this pattern creates a tiered system where the database handles cold reads, initial population, and writes, while the cache handles the bulk of read traffic.

This has an important implication for schema design. Data that benefits most from application-level caching tends to be read-heavy, relatively stable, and natural to serialize as a whole unit — a product catalog row, a user profile, a configuration setting. Data that changes frequently, or that requires joining many tables to assemble, is harder to cache correctly because cache invalidation becomes complex.

Write-through caching ensures that every write goes to both the cache and the database simultaneously, keeping the cache consistent. Write-behind caching (also called write-back) buffers writes in the cache and flushes them to the database asynchronously. Write-behind can significantly reduce database write throughput pressure, but it introduces risk: if the cache layer fails before flushing, those writes are lost. As a DBA, you should be skeptical of write-behind designs for anything that requires durability, and you should ensure that any such design has explicit failure handling and monitoring.

One pattern that databases themselves support, and that serves as an alternative to external caches for certain workloads, is materialized views. A materialized view pre-computes the result of a complex query and stores it as a physical table. Queries that would otherwise join several large tables and aggregate millions of rows can instead read from the materialized view in milliseconds.

-- Indexed view (SQL Server's equivalent of a materialized view)
CREATE VIEW monthly_sales_summary
WITH SCHEMABINDING
AS
SELECT
    DATEFROMPARTS(YEAR(o.order_date), MONTH(o.order_date), 1) AS month,
    p.product_category,
    SUM(o.order_total) AS total_revenue,
    COUNT_BIG(*) AS order_count
FROM dbo.orders AS o
JOIN dbo.products AS p ON o.product_id = p.product_id
GROUP BY
    DATEFROMPARTS(YEAR(o.order_date), MONTH(o.order_date), 1),
    p.product_category;

-- Create a unique clustered index to materialize it
CREATE UNIQUE CLUSTERED INDEX IX_monthly_sales_summary
ON monthly_sales_summary (month, product_category);

SQL Server's indexed views are automatically maintained as the underlying data changes, which is both convenient and a source of overhead on write-heavy tables — every write to the base tables also maintains the view's clustered index. The DBA must weigh the write overhead against the query performance gain. Indexed views come with strict requirements (schema binding, deterministic expressions, and in Standard Edition the NOEXPAND hint to use them), so for refresh-on-schedule semantics many shops instead maintain snapshot tables via Agent jobs — a manual materialized view with full control over refresh timing and locking.

Cache Eviction, Pollution, and Connection Pooling Interactions

Understanding that caching exists is one thing; understanding when it works against you is another. Three specific problems — cache eviction under pressure, cache pollution from large scans, and the interaction between connection poolers and plan caches — represent the production edge cases that experienced DBAs encounter and that are rarely documented clearly.

Cache eviction under memory pressure occurs when the buffer pool fills and the eviction algorithm must push out pages. If a large ETL job or reporting query scans a multi-gigabyte table, it will load millions of pages into the buffer pool, potentially evicting hot pages that the OLTP workload depends on. SQL Server has no ring-buffer protection for this — a big scan genuinely washes through the pool. The mitigations are architectural: route analytics to a readable secondary, reach for a columnstore index so the scan touches far fewer pages, or schedule the heavy scan for off-peak hours. Never "fix" it with DBCC DROPCLEANBUFFERS in production — that evicts everything, including the hot pages you were trying to protect.

SQL Server provides the Resource Governor feature to limit memory grants to specific workloads. By classifying connections into resource pools, you can ensure that a reporting query cannot consume buffer pool space at the expense of OLTP queries. This is one of the most underused features in SQL Server environments where mixed workloads run on the same instance.

Cache pollution from analytics workloads is a real problem that many teams address by routing analytical queries to a readable secondary. With read-only routing on the AG listener, connections marked ApplicationIntent=ReadOnly land on secondaries automatically. Directing reporting workloads there not only keeps the primary's buffer pool clean but also offloads CPU and I/O from the primary entirely.

Connection pooling and the plan cache interact more benignly in SQL Server than in systems where pooling is a separate tier. Plans are cached server-side by query hash, independent of which pooled connection executed them — sp_reset_connection resets session state between checkouts but never evicts plans. So a well-pooled application using sp_executesql gets both benefits at once: cheap connection checkout and a warm plan cache. The thing pooling does not fix is cache bloat from non-parameterized ad-hoc SQL; that's a query-text problem, solved with parameterization, not with pool tuning.

In SQL Server, connection pooling is typically handled by the client driver (ADO.NET, JDBC), and the plan cache is server-side and query-keyed rather than connection-keyed. Switching pooling modes is less disruptive to plan caching. However, frequent DBCC FREEPROCCACHE calls — sometimes used as a troubleshooting step — clear the entire plan cache, forcing recompilation of everything. This is rarely the right production action; targeted eviction using the plan handle is always preferable.

-- Find plans with high recompile counts
SELECT
    qs.sql_handle,
    qs.plan_generation_num,
    qs.execution_count,
    qs.total_worker_time / 1000 AS total_cpu_ms,
    SUBSTRING(st.text, 1, 300) AS query_text
FROM sys.dm_exec_query_stats AS qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS st
WHERE qs.plan_generation_num > 1
ORDER BY qs.plan_generation_num DESC;

A query with a high plan_generation_num in SQL Server is being recompiled repeatedly — typically because of statistics changes, schema changes, or explicit RECOMPILE hints. Each recompile consumes CPU and represents time where the query is not being executed. If recompiles are frequent and the query is hot, investigate whether the triggering cause (often a statistics update on a large table) can be controlled through manual statistics management or table variable instead of temp table usage.

---

Key Takeaways

  • → **The buffer pool is the primary cache** in SQL Server. Sizing it via max server memory — appropriately for the working data set, with real OS headroom — is the single most impactful caching configuration decision a DBA makes.
  • → **Cache hit rate is a key health metric.** Values below 95% warrant investigation into buffer pool sizing, workload patterns, and whether large analytical scans are evicting hot OLTP pages. Both engines expose this data through system views and DMVs.
  • → **Plan caching reduces compilation overhead**, but its failure modes — parameter sniffing and single-use plan bloat — are among the most common SQL Server performance problems. Understanding how to diagnose them with Query Store and address them without blunt tools like DBCC FREEPROCCACHE is an important production skill.
  • → **Application-layer caching through indexed views, snapshot tables, Redis, or similar systems** reduces database read pressure for stable data, but requires careful invalidation strategies. SQL Server's auto-maintained indexed views are a powerful database-native option that does not require external infrastructure — as long as you budget for their write overhead.
  • → **Cache pollution and memory pressure from mixed workloads** are common in production environments that run OLTP and analytics on the same instance. Read replicas, resource pools, and understanding each engine's sequential scan buffering behavior are the tools for keeping caches effective under these conditions.
