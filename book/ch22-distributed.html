Chapter 22: Distributed Systems

Distributed systems represent one of the most profound shifts in how databases are architected, operated, and reasoned about. When a single server is no longer sufficient — whether due to data volume, throughput demands, fault tolerance requirements, or geographic distribution — databases must be spread across multiple nodes, and suddenly the comfortable guarantees DBAs rely on in standalone systems begin to bend. This chapter examines how PostgreSQL and SQL Server approach distributed architectures: the theory that underpins them, the replication and sharding mechanisms that make them possible, the consistency trade-offs that must be navigated, and the operational realities that separate a well-run distributed database from one that causes production incidents at 2 a.m.

---

Why Single-Node Databases Eventually Break Down

Every database starts on a single server. For a long time, that server is adequate — more RAM, faster disks, and a bigger CPU handle growth. This vertical scaling strategy works until it doesn't, and the inflection point arrives in one of a few recognizable ways.

The first is storage capacity. A single server has a ceiling. Even with petabyte-scale storage attached via SAN or NVMe arrays, managing hundreds of terabytes on a single logical instance carries enormous operational risk. A corrupt index, a botched migration, or a long-running transaction can cripple the entire dataset.

The second is read throughput. A single write-primary instance can only handle so many concurrent reads before queries start competing for buffer pool space and CPU. Read replicas alleviate this, but they are still a form of distribution — you have already left the world of a single node.

The third is write throughput. This is where distribution becomes genuinely hard. Reads can be fanned out to replicas with relatively simple routing logic. Writes, however, require coordination. If two nodes can each accept writes, you must decide how they reconcile differences, which one wins conflicts, and what happens when the network between them partitions.

The fourth is availability. A single node is a single point of failure. Distributing a database across nodes and data centers means that the failure of any one node does not take the system offline — but only if the architecture is designed correctly.

Understanding these four pressures shapes every architectural decision in distributed database design. DBAs who appreciate why distribution is necessary are far better equipped to choose the right approach than those who treat it as a purely technical puzzle.

CAP Theorem and the Consistency Spectrum

No conversation about distributed databases is complete without the CAP theorem, and no treatment of CAP is useful without acknowledging its nuance. The theorem, articulated by Eric Brewer in 2000 and formally proved by Gilbert and Lynch in 2002, states that a distributed data system can provide at most two of three properties simultaneously: Consistency, Availability, and Partition tolerance.

Consistency here means that every read receives the most recent write or an error. Availability means that every request receives a response, though not necessarily the most recent data. Partition tolerance means the system continues operating when network communication between nodes is disrupted.

The practical reality is that network partitions are not optional — they happen in any real distributed system. This means every distributed database is choosing between consistency and availability during a partition event. Most production systems actually operate on a spectrum rather than at hard extremes, and the nuanced version of this idea is captured by the PACELC model, which adds latency into the equation: even when there is no partition, distributed systems must trade off latency against consistency.

PostgreSQL's native streaming replication sits toward the CP end when synchronous commit is required: the primary waits for at least one standby to acknowledge a WAL record before confirming the transaction to the client. If the standby is unreachable, writes can be blocked. With asynchronous replication, the system leans toward availability, accepting the possibility that a failover will reveal a small data loss window.

SQL Server's Always On Availability Groups offer the same spectrum. A synchronous-commit replica guarantees no data loss at failover but introduces latency on every write. An asynchronous-commit replica allows faster writes but accepts potential data loss measured in seconds or minutes depending on replication lag.

The correct position on this spectrum is a business decision as much as a technical one. Financial transaction systems typically demand strong consistency. Content delivery systems, analytics pipelines, and social feed applications often tolerate eventual consistency in exchange for lower latency and higher availability.

The term "eventual consistency" deserves precision. It does not mean arbitrary inconsistency. It means that, given no new writes, all replicas will converge to the same state. The time to convergence and the visibility of stale reads during that window are the variables a DBA controls through replication configuration and application design.

Replication Architecture in PostgreSQL and SQL Server

Replication is the foundation of most distributed database deployments. Both PostgreSQL and SQL Server have mature replication subsystems, but they implement them differently, and choosing between replication topologies depends on the workload and failure model.

PostgreSQL Streaming Replication

PostgreSQL's built-in replication is physical streaming replication. The primary server generates Write-Ahead Log (WAL) records for every data change. Standby servers connect to the primary, receive the WAL stream, and replay it against their own copy of the data. Because WAL operates at the block level, standbys receive an exact byte-for-byte replica of the primary's data files.

This approach is reliable and straightforward, but it has constraints. A standby server must be at the same major PostgreSQL version. It inherits everything from the primary — all databases, all tables, all schemas — with no ability to replicate a subset. Read-only queries can be routed to standbys using hot_standby = on, but standbys cannot accept writes.

Replication slots ensure that standbys do not fall so far behind that the primary discards WAL they still need. However, an abandoned slot with a lagging standby can cause WAL to accumulate indefinitely, filling the disk on the primary. This is one of the most common operational mistakes in PostgreSQL replication deployments.

-- Check replication distributor agent status and latency
SELECT publisher_db,
       publication,
       subscriber,
       subscriber_db,
       delivery_latency,
       delivered_commands,
       last_updated
FROM distribution.dbo.MSdistribution_status
ORDER BY delivery_latency DESC;

Logical replication, introduced in PostgreSQL 10, provides a different model. Rather than replicating raw WAL blocks, logical replication decodes WAL into row-level change events (INSERT, UPDATE, DELETE) and streams those to subscribers. Subscribers can be different major versions of PostgreSQL, can replicate a single table or a filtered subset of tables, and can apply changes to databases with a different schema structure. This flexibility makes logical replication valuable for zero-downtime major version upgrades, cross-region data synchronization, and feeding data pipelines.

SQL Server Replication and Availability Groups

SQL Server offers several replication types: snapshot, transactional, and merge. Transactional replication is the workhorse for low-latency data propagation. The Log Reader Agent reads committed transactions from the publication database's transaction log and stores them in the distribution database. Distribution Agents then deliver those changes to subscribers. Unlike PostgreSQL streaming replication, transactional replication can be selective — specific tables, columns, or even filtered rows can be included in a publication.

Always On Availability Groups (AG) are the modern high-availability mechanism in SQL Server, functioning more like PostgreSQL streaming replication in that they replicate at the log block level. An AG groups databases together and synchronizes them to secondary replicas. Readable secondaries allow read workloads to be offloaded. Automatic failover can be configured for synchronous replicas within the same data center, while asynchronous replicas in remote data centers serve as disaster recovery targets.

-- Check Always On AG replica health and synchronization lag
SELECT ag.name AS ag_name,
       ar.replica_server_name,
       ars.role_desc,
       ars.synchronization_health_desc,
       ars.connected_state_desc,
       adb.database_name,
       adbs.synchronization_state_desc,
       adbs.log_send_queue_size / 1024.0 AS log_send_queue_mb,
       adbs.redo_queue_size / 1024.0 AS redo_queue_mb,
       adbs.log_send_rate,
       adbs.redo_rate
FROM sys.availability_groups ag
JOIN sys.availability_replicas ar ON ag.group_id = ar.group_id
JOIN sys.dm_hadr_availability_replica_states ars ON ar.replica_id = ars.replica_id
JOIN sys.availability_databases_cluster adb ON ag.group_id = adb.group_id
JOIN sys.dm_hadr_database_replica_states adbs 
    ON adb.group_id = adbs.group_id 
    AND adb.group_database_id = adbs.group_database_id
    AND ars.replica_id = adbs.replica_id
ORDER BY ag.name, ar.replica_server_name;

One important operational distinction: PostgreSQL streaming replication is built into the database engine and is free. SQL Server Always On Availability Groups require Enterprise Edition or, in limited form, Standard Edition. This cost consideration influences architecture decisions in cost-sensitive environments and should be factored into total cost of ownership calculations.

Sharding, Partitioning, and Horizontal Scale-Out

Replication solves read scale and high availability. It does not, by itself, solve write scale or storage scale. When the volume of writes or data exceeds what a single primary can handle, horizontal partitioning — sharding — becomes necessary.

Sharding means dividing data across multiple independent nodes, each owning a subset of the total dataset. A user with ID 1–1,000,000 might live on shard 1, users 1,000,001–2,000,000 on shard 2, and so on. Alternatively, sharding can be based on a hash of a key, a range of values, or geographic region. Each strategy has trade-offs.

Range-based sharding is natural and makes range queries efficient. If you query users created between two dates, a range shard key on creation date ensures most such queries hit a single shard. The risk is hotspots: if new records always have a higher key value, all new writes land on the last shard.

Hash-based sharding distributes writes evenly, eliminating hotspots. The trade-off is that range queries must scatter to all shards, which increases latency and coordination overhead.

PostgreSQL and Sharding

PostgreSQL does not have built-in sharding in the same way it has built-in replication. Declarative table partitioning, introduced in PostgreSQL 10 and significantly improved through version 14 and beyond, handles partitioning within a single instance. Postgres Foreign Data Wrappers (FDW) with postgres_fdw can make remote tables appear local, enabling a primitive form of manual sharding, but this lacks sophisticated query planning across shards.

For genuine distributed sharding, the ecosystem relies on third-party solutions: Citus (now part of the Microsoft ecosystem but still open source), which transforms PostgreSQL into a sharded distributed database; Patroni for HA coordination; and PgBouncer for connection pooling across shards.

Citus distributes tables across worker nodes using a distribution column. When a query filters on that column, Citus routes it to the correct shard. When the query touches multiple shards or must join distributed tables, Citus coordinates parallel execution across workers.

PostgreSQL (with declarative partitioning as a foundation for sharding logic):

-- Create a range-partitioned table suitable for per-shard attachment via FDW
CREATE TABLE orders (
    order_id     BIGINT NOT NULL,
    customer_id  BIGINT NOT NULL,
    order_date   DATE NOT NULL,
    total_amount NUMERIC(12, 2),
    status       TEXT
) PARTITION BY RANGE (order_date);

-- Create individual partitions (in a sharded setup, each would live on a different node via FDW)
CREATE TABLE orders_2023 PARTITION OF orders
    FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');

CREATE TABLE orders_2024 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

CREATE TABLE orders_2025 PARTITION OF orders
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

-- Verify partition pruning is applied (only relevant partition scanned)
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE order_date BETWEEN '2024-03-01' AND '2024-06-30'
  AND customer_id = 42;

SQL Server and Sharding

SQL Server also lacks native sharding, though its partitioned tables provide intra-instance range partitioning. For true horizontal scale-out, the historical approach involved Elastic Database tools in Azure SQL, which allow a database to be split across multiple Azure SQL databases with a shard map that routes queries to the correct database. On-premises SQL Server sharding typically requires application-level routing or middleware.

SQL Server partitioned tables use a partition function and scheme to place data across filegroups. This enables efficient partition elimination in queries and the ability to archive or purge partitions with low overhead.

-- Create a partition function and scheme for date-based partitioning
CREATE PARTITION FUNCTION pf_OrderDate (DATE)
AS RANGE RIGHT FOR VALUES (
    '2023-01-01',
    '2024-01-01',
    '2025-01-01',
    '2026-01-01'
);

CREATE PARTITION SCHEME ps_OrderDate
AS PARTITION pf_OrderDate
TO ([PRIMARY], [FG_2023], [FG_2024], [FG_2025], [FG_2026]);

CREATE TABLE dbo.Orders (
    OrderID     BIGINT NOT NULL,
    CustomerID  BIGINT NOT NULL,
    OrderDate   DATE NOT NULL,
    TotalAmount DECIMAL(12, 2),
    Status      NVARCHAR(50)
) ON ps_OrderDate(OrderDate);

-- Check which partition a specific date maps to
SELECT $PARTITION.pf_OrderDate('2024-06-15') AS PartitionNumber;

-- Review row counts per partition
SELECT p.partition_number,
       p.rows AS row_count,
       prv.value AS boundary_value
FROM sys.partitions p
JOIN sys.partition_schemes ps ON ps.data_space_id = p.data_space_id
JOIN sys.objects o ON o.object_id = p.object_id
LEFT JOIN sys.partition_range_values prv 
    ON prv.function_id = ps.function_id 
    AND prv.boundary_id = p.partition_number - 1
WHERE o.name = 'Orders'
  AND p.index_id IN (0, 1)
ORDER BY p.partition_number;

The critical operational lesson with sharding is that cross-shard queries are expensive and must be minimized by design. An application that frequently needs to join data from multiple shards — for example, a report that aggregates orders across all customer regions — will see those queries become the performance bottleneck in any sharded architecture. The data model must be designed with the shard key in mind from the beginning. Retrofitting sharding onto an existing schema is one of the most painful database migrations a team can undertake.

Distributed Transactions, Two-Phase Commit, and Coordination Costs

When data is distributed across nodes, maintaining transactional consistency across those nodes introduces the hardest problem in distributed databases: the distributed transaction. If a business operation must update data on two separate nodes atomically, how do you ensure either both updates succeed or neither does?

The classical answer is the Two-Phase Commit (2PC) protocol. In 2PC, a coordinator node asks all participating nodes to prepare the transaction (Phase 1). Each node locks the affected rows and responds with a "yes" or "no." If all nodes say yes, the coordinator sends a commit message (Phase 2); if any node says no, the coordinator sends a rollback. All participants then execute accordingly.

2PC has well-known problems in the presence of failures. If the coordinator crashes after all participants have prepared but before the commit message is sent, participants are left in a blocking state — they hold locks but cannot release them without instruction from the coordinator. This is called the in-doubt transaction problem. It can cause deadlocks and requires manual DBA intervention to resolve.

PostgreSQL Prepared Transactions

PostgreSQL supports prepared transactions natively via PREPARE TRANSACTION and COMMIT PREPARED / ROLLBACK PREPARED. These are the building blocks for external 2PC coordinators to use.

In-doubt transactions visible in pg_prepared_xacts that are hours or days old are a red flag. If the coordinator that created them is permanently gone, the DBA must determine the correct outcome from application logs and manually commit or roll back each one.

SQL Server Distributed Transactions

SQL Server uses the Microsoft Distributed Transaction Coordinator (MSDTC) for distributed transactions. Any operation that spans multiple SQL Server instances, linked servers, or external resource managers (like MSMQ) enlists MSDTC as the coordinator. MSDTC implements 2PC and manages in-doubt transactions in its log.

-- Check for in-doubt distributed transactions
SELECT transaction_id,
       name,
       transaction_begin_time,
       dtc_state,
       dtc_status,
       dtc_isolation_level
FROM sys.dm_tran_active_transactions
WHERE dtc_state IS NOT NULL
ORDER BY transaction_begin_time;

-- Find all distributed transactions currently active
SELECT session_id,
       transaction_id,
       is_local,
       is_enlisted,
       is_bound,
       open_transaction_count
FROM sys.dm_tran_session_transactions
WHERE is_enlisted = 1;

The performance cost of distributed transactions is significant and often underestimated. 2PC adds at minimum two round trips to every participating node for every transaction. In a system where nodes are geographically separated, this directly translates to latency measured in tens to hundreds of milliseconds per transaction. A system that processes 5,000 write transactions per second on a single node may only sustain 500 per second once distributed 2PC overhead is introduced — without any change in the underlying data volume.

This is why modern distributed systems often avoid distributed transactions entirely. Rather than using 2PC, they use saga patterns, event sourcing, or compensating transactions that undo already-committed work if a later step fails. These approaches accept eventual consistency in exchange for eliminating coordination bottlenecks. DBAs working with distributed architectures must understand both the mechanics of 2PC and the alternatives so they can push back intelligently when application teams propose designs that would require distributed transactions at high throughput.

Operational Realities: Monitoring, Failover, and Split-Brain Prevention

Designing a distributed system on paper is one challenge. Keeping it healthy in production is another entirely. Distributed systems fail in ways that single-node databases do not, and the failure modes are often subtle.

Monitoring Replication Lag

In any replicated system, lag — the delay between a write on the primary and its application on a replica — is the primary operational metric. A replica that has fallen behind by seconds is usually acceptable. A replica that has fallen behind by hours is a disaster waiting for a failover event to expose it. Both PostgreSQL and SQL Server provide views to monitor this, and both should be feeding alerting systems continuously.

The pg_stat_replication view on PostgreSQL (shown earlier) exposes the LSN positions of every connected standby. The difference between the primary's current WAL position and a standby's replay LSN is the lag, expressed in bytes. Dividing this by the replication rate gives an estimate in time, though replication rate is variable.

SQL Server's sys.dm_hadr_database_replica_states exposes log_send_queue_size and redo_queue_size for AG replicas. These are the backlog of redo waiting to be sent and the backlog waiting to be applied, respectively. Both should be close to zero in a healthy deployment.

Automatic Failover and Fencing

When a primary fails, a replica must be promoted. This is straightforward in concept and treacherous in practice. The central danger is split-brain: a situation where the original primary recovers from a transient failure after a replica has been promoted, and now two nodes both believe they are the primary and accept writes. The resulting data divergence is painful to reconcile and may be irrecoverable without data loss.

Preventing split-brain requires fencing — a mechanism that guarantees the old primary cannot accept writes after a new one has been promoted. Common approaches include:

  • → **STONITH (Shoot The Other Node In The Head)**: Physically power off or network-isolate the old primary before promotion proceeds. Used in Linux Pacemaker clusters with PostgreSQL.
  • → **Lease-based fencing**: The primary holds a time-limited lease from a consensus system (like etcd or ZooKeeper). Patroni, the most widely deployed PostgreSQL HA solution, uses this approach. If the primary cannot renew its lease, it fences itself by stopping write acceptance.
  • → **Quorum-based failover**: SQL Server's Windows Server Failover Cluster (WSFC) uses quorum — a majority of cluster nodes must agree before a failover proceeds. If quorum is lost, the cluster stops operations rather than risk split-brain.

    • Patroni's architecture is worth understanding in detail because it represents production-grade PostgreSQL HA. Patroni uses etcd, Consul, or ZooKeeper as a distributed consensus store. The current primary continuously updates a key in that store. If the primary fails to update the key within a configurable TTL, standby nodes race to acquire the leader key. The winner promotes itself to primary. The loser becomes a standby of the new primary. The former primary, if it recovers, finds that it cannot acquire the leader key and fences itself by refusing connections. No human intervention is required for a clean failover, typically completing in 10–30 seconds.

    SQL Server's Always On AG automatic failover uses WSFC quorum. The replica configured for automatic failover monitors the primary via a lease mechanism. If the primary lease expires and quorum exists, failover is triggered. The listener — a virtual network name that applications connect to — is updated to point to the new primary, and application connections are rerouted automatically.

    Detecting and Recovering from Network Partitions

    A network partition is when some nodes can communicate with each other but not with all nodes. This is different from a total failure. In a three-node cluster with nodes A, B, and C, a partition might leave A able to communicate with B but neither A nor B able to reach C. If C was the primary, A and B should promote a new primary between themselves. But if C can still reach the majority of nodes via another path, split-brain is again the risk.

    Quorum resolves this: only the partition with a majority of nodes can elect a new primary. In a three-node cluster, a majority is two nodes. The partition containing two nodes can elect a new primary; the partition with one node cannot. The isolated node fences itself.

    DBAs must design cluster topology with odd numbers of voters to avoid tie-breaking problems. A two-node cluster with no external quorum witness cannot safely achieve automatic failover without split-brain risk, because each partition of one node cannot determine whether it has a majority. Adding a third node — or a lightweight quorum witness (an etcd node, a file share witness in WSFC, or Patroni's third etcd node) — breaks the tie and makes automatic failover safe.

    PostgreSQL: Checking for Network Partition Effects

    When network instability occurs, replication connections may drop and reconnect repeatedly. The primary's pg_stat_replication view will show standbys appearing and disappearing. A standby that is disconnected but not failed may also hold a replication slot open, preventing WAL cleanup.

    -- Identify inactive replication slots that may be accumulating WAL
SELECT slot_name,
       slot_type,
       active,
       active_pid,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS wal_retained,
       restart_lsn,
       wal_status
FROM pg_replication_slots
WHERE active = FALSE
ORDER BY pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) DESC;

-- Drop a slot that has become dangerously stale (confirm replica is gone first)
-- SELECT pg_drop_replication_slot('stale_slot_name');

    Consistency Models in Practice: Read-Your-Writes, Monotonic Reads, and Causal Consistency

    CAP theorem describes system-level guarantees. Application developers and DBAs also need to reason about session-level consistency guarantees, because even in an eventually consistent system, certain properties can be preserved without sacrificing availability.

    Read-Your-Writes (RYW): A client that performs a write should always see that write in subsequent reads. This sounds obvious but breaks in distributed systems when reads are routed to a replica that has not yet applied the write. An e-commerce application where a user updates their shipping address and then immediately views their order — and sees the old address — has violated RYW. The fix is either to route reads for that session to the primary temporarily, or to track the write's LSN and ensure the replica has reached that LSN before serving the read.

    PostgreSQL provides pg_current_wal_lsn() on the primary and pg_last_wal_replay_lsn() on standbys. Application-level RYW logic can capture the LSN at write time and wait until a chosen replica reaches that LSN before redirecting reads.

    -- On standby: wait until the replica has replayed past a given LSN
-- pg_wal_lsn_diff returns 0 or negative when standby has caught up
SELECT pg_wal_lsn_diff('0/1A3F2C0'::pg_lsn, pg_last_wal_replay_lsn()) AS bytes_behind;

    SQL Server readable secondaries face the same challenge. The sys.dm_hadr_database_replica_states view exposes last_received_lsn and last_hardened_lsn, which can be used to implement similar application-level RYW logic.

    Monotonic Reads: A client should not observe older data after having observed newer data. If a user refreshes a page and their query is routed to different replicas on each refresh, and one replica is slightly behind the other, the user might see a post appear and then disappear on the next refresh. Sticky session routing — always routing a given user's reads to the same replica — is the simplest mitigation, at the cost of uneven load distribution.

    Causal Consistency: A stronger property than eventual consistency but weaker than strong consistency. If operation B depends causally on operation A, any client that observes B must also observe A. Distributed systems that implement vector clocks or hybrid logical clocks can track causality and ensure that reads never violate causal ordering. CockroachDB and YugabyteDB (both PostgreSQL-compatible distributed databases) implement causal consistency at the engine level. PostgreSQL itself, when used with a single primary, provides full linearizability for transactions on that primary; it is only in the multi-primary or replica-read path that these weaker consistency models become relevant.

    DBAs rarely need to implement causal consistency infrastructure themselves, but they need to understand it well enough to evaluate claims made by middleware vendors and to diagnose application bugs that manifest as "data flickering" or "ghost writes."

    Geographic Distribution: Multi-Region Deployments

    When data must be served from multiple geographic regions — whether for latency reduction, data sovereignty compliance, or disaster recovery — the distributed database problem gains another dimension.

    A multi-region deployment must answer several questions:

  • → Where do writes originate, and how are they propagated to other regions?
  • → How is failover handled if the primary region becomes unreachable?
  • → How is read latency minimized for users in distant regions?
  • → How do data residency regulations affect which data can live in which region?

    • Single-Primary Multi-Region

    The simplest model is a single primary in one region with asynchronous replicas in other regions. Reads from distant regions are served locally; writes always travel to the primary region. This introduces write latency proportional to the round-trip time between the user's region and the primary region. For a user in Singapore writing to a primary in Virginia, that round trip can exceed 200 milliseconds — acceptable for some workloads, unacceptable for others.

    PostgreSQL achieves this with streaming replication across regions. The primary is in one availability zone or data center; standbys in each remote region connect and replay WAL. A connection pooler or load balancer in each region routes read queries to the local standby and write queries to the primary.

    SQL Server achieves the same with AG replicas distributed across Azure regions or on-premises data centers. The readable secondary in each region serves local reads; the primary handles all writes.

    Active-Active Multi-Region

    The more ambitious architecture is active-active: each region can accept writes. This eliminates write latency for all users but introduces the hardest problem in distributed databases — multi-master conflict resolution. Two users in different regions modifying the same row simultaneously will produce a conflict that the system must detect and resolve.

    PostgreSQL does not natively support active-active multi-master replication. The ecosystem solutions are BDR (Bi-Directional Replication), provided by EDB (EnterpriseDB), and Citus. BDR implements last-write-wins (LWW) conflict resolution by default, with hooks for custom conflict handlers. It uses logical replication extended to propagate changes in both directions between nodes. Conflicts are detected by comparing transaction timestamps from a clock synchronization layer.

    SQL Server has no native active-active multi-master replication for OLTP workloads either. Merge replication, an older feature, implements a form of it with conflict resolution rules, but it has well-known scalability limitations and is generally not recommended for high-throughput systems. Azure Cosmos DB, Microsoft's globally distributed NoSQL database, was built from the ground up for multi-master with configurable consistency levels, but it is a different product and data model.

    The operational lesson here is firm: active-active multi-master OLTP replication is genuinely difficult, and any vendor claiming it is simple deserves scrutiny. The complexity lives in conflict detection, conflict resolution, schema change management across nodes, and the testing burden of validating that the application behaves correctly under conflict conditions.

    Data Sovereignty and Partitioned Geographic Data

    Some workloads cannot use a single global replica set due to regulatory requirements — the data for EU users must remain in the EU, data for US users must remain in the US. This mandates a geographically partitioned data model: EU users' data physically stored only on EU-region nodes, US users' data on US-region nodes, with no cross-region replication of user-identifiable records.

    This is a sharding problem with geographic constraints. The shard key is user region or data residency classification. A global coordination layer routes requests to the correct regional shard. Each regional shard is independently replicated for HA within its region. Cross-region reporting must be carefully designed to use only anonymized or aggregated data that is permitted to cross borders.

    Distributed Query Processing and the Cost of Cross-Node Joins

    In a distributed database, the query planner faces a problem that does not exist in a single-node system: data needed for a join might reside on a different node, and retrieving it requires a network transfer. This transfer — called a data shuffle or broadcast — is often the dominant cost in distributed queries.

    Citus (PostgreSQL) and Azure Synapse Analytics (SQL Server's distributed analytics engine) both implement distributed query planners that optimize this problem. The key insight is co-location: if two tables are distributed by the same column and their shard keys match, a join between them can be executed entirely on individual worker nodes without any data transfer. If they are not co-located, the planner must choose between broadcasting the smaller table to all workers or redistributing one table by the join key.

    Citus co-location example:

    -- Distribute orders and order_items on customer_id so joins are co-located
SELECT create_distributed_table('orders', 'customer_id');
SELECT create_distributed_table('order_items', 'customer_id', colocate_with => 'orders');

-- This join executes locally on each shard — no cross-node data movement
SELECT o.order_id,
       o.order_date,
       SUM(oi.quantity * oi.unit_price) AS total
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
                    AND o.customer_id = oi.customer_id
WHERE o.customer_id = 98765
GROUP BY o.order_id, o.order_date;

    When queries cannot be co-located — for example, a report that aggregates across all customers — Citus parallelizes execution across all workers and merges results on the coordinator. The coordinator becomes the bottleneck for such queries, which is why distributed OLTP systems require careful schema design to ensure the hot path (per-customer or per-tenant operations) is always co-located.

    SQL Server Distributed Query via Linked Servers and PolyBase

    SQL Server's traditional approach to cross-node queries is linked servers, which allow a query on one instance to reference tables on another using four-part naming (server.database.schema.table). The query optimizer can push some predicates down to the remote server, but complex joins involving remote tables are expensive and often result in the local instance pulling the full remote table and joining locally.

    PolyBase, introduced for SQL Server in version 2016, is a more modern approach to distributed queries. It was designed for querying external data sources — Hadoop, Azure Blob Storage, Azure Data Lake — using T-SQL. In SQL Server 2019 and later, PolyBase Scale Out Groups allow a primary SQL Server compute head node to distribute query execution across multiple compute nodes, each reading from external data. This is targeted at analytical workloads, not OLTP.

    -- SQL Server: Create an external data source for PolyBase
CREATE EXTERNAL DATA SOURCE AzureDataLakeSource
WITH (
    LOCATION = 'abfss://container@storageaccount.dfs.core.windows.net',
    CREDENTIAL = AzureStorageCredential
);

-- Define external file format
CREATE EXTERNAL FILE FORMAT ParquetFormat
WITH (FORMAT_TYPE = PARQUET);

-- Query external data as if it were a local table
CREATE EXTERNAL TABLE dbo.ExternalOrders (
    OrderID     BIGINT,
    CustomerID  BIGINT,
    OrderDate   DATE,
    TotalAmount DECIMAL(12, 2)
)
WITH (
    LOCATION = '/orders/2024/',
    DATA_SOURCE = AzureDataLakeSource,
    FILE_FORMAT = ParquetFormat
);

SELECT CustomerID,
       COUNT(*) AS order_count,
       SUM(TotalAmount) AS revenue
FROM dbo.ExternalOrders
WHERE OrderDate >= '2024-01-01'
GROUP BY CustomerID
ORDER BY revenue DESC;

    The consistent theme across both platforms is that distributed query processing requires the DBA and data architect to deeply understand where data lives and to design schemas and query patterns that minimize cross-node data movement. Treating a distributed system as if it were a single node — writing queries without regard to data locality — consistently produces the worst possible performance outcomes.

    Handling Schema Changes in Distributed Systems

    Schema migrations in single-node databases are disruptive but manageable. In distributed systems, they become a coordination problem of a different order. If you have eight shards and need to add a column, you must apply that migration to all eight shards in a way that does not break the application during the migration window.

    The fundamental challenge is that schema changes are not atomic across nodes. While node 1 is receiving the migration, node 2 may still be running the old schema. During this window, if an application query involves both nodes, the result depends on which schema version each node is executing against. Columns that exist on one node but not another will cause errors or incorrect results.

    Online Schema Change Strategies

    The safe approach for high-availability distributed systems is the expand/contract pattern:

    1. Expand: Add the new column (or table, or index) as nullable with no constraints. All nodes can accept writes in both the old and new schema because the new column is optional. Deploy this migration to all nodes before changing application code.

    2. Migrate: Backfill existing rows with values for the new column, in batches, to avoid long-running transactions that hold locks.

    3. Contract: Once all application code has been updated to write to the new column and all existing rows have been backfilled, add constraints, set defaults, or drop old columns.

    PostgreSQL's ALTER TABLE ... ADD COLUMN with a default value that requires a table rewrite was historically a long-blocking operation. Since PostgreSQL 11, adding a column with a non-volatile default does not require a table rewrite and takes only a brief lock. This makes expand operations much faster. However, adding a NOT NULL constraint without a default still requires scanning the entire table.

    Tools like pg_repack and pglogical-based online migrations are commonly used in Citus or manual sharding deployments to apply schema changes with minimal downtime.

    SQL Server offers ALTER TABLE ... ADD for new nullable columns as a metadata-only operation, similarly fast. Adding constraints, however, can require full table scans. WITH NOCHECK defers constraint validation, allowing the schema change to complete quickly while accepting that existing data has not been validated — a trade-off that must be explicitly acknowledged and managed.

    -- PostgreSQL: Add column safely (metadata-only if default is immutable, PG11+)
ALTER TABLE orders ADD COLUMN shipping_region TEXT DEFAULT 'UNASSIGNED';

-- Add NOT NULL constraint without full scan by using a check constraint trick
-- Step 1: Add as nullable first
ALTER TABLE orders ADD COLUMN priority_level INT;
-- Step 2: Set constraint as NOT VALID (applies to new rows only, no full scan)
ALTER TABLE orders ADD CONSTRAINT chk_priority_not_null CHECK (priority_level IS NOT NULL) NOT VALID;
-- Step 3: Validate existing rows in a separate operation (takes ShareUpdateExclusiveLock, not AccessExclusiveLock)
ALTER TABLE orders VALIDATE CONSTRAINT chk_priority_not_null;
    -- SQL Server: Add nullable column (metadata-only, no table rebuild)
ALTER TABLE dbo.Orders ADD ShippingRegion NVARCHAR(100) NULL DEFAULT 'UNASSIGNED';

-- Add constraint with NOCHECK to defer validation of existing rows
ALTER TABLE dbo.Orders WITH NOCHECK
ADD CONSTRAINT chk_PriorityNotNull CHECK (PriorityLevel IS NOT NULL);

-- Later, validate existing rows explicitly
ALTER TABLE dbo.Orders WITH CHECK CHECK CONSTRAINT chk_PriorityNotNull;

    In a distributed deployment, each of these steps must be applied to every node before proceeding to the next step. Automation tools — Flyway, Liquibase, or custom migration frameworks — should be configured to apply migrations serially across all nodes with health checks between each application. A failed migration on one node must halt the entire migration run, not be silently skipped.

    Observability in Distributed Database Systems

    Single-node database monitoring is straightforward: connect to the instance, query the system catalog and wait event views, check slow query logs. Distributed systems require a more sophisticated observability approach because a problem may manifest on one node but originate on another, and correlating events across nodes requires that all nodes share a common time reference and that telemetry is aggregated centrally.

    Distributed Tracing

    In a distributed application, a single user request may touch a connection pooler, the coordinator node of a Citus cluster, multiple worker nodes, and then an application server. Understanding the latency breakdown requires distributed tracing — each component emitting spans that can be correlated by a shared trace ID. OpenTelemetry is the emerging standard for this. PostgreSQL itself does not yet emit OpenTelemetry spans natively, but instrumentation can be added at the connection pooler layer (PgBouncer, pgcat) and at the application layer.

    SQL Server in Azure emits distributed tracing telemetry through Azure Monitor and Application Insights. On-premises, SQL Server Extended Events can capture query execution at each node, and correlation can be done by matching session IDs and timestamps, though this is considerably more manual.

    Centralized Log Aggregation

    Every node in a distributed database cluster must ship its logs to a central store. Elasticsearch, Loki, or a SIEM platform are common targets. Structured logging — JSON-formatted log lines with consistent field names — makes cross-node correlation possible. PostgreSQL's log_line_prefix should include %t (timestamp), %p (PID), %a (application name), and %d (database name) at minimum. In a distributed deployment, adding the hostname is essential.

    # postgresql.conf: structured log prefix for distributed environments
log_line_prefix = '{"time":"%t","pid":%p,"user":"%u","db":"%d","app":"%a","host":"%h"} '

    SQL Server's default logging to the Windows Event Log is insufficient for distributed deployments. Configuring SQL Server Agent alerts to ship critical events to a centralized SIEM, combined with shipping XEvent trace files to a central repository, provides the necessary visibility.

    Metrics and Alerting

    Prometheus with postgres_exporter is the standard metrics pipeline for PostgreSQL clusters. In a distributed deployment, each node — primary, standbys, Citus workers — runs its own exporter. Prometheus scrapes all exporters; Grafana provides dashboards that display per-node metrics side by side. Key metrics to alert on:

  • → Replication lag (bytes and estimated seconds) per standby
  • → WAL generation rate on the primary
  • → Replication slot WAL retention (to catch runaway slots)
  • → Connection count vs. `max_connections` per node
  • → Lock wait events and deadlock rates
  • → Query percentile latencies (p50, p95, p99) per node and per query fingerprint

    • SQL Server deployments commonly use SQL Server Management Data Warehouse, Azure Monitor, or third-party tools like SolarWinds DPA or Datadog's SQL Server integration. The equivalent key metrics are AG synchronization lag, log send queue depth, redo queue depth, blocking chains, and wait statistics per node.

    When to Choose Managed Distributed Database Services

    The operational burden of running a distributed database — configuring replication, managing failover, handling schema changes across shards, setting up observability — is substantial. For many organizations, managed cloud database services transfer much of that burden to the cloud provider.

    For PostgreSQL workloads, the managed options include:

  • → **Amazon Aurora for PostgreSQL**: A distributed storage layer that replicates six copies of data across three Availability Zones, with a PostgreSQL-compatible compute layer. Aurora handles storage replication transparently; the DBA manages the compute instances and read replica routing.
  • → **Google Cloud Spanner**: A globally distributed, strongly consistent database with a PostgreSQL interface. Spanner uses TrueTime (GPS- and atomic-clock-based time synchronization) to achieve external consistency without sacrificing global write throughput. It abstracts all sharding and replication from the operator.
  • → **Azure Database for PostgreSQL – Flexible Server**: Provides HA with zone-redundant standby, automated backups, and read replicas. Less complex than self-managed Citus but less horizontally scalable.
  • → **CockroachDB and YugabyteDB**: PostgreSQL-compatible distributed databases built from the ground up for horizontal scale with strong consistency. They handle sharding, replication, and distributed transaction coordination internally.

    • For SQL Server workloads, the primary managed options include:

  • → **Azure SQL Database**: Offers built-in HA, geo-redundant backups, active geo-replication, and auto-failover groups. The Business Critical tier replicates across three nodes using an Always On AG under the hood, transparently managed.
  • → **Azure SQL Managed Instance**: A fully managed instance with near-complete compatibility with on-premises SQL Server, supporting AG-based HA and geo-replication. Suitable for lift-and-shift migrations that require features unavailable in Azure SQL Database.

    • The DBA's role in managed distributed services shifts from infrastructure management to configuration governance, query performance optimization, capacity planning, and cost control. These are not lesser concerns — poorly configured managed services can be more expensive and less performant than well-tuned self-managed deployments — but they are different skills from the low-level cluster management that self-managed distributed databases require.

    ---

    Key Takeaways

  • → **Distribution is driven by specific pressures** — storage limits, read throughput, write throughput, and availability requirements — and the right architecture depends on which pressure is dominant. Applying full horizontal sharding to solve a read-scale problem is over-engineering; using a simple read replica set when writes exceed single-node capacity is under-engineering.
  • → **Replication is the foundation of every distributed PostgreSQL and SQL Server deployment**, but replication type — physical vs. logical in PostgreSQL, transactional vs. AG-based in SQL Server — determines what operations are possible, what consistency guarantees apply, and what the operational overhead looks like. Choosing the wrong replication model creates constraints that are expensive to reverse.
  • → **Distributed transactions via two-phase commit carry significant performance costs** and introduce failure modes — in-doubt transactions, coordinator crashes — that require operational procedures beyond normal database administration. Where throughput demands are high, alternative patterns (sagas, event sourcing, compensating transactions) are often preferable to 2PC.
  • → **Split-brain prevention through fencing is non-negotiable** in any system with automatic failover. A distributed database architecture that cannot guarantee fencing will eventually experience a split-brain event, and the data divergence that results is among the most costly incidents a database team can face. Quorum-based solutions (Patroni with etcd, WSFC with quorum) are the standard approach.
  • → **Observability in distributed systems requires centralized log aggregation, unified metrics collection across all nodes, and an understanding of per-node health that goes beyond what single-instance monitoring provides.** Replication lag, WAL retention by replication slots, cross-node query latency, and schema migration status across all nodes must be continuously monitored and alerted upon. The invisible failure — a replica quietly falling behind, a stale replication slot slowly filling the disk — is the distributed system's most insidious threat.
