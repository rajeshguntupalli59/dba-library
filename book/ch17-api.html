Chapter 17: API Interactions

Modern applications rarely talk to a database directly through a query tool. Instead, they interact through layers of code — REST APIs, GraphQL endpoints, microservices, and background workers — all of which ultimately translate user actions into SQL. As a DBA, understanding how these API layers communicate with your database is no longer optional. The queries that arrive at your server carry context from the calling application: how connections are managed, how parameters are passed, how transactions are scoped, and how errors flow back to the client. This chapter covers what DBAs need to know about API-to-database interactions, from connection patterns and parameterized queries to bulk operations, pagination, and the failure modes that only reveal themselves under production load.

---

How Applications Connect: Connection Pooling and the DBA's Role

Every API call that needs data starts with a connection. In a naive implementation, the application opens a new database connection for each request and closes it when done. This works fine for a single developer testing locally and falls apart completely when a thousand users hit the service simultaneously. Establishing a SQL Server connection involves TCP handshaking, authentication, session initialization, and memory allocation on the server — often 5–50ms of overhead that adds up fast.

Connection pooling sits between the application and the database, maintaining a pool of pre-established connections handed to incoming requests. SQL Server applications rely on ADO.NET/SqlClient connection pooling built into the .NET runtime — enabled by default, keyed by the exact connection string, governed by Min Pool Size and Max Pool Size. ODBC and JDBC drivers pool the same way. The key DBA-visible point: pooling is per application process, so a fleet of app servers multiplies the real connection count — size pools against the fleet, not a single instance.

From the DBA's perspective, the first thing to know is how many connections your server is actually handling. In SQL Server, sys.dm_exec_sessions shows every session and what it is doing; join it to sys.dm_exec_requests for the currently executing batch. Monitoring these views regularly reveals whether a connection pool is sized correctly, whether connections are leaking, or whether a runaway service is spawning connections without releasing them.

-- See all active sessions, their status, and what they're waiting on
SELECT
    s.session_id,
    s.login_name,
    s.program_name,
    s.client_interface_name,
    s.status,
    s.last_request_start_time,
    wt.wait_type,
    wt.wait_duration_ms,
    LEFT(qt.text, 80) AS current_query
FROM sys.dm_exec_sessions s
LEFT JOIN sys.dm_exec_requests r ON s.session_id = r.session_id
LEFT JOIN sys.dm_os_waiting_tasks wt ON r.task_address = wt.task_address
OUTER APPLY sys.dm_exec_sql_text(r.sql_handle) qt
WHERE s.is_user_process = 1
ORDER BY s.last_request_start_time DESC;

Understanding what happens when a pooled connection is reused matters too. When SqlClient returns a connection to the pool and hands it out again, the driver issues sp_reset_connection — a lightweight server-side reset that rolls back open transactions, drops temp tables, and reverts most SET options. It does not reset everything: some session state can leak between checkouts if the application set options the reset doesn't cover. DBAs who get complaints about inconsistent behavior across requests need to check whether the application is relying on session-level settings that aren't surviving the reset — the fix is to set required options explicitly per batch, not to assume they persist.

One thing worth tracking is connection count against worker-thread capacity. In SQL Server each connection consumes a worker thread; max worker threads scales with CPU count, but thousands of concurrently active connections still cause scheduler contention. The database handles hundreds of connections comfortably — but each idle connection still costs memory and each active one costs a worker. Size pools (Max Pool Size) from measured concurrency, not guesswork, and watch sys.dm_os_schedulers for runnable-queue buildup that signals thread pressure.

SQL Server uses a thread-based model rather than a process-per-connection model, making it more tolerant of high connection counts, but connection sprawl still causes contention on internal memory structures and the thread scheduler. Keeping connection counts disciplined matters regardless of platform.

Parameterized Queries: Safety, Performance, and What DBAs Actually See

The most important habit any API developer can have is using parameterized queries. As a DBA, you care about parameterization for three separate reasons: security, plan reuse, and query diagnostics.

The security argument is well known — string interpolation allows SQL injection. The performance argument is less appreciated but equally important. When a query arrives at SQL Server with a hardcoded literal, the optimizer treats each unique literal as a potentially unique query and may compile it separately — flooding the plan cache with single-use plans. When queries are parameterized, the planner can recognize that the structure is the same and reuse a cached execution plan, saving planning overhead on every subsequent execution.

In SQL Server, Query Store tracks query performance by query hash — parameterized queries appear with their parameter placeholders intact (as @P1, @P2), making it easy to identify slow query patterns. Ad-hoc queries with literals get normalized too, but parameterized batches go further: the plan cache reuses the compiled plan across executions, saving compile overhead on every subsequent call.

In SQL Server, the equivalent mechanism is plan caching in the procedure cache. Parameterized queries submitted through sp_executesql are the T-SQL equivalent of prepared statements, and they allow the server to match the query to an existing cached plan by its hash.

-- Check plan cache for most expensive queries by total CPU
SELECT TOP 20
    qs.execution_count,
    qs.total_worker_time / 1000             AS total_cpu_ms,
    qs.total_worker_time / qs.execution_count / 1000 AS avg_cpu_ms,
    qs.total_elapsed_time / 1000            AS total_elapsed_ms,
    LEFT(qt.text, 100)                      AS query_pattern,
    qp.query_plan
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) qt
CROSS APPLY sys.dm_exec_query_plan(qs.plan_handle) qp
ORDER BY qs.total_worker_time DESC;

One subtle issue DBAs encounter with parameterized queries is parameter sniffing in SQL Server. The first time a parameterized query executes, the optimizer generates a plan based on the actual parameter values provided. If that first execution happens to use a highly selective value, the cached plan will assume a small result set and use an index seek. When the same query later runs with a parameter that matches millions of rows, it still uses the seek plan, which is now catastrophically inefficient. This is one of the more common causes of intermittent performance problems in production SQL Server environments.

The SQL Server version of this problem is parameter sniffing: the first execution's parameter values shape the cached plan, and later executions with very different values can get a terrible plan. The mitigations live in the usual toolbox — OPTION (RECOMPILE), OPTIMIZE FOR hints, plan guides, Query Store forced plans — but the DBA's first job is recognizing the signature: one query, wildly varying runtimes, same plan hash.

APIs built on ORMs (Object-Relational Mappers like Hibernate, Entity Framework, or SQLAlchemy) typically parameterize queries automatically, which is good for security but creates its own diagnostics challenges. The SQL that arrives at the server is often unrecognizable from the ORM code that generated it — aliased tables, redundant joins, and nested subqueries are common. When a developer tells you "this endpoint is slow," your first step is capturing the actual SQL hitting the database, not the ORM method call.

Transaction Scope and API Design: Where Things Go Wrong

Transactions in API contexts fail in two distinct directions: they are either too long or too short. Both cause production problems, and as a DBA you are usually the one who discovers the evidence after something has gone wrong.

Long transactions occur when an API endpoint opens a transaction, does some work, and then makes a network call (to another service, to an external payment provider, to a file system) while the transaction is still open. If the network call takes 3 seconds and the API handles 200 concurrent requests, you can have 200 transactions open simultaneously, each holding locks on rows they have already touched. In SQL Server, long-running transactions also block version-store cleanup under row-versioning isolation (RCSI/snapshot), which bloats tempdb — and they hold locks that block everyone else for the duration.

You can identify long-running transactions and their oldest open transaction age directly from the catalog:

-- Find long-running transactions and associated blocking
SELECT
    at.transaction_id,
    at.name                             AS transaction_name,
    at.transaction_begin_time,
    DATEDIFF(SECOND, at.transaction_begin_time, GETDATE()) AS age_seconds,
    s.session_id,
    s.login_name,
    s.program_name,
    LEFT(qt.text, 120)                  AS last_query
FROM sys.dm_tran_active_transactions at
JOIN sys.dm_tran_session_transactions st ON at.transaction_id = st.transaction_id
JOIN sys.dm_exec_sessions s ON st.session_id = s.session_id
LEFT JOIN sys.dm_exec_requests r ON s.session_id = r.session_id
OUTER APPLY sys.dm_exec_sql_text(r.sql_handle) qt
WHERE DATEDIFF(SECOND, at.transaction_begin_time, GETDATE()) > 30
ORDER BY age_seconds DESC;

Short transactions (or rather, the lack of explicit transactions in multi-step operations) are equally problematic. An API that performs a debit from one account and a credit to another as two separate, autocommitted statements risks ending up in a state where the debit succeeds and the credit fails — a real data integrity problem. ORMs with lazy loading or deferred constraint checking can also execute statements in an order that surprises developers if they have not thought carefully about transaction boundaries.

The correct design principle is that a transaction should encompass exactly the database operations that must succeed or fail together — nothing more, nothing less. In practice, this means API handlers should open a transaction, complete all database work, and commit before doing anything that might block or fail externally. This is standard advice that gets violated constantly under deadline pressure, and the DBA is usually the one producing the evidence of what happened.

Savepoints are a useful but underused feature in API-driven transaction design. They allow an application to mark a point within a transaction to which it can roll back partially, without aborting the entire transaction. SQL Server supports them as partial rollbacks: SAVE TRANSACTION marks the point, ROLLBACK TRANSACTION savepoint_name rolls back to it.

One nuance specific to pooled connections: if an application begins a transaction and then crashes or loses its connection before committing, sp_reset_connection rolls back the orphaned transaction when the connection is reclaimed — but until that connection is reused, its locks can linger. Building retry logic and monitoring for blocked queries (sys.dm_exec_requests with a non-null blocking_session_id) are both essential defenses.

Bulk Operations and Efficient Data Loading via APIs

A common pattern in API-driven systems is the batch endpoint: receive a payload of 100, 1000, or 10,000 records from an upstream service and persist them in the database. How you implement the persistence layer for these operations has an enormous effect on throughput, lock contention, and recoverability.

The worst approach is a loop: iterate over the records in application code and execute one INSERT per row. This results in one network round-trip per row, one transaction per row if autocommit is on, and minimal throughput. A service loading 10,000 records one at a time with a 1ms round-trip time will spend at least 10 seconds just on network overhead.

The better approach is multi-row INSERT, which batches multiple rows into a single statement. Most drivers support this transparently when you use their batch insert APIs. SQL Server handles multi-row inserts efficiently — one round trip, one transaction, one log stream.

For very large volumes, the SqlBulkCopy API in .NET (or BULK INSERT / bcp) is the fastest ingestion mechanism available. It bypasses much of the per-row overhead of individual INSERT statements and is optimized for streaming large datasets — and with minimal-logging prerequisites met, it keeps the transaction log lean too.

-- Multi-row INSERT with OUTPUT clause for API response building
INSERT INTO orders (customer_id, product_id, quantity, created_at)
OUTPUT INSERTED.order_id, INSERTED.created_at
VALUES
    (@cust1, @prod1, @qty1, GETDATE()),
    (@cust2, @prod2, @qty2, GETDATE()),
    (@cust3, @prod3, @qty3, GETDATE());

-- For large bulk loads, use SqlBulkCopy from .NET or:
-- BULK INSERT orders
-- FROM 'C:\data\orders.csv'
-- WITH (FORMAT = 'CSV', FIRSTROW = 2);

An important consideration for bulk INSERT operations in production is what happens when some rows violate constraints. A batch of 1,000 records where row 743 has a duplicate key will, by default, fail the entire statement and insert nothing. Applications need a strategy for handling partial failures.

SQL Server provides MERGE for upsert semantics, though MERGE has well-documented edge cases around race conditions and should be used carefully in high-concurrency environments. A safer pattern for many upsert scenarios is a targeted UPDATE followed by an INSERT WHERE NOT EXISTS.

Index maintenance during bulk loads deserves attention. If you are loading data into a table with many indexes, each inserted row triggers index updates. For very large loads into a table where you control the process (a data warehouse refresh, for instance), dropping non-essential indexes before the load and rebuilding them afterward is often faster than loading with indexes in place. For OLTP tables where you cannot drop indexes, loading in smaller batches during off-peak hours and monitoring lock contention is a more realistic approach.

Pagination, Cursor-Based Reads, and Result Set Design

APIs that expose query results to clients almost always need pagination. Returning all 500,000 rows from an orders table in a single API response is not a design option. The two dominant approaches — offset-based pagination and cursor-based pagination — have very different performance profiles, and the choice matters as table sizes grow.

Offset-based pagination uses OFFSET FETCH in SQL Server. It is simple to implement and easy to understand: the client requests page 1, page 2, page 3. The problem is that OFFSET N is not free. The database must scan and discard the first N rows to reach the page you want. Page 1 is fast. Page 1000 of a 1,000-row page size requires the database to process 999,000 rows before returning anything. For many API use cases — mobile feeds, admin dashboards, reports — users rarely navigate past the first few pages, and offset pagination is perfectly adequate. For deep pagination scenarios, it breaks down.

Cursor-based pagination uses a stable column value (typically a primary key or a timestamp + ID combination) as an anchor point. Instead of "give me rows 10,000 through 10,025," the query says "give me the 25 rows where the ID is greater than the last ID I saw." This is consistently fast regardless of how deep into the dataset you are, because the database uses an index seek rather than a scan-then-skip.

-- Offset-based pagination using OFFSET-FETCH
SELECT order_id, customer_id, total_amount, created_at
FROM orders
WHERE status = @status
ORDER BY created_at DESC, order_id DESC
OFFSET @offset ROWS
FETCH NEXT @page_size ROWS ONLY;

-- Cursor-based (keyset) pagination
SELECT TOP (@page_size)
    order_id, customer_id, total_amount, created_at
FROM orders
WHERE status = @status
  AND (created_at < @last_created_at
       OR (created_at = @last_created_at AND order_id < @last_order_id))
ORDER BY created_at DESC, order_id DESC;

The keyset approach has a meaningful limitation: you cannot jump to an arbitrary page number. The client must walk forward sequentially, using the last-seen values as its bookmark. This is exactly the right behavior for infinite scroll UIs and API consumers processing a full dataset in order, but it does not suit UIs that show numbered page links.

From the DBA's perspective, there is another pagination-related problem that surfaces in production: the count query. Many APIs return a total record count alongside each page so the UI can display "Page 3 of 47." This requires a COUNT(*) over the full filtered dataset on every page request. For large tables with complex WHERE clauses, this count query can be more expensive than the page query itself. Partial solutions include caching the count for short periods, using SQL Server's sys.partitions for approximate counts, or simply omitting exact counts and using "has more results" indicators instead.

A related issue is sort stability. If rows can be inserted or deleted between page requests, an ORDER BY created_at DESC may produce different row orderings on subsequent pages. Rows can be skipped or appear twice if a new row is inserted at the boundary between pages. Adding the primary key as a secondary sort column (as shown in the examples above) makes the sort deterministic and ensures stable pagination even under concurrent writes.

Error Handling, Retries, and the API-Database Contract Under Pressure

Production API systems fail in ways that development environments never simulate. Network partitions, connection pool exhaustion, deadlocks, serialization failures, and query timeouts all arrive at runtime, and how the application handles them determines whether end users see a graceful degradation or a cascade failure.

From the database side, errors come with codes that carry meaning. SQL Server uses error numbers and severity levels — capture both in your error handling, because the number identifies the condition and the severity tells you how bad it is. API developers often treat all database errors as equivalent "something went wrong" conditions and return a 500 to the client. As a DBA, you want developers to distinguish between categories of errors because the correct response differs.

A serialization failure (error 3960 under snapshot isolation, when an update conflicts with a concurrent one) is a signal to retry the transaction, not to fail it permanently. The database is telling the application: "Your transaction would have produced an incorrect result due to concurrent activity, so I aborted it. Try again." Applications that catch this error and retry with exponential backoff will succeed. Applications that propagate it as an error will confuse users.

A deadlock (error 1205 in SQL Server) is similar — it is a recoverable condition that indicates two transactions were waiting on each other's locks. The database kills one of them and the application should retry. Frequent deadlocks indicate that either the order of lock acquisition is inconsistent across transactions (a design problem) or that contention on hot rows is high (a schema or indexing problem).

A connection pool exhaustion error is a different category entirely. If the SqlClient pool cannot hand a connection to the caller — all Max Pool Size connections busy past the connection timeout — the request should be rejected quickly rather than queued indefinitely, because queuing without a timeout will cause the application to accumulate threads or goroutines waiting for connections, eventually exhausting other resources. The correct response is a 503 Service Unavailable with a Retry-After header, not a 500.

Statement timeouts are an important tool for protecting the database from runaway queries originating from API calls. SQL Server's defenses are layered: the driver's CommandTimeout (SqlClient, JDBC) cancels a runaway command client-side; QUERY_GOVERNOR_COST_LIMIT stops estimated-expensive queries before they start; Resource Governor's REQUEST_MAX_CPU_TIME_SEC caps execution server-side. Set a command timeout on every API data-access call — an endpoint with no timeout is a runaway query waiting for a bad parameter.

Setting appropriate timeouts is a balancing act. Too tight, and legitimate slow queries start failing. Too loose, and a slow query from a misbehaving API endpoint monopolizes connections and degrades the whole system. A common production approach is to set a conservative default (say, 30 seconds at the role level for API service accounts) and override it upward for specific long-running operations like report generation, rather than setting a single permissive timeout for everything.

For teams adopting microservices, the concept of circuit breakers in the API layer has a direct relationship to database health. A circuit breaker monitors the error rate from the database and, when it exceeds a threshold, stops sending requests for a cooldown period. This prevents a struggling database — one that is under lock contention or I/O pressure — from being hammered with retry storms that make recovery slower. This is application-level behavior, but DBAs who understand it can collaborate more effectively with developers when diagnosing cascading failures.

Finally, observability: the most useful thing an API service can do from the DBA's perspective is propagate a correlation ID from the HTTP request into the database session. SQL Server's Application Name connection-string keyword and sp_set_session_context carry arbitrary string metadata that appears in the server's activity views. When an alert fires at 2 AM and you need to know which API endpoint is generating the slow queries, a correlation ID in the session context is the difference between a five-minute diagnosis and a two-hour investigation.

Key Takeaways

  • → **Connection pooling is a shared responsibility** between DBAs and developers. DBAs must set server limits appropriately, monitor active connections continuously, and communicate pool configuration constraints — especially around session-level state like prepared statements and `SET` commands that don't survive transaction-mode pooling.
  • → **Parameterized queries matter for three reasons, not just one.** Beyond preventing SQL injection, parameterization enables plan reuse and makes query diagnostics tractable — but it also introduces parameter sniffing as a real, intermittent performance failure mode — one query, wildly varying runtimes, same plan hash.
  • → **Transaction scope should match exactly the database work that must succeed or fail together.** Transactions held open across external network calls cause lock contention and block version-store cleanup under RCSI; conversely, related writes executed without a transaction at all risk partial failure and real data integrity problems.
  • → **Bulk operations need a batching strategy, not a row-by-row loop.** Multi-row inserts, `BULK INSERT`/`bcp` for large volumes, and an explicit upsert pattern (`MERGE`) for handling partial failures are what separate an API endpoint that scales from one that collapses under real load.
  • → **Pagination strategy should match access pattern.** Offset-based pagination is simple and fine for shallow browsing, but degrades badly at depth; keyset/cursor pagination stays fast at any depth but can't jump to an arbitrary page — and a stable secondary sort key (usually the primary key) is required either way to avoid skipped or duplicated rows under concurrent writes.
  • → **Database errors carry meaning that API code should respect.** Serialization failures and deadlocks are recoverable conditions meant to be retried; connection pool exhaustion should fail fast with a `Retry-After` rather than queue indefinitely; and propagating a correlation ID from the HTTP request into the database session (`application_name`, `sp_set_session_context`) turns a multi-hour production investigation into a five-minute one.
