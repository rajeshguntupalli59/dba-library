Chapter 5: Storage Models

How a database stores data on disk is not just a mechanical detail — it is one of the most consequential architectural decisions shaping query performance, write throughput, compression ratios, and maintenance overhead. SQL Server takes a deliberate, layered approach to organizing data on storage, and understanding it at a fundamental level separates DBAs who tune by intuition from those who tune by understanding. This chapter covers how rows and pages are structured, how heaps and clustered indexes differ as storage strategies, how columnar storage changes the game for analytical workloads, and how the engine manages free space and page layout internally. By the time you finish this chapter, you will be able to look at a slow query or a bloated table and reason from first principles about what the storage layer is doing.

---

Pages, Blocks, and the Unit of I/O

Every database operation — whether it reads one row or one million — ultimately works in units of pages. Understanding the page is the starting point for everything else in this chapter.

In SQL Server, data is not read byte-by-byte from disk. The database engine reads and writes entire fixed-size blocks, and these blocks are what live in the buffer pool. Any time you read a single row, the engine loads the entire page that contains that row into memory. This is why page size, row size, and row density matter so much.

SQL Server uses a fixed page size of 8 KB — not configurable, which simplifies every capacity calculation you will ever do. Pages are grouped into extents of eight contiguous pages (64 KB), and allocation is tracked by a centralized metadata layer: PFS (Page Free Space) pages record how full each page is, GAM and SGAM pages track which extents are free or in use, and IAM (Index Allocation Map) pages record which extents belong to which object. Finding free space for an insert is a metadata lookup against this layer, never a scan.

SQL Server uses a fixed page size of 8 KB, and this is not configurable. SQL Server pages are organized into extents — a group of eight contiguous 8 KB pages — and there are two types: uniform extents (owned by one object) and mixed extents (shared among multiple small objects, used for the first eight pages of any object to avoid wasting space).

Understanding that the page is the atomic unit of I/O has immediate practical consequences. A query that reads 10 rows scattered across 10 different pages causes 10 page reads, while a query that reads 1,000 rows all on the same page causes just 1 page read. This is the physical reason why data locality matters, and it is the foundational argument behind index clustering, table organization, and fill factor settings.

---

SQL Server Heap Storage and Page Layout

A SQL Server heap is an unordered collection of pages where rows are inserted wherever free space is available. There is no physical ordering of rows on disk; the heap is a flat, unordered structure, and each row is located by its RID — the combination of file ID, page ID, and slot number.

Each SQL Server page contains three distinct areas: a 96-byte page header (metadata including page type, allocation status, and free-space pointers), the data rows themselves, and a row-offset array — the slot array — at the end of the page. Rows are addressed through the slot array rather than by physical byte offset, which lets the engine compact free space within a page without invalidating references. Data grows from the top of the usable area downward while the slot array grows from the bottom upward; when the two regions meet, the page is full.

Each row stored in a SQL Server page carries a small record header with status bits, the record length, and — for rows under versioning — a 14-byte versioning tag pointing into tempdb's version store. An UPDATE modifies the row in place when the new version fits on the page; when a variable-length row outgrows its page, the engine forwards the row (in a heap, leaving a forwarding pointer behind) or splits the page (in a clustered index, moving half the rows to a new page). Forwarding pointers and page splits are the two fragmentation mechanisms that make index maintenance a routine DBA task rather than an occasional emergency.

You can inspect page-level information using the pageinspect extension:

-- SQL Server equivalent: examine page internals using DBCC PAGE
-- First find a page number for the orders table
SELECT TOP 1
    allocated_page_page_id,
    allocated_page_file_id
FROM sys.dm_db_database_page_allocations(
    DB_ID(), OBJECT_ID('orders'), NULL, NULL, 'DETAILED'
);

-- Then inspect that page (output goes to the error log / DBCC output)
-- Replace 1 and 123 with your file_id and page_id from above
DBCC PAGE(0, 1, 123, 3) WITH TABLERESULTS;

SQL Server tables are physically stored as extents in the database's data files (.mdf/.ndf), organized by filegroup. Each table or index partition gets its own allocation units — IN_ROW_DATA for regular rows, LOB_DATA for large values, ROW_OVERFLOW_DATA for variable-length columns pushed off-row. The sys.allocation_units catalog view exposes exactly how many pages each allocation unit consumes, which is the ground truth for every "where did my space go" investigation.

One consequence of the heap model is that SQL Server heaps have no concept of a "natural" row order. If you write a query without an ORDER BY, rows can come back in any sequence — not necessarily insertion order, and not the same sequence on repeated runs, especially after rebuilds and new allocations shift row positions. Never rely on observed order without an explicit ORDER BY.

SQL Server's Page Types and the Clustered Index as the Table

SQL Server takes a fundamentally different approach. Rather than a plain heap as the default storage structure, SQL Server organizes the primary copy of table data within a B-tree structure called a clustered index. When you create a table with a primary key, SQL Server creates a clustered index on that key automatically. The leaf level of that B-tree *is* the table data — there is no separate heap file. This makes the clustered index the most architecturally significant index in SQL Server, because choosing the wrong clustering key can affect every other index and every query against that table.

SQL Server uses several specialized page types beyond the basic data page:

  • → **Data pages (type 1):** Store actual row data.
  • → **Index pages (type 2):** Store B-tree index entries.
  • → **Text/Image pages (type 3):** Store LOB data (overflows for large values).
  • → **IAM pages (type 10):** Index Allocation Maps, tracking which extents belong to an object.
  • → **PFS pages (type 11):** Page Free Space pages, recording how full each page is and whether it belongs to a mixed or uniform extent.
  • → **GAM / SGAM pages (types 8 and 9):** Global Allocation Maps, tracking extent ownership across the file.

    • Every SQL Server data file contains a PFS page at page 1, then GAM and SGAM pages at regular intervals, forming an allocation metadata layer the engine consults on every insert — finding a page with free space is a metadata lookup, never a scan.

    When a table does not have a clustered index, it is stored as a heap — an unordered collection of pages with rows addressed by RID. Heaps come with their own maintenance concerns: forwarding pointers accumulate when variable-length rows grow and must be moved, and the only way to clean those up is to rebuild the heap (ALTER TABLE ... REBUILD) or add a clustered index.

    You can check whether your tables are heaps or clustered index structures:

    -- Find all tables that are stored as heaps (no clustered index)
SELECT
    t.name AS table_name,
    SUM(p.rows) AS row_count,
    SUM(a.total_pages) * 8 AS total_space_kb
FROM sys.tables t
JOIN sys.indexes i ON t.object_id = i.object_id
JOIN sys.partitions p ON i.object_id = p.object_id AND i.index_id = p.index_id
JOIN sys.allocation_units a ON p.partition_id = a.container_id
WHERE i.type = 0  -- 0 = HEAP
GROUP BY t.name
ORDER BY total_space_kb DESC;

    A clustered index continuously maintains physical row order as data is inserted, updated, and deleted — at the cost of page splits when rows arrive in non-sequential key order. This self-maintaining order is the clustered index's great strength and its great danger: it makes range scans on the key nearly free, and it makes a poor key choice (random GUIDs, wide volatile columns) a permanent tax on every write and every nonclustered index on the table.

    Columnar Storage: When Row-by-Row Is the Wrong Model

    Row-based storage (both heap and clustered B-tree) works well when queries need entire rows — transactional workloads, point lookups, row updates. But for analytical queries that aggregate a handful of columns across millions of rows, row storage is fundamentally inefficient: the engine reads entire pages containing many columns just to use one or two of them.

    Columnar storage addresses this by storing each column's values contiguously on disk, rather than storing each row's values together. When a query aggregates SUM(revenue) across ten million rows, a columnar engine reads only the revenue column's data — skipping every other column entirely. This reduces I/O dramatically and enables aggressive compression because values within a single column tend to be similar (same data type, often repeating values).

    SQL Server's Columnstore Indexes are its primary columnar storage mechanism. Introduced in SQL Server 2012 and substantially improved in 2016 and 2019, columnstore indexes store data in compressed column segments of roughly one million rows each, grouped into rowgroups. Each rowgroup is compressed independently. SQL Server uses two main compression schemes within columnstores: value encoding and dictionary encoding for low-cardinality columns, and delta encoding for near-sorted numeric sequences.

    There are two types of columnstore indexes in SQL Server:

  • → **Nonclustered columnstore indexes (NCCI):** Added to a row-store table. The table stays in B-tree/heap format, and the NCCI provides an alternate columnar path for analytical queries.
  • → **Clustered columnstore indexes (CCI):** Replace the row-store entirely. The table's primary storage is columnar. This is the right choice for pure data warehouse tables.

    • Operating a columnstore has its own discipline. Trickle inserts and singleton updates fight the format: small batches land in the delta store (a rowstore staging area per rowgroup) and are only compressed into column segments when the rowgroup closes — a table fed one row at a time will sit in the delta store forever and perform like a bad rowstore. Bulk loads, by contrast, bypass the delta store and compress directly. Segment elimination — skipping entire rowgroups using min/max metadata — is what makes columnstore scans fast, and it depends on data being ordered or at least correlated by the filtered columns; randomly ordered loads eliminate nothing. Monitor sys.dm_db_column_store_row_group_physical_stats for rowgroup health: many small OPEN or TRIMMED rowgroups are the signature of a load pattern fighting the format.

    You can create and inspect a columnstore index in SQL Server:

    -- Create a clustered columnstore index on a fact table
-- (This replaces the existing clustered B-tree index)
CREATE CLUSTERED COLUMNSTORE INDEX cci_fact_sales
ON fact_sales
WITH (DROP_EXISTING = OFF, MAXDOP = 4);

-- Inspect columnstore rowgroup health
-- Compressed = good, OPEN = accumulating, TOMBSTONE = being cleaned
SELECT
    object_name(object_id) AS table_name,
    row_group_id,
    state_description,
    total_rows,
    deleted_rows,
    size_in_bytes / 1024.0 / 1024.0 AS size_mb
FROM sys.column_store_row_groups
WHERE object_id = OBJECT_ID('fact_sales')
ORDER BY row_group_id;

    For SQL Server environments that mix OLTP and analytics on the same tables — a pattern called HTAP (Hybrid Transactional/Analytical Processing) — a nonclustered columnstore index on a row-store table is a powerful option. The optimizer will automatically choose the columnstore path for aggregation queries and the B-tree path for single-row lookups. In practice, this requires careful testing: the overhead of maintaining the columnstore's delta store during heavy OLTP writes can become noticeable.

    Free Space Management, Bloat, and Fill Factor

    Even with a well-chosen storage model, tables accumulate waste over time. Understanding how each database manages free space — and how to control it — is a daily operational concern for any production DBA.

    Page Free Space (PFS) pages are the allocation layer's answer to "where can I put this row". Each PFS page tracks roughly 8,000 data pages, recording how full each page is and whether it belongs to a mixed or uniform extent. When the engine needs space for an insert, it consults PFS rather than scanning — and DBCC PAGE can show you the PFS bytes for any page when you are diagnosing allocation anomalies at the physical level.

    Fill factor is the DBA's direct control over free space: CREATE INDEX ... WITH (FILLFACTOR = 80) leaves 20% of each leaf page empty at build time, reserving room for future inserts without immediate page splits. The right fill factor follows the write pattern — 100 (or 0, which means 100) for read-mostly tables, lower for random-insert workloads — and it applies only at index build or rebuild time; everyday inserts still fill pages toward 100% between maintenance windows. This is why rebuild cadence and fill factor are tuned together, never separately.

    Bloat in SQL Server takes three familiar forms. Ghost records from deletes linger until the ghost cleanup task sweeps them, so a table can report more pages than its live rows justify. Forwarded records in heaps accumulate when variable-length rows outgrow their page — each forward adds a page hop to every read of that row. And index fragmentation — logical order diverging from physical order through page splits — degrades range scans until a rebuild or reorganize restores order. sys.dm_db_index_physical_stats reports all of it; the maintenance question is always rebuild versus reorganize, keyed off fragmentation percentage and page count.

    SQL Server manages free space through PFS pages, which record each page's fill percentage in one of five buckets: 0%, 1–50%, 51–80%, 81–95%, and 96–100%. When the storage engine needs a page for a new row, it walks the PFS to find a sufficiently empty page. SQL Server's equivalent of bloat is page fragmentation — both internal (wasted space within a page due to deletes) and external (pages out of logical order on disk). Index rebuild (ALTER INDEX ... REBUILD) eliminates both; index reorganize (ALTER INDEX ... REORGANIZE) reduces external fragmentation without taking a full lock.

    Fill factor is the control knob for proactive free space management. Setting fill factor below 100% instructs the engine to leave a percentage of each page empty during index builds. This reserves space for future inserts and in-place updates, reducing page splits for non-sequential insert patterns.

    -- Rebuild an index with a fill factor of 80% to reduce page splits
-- on a table with frequent inserts in the middle of the key range
ALTER INDEX ix_orders_customer_date
ON orders
REBUILD WITH (FILLFACTOR = 80, ONLINE = ON, MAXDOP = 4);

-- Check current fragmentation and fill factor for all indexes on a table
SELECT
    i.name AS index_name,
    ips.avg_fragmentation_in_percent,
    ips.avg_page_space_used_in_percent,
    ips.page_count
FROM sys.indexes i
CROSS APPLY sys.dm_db_index_physical_stats(
    DB_ID(), OBJECT_ID('orders'), i.index_id, NULL, 'SAMPLED') ips
WHERE ips.page_count > 100
ORDER BY ips.avg_fragmentation_in_percent DESC;

    Choosing the right fill factor is not a universal number. A table with purely sequential inserts (like an append-only log table keyed by an identity column) can safely use fill factor 100 — new rows always go to the end, and no page splits occur. A table with random key inserts (like a UUID primary key) needs a lower fill factor, typically 70–85%, to absorb inserts across the key range. Setting it too low wastes disk space and forces more page reads; setting it too high for a random-insert workload causes constant page splits, generating fragmentation faster than maintenance jobs can address it.

    Row Overflow and Large Object Handling

    Real-world tables frequently contain columns that can be very large — JSON documents, binary files, long text fields, XML payloads. Both databases have mechanisms to handle values that exceed the maximum row size, and understanding these mechanisms helps explain performance surprises with large-value columns.

    Row overflow and LOB storage are SQL Server's answer to oversized values. A row must fit on a single 8 KB page, but variable-length columns (varchar, nvarchar, varbinary) that push the row past ~8,060 bytes are moved off-row into ROW_OVERFLOW_DATA allocation units, leaving only a 24-byte pointer behind. True large values — varchar(max), nvarchar(max), varbinary(max), xml — live in LOB_DATA allocation units as a tree of pages per value. For values that are really files, FILESTREAM and FileTable store the bytes in the NTFS filesystem while keeping them transactionally consistent with the database.

    SQL Server applies one of four storage strategies to large values:

    1. In-row: Values that keep the row under ~8,060 bytes live on the data page itself — the fastest access path, and the reason narrow rows matter.

    2. Row-overflow: Variable-length values that push the row past the limit move to ROW_OVERFLOW_DATA pages, leaving a pointer. The large value types out of row table option can force even small (max) values off-row.

    3. LOB: (max) types and xml live in LOB_DATA allocation units — a B-tree of pages per value, efficient for large documents, expensive for small ones.

    4. FILESTREAM / FileTable: For values that are really files — documents, images, video — bytes live in the filesystem under transactional control, queryable with T-SQL but streamed without dragging them through the buffer pool.

    Off-row storage is largely transparent, but it has a visible performance cost: accessing an overflow or LOB column requires additional page reads beyond the data page. Queries that select SELECT * on a table with large nvarchar(max) or varbinary(max) columns read dramatically more data than queries that select only the small columns. This is one of the most common sources of unexpected I/O — SELECT * on a table with a multi-megabyte JSON payload column can be orders of magnitude slower than selecting the specific columns the query actually needs.

    SQL Server handles large values through row overflow pages and LOB (Large Object) pages. For VARCHAR(MAX), NVARCHAR(MAX), VARBINARY(MAX), XML, and spatial types, SQL Server stores a 24-byte pointer in the main data page and places the actual content on separate LOB allocation units. For VARCHAR(n) and NVARCHAR(n) columns with n > 8000 / 2, the value can overflow onto a row-overflow page if the row's total width exceeds 8,060 bytes.

    SQL Server also supports sparse columns, which store NULL values without any physical space cost. This is a useful feature when a table has hundreds of potential attributes but any given row populates only a small fraction of them — a pattern common in EAV (Entity-Attribute-Value) schemas.

    You can identify tables with significant LOB or row-overflow usage:

    -- Find tables with significant LOB allocation unit usage
SELECT
    t.name AS table_name,
    SUM(CASE WHEN au.type_desc = 'IN_ROW_DATA'
             THEN au.used_pages END) * 8 AS in_row_kb,
    SUM(CASE WHEN au.type_desc = 'LOB_DATA'
             THEN au.used_pages END) * 8 AS lob_kb,
    SUM(CASE WHEN au.type_desc = 'ROW_OVERFLOW_DATA'
             THEN au.used_pages END) * 8 AS overflow_kb
FROM sys.tables t
JOIN sys.partitions p ON t.object_id = p.object_id
JOIN sys.allocation_units au ON p.partition_id = au.container_id
GROUP BY t.name
HAVING SUM(CASE WHEN au.type_desc = 'LOB_DATA'
               THEN au.used_pages END) > 0
ORDER BY lob_kb DESC;

    A practical guideline from production experience: if you have a table where most queries access only a few columns but one or two columns are large and rarely accessed (audit history, raw payload, attachment blob), consider splitting the table vertically — keeping the frequently accessed columns in one table and the large values in a related table accessed only when explicitly needed. This is not premature optimization; it is sound physical design that the engine's overflow architecture does not automatically compensate for.

    ---

    Key Takeaways

  • → **The 8 KB page is the fundamental unit of I/O** in SQL Server. Every performance decision around data layout, index design, and fill factor ultimately comes down to how many pages a query must read — minimizing that number is the goal.
  • → **SQL Server stores tables as heaps or clustered indexes**: heaps carry no physical row order and accumulate forwarded records; clustered indexes make the B-tree leaf level *the table itself* — making clustering-key selection (narrow, static, ever-increasing) one of the most impactful physical design decisions you will make.
  • → **Columnar storage fundamentally changes the I/O pattern for analytical queries**, reading only the columns referenced rather than entire rows; watch rowgroup health in `sys.dm_db_column_store_row_group_physical_stats`, because trickle-fed delta stores and untrimmed rowgroups silently destroy the segment elimination that makes columnstore fast.
  • → **LOB and row-overflow pages** transparently handle large column values, but they carry a real access cost: fetching an off-row column means extra reads beyond the data page, so `SELECT *` on a table with large JSON, text, or binary columns can be far slower than selecting only the columns a query needs. Splitting rarely-accessed large columns into a separate table is a legitimate physical design pattern, not premature optimization.
