Chapter 34: Compliance and Governance

Compliance and governance are not the most glamorous parts of database administration, but they are among the most consequential. A missed audit requirement or an improperly protected column of personally identifiable information can result in regulatory fines, legal liability, and reputational damage that no index tuning or query optimization can fix. This chapter covers what compliance and governance actually mean in the context of SQL Server, how major regulatory frameworks translate into database-level controls, and how to implement auditing, access control, data masking, and retention policies that satisfy both security teams and external auditors. By the end, you will have a working mental model for building a compliant database environment rather than scrambling to patch gaps when an audit arrives.

---

What Compliance Means for a Database Administrator

The word "compliance" covers a wide range of obligations depending on your industry and geography. HIPAA governs the handling of protected health information in the United States. PCI DSS applies to any system that stores, processes, or transmits payment card data. GDPR extends data protection obligations to any organization that handles the personal data of EU residents, regardless of where that organization is headquartered. SOC 2 is an auditing framework used primarily by technology companies to demonstrate controls around security, availability, and confidentiality. Each framework has its own vocabulary and emphasis, but from a DBA's perspective they share a common core set of requirements: know who has access to data, record what was done with it, protect sensitive values at rest and in transit, and be able to prove all of this to an auditor.

The DBA's role in compliance is not to become a lawyer or a compliance officer. It is to translate the requirements handed down from those roles into concrete database controls. When a compliance officer says "we need to know every time someone reads a Social Security Number," that maps to row-level auditing on a specific column. When legal says "GDPR requires us to delete all data about a user upon request," that maps to a data lifecycle management process with verifiable deletion logs.

Understanding the mapping between regulatory language and database features is what separates a DBA who is a genuine asset in a compliance program from one who waits to be told exactly what to click. The frameworks themselves do not mandate specific technology implementations. PCI DSS does not say "use column-level encryption in SQL Server." It says cardholder data must be protected, and it is your job to determine that column-level encryption satisfies that requirement in your environment.

One concept that runs through every compliance framework is the principle of least privilege. Users and applications should have access to exactly what they need to do their jobs, and nothing more. This principle has direct database implications: avoiding shared service accounts, granting SELECT instead of broad data access roles, and separating the DBA role from application roles. Compliance auditors will ask to see evidence that this principle is enforced, not just declared.

Auditing: Recording What Happens to Your Data

An audit trail is a chronological record of who accessed or modified data, when, and from where. In a compliance context, the absence of an audit trail is itself a finding. Auditors need to see evidence that you can detect unauthorized access, and detecting it requires having a record of all access.

SQL Server Audit is the native, comprehensive audit facility: server audits, server audit specifications, and database audit specifications capture logins, permission changes, and DDL/DML at whatever granularity compliance requires. For compliance purposes, object-level auditing is usually what you want, because session-level logging tends to produce enormous volumes of noise.

-- SQL Server has native auditing via SQL Server Audit
-- Create a server audit that writes to a file
CREATE SERVER AUDIT PatientDataAudit
TO FILE (
    FILEPATH = 'C:\SQLAudit\',
    MAXSIZE = 100 MB,
    MAX_ROLLOVER_FILES = 10,
    RESERVE_DISK_SPACE = OFF
)
WITH (
    QUEUE_DELAY = 1000,
    ON_FAILURE = CONTINUE
);

-- Enable the server audit
ALTER SERVER AUDIT PatientDataAudit WITH (STATE = ON);

-- Create a database audit specification targeting specific tables
USE HealthcareDB;
GO
CREATE DATABASE AUDIT SPECIFICATION AuditSensitiveAccess
FOR SERVER AUDIT PatientDataAudit
ADD (SELECT, INSERT, UPDATE, DELETE
     ON dbo.Patients BY public),
ADD (SELECT ON dbo.SSNData BY public)
WITH (STATE = ON);

With SQL Server Audit, you can also write to the Windows Security Event Log or the Application Event Log, which is useful when your organization aggregates logs into a SIEM like Splunk or Microsoft Sentinel. Writing audit data to files on the database server itself is convenient, but it creates a risk: a compromised database administrator could potentially alter or delete those files. For high-assurance environments, audit data should flow to a system that the DBA does not have write access to.

SQL Server also provides the sys.fn_get_audit_file function for querying audit logs programmatically, which lets you build dashboards or feed audit events into monitoring systems without exporting raw log files.

-- Query audit log files to find all SELECT operations on Patients
SELECT
    event_time,
    server_principal_name,
    database_name,
    object_name,
    statement,
    succeeded,
    client_ip
FROM sys.fn_get_audit_file(
    'C:\SQLAudit\PatientDataAudit*.sqlaudit',
    DEFAULT,
    DEFAULT
)
WHERE object_name = 'Patients'
  AND action_id = 'SL'  -- SL = SELECT
ORDER BY event_time DESC;

Beyond native auditing, SQL Server supports trigger-based audit tables — a traditional approach where INSERT, UPDATE, and DELETE operations on a table fire a trigger that writes to an audit log table. Triggers are flexible and require no additional tooling, but they have real costs: every write operation incurs the overhead of the trigger execution, and if the audit table is in the same database, a transaction that rolls back will also roll back the audit entry, which means you can lose the record of an attempted change. The robust answer is SQL Server Audit's file target, which is written outside the transaction and cannot be rolled back with it.

For GDPR specifically, auditing needs to cover not just who modified data but also who read it, because access to personal data without a legitimate purpose is itself a potential violation. That means READ auditing, not just write auditing, which increases log volume substantially. When implementing read auditing for GDPR, be selective: focus on tables that actually contain personal data, log the user and timestamp, and ensure the audit logs themselves are protected from unauthorized access.

Access Control and Role-Based Security

Access control is the practical expression of the least privilege principle. Every user account, service account, and application connection that touches your database should have exactly the permissions needed and nothing more. This is not just good security hygiene; it is a documented requirement in PCI DSS (Requirement 7), HIPAA (§164.312(a)(1)), and GDPR (Article 25, data protection by design).

SQL Server's permission model is built around server roles, database roles, and securables. Logins authenticate at the server level, users map them into databases, and roles collect permissions by job function. This makes it straightforward to build a layered permission model where you define roles by job function and assign those roles to users.

-- Create database roles by job function
USE HealthcareDB;
GO

CREATE ROLE AppReadOnly;
CREATE ROLE AppReadWrite;
CREATE ROLE ReportingUsers;
CREATE ROLE PIIAccess;

-- Assign permissions to roles
GRANT SELECT ON SCHEMA::dbo TO AppReadOnly;
GRANT SELECT, INSERT, UPDATE ON SCHEMA::dbo TO AppReadWrite;
GRANT SELECT ON SCHEMA::reporting TO ReportingUsers;

-- Create logins and users, then assign roles
CREATE LOGIN app_service WITH PASSWORD = 'StrongPassword123!';
CREATE USER app_service FOR LOGIN app_service;
ALTER ROLE AppReadWrite ADD MEMBER app_service;

CREATE LOGIN analyst_jane WITH PASSWORD = 'StrongPassword456!';
CREATE USER analyst_jane FOR LOGIN analyst_jane;
ALTER ROLE ReportingUsers ADD MEMBER analyst_jane;

-- Deny direct table access to force role-based access
DENY SELECT ON dbo.SSNData TO AppReadOnly;
GRANT SELECT ON dbo.SSNData TO PIIAccess;

One common compliance failure is the accumulation of permissions over time. An analyst who needed temporary access to a production table six months ago still has that access because no one revoked it. This is called privilege creep, and it is one of the most common findings in access control audits. The DBA's job is not just to grant access correctly but to have a process for reviewing and revoking it.

A quarterly access review process should query the database for all users and their effective permissions and compare that list to an authoritative source like an HR system or an access request ticketing system. Any account in the database that is not in the authoritative source should be flagged for review.

-- Query all database users and their role memberships
SELECT
    dp.name AS username,
    dp.type_desc AS principal_type,
    dp.create_date,
    dp.modify_date,
    dp.default_schema_name,
    STRING_AGG(rp.name, ', ') WITHIN GROUP (ORDER BY rp.name) AS role_memberships
FROM sys.database_principals dp
LEFT JOIN sys.database_role_members drm ON dp.principal_id = drm.member_principal_id
LEFT JOIN sys.database_principals rp ON drm.role_principal_id = rp.principal_id
WHERE dp.type IN ('S', 'U', 'G')  -- SQL users, Windows users, Windows groups
  AND dp.name NOT IN ('dbo', 'guest', 'INFORMATION_SCHEMA', 'sys')
GROUP BY dp.name, dp.type_desc, dp.create_date, dp.modify_date, dp.default_schema_name
ORDER BY dp.name;

Service accounts deserve special attention. Application service accounts often end up with broader permissions than they need because it was easier during development to grant db_owner than to figure out the exact minimum permissions required. In a production compliance environment, this is unacceptable. Every service account should have its permissions documented, and those permissions should be the minimum necessary. If an application only needs to read from two tables and write to one, it should have exactly SELECT on those two tables and INSERT/UPDATE on the third, and nothing else.

Protecting Sensitive Data: Encryption, Masking, and Tokenization

Access control determines who can see data. Encryption and masking determine what they see when they do. These are complementary controls. A user with SELECT permission on a table containing credit card numbers should still see only masked values unless they have a specific additional authorization.

Encryption at rest protects data if physical media is stolen or a backup file is accessed without authorization. SQL Server supports transparent data encryption (TDE) at the storage level natively, in Standard and Enterprise editions as well as Azure SQL Database. TDE encrypts data and log files with a database encryption key protected by a certificate in master — backups are encrypted too, which closes the backup-file exposure that auditors always ask about.

Column-level encryption protects specific sensitive values even from database users who can access the table. In SQL Server, Always Encrypted shifts encryption key management to the client application so that even the DBA cannot read plaintext values. For in-database column encryption without application changes, cell-level encryption with ENCRYPTBYKEY and symmetric keys protects specific values from users who can read the table.

-- SQL Server Always Encrypted (column master key stored outside SQL Server)
-- First, create the column master key and column encryption key in SSMS or via PowerShell
-- Then define the table with encrypted columns

CREATE TABLE dbo.PatientSSN (
    PatientID    UNIQUEIDENTIFIER DEFAULT NEWID() PRIMARY KEY,
    PatientName  NVARCHAR(200) NOT NULL,
    SSN          NVARCHAR(11)
        ENCRYPTED WITH (
            ENCRYPTION_TYPE = DETERMINISTIC,
            ALGORITHM = 'AEAD_AES_256_CBC_HMAC_SHA_256',
            COLUMN_ENCRYPTION_KEY = SSNEncryptionKey
        ) NOT NULL
);
-- With Always Encrypted, the SQL Server engine never sees plaintext SSN values
-- Encryption and decryption happen in the client driver
-- DBAs with full SQL Server access still cannot read SSN values

Data masking is a different layer: it presents substitute values to unauthorized users while showing real values to authorized ones. SQL Server has built-in Dynamic Data Masking (DDM), which is a policy-based feature that applies masking rules to columns. It is worth noting that DDM does not encrypt data — it only transforms the output seen by certain users. A user with sufficient permissions can bypass masking, so it should not be relied upon as the sole protection mechanism.

-- Add dynamic data masking to existing columns
ALTER TABLE dbo.Customers
ALTER COLUMN CreditCardNumber
    ADD MASKED WITH (FUNCTION = 'partial(0,"XXXX-XXXX-XXXX-",4)');

ALTER TABLE dbo.Customers
ALTER COLUMN EmailAddress
    ADD MASKED WITH (FUNCTION = 'email()');

ALTER TABLE dbo.Customers
ALTER COLUMN PhoneNumber
    ADD MASKED WITH (FUNCTION = 'default()');

-- Grant UNMASK permission only to privileged roles
GRANT UNMASK ON dbo.Customers TO PIIAccess;

-- Verify masking is working for a low-privilege user
EXECUTE AS USER = 'analyst_jane';
SELECT CreditCardNumber, EmailAddress, PhoneNumber FROM dbo.Customers;
REVERT;

Dynamic Data Masking (DDM) is built into SQL Server: define masking functions on columns (default, email, random, custom string) and unprivileged users see masked values while privileged users see the real data. No application changes are needed — masking happens at query time based on the UNMASK permission.

Tokenization is a technique commonly used for PCI DSS compliance where the actual sensitive value (like a PAN — primary account number) is stored in a separate, highly secured token vault and replaced in the application database with a randomly generated token that has no mathematical relationship to the original value. From a database architecture perspective, this means your primary application database never holds actual cardholder data. The token is meaningless to an attacker who compromises the application database. Implementing tokenization typically involves an external tokenization service or vault (like HashiCorp Vault with a transit secrets engine), and the DBA's role is to ensure the application database stores only tokens and that the token vault's database is treated as a separate, higher-security tier.

Data Retention, Deletion, and the Right to Be Forgotten

Data governance is not only about protecting data while it exists — it is also about managing its lifecycle from creation through deletion. Regulatory frameworks have specific requirements on both ends: HIPAA requires that certain records be retained for at least six years; GDPR requires that personal data not be kept longer than necessary and that individuals have the right to request deletion. These requirements can pull in opposite directions, and the DBA's job is to implement a system that satisfies both.

Retention policies typically involve archiving data that is past its active use period but must still be kept for legal reasons, and permanently deleting data that has exceeded its required retention period. In SQL Server, partitioning by date with a sliding window makes retention management cleaner: a partition covering a specific month or year can be removed with TRUNCATE TABLE ... WITH (PARTITIONS (...)) or switched out and dropped, which is far faster and less disruptive than a DELETE statement against millions of rows.

-- SQL Server partition scheme for time-based retention
-- First create a partition function
CREATE PARTITION FUNCTION AuditLogPF (DATETIME2)
AS RANGE RIGHT FOR VALUES (
    '2023-01-01', '2023-07-01',
    '2024-01-01', '2024-07-01',
    '2025-01-01'
);

-- Create partition scheme mapping to filegroups
CREATE PARTITION SCHEME AuditLogPS
AS PARTITION AuditLogPF
ALL TO ([PRIMARY]);  -- In production, use separate filegroups

-- Create partitioned table
CREATE TABLE dbo.AuditLog (
    LogID      BIGINT IDENTITY(1,1),
    EventTime  DATETIME2 NOT NULL,
    UserName   NVARCHAR(128),
    Action     NVARCHAR(50),
    TableName  NVARCHAR(128),
    RowID      NVARCHAR(200)
) ON AuditLogPS(EventTime);

-- To remove old partitions, use SWITCH to move data to a staging table
-- then truncate the staging table (avoids logging overhead of DELETE)
CREATE TABLE dbo.AuditLog_Archive (
    LogID      BIGINT,
    EventTime  DATETIME2 NOT NULL,
    UserName   NVARCHAR(128),
    Action     NVARCHAR(50),
    TableName  NVARCHAR(128),
    RowID      NVARCHAR(200)
) ON [PRIMARY];

ALTER TABLE dbo.AuditLog
SWITCH PARTITION 1 TO dbo.AuditLog_Archive;

TRUNCATE TABLE dbo.AuditLog_Archive;

The right to be forgotten under GDPR is technically called the right to erasure. When a user submits a deletion request, you must be able to delete or irreversibly anonymize all personal data about that individual across all tables, and you must be able to prove you did it. The complication is that "all tables" includes backups and archive stores, not just the live database. This is an area where many organizations struggle: their backup strategy was designed purely for recovery, with no thought given to targeted deletion of specific records from backup media.

There are two common approaches. The first is to not store actual personal data in backups — instead store cryptographic tokens, and when a deletion request comes in, delete the encryption key associated with that user's data. The backed-up data remains, but it is permanently unreadable without the key. The second approach is to document that backup data is excluded from right-to-erasure scope based on a legal basis (usually a "legitimate interest" or "legal obligation" basis), combined with a defined backup retention window so that the data will be purged automatically when backups age out. Either approach requires deliberate architectural decisions made in advance, not after a deletion request arrives.

A practical deletion process for GDPR starts with a subject access request catalog — a mapping of every table and column that contains personal data, indexed by how to find records for a specific individual. Without this catalog, responding to a deletion request becomes an ad-hoc investigation into your own schema. Building this catalog during schema design rather than after the fact is significantly easier.

Governance Infrastructure: Policies, Change Control, and Evidence

Technical controls alone do not constitute a compliant environment. Auditors reviewing a HIPAA or PCI DSS program want to see documented policies, change management processes, evidence of periodic reviews, and incident response procedures. The DBA's role extends into providing the evidence and supporting the processes that make governance real.

Change control for database objects is an area where development practices and compliance requirements overlap directly. Every change to a production database — schema changes, stored procedure modifications, permission grants, configuration changes — should go through a documented process with an approver, a tested rollback plan, and a record of who made the change and when. This is both good operational practice and a compliance requirement (PCI DSS Requirement 6, for example, requires change management for all system components).

Version-controlled database migrations using tools like Flyway, Liquibase, or for SQL Server specifically, Redgate SQL Change Automation, provide the documented change history that auditors want to see. Each migration file is timestamped, authored, and committed to source control. The execution history is tracked in a metadata table in the database itself. When an auditor asks "who changed the schema of the Patients table on March 14th and was that change approved," you can point to a commit in version control with the author's identity, the pull request or code review that approved it, and the migration execution record in the database.

Flyway migration tracking table (SQL Server):

-- Flyway creates this table automatically; you can query it for audit evidence
SELECT
    installed_rank,
    version,
    description,
    type,
    script,
    checksum,
    installed_by,
    installed_on,
    execution_time,
    success
FROM flyway_schema_history
ORDER BY installed_rank DESC;

SQL Server (Liquibase tracking table):

-- Liquibase creates DATABASECHANGELOG automatically
SELECT
    ID,
    AUTHOR,
    FILENAME,
    DATEEXECUTED,
    ORDEREXECUTED,
    EXECTYPE,
    MD5SUM,
    DESCRIPTION,
    DEPLOYMENT_ID
FROM dbo.DATABASECHANGELOG
ORDER BY DATEEXECUTED DESC;

Configuration management is a related concern. Your database server configuration — SQL Server's sp_configure settings, TLS certificate configurations, login and authentication settings — should be version-controlled and reviewed periodically. A SQL Server configuration change that enables xp_cmdshell or weakens login auditing is exactly the kind of drift that auditors look for and that can go unnoticed in an environment with poor change control.

Documenting your security baseline and then detecting drift from it is the essence of configuration compliance. Tools like Chef InSpec, OpenSCAP, or the CIS Benchmark hardening scripts for SQL Server provide codified security baselines that you can run against your servers to generate compliance evidence automatically.

SQL Server — checking key configuration values against a security baseline:

-- Query current configuration to compare against documented baseline
SELECT name,
       value_in_use,
       is_advanced
FROM sys.configurations
WHERE name IN (
    'xp_cmdshell',
    'Ole Automation Procedures',
    'clr enabled',
    'cross db ownership chaining',
    'remote access',
    'Database Mail XPs',
    'backup compression default'
)
ORDER BY name;

SQL Server — checking key configuration values:

-- Review security-relevant configuration settings
SELECT
    name,
    value,
    value_in_use,
    description,
    is_advanced
FROM sys.configurations
WHERE name IN (
    'cross db ownership chaining',
    'xp_cmdshell',
    'remote access',
    'Ole Automation Procedures',
    'clr enabled',
    'clr strict security',
    'contained database authentication'
)
ORDER BY name;

-- Also check that SQL Server is using TLS for connections
SELECT
    net_transport,
    encrypt_option,
    auth_scheme,
    client_net_address,
    local_net_address
FROM sys.dm_exec_connections
WHERE session_id = @@SPID;

Separation of duties is a governance principle that appears explicitly in SOC 2 and PCI DSS. It requires that no single individual have end-to-end control over a sensitive process. In a database context, this typically means that the DBA who can deploy schema changes should not be the same person who approves them, and that the person who manages encryption keys should not also have unrestricted access to the data those keys protect. Implementing separation of duties in small teams is genuinely difficult — you may have only one or two DBAs — but the principle can still be approximated through documented peer review requirements, two-person authorization for certain administrative actions, and audit logging of privileged operations.

SQL Server provides a useful mechanism for this through database auditing combined with server-level audit specifications that capture DDL changes:

-- Audit all DDL changes made by DBAs at the server level
CREATE SERVER AUDIT DDLChangeAudit
TO FILE (
    FILEPATH = 'C:\SQLAudit\DDL\',
    MAXSIZE = 200 MB,
    MAX_ROLLOVER_FILES = 20
)
WITH (QUEUE_DELAY = 1000, ON_FAILURE = CONTINUE);

ALTER SERVER AUDIT DDLChangeAudit WITH (STATE = ON);

-- Create server audit specification for schema changes
CREATE SERVER AUDIT SPECIFICATION DDLAuditSpec
FOR SERVER AUDIT DDLChangeAudit
ADD (SCHEMA_OBJECT_CHANGE_GROUP),
ADD (DATABASE_OBJECT_CHANGE_GROUP),
ADD (SERVER_ROLE_MEMBER_CHANGE_GROUP),
ADD (DATABASE_ROLE_MEMBER_CHANGE_GROUP),
ADD (LOGIN_CHANGE_PASSWORD_GROUP),
ADD (AUDIT_CHANGE_GROUP)
WITH (STATE = ON);

Capturing AUDIT_CHANGE_GROUP is particularly important — it records changes to the audit configuration itself, which means you have evidence if someone attempts to disable or modify auditing to cover their tracks.

Evidence collection should be treated as an ongoing operational task rather than a pre-audit scramble. Establish a governance evidence repository — this can be as simple as a structured shared folder or as formal as a GRC (Governance, Risk, and Compliance) platform — where you store quarterly access reviews, configuration baseline reports, audit log samples, and change control records. When an auditor arrives, you should be able to produce evidence for any control question without running an emergency investigation.

Row-Level Security for Multi-Tenant and Sensitive Environments

Row-level security (RLS) is a database feature that enforces data access policies at the row level, transparently filtering which rows a query can see based on the identity of the user executing it. For compliance purposes, RLS is relevant in two scenarios: multi-tenant applications where each tenant should only see their own data, and environments where different classes of users should see different subsets of rows (for example, a healthcare system where a nurse can see only patients in their assigned ward).

SQL Server provides Row-Level Security, implemented through inline table-valued functions used as security predicates bound to tables by a security policy.

-- Create a schema to hold the security predicate function
CREATE SCHEMA Security;
GO

-- Create the filter predicate function
CREATE FUNCTION Security.WardAccessPredicate(@WardID INT)
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN
    SELECT 1 AS AccessResult
    WHERE
        IS_MEMBER('ClinicalAdmin') = 1  -- admins see everything
        OR
        EXISTS (
            SELECT 1
            FROM dbo.StaffWardAssignment swa
            INNER JOIN sys.database_principals dp
                ON dp.name = USER_NAME()
            WHERE swa.WardID = @WardID
              AND swa.StaffUserName = USER_NAME()
        );
GO

-- Apply the security policy
CREATE SECURITY POLICY WardIsolationPolicy
ADD FILTER PREDICATE Security.WardAccessPredicate(WardID) ON dbo.Patients,
ADD BLOCK PREDICATE Security.WardAccessPredicate(WardID) ON dbo.Patients AFTER INSERT
WITH (STATE = ON);

The BLOCK predicate in SQL Server RLS prevents users from inserting rows that they would not be able to see after insertion, which closes a subtle data integrity gap. For write restrictions in addition to read filtering, add a block predicate to the same security policy.

RLS is powerful, but it has performance implications that must be tested in your specific environment. Every query against an RLS-protected table carries the overhead of evaluating the security predicate for each row candidate. If the predicate involves a subquery or a join to another table, that join runs for every query. In high-throughput environments, poorly designed RLS predicates can become significant bottlenecks. Always examine the query plan of queries against RLS-protected tables to verify that the predicate is being pushed down efficiently and that appropriate indexes support it.

Compliance in Cloud and Managed Database Environments

Many organizations now run SQL Server in cloud-managed environments — Amazon RDS for SQL Server, Google Cloud SQL for SQL Server, Azure SQL Database, and Azure SQL Managed Instance. Managed environments simplify infrastructure but shift which compliance controls are your responsibility and which belong to the cloud provider.

In a managed database service, the cloud provider typically handles physical security, disk encryption at rest (usually enabled by default), patch management for the database engine, and infrastructure-level logging. This means you inherit a set of controls for free, which you can reference in your compliance documentation using the provider's compliance attestations (AWS issues SOC 2 Type II reports, Azure publishes its own compliance documentation, and so on).

What remains squarely your responsibility in a managed database environment is everything above the engine level: user access control, audit logging configuration, application-level encryption, data classification, retention policies, and RLS policies. You cannot assume the cloud provider's SOC 2 compliance covers your application's data handling.

For auditing in cloud environments, both AWS and Azure provide native logging services that integrate with their managed database offerings. For SQL Server, Azure SQL Database has its own built-in auditing feature that writes to Azure Blob Storage or Azure Log Analytics, and this is generally preferable to the file-based SQL Server Audit approach in on-premises environments. RDS for SQL Server can publish audit and error logs to CloudWatch Logs for the same centralized-analysis pattern.

Azure SQL Database auditing (T-SQL configuration):

-- Azure SQL Database audit is primarily configured through the Azure portal or PowerShell
-- but you can verify audit state and query audit logs via T-SQL

-- Check if auditing is enabled at the database level
SELECT
    server_specification_id,
    audit_action_name,
    class_desc,
    is_group,
    audit_action_id
FROM sys.database_audit_specifications das
JOIN sys.database_audit_specification_details dasd
    ON das.database_specification_id = dasd.database_specification_id;

-- Query Azure SQL audit logs stored in a storage account
-- (After configuring the external data source for the storage account)
SELECT
    event_time,
    session_server_principal_name,
    database_name,
    object_name,
    statement,
    succeeded,
    client_ip
FROM sys.fn_get_audit_file(
    'https://mystorageaccount.blob.core.windows.net/sqldbauditlogs/myserver/mydb/SqlDbAuditing_*.xel',
    DEFAULT,
    DEFAULT
)
WHERE succeeded = 1
ORDER BY event_time DESC;

Network controls in cloud environments replace some of the physical network controls that on-premises environments rely on. Private endpoints and VPC/VNet peering ensure that database traffic never traverses the public internet. Security groups and firewall rules restrict which application tiers can reach the database. These are the cloud-environment equivalents of network segmentation requirements found in PCI DSS and HIPAA, and they need to be documented and verified just as on-premises network controls do.

Building a Compliance Posture That Survives Audits

The practical goal of everything in this chapter is to arrive at an audit in a position of confidence rather than one of reactive scrambling. The organizations that perform well in compliance audits are not the ones that do the most work in the month before the audit — they are the ones that have made compliance controls a routine part of how the database environment operates year-round.

Concretely, this means running your access review queries on a schedule and filing the results. It means treating your audit log pipeline as a production-critical system, not an optional extra, so that a log shipping failure gets the same attention as a replication lag alert. It means including security baseline checks in your change management process so that configuration drift is caught before it becomes a finding. And it means keeping your data classification catalog current as the schema evolves, so that a new column containing phone numbers does not go unprotected because no one thought to flag it.

The DBA who understands these controls deeply — who can explain to an auditor exactly why a particular role has a particular permission, point to the audit record that proves a specific access event was captured, and demonstrate that an RLS policy correctly isolates tenant data — is the DBA who makes compliance audits into confirmations of good work rather than exposures of hidden risk.

Key Takeaways

  • → Compliance frameworks like HIPAA, PCI DSS, GDPR, and SOC 2 do not mandate specific database technologies — they mandate outcomes such as access control, audit trails, and data protection, and the DBA's job is to map those outcomes to concrete database features and configurations.
  • → Auditing should be implemented through purpose-built tools (SQL Server Audit) rather than relying solely on trigger-based approaches, because dedicated audit facilities are more tamper-resistant and produce structured, queryable output; audit log data should flow to a destination the DBA cannot modify unilaterally.
  • → The principle of least privilege requires not just correctly granting permissions at provisioning time, but running regular access reviews to detect and remediate privilege creep — automated queries against `sys.server_principals` and `sys.database_principals` make this process repeatable and auditable.
  • → Sensitive data protection requires layered controls: encryption at rest (TDE or filesystem encryption) prevents exposure from stolen media, column-level encryption (cell-level encryption, Always Encrypted) protects values from privileged database users, and data masking (Dynamic Data Masking) limits what authorized users see during normal operations.
  • → Governance infrastructure — version-controlled schema migrations, documented configuration baselines, change control processes, and a maintained evidence repository — transforms compliance from a reactive audit exercise into a continuous operational discipline, and is ultimately what separates organizations that pass audits confidently from those that are perpetually caught unprepared.
