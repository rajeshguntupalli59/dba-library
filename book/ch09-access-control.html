Chapter 9: Access Control

Access control is the mechanism by which a database system determines who can connect, what objects they can see, and what operations they are permitted to perform. It sounds simple in principle — give users what they need, deny them what they don't — but in practice it becomes one of the most operationally complex responsibilities a DBA carries. Misconfigured permissions are among the most common causes of both accidental data loss and deliberate data breaches. This chapter walks through the complete access control model in SQL Server: how authentication and authorization work, how roles and privileges are structured, how to lock down a production environment, and how to audit who has access to what. By the end, you will have the mental model and the SQL vocabulary to design and enforce a security posture that holds up under real scrutiny.

---

Authentication vs. Authorization: Two Different Problems

These two concepts are often lumped together under the word "security," but they are distinct and handled differently in both systems.

Authentication answers the question: *Is this person who they claim to be?* Before a user can interact with a database at all, the system needs to verify their identity. In SQL Server, authentication is controlled by the server's authentication mode — Windows Authentication mode or Mixed Mode — set at install and changeable under Server Properties → Security (restart required). Windows/AD logins delegate to the domain (Kerberos preferred; confirm with the auth_scheme column in sys.dm_exec_connections), while SQL logins are managed inside the instance with password policy enforcement via CHECK_POLICY and CHECK_EXPIRATION.

In SQL Server, authentication happens at two layers. The first is the login, which is a server-level principal that grants access to the SQL Server instance. Logins can be SQL Server logins (username and password stored in the instance) or Windows logins (authenticated by Active Directory). The second layer is the user, which is a database-level principal mapped to a login. A login can exist without a corresponding user in a database, and in that case the login can connect to the instance but cannot access that database.

Authorization answers the question: *What is this authenticated identity allowed to do?* This is where GRANT, REVOKE, DENY, roles, and schemas come into play — the entire subject of permissions management. SQL Server separates authentication from authorization with a strict two-tier design: logins (server-level identities) are mapped to users (database-level identities), and permissions flow through role membership — which is where least privilege is actually implemented.

Understanding this distinction prevents a class of common mistakes. A DBA who revokes all privileges from a user but leaves their login intact has not actually removed access — the user can still connect. Conversely, dropping a login while its database users still exist leaves orphaned users behind — always drop the database users first, then the login.

The Login/User Model in SQL Server

SQL Server uses the role as the primary unit of permission — server roles at the instance level, database roles at the database level — with logins and users as the identity endpoints that get placed into those roles.

SQL Server separates identity from permission deliberately. A login proves who you are to the instance; a user is that login's presence inside a database; roles — server-level and database-level, fixed and user-defined — carry the permissions. You create the login, create the user mapped to it, and add the user to roles. Custom database roles with explicit grants are the right approach for anything beyond development — the fixed roles (db_datareader, db_datawriter, db_owner) are convenient but coarse.

-- Create a login at the server level
CREATE LOGIN alice WITH PASSWORD = 'SecurePassword123!';

-- Create a corresponding user in a specific database
USE SalesDB;
CREATE USER alice FOR LOGIN alice;

-- Create a database role (equivalent to a group)
CREATE ROLE reporting_team;

-- Add the user to the role
ALTER ROLE reporting_team ADD MEMBER alice;

-- Verify role membership
SELECT dp.name AS role,
       mp.name AS member
FROM sys.database_role_members drm
JOIN sys.database_principals dp ON dp.principal_id = drm.role_principal_id
JOIN sys.database_principals mp ON mp.principal_id = drm.member_principal_id
WHERE dp.name = 'reporting_team';

The fixed server roles control powerful instance-level capabilities — sysadmin above all. Treat sysadmin membership like production keys: only for accounts that genuinely require it, ideally service accounts with no interactive use rather than personal accounts. Members of sysadmin bypass every permission check in the system, including RLS predicates and DENY.

Membership in the sysadmin server role grants complete control over the instance. Members of sysadmin can do anything — there is no permission check they don't pass. At the database level, the db_owner fixed database role grants complete control over a single database. These fixed roles — db_datareader, db_datawriter, db_owner, and others — are convenient but coarse. For anything beyond a development environment, custom roles with explicit grants are the right approach.

One SQL Server behavior that surprises many DBAs is the guest user. Every SQL Server database has an implicit guest account. If guest is enabled (it is by default in some older configurations), any authenticated login that doesn't have an explicit user mapping in a database can still connect to that database through the guest account and receive whatever permissions guest holds. Unless you have a documented reason to use it, guest should be disabled in every user database by revoking its CONNECT permission.

-- Disable the guest user in a database (recommended in production)
USE SalesDB;
REVOKE CONNECT FROM guest;

-- Verify guest connection permission
SELECT name, type_desc, authentication_type_desc,
       HAS_PERMS_BY_NAME('SalesDB', 'DATABASE', 'CONNECT') AS can_connect
FROM sys.database_principals
WHERE name = 'guest';

Granting, Revoking, and the Principle of Least Privilege

The principle of least privilege states that every identity should have exactly the permissions needed to do its job — no more. This sounds obvious, but it requires discipline to maintain in production environments that evolve over time. Schemas change, new tables get added, and permissions granted in urgency during an incident often never get cleaned up.

In SQL Server, the privilege system operates at several levels: server, database, schema, table, column, and more. The three commands you use most are GRANT, REVOKE, and DENY. Permissions can be granted at the schema level — GRANT SELECT ON SCHEMA::sales TO reporting_team — which automatically covers future tables created in that schema. Schema-level grants are the cleanest way to handle a growing schema without per-table grant maintenance.

-- Grant read-only access to a schema
GRANT SELECT ON SCHEMA::sales TO reporting_team;

-- Grant write access on specific tables only
GRANT INSERT, UPDATE, DELETE ON sales.orders TO app_writer;

-- Deny access to a sensitive table (DENY overrides GRANT)
DENY SELECT ON sales.customer_pii TO app_writer;

-- Revoke a previously granted permission
REVOKE SELECT ON sales.orders FROM reporting_team;

One of the sharpest tools in SQL Server's model is the DENY command. DENY explicitly prohibits an action and takes precedence over any GRANT — even grants inherited through role membership. If alice is a member of reporting_team which has SELECT on sales.orders, but alice has been individually DENY-ed SELECT on that table, she cannot read it. Use DENY sparingly — because it overrides grants even through role inheritance, it makes effective-permission auditing harder to reason about. Prefer designing roles so that DENY is rarely needed.

This has a practical consequence. In a multi-tenant application where different users need access to different row subsets of the same table, row-level security (covered in the next section) is usually the right tool. You might also use DENY at the table level and then GRANT through carefully scoped views or procedures to achieve granular control.

Schema ownership matters in both systems but is particularly important in SQL Server. In SQL Server, a schema is both a namespace and a security boundary. The schema owner has implicit control over all objects within it. When an application user is also the schema owner, it often ends up with more privileges than intended — a consequence of convenience-driven setup. Best practice is to use a service account as the schema owner and grant explicit permissions to application and reporting roles separately.

In SQL Server, the public role and the guest user deserve special attention. Every database has an implicit guest account — if it's enabled, any authenticated login without an explicit user mapping can connect through it. And the public role holds default grants that are broader than most organizations realize. At database setup time, audit both:

-- Lock down defaults (run in each user database)
REVOKE CONNECT FROM guest;
-- Audit what the public role can actually do:
SELECT p.permission_name, p.state_desc, o.name AS object_name
FROM sys.database_permissions AS p
LEFT JOIN sys.objects AS o ON p.major_id = o.object_id
WHERE p.grantee_principal_id = DATABASE_PRINCIPAL_ID('public');

Verify these settings on every inherited database, not just new builds — defaults drift, and the databases you didn't set up are the ones most likely to carry surprises.

Row-Level Security and Column-Level Permissions

Standard table-level permissions control whether a user can touch a table at all. But in many real applications, the question isn't whether a user can read *orders* — it's whether a user can read *their own* orders, or the orders assigned to their region. That's where row-level security (RLS) and column-level permissions come in.

Row-Level Security is implemented through security policies. You create an inline table-valued predicate function and bind it to the table with CREATE SECURITY POLICY; the engine then applies the filter transparently — the application doesn't need to add any WHERE clause, and the user can't remove the filter.

A subtlety worth knowing: the filter predicate controls which rows are visible for reads and which rows can be modified. Block predicates validate writes — without them, a user could insert rows they'd never be able to read back, or update rows out of their own visibility. Most production policies should define both filter and block predicates.

Superusers and roles with BYPASSRLS bypass all row-level security policies. If you're using a superuser as your application database connection (a common but unfortunate pattern), RLS provides no protection at all.

SQL Server Row-Level Security is implemented through inline table-valued functions and security policies that wrap them. The mechanism is more verbose but conceptually similar.

-- Create the filter function
CREATE FUNCTION sales.fn_order_security_predicate
    (@assigned_rep NVARCHAR(128))
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN
    SELECT 1 AS result
    WHERE @assigned_rep = USER_NAME()
       OR IS_MEMBER('sales_managers') = 1;
GO

-- Create the security policy using the function
CREATE SECURITY POLICY sales.OrderAccessPolicy
    ADD FILTER PREDICATE sales.fn_order_security_predicate(assigned_rep)
    ON sales.orders
    WITH (STATE = ON);
GO

For column-level permissions, both systems let you restrict access to individual columns rather than entire tables. This is useful for sensitive fields like Social Security numbers, salaries, or PII that only certain roles should see.

-- Grant column-level SELECT on non-sensitive columns
GRANT SELECT ON sales.orders (order_id, order_date, status) TO reporting_team;

-- Deny access to sensitive column specifically
DENY SELECT ON sales.orders (ssn, salary) TO reporting_team;

-- Verify column permissions
SELECT class_desc, major_id, minor_id, grantee_principal_id,
       permission_name, state_desc
FROM sys.database_permissions
WHERE class = 1 -- object-level
  AND permission_name = 'SELECT';

An important operational note: column-level grants interact with SELECT * in sometimes unintuitive ways. In SQL Server, if a user has SELECT on only specific columns and executes SELECT *, the query fails entirely rather than returning only the permitted columns. Applications should always specify columns explicitly — this is good practice regardless of security constraints — but it becomes a hard requirement when column-level permissions are in play.

Auditing Access: Who Has What, and What Happened

Permissions drift over time. A developer gets temporary access during an incident, the incident resolves, and the access never gets revoked. A role accumulates grants from three different DBAs over two years. An application user turns out to have db_owner because someone didn't want to figure out the exact rights needed. Auditing is the only systematic way to catch this drift before it becomes a problem.

Querying the current permission state is the first step. Both systems expose this through catalog views.

-- Show all effective permissions for all users in the current database
SELECT dp.name       AS principal,
       dp.type_desc  AS principal_type,
       o.name        AS object_name,
       o.type_desc   AS object_type,
       p.permission_name,
       p.state_desc
FROM sys.database_permissions p
JOIN sys.database_principals dp ON dp.principal_id = p.grantee_principal_id
LEFT JOIN sys.objects o         ON o.object_id = p.major_id
WHERE dp.type NOT IN ('R') -- exclude roles, show only users
ORDER BY dp.name, o.name;

Beyond static permission snapshots, you need event-level auditing — a record of who actually did what, and when.

SQL Server Audit integrates with the instance to produce structured audit logs at the server and database level. At the database level, a database audit specification defines which operations on which objects get logged. Audit output goes to files, the Security log, or the Application log — so your existing log shipping and SIEM integration infrastructure applies.

SQL Server has a native SQL Server Audit feature built into the engine. You create an audit object pointing to a destination (a file, the Windows Security log, or the Application log), then create a server audit specification or database audit specification that defines which events to capture. The built-in DATABASE_OBJECT_ACCESS_GROUP, SCHEMA_OBJECT_ACCESS_GROUP, and DATABASE_PRINCIPAL_IMPERSONATION_GROUP audit action groups cover most production needs.

Beyond formal audit tooling, both systems maintain system views that reveal useful security-related state. In SQL Server, sys.server_principals and sys.database_principals give you the current principal inventory. sys.login_token and sys.user_token show the effective permissions and group memberships of the current session — invaluable when debugging why a user can or cannot perform an operation. fn_my_permissions lets you test effective permissions from within the session, which is far faster than hunting through catalog joins.

Periodic access reviews should be a scheduled operational activity, not something done only when there's a problem. A practical pattern is to export the permission snapshot query above on a regular cadence and diff it against the previous period. Any change — a new grant, a role membership addition, a privilege on a newly created table — surfaces immediately. This is light infrastructure that catches a large class of security drift before it becomes a compliance issue.

One production scenario that illustrates why this matters: when a database is restored from a backup to a different server, the SIDs of SQL logins may not match the SIDs of users inside the database. The user exists in the database but has no corresponding server login — an "orphaned user." Running sp_change_users_login or ALTER USER ... WITH LOGIN resolves it, but it's easy to miss, and the result is a database where no one can connect using SQL authentication.

Ownership Chains, Impersonation, and the Edges of the Permission Model

Most access control discussions cover the straightforward path: user requests access, permission is checked, access is granted or denied. Production systems have edges — places where the normal rules don't apply in the way you'd expect.

Ownership chaining in SQL Server is one such edge. When a stored procedure and the tables it references are owned by the same principal, SQL Server does not re-check permissions on the underlying tables when the procedure executes. The permission check applies only to the procedure itself. This is by design — it allows you to grant EXECUTE on a procedure to a user who has no direct access to the underlying tables, which is a clean and useful security pattern. But it has a trap: if the procedure and one of the referenced tables are owned by *different* principals, the chain breaks and SQL Server checks permissions on that table against the calling user. In a schema where object ownership is inconsistent, a procedure that worked fine for years suddenly starts failing for certain users after an ownership change on a table it references.

Impersonation in SQL Server (EXECUTE AS) lets a principal temporarily assume the identity of another for the scope of a session or a module. This is useful for testing permissions, for delegation scenarios, and for creating security contexts within stored procedures. EXECUTE AS USER switches to a database user, EXECUTE AS LOGIN switches to a server login. Both require the caller to have IMPERSONATE permission on the target principal.

-- Temporarily execute as another user to test permissions
EXECUTE AS USER = 'alice';

SELECT HAS_PERMS_BY_NAME('sales.orders', 'OBJECT', 'SELECT') AS can_select;

-- Return to original context
REVERT;

-- Grant impersonate permission explicitly
GRANT IMPERSONATE ON USER::alice TO dba_support;

Stored procedures defined WITH EXECUTE AS OWNER deserve attention here. Such a procedure executes with the privileges of the specified principal — typically the schema owner — not the calling user. Combined with ownership chaining (same-owner procedure and tables need no explicit table grants), this is the controlled way to let non-privileged users perform specific operations on objects they otherwise cannot access. The risk is real: a procedure that takes unsanitized input and builds dynamic SQL is a privilege escalation vector. Any procedure using EXECUTE AS should be written with the same care as security-critical code: input validation, parameterized queries via sp_executesql, and a clear understanding of what the owner's privileges allow.

Cross-database access is another edge worth understanding. In SQL Server, linked servers and three-part names (OtherDB.dbo.tablename) allow cross-database queries, which creates cross-database permission dependencies that need to be tracked. The TRUSTWORTHY database property in SQL Server is particularly worth auditing: if enabled, it allows code in that database to access server-level resources using the database owner's server-level credentials. TRUSTWORTHY is off by default and should stay off in production unless there is a specific, documented need.

-- Audit databases with TRUSTWORTHY enabled (should be rare)
SELECT name,
       is_trustworthy_on,
       owner_sid,
       SUSER_SNAME(owner_sid) AS owner_name
FROM sys.databases
WHERE is_trustworthy_on = 1
  AND name NOT IN ('msdb'); -- msdb legitimately uses TRUSTWORTHY

-- Check for EXECUTE AS in stored procedures (review these carefully)
SELECT SCHEMA_NAME(o.schema_id) AS schema_name,
       o.name                   AS procedure_name,
       m.execute_as_principal_id,
       dp.name                  AS execute_as_principal
FROM sys.sql_modules m
JOIN sys.objects o ON o.object_id = m.object_id
LEFT JOIN sys.database_principals dp
    ON dp.principal_id = m.execute_as_principal_id
WHERE m.execute_as_principal_id IS NOT NULL
  AND o.type = 'P';

The theme across all of these edge cases is that the permission model has complexity that goes beyond simple grant/revoke. Ownership, impersonation, function security attributes, and cross-database trust are all mechanisms that can override the apparent permission state. Knowing they exist — and knowing where to look for them — is what separates a DBA who manages access control from one who merely administers it.

---

Key Takeaways

  • → **Authentication and authorization are separate concerns.** Authentication controls who can connect; authorization controls what they can do. Resolving a security issue often requires addressing both independently.
  • → **Design roles around job functions, not individuals.** Grant permissions to roles, add users to roles. This makes access reviews tractable and ensures that when people change jobs, permissions change with them rather than accumulating silently.
  • → **SQL Server's permission model is not purely additive.** DENY overrides grants even through role inheritance, which enables fine-grained restriction but adds a second mechanism a DBA must account for when reasoning about a principal's effective permissions — use it sparingly and document every one.
  • → **Row-level and column-level security enforce access at a finer grain than table permissions can.** SQL Server's security policies (built on inline table-valued functions) filter rows transparently at the engine level, but they don't protect against a `sysadmin`-level connection — those bypass the policy entirely, which is a strong argument against using highly-privileged accounts for routine application access.
  • → **Static permission snapshots are not enough; you need both audit logging and periodic review.** Native SQL Server Audit provides event-level trails of who did what, while a recurring diff of the current permission state against a prior snapshot catches drift — orphaned grants, stale role memberships, and privileges nobody remembers approving — before it becomes a compliance or security incident.
  • → **Ownership, impersonation, and cross-database trust settings can override the permission model you think is in effect.** Ownership chaining, `EXECUTE AS`, and the `TRUSTWORTHY` database property all create paths where effective privilege differs from what a straightforward `GRANT`/`REVOKE` audit would show — knowing where to look for them is part of managing access control seriously.
