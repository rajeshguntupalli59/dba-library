Chapter 28: Containerization

Running databases in containers was once considered a risky experiment — something you did for development environments and testing pipelines, not for anything you cared about. That perception has changed substantially. Today, containerized SQL Server instances run in production at companies of every size, managed by orchestration platforms like Kubernetes, backed by persistent storage, monitored with the same rigor as bare-metal systems, and capable of surviving node failures gracefully. This chapter covers the full arc: what containers are, why databases present unique challenges inside them, how to run SQL Server correctly in Docker and Kubernetes, how to handle storage and networking, and how to operate containerized databases in production without losing sleep.

---

Why Containers and Why Now

Containers are lightweight, isolated runtime environments that package an application together with everything it needs to run — libraries, configuration files, binaries — into a single portable image. Unlike virtual machines, containers share the host operating system kernel, which makes them fast to start and cheap on resources. Docker popularized the container format, and the Open Container Initiative (OCI) standardized it so that images built with Docker run equally well under containerd, Podman, or any OCI-compliant runtime.

For databases, the appeal is real. A containerized database image is reproducible. The same image you tested last Tuesday is the exact image running in production on Friday — same SQL Server build and CU, same shared libraries, same locale settings. Deployment becomes a configuration problem rather than an installation problem. When a new team member joins, they run docker compose up and have a fully functional database environment within seconds, not hours.

The deeper value emerges in orchestrated environments. Kubernetes can restart a failed database container automatically, schedule it onto healthy nodes, apply resource limits so a runaway query doesn't starve the host, and roll out configuration changes without manual intervention. For organizations running dozens or hundreds of database instances, the operational leverage is significant.

None of this comes free. Databases are stateful. Containers are designed to be ephemeral. Bridging that mismatch — making containers behave reliably for workloads that absolutely cannot lose data — is where most of the complexity lives, and where this chapter spends most of its time.

Running SQL Server in Docker

Docker is the natural starting point. Even if your production environment is Kubernetes, you will work with Docker images constantly — building them, inspecting them, testing configurations locally.

Microsoft maintains the SQL Server image under mcr.microsoft.com/mssql/server. The basic pattern is: pull an image, provide environment variables for initialization (notably ACCEPT_EULA and MSSQL_SA_PASSWORD), mount a volume for data persistence.

A minimal SQL Server container:

docker run -d \
  --name mssql-prod \
  -e ACCEPT_EULA=Y \
  -e MSSQL_SA_PASSWORD=StrongP@ssword1 \
  -e MSSQL_PID=Developer \
  -v mssqldata:/var/opt/mssql \
  -p 1433:1433 \
  mcr.microsoft.com/mssql/server:2022-latest

The -v flag mounts a named Docker volume. Without it, the database files live inside the container's writable layer, which disappears the moment the container is removed. Named volumes persist independently of container lifecycle — a distinction that cannot be overstated.

Once a container is running, you connect and manage it exactly as you would any other instance. The database doesn't know it's in a container.

-- Check SQL Server version and data directory inside container
SELECT @@VERSION;
SELECT physical_name
FROM sys.master_files
WHERE database_id = DB_ID('master');

Docker Compose becomes essential as soon as you add more than one service. A typical development stack includes a database, an application server, and perhaps a caching layer. Compose lets you define all of them in a single YAML file and manage them together.

The healthcheck entry is not cosmetic. Compose and Kubernetes both use health checks to know when a container is genuinely ready to accept connections, not just running as a process. For a database, there is a meaningful gap between "process started" and "accepting queries."

Persistent Storage: The Non-Negotiable Requirement

Storage is where containerized database deployments succeed or fail. Understanding the options and their trade-offs is not optional knowledge — it's the foundation every other decision rests on.

Docker volumes are the default recommendation for most scenarios. They are managed by Docker, stored outside the container filesystem, survive container removal, and can be backed up with standard tooling. When you declare mssqldata:/var/opt/mssql, Docker creates a volume at a path like /var/lib/docker/volumes/mssqldata/_data on the host and mounts it into the container.

Bind mounts map a specific host directory into the container. They give you direct visibility into the files from the host:

docker run -d \
  --name mssql-dev \
  -e ACCEPT_EULA=Y \
  -e MSSQL_SA_PASSWORD='' \
  -v /data/mssql:/var/opt/mssql \
  mcr.microsoft.com/mssql/server:2022-latest

Bind mounts are convenient for development and for situations where your storage team provisions specific mount points. In production Kubernetes, bind mounts give way to Persistent Volumes.

Kubernetes introduces PersistentVolume (PV) and PersistentVolumeClaim (PVC) as abstractions over physical storage. A PVC requests storage of a specific size and access mode, and Kubernetes satisfies it by binding a matching PV — which could be backed by AWS EBS, Azure Disk, GCP Persistent Disk, NFS, or a local SSD. The StatefulSet controller, which is the right workload type for databases, automatically creates and manages PVCs for each database pod.

The access mode matters enormously for databases. ReadWriteOnce (RWO) means only one node can mount the volume at a time in read-write mode — correct for a single database instance. ReadWriteMany (RWX) allows multiple nodes to mount simultaneously, which sounds useful but is almost never appropriate for a database data directory. Two SQL Server instances writing to the same data directory simultaneously is not high availability — it is corruption.

I/O performance from container storage varies widely. A database on local NVMe storage gets very different throughput than one writing to a network-attached volume over iSCSI. When evaluating storage options, measure directly. Run fio benchmarks against the actual storage class you intend to use before committing to it for a production workload.

-- Check I/O statistics inside a running SQL Server container
SELECT
    DB_NAME(vfs.database_id) AS database_name,
    vfs.io_stall_read_ms,
    vfs.io_stall_write_ms,
    vfs.num_of_reads,
    vfs.num_of_writes,
    mf.physical_name
FROM sys.dm_io_virtual_file_stats(NULL, NULL) vfs
JOIN sys.master_files mf
    ON vfs.database_id = mf.database_id
    AND vfs.file_id = mf.file_id
ORDER BY vfs.io_stall_read_ms + vfs.io_stall_write_ms DESC;

One configuration detail that catches teams off guard: durability. SQL Server opens data files with unbuffered I/O and depends on the storage stack honoring flush (write-through / FUA) faithfully. Most production storage backends do. Some cloud-managed NFS implementations have quirks. Verify durable flush before chasing performance — the result of getting that wrong is a data directory that looks intact but has torn pages after an unexpected shutdown. Run DBCC CHECKDB after any storage-level incident; it is non-negotiable.

Configuration Management for Containerized Databases

Running a database in a container without customizing its configuration means accepting defaults, which are rarely appropriate for production workloads. The challenge is doing configuration correctly within the container model, where immutable images and dynamic environments are the norm.

SQL Server reads its configuration from environment variables and mssql.conf at startup. There are three approaches to customizing them in containers.

The first approach uses environment variables, which the container honors directly — no config file needed:

docker run -d \
  --name mssql-tuned \
  -e ACCEPT_EULA=Y \
  -e MSSQL_SA_PASSWORD='' \
  -e MSSQL_PID=Developer \
  -e MSSQL_MEMORY_LIMIT_MB=2048 \
  -v mssqldata:/var/opt/mssql \
  mcr.microsoft.com/mssql/server:2022-latest

The second mounts a custom mssql.conf (normally at /var/opt/mssql/mssql.conf inside the container):

docker run -d \
  --name mssql-custom \
  -v /etc/mssql/mssql.conf:/var/opt/mssql/mssql.conf \
  -v mssqldata:/var/opt/mssql \
  mcr.microsoft.com/mssql/server:2022-latest

The third bakes configuration into a derived image:

FROM mcr.microsoft.com/mssql/server:2022-latest
COPY mssql.conf /var/opt/mssql/mssql.conf

In Kubernetes, ConfigMaps and Secrets serve this role. ConfigMaps hold non-sensitive configuration like mssql.conf. Secrets hold credentials. Both are mounted into pods as files or environment variables, keeping sensitive data out of images and out of source control.

For SQL Server, configuration works through environment variables and mssql.conf, the SQL Server configuration file that lives at /var/opt/mssql/mssql.conf inside the container. You can mount a custom mssql.conf with a plain Docker volume mount, as shown in the examples above.

-- Verify SQL Server configuration settings
SELECT
    name,
    value,
    value_in_use,
    description
FROM sys.configurations
WHERE name IN (
    'max degree of parallelism',
    'cost threshold for parallelism',
    'max server memory (MB)',
    'min server memory (MB)'
)
ORDER BY name;

Memory limits require special attention. When you set --memory=8g on a Docker container or a resources.limits.memory in a Kubernetes pod spec, the container's memory is capped at that value. SQL Server's max server memory must stay within that limit — use the MSSQL_MEMORY_LIMIT_MB environment variable to cap the engine directly. If you let SQL Server size itself for a 256 GB host while the container is limited to 8 GB, the configuration won't match reality and you will meet the OOM killer.

Kubernetes Orchestration for Database Workloads

Kubernetes is where containerized databases get serious. It provides automated scheduling, self-healing, resource management, rolling upgrades, and service discovery — capabilities that matter enormously when you're running databases at scale. It also introduces enough complexity that understanding the database-specific concerns is essential before going to production.

StatefulSets are the right Kubernetes workload type for databases. Unlike Deployments, StatefulSets give each pod a stable network identity and a persistent volume that follows it. When a pod named mssql-0 restarts, Kubernetes ensures it gets the same PVC it had before. The pod name is stable and predictable, which matters for primary-replica configurations.

graph TD\n    SS["StatefulSet: mssql"]\n    SS --> Pod0["Pod mssql-0"]\n    Pod0 --> PVC0[("PVC: sqldata-mssql-0")]\n    Headless["Headless Service"] --> Pod0

*Figure: A SQL Server StatefulSet on Kubernetes — the pod keeps a stable identity and its own dedicated PersistentVolumeClaim across restarts and rescheduling.*

A minimal StatefulSet for SQL Server:

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mssql
spec:
  serviceName: "mssql"
  replicas: 1
  selector:
    matchLabels:
      app: mssql
  template:
    metadata:
      labels:
        app: mssql
    spec:
      containers:
        - name: mssql
          image: mcr.microsoft.com/mssql/server:2022-latest
          env:
            - name: ACCEPT_EULA
              value: "Y"
            - name: MSSQL_PID
              value: Developer
            - name: MSSQL_SA_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: mssql-secret
                  key: sapassword
            - name: MSSQL_MEMORY_LIMIT_MB
              value: "6144"
          ports:
            - containerPort: 1433
          resources:
            requests:
              memory: "4Gi"
              cpu: "2"
            limits:
              memory: "8Gi"
              cpu: "4"
          volumeMounts:
            - name: sqldata
              mountPath: /var/opt/mssql
  volumeClaimTemplates:
    - metadata:
        name: sqldata
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: "fast-ssd"
        resources:
          requests:
            storage: 100Gi

The volumeClaimTemplates section is what separates StatefulSets from Deployments for database use. Each replica gets its own dedicated PVC. For a primary-only deployment, there is one PVC. For a three-node replica set, there are three PVCs, each attached exclusively to its pod.

Services in Kubernetes expose database pods to other workloads. A headless service (with clusterIP: None) allows direct DNS-based resolution to individual pod addresses, which replication configurations use to identify specific peers. A standard ClusterIP service load-balances across all matching pods — appropriate for read replicas but not for writes if you have multiple instances.

Liveness and readiness probes replace the healthcheck you define in Docker Compose. A readiness probe controls when a pod receives traffic. A liveness probe controls when Kubernetes restarts an unhealthy pod:

livenessProbe:
  exec:
    command:
      - /bin/sh
      - -c
      - /opt/mssql-tools/bin/sqlcmd -S localhost -U sa -P "$MSSQL_SA_PASSWORD" -Q "SELECT 1" -b
  initialDelaySeconds: 60
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  exec:
    command:
      - /bin/sh
      - -c
      - /opt/mssql-tools/bin/sqlcmd -S localhost -U sa -P "$MSSQL_SA_PASSWORD" -Q "SELECT 1" -b
  initialDelaySeconds: 10
  periodSeconds: 5

The initialDelaySeconds on the liveness probe deserves thought. SQL Server running database recovery (redo/undo) after an unexpected shutdown may take minutes to complete before accepting connections. If the liveness probe fires before recovery finishes and restarts the pod, it will interrupt recovery, causing the pod to loop indefinitely. Set initialDelaySeconds conservatively — longer than the worst-case recovery time for your workload.

Operators extend Kubernetes with database-specific intelligence, encoding operational runbooks as code. For SQL Server the operator ecosystem is thin — most production teams run StatefulSets directly, handle failover with availability groups outside Kubernetes (or accept a single instance with fast rescheduling), and automate backups and configuration with CronJobs and mounted mssql.conf files.

-- Inside a Kubernetes-hosted SQL Server, check AG replica status
SELECT
    ar.replica_server_name,
    rs.role_desc,
    rs.operational_state_desc,
    rs.connected_state_desc,
    rs.synchronization_health_desc,
    ars.log_send_queue_size,
    ars.redo_queue_size
FROM sys.availability_replicas ar
JOIN sys.dm_hadr_availability_replica_states rs
    ON ar.replica_id = rs.replica_id
JOIN sys.dm_hadr_database_replica_states ars
    ON ar.replica_id = ars.replica_id;

Production Operations: Backups, Upgrades, and Observability

Getting a containerized database running is one challenge. Keeping it running reliably over months and years — while upgrading it, backing it up, and troubleshooting it when problems arise — is the sustained work of production operations.

Backups in containerized databases require connecting the backup tooling to both the database process and the underlying persistent volume. The container abstraction doesn't change what constitutes a valid backup, but it does change how you execute one.

For SQL Server, BACKUP DATABASE ... TO URL runs inside the container via docker exec or kubectl exec, writing to Azure Blob Storage or a mounted backup volume. A sidecar container — a second container in the same pod sharing the same volume mount — can run backup tooling continuously without interfering with the primary container.

-- Full backup to Azure Blob Storage, run inside the container
BACKUP DATABASE [appdb]
TO URL = 'https://myaccount.blob.core.windows.net/backups/appdb_full.bak'
WITH COMPRESSION, CHECKSUM;
# Or via docker exec with sqlcmd, writing to a mounted backup volume
docker exec -t mssql-prod /opt/mssql-tools/bin/sqlcmd \
  -S localhost -U sa -P "$MSSQL_SA_PASSWORD" \
  -Q "BACKUP DATABASE [appdb] TO DISK = '/var/opt/mssql/backup/appdb_full.bak' WITH COMPRESSION, CHECKSUM"

For Kubernetes, backup CronJobs are a common pattern — a scheduled pod that runs, performs the backup, ships the result to object storage (S3, Azure Blob, GCS), and exits. CloudNativePG manages this automatically if you configure it with a backup policy.

Major version upgrades of containerized SQL Server are operationally cleaner than bare-metal upgrades in one important way: you stop the old container, pull the new image, and start it against the same data volume — the engine upgrades the system databases automatically on first boot. For large fleets, run old and new in parallel, replicate or restore across, and cut over:

# Major-version upgrade: stop, pull the new image, start against the same volume
docker stop mssql-prod
docker pull mcr.microsoft.com/mssql/server:2025-latest
docker run -d \
  --name mssql-prod \
  -e ACCEPT_EULA=Y \
  -e MSSQL_SA_PASSWORD="$MSSQL_SA_PASSWORD" \
  -v mssqldata:/var/opt/mssql \
  -p 1433:1433 \
  mcr.microsoft.com/mssql/server:2025-latest
# The engine upgrades the system databases automatically on first boot

Because the upgrade happens on first boot against the existing data files, keep a tested backup from before the switch — a failed automatic upgrade you cannot roll back is worse than a slow planned one.

Observability inside containers uses the same tools as observability outside them, with the addition of container-level metrics. Prometheus with the mssql_exporter (or sql_exporter) sidecar collects database metrics and exposes them for scraping. Grafana dashboards built on top of those metrics give you the same visibility you'd have on bare metal.

Resource metrics at the container level — CPU usage, memory consumption, network I/O — come from cAdvisor, which Kubernetes ships as part of the node agent. Correlating database-level metrics (query latency, lock waits, buffer cache hit ratios) with container-level metrics (memory near the limit, CPU throttling) gives you the full picture when diagnosing performance problems.

CPU throttling is a particularly common issue for database containers. When a container's CPU usage hits the cpu.limits value, the kernel throttles it — slices of CPU time are withheld. A database that looks fine from a query perspective but shows elevated latency inconsistently may be experiencing CPU throttling. Check the container_cpu_cfs_throttled_seconds_total metric in Prometheus before assuming the problem is a slow query.

-- Check index fragmentation inside a production SQL Server container
SELECT
    DB_NAME() AS database_name,
    OBJECT_NAME(ips.object_id) AS table_name,
    i.name AS index_name,
    ips.index_type_desc,
    ROUND(ips.avg_fragmentation_in_percent, 2) AS fragmentation_pct,
    ips.page_count
FROM sys.dm_db_index_physical_stats(
    DB_ID(), NULL, NULL, NULL, 'LIMITED'
) ips
JOIN sys.indexes i
    ON ips.object_id = i.object_id
    AND ips.index_id = i.index_id
WHERE ips.avg_fragmentation_in_percent > 10
    AND ips.page_count > 1000
ORDER BY ips.avg_fragmentation_in_percent DESC;

Log management in containers follows the principle that logs should go to stdout and stderr, where the container runtime captures them. SQL Server's error log writes to /var/opt/mssql/log/errorlog by default — a volume-backed path that persists across container restarts. Tail it through your container log driver or ship it with Fluentd, Loki, or CloudWatch Logs like any other container log stream.

---

Key Takeaways

  • → Containers package databases with their dependencies into reproducible, portable images that eliminate environment inconsistency — but the ephemeral nature of containers requires explicit, volume-backed persistence for all database data files.
  • → Named Docker volumes and Kubernetes PersistentVolumes are the correct storage mechanisms for containerized databases; binding data directories to container-layer storage guarantees data loss on container removal.
  • → StatefulSets in Kubernetes — not Deployments — are the appropriate workload type for databases, because they provide stable pod identities and per-replica persistent volumes that survive pod restarts and rescheduling.
  • → Memory and CPU resource limits set at the container level must be reflected in database memory configuration (`max server memory` / `MSSQL_MEMORY_LIMIT_MB`) — a mismatch between container limits and database configuration leads to OOM kills and CPU throttling that appears as unexplained latency.
  • → Production operations for containerized databases — including backups, major version upgrades, and observability — follow the same logical requirements as bare-metal operations, but use container-native patterns like sidecar containers, CronJob-based backup pipelines, and Prometheus exporters to satisfy those requirements within the orchestration model.
