Chapter 6: Indexing and Retrieval

Few decisions affect database performance more than how you index your tables. Get indexing right and queries that once took minutes run in milliseconds. Get it wrong and you'll spend your career chasing slow queries, watching disk I/O spike, and apologizing to application teams. This chapter walks through how indexes actually work under the hood, how query planners decide whether to use them, how to build and maintain a sensible indexing strategy, and how to push that strategy further when standard B-tree indexes aren't enough. The concepts are universal but the implementation details are SQL Server's throughout — and those details are what matter in production.

---

What an Index Is and How It Actually Works

An index is a separate data structure maintained alongside a table, designed to let the database engine locate rows without scanning every page in the table. The analogy to a book's index is apt but incomplete — a database index also maintains physical or logical pointers back to the actual data, and the database engine must decide at query time whether using that index is faster than ignoring it entirely.

The default index type in SQL Server is the B-tree (balanced tree). A B-tree organizes values in sorted order across a hierarchy of nodes. At the top sits the root node, branching down through intermediate nodes to leaf nodes at the bottom. Each leaf node contains index entries and a pointer to the corresponding row locator — the clustered index key, or the RID for a heap. When a query filters on an indexed column, the engine traverses the tree from root to leaf — typically in O(log n) time — rather than reading every data page in the table linearly.

graph TD
    Root["Root Node\n(M)"]
    Root --> I1["Intermediate\n(D–H)"]
    Root --> I2["Intermediate\n(N–S)"]
    Root --> I3["Intermediate\n(T–Z)"]
    I1 --> L1["Leaf: D, E, F"]
    I1 --> L2["Leaf: G, H"]
    I2 --> L3["Leaf: N, P, Q"]
    I2 --> L4["Leaf: R, S"]
    I3 --> L5["Leaf: T, U, V"]
    I3 --> L6["Leaf: W, X, Y, Z"]
    L1 -.-> L2 -.-> L3 -.-> L4 -.-> L5 -.-> L6

*Figure: A B-tree index — the engine walks from root to leaf in O(log n) time, and leaf pages are linked so range scans can move sequentially without re-traversing the tree.*

The key word is "sorted." A B-tree index on a last_name column stores last names alphabetically across its leaf pages. This means the index supports not just equality lookups (WHERE last_name = 'Smith') but also range predicates (WHERE last_name BETWEEN 'R' AND 'T'), prefix matches (WHERE last_name LIKE 'Sm%'), and ORDER BY operations without a separate sort step. The sort order embedded in the index is one of the most underappreciated features of B-tree indexes — when a query's ORDER BY matches the index order, the planner can often skip sorting entirely, which is expensive for large result sets.

Under the hood, SQL Server stores indexes in 8KB pages. As rows are inserted, updated, or deleted, index pages fragment over time. Insertions near a full page cause a page split, dividing the page and creating slack space that gradually accumulates. This fragmentation is why index maintenance — rebuilding or reorganizing indexes — is a routine DBA task, not an occasional emergency.

In SQL Server, the leaf level of a clustered index is the table itself. The data pages are physically ordered by the clustered index key, which is why a table can have only one clustered index. Every other index is a nonclustered index, whose leaf pages store the clustered index key (or the Row ID if there's no clustered index) as a row locator. A nonclustered index seek followed by a key lookup into the clustered index is the most common plan shape in OLTP — and the tipping point, where the optimizer abandons seek-plus-lookup for a straight scan, is exactly what covering indexes and INCLUDE columns exist to move in your favor.

This distinction has real consequences. A range scan on the clustered index reads contiguous data pages, which is extremely efficient. A nonclustered index seek that must then perform key lookups into the clustered index for each row pays random I/O per row — cheap for ten rows, ruinous for ten million. The optimizer's tipping-point math between seek-plus-lookup and a straight scan is driven by statistics, which is why stale statistics so often manifest as "the index is being ignored".

How the Query Planner Decides Whether to Use an Index

Building an index doesn't guarantee the planner will use it. SQL Server uses a cost-based query optimizer that estimates the total cost of different execution plans and chooses the cheapest one. Understanding this decision-making process is what separates a DBA who creates indexes from one who creates *effective* indexes.

The optimizer estimates two things: how selective the index is (how many rows it will eliminate), and how expensive the I/O path through that index will be compared to alternative paths. For a highly selective predicate — say, looking up a single customer by their email address — the index path is almost always cheaper. For a low-selectivity predicate — say, filtering a status column that contains only three distinct values across 50 million rows — a full table scan may actually be cheaper, because the index lookup would scatter I/O across too many heap pages.

The optimizer's cost estimates depend heavily on statistics: the distribution of values in each column, the number of distinct values, histograms of value frequency, and the correlation between column order and physical storage order. In SQL Server, statistics are gathered automatically by default and stored in objects accessible via sys.stats and viewable with DBCC SHOW_STATISTICS — including the 200-step histogram the optimizer actually reasons with when it estimates how many rows your predicate will return.

-- View statistics for a specific table and column
DBCC SHOW_STATISTICS ('dbo.orders', 'IX_orders_status');

-- Or query the stats metadata
SELECT
    s.name         AS stats_name,
    s.auto_created,
    s.user_created,
    sp.last_updated,
    sp.rows,
    sp.rows_sampled,
    sp.unfiltered_rows
FROM sys.stats s
CROSS APPLY sys.dm_db_stats_properties(s.object_id, s.stats_id) sp
WHERE OBJECT_NAME(s.object_id) = 'orders';

Execution plan output reveals what the optimizer chose and why. Reading actual execution plans is one of the most important skills a DBA develops. The plan shows whether an index seek, index scan, key lookup, or table scan was used, what the estimated vs. actual row counts were, and where in the plan execution time is concentrated.

-- View estimated plan in SSMS or capture actual plan at runtime
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT customer_id, order_date, total_amount
FROM dbo.orders
WHERE customer_id = 10042
  AND order_date >= '2024-01-01';

-- Or use the DMV to capture recent query plans
SELECT TOP 10
    qs.total_elapsed_time / qs.execution_count AS avg_elapsed_us,
    qs.execution_count,
    SUBSTRING(st.text, (qs.statement_start_offset/2)+1,
        ((CASE qs.statement_end_offset WHEN -1 THEN DATALENGTH(st.text)
          ELSE qs.statement_end_offset END - qs.statement_start_offset)/2)+1) AS query_text,
    qp.query_plan
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
CROSS APPLY sys.dm_exec_query_plan(qs.plan_handle) qp
ORDER BY avg_elapsed_us DESC;

When you see the planner ignoring an index you believe should help, the common culprits are stale statistics, parameter sniffing, or plan caching effects. Running UPDATE STATISTICS after significant data changes is often the first thing to try. If statistics are fresh but the index is still ignored, check the actual selectivity — the planner may simply be right that the index isn't worth using for that predicate.

One scenario worth understanding explicitly: a query that returns a large fraction of the table may trigger a sequential scan even when an index exists. In SQL Server, you can use query hints (WITH (INDEX(...)), OPTION (RECOMPILE), OPTIMIZE FOR) to test alternatives for investigation purposes. Never leave these forcing mechanisms in production code — use them only for diagnosis, then fix the underlying cause (usually statistics, index design, or the query itself).

Building and Maintaining Indexes in Production

Creating an index in production without disrupting users is something every DBA eventually needs to do. Both databases support online index creation, but the mechanics differ.

In SQL Server, CREATE INDEX ... WITH (ONLINE = ON) builds the index without taking a long-term table lock (Enterprise edition), letting reads and writes continue during the build. The build takes longer, uses more tempdb, and still needs brief locks at the start and end of the operation — so schedule large builds with that in mind. For very large tables, resumable index builds (WITH (ONLINE = ON, RESUMABLE = ON)) let a multi-hour build be paused and resumed across maintenance windows instead of starting over when the window closes.

In SQL Server, CREATE INDEX ... WITH (ONLINE = ON) performs a similar function for Enterprise Edition. The index is built alongside ongoing DML, with a brief schema modification lock taken only at the start and end of the operation. For Standard Edition, online index builds are not available, which is a real operational constraint in busy systems.

-- Create an index online (Enterprise Edition)
CREATE NONCLUSTERED INDEX IX_orders_customer_date
ON dbo.orders (customer_id, order_date DESC)
WITH (ONLINE = ON, SORT_IN_TEMPDB = ON);

-- Check index fragmentation before deciding rebuild vs. reorganize
SELECT
    i.name                          AS index_name,
    ips.avg_fragmentation_in_percent,
    ips.page_count,
    ips.avg_page_space_used_in_percent
FROM sys.dm_db_index_physical_stats(
         DB_ID(), OBJECT_ID('dbo.orders'), NULL, NULL, 'LIMITED') ips
JOIN sys.indexes i
    ON ips.object_id = i.object_id
   AND ips.index_id  = i.index_id
WHERE ips.page_count > 100
ORDER BY ips.avg_fragmentation_in_percent DESC;

Index maintenance strategy should be data-driven. In SQL Server, the standard guidance is to reorganize indexes with 10–30% fragmentation (a lightweight, online operation that defragments leaf pages in place) and rebuild indexes above 30% (which rewrites the entire index, reclaims space, and refreshes statistics with a full scan). Ola Hallengren's IndexOptimize remains the community-standard implementation — it encodes the rebuild-vs-reorganize decision, the online options, and statistics updates as one maintained solution rather than hand-rolled Agent jobs you have to debug at 2 a.m.

Fill factor deserves mention here. When an index page is built, fill factor determines how full each leaf page is left. A fill factor of 80 leaves 20% of each page empty, providing room for future insertions without immediate page splits. The trade-off is larger index size and slightly more I/O for reads. For tables that are mostly read, use a high fill factor (90–100). For tables with heavy insert or update patterns on sequential key columns, a lower fill factor reduces split activity. For tables with random inserts (e.g., UUID primary keys), low fill factors help considerably.

Index maintenance should also account for unused indexes. Every index on a table adds overhead to every INSERT, UPDATE, and DELETE operation on that table. A table with 12 indexes has 12 structures that must be kept current on every write — the read benefits of those indexes must outweigh the write cost. This is the balance that makes indexing a judgment call rather than a mechanical exercise.

Index Types and When Each One Fits

B-tree indexes handle the majority of workloads, but SQL Server offers specialized index types that dramatically outperform B-trees for specific access patterns.

Hash Indexes

Hash indexes store a hash of the indexed value and support only equality lookups — no ranges, no ordering. In SQL Server they exist for memory-optimized (In-Memory OLTP) tables, where they are the dominant index type for point lookups on in-memory data. The critical tuning knob is bucket_count: too few buckets creates long hash chains that serialize lookups, too many wastes memory — size it at roughly 1–2x the expected row count, and monitor for empty vs. chained buckets.

Full-Text Search

Full-text search handles the "find documents containing these words" problem that B-trees cannot touch. SQL Server's full-text engine builds inverted indexes over character columns through full-text catalogs, queried with CONTAINS (precise predicates, including NEAR proximity and FORMSOF inflectional matching) and FREETEXT (meaning-based matching), or the table-valued CONTAINSTABLE / FREETEXTTABLE for ranked results. Stoplists filter noise words, and thesaurus files expand synonyms. For JSON payloads in nvarchar columns, the modern pattern is computed columns over JSON_VALUE with ordinary B-tree indexes for structured predicates — reserving full-text indexes for queries that are genuinely textual.

Spatial Indexes

Spatial indexes accelerate geometry and geography queries — "find all locations within 5km of this point." SQL Server tessellates space into a grid hierarchy and indexes which cells each spatial object touches, so a bounding-box filter eliminates the vast majority of candidates before exact geometric tests run. Spatial indexes demand attention to tessellation density: too coarse and every query scans too many candidates; too fine and the index itself becomes the bottleneck.

Columnstore for Ordered Large Tables

For the "naturally ordered large table" pattern — time-series, append-only event logs — SQL Server's answer is the clustered columnstore index from Chapter 5. Segment elimination over min/max metadata plays the same role as block-range indexing: the engine skips entire rowgroups without reading them. It works when data is ordered, or at least correlated, by the filtered columns; randomly ordered loads eliminate nothing. This is why load discipline (ordered bulk loads, partition-aligned trickle feeds) is a columnstore performance feature, not just tidiness.

Filtered/Partial Indexes

SQL Server supports filtered indexes — built only over rows that satisfy a WHERE condition. This is one of the most powerful indexing techniques available, and it's underused in most production systems.

Consider a jobs table with 100 million rows, where only 50,000 rows have status = 'pending'. A standard index on status would index all 100 million rows. A partial index on status = 'pending' indexes only 50,000 rows — it's smaller, faster to scan, and faster to update since completed jobs never touch it.

-- Filtered index covering only pending jobs
CREATE NONCLUSTERED INDEX IX_jobs_pending
ON dbo.jobs (created_at, priority)
WHERE status = 'pending';

-- Queries must include the filter predicate to use the filtered index
SELECT job_id, created_at, priority
FROM dbo.jobs
WHERE status = 'pending'
  AND created_at > DATEADD(HOUR, -24, GETDATE())
ORDER BY priority DESC;

Covering Indexes and INCLUDE Columns

A covering index satisfies a query entirely from the index without touching the base table. When the index contains all the columns needed by a query — both for filtering and for projection — the engine never has to follow a pointer back to the clustered index. This eliminates the key lookup — random I/O per row that is cheap for ten rows and ruinous for ten million under high concurrency.

Both databases allow extra columns to be stored in the leaf level of the index without participating in the sort order, using the INCLUDE clause. This lets you add projection columns to an index without widening the sort key (which would make the index larger and slower for range scans).

-- Covering index with included columns
CREATE NONCLUSTERED INDEX IX_orders_covering
ON dbo.orders (customer_id)
INCLUDE (order_date, total_amount, status);

In the execution plan, the shape you want for a covering index is an index seek with no key lookup — every column the query needs comes from the index's leaf pages (key columns plus INCLUDE columns). When you see a seek followed by thousands of key lookups, the index is almost-covering: adding the missing columns as INCLUDE (which don't affect key order, size limits aside) converts random I/O into a pure index operation. This is the highest-ROI index tuning move in OLTP.

Finding What's Missing, What's Redundant, and What's Hurting You

A production database that's been running for two or three years accumulates indexing debt: missing indexes on columns that are now heavily queried, duplicate indexes created by different developers who didn't realize an equivalent index already existed, and indexes that made sense when a feature launched but are now completely unused. Auditing the index landscape is a regular DBA responsibility, not a one-off exercise.

Identifying missing indexes

Both databases offer tooling to identify frequently accessed queries that lack supporting indexes.

In SQL Server, sys.dm_db_missing_index_details and sys.dm_db_missing_index_group_stats capture information about index opportunities the optimizer identified during query compilation. These DMVs are reset when SQL Server restarts, so they reflect only the period since the last restart (or the last DMV clear). The output is useful but should be treated as suggestions — the optimizer sometimes recommends indexes that would help individual queries but would harm overall workload throughput.

Query Store complements the missing-index DMVs with the history they lack: it persists query plans and runtime statistics across restarts, so you can correlate a missing-index suggestion with the actual workload it would serve and verify the improvement after creating the index. Many organizations run automated pipelines over Query Store data that flag regressed queries and candidate indexes together — turning index tuning from archaeology into a repeatable process.

-- Missing index recommendations from the optimizer
SELECT
    mid.statement                              AS table_name,
    migs.avg_total_user_cost * migs.avg_user_impact
        * (migs.user_seeks + migs.user_scans)  AS index_benefit_score,
    migs.user_seeks,
    migs.user_scans,
    mid.equality_columns,
    mid.inequality_columns,
    mid.included_columns
FROM sys.dm_db_missing_index_groups mig
JOIN sys.dm_db_missing_index_group_stats migs
    ON mig.index_group_handle = migs.group_handle
JOIN sys.dm_db_missing_index_details mid
    ON mig.index_handle = mid.index_handle
WHERE migs.avg_total_user_cost * migs.avg_user_impact
        * (migs.user_seeks + migs.user_scans) > 1000
ORDER BY index_benefit_score DESC;

Identifying unused indexes

Unused indexes are pure write overhead. Every time a row is modified, the database must update all indexes on that table, whether or not those indexes are ever read. Removing unused indexes reduces DML overhead and can meaningfully improve write throughput on busy OLTP tables.

In SQL Server, sys.dm_db_index_usage_stats tracks index seeks, scans, lookups, and updates since the last restart. An index with zero reads after weeks of normal workload is a strong candidate for removal — but verify against Query Store history and consider whether the index serves monthly batch jobs that haven't run during your observation window. Every unused index is pure write overhead: it costs on every INSERT, UPDATE, and DELETE and buys nothing.

In SQL Server, sys.dm_db_index_usage_stats provides read and write counts per index since the last restart. An index with high user_updates (write overhead) and zero or near-zero user_seeks + user_scans + user_lookups is a candidate for removal.

Before dropping any index in production, always script it first. A single CREATE INDEX statement stored somewhere accessible means you can recreate the index within minutes if something that depended on it surfaces after the drop.

Identifying duplicate and redundant indexes

Duplicate indexes are exact duplicates — same columns, same order. Redundant indexes are indexes where one index's leading columns are a prefix of another's. For example, if you have an index on (customer_id) and another on (customer_id, order_date), the second index can serve all the same equality lookups as the first, making the first index redundant for most purposes (unless you need to support an index-only scan that doesn't need order_date).

Detecting these requires querying index metadata and comparing column lists. There is no single built-in tool for it, but the query is straightforward to write against sys.index_columns and sys.columns — look for indexes whose leading key columns are identical prefixes of another index's key.

Advanced Indexing for High-Throughput and Complex Workloads

At sufficient scale, standard indexing practice reaches its limits, and the strategies that work for a 10GB database need rethinking for a 10TB one. The following scenarios represent the kind of indexing problems that separate routine database administration from performance engineering.

UUID Primary Keys and Random Index Fragmentation

One of the most common performance problems in SQL Server systems that use UUID (universally unique identifier) primary keys is extreme index fragmentation. Because UUIDs are randomly distributed, new index entries land randomly across the B-tree leaf level rather than at the end. Every page fills up and splits constantly, leading to high fragmentation, low page density, and excessive I/O.

In SQL Server, NEWID() produces random UUIDs that scatter inserts across the B-tree and fragment it relentlessly, while NEWSEQUENTIALID() generates sequential GUIDs suitable for clustered index keys. The practical solutions are: use an IDENTITY surrogate key with the GUID as an alternate key, use NEWSEQUENTIALID() for the clustered key, or — if the GUID must be the clustered key — accept the fragmentation and maintain it with aggressive rebuilds and a lower fill factor.

Composite Index Column Ordering

The leading column of a composite index is the one the engine filters first — only predicates on the leading column (or a prefix of leading columns in order) can use the index for range access. A query filtering on order_date alone cannot make effective use of an index defined as (customer_id, order_date), because the index is sorted by customer_id first; order_date values are only sorted within each customer_id group. The general rule of thumb that holds up well in practice: put equality-filtered columns first, range-filtered columns last. If a query does WHERE customer_id = 10042 AND order_date >= '2024-01-01', an index on (customer_id, order_date) lets the engine jump straight to the matching customer_id block and then scan a contiguous range within it. Reversing the column order — (order_date, customer_id) — would force the engine to scan every date first and filter customer_id afterward, touching far more index entries.

Column order also determines whether an index can eliminate a sort. If a query does ORDER BY customer_id, order_date DESC, an index defined as (customer_id, order_date DESC) lets the engine return rows already in the required order, avoiding a separate sort step entirely — a significant win for large result sets. This is one of the most common reasons an index that "should" be helping isn't: the column order matches the filter predicates but not the sort order the query actually needs, or vice versa.

There is no universal ordering rule that fits every workload. The right approach is to look at the actual queries hitting the table — their filter predicates, their sort clauses, their selectivity — and design composite indexes around the query patterns that matter most, rather than around a generic convention.

---

Key Takeaways

  • → B-tree indexes are the default in SQL Server, storing values in sorted order so the engine can support equality lookups, range scans, and ORDER BY without a separate sort — but the optimizer only uses an index when its cost estimate, driven by table and column statistics, comes out cheaper than a scan.
  • → Building indexes without disrupting production traffic is possible with `WITH (ONLINE = ON)` (Enterprise Edition), and multi-hour builds can be made resumable — but online builds still take longer, use more tempdb, and need brief locks at start and end, so plan the maintenance window honestly.
  • → Beyond the default B-tree, SQL Server offers hash indexes for memory-optimized tables, full-text indexes for document search, spatial indexes for geometry/geography, and columnstore for analytics — each dramatically outperforming B-trees on its home workload and useless outside it.
  • → Filtered indexes and covering indexes using `INCLUDE` let you build smaller, faster indexes tailored to the queries that actually run — reducing both index size and write overhead compared to indexing entire tables.
  • → Index maintenance is an ongoing responsibility, not a one-time task: monitor fragmentation with `sys.dm_db_index_physical_stats`, remove unused and redundant indexes using usage statistics, and order composite index columns to match real query filter and sort patterns rather than guessing.
