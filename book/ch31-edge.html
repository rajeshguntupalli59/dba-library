Chapter 31: Edge Computing

Edge computing has fundamentally changed the assumptions database administrators have been able to make for decades. For most of computing history, the database lived in a data center — a controlled environment with reliable power, fast interconnects, abundant storage, and teams of people available to maintain it. Edge computing dismantles every one of those assumptions. Now, database instances run on oil rigs, in autonomous vehicles, inside retail stores, on factory floors, and aboard ships crossing the ocean. SQL Server has a real deployment story in these environments through Azure SQL Edge, and understanding how to design, deploy, and maintain those databases is no longer optional. This chapter covers what edge computing actually means for database infrastructure, how to architect SQL Server deployments for constrained and intermittently connected environments, synchronization strategies that keep edge data consistent with central systems, and the operational realities of managing databases you cannot always reach.

---

What Edge Computing Actually Means for a Database

The term "edge computing" gets used loosely in marketing, so it is worth establishing a precise definition before discussing database architecture. Edge computing places compute and storage resources physically close to where data is generated and consumed, rather than routing everything to a centralized cloud or data center. The "edge" might be a small server running inside a wind turbine enclosure, a Raspberry Pi attached to a conveyor belt, a ruggedized laptop in a field service vehicle, or a full rack of equipment in a regional distribution center. The common thread is that the edge node operates with some degree of independence from central infrastructure.

For a database, this independence has four practical consequences. First, connectivity is unreliable. An edge node might have milliseconds of high-bandwidth connectivity followed by hours of complete isolation. Second, hardware is constrained. Edge devices often run on limited RAM, slower storage, and processors with restricted thermal envelopes. Third, physical access is limited or expensive. Rebooting a server in a remote oil platform field requires a helicopter. Fourth, the edge database is rarely the system of record — it is typically a participant in a larger data ecosystem that includes a central database, and keeping those two in sync is where most of the complexity lives.

Understanding these four pressures is the starting point for every architectural decision that follows. A configuration that works perfectly in a data center — aggressive parallel query execution, large buffer pools, synchronous replication, frequent index maintenance — may perform terribly or fail outright at the edge. The DBA's job is to adapt every default assumption.

SQL Server has a dedicated edge offering — Azure SQL Edge — that runs as a container on ARM64 and x64 hardware, specifically targeting IoT and industrial scenarios. It brings the familiar T-SQL engine, Query Store, and CDC to devices with as little as a few gigabytes of RAM, so the same skills, DMVs, and scripts you use in the datacenter transfer directly to the field.

Designing Schemas and Storage for Constrained Hardware

Schema design for edge deployments is driven by a simple goal: store the minimum necessary data, in the most efficient format, with the most efficient access patterns. This sounds obvious, but most schema designs are created in the context of enterprise servers with terabytes of storage and hundreds of gigabytes of RAM. Transplanting those schemas to edge hardware without adaptation is a common and expensive mistake.

Start with data types. On edge hardware, choosing SMALLINT over INTEGER or REAL over DOUBLE PRECISION has measurable impact at scale. A table storing sensor readings at 10Hz across 500 sensors accumulates 432 million rows per day. Reducing each row by 4 bytes saves 1.6 GB per day — significant when your total storage is 64 GB and you need to retain 30 days of data locally.

Partitioning by time is almost always appropriate for edge telemetry workloads. On SQL Server, partitioned tables using a partition function and sliding-window maintenance let you drop old partitions instantly with SWITCH — no slow DELETE operations that fill the log and lock rows. Partition elimination also keeps edge queries scanning only the recent partitions they actually need.

-- Time-partitioned sensor table for edge deployment
CREATE PARTITION FUNCTION pf_sensor_monthly (DATETIME2)
AS RANGE RIGHT FOR VALUES (
    '2024-01-01', '2024-02-01', '2024-03-01'
);

CREATE PARTITION SCHEME ps_sensor_monthly
AS PARTITION pf_sensor_monthly ALL TO ([PRIMARY]);

CREATE TABLE sensor_readings (
    reading_id      BIGINT          IDENTITY(1,1),
    sensor_id       SMALLINT        NOT NULL,
    recorded_at     DATETIME2       NOT NULL,
    temperature     REAL,
    pressure        REAL,
    humidity        REAL
) ON ps_sensor_monthly(recorded_at);

-- Switch old partition out (near-instant, metadata-only)
ALTER TABLE sensor_readings
    SWITCH PARTITION 1 TO sensor_readings_archive PARTITION 1;

Indexes at the edge require discipline. Each index consumes storage and, more importantly, consumes write throughput — a resource that is often the bottleneck in high-ingestion edge scenarios. Limit indexes to those required by the actual queries running on the edge node. In most edge deployments, those queries are: ingest writes, recent-window range reads by sensor ID, and outbound sync queries that extract rows modified since the last sync checkpoint. Three indexes maximum on a high-ingestion table is a reasonable default to start from and deviate from only with evidence.

Compression is another lever. On SQL Server, row and page compression are available even in the Edge edition and are straightforward to enable — page compression routinely halves the footprint of numeric telemetry data. For the most aggressive storage savings, clustered columnstore indexes (supported on Azure SQL Edge) compress telemetry several-fold and accelerate analytic scans:

-- Enable page compression on sensor_readings table
ALTER TABLE sensor_readings REBUILD
WITH (DATA_COMPRESSION = PAGE);

-- Enable compression on a specific partition
ALTER TABLE sensor_readings REBUILD
PARTITION = 2
WITH (DATA_COMPRESSION = PAGE);

-- Check compression ratios in sys DMVs
SELECT
    p.object_id,
    OBJECT_NAME(p.object_id)   AS table_name,
    p.partition_number,
    p.data_compression_desc,
    p.rows,
    a.total_pages * 8          AS total_kb
FROM sys.partitions p
JOIN sys.allocation_units a
    ON a.container_id = p.partition_id
WHERE OBJECT_NAME(p.object_id) = 'sensor_readings';

Transaction log sizing on SQL Server edge nodes deserves attention. The log cannot truncate past the oldest active transaction, so it will accumulate if sync or backups are interrupted. Size the log for your storage budget and monitor log_reuse_wait_desc — during a multi-day connectivity outage, an unshipped log on a constrained disk is fatal.

Synchronization Strategies Between Edge and Central

Synchronization is where edge database architecture becomes genuinely hard. The fundamental problem is that the edge database and the central database diverge during disconnection and must be reconciled when connectivity resumes — correctly, completely, and without overwhelming the central system when dozens of edge nodes reconnect simultaneously.

The synchronization strategy you choose depends on answers to three questions: Does data flow one direction (edge to center only), or must data flow both ways? How long can the edge node be disconnected before data loss becomes a business problem? And can conflicts occur — that is, can the same row be modified at both edge and center while disconnected?

Unidirectional upload is the simplest case. Edge nodes collect telemetry data that is never modified by the central system. In this pattern, the edge node buffers rows locally and periodically flushes them upstream. Transactional replication handles this natively: the edge node is the publisher, the central server is the subscriber, and the distribution database buffers changes while disconnected. When connectivity resumes, the distribution agent catches the subscriber up automatically.

Sensors write to the edge database's local buffer even with no connectivity; when the link returns, the dashed sync arrow pushes changes to the central database. Configuration and reference data flow the opposite direction, from center to edge. Design for the disconnected state first — sync is the exception handler, not the steady state.

*Figure: Edge-to-central synchronization — the edge node buffers locally during disconnection and drains to the central database once connectivity resumes, while ownership of each table is fixed to one side to avoid write conflicts.*

The risk here is distribution backlog. Undistributed commands accumulate in the distribution database indefinitely while the edge node is disconnected. On a constrained disk, this is fatal. Set the distribution retention conservatively and monitor the backlog of undistributed commands. If the backlog exceeds your storage budget, you must either expand storage, reduce the outage tolerance, or switch to a polling-based sync approach.

-- Azure SQL Edge uses SQL Server replication or Sync Agent
-- Check distribution agent status for a subscription
SELECT
    s.subscriber_db,
    h.runstatus,
    h.comments,
    h.delivered_commands,
    h.delivery_latency,
    h.time
FROM MSsubscription_properties s
JOIN MSdistribution_history h
    ON h.agent_id = s.agent_id
ORDER BY h.time DESC;

-- Check pending commands waiting for delivery
SELECT
    agent_id,
    pending_commands,
    pending_transactions
FROM MSsubscriptions
WHERE subscriber_db = 'EdgeSensorDB';

Bidirectional sync with conflict resolution is substantially more complex. This pattern arises when a central system needs to push configuration or lookup data down to the edge, and the edge pushes readings back up. You now have two writable copies of some data, and conflicts are possible.

The most practical approach for most edge deployments is to partition ownership. Define, at design time, which tables are "edge-owned" (the edge can insert and update them, the center can only read them) and which tables are "center-owned" (the center can insert and update them, the edge can only read them). This eliminates conflicts by construction, which is far simpler than building conflict resolution logic.

When bidirectional ownership of the same table cannot be avoided, you need either timestamp-based last-write-wins (simple but can silently discard legitimate writes) or application-level merge logic where conflicts are surfaced to a human or business rule. Neither option is comfortable. Design your schema to avoid this situation if at all possible.

For SQL Server deployments, Azure Data Sync provides a managed service for hub-and-spoke synchronization between an Azure SQL Database hub and Azure SQL Edge nodes. It handles conflict detection with configurable hub-wins or member-wins policies. The trade-off is that Azure Data Sync adds latency and has throughput limits that make it unsuitable for high-velocity sensor data; it works well for lower-frequency configuration and reference data.

Checkpoint-based polling is an alternative to log-based replication that is more robust during extended outages. Instead of relying on log retention, each table carries a modified_at timestamp column updated by a trigger or application code. The central sync process records the last-synced timestamp per edge node and queries for rows modified after that checkpoint. This approach survives arbitrary outages because it requires no server-side state on the edge — only the checkpoint timestamp stored centrally.

-- Checkpoint-based sync using a rowversion/timestamp column
ALTER TABLE sensor_readings
    ADD row_version ROWVERSION NOT NULL;

-- The ROWVERSION column auto-increments on every insert/update
-- Store the last synced rowversion value in the sync state table
CREATE TABLE sync_state (
    edge_node_id    INT           NOT NULL PRIMARY KEY,
    last_row_version BINARY(8)   NOT NULL DEFAULT 0x0000000000000000,
    last_sync_at    DATETIME2     NOT NULL DEFAULT GETUTCDATE()
);

-- Central sync query: fetch rows modified since last checkpoint
DECLARE @last_rv BINARY(8);
SELECT @last_rv = last_row_version
FROM sync_state
WHERE edge_node_id = @edge_node_id;

SELECT
    reading_id, sensor_id, recorded_at,
    temperature, pressure, humidity, row_version
FROM sensor_readings
WHERE row_version > @last_rv
ORDER BY row_version
OFFSET 0 ROWS FETCH NEXT 50000 ROWS ONLY;

The ROWVERSION type on SQL Server is particularly well-suited to this pattern because it is database-scoped, monotonically increasing, and updated automatically on every write — no trigger required. For tables without a rowversion column, a trigger-maintained modified_at timestamp is the fallback.

Configuration Tuning for Edge Hardware

Tuning a database for edge hardware is the inverse of tuning for a large server. On a 512 GB RAM enterprise server, you tune to exploit all available memory. On an edge node with 4 GB RAM running alongside an operating system, application code, and networking daemons, you tune to stay within your memory budget and to behave gracefully when that budget is under pressure.

For SQL Server on a 4 GB edge node, a conservative baseline configuration looks like this: max server memory = 2048MB (leave headroom for the OS and the container runtime), max degree of parallelism = 2, cost threshold for parallelism = 50, and small application connection pools (edge applications rarely need more than a dozen connections). Parallel query is valuable on large servers; on edge hardware, it competes with other processes for CPU time and does not deliver proportional benefit.

Log durability for edge reliability: keep the transaction log on the most reliable storage attached to the device and never trade durability knobs for write performance — on edge hardware where power can be interrupted without warning, losing committed transactions is unacceptable. Set the recovery interval modestly so crash recovery completes quickly when the device restarts.

For SQL Server (Azure SQL Edge), the equivalent tuning focuses on max server memory, which defaults to a value that will consume everything available. Set it explicitly. On a 4 GB node, setting max server memory (MB) = 2048 leaves room for the OS, the sync agent, and any other processes. Enable the Resource Governor if your workload mixes high-priority telemetry ingestion with lower-priority sync queries — this prevents batch sync operations from starving real-time writes.

Index and statistics maintenance on edge deployments needs explicit attention. Automatic maintenance is calibrated for servers with idle windows; on edge hardware, a rebuild firing at the wrong time spikes I/O and CPU, causing ingestion latency spikes visible in the telemetry data you are trying to collect. Schedule maintenance in known-idle windows and keep it lightweight — reorganize instead of rebuild where possible. For insert-only sensor tables, fragmentation is minimal; the main job is keeping statistics current so the optimizer doesn't choose nested loops over millions of rows.

-- Set memory ceiling for Azure SQL Edge instance
EXEC sp_configure 'show advanced options', 1;
RECONFIGURE;

EXEC sp_configure 'max server memory (MB)', 2048;
RECONFIGURE;

-- Set max degree of parallelism to limit CPU competition
EXEC sp_configure 'max degree of parallelism', 2;
RECONFIGURE;

-- Check current configuration values
SELECT
    name,
    value_in_use,
    description
FROM sys.configurations
WHERE name IN (
    'max server memory (MB)',
    'max degree of parallelism',
    'cost threshold for parallelism'
);

Disk I/O is often the hardest constraint on edge hardware. Industrial edge devices frequently use SD cards or eMMC storage for cost and power reasons. These have asymmetric read/write performance and limited write endurance. Placing SQL Server's transaction log on a separate storage device from the data files eliminates the I/O contention that causes most edge write latency issues. Even separating onto two partitions of the same physical device helps if the storage controller has independent queues per partition. The same separation of data files and log files applies on any engine.

Monitoring and Managing Databases You Cannot Directly Reach

Managing a database you cannot physically touch — and may not be able to connect to on demand — requires building observability into the system itself, rather than relying on someone being present to investigate. This is the operational discipline that separates production edge deployments from prototypes that happen to be running outside a data center.

The foundation is local metric collection that persists regardless of connectivity. Do not rely on a centralized monitoring system to pull metrics from edge nodes — if the node is offline, those metrics are lost. Instead, write database health metrics to a local table on the edge node, include those metrics in your regular sync batch, and import them into your central monitoring system when connectivity is available. This gives you a complete health picture even if the node was isolated for three days.

Key metrics to collect locally every minute include: active connection count, longest running query duration, replication backlog, index fragmentation from sys.dm_db_index_physical_stats, page life expectancy from sys.dm_os_performance_counters, and available disk space. Long-running sessions come from sys.dm_exec_requests, and instance-level counters from sys.dm_os_sys_info.

-- Local health metrics table on SQL Edge node
CREATE TABLE node_health_metrics (
    captured_at         DATETIME2       NOT NULL DEFAULT GETUTCDATE(),
    active_connections  SMALLINT,
    longest_query_sec   REAL,
    buffer_cache_ratio  REAL,
    pending_log_kb      BIGINT,
    free_disk_mb        INTEGER,
    synced_to_central   BIT             NOT NULL DEFAULT 0
);

-- Populate via SQL Server Agent job or external scheduler
INSERT INTO node_health_metrics (
    active_connections,
    longest_query_sec,
    buffer_cache_ratio,
    pending_log_kb
)
SELECT
    (SELECT COUNT(*) FROM sys.dm_exec_requests
     WHERE status = 'running'),
    (SELECT ISNULL(MAX(total_elapsed_time / 1000.0), 0)
     FROM sys.dm_exec_requests
     WHERE status = 'running'),
    (SELECT ROUND(cntr_value, 2)
     FROM sys.dm_os_performance_counters
     WHERE counter_name = 'Buffer cache hit ratio'
       AND object_name LIKE '%Buffer Manager%'),
    (SELECT SUM(cntr_value)
     FROM sys.dm_os_performance_counters
     WHERE counter_name = 'Log File(s) Used Size (KB)'
       AND instance_name NOT IN ('_Total', 'mssqlsystemresource'));

Alerting at the edge must be self-contained. A monitoring agent that sends alerts to a central system cannot alert you when the central connection is unavailable — precisely the situation where alerts are most needed. Build a local alert table and a local response mechanism. A simple pattern is a scheduled job that evaluates thresholds against node_health_metrics and writes records to a local node_alerts table. When connectivity resumes and metrics sync, the alerts sync with them. Pair this with a watchdog process on the edge device itself — outside the database — that monitors for conditions like disk full or database process crash, and can take local remediation actions such as dropping the oldest partition or restarting the service.

Remote administration, when connectivity is available, should happen over an encrypted tunnel. Direct database port exposure over a cellular or satellite WAN link is not acceptable. The standard pattern is a VPN (WireGuard is common in edge deployments for its low overhead and reliability) combined with a jump host. All DBA connections route through the jump host. Credentials are never stored on the edge device in plaintext; use certificate-based authentication — SQL Server's certificate-based logins, provisioned at deployment time.

Upgrade management for edge databases is its own discipline. You cannot roll out a SQL Server CU upgrade to hundreds of field devices the way you upgrade a cloud instance. The practical approach is to:

1. Build database upgrades into device firmware update packages, tested thoroughly in a lab with representative data volumes.

2. Stage rollouts across a small percentage of the fleet first, monitoring for failures before wider deployment.

3. Maintain a rollback package that can revert the database version if the upgrade fails.

4. Accept that some devices in the field will run older versions for longer than you would prefer, and ensure your sync protocol is version-tolerant.

For SQL Server Edge, in-place upgrades of the container image are the standard mechanism: pull the new image, recreate the container against the same persistent volume, and let crash recovery bring the databases online. For major version jumps, back up first — downgrading a container image does not downgrade the database files.

Security Considerations Specific to Edge

Edge nodes present a different threat model than data center servers. Physical access by unauthorized parties is a realistic possibility — a retail store database server in a back room, an industrial controller in an unlocked electrical cabinet. Encryption at rest is not optional in these environments.

On Linux edge devices, full disk encryption via LUKS (Linux Unified Key Setup) is the standard approach. Enable TDE on the SQL Server databases as well, so the data files stay encrypted even if the volume is detached from the device. The encryption key can be stored in a TPM (Trusted Platform Module) chip on the device, which binds decryption to that specific hardware and prevents drive removal attacks. Key rotation and TPM provisioning should be part of your device deployment runbook.

SQL Server Edge on Linux supports Transparent Data Encryption (TDE), which encrypts data files and backups at the storage layer without requiring application changes. Enable TDE during initial deployment, not after — enabling it on an existing database requires re-encrypting all data pages, which is I/O intensive and time-consuming on edge hardware.

-- Enable TDE on an Azure SQL Edge database
-- Step 1: Create master key in master database
USE master;
CREATE MASTER KEY ENCRYPTION BY PASSWORD = 'StrongPassphr@se1!';

-- Step 2: Create certificate protected by master key
CREATE CERTIFICATE EdgeNodeCert
    WITH SUBJECT = 'Edge Node TDE Certificate',
    EXPIRY_DATE = '2030-01-01';

-- Step 3: Create database encryption key in target database
USE EdgeSensorDB;
CREATE DATABASE ENCRYPTION KEY
    WITH ALGORITHM = AES_256
    ENCRYPTION BY SERVER CERTIFICATE EdgeNodeCert;

-- Step 4: Enable encryption
ALTER DATABASE EdgeSensorDB
    SET ENCRYPTION ON;

-- Verify encryption status
SELECT
    db.name,
    dek.encryption_state,
    dek.encryption_state_desc,
    dek.percent_complete,
    dek.key_algorithm,
    dek.key_length
FROM sys.dm_database_encryption_keys dek
JOIN sys.databases db ON db.database_id = dek.database_id;

Network-level security at the edge extends beyond VPN tunnels. The SQL Server instance should accept connections only from localhost and the VPN interface — disable all unnecessary protocols so only TCP/IP over the VPN interface is active, and disable the SQL Server Browser service. Prefer Windows or certificate authentication over SQL logins with passwords.

Audit logging at the edge is important, but log volume must be managed. Enable logging of connection attempts, privilege escalations, and DDL statements. Do not log every SELECT or INSERT — on a high-ingestion edge node, that will overwhelm disk I/O. SQL Server Audit configured to capture server-level events and DDL changes is the practical starting point; keep the audit target small and roll it aggressively so it never competes with telemetry for disk.

Handling Connectivity Loss Gracefully

Connectivity loss is not an exception in edge deployments — it is a normal operating condition. Your database architecture must accommodate it as a first-class concern rather than a rare failure mode.

The most important design pattern for handling disconnection is local-first operation. The edge database must be able to accept writes and serve reads without any connection to the central system. This sounds obvious, but it fails in practice when applications are designed to validate lookups against a central database, or when identity sequences are centrally coordinated, or when synchronous replication is configured so that the edge cannot commit without central acknowledgment.

Sequence management deserves specific attention. If both the edge database and the central database use a shared sequence for primary keys, disconnection makes that sequence unavailable. Use UUID primary keys generated locally (NEWSEQUENTIALID() for index-friendly UUIDs) or allocate sequence ranges to each edge node at deployment time. The range allocation approach — where edge node 47 uses IDs 47000000000 to 47999999999 — is simple and guarantees no collisions without any connectivity.

-- UUID primary key using NEWSEQUENTIALID for index efficiency
CREATE TABLE device_events (
    event_id        UNIQUEIDENTIFIER NOT NULL DEFAULT NEWSEQUENTIALID(),
    device_id       SMALLINT        NOT NULL,
    event_type      NVARCHAR(50)    NOT NULL,
    occurred_at     DATETIME2       NOT NULL DEFAULT GETUTCDATE(),
    payload         NVARCHAR(MAX),
    CONSTRAINT pk_device_events PRIMARY KEY (event_id)
);

-- Pre-allocated BIGINT range using SEQUENCE object
CREATE SEQUENCE dbo.device_events_seq
    AS BIGINT
    START WITH 4700000000000
    INCREMENT BY 1
    MINVALUE 4700000000000
    MAXVALUE 4799999999999
    NO CYCLE;

Application-level retry and queue behavior must also be designed for disconnection. When the edge application cannot reach the central API or message broker, it must buffer events locally. The edge database is a natural buffer. A local outbound queue table — rows written by the application, read by the sync process, deleted after confirmed central delivery — is more durable than an in-memory queue and survives process restarts and system reboots.

Backpressure management becomes important when the edge node reconnects after an extended outage. A node that was isolated for 72 hours may attempt to upload millions of rows to the central system simultaneously. If dozens of edge nodes reconnect at the same time — common after a network infrastructure outage — the central system faces a thundering herd problem. Build rate limiting into your sync process: upload a bounded batch, confirm receipt, wait a short interval, upload the next batch. This smooths reconnection load and prevents the central database from being overwhelmed.

Testing Edge Deployments in a Lab Environment

Testing edge database deployments requires simulating the conditions that make edge environments challenging: limited resources, intermittent connectivity, unexpected power loss, and hardware degradation. A deployment that works in ideal conditions but fails under realistic edge conditions is not production-ready.

Connectivity simulation can be done with Linux traffic control (tc) commands that add latency, limit bandwidth, and introduce packet loss between your test edge node and the central test system. Before validating your sync mechanism, establish a baseline with perfect connectivity, then repeat the tests with 500ms latency and 5% packet loss, then with complete connectivity blackouts of varying duration.

# Simulate 500ms latency and 5% packet loss on the sync interface
tc qdisc add dev eth0 root netem delay 500ms loss 5%

# Simulate complete outage
tc qdisc add dev eth0 root netem loss 100%

# Remove simulation
tc qdisc del dev eth0 root

Power loss simulation is harder to automate but essential. An edge database that loses power mid-write must recover cleanly on restart. Test this by literally cutting power to your test device at random intervals during a write-heavy load test. SQL Server's write-ahead logging guarantees crash recovery — never disable write-through behavior on edge hardware to chase write performance. After each simulated power loss, verify row counts, check for corruption with DBCC CHECKDB, and validate that the sync checkpoint is consistent.

Load testing at the hardware limits reveals where memory pressure or I/O saturation causes database behavior to change. Run an ingest load generator (HammerDB or a custom T-SQL loop) against your edge hardware at ingest rates that exceed your expected production peak by 50%. Watch for: buffer pool eviction causing physical reads to spike, automatic maintenance triggering during the peak and competing for I/O, log write latency growing until commit latency becomes user-visible. These failure modes in a lab are far preferable to discovering them on a device a thousand miles away.

Key Takeaways

  • → **Edge databases operate under four distinct pressures** that data center assumptions cannot address: unreliable connectivity, hardware constraints, limited physical access, and dependency on a central system of record. Every architectural decision must account for all four simultaneously.
  • → **Schema design for the edge prioritizes storage efficiency and write throughput** over query flexibility. Time-partitioned tables, minimal indexes, appropriate data types, and compression (columnstore and page compression for SQL Server) are the primary tools for staying within constrained disk and I/O budgets.
  • → **Synchronization strategy is the most complex aspect of edge database architecture.** The simplest correct approach is partition ownership — define at design time which system owns each table, eliminating the possibility of write conflicts. When bidirectional ownership of the same data is unavoidable, checkpoint-based polling with `ROWVERSION` or trigger-maintained `modified_at` timestamps is more robust during extended outages than replication slot-based approaches.
  • → **Local-first operation must be a hard requirement**, not an aspiration. UUID or range-allocated primary keys, local outbound queue tables, and architectures that never require central connectivity for a commit to succeed are the building blocks of a genuinely resilient edge deployment.
  • → **Observability and security require edge-specific design.** Metrics must persist locally and sync to central monitoring, not depend on continuous connectivity to a remote collector. Encryption at rest (LUKS or TDE), certificate-based authentication, and restricted network access are baseline requirements when physical security of the device cannot be guaranteed.
