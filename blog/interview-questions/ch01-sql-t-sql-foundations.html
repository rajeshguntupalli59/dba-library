Chapter 1: SQL & T-SQL Foundations

Every interview starts with the foundations: what SQL Server is, how data is stored, and how to ask for it with T-SQL. This chapter covers instances, databases, basic queries, filtering, sorting, NULL handling, data types, and script structure. If these ideas are solid, the harder topics in later chapters are much easier to explain.

In this chapter:

  • →Clustered indexes vs primary keys, databases vs schemas, and instances
  • →System databases and what each one is used for
  • →SELECT and SELECT * pitfalls, the transaction log, and the error log
  • →TOP, DISTINCT, and OFFSET/FETCH for limiting and paging results
  • →NULL behavior, CASE expressions, and common data types
  • →Moving a database to another server

    • Key learning: SQL Server is the database engine, SQL is the language for working with data, and T-SQL is the dialect SQL Server uses. A solid grasp of SELECT, filtering, sorting, NULL, and data types lets you read and explain almost any basic query with confidence.

    Q1. What is the difference between a clustered index and a primary key? Can a primary key be nonclustered?

    Answer: A primary key is a logical constraint: it says one column, or a set of columns, uniquely identifies each row and cannot be NULL. A clustered index is a physical structure: it defines the order in which the table's rows are stored, with the data itself at the leaf level. They are independent ideas, and a table can have one of each, one without the other, or neither.

    By default, creating a primary key also creates a clustered index on that key, which is why the two are confused. But you can separate them: create the primary key as NONCLUSTERED and put the clustered index on the column your queries actually range-filter, such as an order date. A common pattern is a nonclustered primary key on a narrow surrogate key and a clustered index on the date column, so range scans read sequentially instead of jumping around. A table can also have a clustered index with no primary key at all.

    CREATE TABLE dbo.Orders
(
    OrderID INT NOT NULL,
    OrderDate DATE NOT NULL,
    CustomerID INT NOT NULL,
    TotalAmount DECIMAL(12, 2) NOT NULL,
    CONSTRAINT PK_Orders PRIMARY KEY NONCLUSTERED (OrderID)
);

-- Clustered index on the column queries range-filter, not on the key
CREATE CLUSTERED INDEX IX_Orders_OrderDate
    ON dbo.Orders (OrderDate);

    Key learning: A primary key is a uniqueness rule and a clustered index is a storage order; they are independent, so a primary key can be nonclustered while the clustered index sits on the column queries filter by range.

    Q2. What is a SQL Server instance, and what is the difference between a default instance and a named instance?

    Answer: A SQL Server instance is one installation of the SQL Server database engine on a server. Each instance has its own services, system databases, configuration, logins, and memory settings. It behaves like an independent SQL Server, even when it shares hardware with other instances.

    A default instance is the unnamed instance on a machine. You connect to it with just the server name, and there can be only one default instance per machine. Its service name is MSSQLSERVER. A named instance has a name you choose at install time, you connect to it as ServerName\InstanceName, and you can run several named instances on the same machine. Each named instance has its own service name in the form MSSQL$InstanceName.

    SELECT @@SERVERNAME AS ServerName,
       @@SERVICENAME AS InstanceName;

    Key learning: An instance is one independent installation of the engine, a default instance is addressed by server name alone, and a named instance is addressed by server name plus instance name.

    Q3. What is the difference between a database and a schema?

    Answer: A database is the container and the boundary: it has its own files, its own transaction log, its own recovery model, and its own backup and restore. Security, backup, and most day-to-day work stop at the database boundary. An instance can hold many databases, and a query that crosses databases needs a three-part name such as OtherDB.dbo.Orders.

    A schema is a namespace inside one database. Every object has a two-part name such as Sales.Orders, and the default schema is dbo. Schemas organize objects by business area, so Sales, HR, and Reporting can each own their tables without name collisions, and they are also a security boundary: you can grant permissions once at the schema level instead of object by object. A user has a default schema that SQL Server uses when a query omits the schema name, which is why fully qualifying names is a good habit.

    CREATE SCHEMA Sales AUTHORIZATION dbo;
GO
CREATE TABLE Sales.Orders
(
    OrderID INT PRIMARY KEY,
    OrderDate DATE NOT NULL,
    Amount DECIMAL(10, 2) NOT NULL
);
GO
-- Grant once at the schema level, not object by object
GRANT SELECT ON SCHEMA::Sales TO AppUser;

    Key learning: A database is the container with its own files, log, and backups, while a schema is a namespace inside a database that organizes objects and carries permissions.

    Q4. What is a database, and what are the SQL Server system databases?

    Answer: A database is a container for related data and the objects that describe it, such as tables, views, indexes, stored procedures, and functions. Physically, a database is stored in at least one data file and one transaction log file. Logically, it is the boundary for security, backup, recovery, and most day-to-day work.

    SQL Server ships with five system databases. The master database holds instance-wide information, including logins, configuration, and the list of all databases. The model database is the template copied for every new database. The msdb database stores SQL Server Agent jobs, backup history, and related automation data. The tempdb database holds temporary tables, table variables, intermediate query results, and the version store, and it is recreated each time SQL Server starts. The resource database is a hidden, read-only database that holds the definitions of system objects and cannot be modified directly.

    SELECT name, database_id, create_date
FROM sys.databases
ORDER BY name;

    Key learning: A database is a container for tables and related objects, and the system databases master, model, msdb, tempdb, and resource support the instance itself.

    Q5. What does a basic SELECT statement do, what does SELECT * return, and why should you avoid it?

    Answer: A SELECT statement reads data from one or more tables and returns it as a result set. In its simplest form you list the columns you want and the table to read them from. Without an ORDER BY clause, SQL Server does not guarantee the order of the returned rows.

    SELECT * returns every column in the table, in the order the columns were defined. Avoid it in production code and interview answers for four reasons. It returns columns you do not need, which wastes I/O and network traffic. It can prevent the use of a narrow covering index. It breaks or changes behavior when columns are added, removed, or reordered. It also hides intent, so a reader cannot tell which columns the query actually needs. List only the columns you need.

    SELECT EmployeeID, FirstName, LastName, HireDate
FROM Employees;

    Key learning: SELECT reads data into a result set, SELECT * returns every column, and listing only needed columns is faster, safer, and clearer.

    Q6. What is the transaction log, and why does every database need one?

    Answer: The transaction log is the sequential record of every change made to a database, and every database has one. Before SQL Server writes a changed data page to disk, it first writes the change to the log, which is called write-ahead logging. That ordering is what makes a committed transaction durable: if the server crashes, SQL Server replays the log during recovery to redo committed work and roll back uncommitted work.

    The log does more than crash recovery. It is the source for point-in-time restores, for log shipping, for transactional replication, and for Availability Group synchronization, all of which read log records and apply them elsewhere. The log is divided into virtual log files that get reused once their records are no longer needed, and what makes them reusable depends on the recovery model: in SIMPLE it is the checkpoint, in FULL it is a log backup. Never delete a log file or shrink the log as a routine fix, because a log that cannot grow stops all writes with error 9002.

    -- What is blocking log reuse right now?
SELECT name, recovery_model_desc, log_reuse_wait_desc
FROM sys.databases
WHERE name = 'SalesDB';

-- How big is the log, and how fast is it growing?
SELECT name, size * 8 / 1024 AS SizeMB, growth, is_percent_growth
FROM sys.master_files
WHERE database_id = DB_ID('SalesDB')
  AND type = 1;

    Key learning: The transaction log records every change before the data page is written, which makes committed work durable and powers recovery, point-in-time restores, replication, and Availability Groups.

    Q7. Where is the SQL Server error log, and what do you check in it first?

    Answer: The SQL Server error log is the text log where the engine records startup, errors, warnings, login failures, backups, restores, and Availability Group events. It lives in the instance log folder, by default under the SQL Server install path in MSSQL\Log, in a file named ERRORLOG, with older copies kept as ERRORLOG.1, ERRORLOG.2, and so on. You can read it in SQL Server Management Studio under Management, SQL Server Logs, or with xp_readerrorlog, which also lets you filter by text and date.

    When something goes wrong, check the error log before guessing. First look for startup errors and the recovery messages that say which databases came online. Then look for login failures, error 18456, and read the state code, because the state tells you whether the login does not exist, the password is wrong, or the login is disabled. Then look for IO errors 823, 824, and 825, which point to storage, and for corruption messages from CHECKDB. Cycle the log regularly with sp_cycle_errorlog so one file does not grow for months, and keep at least seven archived copies so a problem from last week is still readable.

    -- Read the current error log, filtered to login failures
EXEC xp_readerrorlog 0, 1, N'Login failed';

-- Read the current error log, filtered to IO errors
EXEC xp_readerrorlog 0, 1, N'823';

-- Cycle the log so a new file starts (keep old copies)
EXEC sp_cycle_errorlog;

    Key learning: The error log records startup, login failures, IO errors, and recovery, so read it before guessing, and cycle it regularly so history stays available.

    Q8. What do TOP, DISTINCT, and OFFSET/FETCH do, and when would you use each one?

    Answer: TOP limits how many rows are returned. TOP 10 returns the first ten rows, and TOP 10 PERCENT returns the first ten percent of rows. Always use TOP with ORDER BY, because without it the rows returned are not predictable. TOP WITH TIES also returns extra rows that tie with the last row on the ORDER BY values.

    DISTINCT removes duplicate rows from the result set. It considers the full combination of listed columns, so two rows are duplicates only when every listed column matches. OFFSET/FETCH is the paging syntax: OFFSET skips a number of rows and FETCH NEXT returns the next page. It requires ORDER BY and is the standard way to page results a page at a time.

    SELECT TOP 10 EmployeeID, FirstName, LastName
FROM Employees
ORDER BY HireDate DESC;

SELECT DISTINCT City
FROM Customers
ORDER BY City;

SELECT OrderID, OrderDate, TotalAmount
FROM Orders
ORDER BY OrderDate DESC
OFFSET 10 ROWS FETCH NEXT 10 ROWS ONLY;

    Key learning: TOP limits rows, DISTINCT removes duplicates, and OFFSET with FETCH pages through an ordered result set.

    Q9. What is NULL, and how does it behave in comparisons and arithmetic?

    Answer: NULL means unknown or missing, not zero and not an empty string. A NULL salary does not mean the salary is zero. It means the value is not known or was not supplied. That distinction drives all NULL behavior in SQL Server.

    Comparisons with NULL use three-valued logic: true, false, and unknown. The expression Salary = NULL never returns true, it returns unknown, so the row is filtered out by WHERE. Use IS NULL to test for NULL and IS NOT NULL to test for a value. Arithmetic with NULL also returns NULL, so 10 + NULL is NULL, and string concatenation with + and a NULL operand returns NULL. Aggregate functions ignore NULL values, except COUNT(*) which counts rows.

    SELECT EmployeeID, FirstName, LastName
FROM Employees
WHERE ManagerID IS NULL;

SELECT 10 + NULL AS Result,
       'Name: ' + NULL AS Concatenated;

    Key learning: NULL means unknown, so test it with IS NULL or IS NOT NULL because ordinary comparisons and arithmetic with NULL return unknown or NULL.

    Q10. What is a CASE expression, and what is the difference between simple CASE and searched CASE?

    Answer: CASE is an expression, not a statement, so it returns a single value and can be used in the SELECT list, WHERE clause, ORDER BY clause, and other places where a value is allowed. It evaluates conditions in order and returns the value for the first condition that is true. If no condition matches, it returns the ELSE value, or NULL when there is no ELSE clause. Every CASE must end with END.

    A simple CASE compares one expression with a list of values. A searched CASE evaluates a separate Boolean condition in each WHEN clause, which makes it more flexible because each condition can test different columns and operators. Use simple CASE for equality checks against one column and searched CASE for ranges, multiple columns, or mixed conditions.

    SELECT EmployeeID,
       CASE Department
           WHEN 'Sales' THEN 'Sales team'
           WHEN 'HR' THEN 'People team'
           ELSE 'Other team'
       END AS TeamLabel,
       CASE
           WHEN Salary >= 80000 THEN 'Senior band'
           WHEN Salary >= 50000 THEN 'Mid band'
           ELSE 'Entry band'
       END AS SalaryBand
FROM Employees;

    Key learning: CASE returns one value from the first matching condition, simple CASE compares one expression to values, and searched CASE tests separate conditions in each WHEN clause.

    Q11. What are the common SQL Server data types, including INT, VARCHAR versus NVARCHAR, DATETIME2, DECIMAL, BIT, and UNIQUEIDENTIFIER?

    Answer: INT is a 4-byte whole number from about negative 2.1 billion to positive 2.1 billion and is the usual choice for counts and identifier columns that do not need a larger range. DECIMAL(p, s) is an exact fixed-precision number where p is the total digits and s is the digits after the decimal point, so DECIMAL(10, 2) is a good choice for money. BIT holds 0, 1, or NULL and is used for true or false flags.

    VARCHAR(n) stores variable-length non-Unicode text using one byte per character, while NVARCHAR(n) stores Unicode text using two bytes per character and can hold characters from any language. Use NVARCHAR when the data can contain non-English text, and prefix Unicode string literals with N, as in N'Mumbai'. DATETIME2 is the preferred date and time type, with a range from year 1 to year 9999 and precision up to 100 nanoseconds. UNIQUEIDENTIFIER holds a 16-byte globally unique identifier, or GUID, often generated with NEWID() when a globally unique key is needed.

    CREATE TABLE Products
(
    ProductID   INT PRIMARY KEY,
    ProductName NVARCHAR(100) NOT NULL,
    Description VARCHAR(500) NULL,
    Price       DECIMAL(10, 2) NOT NULL,
    IsActive    BIT NOT NULL,
    CreatedOn   DATETIME2(3) NOT NULL,
    RowGuid     UNIQUEIDENTIFIER NOT NULL DEFAULT NEWID()
);

    Key learning: Choose the type that matches the data, using INT for whole numbers, DECIMAL for exact money, NVARCHAR for Unicode text, DATETIME2 for dates and times, BIT for flags, and UNIQUEIDENTIFIER for GUID values.

    Q12. How do you move a database to another server: detach/attach versus backup/restore?

    Answer: Backup and restore is the standard way to move a database. Take a full backup on the source, copy the file to the target, and restore it with MOVE to place the data and log files in their new locations. It keeps the backup chain intact, the source stays online and untouched, and you can rehearse the move as many times as you like. After the restore, fix the things that do not travel with the backup: orphaned users, because logins are mapped by SID, and Agent jobs, which live in msdb on the source.

    Detach and attach is the alternative: sp_detach_db takes the database offline and releases its files, you copy the data and log files, then CREATE DATABASE ... FOR ATTACH on the target. It is faster for very large databases because there is no backup and restore pass, but the database is offline from the detach until the attach completes, and if the copy fails mid-move you have no database and no fresh backup unless you took one first. Never copy database files while SQL Server is running. For minimal downtime, neither method is the answer: use log shipping or replication to keep the target in sync and cut over.

    -- Preferred: backup on the source, restore on the target
BACKUP DATABASE SalesDB
TO DISK = 'E:\Backups\SalesDB.bak' WITH INIT;

-- On the target, place the files in their new locations
RESTORE DATABASE SalesDB
FROM DISK = 'E:\Backups\SalesDB.bak'
WITH MOVE 'SalesDB' TO 'D:\Data\SalesDB.mdf',
     MOVE 'SalesDB_log' TO 'L:\Logs\SalesDB.ldf',
     RECOVERY;

-- Alternative: detach on the source, attach on the target
EXEC sp_detach_db 'SalesDB';
-- Copy the .mdf and .ldf files, then on the target:
CREATE DATABASE SalesDB
ON (FILENAME = 'D:\Data\SalesDB.mdf'),
   (FILENAME = 'L:\Logs\SalesDB.ldf')
FOR ATTACH;

    Key learning: Move a database with backup and restore for safety and rehearsal, use detach and attach only when speed matters and a backup exists, and fix orphaned users and Agent jobs after either method.
