Chapter 17: Backup, Restore, Corruption & RTO/RPO

Backups only matter if restores work under pressure. This chapter covers how SQL Server protects data, how to bring it back, and how to prove the plan works before a real failure. It also covers corruption detection and the recovery choices when a bad data change is already committed.

Regular restore tests on a separate machine prove the backups are usable and give real RTO and RPO numbers. When corruption or a bad committed change happens, protect the fallback copy first and restore to a second copy before you touch production.

    Q181. What are the differences between the SIMPLE, FULL, and BULK_LOGGED recovery models, and how do you choose between them?

    Answer: The recovery model controls how the transaction log is managed and whether point-in-time recovery is possible. It is a database setting, not a server setting, and it decides what you can restore after a failure.

  • →SIMPLE: The log is truncated at each checkpoint, so you can only restore to the last full or differential backup. There are no log backups and no point-in-time restore. Use it for development, test, or data you can rebuild.
  • →FULL: The log is kept until a log backup runs, so you can restore to any point in time up to the last log backup. Use it for production data where data loss must be small. Log backups must run on schedule or the log will grow.
  • →BULK_LOGGED: Like FULL, but minimally logged bulk operations are not fully logged, so point-in-time restore is limited if a bulk operation is in the log interval. Use it temporarily for large bulk loads, then switch back to FULL and take a log backup.

    • Choose FULL when the business cannot accept losing work since the last backup. Choose SIMPLE only when losing that work is acceptable and documented. Always take a full backup after switching from SIMPLE to FULL, because the log chain starts at that point.

    SELECT name, recovery_model_desc
FROM sys.databases
WHERE name = 'SalesDB';

ALTER DATABASE SalesDB SET RECOVERY FULL;

    Key learning: The recovery model decides whether point-in-time restore is possible, so choose FULL for production data you cannot afford to lose and SIMPLE only when losing work since the last backup is acceptable.

    Q182. What are full, differential, and transaction log backups, and when do you use COPY_ONLY and backup compression?

    Answer: A full backup copies the whole database and anchors the restore chain. A differential backup copies only the extents changed since the last full backup, so it is usually smaller and faster than another full backup. A transaction log backup copies the log records since the last log backup and, in the FULL recovery model, makes point-in-time restore possible and allows log truncation.

    COPY_ONLY takes a full or log backup that does not break the normal backup chain. Use it for an ad hoc copy for development, testing, or migration, when you do not want to reset the differential base or interrupt the log chain. A COPY_ONLY log backup does not truncate the log, so the regular log backup schedule still controls log reuse.

    Backup compression shrinks backup files and usually shortens backup time by reducing IO, at the cost of extra CPU. It is a good default for most systems unless CPU is already saturated. SQL Server 2025 adds ZSTD as a backup compression algorithm, which compresses faster and smaller than the older MS_XPRESS algorithm, so it is worth testing on large backups. Always test restore time with compression on, and confirm the backup destination has enough space for the uncompressed size during a restore.

    BACKUP DATABASE SalesDB
TO DISK = 'D:\Backups\SalesDB_Full.bak'
WITH COMPRESSION, INIT, NAME = 'SalesDB Full Backup';

BACKUP DATABASE SalesDB
TO DISK = 'D:\Backups\SalesDB_Diff.bak'
WITH DIFFERENTIAL, COMPRESSION;

BACKUP LOG SalesDB
TO DISK = 'D:\Backups\SalesDB_Log.trn'
WITH COMPRESSION;

BACKUP DATABASE SalesDB
TO DISK = 'D:\Backups\SalesDB_CopyOnly.bak'
WITH COPY_ONLY, COMPRESSION;

    Key learning: Full backups anchor the chain, differential backups shorten restores, log backups enable point-in-time recovery, and COPY_ONLY protects that chain when you need an extra copy.

    Q183. What are RTO and RPO, and how do you measure and test them?

    Answer: RTO, or recovery time objective, is the maximum time allowed to restore service after a failure. RPO, or recovery point objective, is the maximum amount of data loss allowed, measured in time. For example, an RPO of 15 minutes means the business accepts losing up to the last 15 minutes of work, so log backups must run at least that often.

    Measure RPO from the backup schedule and the last restorable point. If log backups run every 15 minutes and the tail-log backup succeeds, the achievable RPO is close to zero. If log backups run hourly, the RPO cannot be better than one hour. Measure RTO by timing a real restore, including copying files, restoring the chain, running CHECKDB, fixing logins and jobs, and completing an application smoke test.

    Test both with scheduled restore drills on a separate machine. Record start and finish times for each step, compare them with the agreed targets, and fix gaps in backup frequency, restore scripts, permissions, or storage speed. Targets that have never been timed are guesses, not guarantees.

    SELECT database_name, type, backup_start_date, backup_finish_date,
    DATEDIFF(SECOND, backup_start_date, backup_finish_date) AS duration_seconds
FROM msdb.dbo.backupset
WHERE database_name = 'SalesDB'
ORDER BY backup_start_date DESC;

    Key learning: RTO is how long recovery may take and RPO is how much data loss is acceptable, and both must be proven by timed restore tests rather than assumed from backup jobs.

    Q184. What is the correct restore sequence for full, differential, and log backups, and when do you use NORECOVERY, RECOVERY, and STANDBY?

    Answer: Restore in this order: the full backup, then the latest differential backup taken after that full backup, then the transaction log backups in sequence. Older differentials are not needed once a newer differential is restored. Every step except the last uses NORECOVERY, which leaves the database in a restoring state so more backups can be applied.

    RECOVERY is used only on the final step. It rolls back uncommitted transactions and brings the database online. Once RECOVERY is used, no more backups can be applied to that restore chain. If you use RECOVERY too early, you must start the restore again from the full backup.

    STANDBY brings the database online in read-only mode with an undo file, so you can query it between log restores. It is used mainly for log shipping secondaries and for checking data during a staged restore. It adds overhead and requires managing the undo file, so do not use it for a normal disaster recovery restore.

    RESTORE DATABASE SalesDB
FROM DISK = 'D:\Backups\SalesDB_Full.bak'
WITH NORECOVERY;

RESTORE DATABASE SalesDB
FROM DISK = 'D:\Backups\SalesDB_Diff.bak'
WITH NORECOVERY;

RESTORE LOG SalesDB
FROM DISK = 'D:\Backups\SalesDB_Log1.trn'
WITH NORECOVERY;

RESTORE LOG SalesDB
FROM DISK = 'D:\Backups\SalesDB_Log2.trn'
WITH RECOVERY;

    Key learning: Restore the full backup, then the latest differential, then the log backups in order with NORECOVERY until the final step uses RECOVERY to bring the database online.

    Q185. How do you perform a point-in-time restore with STOPAT, and why do you take a tail-log backup first?

    Answer: A point-in-time restore replays the backup chain and stops at a chosen time, mark, or log sequence number. In the FULL recovery model you restore the full backup and any differential with NORECOVERY, then restore the log backups with STOPAT set to just before the bad change. The final log restore uses RECOVERY so the database comes online at that point.

    Take a tail-log backup first to capture the log records written since the last scheduled log backup. Without it, you lose all work after that backup, and you may not be able to reach the exact STOPAT time. Use NORECOVERY for the tail-log backup when the database is damaged or must stay in a restoring state, and confirm the backup file is valid before you start restoring.

    Get the STOPAT time right. Confirm the time zone, the server clock, and the exact commit time of the bad change from the application log or the transaction log history. Stopping too early loses good work, and stopping too late brings the bad change back, so restore to a second copy first when the exact time is uncertain.

    BACKUP LOG SalesDB
TO DISK = 'D:\Backups\SalesDB_Tail.trn'
WITH NORECOVERY;

RESTORE DATABASE SalesDB
FROM DISK = 'D:\Backups\SalesDB_Full.bak'
WITH NORECOVERY;

RESTORE LOG SalesDB
FROM DISK = 'D:\Backups\SalesDB_Log.trn'
WITH RECOVERY, STOPAT = '2026-11-17T10:15:00';

    Key learning: Take a tail-log backup first to capture the log up to the failure, then restore the chain with STOPAT to stop just before the bad change.

    Q186. What is the difference between RESTORE VERIFYONLY and an actual restore test, and how do you run a clean-machine restore drill?

    Answer: RESTORE VERIFYONLY checks that a backup file is readable, that the header is complete, and that checksums validate if they were written. It does not restore any data, does not check that the database is consistent, and does not prove that the restore will succeed on the target server. It is a quick sanity check, not a recovery test.

    An actual restore test restores the full chain to a database, runs DBCC CHECKDB, and confirms the application can connect and read expected data. It proves the backup files, the restore scripts, the file paths, the permissions, and the available disk space all work together. It also gives a real RTO measurement.

    A clean-machine drill runs that test on a separate server with no dependence on production disks, shares, or credentials. Restore from the offsite or copied backup files, use MOVE to place files on the test server, run CHECKDB, run a smoke test, and time every step. Document what failed, fix the runbook, and repeat on a schedule so the drill stays current as the database grows.

    RESTORE VERIFYONLY
FROM DISK = 'D:\Backups\SalesDB_Full.bak';

RESTORE DATABASE SalesDB_Test
FROM DISK = 'D:\Backups\SalesDB_Full.bak'
WITH MOVE 'SalesDB' TO 'D:\Test\SalesDB_Test.mdf',
     MOVE 'SalesDB_log' TO 'D:\Test\SalesDB_Test.ldf',
     RECOVERY;

DBCC CHECKDB ('SalesDB_Test') WITH NO_INFOMSGS;

    Key learning: RESTORE VERIFYONLY only checks that a backup is readable while a real restore on a clean machine proves the backup, the restore steps, and the recovery time all work.

    Q187. What are page restore and piecemeal restore, and when do you use each one?

    Answer: Page restore repairs a small number of damaged pages without restoring the whole database. It works in the FULL and BULK_LOGGED recovery models, restores the listed pages from a full backup, and then applies log backups to bring those pages current. The database can stay online for unaffected data, although the damaged pages stay offline until the restore finishes. It is the right choice when CHECKDB or suspect_pages shows only a few bad pages and the rest of the database is healthy.

    Piecemeal restore restores a database in stages by filegroup. You restore the PRIMARY filegroup first with the PARTIAL option, bring the database online, and restore the remaining filegroups later. The data in unrestored filegroups stays offline, but the core tables are available sooner. It is the right choice for very large databases where a full restore would take too long and only part of the data is needed urgently.

    Both methods need a valid backup chain and careful planning. Page restore is not a fix for widespread corruption, and piecemeal restore needs a filegroup design that puts urgent tables in the first filegroup. For large-scale damage, a full restore to a second copy is usually safer and simpler.

    RESTORE DATABASE SalesDB PAGE = '1:234'
FROM DISK = 'D:\Backups\SalesDB_Full.bak'
WITH NORECOVERY;

RESTORE LOG SalesDB
FROM DISK = 'D:\Backups\SalesDB_Log.trn'
WITH RECOVERY;

RESTORE DATABASE SalesDB FILEGROUP = 'PRIMARY'
FROM DISK = 'D:\Backups\SalesDB_Full.bak'
WITH PARTIAL, NORECOVERY;

    Key learning: Page restore fixes a small number of damaged pages without a full restore while piecemeal restore brings the primary filegroup online first and restores the remaining filegroups later.

    Q188. What does DBCC CHECKDB check, what options does it offer, and what are the risks of REPAIR_ALLOW_DATA_LOSS?

    Answer: DBCC CHECKDB checks the logical and physical integrity of a database. It runs CHECKALLOC for allocation structures, CHECKTABLE for tables and indexes, and CHECKCATALOG for system catalog consistency. It finds torn pages, bad pointers, broken index links, and allocation errors that normal queries may not surface until they hit the damaged pages.

    Common options include PHYSICAL_ONLY for a faster check of page headers and allocation without full logical checks, NOINDEX to skip nonclustered indexes, NO_INFOMSGS to reduce output, ALL_ERRORMSGS to show every error, and MAXDOP to limit parallelism. PHYSICAL_ONLY is useful for a quick daily check, but a full CHECKDB is still needed on a regular schedule. Run CHECKDB against a restored copy or a secondary when the production impact is too high, and always capture the output.

    Repair levels are REPAIR_FAST for minor fixes, REPAIR_REBUILD for repairs without data loss, and REPAIR_ALLOW_DATA_LOSS for repairs that may deallocate damaged pages and delete rows. REPAIR_ALLOW_DATA_LOSS can silently remove data, break referential integrity, and leave the database logically inconsistent even though CHECKDB then passes. It requires single-user mode, must never be the first response, and should only follow a backup of the damaged database and a failed attempt to restore from a good backup.

    DBCC CHECKDB ('SalesDB') WITH NO_INFOMSGS, ALL_ERRORMSGS;

DBCC CHECKDB ('SalesDB') WITH PHYSICAL_ONLY, NO_INFOMSGS;

ALTER DATABASE SalesDB SET SINGLE_USER WITH ROLLBACK IMMEDIATE;
DBCC CHECKDB ('SalesDB', REPAIR_ALLOW_DATA_LOSS);
ALTER DATABASE SalesDB SET MULTI_USER;

    Key learning: DBCC CHECKDB is the integrity check to run regularly, and REPAIR_ALLOW_DATA_LOSS is a last resort that can delete data and should never replace a restore from a good backup.

    Q189. What causes database corruption, how do you detect it through suspect pages and errors 823 and 824, and what are the response steps?

    Answer: Corruption is usually caused by the storage layer, not by SQL Server alone. Common causes are failing disks, faulty controllers, firmware or driver bugs, bad memory, power loss during a write, and torn pages where only part of a page reaches disk. It can also follow an unsafe shutdown or a storage snapshot taken without database coordination.

    Detection starts with the error log and alerts. Error 823 is a severe IO error from the operating system during a read or write. Error 824 is a logical consistency error, such as a bad checksum or torn page, found when SQL Server reads a page. Error 825 is a read-retry warning that often predicts a future 823 or 824. The suspect_pages table in msdb records pages that failed, and DBCC CHECKDB confirms the scope of the damage.

    Respond in order: preserve evidence, check storage health, and confirm the backup chain before you change anything. Capture the error log entries and CHECKDB output, ask the storage team to check disks and controllers, and check whether the same pages fail on a restored copy. Restore the damaged pages or the full database from a good backup, run CHECKDB after the restore, and do not run repair until restore has been ruled out. Keep the damaged files until the recovery is verified.

    SELECT database_id, file_id, page_id, event_type, error_count, last_update_date
FROM msdb.dbo.suspect_pages
WHERE database_id = DB_ID('SalesDB');

DBCC CHECKDB ('SalesDB') WITH NO_INFOMSGS;

    Key learning: Treat errors 823 and 824 and entries in suspect_pages as urgent corruption signals, preserve evidence and backups first, and restore from a good backup before considering repair.

    Q190. Scenario: A DELETE has already been committed by mistake. What are your recovery options?

    Answer: First, stop further writes to the affected table and confirm the exact commit time, the statement used, the login, and how many rows were deleted, because the recovery target and the safest path depend on those facts. Tell the application owners what happened, freeze related jobs that might overwrite the evidence, and take a tail-log backup plus a full backup of the current state so you keep a fallback.

    A committed DELETE cannot be rolled back, so recovery means restoring the deleted rows from a backup. The standard path is a point-in-time restore to a second copy of the database, stopped just before the DELETE. Restore the full backup, the differential, and the logs with STOPAT to the new database name, then verify row counts, check related tables and foreign keys, and confirm the recovered rows match what was lost.

    Only after verification, copy the recovered rows back into production or swap the databases during a maintenance window, and re-check counts and application behavior. Never restore on top of production without a fallback, because a wrong STOPAT time or a bad backup chain would destroy the current data as well. If the database uses temporal tables, change data capture, or a reporting replica, check those sources first, as they may give a faster row-level recovery without a full restore.

    RESTORE DATABASE SalesDB_Recovery
FROM DISK = 'D:\Backups\SalesDB_Full.bak'
WITH MOVE 'SalesDB' TO 'D:\Recovery\SalesDB_Recovery.mdf',
     MOVE 'SalesDB_log' TO 'D:\Recovery\SalesDB_Recovery.ldf',
     NORECOVERY;

RESTORE LOG SalesDB_Recovery
FROM DISK = 'D:\Backups\SalesDB_Log.trn'
WITH RECOVERY, STOPAT = '2026-11-17T10:15:00';

    Key learning: After a committed DELETE, restore to a second copy to a point before the change, verify the recovered data, and only then move it back without ever overwriting production without a fallback.
