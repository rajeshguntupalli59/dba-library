Chapter 19: Advanced & Emerging Topics

The last chapter covers the features that separate a senior DBA from a mid-level one: the specialist engine features that solve narrow problems very well, the maintenance and integration tools that real shops run every day, and the newest capabilities that 2025–26 interviews are starting to ask about. None of these is a daily task for most DBAs, which is exactly why interviewers ask about them: they show whether you keep up with the platform instead of only the features you already use.

    Q201. What is In-Memory OLTP, and when should you use memory-optimized tables?

    Answer: In-Memory OLTP is SQL Server's engine for tables that live in memory instead of on disk. A memory-optimized table stores its rows in memory with latch-free, lock-free structures and hash or nonclustered indexes, so high-volume point lookups and short transactions run far faster than on a disk-based table. Natively compiled stored procedures are compiled to machine code at creation time and run against these tables without the usual interpretation overhead. You need a MEMORY_OPTIMIZED_DATA filegroup on the database before you can create one.

    The use case is narrow: high-throughput OLTP with many short transactions, such as session state, shopping carts, and staging tables for high-speed ingestion. Durability is a choice: SCHEMA_AND_DATA keeps the data through a restart by writing it to the filegroup, while SCHEMA_ONLY keeps only the structure and loses the rows, which is right for scratch data. The limits are what interviewers test: no foreign keys, no triggers, no CHECK constraints, a maximum row size of 8,060 bytes, character indexes that need a BIN2 collation, and poor performance for full scans and reporting. If the workload is mostly scans and aggregations, a disk-based table with a columnstore index is the better answer.

    -- The database needs a memory-optimized filegroup first
ALTER DATABASE SalesDB
ADD FILEGROUP SalesDB_mod CONTAINS MEMORY_OPTIMIZED_DATA;

ALTER DATABASE SalesDB
ADD FILE (NAME = 'SalesDB_mod', FILENAME = 'D:\Data\SalesDB_mod')
TO FILEGROUP SalesDB_mod;

-- A memory-optimized table for high-volume session state
CREATE TABLE dbo.SessionState
(
    SessionID UNIQUEIDENTIFIER NOT NULL PRIMARY KEY NONCLUSTERED HASH WITH (BUCKET_COUNT = 1000000),
    UserID INT NOT NULL,
    CreatedAt DATETIME2 NOT NULL,
    Payload NVARCHAR(1000) NOT NULL,
    INDEX IX_SessionState_UserID NONCLUSTERED (UserID)
)
WITH (MEMORY_OPTIMIZED = ON, DURABILITY = SCHEMA_AND_DATA);

    Key learning: In-Memory OLTP keeps tables in memory with latch-free structures for high-volume short transactions, and it is the wrong tool for scans, reporting, and tables that need foreign keys or triggers.

    Q202. What is Resource Governor, and how do you isolate a reporting workload from OLTP?

    Answer: Resource Governor lets you cap how much CPU, memory, and IO a group of sessions can consume, so one workload cannot starve another. It has three parts: a resource pool, which sets the limits, a workload group, which holds the sessions, and a classifier function, which runs at login and assigns each session to a group based on something like the login name or the application name. The classic use case is a reporting workload that runs heavy queries against the same instance as OLTP: put the reports in their own pool with a CPU and memory cap, and a runaway report slows down instead of taking the order system with it.

    Resource Governor is an Enterprise Edition feature. A pool sets a minimum and maximum CPU percentage, a minimum and maximum memory percentage, and, since SQL Server 2014, minimum and maximum IO per volume. The default pool and default group exist already, and every session starts in the default group unless the classifier function moves it. Changes need ALTER RESOURCE GOVERNOR RECONFIGURE to take effect. Monitor it with sys.dm_resource_governor_resource_pools and sys.dm_resource_governor_workload_groups, which show the limits and the actual usage. Say in the interview that Resource Governor is a safety net, not a performance fix: it stops a bad workload from hurting others, but it does not make the bad workload fast.

    -- A pool that caps the reporting workload at 30% CPU and 20% memory
CREATE RESOURCE POOL ReportingPool
WITH (
    MIN_CPU_PERCENT = 0,
    MAX_CPU_PERCENT = 30,
    MIN_MEMORY_PERCENT = 0,
    MAX_MEMORY_PERCENT = 20
);
GO
CREATE WORKLOAD GROUP ReportingGroup
USING ReportingPool;
GO

-- The classifier function runs at login and routes reporting sessions
CREATE FUNCTION dbo.RGClassifier()
RETURNS SYSNAME
WITH SCHEMABINDING
AS
BEGIN
    DECLARE @Group SYSNAME = 'default';
    IF APP_NAME() = 'ReportingApp'
        SET @Group = 'ReportingGroup';
    RETURN @Group;
END;
GO
ALTER RESOURCE GOVERNOR
    WITH (CLASSIFIER_FUNCTION = dbo.RGClassifier);
ALTER RESOURCE GOVERNOR RECONFIGURE;
GO

-- Check the limits and the actual usage
SELECT pool_id, name, min_cpu_percent, max_cpu_percent,
       min_memory_percent, max_memory_percent
FROM sys.dm_resource_governor_resource_pools;

    Key learning: Resource Governor caps CPU, memory, and IO per workload group through a classifier function, so a reporting workload can be slowed down without starving OLTP, but it is a safety net, not a performance fix.

    Q203. What are temporal tables, and how do you query a table as it looked last week?

    Answer: A temporal table, also called a system-versioned table, keeps a full history of every row change automatically. It has two DATETIME2 columns, usually named ValidFrom and ValidTo, marked GENERATED ALWAYS AS ROW START and ROW END, and a PERIOD FOR SYSTEM_TIME over them. When SYSTEM_VERSIONING is on, every UPDATE and DELETE moves the old row version into a history table with its validity period, so the current table always shows the present state and the history table holds the past.

    You query the past with FOR SYSTEM_TIME: AS OF a point in time, BETWEEN two points, CONTAINED IN a range, or ALL for the full history. The use cases are auditing, point-in-time reporting, and recovering from an accidental change without a restore: if someone updated every price yesterday, AS OF yesterday gives you the old values. Since SQL Server 2017 you can set HISTORY_RETENTION_PERIOD so old history is cleaned up automatically instead of growing forever. Temporal tables are not a replacement for backups: they record what changed, but if the database itself is lost, the history goes with it.

    -- A temporal table with a two-year history retention
CREATE TABLE dbo.ProductPrices
(
    ProductID INT NOT NULL PRIMARY KEY,
    UnitPrice DECIMAL(10, 2) NOT NULL,
    ValidFrom DATETIME2 GENERATED ALWAYS AS ROW START NOT NULL,
    ValidTo DATETIME2 GENERATED ALWAYS AS ROW END NOT NULL,
    PERIOD FOR SYSTEM_TIME (ValidFrom, ValidTo)
)
WITH (SYSTEM_VERSIONING = ON (
    HISTORY_TABLE = dbo.ProductPricesHistory,
    HISTORY_RETENTION_PERIOD = 2 YEARS
));

-- What did the prices look like last Monday at 9 AM?
SELECT ProductID, UnitPrice
FROM dbo.ProductPrices
FOR SYSTEM_TIME AS OF '2026-11-09 09:00:00';

-- Every price change in the last week
SELECT ProductID, UnitPrice, ValidFrom, ValidTo
FROM dbo.ProductPrices
FOR SYSTEM_TIME BETWEEN '2026-11-09' AND '2026-11-16';

    Key learning: Temporal tables keep every row version in a history table automatically, so FOR SYSTEM_TIME AS OF answers what the data looked like at any point, and they are an audit and recovery aid, not a backup replacement.

    Q204. What is the difference between Change Data Capture and Change Tracking?

    Answer: Both tell you what changed, but they answer different questions. Change Data Capture, or CDC, captures the actual changed data: the before and after values of every INSERT, UPDATE, and DELETE, written to change tables by a log reader agent. It is asynchronous, it needs SQL Server Agent running, and it is the right choice for ETL and auditing, because the downstream system receives the real rows that changed. Change Tracking, or CT, only records that a row changed, with its primary key and a version number. It is synchronous and lightweight, and it is the right choice for synchronization, such as a mobile app that asks the server what changed since its last sync.

    The trade-offs decide the choice. CDC keeps history, so you can ask what a row looked like before the change, but it costs more: a capture job, change tables, and storage for every change. Change Tracking is cheap and simple, but it cannot tell you what the old value was, and if a row is deleted and recreated, CT only sees a change, not the details. Enable CDC with sys.sp_cdc_enable_db and sys.sp_cdc_enable_table, and enable Change Tracking at the database level with ALTER DATABASE ... SET CHANGE_TRACKING = ON, then per table. A common interview follow-up is whether CDC needs Agent: yes, the capture and cleanup jobs are Agent jobs, so CDC does not work on editions or setups without Agent.

    -- CDC: capture the before and after values of every change
EXEC sys.sp_cdc_enable_db;
EXEC sys.sp_cdc_enable_table
    @source_schema = 'dbo',
    @source_name = 'Orders',
    @role_name = NULL;

-- Read all changes to Orders between two log sequence numbers
SELECT *
FROM cdc.fn_cdc_get_all_changes_dbo_Orders
    (@from_lsn, @to_lsn, 'all');

-- Change Tracking: only which rows changed, and at which version
ALTER DATABASE SalesDB SET CHANGE_TRACKING = ON
    (CHANGE_RETENTION = 2 DAYS, AUTO_CLEANUP = ON);
ALTER TABLE dbo.Orders ENABLE CHANGE_TRACKING;

SELECT OrderID, SYS_CHANGE_OPERATION, SYS_CHANGE_VERSION
FROM CHANGETABLE(CHANGES dbo.Orders, @last_sync_version) AS Changes;

    Key learning: CDC captures the before and after values of every change for ETL and auditing and needs Agent, while Change Tracking only records which rows changed for synchronization, and it cannot tell you the old values.

    Q205. What is row and page data compression, and when should you use it?

    Answer: Data compression shrinks tables and indexes on disk and in memory, which saves storage and reduces IO, at the cost of extra CPU when rows are written. Row compression stores fixed-length values in variable-length form, so an INT that only holds small numbers takes fewer bytes. Page compression adds two more tricks on top of row compression: prefix compression, which stores repeated leading values once per column, and dictionary compression, which replaces repeated values across the page with short references. Typical savings are 40 to 60 percent on ordinary OLTP data, and the benefit is biggest on large, mostly-read tables with repeated values.

    Do not compress blindly. Compression costs CPU on INSERT, UPDATE, and DELETE, so on a write-heavy table the CPU cost can outweigh the IO saving, and it can also slow down index rebuilds. Do not compress data that is already compressed, such as images or encrypted columns, because there is nothing to gain. Estimate the saving first with sp_estimate_data_compression_savings, and test on a copy of the table before applying it. Page compression is not the same as columnstore: columnstore compresses far more aggressively and is the right choice for analytics, while row and page compression are for rowstore OLTP tables.

    -- Estimate the saving before committing to it
EXEC sp_estimate_data_compression_savings
    'dbo', 'Orders', NULL, NULL, 'PAGE';

-- Apply page compression to a table
ALTER TABLE dbo.Orders REBUILD WITH (DATA_COMPRESSION = PAGE);

-- Apply it to a single index instead
ALTER INDEX IX_Orders_CustomerID ON dbo.Orders
REBUILD WITH (DATA_COMPRESSION = PAGE);

    Key learning: Page compression saves 40 to 60 percent on typical OLTP data by storing repeated values once, but it costs CPU on writes, so estimate first and do not compress data that is already compressed.

    Q206. What is a linked server, and what are the pitfalls of distributed queries?

    Answer: A linked server lets one SQL Server instance query another server, or a different data source such as Oracle, directly from T-SQL, using a four-part name such as RemoteServer.SalesDB.dbo.Orders, or OPENQUERY for a pass-through query that runs entirely on the remote side. You create one with sp_addlinkedserver and control the security context with sp_addlinkedsrvlogin: either impersonate the current login, which needs delegation configured, or map everyone to one fixed remote login. Linked servers are useful for occasional cross-server lookups, migrations, and reporting that pulls from two systems.

    The pitfalls are what interviewers want. Performance is the first: the local optimizer has no statistics for the remote table, so it often pulls the whole table across the network and filters locally, which is slow and can lock the remote side. Push the filter to the remote side with OPENQUERY or a remote stored procedure instead of joining a local table to a remote one. Security is the second: a fixed login mapping means every local user acts as one remote account, which is hard to audit, while impersonation needs Kerberos delegation. Collation is the third: mismatched collations cause errors or force a COLLATE clause. Finally, a transaction that touches two servers needs the Microsoft Distributed Transaction Coordinator, MSDTC, and if it is not configured, the transaction fails. For regular data movement, replication or SSIS is usually the better design than a linked server.

    -- Create a linked server to another SQL Server instance
EXEC sp_addlinkedserver
    @server = 'RemoteServer',
    @srvproduct = 'SQL Server';

-- Map local logins to one fixed remote login
EXEC sp_addlinkedsrvlogin
    @rmtsrvname = 'RemoteServer',
    @useself = 'false',
    @locallogin = NULL,
    @rmtuser = 'RemoteAppUser',
    @rmtpassword = 'StrongPassword123!';

-- Bad: pulls the whole remote table locally, then filters
SELECT *
FROM RemoteServer.SalesDB.dbo.Orders
WHERE OrderDate >= '2026-11-01';

-- Good: the filter runs on the remote side
SELECT *
FROM OPENQUERY(RemoteServer,
    'SELECT * FROM SalesDB.dbo.Orders WHERE OrderDate >= ''2026-11-01''');

    Key learning: Linked servers let you query another server by four-part name, but the optimizer has no remote statistics, so push filters to the remote side with OPENQUERY and use replication or SSIS for regular data movement.

    Q207. What are the Ola Hallengren maintenance scripts, and why do DBAs use them instead of maintenance plans?

    Answer: The Ola Hallengren Maintenance Solution is a free, community-maintained set of stored procedures that most production SQL Servers use for routine maintenance: IndexOptimize rebuilds or reorganizes fragmented indexes and updates statistics, DatabaseBackup takes full, differential, and log backups with compression, verification, and cleanup, and DatabaseIntegrityCheck runs DBCC CHECKDB. They are installed once, scheduled as SQL Server Agent jobs, and every run is logged to a CommandLog table, so you can see exactly what ran, how long it took, and what failed.

    DBAs prefer them over the built-in maintenance plans for four reasons. First, they are parameterized: you can say rebuild only indexes over 30 percent fragmentation, reorganize between 5 and 30 percent, and update statistics only where they are stale. Second, they handle details maintenance plans do not, such as backing up to multiple files, verifying backups with RESTORE VERIFYONLY, and cleaning up old files by age. Third, the logging is real: CommandLog gives you a history you can query, while a maintenance plan failure is often just a red job with a vague message. Fourth, they are the same scripts everywhere, so a DBA who joins a new team already knows them. The interview answer is that you use them because they are the industry standard, not because maintenance plans are broken: plans are fine for a single small server, but they do not scale to a fleet.

    -- Rebuild fragmented indexes, reorganize the middling ones, update statistics
EXECUTE dbo.IndexOptimize
    @Databases = 'USER_DATABASES',
    @FragmentationLevel1 = 5,
    @FragmentationLevel2 = 30,
    @UpdateStatistics = 'ALL',
    @LogToTable = 'Y';

-- Full backup with compression, verification, and 7-day cleanup
EXECUTE dbo.DatabaseBackup
    @Databases = 'USER_DATABASES',
    @Directory = 'E:\Backups',
    @BackupType = 'FULL',
    @Compress = 'Y',
    @Verify = 'Y',
    @CleanupTime = 168,
    @LogToTable = 'Y';

-- What ran, and did it fail?
SELECT StartTime, DatabaseName, Command, ErrorNumber, ErrorMessage
FROM dbo.CommandLog
WHERE ErrorNumber <> 0
ORDER BY StartTime DESC;

    Key learning: The Ola Hallengren scripts are the industry-standard maintenance procedures for indexes, backups, and CHECKDB, and they beat maintenance plans on parameters, logging, and fleet-wide consistency.

    Q208. What is MCP, and why does the DBA own the security layer for AI access to SQL Server?

    Answer: MCP, the Model Context Protocol, is an open protocol that lets an AI assistant call tools exposed by a server. A SQL Server MCP server exposes tools such as run a query, list tables, and describe a schema, so an AI agent or a Copilot in SSMS can answer questions about the database and even run queries on your behalf. The protocol itself is simple; the hard part is that the AI is now a database user with a keyboard, and it will do exactly what it is asked to do, including destructive things if nobody stops it.

    That is why the DBA owns the security layer. First, give the AI its own dedicated login with the least privilege it needs, usually read-only on the databases it may touch, and never reuse an application or admin account. Second, block destructive keywords at the tool layer, so DROP, DELETE, TRUNCATE, and UPDATE cannot reach the engine from an AI call, even if the model generates them. Third, cap the result size, because an AI that asks for a full table will pull millions of rows into its context. Fourth, audit every tool call, so there is a record of what the AI ran, when, and for whom. The interview point is that MCP does not change database security, it just adds a new kind of client, and the same principles apply: least privilege, a allowlist of what is permitted, and an audit trail.

    -- A dedicated read-only login for the AI tool, nothing more
CREATE LOGIN AiAssistant
WITH PASSWORD = 'StrongPassword123!';
GO
USE SalesDB;
GO
CREATE USER AiAssistant FOR LOGIN AiAssistant;
-- Read-only on the reporting schema, no write, no DDL
ALTER ROLE db_datareader ADD MEMBER AiAssistant;
DENY INSERT, UPDATE, DELETE ON SCHEMA::dbo TO AiAssistant;
DENY ALTER, CONTROL ON DATABASE::SalesDB TO AiAssistant;

-- Audit everything the AI login runs
CREATE SERVER AUDIT AiAccessAudit
TO FILE (FILEPATH = 'E:\Audit\');
ALTER SERVER AUDIT AiAccessAudit WITH (STATE = ON);

    Key learning: MCP lets AI assistants call SQL Server tools, so the DBA must give the AI its own least-privilege read-only login, block destructive statements, cap result sizes, and audit every call.

    Q209. What are ledger tables, and how do you prove nobody changed the data?

    Answer: Ledger tables, available since SQL Server 2022, make a table tamper-evident: every transaction against the table is hashed with SHA-256 into a Merkle tree, and the hashes are chained together, so changing an old row breaks the chain. The latest hash is called the digest, and you store it outside the database, where the people being audited cannot reach it. Later, you hand the digest back to SQL Server and it recomputes the hashes from the data: if they match, the data is unchanged; if they do not, something was tampered with. That is the answer to an auditor who asks you to prove nobody, including your own DBAs, quietly edited a record.

    There are two kinds. Updatable ledger tables allow INSERT, UPDATE, and DELETE, and keep the old versions in a history table, like temporal tables with cryptographic proof. Append-only ledger tables refuse UPDATE and DELETE entirely, so the table is a write-once audit log. Create one with LEDGER = ON, and add APPEND_ONLY = ON for the append-only kind. To verify, generate a digest with sys.sp_generate_database_ledger_digest, store it externally, and later run sys.sp_verify_database_ledger with that digest, or sys.sp_verify_database_ledger_from_digest_storage when digests are stored automatically. Verification needs ALLOW_SNAPSHOT_ISOLATION on the database. The honest caveat is that a ledger proves the recorded data was not changed, not that the application told the truth when it wrote it: garbage in becomes tamper-proof garbage.

    -- An append-only ledger table: inserts only, no updates or deletes
CREATE TABLE dbo.AuditLog
(
    LogID INT PRIMARY KEY IDENTITY,
    EventDescription NVARCHAR(500) NOT NULL,
    EventTime DATETIME2 NOT NULL
)
WITH (LEDGER = ON (APPEND_ONLY = ON));

-- Generate a digest and store it outside the database
DECLARE @Digest TABLE (digest NVARCHAR(MAX));
INSERT @Digest EXEC sys.sp_generate_database_ledger_digest;
SELECT digest FROM @Digest;

-- Later, verify the data against a stored digest
ALTER DATABASE SalesDB SET ALLOW_SNAPSHOT_ISOLATION ON;
DECLARE @Digests NVARCHAR(MAX) =
    N'[' + (SELECT digest FROM @Digest) + N']';
EXEC sys.sp_verify_database_ledger @Digests;

    Key learning: Ledger tables hash every transaction into a chained digest you store externally, so verification proves the recorded data was not changed, but it cannot prove the application told the truth when it wrote it.

    Q210. What does the native JSON type in SQL Server 2025 change, and what are the new regular expression functions?

    Answer: Before SQL Server 2025, JSON was stored as NVARCHAR, which meant it was just text: invalid JSON could be inserted, every query had to parse the text again, and indexing a JSON value meant a computed column over JSON_VALUE. The native JSON type stores the document in an optimized binary form, validates it on write so malformed JSON is rejected at insert time, and lets you create indexes directly on JSON path expressions. New functions arrive with it: JSON_CONTAINS for subset matching, and JSON_OBJECTAGG and JSON_ARRAYAGG for building documents from a result set. The familiar functions JSON_VALUE, JSON_QUERY, OPENJSON, and FOR JSON still work, and they are faster on the native type because the document is already parsed.

    The same release adds native regular expressions based on the RE2 engine: REGEXP_LIKE to test a pattern, REGEXP_REPLACE to substitute matches, REGEXP_SUBSTR to extract a match, and REGEXP_INSTR and REGEXP_COUNT for position and counting. They replace CLR assemblies and nested PATINDEX tricks for pattern matching, and they are the right tool for validation such as email formats. Two honest caveats belong in the answer. First, hands-on tests show the native JSON type is not automatically faster or smaller than NVARCHAR for simple filters: its value is validation on write and the new functions, not speed you will measure on day one. Second, use REGEXP functions for patterns LIKE cannot express, not as a replacement for LIKE, because a simple prefix match is still faster with LIKE and an index.

    -- Native JSON column: validated on write, stored in binary form
CREATE TABLE dbo.Products
(
    ProductID INT PRIMARY KEY,
    ProductData JSON NOT NULL
);

-- Index directly on a JSON path, no computed column needed
CREATE INDEX IX_Products_Color
    ON dbo.Products (JSON_VALUE(ProductData, '$.color'));

-- Query it with the familiar functions
SELECT ProductID,
       JSON_VALUE(ProductData, '$.name') AS ProductName,
       JSON_VALUE(ProductData, '$.price') AS Price
FROM dbo.Products
WHERE JSON_VALUE(ProductData, '$.color') = 'red';

-- Native regex: validate an email format without CLR
SELECT CustomerID, Email
FROM dbo.Customers
WHERE REGEXP_LIKE(Email,
    '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$') = 1;

    Key learning: The native JSON type validates documents on write and supports indexes on JSON paths, and the new REGEXP functions handle patterns LIKE cannot express, but neither is automatically faster than the older approach for simple queries.
