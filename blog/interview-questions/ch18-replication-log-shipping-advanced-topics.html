Chapter 18: Replication, Log Shipping & Advanced Topics

Advanced availability and scale features trade complexity for capability, so a DBA must know when each one helps and when it adds risk. This chapter covers replication and log shipping, large-table design, and newer engine features that change blocking, search, and query processing. It closes with two troubleshooting scenarios that tie diagnosis, Query Store, and methodical testing together.

In this chapter:

  • →Snapshot, transactional, and merge replication and their use cases
  • →Log shipping architecture, setup, failover, and monitoring
  • →Extended investigation of time-based timeouts with no blocking
  • →Partitioning at scale, sliding windows, and partition-level operations
  • →Vector search, the VECTOR type, and DiskANN indexes
  • →New DBA features in SQL Server 2025
  • →Optimized Locking, lock after qualification, and transaction IDs
  • →Columnstore indexes, batch mode, segment elimination, and maintenance
  • →Diagnosis of slowness after a statistics update
  • →End-to-end slow-query troubleshooting methodology

    • Key learning: Replication and log shipping solve different availability and distribution problems, and partitioning and columnstore solve different scale problems, so match the feature to the workload instead of applying every feature at once. Newer features such as vector search and Optimized Locking change storage, indexing, and blocking behavior, so test them for backup size, recovery time, and plan stability before wide rollout. For every slowdown, follow evidence from waits and Query Store before changing code or configuration.

    Q191. What are snapshot, transactional, and merge replication, and what are the use cases for each?

    Answer: Replication copies data from a publisher to one or more subscribers through a distributor. The publisher owns the source tables, articles define what is copied, and agents move the data. The three types differ in how often data moves and whether subscribers can change it.

  • →Snapshot replication copies a full snapshot of the published data at scheduled intervals. Use it for reference data that changes rarely, for small tables, or when subscribers can accept stale data. It is simple but sends the whole article each time, so it does not suit large or fast-changing tables.
  • →Transactional replication reads committed transactions from the log and applies them to subscribers in near real time. Use it for one-way distribution to reporting servers, data warehouses, or read copies. Subscribers are normally read-only, latency is low, and the publisher must stay available for the log reader to keep up.
  • →Merge replication allows publishers and subscribers to change data independently and then merges the changes with conflict resolution. Use it only for disconnected or mobile users who must work offline and sync later. It is the most complex type, needs conflict rules and careful testing, and is rarely the right first choice.

    • Choose transactional replication for reporting, snapshot replication for infrequent full copies, and merge replication only when disconnected bidirectional updates are truly required.

    USE SalesDB;
EXEC sp_helppublication;
EXEC sp_helpsubscription @publication = 'SalesPublication';

    Key learning: Use snapshot replication for infrequent full copies, transactional replication for near real-time one-way distribution, and merge replication only when disconnected bidirectional updates and conflict handling are truly required.

    Q192. How does log shipping work, and how do you set it up, fail over, and monitor it?

    Answer: Log shipping automates three jobs: backup the transaction log on the primary, copy the log backup files to the secondary, and restore them on the secondary with NORECOVERY or STANDBY. The secondary stays behind the primary by the backup and restore intervals, so it is a disaster recovery copy, not a real-time replica. The database must use the FULL recovery model, and the primary, the shared folder, and the secondary must all be reachable by the SQL Server Agent jobs.

    Setup starts with a full backup restored on the secondary with NORECOVERY, a shared backup folder with correct permissions, and schedules for the backup, copy, and restore jobs. Choose intervals that match the RPO, set the restore mode to NORECOVERY for pure disaster recovery or STANDBY if read-only reporting is needed between restores, and copy logins, jobs, and linked servers separately because log shipping does not copy them.

    Failover is manual. Take a tail-log backup on the primary if it is still available, copy and restore any remaining logs, restore the last log with RECOVERY, redirect applications to the secondary, and fix orphaned users and jobs. Monitoring checks job history, the copy and restore delay, and the alert thresholds in msdb, and failover must be rehearsed so the steps and the timings are known before a real outage.

    SELECT * FROM msdb.dbo.log_shipping_primary_databases;
SELECT * FROM msdb.dbo.log_shipping_secondary_databases;

    Key learning: Log shipping is a simple manual disaster recovery method that copies and restores log backups on a schedule, so its recovery point depends on the backup and restore intervals and failover must be practiced.

    Q193. How do you investigate time-based timeouts when there is no blocking in sys.dm_exec_requests?

    Answer: First, capture what is waiting right now with sys.dm_os_waiting_tasks while the timeout is happening, because sys.dm_exec_requests only shows currently executing requests and misses waits between batches, waits during login, and waits that have already finished. Record the wait type, the wait duration, the blocking session if any, and the resource description, and repeat the capture several times during the bad window.

    Next, check wait history and the pattern over time. Compare sys.dm_os_wait_stats before and after the window, check Query Store wait stats for the affected queries, and look for waits such as ASYNC_NETWORK_IO, RESOURCE_SEMAPHORE, THREADPOOL, SOS_SCHEDULER_YIELD, or PAGEIOLATCH that point to the client, memory grants, worker pressure, CPU, or storage. A timeout that happens at the same time each day usually points to scheduled work, so check Agent jobs, backups, CHECKDB, index maintenance, statistics updates, ETL loads, antivirus scans, and storage snapshots that run at that time.

    Use Extended Events to catch what polling misses. Capture attention events for timeouts, sql_batch_completed and rpc_completed for slow completions, and login and logout events for connection pressure, filtered to the affected application and time window. Correlate the results with PerfMon or server metrics for CPU, memory, disk latency, and network, and check the application side for connection pool exhaustion, command timeouts set too low, and retries that amplify the load.

    SELECT session_id, wait_type, wait_duration_ms, blocking_session_id, resource_description
FROM sys.dm_os_waiting_tasks
WHERE session_id > 50;

SELECT wait_type, waiting_tasks_count, wait_time_ms
FROM sys.dm_os_wait_stats
WHERE wait_type NOT IN ('CLR_SEMAPHORE', 'LAZYWRITER_SLEEP')
ORDER BY wait_time_ms DESC;

    Key learning: When timeouts follow a clock pattern with no blocking, look beyond current requests to waiting tasks, wait history, Extended Events, and scheduled work that runs at the same time.

    Q194. How does partitioning work at scale, including the sliding window pattern, partition-level operations, and common pitfalls?

    Answer: Partitioning splits a table or index into partitions by a partition function, usually on a date or ID column, and maps each partition to a filegroup through a partition scheme. Queries that filter on the partition key can use partition elimination and read only the needed partitions. Partitioning is mainly a manageability feature for large tables, not a general performance fix for small tables.

    The sliding window pattern keeps a rolling set of partitions, such as one per month. New data arrives in a staging table with the same structure, is switched into an empty new partition with SWITCH, and old data is switched out to an archive table and then truncated or dropped. SPLIT RANGE adds a new boundary and MERGE RANGE removes one. SWITCH is a metadata-only move, so it is far faster than DELETE or INSERT for moving large volumes, but the staging table must match the partition schema, indexes, and constraints exactly.

    Common pitfalls are partitioning on the wrong key so queries scan every partition, creating too many small partitions, skewed partitions where one partition holds most rows, and unaligned indexes that block SWITCH. Partition-level operations such as rebuilding one partition or truncating one partition help, but SPLIT and MERGE on a populated partition can be expensive and move data. Test the partition count, the elimination behavior in execution plans, and the maintenance window before partitioning a production table.

    CREATE PARTITION FUNCTION PF_Monthly (datetime2)
AS RANGE RIGHT FOR VALUES ('2026-01-01', '2026-02-01', '2026-03-01');

CREATE PARTITION SCHEME PS_Monthly
AS PARTITION PF_Monthly ALL TO ([PRIMARY]);

CREATE TABLE dbo.Orders
(
    OrderID int NOT NULL,
    OrderDate datetime2 NOT NULL,
    Amount decimal(10, 2) NOT NULL
)
ON PS_Monthly (OrderDate);

SELECT partition_number, rows
FROM sys.partitions
WHERE object_id = OBJECT_ID('dbo.Orders');

    Key learning: Partitioning helps manageability and partition elimination at scale when the partition key matches common filters and the sliding window uses SWITCH instead of DELETE for data movement.

    Q195. What is vector search in SQL Server and Azure SQL, and what are the DBA implications of the VECTOR type and DiskANN indexes?

    Answer: Vector search finds rows whose embedding vectors are closest to a query vector, which supports semantic search, recommendations, and retrieval for AI workloads. Embeddings are stored in the VECTOR type with a fixed dimension, such as 1536 for a common embedding model, and similarity is measured with VECTOR_DISTANCE using cosine, Euclidean, or dot product distance. A DiskANN index provides approximate nearest neighbor search so large vector tables can be searched without scanning every row.

    For the DBA, vector data changes capacity and maintenance planning. Embeddings are wide, so tables, indexes, backups, and restores grow quickly, and index builds need memory and time. DiskANN indexes must be built and maintained as data changes, and query performance depends on the metric, the dimension, and the index settings matching the model that produced the embeddings. Changing the embedding model or the dimension means reloading vectors, not just altering a column.

    Test vector workloads for storage growth, backup size, restore time, and RTO before wide rollout. Monitor index size and build time, keep the embedding dimension consistent across the application and the table, and confirm that the top results and the query latency meet the application need. Vector search does not replace full-text search or relational indexes, so use it where similarity ranking is the actual requirement. Note that vector indexes are a preview feature in SQL Server 2025 on premises, so confirm the status in the target build before promising them in production.

    CREATE TABLE dbo.Documents
(
    DocumentID int PRIMARY KEY,
    Title nvarchar(200) NOT NULL,
    Embedding vector(1536) NOT NULL
);

CREATE VECTOR INDEX IX_Documents_Embedding
ON dbo.Documents (Embedding)
WITH (METRIC = 'cosine');

    Key learning: Vector search adds embedding storage and DiskANN indexes that increase database size and backup and restore time, so capacity and recovery testing must include the vector workload.

    Q196. What is new for DBAs in SQL Server 2025?

    Answer: SQL Server 2025 adds native vector search with the VECTOR type and DiskANN indexes, so similarity search can run inside the database without an external vector store. It also adds a native JSON type with storage and query support, which helps applications that store document data alongside relational data. Change event streaming publishes data changes for downstream systems without polling or custom change tracking jobs.

    For performance and availability, Optimized Locking reduces blocking for concurrent updates, and intelligent query processing improvements such as degree of parallelism feedback help the optimizer adjust plans based on actual runtime behavior. Query Store is more capable for tracking plan regressions and forcing good plans. Security and platform work includes stronger authentication options and closer integration with Microsoft Fabric for analytics and mirroring.

    For an interview answer, focus on DBA impact, not a feature list. Vector indexes affect storage and backup size, Optimized Locking affects blocking and lock memory, JSON and change streaming affect application design, and every new feature needs plan stability testing, restore testing, and monitoring before it is used in production. Confirm the exact edition and version behavior in the target environment, because availability and defaults vary by edition and update.

    SELECT SERVERPROPERTY('ProductVersion') AS ProductVersion,
       SERVERPROPERTY('ProductLevel') AS ProductLevel,
       SERVERPROPERTY('Edition') AS Edition;

ALTER DATABASE SCOPED CONFIGURATION SET DOP_FEEDBACK = ON;

    Key learning: SQL Server 2025 adds vector search, Optimized Locking, and stronger intelligent query processing, so DBAs gain new indexing and blocking tools that still require testing for plans, storage, and recovery.

    Q197. What is Optimized Locking in SQL Server 2022 and 2025, and how do lock after qualification and transaction IDs reduce blocking?

    Answer: Optimized Locking reduces the number and duration of locks held during updates. It combines two mechanisms: lock after qualification, often called LAQ, and transaction IDs, often called TIDs. It is enabled at the database level and is designed for workloads with concurrent updates to the same tables, where blocking and lock memory are the main pain.

    Lock after qualification means locks are taken only after a row qualifies for the update, instead of locking rows while they are scanned and evaluated. Rows that do not match the predicate are not locked, so fewer locks are held and less lock memory is used. This helps UPDATE and DELETE statements that scan many rows to change a few, and it reduces blocking for other sessions that need the non-qualifying rows.

    Transaction IDs store the ID of the last modifying transaction with the row version, so SQL Server can determine row visibility with less locking. Readers and writers can proceed with fewer locks held for the life of the transaction, which reduces contention on hot rows. Optimized Locking does not fix missing indexes, bad plans, or long transactions, so still tune the query and keep transactions short, and test blocking, throughput, and tempdb use before enabling it widely.

    ALTER DATABASE SalesDB SET OPTIMIZED_LOCKING = ON;

SELECT name, is_optimized_locking_on
FROM sys.databases
WHERE name = 'SalesDB';

    Key learning: Optimized Locking reduces blocking by taking locks only after rows qualify and by using transaction IDs to track row versions with fewer locks held.

    Q198. How do columnstore indexes work at scale, including batch mode, segment elimination, and maintenance?

    Answer: Columnstore indexes store data by column in compressed segments, grouped into rowgroups of about one million rows. Analytic queries that scan many rows but few columns read only the needed segments, which cuts IO and benefits from compression. Data first lands in a delta store for trickle inserts and is later compressed into rowgroups by the tuple mover. Deleted rows are marked in a delete bitmap until the rowgroup is rebuilt.

    Batch mode processes rows in batches instead of one row at a time, which speeds up scans, joins, and aggregates. Segment elimination uses the minimum and maximum values stored for each segment to skip segments that cannot contain matching rows. It works best when data is loaded in sorted order on the filtered column and when rowgroups are large and well compressed. Small, fragmented rowgroups and unordered loads reduce both benefits.

    Maintenance focuses on rowgroup quality. Use REORGANIZE to compress closed delta stores and remove deleted rows, and REBUILD to fix heavily fragmented indexes or to change compression. Monitor rowgroup state, total rows, and deleted rows, load in bulk through staging tables instead of trickling in small inserts, and keep statistics current. Columnstore suits large analytic scans, not OLTP point lookups or heavy singleton updates.

    CREATE CLUSTERED COLUMNSTORE INDEX CCI_Sales
ON dbo.Sales;

ALTER INDEX CCI_Sales ON dbo.Sales REORGANIZE;

SELECT object_id, index_id, partition_number, row_group_id, state_desc, total_rows, deleted_rows
FROM sys.dm_db_column_store_row_group_physical_stats;

    Key learning: Columnstore performance depends on large compressed rowgroups and segment elimination, so load in bulk and maintain rowgroups regularly instead of trickling in small inserts.

    Q199. Scenario: The application is slow after a statistics update. How do you diagnose it?

    Answer: First, check Query Store for the affected queries and compare the current plan with the previous good plan, including compile time, execution counts, duration, and logical reads around the statistics update. If the plan changed at the same time as the update, treat plan regression as the leading cause and confirm which queries changed before you change anything else.

    Next, compare the plans in detail. Look for a different join type, a scan replacing a seek, a new spool or sort, a large gap between estimated and actual rows, and a different index choice. Check which statistics were updated, whether they used a sample or FULLSCAN, whether auto update ran during peak hours, and whether the update coincided with a data load or a parameter sniffing pattern. Check wait stats for the affected queries to confirm whether the slowdown is CPU, IO, or waiting.

    Restore service first with a reversible fix, then fix the cause. If Query Store shows a previous good plan, force that plan and monitor to confirm the slowdown clears. Then investigate the statistics themselves, test a FULLSCAN update in a non-production copy if sampling is suspect, review the maintenance window and sampling settings, and unforce the plan only after testing proves the new plan is stable. Do not clear the plan cache or update statistics again blindly, because both can make the regression wider.

    SELECT q.query_id, p.plan_id, rs.avg_duration, rs.last_execution_time
FROM sys.query_store_query q
JOIN sys.query_store_plan p ON p.query_id = q.query_id
JOIN sys.query_store_runtime_stats rs ON rs.plan_id = p.plan_id
WHERE q.object_id = OBJECT_ID('dbo.GetOrders')
ORDER BY rs.last_execution_time DESC;

EXEC sp_query_store_force_plan @query_id = 42, @plan_id = 15;

    Key learning: Slowness after a statistics update is usually plan regression, so compare plans in Query Store, force the previous good plan to restore service, and then fix the statistics or plan problem at its cause.

    Q200. Scenario: Walk through your end-to-end methodology for troubleshooting a slow query, from scoping to documentation.

    Answer: First, scope the problem: confirm which query or application is slow, when it started, whether it is one query or server-wide, and whether anything changed just before it started, such as a deployment, a statistics update, an index change, or a data load. Get the exact query text, the parameters used, the expected runtime, and the current runtime, so you are fixing a measured problem and not a vague report.

    Then work in order, from the server inward to the query:

  • →Check server health: CPU, memory pressure, disk latency, and error log entries, to rule out a platform problem before tuning a query.
  • →Check top waits with wait stats and waiting tasks to learn what sessions are waiting on, such as locks, IO, CPU, memory grants, or network.
  • →Find the top queries by elapsed time, CPU, and logical reads, and confirm the reported query is actually the expensive one.
  • →Examine the execution plan for scans, missing index warnings, bad estimates, spools, sorts, key lookups, and parameter sniffing, and compare the current plan with the last good plan in Query Store.
  • →Identify the root cause from that evidence: blocking, stale statistics, a missing or unused index, a plan regression, a bad parameter value, a long transaction, or a resource limit.

    • Fix in order of safety and reversibility: relieve blocking, update statistics or force a known good plan, add or adjust an index, rewrite the query, and change configuration last. Change one thing at a time, capture before-and-after measurements for duration, logical reads, CPU, and the plan, and roll back if the change does not help. Finish by monitoring Query Store and wait stats after the fix, and document the symptom, the evidence, the fix, the measurements, and the follow-up check so the next DBA can repeat the diagnosis without starting over.

    SELECT TOP 10 wait_type, wait_time_ms, waiting_tasks_count
FROM sys.dm_os_wait_stats
ORDER BY wait_time_ms DESC;

SELECT TOP 10 qs.total_elapsed_time, qs.execution_count, st.text
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
ORDER BY qs.total_elapsed_time DESC;

    Key learning: Troubleshoot slow queries in order from scope to server health to waits to queries to plans, fix one cause at a time, and prove each change with before-and-after measurements.
