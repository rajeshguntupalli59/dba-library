Chapter 2: Filtering, Sorting & Aggregates

Once you can read a table, the next step is to shape the result: filter the right rows, combine conditions, and summarize data with aggregates. This chapter covers logical operators, pattern matching, grouping, and the string, date, and math functions interviewers expect you to know. These are the building blocks of almost every reporting query.

In this chapter:

  • →Second-highest salary, latest record per group, and each row's share of the total
  • →Aggregate functions vs window functions, and the COUNT forms
  • →GROUP BY, HAVING, and subtotals with GROUPING SETS
  • →Finding duplicate rows
  • →Splitting strings, date ranges, and the first and last day of the month
  • →COALESCE vs ISNULL

    • Key learning: Filtering decides which rows are considered, grouping decides how rows are summarized, and HAVING filters the groups that result. Knowing when each clause runs and how NULL values flow through aggregates and functions prevents the most common beginner query errors.

    Q13. How do you find the second-highest salary in a table?

    Answer: First decide what second-highest means when salaries repeat. If two people share the highest salary, the second-highest distinct salary is the next value down, and a good answer says so before writing code. The cleanest method is DENSE_RANK, which gives the same rank to equal salaries, so filtering to rank 2 returns everyone at the second distinct salary. ROW_NUMBER also works, but it picks one arbitrary row among ties instead of returning all of them.

    Two other methods are common. OFFSET skips the top row and fetches the next one, which is simple but also returns one row and depends on an ORDER BY. The classic subquery, MAX(Salary) WHERE Salary < (SELECT MAX(Salary) FROM Employees), returns the second distinct salary directly and is easy to read. Whichever method you choose, state the tie rule first, because that is what the interviewer is testing.

    -- Returns everyone at the second distinct salary (handles ties)
SELECT EmployeeID, FirstName, LastName, Salary
FROM (
    SELECT EmployeeID, FirstName, LastName, Salary,
           DENSE_RANK() OVER (ORDER BY Salary DESC) AS SalaryRank
    FROM Employees
) AS Ranked
WHERE SalaryRank = 2;

-- Simple alternative: the highest salary below the maximum
SELECT MAX(Salary) AS SecondHighestSalary
FROM Employees
WHERE Salary < (SELECT MAX(Salary) FROM Employees);

    Key learning: State the tie rule first, then use DENSE_RANK to return everyone at the second distinct salary, or a subquery on MAX to return the value itself.

    Q14. How do you find the latest record for each group?

    Answer: The standard pattern is ROW_NUMBER in a common table expression: number the rows inside each group by date descending, then keep only row number 1. PARTITION BY defines the group, such as one customer, and ORDER BY defines which row is latest. Always add a tiebreaker to the ORDER BY, such as the primary key, because two rows with the same date leave the winner undefined and the query can return a different row on different runs.

    Two other approaches exist but have trade-offs. A correlated subquery comparing the date to MAX(OrderDate) for the group works, but it scans the table once per group and is slower on large data. CROSS APPLY with TOP 1 per group is a good alternative when the groups are few and the table has an index on the grouping and date columns. For most cases, ROW_NUMBER is the answer an interviewer wants to see.

    -- Latest order per customer, with a tiebreaker on OrderID
WITH LatestOrders AS (
    SELECT OrderID, CustomerID, OrderDate, TotalAmount,
           ROW_NUMBER() OVER (
               PARTITION BY CustomerID
               ORDER BY OrderDate DESC, OrderID DESC
           ) AS RowNum
    FROM Orders
)
SELECT OrderID, CustomerID, OrderDate, TotalAmount
FROM LatestOrders
WHERE RowNum = 1;

    Key learning: Use ROW_NUMBER partitioned by the group and ordered by date descending, keep row 1, and add a tiebreaker so the latest row is deterministic.

    Q15. How do you calculate each row's share of the total in one query?

    Answer: Use a window function with an empty OVER clause: SUM(Amount) OVER () computes the total across all rows while keeping every row in the result, so each row can divide its own amount by that total. Add PARTITION BY to get the share within a group instead of across the whole table, such as each product's share of its category total. Window functions run after WHERE and GROUP BY, so the total respects the filters in the query.

    Two details trip people up. First, multiply by 100.0, not 100, because integer division in SQL Server drops the fraction: 1 / 2 returns 0, while 1 * 100.0 / 2 returns 50.0. Second, do not write a subquery that scans the table again for the total when a window function does it in the same pass. The subquery version works, but the window version is the answer that shows you know modern T-SQL.

    -- Each order's share of all sales
SELECT OrderID, CustomerID, TotalAmount,
       TotalAmount * 100.0 / SUM(TotalAmount) OVER () AS PercentOfTotal
FROM Orders;

-- Each product's share of its category total
SELECT ProductID, CategoryID, SalesAmount,
       SalesAmount * 100.0 / SUM(SalesAmount) OVER (PARTITION BY CategoryID) AS PercentOfCategory
FROM ProductSales;

    Key learning: Divide each row by SUM over an empty window for its share of the total, add PARTITION BY for a share within a group, and multiply by 100.0 to avoid integer division.

    Q16. What is the difference between an aggregate function and a window function?

    Answer: An aggregate function with GROUP BY collapses rows: one output row per group, and the detail rows disappear. SUM(Salary) grouped by Department returns one row per department. A window function computes the same aggregate but keeps every row, adding the result as a new column. SUM(Salary) OVER (PARTITION BY Department) returns every employee row with their department total attached.

    Window functions also do things aggregates cannot. With ORDER BY inside OVER they rank rows with ROW_NUMBER, RANK, and DENSE_RANK, and with ROWS BETWEEN they compute running totals and moving averages. They run after WHERE, GROUP BY, and HAVING, so they see the filtered, grouped result. Use an aggregate when the answer is a summary; use a window function when you need the detail rows plus the summary, a rank, or a running total in the same query.

    -- Aggregate: one row per department, detail rows gone
SELECT Department, SUM(Salary) AS DepartmentTotal
FROM Employees
GROUP BY Department;

-- Window: every employee row kept, department total attached
SELECT EmployeeID, FirstName, Department, Salary,
       SUM(Salary) OVER (PARTITION BY Department) AS DepartmentTotal,
       RANK() OVER (PARTITION BY Department ORDER BY Salary DESC) AS SalaryRank
FROM Employees;

    Key learning: An aggregate collapses rows into one row per group, while a window function keeps every row and adds the result as a column, and can also rank rows and compute running totals.

    Q17. What is the difference between COUNT(*), COUNT(column), and COUNT(DISTINCT column)?

    Answer: COUNT(*) counts every row in the group, including rows where every column is NULL. COUNT(column) counts only rows where that column is not NULL, so it can return a smaller number than COUNT(*) when the column has missing values. COUNT(DISTINCT column) counts distinct non-NULL values, so repeated values are counted once and NULL values are not counted at all.

    A common interview follow-up is COUNT(DISTINCT *) which is not valid syntax. DISTINCT must name a column or expression. Choose COUNT(*) when you want the row count, COUNT(column) when you want how many rows have a value, and COUNT(DISTINCT column) when you want how many different values exist.

    SELECT COUNT(*) AS AllEmployees,
       COUNT(Email) AS EmployeesWithEmail,
       COUNT(DISTINCT Department) AS DistinctDepartments
FROM Employees;

    Key learning: COUNT(*) counts all rows, COUNT(column) counts non-NULL values, and COUNT(DISTINCT column) counts distinct non-NULL values.

    Q18. What does GROUP BY do, and how does it group rows for aggregation?

    Answer: GROUP BY collects rows that share the same values in the grouping columns into one group, and the query returns one row per group. Aggregate functions in the SELECT list are then calculated separately for each group, so you can ask for a count or average per department instead of one total for the whole table.

    Every column in the SELECT list must either appear in GROUP BY or be inside an aggregate function. A bare column that varies inside a group has no single value to show, so SQL Server rejects it. GROUP BY does not guarantee sorted output, so add ORDER BY when the order of groups matters. You cannot use a SELECT column alias in GROUP BY in the same query, so repeat the expression or group by the underlying column.

    SELECT Department,
       COUNT(*) AS EmployeeCount,
       AVG(Salary) AS AverageSalary
FROM Employees
GROUP BY Department
ORDER BY Department;

    Key learning: GROUP BY produces one row per distinct grouping key with aggregates calculated separately for each group.

    Q19. What is the difference between HAVING and WHERE?

    Answer: WHERE filters individual rows before grouping happens. It cannot use aggregate functions, because aggregates are not calculated until rows are grouped. Use WHERE to exclude rows that should never be counted, such as orders before a start date.

    HAVING filters groups after grouping happens. It can use aggregate functions, so it answers questions such as which departments have an average salary above a threshold or which customers placed more than ten orders. You can use WHERE and HAVING in the same query: WHERE narrows the rows first, GROUP BY forms the groups, and HAVING keeps only the groups that pass its test.

    SELECT Department,
       AVG(Salary) AS AverageSalary
FROM Employees
WHERE HireDate >= '2020-01-01'
GROUP BY Department
HAVING AVG(Salary) > 60000;

    Key learning: WHERE filters individual rows before grouping and HAVING filters groups after grouping.

    Q20. How do you return subtotals and a grand total in one query?

    Answer: Use GROUPING SETS to list exactly which groupings you want in one pass: one set per detail level, one per subtotal level, and an empty set for the grand total. GROUPING SETS is the most explicit option and the one to reach for first, because it returns only the groupings you ask for. ROLLUP is a shorthand for hierarchical subtotals from left to right, and CUBE returns subtotals for every combination of the grouping columns, which is usually more than you need.

    Subtotal rows show NULL in the rolled-up columns, and that NULL is ambiguous: it could be a subtotal marker or a real NULL in the data. The GROUPING function returns 1 for a subtotal NULL and 0 for a real value, so use it to label the subtotal rows. GROUPING_ID does the same for several columns at once. Prefer GROUPING SETS over separate UNION ALL queries, because it scans the table once instead of once per level.

    -- Detail rows, country subtotals, and a grand total in one pass
SELECT Country, City, COUNT(*) AS CustomerCount,
       GROUPING(Country) AS IsCountryTotal,
       GROUPING(City) AS IsCityTotal
FROM Customers
GROUP BY GROUPING SETS (
    (Country, City),   -- detail rows
    (Country),         -- country subtotals
    ()                 -- grand total
);

-- ROLLUP shorthand for the same hierarchy
SELECT Country, City, COUNT(*) AS CustomerCount
FROM Customers
GROUP BY ROLLUP (Country, City);

    Key learning: Use GROUPING SETS to list the exact subtotals and grand total you want in one pass, and use the GROUPING function to tell a subtotal NULL apart from a real NULL.

    Q21. How do you find duplicate rows in a table?

    Answer: First decide which columns define a duplicate: two rows are duplicates only when every column in that set matches. The fastest way to find them is GROUP BY on those columns with HAVING COUNT(*) > 1, which returns each duplicated combination and how many times it appears. That tells you the scale of the problem before you delete anything.

    To remove the extras, use ROW_NUMBER() OVER (PARTITION BY the duplicate columns ORDER BY the column that decides which row to keep) in a CTE, then delete the rows numbered 2 and above. ORDER BY decides the survivor, for example the earliest created row or the latest updated row, so choose it deliberately and always check the count in a SELECT first. Never delete duplicates without a backup or a transaction you can roll back, and fix the cause afterwards, usually with a UNIQUE constraint or a unique index.

    -- Find the duplicated combinations and how many times each appears
SELECT CustomerID, Email, COUNT(*) AS DuplicateCount
FROM Customers
GROUP BY CustomerID, Email
HAVING COUNT(*) > 1;

-- Keep the earliest row per duplicate set, delete the rest
WITH RankedCustomers AS (
    SELECT CustomerID,
           ROW_NUMBER() OVER (
               PARTITION BY Email
               ORDER BY CreatedDate ASC
           ) AS RowNum
    FROM Customers
)
DELETE FROM RankedCustomers
WHERE RowNum > 1;

    Key learning: GROUP BY with HAVING COUNT(*) > 1 finds duplicates, and ROW_NUMBER() in a CTE deletes the extras while ORDER BY decides which row survives.

    Q22. How do you split a comma-separated string into rows?

    Answer: Use STRING_SPLIT, available since SQL Server 2016. It takes the string and the separator and returns a table with one row per value in a column named value. It is the answer an interviewer wants, and it replaces the old workarounds of looping through the string or using an XML trick. For ordered results, SQL Server 2022 added an optional third argument that returns an ordinal column with the position of each value.

    Two details matter. First, STRING_SPLIT does not guarantee the order of the returned rows before SQL Server 2022, so if order matters, use the ordinal argument on 2022 or a different method. Second, it does not trim spaces, so 'Sales, HR' returns ' HR' with a leading space unless you wrap the result in TRIM. The deeper point to make in an interview is that a comma-separated list in a column is usually a design smell: a properly normalized table would store one value per row in the first place.

    -- Split a list into rows, trimming spaces
SELECT TRIM(value) AS Tag
FROM STRING_SPLIT('Sales,HR,IT', ',');

-- SQL Server 2022 and later: keep the original order with ordinal
SELECT value, ordinal
FROM STRING_SPLIT('Sales,HR,IT', ',', 1)
ORDER BY ordinal;

    Key learning: Use STRING_SPLIT to turn a delimited string into rows, use the 2022 ordinal argument when order matters, and remember a comma-separated column is usually a design smell.

    Q23. How do you get the first and last day of the current month, and all rows from the last 30 days?

    Answer: Build the first day with DATEFROMPARTS from the current year and month, and get the last day with EOMONTH, which returns the last day of the month containing a date and accepts an optional month offset. For the last 30 days, use a range on the date column: OrderDate >= DATEADD(DAY, -30, CAST(GETDATE() AS DATE)) AND OrderDate < CAST(GETDATE() AS DATE). The range form matters because it is SARGable: SQL Server can seek the index on OrderDate instead of scanning the table.

    The common mistake is to wrap the column in a function, such as DATEDIFF(DAY, OrderDate, GETDATE()) <= 30. That works, but it makes the predicate non-SARGable, so the optimizer cannot use an index seek and scans instead. Keep the column bare and put the calculation on the constant side. Also prefer SYSDATETIME and SYSUTCDATETIME over GETDATE for new code, because they return DATETIME2 with higher precision, and use UTC when the application spans time zones.

    -- First and last day of the current month
SELECT DATEFROMPARTS(YEAR(GETDATE()), MONTH(GETDATE()), 1) AS FirstDayOfMonth,
       EOMONTH(GETDATE()) AS LastDayOfMonth,
       EOMONTH(GETDATE(), 1) AS LastDayOfNextMonth;

-- All rows from the last 30 days, SARGable so the index seek works
SELECT OrderID, OrderDate, TotalAmount
FROM Orders
WHERE OrderDate >= DATEADD(DAY, -30, CAST(GETDATE() AS DATE))
  AND OrderDate < CAST(GETDATE() AS DATE);

    Key learning: Use DATEFROMPARTS and EOMONTH for month boundaries, and filter date ranges with a bare column and a computed constant so the index seek still works.

    Q24. What is the difference between COALESCE and ISNULL, and when does it matter?

    Answer: Both replace NULL with another value, but they differ in three ways that interviewers test. First, COALESCE takes any number of arguments and returns the first non-NULL one, while ISNULL takes exactly two. Second, COALESCE is standard SQL and ISNULL is specific to T-SQL, so COALESCE is the portable choice. Third, and most important in practice, ISNULL returns the data type of its first argument, so a replacement value can be silently truncated to fit, while COALESCE follows data type precedence across all its arguments.

    There is one more subtle difference: COALESCE is expanded to a CASE expression, so an argument that is a subquery or a function can be evaluated more than once, while ISNULL evaluates its arguments once. In practice, use COALESCE when you have several fallbacks or want portable code, and use ISNULL when you have exactly two values and want the result typed as the first one. Either is fine for a single simple fallback, and saying so is a good answer.

    -- COALESCE: any number of fallbacks, standard SQL
SELECT EmployeeID,
       COALESCE(Phone, Email, 'No contact') AS PreferredContact
FROM Employees;

-- ISNULL: exactly two arguments, result typed as the first one
SELECT EmployeeID,
       ISNULL(Phone, 'No phone') AS PhoneOrDefault
FROM Employees;

-- The truncation trap: ISNULL returns the type of its first argument
DECLARE @Short VARCHAR(5) = NULL;
SELECT ISNULL(@Short, 'Longer default');  -- returns 'Longe', truncated to 5
SELECT COALESCE(@Short, 'Longer default'); -- returns 'Longer default'

    Key learning: COALESCE takes any number of arguments and is standard SQL, ISNULL takes two and returns the type of its first argument, which can silently truncate the replacement value.
