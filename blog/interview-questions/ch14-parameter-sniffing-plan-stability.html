Chapter 14: Parameter Sniffing & Plan Stability

Parameter sniffing is one of the most common causes of a query that is fast for one value and slow for another. This chapter explains how SQL Server builds one plan from the first parameter value it sees, how to prove sniffing with a simple test, and how to choose a fix that fits the workload. It also covers plan stability tools in Query Store, Query Store hints, and SQL Server 2022 Parameter Sensitive Plan optimization.

In this chapter:

  • →What parameter sniffing is and how it produces a plan that fits one value badly for others
  • →How to test for sniffing by comparing plans and using OPTION (RECOMPILE)
  • →The fix ladder from RECOMPILE and OPTIMIZE FOR to local variables and branching
  • →Parameter Sensitive Plan optimization in SQL Server 2022
  • →Query Store hints, plan forcing, and Automatic Plan Correction
  • →How to verify a forced plan and diagnose fast in SSMS and slow from the app

    • Key learning: A good fix starts with proof, not a hint, so test with different values and OPTION (RECOMPILE) before changing code. Choose the least invasive fix that stays stable when data and statistics change, and verify the result with runtime statistics after forcing or tuning. Plan stability is ongoing work, because a plan that is good today can go bad after a statistics update or a workload shift.

    Q145. What is parameter sniffing, and how does it cause bad execution plans?

    Answer: Parameter sniffing is the behavior where SQL Server looks at the actual parameter values supplied on first compile and builds an execution plan optimized for those values. That plan is then cached and reused for later executions with different values. When data distribution is uneven, a plan that is ideal for one value can be very poor for another value.

    For example, a selective customer with only a few orders is best served by an index seek, while a common customer with many orders may be best served by a scan. If the procedure is first compiled for the selective customer, later calls for the common customer reuse the seek plan and perform many inefficient lookups. If it is first compiled for the common customer, later calls for the selective customer reuse the scan plan and read far more data than needed.

    The problem is not sniffing itself, because sniffing often produces good plans. The problem is plan reuse across values with very different selectivity, especially when statistics are stale, data is skewed, or the first compiled value is an outlier. That is why the same procedure can be fast in testing and slow in production, or fast at one time of day and slow at another.

    CREATE OR ALTER PROCEDURE dbo.GetOrdersByCustomer
    @CustomerID INT
AS
BEGIN
    SELECT OrderID, CustomerID, OrderDate, Status, TotalAmount
    FROM dbo.Orders
    WHERE CustomerID = @CustomerID
    ORDER BY OrderDate DESC;
END;

EXEC dbo.GetOrdersByCustomer @CustomerID = 101;
EXEC dbo.GetOrdersByCustomer @CustomerID = 207;

    Key learning: Parameter sniffing happens when one compiled plan built for one value is reused for very different values that need a different plan.

    Q146. How do you test whether a slow query is caused by parameter sniffing?

    Answer: Run the query with two very different parameter values and compare the actual execution plans, logical reads, and duration. Use a selective value that returns few rows, such as customer 101, and a common value that returns many rows, such as customer 207. If the plans differ in shape or one value is fast while the other is slow with the same cached plan, sniffing is a strong suspect. Enable statistics for IO and time so the comparison is based on reads and duration, not only on elapsed time.

    The settling test is OPTION (RECOMPILE). Run the slow value with OPTION (RECOMPILE) so SQL Server builds a fresh plan for that exact value using current statistics. If the slow value becomes fast with RECOMPILE and slow again without it, parameter sniffing is the likely cause. Also check the plan cache to confirm that one plan is being reused across values, and check whether the problem follows the first compiled value after a recompile.

    Do not clear the whole plan cache in production to test. Test in a non-production copy or use a targeted recompile for the single statement or procedure, and capture plans before and after so the evidence is repeatable. A test that only shows one slow run without a RECOMPILE comparison does not prove sniffing.

    SET STATISTICS IO, TIME ON;

SELECT OrderID, CustomerID, OrderDate, Status, TotalAmount
FROM dbo.Orders
WHERE CustomerID = 101;

SELECT OrderID, CustomerID, OrderDate, Status, TotalAmount
FROM dbo.Orders
WHERE CustomerID = 207;

SELECT OrderID, CustomerID, OrderDate, Status, TotalAmount
FROM dbo.Orders
WHERE CustomerID = 207
OPTION (RECOMPILE);

SET STATISTICS IO, TIME OFF;

    Key learning: If two values produce very different plans and RECOMPILE fixes the slow value, parameter sniffing is the likely cause.

    Q147. How does OPTION (RECOMPILE) fix parameter sniffing, and when should you use it?

    Answer: OPTION (RECOMPILE) forces SQL Server to compile a fresh plan for every execution using the actual runtime parameter values and current statistics. The plan is not reused from cache for that statement, so each value gets a plan built for its own selectivity. This removes the stale-plan reuse that causes sniffing problems and is the most direct fix when values differ greatly.

    Use RECOMPILE when the query runs infrequently, when compile cost is small compared with execution savings, or when correctness and stable performance across values matter more than CPU spent on compilation. It is a good fit for reports, ad hoc queries with skewed parameters, and procedures where a bad plan is very expensive. Statement-level RECOMPILE affects only that statement, while procedure-level RECOMPILE affects the whole procedure, so prefer statement level to limit the cost.

    Do not use RECOMPILE blindly on high-frequency OLTP queries. Frequent recompilation adds CPU overhead, can increase compile contention, and can hurt throughput when the query runs hundreds of times per second. Measure compile CPU and execution savings, and consider a more targeted fix such as OPTIMIZE FOR, branching, or Parameter Sensitive Plan optimization when the query is hot.

    CREATE OR ALTER PROCEDURE dbo.GetOrdersByCustomer
    @CustomerID INT
AS
BEGIN
    SELECT OrderID, CustomerID, OrderDate, Status, TotalAmount
    FROM dbo.Orders
    WHERE CustomerID = @CustomerID
    ORDER BY OrderDate DESC
    OPTION (RECOMPILE);
END;

    Key learning: RECOMPILE trades compile cost for a plan built for the current values, so use it where correctness matters more than compile overhead.

    Q148. How do OPTIMIZE FOR and OPTIMIZE FOR UNKNOWN work, and when should you use each one?

    Answer: OPTIMIZE FOR tells the optimizer to build the plan as if a specific parameter value had been supplied, regardless of the runtime value. For example, OPTIMIZE FOR with customer 101 builds a plan suited to a selective value, and that plan is reused for all values. Use it when one value dominates the workload, when you know the typical value that must perform well, or when you need a stable plan and can accept poorer performance for outlier values.

    OPTIMIZE FOR UNKNOWN tells the optimizer to ignore the runtime value and use average distribution statistics instead of sniffing a specific value. The result is a middle-ground plan that is stable across values but rarely optimal for extreme values. Use it when no single value dominates, when values vary widely, and when stability matters more than peak performance for any one value.

    Both hints freeze the optimization choice at compile time and do not adapt when data distribution changes. Revisit the choice after major data changes, statistics updates, or workload shifts, and verify with runtime statistics that the chosen plan still performs well for the values that matter most.

    DECLARE @CustomerID INT = 207;

SELECT OrderID, CustomerID, OrderDate, Status, TotalAmount
FROM dbo.Orders
WHERE CustomerID = @CustomerID
OPTION (OPTIMIZE FOR (@CustomerID = 101));

SELECT OrderID, CustomerID, OrderDate, Status, TotalAmount
FROM dbo.Orders
WHERE CustomerID = @CustomerID
OPTION (OPTIMIZE FOR UNKNOWN);

    Key learning: OPTIMIZE FOR pins the plan to a chosen value while OPTIMIZE FOR UNKNOWN pins it to average distribution, and neither adapts when data changes.

    Q149. How can local variables defeat parameter sniffing, and what is the trade-off?

    Answer: Copying a parameter into a local variable hides the runtime value from the optimizer at compile time. The optimizer does not know the local variable value when it builds the plan, so it uses average density statistics to estimate rows, similar to OPTIMIZE FOR UNKNOWN. The result is a single stable plan that does not change based on the first compiled value.

    This is simple to implement and requires no query hint, which makes it attractive for legacy code. It works best when values are moderately skewed and a stable average plan performs acceptably for most executions. It is also useful when you cannot easily add hints or when you need a quick stabilization while a better fix is tested.

    The trade-off is that the average plan is rarely optimal for extreme values. A selective value that should use a seek may get a scan, and a common value that should use a scan may get a seek with many lookups. For highly skewed data, local variables can stabilize performance at a mediocre level rather than fixing the slow case, so measure reads and duration for both selective and common values before keeping this fix.

    CREATE OR ALTER PROCEDURE dbo.GetOrdersByCustomer
    @CustomerID INT
AS
BEGIN
    DECLARE @LocalCustomerID INT = @CustomerID;

    SELECT OrderID, CustomerID, OrderDate, Status, TotalAmount
    FROM dbo.Orders
    WHERE CustomerID = @LocalCustomerID
    ORDER BY OrderDate DESC;
END;

    Key learning: Local variables hide the runtime value from the optimizer and produce an average plan that is stable but rarely optimal for extreme values.

    Q150. When should you use IF/ELSE branching or separate procedures to handle parameter sniffing?

    Answer: Use branching when different parameter values genuinely need different plans and the split between them is clear, stable, and easy to maintain. An IF/ELSE block lets each branch compile its own plan for its own value range, so a common customer can use one plan shape while other customers use another. This is effective when the skew is driven by a small number of known values or by a clear threshold, such as a status, region, or high-volume customer.

    Separate procedures go one step further by giving each path its own cached plan and its own tuning surface. A wrapper procedure can route to a procedure for common values and a procedure for selective values, which keeps each plan independent and easier to test. This is cleaner when the logic differs beyond a single predicate or when each path needs different hints, indexes, or maintenance.

    The cost is duplication and maintenance risk. Logic must be kept in sync across branches, and a new skewed value can fall through the wrong branch if the split is hard-coded. Use branching only after proving sniffing with the RECOMPILE test, keep the branch condition simple and documented, and recheck the split when data distribution changes.

    CREATE OR ALTER PROCEDURE dbo.GetOrdersByCustomer
    @CustomerID INT
AS
BEGIN
    IF @CustomerID = 207
    BEGIN
        SELECT OrderID, CustomerID, OrderDate, Status, TotalAmount
        FROM dbo.Orders
        WHERE CustomerID = @CustomerID
        ORDER BY OrderDate DESC
        OPTION (OPTIMIZE FOR (@CustomerID = 207));
    END
    ELSE
    BEGIN
        SELECT OrderID, CustomerID, OrderDate, Status, TotalAmount
        FROM dbo.Orders
        WHERE CustomerID = @CustomerID
        ORDER BY OrderDate DESC
        OPTION (RECOMPILE);
    END
END;

    Key learning: Branching is the right fix when different parameter values genuinely need different plans and the split is stable and easy to maintain.

    Q151. How does Parameter Sensitive Plan optimization in SQL Server 2022 work, and what are its requirements?

    Answer: Parameter Sensitive Plan optimization allows SQL Server to store multiple execution plans for a single parameterized query and choose among them at runtime based on the parameter values. The optimizer detects that different values need different plans, builds a dispatcher plan that routes each execution to the right variant, and caches the variants together. This addresses sniffing without hints, recompilation on every run, or manual branching.

    Requirements include SQL Server 2022 and database compatibility level 160, with the database scoped configuration for Parameter Sensitive Plan optimization enabled. It applies to parameterized queries where the optimizer can identify sensitivity, typically equality predicates on skewed columns in stored procedures and parameterized batches. It does not apply to every query shape, and it still depends on statistics that reflect the skew.

    Monitor the result through Query Store and plan cache inspection, and verify that different values are actually using different variants with better reads and duration. If the feature does not trigger, the query may not meet the sensitivity criteria, statistics may not show the skew, or compatibility settings may be wrong. Treat it as a strong first option on SQL Server 2022, but still verify with runtime data.

    USE SalesDB;

SELECT name, compatibility_level
FROM sys.databases
WHERE name = N'SalesDB';

SELECT name, value, value_for_secondary
FROM sys.database_scoped_configurations
WHERE name = N'PARAMETER_SENSITIVE_PLAN_OPTIMIZATION';

ALTER DATABASE SCOPED CONFIGURATION
SET PARAMETER_SENSITIVE_PLAN_OPTIMIZATION = ON;

    Key learning: Parameter Sensitive Plan optimization in SQL Server 2022 keeps separate plans for different parameter sensitivities when the database meets the compatibility and configuration requirements.

    Q152. What are Query Store hints, and when do you use them?

    Answer: Query Store hints, available from SQL Server 2022, attach a query hint to a query that is already captured in Query Store, without changing the application code. Find the query_id in the Query Store catalog views, then call sp_query_store_set_hints with an OPTION string, for example OPTION(RECOMPILE) for a query that suffers from parameter sniffing, or OPTION(MAXDOP 1) for a query that parallelizes badly. The hint applies to that query_id only, and it overrides statement-level hints and plan guides.

    Use them as a targeted, last-resort fix when you cannot change the query text: vendor code, framework-generated SQL, or a query owned by another team. Verify the hint in sys.query_store_query_hints and confirm the plan actually changed in the Query Store reports, because a hint that does not help is worse than no hint. Remove a hint with sp_query_store_clear_hints. SQL Server 2025 adds ABORT_QUERY_EXECUTION, which blocks a known bad query from running at all.

    Plan guides are the legacy mechanism for the same job: they match incoming query text and apply a hint at compile time, but they break when the text changes by even a whitespace, and they are invisible to anyone reading the application. Prefer Query Store hints, which are tied to a stable query_id and visible in the Query Store views, and keep plan guides only for versions that do not have Query Store hints.

    -- Find the query_id for the slow query in Query Store
SELECT q.query_id, qt.query_sql_text
FROM sys.query_store_query_text AS qt
INNER JOIN sys.query_store_query AS q
    ON q.query_text_id = qt.query_text_id
WHERE qt.query_sql_text LIKE N'%GetOrdersByCustomer%';

-- Attach a RECOMPILE hint to that query, no code change needed
EXEC sys.sp_query_store_set_hints
    @query_id = 39,
    @query_hints = N'OPTION(RECOMPILE)';

-- Verify the hint and remove it when no longer needed
SELECT query_id, query_hint_text
FROM sys.query_store_query_hints
WHERE query_id = 39;

EXEC sys.sp_query_store_clear_hints @query_id = 39;

    Key learning: Query Store hints attach an OPTION hint to a query_id without changing application code, they override plan guides, and they are the modern replacement for fragile text-matched plan guides.

    Q153. How do you force a plan with Query Store, and what safeguards and verification steps apply?

    Answer: Query Store plan forcing pins a specific execution plan for a query so the optimizer reuses it instead of choosing a new plan. Identify the query and the good plan in Query Store, verify the plan with runtime statistics, then force it with the Query Store procedure. Keep the query identifier and plan identifier from the Query Store views so the force operation targets the exact plan you tested.

    Safeguards start with testing and reversibility. Test the forced plan in a non-production environment with representative data and workload, document the reason for forcing and the expected improvement, and set a review date to recheck the force. Forcing can fail if the schema changes, if the plan is no longer valid, or if statistics change the plan shape, so check force status and failure reasons after forcing and after deployments.

    Verification is mandatory, not optional. Compare duration, CPU, logical reads, and execution count before and after forcing, and confirm the forced plan is actually being used. Unforce the plan promptly if performance gets worse or if a better plan emerges, and keep Query Store enabled so you can see regressions and forcing history over time.

    USE SalesDB;

SELECT
    q.query_id,
    p.plan_id,
    p.is_forced_plan,
    q.last_execution_time
FROM sys.query_store_query AS q
JOIN sys.query_store_plan AS p
    ON p.query_id = q.query_id
WHERE q.object_id = OBJECT_ID(N'dbo.GetOrdersByCustomer')
ORDER BY q.last_execution_time DESC;

EXEC sys.sp_query_store_force_plan @query_id = 12, @plan_id = 34;
EXEC sys.sp_query_store_unforce_plan @query_id = 12, @plan_id = 34;

    Key learning: Force only a plan you have verified with runtime statistics, keep the forcing reversible, and recheck it after data and workload changes.

    Q154. How does Automatic Plan Correction work, and what are its limits?

    Answer: Automatic Plan Correction uses Query Store history to detect plan regressions and force the last good plan automatically. When Query Store is enabled and automatic tuning for FORCE_LAST_GOOD_PLAN is on, SQL Server compares recent performance with earlier baseline performance for the same query. If it finds a regression with enough confidence, it creates a tuning recommendation and forces the last good plan, then verifies the improvement.

    The feature helps with regressions caused by plan changes, such as a new plan after a statistics update or recompilation that performs worse than the previous plan. It is valuable because it can respond faster than manual review and because it keeps a record of recommendations, actions, and verification results. It still requires Query Store to be enabled and in read-write mode, with enough history to compare.

    Limits are important. Automatic Plan Correction only addresses regressions it can detect and verify from Query Store data, and it does not fix missing indexes, bad statistics, parameter sniffing root causes, or resource pressure. It can only force a previous good plan that still exists and is still valid, and it will not help if no good plan was ever captured. Monitor recommendations and forced plans, and treat automatic correction as a safety net, not a replacement for tuning.

    USE SalesDB;

SELECT
    name,
    desired_state_desc,
    actual_state_desc,
    reason_desc
FROM sys.database_automatic_tuning_options
WHERE name = N'FORCE_LAST_GOOD_PLAN';

SELECT
    name,
    type,
    state_desc
FROM sys.dm_db_tuning_recommendations;

    Key learning: Automatic Plan Correction can force the last good plan for a regression, but it only helps Query Store regressions it can verify with confidence.

    Q155. Why is a forced plan not necessarily a recovered query, and how do you verify the fix?

    Answer: A forced plan only tells the optimizer which plan shape to use, and it does not guarantee that the query is fast again. Data distribution, parameter values, statistics, indexes, and resource pressure can all make a previously good plan perform poorly today. Forcing can also fail silently in effect if the plan is not used, if the force is ignored due to a schema change, or if the workload has shifted to values the forced plan does not suit.

    Verify with runtime statistics after forcing, not only with the force status. Check duration, CPU, logical reads, physical reads, and execution count for the forced plan in Query Store, and compare with the period before forcing under similar workload. Confirm the plan in use is the forced plan, check for force failures, and test the selective and common parameter values separately so a single average does not hide a slow case.

    Re-check after statistics updates and workload shifts, because a forced plan that is good today can go bad tomorrow. Set a review date, re-measure after major data loads, index changes, or statistics updates, and unforce if the query regresses or if a new plan performs better. A fix is only proven when the query stays fast under real workload over time, not when the force command succeeds.

    USE SalesDB;

SELECT
    p.plan_id,
    p.is_forced_plan,
    rs.count_executions,
    rs.avg_duration,
    rs.avg_logical_io_reads,
    rs.last_execution_time
FROM sys.query_store_plan AS p
JOIN sys.query_store_runtime_stats AS rs
    ON rs.plan_id = p.plan_id
WHERE p.query_id = 12
ORDER BY rs.last_execution_time DESC;

    Key learning: A forced plan is only a fix when runtime statistics after forcing show the query is actually fast again under real workload.

    Q156. Scenario: A report runs fast in SSMS but slow from the application. How do you diagnose it?

    Answer: First, compare SET options and execution plans for the SSMS session and the application session. SSMS and application drivers often use different default SET options, and different options can produce different cached plans for the same query text. Check ARITHABORT in particular, because SSMS sets it ON by default while many application connections leave it OFF, and that difference alone can lead to a different plan. Capture the actual plan and session options from both sides before changing code.

    Next, check for parameter sniffing and different parameter values. The report may be fast in SSMS because it was tested with a selective value and slow from the app because it runs with a common value, or vice versa. Compare the query hash in the plan cache to see whether multiple plans exist for the same query, and test the slow value with OPTION (RECOMPILE) to see whether a fresh plan fixes it. Also confirm the database, user, connection settings, and data are the same, because a different database or stale statistics in one environment can mimic a plan problem.

    Fix the root cause, not the symptom. Align SET options where the application allows it, fix sniffing with the appropriate ladder step, and verify the application plan after the change with runtime statistics. Do not conclude the application is at fault until you have compared options, values, and plans side by side with evidence from both sessions.

    DBCC USEROPTIONS;

SELECT session_id, login_name, program_name, arithabort, ansi_nulls, quoted_identifier
FROM sys.dm_exec_sessions
WHERE is_user_process = 1;

SELECT
    query_hash,
    COUNT(DISTINCT plan_handle) AS plan_count,
    SUM(execution_count) AS total_executions
FROM sys.dm_exec_query_stats
GROUP BY query_hash
HAVING COUNT(DISTINCT plan_handle) > 1
ORDER BY total_executions DESC;

    Key learning: Different SET options or different parameter values can produce different plans, so compare options and plans before assuming the application is at fault.
