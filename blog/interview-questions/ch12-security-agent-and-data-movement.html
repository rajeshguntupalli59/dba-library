Chapter 12: Security, Agent and Data Movement

Security controls who can connect and what they can do, Agent automates the work that must run on schedule, and data movement tools copy and transform data between systems. This chapter connects those three areas because interviewers often test them together. You need the principal model, the role model, and a working picture of Agent, SSIS, and encryption.

In this chapter:

  • →Logins versus users and server principals versus database principals
  • →Fixed server roles and fixed database roles
  • →GRANT, DENY, REVOKE, permission hierarchy, and ownership chaining
  • →Orphaned users after a restore and how to fix them
  • →SQL Server Agent jobs, steps, schedules, operators, and alerts
  • →SSIS packages and the SSISDB catalog
  • →TDE versus Always Encrypted, and Azure SQL deployment options

    • Key learning: Use least privilege through roles and schemas, automate routine work with Agent jobs you can audit, and choose the data movement tool that fits where the data lives and who will maintain it. The Azure choice follows the same rule: pick the platform service that removes the most undifferentiated administration without breaking compatibility.

    Q123. What is the difference between a login and a user, and between server principals and database principals?

    Answer: A login is a server-level principal used for authentication. It proves who you are when you connect, using Windows authentication or SQL Server authentication, and it needs CONNECT SQL permission to connect at all. A user is a database-level principal used for authorization. It controls what you can do inside one database, and it is mapped to a login by security identifier.

    Server principals include logins and server roles, and they are stored in sys.server_principals. Database principals include users, database roles, and application roles, and they are stored in sys.database_principals. A login with no mapped user in a database cannot access that database, except through guest access or a contained user. After a restore to another server, a user whose login is missing or has a different identifier becomes orphaned and must be remapped.

    CREATE LOGIN AppLogin WITH PASSWORD = 'StrongPassword123!';
GO
USE SalesDB;
GO
CREATE USER AppUser FOR LOGIN AppLogin;
GO
ALTER ROLE db_datareader ADD MEMBER AppUser;
GO

    Key learning: A login proves who you are at the server level and a user controls what you can do inside one database, so a login without a mapped user cannot access that database.

    Q124. What are the fixed server roles and fixed database roles, and when should each be used?

    Answer: Fixed roles bundle common permissions and cannot be changed or dropped, but you can add and remove members. Fixed server roles apply at the server level and include sysadmin for full control, securityadmin for managing logins and permissions, serveradmin for server settings, setupadmin for linked servers, processadmin for ending processes, diskadmin for disk files, dbcreator for creating databases, bulkadmin for bulk inserts, and public for every login.

    Fixed database roles apply inside one database and include db_owner for full control of the database, db_accessadmin for adding users, db_securityadmin for managing permissions, db_ddladmin for creating and altering objects, db_backupoperator for backups, db_datareader for reading all tables, db_datawriter for writing all tables, db_denydatareader for denying all reads, and db_denydatawriter for denying all writes. Use the narrowest role that covers the job, prefer custom roles for application permissions, and reserve sysadmin and db_owner for a small number of trusted accounts.

    ALTER SERVER ROLE securityadmin ADD MEMBER AuditLogin;
GO
USE SalesDB;
GO
ALTER ROLE db_datareader ADD MEMBER AppUser;
GO
ALTER ROLE db_datawriter ADD MEMBER AppUser;
GO

    Key learning: Fixed roles bundle common permissions for convenience, but least privilege means granting only the narrowest fixed or custom role that covers the job.

    Q125. How do GRANT, DENY, and REVOKE work, and what are the permission hierarchy and ownership chaining?

    Answer: GRANT allows a permission, DENY explicitly blocks it, and REVOKE removes a prior GRANT or DENY and returns the permission to a neutral state. DENY always wins over GRANT, so a user who is denied a permission cannot use it even if another role grants it. REVOKE does not block access, it only removes the explicit grant or deny, so access can still come from another grant.

    Permissions form a hierarchy from server to database to schema to object, and a permission granted at a higher level covers the levels below it unless a DENY blocks it. Ownership chaining means that when a view or procedure and the tables it reads have the same owner, SQL Server checks permission only on the outer object and skips checks on the underlying objects. The chain breaks when ownership changes, when dynamic SQL is used, or when objects are in different databases, unless cross-database ownership chaining is enabled.

    USE SalesDB;
GO
GRANT SELECT, INSERT ON dbo.Orders TO AppUser;
GO
DENY DELETE ON dbo.Orders TO AppUser;
GO
REVOKE INSERT ON dbo.Orders FROM AppUser;
GO

    Key learning: DENY always beats GRANT, REVOKE simply removes a prior grant or deny, and ownership chaining skips checks only while every object in the chain has the same owner.

    Q126. After restoring a database on another server, logins cannot connect. What are orphaned users, and how do you fix them?

    Answer: A database user is mapped to a server login by SID, not by name. A backup carries the database users with their SIDs, but it does not carry the logins. After a restore on another server, the login either does not exist or exists with the same name but a different SID, so the user is orphaned: the name matches, the SID does not, and the login fails with "Login failed for user" even though the password is right. This is one of the first things to check after any restore or migration.

    Find orphans by comparing sys.database_principals against sys.server_principals on SID, or with the report mode of the older sp_change_users_login procedure. Fix each one by remapping the user to the correct login with ALTER USER ... WITH LOGIN, and create the login first if it does not exist on the new server. The cleanest prevention is contained database users, which store the authentication inside the database itself, so a restore to another server just works. Always verify logins as part of a restore drill, not only the data.

    -- Find orphaned users: database users with no matching login SID
SELECT dp.name AS OrphanedUser, dp.sid
FROM sys.database_principals AS dp
LEFT JOIN sys.server_principals AS sp
    ON sp.sid = dp.sid
WHERE dp.type IN ('S', 'U')
  AND dp.name NOT IN ('dbo', 'guest', 'INFORMATION_SCHEMA', 'sys')
  AND sp.sid IS NULL;

-- Fix by remapping the user to the correct login
ALTER USER AppUser WITH LOGIN = AppUser;

-- Prevent it entirely with a contained database user
CREATE USER AppUser WITH PASSWORD = 'UseA-Strong-Password-1';
ALTER DATABASE SalesDB SET CONTAINMENT = PARTIAL;

    Key learning: Users map to logins by SID, so a restore orphans them when the login is missing or has a different SID; remap with ALTER USER ... WITH LOGIN, or use contained users to avoid the problem.

    Q127. How does SQL Server Agent work, including jobs, steps, schedules, operators, and alerts?

    Answer: SQL Server Agent is the scheduling and automation service for SQL Server, and its definitions and history are stored in msdb. A job is a unit of work, made up of one or more steps that run in order. Each step has a type, such as Transact-SQL, SSIS package, PowerShell, or operating system command, and each step defines what happens on success and on failure, including moving to the next step, quitting, or retrying.

    A schedule controls when a job runs, on a recurring pattern, at a single time, when Agent starts, or when CPU usage is idle. An operator is a person or group that receives notifications, usually by email through Database Mail. An alert responds to an event, such as a specific error number, a severity level, or a performance condition, and can run a job or notify an operator. Proxies let non-sysadmin job owners run steps under a stored credential with only the permissions that step needs.

    SELECT j.name AS job_name, j.enabled, s.name AS step_name, s.command, sch.name AS schedule_name
FROM msdb.dbo.sysjobs AS j
INNER JOIN msdb.dbo.sysjobsteps AS s ON s.job_id = j.job_id
LEFT JOIN msdb.dbo.sysjobschedules AS js ON js.job_id = j.job_id
LEFT JOIN msdb.dbo.sysschedules AS sch ON sch.schedule_id = js.schedule_id
WHERE j.enabled = 1
ORDER BY j.name, s.step_id;

    Key learning: A job is a sequence of steps run on a schedule, with operators and alerts telling the right people when it succeeds, fails, or hits a monitored condition.

    Q128. What is SSIS, and how do packages, control flow, data flow, and the SSISDB catalog fit together?

    Answer: SQL Server Integration Services, or SSIS, is the extract, transform, and load platform for SQL Server. A package is a saved workflow file with a .dtsx extension that defines one integration task. Packages are built in SQL Server Data Tools, use connection managers for sources and destinations, and use variables and parameters for values that change between environments.

    Control flow is the workflow layer: tasks, containers, and precedence constraints that define the order of work, such as running a SQL task, then a data flow, then sending an email. Data flow is the pipeline layer inside a Data Flow Task: sources read rows, transformations clean, join, aggregate, or convert them, and destinations write them, with data moving through memory buffers for speed. With project deployment, packages are deployed as a project to the SSISDB catalog database, which stores folders, projects, environments, execution history, and logging, and lets you run and monitor packages from SQL Server Management Studio.

    SELECT e.execution_id, e.folder_name, e.project_name, e.package_name, e.status, e.start_time, e.end_time
FROM SSISDB.catalog.executions AS e
ORDER BY e.start_time DESC;

    Key learning: Control flow orchestrates the work, data flow moves and transforms the rows, and the SSISDB catalog stores, runs, and logs deployed projects.

    Q129. Transparent Data Encryption or Always Encrypted — how do you choose?

    Answer: Transparent Data Encryption, or TDE, encrypts the data files, log file, and backups at rest. A database encryption key protected by a certificate in master encrypts every page as it is written, and the application sees nothing different. TDE protects a stolen disk, a stolen backup, or a detached data file, but it does not protect data in memory or on the network: once a page is read into the buffer pool it is decrypted, and traffic still needs TLS. A TDE backup can only be restored on a server that has the certificate and private key, so back those up separately and test the restore.

    Always Encrypted encrypts individual columns, and the keys never reach the engine: the column master key lives with the application or in a key vault, and the client driver encrypts values before sending them. That protects sensitive columns from DBAs, from cloud operators, and from memory dumps. The trade-offs are real: randomized encryption cannot be searched, joined, or range-filtered, deterministic encryption allows equality only, and some operations and data types are unsupported, so it needs application and driver support.

    Choose TDE when the requirement is encryption at rest and compliance for files and backups. Choose Always Encrypted when specific columns must stay hidden from everyone who can touch the server, including administrators. The two can be combined: TDE for the files, Always Encrypted for the columns that must never be visible in plaintext on the server.

    -- TDE: master key, certificate, database encryption key, then switch on
USE master;
CREATE MASTER KEY ENCRYPTION BY PASSWORD = 'UseA-Strong-Password-1';
CREATE CERTIFICATE TDECert WITH SUBJECT = 'TDE Certificate';
GO
USE SalesDB;
CREATE DATABASE ENCRYPTION KEY
WITH ALGORITHM = AES_256
ENCRYPTION BY SERVER CERTIFICATE TDECert;
ALTER DATABASE SalesDB SET ENCRYPTION ON;
GO
-- Always Encrypted: the column is encrypted by the client driver
CREATE TABLE dbo.Customers
(
    CustomerID INT PRIMARY KEY,
    NationalID NVARCHAR(11)
        COLLATE Latin1_General_BIN2
        ENCRYPTED WITH (
            COLUMN_ENCRYPTION_KEY = CEK1,
            ENCRYPTION_TYPE = DETERMINISTIC,
            ALGORITHM = 'AEAD_AES_256_CBC_HMAC_SHA_256'
        )
);

    Key learning: TDE encrypts files and backups at rest and is transparent to applications, while Always Encrypted encrypts columns with keys the engine never sees, so choose TDE for at-rest compliance and Always Encrypted when columns must stay hidden from administrators.

    Q130. How do Azure SQL Database, SQL Managed Instance, and SQL Server on an Azure VM differ, and how do you choose between them?

    Answer: Azure SQL Database is a fully managed platform service for single databases or elastic pools. Microsoft handles patching, backups, and high availability, you pay by DTU or vCore model, and you get features such as automatic tuning and serverless compute. It has no server-level access, no SQL Server Agent, and limited cross-database and instance-level features, so it fits new cloud-native applications best.

    SQL Managed Instance is also fully managed, but it offers near-complete compatibility with on-premises SQL Server at the instance level. It supports SQL Server Agent, Database Mail, linked servers, CLR, Service Broker, and native virtual network integration, so most existing applications migrate with few changes. SQL Server on an Azure VM is infrastructure as a service: you get a virtual machine with full operating system and SQL Server control, any supported version and edition, and responsibility for patching, backups, and high availability. Choose the virtual machine only when you need operating system access, a specific version, or control the platform services do not offer.

    Key learning: Choose Azure SQL Database for new cloud-native databases, Managed Instance for near-complete compatibility with minimal changes, and SQL Server on a VM only when you need full operating system control.
