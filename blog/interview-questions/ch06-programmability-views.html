Chapter 6: Programmability & Views

Views, stored procedures, functions, and triggers move reusable logic into the database, close to the data it operates on. Variables, temp storage, error handling, and transactions control how that logic runs and how it recovers when something fails. Backups and recovery models, plus the OUTPUT clause for data changes, complete the basic toolkit for safe and auditable data work.

  • →Scalar, inline table-valued, and multi-statement table-valued functions

    • Key learning: Programmability objects put reusable logic and rules inside the database, where they can be secured, shared, and kept consistent for every caller. Views simplify access, procedures and functions encapsulate work, triggers enforce row-level rules, and transactions, error handling, and backups protect correctness and recoverability.

    Q51. What is a view? What are its benefits and limitations, and what is an indexed view?

    Answer: A view is a saved SELECT statement that behaves like a virtual table. It stores no data itself: each query against the view runs the underlying query against the base tables. Views simplify complex joins into a single named object, hide columns or rows for security, and give every caller one consistent definition of a concept such as an active customer.

    Views have limits. They accept no parameters, they cannot include ORDER BY unless TOP, OFFSET, or FOR XML is also used, and INSERT, UPDATE, and DELETE through a view work only when the view maps cleanly to one base table without aggregates or DISTINCT. An indexed view goes further: created WITH SCHEMABINDING and then given a unique clustered index, its result is materialized and maintained like a table. Indexed views can speed up expensive aggregates and joins, but they carry many restrictions, including deterministic expressions and COUNT_BIG instead of COUNT, and they add overhead to writes on the base tables.

    CREATE VIEW dbo.vw_CustomerOrderCounts AS
SELECT c.CustomerID, c.CustomerName, COUNT(o.OrderID) AS OrderCount
FROM dbo.Customers AS c
LEFT JOIN dbo.Orders AS o ON o.CustomerID = c.CustomerID
GROUP BY c.CustomerID, c.CustomerName;

    Key learning: A view is a stored query that looks like a table, simplifying access and security, while an indexed view also stores its result behind a unique clustered index.

    Q52. What is a stored procedure? Explain its benefits, creation, execution, and input and output parameters.

    Answer: A stored procedure is a named batch of T-SQL stored in the database and run with EXEC. Procedures promote reuse, since one procedure can be called from many places, and security, since callers can be granted EXECUTE on the procedure without direct access to the underlying tables. They also reduce network traffic, encourage plan reuse, and let a whole multi-step operation run as one unit.

    A procedure is created with CREATE PROCEDURE, followed by its parameter list and body. Input parameters pass values in, with optional default values, and output parameters return values to the caller and must be marked OUTPUT both in the definition and at execution. Use SET NOCOUNT ON to suppress row-count messages, and avoid the sp_ prefix, which SQL Server reserves for system procedures and resolves in the master database first.

    CREATE PROCEDURE dbo.GetOrdersByCustomer
    @CustomerID INT,
    @OrderCount INT OUTPUT
AS
BEGIN
    SET NOCOUNT ON;
    SELECT OrderID, OrderDate, TotalAmount
    FROM dbo.Orders
    WHERE CustomerID = @CustomerID;
    SELECT @OrderCount = COUNT(*)
    FROM dbo.Orders
    WHERE CustomerID = @CustomerID;
END;

DECLARE @Count INT;
EXEC dbo.GetOrdersByCustomer @CustomerID = 1, @OrderCount = @Count OUTPUT;
SELECT @Count AS OrderCount;

    Key learning: A stored procedure packages reusable T-SQL behind a name, accepts input and output parameters, and is run with EXEC.

    Q53. What is the difference between scalar functions, inline table-valued functions, and multi-statement table-valued functions?

    Answer: A scalar function returns a single value, such as a number or a string, and is used in a SELECT list, WHERE clause, or expression. Its body uses BEGIN and END and finishes with RETURN. Scalar functions historically performed poorly when called once per row, although SQL Server 2019 and later can inline eligible scalar functions into the calling query.

    An inline table-valued function returns a table from a single RETURN statement containing one SELECT, with no BEGIN and END block. The optimizer expands it much like a view, so it usually performs well and is the preferred form for reusable row sets. A multi-statement table-valued function declares a table variable as its return value, fills it with several statements inside BEGIN and END, and then returns it. That flexibility comes at a cost: the optimizer has no statistics on the returned table, which can lead to poor cardinality estimates and slow plans.

    CREATE FUNCTION dbo.fn_OrdersByCustomer (@CustomerID INT)
RETURNS TABLE
AS
RETURN (
    SELECT OrderID, OrderDate, TotalAmount
    FROM dbo.Orders
    WHERE CustomerID = @CustomerID
);

SELECT OrderID, TotalAmount
FROM dbo.fn_OrdersByCustomer(1);

    Key learning: Scalar functions return one value, inline table-valued functions return a table from a single query the optimizer can expand, and multi-statement table-valued functions build a table variable with several statements at a higher performance cost.

    Q54. What is the difference between a stored procedure and a function?

    Answer: A stored procedure is executed with EXEC to perform an action, while a function is used inside a query, in a SELECT list, WHERE clause, or FROM clause, to return a value. A procedure can return several result sets, output parameters, and a return code, and it may return nothing at all. A function must return exactly one value: a scalar value or a table.

    Procedures can change data, use transactions, call other procedures, use dynamic SQL and temp tables, and handle errors with TRY and CATCH. Functions cannot modify permanent tables, cannot use TRY and CATCH or dynamic SQL, cannot create temp tables, and cannot call a procedure that has side effects. In short, use a procedure for work to be done and a function for a value to be computed as part of a query.

    DECLARE @Count INT;
EXEC dbo.GetOrdersByCustomer @CustomerID = 1, @OrderCount = @Count OUTPUT;

SELECT OrderID, TotalAmount
FROM dbo.fn_OrdersByCustomer(1);

    Key learning: Stored procedures are executed for actions and can change data and return many result sets, while functions are used inside queries and must return a single value or table without side effects.

    Q55. What are triggers? Explain AFTER vs INSTEAD OF triggers and the inserted and deleted tables.

    Answer: A trigger is a special stored procedure that fires automatically when an INSERT, UPDATE, or DELETE statement runs against a table or view. Triggers enforce rules, audit changes, and maintain related data without requiring every caller to remember the extra step. DML triggers fire once per statement, not once per row, so trigger code must handle multi-row sets.

    An AFTER trigger fires after the statement runs and after constraints are checked, and it can roll back the statement if a rule fails. An INSTEAD OF trigger replaces the triggering action: the original statement does not run, and the trigger code decides what happens instead. INSTEAD OF triggers can also be placed on views to make them updatable, while AFTER triggers cannot. Both kinds read two logical tables: inserted holds the new rows for INSERT and the after-image for UPDATE, and deleted holds the old rows for DELETE and the before-image for UPDATE. For INSERT, deleted is empty, and for DELETE, inserted is empty.

    CREATE TRIGGER dbo.trg_Orders_AfterInsert
ON dbo.Orders
AFTER INSERT
AS
BEGIN
    SET NOCOUNT ON;
    INSERT INTO dbo.OrderAudit (OrderID, CustomerID, ActionTaken, ActionDate)
    SELECT OrderID, CustomerID, 'INSERT', SYSUTCDATETIME()
    FROM inserted;
END;

    Key learning: AFTER triggers run after the change, INSTEAD OF triggers replace it, and both read the new rows from inserted and the old rows from deleted.

    Q56. How do you declare and assign variables in T-SQL, and what is the difference between table variables and temp tables?

    Answer: Variables are declared with DECLARE, using an @ prefix, a data type, and an optional initial value. SET assigns one variable at a time and raises an error if a subquery returns more than one row, while SELECT can assign several variables at once and silently keeps the last row when a query returns more than one. A useful difference: if a query returns no rows, SELECT leaves the variable unchanged, while SET with a scalar subquery sets it to NULL.

    Table variables are declared with DECLARE and a TABLE type, live only for the batch, and are stored in tempdb, not in memory. They support only inline indexes through PRIMARY KEY, UNIQUE, or CHECK constraints, have no statistics, and cannot be altered or truncated, which suits small row sets. From compatibility level 150 onward, deferred compilation gives the optimizer the actual table-variable row count at compile time, which improves plans, but table variables still have no persisted statistics object. Temp tables, created with a # prefix for a session-local table or ## for a global table, also live in tempdb but support statistics, indexes added after creation, ALTER, and TRUNCATE, which suits larger sets and complex joins. Choose table variables for small sets and temp tables when the optimizer needs statistics to plan well.

    DECLARE @TopPrice DECIMAL(10, 2);
SET @TopPrice = (SELECT MAX(UnitPrice) FROM dbo.Products);
SELECT @TopPrice AS TopPrice;

DECLARE @ActiveProducts TABLE (
    ProductID INT PRIMARY KEY,
    ProductName NVARCHAR(100) NOT NULL
);
INSERT INTO @ActiveProducts (ProductID, ProductName)
SELECT ProductID, ProductName FROM dbo.Products;

CREATE TABLE #TempProducts (
    ProductID INT PRIMARY KEY,
    ProductName NVARCHAR(100) NOT NULL
);
INSERT INTO #TempProducts (ProductID, ProductName)
SELECT ProductID, ProductName FROM dbo.Products;
DROP TABLE #TempProducts;

    Key learning: Variables hold single values assigned with SET or SELECT, table variables suit small sets with limited indexing, and temp tables suit larger sets that need statistics and indexes.

    Q57. How does error handling work in T-SQL? Explain TRY...CATCH, @@ERROR, and THROW vs RAISERROR.

    Answer: TRY...CATCH runs the TRY block and, when an error with severity above 10 occurs, transfers control to the CATCH block. Inside CATCH, the ERROR_NUMBER, ERROR_MESSAGE, ERROR_SEVERITY, ERROR_STATE, ERROR_PROCEDURE, and ERROR_LINE functions describe the error, and XACT_STATE shows whether the transaction can still be committed. Errors that abort the batch or the connection, such as compile errors and severity 20 and above, are generally not caught.

    @@ERROR holds the error number of the immediately preceding statement, or 0 when it succeeded, and it resets after every statement, so its value must be captured into a variable right away. THROW is the modern way to raise errors: a bare THROW inside CATCH rethrows the original error with its number and line, and THROW with an error number, message, and state raises a new error with severity 16. RAISERROR is the older statement: it supports formatted messages, message IDs, custom severity, and WITH LOG, but it does not preserve the original error as cleanly. Prefer THROW in new code.

    BEGIN TRY
    INSERT INTO dbo.Customers (CustomerID, CustomerName)
    VALUES (1, 'Acme Corp');
END TRY
BEGIN CATCH
    SELECT ERROR_NUMBER() AS ErrorNumber,
           ERROR_MESSAGE() AS ErrorMessage,
           ERROR_LINE() AS ErrorLine;
    THROW;
END CATCH;

    Key learning: The TRY CATCH construct handles errors with the ERROR functions, @@ERROR only reports the last statement, and THROW is the modern way to raise or rethrow an error.

    Q58. What are transactions in SQL Server? Explain BEGIN TRAN, COMMIT, ROLLBACK, and @@TRANCOUNT.

    Answer: A transaction is a unit of work that is atomic: either all of its statements succeed together, or none of them take effect. By default SQL Server uses autocommit, where each statement is its own transaction. An explicit transaction starts with BEGIN TRANSACTION, or BEGIN TRAN for short, makes its changes permanent with COMMIT TRANSACTION, and undoes them all with ROLLBACK TRANSACTION. SAVE TRANSACTION creates a savepoint that a partial rollback can return to.

    @@TRANCOUNT reports how many transactions are open in the current session. BEGIN TRANSACTION increments it, COMMIT decrements it, and ROLLBACK resets it to zero. Nested BEGIN statements only increment the count: only the outermost COMMIT actually commits, while any ROLLBACK undoes everything. Always check @@TRANCOUNT or XACT_STATE in error handling, because a transaction left open holds locks and blocks other sessions.

    BEGIN TRANSACTION;
UPDATE dbo.Products
SET UnitPrice = 19.99
WHERE ProductID = 1;
COMMIT TRANSACTION;
SELECT @@TRANCOUNT AS OpenTransactions;

BEGIN TRANSACTION;
DELETE FROM dbo.Orders WHERE OrderID = 100;
ROLLBACK TRANSACTION;
SELECT @@TRANCOUNT AS OpenTransactions;

    Key learning: BEGIN TRAN starts a unit of work, COMMIT makes it permanent, ROLLBACK undoes it all, and @@TRANCOUNT shows how many transactions are still open.

    Q59. What are the basic backup types in SQL Server, and what are the recovery models?

    Answer: A full backup captures the entire database and is the base for every other backup type. A differential backup captures all extents changed since the last full backup, so it is smaller and faster than a full backup but grows as more changes accumulate, and a restore needs the last full backup plus the latest differential. A transaction log backup captures log records since the last log backup, keeps the log chain intact, and enables point-in-time restore.

    The recovery model controls log behavior. Simple truncates the log at checkpoints, allows no log backups, and restores only to the last full or differential backup. Full keeps log records until a log backup is taken, supports point-in-time restore, and requires regular log backups to control log growth. Bulk-logged behaves like Full except that bulk operations are minimally logged, which speeds up bulk loads but limits point-in-time restore when bulk operations are in the interval. Choose Simple when point-in-time recovery is not needed, and Full when it is.

    BACKUP DATABASE SalesDB
TO DISK = 'C:\Backups\SalesDB_Full.bak'
WITH INIT;

BACKUP DATABASE SalesDB
TO DISK = 'C:\Backups\SalesDB_Diff.bak'
WITH DIFFERENTIAL;

BACKUP LOG SalesDB
TO DISK = 'C:\Backups\SalesDB_Log.trn';

    Key learning: Full backups capture the whole database, differential backups capture changes since the last full backup, and log backups enable point-in-time restore when the database uses the Full or Bulk-logged recovery model.

    Q60. What is the MERGE statement, and why do DBAs warn against it?

    Answer: MERGE does an INSERT, UPDATE, and DELETE in one statement, matching a source to a target on a key and taking a different action for matched, unmatched, and source-missing rows. It looks like the perfect upsert, but the SQL Server community warns against it for three reasons. First, it has a known race condition: without HOLDLOCK, two concurrent MERGE statements can both decide a row does not exist and both try to insert it, failing with a unique key violation. Second, a source with duplicate matches produces wrong results or an error, and the error is hard to trace. Third, the plans it generates are often worse than separate statements, and the statement is harder to read and debug.

    If you must use MERGE, add WITH (HOLDLOCK) on the target and end the statement with a semicolon, because MERGE requires one. The safer pattern most teams prefer is separate statements in one transaction: UPDATE the matched rows first, then INSERT the rows that do not exist, using WHERE NOT EXISTS. It is longer, but it has no race condition, no duplicate-match surprise, and a plan you can read. Many shops ban MERGE outright, and knowing that is itself a good interview answer.

    -- MERGE with HOLDLOCK: the minimum safe form
MERGE INTO dbo.Products AS Target
USING dbo.StagingProducts AS Source
    ON Target.ProductID = Source.ProductID
WHEN MATCHED THEN
    UPDATE SET Target.UnitPrice = Source.UnitPrice
WHEN NOT MATCHED BY TARGET THEN
    INSERT (ProductID, ProductName, UnitPrice)
    VALUES (Source.ProductID, Source.ProductName, Source.UnitPrice)
WHEN NOT MATCHED BY SOURCE THEN
    DELETE;

-- Safer pattern: separate statements in one transaction
BEGIN TRANSACTION;
    UPDATE p
    SET p.UnitPrice = s.UnitPrice
    FROM dbo.Products p
    JOIN dbo.StagingProducts s ON p.ProductID = s.ProductID;

    INSERT INTO dbo.Products (ProductID, ProductName, UnitPrice)
    SELECT s.ProductID, s.ProductName, s.UnitPrice
    FROM dbo.StagingProducts s
    WHERE NOT EXISTS (
        SELECT 1 FROM dbo.Products p WHERE p.ProductID = s.ProductID
    );
COMMIT TRANSACTION;

    Key learning: MERGE combines insert, update, and delete in one statement but has a race condition without HOLDLOCK, so most teams use separate statements in a transaction instead.
