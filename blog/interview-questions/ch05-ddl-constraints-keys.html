Chapter 5: DDL, Constraints & Keys

Data definition language creates and changes the structure of a database, while constraints and keys enforce the rules that keep data correct. A well-designed schema uses keys to identify rows, foreign keys to link tables, and constraints to reject invalid values at the point of entry. Normalization organizes tables so each fact is stored once, and the choice between DELETE, TRUNCATE, and DROP controls how data is removed.

In this chapter:

  • →DDL, DML, and DCL statements and what each group changes
  • →Primary keys, foreign keys, and referential integrity actions
  • →UNIQUE, CHECK, and DEFAULT constraints
  • →IDENTITY columns, SEQUENCE objects, and collation mismatches
  • →Normalization to 1NF, 2NF, and 3NF, when to denormalize, and DELETE vs TRUNCATE vs DROP

    • Key learning: Constraints and keys enforce correctness at the database level, where every application must obey them, instead of relying on each caller to check the rules. Normalization removes redundancy and update anomalies, while DELETE, TRUNCATE, and DROP differ sharply in scope, logging, and recoverability, so the choice must match the intent.

    Q43. What is the difference between DDL, DML, and DCL?

    Answer: DDL, or Data Definition Language, defines and changes schema objects. CREATE, ALTER, and DROP create, modify, and remove tables, views, procedures, and other objects. TRUNCATE is also a DDL statement in SQL Server, even though it removes data.

    DML, or Data Manipulation Language, changes the data inside objects: INSERT adds rows, UPDATE changes rows, DELETE removes rows, and MERGE combines those actions. SELECT is often grouped separately as a query or data query statement, but interviewers commonly discuss it alongside DML. DCL, or Data Control Language, controls permissions: GRANT gives a permission, REVOKE removes it, and DENY explicitly blocks it, overriding a grant.

    CREATE TABLE Customers (
    CustomerID INT PRIMARY KEY,
    CustomerName NVARCHAR(100) NOT NULL
);

INSERT INTO Customers (CustomerID, CustomerName)
VALUES (1, 'Acme Corp');

GRANT SELECT ON Customers TO SalesRole;

    Key learning: DDL defines schema objects, DML changes the data inside them, and DCL controls who is allowed to use them.

    Q44. What is a primary key? What rules apply to it?

    Answer: A primary key uniquely identifies each row in a table and enforces entity integrity: no two rows can have the same key, and the key can never be NULL. It is the standard target for foreign keys from other tables, and it gives joins a stable, unique row to match on.

    The rules are strict. Values must be unique, columns in the key are implicitly NOT NULL, and a table can have only one primary key, although that key may span several columns. SQL Server creates a unique index to enforce the key, clustered by default unless a clustered index already exists or NONCLUSTERED is specified. Good primary keys are narrow, stable, and never reused for a different row.

    CREATE TABLE Employees (
    EmployeeID INT NOT NULL,
    EmployeeName NVARCHAR(100) NOT NULL,
    CONSTRAINT PK_Employees PRIMARY KEY (EmployeeID)
);

    Key learning: A primary key uniquely identifies every row with unique, non-null values, and each table can have only one.

    Q45. What is a foreign key, and how do ON DELETE and ON UPDATE actions work?

    Answer: A foreign key is a column or set of columns in a child table that references the primary key or a unique key in a parent table. It enforces referential integrity: a child row cannot reference a parent row that does not exist, and a parent row cannot be removed or changed in a way that would leave orphaned children, unless an action permits it.

    The ON DELETE and ON UPDATE actions decide what happens when the parent row is deleted or its key is updated. NO ACTION, the default, raises an error and blocks the change. CASCADE deletes or updates the child rows as well. SET NULL sets the child foreign key to NULL, which requires a nullable column, and SET DEFAULT sets it to its default value, which must exist in the parent table. A foreign key does not automatically create an index on the child columns, so add one when the child table is joined or the parent is deleted often.

    CREATE TABLE Orders (
    OrderID INT PRIMARY KEY,
    CustomerID INT NOT NULL,
    OrderDate DATE NOT NULL,
    CONSTRAINT FK_Orders_Customers FOREIGN KEY (CustomerID)
        REFERENCES Customers (CustomerID)
        ON DELETE NO ACTION
        ON UPDATE CASCADE
);

    Key learning: A foreign key keeps child rows linked to a real parent row, and its ON DELETE and ON UPDATE actions decide what happens to children when the parent changes.

    Q46. What do UNIQUE, CHECK, and DEFAULT constraints do?

    Answer: A UNIQUE constraint prevents duplicate values in a column or set of columns, and SQL Server enforces it with a unique index. Unlike a primary key, a table can have several UNIQUE constraints, and a UNIQUE column in SQL Server allows one NULL unless a filtered unique index is used to allow more.

    A CHECK constraint validates each row against a logical expression, such as requiring a price to be zero or higher, and rejects any INSERT or UPDATE that fails the test. A CHECK can reference columns in the same row but cannot contain a subquery. A DEFAULT constraint supplies a value when an INSERT omits the column or uses the DEFAULT keyword, but it does not apply when NULL is inserted explicitly.

    CREATE TABLE Products (
    ProductID INT PRIMARY KEY,
    ProductCode NVARCHAR(20) NOT NULL UNIQUE,
    UnitPrice DECIMAL(10, 2) NOT NULL CHECK (UnitPrice >= 0),
    Discontinued BIT NOT NULL DEFAULT 0,
    CreatedDate DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);

    Key learning: UNIQUE prevents duplicate values, CHECK restricts values to a valid range or list, and DEFAULT supplies a value when none is given.

    Q47. What are IDENTITY columns and SEQUENCE objects, and how do they differ?

    Answer: An IDENTITY column auto-generates an increasing number for each inserted row, defined with a seed and an increment such as IDENTITY(1, 1). A table can have only one IDENTITY column. Gaps are normal: rolled-back transactions, deletes, and server restarts can all skip numbers, so IDENTITY values must never be assumed to be gap-free. Use SCOPE_IDENTITY to read the last value generated in the current scope, and SET IDENTITY_INSERT ON to insert an explicit value.

    A SEQUENCE is an independent database object that generates numbers on request with NEXT VALUE FOR. It is not tied to one table, so several tables or statements can share one numbering series, and it supports options such as CYCLE, CACHE, and minimum and maximum values. Sequences can also produce gaps, especially with caching, so choose them for shared or flexible numbering and IDENTITY for simple per-table auto-numbering.

    CREATE TABLE Customers (
    CustomerID INT IDENTITY(1, 1) PRIMARY KEY,
    CustomerName NVARCHAR(100) NOT NULL
);

CREATE SEQUENCE dbo.InvoiceSeq
    AS INT START WITH 1000 INCREMENT BY 1;

SELECT NEXT VALUE FOR dbo.InvoiceSeq AS NextInvoiceNumber;

    Key learning: IDENTITY auto-numbers one table column, while a SEQUENCE is an independent counter that any table or statement can draw numbers from.

    Q48. What is collation, and what problems do collation mismatches cause?

    Answer: A collation is the set of rules SQL Server uses to sort and compare character data: which characters sort before others, and whether comparisons are case sensitive, accent sensitive, and width sensitive. Collation is set at three levels: the server, the database, and the column, with each level inheriting from the one above unless it is overridden. A typical name such as SQL_Latin1_General_CP1_CI_AS means case-insensitive (CI) and accent-sensitive (AS).

    Mismatches cause the error "Cannot resolve the collation conflict between ... in the equal to operation", usually when joining or comparing columns from databases with different collations, or when a temp table inherits tempdb's collation while the user database uses another. The quick fix in a query is the COLLATE clause, for example COLLATE DATABASE_DEFAULT, which makes the comparison use the current database collation. The durable fix is to align collations: set the column collation at creation time, or change a database collation with ALTER DATABASE ... COLLATE, which rebuilds affected indexes and needs a maintenance window. Always check collation before a migration or a restore to another server, because a mismatch only shows up when the first comparison runs.

    -- Check the collation at each level
SELECT SERVERPROPERTY('Collation') AS ServerCollation;
SELECT name, collation_name FROM sys.databases WHERE name = 'SalesDB';
SELECT name, collation_name FROM sys.columns
WHERE object_id = OBJECT_ID('dbo.Customers') AND name = 'Email';

-- Fix a comparison conflict in the query
SELECT *
FROM dbo.Customers AS c
INNER JOIN dbo.Orders AS o
    ON o.CustomerEmail COLLATE DATABASE_DEFAULT = c.Email COLLATE DATABASE_DEFAULT;

    Key learning: Collation decides how strings sort and compare, and mismatches between databases or tempdb break joins until you align them with COLLATE or a collation change.

    Q49. What is normalization? Explain 1NF, 2NF, and 3NF, and when to denormalize.

    Answer: Normalization organizes tables to reduce redundancy and prevent update, insert, and delete anomalies, so each fact is stored in one place. First normal form, 1NF, requires atomic values: one value per cell, no repeating groups, and each row uniquely identifiable. For example, separate phone columns or a comma-separated list should become separate rows in a phone numbers table.

    Second normal form, 2NF, requires 1NF plus no partial dependency: every non-key column must depend on the whole primary key, not part of a composite key. If OrderDetails has a composite key of OrderID and ProductID, ProductName depends only on ProductID and belongs in Products. Third normal form, 3NF, requires 2NF plus no transitive dependency: every non-key column must depend only on the key, not on another non-key column. If Customers stores ZipCode, City, and State, City and State depend on ZipCode and belong in a ZipCodes table.

    Denormalization deliberately reintroduces redundancy, usually for read-heavy reporting, to avoid expensive joins or to store a precomputed value. It is justified only when measured performance needs it and the extra update cost and risk of inconsistent copies are controlled.

    CREATE TABLE ZipCodes (
    ZipCode CHAR(5) PRIMARY KEY,
    City NVARCHAR(50) NOT NULL,
    StateCode CHAR(2) NOT NULL
);

CREATE TABLE Customers (
    CustomerID INT PRIMARY KEY,
    CustomerName NVARCHAR(100) NOT NULL,
    ZipCode CHAR(5) NOT NULL,
    CONSTRAINT FK_Customers_ZipCodes FOREIGN KEY (ZipCode)
        REFERENCES ZipCodes (ZipCode)
);

    Key learning: Normalization to 3NF removes repeating groups, partial dependencies, and transitive dependencies so each fact is stored once, while denormalization trades some redundancy for faster reads.

    Q50. What is the difference between DELETE, TRUNCATE, and DROP?

    Answer: DELETE is a DML statement that removes rows one by one, with an optional WHERE clause to choose which rows go. Every deleted row is logged, DELETE triggers fire, the identity seed is unchanged, and the statement can be rolled back. DELETE respects foreign keys, so a parent row cannot be deleted while child rows reference it unless a cascade action applies.

    TRUNCATE is a DDL statement that removes all rows from a table at once, with no WHERE clause. It deallocates data pages with minimal logging, so it is much faster for emptying a table, it resets the IDENTITY seed, and DELETE triggers do not fire. A table referenced by a foreign key cannot be truncated until the foreign key is dropped or disabled, and TRUNCATE requires ALTER permission. TRUNCATE is transactional, so inside an explicit transaction it can be rolled back like DELETE, which is a common interview trap: the minimal logging is about speed, not about losing the ability to roll back. DROP is also DDL, but it removes the table itself: its definition, data, indexes, constraints, and triggers are all gone, and recovery requires a restore.

    DELETE FROM Orders WHERE OrderDate < '2020-01-01';

TRUNCATE TABLE Orders_Staging;

DROP TABLE Orders_Staging;

    Key learning: DELETE removes selected rows with full logging and triggers, TRUNCATE empties a whole table quickly and resets IDENTITY, and DROP removes the table itself.
