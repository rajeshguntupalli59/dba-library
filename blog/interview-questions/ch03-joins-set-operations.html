Chapter 3: Joins & Set Operations

Relational data lives in separate tables, so most real queries must combine tables to answer a question. This chapter covers every join type, the difference between join conditions and WHERE filters, and the set operations that combine whole result sets. Getting joins right is what separates a query that returns the right rows from one that returns too many or too few.

In this chapter:

  • →INNER JOIN and how matching rows are combined
  • →LEFT JOIN, RIGHT JOIN, and FULL OUTER JOIN
  • →CROSS JOIN and self joins
  • →ON clause filtering versus WHERE clause filtering for outer joins
  • →UNION, UNION ALL, INTERSECT, and EXCEPT
  • →CROSS APPLY and OUTER APPLY, and avoiding Cartesian products

    • Key learning: The join type decides which unmatched rows survive: INNER JOIN keeps only matches, LEFT JOIN keeps every left row, RIGHT JOIN keeps every right row, and FULL OUTER JOIN keeps every row from both sides. Set operations combine result sets instead of tables, and every join needs a correct ON condition to avoid a Cartesian product.

    Q25. What is a JOIN, and how does an INNER JOIN work?

    Answer: A JOIN combines rows from two or more tables into a single result set, based on a relationship between columns, usually a foreign key matching a primary key. Without joins, each query could only read one table at a time, and questions such as which customer placed each order would need several separate queries.

    An INNER JOIN returns only rows that have a match on both sides. If a customer has no orders, that customer does not appear. If an order has no matching customer, that order does not appear. The ON clause states the match condition. INNER JOIN and JOIN mean the same thing in T-SQL, but writing INNER JOIN makes the intent explicit.

    SELECT c.CustomerName, o.OrderID, o.OrderDate, o.TotalAmount
FROM Customers AS c
INNER JOIN Orders AS o
    ON o.CustomerID = c.CustomerID
ORDER BY o.OrderDate;

    Key learning: A JOIN combines rows from two tables on a related condition, and an INNER JOIN returns only rows that match on both sides.

    Q26. What is the difference between a LEFT JOIN and a RIGHT JOIN?

    Answer: A LEFT JOIN, also called LEFT OUTER JOIN, returns every row from the left table, plus matching rows from the right table. When a left row has no match, it still appears, with NULL values in the right table columns. This is how you find customers with no orders, or employees with no assigned manager record in another table.

    A RIGHT JOIN, also called RIGHT OUTER JOIN, does the reverse: it returns every row from the right table, plus matching rows from the left table, with NULL values where the left side has no match. In practice RIGHT JOIN is rarely used, because any RIGHT JOIN can be rewritten as a LEFT JOIN by swapping the table order, and most teams standardize on LEFT JOIN for consistency.

    SELECT c.CustomerName, o.OrderID, o.OrderDate
FROM Customers AS c
LEFT JOIN Orders AS o
    ON o.CustomerID = c.CustomerID
ORDER BY c.CustomerName;

SELECT c.CustomerName, o.OrderID, o.OrderDate
FROM Customers AS c
RIGHT JOIN Orders AS o
    ON o.CustomerID = c.CustomerID
ORDER BY o.OrderDate;

    Key learning: A LEFT JOIN keeps every row from the left table and a RIGHT JOIN keeps every row from the right table, filling unmatched columns with NULL values.

    Q27. What does a FULL OUTER JOIN return?

    Answer: A FULL OUTER JOIN returns every row from both tables. Rows that match on the join condition appear combined in one row. Rows with no match on the other side still appear, with NULL values in the columns of the table that had no match. FULL JOIN and FULL OUTER JOIN mean the same thing in T-SQL.

    Use a FULL OUTER JOIN when you need to see gaps on both sides at once, such as customers with no orders and orders with no matching customer in the same result. To find only the unmatched rows, add a WHERE clause that tests for NULL in a non-nullable column from one side, such as WHERE o.OrderID IS NULL OR c.CustomerID IS NULL.

    SELECT c.CustomerName, o.OrderID, o.OrderDate
FROM Customers AS c
FULL OUTER JOIN Orders AS o
    ON o.CustomerID = c.CustomerID
ORDER BY c.CustomerName;

    Key learning: A FULL OUTER JOIN returns every row from both tables with NULL values where either side has no match.

    Q28. What is a CROSS JOIN, and when would you use one?

    Answer: A CROSS JOIN returns every possible pairing of rows from two tables, with no ON clause and no match condition. If the first table has 100 rows and the second has 5 rows, the result has 500 rows. The size grows by multiplication, so CROSS JOIN results can explode quickly when either table is large.

    Deliberate uses are narrow. Use a CROSS JOIN to build small combination matrices, such as every product in every size, to generate test data, or to pair each row with a single-row value such as a report parameter. Never use it as a substitute for a missing join condition. If you see CROSS JOIN in a query, check that the combination is intentional and that both sides are small.

    SELECT p.ProductName, s.SizeLabel
FROM Products AS p
CROSS JOIN (VALUES ('S'), ('M'), ('L')) AS s (SizeLabel)
ORDER BY p.ProductName, s.SizeLabel;

    Key learning: A CROSS JOIN returns every possible pairing of rows with no join condition and is useful only for small deliberate combinations.

    Q29. What is a self join, and when would you use one?

    Answer: A self join joins a table to itself. SQL Server treats the two copies as separate tables, so you must give each copy a different table alias. Without aliases, column references would be ambiguous and the query would fail.

    The classic example is an employee hierarchy, where Employees.ManagerID points to Employees.EmployeeID. A self join pairs each employee row with the row for that employee's manager. Self joins are also used to compare rows within the same table, such as finding pairs of employees in the same department, or comparing a row with the previous row for the same entity. Use a LEFT JOIN when some rows have no counterpart, such as the top manager who has no manager.

    SELECT e.FirstName AS EmployeeFirstName,
       e.LastName AS EmployeeLastName,
       m.FirstName AS ManagerFirstName,
       m.LastName AS ManagerLastName
FROM Employees AS e
LEFT JOIN Employees AS m
    ON m.EmployeeID = e.ManagerID
ORDER BY e.LastName;

    Key learning: A self join joins a table to itself with two aliases so one row can be compared with another row from the same table.

    Q30. What is the difference between filtering in the JOIN ON clause and filtering in the WHERE clause, especially for outer joins?

    Answer: For an INNER JOIN, the difference is only stylistic, because only matching rows survive either way and the optimizer treats the two forms the same. Keep match conditions in ON and row filters in WHERE for readability, but the result will be the same.

    For an outer join, the placement changes the result. A condition in the ON clause filters the right table before unmatched left rows are preserved, so left rows with no qualifying match still appear with NULL values. A condition in the WHERE clause filters after the join, and a test such as TotalAmount > 1000 rejects NULL values, so preserved rows with no match disappear and the LEFT JOIN behaves like an INNER JOIN. If you want all left rows kept, put the right-side filter in ON, or add OR with an IS NULL test in WHERE.

    SELECT c.CustomerName, o.OrderID, o.TotalAmount
FROM Customers AS c
LEFT JOIN Orders AS o
    ON o.CustomerID = c.CustomerID
   AND o.TotalAmount > 1000;

SELECT c.CustomerName, o.OrderID, o.TotalAmount
FROM Customers AS c
LEFT JOIN Orders AS o
    ON o.CustomerID = c.CustomerID
WHERE o.TotalAmount > 1000;

    Key learning: For outer joins, a condition in ON filters before unmatched rows are preserved while a condition in WHERE filters after the join and can remove preserved rows.

    Q31. What is the difference between UNION and UNION ALL?

    Answer: UNION and UNION ALL both combine the results of two or more SELECT statements into one result set, stacked vertically. Both require the same number of columns in each SELECT, with compatible data types in each position. Column names in the output come from the first SELECT, and a single ORDER BY at the end sorts the combined result.

    The difference is duplicate handling. UNION removes duplicate rows, which requires extra work to sort or hash the combined set. UNION ALL keeps every row, including duplicates, and is faster because it skips that step. Use UNION ALL by default when duplicates are impossible or acceptable, and use UNION only when you need duplicates removed.

    SELECT City
FROM Customers
UNION
SELECT City
FROM Employees;

SELECT City
FROM Customers
UNION ALL
SELECT City
FROM Employees;

    Key learning: UNION combines results and removes duplicates while UNION ALL keeps every row including duplicates and runs faster.

    Q32. What do INTERSECT and EXCEPT do?

    Answer: INTERSECT returns only the distinct rows that appear in both result sets. It answers which values exist on both sides, such as customers who have also placed orders. EXCEPT returns the distinct rows that appear in the first result set but not in the second, so it answers which values exist on one side only, such as customers who have never placed an order.

    Both operators require the same number of columns with compatible types, both return distinct rows, and both treat NULL values as equal to each other for comparison purposes, which is different from the = operator. Order matters for EXCEPT, because swapping the two queries changes the question, while INTERSECT gives the same result either way.

    SELECT CustomerID
FROM Orders
INTERSECT
SELECT CustomerID
FROM Customers;

SELECT CustomerID
FROM Customers
EXCEPT
SELECT CustomerID
FROM Orders;

    Key learning: INTERSECT returns only distinct rows present in both results and EXCEPT returns distinct rows present in the first result but not the second.

    Q33. What are CROSS APPLY and OUTER APPLY, and when do you use them?

    Answer: APPLY runs a table expression once for each row of the outer query, and the expression can reference columns from that row. That makes it the tool for row-by-row table logic that a plain JOIN cannot express. CROSS APPLY behaves like an INNER JOIN: rows with no matching result from the applied expression are dropped. OUTER APPLY behaves like a LEFT JOIN: outer rows are kept, with NULLs where the expression returns nothing.

    The two classic uses are calling a table-valued function per row, and getting the TOP N rows per group, for example the latest two orders per customer, which is awkward with GROUP BY alone. APPLY is also the standard way to split delimited strings with STRING_SPLIT per row. Performance depends on the plan: APPLY can be very fast when the inner expression seeks, and very slow when it scans per row, so always check the execution plan and the row counts before assuming it is cheap.

    -- Latest two orders per customer: TOP N per group
SELECT c.CustomerName, Recent.OrderID, Recent.OrderDate, Recent.TotalAmount
FROM Customers AS c
CROSS APPLY (
    SELECT TOP (2) o.OrderID, o.OrderDate, o.TotalAmount
    FROM Orders AS o
    WHERE o.CustomerID = c.CustomerID
    ORDER BY o.OrderDate DESC
) AS Recent;

-- OUTER APPLY keeps customers with no orders, with NULLs
SELECT c.CustomerName, Recent.OrderID
FROM Customers AS c
OUTER APPLY (
    SELECT TOP (1) o.OrderID
    FROM Orders AS o
    WHERE o.CustomerID = c.CustomerID
    ORDER BY o.OrderDate DESC
) AS Recent;

    Key learning: APPLY runs a table expression per outer row, CROSS APPLY drops non-matching rows like an inner join, OUTER APPLY keeps them like a left join, and TOP N per group is its classic use.

    Q34. What is a Cartesian product, and how do you avoid creating one by accident?

    Answer: A Cartesian product pairs every row in one table with every row in another table. A table with 1,000 customers joined to a table with 5,000 orders without a join condition returns 5,000,000 rows. The result is usually wrong, slow, and full of meaningless combinations.

    Accidental Cartesian products happen when a join condition is missing, when the old comma syntax is used without a WHERE clause linking the tables, or when the ON condition references the wrong columns. Avoid them by always using explicit JOIN with ON syntax, never comma joins, and by qualifying columns with table aliases. Check the row count as you build the query: a sudden jump into the millions is the classic symptom of a missing or wrong join condition.

    SELECT c.CustomerName, o.OrderID
FROM Customers AS c, Orders AS o;

SELECT c.CustomerName, o.OrderID
FROM Customers AS c
INNER JOIN Orders AS o
    ON o.CustomerID = c.CustomerID;

    Key learning: A Cartesian product pairs every row with every row, so always use an explicit JOIN with a correct ON condition and check row counts for unexpected growth.
