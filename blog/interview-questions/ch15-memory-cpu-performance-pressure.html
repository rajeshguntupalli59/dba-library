Chapter 15: Memory, CPU & Performance Pressure

Memory and CPU problems often look like slow queries, but the fix is not always a new index. This chapter covers how SQL Server uses memory and schedulers, and how to tell real pressure from a noisy counter. You will learn the waits and counters that point to the true bottleneck.

    Q157. How does SQL Server use the buffer pool, and why does max server memory matter?

    Answer: The buffer pool is the main memory cache for 8 KB data pages. When a query reads a page, SQL Server loads it into the buffer pool if it is not already there, and later reads can reuse the cached copy instead of reading from disk. Dirty pages stay in the pool until a checkpoint or lazy writer flushes them, so a warm cache is often the difference between fast and slow reads.

    Max server memory caps how much memory SQL Server will use for the buffer pool and most other internal caches. Without a cap, SQL Server will keep growing toward all available memory and can starve the operating system, agents, backup tools, and other processes on the same host. Min server memory is a floor SQL Server tries to keep once reached, but it is not reserved at startup.

    Set max server memory with headroom for the operating system and anything else on the box, and review it after memory changes or when new workloads arrive. On a dedicated database server, a common starting point is to leave several GB for the operating system, more on large hosts, and then tune from observed pressure rather than guessing.

    SELECT name, value_in_use, description
FROM sys.configurations
WHERE name IN ('max server memory (MB)', 'min server memory (MB)');

SELECT COUNT(*) AS cached_pages, COUNT(*) * 8 / 1024 AS cached_mb
FROM sys.dm_os_buffer_descriptors;

    Key learning: The buffer pool caches data pages in memory, and max server memory caps SQL Server memory so the operating system and other processes keep room to run.

    Q158. What is Page Life Expectancy (PLE), and what are its limits as a metric?

    Answer: Page Life Expectancy estimates how many seconds a data page stays in the buffer pool without being referenced before it is aged out. A falling PLE often means pages are churning quickly, which can happen under memory pressure or when a large scan floods the cache with pages that are read once.

    PLE has real limits, so do not treat one number as a pass or fail test. The old 300 second rule does not scale: a server with hundreds of GB of memory should normally show a much higher PLE than a small server, and PLE is tracked per NUMA node, so one low node can hide behind a healthy average. Workload matters too, because reporting scans, index rebuilds, and large ETL loads can drop PLE without proving the server needs more memory.

    Read PLE as a trend alongside page reads per second, lazy writes, buffer cache hit ratio, and memory grant waits. A sustained drop from the normal baseline, plus high disk reads and grant waits, is a stronger signal than any single reading.

    SELECT object_name, counter_name, cntr_value
FROM sys.dm_os_performance_counters
WHERE counter_name = 'Page life expectancy'
  AND object_name LIKE '%Buffer Manager%';

SELECT object_name, counter_name, cntr_value
FROM sys.dm_os_performance_counters
WHERE counter_name IN ('Buffer cache hit ratio', 'Lazy writes/sec', 'Page reads/sec')
  AND object_name LIKE '%Buffer Manager%';

    Key learning: Page Life Expectancy shows how long pages stay cached, but it must be read as a trend with workload and memory size, not as a single pass or fail number.

    Q159. What are memory grants, what causes RESOURCE_SEMAPHORE waits, and how does memory grant feedback help?

    Answer: A memory grant is workspace memory given to a query for sorts, hashes, and other memory-hungry operators before execution starts. SQL Server estimates how much memory the plan needs from row estimates, and the query waits if that memory is not available. Large sorts, hash joins, and parallel plans are the most common grant consumers.

    RESOURCE_SEMAPHORE means a query is waiting for a memory grant. Common causes are many concurrent grants, oversized grants from bad cardinality estimates, very large sorts or hashes, and a max server memory setting that leaves too little grant memory. The symptom is queries stuck before they run, not blocked by locks, and the fix is rarely to let every query take more memory.

    Memory grant feedback learns from the last execution and adjusts the grant for the next run of the same plan, reducing grants that were wasteful and increasing grants that spilled. In SQL Server 2022 the feedback can persist across restarts and plan cache clears. Also fix the root cause with current statistics, better indexes, smaller sorts, and batching, and use Resource Governor or grant hints only as a targeted control.

    SELECT wait_type, waiting_tasks_count, wait_time_ms
FROM sys.dm_os_wait_stats
WHERE wait_type = 'RESOURCE_SEMAPHORE';

SELECT session_id, requested_memory_kb, granted_memory_kb, ideal_memory_kb, wait_time_ms
FROM sys.dm_exec_query_memory_grants;

    Key learning: Memory grants pay for sorts and hashes, and RESOURCE_SEMAPHORE waits mean queries are waiting for grant memory that feedback and better estimates can reduce.

    Q160. What are the signs of memory pressure, including stolen memory, lazy writes, and buffer cache hit ratio?

    Answer: Stolen memory is buffer pool memory taken for other uses such as plan cache, connection memory, and query workspace instead of data pages. When stolen memory grows, fewer data pages fit in cache, PLE falls, and disk reads rise. Check memory clerks and the balance between cache and workspace before assuming the server simply needs more RAM.

    Lazy writes per second counts dirty pages flushed by the lazy writer when free buffers run low. Occasional lazy writes are normal, but sustained high lazy writes with falling PLE point to pressure. Buffer cache hit ratio is a weak signal on its own: it can stay above 99 percent while PLE collapses, because it counts logical reads and hides how much work still hits disk.

    Look for the pattern together: low available physical memory, high page reads per second, RESOURCE_SEMAPHORE waits, growing grants, and paging at the operating system level. Confirm with trends and workload timing, then tune queries, statistics, and memory settings before adding hardware.

    SELECT object_name, counter_name, cntr_value
FROM sys.dm_os_performance_counters
WHERE object_name LIKE '%Buffer Manager%'
  AND counter_name IN ('Buffer cache hit ratio', 'Lazy writes/sec', 'Page life expectancy');

SELECT total_physical_memory_kb, available_physical_memory_kb, system_memory_state_desc
FROM sys.dm_os_sys_memory;

SELECT physical_memory_in_use_kb, locked_page_allocations_kb, virtual_address_space_committed_kb
FROM sys.dm_os_process_memory;

    Key learning: Real memory pressure shows up across several signals at once, so check stolen memory, lazy writes, and wait trends together before adding memory.

    Q161. How do you diagnose CPU pressure using SOS_SCHEDULER_YIELD, signal waits, and the runnable queue?

    Answer: SOS_SCHEDULER_YIELD means a task used its scheduler quantum and yielded so another task could run. Some yields are normal on a busy server, but a high and rising SOS_SCHEDULER_YIELD wait, especially as a top wait, means threads are competing for CPU time. It points to CPU-bound work, not to blocking or disk waits.

    Signal wait time is the gap between a task becoming runnable and actually getting CPU time. When signal waits are a large share of total waits, tasks are ready but waiting for a scheduler, which is a classic CPU pressure signal. The runnable queue makes it concrete: check runnable_tasks_count in sys.dm_os_schedulers, where a sustained value above zero means runnable tasks are queuing for CPU.

    Next, find the CPU consumers with top queries by worker time, check for excessive parallelism, compiles, and scans, and confirm the pattern is sustained rather than a short spike. Fix the expensive queries first, then review MAXDOP, Cost Threshold for Parallelism, and missing indexes before adding cores.

    SELECT wait_type, waiting_tasks_count, wait_time_ms, signal_wait_time_ms,
       wait_time_ms - signal_wait_time_ms AS resource_wait_time_ms
FROM sys.dm_os_wait_stats
WHERE wait_type = 'SOS_SCHEDULER_YIELD';

SELECT scheduler_id, current_tasks_count, runnable_tasks_count, work_queue_count
FROM sys.dm_os_schedulers
WHERE scheduler_id < 255;

SELECT TOP 20 total_worker_time / execution_count AS avg_cpu_ms, execution_count, total_worker_time
FROM sys.dm_exec_query_stats
ORDER BY total_worker_time DESC;

    Key learning: High signal waits and a sustained runnable queue mean threads are ready but waiting for CPU, which points to CPU pressure rather than blocking or disk waits.

    Q162. What are MAXDOP and Cost Threshold for Parallelism, and what does DOP feedback do in SQL Server 2022?

    Answer: MAXDOP limits how many threads one query can use in a parallel plan. Cost Threshold for Parallelism is the minimum estimated cost a query must reach before SQL Server will even consider a parallel plan. The old defaults of MAXDOP 0 and Cost Threshold 5 let many small queries go parallel, which can waste CPU on thread coordination and create CXPACKET and CXCONSUMER waits.

    Tune both together for the workload. OLTP systems usually need a modest MAXDOP tied to cores per NUMA node and a higher Cost Threshold, often 30 to 50 as a starting point, so only truly expensive queries go parallel. MAXDOP can be set at server level, database level, and per query with a hint, so a reporting query can still use more threads without changing the whole server.

    DOP feedback in SQL Server 2022 watches repeating queries that suffer from excessive parallelism and lowers the degree of parallelism for later executions. It is part of Intelligent Query Processing and helps when a plan goes too wide, but it does not replace sensible MAXDOP and Cost Threshold baselines.

    SELECT name, value_in_use
FROM sys.configurations
WHERE name IN ('max degree of parallelism', 'cost threshold for parallelism');

SELECT name, value, value_for_secondary
FROM sys.database_scoped_configurations
WHERE name = 'DOP_FEEDBACK';

    Key learning: MAXDOP and Cost Threshold for Parallelism control when and how widely queries go parallel, and DOP feedback in SQL Server 2022 tunes excessive parallelism for repeating queries.

    Q163. What are tempdb spills and hash spills, and how do you find and fix sort and hash warnings?

    Answer: A spill happens when a sort or hash operator needs more memory than its grant and writes part of its work to tempdb. Sort warnings and hash warnings flag this behavior, and actual execution plans show spill warnings with the spilled data size and spill level. Spills slow the query with tempdb IO and often signal a bad row estimate rather than a tempdb sizing problem.

    Common causes are outdated or missing statistics, bad cardinality estimates from skewed data or complex predicates, missing indexes that force large sorts, and grants that are too small for the real row count. Hash spills add hash recursion or hash bailout when the build side does not fit, which is even more expensive than a simple sort spill.

    Find spills in Query Store, plan warnings, and sys.dm_exec_query_stats spill counters, then fix the estimate first: update statistics, add a supporting index to avoid the sort, simplify the predicate, or break the work into batches. Only raise the grant or tune tempdb after the plan is sound, and recheck the plan to confirm the spill is gone.

    SELECT qs.execution_count, qs.total_spills, qs.last_spills,
       SUBSTRING(st.text, 1, 200) AS query_text
FROM sys.dm_exec_query_stats AS qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS st
WHERE qs.total_spills > 0
ORDER BY qs.total_spills DESC;

    Key learning: Spills mean a sort or hash ran out of grant memory and used tempdb, so fix the estimate, the index, or the grant instead of only tuning tempdb.

    Q164. What is cardinality feedback in SQL Server 2022, and what other Intelligent Query Processing features should you know?

    Answer: Cardinality feedback compares estimated rows with actual rows for a repeating query and adjusts the estimate for later executions so the optimizer can pick a better plan. It helps when the first estimate is badly wrong because of skew, correlated predicates, or complex filters, and the learned adjustment applies to the same query pattern. It needs a current compatibility level and is controlled by database scoped configuration.

    Other Intelligent Query Processing features to know are adaptive joins, which defer the choice between nested loop and hash join until the actual row count is known, and interleaved execution, which gives multi-statement table-valued functions real row counts instead of a fixed guess. Batch mode on rowstore lets analytic operators use batch processing without a columnstore index, and table variable deferred compilation fixes the old one-row guess for table variables.

    Memory grant feedback and DOP feedback belong in the same family, plus Parameter Sensitive Plan optimization, which keeps more than one plan for a parameter-sensitive query. In an interview, name the problem each feature solves and note that most require a modern compatibility level and can be toggled per database.

    SELECT name, value, value_for_secondary
FROM sys.database_scoped_configurations
WHERE name IN ('CE_FEEDBACK', 'DOP_FEEDBACK', 'MEMORY_GRANT_FEEDBACK_PERSISTENCE');

ALTER DATABASE SCOPED CONFIGURATION SET CE_FEEDBACK = ON;

    Key learning: Cardinality feedback learns from past misestimates to improve repeat plans, and it works best with other Intelligent Query Processing features under a current compatibility level.

    Q165. What causes high query compile time and frequent recompilations, and how do you fix them?

    Answer: High compile time comes from complex plans that are expensive to optimize: many joins, large IN lists, wide OR logic, heavy dynamic SQL, and ORM-generated queries with hundreds of parameters. Frequent recompiles add to the cost when plans cannot be reused and SQL Server must optimize the same shape again and again.

    Common recompile triggers are statistics updates, schema changes, SET option changes, temp table definition changes inside a procedure, and explicit RECOMPILE hints. Ad hoc SQL without parameterization is a frequent culprit, because each literal value creates a separate plan and floods the plan cache. Plan cache pressure and memory pressure can then evict plans early and force even more compiles.

    Fix reuse first: parameterize queries, use stored procedures, enable optimize for ad hoc workloads where it fits, and reduce dynamic SQL churn. Schedule statistics updates in maintenance windows, avoid DDL during peak hours, and use RECOMPILE only for truly parameter-sensitive queries where one plan cannot serve all values. Check plan generation counts to confirm recompiles are falling.

    SELECT TOP 20 total_worker_time, execution_count,
       total_elapsed_time / execution_count AS avg_elapsed_ms,
       SUBSTRING(st.text, 1, 200) AS query_text
FROM sys.dm_exec_query_stats AS qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS st
ORDER BY total_worker_time DESC;

SELECT sql_handle, plan_generation_num, execution_count, creation_time, last_execution_time
FROM sys.dm_exec_query_stats
WHERE plan_generation_num > 5;

    Key learning: Frequent recompiles and slow compiles usually trace to plan reuse problems, unstable statistics, or schema churn, so stabilize the plan and the statistics schedule first.

    Q166. Scenario: The server is slow at the same time every day, but sys.dm_exec_requests shows no blocking. How do you diagnose it?

    Answer: First, check sys.dm_os_waiting_tasks while the slowdown is happening, because sys.dm_exec_requests only shows currently running requests and can miss waits that are short, sampled between polls, or sitting in tasks that are not visible as blocking. Look for the dominant wait types, the waiting sessions, and whether any session has a blocking session id that appears only in the waiting tasks view. Capture the waits live during the slow window instead of checking after it clears.

    Second, use a lightweight Extended Events session to capture waits, slow queries, and blocking chains during the window, and avoid a heavy server-side trace that adds its own load. Correlate the capture with wait statistics history and Query Store so you can see which queries regress at that time and whether the top waits change from the normal baseline. Check for PAGEIOLATCH, CPU, memory grant, and IO waits that would not show as blocking.

    Third, check scheduled work that runs at that time: SQL Agent jobs, backups, index maintenance, statistics updates, ETL loads, reporting extracts, antivirus scans, and virtual host snapshots. A fixed daily time almost always means a job or an external process, so map the slow window to the job schedule, confirm start and end times, and test by moving or staggering the suspect job. Fix the schedule or the heavy job first, and only tune queries after the timing pattern is explained.

    SELECT session_id, wait_type, wait_duration_ms, blocking_session_id, resource_description
FROM sys.dm_os_waiting_tasks
WHERE session_id > 50;

SELECT wait_type, waiting_tasks_count, wait_time_ms
FROM sys.dm_os_wait_stats
ORDER BY wait_time_ms DESC;

SELECT j.name AS job_name, h.run_date, h.run_time, h.run_duration
FROM msdb.dbo.sysjobs AS j
INNER JOIN msdb.dbo.sysjobhistory AS h ON h.job_id = j.job_id
WHERE h.run_date = CONVERT(INT, CONVERT(CHAR(8), GETDATE(), 112));

    Key learning: A daily slowdown with no blocking is usually scheduled work or a resource wait, so capture waits live and check jobs and wait history before changing queries.
