Cutting your AI-inference database costs: connection pooling for LLM workloads

Rajesh Guntupalli·August 2026·5 min read

A client asked me to look at their RDS bill after it grew 3x in two months with no corresponding growth in user traffic. The culprit wasn't storage, wasn't compute — it was connection count, driven entirely by an AI agent framework that opened a fresh database connection per tool call and let the pool grow until they'd upsized the instance twice just to stop hitting max_connections. This is a pattern I now see constantly, and it's specific to how AI workloads talk to databases.

Why AI workloads break normal connection assumptions

Traditional web application connection patterns are predictable: a request comes in, does a handful of queries, releases the connection, all within tens of milliseconds. Standard pool sizing assumes this shape. AI agent workloads violate it in two specific ways.

First, a single agent "turn" often spans a model inference call — anywhere from 500ms to several seconds — sandwiched between two database queries, and a naive integration holds the connection open across that entire span, including the part where nothing is happening on the database side at all. Second, agent frameworks tend to spin up a new connection per tool invocation rather than reusing one across a session, because the tool-calling abstraction doesn't naturally carry connection state the way a request handler does.

-- What this looks like in sys.dm_exec_sessions during an incident
SELECT status, COUNT(*) AS session_count,
       CAST(AVG(DATEDIFF(SECOND, last_request_end_time, GETUTCDATE())) AS DECIMAL(10,1)) AS avg_idle_seconds
FROM sys.dm_exec_sessions
WHERE program_name = 'ai-agent-worker'
GROUP BY status;

--   status    | session_count | avg_idle_seconds
-- sleeping    |         340 |             4.2
-- running     |          28 |            11.7

340 idle connections, each one reserving memory on the database server whether or not it's doing anything, is what forces the instance upsize — not query volume, not data volume. The bill goes up because of connection *count*, and connection count went up because of an integration pattern nobody was watching.

The fix: pool at the transaction level, not the session level

Client-side pooling with aggressive connection lifetime management is the single highest-leverage change here. SQL Server drivers pool connections in the client (ADO.NET, ODBC, JDBC all do this by default), so the fix is to make every agent worker check a connection out only for the milliseconds it is actually running a query — open late, close early — and never hold one across the model inference call in between.

// Connection string: small, bounded pool shared by all agent workers
"Server=db.internal;Database=app_production;Integrated Security=true;"
+ "Max Pool Size=25;Min Pool Size=0;Connection Lifetime=30;"
+ "Connect Timeout=5;"

// The pattern that matters: open late, close early —
// never hold the connection across the inference call
async Task<string> AgentTurnAsync(string prompt)
{
    var answer = await model.GenerateAsync(prompt);   // no connection held here
    await using var conn = new SqlConnection(connString);
    await conn.OpenAsync();                            // checked out of the pool
    await using var cmd = new SqlCommand(
        "INSERT INTO agent_turns (prompt, answer) VALUES (@p, @a);", conn);
    cmd.Parameters.AddWithValue("@p", prompt);
    cmd.Parameters.AddWithValue("@a", answer);
    await cmd.ExecuteNonQueryAsync();
} // disposed here → returned to the pool immediately

2,000 agent workers can now share 25 real backend connections, because each one only holds a connection for the milliseconds it's actually running a query — not for the seconds it's waiting on the model. This is the same pattern serverless applications have used for years; AI agent frameworks just haven't caught up to it yet, so most teams are shipping the naive version by default.

Two real constraints to audit before you rely on this. First, pooling is per distinct connection string and security context — if each agent worker connects as a different login or with a slightly different connection string, you get one pool per variation and the math above falls apart; use a single service login for agent database access. Second, sp_reset_connection runs every time a connection is reused, so session-level SET options, temp tables, and transaction state do not survive a trip back to the pool — design agent tooling to be stateless across queries.

Measure the actual saving, not the theoretical one

For the client above: instance size went from db.r6g.2xlarge back to db.r6g.xlarge once connection pressure stopped forcing the upsize — roughly 45% of the monthly RDS bill for that database, with no change to query patterns, data volume, or user-facing latency. The saving wasn't from making anything faster. It was from stopping the database from paying, in memory and instance size, for idle time that belonged to the model, not the database.

Before and after any pooling change, watch sys.dm_exec_sessions connection counts by status over a full day, not a snapshot — idle-in-transaction spikes during specific agent workflows are common and easy to miss with a point-in-time check. The goal isn't zero idle connections; it's making sure the ones you're paying for are actually doing something close to what you're paying for.
