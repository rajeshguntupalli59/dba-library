Transaction log full: why SQL Server stopped accepting writes — and the 5-minute triage

Rajesh Guntupalli·November 2026·6 min read

Error 9002 is one of the few SQL Server errors that stops the business cold: "The transaction log for database 'X' is full due to 'LOG_BACKUP'." Inserts fail, updates fail, and every write-heavy application starts throwing errors at the same time. It feels like a disk problem. It usually isn't.

The transaction log is not a trash can that fills up and gets emptied. It is a circular file: SQL Server reuses space once the transactions recorded in it are no longer needed. A "full" log almost never means the log file is too small. It means something is preventing reuse — and SQL Server will tell you exactly what, if you ask the right DMV first. That is the whole triage: find the blocker, clear it, then fix the setup so it does not come back.

Here is the order I run it in, during an incident.

1. Ask SQL Server why the log cannot reuse space

Before touching anything, run two checks. The first tells you how full the log really is; the second tells you the reason reuse is blocked. That reason — log_reuse_wait_desc — decides the entire fix, so read it before you act.

-- How full is every log, and what is blocking reuse?
SELECT
    d.name AS database_name,
    d.log_reuse_wait_desc,
    d.recovery_model_desc
FROM sys.databases d
WHERE d.database_id > 4;

-- Log size and percent used, per database
DBCC SQLPERF(LOGSPACE);

The value in log_reuse_wait_desc is the diagnosis. LOG_BACKUP means no log backup has run since the last checkpoint. ACTIVE_TRANSACTION means an open transaction is holding the log hostage. REPLICATION or AVAILABILITY_REPLICA means a downstream consumer has not read the log yet. NOTHING with a full log usually means the file hit its max size or the disk is genuinely out of space. Each one has a different fix — and the wrong fix wastes the incident.

2. The usual suspect: a long-running transaction

In my experience, ACTIVE_TRANSACTION is the most common cause, and it is the sneakiest. A single transaction that started hours ago — a bulk load in a test window, a forgotten BEGIN TRAN in an SSMS window, a job that errored out before its COMMIT — pins the log at the point where it started. Everything written since then cannot be reused, no matter how many log backups you take. The log grows until it hits its ceiling, and then writes stop.

Find the oldest open transaction in the affected database:

-- Oldest open transactions, with who started them and when
SELECT
    t.session_id,
    s.login_name,
    s.host_name,
    s.program_name,
    t.transaction_begin_time,
    DATEDIFF(MINUTE, t.transaction_begin_time, GETDATE())
        AS open_minutes,
    t.transaction_state
FROM sys.dm_tran_active_transactions t
JOIN sys.dm_exec_sessions s
    ON s.session_id = t.transaction_id
WHERE t.transaction_state = 2  -- active
ORDER BY t.transaction_begin_time;

Once you know the session, decide deliberately. If it is a forgotten SSMS window or a runaway ad-hoc load, kill it — KILL <session_id> — and watch the log start reusing space within seconds. If it is a real business transaction, talk to the application owner before killing anything: rolling back a six-hour load is also a business decision. But either way, you now know the cause instead of guessing.

3. Clear it the right way — and the two "fixes" that make it worse

If the blocker is LOG_BACKUP, the fix is a transaction log backup. In the FULL recovery model, the log is only reusable after a log backup marks those virtual log files as inactive. No backup, no reuse — the file grows forever. That is by design: the FULL model exists so you can restore to a point in time, and that promise costs log backups.

-- BAD: switching to SIMPLE to "fix" a full log in production
-- You just broke the log chain and lost point-in-time recovery.
ALTER DATABASE SalesDB SET RECOVERY SIMPLE;
DBCC SHRINKFILE (SalesDB_log, 100);

-- GOOD: back up the log, then let reuse happen on its own
BACKUP LOG SalesDB
    TO DISK = 'D:\Backups\SalesDB_log.trn'
    WITH COMPRESSION;
DBCC SQLPERF(LOGSPACE);  -- confirm the used % dropped

Two traps to avoid during the incident. First, flipping to SIMPLE recovery mid-incident breaks the log chain: your next full backup becomes the new base, and everything between the last full backup and the switch is unrecoverable. If the database genuinely does not need point-in-time recovery, SIMPLE is a legitimate choice — but make it a planned decision, not a panic move at 2 AM. Second, do not shrink the log file first. Shrinking while the blocker is still active does nothing, and shrinking after the fact just guarantees the file has to grow again — slowly, one autogrowth event at a time — during the next busy period.

4. When the blocker is downstream: replication and Availability Groups

If log_reuse_wait_desc says REPLICATION, the Log Reader Agent has not delivered the transactions yet — usually because the distributor is down, the agent job failed, or a subscriber is offline. Fix the agent, not the log. If it says AVAILABILITY_REPLICA, a secondary replica has not hardened the log records yet. Check the replica's synchronization state and its network path before you touch the primary.

In both cases the log on the primary is doing exactly what it should: holding records until every consumer has them. Growing the log file buys you time while you fix the real problem. Deleting or shrinking it does not — and if you force the issue, you can break replication or the AG instead. When a replica is permanently gone, remove it from the Availability Group or drop the publication cleanly; do not leave a dead consumer pinning your log forever.

5. Stop it coming back: size, growth, and an alert

Once writes are flowing again, fix the setup. Most log-full incidents I see are really three configuration problems: no scheduled log backups, a log file sized for a quiet day, and nobody watching the used percentage. All three are cheap to fix.

-- GOOD: log backups every 15 minutes, sized log, fixed growth
-- 1. Schedule this in a SQL Agent job, every 15 minutes:
BACKUP LOG SalesDB
    TO DISK = 'D:\Backups\SalesDB_log.trn'
    WITH COMPRESSION;

-- 2. Pre-size the log to a realistic working size (e.g. 8 GB)
--    instead of letting it grow 10% at a time under load:
ALTER DATABASE SalesDB
MODIFY FILE (NAME = N'SalesDB_log', SIZE = 8192MB);

-- 3. Fixed growth in MB, not percent — 10% of 50 GB is a
--    5 GB growth event that freezes writes while it happens:
ALTER DATABASE SalesDB
MODIFY FILE (NAME = N'SalesDB_log', FILEGROWTH = 512MB);

-- 4. Alert when log use passes 70% — the warning you want
--    at 10 AM, not the error you get at 2 AM:
SELECT name, log_reuse_wait_desc
FROM sys.databases
WHERE database_id > 4;

A word on size: do not just make the log enormous and walk away. An oversized log with hundreds of tiny virtual log files slows down startup, restore, and replication. Size it to the largest transaction your workload actually runs, plus headroom — then let the 15-minute backups keep it recycling. And set the alert. The alert is the difference between a five-minute fix during business hours and a 2 AM page.

Closing Thoughts

A full transaction log is rarely a storage problem. It is a reuse problem, and SQL Server names the blocker in one column: log_reuse_wait_desc. Read it first, clear the real cause — a stale transaction, a missing log backup, a stalled replica — and only then think about file size. The five-minute version of this triage is worth memorizing, because error 9002 always arrives at the worst possible moment.
