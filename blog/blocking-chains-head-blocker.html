# Blocking Chains in SQL Server: Finding the Real Head Blocker in 60 Seconds

*By Rajesh Guntupalli*

---

It's 2 AM and your phone is vibrating itself off the nightstand. The app is timing out. You log in, see 200 sessions all showing LCK_M_X waits, and panic starts to set in. The worst thing you can do right now is kill sessions at random. One of those 200 sessions is the head blocker — everything else is just collateral damage. Find that one session and the whole chain resolves itself.

Here's the method I use every single time.

---

1. See the whole chain with one query

Don't look at sessions one by one. One query against sys.dm_exec_requests and sys.dm_exec_sessions shows you every waiting session, who it's blocked by, and how long it's been waiting:

-- Show every blocked session and its blocker
SELECT
    r.session_id,
    r.blocking_session_id,
    r.wait_type,
    r.wait_time / 1000 AS wait_seconds,
    s.login_name,
    s.host_name,
    s.program_name,
    DB_NAME(r.database_id) AS database_name
FROM sys.dm_exec_requests r
JOIN sys.dm_exec_sessions s
    ON s.session_id = r.session_id
WHERE r.blocking_session_id <> 0
   OR r.session_id IN (
       SELECT DISTINCT blocking_session_id
       FROM sys.dm_exec_requests
       WHERE blocking_session_id <> 0
   )
ORDER BY r.blocking_session_id, r.session_id;

The head blocker is the session whose blocking_session_id is 0 (it appears in the result because it IS blocking others) but which is itself not waiting on anyone. That's the single session holding the lock everyone else wants. Everything downstream of it is just a symptom.

---

2. Find out what the head blocker is actually doing

Knowing the session ID is only half the answer. You need its SQL text, and critically, whether it's idle in a transaction — a session doing nothing can still hold locks if the app never issued a COMMIT:

-- What is session 87 (the head blocker) running, and how long has the
-- transaction been open?
DECLARE @spid INT = 87;

SELECT
    r.session_id,
    r.status,
    r.command,
    r.cpu_time,
    r.total_elapsed_time / 1000 AS elapsed_seconds,
    t.text AS current_sql,
    DATEDIFF(SECOND, dt.transaction_begin_time, GETDATE()) AS tran_open_seconds
FROM sys.dm_exec_requests r
LEFT JOIN sys.dm_tran_session_transactions st
    ON st.session_id = r.session_id
LEFT JOIN sys.dm_tran_active_transactions dt
    ON dt.transaction_id = st.transaction_id
OUTER APPLY sys.dm_exec_sql_text(r.sql_handle) t
WHERE r.session_id = @spid;

The pattern I see most often: an app opens a transaction, runs an UPDATE, then waits on some downstream API call before committing. The transaction stays open for minutes holding locks, and the whole database queues up behind it. The fix is rarely on the SQL side — it's in the app code.

---

3. Check the kill cost before you kill anything

If the head blocker is a legit transaction that's almost done, killing it triggers a rollback — and rollbacks are single-threaded, can't be interrupted, and can take longer than just letting the transaction finish. Check how much work it has done first:

-- Estimate rollback cost for a transaction's database work
SELECT
    dt.database_id,
    DB_NAME(dt.database_id) AS database_name,
    dt.database_transaction_log_bytes_used / 1024 / 1024 AS log_mb_used,
    dt.database_transaction_log_bytes_reserved / 1024 / 1024 AS log_mb_reserved
FROM sys.dm_tran_database_transactions dt
JOIN sys.dm_tran_session_transactions st
    ON st.transaction_id = dt.transaction_id
WHERE st.session_id = 87;

If the blocker has written hundreds of megabytes to the log, KILL will start a rollback that undoes all of it — potentially making the outage longer, not shorter. My rule: if the transaction is actively running and close to finishing, let it finish. If it's an idle session holding locks with no work happening, kill it without hesitation — there's nothing to roll back.

---

4. NOLOCK is not the fix

The most common reaction to a blocking incident is sprinkling WITH (NOLOCK) on everything. It hides the blocking by letting reads ignore locks, but you're trading correctness for speed — dirty reads, duplicated rows from page splits, even reading rows that get rolled back. I've seen financial reports built on NOLOCK return wrong totals. You don't want that on call at 3 AM.

The real fixes, in order of preference:

Enable READ_COMMITTED_SNAPSHOT. One ALTER DATABASE and readers stop blocking writers entirely — they read the last committed version from the version store instead. This single change ends most chronic blocking chains in OLTP workloads:

-- Check if it's already on (1 = enabled)
SELECT name, is_read_committed_snapshot_on
FROM sys.databases
WHERE name = 'YourDB';

-- Enable it (needs a quiet moment: takes a schema modification lock)
ALTER DATABASE YourDB SET READ_COMMITTED_SNAPSHOT ON;

Shorten transactions. The blocker is usually an app that opens a transaction, does work, then calls a web service before committing. Transactions should never span network calls. Commit before you leave the database layer.

Fix the missing index. An UPDATE that should touch 10 rows but scans 10 million takes exclusive locks on everything it scans. Proper indexing turns a table-wide lock storm into a few key locks held for milliseconds.

---

5. Build the habit: catch it before your users do

The best blocking incidents are the ones you find in your inbox, not from your users. Set up a lightweight agent job that runs every 5 minutes, logs chains lasting longer than 30 seconds into a history table, and alerts you when the same blocker repeats. Trending data tells you whether this was a one-off or a recurring pattern that needs the real fix.

Keep the head-blocker query from section 1 saved as a snippet in SSMS. When the alert fires at 2 AM, you want muscle memory, not a Google search. The whole diagnosis — find the chain, find the head blocker, see what it's doing, decide whether to kill — should take under 60 seconds.

---

Closing Thoughts

Blocking incidents feel chaotic because the symptoms are everywhere — hundreds of waiting sessions, cascading timeouts, dashboards on fire. But the root cause is always one session holding a lock it shouldn't hold. Find the head blocker, understand why it's holding that lock, and act on that one session. Everything else resolves itself.

And resist the urge to NOLOCK your way out of the 2 AM incident. Your future self, debugging a wrong totals report at 3 AM, will thank you.
