Index maintenance in SQL Server: when to rebuild, when to reorganize, and when to stop

Rajesh Guntupalli·November 2026·6 min read

Almost every SQL Server I inherit has the same maintenance plan: rebuild every index, every night, no exceptions. It is the most common waste of I/O, log space, and maintenance-window time in the DBA world — and in most cases it buys nothing.

Fragmentation is real, but it is not the emergency the default maintenance plan thinks it is. On modern storage, a fragmented index rarely hurts a query that seeks a handful of rows. What hurts is a nightly rebuild of a 200 GB index that was barely fragmented, blocking writes, filling the transaction log, and generating a mountain of log backups — for a 2% improvement nobody will ever feel.

Here is how I decide what to maintain, and what to leave alone.

1. Measure fragmentation before you touch anything

Never maintain an index you have not measured. sys.dm_db_index_physical_stats tells you the truth in one query — logical fragmentation, page count, and page density — for every index in the database.

SELECT
    OBJECT_NAME(ips.object_id) AS table_name,
    i.name AS index_name,
    ips.avg_fragmentation_in_percent,
    ips.page_count,
    ips.avg_page_space_used_in_percent
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'SAMPLED') ips
JOIN sys.indexes i
    ON i.object_id = ips.object_id
    AND i.index_id = ips.index_id
WHERE ips.page_count > 1000          -- ignore tiny indexes
  AND ips.index_level = 0
  AND ips.avg_fragmentation_in_percent > 10
ORDER BY ips.page_count DESC;

The page_count > 1000 filter matters. A 12-page index at 90% fragmentation is irrelevant — the whole thing fits in a handful of reads. Small indexes are noise; only maintain indexes big enough for fragmentation to cost real I/O.

2. Reorganize below 30%, rebuild above it

The old rule still holds, and it is worth keeping because it matches what each operation actually does. REORGANIZE compacts pages in place, is always online, and is gentle on the log. REBUILD creates a fresh copy of the index — faster to fix heavy fragmentation, but far more expensive.

-- 10-30% fragmented: reorganize, always online, light on the log
ALTER INDEX IX_Orders_CustomerId ON dbo.Orders REORGANIZE;

-- Over 30% fragmented: rebuild, online where the edition allows
ALTER INDEX IX_Orders_CustomerId ON dbo.Orders
REBUILD WITH (ONLINE = ON, MAXDOP = 4);

-- Under 10%: do nothing. Seriously. Leave it alone.

One more thing a rebuild gives you that reorganize does not: it updates statistics on that index with a full scan. If a query got slow right after a big data load, a rebuild can fix the plan as a side effect — but if that is all you need, UPDATE STATISTICS ... WITH FULLSCAN is far cheaper than rebuilding the index to get it.

3. Stop rebuilding indexes that re-fragment by morning

Some indexes are fragmentation factories. A nonclustered index on a uniqueidentifier column fed by NEWID(), or an index on a random hash key, will be 60% fragmented again within hours of a rebuild. Rebuilding it nightly is mopping the floor while the tap is running.

For these, the fix is not maintenance — it is design. A sequential key such as NEWSEQUENTIALID() or an identity column inserts at the end of the index instead of in the middle, and fragmentation mostly stops happening. If you cannot change the key, accept the fragmentation: a seek on a fragmented index still finds its rows, and the rebuild was buying you nothing a seek could feel.

4. Rebuilds have a hidden cost: the transaction log

This is the one that bites people. An offline rebuild of a large index is fully logged, and even an online rebuild generates substantial log traffic. I have seen a nightly rebuild job fill a transaction log, stall log backups, and delay an availability group replica — all to defragment indexes that were barely fragmented.

Before you schedule a rebuild, check two things: that the log has room for roughly the size of the index being rebuilt, and that the job runs when log backups can keep up. If the maintenance window is tight, reorganize instead, or split the rebuild across nights by index size. A rebuild that cannot finish inside its window is worse than no rebuild at all.

5. The indexes you should stop maintaining entirely

Not every index deserves maintenance, because not every index deserves to exist. Heaps with no clustered index, duplicate indexes left over from a migration, and indexes on tables that are truncated and reloaded every night do not need a maintenance plan — they need a decision.

-- Find indexes that are never used for seeks or scans
SELECT
    OBJECT_NAME(s.object_id) AS table_name,
    i.name AS index_name,
    s.user_seeks, s.user_scans, s.user_lookups,
    s.user_updates
FROM sys.dm_db_index_usage_stats s
JOIN sys.indexes i
    ON i.object_id = s.object_id
    AND i.index_id = s.index_id
WHERE s.database_id = DB_ID()
  AND s.user_seeks = 0
  AND s.user_scans = 0
  AND s.user_lookups = 0
ORDER BY s.user_updates DESC;

An index with zero reads and thousands of writes is pure overhead: every insert and update pays to maintain it, and no query ever benefits. Drop it — after checking it is not a unique constraint or supporting a foreign key — and you have removed both the index and its maintenance cost in one move.

6. Automate by threshold, not by calendar

The maintenance job that works is one that reads the measurements and acts only where the thresholds say so. A simple cursor over the fragmentation query, reorganizing below 30% and rebuilding above it, replaces the blanket rebuild job entirely — and it finishes in minutes instead of hours because most nights there is almost nothing to do.

DECLARE @sql NVARCHAR(MAX);

DECLARE cur CURSOR LOCAL FAST_FORWARD FOR
SELECT
    CASE
        WHEN ips.avg_fragmentation_in_percent >= 30
        THEN 'ALTER INDEX ' + QUOTENAME(i.name)
             + ' ON ' + QUOTENAME(OBJECT_SCHEMA_NAME(ips.object_id))
             + '.' + QUOTENAME(OBJECT_NAME(ips.object_id))
             + ' REBUILD WITH (ONLINE = ON);'
        ELSE 'ALTER INDEX ' + QUOTENAME(i.name)
             + ' ON ' + QUOTENAME(OBJECT_SCHEMA_NAME(ips.object_id))
             + '.' + QUOTENAME(OBJECT_NAME(ips.object_id))
             + ' REORGANIZE;'
    END
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'SAMPLED') ips
JOIN sys.indexes i
    ON i.object_id = ips.object_id
    AND i.index_id = ips.index_id
WHERE ips.page_count > 1000
  AND ips.index_level = 0
  AND ips.avg_fragmentation_in_percent > 10;

OPEN cur;
FETCH NEXT FROM cur INTO @sql;
WHILE @@FETCH_STATUS = 0
BEGIN
    EXEC sp_executesql @sql;
    FETCH NEXT FROM cur INTO @sql;
END
CLOSE cur;
DEALLOCATE cur;

Run this weekly, not nightly — fragmentation builds slowly on most workloads, and a weekly run keeps the job small enough to finish inside any maintenance window. Log the indexes it touches so you can spot the ones it rebuilds every single week; those are the fragmentation factories from section 3, and they need a design fix, not more maintenance.

Closing Thoughts

Good index maintenance is boring on purpose: measure first, reorganize the mildly fragmented, rebuild only the badly fragmented and large, and stop maintaining indexes that re-fragment by morning or never get read. The goal is not zero fragmentation. The goal is queries that stay fast without the maintenance job becoming the biggest workload on the server.

If you are still running a blanket rebuild-everything job, replace it with the measurement query above and a threshold-based job this week. Your transaction log will thank you.
