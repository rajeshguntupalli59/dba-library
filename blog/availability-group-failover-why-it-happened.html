Your Availability Group failed over at 2 AM: how to find out why

Rajesh Guntupalli·October 2026·7 min read

The alert wakes you up: the Availability Group failed over. The application reconnected, the databases are online on the new primary, and everyone is asking the same question — why did it fail over? "The AG failed over" is not a root cause. It is the start of the investigation, and if you do not nail down the cause now, it will happen again next week, probably at 2 AM again.

Here is the order I work through, every time. It takes about twenty minutes, and it ends with an answer you can defend in the incident review.

1. First, establish what actually happened

Before touching any log, answer three questions: which replica is primary now, when exactly did the role change, and was the failover planned or automatic? A planned manual failover during a patching window and an automatic failover caused by a lease timeout are two completely different incidents, and confusing them wastes the whole investigation.

This query gives you the current state of every replica and database in the group:

SELECT
    ag.name AS ag_name,
    ar.replica_server_name,
    ars.role_desc,
    ars.operational_state_desc,
    ars.connected_state_desc,
    ars.synchronization_health_desc,
    drs.database_name,
    drs.synchronization_state_desc,
    drs.is_suspended
FROM sys.dm_hadr_availability_replica_states ars
JOIN sys.availability_replicas ar
    ON ar.replica_id = ars.replica_id
JOIN sys.availability_groups ag
    ON ag.group_id = ar.group_id
LEFT JOIN sys.dm_hadr_database_replica_states drs
    ON drs.replica_id = ars.replica_id
ORDER BY ag.name, ars.role_desc;

Run it on the new primary. If any database shows NOT SYNCHRONIZING or SUSPENDED, you have a second problem hiding behind the first one — deal with the failover cause first, then fix synchronization before anyone calls the incident closed.

2. Ask the wrong witness last: do not start with the application logs

The instinct is to start with whatever paged you — the application errors, the connection timeouts, the monitoring alert. Those tell you the failover hurt, not why it happened. The failover has exactly three reliable witnesses, and you should question them in this order: the Windows cluster log, the SQL Server error log, and the AG DMVs.

The mistake I see most often looks like this:

-- BAD: Only proves the failover happened, not why
SELECT * FROM sys.dm_hadr_availability_replica_states;
-- "The secondary is primary now." Yes. Why?

-- GOOD: Start from the failover event and work backwards
-- 1. Cluster log: what did the cluster decide, and when?
-- 2. SQL Server error log: what did the instance see?
-- 3. DMVs: what is the state right now?

3. Read the cluster log — the cluster made the decision

For an automatic failover, the Windows Server Failover Cluster is the thing that actually decided to move the group. Its log is the only place that records the decision and the reason. Generate it from any cluster node:

# Run in PowerShell on any cluster node
Get-ClusterLog -Destination C:\Temp -TimeSpan 60
# Then search the log for the AG resource name and the failover time window

Search around the failover timestamp for phrases like lost lease, health check timeout, quorum was lost, or resource failed. One of these is almost always there. The cluster log is noisy — thousands of lines per hour — so filter hard on the time window and the AG resource name, or you will drown in it.

If the log shows a manual failover command, your investigation is nearly over: find out who ran it and whether it was the planned maintenance you already knew about. Check the change log before you declare a mystery.

4. Match the cluster's story against the SQL Server error log

Now open the SQL Server error log on the old primary for the same time window. You are looking for what the instance experienced: lease timeouts, I/O stalls, or the instance going unresponsive. A lease timeout means the cluster could not reach the instance — the instance may have been perfectly healthy but starved of CPU, or the host may have been frozen by a backup, a snapshot, or a runaway process.

Cross-check with the system event log on the old primary's host for the same minutes: disk errors, network adapter resets, or a host-level freeze all show up there and explain a lease timeout that SQL Server alone cannot. I once chased a "SQL Server problem" for two days before the host event log showed a storage path flapping every night during the backup window. The database was the victim, not the cause.

5. Learn the five usual suspects by heart

Almost every unplanned AG failover I have investigated comes down to one of these five. Run through them in order and most investigations end at step two:

Lease timeout — the instance was too busy or frozen to renew its cluster lease. Look for CPU pressure, memory pressure, or a host freeze. Health check timeout — the sp_server_diagnostics check did not complete in time, usually because the instance was under severe resource pressure. Quorum loss — the cluster lost too many votes, often after a network partition or a second node going down for maintenance at the same time. Manual failover — someone, or some automation, moved the group on purpose. Resource failure — the AG resource itself failed, which usually means the instance crashed or was stopped.

If none of the five fits, widen the window: check whether a patching or backup job overlapped the failover time, and whether the same failover has happened before at the same hour. Recurring failovers on a schedule are almost always a job, not a fault.

6. Before you close the incident, prove the new primary is actually healthy

A failover is not over when the role moves. Check synchronization health on every database, confirm the redo queue on the new secondary is draining rather than growing, and verify the listener is pointing clients at the right replica. This is also the moment to check failover readiness for next time:

-- Failover readiness: every database synchronized, no suspended replicas?
SELECT
    drs.database_name,
    drs.synchronization_state_desc,
    drs.synchronization_health_desc,
    drs.redo_queue_size,
    drs.redo_rate,
    drs.log_send_queue_size
FROM sys.dm_hadr_database_replica_states drs
JOIN sys.availability_replicas ar
    ON ar.replica_id = drs.replica_id
WHERE drs.is_local = 0
  AND drs.synchronization_state_desc <> 'SYNCHRONIZED';

An empty result here means every remote database is synchronized and ready to take over. Anything in the result is a failover that will hurt — fix it now, while nobody is paging you.

Closing takeaway

Write the cause down the same night, while the logs are fresh. "AG failed over, cause unknown, monitoring" is how teams end up explaining the same incident three times. The cluster log tells you what was decided, the error log tells you what the instance felt, and the DMVs tell you where you stand now. Twenty minutes with all three, and the 2 AM mystery becomes a one-line entry in the incident log — and a fix you can actually schedule.
