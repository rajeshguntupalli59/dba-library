RAG on your own SQL Server data: a production-ready pipeline

Rajesh Guntupalli·August 2026·6 min read

Most RAG tutorials show you embeddings, a similarity search, and a prompt template, then stop right before the part that actually determines whether the system is useful: what happens when the underlying data changes. I've shipped three RAG systems entirely on SQL Server, and the pipeline that survives contact with production looks different from the demo in three specific ways.

Chunking: boring beats clever

I started with semantic chunking — using a model to decide chunk boundaries based on topic shifts — and it produced noticeably better-feeling demo results and noticeably worse production reliability, because chunk boundaries became nondeterministic across re-ingestion runs. What actually shipped: fixed-size chunks with overlap, respecting paragraph and heading boundaries where they exist, with metadata that preserves the document structure the chunk came from.

CREATE TABLE document_chunks (
  id BIGINT IDENTITY(1,1)
    CONSTRAINT PK_document_chunks PRIMARY KEY,
  document_id BIGINT NOT NULL REFERENCES documents(id),
  chunk_index INT NOT NULL,
  heading_path NVARCHAR(500),          -- "Chapter 3 > Indexing > B-tree structure"
  content NVARCHAR(MAX) NOT NULL,
  embedding VECTOR(1536) NOT NULL,     -- native vector type (SQL Server 2025)
  source_updated_at DATETIME2 NOT NULL,
  CONSTRAINT UQ_document_chunks UNIQUE (document_id, chunk_index)
);

-- DiskANN-backed vector index for fast similarity search
CREATE VECTOR INDEX IX_document_chunks_embedding
  ON document_chunks (embedding);

The heading_path column is the detail most tutorials skip, and it's the one that makes retrieved chunks actually usable — when the model cites "Chapter 3 > Indexing > B-tree structure" instead of an anonymous paragraph, both the model's reasoning and the user's trust improve measurably.

Retrieval: hybrid, not just vector

Pure vector similarity misses exact-match queries embarrassingly often — someone searching for an error code, a specific function name, or a SKU wants keyword precision, not semantic similarity, and a vector-only pipeline will confidently return something topically related but wrong. Combining SQL Server full-text search with vector similarity, using reciprocal rank fusion, fixes this without needing a separate system:

-- Full-text index for the keyword half of hybrid search
CREATE FULLTEXT CATALOG ft_catalog;
CREATE FULLTEXT INDEX ON document_chunks(content)
  KEY INDEX PK_document_chunks;
GO

DECLARE @q VECTOR(1536) = ...;      -- the query embedding
DECLARE @keywords NVARCHAR(4000) = N'...';  -- the raw query text

WITH vector_results AS (
  SELECT TOP (20) id,
         RANK() OVER (ORDER BY VECTOR_DISTANCE('cosine', embedding, @q)) AS rnk
  FROM document_chunks
  ORDER BY VECTOR_DISTANCE('cosine', embedding, @q)
),
text_results AS (
  SELECT TOP (20) c.id,
         RANK() OVER (ORDER BY ft.[RANK] DESC) AS rnk
  FROM document_chunks AS c
  INNER JOIN FREETEXTTABLE(document_chunks, content, @keywords) AS ft
    ON ft.[KEY] = c.id
)
SELECT c.id, c.content, c.heading_path,
       COALESCE(1.0 / (60 + v.rnk), 0) + COALESCE(1.0 / (60 + t.rnk), 0) AS score
FROM document_chunks AS c
LEFT JOIN vector_results AS v ON v.id = c.id
LEFT JOIN text_results AS t ON t.id = c.id
WHERE v.id IS NOT NULL OR t.id IS NOT NULL
ORDER BY score DESC
OFFSET 0 ROWS FETCH NEXT 8 ROWS ONLY;

This single query does what two separate systems and an application-layer merge step would otherwise need to do, and it stays inside one transactional boundary with the rest of your data.

Freshness: the problem every demo skips

A RAG demo ingests a static document set once. A production system has source data that changes constantly, and stale embeddings are a worse failure mode than no RAG at all — a confidently wrong answer based on last month's pricing is more damaging than "I don't know." The fix is treating embedding freshness as a first-class operational concern, not an afterthought:

Track source_updated_at against the chunk's own embedding timestamp, and re-embed anything where the source moved. For content that changes on a predictable schedule (product catalogs, pricing pages), a scheduled job is enough. For content that changes unpredictably, a trigger-driven approach — flag the row dirty on write, re-embed in a background worker — keeps the lag bounded without re-embedding your entire corpus on every write:

CREATE TABLE embedding_refresh_queue (
  chunk_id BIGINT PRIMARY KEY REFERENCES document_chunks(id),
  queued_at DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);
GO

CREATE TRIGGER trg_document_chunks_dirty
ON document_chunks
AFTER UPDATE
AS
BEGIN
  SET NOCOUNT ON;
  IF UPDATE(content)
  BEGIN
    INSERT INTO embedding_refresh_queue (chunk_id)
    SELECT i.id
    FROM inserted AS i
    WHERE NOT EXISTS (
      SELECT 1 FROM embedding_refresh_queue AS q
      WHERE q.chunk_id = i.id
    );
  END
END;

A worker drains that queue, calls the embedding API, and updates the row. Simple, observable (queue depth tells you exactly how stale your worst-case chunk is), and it turns "did we remember to re-embed this" from a hope into a measured SLA.

None of this is exotic. It's the same operational discipline — track state explicitly, make staleness observable, keep the blast radius of any single failure small — that applies to any production data pipeline. RAG doesn't get a pass on that discipline just because there's a model in the loop.
