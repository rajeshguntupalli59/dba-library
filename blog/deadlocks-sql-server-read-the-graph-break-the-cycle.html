Deadlocks in SQL Server: read the graph, break the cycle

# Deadlocks in SQL Server: Read the Graph, Break the Cycle

*By Rajesh Guntupalli*

---

Every SQL Server DBA has a deadlock story. Mine involves a 3 AM alert, a payment processing job, and an error 1205 that kept reappearing no matter how many times the job retried. The app team wanted a retry loop. I wanted the actual cause. The retry loop lost — temporarily — and the deadlock graph told me exactly why.

Deadlocks aren't random. They're a deterministic cycle of lock requests, and the deadlock graph shows you every step of it. Here's how to read one and how to break the cycle for good.

---

1. What a deadlock actually is (and how SQL Server picks a victim)

A deadlock is a circle of waiting: process A holds a lock on row 1 and wants row 2, while process B holds a lock on row 2 and wants row 1. Neither can proceed. SQL Server's lock monitor detects the cycle and picks a victim to roll back.

Victim selection isn't random either. SQL Server first honors DEADLOCK_PRIORITY — higher values survive, lower ones die. If priorities tie, it kills the session with the lowest estimated rollback cost, which is usually the transaction that has done the least work. The survivor gets the locks and finishes; the victim gets error 1205.

-- Which session is running with an unusual deadlock priority?
SELECT session_id, deadlock_priority
FROM sys.dm_exec_sessions
WHERE deadlock_priority <> 0
  AND is_user_process = 1;

If you've ever set DEADLOCK_PRIORITY HIGH to "fix" a deadlock, all you did was move the error 1205 to somebody else. Priorities manage consequences, not causes.

---

2. Capturing deadlock graphs without a trace flag

The good news: you don't need trace flag 1222. The built-in system_health extended event session captures every deadlock graph by default on SQL Server 2012 and later. No setup, no restart.

-- Pull the most recent deadlock graphs from the system_health ring buffer
WITH events AS (
    SELECT CAST(t.target_data AS xml) AS target_xml
    FROM sys.dm_xe_sessions s
    JOIN sys.dm_xe_session_targets t
        ON t.event_session_address = s.address
    WHERE s.name = N'system_health'
      AND t.target_name = N'ring_buffer'
)
SELECT
    event_xml.value('(event/@timestamp)[1]', 'datetime2') AS deadlock_time,
    event_xml.query('(event/data/value/deadlock)[1]')     AS deadlock_graph
FROM events
CROSS APPLY target_xml.nodes('RingBufferTarget/event') AS x(event_xml)
WHERE event_xml.value('(event/@name)[1]', 'varchar(50)') = 'xml_deadlock_report'
ORDER BY deadlock_time DESC;

Run that right after a deadlock alert and you get the full XML graph. On a busy server, the ring buffer recycles — if you need history, set up your own XE session writing to a file target. One recurring deadlock a week is worth a permanent capture.

---

3. Reading the graph: process-list, resource-list, and the one line that matters

A deadlock graph XML has two lists that matter: process-list (who was involved) and resource-list (what they were fighting over). In SSMS, the graphical deadlock graph view shows the same thing — the classic "process 1 → resource → process 2 → resource → process 1" circle.

Each process entry includes the inputbuf — the actual batch the session was running. That's the shortcut: in almost every graph I've analyzed, reading the two input buffers tells you the story before you decode a single lock mode.

-- BAD: two procedures touch the same two tables in opposite order
-- proc_payments updates orders, then payments
UPDATE dbo.orders   SET status = 'Paid' WHERE order_id = @id;
UPDATE dbo.payments  SET status = 'Done' WHERE order_id = @id;

-- proc_refunds updates payments, then orders  -- deadlock magnet
UPDATE dbo.payments  SET status = 'Reversed' WHERE order_id = @id;
UPDATE dbo.orders    SET status = 'Refunded' WHERE order_id = @id;

That was my 3 AM story: payments touched orders then payments; refunds touched payments then orders. Two X locks acquired in opposite order. The graph's owner-list and waiter-list confirmed it in under a minute.

---

4. Fix #1: touch tables in the same order, everywhere

The single highest-value deadlock fix I know: establish a canonical access order and enforce it in every procedure. If everything updates orders before payments, the circle can never form.

-- GOOD: both procedures use the same canonical order (orders, then payments)
CREATE PROCEDURE dbo.ApplyRefund (@id int)
AS
BEGIN
    SET NOCOUNT ON;
    UPDATE dbo.orders   SET status = 'Refunded' WHERE order_id = @id;
    UPDATE dbo.payments  SET status = 'Reversed' WHERE order_id = @id;
END;

This is a code-review discipline, not a server setting. I keep a one-page "lock order" note in the runbook for each database — orders → payments → audit — and any procedure that violates it gets flagged. Sounds boring. It eliminated 90% of our deadlocks in one sprint.

---

5. Fix #2: shorten transactions and use the right isolation level

Long transactions hold locks long. Locks held long overlap with other transactions. Overlap is where deadlocks live. The second fix is shrinking the window: do your reads, business logic, and validation outside the transaction, then open it only for the writes.

Where readers fight writers, enable read committed snapshot isolation (RCSI). Readers take no shared locks, so read/write cycles — the most common deadlock shape — disappear.

-- BAD: transaction spans slow app work; locks held the whole time
BEGIN TRAN;
    EXEC dbo.CallPaymentGateway @id;   -- seconds of blocking
    UPDATE dbo.orders SET status = 'Paid' WHERE order_id = @id;
COMMIT;

-- GOOD: transaction covers only the writes
EXEC dbo.CallPaymentGateway @id;       -- outside the transaction
BEGIN TRAN;
    UPDATE dbo.orders SET status = 'Paid' WHERE order_id = @id;
COMMIT;

-- Enable RCSI once per database (test in staging first — row versions add tempdb load)
ALTER DATABASE Sales SET READ_COMMITTED_SNAPSHOT ON;

RCSI is not free: version store writes go to tempdb, so monitor tempdb after enabling. But trading reader-writer deadlocks for a tempdb load you can plan for is almost always a good deal.

---

6. Fix #3: add the covering index that stops lock escalation

Some deadlocks come from missing indexes. A lookup on an unindexed foreign key scans rows, taking shared locks on everything it touches — and a concurrent writer then needs exclusive locks on those same rows. A covering index turns that scan into a narrow seek, taking far fewer locks for a far shorter time.

The deadlock graph tells you exactly which columns are involved: the resource-list shows the key or page each process was waiting on. When I see deadlocks on the same two keys from lookup-heavy procedures, a targeted index usually ends it.

-- The graph showed waits on payments(order_id) via scan; a seek takes one key lock
CREATE INDEX IX_payments_order_id
    ON dbo.payments (order_id)
    INCLUDE (status, updated_at);

This is also where the missing-index DMVs earn their keep — sys.dm_db_missing_index_details often points at the same columns the deadlock graph does. Two independent signals agreeing is the strongest evidence you'll get.

---

Closing takeaway

Stop treating deadlocks as random flakiness and stop papering over them with DEADLOCK_PRIORITY or blind retries. Pull the graph from system_health, read the two input buffers, and you'll almost always find one of three things: opposite table access order, a transaction that's too fat, or a missing index turning seeks into scans. Fix the cause and the 1205s stop.
