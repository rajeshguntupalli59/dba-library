How to find missing indexes in SQL Server in 30 seconds

Rajesh Guntupalli · May 2026 · 5 min read

Every SQL Server DBA has been there — a query that was fast last month is suddenly taking 10 seconds. You run it with the actual execution plan turned on, stare at the output, and wonder where to start.

The plan looks something like this:

Clustered Index Scan on orders  (Cost: 92% of batch)
  Predicate: [orders].[customer_id] = 42
  Actual Rows: 2000    Actual Executions: 1
  Logical Reads: 1,240

You can see "Clustered Index Scan" eating 92% of the batch, and 1,240 logical reads for 2,000 rows, which definitely is bad. But what exactly do you do about it?

The problem with manual plan reading

Reading execution plans well takes years of practice. You need to know that a Clustered Index Scan on a large table means no useful nonclustered index exists, that cost percentages are relative to the batch (not milliseconds), and that the fix in this case is an index on customer_id.

Most developers don't have that experience. And even experienced DBAs spend more time than necessary on this for every single slow query.

A faster way — let the DMVs tell you

SQL Server tracks exactly which indexes the optimizer wished it had. The missing-index DMVs — sys.dm_db_missing_index_details, sys.dm_db_missing_index_groups, and sys.dm_db_missing_index_group_stats — record every query the optimizer planned without an ideal index, along with the estimated improvement:

SELECT
    migs.avg_total_user_cost * migs.avg_user_impact
        * (migs.user_seeks + migs.user_scans) AS improvement_measure,
    OBJECT_SCHEMA_NAME(mid.object_id) AS schema_name,
    OBJECT_NAME(mid.object_id) AS table_name,
    mid.equality_columns,
    mid.inequality_columns,
    mid.included_columns,
    migs.user_seeks, migs.user_scans
FROM sys.dm_db_missing_index_groups AS mig
JOIN sys.dm_db_missing_index_group_stats AS migs
    ON migs.group_handle = mig.index_group_handle
JOIN sys.dm_db_missing_index_details AS mid
    ON mid.index_handle = mig.index_handle
WHERE migs.avg_user_impact > 50
ORDER BY improvement_measure DESC;

Sort by improvement_measure and the top rows are the indexes that would help the most, across your entire workload — not just one query. Cross-reference the top candidates with Query Store to confirm the queries behind them actually matter before you create anything.
