Tempdb under pressure: diagnosing allocation contention and spills

# Tempdb Under Pressure: Diagnosing Allocation Contention and Spills

*By Rajesh Guntupalli*

---

Tempdb is the one database on your instance that you never backed up, never tuned, and never thought about — until it becomes the bottleneck for everything. Every query that sorts, hashes, spools, or builds a temp table leans on tempdb. When it slows down, symptoms look like everything else: queries get slower, waits climb, and nothing obvious is blocked. I've walked into more than one "the server is slow" incident where tempdb was the whole story.

Tempdb pain comes from three directions: file-level allocation contention, sort and hash spills, and version store growth. They have different signatures and different fixes. Here's how I diagnose each.

---

1. Start with the basics: space, latency, and version store

Before chasing exotic causes, rule out the obvious. Is tempdb full, is it slow, and is the version store ballooning? One script answers all three:

-- Tempdb health snapshot: free space, file latency, version store size
SELECT
    DB_NAME(f.database_id) AS database_name,
    f.name AS file_name,
    f.type_desc,
    f.size * 8.0 / 1024 AS size_mb,
    (f.size - FILEPROPERTY(f.name, 'SpaceUsed')) * 8.0 / 1024 AS free_mb,
    fs.num_of_reads,
    fs.num_of_writes,
    CASE WHEN fs.num_of_reads + fs.num_of_writes > 0
         THEN (fs.io_stall_read_ms + fs.io_stall_write_ms) / (fs.num_of_reads + fs.num_of_writes)
         ELSE 0 END AS avg_io_stall_ms
FROM tempdb.sys.database_files f
LEFT JOIN sys.dm_io_virtual_file_stats(2, NULL) fs
    ON fs.file_id = f.file_id;

-- Version store size in tempdb (should stay small; watch it grow with SNAPSHOT isolation)
SELECT
    SUM(version_store_reserved_page_count) * 8.0 / 1024 AS version_store_mb
FROM sys.dm_db_file_space_usage;

If avg_io_stall_ms is consistently above 20–30ms on tempdb files, your tempdb is waiting on storage. That's the simplest possible finding and it happens more than people admit — tempdb on the same slow volume as everything else, or a virtual disk that someone provisioned thin.

---

2. Check for allocation page contention (the classic 2:1:1 problem)

This is the famous one. Tempdb has shared allocation pages — GAM, SGAM, and PFS — and on a busy server hundreds of threads can pile up waiting on the same handful of pages. The signature is heavy PAGELATCH_EX or PAGELATCH_SH waits with page IDs pointing at tempdb (database_id 2). This query finds it directly:

-- Find which pages latch waits are waiting on right now
SELECT
    d.name AS database_name,
    wt.wait_type,
    wt.waiting_task_address,
    PAGE_ADDRESS = wt.resource_description,
    s.session_id,
    s.login_name,
    s.program_name
FROM sys.dm_os_waiting_tasks wt
JOIN sys.dm_exec_sessions s
    ON s.session_id = wt.session_id
JOIN sys.databases d
    ON d.database_id = CASE
        WHEN wt.resource_description LIKE '2:%' THEN 2
        ELSE wt.database_id END
WHERE wt.wait_type LIKE 'PAGELATCH%'
ORDER BY wt.wait_duration_ms DESC;

If you see a wall of PAGELATCH_EX waits on resources like 2:1:1, 2:1:3 — PFS pages — that's allocation contention. The classic fix, still valid: add more tempdb data files, one per logical CPU up to 8, all sized identically with identical autogrowth. Also make sure you don't have one file at 10 GB and seven at 100 MB — the proportional-fill algorithm will hammer the empty ones.

-- How many tempdb data files do you have, and are they evenly sized?
SELECT name, size * 8.0 / 1024 AS size_mb, growth * 8.0 / 1024 AS growth_mb
FROM tempdb.sys.database_files
WHERE type = 0;

-- Add files so you have 8 equally sized data files (run during a maintenance window)
ALTER DATABASE tempdb
ADD FILE (NAME = tempdev2, FILENAME = 'D:\Data\tempdev2.ndf', SIZE = 4096MB, FILEGROWTH = 512MB);

On modern SQL Server versions, enabling trace flags 1117 and 1118 via the configuration option for uniform autogrowth also helps — the fix is structural, not per-query.

---

3. Hunt down spills: sorts and hashes that overflow to disk

The second flavor of tempdb pain is query plans that expected a small sort or hash table, got a big one, and spilled to tempdb. Spills are 10–100x slower than the in-memory operation the plan was built for. The giveaway is the "Sort Warnings" or "Hash Warning" event, and in modern plans you can see spill sizes directly. This finds the worst spillers in your plan cache:

-- Top queries by estimated spills to tempdb (SQL Server 2019+)
SELECT TOP 20
    qs.total_spills / NULLIF(qs.execution_count, 0) AS avg_spills_per_exec,
    qs.total_spills,
    qs.execution_count,
    SUBSTRING(t.text, 1, 200) AS query_snippet
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) t
WHERE qs.total_spills > 0
ORDER BY qs.total_spills DESC;

Spills almost always mean the optimizer guessed wrong about row counts. The root cause is stale or missing statistics, or parameter sniffing that built a plan for one value and ran it for another. Fix order: update statistics on the involved tables, look at the actual vs. estimated rows in the plan, and consider OPTION (RECOMPILE) for queries with volatile parameters. In SQL Server 2022+, memory grant feedback can automatically correct recurring spills — check sys.dm_exec_query_stats for last_dop and memory grant adjustments before rewriting the query.

---

4. Find what's bloating the version store

If you're running READ_COMMITTED_SNAPSHOT or SNAPSHOT isolation — and you should be — tempdb hosts the version store: old row versions kept alive so readers see a consistent picture. It stays small as long as transactions finish quickly. The moment one session leaves a transaction open for an hour, the version store grows and every new version chains onto it. This finds the culprit:

-- Sessions holding the version store open with long transactions
SELECT
    s.session_id,
    s.login_name,
    s.host_name,
    s.program_name,
    DATEDIFF(MINUTE, dt.transaction_begin_time, GETDATE()) AS tran_open_minutes,
    dt.transaction_id
FROM sys.dm_tran_active_snapshot_database_transactions st
JOIN sys.dm_tran_active_transactions dt
    ON dt.transaction_id = st.transaction_id
JOIN sys.dm_tran_session_transactions sst
    ON sst.transaction_id = dt.transaction_id
JOIN sys.dm_exec_sessions s
    ON s.session_id = sst.session_id
ORDER BY dt.transaction_begin_time;

In practice it's usually a report or an ETL step that opens a transaction and then sits on it. The fix is the same as in every blocking story: keep transactions short and never let them span network calls or user think-time.

---

5. Make it boring: baseline tempdb before the incident

Everything above is reactive. The move that pays off long-term is a lightweight baseline: every 10 minutes, log tempdb file space usage, version store size, and PAGELATCH wait counts into a history table. Ten rows an hour, nothing. When a slowdown hits, you can immediately answer "was tempdb different an hour ago?" instead of guessing.

I keep one alert on top of it: version store above 20% of tempdb, or a data file with less than 10% free space. Those two thresholds have caught nearly every tempdb incident I've seen before users noticed.

---

Closing Thoughts

Tempdb incidents are confusing because the symptoms are generic — everything gets a little slower, waits climb across the board, and no single query looks guilty. The diagnosis is simple once you know the three flavors: latch waits on 2:x pages mean allocation contention, spill warnings mean the optimizer misestimated, and a growing version store means someone left a transaction open.

Check tempdb first, not last. It's the one database every query shares, and it's usually the one nobody tuned.
