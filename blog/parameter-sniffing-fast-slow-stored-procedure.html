Parameter sniffing in SQL Server: why the same stored procedure runs fast and slow

Rajesh Guntupalli·October 2026·7 min read

Few production mysteries are as frustrating as this one: a stored procedure runs in 200 milliseconds for one customer and takes 90 seconds for another. Same procedure, same code, same indexes. The developers swear nothing changed. The execution plans look like two completely different queries. And sometimes they are — in spirit, if not in text.

This is parameter sniffing, and it is one of the most common root causes I find behind "intermittent" slowdowns in SQL Server environments. Here is what is actually happening, how to prove it in about five minutes, and the fixes that actually hold up.

1. The first call compiles the plan; everyone else inherits it

When SQL Server executes a stored procedure for the first time (or after a plan cache flush), it compiles an execution plan based on the actual parameter values passed in that first call. That compiled plan is then cached and reused for every subsequent call — regardless of how different the new parameter values are.

The optimizer does its job perfectly for the value it saw. The problem is skewed data. Imagine a procedure that looks up orders by customer_id. One customer has 12 orders; another has 400,000. If the first call compiles for the 12-order customer, the cached plan might choose nested loops with a key lookup — elegant for 12 rows, catastrophic for 400,000. Flip it around and the 12-order customer gets a hash join over a giant scan.

So the plan is not "wrong" — it was optimized for a reality that no longer applies. This is why the slowness comes and goes: whoever calls first after a recompile wins, and everyone else pays.

2. Prove it before you touch anything

Do not start with fixes. Start with evidence. The cheapest proof is to run the procedure with the bad parameter right after evicting its cached plan, and watch whether it suddenly gets fast:

-- Find the plan handle for your procedure
SELECT qs.plan_handle, st.text
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
WHERE st.text LIKE '%dbo.GetCustomerOrders%';

-- Evict ONLY that plan (never run DBCC FREEPROCCACHE on a whole server in prod)
DBCC FREEPROCCACHE (0x06000...);  -- paste the real plan_handle here

-- Re-run with the "bad" parameter and compare duration
EXEC dbo.GetCustomerOrders @customer_id = 42;

If the slow call becomes fast after the cache eviction, you have your diagnosis. For ongoing confirmation, Query Store is even better — it keeps the history of which plans ran, with which runtime stats, so you can watch the fast and slow plans take turns:

-- Plans and their average durations for one procedure, from Query Store
SELECT p.plan_id,
       AVG(rs.avg_duration) / 1000.0 AS avg_ms,
       COUNT(*) AS executions
FROM sys.query_store_plan p
JOIN sys.query_store_query q ON q.query_id = p.query_id
JOIN sys.query_store_query_text qt ON qt.query_text_id = q.query_text_id
JOIN sys.query_store_runtime_stats rs ON rs.plan_id = p.plan_id
WHERE qt.query_sql_text LIKE '%dbo.GetCustomerOrders%'
GROUP BY p.plan_id
ORDER BY avg_ms DESC;

Two plans for the same query with wildly different average durations is the classic signature. Also compare estimated vs. actual row counts in the plan — a sniffed plan shows an estimate matching the first call's selectivity, not the current one.

3. Fix it the cheap way first: OPTION (RECOMPILE)

If the procedure executes dozens or hundreds of times per minute, recompile cost is trivial compared to running the wrong plan for 90 seconds:

-- GOOD: each call gets a plan built for ITS parameter values
CREATE OR ALTER PROCEDURE dbo.GetCustomerOrders
    @customer_id INT
AS
SELECT o.order_id, o.order_date, o.total
FROM dbo.orders o
WHERE o.customer_id = @customer_id
OPTION (RECOMPILE);

I reach for this first whenever the procedure is not called hundreds of times per second and the plan is sensitive to the parameter. It is also the safest to test in a crisis because it changes nothing structural. The tradeoff: compilation cost on every execution. On a hot loop of 2,000 calls per second, that cost matters — but that is the rare case, not the default one.

4. Fix it the targeted way: OPTIMIZE FOR the reality of your data

Sometimes you know your workload's shape: 95% of calls pass a small customer ID, 5% pass the whales. Instead of letting a random first call decide, you tell the optimizer which reality to optimize for:

-- BAD: plan flips based on whoever called first after a recompile
SELECT o.order_id, o.order_date, o.total
FROM dbo.orders o
WHERE o.customer_id = @customer_id;

-- GOOD: compile for the value that represents your dominant workload
SELECT o.order_id, o.order_date, o.total
FROM dbo.orders o
WHERE o.customer_id = @customer_id
OPTION (OPTIMIZE FOR (@customer_id = 11842));  -- your typical customer

-- GOOD: or admit you cannot know and ask for an average-statistics plan
SELECT o.order_id, o.order_date, o.total
FROM dbo.orders o
WHERE o.customer_id = @customer_id
OPTION (OPTIMIZE FOR UNKNOWN);

There is a related trick worth knowing: copying the parameter into a local variable inside the procedure defeats sniffing (the optimizer uses density statistics instead of the specific value). It is less explicit than OPTIMIZE FOR UNKNOWN but achieves a similar averaging effect, and it requires no hints on the statement.

5. Fix it the durable way: Query Store plan forcing

Hints change the code, and code changes need deployments. When you already have a known-good plan recorded in Query Store and you just need to stop the flip-flopping today, force the good plan:

-- Pin the good plan so the bad one never gets picked again
EXEC sys.sp_query_store_force_plan
     @query_id = 1284,
     @plan_id  = 9051;

-- Remove the pin later, after you've fixed the underlying sensitivity
EXEC sys.sp_query_store_unforce_plan @query_id = 1284;

I treat plan forcing as a stabilizer, not a cure. It locks you to today's good plan while you apply one of the structural fixes above. Revisit forced plans after data growth or schema changes — a forced plan that quietly becomes the wrong plan is parameter sniffing wearing a different mask.

Closing takeaway

Parameter sniffing is the optimizer doing exactly what it was asked to do — optimize for the values it saw. The instability is a feature of the cache, not a bug in your query. So the diagnosis is always the same sequence: confirm with a cache eviction, watch the plans fight in Query Store, then pick the fix that matches your call rate and data skew — recompile for low-frequency sensitivity, optimize-for for skewed-but-predictable workloads, and plan forcing to stabilize while you fix the structure.

The next time someone tells you "the stored procedure is slow for some users," resist the urge to tune indexes first. Ask which parameter they passed.
