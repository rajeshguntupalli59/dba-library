How AI-assisted index advisors actually decide what to recommend

Rajesh Guntupalli·August 2026·5 min read

I built the index advisor in QueryOptimizer to give a recommendation and a reason, not just a CREATE INDEX statement to copy-paste. That distinction turned out to matter more than I expected, because the moment DBAs started asking the tool "why," I had to be honest with myself about what the underlying model was actually weighing — and where that reasoning breaks down.

The signals that actually drive a good recommendation

Selectivity and access pattern do most of the work, and neither requires AI — they're the same signals a skilled human DBA reads from an execution plan. What AI genuinely adds is correlating those signals across a query workload instead of one query at a time. Feed a model a week of Query Store data, and it can spot that fourteen different queries all filter on (tenant_id, status, created_at) in slightly different orders — a pattern a human reviewing queries one at a time is unlikely to notice, but that points clearly at one well-chosen composite index instead of four narrow ones.

-- Workload signal: 14 queries share this filter shape
SELECT * FROM invoices
WHERE tenant_id = $1 AND status = 'pending' AND created_at > $2;

SELECT COUNT(*) FROM invoices
WHERE tenant_id = $1 AND created_at > $2 AND status != 'void';

-- Recommendation: one composite index serves both access patterns
CREATE INDEX idx_invoices_tenant_status_created
  ON invoices (tenant_id, status, created_at);

Write amplification is the second real signal, and it's the one naive advisors skip. Every index speeds up the reads it serves and slows down every write to that table. A workload-aware advisor needs write frequency and write latency budget as inputs, not just query frequency — otherwise you get "correct" recommendations that quietly regress your busiest write path.

Where the reasoning breaks down

The advisor has no idea what your deployment actually looks like unless you tell it. It doesn't know your table gets a nightly bulk load that would make index maintenance during that window expensive, that you're two weeks from a migration that drops the column it wants to index, or that your team has an unwritten rule against indexes over three columns because of a past incident. This is the same gap I hit with text-to-SQL and with MCP-connected agents generally — the model is reasoning from what's in front of it, and a huge amount of what actually matters for a production decision isn't in front of it unless someone puts it there.

The second failure mode is subtler: an advisor optimizing for the queries it can see will happily recommend an index that helps a slow reporting query at the cost of a hot-path write it either can't see clearly or doesn't weight heavily enough. I've caught recommendations that would have shaved 200ms off a once-a-day dashboard query while adding measurable write latency to a table taking thousands of inserts per second. The math wasn't wrong given the inputs — the inputs were incomplete.

The workflow that actually works

Treat every recommendation as a hypothesis, not a directive. The advisor's real job is compressing the time to a good hypothesis — same as AI-assisted query tuning generally — not replacing the validation step. Before I apply anything, I check three things it can't fully see on its own: current write volume on the target table, whether an existing index already covers most of the same ground (index consolidation opportunities get missed more often than you'd think), and whether the workload sample it reasoned from is actually representative or just captured a quiet Tuesday.

-- Before applying: check write volume on the target table
SELECT OBJECT_NAME(object_id) AS table_name,
       SUM(leaf_insert_count + leaf_update_count + leaf_delete_count) AS total_writes
FROM sys.dm_db_index_operational_stats(DB_ID(), OBJECT_ID('invoices'), NULL, NULL)
GROUP BY object_id;

-- And check for existing overlapping indexes
SELECT i.name AS index_name, i.type_desc
FROM sys.indexes AS i
WHERE i.object_id = OBJECT_ID('invoices');

Autonomous index management — where the system applies its own recommendations without a human in the loop — is a real and growing capability, and I cover the guardrails that make it safe (staged rollout, automatic rollback on regression, blast-radius limits) separately, because it deserves more than a paragraph here. For now, the honest state of the art: AI-assisted index advice is genuinely good at surfacing the hypothesis. It is not yet good enough to skip the DBA who knows what the model can't see.
