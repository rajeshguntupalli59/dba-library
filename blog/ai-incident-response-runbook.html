AI-assisted incident response: from alert to root cause in under 5 minutes

Rajesh Guntupalli·August 2026·5 min read

"AI helps with incidents" is true but vague enough to be useless as advice. Here's the specific, repeatable playbook I run when a database alert fires — the snapshot I capture, the exact prompt structure, and the point at which I stop trusting the model's judgment and start trusting my own.

Minute one: capture state before it changes

The most common mistake in incident response, AI-assisted or not, is investigating live instead of capturing a snapshot first. Locks clear, queries finish, and the exact state that caused the page often looks completely different two minutes later when you finally start looking. My incident script runs first, before I do anything else, and captures everything in one shot:

-- incident_snapshot.sql — run this before touching anything else
-- sqlcmd -S $server -d master -E -i incident_snapshot.sql -o incident.txt

-- === Active requests running longer than 5 seconds ===
SELECT r.session_id, s.login_name, r.status, r.command,
       DATEDIFF(SECOND, r.start_time, SYSUTCDATETIME()) AS duration_s,
       r.wait_type, r.wait_time,
       SUBSTRING(t.text, 1, 200) AS query_text
FROM sys.dm_exec_requests AS r
JOIN sys.dm_exec_sessions AS s ON s.session_id = r.session_id
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) AS t
WHERE r.session_id > 50
  AND r.start_time < DATEADD(SECOND, -5, SYSUTCDATETIME())
ORDER BY duration_s DESC;
GO

-- === Lock waits: who is waiting, and who is holding the lock ===
SELECT l.request_session_id AS waiting_session,
       wt.blocking_session_id,
       l.resource_type, l.resource_database_id,
       l.request_mode, l.request_status,
       SUBSTRING(t.text, 1, 200) AS waiting_query
FROM sys.dm_tran_locks AS l
LEFT JOIN sys.dm_os_waiting_tasks AS wt
  ON wt.session_id = l.request_session_id
OUTER APPLY (
    SELECT sql_handle FROM sys.dm_exec_requests
    WHERE session_id = l.request_session_id
) AS rh
OUTER APPLY sys.dm_exec_sql_text(rh.sql_handle) AS t
WHERE l.request_status = 'WAIT';
GO

-- === Recent errors from the SQL error log ===
EXEC xp_readerrorlog 0, 1, N'error', NULL, NULL, NULL, N'desc';

This takes under ten seconds to run and gives you a frozen record of exactly what the database was doing when the alert fired — which matters twice: once for diagnosis, and again afterward when you write the postmortem and can't remember exactly what you saw.

Minute two: structure the prompt like you'd brief a colleague

The quality of AI-assisted triage lives almost entirely in how much relevant context you give it, not in the model. A raw snapshot dump gets a generic answer. A snapshot plus what changed recently gets a specific, testable hypothesis:

Alert: p99 latency on orders_service jumped from 40ms to 4s starting 14:32 UTC.
Deploys in the last 2 hours: none.
Recent schema changes: none in the last 7 days.
Traffic: normal, matches yesterday's pattern at this time.

The "no deploys, no schema changes, normal traffic" framing does real work — it tells the model to rule out the most common explanations up front, so it doesn't waste your first response cycle suggesting "check if you just deployed something." Asking for a ranked list with a specific confirming query, rather than a paragraph of prose, is what makes the output actionable in the next sixty seconds instead of requiring another round of back-and-forth.

Minute three: confirm, don't trust

Whatever the model returns is a hypothesis, and I run the confirming query before touching anything. In the incident this playbook is built from, the model's top hypothesis was a long-running analytics query holding a row lock that was blocking the order-update path — and the lock-wait snapshot confirmed it in about fifteen seconds. Total time from alert to confirmed root cause: three minutes and change, most of it spent on the snapshot capture and the read, not on waiting for the model.

The model does not get to decide the fix. Once the cause is confirmed, that's a human decision — kill the blocking query, or let it finish if it's close to done and killing it would waste more time than it saves. This is the same principle as AI-assisted index advice: the model compresses time-to-hypothesis dramatically, and a person who understands the actual system makes the call on what to do about it.

Where this breaks down

This playbook is built for the class of incident where the database itself has clear, queryable state to reason about — locks, long queries, connection saturation. It's much weaker for incidents where the cause is outside the database entirely (a bad deploy in a service three hops away, a network partition, a downstream API degrading), because the snapshot won't contain the signal. Know which kind of incident you're in before trusting the triage speed this playbook promises — a fast wrong hypothesis costs more time than a slower correct one.
