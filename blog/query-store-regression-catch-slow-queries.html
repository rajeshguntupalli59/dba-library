Query Store in SQL Server: catching the query that quietly got slow

Rajesh Guntupalli·November 2026·6 min read

The worst performance problems are not the ones that blow up on deploy day. They are the ones that creep in on a Tuesday: a report that took 200 milliseconds last month now takes 20 seconds, nobody changed the query, nobody changed the code, and the application team is convinced the database is "just slow now." I have had this conversation more times than I can count, and every time the answer was the same — the query did not get slower, its plan changed.

SQL Server has a built-in flight recorder for exactly this situation: Query Store. It remembers every query, every plan it used, and how long each plan took. When something regresses, you do not have to guess what changed. You can open the history, point at the moment the plan flipped, and prove it. Here is how I use it, in the order I actually run it during an incident.

1. Turn Query Store on — and check it is still on

Query Store has been on by default for new databases since SQL Server 2016, but plenty of production databases predate that, or had it switched off during a migration and never switched back on. The first step is always the same: confirm it is actually capturing data, because a Query Store that is off is just an empty set of views.

-- Is Query Store on, and is it actually capturing?
SELECT
    name,
    is_query_store_on,
    query_store_capture_mode_desc
FROM sys.databases
WHERE database_id > 4;

-- GOOD: enable it with sane retention and size limits
ALTER DATABASE SalesDB
SET QUERY_STORE = ON (
    OPERATION_MODE = READ_WRITE,
    CLEANUP_POLICY = (STALE_QUERY_THRESHOLD_DAYS = 30),
    DATA_FLUSH_INTERVAL_SECONDS = 900,
    MAX_STORAGE_SIZE_MB = 1000,
    QUERY_CAPTURE_MODE = AUTO
);

Two settings matter more than the rest. QUERY_CAPTURE_MODE = AUTO skips queries that run once and never come back, so the store does not fill up with ad-hoc noise. And MAX_STORAGE_SIZE_MB is the ceiling: when Query Store hits it, it silently flips to read-only mode and stops recording — which is exactly when you need it most. Set the size generously and put an alert on the read-only state. I will come back to that in section 5.

2. Find the queries that regressed

When someone reports "the app is slow," do not start with the slowest query right now. Start with the queries whose performance changed. A query that has always taken 10 seconds is a tuning problem; a query that took 200 milliseconds yesterday and takes 20 seconds today is a regression, and regressions have a cause you can find.

This query compares each query's recent average duration against its best historical average, and surfaces the ones that got dramatically worse:

-- Queries whose recent average is far worse than their best
SELECT TOP 20
    q.query_id,
    OBJECT_NAME(q.object_id) AS object_name,
    SUBSTRING(qt.query_sql_text, 1, 120) AS query_text,
    rs_recent.avg_duration / 1000.0 AS recent_avg_ms,
    rs_best.avg_duration / 1000.0 AS best_avg_ms,
    rs_recent.avg_duration * 1.0 / NULLIF(rs_best.avg_duration, 0)
        AS regression_factor
FROM sys.query_store_query q
JOIN sys.query_store_query_text qt
    ON qt.query_text_id = q.query_text_id
CROSS APPLY (
    SELECT AVG(rs.avg_duration) AS avg_duration
    FROM sys.query_store_plan p
    JOIN sys.query_store_runtime_stats rs
        ON rs.plan_id = p.plan_id
    WHERE p.query_id = q.query_id
      AND rs.last_execution_time > DATEADD(HOUR, -24, GETUTCDATE())
) rs_recent
CROSS APPLY (
    SELECT MIN(rs.avg_duration) AS avg_duration
    FROM sys.query_store_plan p
    JOIN sys.query_store_runtime_stats rs
        ON rs.plan_id = p.plan_id
    WHERE p.query_id = q.query_id
) rs_best
WHERE rs_recent.avg_duration > rs_best.avg_duration * 5
  AND rs_recent.avg_duration > 100000  -- slower than 100ms
ORDER BY regression_factor DESC;

Read the regression_factor column first. A factor of 100 means the query is running a hundred times slower than its best recorded plan — that is not a gradual drift, that is a plan flip, and it is the first thing to investigate. Note the query_id at the top of the list: everything after this uses it.

3. Read the plan change — what actually flipped?

Once you have the query_id, look at every plan that query has used and when each one was active. This is the part the plan cache can never give you, because the plan cache only holds the current plan — the old, fast one is already gone from memory. Query Store kept it.

-- All plans for one regressed query, with their history
-- Replace @QueryId with the query_id from the previous step
SELECT
    p.plan_id,
    p.last_compile_start_time,
    rs.first_execution_time,
    rs.last_execution_time,
    rs.count_executions,
    rs.avg_duration / 1000.0 AS avg_duration_ms,
    rs.avg_logical_io_reads,
    rs.avg_rowcount
FROM sys.query_store_plan p
JOIN sys.query_store_runtime_stats rs
    ON rs.plan_id = p.plan_id
WHERE p.query_id = 42  -- <-- your query_id here
ORDER BY rs.last_execution_time;

What you are looking for is the boundary: the old plan with a low average duration, and the new plan that started at a specific time with a much higher one. That timestamp is gold — it tells you what else happened at that moment. In my experience the usual suspects are: statistics updated after a big data load, which changed the row estimates; a plan recompiled with an atypical parameter value (parameter sniffing again); or an index that was dropped, disabled, or rebuilt during maintenance. The plan change is the symptom; the timestamp tells you where to look for the cause.

4. Force the good plan back — and know when to let go

Here is the part that makes Query Store more than a diagnostic tool: you can pin the query to the plan that used to be fast, right now, without changing a line of application code. This is a stabilizer, not a cure — it buys you a calm production system while you fix the real cause. But on a bad day, a calm production system is exactly what you need.

-- GOOD: pin the query to the plan that was fast
EXEC sp_query_store_force_plan
    @query_id = 42,
    @plan_id = 7;   -- the old plan with the low avg_duration

-- Check what is currently forced
SELECT
    q.query_id,
    p.plan_id,
    p.is_forced_plan
FROM sys.query_store_query q
JOIN sys.query_store_plan p
    ON p.query_id = q.query_id
WHERE p.is_forced_plan = 1;

-- BAD: forcing a plan and forgetting about it forever
-- The data will keep changing, and a forced plan that was
-- perfect in November can be the wrong plan by March.

-- When the root cause is fixed, release the plan:
EXEC sp_query_store_unforce_plan
    @query_id = 42,
    @plan_id = 7;

Treat every forced plan like a bandage with an expiry date. I keep a short list of forced plans and review it monthly: if the statistics are fresh, the missing index is in place, or the bad parameter value is gone, unforce the plan and let the optimizer do its job. A forced plan that outlives its reason is how you end up with a query that is slow for a completely new reason six months later — and this time Query Store cannot help you, because you told it not to choose.

5. The maintenance nobody does — until Query Store goes silent

Query Store fails in the quietest way possible: it fills up, flips itself to read-only, and stops recording. Nothing errors. No alert fires. You only discover it three weeks later, when a query regresses and the history you needed was never captured. Check the state as part of your regular health checks, not after the incident.

-- Health check: state, size, and how much history you have
SELECT
    d.name AS database_name,
    q.actual_state_desc,
    q.current_storage_size_mb,
    q.max_storage_size_mb,
    q.readonly_reason
FROM sys.database_query_store_options q
JOIN sys.databases d
    ON d.database_id = q.database_id;

-- If it went read-only because it filled up, clear it and
-- raise the ceiling — then find out why it filled up:
-- (usually QUERY_CAPTURE_MODE = ALL on a busy ad-hoc workload)
ALTER DATABASE SalesDB
SET QUERY_STORE CLEAR;
ALTER DATABASE SalesDB
SET QUERY_STORE (MAX_STORAGE_SIZE_MB = 2000);

If you see readonly_reason showing size, the fix is not just clearing it — it is finding out why it filled. The usual culprit is QUERY_CAPTURE_MODE = ALL on a database full of one-off ad-hoc queries, or a retention window far longer than the workload justifies. Switch to AUTO, keep 30 days, and size the store for your busiest day, not your quietest. A flight recorder that stops recording is worse than no flight recorder at all — at least then you know you have no data.

Closing Thoughts

"The database got slow" is almost never the whole story. Most of the time one query changed plans, and everything downstream — the timeouts, the blocking, the angry tickets — is just that one regression echoing through the system. Query Store turns that from a guessing game into a five-minute investigation: find the regressed query, find the moment the plan flipped, force the good plan back, then fix the cause. The next time a report quietly goes from 200 milliseconds to 20 seconds, you will not be asking what changed. You will already know.
