SQL Server backup failures: 6 ways they break and how to catch each one

Rajesh Guntupalli·October 2026·6 min read

A backup that fails is almost worse than no backup at all — it gives you confidence you don't deserve. I've seen teams discover their backups were broken only when they needed to restore. That's the worst possible time to learn.

Here are the six failure patterns I keep seeing, and the T-SQL to catch each one before disaster does.

---

1. The backup share is unreachable

The classic: your job writes to \\nas\backups\, someone renames the share or the service account password expires, and every job fails with operating system error 53 or 1326. The SQL Server service account — not you — needs write access to that path.

Check what's actually failing before you blame the network:

-- Which databases never got a successful backup, and why the last one failed
SELECT
    d.name AS database_name,
    MAX(b.backup_finish_date) AS last_successful_backup,
    DATEDIFF(DAY, MAX(b.backup_finish_date), GETDATE()) AS days_since_backup
FROM sys.databases d
LEFT JOIN msdb.dbo.backupset b
    ON b.database_name = d.name
    AND b.type = 'D'
    AND b.is_copy_only = 0
WHERE d.database_id > 4
  AND d.state_desc = 'ONLINE'
GROUP BY d.name
HAVING MAX(b.backup_finish_date) IS NULL
    OR MAX(b.backup_finish_date) < DATEADD(DAY, -2, GETDATE());

Then read the real error in the SQL Server error log — the job history message alone is usually truncated. If you see error 3201 ("Cannot open backup device"), fix the share and the service account permissions first, and back the share path itself: test it with a COPY_ONLY backup to the NUL device so the real job never discovers the problem for you.

---

2. The drive fills up mid-backup

A full backup of a 400 GB database with no compression and no retention cleanup will happily fill a 1 TB drive — and then fail with error 3257 ("There is insufficient free space on disk"). The backup dies, the old files stay, and the next night's job fails faster.

Two fixes. Turn on compression — it usually cuts backup size by 60–80% with barely any CPU cost on modern servers — and check free space before the job runs:

-- GOOD: compressed backup with checksum verification
BACKUP DATABASE MyDb
TO DISK = '\\nas\backups\MyDb_full.bak'
WITH COMPRESSION, CHECKSUM, STATS = 10;

-- Free space on every drive SQL Server can see
SELECT DISTINCT
    volume_mount_point,
    CAST(total_bytes / 1024.0 / 1024 / 1024 AS DECIMAL(10,2)) AS total_gb,
    CAST(available_bytes / 1024.0 / 1024 / 1024 AS DECIMAL(10,2)) AS free_gb
FROM sys.master_files
CROSS APPLY sys.dm_os_volume_stats(database_id, file_id);

Add the free-space check to your backup job's first step. If a drive is under, say, 20% free, fail the step with a clear message instead of letting the backup die halfway through at 3 AM.

---

3. BACKUP LOG in SIMPLE recovery model

Error 4208: "The statement BACKUP LOG is not allowed while the recovery model is SIMPLE." Someone changed the recovery model to SIMPLE during a migration, the log backup job kept running, and now you have a nightly error that's been ignored for six months.

If the database is supposed to be in FULL recovery, switch it back and take a full backup immediately — the log chain is broken, and until you take a full backup, point-in-time recovery is not possible:

-- GOOD: repair the log chain after a recovery-model mix-up
ALTER DATABASE MyDb SET RECOVERY FULL;

BACKUP DATABASE MyDb
TO DISK = '\\nas\backups\MyDb_full.bak'
WITH COMPRESSION, CHECKSUM;

BACKUP LOG MyDb
TO DISK = '\\nas\backups\MyDb_log.trn'
WITH COMPRESSION, CHECKSUM;

And add a guard to your log-backup job so it skips SIMPLE-recovery databases instead of failing noisily — alert fatigue is how real failures get ignored.

---

4. Overlapping backup jobs stepping on each other

Error 3023: "Backup, file manipulation operations... are not allowed on a database that is in use when any... operation is in progress." Your full backup starts at 1 AM, the differential starts at 1:05 AM on the same database, and one of them dies every night.

SQL Server can't run two backup operations on the same database at the same time. Look for overlaps in your Agent job schedules — this often happens after someone adds a new job or a maintenance plan runs longer than expected and cascades into the next window.

The fix is schedule hygiene, not retry logic: stagger jobs, keep a single backup window per instance, and make long-running jobs fail loudly instead of quietly spilling into the next slot.

---

5. Checksum errors — the backup that was already corrupt

This is the scary one. Error 3041: the backup hit a page with a checksum mismatch. The data was already corrupt on disk — the backup just told you about it. If your backups don't use WITH CHECKSUM, and the database doesn't have PAGE_VERIFY CHECKSUM enabled, corruption can sit there silently for years.

-- GOOD: enable page checksums so corruption is caught on write, not at restore
ALTER DATABASE MyDb SET PAGE_VERIFY CHECKSUM;

-- Find databases that are still on the old detection method
SELECT name, page_verify_option_desc
FROM sys.databases
WHERE page_verify_option_desc <> 'CHECKSUM'
  AND database_id > 4;

Run a weekly DBCC CHECKDB on every production database and treat checksum errors as a severity-1 incident. A backup of a corrupt database is just a corrupt database with extra steps.

---

6. Nobody ever verified the backup

The most common failure of all: the backup job succeeds every night, nobody checks whether the file is actually restorable, and during an outage you discover the media set is incomplete or the header is unreadable. A green job history is not a restore plan.

At minimum, verify the media header after every backup. Better: automate a monthly restore test to a scratch server and confirm the database comes online.

-- GOOD: quick media verification — catches incomplete or damaged backup files
RESTORE VERIFYONLY
FROM DISK = '\\nas\backups\MyDb_full.bak'
WITH CHECKSUM;

---

Closing takeaway

Backups fail in boring, repeatable ways — and that's good news, because boring problems can be monitored. Build yourself a daily check: every database with a recent successful full, free space on every target drive, no SIMPLE-recovery databases running log jobs, PAGE_VERIFY set to CHECKSUM everywhere, and a restore test you actually run. The five minutes you spend each morning beats the five hours you'll spend explaining a gap in the backup chain.
