Chapter 4: Subqueries, CTEs & Ranking

Subqueries and common table expressions let you build a query in steps instead of writing one long statement. Ranking and window functions extend that idea by comparing rows within a group without collapsing the group into one row. Together they cover most reporting patterns, from top rows per group to running totals and hierarchies.

In this chapter:

  • →What a subquery is and how scalar and correlated subqueries work
  • →How EXISTS and IN differ, including NULL handling and performance
  • →Where subqueries can appear in SELECT, FROM, WHERE, and HAVING
  • →CTE syntax, benefits, and recursive CTEs for hierarchies
  • →ROW_NUMBER, RANK, and DENSE_RANK, and window functions with OVER and PARTITION BY

    • Key learning: Subqueries and CTEs express logic in readable steps, and the optimizer often treats the two forms alike, so choose the clearer form and test performance on real data. Ranking and window functions solve per-group and running-total problems in a single pass without collapsing rows, which makes them essential for reporting queries.

    Q35. What is a subquery, and how does a scalar subquery work?

    Answer: A subquery is a query nested inside another query, enclosed in parentheses. The outer query is the main statement, and the inner query supplies values or rows for it to use. Subqueries can return a single value, a single column of values, or a full set of rows.

    A scalar subquery returns exactly one value: one row and one column. It can be used anywhere a single value is expected, such as in a SELECT list or in a comparison in a WHERE clause. If it returns more than one row, SQL Server raises an error, and if it returns no rows, the result is NULL.

    SELECT ProductName, UnitPrice
FROM Products
WHERE UnitPrice > (SELECT AVG(UnitPrice) FROM Products);

    Key learning: A scalar subquery returns exactly one value and can be used anywhere a single value is expected.

    Q36. What is a correlated subquery, and how does it differ from a regular subquery?

    Answer: A correlated subquery references columns from the outer query, so it cannot be evaluated on its own. SQL Server evaluates it once for each row of the outer query, using that row's values in the inner filter. The correlation is normally written with table aliases, so the inner query can refer to the outer table.

    A regular, or independent, subquery does not reference the outer query and runs once, with its result reused by the outer statement. Correlated subqueries are a natural fit for row-by-row comparisons, such as finding employees paid above their own department average, but they can be slower on large tables. Many correlated subqueries can be rewritten as a JOIN or a window function for better performance.

    SELECT e.EmployeeName, e.DepartmentID, e.Salary
FROM Employees AS e
WHERE e.Salary > (
    SELECT AVG(e2.Salary)
    FROM Employees AS e2
    WHERE e2.DepartmentID = e.DepartmentID
);

    Key learning: A correlated subquery references the outer query and is evaluated once per outer row, unlike an independent subquery that runs once.

    Q37. What is the difference between EXISTS and IN, and when is each faster?

    Answer: IN tests whether a value appears in a list or in the result of a subquery. EXISTS tests whether the subquery returns any rows at all, and it is almost always written as a correlated subquery. EXISTS returns true as soon as the first matching row is found, so it can stop scanning early.

    The important difference is NULL handling. If the IN list contains a NULL, IN can return UNKNOWN instead of true or false, and NOT IN with a NULL in the subquery returns no rows at all. EXISTS is not affected by NULLs in the same way, which makes NOT EXISTS the safer choice for "rows with no match" queries. For performance, EXISTS often wins when the subquery is large, but the optimizer frequently rewrites IN to a similar semi-join plan, so test both forms on real data and check the execution plan.

    SELECT CustomerName
FROM Customers
WHERE CustomerID IN (SELECT CustomerID FROM Orders);

SELECT CustomerName
FROM Customers AS c
WHERE EXISTS (
    SELECT 1
    FROM Orders AS o
    WHERE o.CustomerID = c.CustomerID
);

    Key learning: EXISTS tests for the presence of any matching row and is safe with NULLs, while IN tests membership and can return UNKNOWN when the list contains NULL.

    Q38. Where can subqueries appear in a query: SELECT, FROM, WHERE, and HAVING?

    Answer: A subquery in the SELECT list must be scalar, returning one value per row, and it is often correlated to the outer row. A subquery in the FROM clause is a derived table: it returns a row set that the outer query treats like a table, and it must have an alias in SQL Server.

    In the WHERE clause, subqueries filter rows with IN, EXISTS, or a comparison such as greater than an average. In the HAVING clause, a subquery can supply a value to compare against a group aggregate, for example comparing each department average salary with the overall average. The placement decides what the subquery must return: a single value in SELECT and HAVING comparisons, a row set in FROM, and a value list or existence test in WHERE.

    SELECT OrderID,
       (SELECT c.CustomerName FROM Customers AS c WHERE c.CustomerID = Orders.CustomerID) AS CustomerName
FROM Orders;

SELECT DeptID, AvgSalary
FROM (
    SELECT DepartmentID AS DeptID, AVG(Salary) AS AvgSalary
    FROM Employees
    GROUP BY DepartmentID
) AS DeptAvg
WHERE AvgSalary > 50000;

SELECT ProductName
FROM Products
WHERE CategoryID IN (
    SELECT CategoryID FROM Categories WHERE CategoryName = 'Beverages'
);

SELECT DepartmentID
FROM Employees
GROUP BY DepartmentID
HAVING AVG(Salary) > (SELECT AVG(Salary) FROM Employees);

    Key learning: Subqueries can supply a single value in SELECT or HAVING, a row set in FROM, or a filter in WHERE, with each placement having its own rules.

    Q39. What is a common table expression (CTE), and what are its benefits?

    Answer: A common table expression, or CTE, is a named temporary result set defined with WITH and used by the single statement that follows it. It exists only for that statement: it is not stored, and it cannot be referenced by a later statement. If a CTE follows another statement in the same batch, the previous statement must end with a semicolon, which is why CTE examples often start with a leading semicolon.

    CTEs improve readability by naming each step of a complex query, and the same CTE can be referenced more than once in the following statement. They can replace nested derived tables, support recursion for hierarchies, and be used with SELECT, INSERT, UPDATE, and DELETE. A CTE is not automatically materialized or indexed, so referencing it several times can cause the underlying query to run several times.

    ;WITH HighEarners AS (
    SELECT EmployeeID, EmployeeName, Salary
    FROM Employees
    WHERE Salary > 80000
)
SELECT EmployeeID, EmployeeName, Salary
FROM HighEarners
ORDER BY Salary DESC;

    Key learning: A CTE is a named, single-statement result set that makes complex queries more readable and can be referenced more than once in the statement that follows it.

    Q40. What is a recursive CTE? Show an example using an employee hierarchy.

    Answer: A recursive CTE references itself to walk hierarchical or tree-structured data, such as an organization chart, a bill of materials, or a folder tree. It has two parts joined by UNION ALL: an anchor query that returns the starting rows, and a recursive query that joins back to the CTE to find the next level. SQL Server runs the anchor once, then repeats the recursive part until it returns no more rows.

    Both parts must return the same number of columns with compatible types. The default recursion limit is 100 levels, controlled by the MAXRECURSION query hint, and a cycle in the data can cause the recursion to run until that limit is hit. Recursive CTEs are the standard way to answer "all reports under this manager" or "the full chain above this employee" in a single query.

    ;WITH OrgHierarchy AS (
    SELECT EmployeeID, EmployeeName, ManagerID, 0 AS OrgLevel
    FROM Employees
    WHERE ManagerID IS NULL
    UNION ALL
    SELECT e.EmployeeID, e.EmployeeName, e.ManagerID, h.OrgLevel + 1
    FROM Employees AS e
    INNER JOIN OrgHierarchy AS h ON e.ManagerID = h.EmployeeID
)
SELECT EmployeeID, EmployeeName, ManagerID, OrgLevel
FROM OrgHierarchy
ORDER BY OrgLevel, EmployeeName;

    Key learning: A recursive CTE combines an anchor query with a recursive query joined back to itself to walk a hierarchy level by level until no more rows are returned.

    Q41. What is the difference between ROW_NUMBER(), RANK(), and DENSE_RANK()?

    Answer: All three assign a number to each row within a partition, ordered by the ORDER BY inside the OVER clause. ROW_NUMBER gives every row a unique sequential number, even when the ordering values tie, and the order among tied rows is arbitrary unless the ORDER BY is deterministic. RANK gives tied rows the same number and then skips the next numbers, so ranks can be 1, 2, 2, 4. DENSE_RANK also gives tied rows the same number, but it does not skip, so ranks are 1, 2, 2, 3.

    Use ROW_NUMBER for paging, deduplication, and "one row per group" logic where exactly one winner is needed. Use RANK or DENSE_RANK when ties must share a position, such as a leaderboard, and choose DENSE_RANK when the next position must follow immediately after a tie.

    SELECT EmployeeName, DepartmentID, Salary,
       ROW_NUMBER() OVER (PARTITION BY DepartmentID ORDER BY Salary DESC) AS RowNum,
       RANK() OVER (PARTITION BY DepartmentID ORDER BY Salary DESC) AS RankVal,
       DENSE_RANK() OVER (PARTITION BY DepartmentID ORDER BY Salary DESC) AS DenseRankVal
FROM Employees;

    Key learning: ROW_NUMBER gives every row a unique number, RANK shares numbers for ties and then skips, and DENSE_RANK shares numbers for ties without skipping.

    Q42. What are window functions? Explain the OVER clause, PARTITION BY, and running totals.

    Answer: A window function performs a calculation across a set of rows related to the current row, called a window, without collapsing the rows into groups. Unlike GROUP BY, which returns one row per group, a window function returns one result per input row alongside the original row data. Ranking functions, aggregates such as SUM and AVG, and offset functions such as LAG and LEAD can all be used as window functions.

    The OVER clause defines the window. PARTITION BY divides rows into groups, and the function restarts for each group, similar to GROUP BY but without collapsing rows. ORDER BY inside OVER defines the order within the window, which ranking functions need and which running totals need to know which rows come before the current row. A running total uses an aggregate with ORDER BY and a frame such as ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, so each row sums all rows from the start of its partition up to itself. Window functions cannot be used directly in a WHERE clause, so filter on their results with a subquery or a CTE.

    SELECT OrderID, CustomerID, OrderDate, TotalAmount,
       SUM(TotalAmount) OVER (
           PARTITION BY CustomerID
           ORDER BY OrderDate
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS RunningTotal,
       AVG(TotalAmount) OVER (PARTITION BY CustomerID) AS AvgPerCustomer
FROM Orders
ORDER BY CustomerID, OrderDate;

    Key learning: Window functions use OVER to define a group of related rows so aggregates and rankings can be calculated without collapsing the rows like GROUP BY does.
