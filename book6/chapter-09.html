Semantic Memory: Facts the AI Remembers

Chapter 8 built the long-term memory store from distilled summaries and facts. But distillation loses detail, and sometimes the user asks about something specific that happened three months ago — "what did we decide about the refund policy back in June?" Semantic memory answers by searching the raw conversation history itself: every past conversation gets an embedding, and a new question retrieves the most semantically relevant past conversations. This chapter builds that capability — conversation-level embeddings, the retrieval procedure, and the UX patterns that make past conversations genuinely useful instead of a gimmick.

---

9.1 What Gets Embedded: Conversation-Level Representations

A conversation is hundreds of turns; an embedding model takes a few thousand tokens. The representation must compress without losing the "aboutness" of the conversation. Three strategies, in increasing quality:

  • → Title + first user message. Cheap, often sufficient for "find the conversation about X." Fails when the topic drifts mid-conversation.
  • → LLM-generated summary. The Chapter 8 promotion summary, embedded. Captures the full arc of the conversation in the model's own words. The recommended default.
  • → Multi-vector: summary + key turns. Embed the summary plus the 3–5 highest-signal turns (questions asked, decisions made), store all vectors, and take the max similarity at query time. Best recall, 4–6x the storage.
    • -- Conversation-level embeddings for semantic recall
CREATE TABLE dbo.conversation_embeddings (
    conversation_id UNIQUEIDENTIFIER PRIMARY KEY
                    CONSTRAINT FK_ce_conversation
                    REFERENCES dbo.conversations(conversation_id) ON DELETE CASCADE,
    tenant_id       UNIQUEIDENTIFIER NOT NULL,
    user_id         UNIQUEIDENTIFIER NOT NULL,
    -- representation: 'summary' | 'title_first' | 'multivector'
    representation  NVARCHAR(20) NOT NULL DEFAULT N'summary',
    summary_text    NVARCHAR(MAX) NULL,     -- the embedded text, for display
    embedding       VECTOR(1536) NOT NULL,
    embedded_at     DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);
CREATE VECTOR INDEX IX_ce_embedding
    ON dbo.conversation_embeddings (embedding)
    WITH (METRIC = 'cosine', TYPE = 'diskann');
CREATE INDEX IX_ce_user ON dbo.conversation_embeddings(user_id, embedded_at DESC);

    Populate this table in the Chapter 8 promotion pipeline — the summary already exists there, so embedding it is one extra API call per closed conversation.

    9.2 Retrieval: "Have We Talked About This Before?"

    The retrieval procedure finds past conversations relevant to the current message, excluding the active conversation:

    CREATE OR ALTER PROCEDURE dbo.usp_find_related_conversations
    @user_id         UNIQUEIDENTIFIER,
    @current_conversation_id UNIQUEIDENTIFIER,
    @query_vector    VECTOR(1536),
    @top_n           INT = 3,
    @min_similarity  FLOAT = 0.75   -- cosine similarity floor
AS
BEGIN
    SET NOCOUNT ON;
    SELECT TOP (@top_n)
        ce.conversation_id,
        c.title,
        ce.summary_text,
        (1 - VECTOR_DISTANCE('cosine', ce.embedding, @query_vector) / 2.0) AS similarity,
        c.created_at,
        (SELECT COUNT(*) FROM dbo.messages m
          WHERE m.conversation_id = ce.conversation_id) AS turn_count
    FROM dbo.conversation_embeddings AS ce
    JOIN dbo.conversations AS c ON c.conversation_id = ce.conversation_id
    WHERE ce.user_id = @user_id
      AND ce.conversation_id <> @current_conversation_id
      AND (1 - VECTOR_DISTANCE('cosine', ce.embedding, @query_vector) / 2.0) >= @min_similarity
    ORDER BY VECTOR_DISTANCE('cosine', ce.embedding, @query_vector);
END;
GO

    The @min_similarity floor is critical: without it, the procedure always returns something, and "something" is often irrelevant. Tune the floor on real data — start at 0.75 and adjust until fewer than 5% of surfaced conversations get dismissed by users.

    9.3 Three UX Patterns for Surfacing the Past

    Retrieval is only half the problem; presentation determines whether users trust it:

  • → Silent context injection. The related conversation's summary is added to the prompt's long-term section without telling the user. Best for continuity ("as we discussed last month…"), but risks confusion if the recall is wrong — keep the similarity floor high.
  • → Suggested reference. The UI shows "Related: Refund policy discussion (Jun 12)" as a clickable chip; the user decides whether to include it. Lower risk, slightly more friction. The recommended default for most products.
  • → Explicit search. A "search past conversations" box powered by usp_find_related_conversations with a lower similarity floor and more results. Power-user feature; also the easiest to evaluate (Chapter 19).

    • Log which pattern surfaces which conversation and whether the user engages — that feedback tunes both the similarity floor and the promotion quality over time.

    9.4 Privacy Boundaries in Semantic Recall

    Semantic memory crosses a privacy line that short-term history does not: it resurfaces things the user may have forgotten they said. Three guardrails:

  • → Strict user scoping. The procedure filters user_id = @user_id — never recall across users, even within a tenant. Add the RLS policy from Chapter 1 on top for defense in depth.
  • → Sensitive-topic exclusion. Let users mark conversations private; private conversations get no embedding row at all. Deletion must cascade to the embedding (the foreign key with ON DELETE CASCADE handles this).
  • → Transparency. When the assistant uses a past conversation, say so: "Based on our June discussion…". Silent use of forgotten statements erodes trust fast.

    • Chapter 38 extends these guardrails into full GDPR compliance — the right to be forgotten must reach embeddings, summaries, and memories, not just raw messages.

    9.5 Fact Lifecycle in Practice: A Worked Example

    Watch a single fact travel the full lifecycle. A user says "we migrated to Azure SQL last quarter" in March:

  • → Extraction (§9.2): the consolidation worker emits ("user's database platform", "Azure SQL", confidence 0.85, durable), sourced to the conversation.
  • → Resolution (§9.3): the old fact ("user's database platform", "on-prem SQL Server 2019", confidence 0.9) conflicts on the same attribute. The new statement is explicit and recent, so it wins; the old fact is superseded, not deleted.
  • → Recall (§9.4): in June the user asks "how do I tune my database?" — retrieval surfaces the Azure SQL fact, and the assistant's advice targets Azure SQL specifics (elastic pools, Hyperscale) instead of on-prem trace flags. The superseded 2019 fact stays buried.
  • → Decay: by December the fact's confidence has decayed to 0.45 with no reinforcement. It still retrieves, but ranked below fresher facts — appropriately tentative.
  • → Resurrection: the user mentions "our Azure SQL costs" — an implicit confirmation. Confidence jumps back to 0.8, last_confirmed_at updates, and the fact is durable again.
    • -- The full lifecycle as queries the consolidation worker runs nightly
-- 1) Decay stale durable facts
UPDATE dbo.user_facts
SET confidence = confidence * 0.97
WHERE fact_type = N'durable'
  AND last_confirmed_at < DATEADD(day, -30, SYSUTCDATETIME())
  AND confidence > 0.3;
-- 2) Resurrect implicitly confirmed facts (reinforcement signal from §9.2)
UPDATE f SET confidence = LEAST(0.95, f.confidence + 0.25),
             last_confirmed_at = SYSUTCDATETIME()
FROM dbo.user_facts AS f
JOIN dbo.fact_confirmations AS c
  ON c.fact_id = f.fact_id AND c.confirmed_at > f.last_confirmed_at;
-- 3) Compact: merge near-duplicate facts the extractor created separately
--    (same user, same attribute, cosine-similar values → keep highest confidence)

    The lifecycle is what separates a fact table from a junk drawer: every fact has a confidence trajectory, a provenance chain, and a defined end (superseded, decayed below threshold, or explicitly retracted). Build the worker that runs these three statements nightly before you have ten thousand facts — retrofitting lifecycle management onto an unmanaged fact table means deciding the fate of each row by hand.

    Key Takeaways

  • → Embed conversation summaries (from the promotion pipeline) for semantic recall of past conversations. Summary-level embeddings capture aboutness; multi-vector representations buy extra recall at 4–6x storage.
  • → Enforce a similarity floor so retrieval returns nothing rather than something irrelevant. Tune it on real dismissal data, not intuition.
  • → Default to suggested references over silent injection until your recall precision earns the user's trust.
  • → Scope recall strictly to the user, support private conversations with no embeddings, and always disclose when past conversations inform an answer. Semantic memory is powerful precisely because it remembers what users forgot — handle that power explicitly.
