Streaming Chat Responses with SqlDataReader

Users perceive latency, not throughput: a chat response that streams its first token in 300ms feels instant even if the full answer takes 10 seconds; a response that arrives complete after 10 seconds feels broken. Streaming is therefore a UX requirement, and the database side has its own streaming story: reading large result sets without buffering them in memory, writing streaming tokens without one INSERT per token, and keeping the connection healthy across a long-lived stream. This chapter covers streaming on both sides of the wire.

---

29.1 Streaming Reads: SequentialAccess and Yield

Retrieval for a streaming chat (Chapter 13) can return hundreds of chunks; buffering them all in a DataTable before generation starts adds latency and memory pressure. Stream them instead:

// C# — stream retrieval rows straight into the prompt builder
async IAsyncEnumerable<Chunk> StreamChunksAsync(
    Guid tenantId, float[] queryVector, int topK)
{
    using var conn = new SqlConnection(_connStr);
    await conn.OpenAsync();
    using var cmd = new SqlCommand("dbo.usp_vector_search", conn);
    cmd.CommandType = CommandType.StoredProcedure;
    cmd.Parameters.AddWithValue("@tenant_id", tenantId);
    cmd.Parameters.AddWithValue("@qv", queryVector);  // SqlClient 2025: float[] → VECTOR
    cmd.Parameters.AddWithValue("@top_k", topK);

    // SequentialAccess: streams large NVARCHAR/VECTOR columns without
    // buffering the whole row; CommandBehavior.SequentialAccess + yield
    // keeps memory flat regardless of result size.
    using var reader = await cmd.ExecuteReaderAsync(CommandBehavior.SequentialAccess);
    while (await reader.ReadAsync())
    {
        yield return new Chunk {
            ChunkId = reader.GetGuid(0),
            Text    = reader.GetString(1),   // streamed, not buffered
            Score   = reader.GetDouble(2)
        };
    }
}
// The caller appends chunks to the prompt as they arrive and can even
// start generation once enough context is assembled (early cutoff).

The pattern generalizes: any large read on the chat path — conversation history replay (§6.2), blackboard snapshots (§26.1) — should stream rather than buffer. CommandBehavior.SequentialAccess is the one-line change that converts a memory spike into a flat line.

29.2 Streaming Writes: Buffering Token Batches

As the LLM streams tokens, the application must persist the growing message — for crash recovery (§6.3's atomic assistant insert) and so the user sees progress. One INSERT per token is absurd; one INSERT at the end loses everything on crash. The middle path: buffer tokens and flush periodically:

// Token persistence: buffer 50 tokens or 2 seconds, whichever comes first,
// then UPDATE the in-progress message row (created at stream start).
async Task StreamAndPersistAsync(Guid messageId, IAsyncEnumerable<string> tokens,
                                SqlConnection conn /* held open for the stream */)
{
    var buffer = new StringBuilder();
    var lastFlush = DateTime.UtcNow;
    int count = 0;

    await foreach (var token in tokens)
    {
        ForwardToClient(token);              // SSE / websocket → user sees it now
        buffer.Append(token);
        if (++count % 50 == 0 || DateTime.UtcNow - lastFlush > TimeSpan.FromSeconds(2))
        {
            // Single UPDATE per flush — cheap, and crash recovery replays
            // from the last flush point, not from zero.
            using var cmd = new SqlCommand(
                "UPDATE dbo.messages SET content = @c, updated_at = SYSUTCDATETIME() " +
                "WHERE message_id = @m", conn);
            cmd.Parameters.AddWithValue("@c", buffer.ToString());
            cmd.Parameters.AddWithValue("@m", messageId);
            await cmd.ExecuteNonQueryAsync();
            lastFlush = DateTime.UtcNow;
        }
    }
    // Finalize: mark complete, record token counts for audit (§24.1)
    using var done = new SqlCommand(
        "UPDATE dbo.messages SET content = @c, status = N'complete', " +
        "prompt_tokens = @pt, completion_tokens = @ct, " +
        "updated_at = SYSUTCDATETIME() WHERE message_id = @m", conn);
    ...
}

Holding one pooled connection open for the stream's duration is fine — but size the pool (§5.1) for concurrent streams, not just concurrent requests. A thousand users each streaming on a held connection needs a thousand pool slots (or multiplexed streaming with fewer, longer-held connections — measure your actual concurrency).

29.3 Heartbeats, Timeouts, and Broken Streams

Streams break: networks drop, clients navigate away, providers stall. Three defenses:

  • → Server-sent heartbeats. Send a comment/keep-alive frame every 15 seconds during generation gaps so proxies and load balancers don't kill idle connections. The client's EventSource ignores them; the infrastructure stays happy.
  • → Command timeouts with resume. Set the generation's database operations to sane timeouts; on timeout, the message row's status = 'streaming' plus last flush position lets a retry resume from the last flush instead of restarting (§11.2's checkpoint pattern applied to streams).
  • → Orphan-stream reaper. A scheduled job marks streaming messages older than N minutes (no flush, no finalize) as abandoned — they render as partial responses with a "regenerate" affordance instead of hanging forever.
    • -- Orphan-stream reaper: runs every 5 minutes
UPDATE dbo.messages
SET status = N'abandoned', updated_at = SYSUTCDATETIME()
OUTPUT INSERTED.message_id, INSERTED.conversation_id
INTO @reaped  -- notify the client to offer "regenerate"
WHERE status = N'streaming'
  AND updated_at < DATEADD(minute, -10, SYSUTCDATETIME());
-- 10 minutes without a flush: the stream is dead. The partial content stays
-- (better than nothing), flagged so the UI can offer regeneration.

    29.4 Backpressure: When Generation Outruns Consumption

    Fast providers can emit tokens faster than slow clients consume them. Unbounded server-side buffering of a fast stream for a slow client is a memory leak with extra steps. Apply backpressure:

  • → Bounded channels between the provider stream and the response writer (e.g., Channel<string> with capacity 200). When full, the reader pauses — the provider's HTTP stream buffers in the OS, which is its job.
  • → Client disconnect detection: stop generation when the client goes away (HttpContext.RequestAborted). Continuing to burn tokens for nobody is the streaming equivalent of the runaway agent.
  • → Flush the token buffer on disconnect before abandoning — the partial message is still valuable context for the next turn.

    29.5 Mobile and Low-Bandwidth Clients

    Streaming assumes a stable connection — mobile clients violate that assumption constantly: tunnels, elevators, network handoffs. Design the stream protocol for hostile networks. Resumable streams: every flushed token batch (§29.2) carries a sequence number, and the client tracks the last sequence it rendered — on reconnect, it requests "resume from sequence N" and the server replays from the persisted buffer instead of restarting generation. Adaptive verbosity: when the client's measured bandwidth drops, the server can truncate the in-progress response gracefully (finish the current sentence, mark the message truncated_low_bandwidth) rather than letting the stream stall until the user gives up — a complete short answer beats an abandoned long one. Offline queuing: the mobile client queues the user's message locally and syncs when connectivity returns; the server-side idempotency key (conversation_id + client_message_id) makes the retry safe. Test the mobile path with a network conditioner that injects 30% packet loss and 2-second latency spikes — if the chat still feels usable, the streaming layer is production-ready. If it falls over, no amount of server-side optimization will save it.

    ---

    One final streaming consideration: log stream lifecycle events (started, first-token latency, flush count, completion or abandonment reason) into the audit tables. Stream telemetry is the only way to distinguish "the model is slow" from "the network is slow" from "the client went away" — three problems with three different owners and three different fixes. Without per-stream telemetry, every streaming complaint becomes a guessing game.

    ---

    Key Takeaways

  • → Stream reads with SequentialAccess and IAsyncEnumerable — never buffer large result sets on the chat path; memory stays flat and generation can start early.
  • → Stream writes with periodic buffered flushes (50 tokens or 2 seconds) — crash recovery replays from the last flush, and pool sizing must account for held streaming connections.
  • → Defend the stream: heartbeats for idle connections, timeouts with resume-from-flush, and an orphan-stream reaper that converts dead streams into partial responses with regenerate affordances.
  • → Apply backpressure with bounded channels and stop generating when the client disconnects — tokens burned for nobody are pure waste.
