Rate Limiting and Quota Tracking for AI Features

Every AI feature has a marginal cost — tokens are money, and money needs limits. Rate limiting protects the system (no single user can drown the API), quota tracking protects the business (usage maps to plan tiers and invoices), and both protect users from runaway agents burning budget in a loop. This chapter builds the complete limiting layer in SQL Server: token-bucket rate limiting with atomic consumption, multi-window quotas (per-minute, per-day, per-month), per-feature cost weighting, and the UX of communicating limits to users and agents.

---

25.1 Token Buckets in SQL Server

The token bucket is the right algorithm for AI rate limiting: it allows bursts (a user pasting five questions at once) while enforcing a sustained rate. The bucket state lives in a table; consumption is a single atomic statement:

CREATE TABLE dbo.rate_buckets (
    bucket_id     UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    tenant_id     UNIQUEIDENTIFIER NOT NULL,
    user_id       UNIQUEIDENTIFIER NULL,      -- NULL = tenant-level bucket
    feature       NVARCHAR(100) NOT NULL,     -- 'chat', 'embed', 'agent_run'
    tokens        DECIMAL(12,2) NOT NULL,     -- current balance
    capacity      DECIMAL(12,2) NOT NULL,     -- max burst
    refill_rate   DECIMAL(12,4) NOT NULL,     -- tokens per second
    last_refill_at DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    CONSTRAINT UQ_bucket UNIQUE (tenant_id, user_id, feature)
);

-- Atomic consume: refill lazily, deduct, succeed/fail in ONE statement.
-- Returns 1 row on success (with remaining balance), 0 rows when limited.
CREATE OR ALTER PROCEDURE dbo.usp_consume_rate_tokens
    @tenant_id UNIQUEIDENTIFIER,
    @user_id   UNIQUEIDENTIFIER,
    @feature   NVARCHAR(100),
    @cost      DECIMAL(12,2) = 1
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @now DATETIME2 = SYSUTCDATETIME();
    UPDATE dbo.rate_buckets
    SET tokens = CASE
                     WHEN tokens + DATEDIFF(millisecond, last_refill_at, @now)
                                       / 1000.0 * refill_rate > capacity
                     THEN capacity ELSE tokens + DATEDIFF(millisecond, last_refill_at, @now)
                                       / 1000.0 * refill_rate
                 END - @cost,
        last_refill_at = @now
    OUTPUT INSERTED.tokens AS remaining
    WHERE tenant_id = @tenant_id
      AND ((@user_id IS NULL AND user_id IS NULL) OR user_id = @user_id)
      AND feature = @feature
      AND tokens + DATEDIFF(millisecond, last_refill_at, @now)
                 / 1000.0 * refill_rate >= @cost;
    -- @@ROWCOUNT = 0 → rate limited. Caller reads remaining for the
    -- Retry-After header: (cost - remaining) / refill_rate seconds.
END;
GO

Lazy refill (computing accrued tokens at consume time rather than on a timer) means no background job and no write amplification — the bucket only writes when consumed. The single-statement UPDATE…WHERE…OUTPUT is atomic: concurrent requests cannot overspend the bucket.

25.2 Multi-Window Quotas

Rate limits handle bursts; quotas handle budgets. Track three windows simultaneously — per-minute (abuse), per-day (fair use), per-month (billing):

CREATE TABLE dbo.usage_windows (
    tenant_id     UNIQUEIDENTIFIER NOT NULL,
    user_id       UNIQUEIDENTIFIER NULL,
    window_start  DATETIME2 NOT NULL,        -- truncated to window grain
    window_grain  NVARCHAR(10) NOT NULL      -- 'minute', 'day', 'month'
                  CONSTRAINT CK_uw_grain CHECK (window_grain IN
                      (N'minute', N'day', N'month')),
    tokens_used   BIGINT NOT NULL DEFAULT 0,
    requests      INT NOT NULL DEFAULT 0,
    CONSTRAINT PK_usage_windows PRIMARY KEY (tenant_id, user_id, window_grain, window_start)
);

-- Increment all three windows atomically (MERGE per grain, one transaction)
CREATE OR ALTER PROCEDURE dbo.usp_record_usage
    @tenant_id UNIQUEIDENTIFIER, @user_id UNIQUEIDENTIFIER, @tokens BIGINT
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @now DATETIME2 = SYSUTCDATETIME();
    BEGIN TRAN;
    MERGE dbo.usage_windows AS t
    USING (VALUES
        (N'minute', DATEADD(minute, DATEDIFF(minute, 0, @now), 0)),
        (N'day',    CAST(@now AS DATE)),
        (N'month',  DATEFROMPARTS(YEAR(@now), MONTH(@now), 1))
    ) AS s (grain, wstart)
      ON t.tenant_id = @tenant_id AND t.user_id = @user_id
     AND t.window_grain = s.grain AND t.window_start = s.wstart
    WHEN MATCHED THEN UPDATE SET tokens_used = t.tokens_used + @tokens,
                                 requests = t.requests + 1
    WHEN NOT MATCHED THEN INSERT (tenant_id, user_id, window_start, window_grain,
                                   tokens_used, requests)
                           VALUES (@tenant_id, @user_id, s.wstart, s.grain,
                                   @tokens, 1);
    COMMIT;
END;
GO
-- Cleanup job: drop minute windows older than 2 hours, day windows older
-- than 90 days. Month windows persist for billing history.

25.3 Per-Feature Cost Weighting

Not all tokens cost the same: GPT-4o output tokens cost more than input tokens, embeddings are nearly free, and agent tool calls have their own pricing. Weight consumption by feature so one unit of quota means one unit of cost:

CREATE TABLE dbo.feature_costs (
    feature       NVARCHAR(100) PRIMARY KEY,  -- 'chat_input', 'chat_output',
                                             -- 'embedding', 'rerank', 'agent_tool'
    cost_per_1k   DECIMAL(10,4) NOT NULL,     -- in quota units per 1k tokens/calls
    updated_at    DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);
-- Example weights (quota units per 1k):
--   chat_input 1.0, chat_output 4.0, embedding 0.05, rerank 0.5, agent_tool 2.0
-- The chat path computes: cost = (in_tokens/1000)*1.0 + (out_tokens/1000)*4.0
-- and consumes that from the bucket — so a long answer costs proportionally
-- more quota than a short one. Update weights when provider pricing changes;
-- keep history in a versioned table for invoice disputes.

Cost weighting is what makes quotas fair across features: without it, users arbitrage the cheapest feature, and your margin evaporates on the expensive ones.

25.4 Communicating Limits: Headers, Errors, and Agent Behavior

A rate limit the user does not understand is a support ticket. Every limited response carries machine-readable headers:

  • → HTTP 429 with Retry-After (seconds until the bucket affords the request) and X-RateLimit-Remaining.
  • → Quota exhaustion (monthly) is HTTP 402 (payment required), not 429 — it needs a plan upgrade, not a retry. The response includes the upgrade URL.
  • → Agents get structured limit signals in tool results, not HTTP codes: {"limited": true, "retry_after_s": 12, "quota_resets_at": "…"} — so the agent loop can back off intelligently instead of erroring the run (§20.1).

    • Also expose a quota-status endpoint backed by the usage_windows table — "you've used 62% of your monthly tokens" in the UI prevents most limit surprises. Transparency about limits is a retention feature.

    25.5 Quota Borrowing and Grace Periods

    Hard quota walls create terrible user experiences: a customer mid-demo hits their monthly cap and the product stops working in front of their prospect. Soften the wall without removing it. Grace periods: when a tenant exhausts their monthly quota, allow a configurable overage (say 10%) while notifying both the tenant admin and your billing team — the overage is invoiced, and the notification starts the upsell conversation with evidence of need. Borrowing: let tenants borrow against next month's quota up to a limit, recorded as a negative carryover in the ledger (§33.2) so accounting stays exact. Never extend grace to the per-minute abuse bucket (§25.2) — grace is a billing feature, not a security feature, and abuse limits stay absolute. The policy table that configures grace per plan tier is a business decision; the enforcement stays in the same atomic consume procedures, so grace can't be bypassed by calling a different code path.

    ---

    Key Takeaways

  • → Implement token buckets with lazy refill and single-statement atomic consumption — no background jobs, no overspend under concurrency, bursts allowed with sustained-rate enforcement.
  • → Track minute/day/month windows simultaneously with MERGE-based atomic increments; each window serves a different purpose (abuse, fair use, billing).
  • → Weight quota consumption by feature cost so one quota unit equals one cost unit — update weights when provider pricing changes and version them for invoice disputes.
  • → Communicate limits precisely: 429 + Retry-After for rate limits, 402 + upgrade URL for exhausted quotas, structured signals for agents, and a visible quota-status UI to prevent surprises.
