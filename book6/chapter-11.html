Conversation Compression and Summarization

Context windows are finite; conversations are not. When history exceeds the token budget (§6.2), the naive approach drops the oldest turns — silently discarding the very context that makes long conversations valuable. Summarization replaces dropped turns with a compressed representation: the model reads the expiring turns, writes a dense summary, and the summary takes their place in the prompt. This chapter builds the summarization pipeline — when to trigger it, how to summarize without losing critical detail, where to store summaries, and the recursive summarization pattern for conversations that outlive even their summaries.

---

11.1 When to Summarize: The Trigger Conditions

Summarization triggers on three conditions, checked whenever history is loaded:

  • → Budget pressure. History tokens exceed ~70% of the allocated history budget. Summarize the oldest 50% of turns, keep the newest verbatim. The 70% threshold (not 100%) leaves room for the summary itself plus the current turn.
  • → Session close. The Chapter 7 expiry job fires summarization for the whole conversation — this is the archival summary stored in long-term memory (§8.3).
  • → Explicit checkpoint. Long-running agent tasks (Chapter 26) checkpoint their state periodically; each checkpoint includes a summary so a crashed agent resumes from the summary rather than replaying hundreds of turns.
    • CREATE TABLE dbo.conversation_summaries (
    summary_id      UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    conversation_id UNIQUEIDENTIFIER NOT NULL
                    CONSTRAINT FK_sum_conversation
                    REFERENCES dbo.conversations(conversation_id) ON DELETE CASCADE,
    tenant_id       UNIQUEIDENTIFIER NOT NULL,
    -- The turn range this summary covers (inclusive)
    from_seq        INT NOT NULL,
    to_seq          INT NOT NULL,
    summary_text    NVARCHAR(MAX) NOT NULL,
    summary_tokens  INT NOT NULL,
    model           NVARCHAR(100) NOT NULL,   -- which model wrote the summary
    created_at      DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    CONSTRAINT CK_sum_range CHECK (from_seq <= to_seq)
);
CREATE INDEX IX_summaries_conversation
    ON dbo.conversation_summaries(conversation_id, from_seq);

    The from_seq / to_seq range is the crucial design element: it records exactly which turns the summary replaces, so history assembly can splice summaries and verbatim turns without gaps or overlaps.

    11.2 Writing Good Summaries: The Prompt Contract

    A summary prompt needs a contract — the summary will be read by a model, not a human, so optimize for machine consumption:

  • → Preserve decisions, commitments, and open questions. "User decided to use the pro plan" matters; "user said hello" does not.
  • → Preserve entities and identifiers. Order numbers, names, dates, error codes — the tokens most likely to be referenced later.
  • → Preserve unresolved state. "Waiting on the user to provide the log file" — the summary must capture what happens next.
  • → Target a compression ratio, not a length. "Compress to ~15% of input tokens" adapts to conversation length better than "write 5 sentences."
    • # Summarization worker (Python)
SUMMARY_PROMPT = """You are compressing a conversation for future reference.
The summary will be read by an AI assistant continuing this conversation.
Rules:
- Preserve all decisions, commitments, entities, identifiers, and open questions.
- Drop greetings, small talk, and restated information.
- Write in third person, present tense, dense factual style.
- Target approximately 15% of the input token count.
- End with an 'Open items:' list if anything is unresolved."""

def summarize_range(conversation_id, from_seq, to_seq, tenant_id):
    turns = load_turns(conversation_id, from_seq, to_seq)
    text = "\n".join(f"{t.role}: {t.content}" for t in turns)
    summary = llm(SUMMARY_PROMPT + "\n\n" + text, model="gpt-4o-mini")
    # Use a cheap model: summarization quality plateaus quickly,
    # and this runs on every long conversation.
    with db(tenant_id) as conn:
        conn.execute("""
            INSERT INTO dbo.conversation_summaries
                (conversation_id, tenant_id, from_seq, to_seq,
                 summary_text, summary_tokens, model)
            VALUES (?, ?, ?, ?, ?, ?, 'gpt-4o-mini')""",
            conversation_id, tenant_id, from_seq, to_seq,
            summary, count_tokens(summary))
        conn.commit()

    Use a cheap model for summarization. Empirical testing across many deployments shows summary quality plateaus quickly — a mini-class model at 15% compression is nearly indistinguishable from a frontier model for this task, at one-tenth the cost.

    11.3 Assembling History with Summaries Spliced In

    The history loader from §6.2 gains a splicing step: covered turn ranges are replaced by their summaries, newest turns stay verbatim:

    CREATE OR ALTER PROCEDURE dbo.usp_load_history_with_summaries
    @conversation_id UNIQUEIDENTIFIER,
    @token_budget    INT = 6000
AS
BEGIN
    SET NOCOUNT ON;
    -- Summaries first (oldest), as system-context blocks
    SELECT N'summary' AS kind, from_seq AS seq,
           N'[Summary of turns ' + CAST(from_seq AS NVARCHAR(10)) + N'-'
             + CAST(to_seq AS NVARCHAR(10)) + N'] ' + summary_text AS content,
           summary_tokens AS tokens
    FROM dbo.conversation_summaries
    WHERE conversation_id = @conversation_id
    UNION ALL
    -- Then verbatim turns NOT covered by any summary
    SELECT N'turn', m.seq, m.content, m.token_count
    FROM dbo.messages AS m
    WHERE m.conversation_id = @conversation_id
      AND m.is_current = 1
      AND NOT EXISTS (
          SELECT 1 FROM dbo.conversation_summaries AS s
          WHERE s.conversation_id = m.conversation_id
            AND m.seq BETWEEN s.from_seq AND s.to_seq)
    ORDER BY seq ASC;
    -- Caller applies the token-budget window (§6.2) over this unified stream.
END;
GO

    The NOT EXISTS anti-join guarantees no turn is ever double-counted — a summary and its covered turns never appear together. The bracketed prefix tells the model what it is reading, which measurably reduces confabulation about summarized events.

    11.4 Recursive Summarization for Very Long Conversations

    Summaries themselves accumulate. A conversation with 50 summaries has the same budget problem one level up. The fix is recursive: when summary tokens exceed their own budget, summarize the summaries.

    -- Summaries reference their children for the recursive rollup
ALTER TABLE dbo.conversation_summaries
    ADD parent_summary_id UNIQUEIDENTIFIER NULL
        CONSTRAINT FK_sum_parent
        REFERENCES dbo.conversation_summaries(summary_id),
        summary_level INT NOT NULL DEFAULT 0;
GO
-- Level 0: summarizes raw turns. Level 1: summarizes level-0 summaries, etc.
-- The loader prefers the highest level available for old ranges:
--   WHERE summary_level = (SELECT MAX(summary_level) ... for that range)

    In practice, two levels handle essentially every real conversation: level-0 summaries of turn ranges, and a single level-1 "conversation so far" summary. Three levels is a sign the conversation should have been split — consider suggesting a fresh conversation to the user at that point.

    11.5 Validating Summary Quality

    Summaries are lossy by design; validate that the loss is acceptable. The automated check: an LLM judge compares answers generated with full history versus summarized history on a sample of questions about the conversation. If answer equivalence drops below your threshold (typically 90%), the compression ratio is too aggressive or the summary prompt needs the contract terms from §11.2 reinforced. Run this evaluation monthly — it is cheap and it catches prompt drift (Chapter 19).

    ---

    Key Takeaways

  • → Record the exact turn range each summary covers (from_seq/to_seq) so history assembly splices summaries and verbatim turns with no gaps or overlaps — enforced by a NOT EXISTS anti-join.
  • → Summarize for machine consumption: decisions, entities, open items, ~15% compression ratio, third-person dense style — written by a cheap model, since quality plateaus quickly.
  • → Trigger on budget pressure (70% of history budget), session close, and agent checkpoints — and recurse summaries into higher levels when they accumulate.
  • → Validate with an LLM judge comparing full-history vs. summarized-history answers monthly. Summarization is lossy; measure the loss instead of assuming it.
