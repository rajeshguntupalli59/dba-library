Schema Introspection for AI Query Generation

Chapter 22 assumed a curated schema catalog. This chapter builds the machinery that keeps that catalog honest: automated introspection of the live database — tables, columns, keys, statistics, and data profiles — so the catalog reflects reality instead of documentation aspirations. You will learn what to introspect and how often, how to detect schema drift that breaks generated queries, data profiling that grounds the model's assumptions, and the self-healing loop where introspection updates the catalog automatically. The catalog is a cache; introspection is the source of truth.

---

23.1 What to Introspect

SQL Server's catalog views expose everything the model needs, in four layers:

  • → Structure: tables, columns, types, nullability from INFORMATION_SCHEMA / sys.columns. The skeleton.
  • → Relationships: primary keys, foreign keys, unique constraints from sys.foreign_keys. The join graph — the model's most common source of errors when missing.
  • → Statistics: row counts, value distributions from sys.dm_db_partition_stats and column statistics. Tells the model which tables are large (aggregate, don't scan) and which columns are selective.
  • → Data profile: sampled distinct values, min/max, null fraction per column. Grounds the model's assumptions about formats and enums far better than type names alone.
    • -- The introspection sweep: structure + relationships in one pass
-- (run by a scheduled job; results upserted into the catalog tables)
SELECT
    s.name AS schema_name, t.name AS table_name,
    c.name AS column_name,
    TYPE_NAME(c.user_type_id) AS data_type,
    c.max_length, c.precision, c.scale, c.is_nullable,
    CASE WHEN pk.column_id IS NOT NULL THEN 1 ELSE 0 END AS is_pk,
    fk.ref_table, fk.ref_column
FROM sys.tables AS t
JOIN sys.schemas AS s ON s.schema_id = t.schema_id
JOIN sys.columns AS c ON c.object_id = t.object_id
LEFT JOIN (
    SELECT ic.object_id, ic.column_id
    FROM sys.indexes AS i
    JOIN sys.index_columns AS ic
      ON ic.object_id = i.object_id AND ic.index_id = i.index_id
    WHERE i.is_primary_key = 1
) AS pk ON pk.object_id = c.object_id AND pk.column_id = c.column_id
LEFT JOIN (
    SELECT fkc.parent_object_id AS object_id, fkc.parent_column_id AS column_id,
           OBJECT_NAME(fk.referenced_object_id) AS ref_table,
           COL_NAME(fk.referenced_object_id, fkc.referenced_column_id) AS ref_column
    FROM sys.foreign_keys AS fk
    JOIN sys.foreign_key_columns AS fkc
      ON fkc.constraint_object_id = fk.object_id
) AS fk ON fk.object_id = c.object_id AND fk.column_id = c.column_id
WHERE s.name = 'dbo'
ORDER BY schema_name, table_name, c.column_id;

    23.2 Data Profiling: Grounding the Model's Assumptions

    Types lie by omission: NVARCHAR(30) does not tell the model the column holds 'pending'/'shipped'/'delivered'. Profiling samples each exposed column and records the reality:

    -- Profile: distinct values (if few), min/max, null fraction
-- Run per exposed column; store in schema_column_catalog
CREATE OR ALTER PROCEDURE dbo.usp_profile_column
    @schema NVARCHAR(128), @table NVARCHAR(128), @column NVARCHAR(128)
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @sql NVARCHAR(MAX) = N'
    SELECT @distinct_out = COUNT(DISTINCT ' + QUOTENAME(@column) + N'),
           @nulls_out   = SUM(CASE WHEN ' + QUOTENAME(@column) + N' IS NULL THEN 1 ELSE 0 END),
           @total_out   = COUNT(*)
    FROM ' + QUOTENAME(@schema) + N'.' + QUOTENAME(@table) + N'
    TABLESAMPLE SYSTEM (10 PERCENT);';
    -- If distinct <= 20, capture the value list as example_values.
    -- Always capture min/max for dates and numbers.
    -- QUOTENAME everywhere: this is dynamic SQL over catalog inputs.
END;
GO

    Profile on a schedule matched to data volatility (weekly for most tables, daily for fast-moving ones), and always with TABLESAMPLE — full scans of the messages table for profiling would be absurd. The profile deltas (new distinct values appearing) are themselves a signal: a new status value the model has never seen is a generation risk worth flagging.

    23.3 Schema Drift Detection

    Schemas change: columns added, renamed, dropped; tables partitioned; types widened. Every change is a potential text-to-SQL breakage. The drift detector compares the live introspection against the catalog snapshot:

  • → Added columns/tables: introspect, profile, and propose catalog entries — a human approves exposure (new columns are not auto-exposed; §22.1's allowlist is a security boundary).
  • → Dropped/renamed columns: immediately invalidate cached queries referencing them (§22.4's schema_version bump) and alert — generated SQL will fail validation until the prompt's schema is refreshed.
  • → Type changes: flag for review; a widened NVARCHAR is harmless, a changed date semantics is not.
    • -- Drift detection: live schema vs. catalog snapshot
-- Returns added/dropped/changed objects since the last sweep
WITH live AS (
    SELECT s.name AS sch, t.name AS tbl, c.name AS col,
           TYPE_NAME(c.user_type_id) AS typ, c.is_nullable
    FROM sys.tables AS t
    JOIN sys.schemas AS s ON s.schema_id = t.schema_id
    JOIN sys.columns AS c ON c.object_id = t.object_id
),
snap AS (
    SELECT object_schema AS sch, object_name AS tbl, column_name AS col
    FROM dbo.schema_column_catalog
)
SELECT 'dropped_or_renamed' AS drift, s.sch, s.tbl, s.col
FROM snap AS s
WHERE NOT EXISTS (SELECT 1 FROM live AS l
                  WHERE l.sch = s.sch AND l.tbl = s.tbl AND l.col = s.col)
UNION ALL
SELECT 'added', l.sch, l.tbl, l.col
FROM live AS l
WHERE NOT EXISTS (SELECT 1 FROM snap AS s
                  WHERE s.sch = l.sch AND s.tbl = l.tbl AND s.col = l.col);
-- DDL trigger on the database keeps a change log so drift is attributed,
-- not just detected: who changed what, when.

    23.4 The Self-Healing Loop

    Tie introspection, drift detection, and the text-to-SQL layer into a loop:

  • → Nightly: introspection sweep → catalog upsert → profile refresh → drift report.
  • → On drift: bump schema_version (invalidates cached SQL), re-embed changed table descriptions (schema retrieval stays current), alert on dropped objects.
  • → On validation failure spike: if Gate 2 (allowlist) rejections spike, the catalog is stale — trigger an out-of-cycle sweep instead of blaming the model.
  • → Quarterly: human review of proposed exposures (added columns awaiting approval) and glossary updates from failed questions.

    • The loop's invariant: the catalog never drifts more than 24 hours from the live schema, cached SQL never survives a schema change, and every automated step leaves an audit trail of what changed and why.

    ---

    23.5 Glossary Management: The Human Layer

    Introspection captures what the database is; the glossary captures what it means. "Active customer" might mean status = 'A' AND last_order_date > DATEADD(year, -1, GETDATE()) — no catalog view will tell the model that. Maintain the glossary as a versioned table (term, definition, canonical SQL fragment, owner), let the text-to-SQL prompt inject relevant entries (§22.2), and source new entries from failed questions: every week, review the questions the model got wrong and ask "which glossary entry would have prevented this?" The glossary is the highest-leverage text-to-SQL investment — one well-written definition fixes a whole class of errors, and unlike prompt tuning, it compounds.

    ---

    Key Takeaways

  • → Introspect four layers — structure, relationships, statistics, data profile — on a schedule, and treat the catalog as a cache with the live database as the source of truth.
  • → Profile with TABLESAMPLE and record distinct values, min/max, and null fractions. Example values ground the model's assumptions; new distinct values are an early warning.
  • → Detect drift by diffing live introspection against the catalog snapshot, invalidate cached SQL on any change, and never auto-expose new columns — the allowlist is a security boundary.
  • → Close the loop: nightly sweeps, drift-triggered version bumps and re-embedding, validation-spike-triggered out-of-cycle sweeps, quarterly human review.
