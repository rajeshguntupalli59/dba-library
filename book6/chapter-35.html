Scaling AI Apps on Azure SQL

Everything so far assumed a single SQL Server. Growth breaks that assumption along three axes: read volume (more chat users), write volume (more ingestion), and data size (more vectors, more history). Azure SQL is the scaling path this book standardizes on — but scaling is a sequence of deliberate steps, not a single migration. This chapter walks the ladder: read scale-out with replicas, elastic pools for multi-tenant economics, Hyperscale for very large vector stores, and the sharding decision you should defer as long as possible.

---

35.1 Read Scale-Out: Replicas for Chat Workloads

Chat workloads are read-heavy: history replay, vector search, semantic cache lookups, dashboard reads. Azure SQL's read scale-out routes these to free readable secondaries:

  • → Route by operation: writes (message inserts, audit writes, bucket consumption) go to the primary; reads (history replay, vector search, cache lookups) go to the secondary via ApplicationIntent=ReadOnly in the connection string.
  • → Accept replication lag consciously: a message inserted on the primary may not be visible on the secondary for a second or two. The chat path reads the just-written conversation from the primary (§6.2's replay-after-write); background reads (analytics, eval sampling) tolerate the lag.
  • → Vector search scales beautifully on replicas: it's CPU-bound and read-only — the ideal secondary workload. Size the secondary for vector-search concurrency, not the primary.
    • // Two connection strings, one decision per operation
var writeDb = "Server=tcp:aiapp.database.windows.net;Database=aiapp;"
            + "ApplicationIntent=ReadWrite;...";   // default
var readDb  = "Server=tcp:aiapp.database.windows.net;Database=aiapp;"
            + "ApplicationIntent=ReadOnly;...";     // readable secondary

// The data layer picks: writes + read-your-write → writeDb;
// everything else → readDb. One helper, used everywhere:
IDbConnection ForQuery(bool mustSeeOwnWrites) =>
    new SqlConnection(mustSeeOwnWrites ? writeDb : readDb);

    35.2 Elastic Pools: Multi-Tenant Economics

    Multi-tenant AI apps (§18) often run one database per tenant — which means hundreds of databases with spiky, uncorrelated usage. Elastic pools share DTUs/vCores across the pool: quiet tenants subsidize busy ones, and you pay for the pool's peak rather than each database's peak:

  • → Pool by usage profile, not randomly: put tenants with similar vector-search intensity in the same pool so the shared resources match the workload shape.
  • → Set per-database min/max so one tenant's embedding backfill (§14.2) can't starve the pool — the noisy-neighbor guard from §18.4, now at the infrastructure layer.
  • → Monitor pool utilization, not just database utilization: the pool eDTU/vCore percentage is the scaling signal; add capacity when sustained above 70%, not when one tenant spikes.

    35.3 Hyperscale: When Vectors Get Very Large

    The vector store (§3.2) grows linearly with documents × chunks — millions of 1536-dimensional vectors is tens of gigabytes before indexes. Hyperscale separates compute from storage (up to 128 TB) and scales them independently:

  • → Scale compute for search concurrency, storage for corpus size — independently. A 50 GB vector store with 200 concurrent searches needs big compute and modest storage; Hyperscale prices them separately.
  • → Named replicas give isolated read scale-out for specific workloads: one replica for the chat vector search, another for the analytics team's embedding scans — each sized to its workload.
  • → Rapid scale-up handles the predictable spikes: scale compute up before the Monday-morning ingest backfill, down after. The vector index rebuilds (§15.3) run faster on bigger compute — schedule them during scaled-up windows.

    • ---

    35.4 The Sharding Decision (Defer It)

    True sharding — splitting tenants across databases/servers with a shard map — is the last resort, not the first. Before sharding, exhaust:

  • → Read scale-out (§35.1) for read pressure.
  • → Bigger compute / Hyperscale for data size and search concurrency.
  • → Caching (Chapter 34) to cut the load itself — a 40% semantic-cache hit rate is a 40% load reduction no infrastructure change can match.
  • → Workload isolation — move batch analytics (§4.5's columnstore queries) and embedding backfills to replicas or separate databases before they contend with chat.

    • When sharding becomes unavoidable (single-database limits genuinely bind), shard by tenant with the tenant_id → database map in a small shard-map database — the application's connection factory (§35.1's helper) resolves the database per tenant. Cross-shard queries go through the analytics pipeline (§4.5), never through cross-database joins on the chat path. And note what sharding costs: every pattern in this book that assumed one database (RLS, hash chains, CDC cursors) now needs a per-shard instance.

    35.5 Disaster Recovery for AI Applications

    Scaling (§35.1–35.4) is about handling growth; disaster recovery is about surviving loss — and AI applications have recovery requirements beyond the database backup. The RPO/RTO conversation needs four tiers, because not all AI state is equal:

  • → Tier 0 — Conversations, audit, ledger: zero data loss tolerated. Synchronous replication (Availability Groups / Azure SQL's built-in HA) plus point-in-time restore. The audit log's hash chain (§24.3) verifies post-recovery integrity — recompute the chain after any restore and alert on mismatch.
  • → Tier 1 — Vector store and derived indexes: recoverable by re-running ingestion (§14), so the RPO can be hours — but re-embedding a large corpus takes time and API budget. Keep geo-replicated backups of the vector tables anyway; the re-ingest path is the fallback, not the plan.
  • → Tier 2 — Caches and ephemeral state: not backed up at all. The warming procedure (§34.5) rebuilds them after failover — which is why warming must be automated, because failovers happen at the worst possible time.
  • → Tier 3 — Sessions and in-flight streams: expected to be lost. Clients reconnect, resume from persisted buffers (§29.5), and the orphan reaper (§29.3) cleans up whatever didn't survive.

    • Drill the failover quarterly (§40.4): restore the backup to a secondary region, verify the chain, warm the caches, replay yesterday's erasure requests (§38.3's backup-window rule), and measure the actual RTO against the SLA. The drill's most common finding is not a database problem — it's that the application's connection strings, key vault references, or model provider keys weren't part of the recovery plan. DR for an AI app is a system drill, not a database drill.

    ---

    One more scaling lever that teams overlook: move the embedding workload off the database entirely. Embedding computation (§14.2) is CPU/GPU-bound batch work that gains nothing from running near the data — run it on a dedicated compute pool (Azure Container Instances, a Kubernetes job) that writes vectors back through the ingest queue. This isolates the spikiest, least latency-sensitive workload from the chat path, letting the database tier scale for queries while the embedding tier scales for throughput. Separation of workloads is scaling's quiet superpower.

    ---

    Whatever tier you run, keep one non-production environment at production scale for the load tests (§39.4) and chaos experiments (§39.5). Scaling confidence comes from evidence, not architecture diagrams — and the cost of that environment is rounding error next to a single scaling-related outage.

    ---

    Key Takeaways

  • → Scale reads first: ApplicationIntent=ReadOnly routes chat's read-heavy workload to secondaries; keep read-your-write operations on the primary.
  • → Use elastic pools for multi-tenant economics — pool by usage profile, cap per-database consumption, and scale on pool utilization.
  • → Hyperscale separates vector-store compute from storage — scale each independently, isolate workloads on named replicas, and exploit rapid scale-up for batch windows.
  • → Defer sharding until every cheaper option is exhausted, then shard by tenant with a shard-map database — and budget for per-shard instances of every pattern in this book.
