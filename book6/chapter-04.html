Designing AI-Ready Schemas in SQL Server

Chapter 1 handed you a complete schema; this chapter explains the design decisions behind it so you can extend it with confidence. AI workloads stress databases in unusual ways: very wide rows (embeddings), very high insert rates (messages, audit logs), mixed access patterns (point lookups plus vector scans plus analytics), and payloads whose shape is defined by model vendors rather than by you. Good schema design absorbs all four. You will learn normalization boundaries for AI entities, when JSON beats columns and vice versa, indexing strategy for the five dominant access patterns, partitioning for hot tables, and the temporal-table pattern that makes AI outputs auditable by default.

---

4.1 The Five Dominant Access Patterns

Design starts from queries, not entities. Every AI application in this book serves five access patterns; the schema must make all five fast:

  • → Point lookups by key. Fetch a conversation, a user, a chunk. Clustered primary keys on UNIQUEIDENTIFIER handle these — but consider NEWSEQUENTIALID() instead of NEWID() for insert-heavy tables to avoid page splits and index fragmentation.
  • → Range scans by tenant and time. "Last 10 messages in this conversation," "audit rows for this tenant this month." Composite indexes with tenant first, time second: (tenant_id, created_at DESC).
  • → Vector similarity with filters. The hybrid search procedure. Needs the vector index plus selective relational predicates applied before or during the ANN walk.
  • → Analytical aggregations. Token usage by tenant, error rates by model. Columnstore indexes on the audit and messages tables make these scans 10–100x faster (see §4.5).
  • → High-rate appends. Messages, audit rows, chunk inserts. Minimal indexing on the write path, delayed durability where acceptable, and partitioning so old data can age out without deletes.

    • When two patterns conflict — analytics wants a columnstore, point lookups want a rowstore — use a nonclustered columnstore index on top of the rowstore table. You get both: transactional writes plus analytical scans, maintained by the engine.

    4.2 Normalization Boundaries: What Gets Its Own Table

    The Chapter 1 schema normalizes along entity lifecycle boundaries:

  • → Documents vs. chunks. Separate tables because they have different lifecycles (documents version; chunks are immutable once embedded), different sizes (one document → hundreds of chunks), and different indexes (full-text on documents, vector on chunks).
  • → Conversations vs. messages. Separate tables because message volume dwarfs conversation volume 50:1, and the two are queried differently (conversation lists vs. message streams). A conversation row holds aggregates — total tokens, title — maintained by triggers or application writes.
  • → Audit log as its own table. Never reuse the messages table for audit. Audit rows have different retention, different access control (support staff read audit; never messages), and different indexing. Physical separation is a compliance feature.

    • The anti-pattern is the "one big AI table" — stuffing messages, chunks, and audit events into a single events table with a type discriminator. It destroys indexing selectivity, makes retention policies impossible to express, and turns every query into a filter on the discriminator column. Normalize on lifecycle, denormalize on read path (covering indexes, indexed views) — never the reverse.

    4.3 Columns vs. JSON: The Decision Rule

    Chapter 3 stated the rule; here is the full decision procedure for every new field:

  • → Make it a column if: you filter on it, join on it, aggregate it, constrain it (CHECK/FOREIGN KEY), or index it for ordering. Examples: token_count, status, role, latency_ms.
  • → Make it JSON if: its schema is defined by a model vendor, it varies per model version, it is write-once/read-rarely, or it is genuinely schemaless user data. Examples: tool_calls, citations, raw provider responses.
  • → Promote JSON paths to computed columns when a JSON field becomes hot. SQL Server makes this painless:
    • -- A JSON field got hot: promote it to an indexed computed column
-- without changing the application write path.
ALTER TABLE dbo.messages
    ADD first_tool AS (JSON_VALUE(tool_calls, '$[0].function.name')) PERSISTED;

CREATE INDEX IX_messages_first_tool
    ON dbo.messages (first_tool)
    WHERE first_tool IS NOT NULL;

-- Now "all conversations that called get_refund_policy" is an index seek:
SELECT conversation_id, COUNT(*)
FROM dbo.messages
WHERE first_tool = 'get_refund_policy'
GROUP BY conversation_id;

    This promotion path is the reason to start with JSON for uncertain fields: you are never locked in. The persisted computed column materializes the value, the index makes it searchable, and the application keeps writing the same JSON.

    4.4 Keys, Identity, and the NEWSEQUENTIALID Decision

    AI tables are insert-heavy: every chat turn writes rows, every ingestion writes hundreds of chunks. Random NEWID() values as clustered keys cause page splits and fragmentation under sustained inserts. The fix is NEWSEQUENTIALID() for clustered keys on hot tables:

    -- Hot append tables: sequential GUIDs keep inserts at the end of the index
CREATE TABLE dbo.messages_hot (
    message_id      UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWSEQUENTIALID(),
    ...
);

-- Reference/dimension tables: NEWID() is fine, inserts are rare
-- Public-facing IDs: keep random NEWID() so IDs are unguessable in URLs/APIs.
-- Internal hot tables: NEWSEQUENTIALID() for insert performance.

    The nuanced rule: use NEWSEQUENTIALID() on the clustered key of append-heavy tables (messages, audit log, chunks), and expose a separate random external ID if the key ever appears in a URL. Sequential GUIDs are guessable across restarts on some versions — never use a clustered sequential key as a capability token.

    4.5 Columnstore for the Analytics Path

    The audit log and messages tables serve two masters: transactional appends and analytical scans ("tokens per tenant per day"). A nonclustered columnstore index gives you both without ETL:

    -- Analytical accelerator on the audit log: rowstore stays for OLTP,
-- columnstore serves the dashboards.
CREATE NONCLUSTERED COLUMNSTORE INDEX NCCI_audit_analytics
    ON dbo.llm_audit_log (tenant_id, model, status, total_tokens,
                          latency_ms, created_at);

-- The "tokens per tenant per day" dashboard query now scans compressed
-- column segments instead of millions of rows:
SELECT tenant_id,
       CAST(created_at AS DATE) AS day,
       SUM(total_tokens) AS tokens,
       AVG(CAST(latency_ms AS FLOAT)) AS avg_latency
FROM dbo.llm_audit_log
WHERE created_at >= DATEADD(day, -90, SYSUTCDATETIME())
GROUP BY tenant_id, CAST(created_at AS DATE);

    Columnstore compression on audit data is typically 5–10x, and aggregation queries run an order of magnitude faster. The tradeoff is a small write-amplification cost as rows move from the delta store to compressed segments — negligible next to the LLM latencies dominating the pipeline.

    4.6 Partitioning Hot Tables by Time

    Messages and audit tables grow without bound. Partitioning by month on created_at gives you three superpowers: partition elimination for time-range queries, fast archival via partition switching instead of deletes, and isolated index maintenance per partition.

    -- Monthly partitions on the audit log
CREATE PARTITION FUNCTION PF_audit_monthly (DATETIME2)
    AS RANGE RIGHT FOR VALUES
    ('2026-01-01','2026-02-01','2026-03-01','2026-04-01','2026-05-01','2026-06-01',
     '2026-07-01','2026-08-01','2026-09-01','2026-10-01','2026-11-01','2026-12-01');

CREATE PARTITION SCHEME PS_audit_monthly
    AS PARTITION PF_audit_monthly ALL TO ([PRIMARY]);

-- Recreate the table on the scheme (do this at design time, not later)
CREATE TABLE dbo.llm_audit_log (
    ... -- same columns as §1.2
    CONSTRAINT PK_audit PRIMARY KEY (log_id, created_at)
) ON PS_audit_monthly (created_at);

-- Age out old data in milliseconds: switch the oldest partition out
-- instead of DELETEing millions of rows.
ALTER TABLE dbo.llm_audit_log
    SWITCH PARTITION 2 TO dbo.llm_audit_log_archive PARTITION 2;

    Plan the partition function a year ahead and add future boundary points with SPLIT RANGE monthly — a one-line maintenance job. GDPR's right-to-be-forgotten (Chapter 38) becomes dramatically cheaper when a user's data can be located by time partition first.

    4.7 Temporal Tables: Auditable AI Outputs by Default

    AI outputs change meaning over time — a regenerated answer, a corrected summary, a re-ranked result. System-versioned temporal tables keep every version automatically, which is the cheapest possible compliance story:

    -- Every version of every AI-generated summary, kept automatically
CREATE TABLE dbo.ai_summaries (
    summary_id      UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    conversation_id UNIQUEIDENTIFIER NOT NULL,
    summary_text    NVARCHAR(MAX) NOT NULL,
    model           NVARCHAR(100) NOT NULL,
    valid_from      DATETIME2 GENERATED ALWAYS AS ROW START NOT NULL,
    valid_to        DATETIME2 GENERATED ALWAYS AS ROW END NOT NULL,
    PERIOD FOR SYSTEM_TIME (valid_from, valid_to)
) WITH (SYSTEM_VERSIONING = ON (HISTORY_TABLE = dbo.ai_summaries_history));

-- "What did the summary say last Tuesday?" — time travel in one clause
SELECT summary_text
FROM dbo.ai_summaries
FOR SYSTEM_TIME AS OF '2026-09-22 12:00:00'
WHERE conversation_id = @cid;

    Temporal tables answer the question every AI incident review asks — "what exactly did the system say at the time?" — without application code. Use them for summaries, generated reports, and any AI output a human might later dispute. Chapter 32 builds the full versioning strategy on this foundation.

    ---

    Key Takeaways

  • → Design from the five access patterns. Point lookups, tenant-time ranges, filtered vector search, analytical aggregations, and high-rate appends — every index and partitioning decision traces back to one of these.
  • → Normalize on entity lifecycle. Documents vs. chunks, conversations vs. messages, audit as its own table. Never the "one big AI events table."
  • → Columns for filter/join/aggregate; JSON for vendor-shaped payloads; promote hot JSON paths to persisted computed columns. The promotion path means you are never locked into an early guess.
  • → NEWSEQUENTIALID on hot clustered keys, nonclustered columnstore for analytics, monthly partitioning for retention, temporal tables for versioned outputs. These four features together handle the scale and compliance demands of production AI data.
