Evaluating RAG: Metrics and Feedback Loops

"The assistant feels worse this week" is not a diagnosable statement. RAG evaluation turns that feeling into numbers: retrieval recall, answer groundedness, citation precision, user satisfaction — measured continuously, stored in SQL Server, and wired into feedback loops that improve the system. This chapter builds the evaluation harness: the golden dataset, the metrics that matter, LLM-as-judge scoring, user feedback capture, and the closed loop from measurement to prompt/config change. If you cannot measure it, you cannot ship changes to it safely.

---

19.1 The Golden Dataset

Evaluation starts with a dataset of questions with known-good answers, stored as tables — versioned, reviewable, and queryable:

CREATE TABLE dbo.eval_sets (
    eval_set_id   UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    name          NVARCHAR(200) NOT NULL,
    description   NVARCHAR(MAX) NULL,
    version       INT NOT NULL DEFAULT 1,
    is_active     BIT NOT NULL DEFAULT 1,
    created_at    DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);

CREATE TABLE dbo.eval_questions (
    question_id     UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    eval_set_id     UNIQUEIDENTIFIER NOT NULL
                    CONSTRAINT FK_eq_set REFERENCES dbo.eval_sets(eval_set_id),
    question        NVARCHAR(MAX) NOT NULL,
    -- What a good answer must contain (judged semantically, not string-matched)
    expected_points JSON NOT NULL,      -- ["mentions 30-day window", "cites policy §4.2"]
    -- Chunks that SHOULD be retrieved for this question
    expected_chunk_ids JSON NULL,       -- ["guid1", "guid2"]
    category        NVARCHAR(50) NULL,  -- 'factual', 'multi-hop', 'adversarial'
    difficulty      INT NULL            -- 1-5, for stratified sampling
);
CREATE INDEX IX_eq_set ON dbo.eval_questions(eval_set_id);

Build the golden set from real user questions: sample production queries (anonymized), have domain experts write the expected points, and review quarterly. A golden set of 100–200 questions beats a synthetic set of 10,000 — it measures what users actually ask.

19.2 The Metrics That Matter

  • → Retrieval recall@k. Fraction of expected_chunk_ids present in the top-k retrieved. Measures the retrieval path in isolation — chunking, embeddings, index, filters.
  • → Answer groundedness. Does the answer's every factual claim trace to a cited chunk? Scored by an LLM judge (next section). The single most important quality metric for RAG.
  • → Citation precision/recall. Of the cited chunks, how many were relevant (precision)? Of the relevant chunks, how many were cited (recall)? Catches both over-citation (padding) and under-citation (missing support).
  • → Expected-point coverage. Fraction of expected_points present in the answer. Measures end-to-end usefulness.
  • → User feedback rate. Thumbs up/down per answer in production. Noisy but real — the only metric measured on actual usage.
    • CREATE TABLE dbo.eval_runs (
    run_id          UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    eval_set_id     UNIQUEIDENTIFIER NOT NULL,
    -- What changed in this run: prompt version, k, model, flags...
    config_snapshot JSON NOT NULL,
    started_at      DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    completed_at    DATETIME2 NULL,
    status          NVARCHAR(20) NOT NULL DEFAULT N'running'
);

CREATE TABLE dbo.eval_results (
    result_id       UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    run_id          UNIQUEIDENTIFIER NOT NULL
                    CONSTRAINT FK_er_run REFERENCES dbo.eval_runs(run_id),
    question_id     UNIQUEIDENTIFIER NOT NULL,
    retrieved_chunk_ids JSON NULL,
    answer          NVARCHAR(MAX) NULL,
    -- Metrics, all 0..1 unless noted
    retrieval_recall_at_k  DECIMAL(4,3) NULL,
    groundedness           DECIMAL(4,3) NULL,
    citation_precision     DECIMAL(4,3) NULL,
    citation_recall        DECIMAL(4,3) NULL,
    point_coverage         DECIMAL(4,3) NULL,
    latency_ms             INT NULL,
    judge_model            NVARCHAR(100) NULL,
    judged_at              DATETIME2 NULL
);
CREATE INDEX IX_er_run ON dbo.eval_results(run_id);

    19.3 LLM-as-Judge Scoring

    Human grading does not scale; LLM judges do, with known biases. The discipline that makes judges trustworthy:

  • → Judge with a different model than the generator (or at least a different prompt) to avoid self-preference bias.
  • → Calibrate against humans quarterly: grade 50 answers both ways; if judge-human agreement drops below 85%, rewrite the judge prompt.
  • → Score with rubrics, not vibes: the judge gets the expected points and scores each as present/absent with a quote — structured output, auditable.
    • # Judge prompt (Python): structured, quotable, auditable
JUDGE_PROMPT = """You are grading a RAG answer. Be strict and literal.

Question: {question}

Expected points (each must be addressed for full marks):
{expected_points}

Retrieved chunks (the ONLY allowed sources):
{chunks}

Answer to grade:
{answer}

Return JSON:
{{
  "points_covered": [{{"point": "...", "covered": true, "quote": "..."}}],
  "ungrounded_claims": ["claim with no chunk support", ...],
  "citations_valid": true/false,
  "notes": "..."
}}"""

    Store the judge's raw JSON in the result row. When a metric moves unexpectedly, the raw judgments are the first place you look — and they are the evidence you show stakeholders who question the numbers.

    19.4 User Feedback Capture

    Production feedback is the ground truth that eval sets approximate. Capture it frictionlessly and store it richly:

    CREATE TABLE dbo.answer_feedback (
    feedback_id   UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    message_id    UNIQUEIDENTIFIER NOT NULL
                  CONSTRAINT FK_fb_message REFERENCES dbo.messages(message_id),
    tenant_id     UNIQUEIDENTIFIER NOT NULL,
    user_id       UNIQUEIDENTIFIER NOT NULL,
    rating        NVARCHAR(20) NOT NULL
                  CONSTRAINT CK_fb_rating CHECK (rating IN
                      (N'up', N'down', N'regenerated')),
    category      NVARCHAR(50) NULL,   -- 'wrong', 'incomplete', 'hallucinated', ...
    comment       NVARCHAR(MAX) NULL,
    created_at    DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);
CREATE INDEX IX_fb_message ON dbo.answer_feedback(message_id);

-- Feedback analytics: where is quality actually failing?
SELECT f.category, COUNT(*) AS n,
       AVG(CAST(er.groundedness AS FLOAT)) AS avg_groundedness
FROM dbo.answer_feedback AS f
LEFT JOIN dbo.messages AS m ON m.message_id = f.message_id
-- join to eval-style judgments if the message was graded
GROUP BY f.category ORDER BY n DESC;

    Treat "regenerated" as an implicit down-vote — the user rejected the answer strongly enough to ask again. And mine down-voted answers for golden-set additions: every real failure is a future regression test.

    19.5 Closing the Loop

    Metrics without action are dashboard decoration. The weekly quality loop:

  • → Run the eval set on every prompt/config change before deploy — the config_snapshot column makes every run reproducible and comparable.
  • → Diff metrics between runs with a simple query: which questions got worse, which got better? A change that improves 80 questions and regresses 20 needs investigation, not celebration.
  • → Promote production failures into the golden set. Down-voted answers with clear expected points become new eval questions — the set grows with real usage.
  • → Track metric trends, not snapshots. A dashboard of groundedness and recall over time, annotated with deploy markers, shows whether the system is improving or drifting.
    • -- Regression diff between two eval runs: what got worse?
SELECT cur.question_id, q.question,
       prev.point_coverage AS before_cov, cur.point_coverage AS after_cov,
       prev.groundedness    AS before_grd, cur.groundedness    AS after_grd
FROM dbo.eval_results AS cur
JOIN dbo.eval_results AS prev
  ON prev.question_id = cur.question_id AND prev.run_id = @prev_run
JOIN dbo.eval_questions AS q ON q.question_id = cur.question_id
WHERE cur.run_id = @cur_run
  AND (cur.point_coverage < prev.point_coverage
       OR cur.groundedness < prev.groundedness)
ORDER BY (prev.point_coverage - cur.point_coverage) DESC;

    ---

    Key Takeaways

  • → Build the golden set from real user questions with expert-written expected points — 100 real questions beat 10,000 synthetic ones. Version the set and review it quarterly.
  • → Measure retrieval recall, groundedness, citation precision/recall, point coverage, and user feedback — and store every run with its config snapshot for reproducibility.
  • → Judge with rubrics and structured output, calibrate against humans quarterly, and keep the raw judgments as auditable evidence.
  • → Close the loop weekly: eval every config change before deploy, diff runs for regressions, and promote production failures into the golden set.
