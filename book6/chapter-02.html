The AI Application Stack on SQL Server

Chapter 1 argued that SQL Server can be the single operational backbone for AI applications. This chapter zooms out to the full stack: where the LLM sits, where the vector layer lives, where relational data fits, and how the three interact in a production topology. You will learn the reference architecture that the rest of this book implements piece by piece, the request lifecycle of a single chat turn across every layer, and how to make build-vs-buy decisions for each component without painting yourself into a corner. Everything here maps to SQL Server 2025 and Azure services, so the architecture you design on your laptop deploys to the cloud without a rewrite.

---

2.1 The Three Layers of an AI Application

Every production AI application decomposes into three layers, regardless of framework or vendor:

  • → The reasoning layer (LLM). A hosted model API — Azure OpenAI, Anthropic, or a self-hosted model — that turns prompts into text, tool calls, and structured outputs. It is stateless: every call must carry its full context.
  • → The retrieval layer (vectors + relational). Embeddings, similarity search, metadata filters, conversation history, and permissions. In this book this entire layer is SQL Server: the native VECTOR type, DiskANN vector indexes, full-text search, and T-SQL.
  • → The system-of-record layer (relational). Users, tenants, billing, audit logs, quotas, and configuration. Also SQL Server — the same database, the same transactions, the same backup story.

    • The critical design decision is that layers two and three are the same database. Splitting retrieval and system-of-record across two systems forces you to solve distributed transactions for operations as simple as "store the answer and charge the user." Keeping them together means one transaction, one backup, one security model.

    Notice what is missing from the diagram: no standalone vector database, no separate cache tier for correctness-critical data, no message broker for internal events. Each of those can be added later for scale, but none is required to ship.

    2.2 The Lifecycle of a Single Chat Turn

    Tracing one request through the stack makes the layering concrete. A user sends "What is our refund policy for enterprise customers?" Here is what happens, in order, with timings from a typical production deployment:

  • → 0–5 ms — Authenticate and set context. The API validates the JWT, resolves the tenant, and checks out a pooled SqlClient connection. sp_set_session_context stamps the tenant ID so row-level security applies to every subsequent statement on that connection.
  • → 5–15 ms — Quota check. A single indexed lookup against a quotas table verifies the tenant has not exhausted its monthly token budget. Denied requests fail fast here, before any LLM spend.
  • → 15–250 ms — Embed the query. The API calls the embedding model. This is the first network hop outside your infrastructure and usually the largest fixed cost in the pipeline after the LLM call itself.
  • → 250–300 ms — Hybrid retrieval. usp_hybrid_search runs the vector arm (VECTOR_DISTANCE over the DiskANN index) and the full-text arm (CONTAINSTABLE), fuses the rankings, and returns the top chunks — all tenant-filtered by the security policy.
  • → 300–320 ms — Load conversation history. The last N messages come from the messages table, ordered by creation time. A covering index on (conversation_id, created_at) keeps this at single-digit milliseconds.
  • → 320–2500 ms — LLM call. The prompt (system instructions + retrieved context + history + user message) goes to the model. This dominates wall-clock time; everything else in the pipeline exists to make this call as effective as possible.
  • → 2500–2540 ms — Persist atomically. User message, assistant message, token accounting, quota decrement, and audit log row commit in one transaction. Service Broker emits the post-commit event for downstream consumers.

    • Two observations fall out of this trace. First, the database is on the critical path three times (quota, retrieval, persist) and each visit is tens of milliseconds — the database is never the bottleneck when indexed correctly. Second, the LLM call is 80%+ of latency, which means retrieval quality (getting the right context) matters far more than retrieval speed for end-user experience.

    2.3 Where Each Piece Runs: On-Prem, Container, Azure

    The same T-SQL runs in three deployment shapes. Choosing between them is an operational decision, not an application rewrite:

  • → SQL Server 2025 on your own hardware or VM. Full control, bring your own GPUs for ML Services scoring, predictable cost at scale. You own backups, patching, and high availability (Always On availability groups).
  • → SQL Server 2025 in containers. The mcr.microsoft.com/mssql/server:2025-latest image from Chapter 1. Ideal for development and CI; viable in production on Kubernetes with persistent volumes, though availability-group orchestration takes real effort.
  • → Azure SQL Database / Managed Instance. Automated backups with point-in-time restore, built-in HA, serverless auto-pause for dev workloads, Hyperscale for very large vector corpora. The VECTOR type and vector indexes are available in Azure SQL Database, so the schema from Chapter 1 deploys unchanged.

    • The recommended progression is: containers for local development, Azure SQL Database serverless for staging and early production, then Hyperscale or Managed Instance (or self-hosted) as data volume and compliance requirements grow. Because the application talks to all three through the same TDS protocol and the same T-SQL, environment promotion is a connection-string change.

    2.4 The Embedding Pipeline as a First-Class Citizen

    Embeddings are the bridge between the reasoning layer and the retrieval layer, and they deserve the same engineering rigor as any other data pipeline. A production embedding pipeline has four stages:

  • → Chunking. Splitting documents into retrievable units (Chapter 14). Chunk boundaries determine retrieval granularity; overlap preserves context across boundaries.
  • → Embedding. Calling the embedding model in batches. Batch size, retry policy, and rate-limit handling live here.
  • → Storage. Writing vectors into VECTOR columns transactionally alongside their source text and metadata.
  • → Indexing. The DiskANN vector index makes new vectors searchable. Unlike some systems, SQL Server's vector index handles incremental inserts without a full rebuild.

    • Model versioning cuts across all four stages: the embedding_model column from Chapter 1 exists because vectors from different models live in different geometric spaces and cannot be compared. The pipeline must never mix models within a single searchable set — a constraint best enforced with a filtered index or check constraint, not application discipline.

    -- Guardrail: one embedding model per tenant corpus at a time.
-- The filtered unique index below permits exactly one "active" model
-- per tenant; flip the flag only after the re-embed completes.
ALTER TABLE dbo.document_chunks
    ADD embedding_active BIT NOT NULL DEFAULT 1;

CREATE UNIQUE INDEX UQ_chunks_active_model
    ON dbo.document_chunks(tenant_id, embedding_model)
    WHERE embedding_active = 1;

    2.5 Caching Strategy Across the Stack

    AI applications have three distinct cacheable surfaces, each with different invalidation semantics:

  • → Embedding cache. The mapping from text to vector is deterministic per model. Cache embeddings by SHA2_256(text + model) in a table; repeated queries for the same question skip the embedding API call entirely. This is a correctness-safe cache — the value never changes.
  • → Retrieval cache. The mapping from (query vector, filters) to chunk lists changes whenever the corpus changes. Cache with a short TTL or invalidate via Change Tracking on the chunks table (Chapter 34).
  • → Completion cache. The mapping from prompt to LLM response. Exact-match caching saves the most money but risks stale answers; semantic caching (match on similar prompts via vector search) trades precision for hit rate. Both live naturally in SQL Server tables keyed by request hash or vector.
    • -- Embedding cache: deterministic, never stale for a fixed model
CREATE TABLE dbo.embedding_cache (
    cache_key   CHAR(64) PRIMARY KEY,      -- SHA2_256(model + NUL + text)
    model       NVARCHAR(100) NOT NULL,
    embedding   VECTOR(1536) NOT NULL,
    created_at  DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);

-- Lookup-or-compute pattern in T-SQL
CREATE OR ALTER PROCEDURE dbo.usp_get_embedding
    @model NVARCHAR(100), @text NVARCHAR(MAX), @embedding VECTOR(1536) OUTPUT
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @key CHAR(64) =
        CONVERT(CHAR(64), HASHBYTES('SHA2_256', @model + NCHAR(0) + @text), 2);
    SELECT @embedding = embedding FROM dbo.embedding_cache WHERE cache_key = @key;
    -- Caller computes the embedding on NULL and calls usp_put_embedding.
END;
GO

    2.6 Build-vs-Buy Decisions Per Layer

    For each layer, the pragmatic default is:

  • → LLM: buy. Use Azure OpenAI or a managed model API. Self-hosting a frontier-class model is a research project, not an infrastructure decision. Reserve self-hosting for small classification or embedding models where latency and data-residency demand it.
  • → Embeddings: buy the API, own the storage. Call a managed embedding API, but store the vectors in your own SQL Server. This keeps you portable across embedding providers — re-embedding is expensive, so the vectors are the asset.
  • → Retrieval and system of record: build on SQL Server. This is the thesis of the book. The moat of an AI application is its data model — tenants, permissions, history, feedback — and that moat lives in your schema, not in a vendor's API.
  • → Observability: buy the platform, own the data. Ship traces and metrics to your observability platform, but keep the raw audit rows in SQL Server (Chapter 36). The raw rows are what let you answer "what exactly did the model see?" during an incident.

    • The unifying principle: own everything that is a durable asset (vectors, history, feedback, audit trails) and rent everything that is fungible compute (model inference, embedding calls). SQL Server is where the durable assets live.

    ---

    Key Takeaways

  • → The stack has three layers — reasoning, retrieval, system of record — and the last two are the same SQL Server database. Collapsing retrieval and system-of-record into one engine eliminates distributed transactions from the hottest paths in the application.
  • → A single chat turn touches SQL Server three times and the LLM once; the LLM dominates latency. Optimize retrieval for quality (right context) over raw speed, and keep every database visit indexed and measured in milliseconds.
  • → The same T-SQL runs on-prem, in containers, and on Azure SQL. Environment promotion is a connection-string change, which makes the local-to-cloud path genuinely incremental.
  • → Own durable assets, rent fungible compute. Vectors, history, feedback, and audit trails live in your SQL Server; model inference and embedding calls are rented APIs. The embedding cache table is the cheapest latency win in the whole stack.
