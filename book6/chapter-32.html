Conversation Versioning and Edit History

Users edit their messages. They regenerate assistant responses. They branch a conversation to try a different direction. Each of these creates versions — and versions need storage, semantics, and UI. This chapter builds the versioning model: message edits as version chains, regenerations as sibling branches, conversation forks as first-class objects, and the retention policy that keeps version history from growing unbounded. The goal: users can always go back, the database always knows which version is current, and nothing the model saw is ever silently rewritten.

---

32.1 Message Edits: Version Chains, Not Overwrites

When a user edits a sent message, never UPDATE the row in place. The original message is part of the audit trail (§24) — the model may have already responded to it, and rewriting history corrupts both forensics and the conversation's causal chain. Append a new version instead:

-- Versions live alongside messages; the message row points at "current"
ALTER TABLE dbo.messages
    ADD version_number INT NOT NULL DEFAULT 1,
        superseded_by UNIQUEIDENTIFIER NULL;   -- the edit that replaced this

CREATE TABLE dbo.message_versions (
    version_id   UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    message_id   UNIQUEIDENTIFIER NOT NULL
                 CONSTRAINT FK_mv_msg REFERENCES dbo.messages(message_id),
    version_number INT NOT NULL,
    content      NVARCHAR(MAX) NOT NULL,
    edited_at    DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    edit_reason  NVARCHAR(200) NULL,
    CONSTRAINT UQ_mv UNIQUE (message_id, version_number)
);

-- Edit: freeze the current content as a version, then update the message
CREATE OR ALTER PROCEDURE dbo.usp_edit_message
    @message_id UNIQUEIDENTIFIER, @new_content NVARCHAR(MAX),
    @edit_reason NVARCHAR(200) = NULL
AS
BEGIN
    SET NOCOUNT ON;
    BEGIN TRAN;
    DECLARE @v INT, @old NVARCHAR(MAX);
    SELECT @v = version_number, @old = content
    FROM dbo.messages WITH (UPDLOCK) WHERE message_id = @message_id;

    INSERT INTO dbo.message_versions (message_id, version_number, content, edit_reason)
    VALUES (@message_id, @v, @old, @edit_reason);

    UPDATE dbo.messages
    SET content = @new_content, version_number = @v + 1,
        updated_at = SYSUTCDATETIME()
    WHERE message_id = @message_id;
    -- Downstream effect: assistant messages AFTER this one were generated
    -- from the old content. Mark them stale (§32.2) rather than deleting.
    UPDATE dbo.messages
    SET is_stale = 1
    WHERE conversation_id = (SELECT conversation_id FROM dbo.messages
                             WHERE message_id = @message_id)
      AND created_at > (SELECT created_at FROM dbo.messages
                        WHERE message_id = @message_id)
      AND role = N'assistant';
    COMMIT;
END;
GO

32.2 Regenerations: Sibling Branches

Regenerating an assistant response creates siblings — multiple candidate answers to the same prompt. Store them as a branch group with one active member:

ALTER TABLE dbo.messages
    ADD branch_group_id UNIQUEIDENTIFIER NULL,  -- siblings share this
        is_active BIT NOT NULL DEFAULT 1,       -- the visible sibling
        is_stale  BIT NOT NULL DEFAULT 0;       -- generated from edited content

-- Regenerate: deactivate current, insert new sibling (same branch group)
CREATE OR ALTER PROCEDURE dbo.usp_regenerate_response
    @message_id UNIQUEIDENTIFIER, @new_content NVARCHAR(MAX)
AS
BEGIN
    SET NOCOUNT ON;
    BEGIN TRAN;
    DECLARE @conv UNIQUEIDENTIFIER, @grp UNIQUEIDENTIFIER, @model NVARCHAR(100);
    SELECT @conv = conversation_id, @model = model,
           @grp = ISNULL(branch_group_id, message_id)
    FROM dbo.messages WITH (UPDLOCK) WHERE message_id = @message_id;

    UPDATE dbo.messages SET is_active = 0
    WHERE branch_group_id = @grp OR message_id = @grp;

    INSERT INTO dbo.messages (conversation_id, role, content, model,
                              branch_group_id, is_active)
    VALUES (@conv, N'assistant', @new_content, @model, @grp, 1);
    COMMIT;
    -- The UI shows the active sibling with ← → navigation; inactive
    -- siblings persist for comparison and for evaluation (§19: which
    -- sibling got the better rating? that's preference data).
END;
GO

Siblings are preference data gold: the user picked one and rejected others — the raw material for RLHF-style training (§30.3's training pairs, extended with chosen/rejected labels).

32.3 Conversation Forks

A fork copies a conversation's history up to a point so the user can try a different direction without losing the original. Implement forks as new conversations sharing history by reference:

ALTER TABLE dbo.conversations
    ADD forked_from_conversation_id UNIQUEIDENTIFIER NULL
        CONSTRAINT FK_conv_fork REFERENCES dbo.conversations(conversation_id),
        forked_at_message_id UNIQUEIDENTIFIER NULL;  -- fork point

-- Fork: new conversation row; history read = original's messages up to the
-- fork point + this conversation's own messages. No copying.
CREATE OR ALTER PROCEDURE dbo.usp_fork_conversation
    @conversation_id UNIQUEIDENTIFIER, @at_message_id UNIQUEIDENTIFIER,
    @title NVARCHAR(200) = NULL
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @new_id UNIQUEIDENTIFIER = NEWID();
    INSERT INTO dbo.conversations (conversation_id, tenant_id, user_id, title,
                                   forked_from_conversation_id, forked_at_message_id)
    SELECT @new_id, tenant_id, user_id,
           ISNULL(@title, title + N' (fork)'),
           @conversation_id, @at_message_id
    FROM dbo.conversations WHERE conversation_id = @conversation_id;

    -- History view: UNION ALL of shared prefix + own messages
    -- (implement as a view or in the replay procedure §6.2)
    SELECT @new_id AS new_conversation_id;
END;
GO
-- Copy-on-write: the fork shares history by reference until the user edits
-- a shared message — then §32.1's version chain records the divergence
-- against the fork's conversation, leaving the original untouched.

Reference-sharing keeps forks cheap (no data duplication); the version chain handles divergence. Deleting the original conversation must not cascade into shared history still referenced by forks — use reference counting or soft deletes (§38.2's erasure rules apply per-conversation).

---

32.4 Retention: Keeping Version History Bounded

Versions accumulate: every edit, every regeneration, every fork. Bound them:

  • → Inactive siblings: keep the active sibling plus the N most recent (N=5 default); older siblings compress to metadata (model, tokens, rating) with content purged — the preference signal survives, the storage doesn't.
  • → Edit versions: retain per the audit policy (§24.1's prompt tier, 90 days) — edits are forensic evidence.
  • → Forks: inherit the conversation retention policy; abandoned forks (no activity in 90 days, never shared) are eligible for cleanup with user notice.

    • The invariant: the user can always navigate back through their own visible history, while the database never grows a version graveyard nobody will ever read.

    ---

    32.5 UI Patterns for Version Navigation

    Version storage (§32.1–32.3) is only half the feature — users need to see and navigate it. Three patterns cover the cases: inline edit affordance (hover reveals "edited" with a timestamp; clicking opens the version diff — old vs new side by side, computed at read time from message_versions); sibling carousel for regenerations (← 2/4 → arrows under the active response, each sibling showing its model and token cost so users learn which models answer them best); and fork graph for power users (a lightweight branch diagram showing where conversations forked — essential when a user has five forks of the same debugging session and can't remember which one had the working answer). Keep the default view clean: versions are progressive disclosure, visible on demand, never cluttering the main reading flow. The rule is that no user should ever wonder "did I already ask this?" — the version UI answers by showing, not by making them remember.

    ---

    Key Takeaways

  • → Never overwrite edited messages: freeze the old content as a version, update the message, and mark downstream assistant messages stale — history is append-only.
  • → Model regenerations as sibling branches with one active member; inactive siblings are preference data for training, not garbage.
  • → Fork by reference, diverge by version chain: shared history costs nothing until edited, and deletes must respect surviving forks.
  • → Bound version growth with sibling limits, audit-aligned edit retention, and abandoned-fork cleanup — navigable history without a version graveyard.
