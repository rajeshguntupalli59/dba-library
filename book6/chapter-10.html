User Preferences and Personalization

Preferences are the highest-value memories in the system: "prefers terse answers," "works in healthcare," "allergic to peanuts," "wants code in Python, not JavaScript." A single preference, correctly applied, improves every future interaction. This chapter builds the preference store — explicit preferences the user states, implicit preferences inferred from behavior, conflict resolution when they disagree, and the injection mechanism that gets preferences into the prompt without bloating it. Preferences are also the most privacy-sensitive data in the system, so the chapter closes with the consent and visibility model.

---

10.1 Explicit vs. Implicit Preferences

Preferences arrive through two channels with very different trust levels:

  • → Explicit: the user says "always answer concisely" or toggles a setting. High confidence, stored verbatim, applied unconditionally.
  • → Implicit: inferred from behavior — the user always asks for Python examples, always dismisses long answers, always converts times to IST. Medium confidence, needs corroboration before being treated as fact.
    • CREATE TABLE dbo.user_preferences (
    preference_id   UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    user_id         UNIQUEIDENTIFIER NOT NULL
                    CONSTRAINT FK_pref_user REFERENCES dbo.users(user_id) ON DELETE CASCADE,
    tenant_id       UNIQUEIDENTIFIER NOT NULL,
    category        NVARCHAR(50) NOT NULL
                    CONSTRAINT CK_pref_category CHECK (category IN
                        (N'communication', N'domain', N'format', N'privacy', N'other')),
    preference_key  NVARCHAR(200) NOT NULL,   -- e.g. 'answer_style', 'code_language'
    preference_value NVARCHAR(MAX) NOT NULL,  -- e.g. 'terse', 'python'
    source          NVARCHAR(20) NOT NULL
                    CONSTRAINT CK_pref_source CHECK (source IN (N'explicit', N'inferred')),
    confidence      DECIMAL(3,2) NOT NULL DEFAULT 1.00,  -- 1.0 for explicit
    observations    INT NOT NULL DEFAULT 1,   -- corroboration count for inferred
    is_active       BIT NOT NULL DEFAULT 1,
    created_at      DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    updated_at      DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    CONSTRAINT UQ_pref_user_key UNIQUE (user_id, preference_key, is_active)
);
CREATE INDEX IX_pref_user_cat ON dbo.user_preferences(user_id, category)
    WHERE is_active = 1;

    The partial unique index on (user_id, preference_key) where active enforces the one-active-value rule: a user has exactly one active answer_style at a time. History of superseded preferences stays in the table with is_active = 0 — useful for understanding preference drift.

    10.2 Inferring Preferences from Behavior

    Inference runs as a background job over recent conversations, looking for repeated patterns. The rules must be conservative — a single observation is noise, three is signal:

    -- Example inference: user consistently asks for a specific code language.
-- Runs nightly over the last 7 days of assistant messages containing code.
WITH code_requests AS (
    SELECT m.conversation_id, c.user_id,
           JSON_VALUE(m.tool_calls, '$[0].function.name') AS tool_used,
           m.content
    FROM dbo.messages AS m
    JOIN dbo.conversations AS c ON c.conversation_id = m.conversation_id
    WHERE m.role = 'user'
      AND m.created_at >= DATEADD(day, -7, SYSUTCDATETIME())
      AND m.content LIKE N'%python%'
)
-- In practice this is an LLM classification job; the SQL identifies
-- candidate conversations and the model confirms the pattern.
-- Promotion rule (in the worker):
--   observations >= 3 AND no conflicting explicit preference
--   → INSERT inferred preference with confidence 0.6 + observations count

    The promotion rule has two gates: corroboration (≥3 independent observations) and non-conflict (no explicit preference on the same key). Inferred preferences start at confidence 0.6 and gain 0.1 per additional observation week, capped at 0.9 — they never reach 1.0, which is reserved for explicit statements.

    10.3 Conflict Resolution

    Preferences conflict. The user said "terse answers" in January but has been asking follow-up "explain more" questions all March. Resolution rules, in priority order:

  • → Explicit beats inferred, always. An explicit statement is a deliberate act; inference is a guess. Never let an inferred preference override an explicit one on the same key.
  • → Newer explicit beats older explicit. Supersede the old row (is_active = 0), insert the new one. People change.
  • → Contradictory inferred preferences decay each other. If behavior supports both "terse" and "detailed," reduce both confidences — the truth is probably "it depends on topic," which is a refinement, not a contradiction.
    • CREATE OR ALTER PROCEDURE dbo.usp_set_preference
    @user_id UNIQUEIDENTIFIER, @tenant_id UNIQUEIDENTIFIER,
    @category NVARCHAR(50), @key NVARCHAR(200), @value NVARCHAR(MAX),
    @source NVARCHAR(20) = N'explicit'
AS
BEGIN
    SET NOCOUNT ON;
    BEGIN TRAN;
    -- Explicit statements retire any active preference on the same key,
    -- including inferred ones.
    IF @source = N'explicit'
        UPDATE dbo.user_preferences
        SET is_active = 0, updated_at = SYSUTCDATETIME()
        WHERE user_id = @user_id AND preference_key = @key AND is_active = 1;

    INSERT INTO dbo.user_preferences
        (user_id, tenant_id, category, preference_key, preference_value,
         source, confidence)
    VALUES (@user_id, @tenant_id, @category, @key, @value,
            @source, CASE WHEN @source = N'explicit' THEN 1.00 ELSE 0.60 END);
    COMMIT;
END;
GO

    10.4 Injecting Preferences into the Prompt

    Preferences must reach the model without consuming the context budget. The technique: compile active preferences into a compact "user profile" block, cached per user and invalidated on preference change:

    CREATE OR ALTER PROCEDURE dbo.usp_get_user_profile_block
    @user_id UNIQUEIDENTIFIER
AS
BEGIN
    SET NOCOUNT ON;
    -- One row per category, compact "key: value" lines
    SELECT category,
           STRING_AGG(preference_key + ': ' + preference_value,
                       '; ') WITHIN GROUP (ORDER BY preference_key) AS block
    FROM dbo.user_preferences
    WHERE user_id = @user_id AND is_active = 1
      AND (source = N'explicit' OR confidence >= 0.7)
    GROUP BY category;
END;
GO
-- Rendered into the system prompt as:
--   [User profile — communication] answer_style: terse; greeting: none
--   [User profile — format] code_language: python; units: metric
-- Typical cost: 30-60 tokens. Highest ROI tokens in the entire prompt.

    The confidence gate (≥0.7 for inferred) keeps half-baked inferences out of the prompt. Cache the rendered block per user with a version counter incremented by usp_set_preference — profile blocks change rarely and are read on every turn.

    10.5 Consent and Visibility

    Preferences are surveillance-adjacent: the system watches behavior and writes down conclusions. The consent model must be explicit:

  • → Show users what you inferred. A "What the assistant knows about you" page listing every active preference with its source. Inferred preferences get a confirm/dismiss control — dismissal sets is_active = 0 and blocks re-inference of that key for 90 days.
  • → Category-level opt-out. A user can disable inference entirely while keeping explicit preferences. Store the opt-out on the users table, checked by the inference job.
  • → Export and delete with the user record. Preferences are personal data under GDPR — the Chapter 38 deletion procedure must cover this table, including the inactive history rows.

    • ---

    10.6 Preference Expiry: Tastes Change

    Preferences rot faster than facts. A user's "concise answers" preference from onboarding may not survive their first complex debugging session; a saved "Python 3.10" may be two versions stale. Give learned preferences a time-to-live: high-confidence explicit preferences last a year, inferred preferences decay in 90 days without reinforcement, and every applied preference carries its age so the model can hedge ("you usually prefer concise answers — want the detailed version this time?"). Expiry is not deletion — expired preferences move to a history table where they remain visible in the preference UI (§10.5) and can be reactivated with one click. The alternative is a personalization system that confidently serves who the user was two years ago.

    ---

    Key Takeaways

  • → Separate explicit from inferred preferences, with confidence and corroboration counts on inferred rows. Promote inference to fact only after ≥3 independent observations and no conflicting explicit preference.
  • → Enforce one active value per key with a partial unique index; supersede instead of deleting. Preference history reveals drift that current values hide.
  • → Compile preferences into a compact cached profile block in the system prompt. At 30–60 tokens, these are the highest-ROI tokens in the prompt — but gate inferred preferences on confidence.
  • → Make inference visible and revocable. A "what the assistant knows" page, per-key dismissal with a cooling-off period, and category-level opt-out are not optional features — they are the consent model.
