Memory Isolation and Row-Level Security

Chapters 6–11 built a rich memory system. Now the hard question: how do you guarantee that User A's memories never leak into User B's conversations? In a multi-tenant AI application, a memory leak is not a bug — it is a data breach. This chapter builds isolation as a layered defense: row-level security as the enforcement backbone, session context as the identity carrier, application-level checks as the first line, and the audit and testing practices that prove isolation holds. The principle is defense in depth: no single layer is trusted alone.

---

12.1 The Threat Model

Memory leaks happen through four paths, each needing its own mitigation:

  • → Query leakage. A missing WHERE user_id = ? returns another user's memories. Mitigation: RLS policies that make the filter automatic.
  • → Retrieval leakage. Vector search returns chunks or memories from another tenant because the ANN query lacked a tenant predicate. Mitigation: tenant predicates composed with vector ordering (Chapter 15), enforced by RLS.
  • → Prompt leakage. Correctly retrieved memories for User A get injected into User B's prompt because of a session mix-up. Mitigation: session binding validated on every turn (§12.3).
  • → Inference leakage. The model itself reveals memorized training-adjacent data. Mitigation: this is a model-behavior problem — keep sensitive data out of prompts sent to shared models, and prefer Azure OpenAI's data-residency commitments for regulated workloads.

    12.2 RLS Policies Across Every Memory Table

    Chapter 1 put RLS on chunks and documents. Extend the same pattern to every memory-bearing table — messages, sessions, long-term memories, preferences, summaries, embeddings:

    -- One predicate function per identity grain, then one policy per table.
-- Tenant grain (shared within a tenant's support staff, for example):
CREATE FUNCTION security.fn_tenant_filter(@tenant_id UNIQUEIDENTIFIER)
RETURNS TABLE WITH SCHEMABINDING
AS RETURN SELECT 1 AS access
           WHERE @tenant_id = CAST(SESSION_CONTEXT(N'tenant_id') AS UNIQUEIDENTIFIER);
GO

-- User grain (strictest: the user sees only their own rows)
CREATE FUNCTION security.fn_user_filter(@user_id UNIQUEIDENTIFIER)
RETURNS TABLE WITH SCHEMABINDING
AS RETURN SELECT 1 AS access
           WHERE @user_id = CAST(SESSION_CONTEXT(N'user_id') AS UNIQUEIDENTIFIER);
GO

-- Apply user-grain policies to every memory table
CREATE SECURITY POLICY security.memory_isolation_policy
    ADD FILTER PREDICATE security.fn_user_filter(user_id) ON dbo.messages,
    ADD FILTER PREDICATE security.fn_user_filter(user_id) ON dbo.chat_sessions,
    ADD FILTER PREDICATE security.fn_user_filter(user_id) ON dbo.long_term_memories,
    ADD FILTER PREDICATE security.fn_user_filter(user_id) ON dbo.user_preferences,
    ADD FILTER PREDICATE security.fn_user_filter(user_id) ON dbo.conversation_embeddings,
    ADD FILTER PREDICATE security.fn_tenant_filter(tenant_id) ON dbo.document_chunks,
    ADD FILTER PREDICATE security.fn_tenant_filter(tenant_id) ON dbo.documents
    WITH (STATE = ON);
GO

    Note the two grains: user-grain for personal memory tables, tenant-grain for the shared knowledge corpus. Support staff who need cross-user visibility get a separate login whose session context carries an is_support flag checked by a second predicate — never by disabling the policy.

    12.3 Session Binding: Tying Every Turn to Its Identity

    RLS enforces the database boundary, but the application must still bind each request to the right identity before the first query. The binding check runs at the top of every chat request:

    -- Validate that the session belongs to the authenticated user
-- AND the conversation belongs to that session, in one query.
-- Returns the tenant for SESSION_CONTEXT; raises if anything mismatches.
CREATE OR ALTER PROCEDURE dbo.usp_bind_session
    @session_id UNIQUEIDENTIFIER,
    @auth_user_id UNIQUEIDENTIFIER
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @tenant_id UNIQUEIDENTIFIER;

    SELECT @tenant_id = s.tenant_id
    FROM dbo.chat_sessions AS s
    WHERE s.session_id = @session_id
      AND s.user_id = @auth_user_id      -- the binding check
      AND s.status <> N'closed';

    IF @tenant_id IS NULL
        THROW 50002, 'Session binding failed: session does not belong to user.', 1;

    -- Stamp BOTH identities for the RLS predicates
    EXEC sp_set_session_context 'tenant_id', @tenant_id;
    EXEC sp_set_session_context 'user_id', @auth_user_id;

    -- Return conversation for the caller
    SELECT s.conversation_id, s.model, s.system_prompt_version,
           s.status, s.turn_count
    FROM dbo.chat_sessions AS s
    WHERE s.session_id = @session_id;
END;
GO

    This procedure is the choke point: every turn calls it first, and no database work happens before it succeeds. The JWT's subject claim supplies @auth_user_id — never a client-supplied user ID from the request body.

    12.4 The Application Layer: Belt and Suspenders

    RLS is the enforcement layer, but application code should still pass explicit predicates — not because RLS might fail, but because explicit predicates make queries sargable and intent obvious. The rule: every query includes the identity predicate AND relies on RLS as the backstop. Code review rejects any data-access query missing the explicit user_id/tenant_id filter, even though RLS would technically enforce it.

    Additionally, separate database principals by role: the API's login gets only EXECUTE on procedures and the RLS-filtered table access it needs; the background workers get their own login; human support staff get a third with the support predicate. A compromised API credential then cannot disable policies or read across users — it lacks the permissions.

    -- Least-privilege roles: the API login cannot touch RLS or other users' rows
CREATE ROLE api_role;
GRANT EXECUTE ON SCHEMA::dbo TO api_role;
-- Table access is filtered by the security policy automatically;
-- DENY direct writes to memory tables so all writes go through procedures:
DENY INSERT, UPDATE, DELETE ON dbo.long_term_memories TO api_role;
DENY INSERT, UPDATE, DELETE ON dbo.user_preferences TO api_role;
-- Writes flow through usp_append_message / usp_set_preference, which
-- re-validate identity. The API login cannot bypass them.

    12.5 Proving Isolation: The Adversarial Test Suite

    Isolation is a claim; tests make it a fact. The adversarial suite runs in CI against a realistic seed dataset:

  • → Cross-user read attempts. For every memory procedure, call it as User A with User B's IDs — expect zero rows or an error, never User B's data. Parameterize over all procedures.
  • → Missing-context simulation. Open a connection, deliberately skip usp_bind_session, and query memory tables — RLS must return zero rows (NULL context matches nothing).
  • → Vector-search isolation. Seed two tenants with similar documents; verify usp_hybrid_search as Tenant A never returns Tenant B's chunks, even for near-identical query vectors.
  • → Session-fixation attempts. Present User B's session ID with User A's token — usp_bind_session must throw.
    • -- T-SQL smoke test: no session context → RLS returns nothing
-- (run as the api_role login in CI)
EXEC sp_set_session_context 'tenant_id', NULL;
EXEC sp_set_session_context 'user_id', NULL;
SELECT COUNT(*) AS rows_visible FROM dbo.long_term_memories;
-- Expected: 0. If this ever returns nonzero, the policy is broken.
SELECT COUNT(*) AS chunks_visible FROM dbo.document_chunks;
-- Expected: 0.

    Run the full suite on every migration that touches a memory table or a security policy. Isolation regressions are silent — no error, just wrong rows — so only tests catch them.

    ---

    Key Takeaways

  • → Treat memory leakage as a data breach, and defend in four layers: RLS policies (enforcement), session binding (identity), explicit application predicates (intent + sargability), and least-privilege roles (blast radius).
  • → Use two RLS grains: user-grain for personal memory tables, tenant-grain for the shared corpus — with a separate support predicate rather than policy exceptions.
  • → Make usp_bind_session the choke point of every turn: validate session ownership from the JWT subject, stamp both identities into SESSION_CONTEXT, and do no database work before it succeeds.
  • → Prove isolation with an adversarial CI suite covering cross-user reads, missing context, vector-search tenant separation, and session fixation — because isolation regressions are silent.
