Efficient Vector Retrieval at Scale

Ingestion determines what can be found; query-time retrieval determines what is found — and how fast. This chapter is the performance and quality manual for the retrieval path: writing vector queries the optimizer can accelerate, tuning the recall/latency tradeoff of the DiskANN index, pre-filtering vs. post-filtering for metadata constraints, the oversample-and-rerank pattern, and diagnosing retrieval problems with execution plans and DMVs. Every millisecond here multiplies across thousands of chat turns per hour.

---

15.1 Anatomy of an Efficient Vector Query

The canonical pattern from §3.2, annotated with what the optimizer needs:

DECLARE @q VECTOR(1536) = CAST(@query_json AS VECTOR(1536));

SELECT TOP (@k)
    chunk_id, document_id, chunk_index, content,
    VECTOR_DISTANCE('cosine', embedding, @q) AS distance
FROM dbo.document_chunks
WHERE tenant_id = @tenant_id        -- (1) selective relational predicate
  AND embedding IS NOT NULL         -- (2) excludes un-embedded rows
  AND is_active = 1                 -- (3) any other cheap filters
ORDER BY VECTOR_DISTANCE('cosine', embedding, @q);  -- (4) matches index metric
-- Requirements for index use:
--   * ORDER BY expression exactly matches the indexed VECTOR_DISTANCE call
--   * metric ('cosine') matches the CREATE VECTOR INDEX metric
--   * TOP(@k) present — the index is a top-k structure, not a sort

Verify index usage with the actual execution plan: look for the vector index seek operator. If you see a clustered index scan with a sort, one of the four requirements is violated — most commonly a metric mismatch or the ORDER BY expression differing subtly from the indexed expression (e.g., different argument order).

15.2 Pre-Filtering vs. Post-Filtering

Metadata constraints ("only docs from the last 90 days," "only the contracts folder") interact with ANN search in two ways:

  • → Pre-filtering: apply the relational predicate first, then ANN-search within the filtered set. Correct and precise, but the ANN graph was built over the full corpus — heavily filtered queries may find too few candidates in the pruned subgraph.
  • → Post-filtering: ANN-search the full corpus for oversampled candidates (e.g., top 100), then apply the filter. Better recall when filters are selective, but wasteful when the filter eliminates most candidates.

    • The rule of thumb: if the filter selects more than ~5% of the corpus, pre-filter; if less, post-filter with oversampling. SQL Server's approach — relational predicates in the WHERE clause composed with the vector ORDER BY — effectively pre-filters, which is correct for the tenant predicate (always selective enough in multi-tenant corpora) and for most metadata filters in this book. For extremely selective filters (a single document out of millions), skip the vector index entirely and brute-force within the filtered set:

    -- Extremely selective filter: brute force beats the index
-- (a few hundred rows; the graph walk overhead isn't worth it)
SELECT TOP (@k) chunk_id, content,
       VECTOR_DISTANCE('cosine', embedding, @q) AS distance
FROM dbo.document_chunks
WHERE document_id = @single_doc     -- ultra-selective: hundreds of rows
  AND embedding IS NOT NULL
ORDER BY VECTOR_DISTANCE('cosine', embedding, @q);
-- The optimizer chooses a scan + sort here; that's the right plan.
-- Don't fight it with index hints.

    15.3 Oversample and Rerank

    ANN search is approximate; the top-8 by cosine distance is not always the best-8 for the user's question. The production pattern: oversample cheaply, rerank expensively.

  • → Stage 1 — ANN oversample: retrieve top 50–100 by VECTOR_DISTANCE. Milliseconds, approximate.
  • → Stage 2 — RRF fusion: merge with the full-text arm's top 50–100 (Chapter 1's procedure already does this).
  • → Stage 3 — cross-encoder rerank (optional): score the top 20–30 candidates with a dedicated reranking model (Cohere Rerank, or a self-hosted cross-encoder). 50–200 ms for dramatically better ordering on hard queries.
    • # Stage 3 rerank in Python (only when the query warrants it)
def retrieve_with_rerank(question, qvec, tenant_id, k_final=8):
    # Stages 1+2: oversampled hybrid search from SQL Server
    candidates = hybrid_search(tenant_id, question, qvec, k=60)
    if len(candidates) < 20 or is_simple_question(question):
        return candidates[:k_final]   # skip rerank: not worth the latency
    # Stage 3: cross-encoder rerank of the top 30
    texts = [c.content for c in candidates[:30]]
    scores = rerank_model.score(question, texts)  # e.g. Cohere Rerank API
    ranked = sorted(zip(candidates[:30], scores),
                    key=lambda x: x[1], reverse=True)
    return [c for c, _ in ranked[:k_final]]

    Gate the rerank on query complexity — simple factual questions rarely benefit, while ambiguous multi-hop questions often do. Log the rerank delta (how much the ordering changed) to decide whether the stage earns its latency.

    15.4 Tuning Recall vs. Latency

    The DiskANN search exposes the candidate list size ("search list") as the recall/latency knob: larger lists explore more of the graph (higher recall, higher latency). Tune it empirically:

  • → Build a recall benchmark. Sample 200 representative queries; compute brute-force top-10 (exact) and index top-10; recall = overlap / 10. Store this as a scheduled job — recall drifts as the corpus grows.
  • → Set per-workload search lists. Interactive chat wants p95 under 100 ms even at 95% recall; nightly evaluation harnesses can afford 500 ms for 99% recall. Different callers, different settings.
  • → Watch the tradeoff curve, not a single point. Plot recall vs. p95 latency across search-list sizes; the knee of the curve is your operating point. Re-plot quarterly or after large ingestions.

    15.5 Diagnosing Retrieval Problems

    When users report "the assistant can't find things," work through this checklist:

  • → Is the content in the corpus? Query dbo.documents for the expected document and dbo.ingest_log for its ingestion status. Half of "retrieval failures" are ingestion failures.
  • → Is it embedded? Check embedding IS NOT NULL and embedding_model on the expected chunks. A failed embed stage leaves NULLs that the query silently excludes.
  • → Does brute force find it? Run the exact VECTOR_DISTANCE ORDER BY without TOP (or with a huge TOP) and see where the expected chunk ranks. If brute force ranks it #3 but the index missed it, widen the search list. If brute force ranks it #200, the problem is chunking or the embedding model — not the index.
  • → Is the query the problem? Try the rewritten standalone query (§13.3) and key phrases from the expected chunk. Vague questions retrieve vaguely — sometimes the fix is query rewriting, not index tuning.
  • → Check the plan. Actual execution plan on the retrieval procedure: vector index seek present? Predicate pushed before the ANN walk? Stale statistics on the chunks table can mislead the optimizer after bulk ingestions — UPDATE STATISTICS after large loads.
    • -- Brute-force rank check: where SHOULD the expected chunk have ranked?
DECLARE @q VECTOR(1536) = CAST(@query_json AS VECTOR(1536));
WITH ranked AS (
    SELECT chunk_id,
           ROW_NUMBER() OVER (
               ORDER BY VECTOR_DISTANCE('cosine', embedding, @q)) AS brute_rank
    FROM dbo.document_chunks
    WHERE tenant_id = @tenant_id AND embedding IS NOT NULL
)
SELECT brute_rank FROM ranked WHERE chunk_id = @expected_chunk_id;
-- brute_rank <= 10 but index missed it → widen search list
-- brute_rank = 347 → chunking/embedding problem, not an index problem

    Key Takeaways

  • → Match the ORDER BY expression and metric exactly to the vector index definition, always use TOP, and keep selective relational predicates in the WHERE clause. Verify with the actual execution plan.
  • → Pre-filter for normal metadata constraints; post-filter with oversampling for ultra-selective ones; brute-force when the filter leaves only hundreds of rows. Let the optimizer choose — don't hint it into a bad plan.
  • → Oversample with ANN, fuse with RRF, rerank the top candidates with a cross-encoder only when query complexity justifies the latency. Log the rerank delta to keep the stage honest.
  • → Diagnose retrieval failures bottom-up: corpus → embedded → brute-force rank → query quality → execution plan. Most "search is broken" reports are ingestion gaps or chunking problems, not index problems.
