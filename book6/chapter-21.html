MCP and SQL Server: Direct AI Access to Your Database

The Model Context Protocol (MCP) standardizes how AI applications connect to data sources: instead of every app writing bespoke database integrations, an MCP server exposes your database's capabilities — schema, queries, procedures — over a uniform protocol that any MCP client (Claude, IDE assistants, agent frameworks) can consume. This chapter builds an MCP server over SQL Server: exposing safe read tools, the schema-introspection resources, the security model that keeps "direct AI access" from becoming "unrestricted AI access," and the operational practices for running MCP in production.

---

21.1 What MCP Gives You

Without MCP, each AI client needs custom code to reach your database: connection handling, schema discovery, query execution, result formatting. With MCP, you write one server that exposes:

  • → Tools: callable functions like run_report, lookup_customer — the same stored-procedure tools from Chapter 20, now protocol-accessible.
  • → Resources: readable data like schema://tables/orders — the model's way of discovering what exists.
  • → Prompts: pre-built prompt templates like analyze_churn that encode your team's analytical best practices.

    • The MCP server in this chapter is a Python process using the MCP SDK, with pyodbc underneath — the same data-access layer as the rest of the book, so the security model (RLS, least-privilege logins, procedure-only access) carries over unchanged.

    21.2 Building the MCP Server

    # mcp_server.py — MCP server over SQL Server
# Dependencies: pip install mcp pyodbc
import json
import pyodbc
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("sqlserver-ai")
CONN_STR = ("DRIVER={ODBC Driver 18 for SQL Server};SERVER=localhost,1433;"
            "DATABASE=aiapp;UID=mcp_reader;PWD=secret;TrustServerCertificate=yes;")
# NOTE: mcp_reader is a least-privilege login: EXECUTE on whitelisted
# procedures only, RLS policies applied. See §21.4.

def q(proc: str, *params):
    with pyodbc.connect(CONN_STR) as conn:
        cur = conn.cursor()
        # Tenant/user context comes from the MCP session (authenticated caller)
        cur.execute("EXEC sp_set_session_context 'tenant_id', ?", TENANT.get())
        cur.execute("EXEC sp_set_session_context 'user_id', ?", USER.get())
        rows = cur.execute(f"EXEC {proc} " + ",".join("?" * len(params)),
                           *params).fetchall()
        cols = [c[0] for c in cur.description]
        return [dict(zip(cols, r)) for r in rows]

@mcp.tool()
def lookup_orders(status: str = None, max_rows: int = 20) -> str:
    """Look up the caller's orders, optionally filtered by status."""
    rows = q("dbo.tool_lookup_orders", TENANT.get(), USER.get(),
             status, None, max_rows, None)
    return json.dumps(rows, default=str)

@mcp.tool()
def hybrid_search(question: str, k: int = 8) -> str:
    """Semantic + keyword search over the knowledge base."""
    import openai
    vec = openai.OpenAI().embeddings.create(
        model="text-embedding-3-small", input=question).data[0].embedding
    rows = q("dbo.usp_hybrid_search", TENANT.get(), question,
             json.dumps(vec), k)
    return json.dumps(rows, default=str)

@mcp.resource("schema://tables/{table}")
def table_schema(table: str) -> str:
    """Column definitions for a whitelisted table."""
    if table not in {"orders", "documents", "conversations"}:
        raise ValueError("Table not exposed via MCP")
    with pyodbc.connect(CONN_STR) as conn:
        rows = conn.execute("""
            SELECT COLUMN_NAME, DATA_TYPE, IS_NULLABLE
            FROM INFORMATION_SCHEMA.COLUMNS
            WHERE TABLE_SCHEMA = 'dbo' AND TABLE_NAME = ?
            ORDER BY ORDINAL_POSITION""", table).fetchall()
        return json.dumps([{"column": r[0], "type": r[1],
                            "nullable": r[2]} for r in rows])

@mcp.prompt()
def analyze_churn() -> str:
    """Best-practice prompt for churn analysis over the orders schema."""
    return ("Analyze customer churn using the orders table. "
            "1) Call lookup_orders for recent cancelled orders. "
            "2) Summarize cancellation patterns by product line. "
            "3) Never reveal other customers' data.")

if __name__ == "__main__":
    mcp.run()

    Three design decisions are load-bearing. First, tools wrap stored procedures — never raw SQL. Second, the resource allowlist ({"orders", "documents", "conversations"}) is explicit; schema discovery does not mean schema exposure. Third, session context is stamped per MCP session from the authenticated caller — the same RLS enforcement as every other path.

    21.3 Text-to-SQL Through MCP: Guardrailed Generation

    MCP clients will ask to "run a query." The safe answer is a text-to-SQL tool with guardrails, not an open query endpoint:

  • → Generate against the allowlisted schema only — the model sees the resource schemas from §21.2, nothing else.
  • → Validate the generated SQL before execution: parse it, reject anything that is not a single SELECT (no INSERT/UPDATE/DELETE/DROP/EXEC), reject access to non-allowlisted tables, enforce TOP.
  • → Execute as the least-privilege login with RLS active — the final backstop if validation misses something.
    • @mcp.tool()
def ask_data(question: str) -> str:
    """Answer a data question by generating and running a safe SELECT."""
    sql = llm_generate_sql(question, ALLOWED_SCHEMAS)  # Chapter 22
    validate_select_only(sql, ALLOWED_TABLES)          # raises on violation
    sql = enforce_top(sql, 100)
    with pyodbc.connect(CONN_STR) as conn:
        stamp_context(conn)
        rows = conn.execute(sql).fetchall()
        return json.dumps([dict(zip([c[0] for c in conn.description], r))
                           for r in rows], default=str)

    Chapter 22 covers the generation side in depth; the MCP chapter's contribution is the execution sandbox around it.

    21.4 The Security Model

    "Direct AI access to your database" sounds alarming because, done naively, it is. The layered model:

  • → Authentication at the MCP transport. The MCP client authenticates (OAuth/API key); the server maps the identity to tenant_id/user_id. Anonymous MCP access to production data is never acceptable.
  • → Least-privilege SQL login per MCP deployment. mcp_reader gets EXECUTE on whitelisted procedures and nothing else. A separate mcp_writer exists only if write tools are exposed — most deployments are read-only.
  • → RLS on every table (§12.2) — the model cannot query its way across tenants even with a valid session.
  • → Audit everything. Every MCP tool call logs to dbo.llm_audit_log (or the agent action log for agentic clients) with the MCP session ID. "The AI looked at what?" must always be answerable.
    • -- MCP reader login: procedure-only access, RLS-enforced reads
CREATE LOGIN mcp_reader WITH PASSWORD = '...';
CREATE USER mcp_reader FOR LOGIN mcp_reader;
CREATE ROLE mcp_read_role;
ALTER ROLE mcp_read_role ADD MEMBER mcp_reader;
GRANT EXECUTE ON dbo.tool_lookup_orders TO mcp_read_role;
GRANT EXECUTE ON dbo.usp_hybrid_search TO mcp_read_role;
GRANT EXECUTE ON dbo.usp_filtered_vector_search TO mcp_read_role;
-- No direct table SELECT grants: all reads flow through procedures,
-- and RLS policies filter every row by the stamped session context.

    21.5 Running MCP in Production

  • → Rate-limit per MCP client (Chapter 25's quota procedures apply — MCP tool calls consume the same token/row budgets).
  • → Version your tool contracts. Tools are an API; changing a procedure signature breaks deployed clients. Version tools (lookup_orders_v2) and deprecate, don't mutate.
  • → Monitor tool-call patterns for anomalies — a client calling ask_data in a tight loop is either a runaway agent or an exfiltration attempt; alert on both.
  • → Test with the adversarial suite from §12.5, extended to MCP: cross-tenant tool calls, schema resources for non-allowlisted tables, and SQL-injection attempts through the text-to-SQL tool.

    Key Takeaways

  • → An MCP server over SQL Server exposes tools (procedures), resources (allowlisted schemas), and prompts (analytical templates) — one integration that every MCP client can consume.
  • → Tools wrap stored procedures, never raw SQL; text-to-SQL goes through generate → validate (SELECT-only, allowlisted tables, enforced TOP) → execute as a least-privilege login.
  • → Security is four layers: authenticated MCP transport mapped to tenant/user, least-privilege SQL logins, RLS on every table, and complete audit logging of every tool call.
  • → Operate MCP like an API: rate limits, versioned tool contracts, anomaly monitoring on call patterns, and the adversarial test suite extended to the MCP surface.
