Observability: DMVs, Query Store, and AI Metrics

You cannot operate what you cannot see. AI applications add a new observability dimension on top of the classic database one: alongside query performance and resource pressure, you must watch token spend, model latency, retrieval quality, and agent behavior. SQL Server's native observability — Dynamic Management Views and Query Store — covers the database half; the audit and metrics tables from earlier chapters cover the AI half. This chapter unifies them into one operational picture.

---

36.1 DMVs for AI Workload Health

The DMVs that matter most for AI workloads are the ones around the three bottlenecks: vector search CPU, connection pool pressure, and blocking on hot rows:

-- 1) What is the vector search costing? Top queries by CPU.
SELECT TOP 10
    qs.execution_count,
    qs.total_worker_time / 1000 AS total_cpu_ms,
    qs.total_worker_time / qs.execution_count / 1000 AS avg_cpu_ms,
    SUBSTRING(st.text, 1, 120) AS query_preview
FROM sys.dm_exec_query_stats AS qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS st
WHERE st.text LIKE N'%usp_vector_search%'
ORDER BY qs.total_worker_time DESC;
-- avg_cpu_ms climbing over weeks → the vector index needs attention (§15.3).

-- 2) Connection pressure: waiting tasks and what they're waiting on
SELECT wt.wait_type, COUNT(*) AS waiting_tasks,
       AVG(wt.wait_duration_ms) AS avg_wait_ms
FROM sys.dm_os_waiting_tasks AS wt
GROUP BY wt.wait_type ORDER BY waiting_tasks DESC;
-- LCK_M_X on rate_buckets → bucket row contention (§5.3's hot-row pattern).
-- THREADPOOL → pool exhaustion: add pool capacity or cut held connections.

-- 3) Who is blocking whom right now?
SELECT s.session_id, s.login_name, s.program_name,
       r.blocking_session_id, r.wait_type, r.wait_time,
       SUBSTRING(t.text, 1, 100) AS running_sql
FROM sys.dm_exec_sessions AS s
JOIN sys.dm_exec_requests AS r ON r.session_id = s.session_id
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) AS t
WHERE r.blocking_session_id > 0;

36.2 Query Store: Regression Detection for Generated SQL

Text-to-SQL (§22) and agent tool SQL (§20.2) generate queries the DBA never wrote — which makes plan regressions invisible until users complain. Query Store captures query history and plans automatically:

-- Enable Query Store (on by default in Azure SQL)
ALTER DATABASE aiapp SET QUERY_STORE = ON;
GO

-- Find queries whose performance regressed recently
SELECT q.query_id, p.plan_id,
       rs.avg_duration / 1000 AS avg_duration_ms,
       rs.avg_cpu_time / 1000 AS avg_cpu_ms,
       rs.count_executions,
       q.query_sql_text
FROM sys.query_store_query AS q
JOIN sys.query_store_plan AS p ON p.query_id = q.query_id
JOIN sys.query_store_runtime_stats AS rs ON rs.plan_id = p.plan_id
WHERE rs.runtime_stats_interval_id IN (
        SELECT runtime_stats_interval_id
        FROM sys.query_store_runtime_stats_interval
        WHERE start_time > DATEADD(day, -7, SYSUTCDATETIME()))
ORDER BY rs.avg_duration DESC;
-- For generated SQL: force the good plan (sp_query_store_force_plan) while
-- the prompt/guardrails are fixed — Query Store buys time for the AI layer.

Query Store is also the audit trail for generated SQL: every distinct generated query text is captured with its plans and runtime stats — the DBA can see exactly what the AI asked the database to do, and how often.

36.3 The AI Metrics Layer

Database observability covers the "how fast"; the AI metrics cover the "how well and at what cost." Build them as views over the audit tables:

-- AI operational dashboard: one view, refreshed every 5 minutes
CREATE OR ALTER VIEW dbo.vw_ai_ops_dashboard AS
SELECT
    (SELECT COUNT(*) FROM dbo.llm_audit_log
     WHERE created_at >= DATEADD(hour, -1, SYSUTCDATETIME())) AS llm_calls_last_hour,
    (SELECT SUM(ISNULL(input_cost,0)+ISNULL(output_cost,0))
     FROM dbo.llm_audit_log
     WHERE CAST(created_at AS DATE) = CAST(SYSUTCDATETIME() AS DATE)) AS spend_today,
    (SELECT AVG(CAST(latency_ms AS FLOAT)) FROM dbo.llm_audit_log
     WHERE created_at >= DATEADD(hour, -1, SYSUTCDATETIME())) AS avg_latency_ms_1h,
    (SELECT COUNT(*) FROM dbo.llm_audit_log
     WHERE created_at >= DATEADD(hour, -1, SYSUTCDATETIME())
       AND status != N'ok') AS errors_last_hour,
    (SELECT COUNT(*) FROM dbo.agent_runs
     WHERE started_at >= DATEADD(hour, -1, SYSUTCDATETIME())) AS agent_runs_1h,
    (SELECT AVG(CAST(confidence AS FLOAT)) FROM dbo.retrieval_feedback
     WHERE created_at >= DATEADD(day, -1, SYSUTCDATETIME())) AS avg_retrieval_conf_24h,
    (SELECT COUNT(*) FROM dbo.ai_dead_letters
     WHERE failed_at >= DATEADD(hour, -1, SYSUTCDATETIME())) AS dead_letters_1h;
GO
-- Alert thresholds: errors_last_hour > 50, spend_today > 2× daily budget,
-- dead_letters_1h > 0, avg_latency_ms_1h > p99 SLO. Wire to your alerting.

36.4 Correlating the Two Halves

The most powerful observability comes from joining the halves: a latency spike in the AI dashboard correlated with a plan regression in Query Store, or a cost spike (§33.4) correlated with a specific generated query's execution count exploding. Practical correlation keys:

  • → Time: both halves share created_at — the incident timeline (§24.4) overlaid with wait stats tells the story.
  • → Query text hash: hash generated SQL at the tool layer and store it in agent_actions; join to Query Store's query_sql_text for cost-per-generated-query.
  • → Tenant: every audit row carries tenant_id; Resource Governor / workload groups tag database work per tenant — the join identifies the noisy tenant in both cost and resource terms.

    • Build one incident runbook that starts from the AI dashboard, drills into the audit timeline, and lands on the DMV/Query Store evidence. Two observability halves with one runbook is what "operated" actually means.

    36.5 SLOs for AI Features

    Observability (§36.1–36.4) without objectives is just expensive logging. Define SLOs per AI feature, measured from the audit tables:

  • → Chat latency: p95 time-to-first-token < 1.5s, p95 full-response < 15s. Time-to-first-token is the UX metric (§29); full-response bounds the tail.
  • → Availability: 99.9% of chat requests succeed (status = 'ok'), excluding provider outages — track provider-attributed failures separately so you're not SLO-violated by someone else's incident.
  • → Answer quality: weekly golden-set faithfulness ≥ baseline (§19.3) — a quality SLO, unusual for infrastructure teams, essential for AI.
  • → Cost efficiency: tokens per successful task trending down or flat — the anti-SLO that catches the slow cost creep of growing prompts and chatty agents.

    • Publish the SLOs on the same dashboard as the metrics, with burn-rate alerts (fast-burn: page; slow-burn: ticket). Review them quarterly: an SLO nobody can meet is a fiction, and an SLO always met with room to spare is a missed opportunity to promise more. The quality SLO deserves special attention — it is the one your competitors aren't measuring, and the one your users feel most directly.

    ---

    Key Takeaways

  • → Watch the three AI bottlenecks with DMVs: vector-search CPU (query stats), connection pressure (waiting tasks), and hot-row blocking (exec requests).
  • → Query Store is the safety net for generated SQL — automatic plan history, regression detection, and plan forcing while the AI layer is fixed.
  • → Build the AI metrics as views over audit tables: call volume, spend, latency, errors, agent runs, retrieval confidence, dead letters — with alert thresholds.
  • → Correlate the halves with shared keys (time, query hash, tenant) and run one incident runbook across both.
