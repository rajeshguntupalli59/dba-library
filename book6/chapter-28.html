Event-Driven AI with Service Broker and Query Notifications

Chapter 27 polled for changes; this chapter pushes. SQL Server offers two push mechanisms for event-driven AI: Service Broker — reliable, transactional, queued messaging inside the database — and Query Notifications (SqlDependency) — cache invalidation when a query's results change. Together they cover the two event shapes AI applications need: "do this work now" (Broker) and "your cached answer is stale" (notifications). This chapter builds both, with the reliability patterns that make push safe in production.

---

28.1 Service Broker: Reliable Intra-Database Messaging

Service Broker was introduced in §1.7 for document-ingested events. The full pattern has four parts: message types and contracts (the schema of the conversation), queues (durable storage), services (addressable endpoints), and activation (automatic processing):

-- Event vocabulary for the AI application
CREATE MESSAGE TYPE [//aiapp/DocumentIngested] VALIDATION = WELL_FORMED_XML;
CREATE MESSAGE TYPE [//aiapp/TriageRequested]  VALIDATION = WELL_FORMED_XML;
CREATE MESSAGE TYPE [//aiapp/QuotaExhausted]   VALIDATION = WELL_FORMED_XML;
CREATE MESSAGE TYPE [//aiapp/RunCompleted]      VALIDATION = WELL_FORMED_XML;

CREATE CONTRACT [//aiapp/AIContract] (
    [//aiapp/DocumentIngested] SENT BY INITIATOR,
    [//aiapp/TriageRequested]  SENT BY INITIATOR,
    [//aiapp/QuotaExhausted]   SENT BY INITIATOR,
    [//aiapp/RunCompleted]     SENT BY INITIATOR
);

CREATE QUEUE dbo.AIEventQueue WITH STATUS = ON;
CREATE SERVICE [//aiapp/AIService]
    ON QUEUE dbo.AIEventQueue ([//aiapp/AIContract]);
GO

-- Activated stored procedure: processes messages automatically on arrival
CREATE OR ALTER PROCEDURE dbo.usp_ai_event_activator
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @h UNIQUEIDENTIFIER, @mtype NVARCHAR(256), @body NVARCHAR(MAX);
    WHILE (1 = 1)
    BEGIN
        BEGIN TRAN;
        WAITFOR (
            RECEIVE TOP (1) @h = conversation_handle,
                            @mtype = message_type_name,
                            @body = CAST(message_body AS NVARCHAR(MAX))
            FROM dbo.AIEventQueue
        ), TIMEOUT 5000;
        IF @@ROWCOUNT = 0 BEGIN ROLLBACK; BREAK; END;

        -- Route by message type; each handler is idempotent (§20.2)
        IF @mtype = N'//aiapp/DocumentIngested'
            EXEC dbo.usp_on_document_ingested @body;
        ELSE IF @mtype = N'//aiapp/TriageRequested'
            EXEC dbo.usp_on_triage_requested @body;
        ELSE IF @mtype = N'//aiapp/QuotaExhausted'
            EXEC dbo.usp_on_quota_exhausted @body;
        ELSE IF @mtype = N'//aiapp/RunCompleted'
            EXEC dbo.usp_on_run_completed @body;

        -- EndDialog / Error messages: always END CONVERSATION to clean up
        IF @mtype IN (N'http://schemas.microsoft.com/SQL/ServiceBroker/EndDialog',
                      N'http://schemas.microsoft.com/SQL/ServiceBroker/Error')
            END CONVERSATION @h;
        COMMIT;
    END
END;
GO
ALTER QUEUE dbo.AIEventQueue WITH ACTIVATION (
    STATUS = ON, PROCEDURE_NAME = dbo.usp_ai_event_activator,
    MAX_QUEUE_READERS = 4, EXECUTE AS OWNER);
GO

Activation is the key feature: SQL Server launches the procedure automatically when messages arrive — no external scheduler, no polling loop. MAX_QUEUE_READERS = 4 gives parallel processing; each RECEIVE is transactional, so a handler failure rolls back the message back onto the queue for retry.

28.2 Poison Messages and Error Handling

A message that always fails will retry forever, blocking the queue. Service Broker's poison-message detection disables the queue after five consecutive rollbacks — which converts a bad message into a full outage. Handle it explicitly:

  • → Catch handler errors inside the activator and move the failed message to a dead-letter table with the error — then COMMIT, so the poison message leaves the queue.
  • → Alert on dead-letter inserts. Every dead letter is a bug or a data problem worth investigating.
  • → Monitor queue depth and disabled queues. A growing queue means handlers can't keep up; a disabled queue means poison-message protection fired.
    • CREATE TABLE dbo.ai_dead_letters (
    dead_letter_id UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    message_type   NVARCHAR(256) NOT NULL,
    body           NVARCHAR(MAX) NULL,
    error_message  NVARCHAR(MAX) NOT NULL,
    failed_at      DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);

-- Inside the activator, wrap each handler:
BEGIN TRY
    EXEC dbo.usp_on_document_ingested @body;
END TRY
BEGIN CATCH
    INSERT INTO dbo.ai_dead_letters (message_type, body, error_message)
    VALUES (@mtype, @body, ERROR_MESSAGE());
    -- COMMIT (not ROLLBACK): the poison message is consumed, recorded,
    -- and the queue keeps moving.
END CATCH;

-- Operational monitors
SELECT name, is_receive_enabled, is_enqueue_enabled
FROM sys.service_queues WHERE name = 'AIEventQueue';
-- is_receive_enabled = 0 → poison protection fired: investigate dead letters,
-- fix the handler, then ALTER QUEUE ... WITH STATUS = ON.

    28.3 Query Notifications: Invalidating Caches on Change

    Service Broker pushes work; Query Notifications push invalidation. Register a query with SqlDependency (SqlClient) and SQL Server notifies you when the results would change — the foundation of the retrieval cache from §2.5:

    // C# — cache the tenant's document list, invalidate on change
async Task<List<Doc>> GetDocumentsAsync(Guid tenantId)
{
    if (_cache.TryGetValue(tenantId, out var docs)) return docs;

    using var conn = new SqlConnection(_connStr);
    await conn.OpenAsync();
    using var cmd = new SqlCommand(
        "SELECT document_id, title, updated_at FROM dbo.documents " +
        "WHERE tenant_id = @t AND is_active = 1", conn);
    cmd.Parameters.AddWithValue("@t", tenantId);

    var dep = new SqlDependency(cmd);
    dep.OnChange += (_, e) => {
        _cache.Remove(tenantId);   // invalidate on ANY change to the result set
        // Re-subscribe on next GetDocumentsAsync call (notifications are one-shot)
    };
    SqlDependency.Start(_connStr);  // once per process

    docs = await LoadAsync(cmd);
    _cache.Set(tenantId, docs, TimeSpan.FromMinutes(10));
    return docs;
}

    Notifications are one-shot (re-subscribe after each fires) and coarse (any change to the result set invalidates, without saying what changed). They are perfect for cache invalidation — "something changed, refetch" — and wrong for change data ("what changed" is Chapter 27/30's job). The query must meet notification requirements: fully qualified names, no SELECT *, no aggregates over the notified query in most cases — keep notified queries simple and put complexity in the refetch.

    28.4 Choosing Between Push Mechanisms

  • → Service Broker: durable, transactional, ordered per conversation, with automatic activation. Use for work dispatch (ingest this, triage that) where losing an event is unacceptable.
  • → Query Notifications: lightweight, one-shot, invalidation-only. Use for cache coherence where the subscriber re-reads authoritative state.
  • → Change Tracking polling (§27.2): simplest, works across any client, latency bounded by poll interval. Use when 5-second latency is fine and you want minimal moving parts.
  • → External bus (Service Bus/Kafka): cross-database, cross-service, replayable. Graduate here when events must leave the database boundary.

    • The progression is deliberate: start with Change Tracking polling, add Query Notifications for hot caches, use Service Broker for transactional work dispatch, and reach for an external bus only when the database boundary becomes the constraint.

    28.5 Monitoring the Event Backbone

    Events are invisible when healthy and catastrophic when not — which is exactly why the event backbone needs dedicated monitoring beyond §28.2's queue checks. Track four signals per queue: depth over time (growth means consumers are falling behind — alert on sustained growth, not spikes), age of oldest message (the true latency signal — a queue with 10,000 fresh messages is fine, one with a 2-hour-old message is not), dead-letter rate (any sustained rate above zero is a bug being fed continuously), and activation health (is the activated procedure actually running, or did someone disable activation during maintenance and forget to re-enable it?). Add one end-to-end canary: every 5 minutes, enqueue a synthetic event with a timestamp and verify a handler processes it within the SLO — this catches the silent failures (disabled queues, broken activation, poisoned handlers that commit without processing) that depth metrics miss. The canary is the difference between "the queue looks fine" and "events actually flow."

    ---

    Key Takeaways

  • → Service Broker gives you transactional, activated messaging inside the database — SEND in the business transaction, automatic procedure activation on arrival, parallel readers, per-conversation ordering.
  • → Defeat poison messages explicitly: catch handler errors into a dead-letter table and COMMIT, alert on dead letters, and monitor queue state — never let the five-rollback protection fire unnoticed.
  • → Use Query Notifications (SqlDependency) for cache invalidation, not change data. One-shot, coarse-grained, perfect for "refetch your cache" — keep notified queries simple.
  • → Progress deliberately: Change Tracking polling → Query Notifications → Service Broker → external bus, each step taken when the previous mechanism's limits bind.
