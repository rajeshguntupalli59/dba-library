AI-Native Apps on SQL Server

Chapter 1 of 40

SQL Server as the AI Application Backend

Every AI application eventually needs a place to store conversations, user profiles, embeddings, audit logs, documents, permissions, and the relational glue that holds all of it together. Developers new to the AI space often reach for a vector database first — Pinecone, Weaviate, Chroma — because that is where the embedding tutorials point. Then they add Redis for sessions, a separate SQL database for user data, another store for conversation history, and find themselves managing five systems instead of one. This chapter makes the case that SQL Server 2025, with its native VECTOR data type, built-in vector search, Machine Learning Services, and JSON support, can serve as the single operational backbone for production AI applications. Not because it is "good enough," but because the relational model, transactional guarantees, row-level security, and change-tracking primitives give you capabilities that purpose-built vector stores cannot replicate. By the end of this chapter you will have a fully operational schema, a working RAG retrieval path, and a production deployment pattern standing on SQL Server alone.

---

1.1 The Vector-Only Trap and Why Relational Wins

The pitch for standalone vector databases sounds compelling: low latency, purpose-built for similarity search, scales horizontally. The pitch collapses the moment you ask a question that is not purely "find me the nearest neighbors." Real AI applications ask questions like:

  • → Find the most relevant documents for this user, but only ones they have permission to read, published in the last 90 days, not previously shown in this session.
  • → Store this conversation turn, update the session token count, emit a notification so the billing service can charge, and roll back everything if the embedding write fails.
  • → Which users have had more than five conversations about topic X in the last week?

    • None of those questions are answerable by a vector store alone. Every single one requires joins, filters, transactions, and access control — the things SQL Server has been doing reliably for three decades.

    The strategic insight is this: SQL Server 2025's native VECTOR type turns SQL Server into a vector database. It does not turn a vector database into SQL Server. You lose nothing by adding vector search to SQL Server; you lose a great deal by starting with a vector store and bolting relational features on top of it.

    The table below summarizes what each layer of a typical AI application needs and which system provides it natively.

    | Capability | Vector-only store | SQL Server 2025 |

    |---|---|---|

    | Embedding storage and ANN search | ✓ | ✓ Native VECTOR + vector index |

    | Exact metadata filtering | Limited | ✓ Full T-SQL |

    | Transactional consistency | ✗ | ✓ ACID |

    | Row-level security | ✗ | ✓ Native RLS |

    | Conversation history | ✗ | ✓ |

    | Full-text search hybrid | ✗ | ✓ Full-text indexes |

    | Change notifications | ✗ | ✓ Change Tracking / Service Broker |

    | JSON document storage | ✗ | ✓ Native JSON type |

    | Audit logging | ✗ | ✓ Temporal tables + triggers |

    | Foreign keys and referential integrity | ✗ | ✓ |

    | In-database ML scoring | ✗ | ✓ ML Services + PREDICT |

    This is not a theoretical argument. Let us build the foundation and prove it with running code.

    1.2 The Core Schema for an AI Application

    Before writing a single line of Python, the schema needs to reflect the actual entities in an AI application. Every production AI system maps to roughly the same set of tables. The names change; the relationships do not. Note the SQL Server idioms throughout: UNIQUEIDENTIFIER with NEWID() defaults, DATETIME2 with SYSUTCDATETIME(), NVARCHAR(MAX) for text, the native JSON type for flexible metadata, and computed columns replacing what other platforms do with generated columns.

    -- ============================================================
-- CORE AI APPLICATION SCHEMA (SQL Server 2025)
-- Run in order. Requires compatibility level 170 for VECTOR.
-- ============================================================

-- ----------------------------------------------------------------
-- Tenants and users — every AI app is multi-tenant at some level
-- ----------------------------------------------------------------
CREATE TABLE dbo.tenants (
    tenant_id   UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),

                CONSTRAINT CK_tenants_plan CHECK (plan IN (N'free',N'pro',N'enterprise')),

    settings    JSON NOT NULL DEFAULT N'{}'
);

CREATE TABLE dbo.users (
    user_id         UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    tenant_id       UNIQUEIDENTIFIER NOT NULL
                    CONSTRAINT FK_users_tenant REFERENCES dbo.tenants(tenant_id) ON DELETE CASCADE,
    email           NVARCHAR(320) NOT NULL,
    display_name    NVARCHAR(200) NULL,
    created_at      DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    last_active_at  DATETIME2 NULL,

CREATE INDEX IX_users_tenant ON dbo.users(tenant_id);

-- Documents — the corpus that gets embedded for RAG
-- ----------------------------------------------------------------

    title           NVARCHAR(500) NOT NULL,
    source_url      NVARCHAR(2000) NULL,
    content         NVARCHAR(MAX) NOT NULL,
    -- Computed hash column: SQL Server's answer to a generated column

-- Full-text catalog + index for the hybrid-search text arm
CREATE FULLTEXT CATALOG ft_catalog AS DEFAULT;
CREATE FULLTEXT INDEX ON dbo.documents(content LANGUAGE 1033)
    KEY INDEX PK__document__... -- replace with your PK name
    ON ft_catalog WITH CHANGE_TRACKING AUTO;

-- ----------------------------------------------------------------
-- Document chunks — what actually gets embedded
-- ----------------------------------------------------------------

-- DiskANN-backed approximate nearest-neighbor vector index

    ON dbo.document_chunks (embedding)

CREATE INDEX IX_chunks_tenant   ON dbo.document_chunks(tenant_id);

    This schema is not a toy. It handles multi-tenancy, document versioning through the persisted hash, hybrid search through the full-text index, embedding provenance through embedding_model, and a complete audit trail. Everything is connected by foreign keys, so you can answer questions like "which tenants consumed the most tokens this month" with a single T-SQL query. Note the VECTOR(1536) column and the DiskANN vector index — native engine features, no extension to install, no separate service to run.

    1.3 Ingestion Pipeline: From Documents to Searchable Embeddings

    Getting documents into this schema requires chunking text, calling an embedding model, and writing the results transactionally. The Python side uses pyodbc with the Microsoft ODBC driver and a background worker (Celery, or Azure Functions, or a simple queue table — Chapter 14 covers the options). SQL Server 2025 accepts a JSON array string cast directly to VECTOR, which makes inserts clean.

    # ingestion/pipeline.py
# Dependencies: pip install openai celery pyodbc tiktoken langchain-text-splitters
# Requires: ODBC Driver 18 for SQL Server

import hashlib
import json
import time
from datetime import datetime, timezone
from typing import Optional

import pyodbc
import tiktoken
from celery import Celery
from langchain_text_splitters import RecursiveCharacterTextSplitter
from openai import OpenAI

# ----------------------------------------------------------------
# Configuration — in production these come from environment variables
# ----------------------------------------------------------------
CONN_STR = (
    "DRIVER={ODBC Driver 18 for SQL Server};"
    "SERVER=localhost,1433;DATABASE=aiapp;"
    "UID=aiapp;PWD=secret;TrustServerCertificate=yes;"
)
REDIS_URL   = "redis://localhost:6379/0"
EMBED_MODEL = "text-embedding-3-small"
EMBED_DIM   = 1536
CHUNK_SIZE  = 512
CHUNK_OVERLAP = 64

openai_client = OpenAI()
celery_app    = Celery("ingestion", broker=REDIS_URL, backend=REDIS_URL)
tokenizer = tiktoken.encoding_for_model("text-embedding-3-small")
splitter = RecursiveCharacterTextSplitter.from_tiktoken_encoder(
    model_name=EMBED_MODEL, chunk_size=CHUNK_SIZE, chunk_overlap=CHUNK_OVERLAP,
)

def embed_texts(texts: list[str]) -> list[list[float]]:
    resp = openai_client.embeddings.create(model=EMBED_MODEL, input=texts)
    return [item.embedding for item in sorted(resp.data, key=lambda x: x.index)]

@celery_app.task(bind=True, max_retries=3, default_retry_delay=30)
def ingest_document(self, document_id: str, tenant_id: str, content: str,
                    title: str, source_url: Optional[str] = None,
                    metadata: Optional[dict] = None) -> dict:
    """Chunk → embed → store, all inside one SQL Server transaction."""
    conn = pyodbc.connect(CONN_STR)
    conn.autocommit = False
    try:
        cur = conn.cursor()

        # Step 1: Upsert document via MERGE
        content_hash = hashlib.sha256(content.encode()).hexdigest()
        cur.execute("""
            MERGE dbo.documents AS tgt
            USING (SELECT ? AS document_id, ? AS tenant_id, ? AS title,
                          ? AS source_url, ? AS content, ? AS metadata) AS src
              ON tgt.tenant_id = src.tenant_id AND tgt.content_hash = ?
            WHEN MATCHED THEN
                UPDATE SET updated_at = SYSUTCDATETIME(), is_active = 1
            WHEN NOT MATCHED THEN
                INSERT (document_id, tenant_id, title, source_url, content, metadata)
                VALUES (src.document_id, src.tenant_id, src.title,
                        src.source_url, src.content, src.metadata)
            OUTPUT INSERTED.document_id;
        """, document_id, tenant_id, title, source_url, content,
             json.dumps(metadata or {}), content_hash)
        actual_doc_id = cur.fetchone()[0]

        # Step 2: Chunk, Step 3: delete stale chunks on re-ingest
        chunks = splitter.split_text(content)
        cur.execute("DELETE FROM dbo.document_chunks WHERE document_id = ?",
                    actual_doc_id)

        # Step 4: Embed in batches of 100
        embeddings: list[list[float]] = []
        for i in range(0, len(chunks), 100):
            embeddings.extend(embed_texts(chunks[i:i + 100]))

        # Step 5: Bulk insert — JSON array string CAST to VECTOR(1536)
        rows = [(
            tenant_id, actual_doc_id, idx, chunk,
            len(tokenizer.encode(chunk)),
            json.dumps(vec),          # '[0.12, -0.04, ...]'
            EMBED_MODEL,
            datetime.now(timezone.utc).strftime("%Y-%m-%d %H:%M:%S.%f")[:-3],
        ) for idx, (chunk, vec) in enumerate(zip(chunks, embeddings))]
        cur.fast_executemany = True
        cur.executemany("""
            INSERT INTO dbo.document_chunks
                (tenant_id, document_id, chunk_index, content, token_count,
                 embedding, embedding_model, embedded_at)
            VALUES (?, ?, ?, ?, ?,
                    CAST(? AS VECTOR(1536)), ?, ?)
        """, rows)

        # Step 6: Notify downstream via Service Broker (see §1.7)
        cur.execute("EXEC dbo.usp_notify_document_ingested @document_id = ?, @tenant_id = ?, @chunks = ?",
                    actual_doc_id, tenant_id, len(chunks))

        conn.commit()
        return {"document_id": str(actual_doc_id), "chunks": len(chunks)}
    except Exception as exc:
        conn.rollback()
        raise self.retry(exc=exc)
    finally:
        conn.close()

    Two design decisions deserve attention. First, the document upsert plus all chunk writes happen inside a single transaction. If the embedding API returns 200 chunks and the database write fails on chunk 150, nothing is committed — no partial state, no phantom documents. Second, the notification fires inside the same transaction via a Service Broker message, so downstream consumers only react to data that is actually committed and readable.

    1.4 Retrieval: Hybrid Search Combines Vector and Full-Text

    Pure vector search misses exact keyword matches. Pure full-text search misses semantic similarity. Production RAG systems use both, and SQL Server is the only single system that makes this a T-SQL procedure rather than an application-level merge: VECTOR_DISTANCE for the semantic arm, CONTAINSTABLE for the keyword arm, and Reciprocal Rank Fusion to merge them.

    -- ============================================================
-- HYBRID SEARCH PROCEDURE (SQL Server 2025)
-- Vector arm: VECTOR_DISTANCE cosine  +  Full-text arm: CONTAINSTABLE
-- Merged with Reciprocal Rank Fusion, tenant-filtered by RLS.
-- ============================================================
CREATE OR ALTER PROCEDURE dbo.usp_hybrid_search
    @tenant_id        UNIQUEIDENTIFIER,
    @query_text       NVARCHAR(MAX),
    @query_vector     VECTOR(1536),
    @match_count      INT = 10,
    @vector_weight    FLOAT = 0.7,
    @fulltext_weight  FLOAT = 0.3,
    @rrf_k            INT = 60
AS
BEGIN
    SET NOCOUNT ON;

    -- Vector arm: nearest chunks by cosine distance
    WITH vector_results AS (
        SELECT TOP (@match_count * 2)
            dc.chunk_id, dc.document_id, dc.chunk_index, dc.content, dc.metadata,
            VECTOR_DISTANCE('cosine', dc.embedding, @query_vector) AS cosine_distance,
            ROW_NUMBER() OVER (
                ORDER BY VECTOR_DISTANCE('cosine', dc.embedding, @query_vector)) AS rnk
        FROM dbo.document_chunks AS dc
        WHERE dc.tenant_id = @tenant_id AND dc.embedding IS NOT NULL
        ORDER BY VECTOR_DISTANCE('cosine', dc.embedding, @query_vector)
    ),
    -- Full-text arm: keyword ranking via CONTAINSTABLE
    fulltext_results AS (
        SELECT TOP (@match_count * 2)
            dc.chunk_id, dc.document_id, dc.chunk_index, dc.content, dc.metadata,
            CAST(0.0 AS FLOAT) AS cosine_distance,
            ROW_NUMBER() OVER (ORDER BY ft.RANK DESC) AS rnk
        FROM dbo.document_chunks AS dc
        INNER JOIN CONTAINSTABLE(dbo.document_chunks, content, @query_text) AS ft
            ON dc.chunk_id = ft.[KEY]
        WHERE dc.tenant_id = @tenant_id
    ),
    all_chunks AS (
        SELECT chunk_id FROM vector_results
        UNION
        SELECT chunk_id FROM fulltext_results
    ),
    rrf AS (
        SELECT
            ac.chunk_id,
            ISNULL(@vector_weight   * (1.0 / (@rrf_k + vr.rnk)), 0)
          + ISNULL(@fulltext_weight * (1.0 / (@rrf_k + fr.rnk)), 0) AS rrf_score,
            ISNULL(vr.rnk, 9999999)          AS vector_rank,
            ISNULL(fr.rnk, 9999999)          AS fulltext_rank,
            ISNULL(vr.cosine_distance, 1.0)  AS cosine_distance
        FROM all_chunks AS ac
        LEFT JOIN vector_results   AS vr ON ac.chunk_id = vr.chunk_id
        LEFT JOIN fulltext_results AS fr ON ac.chunk_id = fr.chunk_id
    )
    SELECT TOP (@match_count)
        dc.chunk_id, dc.document_id, dc.chunk_index, dc.content, dc.metadata,
        r.vector_rank, r.fulltext_rank, r.rrf_score, r.cosine_distance
    FROM rrf AS r
    JOIN dbo.document_chunks AS dc ON r.chunk_id = dc.chunk_id
    ORDER BY r.rrf_score DESC;
END;
GO

-- ============================================================
-- Row-Level Security: tenants can only search their own chunks
-- ============================================================
CREATE SCHEMA security;
GO
CREATE FUNCTION security.fn_tenant_filter(@tenant_id UNIQUEIDENTIFIER)
RETURNS TABLE WITH SCHEMABINDING
AS RETURN SELECT 1 AS access
           WHERE @tenant_id = CAST(SESSION_CONTEXT(N'tenant_id') AS UNIQUEIDENTIFIER);
GO
CREATE SECURITY POLICY security.tenant_policy
    ADD FILTER PREDICATE security.fn_tenant_filter(tenant_id)
        ON dbo.document_chunks,
    ADD FILTER PREDICATE security.fn_tenant_filter(tenant_id)
        ON dbo.documents
    WITH (STATE = ON);
GO

    The RRF merge in T-SQL means there is no Python code sorting two lists from two systems. The database does the work. The RLS security policy means that even if application code forgets a WHERE tenant_id = ? clause, SQL Server enforces the boundary automatically via SESSION_CONTEXT — an enforcement layer no external vector store can provide.

    graph TD
    Q[User query] --> E[Embed query]
    E --> V["Vector arm: ORDER BY VECTOR_DISTANCE cosine"]
    Q --> F["Full-text arm: CONTAINSTABLE RANK"]
    V --> U[UNION of candidate chunk_ids]
    F --> U
    U --> R["Reciprocal Rank Fusion: 1/(k+rank) per arm, summed"]
    R --> RLS["Row-Level Security filters to current tenant"]
    RLS --> TOP[Top-N chunks returned to caller]

    Both retrieval arms run inside a single stored procedure; RRF and tenant isolation happen before a single row leaves SQL Server.

    1.5 The FastAPI RAG Endpoint: Full Stack in Practice

    This is where the schema, search procedure, and LLM come together. The endpoint accepts a user question, retrieves relevant chunks via hybrid search, builds a prompt, calls the model, stores the conversation turn, and writes an audit log entry — all in a single request. Note the SqlClient-style pooling discipline: pyodbc connections are cheap to open because ODBC pooling is enabled by default, and SESSION_CONTEXT sets the RLS tenant on each checkout (Chapter 5 covers pooling in depth).

    # api/rag_endpoint.py
# Dependencies: pip install fastapi anthropic openai pyodbc uvicorn

import json, time, uuid
from contextlib import contextmanager
from fastapi import FastAPI, HTTPException, Header
from openai import OpenAI
import anthropic
import pyodbc
from pydantic import BaseModel

CONN_STR = ("DRIVER={ODBC Driver 18 for SQL Server};SERVER=localhost,1433;"
            "DATABASE=aiapp;UID=aiapp;PWD=secret;TrustServerCertificate=yes;")
# ODBC connection pooling is ON by default; tune via Pooling=yes; Max Pool Size=100

openai_client = OpenAI()
anthropic_client = anthropic.Anthropic()
app = FastAPI()

class ChatRequest(BaseModel):
    conversation_id: str | None = None
    message: str
    user_id: str

@contextmanager
def db(tenant_id: str):
    """Yield a connection with the RLS tenant context set."""
    conn = pyodbc.connect(CONN_STR)
    try:
        conn.execute("EXEC sp_set_session_context 'tenant_id', ?",
                     tenant_id)
        yield conn
    finally:
        conn.close()   # returns to the ODBC pool

@app.post("/chat")
def chat(request: ChatRequest, x_tenant_id: str = Header(alias="X-Tenant-Id")):
    t_start = time.monotonic()
    with db(x_tenant_id) as conn:
        cur = conn.cursor()

        # Resolve or create conversation
        if request.conversation_id:
            row = cur.execute(
                "SELECT conversation_id FROM dbo.conversations "
                "WHERE conversation_id = ? AND user_id = ?",
                request.conversation_id, request.user_id).fetchone()
            if not row: raise HTTPException(404, "Conversation not found")
            conversation_id = row[0]
        else:
            conversation_id = cur.execute(
                "INSERT INTO dbo.conversations (user_id, tenant_id, title) "
                "OUTPUT INSERTED.conversation_id VALUES (?, ?, ?)",
                request.user_id, x_tenant_id, request.message[:80]).fetchone()[0]

        # Recent history for the context window
        hist = cur.execute(
            "SELECT TOP 10 role, content FROM dbo.messages "
            "WHERE conversation_id = ? ORDER BY created_at DESC",
            conversation_id).fetchall()
        history = [{"role": r[0], "content": r[1]} for r in reversed(hist)]

        # Embed + hybrid retrieval
        qvec = openai_client.embeddings.create(
            model="text-embedding-3-small", input=request.message).data[0].embedding
        chunks = cur.execute(
            "EXEC dbo.usp_hybrid_search @tenant_id=?, @query_text=?, "
            "@query_vector=CAST(? AS VECTOR(1536)), @match_count=8",
            x_tenant_id, request.message, json.dumps(qvec)).fetchall()

        context = "\n\n---\n\n".join(
            f"[Source {i}]\n{c.content}" for i, c in enumerate(chunks, 1))
        system = ("Answer using only the provided context. Cite sources as "
                  f"[Source N].\n\nContext:\n{context}")

        resp = anthropic_client.messages.create(
            model="claude-3-5-sonnet-20241022", max_tokens=1024,
            system=system,
            messages=history + [{"role": "user", "content": request.message}])
        answer = resp.content[0].text
        latency_ms = int((time.monotonic() - t_start) * 1000)

        # Persist everything in ONE transaction
        citations = [{"chunk_id": str(c.chunk_id), "score": float(c.rrf_score),
                      "text_snippet": c.content[:200]} for c in chunks]
        cur.execute(
            "INSERT INTO dbo.messages (conversation_id, tenant_id, role, content, token_count)"
            " VALUES (?, ?, 'user', ?, ?)",
            conversation_id, x_tenant_id, request.message, resp.usage.input_tokens)
        cur.execute(
            """INSERT INTO dbo.messages
                 (conversation_id, tenant_id, role, content, token_count, model,
                  finish_reason, citations, latency_ms)
               VALUES (?, ?, 'assistant', ?, ?, ?, ?, ?, ?)""",
            conversation_id, x_tenant_id, answer, resp.usage.output_tokens,
            "claude-3-5-sonnet-20241022", resp.stop_reason,
            json.dumps(citations), latency_ms)
        cur.execute(
            "UPDATE dbo.conversations SET total_tokens = total_tokens + ?, "
            "updated_at = SYSUTCDATETIME() WHERE conversation_id = ?",
            resp.usage.input_tokens + resp.usage.output_tokens, conversation_id)
        cur.execute(
            """INSERT INTO dbo.llm_audit_log
                 (tenant_id, user_id, conversation_id, model, prompt_tokens,
                  completion_tokens, total_tokens, latency_ms, status)
               VALUES (?, ?, ?, ?, ?, ?, ?, ?, 'success')""",
            x_tenant_id, request.user_id, conversation_id,
            "claude-3-5-sonnet-20241022", resp.usage.input_tokens,
            resp.usage.output_tokens,
            resp.usage.input_tokens + resp.usage.output_tokens, latency_ms)
        conn.commit()
        return {"conversation_id": str(conversation_id), "answer": answer,
                "citations": citations, "latency_ms": latency_ms}

    Three things make this production-ready rather than demo-quality. First, the RLS tenant context is set via sp_set_session_context before any query runs, so the security policy enforces the tenant boundary even if application code slips. Second, all writes — user message, assistant message, token totals, audit log — are inside a single transaction committed once. Third, ODBC connection pooling means the pyodbc.connect() call is a pool checkout, not a TCP handshake plus login.

    1.7 Service Broker as an AI Application Event Bus

    SQL Server's Service Broker provides reliable, transactional messaging inside the database — the natural replacement for an external event bus for low-volume internal AI events. The ingestion pipeline calls usp_notify_document_ingested, which sends a Broker message on a queue. Because the SEND happens inside the ingest transaction, the message is only visible after commit: downstream consumers react to events that are guaranteed readable.

    -- One-time setup: message type, contract, queue, service
CREATE MESSAGE TYPE [//aiapp/DocumentIngested] VALIDATION = WELL_FORMED_XML;
CREATE CONTRACT [//aiapp/AIContract] ([//aiapp/DocumentIngested] SENT BY INITIATOR);
CREATE QUEUE dbo.AIEventQueue WITH STATUS = ON, RETENTION = OFF;
CREATE SERVICE [//aiapp/AIService] ON QUEUE dbo.AIEventQueue ([//aiapp/AIContract]);
GO

CREATE OR ALTER PROCEDURE dbo.usp_notify_document_ingested
    @document_id UNIQUEIDENTIFIER, @tenant_id UNIQUEIDENTIFIER, @chunks INT
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @h UNIQUEIDENTIFIER, @body NVARCHAR(MAX);
    SET @body = (SELECT @document_id AS document_id, @tenant_id AS tenant_id,
                        @chunks AS chunks FOR XML PATH('event'), TYPE).value('.', 'NVARCHAR(MAX)');
    BEGIN DIALOG CONVERSATION @h
        FROM SERVICE [//aiapp/AIService] TO SERVICE '//aiapp/AIService'
        ON CONTRACT [//aiapp/AIContract] WITH ENCRYPTION = OFF;
    SEND ON CONVERSATION @h MESSAGE TYPE [//aiapp/DocumentIngested] (@body);
    END CONVERSATION @h;
END;
GO
-- A background worker RECEIVEs from dbo.AIEventQueue, warms caches,
-- triggers re-ranking jobs, or fans out to Azure Service Bus for scale.

    This pattern is powerful because the message send is tied to the transaction. If the ingest rolls back, no message is sent. If the commit succeeds, the message lands on the queue within milliseconds. Azure Service Bus or Kafka are appropriate for higher-throughput or cross-datacenter scenarios, but for intra-service coordination within a single application, Service Broker eliminates an entire infrastructure dependency.

    1.8 Analytical Queries Against the AI Application

    One of the durable advantages of keeping everything in SQL Server is that business-intelligence queries run against the same store without ETL. A few examples that appear in almost every AI product review meeting:

    -- 1. Token consumption by tenant, last 30 days
SELECT t.name AS tenant_name,
       SUM(a.total_tokens) AS total_tokens,
       SUM(CASE WHEN a.status = 'error' THEN a.total_tokens ELSE 0 END) AS error_tokens,
       COUNT(*) AS llm_calls,
       AVG(a.latency_ms) AS avg_latency_ms,
       (SELECT DISTINCT PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY a2.latency_ms)
          OVER () FROM dbo.llm_audit_log a2
         WHERE a2.tenant_id = t.tenant_id
           AND a2.created_at >= DATEADD(day, -30, SYSUTCDATETIME())) AS p95_latency_ms
FROM dbo.llm_audit_log a
JOIN dbo.tenants t ON a.tenant_id = t.tenant_id
WHERE a.created_at >= DATEADD(day, -30, SYSUTCDATETIME())
GROUP BY t.tenant_id, t.name
ORDER BY total_tokens DESC;

-- 2. Most-cited chunks — which content actually influences answers?
SELECT TOP 20 d.title, dc.chunk_index,
       COUNT(*) AS citation_count
FROM dbo.messages m
CROSS APPLY OPENJSON(m.citations)
    WITH (chunk_id UNIQUEIDENTIFIER '$.chunk_id') AS c
JOIN dbo.document_chunks dc ON dc.chunk_id = c.chunk_id
JOIN dbo.documents d ON d.document_id = dc.document_id
WHERE m.role = 'assistant'
  AND m.created_at >= DATEADD(day, -7, SYSUTCDATETIME())
GROUP BY d.title, dc.chunk_index
ORDER BY citation_count DESC;

-- 3. Engagement: average conversation length by plan tier
SELECT t.plan,
       AVG(CAST(mc.msg_count AS FLOAT)) AS avg_messages_per_conversation,
       COUNT(DISTINCT c.conversation_id) AS total_conversations
FROM dbo.conversations c
JOIN dbo.tenants t ON c.tenant_id = t.tenant_id
JOIN (SELECT conversation_id, COUNT(*) AS msg_count
      FROM dbo.messages GROUP BY conversation_id) AS mc
  ON c.conversation_id = mc.conversation_id
WHERE c.created_at >= DATEADD(day, -30, SYSUTCDATETIME())
GROUP BY t.plan;

-- 4. Error rate by model — catch degraded LLM APIs quickly
SELECT model,
       100.0 * SUM(CASE WHEN status = 'error' THEN 1 ELSE 0 END)
           / NULLIF(COUNT(*), 0) AS error_rate_pct,
       COUNT(*) AS total_calls,
       MAX(CASE WHEN status = 'error' THEN created_at END) AS last_error_at
FROM dbo.llm_audit_log
WHERE created_at >= DATEADD(day, -1, SYSUTCDATETIME())
GROUP BY model
ORDER BY error_rate_pct DESC;

    Query 2 uses CROSS APPLY OPENJSON against the citations stored in each assistant message to reconstruct which document chunks influence answers — no data warehouse required, because the JSON column was designed with queryability in mind from the start.

    1.9 Production Deployment Considerations

    Three operational decisions separate a demo from a production deployment. First, put SQL Server behind a proper backup and high-availability story from day one: full + differential + log backups (or Azure SQL's automatic backups with point-in-time restore), and an availability group or Azure SQL's built-in HA for failover. AI workloads are write-heavy on the messages and audit tables, and losing conversation history is a trust-destroying event.

    Second, size the vector index build correctly. DiskANN vector indexes build fastest with a generous maintenance memory grant and parallelism; build them during off-peak ingestion windows, and prefer incremental chunk inserts over rebuilding the index. Monitor index build progress through the vector-index DMVs covered in Chapter 15.

    Third, treat the embedding model version as a schema-level concern. The embedding_model column exists because cosine distances are meaningless across different embedding spaces. When you upgrade from text-embedding-3-small to a newer model, re-embed in the background, dual-write during the transition, and cut the retrieval procedure over only when the new vectors are complete. Chapter 17 walks through this migration pattern step by step.

    Key Takeaways

  • → SQL Server 2025 with the native VECTOR type replaces a vector store, not the other way around. The relational model, transactions, and row-level security provide capabilities no purpose-built vector database can match, and DiskANN vector indexes provide competitive approximate nearest-neighbor performance with zero extra infrastructure.
  • → Schema design is the highest-leverage decision in an AI application. The multi-tenant schema built in this chapter — persisted hash columns, full-text indexes, native JSON metadata, VECTOR columns, and a complete audit table — handles the operational demands of a production AI product without modification for most use cases.
  • → Hybrid search in a single stored procedure outperforms application-level merging. Reciprocal Rank Fusion combining VECTOR_DISTANCE cosine similarity and CONTAINSTABLE full-text ranking runs entirely in SQL Server, eliminating the need to query two systems and merge results in Python.
  • → Transactional integrity is non-negotiable for AI applications. Writing user messages, assistant messages, token counts, and audit records inside one transaction means partial writes never occur. Downstream billing and compliance systems can trust the data.
  • → Service Broker provides a zero-dependency internal event bus. Because messages send inside the ingest transaction, downstream services react only to committed, readable data — no Kafka or Service Bus required for intra-service coordination.
