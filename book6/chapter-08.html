Short-Term and Long-Term Memory Design

Human memory has two systems: working memory (small, fast, fleeting) and long-term memory (vast, slower, durable). AI applications need the same split, and the failure mode of confusing them is expensive — stuffing everything into the prompt wastes tokens and money; storing everything durably and retrieving nothing makes the assistant feel amnesiac. This chapter designs the two-tier memory architecture: the short-term tier (recent turns, session scratch state) optimized for millisecond access, and the long-term tier (summaries, facts, embeddings of past conversations) optimized for relevance-ranked retrieval. Both tiers live in SQL Server, with a promotion pipeline moving memories between them.

---

8.1 The Two Tiers and Their Contracts

Each tier has a distinct contract with the rest of the system:

  • → Short-term memory: the last N turns, verbatim. Sourced from the messages table (§6.2), bounded by the token budget, ordered chronologically. Latency budget: single-digit milliseconds. Eviction policy: oldest turns fall off as the budget fills.
  • → Long-term memory: distilled knowledge about the user. Conversation summaries, extracted facts ("user prefers morning meetings"), preference records, and embeddings of past conversations for semantic recall. Sourced from dedicated tables, retrieved by relevance — not recency. Latency budget: tens of milliseconds.

    • The prompt assembly order is fixed: system prompt → long-term memories (ranked by relevance) → short-term turns (chronological) → current user message. Long-term memories go first because they are the most likely to be truncated if the budget runs out — and a truncated recent turn is worse than a truncated old fact.

    8.2 The Long-Term Memory Schema

    -- Distilled, long-lived memories about a user
CREATE TABLE dbo.long_term_memories (
    memory_id       UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    user_id         UNIQUEIDENTIFIER NOT NULL
                    CONSTRAINT FK_ltm_user REFERENCES dbo.users(user_id) ON DELETE CASCADE,
    tenant_id       UNIQUEIDENTIFIER NOT NULL,
    memory_type     NVARCHAR(30) NOT NULL
                    CONSTRAINT CK_ltm_type CHECK (memory_type IN
                        (N'summary', N'fact', N'preference', N'episode')),
    -- summary: compressed conversation; fact: atomic statement;
    -- preference: durable likes/dislikes; episode: notable past interaction
    content         NVARCHAR(MAX) NOT NULL,
    embedding       VECTOR(1536) NULL,   -- for semantic recall of episodes/facts
    importance      DECIMAL(3,2) NOT NULL DEFAULT 0.50,  -- 0..1, decayed over time
    source_conversation_id UNIQUEIDENTIFIER NULL,
    created_at      DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    last_recalled_at DATETIME2 NULL,
    recall_count    INT NOT NULL DEFAULT 0
);
CREATE VECTOR INDEX IX_ltm_embedding
    ON dbo.long_term_memories (embedding)
    WITH (METRIC = 'cosine', TYPE = 'diskann');
CREATE INDEX IX_ltm_user_type ON dbo.long_term_memories(user_id, memory_type, importance DESC);

    The importance score is the key innovation: every memory carries a weight that decays with time and increases with recall. Retrieval ranks by a blend of semantic similarity and importance, so frequently-useful memories surface and stale ones fade without explicit deletion.

    8.3 The Promotion Pipeline: Short-Term → Long-Term

    When a session closes (Chapter 7's expiry job), the promotion worker distills it into long-term memories. This is a background job, not part of the chat request — it can take seconds and retry freely:

    -- Promotion worker (Python pseudocode, runs off session_close_queue)
def promote_session(session_id, conversation_id, user_id, tenant_id):
    turns = load_full_conversation(conversation_id)   # Chapter 6
    if len(turns) < 4:
        return  # too short to distill; skip

    # 1. Summarize the conversation with the LLM
    summary = llm(f"Summarize this conversation in 5 sentences or less, "
                  f"focusing on durable facts about the user:\n{turns}")

    # 2. Extract atomic facts as structured JSON
    facts = llm_json(f"Extract durable facts about the user as a JSON array "
                     f"of short statements. Omit anything ephemeral:\n{turns}")
    # facts = ["User manages a team of 12 DBAs", "Prefers terse answers", ...]

    # 3. Embed summary + facts, store as long-term memories
    with db(tenant_id) as conn:
        store_memory(conn, user_id, tenant_id, 'summary', summary,
                     embed(summary), importance=0.7,
                     source_conversation_id=conversation_id)
        for fact in facts:
            # Deduplicate: skip if a near-identical fact already exists
            if not near_duplicate(conn, user_id, fact):
                store_memory(conn, user_id, tenant_id, 'fact', fact,
                             embed(fact), importance=0.6,
                             source_conversation_id=conversation_id)

    Deduplication matters: without it, ten conversations about the same preference create ten competing memories. The near_duplicate check runs a vector search for existing facts above a similarity threshold — if found, it bumps the existing memory's importance instead of inserting a duplicate.

    8.4 Recall: Assembling Long-Term Context

    At chat time, long-term recall runs a hybrid query: semantic similarity against the current message, blended with importance, filtered to the user:

    CREATE OR ALTER PROCEDURE dbo.usp_recall_memories
    @user_id      UNIQUEIDENTIFIER,
    @query_vector VECTOR(1536),
    @top_n        INT = 5
AS
BEGIN
    SET NOCOUNT ON;
    -- Blend: 70% semantic similarity, 30% importance.
    -- Cosine distance d in [0,2]; convert to similarity (1 - d/2).
    SELECT TOP (@top_n)
        memory_id, memory_type, content, importance,
        (0.7 * (1 - VECTOR_DISTANCE('cosine', embedding, @query_vector) / 2.0)
         + 0.3 * importance) AS score
    FROM dbo.long_term_memories
    WHERE user_id = @user_id
      AND embedding IS NOT NULL
    ORDER BY score DESC;

    -- Reinforcement: recalled memories get more important, and we record
    -- the recall so rarely-used memories can decay (see §8.5).
    -- (UPDATE issued by the caller for the returned memory_ids.)
END;
GO

    The caller then updates recall_count, last_recalled_at, and bumps importance slightly for returned memories — the reinforcement loop that keeps the memory store self-curating.

    8.5 Forgetting: Decay and Pruning

    A memory system that never forgets becomes a liability — stale facts contradict newer ones and retrieval quality degrades. Two mechanisms keep the store healthy:

  • → Importance decay. A nightly job multiplies importance by 0.99 for memories not recalled in 30 days. Memories that nobody uses fade toward zero and stop being retrieved.
  • → Contradiction resolution. When a new fact near-duplicates an old one with conflicting content ("prefers morning meetings" vs. "moved standup to afternoons"), the promotion worker marks the old memory superseded rather than deleting it — the history of the user's preferences is itself useful signal.
    • -- Nightly decay job
UPDATE dbo.long_term_memories
SET importance = importance * 0.99
WHERE last_recalled_at < DATEADD(day, -30, SYSUTCDATETIME())
   OR (last_recalled_at IS NULL AND created_at < DATEADD(day, -30, SYSUTCDATETIME()));

-- Prune fully-decayed, never-recalled trivia (keep summaries and preferences)
DELETE FROM dbo.long_term_memories
WHERE importance < 0.05 AND recall_count = 0
  AND memory_type IN (N'fact', N'episode');

    ---

    Key Takeaways

  • → Split memory into short-term (verbatim recent turns) and long-term (distilled summaries, facts, preferences). Assemble prompts as system → long-term (relevance-ranked) → short-term (chronological) → current message.
  • → Promote asynchronously on session close: summarize, extract atomic facts, deduplicate against existing memories, and embed — never in the chat request path.
  • → Rank recall by semantic similarity blended with importance, and reinforce on recall. Frequently-useful memories surface; stale ones fade.
  • → Design forgetting deliberately: nightly importance decay, contradiction supersession instead of deletion, and pruning of decayed trivia. A memory store that never forgets rots.
