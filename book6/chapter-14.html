Document Ingestion and Chunking Pipelines

Ingestion is where RAG quality is won or lost. The embedding model and vector index get the glory, but retrieval can only find what chunking preserved: split a document badly and the answer becomes unretrievable no matter how good the search. This chapter goes deep on the ingestion pipeline sketched in Chapters 1 and 13 — chunking strategies for different document types, embedding hygiene (batching, retries, model pinning), transactional storage patterns in SQL Server, and the observability that tells you ingestion is healthy. By the end, your pipeline will handle PDFs, HTML, markdown, and structured exports with per-type strategies.

---

14.1 Chunking Strategies by Document Type

One chunking strategy does not fit all documents. Match the strategy to the structure:

  • → Prose (docs, wikis, articles): recursive character splitting. Split on paragraph → sentence → word boundaries, targeting 400–600 tokens with 10–15% overlap. Overlap preserves context across boundaries — the sentence that completes a thought often starts the next chunk.
  • → Markdown / structured docs: header-aware splitting. Never split inside a section if you can avoid it; prepend the header path ("Refund Policy › Enterprise › Time limits") to each chunk so retrieved chunks carry their context.
  • → Code: function/class boundaries. Split on syntactic units, include the file path and symbol name as metadata. A half-function chunk is worse than useless — it retrieves confidently and answers wrong.
  • → Tables and structured data: row groups with headers. Keep the header row with every chunk; a table chunk without headers is uninterpretable. For wide tables, transpose to "attribute: value" sentences.
  • → PDFs: layout-aware extraction first. Strip headers/footers/page numbers before chunking — they pollute every chunk with repeated noise. Multi-column layouts need reading-order reconstruction.
    • # Header-aware markdown chunking: context travels with the chunk
import re

def chunk_markdown(text: str, max_tokens: int = 500) -> list[dict]:
    chunks, header_stack, buf, buf_tokens = [], [], [], 0
    for line in text.splitlines():
        m = re.match(r"^(#{1,4})\s+(.*)", line)
        if m:
            level = len(m.group(1))
            header_stack = header_stack[:level - 1] + [m.group(2).strip()]
            continue
        toks = len(line.split())  # rough; use tiktoken in production
        if buf_tokens + toks > max_tokens and buf:
            context = " › ".join(header_stack)
            chunks.append({"header_path": context,
                           "content": f"[{context}]\n" + "\n".join(buf)})
            # overlap: carry the last 2 lines into the next chunk
            buf, buf_tokens = buf[-2:], sum(len(l.split()) for l in buf[-2:])
        buf.append(line); buf_tokens += toks
    if buf:
        context = " › ".join(header_stack)
        chunks.append({"header_path": context,
                       "content": f"[{context}]\n" + "\n".join(buf)})
    return chunks

    Store the chunking strategy and parameters in the document's metadata JSON — when you later discover that 800-token chunks outperform 500-token chunks, you need to know which documents used which strategy to re-ingest selectively.

    14.2 Embedding Hygiene

    The embedding API is the most failure-prone step in ingestion. Harden it:

  • → Batch aggressively. Up to 100+ texts per call (provider-dependent). Batching is the difference between 10,000 API calls and 100 for a large corpus.
  • → Retry with backoff and jitter on rate limits (429) and 5xx errors. Never retry on 400s — the input is bad, fix the chunk.
  • → Pin the model version. text-embedding-3-small is not a version — providers update models behind names. Record the exact model version returned by the API in embedding_model.
  • → Validate dimensions on receipt. Assert len(vec) == 1536 before insert — a truncated response that slips into the VECTOR column poisons the index silently.
  • → Normalize text before embedding. Strip excessive whitespace, normalize unicode, remove boilerplate. The embedding should represent content, not formatting accidents.

    14.3 Transactional Storage: The Atomic Unit

    The atomic unit of ingestion is the document: either all of its chunks are stored or none are. Chapter 1's pipeline does this with a single transaction around MERGE + DELETE + bulk INSERT. Three refinements for production:

  • → Bulk insert with Table-Valued Parameters or fast_executemany. Row-by-row inserts of 500 chunks take seconds; batched inserts take milliseconds. For very large documents, SqlBulkCopy (or pyodbc fast_executemany) into a staging table followed by a set-based INSERT…SELECT keeps the transaction short.
  • → Keep transactions short. Do embedding API calls before opening the transaction, not inside it. The transaction should cover only database writes — seconds of API latency inside a transaction holds locks and bloats the log.
  • → Record ingestion metadata. Chunk count, strategy, model version, duration, worker ID — in the document row. When retrieval quality regresses, this metadata is the first place you look.
    • -- Ingestion metadata lives on the document row
ALTER TABLE dbo.documents
    ADD chunk_strategy   NVARCHAR(100) NULL,  -- 'markdown-headers/500t/15%'
        chunk_count      INT NULL,
        ingest_duration_ms INT NULL,
        ingested_by      NVARCHAR(200) NULL,
        ingest_batch_id  UNIQUEIDENTIFIER NULL;  -- group a re-ingest run
GO
-- "Which documents still use the old 800-token strategy?"
SELECT document_id, title, chunk_strategy, chunk_count
FROM dbo.documents
WHERE tenant_id = @tenant_id
  AND chunk_strategy <> N'markdown-headers/500t/15%';

    14.4 Ingestion Observability

    Instrument the pipeline with a dedicated ingestion log — separate from the LLM audit log, because the questions differ:

    CREATE TABLE dbo.ingest_log (
    log_id          UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    tenant_id       UNIQUEIDENTIFIER NOT NULL,
    document_id     UNIQUEIDENTIFIER NULL,
    batch_id        UNIQUEIDENTIFIER NULL,
    stage           NVARCHAR(30) NOT NULL   -- extract/chunk/embed/store
                    CONSTRAINT CK_il_stage CHECK (stage IN
                        (N'extract',N'chunk',N'embed',N'store',N'complete',N'failed')),
    chunks_produced INT NULL,
    duration_ms     INT NULL,
    error_message   NVARCHAR(MAX) NULL,
    created_at      DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);
CREATE INDEX IX_il_batch ON dbo.ingest_log(batch_id, created_at);

-- Pipeline health dashboard queries:
-- 1. Failure rate by stage, last 24h
SELECT stage,
       SUM(CASE WHEN stage = 'failed' THEN 1 ELSE 0 END) AS failures,
       COUNT(*) AS total
FROM dbo.ingest_log
WHERE created_at >= DATEADD(day, -1, SYSUTCDATETIME())
GROUP BY stage;

-- 2. Embed-stage p95 latency trending (catches provider slowdowns)
SELECT CAST(created_at AS DATE) AS day,
       AVG(CAST(duration_ms AS FLOAT)) AS avg_ms,
       MAX(duration_ms) AS max_ms
FROM dbo.ingest_log
WHERE stage = 'embed' AND created_at >= DATEADD(day, -14, SYSUTCDATETIME())
GROUP BY CAST(created_at AS DATE)
ORDER BY day;

    Alert on: failure rate above 1% in any stage, embed p95 latency doubling week-over-week (provider degradation), and queue depth growth (workers not keeping up). Ingestion failures are silent data gaps — nobody complains until the missing document is the one they needed.

    14.5 Handling Poison Documents

    Some documents break pipelines: a 2 GB log file someone uploaded "for the AI to read," a PDF with 50,000 pages, a corrupted file that crashes the parser, a document that is 99% base64-encoded images. The ingestion pipeline needs circuit breakers before these become outages:

  • → Size and page caps enforced at upload: reject files over the limit with a clear message, don't discover the limit mid-parse.
  • → Parse timeouts per document — a parser that hasn't finished in 5 minutes gets killed and the document marked failed_parse, not retried forever.
  • → Content-type sniffing: verify the magic bytes match the extension before parsing — a renamed executable is not a PDF.
  • → Quarantine, don't delete: poison documents land in a quarantine view with the failure reason, so the user understands why their document isn't searchable and support has something concrete to investigate.

    • Track poison-document rates per tenant in the observability dashboard (§14.4): a sudden spike usually means a broken export from the tenant's side, and a proactive "your last 200 uploads failed to parse — here's why" message beats 200 support tickets.

    ---

    Key Takeaways

  • → Match chunking strategy to document structure — recursive splitting for prose, header-aware for markdown, syntactic units for code, header-carrying row groups for tables — and record the strategy per document for selective re-ingestion.
  • → Harden the embedding step: large batches, backoff with jitter, pinned model versions, dimension validation, and text normalization before the API call.
  • → The document is the atomic unit — but keep API calls outside the transaction. Embed first, then open a short transaction for MERGE + DELETE + bulk INSERT.
  • → Log every ingestion stage separately from LLM audit. Alert on stage failure rates, embed latency trends, and queue depth — ingestion gaps are silent until they are critical.
