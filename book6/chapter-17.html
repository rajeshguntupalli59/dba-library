Incremental Indexing and Model Migration

A knowledge base is not a snapshot — documents change, get corrected, expire, and are replaced. The naive approach (re-ingest everything nightly) wastes embedding API budget, churns the vector index, and creates windows where the corpus is half-old and half-new. This chapter builds incremental indexing: detecting what changed, updating only the affected chunks, handling document versioning and deletion, and migrating embedding models without downtime. The goal is a corpus that is always current, with update costs proportional to the change — not to the corpus size.

---

17.1 Change Detection: Hash Before You Embed

The content_hash persisted computed column (§1.2) is the change detector. The sync job compares source documents against stored hashes and classifies each document:

  • → New: hash not present → full ingestion.
  • → Unchanged: hash matches → skip entirely. This is the common case and the source of all savings.
  • → Modified: same document ID, different hash → versioned update (§17.2).
  • → Deleted: document gone from source → tombstone (§17.3).
    • -- Sync classification in one set-based pass.
-- @source is a TVP of (external_id, content_hash, title, ...)
CREATE OR ALTER PROCEDURE dbo.usp_classify_source_changes
    @tenant_id UNIQUEIDENTIFIER,
    @source dbo.SourceDocumentList READONLY
AS
BEGIN
    SET NOCOUNT ON;
    SELECT s.external_id,
           CASE
               WHEN d.document_id IS NULL THEN N'new'
               WHEN d.content_hash <> s.content_hash THEN N'modified'
               ELSE N'unchanged'
           END AS action,
           d.document_id
    FROM @source AS s
    LEFT JOIN dbo.documents AS d
      ON d.tenant_id = @tenant_id AND d.external_id = s.external_id;

    -- Deleted: in our corpus but absent from the source feed
    SELECT d.document_id, d.title
    FROM dbo.documents AS d
    WHERE d.tenant_id = @tenant_id AND d.is_active = 1
      AND NOT EXISTS (SELECT 1 FROM @source AS s
                      WHERE s.external_id = d.external_id);
END;
GO

    The external_id column (source system's document key) is what makes this work across sync runs — add it if you have not already. Hash comparison happens in SQL, so the sync job only downloads content for new and modified documents.

    17.2 Versioned Updates: Replace Without Gaps

    A modified document must never leave the corpus in a half-updated state. The versioned update pattern:

  • → Insert the new version as a new document row (new document_id, same external_id, incremented version), with its chunks fully embedded and stored.
  • → Flip active flags in one transaction: new version is_active = 1, old version is_active = 0. Retrieval filters is_active = 1, so the cutover is atomic — no query ever sees a mix.
  • → Retain old versions per policy (audit, "what did the policy say in March?"). Archive or purge on schedule.
    • ALTER TABLE dbo.documents
    ADD external_id NVARCHAR(500) NULL,
        version     INT NOT NULL DEFAULT 1;
GO

-- Atomic cutover: new version goes live, old version retires, one transaction
CREATE OR ALTER PROCEDURE dbo.usp_publish_document_version
    @new_document_id UNIQUEIDENTIFIER
AS
BEGIN
    SET NOCOUNT ON;
    BEGIN TRAN;
    DECLARE @ext NVARCHAR(500), @tenant UNIQUEIDENTIFIER;
    SELECT @ext = external_id, @tenant = tenant_id
    FROM dbo.documents WHERE document_id = @new_document_id;

    UPDATE dbo.documents
    SET is_active = 0, updated_at = SYSUTCDATETIME()
    WHERE tenant_id = @tenant AND external_id = @ext
      AND document_id <> @new_document_id AND is_active = 1;

    UPDATE dbo.documents
    SET is_active = 1
    WHERE document_id = @new_document_id;
    COMMIT;
END;
GO

    17.3 Deletions and Tombstones

    Deleting a document means deleting its chunks, its embeddings, its full-text entries, and its cached answers — across tables that the foreign keys only partly cover. The tombstone pattern makes deletion safe and auditable:

  • → Mark deleted first (is_active = 0, deleted_at timestamp). Retrieval stops returning it immediately.
  • → Purge asynchronously after a grace period (7–30 days): delete chunks (cascades from the document FK), remove from the embedding cache, invalidate retrieval caches. The grace period allows un-deletion and gives downstream consumers time to react.
  • → Keep the tombstone row (document with no chunks) as the audit record of what was deleted and when — required for compliance in regulated industries.

    17.4 Embedding Model Migration Without Downtime

    Upgrading the embedding model is the most disruptive corpus operation: every vector must be recomputed, and old and new vectors cannot be compared. The dual-write migration:

  • → Phase 1 — backfill. Add a embedding_v2 VECTOR(1536) column (or new dimension if the model changed). A background job re-embeds every chunk with the new model, throttled to stay within API rate limits. The old column keeps serving traffic.
  • → Phase 2 — dual write. New ingestions write both embedding and embedding_v2. Build the new vector index on embedding_v2.
  • → Phase 3 — cutover. When backfill completes, flip the retrieval procedure to embedding_v2 behind a feature flag; compare quality metrics (Chapter 19) for a canary period.
  • → Phase 4 — cleanup. Drop the old column and index, rename embedding_v2 → embedding, update embedding_model.
    • -- Feature-flagged retrieval: one procedure, two vector columns
CREATE OR ALTER PROCEDURE dbo.usp_hybrid_search_v2
    @tenant_id UNIQUEIDENTIFIER, @query_text NVARCHAR(MAX),
    @query_vector_json NVARCHAR(MAX), @match_count INT = 10,
    @use_v2 BIT = 0   -- flag flipped per tenant during canary
AS
BEGIN
    SET NOCOUNT ON;
    IF @use_v2 = 1
        SELECT TOP (@match_count) chunk_id, content,
               VECTOR_DISTANCE('cosine', embedding_v2,
                               CAST(@query_vector_json AS VECTOR(1536))) AS distance
        FROM dbo.document_chunks
        WHERE tenant_id = @tenant_id AND embedding_v2 IS NOT NULL
        ORDER BY VECTOR_DISTANCE('cosine', embedding_v2,
                                 CAST(@query_vector_json AS VECTOR(1536)));
    ELSE
        SELECT TOP (@match_count) chunk_id, content,
               VECTOR_DISTANCE('cosine', embedding,
                               CAST(@query_vector_json AS VECTOR(1536))) AS distance
        FROM dbo.document_chunks
        WHERE tenant_id = @tenant_id AND embedding IS NOT NULL
        ORDER BY VECTOR_DISTANCE('cosine', embedding,
                                 CAST(@query_vector_json AS VECTOR(1536)));
END;
GO

    17.5 The Sync Scheduler

    Tie it together with a scheduled sync job (SQL Agent or an external scheduler): classify changes (§17.1), enqueue new/modified documents to the ingest queue (§13.2), tombstone deletions, and report a summary. Run it on a cadence matched to source volatility — hourly for news-like corpora, daily for documentation, weekly for reference material. The classification query is set-based and cheap; the expensive work (embedding) only happens for genuinely changed documents.

    ---

    17.6 Rollback Plan for Failed Migrations

    Every migration in §17.5 needs a tested rollback, because the failure you discover at 2 AM is always the one the plan didn't cover. The dual-column design (§17.3) makes rollback trivial: the cutover is a metadata update pointing reads at the new column, so rollback is the same update in reverse — one statement, seconds to execute. What makes rollback safe rather than merely fast is the preparation: keep the old column and its index for at least one full retention window after cutover (disk is cheap, re-embedding is not), snapshot the pre-migration recall metrics so you can prove the rollback restored quality, and rehearse the rollback on a staging copy before the production cutover. The rollback runbook fits on an index card: detect (recall drop > 2 points or error spike), decide (on-call has unilateral authority — no committee at 2 AM), execute (one UPDATE to the routing metadata), verify (smoke queries + dashboard), then investigate at leisure. A migration without a rehearsed rollback is a hope, not a plan.

    ---

    Key Takeaways

  • → Hash before you embed: classify every source document as new/modified/unchanged/deleted with set-based hash comparison, and only pay embedding costs for genuine changes.
  • → Version documents with atomic cutover — new version fully ingested first, then a single transaction flips is_active. Retrieval never sees a half-updated document.
  • → Tombstone deletions with a grace period before async purge; keep the tombstone row as the compliance audit record.
  • → Migrate embedding models with dual-write and a feature-flagged retrieval procedure: backfill → dual write → canary cutover → cleanup. Never mix vector spaces in one searchable set.
