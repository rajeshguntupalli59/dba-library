Change Tracking for Real-Time AI Triggers

AI applications need to react to data changes: a new support ticket arrives → draft a response; a document is updated → re-embed it; a user's plan changes → adjust their quotas. Polling the database every few seconds is the naive answer — wasteful, latent, and blind to what actually changed. SQL Server's Change Tracking tells you exactly which rows changed since a version number, with minimal overhead. This chapter builds real-time AI triggers on Change Tracking: the enablement pattern, the poll-and-react worker, change-driven re-embedding, and when to graduate to Change Data Capture (Chapter 30) instead.

---

27.1 Enabling Change Tracking

Change Tracking is a database-level feature with per-table opt-in. It records, per table, the primary keys of changed rows and the change version — not the changed data itself, which keeps overhead minimal:

-- Enable at the database level (retention: how long change metadata is kept)
ALTER DATABASE aiapp
SET CHANGE_TRACKING = ON
(CHANGE_RETENTION = 2 DAYS, AUTO_CLEANUP = ON);
GO

-- Opt in the tables AI triggers care about
ALTER TABLE dbo.documents ENABLE CHANGE_TRACKING
WITH (TRACK_COLUMNS_UPDATED = ON);
ALTER TABLE dbo.users ENABLE CHANGE_TRACKING;
ALTER TABLE dbo.orders ENABLE CHANGE_TRACKING
WITH (TRACK_COLUMNS_UPDATED = ON);
GO

-- What changed since version @last_version? The core query pattern.
DECLARE @last_version BIGINT = 12345;  -- persisted by the worker (see §27.2)
SELECT d.document_id,
       ct.SYS_CHANGE_OPERATION AS op,       -- I, U, D
       ct.SYS_CHANGE_COLUMNS AS changed_cols,
       ct.SYS_CHANGE_VERSION AS ver
FROM CHANGETABLE(CHANGES dbo.documents, @last_version) AS ct
LEFT JOIN dbo.documents AS d ON d.document_id = ct.document_id;
-- For deletes (op = 'D'), the LEFT JOIN yields NULLs — the key comes from ct.

TRACK_COLUMNS_UPDATED = ON records which columns changed — essential for triggers that only care about specific columns (re-embed when content changes, ignore updated_at touches). Without it, every update looks the same.

27.2 The Poll-and-React Worker

Change Tracking is poll-based: a worker asks "what changed since my last version?" on a loop. The version cursor is the worker's state — persisted in a table so restarts resume without gaps or replays:

CREATE TABLE dbo.change_cursors (
    cursor_name   NVARCHAR(200) PRIMARY KEY,  -- 'doc_reembed', 'ticket_triage'
    last_version  BIGINT NOT NULL,
    updated_at    DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);

# Worker loop (Python): poll, react, advance cursor — all transactional
def run_trigger(cursor_name, poll_interval_s=5):
    while True:
        with db() as conn:
            cur = conn.cursor()
            last = cur.execute(
                "SELECT last_version FROM dbo.change_cursors WHERE cursor_name = ?",
                cursor_name).fetchone()[0]
            current = cur.execute(
                "SELECT CHANGE_TRACKING_CURRENT_VERSION()").fetchone()[0]

            # Guard: if retention expired our version, resync from scratch
            min_valid = cur.execute(
                "SELECT CHANGE_TRACKING_MIN_VALID_VERSION("
                "OBJECT_ID('dbo.documents'))").fetchone()[0]
            if last < min_valid:
                last = min_valid  # some changes may be missed: log + alert
                log_resync(cursor_name, last)

            changes = cur.execute("""
                SELECT ct.document_id, ct.SYS_CHANGE_OPERATION AS op
                FROM CHANGETABLE(CHANGES dbo.documents, ?) AS ct
            """, last).fetchall()

            for doc_id, op in changes:
                react_to_change(cursor_name, doc_id, op)  # enqueue work

            cur.execute(
                "UPDATE dbo.change_cursors SET last_version = ?, "
                "updated_at = SYSUTCDATETIME() WHERE cursor_name = ?",
                current, cursor_name)
            conn.commit()
        time.sleep(poll_interval_s)

The retention guard is the critical correctness detail: if the worker is down longer than CHANGE_RETENTION, change metadata is cleaned up and the cursor is invalid. The worker must detect this (CHANGE_TRACKING_MIN_VALID_VERSION) and resynchronize — for the document trigger, that means a full hash-comparison sweep (§17.1).

27.3 Trigger Patterns for AI Workflows

  • → Document changed → re-embed. The worker enqueues modified documents to the ingest queue (§13.2). Column tracking ensures only content changes trigger re-embedding — metadata edits don't waste API budget.
  • → New ticket/order → agentic triage. An insert into the tickets table starts an agent run (§20.1) that classifies, drafts a response, and requests approval — the real-time support copilot.
  • → User plan changed → quota refresh. A plan upgrade updates tenant_config and resets buckets immediately, instead of waiting for the next billing cycle job.
  • → Feedback received → eval signal. A down-vote insert triggers the promotion-to-golden-set review queue (§19.5) — the feedback loop reacting in minutes, not weeks.
    • -- Column-aware reaction: only re-embed when content actually changed
-- (SYS_CHANGE_COLUMNS bitmask → check the content column's bit)
DECLARE @content_col_id INT = COLUMNPROPERTY(
    OBJECT_ID('dbo.documents'), 'content', 'ColumnId');

SELECT ct.document_id
FROM CHANGETABLE(CHANGES dbo.documents, @last_version) AS ct
WHERE ct.SYS_CHANGE_OPERATION IN ('I', 'U')
  AND (ct.SYS_CHANGE_COLUMNS IS NULL  -- NULL = all columns (bulk ops)
       OR CHANGE_TRACKING_IS_COLUMN_IN_MASK(@content_col_id,
                                            ct.SYS_CHANGE_COLUMNS) = 1);

    27.4 Change Tracking vs. Change Data Capture

    Change Tracking answers "which rows changed"; Change Data Capture (Chapter 30) answers "what did the rows look like before and after." Choose by the question:

  • → Change Tracking: lightweight, synchronous, minimal storage. Right when the reaction re-reads the current row anyway (re-embed reads the document; triage reads the ticket). This chapter's triggers.
  • → Change Data Capture: asynchronous log-based capture of before/after images. Right when the reaction needs the old values (audit diffs, feature pipelines computing deltas, syncing to a warehouse). Chapter 30.

    • They compose: Change Tracking for the low-latency trigger ("something changed, go look"), CDC for the analytical consumption ("here's exactly what changed"). Enable both on the tables that need both — the overheads are independent.

    ---

    27.5 Fan-Out: One Change, Many Reactions

    Real systems rarely have one trigger per table — a document change should re-embed the document, invalidate the semantic cache, notify the query-notification subscribers, and update the tenant's search analytics. The naive approach (one poll loop per reaction) multiplies database load; the better pattern is a single change-feed worker that fans out. The worker polls Change Tracking once per table, then publishes the change set to Service Broker (§28.1) — one message per reaction type — and each activated handler processes its own concern independently. Reactions become independently scalable (add queue readers to the slow one), independently retryable (a failed cache invalidation doesn't block re-embedding), and independently observable (queue depth per reaction type shows exactly which downstream is struggling). The fan-out also decouples producers from consumers: adding a fifth reaction to document changes means adding a handler, not touching the poll loop. Keep the fan-out mapping in a table (table → reaction → enabled) so reactions can be toggled without deployments — the on-call will thank you when they need to pause re-embedding during an incident without stopping triage.

    ---

    Key Takeaways

  • → Use Change Tracking for "which rows changed" triggers — minimal overhead, synchronous, with TRACK_COLUMNS_UPDATED so reactions fire only on relevant column changes.
  • → Persist the version cursor per trigger and guard against retention expiry with CHANGE_TRACKING_MIN_VALID_VERSION — a worker down longer than retention must resynchronize, not resume blindly.
  • → Reactions enqueue work; they don't do work. The poll loop stays fast and transactional; the ingest queue, agent runs, and quota procedures do the heavy lifting.
  • → Choose Change Tracking vs. CDC by the question: "which rows" → CT; "what did they look like before/after" → CDC. Enable both where both questions matter.
