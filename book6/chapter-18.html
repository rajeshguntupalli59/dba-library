Multi-Tenant RAG Architectures

Every table in this book carries a tenant_id. This chapter explains the tenancy architecture those columns implement: the three tenancy models (silo, pool, bridge) and when each fits, how the pooled model — one database, all tenants — stays safe and fast at scale, per-tenant configuration and quotas, the noisy-neighbor problem in vector search, and the migration path from pooled to siloed when a tenant outgrows the pool. Multi-tenancy done right is invisible to tenants and cheap to operate; done wrong it is a breach waiting for a headline.

---

18.1 The Three Tenancy Models

  • → Silo: one database per tenant. Maximum isolation, per-tenant scaling and backup, but N databases to patch, monitor, and pay for. Right for enterprise tenants with compliance mandates (data residency, dedicated encryption keys) and for your largest 5% of tenants.
  • → Pool: one database, all tenants. tenant_id on every row, RLS enforcing boundaries. Cheapest to operate, fastest to onboard — a new tenant is an INSERT, not a provisioning workflow. Right for the long tail of small-to-medium tenants. This book's default.
  • → Bridge: pools for the tail, silos for the head. Tenants start pooled and graduate to silos on size, compliance need, or willingness to pay. The application routes by a tenant registry. This is where most successful SaaS products end up.
    • -- Tenant registry: where each tenant lives and how they're configured
CREATE TABLE dbo.tenant_registry (
    tenant_id       UNIQUEIDENTIFIER PRIMARY KEY,
    name            NVARCHAR(200) NOT NULL,
    deployment      NVARCHAR(20) NOT NULL DEFAULT N'pooled'
                    CONSTRAINT CK_tr_deployment CHECK (deployment IN
                        (N'pooled', N'silo')),
    -- For silo tenants: which server/database
    server_name     NVARCHAR(200) NULL,
    database_name   NVARCHAR(200) NULL,
    -- Per-tenant knobs (pooled tenants share the database's)
    embedding_model NVARCHAR(100) NOT NULL DEFAULT N'text-embedding-3-small',
    vector_metric   NVARCHAR(20) NOT NULL DEFAULT N'cosine',
    monthly_token_quota BIGINT NULL,
    data_residency  NVARCHAR(50) NULL,   -- e.g. 'EU', 'US'
    created_at      DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);

    The registry makes the bridge model a routing decision: the API looks up the tenant's deployment and opens the right connection string. Pooled tenants share the procedures in this book; silo tenants get their own database with the same schema.

    18.2 Making the Pool Fast: Tenant-First Indexing

    In the pooled model, every query filters by tenant. Index design follows one rule: tenant_id leads every composite index. This gives the optimizer partition-like elimination — queries touch only the tenant's slice of each index.

    -- Tenant-first indexing across the hot tables
CREATE INDEX IX_chunks_tenant_doc
    ON dbo.document_chunks(tenant_id, document_id, chunk_index);
CREATE INDEX IX_messages_tenant_time
    ON dbo.messages(tenant_id, created_at DESC)
    INCLUDE (conversation_id, role, token_count);
CREATE INDEX IX_audit_tenant_time
    ON dbo.llm_audit_log(tenant_id, created_at DESC)
    INCLUDE (model, status, total_tokens);

-- For very large pools, partitioned alignment: partition the chunks table
-- by tenant hash so each tenant's data is physically clustered.
CREATE PARTITION FUNCTION PF_tenant_hash (INT)
    AS RANGE LEFT FOR VALUES (0,1,2,3,4,5,6,7);  -- 8 partitions
CREATE PARTITION SCHEME PS_tenant_hash AS PARTITION PF_tenant_hash ALL TO ([PRIMARY]);
-- tenant_bucket = ABS(CHECKSUM(tenant_id)) % 8 as persisted computed column,
-- then partition the table on it. Partition elimination per tenant query.

    For vector search specifically, the single shared DiskANN index with a tenant predicate (§15.1) works well into the millions of chunks. Beyond that, consider per-tenant filtered vector indexes for your largest tenants — the vector index equivalent of graduation to a silo, without moving the data.

    18.3 The Noisy-Neighbor Problem

    Tenant A runs a 10-million-chunk backfill; Tenant B's chat latency triples. Three mitigations, in escalating order:

  • → Workload isolation with Resource Governor. Classify sessions by login or application name into workload groups with CPU and memory caps. The ingestion workers' group gets a ceiling; the interactive API group gets a floor.
  • → Throttled ingestion per tenant. The claim procedure (§13.2) takes a per-tenant concurrency limit from the registry — no tenant's backfill starves others' incremental updates.
  • → Graduation. A tenant that consistently exceeds its fair share gets moved to a silo (or a dedicated elastic pool on Azure SQL). The registry makes this a data migration, not an application rewrite.
    • -- Resource Governor: cap the ingestion workload's CPU
CREATE WORKLOAD GROUP wg_ingestion WITH (REQUEST_MAX_CPU_TIME_SEC = 3600);
CREATE WORKLOAD GROUP wg_interactive WITH (REQUEST_MAX_CPU_TIME_SEC = 60);
-- Classifier function routes by login: svc_ingest → wg_ingestion,
-- svc_api → wg_interactive. Interactive queries always get CPU headroom.

    18.4 Per-Tenant Configuration and Quotas

    Tenants differ: embedding models, retrieval depth, prompt versions, token quotas. Store per-tenant configuration in the registry and resolve it once per request:

    CREATE TABLE dbo.tenant_config (
    tenant_id       UNIQUEIDENTIFIER PRIMARY KEY
                    CONSTRAINT FK_tc_tenant REFERENCES dbo.tenants(tenant_id),
    retrieval_k     INT NOT NULL DEFAULT 8,
    similarity_floor DECIMAL(3,2) NOT NULL DEFAULT 0.70,
    enable_rerank   BIT NOT NULL DEFAULT 0,
    monthly_token_quota BIGINT NULL,       -- NULL = unlimited
    tokens_used_this_month BIGINT NOT NULL DEFAULT 0,
    quota_reset_at  DATETIME2 NOT NULL,
    CONSTRAINT CK_tc_k CHECK (retrieval_k BETWEEN 1 AND 50)
);

-- Atomic quota check-and-decrement: exactly one statement, no race
CREATE OR ALTER PROCEDURE dbo.usp_consume_quota
    @tenant_id UNIQUEIDENTIFIER, @tokens INT
AS
BEGIN
    SET NOCOUNT ON;
    UPDATE dbo.tenant_config
    SET tokens_used_this_month = tokens_used_this_month + @tokens
    OUTPUT INSERTED.tokens_used_this_month, INSERTED.monthly_token_quota
    WHERE tenant_id = @tenant_id
      AND (monthly_token_quota IS NULL
           OR tokens_used_this_month + @tokens <= monthly_token_quota);
    IF @@ROWCOUNT = 0
        THROW 50003, 'Monthly token quota exceeded.', 1;
END;
GO

    The single-statement UPDATE…WHERE is the pattern: the quota check and the decrement are atomic, so concurrent requests cannot overshoot. A monthly SQL Agent job resets tokens_used_this_month and advances quota_reset_at.

    18.5 Graduating a Tenant to a Silo

    When a tenant outgrows the pool, migrate with zero downtime:

  • → Provision the silo database with the same schema (source-controlled migrations make this a script run).
  • → Backfill the tenant's rows (all tables, WHERE tenant_id = @t) into the silo. For large tenants, use incremental batches keyed on created_at.
  • → Dual-write new rows to both pool and silo during a cutover window (application feature flag).
  • → Verify row counts match, then flip the registry's deployment to silo — the API routes to the new database on the next request.
  • → Purge the tenant's rows from the pool after a retention window.

    • Because every procedure in this book takes @tenant_id and the schema is identical, the silo database needs no application changes — only the connection string changes, driven by the registry.

    ---

    Key Takeaways

  • → Default to the pooled model, design for the bridge model. One database with tenant_id everywhere and RLS enforcement; the tenant registry routes tenants to pools or silos without application changes.
  • → tenant_id leads every composite index — and consider hash-partitioning the largest tables by tenant for physical isolation within the pool.
  • → Fight noisy neighbors with Resource Governor, per-tenant ingestion throttles, and graduation. A tenant that outgrows its fair share gets a silo, not an apology.
  • → Make quota consumption a single atomic UPDATE…WHERE statement so concurrent requests cannot overshoot, and resolve per-tenant config once per request from the registry.
