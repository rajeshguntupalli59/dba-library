Audit Logging Every AI Action in SQL Server

Every LLM call, every tool execution, every prompt version, every token spent — in a production AI application, all of it must be recorded. Audit logs are the difference between "the AI did something wrong and we don't know what" and a precise, timestamped, replayable record. This chapter builds the complete audit story: what to log and at which granularity, the schema that keeps high-volume logging fast, tamper-evidence for compliance, and the queries that turn audit rows into incident timelines, cost reports, and behavior forensics.

---

24.1 What Gets Logged: The Audit Contract

Log at three granularities, each serving a different consumer:

  • → Request level (llm_audit_log, §1.2). One row per LLM call: model, tokens, latency, status, tenant, user, conversation. Consumers: billing, cost attribution (Chapter 33), latency dashboards.
  • → Action level (agent_actions, §20.3). One row per tool call: arguments, results, approval linkage. Consumers: debugging, compliance, evaluation replay.
  • → Prompt level (new). The exact prompt sent and the exact completion received, stored for a shorter retention window. Consumers: incident forensics ("what exactly did the model see?"), prompt regression analysis. This is the most sensitive tier — prompts contain user data.
    • -- Prompt-level audit: full fidelity, short retention, restricted access
CREATE TABLE dbo.prompt_audit (
    prompt_audit_id UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    log_id          UNIQUEIDENTIFIER NOT NULL   -- FK to llm_audit_log
                    CONSTRAINT FK_pa_log REFERENCES dbo.llm_audit_log(log_id),
    tenant_id       UNIQUEIDENTIFIER NOT NULL,
    system_prompt   NVARCHAR(MAX) NOT NULL,
    messages_json   JSON NOT NULL,             -- the full message array sent
    completion_json JSON NULL,                 -- the raw provider response
    prompt_hash     CHAR(64) NOT NULL,         -- SHA2_256 for dedup/lookup
    created_at      DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);
-- Partitioned monthly (§4.6); retention 90 days, then purged.
-- Access: support-lead role only; every read logged (see §24.4).

    The prompt audit is deliberately separate from the request log: different retention (90 days vs. years), different access control (support-leads only), and different storage economics (prompts are large). Never mix tiers — a single table with mixed retention is a compliance trap.

    24.2 Write Path: Fast, Non-Blocking, Never Lost

    Audit writes happen on the hottest path in the system — every chat turn. Three techniques keep them from becoming the bottleneck:

  • → Write in the request transaction (§1.5), but keep the row narrow. The request-level row is fixed-width-ish and cheap. The prompt-level payload goes to a separate table written by a background worker reading from a queue — never block the chat response on a multi-kilobyte prompt write.
  • → Minimal indexing on the write path. The clustered key plus the two or three indexes from §1.2. Analytical indexes (columnstore, §4.5) absorb the read load without burdening inserts.
  • → Delayed durability for the prompt tier only. Request-level audit must be fully durable (billing depends on it); prompt payloads can tolerate the small data-loss window of delayed durability in exchange for much higher throughput.
    • -- Background prompt-audit writer: dequeue, write, done.
-- The chat path enqueues (Service Broker or table queue); this worker persists.
CREATE OR ALTER PROCEDURE dbo.usp_flush_prompt_audit
AS
BEGIN
    SET NOCOUNT ON;
    -- Claim a batch with READPAST (same pattern as §13.2)
    WITH claimed AS (
        SELECT TOP (500) queue_id, log_id, tenant_id,
               system_prompt, messages_json, completion_json, prompt_hash
        FROM dbo.prompt_audit_queue WITH (READPAST, UPDLOCK, ROWLOCK)
        WHERE status = N'pending'
        ORDER BY created_at
    )
    INSERT INTO dbo.prompt_audit
        (log_id, tenant_id, system_prompt, messages_json,
         completion_json, prompt_hash)
    OUTPUT INSERTED.log_id INTO @done
    SELECT log_id, tenant_id, system_prompt, messages_json,
           completion_json, prompt_hash
    FROM claimed;
    -- Mark claimed rows done in the same transaction.
END;
GO

    24.3 Tamper-Evidence: Hash-Chained Audit Logs

    For regulated industries, "we logged it" is not enough — you must prove the log was not altered. Hash chaining makes each row cryptographically commit to all previous rows:

    -- Each audit row chains to the previous row's hash.
-- Altering any historical row breaks every subsequent chain link.
ALTER TABLE dbo.llm_audit_log
    ADD chain_hash CHAR(64) NULL,
        prev_chain_hash CHAR(64) NULL;
GO

-- Maintained by the insert procedure (single writer serialization per day
-- partition keeps this contention-free in practice):
--   prev = SELECT TOP 1 chain_hash FROM dbo.llm_audit_log ORDER BY created_at DESC
--   chain_hash = SHA2_256(CONCAT(prev, log_id, tenant_id, model,
--                                total_tokens, created_at))
--
-- Nightly verifier job recomputes the chain; any mismatch pages the team.
-- For stronger guarantees, anchor the daily terminal hash externally
-- (write it to immutable blob storage) — then tampering requires
-- rewriting both the database and the external anchor.

    Hash chaining is cheap (one hash per insert, one verification pass nightly) and converts "trust us" into "verify us." Pair it with SQL Server Audit (the built-in feature) capturing DDL and privileged access — the chain proves the rows are intact; SQL Server Audit proves nobody bypassed the application to change them.

    24.4 Forensics Queries: From Rows to Timelines

    The audit schema pays for itself during incidents. The essential forensic queries:

    -- Incident timeline: everything one user did in a window
SELECT a.created_at, a.model, c.title AS conversation,
       a.prompt_tokens, a.completion_tokens, a.status, a.latency_ms,
       LEFT(pa.system_prompt, 120) AS prompt_preview
FROM dbo.llm_audit_log AS a
LEFT JOIN dbo.conversations AS c ON c.conversation_id = a.conversation_id
LEFT JOIN dbo.prompt_audit AS pa ON pa.log_id = a.log_id
WHERE a.user_id = @user_id
  AND a.created_at BETWEEN @from AND @to
ORDER BY a.created_at;

-- Blast radius: which tenants were affected by a bad prompt version?
SELECT a.tenant_id, COUNT(*) AS calls,
       SUM(CASE WHEN f.rating = 'down' THEN 1 ELSE 0 END) AS downvotes
FROM dbo.llm_audit_log AS a
LEFT JOIN dbo.answer_feedback AS f ON f.message_id IN (
    SELECT message_id FROM dbo.messages WHERE conversation_id = a.conversation_id)
WHERE a.created_at >= @deploy_time
GROUP BY a.tenant_id ORDER BY downvotes DESC;

-- Cost spike forensics: what drove yesterday's token surge?
SELECT TOP 20 a.user_id, SUM(a.total_tokens) AS tokens, COUNT(*) AS calls,
       AVG(CAST(a.latency_ms AS FLOAT)) AS avg_latency
FROM dbo.llm_audit_log AS a
WHERE a.created_at >= DATEADD(day, -1, SYSUTCDATETIME())
GROUP BY a.user_id ORDER BY tokens DESC;

    Build these as saved procedures or views before you need them — during an incident is the wrong time to be writing forensic SQL.

    24.5 Access Reviews for Audit Data

    Audit logs concentrate everything sensitive — prompts, user data, behavior patterns — which makes access to the audit log itself a privileged operation requiring oversight. Run quarterly access reviews: who holds the support-lead role that can read prompt_audit, is each grant still justified, and does the read-log show access patterns consistent with their job? Automate the evidence gathering (role membership from the database, read counts from the access log) so the review is a 30-minute sign-off, not a week-long project. Revoke aggressively — audit access should be the hardest permission in the system to keep, because it is the permission that watches all the others.

    ---

    Key Takeaways

  • → Audit at three granularities with separate tables and retentions: request level (billing, years), action level (debugging/compliance, years), prompt level (forensics, 90 days, restricted access).
  • → Keep audit writes off the critical path: narrow rows in the request transaction, bulky prompt payloads via a background queue worker, minimal write-path indexing, delayed durability only for the prompt tier.
  • → Hash-chain the audit log and anchor daily terminal hashes externally for tamper-evidence; pair with SQL Server Audit for privileged-access coverage.
  • → Pre-build forensic queries as procedures — incident timelines, blast-radius analysis, cost-spike forensics — before the incident happens.
