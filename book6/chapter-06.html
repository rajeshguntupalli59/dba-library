Storing Conversation History in SQL Server

Conversation history is the working memory of every AI application: the ordered list of turns that lets the model maintain context across a multi-turn dialogue. It sounds trivial — "just store the messages" — until you face the real requirements: loading the last N turns in milliseconds, enforcing per-user isolation, counting tokens accurately for billing and context-window management, handling edits and regenerations, and aging out old conversations without downtime. This chapter builds the production history store on the messages table from Chapter 1, with the indexes, procedures, and maintenance jobs that keep it fast at millions of rows.

---

6.1 The Message Model

The messages table from §1.2 stores each turn with its role, content, token count, model metadata, citations, and tool calls. Three refinements make it production-grade:

  • → Immutable messages. Never UPDATE a message's content. Edits and regenerations are new rows (see §6.4). Immutability makes caching safe, auditing trivial, and replication conflict-free.
  • → Sequence within the conversation. A seq integer per conversation gives you gap-free ordering even when two messages share a timestamp — which happens constantly under concurrency.
  • → Token counts at write time. Count tokens when the message is created (the application knows the model and tokenizer) and store the count. Recomputing tokens on read is wasteful and tokenizer-version-dependent.
    • -- Refinements to the messages table for production history
ALTER TABLE dbo.messages ADD seq INT NULL;
GO

-- Backfill + enforce gap-free sequencing per conversation
WITH ranked AS (
    SELECT message_id,
           ROW_NUMBER() OVER (PARTITION BY conversation_id
                              ORDER BY created_at, message_id) AS rn
    FROM dbo.messages
)
UPDATE m SET m.seq = r.rn
FROM dbo.messages AS m JOIN ranked AS r ON m.message_id = r.message_id;
GO
ALTER TABLE dbo.messages ALTER COLUMN seq INT NOT NULL;
GO

-- The hot index: conversation history loads are always
-- "this conversation, most recent first"
CREATE UNIQUE INDEX IX_messages_conversation_seq
    ON dbo.messages (conversation_id, seq DESC)
    INCLUDE (role, content, token_count, model, created_at);
GO

-- Insert procedure assigns the next sequence number atomically
CREATE OR ALTER PROCEDURE dbo.usp_append_message
    @conversation_id UNIQUEIDENTIFIER,
    @tenant_id       UNIQUEIDENTIFIER,
    @role            NVARCHAR(20),
    @content         NVARCHAR(MAX),
    @token_count     INT = NULL,
    @model           NVARCHAR(100) = NULL,
    @citations       JSON = NULL,
    @tool_calls      JSON = NULL,
    @latency_ms      INT = NULL
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @seq INT;
    -- UPDLOCK + HOLDLOCK serializes appends within one conversation
    SELECT @seq = ISNULL(MAX(seq), 0) + 1
    FROM dbo.messages WITH (UPDLOCK, HOLDLOCK)
    WHERE conversation_id = @conversation_id;

    INSERT INTO dbo.messages
        (conversation_id, tenant_id, role, content, token_count,
         model, citations, tool_calls, latency_ms, seq)
    OUTPUT INSERTED.message_id, INSERTED.seq
    VALUES (@conversation_id, @tenant_id, @role, @content, @token_count,
            @model, @citations, @tool_calls, @latency_ms, @seq);
END;
GO

    The UPDLOCK, HOLDLOCK hint serializes concurrent appends to the same conversation — two parallel tool-call completions cannot grab the same sequence number. The covering index means the history load never touches the clustered index.

    6.2 Loading History: Windowing for the Context Budget

    The model has a finite context window; history loading is a budgeting problem. The standard policy: take the most recent turns that fit within a token budget, always keeping the system prompt and the latest user message:

    -- Load the most recent messages fitting a token budget.
-- Oldest-first output, ready to append to the LLM message list.
CREATE OR ALTER PROCEDURE dbo.usp_load_history_window
    @conversation_id UNIQUEIDENTIFIER,
    @token_budget    INT = 6000
AS
BEGIN
    SET NOCOUNT ON;
    WITH ordered AS (
        SELECT role, content, token_count, seq,
               SUM(ISNULL(token_count, 0)) OVER (
                   ORDER BY seq DESC
                   ROWS UNBOUNDED PRECEDING) AS running_tokens
        FROM dbo.messages
        WHERE conversation_id = @conversation_id
    )
    SELECT role, content, token_count
    FROM ordered
    WHERE running_tokens - ISNULL(token_count, 0) < @token_budget
    ORDER BY seq ASC;
END;
GO

    The window function accumulates tokens from newest to oldest; the filter keeps every message whose predecessors fit the budget. When history exceeds the budget, the oldest turns fall off — which is exactly when Chapter 11's summarization takes over, replacing dropped turns with a compressed summary so context is never silently lost.

    6.3 Token Accounting: The Running Total

    The conversations table carries total_tokens as a maintained aggregate — updated by the same transaction that appends messages. Do not compute it with SUM() on read; at millions of messages that aggregation becomes the slowest part of loading a conversation list.

    -- Maintain the aggregate in the append procedure (add to usp_append_message)
-- or via an AFTER INSERT trigger for writers that bypass the procedure:
CREATE OR ALTER TRIGGER dbo.trg_messages_token_rollup
ON dbo.messages AFTER INSERT
AS
BEGIN
    SET NOCOUNT ON;
    UPDATE c
    SET c.total_tokens = c.total_tokens + i.tokens_added,
        c.updated_at   = SYSUTCDATETIME()
    FROM dbo.conversations AS c
    JOIN (SELECT conversation_id, SUM(ISNULL(token_count, 0)) AS tokens_added
          FROM inserted GROUP BY conversation_id) AS i
      ON c.conversation_id = i.conversation_id;
END;
GO

-- Reconciliation job: heal any drift (e.g., from backfills) nightly
-- using a set-based MERGE rather than row-by-row fixes.
CREATE OR ALTER PROCEDURE dbo.usp_reconcile_token_totals
AS
BEGIN
    SET NOCOUNT ON;
    WITH actual AS (
        SELECT conversation_id, SUM(ISNULL(token_count, 0)) AS real_total
        FROM dbo.messages GROUP BY conversation_id
    )
    UPDATE c
    SET c.total_tokens = a.real_total
    FROM dbo.conversations AS c
    JOIN actual AS a ON c.conversation_id = a.conversation_id
    WHERE c.total_tokens <> a.real_total;
END;
GO

    6.4 Edits, Regenerations, and Branches

    Real users edit their messages and regenerate answers. Because messages are immutable, these become new rows with lineage:

  • → Edited user message: insert a new message row with supersedes pointing at the old row; the old row stays for audit. History loads filter to the latest version per logical turn.
  • → Regenerated assistant answer: same pattern — new row, supersedes the previous answer. Keep both: the discarded answer is valuable training signal for evaluation (Chapter 19).
  • → Branching ("retry from here"): new messages get a branch_id; the conversation forks without duplicating shared prefix rows.
    • ALTER TABLE dbo.messages
    ADD supersedes_message_id UNIQUEIDENTIFIER NULL
        CONSTRAINT FK_messages_supersedes
        REFERENCES dbo.messages(message_id),
        branch_id UNIQUEIDENTIFIER NULL,
        is_current BIT NOT NULL DEFAULT 1;
GO

-- History load that respects edits: latest version of each logical turn
CREATE OR ALTER PROCEDURE dbo.usp_load_history_current
    @conversation_id UNIQUEIDENTIFIER,
    @branch_id       UNIQUEIDENTIFIER = NULL
AS
BEGIN
    SET NOCOUNT ON;
    SELECT role, content, token_count
    FROM dbo.messages
    WHERE conversation_id = @conversation_id
      AND is_current = 1
      AND (@branch_id IS NULL OR branch_id IS NULL OR branch_id = @branch_id)
    ORDER BY seq ASC;
END;
GO

    When a regeneration supersedes an answer, set is_current = 0 on the old row in the same transaction that inserts the new one. The audit trail stays complete; the model only ever sees current rows.

    6.5 Retention and Archival

    Conversation history grows forever unless you plan otherwise. The tiered strategy:

  • → Hot (0–90 days): rowstore with the covering index from §6.1. All interactive loads hit this tier.
  • → Warm (90 days–2 years): monthly partitions (§4.6) with a columnstore index. Conversation replays and analytics still work; single-conversation loads stay fast via partition elimination.
  • → Cold (2+ years or per policy): partition switch-out to an archive table on cheaper storage, or export to Parquet in Azure Blob Storage. The conversation list shows archived conversations with their summaries (Chapter 11) so the UI never shows a hole.

    • Implement the aging as a monthly SQL Agent job that switches the oldest hot partition to warm and the oldest warm partition to the archive table. No DELETEs, no log bloat, no blocking — partition switching is metadata-only.

    ---

    Key Takeaways

  • → Messages are immutable; edits and regenerations are new rows with lineage. The is_current flag keeps model-visible history clean while the audit trail stays complete.
  • → A per-conversation sequence number plus a covering index makes history loads a single index seek. Serialize appends with UPDLOCK/HOLDLOCK to keep sequences gap-free under concurrency.
  • → Load history against a token budget with a running-total window function, and maintain total_tokens as a write-time aggregate — never SUM() on read.
  • → Tier retention hot → warm → cold with monthly partitions and switch-out archival. Metadata-only moves, no mass deletes, and summaries keep the UI complete for archived conversations.
