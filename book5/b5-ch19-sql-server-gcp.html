Chapter 19: Running SQL Server on Google Cloud: Cloud SQL for SQL Server and GCE

AWS and Azure dominate the SQL Server cloud conversation, but Google Cloud is a legitimate third option — especially for organizations already committed to GCP for analytics, Kubernetes, or data engineering. SQL Server on Google Cloud comes in two flavors: Cloud SQL for SQL Server (the managed service) and SQL Server on Compute Engine (self-managed VMs, the EC2/Azure-VM analog). This chapter covers both, the licensing mechanics unique to GCP, and when GCP is the right cloud for a SQL Server workload at all.

19.1 Cloud SQL for SQL Server: The Managed Option

Cloud SQL for SQL Server is GCP's analog to RDS: automated backups, point-in-time recovery, patching, and high availability via regional persistent disks with automatic failover. The supported versions track the current SQL Server releases (2019, 2022, and newer as Google adds them), in Web, Standard, and Enterprise editions. Key characteristics SQL Server DBAs should know:

  • → HA via regional disks, not AGs. Like RDS Multi-AZ, Cloud SQL HA keeps a standby in another zone with synchronous disk-level replication and automatic failover — you do not get readable secondaries or AG-level control. If you need readable secondaries on GCP, you need Compute Engine.
  • → No SQL Server Agent on some tiers. Agent availability and capability on Cloud SQL is limited compared to self-managed — check the current feature matrix for job scheduling, and plan on Cloud Scheduler + Cloud Functions or Workflows for orchestration (the Chapter 12 patterns, GCP-flavored).
  • → Connectivity via private IP and the Auth Proxy. The Cloud SQL Auth Proxy provides IAM-based, encrypted connectivity without exposing the instance publicly — the GCP analog to RDS Proxy's connection management and Azure Private Link. Private IP on your VPC is the production standard.
  • → Storage autoscaling. Cloud SQL can grow storage automatically as data grows (up to configured limits), which removes the manual storage-scaling runbook — at the cost of storage that only grows, never shrinks.

    • 19.2 Licensing on GCP

    Cloud SQL for SQL Server is license-included: the per-hour price bundles the SQL Server license, with edition (Web/Standard/Enterprise) as a pricing dimension. For Compute Engine, GCP supports both license-included VM images and bring-your-own-license via sole-tenant nodes (dedicated hardware, which satisfies license-mobility hardware-dedication requirements). The cost math mirrors Chapter 8's EC2 analysis: steady-state production favors BYOL on sole-tenant nodes or committed-use discounts; variable workloads favor license-included. Get the licensing position documented — GCP's sole-tenant mechanics differ from AWS dedicated hosts, and the compliance details matter.

    19.3 SQL Server on Compute Engine: Self-Managed on GCP

    Compute Engine VMs with SQL Server preinstalled images are the GCP path to full engine control: Always On availability groups across zones, readable secondaries, SSIS/SSAS/SSRS, and the exact SQL Server version and CU you need. The implementation notes:

  • → AG listeners and GCP load balancing. Like Azure's internal load balancer pattern (Chapter 13), cross-subnet AG listeners on GCP sit behind an internal TCP/UDP load balancer with a health check that only the primary passes. Test listener failover explicitly.
  • → Persistent Disk for data and log. Separate PD volumes for data, log, and tempdb; regional PD for synchronous cross-zone replication of the volumes themselves. PD performance scales with size and type (balanced vs SSD) — provision for throughput, not just capacity.
  • → Backup to Cloud Storage. Native SQL Server backups to Cloud Storage buckets (via the backup-to-URL pattern with GCP's storage), with lifecycle policies for retention and cross-region copies for DR.
  • → Live migration. GCP's transparent maintenance (live migration of VMs during host maintenance) reduces — but does not eliminate — the patching burden. SQL Server patching itself remains yours.

    • 19.4 When GCP Is the Right Cloud for SQL Server

    Choose GCP for SQL Server when the organization is already GCP-committed: BigQuery analytics consuming SQL Server data (Chapter 22's offload pattern is native here), GKE-hosted applications needing a nearby database, or data engineering pipelines built on GCP services. The integration advantages are real: private connectivity between Cloud SQL and BigQuery, unified IAM, and one bill. Do not choose GCP for SQL Server in isolation when the estate is otherwise AWS/Azure — the third cloud adds operational surface for no compensating advantage. And be candid about the ecosystem gap: the SQL Server community, tooling, and third-party integrations are thinnest on GCP, so budget extra validation time for anything beyond the mainstream path.

    19.5 Migrating SQL Server to GCP

    The migration paths from Chapters 33–34 apply with GCP tooling. Database Migration Service (DMS) supports SQL Server as a source for homogeneous migrations into Cloud SQL for SQL Server, handling the initial load and continuous replication with minimal downtime. For Compute Engine targets, the universal method works: native backup to Cloud Storage, restore on the GCE VM, then transactional replication or log shipping to catch up before cutover. For large databases, seed the target with a backup taken as close to cutover as possible — the initial DMS load over the network is the long pole, and a backup-seeded start shortens it dramatically.

    Watch the conversion gotchas: SQL Server Agent jobs must be rebuilt (Cloud SQL's Agent limitations may force the Cloud Scheduler pattern from Chapter 12); linked servers to on-premises systems need Private Service Connect or VPN connectivity validated before cutover; and CLR assemblies, if you use them, must be re-certified on the target version. Run the migrated workload in shadow or read-only mode for a full business cycle before cutover — the migration that "worked" in testing but never saw month-end close is the one that fails on the 31st.

    19.6 Cost: Committed Use and Pricing Gotchas

    GCP's pricing levers for SQL Server: committed use discounts (1- or 3-year commitments on Cloud SQL and Compute Engine, up to roughly half off on-demand) for steady-state workloads, and sustained use discounts that apply automatically to Compute Engine VMs running most of the month. The gotchas: Cloud SQL for SQL Server Enterprise edition pricing multiplies quickly — verify the edition is actually needed (most workloads run fine on Standard); storage autoscaling only grows, so a one-time data load permanently raises the storage bill unless you provision a fresh instance; and cross-region egress for DR copies or BigQuery exports is metered — model it for chatty replication topologies. As with every cloud, the cheapest SQL Server on GCP is the one sized from measurements (Chapter 39) with commitments on the stable baseline and on-demand only for the variable margin.

    19.7 Cross-Cloud Consistency

    If you run SQL Server on multiple clouds, GCP participates in the same patterns as the rest of the book: native backups to object storage as the portable artifact, transactional replication or AGs for cross-cloud data movement where latency allows, and the monitoring/backup/security baselines from Chapters 29–32 applied uniformly. The goal is one operational model with cloud-specific implementations — not three different ways of running SQL Server.

    Key Takeaways

  • → GCP offers both managed and self-managed SQL Server. Cloud SQL for SQL Server for the RDS-like experience (HA via regional disks, no readable secondaries); Compute Engine for full control with AGs across zones.
  • → Licensing: license-included on Cloud SQL, BYOL via sole-tenant nodes on GCE. Document the compliance position — GCP's dedication mechanics differ from AWS and Azure.
  • → AGs on GCE need the load-balancer listener pattern. Same architecture as Azure's ILB approach: health check that only the primary passes, explicit listener failover testing.
  • → Choose GCP for SQL Server when the organization is GCP-committed. BigQuery integration, GKE proximity, and unified IAM are the reasons — not the SQL Server experience in isolation.
  • → One operational model, cloud-specific implementations. Backups to object storage, standard monitoring and security baselines — applied uniformly across every cloud you run.
