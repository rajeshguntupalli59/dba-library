Chapter 6 of 40 The Cloud Database Engineer

Chapter 6: RDS Deep Dive: Engines, Instance Types, and Storage

Amazon RDS is where most DBAs begin their cloud journey, and for good reason — it takes the engine you already know — SQL Server — and wraps it in a managed layer that handles provisioning, patching, and backups. But "managed" does not mean "transparent." The choices you make about engine version, instance family, and storage type have cascading effects on performance, cost, and operational flexibility that cannot be undone without downtime or data migration. This chapter breaks down those choices with the specificity that production systems demand: which instance families to use and why, how RDS storage behaves differently from what you know on-premises, where the hard limits are, and what you give up when AWS takes over the OS layer.

---

6.1 Engine Selection and Version Strategy

RDS supports several database engines; this book covers RDS for SQL Server, which runs on a managed EC2 instance underneath, and the distinction between "RDS for SQL Server" and "self-managed SQL Server on EC2" is not just operational convenience — it represents a fundamental trade-off in control.

What you lose versus self-managed SQL Server on EC2:

  • → No OS-level access. You cannot SSH into the underlying host.
  • → No direct server-property editing. Authentication rules are enforced through security groups, IAM database authentication, and TLS requirements set via parameter groups.
  • → No sysadmin. The master user grants most capabilities, but it is not true sysadmin — you cannot enable arbitrary trace flags, use the dedicated admin connection freely, or load unapproved CLR assemblies.
  • → No transaction log file access. You cannot read the raw LDF files directly; transaction log backups are managed by RDS.
  • → No `BACKUP DATABASE` to local disk. Backups are managed by RDS; native backups to S3 require the SQLSERVER_BACKUP_RESTORE option group.

    • What you gain:

  • → Automated backups with point-in-time recovery (PITR) up to 35 days.
  • → Automated minor version upgrades on a configurable maintenance window.
  • → Multi-AZ failover handled by the platform without you managing Windows Server Failover Clustering.
  • → Monitoring metrics surfaced through CloudWatch without running exporters.

    • Engine version selection is not just about features — it determines your upgrade path. RDS maintains a list of supported minor versions, and AWS periodically deprecates older ones, issuing mandatory upgrades. SQL Server 2012 reached end of extended support and AWS deprecated it on RDS — instances still running deprecated versions receive forced upgrade notices. You should never run more than one major version behind current in production.

    Check available versions before provisioning:

    # List all available SQL Server engine versions in us-east-1
aws rds describe-db-engine-versions \
  --engine sqlserver-se \
  --query 'DBEngineVersions[*].[EngineVersion,DBEngineVersionDescription]' \
  --output table \
  --region us-east-1

# Check which versions support a specific feature (e.g., Kerberos auth)
aws rds describe-db-engine-versions \
  --engine sqlserver-se \
  --query 'DBEngineVersions[?contains(SupportedFeatureNames, `kerberos`) == `true`].[EngineVersion]' \
  --output text \
  --region us-east-1

    SQL Server licensing deserves separate attention. RDS SQL Server offers two licensing models: License Included (LI) and Bring Your Own License (BYOL). License Included is available for Standard and Enterprise editions, with the license cost embedded in the hourly rate. Enterprise edition on a large instance class adds a substantial license-included premium to the hourly rate — check current AWS pricing for the specific instance class and edition. If your organization already has SQL Server Enterprise Agreement licenses, BYOL reduces that cost significantly — but BYOL requires Software Assurance, and AWS audits eligibility.

    Oracle on RDS follows the same LI vs. BYOL model. Oracle Enterprise Edition is only available as BYOL. Standard Edition 2 is available as License Included. The moment you need features like Partitioning, Advanced Compression, or Real Application Testing, you're in Enterprise Edition territory, which means BYOL and your own Oracle licensing agreement.

    Version pinning strategy: In production, pin your minor version explicitly. Do not enable auto minor version upgrade on database instances that have application dependencies on specific behavior (system behavior changed between SQL Server 2019 and 2022, for example). Enable auto minor version upgrade only on development and QA instances.

    # Disable auto minor version upgrade on an existing instance
aws rds modify-db-instance \
  --db-instance-identifier prod-sql-01 \
  --no-auto-minor-version-upgrade \
  --apply-immediately \
  --region us-east-1

# Verify the change
aws rds describe-db-instances \
  --db-instance-identifier prod-sql-01 \
  --query 'DBInstances[0].AutoMinorVersionUpgrade' \
  --region us-east-1

    6.2 Instance Families and Sizing

    The RDS instance naming convention follows the same pattern as EC2: db.{family}{generation}.{size}. Understanding the family is more important than the size, because each family has different CPU architecture, memory ratios, and network characteristics.

    Current generation families:

    | Family | vCPU:Memory Ratio | Use Case | Example |

    |--------|-------------------|----------|---------|

    | db.t3 | Burstable, 1:2 | Dev/test, small workloads | db.t3.medium: 2 vCPU, 4 GB |

    | db.m7i | General purpose, 1:4 | Web applications, moderate OLTP | db.m7i.4xlarge: 16 vCPU, 64 GB |

    | db.r7i | Memory optimized, 1:8 | Large buffers, analytics | db.r7i.8xlarge: 32 vCPU, 256 GB |

    | db.r7i | Memory optimized, Intel | SQL Server (no ARM support) | db.r7i.16xlarge: 64 vCPU, 512 GB |

    | db.x2idn | Memory intensive, 1:32 | SAP HANA, large in-memory | db.x2idn.16xlarge: 64 vCPU, 2048 GB |

    The g suffix means Graviton (ARM-based). Graviton-based instance classes are not available for SQL Server on RDS — choose the Intel/AMD i-family classes (e.g., db.r7i, db.m7i) for SQL Server workloads.

    T-series instances (burstable) in production: The T-series uses CPU credits. When the instance is idle, it accumulates credits. Under sustained load, it burns through credits and throttles to its baseline CPU (which is 20–40% of nominal). This behavior is catastrophic for production OLTP workloads that have sustained query pressure. The only legitimate production use of T-series is for small dev/test instances or internal tooling databases with infrequent queries. (T-series is unavailable for RDS for SQL Server Multi-AZ production workloads — check current docs for edition support.)

    You can detect credit exhaustion in CloudWatch:

    # Check CPU credit balance for a burstable instance
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name CPUCreditBalance \
  --dimensions Name=DBInstanceIdentifier,Value=dev-sqlserver-t4g \
  --start-time 2024-01-15T00:00:00Z \
  --end-time 2024-01-15T23:59:59Z \
  --period 3600 \
  --statistics Minimum \
  --output table

# Also check CPU credit usage rate
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name CPUCreditUsage \
  --dimensions Name=DBInstanceIdentifier,Value=dev-sqlserver-t4g \
  --start-time 2024-01-15T00:00:00Z \
  --end-time 2024-01-15T23:59:59Z \
  --period 3600 \
  --statistics Sum \
  --output table

    Sizing recommendations for SQL Server migration: When migrating a self-managed SQL Server instance, the most important metrics from your source system describe buffer pool behavior — Page Life Expectancy (PLE), buffer cache hit ratio, and lazy writes/sec. On RDS for SQL Server, max server memory is managed by AWS based on instance class. A db.r7i.4xlarge has 128 GB of RAM. If your on-premises system has a 40 GB buffer pool with a healthy PLE and a buffer cache hit ratio above 95%, move to db.r7i.8xlarge (256 GB RAM) with headroom.

    The right way to size using actual database metrics:

    -- Run this on your SOURCE SQL Server instance before migration
-- to understand buffer pool behavior

-- Buffer Manager counters (PLE healthy range scales with RAM: roughly 300s per 4GB)
SELECT counter_name, cntr_value
FROM sys.dm_os_performance_counters
WHERE object_name LIKE '%Buffer Manager%'
  AND counter_name IN (
    'Buffer cache hit ratio',
    'Page life expectancy',
    'Lazy writes/sec',
    'Checkpoint pages/sec'
  );

-- Working set estimate: buffer pool usage by database
SELECT DB_NAME(database_id) AS database_name,
       COUNT(*) * 8 / 1024 AS buffer_pool_mb
FROM sys.dm_os_buffer_descriptors
GROUP BY database_id
ORDER BY buffer_pool_mb DESC;

-- Memory pressure signals: stolen pages and out-of-memory notifications
SELECT counter_name, cntr_value
FROM sys.dm_os_performance_counters
WHERE object_name LIKE '%Memory Manager%'
  AND counter_name IN ('Stolen Server Memory (KB)', 'Out of memory errors');

    Changing instance class: RDS instance class changes require a reboot. On Single-AZ, this means downtime of 3–10 minutes. On Multi-AZ, AWS performs the change on the standby first, then fails over — total visible downtime is typically 30–120 seconds for the failover. Plan instance resizing during low-traffic windows regardless of Multi-AZ, because the failover itself causes connection drops.

    6.3 RDS Storage: gp2, gp3, io1, io2, and Magnetic

    Storage in RDS is EBS-backed, and the storage type you choose determines IOPS characteristics, throughput ceilings, and cost. Getting this wrong is the most common cause of RDS performance problems, because storage bottlenecks in managed services are much harder to diagnose than on-premises where you can run iostat directly.

    Available storage types:

    gp2 (General Purpose SSD): The legacy default. Delivers 3 IOPS per GB of storage, with a burst pool for volumes under 1 TB. A 100 GB gp2 volume gets 300 IOPS baseline with burst to 3,000 IOPS using credits (same credit model as T-series CPU). Above roughly 5.3 TB (where 3 IOPS/GB reaches the 16,000 IOPS ceiling), you get the full ceiling without burst dependency. Maximum throughput: 250 MB/s. Do not use gp2 for new deployments — it has been superseded entirely by gp3.

    gp3 (General Purpose SSD v2): The current recommended default. Provides a baseline of 3,000 IOPS and 125 MB/s throughput regardless of volume size. You can independently provision additional IOPS up to 16,000 and throughput up to 1,000 MB/s at additional cost. A 100 GB gp3 volume gets 3,000 IOPS — the same as a 1 TB gp2 volume, at one-tenth the storage cost. For most OLTP workloads under 16,000 IOPS, gp3 is the right choice.

    io1 (Provisioned IOPS SSD): Allows IOPS provisioning independent of storage size, up to 64,000 IOPS on supported instance types. Maximum throughput: 1,000 MB/s. More expensive than gp3 for the same IOPS level. io1 made sense before gp3 existed; today, it's primarily for workloads needing more IOPS than gp3 provides but that don't require io2's higher durability or ceiling.

    io2 (Provisioned IOPS SSD v2): Higher durability (99.999% vs 99.8% for io1), same IOPS ceiling. For SQL Server and Oracle, io2 supports up to 256,000 IOPS. For most SQL Server workloads, gp3 with provisioned IOPS is sufficient and cheaper.

    Magnetic (standard): Legacy spinning disk. Do not use this for any workload. It exists only for backward compatibility.

    Storage autoscaling: RDS supports automatic storage scaling. When free storage drops below 10% of allocated storage (or below 5 GB, whichever is smaller), RDS automatically increases storage. Autoscaling only increases storage — it never shrinks it. You cannot reduce allocated storage on an RDS instance without creating a new instance and migrating data. Set your initial storage thoughtfully; you will pay for every GB permanently.

    Configure a new SQL Server instance with gp3 and autoscaling via Terraform:

    # terraform/rds_instance.tf
# Production SQL Server RDS with gp3 storage and appropriate settings

resource "aws_db_instance" "prod_sql" {
  identifier        = "prod-sql-primary"
  engine            = "sqlserver-se"
  engine_version    = "16.00"
  instance_class    = "db.r7i.4xlarge"

  # Storage configuration
  storage_type          = "gp3"
  allocated_storage     = 500          # GB - initial allocation
  max_allocated_storage = 2000         # GB - autoscaling ceiling
  iops                  = 12000        # Additional provisioned IOPS above gp3 baseline (3000)
  storage_throughput    = 500          # MB/s - above gp3 baseline (125 MB/s)
  storage_encrypted     = true
  kms_key_id            = aws_kms_key.rds_encryption.arn

  # Engine configuration
  db_name  = "appdb"
  username = "dbadmin"
  password = var.db_password   # Use Secrets Manager in production

  # High availability
  multi_az               = true
  availability_zone      = "us-east-1a"   # for single-AZ; ignored when multi_az=true

  # Backup and maintenance
  backup_retention_period = 14
  backup_window           = "03:00-04:00"
  maintenance_window      = "sun:04:30-sun:05:30"
  deletion_protection     = true

  # Network
  db_subnet_group_name   = aws_db_subnet_group.private.name
  vpc_security_group_ids = [aws_security_group.rds_sqlserver.id]
  publicly_accessible    = false

  # Parameter and option groups
  parameter_group_name = aws_db_parameter_group.sqlserver2022_prod.name

  # Monitoring
  monitoring_interval             = 60   # Enhanced monitoring every 60 seconds
  monitoring_role_arn             = aws_iam_role.rds_enhanced_monitoring.arn
  performance_insights_enabled    = true
  performance_insights_retention_period = 731  # 2 years

  # Upgrade behavior
  auto_minor_version_upgrade = false
  apply_immediately          = false   # Apply changes during maintenance window

  tags = {
    Environment = "production"
    Team        = "platform-db"
    CostCenter  = "engineering"
  }
}

resource "aws_db_parameter_group" "sqlserver2022_prod" {
  name   = "sqlserver2022-prod"
  family = "sqlserver-se-16.0"

  parameter {
    name  = "max server memory (MB)"
    value = "{DBInstanceClassMemory/1048576}*3/4"   # ~75% of instance memory
  }

  parameter {
    name  = "max degree of parallelism"
    value = "8"
  }

  parameter {
    name  = "cost threshold for parallelism"
    value = "50"
  }

  parameter {
    name  = "fill factor (%)"
    value = "90"
  }

  parameter {
    name  = "optimize for ad hoc workloads"
    value = "1"
  }

  parameter {
    name  = "backup compression default"
    value = "1"
  }

  parameter {
    name  = "blocked process threshold (s)"
    value = "30"   # capture blocking chains in the error log
  }
}

    IOPS math for production sizing: On gp3, the baseline 3,000 IOPS costs nothing extra, and each additional IOPS above that baseline is billed incrementally — check current AWS pricing for the exact rate, since it changes. Provisioned IOPS on io1/io2 are billed per-IOPS-month at a materially higher rate than gp3's incremental IOPS pricing, which is why gp3 is the default recommendation for most workloads that don't need io2's higher ceiling or durability.

    Monitoring storage saturation in CloudWatch:

    # Check storage I/O metrics for an RDS instance
# ReadIOPS and WriteIOPS tell you current throughput
# ReadLatency and WriteLatency tell you if storage is saturating

aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name ReadLatency \
  --dimensions Name=DBInstanceIdentifier,Value=prod-sql-primary \
  --start-time 2024-01-15T09:00:00Z \
  --end-time 2024-01-15T10:00:00Z \
  --period 60 \
  --statistics Average Maximum \
  --output table

# DiskQueueDepth > 1 consistently indicates storage saturation
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name DiskQueueDepth \
  --dimensions Name=DBInstanceIdentifier,Value=prod-sql-primary \
  --start-time 2024-01-15T09:00:00Z \
  --end-time 2024-01-15T10:00:00Z \
  --period 60 \
  --statistics Average Maximum \
  --output table

    If DiskQueueDepth averages above 1 and WriteLatency exceeds 10ms consistently, your provisioned IOPS are insufficient. Increase provisioned IOPS without downtime on gp3 — the change is applied immediately (though it takes up to 6 hours for the modification to complete depending on volume size).

    The storage full emergency: RDS will put your database in read-only mode when storage reaches 100%. At that point, you cannot write data including transaction log records. The sequence of events is: free storage drops → autoscaling triggers (if enabled) → scaling takes 5–15 minutes → if autoscaling is not enabled or is at ceiling, the database goes read-only. Set a CloudWatch alarm at 20% free storage, not 10%, so you have time to respond before hitting autoscaling or the ceiling.

    6.4 Parameter Groups: The Replacement for sp_configure

    On a self-managed SQL Server instance, you run sp_configure followed by RECONFIGURE or restart the service. On RDS, that surface is read-only outside the parameter group. All configuration changes go through Parameter Groups — a named collection of configuration values that you associate with one or more DB instances.

    RDS for SQL Server uses DB Parameter Groups (instance-level settings).

    A parameter group has a family (e.g., sqlserver-se-16.0, sqlserver-ee-16.0, sqlserver-ex-16.0) and contains every configurable parameter for that engine version. AWS ships a default.sqlserver-se-16.0 parameter group that contains AWS-optimized defaults. You cannot modify the default group — you must create a custom one and attach it to your instance.

    Parameters have two apply types:

  • → Static: Requires a database restart to take effect. Examples: `max server memory (MB)`, `max degree of parallelism`, `fill factor (%)`.
  • → Dynamic: Takes effect immediately on `apply_immediately` or after the maintenance window. Examples: `cost threshold for parallelism`, `optimize for ad hoc workloads`, `backup compression default`.

    • Common SQL Server parameter customizations for RDS:

    # Create a custom parameter group and configure key parameters

aws rds create-db-parameter-group \
  --db-parameter-group-name sqlserver2022-prod \
  --db-parameter-group-family sqlserver-se-16.0 \
  --description "Production SQL Server 2022 parameters" \
  --region us-east-1

# Apply multiple parameters in one call
aws rds modify-db-parameter-group \
  --db-parameter-group-name sqlserver2022-prod \
  --parameters \
    "ParameterName=cost threshold for parallelism,ParameterValue=50,ApplyMethod=immediate" \
    "ParameterName=max degree of parallelism,ParameterValue=8,ApplyMethod=immediate" \
    "ParameterName=optimize for ad hoc workloads,ParameterValue=1,ApplyMethod=immediate" \
    "ParameterName=backup compression default,ParameterValue=1,ApplyMethod=immediate" \
    "ParameterName=blocked process threshold (s),ParameterValue=30,ApplyMethod=immediate" \
  --region us-east-1

# Static parameters require pending reboot — apply these separately
aws rds modify-db-parameter-group \
  --db-parameter-group-name sqlserver2022-prod \
  --parameters \
    "ParameterName=max server memory (MB),ParameterValue={DBInstanceClassMemory/1048576}*3/4,ApplyMethod=pending-reboot" \
    "ParameterName=fill factor (%),ParameterValue=90,ApplyMethod=pending-reboot" \
  --region us-east-1

# Apply the parameter group to the instance (takes effect after maintenance window
# unless you use --apply-immediately, which causes a brief interruption)
aws rds modify-db-instance \
  --db-instance-identifier prod-sql-primary \
  --db-parameter-group-name sqlserver2022-prod \
  --region us-east-1

    Verifying parameter group status: After applying a parameter group, check whether the instance requires a reboot for any parameters to take effect:

    # Check for pending reboot parameters
aws rds describe-db-instances \
  --db-instance-identifier prod-sql-primary \
  --query 'DBInstances[0].DBParameterGroups' \
  --region us-east-1

    The response includes a ParameterApplyStatus field. A value of pending-reboot means at least one static parameter has been changed and the instance must be restarted before it takes effect. A value of in-sync means all parameters are active.

    You can also verify parameter values from inside SQL Server after applying:

    -- SQL Server: Check current effective values of key parameters
SELECT name, value, value_in_use, description, is_dynamic
FROM sys.configurations
WHERE name IN (
    'max server memory (MB)',
    'max degree of parallelism',
    'cost threshold for parallelism',
    'fill factor (%)',
    'optimize for ad hoc workloads',
    'backup compression default',
    'blocked process threshold (s)',
    'remote query timeout (s)'
)
ORDER BY name;

    For SQL Server on RDS, parameter groups work somewhat differently. SQL Server exposes fewer runtime-adjustable parameters through the RDS parameter group interface than a self-managed instance exposes through sp_configure. Many SQL Server settings that you'd configure via sp_configure on a self-managed instance are either fixed by RDS, exposed as parameter group settings, or must be set at the database level.

    SQL Server parameter group equivalent — key settings:

    -- SQL Server: Check current sp_configure settings on RDS
-- (These reflect what RDS has applied from the parameter group)
EXEC sp_configure 'show advanced options', 1;
RECONFIGURE;

EXEC sp_configure;
GO

-- Check settings that affect query performance
SELECT 
    name,
    value,
    value_in_use,
    description
FROM sys.configurations
WHERE name IN (
    'max degree of parallelism',
    'cost threshold for parallelism',
    'max server memory (MB)',
    'min server memory (MB)',
    'optimize for ad hoc workloads',
    'remote query timeout (s)'
)
ORDER BY name;

    Parameter group gotchas:

    1. max server memory (MB) uses a formula syntax on RDS. You cannot set it to a raw value like 64000 without considering the instance class. Instead, RDS uses expressions like {DBInstanceClassMemory/1048576}*3/4 which resolve at runtime to roughly 75% of instance memory. This is actually better than a hardcoded value because when you resize the instance, the memory setting scales automatically.

    2. user connections defaults to 0 (dynamic self-configuration) on RDS for SQL Server. Leave it there unless you have a specific reason to cap it. Connection pressure on SQL Server shows up as worker thread exhaustion and THREADPOOL waits, not a connection-count error. If you're running RDS Proxy, watch DatabaseConnections in CloudWatch and size the proxy to your workload's actual concurrency.

    3. blocked process threshold (s) is one of the most impactful parameters to set immediately. The default is 0 (disabled). Set it to 30 seconds in production so blocking chains are captured in the error log — exported to CloudWatch Logs via the error log type. The blocked process report is how you identify locking regressions during deployments.

    4. Parameter group changes on a Multi-AZ standby require failover or re-application. The standby does not automatically pick up primary parameter-group changes without an instance reboot cycle. If you want replicas to use the same configuration, create a common parameter group and attach it to each instance individually.

    6.5 Multi-AZ, Read Replicas, and High Availability Architecture

    RDS offers two distinct HA constructs that serve different purposes: Multi-AZ deployments and Read Replicas. They are often conflated by engineers new to RDS, and using them incorrectly produces systems that are either more expensive than necessary or less resilient than assumed.

    Multi-AZ: Synchronous standby for failover

    In a Multi-AZ deployment, RDS maintains a synchronous standby replica in a different Availability Zone. Every write to the primary is synchronously replicated to the standby before the write is acknowledged to the application. This means:

  • → RPO is effectively zero (no committed transactions are lost on failover).
  • → RTO is 60–120 seconds for automatic failover (DNS propagation + database promotion).
  • → The standby cannot serve reads. It exists solely for failover.
  • → You pay for two instances but get one connection endpoint.

    • The Multi-AZ standby is completely transparent to applications — they connect to the instance endpoint (e.g., prod-sql-primary.abc123.us-east-1.rds.amazonaws.com), and that DNS record is automatically updated to point to the new primary after failover.

    Multi-AZ DB Cluster is not available for SQL Server: AWS offers a newer Multi-AZ option called Multi-AZ DB Cluster with two readable standby instances — for other engines. It is not available for RDS for SQL Server. For SQL Server, Multi-AZ uses SQL Server Always On availability groups: the primary replica accepts writes, and the secondary replica exists solely for automatic failover. The secondary is not readable and cannot be queried directly.

    Creating a Multi-AZ SQL Server instance:

    # Create a Multi-AZ SQL Server instance (Always On availability group under the hood)
aws rds create-db-instance \
  --db-instance-identifier prod-sql-primary \
  --db-instance-class db.r7i.4xlarge \
  --engine sqlserver-se \
  --engine-version 16.00 \
  --master-username dbadmin \
  --master-user-password "${DB_PASSWORD}" \
  --allocated-storage 500 \
  --storage-type gp3 \
  --multi-az \
  --backup-retention-period 14 \
  --vpc-security-group-ids sg-0abc123def456789 \
  --db-subnet-group-name private-db-subnets \
  --db-parameter-group-name sqlserver2022-prod \
  --region us-east-1

    Read scaling on RDS for SQL Server: there are no read replicas

    RDS for SQL Server does not offer read replicas — create-db-instance-read-replica is not supported for the sqlserver-* engines. This is the single biggest architectural difference to internalize: on RDS for SQL Server, read scaling must be designed explicitly. Your options are:

  • → Self-managed readable secondaries on EC2: run SQL Server on EC2 with an Always On availability group and add readable secondary replicas for reporting and analytics offload (covered in Chapter 8).
  • → Snapshot-refreshed reporting copies: restore a production snapshot to a separate RDS instance on a schedule (nightly or hourly) for reporting workloads that tolerate stale data.
  • → Cross-region DR via snapshot copy: copy automated or manual snapshots to a second region and restore them there — this is your geographic DR story, not replica promotion.
  • → Reduce primary read load first: before building read-scale infrastructure, verify the primary is not doing avoidable work — missing indexes, unparameterized ad hoc queries, and reporting queries that belong on a copy.

    • Multi-AZ is not a read-scaling feature on RDS for SQL Server. The secondary replica cannot serve reads, so a Multi-AZ primary does nothing for read pressure. The correct production architecture is a Multi-AZ primary for failover plus an explicit read-scaling strategy (readable AG secondaries on EC2, or snapshot-refreshed reporting copies) sized to your reporting workload.

    Cross-region snapshot copy for DR (the RDS-for-SQL-Server alternative to replica promotion):

    # RDS for SQL Server has no create-db-instance-read-replica.
# For cross-region DR, copy the latest automated snapshot and restore it.
# Run the copy in the TARGET region:
aws rds copy-db-snapshot \
  --source-db-snapshot-identifier arn:aws:rds:us-east-1:123456789012:snapshot:rds:prod-sql-primary-2024-01-15-03-00 \
  --target-db-snapshot-identifier prod-sql-dr-copy-20240115 \
  --kms-key-id arn:aws:kms:us-west-2:123456789012:key/mrk-abc123 \
  --region us-west-2

# Restore it as a DR/test instance in the target region
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier prod-sql-dr-usw2 \
  --db-snapshot-identifier prod-sql-dr-copy-20240115 \
  --db-instance-class db.r7i.2xlarge \
  --no-multi-az \
  --region us-west-2

    Monitoring Multi-AZ health (the secondary is not directly queryable):

    # There is no ReplicaLag metric for RDS for SQL Server Multi-AZ.
# Monitor failover and AG health through RDS events instead.
# Subscribe to failover-related events:
aws rds create-event-subscription \
  --subscription-name prod-sql-failover-events \
  --sns-topic-arn arn:aws:sns:us-east-1:123456789012:db-alerts \
  --source-type db-instance \
  --source-ids prod-sql-primary \
  --event-categories "failover" "failure" \
  --region us-east-1

# Review recent failover/failure events
aws rds describe-events \
  --source-identifier prod-sql-primary \
  --source-type db-instance \
  --start-time 2024-01-14T00:00:00Z \
  --query 'Events[*].[Date,Message]' \
  --output table \
  --region us-east-1
    -- On RDS Multi-AZ for SQL Server the secondary replica is NOT queryable.
-- For reference, this is the AG health query you would run on a
-- self-managed / EC2 Always On availability group:
SELECT ar.replica_server_name,
       rs.role_desc,
       rs.connected_state_desc,
       rs.synchronization_state_desc,
       DB_NAME(drs.database_id) AS database_name,
       drs.synchronization_state_desc AS db_sync_state,
       drs.log_send_queue_size AS log_send_queue_kb,
       drs.redo_queue_size AS redo_queue_kb
FROM sys.dm_hadr_availability_replica_states rs
JOIN sys.availability_replicas ar
  ON rs.replica_id = ar.replica_id
JOIN sys.dm_hadr_database_replica_states drs
  ON drs.replica_id = rs.replica_id;

-- On RDS, confirm Multi-AZ status from the control plane instead:
-- aws rds describe-db-instances --db-instance-identifier prod-sql-primary
--   --query 'DBInstances[0].[MultiAZ, SecondaryAvailabilityZone]'

    RDS Proxy: Connection pooling as a managed service

    RDS Proxy sits between your application and the RDS instance and multiplexes database connections. It maintains a warm pool of connections to the database, allowing thousands of application connections to share a smaller number of actual database connections. This is most impactful for:

  • → Serverless workloads (Lambda functions that open and close connections on every invocation)
  • → Applications using a connection-per-request pattern
  • → Instances where connection churn or worker-thread pressure is a bottleneck

    • RDS Proxy also provides a secondary benefit: during Multi-AZ failover, the proxy handles connection re-routing, reducing application-visible downtime from 60–120 seconds to as low as a few seconds.

    # Create an RDS Proxy for the SQL Server instance
aws rds create-db-proxy \
  --db-proxy-name prod-sql-proxy \
  --engine-family SQLSERVER \
  --auth '[{
    "AuthScheme": "SECRETS",
    "SecretArn": "arn:aws:secretsmanager:us-east-1:123456789012:secret:prod/sqlserver/dbadmin",
    "IAMAuth": "DISABLED"
  }]' \
  --role-arn arn:aws:iam::123456789012:role/rds-proxy-role \
  --vpc-subnet-ids subnet-0abc123 subnet-0def456 subnet-0ghi789 \
  --vpc-security-group-ids sg-0proxy123 \
  --require-tls \
  --region us-east-1

# Register the target (point proxy at the RDS instance)
aws rds register-db-proxy-targets \
  --db-proxy-name prod-sql-proxy \
  --db-instance-identifiers prod-sql-primary \
  --region us-east-1

    RDS Proxy for SQL Server authenticates through Secrets Manager — IAM database authentication is not available for SQL Server on RDS. Known limitations for the SQL Server engine family: Windows (Kerberos/NTLM) authentication is not supported through the proxy, so applications must use SQL authentication with the secret; and some connection-string behaviors differ behind the proxy, so test failover and transaction behavior thoroughly before putting Proxy in front of a production SQL Server instance.

    6.6 Backup, Restore, and PITR

    RDS automated backups use EBS volume snapshots plus transaction log backups to enable point-in-time recovery. Understanding the mechanics matters because the recovery behavior has important implications for your RTO.

    How automated backups work:

    1. During the backup window, RDS takes an EBS snapshot of the storage volume. For Multi-AZ, the snapshot is taken from the standby to avoid I/O impact on the primary.

    2. Transaction log backups are taken continuously (roughly every 5 minutes) and uploaded to S3.

    3. PITR works by restoring the nearest snapshot before the target time, then replaying logs forward to the exact target timestamp.

    Retention period: Backups are retained for 0–35 days. Setting retention to 0 disables automated backups (and PITR). Never set retention to 0 on a production instance. The standard retention for production is 14 days; compliance-heavy environments often require 35 days.

    Manual snapshots are independent of the retention period. They persist until you explicitly delete them. Before any major change (schema migration, engine upgrade, instance resizing), take a manual snapshot:

    # Take a manual snapshot before a risky operation
aws rds create-db-snapshot \
  --db-instance-identifier prod-sql-primary \
  --db-snapshot-identifier prod-sql-before-migration-20240115 \
  --region us-east-1

# Wait for the snapshot to complete
aws rds wait db-snapshot-completed \
  --db-snapshot-identifier prod-sql-before-migration-20240115 \
  --region us-east-1

echo "Snapshot complete — safe to proceed with migration"

    Point-in-time restore: PITR creates a new RDS instance restored to the specified timestamp. It does not restore in-place — you always get a new instance. This means you must update your application's connection string after a PITR recovery.

    # Restore to a specific point in time (creates a NEW instance)
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier prod-sql-primary \
  --target-db-instance-identifier prod-sql-recovered-20240115 \
  --restore-time 2024-01-15T08:30:00Z \
  --db-instance-class db.r7i.4xlarge \
  --storage-type gp3 \
  --multi-az \
  --region us-east-1

# Monitor restoration progress
aws rds describe-db-instances \
  --db-instance-identifier prod-sql-recovered-20240115 \
  --query 'DBInstances[0].[DBInstanceStatus,PercentProgress]' \
  --output table \
  --region us-east-1

    The PITR recovery window: The earliest restorable time is limited by the oldest retained backup snapshot. You can check the exact recovery window:

    # Check the earliest and latest restorable times
aws rds describe-db-instances \
  --db-instance-identifier prod-sql-primary \
  --query 'DBInstances[0].{
    EarliestRestorableTime: EarliestRestorableTime,
    LatestRestorableTime: LatestRestorableTime,
    BackupRetentionPeriod: BackupRetentionPeriod
  }' \
  --output table \
  --region us-east-1

    Restoring a snapshot to a different instance class or storage type: This is useful when you want to test a configuration change. Restore a production snapshot to a smaller instance in a non-production environment, validate, and then apply the same change to production.

    # Restore from a manual snapshot to a different (cheaper) instance class
# for testing or data recovery purposes
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier staging-sql-from-prod-snap \
  --db-snapshot-identifier prod-sql-before-migration-20240115 \
  --db-instance-class db.r7i.xlarge \
  --storage-type gp3 \
  --no-multi-az \
  --no-publicly-accessible \
  --vpc-security-group-ids sg-0staging123 \
  --db-subnet-group-name staging-db-subnets \
  --region us-east-1

    Cross-region backup copies: Automated backups do not automatically copy to other regions. For DR, you need to either configure cross-region automated backup copy or copy manual snapshots. AWS recently added automated cross-region backup to RDS, but manual snapshot copy remains the most flexible approach:

    # Copy a manual snapshot to another region for DR
aws rds copy-db-snapshot \
  --source-db-snapshot-identifier \
    arn:aws:rds:us-east-1:123456789012:snapshot:prod-sql-before-migration-20240115 \
  --target-db-snapshot-identifier prod-sql-before-migration-20240115-copy \
  --kms-key-id arn:aws:kms:us-west-2:123456789012:key/mrk-abc123 \
  --region us-west-2

    Note that cross-region snapshot copies transfer data across AWS backbone networks and incur data transfer costs. For large databases, automate periodic snapshot copies rather than copying every snapshot.

    6.7 Upgrade Paths and Maintenance Windows

    RDS engine upgrades come in two types: minor version upgrades (e.g., 16.2 → 16.3) and major version upgrades (e.g., 15 → 16). The operational complexity and risk differ significantly.

    Minor version upgrades:

  • → Applied automatically if `AutoMinorVersionUpgrade` is enabled, during the maintenance window.
  • → Can be applied manually at any time.
  • → For Multi-AZ: zero-downtime upgrade (standby upgraded first, then failover, then original primary upgraded).
  • → For Single-AZ: brief downtime (~5 minutes) during the upgrade.
  • → Generally safe with no application changes required.

    • Major version upgrades:

  • → Always require explicit action — no automatic major version upgrades.
  • → Require a compatible parameter group for the new version (you must create one in advance).
  • → In-place major version upgrades on RDS work for some engine combinations (SQL Server 2019 → 2022 is supported) but not all.
  • → For SQL Server, the in-place upgrade runs the SQL Server setup upgrade path underneath. RDS takes a snapshot first, runs the upgrade, and if it fails, rolls back to the snapshot.
  • → Estimated downtime: 10–60 minutes depending on database size and version gap.

    • Pre-upgrade checklist for a SQL Server major version upgrade:

    -- Run these on the CURRENT version before upgrading
-- to identify potential incompatibilities

-- Check for deprecated features in use (nonzero = in use since last restart)
SELECT object_name, counter_name, cntr_value
FROM sys.dm_os_performance_counters
WHERE object_name LIKE '%Deprecated Features%'
  AND cntr_value > 0;

-- Check database compatibility levels (old levels may block upgrade paths)
SELECT name, compatibility_level
FROM sys.databases
WHERE compatibility_level < 150;

-- Inventory features RDS does not support: linked servers and CLR assemblies
SELECT name, product, provider, data_source
FROM sys.servers
WHERE is_linked = 1;

SELECT name, permission_set_desc
FROM sys.assemblies
WHERE is_user_defined = 1;

    Performing a major version upgrade with pre-upgrade snapshot:

    # Step 1: Take a manual snapshot before upgrading
aws rds create-db-snapshot \
  --db-instance-identifier prod-sql-primary \
  --db-snapshot-identifier pre-upgrade-sql2019-to-sql2022-$(date +%Y%m%d) \
  --region us-east-1

aws rds wait db-snapshot-completed \
  --db-snapshot-identifier pre-upgrade-sql2019-to-sql2022-$(date +%Y%m%d) \
  --region us-east-1

# Step 2: Create the parameter group for the new major version FIRST
aws rds create-db-parameter-group \
  --db-parameter-group-name sqlserver2022-prod \
  --db-parameter-group-family sqlserver-se-16.0 \
  --description "Production SQL Server 2022 parameters" \
  --region us-east-1

# Re-apply all your custom parameters to the new group (use the same
# modify-db-parameter-group commands from section 6.4)

# Step 3: Initiate the upgrade
aws rds modify-db-instance \
  --db-instance-identifier prod-sql-primary \
  --engine-version 16.00 \
  --db-parameter-group-name sqlserver2022-prod \
  --allow-major-version-upgrade \
  --apply-immediately \
  --region us-east-1

# Step 4: Monitor upgrade progress
watch -n 30 'aws rds describe-db-instances \
  --db-instance-identifier prod-sql-primary \
  --query "DBInstances[0].[DBInstanceStatus,EngineVersion,PendingModifiedValues]" \
  --output table \
  --region us-east-1'

    Maintenance windows deserve careful thought in production. The default maintenance window is a 30-minute window during off-peak hours in the instance's region. AWS applies minor patches, security updates, and approved configuration changes during this window. For global applications with no true off-peak window, schedule maintenance during the lowest-traffic window you have, and ensure your application handles connection drops gracefully (retry logic, connection pool reconnect on error).

    # Update the maintenance window to Sunday 2am-3am UTC
aws rds modify-db-instance \
  --db-instance-identifier prod-sql-primary \
  --preferred-maintenance-window "sun:02:00-sun:03:00" \
  --region us-east-1

# Check pending maintenance actions (AWS may schedule security patches)
aws rds describe-pending-maintenance-actions \
  --region us-east-1 \
  --query 'PendingMaintenanceActions[*].{
    ResourceIdentifier: ResourceIdentifier,
    Action: PendingMaintenanceActionDetails[0].Action,
    AutoAppliedAfterDate: PendingMaintenanceActionDetails[0].AutoAppliedAfterDate,
    Description: PendingMaintenanceActionDetails[0].Description
  }' \
  --output table

    If AWS schedules a forced patch with an AutoAppliedAfterDate, that patch will apply automatically after that date regardless of your maintenance window preference. Monitor this endpoint and apply patches proactively before AWS forces them, so you control the timing.

    6.8 RDS Operational Monitoring and Alerting

    The monitoring stack for RDS has three tiers: CloudWatch Basic Metrics (free, 1-minute granularity), Enhanced Monitoring (paid, 1–60 second granularity, OS-level metrics), and Performance Insights (paid, query-level attribution).

    CloudWatch Basic Metrics include CPU utilization, database connections, free storage, read/write IOPS, read/write latency, replica lag, and network throughput. These are sufficient for capacity trend monitoring but insufficient for diagnosing query-level performance issues.

    Enhanced Monitoring adds OS-level metrics that the basic metrics don't expose: per-process CPU, memory by component (RDS process, OS, file system cache), and disk I/O broken down by read/write and user/kernel. Enhanced Monitoring sends data to CloudWatch Logs rather than CloudWatch Metrics, which means you query it differently:

    # Enhanced Monitoring is in the RDSOSMetrics log group
# Get the latest OS metrics for an instance
aws logs filter-log-events \
  --log-group-name "RDSOSMetrics" \
  --log-stream-name-prefix "prod-sql-primary" \
  --start-time $(date -d '5 minutes ago' +%s000) \
  --limit 5 \
  --query 'events[*].message' \
  --output text \
  --region us-east-1

    The output is JSON with detailed OS metrics. Parse it with jq for usable output:

    aws logs filter-log-events \
  --log-group-name "RDSOSMetrics" \
  --log-stream-name-prefix "prod-sql-primary" \
  --start-time $(date -d '5 minutes ago' +%s000) \
  --limit 1 \
  --query 'events[0].message' \
  --output text \
  --region us-east-1 | \
  jq '{
    timestamp: .timestamp,
    cpu_idle: .cpuUtilization.idle,
    cpu_user: .cpuUtilization.user,
    memory_free_mb: (.memory.free / 1024 / 1024),
    disk_read_iops: .diskIO[0].readIOsPS,
    disk_write_iops: .diskIO[0].writeIOsPS,
    load_average_1m: .loadAverageMinute.one
  }'

    Performance Insights is the most powerful diagnostic tool for RDS. It collects query-level wait event data and lets you answer "what was the database doing at 2:34am when latency spiked?" It shows the database load broken down by wait event, SQL statement, user, host, or application. For SQL Server, it leverages DMVs such as sys.dm_exec_query_stats and sys.dm_os_wait_stats internally.

    Set Performance Insights retention to at least 7 days (the free tier) and ideally to 731 days (2 years, paid) for production systems where you need to compare behavior across deployments and seasonal traffic patterns.

    Essential CloudWatch alarms for any production RDS instance:

    # Alarm: CPU utilization above 80% for 10 minutes
aws cloudwatch put-metric-alarm \
  --alarm-name rds-prod-sql-cpu-high \
  --metric-name CPUUtilization \
  --namespace AWS/RDS \
  --dimensions Name=DBInstanceIdentifier,Value=prod-sql-primary \
  --statistic Average \
  --period 300 \
  --evaluation-periods 2 \
  --threshold 80 \
  --comparison-operator GreaterThanThreshold \
  --alarm-actions arn:aws:sns:us-east-1:123456789012:db-alerts \
  --region us-east-1

# Alarm: Free storage below 20% (500 GB instance -> alarm at 100 GB free)
aws cloudwatch put-metric-alarm \
  --alarm-name rds-prod-sql-low-storage \
  --metric-name FreeStorageSpace \
  --namespace AWS/RDS \
  --dimensions Name=DBInstanceIdentifier,Value=prod-sql-primary \
  --statistic Average \
  --period 300 \
  --evaluation-periods 1 \
  --threshold 107374182400 \
  --comparison-operator LessThanThreshold \
  --alarm-actions arn:aws:sns:us-east-1:123456789012:db-alerts \
  --region us-east-1

# Alarm: Freeable memory below 2 GB (memory pressure / buffer pool squeeze)
aws cloudwatch put-metric-alarm \
  --alarm-name rds-prod-sql-low-memory \
  --metric-name FreeableMemory \
  --namespace AWS/RDS \
  --dimensions Name=DBInstanceIdentifier,Value=prod-sql-primary \
  --statistic Average \
  --period 300 \
  --evaluation-periods 2 \
  --threshold 2147483648 \
  --comparison-operator LessThanThreshold \
  --alarm-actions arn:aws:sns:us-east-1:123456789012:db-alerts \
  --region us-east-1

# Alarm: Database connections above 400 (of 500 max)
aws cloudwatch put-metric-alarm \
  --alarm-name rds-prod-sql-connections-high \
  --metric-name DatabaseConnections \
  --namespace AWS/RDS \
  --dimensions Name=DBInstanceIdentifier,Value=prod-sql-primary \
  --statistic Maximum \
  --period 60 \
  --evaluation-periods 2 \
  --threshold 400 \
  --comparison-operator GreaterThanThreshold \
  --alarm-actions arn:aws:sns:us-east-1:123456789012:db-alerts \
  --region us-east-1

    Querying Performance Insights via API for automated reporting:

    # Get top SQL by average active sessions (last hour)
aws pi get-resource-metrics \
  --service-type RDS \
  --identifier db-ABCDEFGHIJ1234567 \
  --start-time $(date -d '1 hour ago' --iso-8601=seconds) \
  --end-time $(date --iso-8601=seconds) \
  --period-in-seconds 3600 \
  --metric-queries '[
    {
      "Metric": "db.load.avg",
      "GroupBy": {
        "Group": "db.sql",
        "Limit": 10
      }
    }
  ]' \
  --region us-east-1

    The identifier in Performance Insights API calls is the DBI resource ID, not the instance name. Get it with:

    aws rds describe-db-instances \
  --db-instance-identifier prod-sql-primary \
  --query 'DBInstances[0].DbiResourceId' \
  --region us-east-1

    Key Takeaways

  • → Engine version and licensing choices are harder to reverse than they appear. Pin minor versions in production, stay within one major version of current, and understand the SQL Server and Oracle licensing models before committing to an instance size and edition — the hourly cost difference between editions on large instances is substantial.
  • → Instance family selection matters more than raw size. Graviton (g-suffix) instances do not support SQL Server at all — for RDS for SQL Server always choose Intel families (db.r7i, db.m7i). Never use T-series burstable instances for production OLTP workloads that sustain CPU pressure — CPU credit exhaustion causes silent, unpredictable throttling.
  • → gp3 storage is the correct default for nearly all new RDS deployments. It decouples IOPS and throughput from storage size, eliminating the gp2 credit model at lower cost. Monitor `DiskQueueDepth` and `WriteLatency` to detect storage saturation; provision additional IOPS on gp3 before reaching the throughput ceiling rather than after observing latency spikes.
  • → Multi-AZ is failover, not read scaling — and RDS for SQL Server has no read replicas. Multi-AZ provides synchronous failover with near-zero RPO but the secondary cannot serve reads. Plan read scaling explicitly: readable Always On secondaries on EC2, or snapshot-refreshed reporting copies. Production architectures pair a Multi-AZ primary with a deliberate read-offload strategy.
  • → RDS backup and restore behavior requires architectural awareness. PITR always produces a new instance — recovery requires updating application connection strings, not just waiting for an in-place restore. Automated backups do not copy cross-region by default. Take manual snapshots before any major change, verify the earliest restorable time matches your RPO requirements, and set CloudWatch alarms at 20% free storage rather than relying solely on autoscaling.
