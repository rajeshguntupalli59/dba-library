Chapter 34: Zero-Downtime Cloud Migrations

Some databases cannot take a maintenance window — the order system, the trading platform, the always-on SaaS. For these, migration must happen with the application running: continuous replication from source to target, a cutover measured in seconds, and a rollback path that works just as fast. This chapter covers the zero-downtime techniques for SQL Server: the replication architectures, the cutover choreography, and the validation that proves the migration before the business notices it.

34.1 What "Zero Downtime" Actually Requires

Zero downtime does not mean zero risk — it means the risk moves from the cutover window to the replication design. The prerequisites: a replication mechanism with seconds of lag (transactional replication, distributed AGs, or DMS CDC — Chapter 33's table); schema parity guaranteed (the target schema deployed via the Chapter 23 pipeline, with drift detection proving source and target match before cutover); a cutover that is a client redirect, not a data move (by cutover time, the data is already there — the only operation is pointing clients at the target); and rehearsal (the full cutover practiced on a staging pair until it is boring). If any prerequisite is missing, you do not have a zero-downtime migration — you have a hope with replication.

34.2 Transactional Replication for Near-Zero Cutover

The classic approach: the on-premises (or source-cloud) SQL Server publishes, the cloud target subscribes, and replication runs continuously for days or weeks before cutover. The engineering details: seed from backup (initialize the subscription from a native backup, not a snapshot — Chapter 25's WAN rule); replicate everything the application needs (tables, of course — but also verify: identity ranges managed so the subscriber doesn't collide, sequences, and any lookup data the application expects); monitor lag as the migration's vital sign (the lag graph should be flat and small for the entire pre-cutover period — a growing lag means the cutover will fail); and handle the non-replicated objects (Agent jobs rebuilt per Chapter 12, logins migrated with SIDs preserved, linked servers recreated — the migration checklist from Chapter 33, executed during the replication window rather than during downtime).

34.3 Distributed AGs as the Migration Vehicle

Where the target is EC2/VMs/GCE, a distributed availability group spanning source and target is the most elegant vehicle: the source AG and the target AG replicate continuously, and cutover is an AG failover — seconds, with the database engine handling the consistency. The setup: seed the target AG from backup, join it to the distributed AG as the secondary, and let it synchronize. The cutover choreography: quiesce writes briefly (or accept the async lag window explicitly), fail over the distributed AG, redirect clients to the target listener. The advantage over replication: whole-database fidelity (everything — including the objects replication forgets — moves as one unit) and engine-managed consistency. The constraint: both sides need AG-capable infrastructure (no managed-service targets).

34.4 DMS and Cloud-Native CDC Paths

For managed-service targets (RDS, Azure SQL, Cloud SQL), the cloud migration services provide the CDC path: AWS DMS (full load plus ongoing CDC from SQL Server sources — verify the source version support and the LOB handling for your schema); Azure Database Migration Service (online migrations to Azure SQL targets with minimal downtime); GCP Database Migration Service (homogeneous SQL Server to Cloud SQL). The universal caveats: test LOB and large-row handling (CDC tools have opinions about varchar(max), varbinary(max), and wide rows — find the limits with your data, not the documentation's); validate data continuously (row counts and checksums during the replication window, not just at cutover — DMS table statistics lie by omission); and understand the cutover model (each service has a specific cutover procedure — rehearse it exactly, because improvising the vendor's procedure under pressure is how migrations fail).

34.5 Cutover Orchestration: The Seconds That Matter

The cutover sequence, orchestrated and timed: pre-cutover checks (lag at zero, schema parity confirmed, target health verified, rollback path armed); the quiet second (drain application connections or briefly pause writes — even "zero downtime" migrations usually have a seconds-long write pause; the honest ones admit it); the redirect (DNS flip with pre-lowered TTL, connection string deployment, or listener update — Chapter 16's discipline); verification (smoke tests against the target within 60 seconds — the business's critical writes succeeding on the new primary); and the point of no return (declared explicitly — after this, rollback means reverse migration, not a quick flip). Automate the sequence; the human's job is go/no-go decisions, not typing commands.

34.6 Post-Migration Validation: Proving It Worked

Validation is a checklist, not a feeling: data validation (row counts per table, checksums on critical tables, spot-checks of recent transactions — the data that arrived in the last replication seconds is the data most likely to be wrong); application validation (the full smoke suite plus the business's day-one critical paths); performance validation (Query Store baselines compared — the new environment's plans will differ; investigate regressions in the first hours, not the first week); and operational validation (backups running, monitoring live, alerting active, Agent jobs executing — Chapter 33's "operated environment" confirmed). Keep the source in rollback-ready state until every validation passes plus a safety margin.

34.7 Rollback at Speed and Post-Migration Cleanup

The zero-downtime rollback: reverse the redirect (clients back to the source — fast, because the source was kept warm); reconcile the writes (the writes that landed on the target during the failed cutover must be replayed to the source or explicitly discarded — this is the hard part, and the reason the verification in 34.5 must be ruthless); reverse replication where available (DMS and distributed AGs can often reverse direction — test this before cutover, not during rollback). After a successful migration: decommission replication (remove publishers, drop the distributed AG, stop DMS tasks — leftover replication is a failure waiting to happen), retire the source on schedule, and hold the post-mortem while memories are fresh — every migration teaches something the runbook should capture.

34.8 Application Compatibility: The Silent Migration Killer

The data migrates cleanly; the application breaks. The compatibility checklist for zero-downtime migrations: connection behavior (connection string changes, TLS requirements, and retry logic — the application must handle the brief redirect at cutover without cascading failures); version-specific behavior (a newer SQL Server version on the target means new cardinality estimator behavior, deprecated features removed, and compatibility-level differences — test the application against the target version under load, not just functionally); case sensitivity and collation (verify the target's collation matches — a collation mismatch surfaces as bizarre, intermittent query failures); and distributed transactions (MSDTC across the migration boundary rarely survives — identify and redesign them before cutover). Run the application's full integration suite against the replicated target during the pre-cutover window; the migration rehearsal that skips application testing is rehearsing half the migration.

Key Takeaways

  • → Zero downtime moves risk to replication design. Seconds of lag, guaranteed schema parity, client-redirect cutover, rehearsed until boring — or it's not zero-downtime.
  • → Seed from backup, monitor lag as the vital sign. Transactional replication, distributed AGs, or DMS CDC — the mechanism matters less than the discipline around it.
  • → Cutover is an orchestrated sequence with a declared point of no return. Automate the steps; humans make go/no-go decisions.
  • → Validate data, application, performance, and operations. Checksums on recent transactions, Query Store baselines, backup/monitoring/Agent jobs confirmed live.
  • → Rollback is reverse-redirect plus write reconciliation. Test reverse replication before cutover; decommission migration infrastructure after success.
