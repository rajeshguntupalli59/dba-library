Chapter 4 of 40 The Cloud Database Engineer

Chapter 4: The Cloud DBA Role: What Changes, What Stays

If you have spent years tuning SQL Server max server memory, managing Always On Availability Groups, and writing runbooks for failover procedures at 2 AM, the shift to managed cloud databases can feel disorienting. AWS, Azure, and Google Cloud take over large portions of the operational work you once owned completely — OS patching, storage provisioning, replication wiring — while introducing entirely new categories of responsibility that did not exist in your on-premises world. This chapter maps that transition precisely. It identifies what the cloud genuinely removes from your plate, what it hands back to you in a different form, and what it adds as net-new work. Understanding this boundary is the foundation for everything else in this book.

---

4.1 The Managed Service Contract: What AWS, Azure, and GCP Actually Own

When you move from self-managed SQL Server to Amazon RDS, you are entering into an implicit contract. The cloud provider owns the hypervisor, the operating system, the storage subsystem, the replication mechanism, and the software patching lifecycle. You own the database configuration, the schema design, the query performance, the access control model, and the backup retention policy. The line between those two domains is firm, and understanding it prevents both false assumptions and wasted effort.

What the provider owns:

On RDS for SQL Server, you will never run Windows Update on the host, restart the OS, or access the SQL Server installation directories directly. AWS handles patching on a schedule you influence but do not fully control unless you take explicit ownership of the maintenance window. The storage layer is EBS-backed with automatic replication within an Availability Zone. Multi-AZ deployments add a synchronous standby in a second AZ, and failover is handled automatically — typically completing in 60–120 seconds for RDS Multi-AZ (Azure SQL Business Critical generally fails over faster due to its AG-based architecture).

On Azure SQL Database, Microsoft manages the underlying SQL Server engine, the Always On availability group that provides HA, and the Intelligent Query Processing features that ship with each compatibility level upgrade. Google Cloud SQL similarly abstracts OS management and handles read replica replication lag monitoring internally.

What you still own:

The provider's ownership does not extend to logical database design, index strategy, connection pooling, application-layer retry logic, or query plans. A poorly written query that causes a full table scan on a 2 TB table will perform exactly as badly on RDS as it did on your on-premises server. Cloud-managed does not mean self-healing at the query level. Your expertise in execution plans, wait events, lock escalation, and statistics management transfers directly and remains essential.

The practical implication is this: you spend less time on infrastructure operations and more time on database architecture decisions, performance engineering, and cost optimization. That is a genuine shift in how a senior DBA allocates time, not a reduction in the need for DBA expertise.

4.2 Access Patterns and Permissions: From Server Logins to IAM

On-premises SQL Server access control flows through two layers: server logins control who can connect, and database users and roles control what they can do once connected. Windows Authentication through Active Directory ties both layers to corporate identity. In the cloud, these familiar mechanisms are extended — not replaced — by identity and access management layers that sit above the database engine.

IAM Authentication on RDS

With IAM database authentication enabled on RDS for SQL Server, a login connects using a short-lived authentication token generated by the AWS IAM service rather than a static password. The token is valid for 15 minutes and is generated using the AWS credentials of the calling identity — an EC2 instance profile, a Lambda execution role, or a developer's IAM user. The database-side configuration still uses SQL Server logins and database users, but the credential presented at connect time is the IAM token instead of the login's password.

# Enable IAM authentication on an existing RDS for SQL Server instance
aws rds modify-db-instance \
  --db-instance-identifier prod-sql-01 \
  --enable-iam-database-authentication \
  --apply-immediately

# Generate an authentication token for a login named "app_user"
aws rds generate-db-auth-token \
  --hostname prod-sql-01.cxyz1234.us-east-1.rds.amazonaws.com \
  --port 1433 \
  --region us-east-1 \
  --username app_user

On the database side, the login must exist on the instance and be associated with the IAM role:

-- Create the login for the application service account.
-- Keep a strong Secrets Manager-backed password as a break-glass fallback;
-- day-to-day authentication is token-based and never uses the static password.
CREATE LOGIN [app_user] WITH PASSWORD = '<managed-by-secrets-manager>';
-- Grant object-level privileges as you normally would
GRANT SELECT, INSERT, UPDATE ON SCHEMA::dbo TO [app_user];

This pattern replaces the practice of embedding static database passwords in application configuration files. The calling application retrieves a fresh token before each connection attempt (or connection pool initialization), using the AWS SDK. The conceptual analog is Kerberos authentication with Active Directory — the application proves its identity to a central authority and receives a time-limited credential.

Azure SQL and Azure Active Directory

Azure SQL Database integrates with Azure Active Directory using contained database users. The model is familiar if you have used Windows Authentication with SQL Server, but the administration happens through the Azure portal, Azure CLI, or Entra ID (formerly Azure AD) rather than through local Windows group policy.

# Set an Azure AD admin for an Azure SQL logical server
az sql server ad-admin create \
  --resource-group prod-rg \
  --server prod-sql-server-01 \
  --display-name "DBA-Team-Admin" \
  --object-id "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"

Inside the database, Entra-backed contained users are created without passwords:

-- Create an Azure AD-backed user in Azure SQL Database
CREATE USER [dba-engineer@company.com] FROM EXTERNAL PROVIDER;
ALTER ROLE db_datareader ADD MEMBER [dba-engineer@company.com];

-- For a managed identity (e.g., an Azure App Service)
CREATE USER [my-app-service] FROM EXTERNAL PROVIDER;
GRANT SELECT, INSERT, UPDATE ON SCHEMA::dbo TO [my-app-service];

The Core Shift

What changes is not the concept of authentication and authorization — it is the locus of control. You now manage database access through the same IAM, RBAC, and identity systems that govern access to every other cloud resource. Permissions are auditable through CloudTrail (AWS), Azure Monitor Activity Log (Azure), and Cloud Audit Logs (GCP). Rotating credentials means updating IAM policies, not editing server logins and coordinating password rotations across application servers. This is a genuine improvement in auditability and a reduction in credential sprawl, but it requires the DBA to become conversant in cloud IAM, which is a new skill domain.

4.3 Configuration Management: Parameter Groups, Server Parameters, and What You Cannot Touch

On self-managed SQL Server, you run sp_configure directly and control every engine setting from max server memory (MB) to cost threshold for parallelism to fill factor (%). On RDS, that surface is owned by AWS. You configure the engine through Parameter Groups — a named collection of engine parameters that you apply to one or more DB instances.

RDS Parameter Groups

The default parameter group for any RDS engine version is managed by AWS and is not modifiable. You create a custom parameter group, copy defaults into it, modify what you need, and associate it with your instance. Changes to dynamic parameters take effect immediately; changes to static parameters require an instance reboot.

# Create a custom parameter group for RDS SQL Server 2022
aws rds create-db-parameter-group \
  --db-parameter-group-name prod-sql2022-custom \
  --db-parameter-group-family sqlserver-se-16.0 \
  --description "Production SQL Server 2022 tuning"

# Modify key parameters
aws rds modify-db-parameter-group \
  --db-parameter-group-name prod-sql2022-custom \
  --parameters \
    "ParameterName=max server memory (MB),ParameterValue={DBInstanceClassMemory/1048576}*3/4,ApplyMethod=pending-reboot" \
    "ParameterName=cost threshold for parallelism,ParameterValue=50,ApplyMethod=immediate" \
    "ParameterName=max degree of parallelism,ParameterValue=8,ApplyMethod=immediate" \
    "ParameterName=fill factor (%),ParameterValue=90,ApplyMethod=pending-reboot" \
    "ParameterName=optimize for ad hoc workloads,ParameterValue=1,ApplyMethod=immediate"

# Associate with an instance
aws rds modify-db-instance \
  --db-instance-identifier prod-sql-01 \
  --db-parameter-group-name prod-sql2022-custom \
  --apply-immediately

Note the formula syntax for max server memory (MB). RDS supports arithmetic expressions using {DBInstanceClassMemory} as a variable — this is how AWS recommends setting memory-relative parameters so the configuration remains valid if you resize the instance class. For a db.r6i.2xlarge with 64 GB RAM, leaving roughly a quarter of memory for the OS is the standard SQL Server practice, which the formula encodes directly.

What You Cannot Configure

This is where experienced DBAs encounter real friction. Several parameters are locked in RDS because they control behaviors that AWS manages on your behalf:

  • → Many `sp_configure` options are restricted to the curated set AWS exposes; arbitrary trace flags and startup parameters are unavailable
  • → Transaction log backup scheduling is managed by AWS; you cannot run your own log backup chain on the instance
  • → Network protocols and endpoints are managed by AWS
  • → TLS is forced on — you cannot disable encryption on RDS connections
  • → `sysadmin` access does not exist on RDS; the master user is a functional substitute but does not grant OS-level access
  • → Components must be on the supported list — no SQL Server Agent, no SSIS, SSAS, or SSRS

    • The absence of true sysadmin is a significant operational change. On RDS for SQL Server you get a master user with broad but not unlimited privileges — the rdsadmin account owns the instance internals, and tasks like killing sessions owned by other logins or accessing server-level internals may require the RDS-specific stored procedures rather than the T-SQL you know. Plan your privilege requirements before migration: anything depending on full sysadmin (certain Agent subsystem access, server-level DDL triggers, OS-level operations) needs a self-managed EC2 deployment instead.

    Azure SQL Server-Level vs. Database-Level Parameters

    Azure SQL Database presents a different model. Many parameters that SQL Server DBAs manage at the server level — max server memory, MAXDOP, cost threshold for parallelism — are controlled through database-scoped configurations or are set by Microsoft at the service tier level.

    -- Azure SQL: set database-scoped configuration
ALTER DATABASE SCOPED CONFIGURATION SET MAXDOP = 4;
ALTER DATABASE SCOPED CONFIGURATION SET LEGACY_CARDINALITY_ESTIMATION = OFF;
ALTER DATABASE SCOPED CONFIGURATION SET QUERY_OPTIMIZER_HOTFIXES = ON;

-- Check current database-scoped configuration
SELECT name, value, value_for_secondary
FROM sys.database_scoped_configurations
ORDER BY name;

    Maximum memory is determined by the service tier and compute size — there is no sp_configure 'max server memory' you can run. Business Critical generally provides a higher memory-to-vCore ratio than General Purpose, since it runs on local SSD-backed hardware rather than remote storage, but the exact figures vary by hardware generation — check current Microsoft documentation rather than assuming a fixed number. What matters operationally is that these ceilings are fixed for the tier and not tunable.

    4.4 High Availability and Failover: Understanding What the Cloud Gives You

    HA in on-premises environments is expensive to build and maintain. A self-managed SQL Server Always On availability group with a Windows Server Failover Cluster, listener, and quorum configuration requires significant operational investment. Self-managed failover clustering demands quorum votes, witness configuration, and careful patch sequencing across nodes. In the cloud, HA is a checkbox during instance creation, and the complexity of maintaining it disappears — but understanding what you got is essential because the behavior is not identical to what you built yourself.

    RDS Multi-AZ: What It Is and Is Not

    RDS Multi-AZ deploys a synchronous standby in a second Availability Zone. Writes are committed to both the primary and standby before returning to the application. Failover is automatic and DNS-based — the endpoint DNS name resolves to the standby after promotion, typically within 60–120 seconds including DNS TTL propagation. The standby is not readable. It is a hot standby only for failover purposes.

    This surprises many DBAs coming from Always On availability groups where secondaries serve read traffic. On RDS for SQL Server Multi-AZ, you pay for the standby instance in full and receive zero read scaling from it — and unlike other RDS engines, SQL Server has no read-replica option on RDS at all. Read scaling for SQL Server means readable AG secondaries on self-managed EC2/VMs (Chapter 8) or the built-in readable secondaries in Azure SQL's Business Critical and Hyperscale tiers (Chapter 7).

    Azure SQL: A Different Architecture

    Azure SQL changes this model substantially. The Business Critical tier runs an Always On availability group across compute nodes: a primary plus replicas with synchronous commit, one of which is readable at no additional replica cost. Failover promotes a replica that already holds a synchronized copy of the data — typically completing faster than RDS Multi-AZ's storage-level failover — and the readable secondary doubles as the read-scale target (Chapter 7). Hyperscale goes further, disaggregating compute from page servers so storage scales independently and restores complete in minutes regardless of database size (Chapter 15).

    # Create an RDS for SQL Server instance with Multi-AZ and encryption
aws rds create-db-instance \
  --db-instance-identifier prod-sqlserver \
  --engine sqlserver-se \
  --engine-version 16.00.4125.1.v1 \
  --db-instance-class db.r7i.2xlarge \
  --allocated-storage 500 --storage-type gp3 \
  --multi-az --storage-encrypted \
  --master-username dbadmin \
  --master-user-password "$(aws secretsmanager get-secret-value \
      --secret-id prod/rds-sqlserver/master-password \
      --query SecretString --output text)" \
  --db-subnet-group-name prod-subnet-group \
  --vpc-security-group-ids sg-0abc123 \
  --backup-retention-period 7

    Azure SQL Business Critical vs. General Purpose

    Azure SQL HA behavior depends on the service tier. General Purpose uses remote storage (Azure Premium SSD) with a database availability SLA achieved through Azure infrastructure-level redundancy. Failover in the General Purpose tier can take 25–30 seconds as data files are remounted on a new compute node. Business Critical deploys an Always On availability group across three replicas using local SSD storage. One of those replicas is readable and accessible to your application — unlike RDS Multi-AZ standby, the Business Critical secondary serves read workloads without additional configuration.

    The read-scale secondary in Business Critical is accessed via a connection string that includes ApplicationIntent=ReadOnly:

    -- Connect string for Azure SQL Business Critical read-only replica
-- Server=prod-sql-server-01.database.windows.net;
-- Database=prod-db;
-- Authentication=Active Directory Default;
-- ApplicationIntent=ReadOnly;

-- Verify you are on the secondary
SELECT DATABASEPROPERTYEX(DB_NAME(), 'Updateability') AS replica_role;
-- Returns: READ_ONLY when connected to secondary
-- Returns: READ_WRITE when connected to primary

    The HA tiers, failover behaviors, and read-scale capabilities across cloud providers have direct cost implications. Choosing between RDS for SQL Server Multi-AZ, SQL Server on EC2 with Always On AGs, Azure SQL General Purpose, and Business Critical is as much an architectural decision as a financial one, and it belongs in the DBA's scope, not just the infrastructure team's.

    4.5 Monitoring: CloudWatch, Azure Monitor, and Cloud Logging vs. What You Had Before

    On-premises DBAs typically own their full monitoring stack — Datadog agents, custom scripts querying sys.dm_exec_requests, sys.dm_os_wait_stats, and sys.dm_tran_locks. In the cloud, the provider delivers a baseline monitoring layer automatically, and the DBA's job shifts from building that layer to interpreting it, extending it, and setting appropriate thresholds.

    CloudWatch and Enhanced Monitoring on RDS

    Every RDS instance publishes a set of CloudWatch metrics automatically with no configuration required: CPUUtilization, DatabaseConnections, FreeableMemory, ReadIOPS, WriteIOPS, ReadLatency, WriteLatency, ReplicaLag. These metrics refresh at 60-second intervals by default.

    Enhanced Monitoring is an additional feature that installs an agent on the DB instance OS (which you cannot access directly) and publishes 50+ OS-level metrics at 1-second to 60-second granularity to CloudWatch Logs. These include per-process CPU, memory, disk I/O broken out by device, and file system metrics. Enable it for production instances — the cost is negligible compared to the diagnostic value during an incident.

    # Enable Enhanced Monitoring with 15-second granularity
aws rds modify-db-instance \
  --db-instance-identifier prod-sql-01 \
  --monitoring-interval 15 \
  --monitoring-role-arn arn:aws:iam::123456789012:role/rds-monitoring-role \
  --apply-immediately

# Query CloudWatch for replica lag over the last hour
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name ReplicaLag \
  --dimensions Name=DBInstanceIdentifier,Value=prod-sql-reader-1 \
  --start-time $(date -u -d '1 hour ago' +%Y-%m-%dT%H:%M:%SZ) \
  --end-time $(date -u +%Y-%m-%dT%H:%M:%SZ) \
  --period 60 \
  --statistics Maximum \
  --output table

    Performance Insights

    Performance Insights is the cloud analog to Oracle's Active Session History and a significant improvement over what most self-managed SQL Server deployments have out of the box. It records database load in terms of active sessions broken down by wait event, SQL statement, host, and user. The default retention is 7 days free; extending to up to 2 years incurs an additional per-vCPU-hour charge — check current AWS pricing.

    For a production workload investigation, Performance Insights replaces the manual practice of sampling sys.dm_exec_requests every few seconds and correlating the results. The UI presents a visual timeline of database load against the max_vCPUs line — anything above that line indicates the database is CPU-bound or waiting on a bottleneck that requires investigation.

    # Retrieve Performance Insights data via boto3
import boto3
from datetime import datetime, timedelta, timezone

pi_client = boto3.client('pi', region_name='us-east-1')

response = pi_client.get_resource_metrics(
    ServiceType='RDS',
    Identifier='db-ABCDEFGHIJ1234567',  # DBI resource ID, not instance ID
    MetricQueries=[
        {
            'Metric': 'db.load.avg',
            'GroupBy': {
                'Group': 'db.wait_event',
                'Limit': 10
            }
        }
    ],
    StartTime=datetime.now(timezone.utc) - timedelta(hours=1),
    EndTime=datetime.now(timezone.utc),
    PeriodInSeconds=60
)

for result in response['MetricList']:
    print(f"Metric: {result['Key']}")
    for dp in result['DataPoints'][-5:]:  # last 5 data points
        print(f"  {dp['Timestamp']}: {dp.get('Value', 'N/A'):.4f}")

    Azure Monitor and Query Performance Insight

    Azure SQL Database surfaces equivalent functionality through Azure Monitor metrics (DTU percentage, CPU percentage, data I/O percentage, log write percentage, connection counts) and the Query Performance Insight blade, which aggregates data from Query Store — a feature that has been running automatically in Azure SQL since it was introduced in SQL Server 2016.

    Query Store is particularly valuable because it captures query plan changes over time. A query that performed well for three months and suddenly regressed after an auto-statistics update will show the plan change in Query Store with the before and after execution statistics.

    -- Azure SQL: find the top 10 queries by total CPU consumption in the last 24 hours
SELECT TOP 10
    q.query_id,
    qt.query_sql_text,
    SUM(rs.avg_cpu_time * rs.count_executions) AS total_cpu_ms,
    SUM(rs.count_executions) AS total_executions,
    SUM(rs.avg_duration * rs.count_executions) AS total_duration_ms
FROM sys.query_store_query_text qt
JOIN sys.query_store_query q ON qt.query_text_id = q.query_text_id
JOIN sys.query_store_plan p ON q.query_id = p.query_id
JOIN sys.query_store_runtime_stats rs ON p.plan_id = rs.plan_id
JOIN sys.query_store_runtime_stats_interval rsi 
    ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
WHERE rsi.start_time >= DATEADD(HOUR, -24, GETUTCDATE())
GROUP BY q.query_id, qt.query_sql_text
ORDER BY total_cpu_ms DESC;

    The monitoring shift is real: you spend less time building monitoring infrastructure and more time interpreting richer, already-collected data. The tradeoff is that cloud monitoring tools have gaps — they do not expose lock wait graphs as clearly as sys.dm_tran_locks queries do on self-managed SQL Server, and correlating application traces with database wait events across CloudWatch, X-Ray, and RDS Performance Insights requires more configuration than running a single monitoring agent that sees both layers.

    4.6 The New DBA Work: Cost Management, IaC, and Architecture Ownership

    The reduction in operational work does not leave a vacuum. Cloud DBAs acquire a meaningful set of responsibilities that did not exist in their on-premises roles: database infrastructure as code, cost engineering, and cross-service architecture design.

    Infrastructure as Code for Databases

    In on-premises environments, provisioning a SQL Server VM involved coordinating with a server team, a storage team, and a network team, filling out a change request, and waiting. In the cloud, a DBA with appropriate IAM permissions can provision a multi-AZ RDS for SQL Server instance with encrypted storage, automated backups, and VPC-isolated networking in under 10 minutes using Terraform. The DBA who understands both the database requirements and the infrastructure configuration is in a stronger position than one who waits for an infrastructure team to provision resources.

    # Terraform: production RDS for SQL Server instance
resource "aws_db_instance" "prod" {
  identifier              = "prod-sqlserver"
  engine                  = "sqlserver-se"
  engine_version          = "16.00.4125.1.v1"
  instance_class          = "db.r7i.2xlarge"
  allocated_storage       = 500
  storage_type            = "gp3"
  multi_az                = true
  storage_encrypted       = true
  backup_retention_period = 7
  deletion_protection     = true
}

    Treating database infrastructure as code gives you version history, peer review, repeatable deployments across environments, and the ability to reconstruct a destroyed environment from source control. These are practices that are standard in software engineering and are now expected of cloud DBAs. If your team does not already do this, starting with a simple Terraform module for a non-production cluster is the practical entry point.

    Cost Engineering

    On-premises database costs are largely fixed — server hardware depreciates, storage is bought in bulk, and the marginal cost of running a query is invisible. In the cloud, every instance-hour, every GB of storage, every I/O operation (on gp2 storage), and every GB of data transferred across AZs has a line-item cost. A cloud DBA who understands the cost model can make architecture recommendations that have direct financial impact.

    The most common cost levers for RDS for SQL Server and Azure SQL are:

    *Instance sizing and Reserved Instances / Savings Plans.* On-demand pricing for a db.r7i.2xlarge running SQL Server Standard in us-east-1 is meaningful at monthly scale — SQL Server licensing is a large share of that line item. Purchasing a one-year Reserved Instance (or Azure's one-/three-year reservations with Hybrid Benefit) for the same size produces a substantial discount compared to on-demand — consult the current pricing calculator for exact figures, as prices change. Most production workloads with stable compute requirements should run on Reserved Instances. A common failure pattern is running development and staging instances on on-demand because they were provisioned ad hoc, then leaving them running indefinitely.

    *Storage autoscaling.* RDS supports storage autoscaling — storage grows automatically when free space falls below a threshold. This prevents the 2 AM call about a full disk but can mask unexpected data growth. Set a MaxAllocatedStorage limit and alert on storage growth rate, not just absolute free space.

    *Readable-secondary sizing (self-managed).* On SQL Server on EC2 or Azure VMs, Always On secondaries that serve reporting workloads do not need to match the primary's instance class. Size secondaries for the read workload — reporting-heavy secondaries may want more memory for sorts and hashes, while simple lookup secondaries can be smaller. (On RDS for SQL Server there are no readable secondaries, so this lever applies to the VM deployments.)

    # List all running RDS instances and their costs-relevant attributes
aws rds describe-db-instances \
  --query 'DBInstances[*].{
    ID:DBInstanceIdentifier,
    Class:DBInstanceClass,
    Engine:Engine,
    EngineVersion:EngineVersion,
    MultiAZ:MultiAZ,
    Storage:AllocatedStorage,
    StorageType:StorageType,
    Status:DBInstanceStatus
  }' \
  --output table

# Identify instances without Reserved Instance coverage using Cost Explorer API
aws ce get-reservation-coverage \
  --time-period Start=2024-01-01,End=2024-01-31 \
  --granularity MONTHLY \
  --filter '{
    "Dimensions": {
      "Key": "SERVICE",
      "Values": ["Amazon Relational Database Service"]
    }
  }' \
  --query 'CoveragesByTime[*].Groups[*].{
    Instance:Attributes.instanceType,
    CoverageHours:Coverage.CoverageHours.CoverageHoursPercentage
  }' \
  --output table

    Architecture Ownership

    The cloud DBA's most expansive new responsibility is architecture ownership — the ability to design and advocate for database solutions that span multiple cloud services rather than a single database engine. An on-premises DBA might optimize a single SQL Server cluster indefinitely. A cloud DBA is frequently asked whether data should live in RDS for SQL Server, SQL Server on EC2, Azure SQL Database, or be offloaded to columnstore analytics (Chapter 22), and the answer requires understanding access patterns, query shapes, consistency requirements, and cost at scale.

    This does not mean the cloud DBA becomes a generalist who knows everything shallowly. It means the DBA's deep expertise in relational database behavior is the anchor for evaluating other options. Understanding why a particular workload is poorly suited for a key-value store, or why an analytical query pattern belongs in a columnar store rather than a row store, is exactly the kind of judgment that deep database expertise develops.

    4.7 What Genuinely Does Not Change

    It is worth being direct about this, because hype around cloud services can create the impression that managed databases are fundamentally different systems that require entirely new skills.

    Query optimization does not change. Actual execution plans on RDS for SQL Server are produced by the same optimizer as on self-managed SQL Server. The same principles govern index selection, join ordering, statistics quality, and plan regression. Query Store on Azure SQL and Performance Insights on RDS give you better visibility into query behavior than most on-premises deployments had, but interpreting that data requires the same foundational knowledge of execution plans and cost estimation.

    -- SQL Server: plan and IO analysis works identically on RDS, Azure SQL, and self-managed
SET STATISTICS IO, TIME ON;
SELECT
    o.order_id,
    o.created_at,
    c.email,
    SUM(oi.quantity * oi.unit_price) AS order_total
FROM dbo.orders o
JOIN dbo.customers c ON o.customer_id = c.customer_id
JOIN dbo.order_items oi ON o.order_id = oi.order_id
WHERE o.created_at >= DATEADD(DAY, -30, GETUTCDATE())
  AND o.status = 'completed'
GROUP BY o.order_id, o.created_at, c.email
ORDER BY o.created_at DESC;

    Schema design does not change. Normalization, denormalization tradeoffs, partitioning strategies, and foreign key design are engine-level concerns that the cloud provider does not touch. A poorly designed schema that causes page splits through inefficient clustered index choices will fragment just as effectively on RDS as on a bare-metal SQL Server.

    Backup and recovery reasoning does not change. The mechanics of backup change — you do not run BACKUP DATABASE manually on RDS for SQL Server, and you do not schedule SQL Server maintenance plan jobs on Azure SQL. But the reasoning about RPO, RTO, backup retention, and recovery testing does not change. The cloud DBA must still define backup retention windows, understand what PITR can recover and what it cannot, and test restore procedures regularly.

    Transaction management and isolation levels do not change. READ COMMITTED, REPEATABLE READ, SERIALIZABLE — these are engine behaviors that the cloud wrapper does not modify. Application developers who write code with implicit assumptions about transaction boundaries will cause the same data integrity problems on RDS that they would cause on your on-premises server.

    Locking and concurrency design does not change. Application locks via sp_getapplock, row-level locking, table-level locking, deadlock detection — these behave identically. The cloud DBA who knows how to diagnose a lock contention issue using sys.dm_tran_locks and sys.dm_exec_requests on self-managed SQL Server will apply exactly the same skills on RDS.

    -- SQL Server: identify blocking chains (works on RDS, Azure SQL, self-managed identically)
-- SQL Server equivalent (Azure SQL)
SELECT
    blocked_req.session_id AS blocked_session,
    blocked_req.wait_type,
    blocked_req.wait_time / 1000.0 AS wait_seconds,
    blocked_req.blocking_session_id AS blocking_session,
    blocked_sql.text AS blocked_query,
    blocking_sql.text AS blocking_query,
    blocked_req.status
FROM sys.dm_exec_requests blocked_req
CROSS APPLY sys.dm_exec_sql_text(blocked_req.sql_handle) blocked_sql
JOIN sys.dm_exec_sessions blocking_sess
    ON blocking_sess.session_id = blocked_req.blocking_session_id
CROSS APPLY sys.dm_exec_sql_text(blocking_sess.most_recent_sql_handle) blocking_sql
WHERE blocked_req.blocking_session_id > 0
ORDER BY blocked_req.wait_time DESC;

    The cloud changes where your database runs and who manages the infrastructure around it. It does not change how relational databases work or what makes them perform well. The DBA who has mastered the fundamentals carries those skills directly into the cloud environment and adds cloud-specific operational knowledge on top of that foundation.

    4.8 Organizational Changes: The DBA in Cloud-Native Teams

    Beyond the technical changes, the cloud DBA role shifts in organizational context. In many organizations that move to cloud-managed databases, the traditional operations-focused DBA headcount decreases while the need for database engineers embedded in development teams or platform teams increases.

    The distinction matters. An operations DBA monitors a fleet of databases, responds to incidents, performs maintenance, and keeps the lights on. A database engineer (the role that cloud-managed services tend to create demand for) contributes to architectural decisions, reviews schema changes, automates database provisioning and migrations, builds the observability layer, and advises development teams on data model and query design choices. If you are currently an operations DBA in an organization moving to managed cloud databases, understanding this shift is important for positioning your career.

    The practical advice is to develop skills in three areas that complement your existing database expertise and increase your value in a cloud context:

    1. Infrastructure as Code fluency. Terraform or Pulumi for database infrastructure is a baseline expectation on mature cloud teams. If you can write and review Terraform for an RDS SQL Server instance, security groups, parameter groups, and Secrets Manager integration, you can contribute directly to platform work rather than waiting for infrastructure teams to provision what you need.

    2. Observability and alerting design. Building CloudWatch alarms, Azure Monitor alert rules, and dashboard configurations that accurately surface real problems without generating noise is a skill. Knowing which thresholds matter (replica lag exceeding a threshold appropriate for your RPO, connection pool saturation, storage growth rate), and knowing how to page on the right signals, is a DBA-specific contribution to the observability stack.

    3. Database migration engineering. Moving data between environments — from on-premises to cloud, between cloud providers, or between database engines — is a domain where deep database knowledge is essential and where mistakes have serious consequences. AWS Database Migration Service, Azure Database Migration Service, native backup/restore to object storage, and log shipping are all in scope. Chapter 9 covers this in depth.

    ---

    Key Takeaways

  • → The cloud provider owns the OS, storage subsystem, replication wiring, and patching lifecycle; the DBA owns configuration, schema design, query performance, access control policy, and backup retention — this division of responsibility is firm and understanding it prevents both misplaced effort and dangerous assumptions.
  • → Authentication and authorization move from engine-native mechanisms (SQL Server logins, Windows authentication) to cloud IAM layers (AWS IAM database authentication, Azure Entra ID contained users), requiring the DBA to become conversant in cloud identity systems while retaining all existing knowledge of database-level privilege management.
  • → Configuration management shifts from editing flat files to managing Parameter Groups (RDS) or database-scoped configurations (Azure SQL), with certain parameters locked because the provider manages them on your behalf — most notably, true superuser access does not exist on RDS, which affects extension management and some administrative operations.
  • → Core DBA expertise — query optimization, execution plan analysis, schema design, locking and concurrency management, transaction isolation reasoning, and backup/recovery strategy — transfers without modification to managed cloud databases; cloud wrappers change where the database runs, not how relational engines work.
  • → Cloud DBAs acquire meaningful net-new responsibilities in infrastructure as code, cost engineering (Reserved Instances, storage tier selection, I/O optimization), and cross-service architecture design, while the organizational context shifts toward database engineering roles embedded in development and platform teams rather than purely operations-focused roles.
