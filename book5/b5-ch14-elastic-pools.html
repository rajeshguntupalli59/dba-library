Chapter 14: Elastic Pools: Multi-Tenant Cost Optimization

The SaaS problem: you have 300 customers, each with their own database. Each database averages 2% CPU utilization but peaks at 60% — at different times. Provisioned individually, you pay for 300 peaks. In an elastic pool, you pay for the aggregate: a shared pool of vCores (or eDTUs) that databases draw from as needed. When peaks do not coincide, the pool costs a fraction of the sum of its databases. This chapter covers how elastic pools work, how to size them, how to keep tenants from hurting each other, and the operational patterns for running hundreds of databases as a fleet.

14.1 How Elastic Pools Work

An elastic pool is a pool of compute and storage resources shared by a set of single databases on a logical server. You set the pool's total vCores (or eDTUs), per-database min/max limits, and storage cap. Each database consumes what it needs moment to moment, up to its max; the pool's total is the only thing you pay for. The key insight: you are buying the sum of average utilization plus headroom for coincident peaks, not the sum of peaks.

Two purchasing models: vCore-based (the modern model — provisioned compute with per-database min/max vCores, available in General Purpose and Business Critical tiers) and DTU-based (the legacy bundled model — eDTUs combining CPU, memory, and I/O). New pools should use vCore; DTU pools exist for legacy estates. Per-database settings matter enormously: min vCores per database guarantees each tenant a floor (set it above zero for databases that must always be responsive), and max vCores per database caps any single tenant from consuming the pool.

# Create an elastic pool: 50 vCores shared, per-DB guardrails
az sql elastic-pool create \
  --resource-group rg-saas \
  --server sqlsrv-saas \
  --name pool-tenants \
  --edition GeneralPurpose \
  --family Gen5 \
  --capacity 50 \
  --db-dtu-max 5 \
  --db-dtu-min 0 \
  --storage 500

# Move a database into the pool
az sql db update \
  --resource-group rg-saas \
  --server sqlsrv-saas \
  --name tenant_042 \
  --elastic-pool pool-tenants

14.2 Sizing: The Math That Makes Pools Win

Size from measurements, not guesses. For each candidate database, capture a week of CPU, data I/O, and log I/O utilization (Azure Monitor metrics per database, or Query Store wait statistics). The pool size formula:

  • → Sum the averages across all databases — this is the pool's baseline load.
  • → Add headroom for coincident peaks. If peaks are uncorrelated, 30–50% headroom over the summed average is typical. If tenants share usage patterns (all B2B customers active 9–5 in one timezone), peaks correlate — size closer to the sum of peaks and reconsider whether pooling fits.
  • → Set per-database max to bound blast radius. A common starting point: max vCores per database at 25–50% of pool vCores. One tenant's runaway query should degrade that tenant, not exhaust the pool.

    • Example: 200 tenant databases averaging 0.25 vCores each (50 vCores of average load), peaks uncorrelated. A 75-vCore pool (50% headroom) replaces 200 individually-provisioned databases — typically a 60–80% cost reduction. The break-even analysis against 200 serverless databases (Chapter 11) depends on idle patterns: pools win when databases are lightly busy around the clock; serverless wins when they are truly idle for long stretches.

    14.3 The Noisy Neighbor Problem

    Pooling's risk is resource contention: one tenant's workload starves the others. The defenses are layered:

  • → Per-database max caps (section 14.2) — the first and most important control.
  • → Resource governance alerts. Alert on pool-level CPU, data I/O, and log I/O utilization, and on per-database utilization approaching its max. The alert should identify the offending database — pool-level metrics alone just tell you the pool is hot.
  • → Query Store per database. When a tenant degrades, Query Store on that database identifies the regressed query in minutes. This is the diagnostic that makes pools operable at scale.
  • → Tenant isolation tiers. Not all tenants belong in the pool: your largest tenants get dedicated provisioned databases (or their own pool), the long tail shares the pool. Revisit placement quarterly as tenants grow — a tenant that outgrows the pool's per-database max needs promotion, not a bigger cap.

    • 14.4 Multi-Tenant Schema Patterns

    Elastic pools assume the database-per-tenant pattern. Two alternatives worth knowing: schema-per-tenant (one database, one schema per tenant — cheaper, but no per-tenant resource isolation and harder per-tenant restore) and shared schema with tenantId (one database, row-level security — cheapest, weakest isolation). Database-per-tenant in a pool is the sweet spot for most SaaS: per-tenant backup/restore, per-tenant Query Store diagnostics, per-tenant max caps, and straightforward tenant onboarding/offboarding (add/remove database from the pool). Use elastic queries or a catalog database for cross-tenant reporting — cross-database queries from the pool work through elastic query, with the performance characteristics of remote queries.

    14.5 Fleet Operations: Managing Hundreds of Databases

    At pool scale, you do not manage databases — you manage the fleet:

  • → Schema deployment: elastic jobs (Chapter 12) execute migrations across all pool databases from a single job definition. Version-gate the rollout: canary tenants first, then waves.
  • → Monitoring: Azure Monitor at pool scope plus per-database Query Store. Build a fleet dashboard: pool utilization, top databases by CPU/I/O, databases hitting per-database max, and tenant growth trends.
  • → Onboarding/offboarding: automate database creation from a template (bacpac or copy), pool assignment, elastic job enrollment, and monitoring registration. Tenant provisioning should be an API call, not a ticket.
  • → Backup and PITR per tenant: Azure SQL backs up each database independently — per-tenant point-in-time restore works even inside a pool. Verify restore drills cover a single-tenant restore, not just pool-level scenarios.

    • 14.6 Disaster Recovery for Pools

    Pools participate in the same DR mechanisms as single databases, with fleet-scale considerations. Failover groups replicate entire pools: add the pool to a failover group and every database in it geo-replicates to the secondary region, failing over together behind one listener endpoint. This is the right model when tenants share a region-failure fate — which, for most SaaS, they do. The secondary pool must be sized to absorb the primary's load; an under-provisioned secondary turns a regional failover into a pool-wide brownout.

    For per-tenant recovery, geo-restore works per database: restore any single tenant's database from geo-redundant backup storage to any region, without touching the rest of the pool. This covers the "one tenant needs yesterday's data" scenario that failover groups cannot address. Drill both: a full-pool failover annually, a single-tenant geo-restore quarterly. And remember the RPO/RTO asymmetry — geo-restore RPO is up to an hour (backup replication lag), while active geo-replication RPO is seconds. Choose per scenario, not per habit.

    14.7 Moving Databases Between Pools and Tiers

    Pool membership is not permanent. The lifecycle operations you will run regularly:

  • → Promoting a tenant out. When a database consistently hits its per-database max, move it to a dedicated provisioned database (or Hyperscale). The move is online; update the tenant's connection string and remove it from the pool's elastic job targets.
  • → Splitting a hot pool. When pool-level utilization stays above 80%, split by tenant cohort (e.g., by region, plan tier, or signup cohort) into two pools rather than just adding vCores. Smaller pools have smaller blast radii and clearer noisy-neighbor attribution.
  • → Tier changes. Moving a pool from General Purpose to Business Critical (for the readable secondary or lower latency) is an online operation but changes the price significantly — model it against the dedicated-database alternative first.
  • → Storage autoscaling. Pool storage caps apply to the aggregate; monitor total pool storage, not just per-database sizes. A single tenant's data growth can push the whole pool toward its cap — set alerts at 70% and have the split/promote runbook ready.

    • Automate placement decisions: a monthly job that reviews per-database utilization against pool headroom and recommends promotions, splits, or vCore adjustments. At fleet scale, placement is a continuous optimization, not a one-time design.

    14.8 When Pools Do Not Fit

    Do not pool when: tenants have correlated peaks (the pool must be sized near the sum of peaks, erasing the savings); a single tenant needs more than the per-database max the pool can offer; tenants need different service tiers or compliance boundaries (a HIPAA tenant and a dev tenant do not share a pool); or databases need features outside the pool's tier. The honest alternative is a hybrid: pool for the long tail, dedicated provisioned or Hyperscale databases for the head. Most mature SaaS estates end up exactly here.

    Key Takeaways

  • → Elastic pools monetize uncorrelated peaks. Size from measured averages plus headroom for coincident peaks, not from summed peaks. The typical win is 60–80% over individual provisioning for long-tail SaaS tenants.
  • → Per-database min/max caps are the control plane. Max caps bound noisy neighbors; min guarantees keep tenants responsive. Set them deliberately and revisit as tenants grow.
  • → Operate the fleet, not the databases. Elastic jobs for schema rollout, pool-scope monitoring with per-database Query Store diagnostics, automated tenant provisioning, and per-tenant PITR drills.
  • → Tier your tenants. Pool the long tail; give large, correlated, or compliance-sensitive tenants dedicated databases or their own pools. Promote tenants that outgrow the pool.
  • → Pools vs serverless is an idle-pattern question. Lightly-busy-around-the-clock fleets belong in pools; truly-idle-for-hours databases belong on serverless. Measure, then choose.
