Chapter 25: Cross-Cloud Replication Architectures

Chapter 24 set the strategy; this chapter is the engineering. Moving SQL Server data between clouds — continuously, reliably, and observably — using the mechanisms SQL Server actually provides: transactional replication, distributed availability groups, CDC-based pipelines, and backup-based seeding. Each mechanism's consistency model, latency profile, failure modes, and cost, so the choice is an engineering decision instead of a guess.

25.1 Understanding the Cross-Cloud Replication Landscape

Every cross-cloud replication design answers four questions: granularity (whole database or selected tables?), latency (seconds, minutes, or hours behind?), direction (one-way or bidirectional?), and conflict policy (what happens when both sides change the same row?). SQL Server's mechanisms span the space: backup/restore (whole database, hours, one-way, no conflicts); transactional replication (tables, seconds, one-way, no conflicts); distributed AGs (whole database, seconds, one-way per AG, no conflicts); merge replication (tables, minutes, bidirectional, resolvable conflicts — with all the caveats of Chapter 24). Match the mechanism to the answers, not the other way around.

25.2 Transactional Replication Across Clouds

Transactional replication is the workhorse for cross-cloud SQL Server data movement: the publisher (on cloud A) streams committed transactions to the distributor, which delivers them to subscribers (on cloud B) with seconds of latency. The cross-cloud specifics:

  • → Distributor placement. Put the distributor on cloud A near the publisher (local latency for the high-volume publisher-to-distributor leg); the distributor-to-subscriber leg crosses the cloud boundary once. Never stretch the publisher-to-distributor link across clouds.
  • → Initialization over the WAN. Snapshot initialization across clouds is slow and expensive (egress on every byte). Seed the subscriber from a native backup restored on cloud B, then initialize replication from the backup (replication supports initialization from backup) — the snapshot crosses the boundary as a compressed backup file, once.
  • → Encryption and authentication. Replication traffic crosses the private interconnect (Chapter 24), encrypted in transit; the replication agents authenticate with certificate-based logins whose secrets live in each cloud's secret store.
  • → Managed-service limits. RDS for SQL Server supports replication with restrictions (verify current publisher/subscriber support); Azure SQL Database can serve as a subscriber in supported configurations. Full topology control needs EC2/Azure VMs/GCE on at least the publisher side.

    • 25.3 CDC-Based Pipelines for Cross-Cloud Data Movement

    When the target is not SQL Server (a warehouse, a lakehouse, a different engine) or when you need transformation in flight, CDC-based pipelines replace replication: SQL Server CDC (or the transaction log via a CDC tool) captures changes, a pipeline (Debezium/Kafka, cloud-native CDC services, or ETL) moves and transforms them, and the target applies them. This is the Chapter 22 offload pattern extended across clouds. The engineering concerns: exactly-once vs at-least-once delivery semantics (design the target apply to be idempotent — the pipeline will redeliver); schema change propagation (the pipeline must handle DDL or fail loudly, never silently); and lag monitoring end to end (source capture lag + pipeline lag + target apply lag = the business's actual data freshness).

    25.4 Distributed AGs Across Clouds

    A distributed availability group with one AG on each cloud gives whole-database replication with seconds of lag and automatic page-repair semantics — the closest SQL Server gets to a cross-cloud standby. Requirements: EC2/VMs/GCE on both sides (managed services cannot participate), private cross-cloud connectivity with latency you have measured (async mode tolerates it; the lag equals roughly the network round trip plus apply time), and independent quorum in each site (cloud witnesses in each cloud's storage — never one witness for both sites). Use it for: DR across clouds (the Chapter 24 active-passive pattern with seconds of RPO), and geographic read locality. Do not use it for bidirectional writes — distributed AGs are one-way per AG, and "we'll coordinate writes" is the conflict problem wearing a different hat.

    25.5 Handling Schema Changes and DDL Propagation

    Schema changes are where cross-cloud replication goes to die. The discipline: DDL goes through the same pipeline as DML — the migration-based deployment from Chapter 23 runs on every replica's database in dependency order (publisher first, then subscribers; primary AG first, then secondaries). Transactional replication propagates some schema changes automatically (configurable per article) — but relying on automatic DDL propagation across a cloud boundary is asking for a 3 AM surprise; explicit deployment is auditable, automatic propagation is not. For CDC pipelines, every DDL change must update the pipeline's schema mapping — make it a checklist item in the migration review, enforced by the pipeline failing closed on unknown schema.

    25.6 Failover and Switchover in Cross-Cloud Architectures

    Failover across clouds is never just a database operation. The sequence: stop writes on cloud A (or confirm it is down), let replication drain (verify zero lag — failing over with 5 minutes of undelivered transactions is data loss you chose), promote on cloud B (restore with recovery, or AG failover, or replication role reversal), redirect clients (DNS/endpoint flip, Chapter 16), and verify the business's critical transactions. Planned switchovers (for maintenance or drills) follow the same sequence without the time pressure — which is why you drill: the planned switchover is the rehearsal for the unplanned failover. And plan the failback before the failover: data written on cloud B must return to cloud A, which means reverse replication configured and tested, not improvised.

    25.7 Conflict Resolution in Bidirectional Replication

    If you truly need both clouds accepting writes to the same data, you need conflict detection and resolution — and you should first re-read Chapter 24's advice to avoid it. When there is no alternative: partition by design (each site owns disjoint key ranges — conflicts impossible, routing mandatory); last-writer-wins with vector clocks or timestamps (simple, lossy — someone's write disappears, and you'd better be able to explain whose and why); or application-level merge (the application understands the domain and can merge meaningfully — the only correct option for data where loss is unacceptable, and the most expensive to build). Log every conflict with both versions preserved; "resolved automatically" without an audit trail is how you discover data loss during the quarterly review.

    25.8 Cost Modeling for Cross-Cloud Replication

    Cross-cloud replication has four cost centers: egress (every replicated byte is metered leaving the source cloud — for chatty OLTP this is often the largest line; compress where possible and model from measured transaction log volume, not guesses); the second cloud's infrastructure (the subscriber/secondary is a real database with real compute and storage); the interconnect (Direct Connect/ExpressRoute ports and hours, or VPN); and operations (the DBA hours spent on the topology — usually underestimated by half). Build the model before committing, re-measure quarterly, and set a billing alert on the egress line specifically — it is the one that surprises.

    Key Takeaways

  • → Answer the four questions first: granularity, latency, direction, conflicts. Then match the mechanism — backup/restore, transactional replication, distributed AGs, or CDC pipelines — to the answers.
  • → Seed across the WAN with backups, not snapshots. Initialize replication from a restored backup; keep the high-volume replication legs local to each cloud.
  • → DDL goes through the pipeline, everywhere, in order. Automatic DDL propagation across cloud boundaries is a 3 AM surprise. Explicit, auditable, reviewed.
  • → Failover is a sequence; failback is the hard part. Drain replication to zero lag, promote, redirect clients, verify business transactions — and have reverse replication ready before you need it.
  • → Model all four cost centers, especially egress. Measure transaction log volume, set billing alerts on egress, and re-measure quarterly.
