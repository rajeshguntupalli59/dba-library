Chapter 3: The SQL Server Cloud Landscape: AWS, Azure, and Google Cloud

Before choosing services, understand the terrain. Each cloud offers SQL Server in managed and self-managed forms, with different architectures under the hood, different identity systems, different backup mechanics, and different cost models. This chapter maps the landscape — the service taxonomy, the compute/storage architectures, authentication, backup, monitoring, and cost — so the chapters that follow have a foundation to build on. Everything here is SQL Server; the comparisons are between clouds and service models, not engines.

3.1 The Service Taxonomy: What Each Cloud Actually Offers

AWS: RDS for SQL Server — the managed service (automated backups, Multi-AZ failover, no readable secondaries, no IAM database authentication — Chapters 6 and 10). SQL Server on EC2 — self-managed on virtual machines with full engine control, Always On AGs, and readable secondaries (Chapter 8). RDS Proxy for SQL Server — managed connection pooling (Chapter 10).

Azure: Azure SQL Database — the PaaS single-database and elastic-pool offering, no SQL Server Agent (Chapter 14). Azure SQL Managed Instance — near-complete engine compatibility with full Agent support, the lift-and-shift target (Chapter 12). Azure SQL Hyperscale — the disaggregated-storage architecture for very large databases (Chapter 15). SQL Server on Azure VMs — self-managed with Azure Hybrid Benefit and constrained vCPUs (Chapter 13).

Google Cloud: Cloud SQL for SQL Server — the managed service with HA via regional disks (Chapter 19). SQL Server on Compute Engine — self-managed VMs with AG support across zones (Chapter 19). The pattern across clouds is consistent: a managed service that trades control for convenience, and a VM offering that trades convenience for control. The choice between them (Chapter 7's framework) is the most consequential decision in the book.

3.2 Compute and Storage Architecture: What Changes Under the Hood

Under every managed service is the same physical reality — VMs and network-attached storage — with different abstractions. RDS runs SQL Server on EC2-equivalent hosts with EBS storage (gp3/io1/io2 — Chapter 36); Multi-AZ keeps a synchronous standby whose storage is independent. Azure SQL General Purpose uses remote storage with local SSD caching; Business Critical uses local SSD with AG replication between nodes; Hyperscale disaggregates compute from page servers for near-instant scaling and fast restores. Cloud SQL uses regional Persistent Disk with automatic failover to a standby zone.

What this means for the DBA: storage latency characteristics differ by architecture (local SSD vs network-attached — measure PAGEIOLATCH waits, Chapter 35), failover times differ (RDS Multi-AZ 60–120 seconds, Azure BC faster, Cloud SQL 60–120 seconds), and the storage abstraction determines what you can observe (no iostat on managed storage — the platform's metrics are your instrumentation, Chapter 30). The architecture also determines the scaling axes: Hyperscale scales storage to 100 TB without the restore-time penalties of monolithic databases; read scale-out requires self-managed AG secondaries on AWS/GCP but is built into Azure's tiers.

3.3 Authentication and Access Control: Identity Is the New Perimeter

Each cloud has its own identity system, and SQL Server meets it differently: Azure leads with Microsoft Entra ID — native to Azure SQL, supporting managed identities (no passwords) and Entra-only authentication mode (Chapter 31). AWS offers Windows Authentication on RDS via Managed Microsoft AD join, but no IAM database authentication for SQL Server — SQL logins with Secrets Manager rotation fill the gap (Chapters 10, 31). GCP uses the Cloud SQL Auth Proxy with Cloud IAM for access control around SQL logins (Chapter 31). Self-managed SQL Server on any cloud's VMs can join Active Directory for full Kerberos parity with on-premises (Chapters 8, 13, 19).

The networking complement (Chapter 32): private subnets, private endpoints (PrivateLink, Azure Private Link, Private Service Connect), firewall least privilege, and TLS enforcement. The identity story and the network story are designed together — the database that requires Entra authentication but accepts connections from the public internet has solved half the problem.

3.4 Backup and Point-in-Time Recovery: What "Managed" Actually Means

"Managed backups" means the platform runs the schedule — it does not mean you can stop thinking about recovery. RDS automated backups with PITR up to 35 days, plus native backups to S3 via stored procedures for portability. Azure SQL fully automated full/differential/log backups with 7–35 day PITR and long-term retention to 10 years. Cloud SQL automated daily backups with PITR via log archiving. On self-managed VMs, you own the schedule — native backups to object storage with the full/differential/log cadence (Chapter 29).

The DBA's responsibilities don't change: verify restores (automated weekly restore tests — Chapter 29), understand RPO/RTO per mechanism (Chapter 16), keep backup copies in a second region and a second account, and know that PITR on managed services creates a new instance/database rather than overwriting in place — the recovery procedure must include the redirect.

3.5 Performance Monitoring: What You Get, What You Have to Build

Each platform provides the telemetry foundation: CloudWatch + Performance Insights (RDS/EC2), Azure Monitor + Query Store + Intelligent Insights (Azure SQL), Cloud Monitoring + Query Insights (Cloud SQL/GCE). What you get: host metrics, database metrics, and query-level telemetry with history. What you build: the dashboards (health, performance, capacity — Chapter 30), the alerting hierarchy (page/ticket/log with runbook links), and the cross-platform standardization so one DBA reads every cloud's metrics. The non-negotiable: query-level visibility enabled everywhere (Query Store, Performance Insights) — platform metrics show that it's slow; query telemetry shows what is slow (Chapter 35).

3.6 The Operational Cost Model: Thinking in Cloud Units

Cloud databases bill in units the on-premises DBA never saw: vCore-hours or DTUs, provisioned IOPS, storage GB-months, backup GB-months, data transfer GB, and (on serverless) seconds of compute. The cost disciplines from the book's final section: right-sizing from measured p95/peak (Chapter 39), commitments for the stable baseline (Chapter 38), storage tier matching (Chapter 36), secondary economics (Chapter 37), and the unified cost-performance dashboard (Chapter 40). The single most important cost habit: the monthly review where engineering and finance walk the numbers together. Everything else is technique; the review is the institution.

Key Takeaways

  • → Every cloud offers the same two shapes: managed service and self-managed VMs. RDS/Azure SQL/Cloud SQL trade control for convenience; EC2/Azure VMs/GCE trade convenience for control. Learn both shapes on your primary cloud first.
  • → Architecture determines failover time, scaling axes, and observability. Hyperscale's disaggregation, BC's local SSD, RDS's EBS — know what's under your database and what it implies.
  • → Identity differs per cloud; Entra ID leads on Azure. No IAM database auth for SQL Server on RDS — plan secrets rotation. Design identity and networking together.
  • → Managed backups don't remove the DBA's recovery responsibilities. Verify restores weekly, understand PITR mechanics (new instance, not in-place), keep cross-region and cross-account copies.
  • → Enable query-level telemetry everywhere; review cost monthly. Query Store/Performance Insights are non-negotiable; the cost review with finance is the institution that makes all cost technique stick.
