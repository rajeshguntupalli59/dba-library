Chapter 38: Reserved Instances vs On-Demand: The Math

Cloud compute pricing is one of the most consequential decisions a cloud DBA makes, yet it's also one of the most frequently delegated to finance teams who lack the technical context to optimize it properly. The result is organizations either overpaying for on-demand flexibility they don't need, or committing to Reserved Instances at the wrong tier and locking in costs that hurt when the architecture changes. This chapter walks through the actual pricing mechanics across AWS RDS, Azure SQL Database, and Google Cloud SQL—with the arithmetic laid out plainly—so you can make purchasing recommendations backed by data rather than guesswork. The patterns here apply regardless of which cloud you're standardizing on, and the tooling examples show how to audit your existing spend before signing anything.

---

38.1 How Cloud Database Pricing Works Under the Hood

Before running any numbers, you need a mental model of what you're actually buying. On-premises, you paid for hardware, licenses, and labor separately. In the cloud, those costs are bundled into an hourly or per-second rate that changes based on your commitment level.

AWS RDS Pricing Layers

RDS charges have four components that stack on top of each other:

1. Instance hours — the compute cost, billed per second with a one-minute minimum

2. Storage — billed per GB-month, with the rate depending on volume type (GP3, io1, io2); provisioned-IOPS tiers add a separate per-IOPS charge

3. I/O requests — GP2 and GP3 include free I/O up to a baseline; io1/io2 charges per million requests

4. Data transfer — inbound is generally free; outbound to the internet and cross-AZ replication traffic are both billed per GB, at different rates

The instance hour rate is where Reserved Instances make their impact, and this is the number you must pull fresh for your own analysis — do not use a remembered or published figure from any point-in-time source, including this book, because RDS on-demand and reserved pricing varies by instance class, region, engine, and changes over time. The mechanics that matter regardless of the specific rate: a 1-year commitment (No Upfront, Partial Upfront, or All Upfront) buys a materially lower effective hourly rate than on-demand, and a 3-year commitment buys a lower rate still. Get the current numbers for your instance class and region from the AWS Pricing Calculator or the Price List API (shown below) before running any break-even analysis — never plug in a percentage discount you recall from elsewhere.

Azure SQL Database Pricing Layers

Azure SQL Database pricing depends on the service tier you're running. The General Purpose tier bills per vCore-hour. The Business Critical tier carries a substantially higher multiplier for the same vCore count due to the in-memory OLTP and local SSD backing — pull the current multiplier for your region rather than assuming a fixed ratio, since Microsoft has adjusted relative pricing between tiers over time.

Reserved Capacity for Azure SQL follows the same shape as AWS RI mechanics: a 1-year reservation buys a lower effective hourly rate than pay-as-you-go, and a 3-year reservation buys a lower rate still. Pull current rates for your vCore count, tier, and region from the Azure Pricing Calculator before modeling savings.

Azure's Reserved Instance discounts apply to the compute portion only. Storage is charged separately, per GB-month, and is not discountable via reservations.

Google Cloud SQL Pricing Layers

Cloud SQL charges per vCPU-hour and per GB RAM-hour separately, plus a separate storage charge. This is different from AWS and Azure, which bundle CPU and RAM into instance family pricing. Google calls its commitment discounts Committed Use Discounts (CUDs) rather than Reserved Instances, but the economic model is the same: commit to a resource quantity for 1 or 3 years in exchange for a lower effective hourly rate than on-demand. Pull current per-vCPU-hour and per-GB-hour on-demand and CUD rates from the GCP Pricing Calculator for your region and instance shape — the discount percentage for 1-year versus 3-year commitments has been published by Google at different points, so verify it rather than citing a remembered figure.

38.2 Running the Break-Even Analysis

The decision to commit always comes down to one question: how long will this workload run at this scale? If the answer is uncertain, on-demand is the defensible choice regardless of the percentage discount. If the answer is "at least 12 months at this capacity," the math almost always favors reserving.

The break-even formula is straightforward:

Break-Even Hours = Upfront Cost / (On-Demand Hourly Rate - Reserved Hourly Rate)

For example, for an AWS RDS instance on a 1-year Partial Upfront term, plug your own current on-demand hourly rate, reserved upfront payment, and reserved hourly rate (all pulled fresh from the AWS Pricing Calculator or Price List API for your specific instance class and region) into the formula:

Break-Even Hours = Upfront Payment / (On-Demand Hourly - Reserved Hourly)
Break-Even Days  = Break-Even Hours / 24

If the instance runs for longer than the break-even point, the Partial Upfront option has already paid for itself compared to pure on-demand. To project the total annual savings once you have current numbers:

Annual Savings = (On-Demand Hourly × 8760) - (Upfront Payment + Reserved Hourly × 8760)
Savings %      = Annual Savings / (On-Demand Hourly × 8760) × 100

Run this with your own instance's real pricing rather than a figure from any published example — the break-even point and savings percentage both shift with instance class, region, term length, and payment option, and change whenever the provider updates pricing. Multiply the per-instance savings across every instance you're evaluating to see the aggregate impact of a commitment decision on a multi-instance production cluster.

The following Python script automates this analysis across multiple instance types by pulling current pricing from the AWS Price List API:

import boto3
import json
from decimal import Decimal

def get_rds_ondemand_price(region_code, instance_class, engine, deployment_option):
    """
    Retrieves on-demand hourly price for an RDS instance.
    Note: AWS Price List API is only available in us-east-1.
    """
    client = boto3.client('pricing', region_name='us-east-1')
    
    filters = [
        {'Type': 'TERM_MATCH', 'Field': 'instanceType',        'Value': instance_class},
        {'Type': 'TERM_MATCH', 'Field': 'databaseEngine',      'Value': engine},
        {'Type': 'TERM_MATCH', 'Field': 'deploymentOption',    'Value': deployment_option},
        {'Type': 'TERM_MATCH', 'Field': 'location',            'Value': region_code},
        {'Type': 'TERM_MATCH', 'Field': 'termType',            'Value': 'OnDemand'},
    ]
    
    response = client.get_products(
        ServiceCode='AmazonRDS',
        Filters=filters,
        MaxResults=1
    )
    
    if not response['PriceList']:
        return None
    
    price_item = json.loads(response['PriceList'][0])
    terms = price_item['terms']['OnDemand']
    
    for term_key in terms:
        for price_dimension_key in terms[term_key]['priceDimensions']:
            pd = terms[term_key]['priceDimensions'][price_dimension_key]
            if pd['unit'] == 'Hrs':
                return Decimal(pd['pricePerUnit']['USD'])
    
    return None

def calculate_breakeven(ondemand_hourly, reserved_hourly, upfront_cost):
    """
    Returns break-even in hours and days.
    """
    hourly_savings = ondemand_hourly - reserved_hourly
    if hourly_savings <= 0:
        return None, None
    
    breakeven_hours = float(upfront_cost) / float(hourly_savings)
    breakeven_days  = breakeven_hours / 24
    return breakeven_hours, breakeven_days

def project_annual_savings(ondemand_hourly, reserved_hourly, upfront_cost, 
                            utilization_hours=8760):
    """
    Projects total cost and savings over one year at a given utilization.
    Assumes utilization_hours = 8760 for 24x7 workloads.
    """
    ondemand_annual  = float(ondemand_hourly) * utilization_hours
    reserved_annual  = float(upfront_cost) + (float(reserved_hourly) * utilization_hours)
    savings          = ondemand_annual - reserved_annual
    savings_pct      = (savings / ondemand_annual) * 100
    
    return {
        'on_demand_annual':  round(ondemand_annual, 2),
        'reserved_annual':   round(reserved_annual, 2),
        'savings':           round(savings, 2),
        'savings_pct':       round(savings_pct, 1)
    }

# Example: db.r6i.2xlarge, SQL Server SE, Multi-AZ, us-east-1
# These rates are illustrative; pull live rates from AWS Price List or Savings Plans API
instances_to_evaluate = [
    {
        'instance_class':    'db.r6i.2xlarge',
        'engine':            'sqlserver-se',
        'deployment':        'Multi-AZ',
        'ondemand_hourly':   0.960,   # Multi-AZ doubles compute cost
        'reserved_upfront':  2200,
        'reserved_hourly':   0.352,
        'term':              '1yr Partial Upfront'
    },
    {
        'instance_class':    'db.r6i.4xlarge',
        'engine':            'sqlserver-se',
        'deployment':        'Multi-AZ',
        'ondemand_hourly':   1.920,
        'reserved_upfront':  4400,
        'reserved_hourly':   0.704,
        'term':              '1yr Partial Upfront'
    }
]

for inst in instances_to_evaluate:
    beh, bed = calculate_breakeven(
        inst['ondemand_hourly'],
        inst['reserved_hourly'],
        inst['reserved_upfront']
    )
    projection = project_annual_savings(
        inst['ondemand_hourly'],
        inst['reserved_hourly'],
        inst['reserved_upfront']
    )
    
    print(f"\n{'='*60}")
    print(f"Instance:      {inst['instance_class']} ({inst['deployment']})")
    print(f"Term:          {inst['term']}")
    print(f"Break-even:    {beh:.0f} hours ({bed:.0f} days)")
    print(f"On-Demand/yr:  ${projection['on_demand_annual']:,.2f}")
    print(f"Reserved/yr:   ${projection['reserved_annual']:,.2f}")
    print(f"Annual savings: ${projection['savings']:,.2f} ({projection['savings_pct']}%)")

Running this against your actual instance inventory gives you a defensible business case for RI purchases without relying on vendor-provided calculators that tend to assume 100% utilization.

38.3 Reserved Instance Mechanics: What the Contracts Actually Say

Understanding the contract structure prevents the most common RI mistakes—buying the wrong scope, overcommitting on instance family, or missing the difference between Convertible and Standard RIs.

AWS RI Types and Flexibility Rules

AWS RDS offers two RI types:

  • → Standard Reserved Instances: Maximum discount, but instance family is fixed. You cannot modify a `db.r6i` Standard RI to cover a `db.r7g` instance.
  • → Convertible Reserved Instances: A somewhat smaller discount than Standard RIs at the same term and payment option — check the current gap for your instance class, since AWS has adjusted relative pricing between the two types over time — but you can exchange them for different instance types, regions, or database engines at any time during the term.

    • The flexibility argument for Convertible RIs is real when you're within 18–24 months of a likely architecture change—say, a SQL Server 2019 cluster that will migrate to SQL Server 2022 (or to Azure SQL Managed Instance) within the RI term. Standard RIs would strand that commitment; Convertible RIs let you exchange them.

    AWS also separates RI scope into Regional and Zonal:

  • → Regional RIs apply to any instance of the matching type in any AZ within that region and get Availability Zone flexibility
  • → Zonal RIs apply to a specific AZ only, but guarantee capacity reservation in that AZ—useful if you're running in capacity-constrained regions

    • For production databases, Regional scope is almost always correct unless you have a specific capacity reservation requirement.

    38.4 Sizing Commitments Against Real Workload Data

    The most expensive RI mistake is buying capacity based on current provisioning rather than actual utilization. If you're running a db.r6i.4xlarge at 15% average CPU utilization because the instance was provisioned for peak load three years ago, committing to that instance class locks in overspend.

    Before any RI purchase, pull at least 90 days of utilization data. For AWS RDS, that data lives in CloudWatch.

    import boto3
from datetime import datetime, timedelta
import statistics

def get_rds_utilization_stats(db_instance_id, region, days=90):
    """
    Retrieves CPU, FreeableMemory, DatabaseConnections, and ReadIOPS/WriteIOPS
    for the last N days to inform RI sizing decisions.
    """
    cloudwatch = boto3.client('cloudwatch', region_name=region)
    
    end_time   = datetime.utcnow()
    start_time = end_time - timedelta(days=days)
    
    metrics = {
        'CPUUtilization':       {'stat': 'Average', 'unit': 'Percent'},
        'FreeableMemory':       {'stat': 'Average', 'unit': 'Bytes'},
        'DatabaseConnections':  {'stat': 'Maximum', 'unit': 'Count'},
        'ReadIOPS':             {'stat': 'Average', 'unit': 'Count/Second'},
        'WriteIOPS':            {'stat': 'Average', 'unit': 'Count/Second'},
    }
    
    results = {}
    
    for metric_name, config in metrics.items():
        response = cloudwatch.get_metric_statistics(
            Namespace='AWS/RDS',
            MetricName=metric_name,
            Dimensions=[{'Name': 'DBInstanceIdentifier', 'Value': db_instance_id}],
            StartTime=start_time,
            EndTime=end_time,
            Period=3600,  # 1-hour granularity
            Statistics=[config['stat']]
        )
        
        datapoints = sorted(response['Datapoints'], key=lambda x: x['Timestamp'])
        values = [dp[config['stat']] for dp in datapoints]
        
        if values:
            results[metric_name] = {
                'mean':    round(statistics.mean(values), 2),
                'median':  round(statistics.median(values), 2),
                'p95':     round(sorted(values)[int(len(values) * 0.95)], 2),
                'p99':     round(sorted(values)[int(len(values) * 0.99)], 2),
                'max':     round(max(values), 2),
                'samples': len(values)
            }
    
    return results

def recommend_instance_class(stats, current_instance_class):
    """
    Provides a rough right-sizing recommendation based on CPU utilization.
    In practice, combine with memory pressure and connection count analysis.
    """
    cpu_p95 = stats.get('CPUUtilization', {}).get('p95', 100)
    cpu_mean = stats.get('CPUUtilization', {}).get('mean', 100)
    
    recommendation = current_instance_class
    notes = []
    
    if cpu_p95 < 20:
        notes.append(f"P95 CPU {cpu_p95}% — strong candidate for downsizing one instance class")
    elif cpu_p95 < 40:
        notes.append(f"P95 CPU {cpu_p95}% — current sizing is adequate; commit at this level")
    elif cpu_p95 < 70:
        notes.append(f"P95 CPU {cpu_p95}% — healthy utilization; commit at this level")
    else:
        notes.append(f"P95 CPU {cpu_p95}% — consider upsizing before committing")
    
    return recommendation, notes

# Example usage
db_instance_id  = 'prod-sqlserver-primary'
region          = 'us-east-1'
current_class   = 'db.r6i.4xlarge'

print(f"Analyzing {db_instance_id} over 90 days...")
stats = get_rds_utilization_stats(db_instance_id, region, days=90)

for metric, values in stats.items():
    print(f"\n{metric}:")
    print(f"  Mean: {values['mean']}  |  Median: {values['median']}")
    print(f"  P95:  {values['p95']}   |  P99:    {values['p99']}   |  Max: {values['max']}")

recommended_class, notes = recommend_instance_class(stats, current_class)
print(f"\nRight-sizing analysis for {current_class}:")
for note in notes:
    print(f"  → {note}")

    For Azure SQL, the equivalent utilization data comes from Azure Monitor. The sys.dm_db_resource_stats DMV provides per-database resource consumption at 15-second intervals for the last hour; sys.resource_stats in the master database covers the last 14 days at 1-minute granularity.

    -- Azure SQL Database: 14-day resource utilization summary
-- Run this against the master database of your Azure SQL logical server
SELECT
    database_name,
    CAST(start_time AS DATE)                         AS sample_date,
    ROUND(AVG(avg_cpu_percent), 2)                   AS avg_cpu_pct,
    ROUND(MAX(avg_cpu_percent), 2)                   AS max_cpu_pct,
    ROUND(AVG(avg_memory_usage_percent), 2)          AS avg_mem_pct,
    ROUND(MAX(avg_memory_usage_percent), 2)          AS max_mem_pct,
    ROUND(AVG(avg_data_io_percent), 2)               AS avg_data_io_pct,
    ROUND(MAX(avg_data_io_percent), 2)               AS max_data_io_pct,
    MAX(max_session_count)                           AS peak_sessions,
    COUNT(*)                                         AS sample_count
FROM
    sys.resource_stats
WHERE
    start_time >= DATEADD(DAY, -14, GETUTCDATE())  -- sys.resource_stats retains 14 days
GROUP BY
    database_name,
    CAST(start_time AS DATE)
ORDER BY
    database_name,
    sample_date DESC;

-- Identify databases consistently below 20% CPU — right-sizing candidates
-- PERCENTILE_CONT is a per-row windowed value, so compute it in a CTE
-- before aggregating — combining it directly with GROUP BY would collapse
-- each database to a single row before the percentile has anything to work over
WITH per_row_percentiles AS (
    SELECT
        database_name,
        avg_cpu_percent,
        PERCENTILE_CONT(0.95) WITHIN GROUP
            (ORDER BY avg_cpu_percent) OVER
            (PARTITION BY database_name) AS p95_cpu_pct
    FROM sys.resource_stats
    WHERE start_time >= DATEADD(DAY, -14, GETUTCDATE())  -- sys.resource_stats retains 14 days
)
SELECT
    database_name,
    ROUND(AVG(avg_cpu_percent), 2) AS avg_cpu_pct,
    ROUND(MAX(p95_cpu_pct), 2)     AS p95_cpu_pct,
    ROUND(MAX(avg_cpu_percent), 2) AS max_cpu_pct
FROM per_row_percentiles
GROUP BY database_name
HAVING
    AVG(avg_cpu_percent) < 20
    AND MAX(avg_cpu_percent) < 40
ORDER BY
    avg_cpu_pct ASC;

    For Google Cloud SQL, utilization data is available through Cloud Monitoring (formerly Stackdriver). The gcloud CLI can pull metric time series, but for bulk analysis the Python client is more practical:

    from google.cloud import monitoring_v3
from datetime import datetime, timedelta
import time

def get_cloudsql_utilization(project_id, instance_id, region, days=90):
    """
    Retrieves CPU utilization and memory utilization for a Cloud SQL instance
    over the specified window.
    """
    client = monitoring_v3.MetricServiceClient()
    project_name = f"projects/{project_id}"

    end_time   = datetime.utcnow()
    start_time = end_time - timedelta(days=days)

    interval = monitoring_v3.TimeInterval(
        {
            "end_time":   {"seconds": int(end_time.timestamp())},
            "start_time": {"seconds": int(start_time.timestamp())},
        }
    )

    metrics_to_pull = {
        "cloudsql.googleapis.com/database/cpu/utilization":    "CPU",
        "cloudsql.googleapis.com/database/memory/utilization": "Memory",
    }

    results = {}

    for metric_type, label in metrics_to_pull.items():
        aggregation = monitoring_v3.Aggregation(
            {
                "alignment_period":   {"seconds": 3600},
                "per_series_aligner": monitoring_v3.Aggregation.Aligner.ALIGN_MEAN,
            }
        )

        filter_str = (
            f'metric.type="{metric_type}" '
            f'AND resource.labels.database_id="{project_id}:{instance_id}"'
        )

        results_iter = client.list_time_series(
            request={
                "name":        project_name,
                "filter":      filter_str,
                "interval":    interval,
                "view":        monitoring_v3.ListTimeSeriesRequest.TimeSeriesView.FULL,
                "aggregation": aggregation,
            }
        )

        values = []
        for series in results_iter:
            for point in series.points:
                values.append(point.value.double_value * 100)  # convert to percentage

        if values:
            sorted_vals = sorted(values)
            results[label] = {
                "mean":    round(sum(values) / len(values), 2),
                "p95":     round(sorted_vals[int(len(sorted_vals) * 0.95)], 2),
                "p99":     round(sorted_vals[int(len(sorted_vals) * 0.99)], 2),
                "max":     round(max(values), 2),
                "samples": len(values),
            }

    return results

# Example usage
project_id  = "your-gcp-project"
instance_id = "prod-sqlserver-primary"
region      = "us-central1"

stats = get_cloudsql_utilization(project_id, instance_id, region, days=90)
for resource, values in stats.items():
    print(f"\n{resource} Utilization (90-day):")
    print(f"  Mean: {values['mean']}%  |  P95: {values['p95']}%  |  P99: {values['p99']}%  |  Max: {values['max']}%")

    The utilization analysis should drive the commitment quantity, not the provisioned instance size. A general rule used in practice: commit at the P75 utilization level for stable workloads, leaving headroom for P95 spikes to absorb against on-demand pricing. For databases with highly seasonal traffic—a retail OLTP database with holiday peaks, for example—consider committing at base load and letting the seasonal burst run on-demand.

    38.5 Cross-Cloud Comparison: Where Each Provider's Model Has Edges

    No single cloud's commitment model is strictly superior. The right choice depends on workload characteristics, architectural stability, and financial flexibility requirements.

    AWS RDS Advantages

  • → Convertible RIs give genuine architectural flexibility without sacrificing the full discount in one step
  • → Per-instance granularity means you can commit selectively: reserve your three stable production primaries, leave dev/test and read replicas on-demand
  • → Multi-AZ RIs are purchased as a single SKU; you don't separately reserve primary and standby
  • → Savings Plans (compute-level, not database-level) can cover EC2-based database workloads if you're running databases on EC2 rather than RDS

    • Azure SQL Advantages

  • → vCore pooling means a single reservation can float across multiple databases as they scale up and down, reducing the risk of stranded reservation capacity
  • → The Azure Hybrid Benefit can stack on top of reservations: if you have existing SQL Server licenses with Software Assurance, you can apply them to reduce the effective rate further by eliminating the license portion of the rate — check current Azure Hybrid Benefit terms and your license entitlement to quantify the exact reduction for your configuration
  • → Reservation exchanges (swapping to a different SKU) are supported in Azure without the Convertible RI equivalent overhead

    • Google Cloud SQL Advantages

  • → CUDs apply at the resource level (vCPUs + memory) rather than the instance level, giving the most flexibility for workloads that fluctuate in instance shape
  • → Unlike Compute Engine VMs, Cloud SQL does not receive automatic Sustained Use Discounts — the CUD is the only discount lever for Cloud SQL compute, so there is no passive safety net for teams that fail to commit; verify current GCP documentation for your specific service before assuming any automatic discount applies

    • When On-Demand Is the Correct Answer

    The math strongly favors reservations for stable production workloads, but on-demand is genuinely correct in several scenarios:

    1. Workloads under 6 months: Even with a 1-year commitment, if there's meaningful probability the workload ends or changes significantly within 6–9 months, on-demand is lower total risk.

    2. Active migration projects: A database in the middle of a cloud-to-cloud or on-prem-to-cloud migration is not a stable commitment candidate. Buy the RI 30–60 days after the migration stabilizes.

    3. Development and testing environments: Unless your dev environment is truly persistent and large enough to make the math work, on-demand keeps options open for scaling down or pausing instances.

    4. Pilot workloads on a new engine: If you're evaluating a new service tier or platform, you don't yet know the steady-state instance class. Running on-demand through the evaluation period is the correct approach.

    38.6 Auditing Existing Commitments for Waste

    Just as important as making the right purchase decision is monitoring whether existing commitments are being utilized. Stranded Reserved Instances—reservations covering instances that were resized, migrated, or decommissioned—are a common source of invisible waste.

    AWS: Checking RI Utilization via Cost Explorer

    AWS Cost Explorer provides RI utilization reports through both the console and the API. The API is useful for scheduled reporting.

    import boto3
from datetime import datetime, timedelta

def get_ri_utilization_report(region, lookback_days=30):
    """
    Pulls RI utilization from AWS Cost Explorer.
    Flags any RI with utilization below 80% as potentially stranded.
    """
    ce_client = boto3.client('ce', region_name='us-east-1')  # CE API is global, endpoint is us-east-1

    end_date   = datetime.utcnow().strftime('%Y-%m-%d')
    start_date = (datetime.utcnow() - timedelta(days=lookback_days)).strftime('%Y-%m-%d')

    response = ce_client.get_reservation_utilization(
        TimePeriod={
            'Start': start_date,
            'End':   end_date,
        },
        GroupBy=[
            {'Type': 'DIMENSION', 'Key': 'SUBSCRIPTION_ID'},
        ],
        Filter={
            'Dimensions': {
                'Key':    'SERVICE',
                'Values': ['Amazon Relational Database Service'],
            }
        }
    )

    print(f"\nRDS RI Utilization Report ({start_date} to {end_date})")
    print("=" * 70)

    total_purchased_hours   = 0
    total_utilized_hours    = 0
    stranded_reservations   = []

    for group in response.get('UtilizationsByTime', []):
        for item in group.get('Groups', []):
            sub_id  = item['Keys'][0]
            util    = item['Utilization']

            purchased_hours = float(util.get('PurchasedHours', 0))
            utilized_hours  = float(util.get('TotalActualHours', 0))
            util_pct        = float(util.get('UtilizationPercentage', 0))
            unused_cost     = float(util.get('UnusedAmortizedUpfrontFeeForBillingPeriod', 0)) \
                            + float(util.get('UnusedRecurringFee', 0))

            total_purchased_hours += purchased_hours
            total_utilized_hours  += utilized_hours

            status = "✓ OK" if util_pct >= 80 else "⚠ REVIEW"
            print(f"{status}  Subscription: {sub_id[:20]:<22} "
                  f"Utilization: {util_pct:5.1f}%  "
                  f"Unused cost: ${unused_cost:,.2f}")

            if util_pct < 80:
                stranded_reservations.append({
                    'subscription_id': sub_id,
                    'utilization_pct': util_pct,
                    'unused_cost':     unused_cost
                })

    overall_util = (total_utilized_hours / total_purchased_hours * 100) \
                   if total_purchased_hours > 0 else 0
    print(f"\nOverall RDS RI Utilization: {overall_util:.1f}%")

    if stranded_reservations:
        total_stranded_cost = sum(r['unused_cost'] for r in stranded_reservations)
        print(f"\n⚠ {len(stranded_reservations)} reservation(s) below 80% utilization")
        print(f"  Estimated wasted spend this period: ${total_stranded_cost:,.2f}")
        print("  Consider modifying, exchanging (Convertible only), or ")
        print("  listing on the AWS Reserved Instance Marketplace.")

    return stranded_reservations

    38.7 The RI Purchase Workflow for Production Teams

    The mechanics of the analysis matter less than having a repeatable process that prevents both panic-buying and perpetual deferral. The following workflow can be run quarterly and produces a prioritized recommendation list ready for finance approval.

    Step 1: Inventory all running database instances

    Pull a complete list of running database instances across all accounts and regions, including their instance class, engine, Multi-AZ status, and whether they're currently covered by an RI.

    # AWS: inventory all RDS instances across regions
for region in $(aws ec2 describe-regions --query 'Regions[].RegionName' --output text); do
  echo "=== $region ==="
  aws rds describe-db-instances \
    --region "$region" \
    --query 'DBInstances[*].{
      ID:DBInstanceIdentifier,
      Class:DBInstanceClass,
      Engine:Engine,
      EngineVersion:EngineVersion,
      MultiAZ:MultiAZ,
      Status:DBInstanceStatus,
      Storage:AllocatedStorage
    }' \
    --output table 2>/dev/null
done

# Cross-reference against existing RIs to find uncovered instances
aws rds describe-reserved-db-instances \
  --region us-east-1 \
  --query 'ReservedDBInstances[?State==`active`].{
    Class:DBInstanceClass,
    Engine:ProductDescription,
    MultiAZ:MultiAZ,
    Count:DBInstanceCount,
    Expiry:StartTime
  }' \
  --output table

    Step 2: Score each instance on commitment suitability

    Not all instances deserve the same commitment strategy. Score each candidate on three axes:

    | Axis | Low Suitability (0) | High Suitability (2) |

    |------|--------------------|-----------------------|

    | Workload stability | Active migration in progress | Running unchanged 12+ months |

    | Utilization efficiency | P95 CPU < 20% (likely to be right-sized) | P95 CPU 40–70% |

    | Time horizon | Architectural change expected < 9 months | No changes planned for 18+ months |

    Instances with a total score of 4 or higher are strong RI candidates. Instances with scores of 2 or below should run on-demand until conditions improve.

    Step 3: Calculate the purchase recommendation

    For each high-scoring instance, run the break-even and annual savings calculation from Section 38.2. Produce a ranked list sorted by total annual savings, not by savings percentage—a 38% discount on a large instance produces more absolute dollars saved than a 40% discount on a small one.

    graph TD
    A[Inventory all running
    database instances] --> B[Score each on stability,
    utilization, time horizon]
    B --> C{Score >= 4?}
    C -->|No| D[Leave on-demand,

    highest-confidence instances first]
    F --> G[Set 90/60/30-day
    expiration alerts]

    *A repeatable quarterly process beats a one-time bulk purchase decision — staging limits exposure if workload assumptions turn out wrong.*

    Step 4: Stage the purchase

    Don't commit the entire inventory in one transaction. A staged approach reduces risk:

  • → Week 1: Purchase RIs for instances with scores of 6 (maximum) that have been running stable for 18+ months
  • → Month 1: Add instances with scores of 4–5 after confirming no architectural changes are imminent
  • → Quarter 2: Reassess remaining on-demand instances for newly earned stability

    • For AWS, if you're uncertain between Standard and Convertible RIs, run the first purchase as Convertible. The discount gap is modest, and the exchange flexibility is genuinely valuable during initial portfolio optimization.

    Step 5: Set expiration alerts

    RI expirations are a known risk: a reservation that expires unnoticed flips the instance back to on-demand rates silently. Set calendar alerts 90, 60, and 30 days before each RI expiration date. For AWS, you can automate this with EventBridge:

    # Create a CloudWatch alarm that fires when an RI is expiring within 60 days
# This uses the AWS Health API to surface RI expiration events
aws events put-rule \
  --name "RDSReservedInstanceExpirationAlert" \
  --event-pattern '{
    "source": ["aws.health"],
    "detail-type": ["AWS Health Event"],
    "detail": {
      "service": ["RDS"],
      "eventTypeCategory": ["scheduledChange"],
      "eventTypeCode": ["AWS_RDS_RESERVED_INSTANCE_EXPIRATION_SCHEDULED"]
    }
  }' \
  --state ENABLED \
  --region us-east-1

# Attach an SNS topic to the rule for notification
aws events put-targets \
  --rule "RDSReservedInstanceExpirationAlert" \
  --targets '[{
    "Id": "1",
    "Arn": "arn:aws:sns:us-east-1:123456789012:db-ops-alerts"
  }]' \
  --region us-east-1

    Key Takeaways

  • → The discount is real and substantial, but so is the commitment risk: across all three major clouds, 1-year commitments deliver a meaningfully lower effective hourly rate than on-demand, and 3-year commitments deliver a lower rate still — but the exact percentage varies by provider, instance class, region, and payment option, and changes as providers update pricing. Pull current numbers before committing, and only after the workload runs as expected. Analyze workload stability before size, and size before committing.
  • → Utilization data must precede the purchase: Committing to an instance class based on provisioned size rather than 90-day utilization history locks in overspend for the entire term. Pull P95 CPU and memory data, right-size first, then commit.
  • → Each cloud's commitment model has distinct flexibility characteristics: AWS Convertible RIs allow mid-term exchanges at the cost of a modest discount reduction; Azure vCore pooling floats coverage across multiple databases automatically; GCP CUDs apply at the resource level and survive instance type changes. Match the commitment type to your architectural confidence level.
  • → Stranded reservations are as costly as missing reservations: A quarterly audit of RI utilization using Cost Explorer (AWS), Azure Cost Management, or GCP Billing export will surface underutilized commitments early enough to exchange or sell them before the waste compounds.
  • → Build a repeatable purchase workflow, not a one-time event: Inventory all instances, score them on stability and utilization efficiency, calculate ranked savings, stage purchases over weeks rather than days, and set automated expiration alerts. Organizations that treat RI management as an ongoing operational process consistently outperform those that approach it as an annual finance exercise.
