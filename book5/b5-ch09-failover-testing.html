Chapter 9: Failover Testing and Game Days: Proving Your SQL Server HA Works

Every architecture in Chapters 6 through 8 — RDS Multi-AZ, Always On availability groups on EC2, Azure failover groups — makes a promise: when the primary fails, the workload continues. That promise is worth exactly as much as your last successful test of it. Untested high availability is not high availability; it is optimism with a diagram. This chapter is about turning the diagrams into evidence: how to test failovers safely, how to measure what actually happens, how to make applications survive the transition, and how to run game days that find the gaps before your customers do.

9.1 The Failover You Never Tested

The pattern repeats across the industry: a team builds Multi-AZ or an availability group, watches one clean failover during the initial setup, and never tests again. Eighteen months later the primary fails at 2 AM and the team discovers that the application connection strings never had MultiSubnetFailover=True, the reporting job points at the old primary's DNS name cached in a config file, the logins on the secondary are missing three service accounts created last quarter, and the runbook describes an architecture that was redesigned six months ago. The failover "worked" — the database came up on the secondary — and the application was down for 47 minutes anyway.

Failover testing has a half-life. Connection strings change, logins drift, DNS TTLs get modified, application retry logic gets refactored away by someone who never saw the original incident. A failover test is a measurement of the entire system — database, network, application, and operations — at a point in time. Repeat it on a schedule or it decays.

9.2 What to Test on Each Platform

RDS Multi-AZ: reboot with failover. The safe, supported test is reboot-db-instance --force-failover. This exercises the real failover path: DNS update, AG replica promotion, and application reconnect. Do it during a maintenance window the first time, then promote it to a quarterly scheduled test. Watch the actual client-observed downtime, not the RDS event timestamps — the gap between "RDS says failover complete" and "application serving traffic" is the number that matters.

# Planned failover test on RDS Multi-AZ (safe: exercises the real path)
aws rds reboot-db-instance \
  --db-instance-identifier prod-sql-primary \
  --force-failover \
  --region us-east-1

# Watch the failover events in real time
aws rds describe-events \
  --source-identifier prod-sql-primary \
  --source-type db-instance \
  --start-time $(date -u -d '10 minutes ago' +%Y-%m-%dT%H:%M:%SZ) \
  --query 'Events[*].[Date,Message]' \
  --output table \
  --region us-east-1

Always On AGs on EC2: manual failover. Use ALTER AVAILABILITY GROUP ... FAILOVER for planned tests — it validates the listener, the quorum, and the client drivers without the chaos of a real crash. Then, once planned failovers are boring, test unplanned: stop the SQL Server service on the primary (not the whole VM — you want to test database-level failure first, host-level failure second). Verify that automatic failover triggers within your configured timeout and that the application reconnects through the multi-subnet listener.

-- Planned AG failover test (run on the primary replica)
ALTER AVAILABILITY GROUP [ag_prod] FAILOVER;
GO

-- Verify the new primary and replica roles after failover
SELECT ar.replica_server_name,
       rs.role_desc,
       drs.synchronization_state_desc,
       drs.last_commit_time
FROM sys.dm_hadr_availability_replica_states rs
JOIN sys.availability_replicas ar ON rs.replica_id = ar.replica_id
JOIN sys.dm_hadr_database_replica_states drs ON drs.replica_id = rs.replica_id
WHERE drs.is_local = 1;

Azure: failover group drills. For Managed Instance and SQL Database failover groups, use a planned failover from the Azure portal or CLI during a window, then graduate to forced failover (which simulates data loss — verify your RPO expectations against reality). Azure's grace period setting exists to prevent flapping; test with the grace period you run in production, because it directly adds to observed downtime.

# Planned failover of an Azure failover group (test the listener endpoint)
az sql failover-group set-primary \
  --resource-group rg-prod \
  --server sqlsrv-secondary \
  --name fg-prod \
  --allow-data-loss false

9.3 Measuring RTO Honestly

Vendor RTO numbers measure the database. Your RTO is measured at the client. Instrument the full chain: a canary job that executes a trivial write every 10 seconds and records gaps; application-level success-rate dashboards during the test; DNS resolution time for the endpoint (RDS endpoint DNS changes propagate in 60–120 seconds, and clients with aggressive DNS caching see longer); and connection-pool drain time (pools full of dead connections to the old primary must detect failure, discard, and reconnect — misconfigured pools turn a 60-second database failover into a 10-minute application outage).

Record three numbers from every test: detection time (failure to failover initiation), promotion time (failover initiation to new primary accepting writes), and client recovery time (new primary accepting writes to application fully serving traffic). The third number is always the largest, and it is the only one your users experience. If client recovery dominates, your next investment is application resilience (section 9.4), not database tuning.

9.4 Application Resilience: Surviving the Transition

The database can fail over perfectly and the application can still fall over. The application-side requirements:

  • → Retry logic with backoff. Transient failures during failover (connection refused, transport errors, 40613 on Azure, 40197 during reconfiguration) must be retried, not surfaced to users. .NET's SqlConnection with ConnectRetryCount/ConnectRetryInterval handles connection-phase retries; command-phase retries belong in your data access layer or a library like Polly.
  • → MultiSubnetFailover=True on every connection string. For AG listeners (EC2) and Azure failover group listeners. Audit relentlessly — the ETL package, the BI tool, and the legacy Windows service are where this gets missed.
  • → Idempotent writes. A write that succeeded on the old primary but whose acknowledgment was lost will be retried by the client. If the retry is not idempotent, failover creates duplicate orders, duplicate payments, duplicate rows. Design for at-least-once delivery at the database boundary.
  • → Read-only intent where possible. Reporting connections using ApplicationIntent=ReadOnly route to readable secondaries where they exist (EC2 AGs, MI Business Critical) and keep the primary's connection budget for writes during the chaos of a failover.

    • 9.5 Designing a Game Day

    A game day is a scheduled, controlled failure exercise with observers, a timeline, and a blameless review. Start small and escalate across quarters:

  • → Level 1: planned failover. Announced, during business hours, full team watching. Success criterion: client-observed downtime within the RTO budget and zero manual steps beyond the planned ones.
  • → Level 2: unplanned primary kill. Stop the SQL Server service (or reboot the primary VM) without warning the application team — but with the DBA team ready. Success criterion: automatic failover completes, application recovers via retry logic, and nobody pages anyone.
  • → Level 3: AZ failure simulation. Block network traffic to the primary's AZ (security group rules or route manipulation) to simulate AZ impairment rather than clean host death. This tests quorum behavior, witness function, and the difference between "host down" and "network partition" — the scenario that causes split-brain anxiety.
  • → Level 4: region drill. Fail over the DR topology (restore from cross-region snapshot, or fail over the Azure failover group with data loss allowed) and run the business's critical transactions against it. This is the only test that validates your actual disaster recovery, as opposed to your high availability.

    • Rules for all levels: never run a game day you cannot abort; have an explicit rollback decision-maker; record everything; and hold the blameless review within 48 hours while memories are fresh. The review's output is not a grade — it is work items: the missing login, the un-audited connection string, the runbook paragraph that lied.

    9.6 Post-Failover Validation Checklist

    The failover completing is the midpoint, not the end. Run this validation before declaring victory — automate it as a post-failover job:

  • → Replica roles and sync state. Confirm the old primary is now a synchronized secondary (not stuck in NOT SYNCHRONIZING), and that all databases joined the AG cleanly. A database that failed to join the group after failover is a data-loss incident wearing a success costume.
  • → Logins and jobs. Compare sys.server_principals and msdb.dbo.sysjobs between replicas. Logins and Agent jobs live outside the availability group — drift here is the number one cause of "failover worked but the app is broken."
  • → Database integrity spot-check. Run DBCC CHECKDB on the most critical database, or at minimum verify the latest backup chain is intact on the new primary.
  • → Application smoke tests. Execute the business's critical transactions end to end — login, search, checkout, report — not just a SELECT 1. Wire these into your deployment pipeline so they exist before you need them.
  • → Monitoring re-baselining. Confirm alerts, dashboards, and backup jobs are pointing at the new primary. Backup jobs that kept targeting the old primary's hostname silently stop protecting you.
    • -- Post-failover drift check: logins present on primary but missing on secondary
-- Run on the secondary; compare against the primary's list
SELECT sp.name AS login_name, sp.type_desc
FROM sys.server_principals sp
WHERE sp.type IN ('S', 'U', 'G')
  AND sp.name NOT LIKE '##%'
  AND NOT EXISTS (
      SELECT 1 FROM [PRIMARY_LINKED].master.sys.server_principals p
      WHERE p.name = sp.name
  );
-- (Replace PRIMARY_LINKED with a linked server to the primary,
--  or export both lists and diff them in your automation.)

    9.7 When Failover Goes Wrong: Real Failure Modes

    Game days exist because failovers fail in specific, repeatable ways. Knowing the failure modes in advance turns a 3 AM mystery into a checklist:

  • → Quorum loss. The cluster loses majority — typically an AZ failure in a two-AZ design without a working witness, or the witness share becoming unreachable at the worst moment. Symptom: the AG goes offline everywhere instead of failing over. Prevention: three AZs or a verified witness, and a game day that actually kills an AZ rather than a SQL Server service.
  • → Database not joined. A database on the new primary sits in NOT SYNCHRONIZING because a log backup chain broke, a file path differs between replicas, or the database was added to the instance but never joined to the group. The AG reports healthy; the database is not protected. Your validation checklist must check per-database state, not just replica state.
  • → Listener DNS staleness. Clients cache the old listener IPs past the DNS TTL — Java JVMs cache DNS forever by default unless networkaddress.cache.ttl is set, and some connection pools hold resolved addresses for the pool's lifetime. After a failover, a subset of application servers keep hammering the dead primary while others work fine — the most confusing partial-outage pattern in this space.
  • → Azure grace period surprise. A failover group with a one-hour grace period will not fail over automatically for one hour after an outage begins — by design, to ride out transient blips. If your RTO budget is 15 minutes, the grace period must be 15 minutes or less. This is a configuration value that directly contradicts the RTO unless someone sets it deliberately.
  • → RDS failover during heavy write load. Failover time stretches when the secondary has redo backlog — the promotion must complete crash recovery before accepting writes. If your workload generates log faster than the secondary redoes it, your tested 90-second failover becomes a 12-minute one under production load. Test failover under load, not just on a quiet Sunday.
  • → Split-brain writes. True split-brain (two primaries accepting writes) is prevented by quorum on AGs and by the platform on RDS/Azure — but application-level split-brain happens when a "failed" primary is actually still alive and serving a subset of clients that never noticed the failover (see DNS staleness above). Fence the old primary: revoke its client network access or stop the service as part of the failover procedure.

    • For each failure mode, your runbook should name the symptom, the detection query or alarm, and the remediation command. The team that has rehearsed quorum loss in a game day recovers in minutes; the team meeting it for the first time at 3 AM recovers in hours.

    9.8 Automating Failover Tests

    Manual failover tests happen twice and then stop. Automated ones happen on schedule. Build a quarterly pipeline: trigger the failover (SSM automation document for EC2, a scheduled Lambda for RDS reboot-db-instance --force-failover, an Azure DevOps pipeline for failover groups), run the canary workload, collect the three RTO numbers, run the validation checklist, and publish the results to the team channel. Alert on regression: if client recovery time grows quarter over quarter, something drifted — find it while it is a graph, not an incident.

    Keep the automation's blast radius explicit: it should only ever target the instances in its scope, require an explicit approval gate for production (at least until the team trusts it), and log every action with timestamps for the review. The goal is boring, repeatable evidence — not chaos for its own sake.

    9.9 The Runbook Is a Product

    Every game day produces runbook updates. Treat the failover runbook as a product with users (the on-call DBA at 3 AM), versioning, and a test suite (the game days themselves). It should contain: the exact commands for planned and forced failover on your platform; the expected timeline with the three RTO numbers from the last test; the validation checklist; the escalation path when failover does not complete; and the known gaps with their work-item links. A runbook nobody has tested is documentation; a runbook validated by last quarter's game day is an operations asset.

    Key Takeaways

  • → Untested HA is optimism, not engineering. Failover capability decays as connection strings, logins, DNS, and application code drift. Test on a schedule — quarterly at minimum — or accept that your RTO is a guess.
  • → Measure client-observed recovery, not database promotion. Detection time, promotion time, and client recovery time are three different numbers; the third is the largest and the only one users feel. Instrument it with canary writes and application dashboards.
  • → Applications must be failover-ready, not just failover-adjacent. Retry logic with backoff, MultiSubnetFailover=True on every connection string, idempotent writes, and read-only intent where possible. Audit the forgotten connection strings — ETL, BI, legacy services.
  • → Escalate game days from planned to adversarial. Planned failover, then unplanned primary kill, then AZ impairment, then full region drill. Each level tests a different failure mode; only the region drill validates disaster recovery rather than high availability.
  • → Validate after every failover and automate the tests. Replica sync state, login/job drift, integrity spot-checks, application smoke tests, monitoring re-baselining. Automate the whole cycle quarterly and alert on RTO regression.
