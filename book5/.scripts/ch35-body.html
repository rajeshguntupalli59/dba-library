Chapter 35: Query Performance Tuning on Managed Services

The cloud does not change the query optimizer — a bad plan is a bad plan on RDS, Azure SQL, or bare metal. What changes is the tooling around tuning: which DMVs you can reach, how execution plans are captured, what index operations are allowed, and how you validate improvements without the on-premises lab. This chapter is SQL Server performance tuning adapted to managed services: finding the slow queries, reading the plans, fixing indexes, analyzing waits, and proving the improvement.

35.1 Capturing and Identifying Slow Queries

The source of truth is Query Store — enabled by default on Azure SQL, available on RDS and self-managed: it captures query text, plans, and runtime statistics persistently, surviving restarts and failovers. The identification query never changes:

-- Top queries by total duration (the tuning backlog, ordered by impact)
SELECT TOP 20
    q.query_id,
    SUM(rs.count_executions) AS executions,
    SUM(rs.avg_duration * rs.count_executions) / 1000000.0 AS total_seconds,
    SUM(rs.avg_cpu_time * rs.count_executions) / 1000000.0 AS total_cpu_seconds,
    SUM(rs.avg_logical_io_reads * rs.count_executions) / 1024.0 AS total_logical_mb
FROM sys.query_store_query q
JOIN sys.query_store_plan p ON q.query_id = p.query_id
JOIN sys.query_store_runtime_stats rs ON p.plan_id = rs.plan_id
GROUP BY q.query_id
ORDER BY total_seconds DESC;

On RDS, supplement with Performance Insights (top SQL by load with wait-event breakdown — the fastest path from "it's slow" to the query); on Azure, Intelligent Insights flags regressions automatically. Tune in order of total impact (total_seconds), not average duration — the query running 100,000 times a day at 50ms matters more than the nightly report at 5 minutes.

35.2 Reading Execution Plans on Managed Services

Execution plans work identically on managed services — capture actual plans via Query Store (forced plans visible per query_id) or SET STATISTICS PROFILE / Extended Events where the platform permits. The reading discipline: find the most expensive operator by actual rows vs estimated rows (the cardinality estimation error is the root of most bad plans); check for implicit conversions (the plan warning that turns a seek into a scan — fix the data type, not the query); look for spills (sort/hash warnings — memory grant issues, section 35.4); and verify parameter sensitivity (the plan that's fast for one parameter value and catastrophic for another — Query Store's plan forcing or OPTION (RECOMPILE) / optimize-for hints, applied surgically).

35.3 Index Tuning in the Cloud: What Works and What Doesn't

Index mechanics are unchanged; the cloud constraints are operational: online index operations (ONLINE = ON) for every production build/rebuild — the managed service won't forgive a blocking offline rebuild any more than on-premises would; missing-index DMVs (sys.dm_db_missing_index_details) as the suggestion feed, filtered by impact and validated against the workload (the DMV suggests per-query indexes — the DBA designs the index set); unused-index removal (sys.dm_db_index_usage_stats — every unused index costs write IOPS and storage, and on provisioned-IOPS cloud storage that cost is metered); and intelligent maintenance (threshold-based rebuild/reorganize, not blanket nightly rebuilds — Chapter 12's rule, because the IOPS are billed).

35.4 Wait Statistics: Finding the Real Bottleneck

When the query is "slow" but the plan looks fine, the answer is in sys.dm_os_wait_stats: the waits tell you what the queries are waiting for. The cloud-relevant wait types: PAGEIOLATCH_* (storage latency — the cloud storage tier is too slow or throttled; Chapter 36); CXPACKET/CXCONSUMER (parallelism — often excessive parallelism on cloud VMs with many vCPUs; tune MAXDOP and cost threshold); LCK_* (blocking — application transaction design, not a cloud problem, but the cloud's latency makes it more visible); RESOURCE_SEMAPHORE (memory grant waits — the instance is under-memory for the workload); ASYNC_NETWORK_IO (the application isn't consuming results — a client problem masquerading as a database problem). Sample waits differentially (snapshot, wait, snapshot) — cumulative counters since restart lie about the present.

35.5 Configuration Tuning Within Managed Limits

Managed services restrict some knobs and expose others. The high-value settings available on RDS (parameter groups), Azure SQL (database scoped configurations), and self-managed: MAXDOP and cost threshold for parallelism (the two most impactful instance-level settings — start MAXDOP at the core count up to 8, raise the cost threshold from the ancient default of 5); max server memory (self-managed and RDS — leave headroom for the OS; on managed services the platform manages it, but verify); database scoped configurations (LEGACY_CARDINALITY_ESTIMATION, PARAMETER_SNIFFING, QUERY_OPTIMIZER_HOTFIXES — per-database, online, and revertible — the safe way to test optimizer behavior changes); and intelligent query processing (batch mode on rowstore, adaptive joins, memory grant feedback — enabled by compatibility level; keep databases at current compat levels to receive them).

35.6 Query Rewrites and Application-Level Optimizations

When indexes and configuration are exhausted, the query itself changes: eliminate the patterns (SELECT *, functions on indexed columns, OR-chains that defeat seeks, cursors doing set work); fix the data types (implicit conversions resolved at the schema or parameter level); batch the chatter (the application doing 1,000 round trips does not get faster with a bigger database — table-valued parameters and set-based APIs); and cache deliberately (the repeated identical query is a caching problem, not a database problem). Every rewrite gets a before/after measurement from Query Store — the tuning that isn't measured is a story, not an improvement.

35.7 Monitoring Performance Over Time

Tuning decays without monitoring: Query Store regression detection (alert on plan changes that increase duration — automatic on Azure, queryable everywhere); the weekly top-queries review (the tuning backlog from 35.1, revisited — new queries enter the top 20 as the workload evolves); wait-trend dashboards (the bottleneck migrates as you fix things — today's PAGEIOLATCH is tomorrow's CXPACKET); and post-deployment verification (every application release gets a Query Store comparison — the release that doubles a key query's runtime is caught in hours, not discovered in the monthly review). Performance is a process with a cadence, not a project with an end date.

Key Takeaways

  • → **Query Store is the source of truth on every platform.** Tune by total impact (total_seconds), not average duration. Performance Insights/Intelligent Insights accelerate the hunt.
  • → **Read plans for cardinality errors, conversions, spills, and parameter sensitivity.** The optimizer is the same in the cloud — the diagnostic discipline is what transfers.
  • → **Index operations are online-only in production.** Missing-index DMVs as suggestions, usage stats for removal, threshold-based maintenance — metered IOPS make every rebuild a cost decision.
  • → **Waits identify the true bottleneck.** Sample differentially; map PAGEIOLATCH to storage, CXPACKET to parallelism, RESOURCE_SEMAPHORE to memory, ASYNC_NETWORK_IO to the client.
  • → **Tune MAXDOP/cost threshold first, use database scoped configurations for the rest.** Keep compat levels current for intelligent query processing. Measure every change in Query Store.
