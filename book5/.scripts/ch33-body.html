Chapter 33: Database Migration to Cloud: The Practical Runbook

Migration is the project where cloud database theory meets the production estate: hundreds of databases, decades of accumulated quirks, linked servers, Agent jobs, CLR assemblies, and a business that expects zero surprises. This chapter is the practical runbook — assessment, method selection, the migration wave plan, cutover, rollback, and the post-migration optimization that finishes the job. Chapter 34 covers the zero-downtime techniques in depth; this chapter covers running the whole program.

33.1 Migration Assessment: Knowing What You're Moving

Inventory before anything moves. For each SQL Server: version and edition, database sizes and growth rates, compatibility level, and the feature inventory that determines the target — Agent jobs (Chapter 12), linked servers, replication topologies, CLR assemblies, Service Broker, FILESTREAM/FileTable, Always On AGs, SSIS/SSAS/SSRS dependencies, cross-database queries and three-part naming. Run the platform assessment tools (Azure Data Migration Assistant / Azure Migrate, AWS DMS Fleet Advisor / Schema Conversion Tool) — they flag breaking changes and unsupported features mechanically, which beats discovering them during cutover. Classify each database: rehost (lift-and-shift to EC2/VMs — minimal change), replatform (to RDS/Azure SQL/MI — some adaptation), or retain/replace (stays on-premises, or the application is being replaced anyway). The classification drives the wave plan.

33.2 Choosing the Migration Method per Database

Method Downtime Best for
Native backup/restoreHours (restore time)Small-medium DBs with maintenance windows; universal fallback
Log shipping / differential catch-upMinutesLarge DBs where the seed restores early and logs catch up
Transactional replicationSeconds–minutesNear-zero downtime; publisher stays live until cutover
Distributed AGSecondsEC2/VM targets; automatic failover semantics for cutover
DMS / cloud migration serviceMinutesManaged-service targets; homogeneous SQL Server supported

The default for most databases: backup/restore for the small ones (simple, well-understood), log-shipping-style catch-up for the large ones, replication or DMS where downtime is constrained. Always have the backup/restore path available as the fallback — the exotic method that fails at 2 AM needs a boring alternative.

33.3 The Wave Plan: Order, Grouping, and Dependencies

Migrate in waves, not all at once: wave zero (non-production, low-risk databases — proves the pipeline, the tooling, and the runbook); early waves (independent production databases with tolerant downtime windows); late waves (the interconnected systems — linked servers, replication chains, shared Agent jobs — migrated as dependency groups, in dependency order). Map the dependencies explicitly (which database's linked server points where, which Agent job touches which databases, which application connects to which) — the migration that breaks an unmapped dependency is the classic program failure. Each wave gets a go/no-go review: the previous wave's lessons incorporated, the next wave's runbook updated.

33.4 The Target Environment: Built Before the First Migration

The cloud landing zone must be production-ready before wave zero: networking (private connectivity, DNS, firewall rules — Chapter 32), identity (Chapter 31), monitoring (Chapter 30), backup (Chapter 29), and the target SQL Server instances sized from the assessment (Chapter 39's right-sizing, applied prospectively). Deploy the automation first: the Agent job equivalents (Chapter 12), the maintenance routines, the alerting — so the first migrated database lands in an operated environment, not an empty cloud account. And load-test the target: restore the largest production database and run the peak workload against it before the business depends on it.

33.5 Cutover Runbook: The Final 60 Minutes

Every cutover follows the same script (customize per database, rehearse per wave): stop application writes (or put the application in read-only/maintenance mode); let replication/logs drain to zero lag (verify — do not assume); run the final differential/log backup and restore; update statistics and check integrity on the target (DBCC CHECKDB — the restore that passes CHECKDB is the restore you trust); redirect connection strings (DNS flip, config deployment, or listener update — Chapter 16's redirection discipline); start the application and run the smoke-test suite (the business's critical transactions, not just "can we connect"); and monitor the new production intensely for the first hours (the query plan regressions from a new environment show up fast). Assign every step an owner and a timebox; the runbook with "someone" as the owner is a wish, not a plan.

33.6 Rollback Plan

Define the rollback trigger before cutover (which failures roll back vs roll forward — Chapter 23's discipline applied to migration): keep the source database intact and replication-capable until the migration is declared successful (the rollback window — typically 24–72 hours); for replication-based migrations, reverse replication can return writes to the source; for backup/restore migrations, rollback means redirecting clients back and accepting the writes made on the target (reconcile or lose them — decide in advance which). The rollback that was never tested is a hope; test it on a non-production wave.

33.7 Post-Migration Optimization

Migration is not finished at cutover. The post-migration checklist: update statistics and rebuild fragmented indexes (the restore process fragments; the new storage has different characteristics); re-baseline performance (Query Store captures the new normal — compare against pre-migration baselines and investigate regressions immediately); right-size the target (the assessed size was a guess — Chapter 39 with real cloud metrics, usually downward); enable the cloud-native features (automated backups verified, monitoring dashboards live, alerting active — the target is not "done" until it's operated); and decommission the source (on a schedule, with a final backup retained — the source server that lingers "just in case" becomes a security and licensing liability).

Key Takeaways

  • → **Assess mechanically, classify explicitly.** Feature inventory per database, platform assessment tools, rehost/replatform/retain classification driving the wave plan.
  • → **Match the method to the downtime budget.** Backup/restore as the universal fallback; log catch-up, replication, or DMS for constrained windows. Boring beats exotic at 2 AM.
  • → **Waves with dependency mapping and go/no-go reviews.** Wave zero proves the pipeline; dependency groups migrate together, in order.
  • → **Cutover is a scripted 60 minutes.** Drain to zero lag, CHECKDB the target, redirect clients, smoke-test the business transactions — every step owned and timeboxed.
  • → **Migration ends with optimization and decommissioning.** Re-baseline performance, right-size on real metrics, operate the target fully, retire the source on schedule.
