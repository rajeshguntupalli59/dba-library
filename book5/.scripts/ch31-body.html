Chapter 31: SQL Server Authentication in the Cloud: Entra ID, Secrets, and Kerberos

Authentication is where cloud SQL Server diverges most from the on-premises world you know. On-premises, it was Windows authentication against Active Directory — simple, integrated, done. In the cloud, each platform offers a different identity story, SQL logins still exist everywhere, and secrets management becomes a first-class operational concern. This chapter maps the authentication options per platform, the secrets lifecycle, and the hardening that keeps the front door locked. One honest note up front: unlike some other engines, RDS for SQL Server does not support IAM database authentication — there is no token-based login for SQL Server on RDS. Plan accordingly.

31.2 Entra ID Authentication for Azure SQL

Azure SQL's native identity is Microsoft Entra ID: users and managed identities authenticate without passwords in connection strings. The production pattern: applications use managed identities (no stored credentials at all — the platform injects the identity), humans use their Entra accounts with MFA, and SQL logins exist only where Entra cannot reach (legacy integrations). Enable Entra-only authentication on servers that have completed the migration — it disables SQL authentication entirely, eliminating the password-spray attack surface. For Managed Instance, Entra authentication works alongside the traditional Windows-auth patterns your team already knows.

31.3 Secrets Management: Rotation Without Outages

Where SQL logins remain (RDS, Cloud SQL, legacy integrations), the credentials live in the platform's secret store — AWS Secrets Manager, Azure Key Vault, GCP Secret Manager — never in code, config files, or (heaven forbid) the deployment pipeline's variables. The rotation discipline: automatic rotation on a schedule (Secrets Manager natively rotates RDS credentials, including through RDS Proxy — Chapter 10); dual-password rotation where supported (the old password stays valid during the transition so in-flight connections survive); and application integration (applications read the secret at startup and handle rotation signals — or better, use the platform's integrated auth and skip passwords entirely). Test rotation in staging first: the rotation that breaks the application's connection pool is discovered at 2 AM on rotation day unless you rehearse it.

31.4 Kerberos and Active Directory in the Cloud

Self-managed SQL Server on EC2, Azure VMs, and GCE can join Active Directory — via AWS Managed Microsoft AD, Entra Domain Services, or an extended on-premises domain over the hybrid link (Chapter 27) — giving full Windows authentication parity: Kerberos for AGs and linked servers, Windows logins, group-based access. The operational requirements: SPNs registered correctly (the AG listener and each replica need proper Service Principal Names — the classic Kerberos failure, now in the cloud); time synchronization (Kerberos tolerates 5 minutes of skew — the cloud's NTP usually handles this, but verify on domain controllers); and constrained delegation configured for double-hop scenarios (application → SQL Server → linked server). RDS supports Windows Authentication via Managed AD join — the one integrated-auth path on RDS, and worth the setup for estates with Windows-auth applications.

31.5 Contained Users and Least Privilege

Regardless of platform, the authorization model should be contained database users where the platform supports them (Azure SQL natively; partially contained on other editions): users authenticated at the database level, portable with the database across failover and migration, with no server-level login to synchronize. The least-privilege discipline: application accounts get exactly the permissions the application needs (execute on specific procedures, not db_owner); human access goes through groups, never individual grants; and the sa / admin credentials are vaulted, never used by applications, with every use alerted. Review effective permissions quarterly — privilege creep is silent and permanent unless audited.

31.6 Auditing Authentication: Who Connected, From Where

Authentication without auditing is trust without verification. The baseline: SQL Server audit capturing successful and failed logins (failed logins are the brute-force signal — alert on bursts); platform audit trails (CloudTrail for Secrets Manager access, Azure Activity Log for Key Vault, Cloud Audit Logs) proving who touched the credentials; and connection source tracking (client IP/hostname in the audit — the login from an unexpected network is the compromised-credential signal). Ship audit records to immutable storage with retention matching the compliance requirement (Chapter 26). And audit the auditors' access — the team that can read the audit logs can also, in principle, modify them; separation of duties applies to observability too.

31.7 Troubleshooting Authentication Failures

The failure taxonomy, in order of frequency: expired/rotated secrets (the application holds the old password — check rotation timing vs application restart); network path (authentication fails because the client cannot reach the domain controller / Entra endpoint / secret store — always verify connectivity before debugging credentials); Kerberos/SPN issues (falling back to NTLM or failing outright — check SPNs, delegation, and time skew); Entra token problems (expired tokens, wrong tenant, managed identity misconfiguration — the Azure-side equivalent of Kerberos issues); and permission changes (the login works but the database denies access — someone changed a role membership). The diagnostic order never changes: network, then credential validity, then identity provider, then authorization. Skipping steps is how a 10-minute fix becomes a 3-hour bridge call.

31.8 Hardening Beyond Authentication

Authentication is one layer. The hardening checklist: TLS everywhere (Chapter 32 — encrypted connections enforced, not optional); no public endpoints on production databases (private networking only); MFA for human access (via Entra / the identity provider — the DBA's account is the highest-value target); break-glass accounts (vaulted, monitored, tested — for the day the identity provider is the problem); and regular access reviews (quarterly: who has access, at what level, on every platform — Chapter 24's per-cloud review rule). Security is a process with a checklist, not a feature with a checkbox.

Key Takeaways

  • → **Know each platform's identity story — including the gaps.** Entra ID natively on Azure SQL; Managed AD join for RDS Windows auth; domain-joined VMs for full Kerberos parity. RDS SQL Server has no IAM database authentication — plan around it.
  • → **Passwords live in secret stores with automatic rotation.** Never in code or config. Rehearse rotation in staging; prefer managed identities and Entra-only mode where available.
  • → **Contained users and least privilege, everywhere.** Portable authentication, application accounts with minimal grants, vaulted admin credentials, quarterly permission reviews.
  • → **Audit logins and credential access.** Failed-login alerting, client source tracking, immutable audit storage. Audit the auditors too.
  • → **Troubleshoot in order: network, credential, identity provider, authorization.** And harden beyond auth: TLS, no public endpoints, MFA, break-glass accounts, quarterly reviews.
