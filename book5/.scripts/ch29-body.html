Chapter 29: Backup and Restore in the Cloud: Automated, Native, and Tested

Backups are the one operational discipline where the cloud changes the mechanics but not the accountability. The platform can automate snapshots, copy them across regions, and enforce retention — but when the restore fails at 3 AM, it is still the DBA explaining. This chapter covers the full SQL Server backup picture in the cloud: platform-automated backups, native backups you control, point-in-time recovery on each platform, cross-region strategies, and the restore testing that makes the whole thing real.

29.1 How Platform-Automated Backups Work

Each managed platform automates the backup chain differently: RDS takes automated snapshots with transaction log backups enabling point-in-time recovery within the retention window (up to 35 days); Azure SQL provides fully automated full, differential, and log backups with PITR (7–35 days configurable) plus long-term retention policies stretching to years; Cloud SQL offers automated daily backups with configurable retention and PITR via log archiving. The common trait: the platform owns the schedule and the storage, and you own the verification. Know exactly what each platform's "automated backup" includes — RDS automated backups do not include the transaction logs you need for sub-hour RPO unless log backup behavior is understood; Azure's PITR granularity depends on log backup frequency, which the platform manages but you should confirm.

29.2 Native Backups: The Backups You Control

Platform backups are convenient; native SQL Server backups are portable. On EC2, Azure VMs, and GCE you run the same BACKUP DATABASE ... TO URL / TO DISK commands as on-premises, writing to S3, Blob storage, or Cloud Storage. On RDS, the rds_backup_database stored procedure takes native backups to S3 — the escape hatch that makes RDS restores portable. The native-backup discipline:

  • → Full + differential + log cadence. Weekly full, daily differential, log backups every 15 minutes is the classic starting point — tune to the RPO. The log backup frequency is the RPO for native chains.
  • → Compression and checksums. WITH COMPRESSION, CHECKSUM on every backup — compression reduces storage and transfer costs; checksums catch corruption at backup time rather than restore time.
  • → Verify with RESTORE VERIFYONLY — and real restores. VERIFYONLY checks readability, not recoverability. Only a real restore proves the chain.

    • 29.3 Backup Windows, Retention, and the RPO Contract

    Set the backup window outside peak hours — but understand what the window actually constrains (on RDS it constrains snapshot timing; log backups continue regardless). Retention is the RPO contract made concrete: 35 days of RDS automated backups means you can reach any point in the last 35 days — and not one day more. For compliance horizons beyond platform maximums, native backups to object storage with lifecycle policies carry the depth (Chapter 16's long-retention discussion). Document the retention per database tier: production 35 days PITR + 1 year native; non-production 7 days. When legal asks "can we restore March?", the answer is in this document, not in someone's memory.

    29.4 Point-in-Time Recovery: Execution Under Pressure

    PITR is the restore you will run during an incident, so rehearse the mechanics: on RDS, restore to a new instance to a specified time (restoring "in place" is not how RDS works — plan for the new-instance workflow including endpoint updates); on Azure SQL, point-in-time restore creates a new database (same server or another); on EC2/VMs, the classic RESTORE ... WITH STOPAT log sequence. The incident-time details that matter: know the exact target time before starting (when did the bad data commit? — find it in the audit/fn_dblog forensics first, because every wrong guess costs another full restore cycle); restore aside, not over (keep the damaged database available for forensics until the recovery is verified); and measure restore throughput now (a 4 TB restore at 200 MB/s is 5.5 hours — that number belongs in the RTO document, not discovered during the outage).

    29.5 Cross-Region and Cross-Account Backup Copies

    Backups in one region protect against database failure; backups in two regions protect against regional failure; backups in a second account protect against compromised credentials (Chapter 16). The implementations: RDS cross-region snapshot copy (automated on a schedule); S3 cross-region replication for native backups; Azure geo-redundant storage for automated backups plus LTR in the paired region; and separate-account backup vaults with write-only access from production (production can write backups, cannot delete them). Automate the copy verification — alert when a scheduled copy does not complete, because a DR copy that silently stopped is the classic audit finding.

    29.6 Restore Testing: The Framework That Makes Backups Real

    The testing cadence: automated weekly restores of a sample of databases (restore to an isolated instance, run DBCC CHECKDB, run a smoke-test query suite, report success/failure); quarterly PITR drills (pick a random point in time, restore to it, verify the data matches expectations — this exercises the log chain, not just the full backup); and annual full DR restores (the Chapter 16 regional drill). Automate the weekly restores completely — a manual restore test gets skipped the week it matters. Track restore success rate as a KPI; anything below 100% is an incident, because a backup that does not restore is not a backup.

    29.7 Backup Encryption, Access Control, and Compliance

    Encrypt everything: platform backups inherit the instance's encryption (RDS encryption at rest via KMS, Azure TDE + storage encryption); native backups get WITH ENCRYPTION using a certificate, with the certificate backed up separately (an encrypted backup without its certificate is a random number collection). Access control: backup storage buckets/accounts allow writes from the database's role and reads only from the restore automation's role — no human needs routine read access to backup storage. For compliance: immutability (S3 Object Lock, immutable blob storage) for the retention period, and the access logs proving who touched the backups. The ransomware scenario from Chapter 16 is defeated here or nowhere.

    29.8 Backup Cost Management

    Backups cost real money at scale: snapshot storage per GB-month, cross-region transfer, long-term retention accumulation. The controls: lifecycle policies (hot storage for recent backups, cooler tiers for aging ones, expiration at the retention boundary — automate it, because manual cleanup never happens); differential discipline (differentials reduce full-backup frequency but grow with change rate — monitor differential size and take fulls before they approach full size); compression everywhere (smaller backups are cheaper to store, faster to restore, and cheaper to replicate); and per-database retention tiers (production keeps 35 days; dev keeps 7 — the backup bill should reflect the data's value). Review backup spend quarterly; it grows silently and is easy to trim once visible.

    Key Takeaways

  • → **The platform automates; you verify.** Know exactly what each platform's automated backup includes, and own the verification regardless of who owns the schedule.
  • → **Native backups are the portable layer.** Full + differential + 15-minute logs, compression and checksums always, stored in object storage you control. Portability is 80% of DR.
  • → **Restore aside, never over — and know the target time first.** Forensics before restore; measured restore throughput in the RTO document.
  • → **Two regions, two accounts, immutable.** Cross-region copies, separate-account vaults with write-only production access, immutability for the retention period.
  • → **Automated weekly restores are non-negotiable.** CHECKDB + smoke tests on every restore, PITR drills quarterly, restore success rate as a KPI. A backup that doesn't restore isn't a backup.
