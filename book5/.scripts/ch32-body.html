Chapter 32: VPC, Private Endpoints, and Network Security

The network is the security perimeter for cloud databases — there is no data-center door to lock, so the virtual network, the firewall rules, and the encryption in transit are the locks. This chapter builds the network security architecture for SQL Server on each cloud: isolation, private connectivity, least-privilege firewalling, TLS enforcement, and the misconfigurations to hunt down.

32.1 Virtual Networks: The Foundation of Isolation

Every production SQL Server lives in a private subnet — no public IP, no internet gateway route — on AWS (VPC), Azure (VNet), and GCP (VPC). The standard topology: public subnets for load balancers and bastion only; private application subnets; isolated database subnets with no route to the internet at all (not even via NAT — patches come through VPC endpoints, backups go through gateway endpoints). Separate subnets per tier (production vs non-production in different subnets or different VPCs/VNets entirely — the blast-radius boundary). And plan the address space once, globally: non-overlapping CIDRs across VPCs, regions, clouds, and the on-premises network (Chapters 24 and 27's rule — renumbering a production VPC is the project nobody wants).

32.2 Private Endpoints: Eliminating Public Exposure

Managed databases get private connectivity through each cloud's private-endpoint mechanism: AWS PrivateLink (interface VPC endpoints for RDS — traffic never leaves the AWS network), Azure Private Link / Private Endpoints (Azure SQL and Managed Instance accessible only via private IPs in your VNet — combined with denying public network access at the server level), and GCP Private Service Connect / private IP for Cloud SQL. The configuration that matters: disable public access explicitly (on Azure SQL, set public network access to Deny — the default-allow posture is the misconfiguration; on RDS, the publicly-accessible flag must be false and verified by audit, not assumed). Private DNS zones must resolve the database hostnames to the private IPs — the application connects to the same hostname everywhere, and DNS decides the path.

32.3 Security Groups, Firewall Rules, and Least Privilege

The firewall discipline, per cloud (security groups / NSGs / firewall rules — same concept): default deny, explicit allow; database ports (1433) reachable only from the application subnets' security groups — never from 0.0.0.0/0, never from "the whole VPC"; reference security groups, not IP addresses (allow from the app tier's security group so autoscaling doesn't break the rules); separate rules per environment; and egress control on the database subnets (the database should not initiate outbound internet connections — if it does, something is wrong or something is exfiltrating). For Azure SQL's server-level firewall: prefer VNet rules and private endpoints over IP rules; IP rules are the exception path for break-glass admin access, time-boxed and audited.

32.4 Cross-VPC Connectivity: Peering, Transit, and Shared Services

When the application and database live in different VPCs/VNets (or different accounts/subscriptions — the landing-zone pattern), connect them with VPC peering (simple, non-transitive — fine for hub-and-spoke pairs), Transit Gateway / Virtual WAN (the enterprise pattern — transitive routing with centralized firewall inspection), or PrivateLink/Private Service Connect (expose the database as a service to consumer VPCs without peering at all — the cleanest isolation). The rules: peering is non-transitive (A↔B and B↔C does not give A↔C — design accordingly); route tables must be updated on both sides (the forgotten return route is the classic peering failure); and DNS must resolve across the peering (private hosted zones associated with all participating VPCs).

32.5 Defense in Depth: Combining Network and Database Security

Network controls and database authentication are independent layers — a failure in one must not mean total compromise: the network restricts who can reach the database (private subnets, firewall rules); authentication restricts who can log in (Chapter 31); authorization restricts what they can do (least privilege); and auditing records what happened (Chapters 26 and 31). Add threat detection where the platform offers it (Azure Defender for SQL's vulnerability assessment and threat detection, GuardDuty for RDS-adjacent anomaly detection) — anomalous login patterns and SQL injection signatures caught by the platform, not by hope. No single layer is trusted alone; the combination is the security posture.

32.6 TLS Enforcement and Certificate Management

Encrypt in transit, enforced: require encrypted connections on every SQL Server (RDS: the rds.force_ssl parameter; Azure SQL: encryption is enforced by default with the option to verify; self-managed: Force Encryption in SQL Server Configuration Manager with a proper certificate). The details that matter: certificate validation — the client must validate the server certificate (TrustServerCertificate=false in production connection strings — the application that skips validation is vulnerable to MITM on its own network); TLS version floor (disable TLS 1.0/1.1 — compliance requires it, and the handshake failures from legacy clients are found in testing, not production); and certificate rotation — platform-managed certificates rotate automatically (verify the rotation doesn't break clients that pinned the old cert); self-managed certificates need a rotation runbook with client trust-store updates.

32.7 Auditing Network Access and Detecting Anomalies

The network audit baseline: flow logs (VPC Flow Logs, NSG flow logs, GCP firewall logging — who connected to the database subnets, when, how much data moved); firewall change auditing (every security group / NSG / firewall rule change logged and alerted — an opened database port is an incident until proven otherwise); and anomaly detection (connections from new networks, unusual data volumes, off-hours access patterns — the compromised-credential signal from Chapter 31, seen at the network layer). Retain flow logs long enough to investigate (30–90 days minimum); the breach discovered in week six needs week-one logs.

32.8 Network Security as Code

Every firewall rule, private endpoint, and route table in version-controlled infrastructure code (Chapter 28's IaC rule) — with policy enforcement (AWS Config rules, Azure Policy, GCP org policies) that deny the dangerous configurations: no public database endpoints, no 0.0.0.0/0 ingress to database ports, mandatory TLS, required tags. Manual console changes to network security are drift (Chapter 23's discipline) — detect and revert automatically. The network security posture is a codebase with tests, not a collection of console clicks someone remembers making.

32.9 Common Misconfigurations and How to Find Them

The hunt list, run quarterly: publicly accessible database flags set true; 0.0.0.0/0 in database security groups; Azure SQL servers with public network access allowed; forgotten IP firewall rules from break-glass sessions; cross-account peering to unknown accounts; expired or self-signed certificates in production; DNS resolving database hostnames to public IPs; and flow logs disabled on database subnets. Automate the hunt — a scheduled audit script across all three clouds (or the CSPM tool you already pay for) — because manual quarterly reviews get skipped exactly when the misconfiguration arrives.

Key Takeaways

  • → **Private subnets, private endpoints, explicit public-access denial.** No production database with a public IP. Private DNS resolving to private IPs.
  • → **Firewall least privilege: 1433 from app-tier security groups only.** Reference groups, not IPs. Egress-controlled database subnets. IP rules as time-boxed exceptions.
  • → **TLS enforced with certificate validation.** Force encryption, validate server certs (TrustServerCertificate=false), TLS 1.2+ floor, rotation runbooks.
  • → **Defense in depth, audited.** Network + auth + authorization + auditing + threat detection. Flow logs, firewall-change alerts, anomaly detection.
  • → **Network security as code with policy enforcement.** Deny the dangerous configurations by policy; hunt the misconfiguration list quarterly, automated.
