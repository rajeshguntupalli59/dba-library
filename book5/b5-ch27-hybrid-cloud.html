Chapter 27: Hybrid Cloud: On-Premises and Cloud Together

Most SQL Server estates will be hybrid for years: production partially in the cloud, partially on-premises, with data flowing between them. Hybrid is not a waystation you pass through on the way to "all cloud" — for regulated industries, latency-sensitive workloads, and sunk data-center investments, it is the steady state. This chapter covers the hybrid architecture for SQL Server: the network, the data synchronization, hybrid DR, identity, and the operational discipline of running one estate across two worlds.

27.1 Network Architecture: Connecting Your Data Center to the Cloud

The foundation is private, reliable connectivity: dedicated circuits (Direct Connect, ExpressRoute, Cloud Interconnect) for production database traffic — consistent latency, no internet traversal, SLA-backed; VPN as backup path or for lower-throughput needs. Design for redundancy from day one: two circuits (or circuit plus VPN failover), because the hybrid architecture's single point of failure is always the link. Size for the replication and backup traffic, not just the application traffic — the initial seeding of a multi-terabyte database across the link is what saturates it. And resolve the address space question early: the data center and cloud networks must not overlap, and DNS must resolve both directions (conditional forwarders or private DNS peering) so connection strings work identically everywhere.

27.2 Data Synchronization Patterns Across Boundaries

The synchronization mechanism follows the use case:

  • → Migration seeding: native backup to cloud object storage, restored on the cloud target — the universal method (Chapters 33–34). For the initial multi-terabyte seed, physical media shipment (AWS Snowball, Azure Data Box) beats the network when the math favors it.
  • → Ongoing replication: transactional replication (on-premises publisher, cloud subscriber — or the reverse) for table-level flows; distributed AGs with one replica on-premises and one in the cloud for whole-database DR with seconds of lag. Both need the distributor/AG topology designed around the link latency (Chapter 25's rules apply within hybrid too).
  • → Azure Arc (Chapter 18): for Azure-hybrid estates, Arc extends management, policy, and (with the right configuration) data services to on-premises SQL Server — one control plane for the hybrid estate.
  • → ETL/ELT pipelines: for analytics offload (on-premises SQL Server to cloud warehouse), CDC-based pipelines on a schedule — with the freshness SLA defined per consumer (Chapter 22).

    • 27.3 Hybrid Failover and Disaster Recovery

    Hybrid DR runs in both directions, and you must design both: on-premises to cloud (data center failure — fail over to the cloud replica; the cloud's elasticity is an advantage here, since the DR target can scale up on demand rather than sitting idle); and cloud to on-premises (cloud region failure or cloud exit — the reverse path, which is always harder because on-premises capacity is fixed). The distributed AG spanning data center and cloud is the cleanest mechanism for the first direction; backup-based restore covers both but with hours of RTO. The critical hybrid-DR question is capacity: the DR side must actually absorb the production workload — an on-premises DR target sized three years ago for a smaller database, or a cloud DR target with no reserved capacity, fails the drill exactly when it matters.

    27.4 Hybrid Identity and Access Management

    One identity system across both worlds — for SQL Server estates this almost always means Active Directory / Entra ID spanning on-premises and cloud: domain-joined cloud VMs (via AD replication to the cloud or Entra Domain Services), Entra authentication for Azure SQL, and Kerberos working across the link for AGs and linked servers (SPNs registered, constrained delegation configured — the classic on-premises Kerberos discipline, now extended across the boundary). The failure mode is always the same: authentication that works inside each world and breaks across the boundary, discovered during the failover drill. Test cross-boundary authentication explicitly and continuously — a scheduled probe that authenticates to every SQL Server from every network segment catches the drift before the incident does.

    27.5 Cross-Boundary Query Patterns and Their Performance Implications

    Queries that span the boundary — linked servers from on-premises to cloud, elastic queries, ETL pulls — pay the latency tax on every round trip. The rules: never run chatty cross-boundary queries (a linked-server query that pulls a million rows row-by-row across the link is the classic hybrid performance disaster — rewrite as a single bulk operation or move the processing to the data); keep joins local (join across the boundary only after filtering each side to the minimum row set); and cache reference data (replicate slow-changing dimensions across the boundary on a schedule rather than querying them live). Monitor cross-boundary query performance as its own category — when the link degrades, these queries are the first symptom and the DBA needs to recognize the pattern instantly.

    27.6 Monitoring a Hybrid Database Environment

    The hybrid monitoring stack has three layers: unified metrics (the same SQL Server DMV-based metric set from on-premises agents and cloud monitoring, in one platform — Chapter 24's one-pane-of-glass rule); link health (circuit/VPN throughput, latency, and loss as first-class metrics — the link is infrastructure your databases depend on, so it gets SLAs and alerts like any other); and synchronization health (replication lag, AG sync state, and backup-copy completion across the boundary). The on-call rotation must cover both worlds with runbooks that assume either side can be the problem — "the cloud is down" and "the data center is down" are both in the playbook.

    27.7 Managing Schema Changes Across Hybrid Environments

    Chapter 23's pipeline extends across the boundary: one migration sequence deployed to on-premises and cloud in dependency order, with the replication topology respected (publishers before subscribers). The hybrid-specific risks: version skew (on-premises SQL Server on an older version than the cloud target — every migration must be compatible with the lowest version in the estate, enforced by the pipeline's compatibility check); and deployment windows (on-premises maintenance windows and cloud deployment automation must be coordinated — the migration that deploys to the cloud at 2 AM but waits for the on-premises window creates a half-migrated estate). Drift detection runs on both sides; the estate is one logical database fleet regardless of where the servers physically sit.

    27.8 Cost Engineering in Hybrid Architectures

    Hybrid cost engineering is placement optimization: run each workload where it is cheapest over its lifetime, counting the fully-loaded costs. On-premises looks cheap per-server until you count power, cooling, hardware refresh, and the DBA hours; cloud looks expensive per-hour until you count elasticity and managed services. The honest model: steady-state predictable workloads often favor on-premises (sunk hardware, AHB-licensed VMs); variable, bursty, or new workloads favor cloud; and the link and egress costs are the hybrid-specific lines that decide close calls (Chapter 25's egress warning applies within hybrid too). Revisit placement annually — hardware refresh cycles and cloud pricing changes move the answer regularly, and "we've always run it on-premises" is not a cost model.

    Key Takeaways

  • → Hybrid is a steady state, not a waystation. Design the network (redundant private links, non-overlapping address space, bidirectional DNS) as permanent infrastructure.
  • → Match the sync mechanism to the use case. Backup-seed for migrations, transactional replication or distributed AGs for ongoing sync, Arc for Azure-hybrid management, CDC pipelines for analytics.
  • → Design DR in both directions and verify capacity. The DR side must absorb production — undersized DR targets fail exactly when needed.
  • → One identity, one pipeline, one dashboard. Federated identity across the boundary, one migration sequence everywhere, unified monitoring with link health as a first-class metric.
  • → Keep cross-boundary queries bulk and local. No chatty linked-server queries across the link; cache reference data; monitor cross-boundary query performance as its own category.
