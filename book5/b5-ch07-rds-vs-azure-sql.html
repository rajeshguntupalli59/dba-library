Chapter 7: RDS for SQL Server vs Azure SQL: When to Choose Which

If you run SQL Server, you have a choice few other database platforms offer: two major clouds provide a first-class managed SQL Server, and both want your workload. Amazon RDS for SQL Server and Azure SQL (Database and Managed Instance) are mature, production-proven platforms — but they are built on different philosophies, metered by different licensing models, and missing different features. Picking wrong does not just cost money; it can force an application rewrite or a painful re-migration eighteen months later when you discover the feature your workload depends on does not exist on the platform you chose.

This chapter is the decision guide. It compares the three real options — RDS for SQL Server, Azure SQL Database, and Azure SQL Managed Instance — across architecture, licensing and cost, feature compatibility, high availability, performance and scaling, security, operations, and migration paths, and ends with a framework you can apply to your own estate.

7.1 Why This Comparison Is the One That Matters

Most SQL Server estates arriving in the cloud fall into one of three situations. First, the AWS-centric organization: the company standardized on AWS years ago, and the SQL Server workload has to live there. RDS for SQL Server is the natural answer, but "natural" is not the same as "optimal" — the licensing math and the feature gaps deserve a real evaluation before you commit. Second, the Microsoft-centric organization: Active Directory, Microsoft 365, existing Enterprise Agreements with Software Assurance. Azure SQL is the natural answer here, and Azure Hybrid Benefit can make it dramatically cheaper than it first appears. Third, the genuinely undecided: a new project, an acquisition, or a renewal moment where either cloud is on the table.

The comparison is asymmetric in an important way. On AWS there is exactly one managed SQL Server: RDS. On Azure there are two, and they are very different products: Azure SQL Database (a PaaS database-as-a-service) and Azure SQL Managed Instance (a PaaS instance-as-a-service with near-complete engine compatibility). Treating "Azure SQL" as one thing is the most common mistake in this evaluation. Throughout this chapter, "Azure SQL Database" and "Managed Instance" (MI) are discussed separately wherever their behavior differs.

A note on Google Cloud: Cloud SQL for SQL Server exists and is covered in Chapter 19. It is a solid option, but in practice the RDS-versus-Azure decision covers the overwhelming majority of SQL Server cloud evaluations, because licensing leverage (your existing Microsoft agreements) and organizational gravity (where the rest of your infrastructure lives) dominate the decision.

7.2 The Three Contenders

Amazon RDS for SQL Server. A managed DB instance running SQL Server 2016 through 2022 in Express, Web, Standard, and Enterprise editions. You choose License Included (the license cost is folded into the hourly rate) or Bring Your Own License via License Mobility (requires Software Assurance). Multi-AZ deployments use Always On availability groups for automatic failover. Storage is EBS-backed (gp3, io1, io2) up to 16 TB. There are no read replicas for SQL Server on RDS, and several engine-adjacent components — SSIS, SSAS, SSRS, and SQL Server Agent — are either unavailable or restricted compared to a full installation. What you get is the relational engine, managed: automated backups, patching windows, CloudWatch monitoring, and Performance Insights.

Azure SQL Database. A pure PaaS offering: you get databases, not a server. There is no OS, no instance-level surface, no SQL Server Agent. You buy single databases or elastic pools (a pool of compute shared across many databases with unpredictable peaks). Purchasing models are vCore-based (the modern model, with provisioned or serverless compute) or the legacy DTU model. The Hyperscale tier scales to 100 TB with rapid scaling and named replicas for read offload. High availability is built in — every database runs with multiple replicas and zone redundancy is a checkbox. This is the most "cloud-native" of the three options and also the furthest from an on-premises SQL Server.

Azure SQL Managed Instance. A managed instance of the SQL Server engine with near-100% compatibility with on-premises SQL Server: SQL Server Agent, linked servers, CLR, Service Broker, Database Mail, cross-database queries, and four-part naming all work. It lives inside your virtual network, which makes hybrid scenarios (Azure ExpressRoute to on-premises, Active Directory integration) natural. It is the lift-and-shift target: the platform where an existing application migrates with the fewest changes. The trade-off is that it is heavier than SQL Database — provisioning takes longer, scaling is an instance-level operation, and you manage (or at least think about) more surface area.

7.3 Architecture Under the Hood

RDS for SQL Server is an instance on managed infrastructure. Underneath, your database runs on an EC2 host that AWS manages; you get a DB instance endpoint, EBS storage, and a managed layer that handles failover, patching, and backups. Multi-AZ adds a synchronous Always On secondary in another Availability Zone. The mental model is familiar to any DBA: it is a SQL Server instance, with the OS and the failover cluster taken away from you.

Azure SQL Database has no instance at all in your mental model. Your database's compute and storage are separated: compute nodes run the query engine, and data lives in Azure Storage with multiple replicas. Failover is a control-plane operation that reattaches storage to a new compute node — typically completing in seconds, with no availability group for you to monitor. The Hyperscale tier takes this further with a page-server architecture that allows near-instant scaling and up to 100 TB per database. You trade control for resilience: there is no AG to tune, no secondary to lag, and no failover cluster to patch.

Managed Instance sits between the two. It is a dedicated set of VMs running the full SQL Server engine inside your VNet, with storage on Azure Premium disks (or faster tiers). High availability uses Always On availability groups internally — the same technology as RDS Multi-AZ — but the replica topology is managed for you, and Business Critical tier instances include a free readable secondary replica you can actually use for reporting. General Purpose tier uses remote storage with local SSD cache; Business Critical uses local SSD with multiple replicas.

The practical consequence: on RDS you still think in instances, endpoints, and failover; on Azure SQL Database you think in databases, elastic pools, and service tiers; on Managed Instance you think in instances again, but with VNet integration and near-complete engine fidelity.

7.4 Licensing and Cost: Where the Decision Is Often Made

For SQL Server, licensing is not a footnote — it is frequently the largest line item and the decisive factor. The three options meter licenses completely differently, and your existing Microsoft agreements change the math more than any technical feature.

RDS licensing: License Included vs BYOL. With License Included, you pay an hourly rate that bundles the SQL Server license; Enterprise Edition LI on a large instance is one of the most expensive ways to run any database on AWS. With BYOL via License Mobility (which requires active Software Assurance), you pay only for the EC2 infrastructure and apply your existing licenses — often cutting the bill dramatically. The catch: License Mobility has rules. You must have Software Assurance, you must report usage, and license mobility through SA does not cover every scenario (short-term or burst BYOL without SA is not permitted). Web and Express editions have their own constraints: Express is free but capped (10 GB per database, limited memory and CPU), Web is LI-only and cannot use BYOL.

Azure SQL and Azure Hybrid Benefit. This is Azure's killer feature in the SQL Server decision. If you have SQL Server licenses with active Software Assurance, Azure Hybrid Benefit lets you apply them to Azure SQL Database and Managed Instance and pay only the compute rate — no SQL Server license cost in the meter. For an organization already paying for SQL Server Enterprise under an Enterprise Agreement, AHB can reduce the Azure SQL bill by 40% or more compared to license-included pricing. There is also a dev/test variant: Azure Dev/Test subscriptions offer steep discounts for non-production workloads. If your organization holds Microsoft licenses with SA and you are comparing RDS License Included against Azure SQL without AHB in the model, you are not comparing real prices.

Purchasing models compared. RDS charges per instance-hour by instance class, plus storage, IOPS, and backup storage — the model Chapter 6 dissected. Azure SQL Database vCore model charges per vCore-hour (provisioned) or per vCore-second with auto-pause (serverless, which can pause compute entirely during idle periods — ideal for dev databases and intermittent workloads). Elastic pools let dozens of small databases share a pool of eDTUs or vCores, which is dramatically cheaper than provisioning each database separately when their peaks do not coincide. Managed Instance charges per vCore-hour at the instance level, with General Purpose and Business Critical tiers at very different price points.

A cost comparison is only honest if it includes the same things on both sides: compute, storage, IOPS/throughput, backup retention beyond the included window, data transfer, and the license. Model a representative month — including a failover test, a PITR drill, and your actual backup retention — before committing. The cheapest option on a pricing calculator is often not the cheapest option in production.

# Azure: create a General Purpose SQL Database with serverless compute
# (auto-pauses during idle — good for dev/test and intermittent workloads)
az sql db create \
  --resource-group rg-prod \
  --server sqlsrv-prod \
  --name appdb \
  --edition GeneralPurpose \
  --family Gen5 \
  --capacity 4 \
  --compute-model Serverless \
  --auto-pause-delay 60 \
  --min-capacity 0.5

# Azure: create a Managed Instance (VNet-integrated, near-full engine compat)
az sql mi create \
  --resource-group rg-prod \
  --name mi-prod \
  --vnet-name vnet-prod \
  --subnet snet-sqlmi \
  --capacity 8 \
  --edition GeneralPurpose \
  --family Gen5 \
  --storage 256 \
  --license-type BasePrice   # BasePrice = Azure Hybrid Benefit applied

7.5 Feature Compatibility: What Breaks Where

This is the section to read with your application inventory in hand. Run the Data Migration Assistant (DMA) or Azure Data Studio's assessment against your databases before you decide — but the high-level map below tells you where the bodies are buried.

RDS for SQL Server gaps. The engine is complete, but the surrounding components are not: no SSIS, SSAS, or SSRS on the RDS instance (run them on EC2 and connect to RDS, or use AWS-native alternatives). SQL Server Agent exists on RDS but with restrictions — notably, replication-related jobs and some job types are limited, and you cannot RDP to the host to manage the Agent directly. CLR is supported in SAFE mode only. Linked servers are supported but restricted to specific providers and targets. Filestream/FileTable, PolyBase scale-out, and machine learning services have limited or no support. Native backup to S3 works well, which partially compensates — you can take native BACKUP DATABASE ... TO URL-style backups to S3 for portability.

Azure SQL Database gaps. This is the longest list, because SQL Database is the least "SQL Server"-like. No SQL Server Agent (use elastic jobs, which are similar but not identical, or Azure Automation). No linked servers (use elastic queries for cross-database reads). No CLR. No Service Broker. No cross-database transactions in the general case. No three- or four-part naming across databases. msdb does not exist as you know it. SQL Profiler-style server traces are replaced by Extended Events scoped to the database. If your application was written against a full SQL Server instance with Agent jobs, linked servers, and cross-database joins, migrating it to SQL Database is a rewrite project, not a migration project.

Managed Instance: the compatibility play. MI supports SQL Server Agent, linked servers, CLR, Service Broker, Database Mail, distributed transactions (via MS DTC in recent updates), and cross-database queries with three-part naming. The remaining gaps are narrow: no SSIS/SSAS/SSRS on the instance itself (use Azure Data Factory / SSIS in ADF), no Filestream in early versions (supported in newer updates), and some server-level settings you cannot change. For lift-and-shift migrations, MI is almost always the right Azure target — and the DMA assessment will confirm it quantitatively.

  • → Inventory before you choose. Query msdb.dbo.sysjobs for Agent jobs, sys.servers for linked servers, sys.assemblies for CLR, and check for cross-database references and Service Broker usage. Every row in those results is a migration work item on SQL Database and a non-issue on MI or RDS.
  • → SSIS/SSAS/SSRS need a home everywhere. None of the three options hosts these components on the database service itself. On AWS, run them on EC2; on Azure, use Azure Data Factory (with the SSIS integration runtime) or VMs. Factor that into the architecture, not just the database decision.

    • 7.6 High Availability and Disaster Recovery Compared

    RDS Multi-AZ gives you a synchronous Always On secondary in a second Availability Zone, automatic failover in 60–120 seconds, and no readable secondary. Cross-region DR is snapshot copy and restore — an RPO measured in snapshot frequency and an RTO measured in restore time. It is simple, well-understood, and exactly what Chapter 6 described.

    Azure SQL Database builds HA in by default: every database has multiple replicas, and zone redundancy (replicas across Availability Zones) is a configuration choice, not an architecture project. Failover is typically measured in seconds. For DR, active geo-replication lets you create up to four readable secondary databases in other regions, and auto-failover groups provide a single listener endpoint with automatic failover across regions, including a grace period you configure to avoid flapping. For a team that needs cross-region DR with readable secondaries and automatic failover, this is the most complete story of the three — and it is included in the service rather than assembled from parts.

    Managed Instance uses Always On availability groups internally. General Purpose tier keeps a single replica with remote storage (failover reattaches storage, similar in spirit to SQL Database); Business Critical tier runs multiple replicas including one free readable secondary you can point reporting at. Failover groups for MI provide cross-region DR with a listener endpoint, mirroring the SQL Database story at instance scope. Failover times are typically under a minute for planned failovers and a few minutes for unplanned.

    The honest summary: if cross-region DR with readable secondaries and automatic failover groups matters to you, Azure's story is more complete out of the box. If single-region HA with a well-understood AG failover is enough, RDS Multi-AZ is simpler to reason about and monitor.

    7.7 Performance, Scaling, and Limits

    Scaling up. On RDS you scale by changing instance class (minutes of downtime for Single-AZ, near-zero for Multi-AZ with failover) and by provisioning IOPS on gp3/io2. On Azure SQL Database you change service tier or vCores online — Hyperscale can scale compute in seconds without moving data, because compute and storage are separated. Managed Instance scales vCores and storage with brief downtime windows. For workloads with sharp, unpredictable peaks, Hyperscale's rapid scaling and serverless auto-pause are unmatched by either RDS or MI.

    Read scaling. RDS for SQL Server has no read replicas — Chapter 6 covered the workarounds. Azure SQL Database Hyperscale offers named replicas: up to 30 readable secondaries you can scale independently for read offload, each with its own compute. MI Business Critical includes one readable secondary. If your workload is read-heavy and you want first-class read scale-out without managing replicas yourself, Hyperscale named replicas are the strongest option in this comparison.

    Limits that surprise people. RDS for SQL Server caps database storage at 16 TB per instance and has no serverless option — you pay for the instance whether it is busy or idle. Azure SQL Database single databases top out at 100 TB on Hyperscale (far beyond RDS), but the General Purpose and Business Critical tiers have much lower per-database limits, and tempdb sizing and log throughput caps per tier cause the classic "it worked on-premises" performance incidents. Managed Instance caps at 16 TB (General Purpose) with instance-level resource governance. Log rate limits on Azure tiers are the most common surprise for write-heavy migrations: measure your log generation rate on-premises (sys.dm_io_virtual_file_stats on the log file, or PerfMon log bytes flushed/sec) and compare it against the tier's documented throughput before you migrate.

    7.8 Security and Compliance

    Both clouds cover the fundamentals: encryption at rest (KMS on AWS, Azure Key Vault / Microsoft-managed keys on Azure), encryption in transit (TLS), private network isolation (VPC security groups and PrivateLink on AWS; VNet service endpoints and Private Endpoint on Azure), and auditing. The differences are in identity integration and the surrounding security services.

  • → Windows Authentication. RDS for SQL Server supports Windows Authentication via AWS Managed Microsoft AD — your domain users and groups can authenticate to RDS. Azure SQL Database and Managed Instance authenticate via Microsoft Entra ID (formerly Azure AD), including managed identities for Azure services, which eliminates connection-string passwords for app-to-database calls. If your application relies on Windows integrated authentication with an on-premises AD, both paths work but the trust topology differs: AWS needs AD connectivity to its managed AD; Azure needs Entra Connect / federation.
  • → TDE and key control. Transparent Data Encryption is available on all three. RDS uses KMS (AWS-managed or customer-managed keys); Azure SQL enables TDE by default on new databases with Microsoft-managed keys and supports customer-managed keys in Key Vault. Both satisfy the "customer controls the key" compliance requirement.
  • → Threat detection. RDS leans on GuardDuty and CloudTrail for the control plane plus Performance Insights for workload anomalies. Azure has Microsoft Defender for SQL, which bundles vulnerability assessment, advanced threat protection, and data discovery/classification into the database service itself. If your compliance regime wants vulnerability assessment reports out of the box, Defender for SQL is the more integrated story.
  • → Auditing. RDS for SQL Server publishes audit logs to CloudWatch/S3 via option settings; Azure SQL auditing writes to Log Analytics, Event Hub, or storage with a single policy switch. Both are straightforward; Azure's policy-driven auditing across an entire estate (via Azure Policy) scales better for large fleets.

    • 7.9 Operations: Patching, Backups, Monitoring

    Patching. RDS patches during your maintenance window; you control the window and can defer, but AWS will eventually force critical patches. Azure SQL Database and Managed Instance are patched automatically by the platform with minimal downtime — you configure a maintenance window for MI to control timing, but there is no "patch Tuesday" you manage. Teams that want patching to disappear entirely prefer Azure; teams that want to correlate patches with their change process prefer RDS's explicit windows.

    Backups. RDS automated backups: snapshots plus log backups, 0–35 day retention, PITR to a new instance, manual snapshots retained indefinitely. Azure SQL automated backups: full/differential/log backups managed entirely by the platform, 7–35 day PITR retention depending on tier, plus long-term retention (LTR) policies up to 10 years for compliance — a first-class feature with no RDS equivalent. Azure backups restore to a new database (like RDS restores to a new instance), and geo-redundant backup storage gives you cross-region restore capability built in. If your compliance team asks for 7-year retention, Azure LTR answers it natively; on RDS you build it from snapshots and lifecycle policies.

    Monitoring. RDS gives you CloudWatch metrics, Enhanced Monitoring, and Performance Insights (Chapter 6). Azure gives you Azure Monitor metrics, Log Analytics, Query Store (on by default — a flight recorder for query plans and runtime stats that RDS does not have natively), and Intelligent Insights for automatic anomaly detection. Query Store deserves emphasis: automatic plan regression detection and forced-plan remediation are built into the engine on Azure, while on RDS you assemble the equivalent from Query Store (available in SQL Server 2016+ on RDS, but you manage it) plus Performance Insights.

    7.10 Migration Paths to Each

    To RDS for SQL Server: AWS Database Migration Service (DMS) with ongoing replication for near-zero downtime, or native backup/restore to S3 for simpler cutovers (take a native backup on-premises, upload to S3, restore with rds_restore_database). AWS Schema Conversion Tool matters less for SQL Server-to-SQL Server than for heterogeneous migrations. Test the restore path first: native restore validates edition compatibility and exposes unsupported features early.

    To Azure SQL: assess with DMA or the Azure Data Studio migration extension, then choose the target the assessment points to (usually MI for existing estates). Migrate with Azure Database Migration Service, or use the MI link — a near-zero-downtime migration path that replicates from your on-premises SQL Server to Managed Instance over Always On technology and fails over when you are ready. The MI link is the smoothest SQL Server cloud migration path that exists on any cloud: it is online, it is built on AG replication you already understand, and rollback is failing back to the primary.

    Whichever target you choose, the migration checklist from Chapter 3 applies: inventory Agent jobs, linked servers, CLR, cross-database dependencies, and SSIS packages; measure log generation rate and peak IOPS; and run a production-scale performance test on the target tier before cutover. The platform decision and the migration plan are the same project.

    7.11 The Decision Framework

    Apply these in order. The first one that fires usually decides it:

  • → Existing Microsoft licenses with Software Assurance? Price Azure SQL with Azure Hybrid Benefit against RDS BYOL/LI. AHB frequently wins by a wide margin — this single factor decides more evaluations than all the technical criteria combined.
  • → Where does the rest of the estate live? Data gravity and operational gravity matter. A workload deeply integrated with AWS services (Lambda, Kinesis, S3 data lakes) usually belongs on RDS; a workload tied to Active Directory, Microsoft 365, and ExpressRoute usually belongs on Azure.
  • → How much application change is acceptable? Zero-to-minimal change points to RDS for SQL Server or Managed Instance. Willingness to modernize (elastic pools, serverless, Hyperscale) opens up Azure SQL Database, which rewards cloud-native design with the best scaling and DR story.
  • → What does the compatibility inventory say? Heavy SQL Agent, linked server, CLR, or cross-database usage eliminates SQL Database and leaves RDS vs MI — decided by the first two questions.
  • → Do you need read scale-out or 100 TB databases? Hyperscale named replicas and 100 TB ceilings are unmatched; if you need them, the answer is Azure SQL Database Hyperscale.
  • → Compliance retention? Multi-year backup retention requirements favor Azure's built-in long-term retention.

    • Key Takeaways

  • → "Azure SQL" is two products, not one. Azure SQL Database (PaaS, no instance, elastic scale, longest feature-gap list) and Managed Instance (near-full engine compatibility, VNet-integrated, the lift-and-shift target) must be evaluated separately. Most existing estates belong on Managed Instance, not SQL Database.
  • → Licensing usually decides before technology does. Azure Hybrid Benefit for licenses with Software Assurance, versus RDS License Included or BYOL via License Mobility — model the real prices with your actual agreements before comparing features. The cheapest technically-sufficient option wins.
  • → Inventory compatibility before choosing. Agent jobs, linked servers, CLR assemblies, cross-database queries, and SSIS packages each eliminate or complicate options. Run DMA or the Azure Data Studio assessment and let the inventory, not intuition, rule out platforms.
  • → For DR depth and read scale-out, Azure's story is more complete. Active geo-replication, auto-failover groups, Hyperscale named replicas, and built-in long-term retention are first-class features; on RDS you assemble equivalents from snapshots, copies, and EC2-based secondaries.
  • → For operational familiarity on AWS, RDS is the simpler mental model. Instances, endpoints, parameter groups, and Multi-AZ failover map directly onto what SQL Server DBAs already know — at the cost of no read replicas, no serverless option, and a 16 TB ceiling.
