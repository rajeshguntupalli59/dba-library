Chapter 15: Azure SQL Hyperscale: When You Need It

Azure SQL Hyperscale is Microsoft's answer to a problem that on-prem DBAs know well: what happens when your database outgrows your storage architecture? Traditional SQL Server installations hit ceiling after ceiling — SAN I/O limits, filegroup management headaches, backup windows measured in hours, and the constant anxiety of a database that has grown beyond what your infrastructure was originally sized to handle. Azure SQL Hyperscale reimagines the storage layer entirely, decoupling compute from storage and introducing a distributed log service and page server architecture that lets you scale to 100 TB without a weekend maintenance window. This chapter covers when Hyperscale is the right choice, how it differs architecturally from standard Azure SQL Database tiers, how to provision and configure it correctly, what the production gotchas look like, and how to migrate into — and out of — it with your eyes open.

---

What Hyperscale Actually Is (And What It Isn't)

Before you provision a Hyperscale database, you need to understand that it is not simply "a bigger Azure SQL Database." It is a fundamentally different storage architecture that happens to present a familiar SQL Server surface. If you treat it like a standard Azure SQL tier with a higher storage cap, you will be surprised by behaviors that don't match your mental model.

The Architecture

In a traditional SQL Server instance — on-prem or in an Azure SQL General Purpose or Business Critical tier — your compute node owns the data files. Pages live on local or attached storage that the database engine reads and writes directly. Backups are full snapshots of that storage. Replica setup involves copying or synchronizing those files. Everything is tightly coupled.

Hyperscale decouples these layers. The architecture has four distinct components:

1. Compute replicas — These are your SQL Server engine instances. They hold the buffer pool (in-memory pages) and execute queries, but they do not own the data files.

2. Log service — A distributed, append-only transaction log service that sits between compute and storage. When your primary compute node commits a transaction, it writes to the log service first. This is where the acknowledged commit happens. Page servers and secondary replicas consume from this log asynchronously.

3. Page servers — Multiple independent page server processes that maintain portions of the database's page space and serve pages to compute nodes on demand. When a compute node needs a page not in its buffer pool, it fetches it from a page server over the network rather than from local disk. Each page server handles a shard of the database's page space, and they scale out as the database grows.

4. Azure Storage — The durable backing store underneath the page servers. This is Azure Premium Storage, providing the actual durability guarantee.

The practical consequence: your compute node's buffer pool is a cache in front of a distributed page store. A cold query that misses the buffer pool on a Hyperscale instance will be slower than the equivalent query on a Business Critical instance with local SSD, because it pays a network round-trip to a page server. On hot, well-cached workloads, Hyperscale performs comparably or better than other tiers for reads because you can add named replicas that each have their own independent buffer pool.

What It Is Designed For

Hyperscale makes sense when one or more of the following conditions apply:

  • → Your database exceeds 4 TB (the limit for General Purpose and Business Critical tiers)
  • → You need near-instant database creation and restore times regardless of database size
  • → Your backup and restore windows are a compliance or operational problem — a 50 TB Hyperscale database restores in roughly 5–10 minutes because Azure only needs to instantiate compute and point it at existing page server snapshots
  • → You have a mixed workload where you want to offload read-heavy reporting or analytics to a separate compute replica with its own memory and CPU, without the overhead of maintaining a full replica
  • → You have bursty storage growth patterns and don't want to over-provision

    • What It Is Not Designed For

    Hyperscale is not a general upgrade from Business Critical. Business Critical uses local SSD with in-memory OLTP support and has lower read latency for cold pages because storage is local. If your workload is primarily OLTP with a well-tuned buffer pool hit ratio above 98%, Business Critical will often outperform Hyperscale for raw query latency. Hyperscale also has restrictions that on-prem DBAs find surprising: as of the current GA release, you cannot change a Hyperscale database back to another service tier. That decision is one-directional. You migrate in, and if you need to migrate out, you do it through export/import or backup/restore — not through a service tier change.

    The no-downgrade restriction is not a technical limitation that might be lifted later. It reflects the fact that Hyperscale storage format is fundamentally different from the other tiers. Plan accordingly before you migrate production.

    Provisioning Hyperscale: Configuration That Matters

    When you create a Hyperscale database, the decisions that matter most are compute generation, vCore count, read replica topology, and backup redundancy. Storage is automatic and does not require sizing decisions the way you were accustomed to on-prem.

    Creating a Hyperscale Database with Azure CLI

    # Create a resource group and logical server first if not already present
az group create \
  --name rg-hyperscale-prod \
  --location eastus2

az sql server create \
  --name sql-hs-prod-eastus2 \
  --resource-group rg-hyperscale-prod \
  --location eastus2 \
  --admin-user sqladmin \
  --admin-password "$(az keyvault secret show \
    --vault-name kv-prod \
    --name sql-admin-password \
    --query value -o tsv)"

# Create the Hyperscale database
# Edition: Hyperscale
# Service objective: HS_Gen5_8 (Gen5, 8 vCores)
# High-availability replicas: 1 (adds a secondary compute replica for HA)
# Backup storage redundancy: Zone (zone-redundant backup storage)
az sql db create \
  --resource-group rg-hyperscale-prod \
  --server sql-hs-prod-eastus2 \
  --name OrdersDB \
  --edition Hyperscale \
  --service-objective HS_Gen5_8 \
  --ha-replicas 1 \
  --backup-storage-redundancy Zone \
  --read-scale Enabled

# Verify the database properties
az sql db show \
  --resource-group rg-hyperscale-prod \
  --server sql-hs-prod-eastus2 \
  --name OrdersDB \
  --query "{tier:sku.tier, size:sku.name, maxSize:maxSizeBytes, haReplicas:highAvailabilityReplicaCount}" \
  --output table

    Compute Tiers and Sizing

    Hyperscale compute uses the same vCore-based sizing as other Azure SQL tiers, but the service objective naming prefix is HS_. Common choices:

    | Service Objective | vCores | Memory | Notes |

    |---|---|---|---|

    | HS_Gen5_4 | 4 | 20.4 GB | Minimum recommended for production |

    | HS_Gen5_8 | 8 | 40.8 GB | Good starting point for moderate OLTP |

    | HS_Gen5_16 | 16 | 83 GB | High-concurrency workloads |

    | HS_Gen5_32 | 32 | 166 GB | Large in-memory working sets |

    | HS_Gen5_80 | 80 | 408 GB | Very large working sets, high throughput |

    There are also Fsv2 (compute-optimized) and M-series (memory-optimized) hardware generations available in select regions. The M-series configurations go up to 128 vCores and 3.7 TB of memory, which is territory that previously required dedicated hardware and significant capital expenditure.

    You can scale compute up or down online. Scaling to a different vCore count within the same hardware generation takes approximately 2–3 minutes with minimal disruption. Changing hardware generation (Gen5 to Fsv2, for example) takes longer and involves a reconfiguration event.

    Backup Storage Redundancy — Read This Before You Deploy

    The --backup-storage-redundancy flag matters more than it appears. The options are:

  • → `Local` — Backups stored in a single datacenter. Lowest cost, lowest durability. Not appropriate for most production workloads.
  • → `Zone` — Zone-redundant backup storage. Appropriate for single-region deployments that need AZ tolerance.
  • → `Geo` — Geo-redundant backup storage. Replicates backups to a paired region. Default for most Azure SQL tiers historically.
  • → `GeoZone` — Zone-redundant in primary region plus geo-replication. Highest durability.

    • The critical gotcha: you can only set backup storage redundancy when you create the Hyperscale database. You cannot change it afterward without creating a new database. If you provision with Local and later realize you need geo-redundant backups for your DR policy, you are rebuilding the database.

    Named Replicas: Read Scale-Out Without the Traditional Overhead

    One of the most operationally useful Hyperscale features is named replicas. A named replica is a Hyperscale compute node pointed at the same page servers as the primary. It sees a consistent, near-real-time view of the data (typically within 1–5 seconds of the primary, sometimes less). Critically, it is a fully independent Azure SQL Database resource with its own service tier, its own connection string, its own buffer pool, and its own independent security configuration.

    On-prem, you might have handled this with Always On readable secondaries. The fundamental difference is that a named replica in Hyperscale shares storage infrastructure with the primary — it is not maintaining a full copy of the data files. Adding a named replica takes minutes regardless of database size, because Azure is not copying 50 TB of data. It is instantiating a new compute node that can already read from the existing page servers.

    When Named Replicas Make Sense

    Named replicas are the right choice when:

  • → You have a large reporting or analytics workload that competes with OLTP on the primary
  • → You need to give a third-party team or application its own connection endpoint with no risk of their workload affecting production OLTP
  • → You need read scale-out during peak periods and want to spin replicas up and down dynamically

    • Named replicas are billed as separate Hyperscale databases with their own vCore cost. If you provision a named replica as HS_Gen5_16, you pay for those 16 vCores separately. For pure read offloading, you can often provision named replicas at a lower vCore count than the primary.

    # Create a named replica of an existing Hyperscale database
# The named replica lives in the same logical server
# It uses a different service objective than the primary if needed

az sql db replica create \
  --resource-group rg-hyperscale-prod \
  --server sql-hs-prod-eastus2 \
  --name OrdersDB \
  --partner-database OrdersDB_ReportingReplica \
  --partner-server sql-hs-prod-eastus2 \
  --service-objective HS_Gen5_4 \
  --partner-resource-group rg-hyperscale-prod

# Verify replication link
az sql db replica list-links \
  --resource-group rg-hyperscale-prod \
  --server sql-hs-prod-eastus2 \
  --name OrdersDB \
  --output table

# Connect to the named replica using its own connection string
# Named replica endpoint: sql-hs-prod-eastus2.database.windows.net

# Server=sql-hs-prod-eastus2.database.windows.net;

    Replication Lag Monitoring

    Named replicas and HA secondary replicas consume the log service asynchronously. You need to monitor replication lag in production, particularly for workloads where reporting queries need data that is close to real-time.

    -- Query replication lag on the primary (connect to primary, not replica)
-- sys.dm_database_replica_states is your tool here
SELECT
    r.replica_id,
    r.role_desc,
    r.secondary_lag_seconds,
    r.log_send_queue_size,
    r.log_send_rate,
    r.redo_queue_size,
    r.redo_rate,
    r.synchronization_health_desc,
    r.last_hardened_lsn,
    r.last_received_lsn
FROM sys.dm_hadr_database_replica_states r
WHERE r.is_local = 0;  -- Non-local = secondary replicas

-- For Hyperscale-specific log service metrics
-- Check log generation rate and log service throughput
SELECT
    database_id,
    log_bytes_used,
    log_bytes_used_percent,
    log_committed_bytes,
    log_committed_percent,
    log_recovery_size_mb,
    log_since_last_log_backup_mb,
    log_since_last_checkpoint_mb
FROM sys.dm_db_log_stats(DB_ID());

-- Monitor page server health and latency from compute node perspective
-- This DMV shows remote page fetches (page server hits vs buffer pool hits)
SELECT
    page_server_reads,
    page_server_reads_in_progress,
    page_server_read_in_progress_ms,
    page_server_read_elapsed_ms,
    checkpoint_phase_desc,
    checkpoint_start_time
FROM sys.dm_exec_requests
WHERE page_server_reads > 0
ORDER BY page_server_reads DESC;

    A replication lag above 30 seconds warrants investigation. Common causes are high log generation rate on the primary (large bulk operations, high-frequency small transactions), temporary page server pressure, or network congestion within the Azure fabric. You cannot directly tune the log service, but you can reduce peak log generation rate by batching large DML operations.

    Migrating Into Hyperscale: Patterns That Work in Production

    Migrating to Hyperscale from an on-prem SQL Server or from another Azure SQL tier requires more planning than a tier change, because Hyperscale is one-directional and the migration itself requires database-level operations rather than just a service tier slider.

    Option 1: Backup and Restore via Azure Blob Storage

    For on-prem databases below roughly 1 TB, this is the fastest path. You take a COPY_ONLY backup, upload to Azure Blob Storage, and restore into a Hyperscale database using RESTORE DATABASE ... FROM URL.

    -- On-premises SQL Server: Create credential and backup to Azure Blob Storage
-- Step 1: Create SAS credential on source SQL Server
CREATE CREDENTIAL [https://storprodmigration.blob.core.windows.net/backups]
WITH IDENTITY = 'SHARED ACCESS SIGNATURE',
SECRET = 'sv=2023-01-03&ss=b&srt=sco&sp=rwdlacupiytfx&se=2024-12-31T00:00:00Z&st=2024-01-01T00:00:00Z&spr=https&sig=<your-sas-token>';
GO

-- Step 2: Full backup with COPY_ONLY (non-disruptive to existing backup chain)
BACKUP DATABASE [OrdersDB]
TO URL = 'https://storprodmigration.blob.core.windows.net/backups/OrdersDB_full_20240115.bak'
WITH 
    COPY_ONLY,
    COMPRESSION,
    STATS = 10,
    BLOCKSIZE = 65536,
    MAXTRANSFERSIZE = 4194304;
GO

-- For large databases, stripe the backup across multiple files
BACKUP DATABASE [OrdersDB]
TO 
    URL = 'https://storprodmigration.blob.core.windows.net/backups/OrdersDB_stripe1.bak',
    URL = 'https://storprodmigration.blob.core.windows.net/backups/OrdersDB_stripe2.bak',
    URL = 'https://storprodmigration.blob.core.windows.net/backups/OrdersDB_stripe3.bak',
    URL = 'https://storprodmigration.blob.core.windows.net/backups/OrdersDB_stripe4.bak'
WITH 
    COPY_ONLY,
    COMPRESSION,
    STATS = 5;
GO

-- Step 3: On the Hyperscale target (via SSMS or Azure Cloud Shell with sqlcmd)
-- Create credential on target server
CREATE CREDENTIAL [https://storprodmigration.blob.core.windows.net/backups]
WITH IDENTITY = 'SHARED ACCESS SIGNATURE',
SECRET = 'sv=2023-01-03&ss=b&srt=sco&sp=rwdlacupiytfx&se=2024-12-31T00:00:00Z&st=2024-01-01T00:00:00Z&spr=https&sig=<your-sas-token>';
GO

-- Step 4: Restore into Hyperscale
-- Note: You must restore to a NEW database name, not overwrite an existing one
RESTORE DATABASE [OrdersDB]
FROM 
    URL = 'https://storprodmigration.blob.core.windows.net/backups/OrdersDB_stripe1.bak',
    URL = 'https://storprodmigration.blob.core.windows.net/backups/OrdersDB_stripe2.bak',
    URL = 'https://storprodmigration.blob.core.windows.net/backups/OrdersDB_stripe3.bak',
    URL = 'https://storprodmigration.blob.core.windows.net/backups/OrdersDB_stripe4.bak'
WITH 
    RECOVERY,
    STATS = 5;
GO

    For minimal-downtime migrations, you restore the full backup, then apply differential and log backups during a short cutover window. This is functionally the same as the SQL Server DBA's traditional migration playbook — the cloud just adds the credential layer.

    Option 2: Azure Database Migration Service

    For larger databases or when you want a more managed migration process, Azure DMS handles the orchestration. You configure it to perform an initial load followed by continuous replication of changes until you cut over. It is comparable in concept to setting up log shipping or replication to a new instance, with the monitoring and retry logic handled for you.

    # Create an Azure DMS instance (Premium tier for online migrations)
az dms create \
  --resource-group rg-hyperscale-prod \
  --name dms-migration-prod \
  --location eastus2 \
  --sku-name Premium_4vCores \
  --subnet /subscriptions/<sub-id>/resourceGroups/rg-network/providers/Microsoft.Network/virtualNetworks/vnet-prod/subnets/snet-dms \
  --storage-account /subscriptions/<sub-id>/resourceGroups/rg-hyperscale-prod/providers/Microsoft.Storage/storageAccounts/storprodmigration

# Create a migration project
az dms project create \
  --resource-group rg-hyperscale-prod \
  --service-name dms-migration-prod \
  --name proj-ordersdb-migration \
  --source-platform SQL \
  --target-platform AzureSqlDb \
  --location eastus2

# Create a migration task (online migration with continuous sync)
az dms project task create \
  --resource-group rg-hyperscale-prod \
  --service-name dms-migration-prod \
  --project-name proj-ordersdb-migration \
  --name task-ordersdb-migrate \
  --task-type OnlineMigration \
  --source-connection-json @source_connection.json \
  --target-connection-json @target_connection.json \
  --database-options-json @database_migration_options.json

# Monitor migration status
az dms project task show \
  --resource-group rg-hyperscale-prod \
  --service-name dms-migration-prod \
  --project-name proj-ordersdb-migration \
  --name task-ordersdb-migrate \
  --expand output \
  --query "output[0].migrationState"

    Pre-Migration Compatibility Check

    Hyperscale supports most SQL Server features, but there are exclusions. Run the Database Experimentation Assistant (DEA) or use the assessment feature in Azure Migrate before committing to a migration timeline. Common compatibility gaps that surface for on-prem databases:

  • → Linked servers — not supported in Azure SQL Database including Hyperscale. Replace with OPENDATASOURCE, external tables, or application-level joins.
  • → SQL Server Agent — not available. Use Azure Elastic Jobs or Azure Automation.
  • → Filestream / Filetable — not supported.
  • → Cross-database queries within the same instance — Azure SQL is database-scoped. If your application uses three-part names to query across databases, that needs rearchitecting.
  • → BULK INSERT from local file paths — requires Azure Blob Storage as the source.

    • These are not Hyperscale-specific limitations. They are Azure SQL Database limitations that apply across all tiers including Hyperscale. The point is that you discover them during migration planning, not after you have committed to the migration.

    Production Gotchas and Operational Patterns

    Hyperscale has behaviors that will surprise experienced SQL Server DBAs because they are not documented in the places you look first. This section covers the ones that cause the most friction in real production deployments.

    Cold Query Latency and Buffer Pool Warming

    After a compute replica failover — whether from a planned scaling event, an unplanned node failure, or the HA replica being promoted to primary — the new compute node starts with a cold buffer pool. Pages must be fetched from page servers on demand. For a large database, the period immediately following a failover will have noticeably higher read latency than steady state.

    On Business Critical, failover also lands you on a cold buffer pool on the new node if it was an unplanned failover, but the page fetch is from local SSD. On Hyperscale, it is a network round-trip to a page server. The latency is typically measured in single-digit milliseconds per page fetch, but queries that scan large ranges and miss the buffer pool can feel sluggish for several minutes to an hour after failover, depending on your working set size and query patterns.

    The mitigation strategies are:

    1. Schedule planned failovers (compute scaling, maintenance) during low-traffic periods when possible.

    2. Use connection retry logic in your application so that the brief (~30 second) failover window does not produce user-visible errors.

    3. For workloads where cold start latency is particularly damaging, consider pre-warming by running a scheduled query after known maintenance windows that touches your most-accessed indexes.

    -- Simple buffer pool pre-warming query pattern
-- Run this after a planned failover or compute scaling event
-- Adjust the table and index list to match your actual hot working set

-- Pre-warm a specific clustered index by scanning it
-- This forces pages into the buffer pool proactively
SELECT COUNT_BIG(*) FROM dbo.Orders WITH (NOLOCK);
SELECT COUNT_BIG(*) FROM dbo.OrderItems WITH (NOLOCK);
SELECT COUNT_BIG(*) FROM dbo.Customers WITH (NOLOCK);

-- You can also pre-warm specific index ranges if full scans are too expensive
-- Warm the last 90 days of orders (typical hot working set for OLTP)
SELECT COUNT_BIG(*) 
FROM dbo.Orders WITH (NOLOCK)
WHERE OrderDate >= DATEADD(DAY, -90, GETDATE());

-- Monitor buffer pool state after warming
-- Check what percentage of a table is currently cached
SELECT
    t.name AS TableName,
    i.name AS IndexName,
    i.type_desc AS IndexType,
    COUNT(1) AS CachedPages,
    COUNT(1) * 8 / 1024 AS CachedMB,
    SUM(CASE WHEN b.is_modified = 1 THEN 1 ELSE 0 END) AS DirtyPages
FROM sys.dm_os_buffer_descriptors b
INNER JOIN sys.allocation_units au 
    ON b.allocation_unit_id = au.allocation_unit_id
INNER JOIN sys.partitions p 
    ON au.container_id = p.hobt_id
INNER JOIN sys.indexes i 
    ON p.object_id = i.object_id AND p.index_id = i.index_id
INNER JOIN sys.tables t 
    ON p.object_id = t.object_id
WHERE b.database_id = DB_ID()
GROUP BY t.name, i.name, i.type_desc
ORDER BY CachedMB DESC;

    The Checkpoint Behavior Difference

    On standard SQL Server, checkpoints flush dirty pages from the buffer pool to disk at the storage layer. On Hyperscale, checkpoint behavior is different because the primary compute node does not own the storage. Checkpoints on Hyperscale flush dirty pages from the compute buffer pool to the page servers. This means the write path goes: application DML → log service (commit acknowledged here) → page server receives log record and applies it → dirty page flushed from compute buffer pool on checkpoint.

    The practical consequence is that I/O patterns around checkpoint look different in wait statistics. You will see WRITELOG waits that correspond to log service throughput, not local disk throughput. If you have historically used WRITELOG waits as a proxy for your storage I/O ceiling, you need to recalibrate — the constraint in Hyperscale is the log service throughput, which scales with your vCore tier.

    -- Monitor log throughput and wait statistics relevant to Hyperscale
SELECT
    wait_type,
    waiting_tasks_count,
    wait_time_ms,
    max_wait_time_ms,
    signal_wait_time_ms,
    wait_time_ms - signal_wait_time_ms AS resource_wait_time_ms
FROM sys.dm_os_wait_stats
WHERE wait_type IN (
    'WRITELOG',
    'LOG_RATE_GOVERNOR',
    'HADR_LOGCAPTURE_WAIT',
    'HADR_WORK_QUEUE',
    'PAGEIOLATCH_SH',
    'PAGEIOLATCH_EX',
    'PAGEIOLATCH_UP',
    'REMOTEBUF_IO_WAIT'  -- Hyperscale-specific: wait for remote page server I/O
)
ORDER BY wait_time_ms DESC;

-- LOG_RATE_GOVERNOR is particularly important for Hyperscale
-- It indicates your workload is hitting the log generation rate limit for your vCore tier
-- If you see high LOG_RATE_GOVERNOR waits, you need to scale up vCores or reduce log throughput

    LOG_RATE_GOVERNOR: The Throttle You Will Hit

    Each Hyperscale vCore tier has a maximum log generation rate measured in MB/s. When your transaction workload generates log records faster than this limit, SQL Server itself throttles new log-generating transactions, producing LOG_RATE_GOVERNOR waits. This is not a bug — it is an intentional throttle that protects the log service and downstream page servers.

    The log rate limits increase with vCore count. If you are routinely hitting LOG_RATE_GOVERNOR waits, the options are:

    1. Scale up vCores to a tier with a higher log rate limit.

    2. Reduce log generation per unit of work — batch your DML operations, minimize unnecessary row-by-row processing, use minimally logged operations where appropriate.

    3. Spread bulk operations over time rather than running them in large single transactions.

    -- Identify the heaviest log-generating operations currently running
SELECT
    r.session_id,
    r.status,
    r.command,
    r.wait_type,
    r.wait_time,
    r.total_elapsed_time,
    r.reads,
    r.writes,
    r.logical_reads,
    t.text AS QueryText,
    qp.query_plan
FROM sys.dm_exec_requests r
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) t
CROSS APPLY sys.dm_exec_query_plan(r.plan_handle) qp
WHERE r.wait_type = 'LOG_RATE_GOVERNOR'
ORDER BY r.total_elapsed_time DESC;

-- Historical log generation rate from ring buffer
-- This gives you a picture of log throughput over recent minutes
SELECT
    end_time,
    delta_log_bytes_used / 1048576.0 AS log_MB_generated,
    avg_log_rate_value / 1048576.0 AS log_rate_MB_per_sec
FROM sys.dm_db_resource_stats
ORDER BY end_time DESC;

    Snapshot Isolation and Read Committed Snapshot

    Hyperscale databases have RCSI (Read Committed Snapshot Isolation) enabled by default and it cannot be disabled. For on-prem DBAs who have spent years managing version store pressure on tempdb, this is actually welcome news — Hyperscale stores version records in the page server layer, not in tempdb. The version store does not create the tempdb pressure that causes headaches on busy on-prem instances.

    However, if your application was written against a database with READ_COMMITTED_SNAPSHOT OFF and relies on blocking behavior for correctness (for example, using locks as a coordination mechanism between application processes), you need to verify that RCSI does not change the behavior. Applications that take explicit UPDLOCK hints or use SERIALIZABLE transactions are not affected. Applications that relied on reader-writer blocking as an implicit synchronization mechanism will behave differently.

    Tempdb Is Still Shared on Standard Compute

    Unlike on-prem SQL Server where each instance has its own tempdb, Azure SQL Database shares tempdb resources across databases on the same logical server. On standard vCore tiers this is per the Azure SQL infrastructure. This is not a Hyperscale-specific behavior, but it catches DBAs who come from dedicated instances. Heavy tempdb consumers (large sorts, hash joins, spill-heavy plans, excessive temp table use) can see unexpected tempdb pressure from neighboring databases.

    Monitor tempdb usage and address spills in your query plans:

    -- Identify queries spilling to tempdb on Hyperscale
SELECT TOP 20
    qs.total_spills / qs.execution_count AS avg_spills_per_exec,
    qs.total_spills,
    qs.execution_count,
    qs.total_elapsed_time / qs.execution_count / 1000 AS avg_elapsed_ms,
    SUBSTRING(st.text, (qs.statement_start_offset / 2) + 1,
        ((CASE qs.statement_end_offset
            WHEN -1 THEN DATALENGTH(st.text)
            ELSE qs.statement_end_offset
          END - qs.statement_start_offset) / 2) + 1) AS QueryText
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
WHERE qs.total_spills > 0
ORDER BY qs.total_spills DESC;

    Monitoring Hyperscale in Production

    Standard Azure SQL monitoring applies to Hyperscale, with some additional dimensions. You should be collecting metrics from Azure Monitor, DMV-based monitoring from within the database, and query store data for workload trends.

    Azure Monitor Metrics for Hyperscale

    The metrics that matter most for Hyperscale, beyond the standard CPU and connection count, are:

  • → `log_write_percent` — how close you are to the log rate limit. Watch for sustained values above 80%.
  • → `storage_percent` — Hyperscale does not have a fixed storage cap in the traditional sense, but this metric reflects page server utilization.
  • → `xtp_storage_percent` — In-Memory OLTP storage (if you use memory-optimized tables).
  • → `dwu_consumption_percent` — effective compute consumption.
  • → `sessions_percent` — connection count relative to the limit for your tier.
    • # Pull Hyperscale-specific metrics via Azure CLI
az monitor metrics list \
  --resource "/subscriptions/<sub-id>/resourceGroups/rg-hyperscale-prod/providers/Microsoft.Sql/servers/sql-hs-prod-eastus2/databases/OrdersDB" \
  --metric "log_write_percent,cpu_percent,physical_data_read_percent,sessions_percent" \
  --interval PT1M \
  --start-time "$(date -u -d '1 hour ago' '+%Y-%m-%dT%H:%MZ')" \
  --end-time "$(date -u '+%Y-%m-%dT%H:%MZ')" \
  --output table

# Set up an alert for log rate throttling
az monitor metrics alert create \
  --name "hs-log-rate-high" \
  --resource-group rg-hyperscale-prod \
  --scopes "/subscriptions/<sub-id>/resourceGroups/rg-hyperscale-prod/providers/Microsoft.Sql/servers/sql-hs-prod-eastus2/databases/OrdersDB" \
  --condition "avg log_write_percent > 80" \
  --window-size 5m \
  --evaluation-frequency 1m \
  --action-group /subscriptions/<sub-id>/resourceGroups/rg-hyperscale-prod/providers/Microsoft.Insights/actionGroups/ag-dba-oncall \
  --description "Hyperscale log rate sustained above 80% - risk of LOG_RATE_GOVERNOR throttling"

    Query Store for Workload Trend Analysis

    Query Store is enabled by default on Hyperscale and is your primary tool for identifying plan regressions, tracking query performance over time, and understanding whether a performance problem is from a plan change or a data volume change.

    -- Configure Query Store for production Hyperscale workloads
-- The defaults are reasonable but you may want to increase retention
ALTER DATABASE [OrdersDB]
SET QUERY_STORE = ON (
    OPERATION_MODE = READ_WRITE,
    CLEANUP_POLICY = (STALE_QUERY_THRESHOLD_DAYS = 90),
    DATA_FLUSH_INTERVAL_SECONDS = 900,
    INTERVAL_LENGTH_MINUTES = 15,
    MAX_STORAGE_SIZE_MB = 4096,
    QUERY_CAPTURE_MODE = AUTO,
    MAX_PLANS_PER_QUERY = 200,
    SIZE_BASED_CLEANUP_MODE = AUTO,
    WAIT_STATS_CAPTURE_MODE = ON
);
GO

-- Find queries with the highest average elapsed time in the last 24 hours
SELECT TOP 20
    q.query_id,
    qt.query_sql_text,
    rs.avg_duration / 1000.0 AS avg_elapsed_ms,
    rs.avg_cpu_time / 1000.0 AS avg_cpu_ms,
    rs.avg_logical_io_reads,
    rs.avg_physical_io_reads,  -- High value here = page server fetches
    rs.count_executions,
    p.plan_id,
    p.last_force_failure_reason_desc
FROM sys.query_store_query q
JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
JOIN sys.query_store_plan p ON q.query_id = p.query_id
JOIN sys.query_store_runtime_stats rs ON p.plan_id = rs.plan_id
JOIN sys.query_store_runtime_stats_interval i ON rs.runtime_stats_interval_id = i.runtime_stats_interval_id
WHERE i.start_time >= DATEADD(HOUR, -24, GETUTCDATE())
ORDER BY rs.avg_duration DESC;

-- Find plan regressions: queries that have gotten slower recently
WITH recent_stats AS (
    SELECT
        q.query_id,
        AVG(rs.avg_duration) AS recent_avg_duration,
        MAX(rs.avg_duration) AS recent_max_duration,
        SUM(rs.count_executions) AS recent_executions
    FROM sys.query_store_query q
    JOIN sys.query_store_plan p ON q.query_id = p.query_id
    JOIN sys.query_store_runtime_stats rs ON p.plan_id = rs.plan_id
    JOIN sys.query_store_runtime_stats_interval i ON rs.runtime_stats_interval_id = i.runtime_stats_interval_id
    WHERE i.start_time >= DATEADD(HOUR, -4, GETUTCDATE())
    GROUP BY q.query_id
),
baseline_stats AS (
    SELECT
        q.query_id,
        AVG(rs.avg_duration) AS baseline_avg_duration
    FROM sys.query_store_query q
    JOIN sys.query_store_plan p ON q.query_id = p.query_id
    JOIN sys.query_store_runtime_stats rs ON p.plan_id = rs.plan_id
    JOIN sys.query_store_runtime_stats_interval i ON rs.runtime_stats_interval_id = i.runtime_stats_interval_id
    WHERE i.start_time >= DATEADD(HOUR, -28, GETUTCDATE())
      AND i.start_time < DATEADD(HOUR, -4, GETUTCDATE())
    GROUP BY q.query_id
)
SELECT
    r.query_id,
    qt.query_sql_text,
    b.baseline_avg_duration / 1000.0 AS baseline_avg_ms,
    r.recent_avg_duration / 1000.0 AS recent_avg_ms,
    r.recent_avg_duration / NULLIF(b.baseline_avg_duration, 0) AS regression_ratio
FROM recent_stats r
JOIN baseline_stats b ON r.query_id = b.query_id
JOIN sys.query_store_query q ON r.query_id = q.query_id
JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
WHERE r.recent_avg_duration > b.baseline_avg_duration * 2  -- 2x regression threshold
  AND r.recent_executions >= 10  -- Only queries with meaningful execution count
ORDER BY regression_ratio DESC;

    Page Server Latency DMV

    Hyperscale exposes a DMV specifically for page server operations that has no equivalent in standard Azure SQL tiers:

    -- sys.dm_user_db_resource_governance includes Hyperscale-specific limits
-- For page server I/O characteristics, use this combination:
SELECT
    io_stall,
    io_stall_read_ms,
    io_stall_write_ms,
    num_of_reads,
    num_of_writes,
    num_of_bytes_read,
    num_of_bytes_written,
    io_stall_queued_read_ms,    -- time spent waiting to issue reads
    io_stall_queued_write_ms    -- time spent waiting to issue writes
FROM sys.dm_io_virtual_file_stats(DB_ID(), NULL)
ORDER BY io_stall DESC;

-- Hyperscale-specific: check page server fetch activity
-- This is available in sys.dm_exec_requests during active queries
SELECT
    r.session_id,
    r.wait_type,
    r.wait_time,
    r.page_server_reads,
    r.page_server_reads_in_progress,
    r.page_server_read_elapsed_ms,
    CASE 
        WHEN r.page_server_reads > 0 
        THEN r.page_server_read_elapsed_ms / r.page_server_reads
        ELSE 0 
    END AS avg_page_server_read_ms,
    SUBSTRING(t.text, r.statement_start_offset / 2 + 1,
        (CASE r.statement_end_offset 
            WHEN -1 THEN DATALENGTH(t.text) 
            ELSE r.statement_end_offset 
         END - r.statement_start_offset) / 2 + 1) AS current_statement
FROM sys.dm_exec_requests r
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) t
WHERE r.page_server_reads > 0
ORDER BY r.page_server_reads DESC;

    If your avg_page_server_read_ms values are consistently above 5–10 ms for a heavily accessed query, it is a signal that your working set does not fit in the buffer pool and you would benefit from more memory — either by scaling vCores up or by adding a named replica that caches a subset of pages independently.

    Migrating Out of Hyperscale

    Because the tier change from Hyperscale back to another Azure SQL tier is not supported through the portal or API, you need a data movement strategy. This is not a frequent operation, but the scenarios where it arises include consolidation, cost reduction after a data archiving project that brought the database below 4 TB, or a strategic decision to move to a different database service entirely.

    Export to BACPAC

    BACPAC export is the simplest path for databases that are not extremely large. It exports the schema and data to an Azure Blob Storage file that can be imported into any Azure SQL tier.

    # Export Hyperscale database to BACPAC
# Note: For very large databases, this can take many hours
# Monitor progress via the export operation status

az sql db export \
  --resource-group rg-hyperscale-prod \
  --server sql-hs-prod-eastus2 \
  --name OrdersDB \
  --admin-user sqladmin \
  --admin-password "$(az keyvault secret show --vault-name kv-prod --name sql-admin-password --query value -o tsv)" \
  --storage-key "$(az storage account keys list --resource-group rg-hyperscale-prod --account-name storprodmigration --query '[0].value' -o tsv)" \
  --storage-key-type StorageAccessKey \
  --storage-uri "https://storprodmigration.blob.core.windows.net/exports/OrdersDB_export.bacpac"

# Monitor the export operation
az sql db op list \
  --resource-group rg-hyperscale-prod \
  --server sql-hs-prod-eastus2 \
  --database OrdersDB \
  --query "[?operation=='ExportDatabase']" \
  --output table

# Import BACPAC to a new General Purpose database
az sql db import \
  --resource-group rg-target \
  --server sql-gp-prod \
  --name OrdersDB \
  --admin-user sqladmin \
  --admin-password "$(az keyvault secret show --vault-name kv-prod --name sql-admin-password --query value -o tsv)" \
  --storage-key "$(az storage account keys list --resource-group rg-hyperscale-prod --account-name storprodmigration --query '[0].value' -o tsv)" \
  --storage-key-type StorageAccessKey \
  --storage-uri "https://storprodmigration.blob.core.windows.net/exports/OrdersDB_export.bacpac" \
  --edition GeneralPurpose \
  --service-objective GP_Gen5_8

    BACPAC export is not point-in-time consistent for active databases. If the database is still receiving writes during export, the resulting BACPAC may have a logically inconsistent state for tables that were modified while the export was running. For a clean migration out of Hyperscale, the safest approach is to quiesce writes during export or use the backup-and-restore path with a log backup applied at cutover.

    Transactional Replication for Live Cutover

    For large databases or workloads that cannot tolerate extended downtime, transactional replication from the Hyperscale source to a target database in a different tier provides continuous synchronization until cutover. You configure Hyperscale as the publisher, the target as the subscriber, let replication catch up, then flip the connection string and remove the replication topology.

    This approach requires careful attention to replication topology setup, but it is the same replication mechanism that on-prem DBAs have used for decades. Hyperscale supports being both a publisher and a subscriber for transactional replication, with the same T-SQL configuration commands that work on-prem.

    Cost Modeling: When Hyperscale Is the Right Economic Choice

    Hyperscale is not always the cheapest choice even for large databases, and it is worth doing the arithmetic before committing.

    The cost components for a Hyperscale database are:

    1. Compute: vCore-hours for the primary compute replica.

    2. HA replicas: Each HA replica is billed at the same vCore rate as the primary. One HA replica effectively doubles your compute cost.

    3. Named replicas: Each named replica is billed at its own vCore rate.

    4. Storage: Hyperscale storage pricing is per-GB per-month beyond the first 100 GB. Storage consumption grows with your database and does not shrink automatically when you delete data (pages are not immediately reclaimed from page servers after DELETE operations — space reclamation happens through index rebuilds and DBCC SHRINKFILE, which should be used judiciously).

    5. Backup storage: Billed per GB-month beyond 1x the database size.

    6. Log service egress: Generally included in the tier, but cross-region configurations may have network transfer costs.

    The inflection point where Hyperscale becomes economically competitive with Business Critical is roughly at the point where:

  • → The database exceeds 4 TB (forced migration anyway for General Purpose or Business Critical)
  • → Or the named replica topology you need would require multiple Always On nodes that would each need to be Business Critical size

    • For databases below 2 TB with no read scale-out requirement and a stable, OLTP-dominant workload, Business Critical often delivers better price-performance because of local SSD and the tighter latency profile.

    Do the vCore math with your actual workload size, your replica topology needs, and the current Azure SQL pricing for your region. Prices change, reserved instance discounts alter the comparison significantly, and the Dev/Test pricing for non-production Hyperscale instances reduces the cost of running staging and QA environments on the same tier as production.

    Key Takeaways

  • → Hyperscale is architecturally distinct, not just a storage upgrade. Its decoupled compute, log service, and page server model gives you near-instant backup and restore at any size, but introduces cold-page network latency that does not exist in Business Critical. Understand the tradeoff before provisioning.
  • → The migration into Hyperscale is one-directional through the service tier API. You can migrate out, but only through data movement operations like BACPAC export, backup/restore, or transactional replication — not through a tier change. Make the decision with full awareness of this constraint.
  • → Named replicas are a genuinely different read scale-out model. Because they share the page server layer rather than maintaining full storage copies, you can add or remove them in minutes regardless of database size. This makes dynamic read scale-out practical in ways that traditional readable secondaries are not.
  • → `LOG_RATE_GOVERNOR` is your primary throughput ceiling indicator. High `LOG_RATE_GOVERNOR` wait times mean your log generation rate exceeds what your vCore tier allows. The response is either to scale vCores up or to reduce log generation through batching and minimally logged patterns.
  • → Backup storage redundancy and RCSI-on behavior are set at creation and cannot be changed. Validate your DR requirements and your application's isolation level assumptions before the first provisioning command runs — these are not settings you can tune after the fact without rebuilding the database.
