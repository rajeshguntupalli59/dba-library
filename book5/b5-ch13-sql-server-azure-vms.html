Chapter 13: SQL Server on Azure VMs: Self-Managed on Azure

Chapter 8 built SQL Server on EC2. This chapter is its Azure twin: SQL Server on Azure Virtual Machines. The motivations rhyme — full engine control, readable secondaries, SSIS/SSAS/SSRS, consolidation — but the implementation is Azure-specific in ways that matter: the load balancer in front of the availability group listener, the cloud witness for quorum, Ultra Disk and caching policies for storage, and Azure Hybrid Benefit applied to VMs. If your organization is Microsoft-centric but your workload needs self-managed SQL Server, this is the chapter.

13.1 When Azure VMs Beat Azure SQL

The decision tree from Chapter 7 points here when: you need the full SQL Server surface (replication topologies Azure SQL does not support, specific CLR or linked-server configurations, PolyBase scale-out); you are consolidating many instances or databases per VM for licensing efficiency; you need a SQL Server version or CU that the PaaS offerings do not offer; or your operational model already manages Windows Server fleets and the team prefers IaaS consistency over PaaS abstraction. Azure VMs are also the natural home for SSIS, SSAS, and SSRS in a Microsoft-centric estate — the same components that pushed EC2 in Chapter 8.

The cost of IaaS is the same on both clouds: you own patching, availability, backup verification, and monitoring. What changes is the tooling around you — and several Azure features exist specifically to make SQL Server on VMs less painful than raw IaaS.

13.2 Licensing: Azure Hybrid Benefit on VMs

SQL Server on Azure VMs has the same two licensing paths as EC2, with Azure's twist. License-included images come from the Azure Marketplace with SQL Server pre-installed (per-minute billing that folds in the license). Azure Hybrid Benefit (AHB) lets you bring existing licenses with Software Assurance and pay only the VM compute rate — the same benefit from Chapter 7, applied to IaaS. For steady-state production VMs, AHB is usually the cheapest compliant path, and unlike AWS License Mobility, it is a first-class Azure billing toggle, not a paperwork exercise.

The licensing lever unique to Azure VMs is constrained vCPUs: several VM sizes can be deployed with fewer active vCPUs than the hardware provides, reducing the SQL Server core-license footprint without sacrificing memory or I/O bandwidth. A VM with 64 vCPUs constrained to 16 active vCPUs needs 16 core licenses instead of 64 — while keeping the memory and disk throughput of the larger size. For Enterprise Edition licensing, this single feature can change the VM selection entirely: choose the size for memory and throughput, constrain vCPUs for licensing.

# Deploy a SQL Server VM from a Marketplace image with AHB applied
az vm create \
  --resource-group rg-prod \
  --name sqlvm-prod-01 \
  --image MicrosoftSQLServer:sql2022-ws2022:enterprise:latest \
  --size Standard_E16s_v5 \
  --vcpus-available 4 \
  --vcpus-per-core 2 \
  --license-type Windows_Server \
  --vnet-name vnet-prod \
  --subnet snet-sql \
  --nsg sg-sql \
  --admin-username sqladmin

# Apply Azure Hybrid Benefit for SQL Server to an existing VM
az sql vm update \
  --resource-group rg-prod \
  --name sqlvm-prod-01 \
  --license-type AHUB

13.3 VM Sizing: E, D, and M Series

The workhorse series for SQL Server on Azure are E-series (memory-optimized, the default choice for OLTP), D-series (balanced compute), and M-series (very large memory for the biggest workloads). Two Azure-specific sizing notes: first, check the uncached disk throughput limits per VM size — your storage design cannot exceed what the VM can push, and the limit is per-VM, not per-disk. Second, Premium SSD v2 and Ultra Disk change the throughput math versus classic Premium SSD; Ultra Disk offers sub-millisecond latency and independently configurable IOPS/throughput, making it the choice for log volumes on demanding workloads.

13.4 Storage: Caching Policies and the Temp Drive

Azure storage caching is the setting EC2 does not have, and getting it wrong costs performance silently. The rules:

  • → Data files: ReadOnly caching. The local SSD cache in the VM accelerates reads; writes bypass the cache to Premium storage. This is the recommended and highest-performing setting for data volumes.
  • → Log files: no caching (None). Write-through latency matters more than read caching for the log, and cached writes risk data loss semantics. Set caching to None on log volumes — this is the most commonly misconfigured setting.
  • → Tempdb: the D: drive. Azure VMs have an ephemeral temp drive (D: on Windows) backed by local SSD — fast, free, and wiped on VM move/redeploy. Point tempdb at D: for maximum tempdb throughput at zero storage cost. The trade-off is ephemerality: tempdb is recreated on SQL Server start anyway, so this is safe — but anything else you put on D: is not.

    • Stripe data volumes across multiple Premium/Ultra disks when a single disk's IOPS or throughput ceiling binds you, and use 64 KB allocation units exactly as on EC2. For the highest-end workloads, Ultra Disk with sub-millisecond latency replaces the "local NVMe" conversation from Chapter 8 — with the advantage of persistence that instance-store volumes lack.

    13.5 Availability Groups on Azure VMs: The Load Balancer Listener

    Always On AGs on Azure VMs work like AGs on EC2 — multi-subnet listeners, quorum planning — with two Azure-specific adaptations. First, the AG listener goes behind an Azure Load Balancer (internal load balancer for VNet-internal listeners). The load balancer holds the listener IP as a frontend, with a health probe (conventionally TCP port 59999) that each replica answers only when it is the primary. Enable floating IP (direct server return) on the load balancing rule so the primary responds directly to clients. Without the load balancer, cross-subnet listener failover does not work on Azure — this is the architectural piece with no EC2 equivalent, and the most common source of "AG works, listener doesn't" incidents.

    Second, quorum uses a cloud witness: a blob storage endpoint that holds the quorum vote, replacing the file-share witness. No third VM to manage, no SMB share to maintain — a storage account and a configuration step. For two-replica AGs, the cloud witness is the deciding vote; for three-replica AGs across three zones, it is resilience depth.

    # Create the internal load balancer for the AG listener
az network lb create \
  --resource-group rg-prod \
  --name lb-aglistener \
  --sku Standard \
  --vnet-name vnet-prod \
  --subnet snet-sql \
  --private-ip-address 10.0.1.50 \
  --frontend-ip-name fe-aglistener

# Health probe: replicas answer only when primary
az network lb probe create \
  --resource-group rg-prod \
  --lb-name lb-aglistener \
  --name probe-ag \
  --protocol Tcp \
  --port 59999 \
  --interval 5 \
  --threshold 2

# Load balancing rule with floating IP enabled
az network lb rule create \
  --resource-group rg-prod \
  --lb-name lb-aglistener \
  --name rule-aglistener \
  --protocol Tcp \
  --frontend-port 1433 \
  --backend-port 1433 \
  --frontend-ip-name fe-aglistener \
  --backend-pool-name be-agreplicas \
  --probe-name probe-ag \
  --floating-ip true \
  --idle-timeout 30

    On each replica, the probe port is served by a lightweight mechanism that returns success only on the primary — commonly a PowerShell-driven firewall rule or the cluster's probe response. Test listener failover explicitly: the AG can fail over cleanly while the load balancer still sends traffic to the old primary if the probe configuration is wrong.

    13.6 Patching: Automated Patching and Maintenance Configurations

    Azure offers automated patching for SQL Server VMs via the SQL IaaS Agent extension: Windows and SQL Server updates install on a schedule you define (e.g., monthly, third Tuesday, 2 AM), with pre/post-patch scripting hooks. For availability groups, enable health-check-driven patching so the platform patches secondaries first and fails over gracefully — the same secondaries-first discipline as Chapter 8, automated. Maintenance configurations give you control over when Azure's own host maintenance (not SQL Server patching) can reboot the VM — pin it to your maintenance window so host updates never surprise a production workload.

    13.7 Backup: Automated Backup to Blob Storage

    The SQL IaaS Agent extension provides automated backup: full and log backups on a schedule you configure, written directly to Azure Blob storage with configurable retention (point-in-time restore within the retention window). This is the closest Azure IaaS gets to RDS automated backups — and unlike RDS, the backup files are native .bak files in your storage account, restorable anywhere. Combine with blob immutability policies (time-based retention / legal hold) for ransomware-resistant backups, and geo-redundant storage for the cross-region copy.

    13.8 Monitoring and the SQL IaaS Extension

    Register every SQL Server VM with the SQL IaaS Agent extension (lightweight mode at minimum). Registration unlocks automated patching, automated backup, and Azure Monitor integration — including SQL-specific metrics and the Azure portal's SQL VM management blade. Unregistered VMs are just Windows VMs that happen to run SQL Server; registered VMs get the manageability layer that narrows the gap with PaaS. For deep diagnostics, the same stack as EC2 applies: PerfMon counters to Azure Monitor, Extended Events, Query Store, and the AG health DMVs from Chapter 8.

    13.9 Cost Comparison: Azure VM vs the Alternatives

    With AHB, a SQL Server VM's cost is the VM compute plus storage — often substantially less than Managed Instance's vCore-hour rate for the same capacity, and less than RDS License Included. The VM wins on raw infrastructure cost and loses on operational cost: your team owns everything Chapter 8 described. The honest comparison, as always, includes engineering time. For consolidated estates (many databases per VM) with AHB, Azure VMs are frequently the cheapest compliant way to run SQL Server in the cloud — which is exactly why the decision deserves the full analysis rather than a PaaS default.

    Key Takeaways

  • → Azure VMs are the self-managed answer for Microsoft-centric estates. Full engine control, readable AG secondaries, SSIS/SSAS/SSRS, and consolidation — with Azure-specific implementation for networking, quorum, and storage.
  • → Licensing is the lever: AHB plus constrained vCPUs. Apply Azure Hybrid Benefit to pay compute-only, and constrain vCPUs to size the license footprint independently of memory and throughput. Get the licensing answer in writing before building.
  • → Storage caching policies are load-bearing. Data volumes ReadOnly, log volumes None, tempdb on the ephemeral D: drive. Ultra Disk for sub-millisecond log latency on demanding workloads.
  • → AG listeners go behind an internal load balancer with floating IP. The health probe answers only on the primary. Cloud witness replaces the file-share witness for quorum. Test listener failover explicitly — AG failover and listener failover are two different things.
  • → Register every VM with the SQL IaaS Agent extension. Automated patching, automated backup to Blob storage, and Azure Monitor integration narrow the IaaS manageability gap. Unregistered VMs are just Windows VMs.
