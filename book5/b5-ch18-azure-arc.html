Chapter 18: Azure Arc-Enabled SQL Server: Hybrid Cloud

Azure Arc-Enabled SQL Server extends Azure's management plane to SQL Server instances running anywhere — on-premises data centers, colocation facilities, edge locations, or competing cloud providers. For DBAs managing hybrid environments, this changes the operational calculus: instead of maintaining separate toolchains for on-prem and cloud databases, you get unified monitoring, policy enforcement, security scanning, and licensing management through a single Azure portal and API surface. This chapter covers how Arc-Enabled SQL Server works architecturally, how to onboard existing SQL Server instances, how to configure Azure services like Microsoft Defender and Azure Monitor against non-Azure hosts, and how to use Arc as a bridge during phased cloud migrations rather than a permanent destination.

---

18.1 Understanding Azure Arc Architecture for SQL Server

Before Arc, hybrid database management meant running parallel monitoring stacks — perhaps SCOM or Datadog for on-premises SQL Server alongside Azure Monitor for Azure SQL. Security assessments ran separately. Licensing compliance was tracked in spreadsheets. Arc collapses this by projecting non-Azure resources into Azure Resource Manager (ARM) as first-class objects.

The architecture rests on two components: the Connected Machine Agent (the Arc agent installed on the host OS) and the Arc SQL Server extension. The Connected Machine agent establishes an outbound HTTPS connection to Azure's Arc service endpoints on port 443. No inbound firewall rules are required. The agent authenticates using a service principal or managed identity, receives its configuration from ARM, and reports telemetry back to Azure. The SQL Server extension layer sits on top, communicating with the local SQL Server instance via a Windows service (SqlServerExtension) or systemd service on Linux.

On-Premises Host
├── SQL Server 2019 (or 2022, 2017, 2016)
├── Arc Connected Machine Agent
│   └── Heartbeat → Azure Arc Service Endpoints (TCP 443)
└── Arc SQL Server Extension
    ├── Reads SQL metadata, license info, configuration
    ├── Sends to Azure Monitor Log Analytics
    └── Applies policies from Azure Policy

From ARM's perspective, your on-premises SQL Server appears under Microsoft.AzureArcData/sqlServerInstances as a resource type. You can tag it, apply RBAC, include it in Azure Policy assignments, and view it in the Azure portal alongside Azure SQL Managed Instances and Azure SQL Databases. This ARM projection is what makes the rest of Arc's capabilities possible — every feature (Defender, Monitor, Best Practices Assessment) hooks into ARM resource identity.

What Arc does not do: It does not move your data. It does not replicate your databases to Azure. It does not change how SQL Server operates internally. The Arc agent has read-only access to SQL Server metadata; it cannot execute DML or DDL. DBAs coming from environments where any agent was treated as a security risk should understand this boundary clearly.

Network requirements differ from what DBAs typically manage. Arc agents must reach several Azure endpoints:

| Endpoint | Purpose |

|---|---|

| management.azure.com | ARM operations |

| login.microsoftonline.com | Azure AD authentication |

| *.his.arc.azure.com | Hybrid Identity Service |

| *.guestconfiguration.azure.com | Policy guest configuration |

| dc.services.visualstudio.com | Telemetry |

In air-gapped environments, Arc supports proxy server configuration — the agent can route all outbound traffic through an authenticated HTTP proxy. Some highly secure environments route Arc traffic through Azure Private Link by deploying a Private Link scope for Azure Monitor and Arc endpoints, though this requires significant network engineering.

Supported SQL Server versions span from SQL Server 2012 through 2022. Extended Security Updates (ESUs) through Arc are a significant licensing benefit for shops still running 2012 or 2014: Microsoft provides ESU patches free of charge for Arc-connected instances (subject to Software Assurance or Azure subscription conditions). For DBAs managing legacy infrastructure that cannot be migrated immediately, this alone often justifies the Arc onboarding effort.

18.2 Onboarding SQL Server Instances to Arc

Onboarding has three paths: single-machine (interactive), at-scale via script, and policy-driven. Interactive onboarding suits labs and initial testing. At-scale is what production environments use.

Single-machine onboarding using Azure CLI:

# Prerequisites: Azure CLI with arcdata extension
az extension add --name arcdata
az extension add --name connectedmachine

# Create a resource group for Arc resources
az group create \
  --name rg-arc-sqlserver-prod \
  --location eastus2

# Create a service principal for Arc onboarding
# Store credentials securely - this SP will be used by agents
az ad sp create-for-rbac \
  --name "sp-arc-onboarding" \
  --role "Azure Connected Machine Onboarding" \
  --scopes "/subscriptions/<subscription-id>/resourceGroups/rg-arc-sqlserver-prod"

# Output:
# {
#   "appId": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
#   "displayName": "sp-arc-onboarding",
#   "password": "xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx",
#   "tenant": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
# }

# Download the onboarding script from Azure portal or generate via CLI
az connectedmachine connect \
  --resource-group rg-arc-sqlserver-prod \
  --location eastus2 \
  --subscription <subscription-id> \
  --tenant-id <tenant-id> \
  --service-principal-id <appId> \
  --service-principal-secret <password>
# Run this command ON the target SQL Server host

For at-scale onboarding across dozens or hundreds of servers, the recommended approach is a PowerShell script deployed via configuration management (Ansible, Chef, SCCM, or GPO):

# Deploy-ArcAgent.ps1
# Run this on each SQL Server host via your configuration management tool

param(
    [Parameter(Mandatory=$true)]
    [string]$TenantId,
    
    [Parameter(Mandatory=$true)]
    [string]$SubscriptionId,
    
    [Parameter(Mandatory=$true)]
    [string]$ResourceGroup,
    
    [Parameter(Mandatory=$true)]
    [string]$Location,
    
    [Parameter(Mandatory=$true)]
    [string]$ServicePrincipalId,
    
    [Parameter(Mandatory=$true)]
    [string]$ServicePrincipalSecret,
    
    [string]$Environment = "Production",
    [string]$CostCenter = "DBA-Ops"
)

# Download the Arc agent installer
$AgentInstallerUrl = "https://aka.ms/AzureConnectedMachineAgent"
$InstallerPath = "$env:TEMP\AzureConnectedMachineAgent.msi"

Write-Host "Downloading Arc Connected Machine Agent..."
Invoke-WebRequest -Uri $AgentInstallerUrl -OutFile $InstallerPath

# Install silently
Write-Host "Installing Arc Connected Machine Agent..."
msiexec.exe /i $InstallerPath /l*v "$env:TEMP\arc_install.log" /qn

# Wait for service to start
Start-Sleep -Seconds 30

# Connect to Azure Arc
$ArcConnectArgs = @(
    "connect",
    "--tenant-id", $TenantId,
    "--subscription-id", $SubscriptionId,
    "--resource-group", $ResourceGroup,
    "--location", $Location,
    "--service-principal-id", $ServicePrincipalId,
    "--service-principal-secret", $ServicePrincipalSecret,
    "--tags", "Environment=$Environment,CostCenter=$CostCenter,OnboardedBy=AutoScript"
)

& "C:\Program Files\AzureConnectedMachineAgent\azcmagent.exe" @ArcConnectArgs

if ($LASTEXITCODE -eq 0) {
    Write-Host "Arc agent connected successfully for $env:COMPUTERNAME"
    
    # Install SQL Server Arc extension
    # This happens automatically if the agent detects SQL Server,
    # but we can trigger it explicitly
    $ExtensionArgs = @(
        "extensions", "install",
        "--name", "WindowsAgent.SqlServer",
        "--publisher", "Microsoft.AzureData",
        "--version", "latest"
    )
    & "C:\Program Files\AzureConnectedMachineAgent\azcmagent.exe" @ExtensionArgs
} else {
    Write-Error "Arc agent connection failed for $env:COMPUTERNAME with exit code $LASTEXITCODE"
    exit 1
}

After onboarding, verify the Arc SQL Server resource exists:

# Verify Arc-connected SQL Server instances
az sql server-arc list \
  --resource-group rg-arc-sqlserver-prod \
  --output table

# Get details of a specific instance
az sql server-arc show \
  --name SQLPROD01 \
  --resource-group rg-arc-sqlserver-prod

# List all databases discovered on the Arc SQL Server
az sql db-arc list \
  --server-name SQLPROD01 \
  --resource-group rg-arc-sqlserver-prod \
  --output table

License type configuration is one of the most operationally important settings. Arc tracks whether each instance uses License Included, Azure Hybrid Benefit, or Pay-As-You-Go licensing. Setting this incorrectly leads to billing surprises or compliance gaps:

# Set Azure Hybrid Benefit license type for an Arc SQL instance
# Use this if you have existing SQL Server licenses with Software Assurance
az sql server-arc update \
  --name SQLPROD01 \
  --resource-group rg-arc-sqlserver-prod \
  --license-type LicenseIncluded

# License type options:
# LicenseIncluded  - You're paying for the license through Azure (ESU scenario)
# PAYG             - Pay-as-you-go (useful for dev/test)
# Paid             - Azure Hybrid Benefit (bring your own SA license)

Gotcha: SQL Server instances with multiple named instances on the same host appear as separate Arc SQL Server resources, but they share the same Connected Machine Agent. If the agent goes offline, all instances become unreachable in Arc simultaneously. Monitor agent health separately from SQL Server health.

Gotcha: Linux-hosted SQL Server (SQL Server on RHEL, Ubuntu, SLES) is fully supported by Arc, but the extension service name differs (mssql-server-arc via systemd). Automation scripts that assume Windows service names will fail silently on Linux hosts.

18.3 Azure Monitor and Log Analytics Integration

Once Arc is connected, Azure Monitor becomes the unified observability layer for both your on-premises SQL Server and Azure SQL services. The key component is the Log Analytics agent (or its newer replacement, Azure Monitor Agent / AMA), which ships SQL Server performance counters and event log data to a Log Analytics workspace.

Configure Log Analytics data collection:

# Create a Log Analytics workspace
az monitor log-analytics workspace create \
  --resource-group rg-arc-sqlserver-prod \
  --workspace-name law-sqlserver-hybrid \
  --location eastus2 \
  --sku PerGB2018 \
  --retention-time 90

# Get workspace ID and key for agent configuration
WORKSPACE_ID=$(az monitor log-analytics workspace show \
  --resource-group rg-arc-sqlserver-prod \
  --workspace-name law-sqlserver-hybrid \
  --query customerId -o tsv)

WORKSPACE_KEY=$(az monitor log-analytics workspace get-shared-keys \
  --resource-group rg-arc-sqlserver-prod \
  --workspace-name law-sqlserver-hybrid \
  --query primarySharedKey -o tsv)

echo "Workspace ID: $WORKSPACE_ID"
echo "Workspace Key: $WORKSPACE_KEY"

# Enable monitoring extension on Arc SQL Server
az connectedmachine extension create \
  --machine-name SQLPROD01 \
  --resource-group rg-arc-sqlserver-prod \
  --name MMA \
  --publisher Microsoft.EnterpriseCloud.Monitoring \
  --type MicrosoftMonitoringAgent \
  --settings "{\"workspaceId\": \"$WORKSPACE_ID\"}" \
  --protected-settings "{\"workspaceKey\": \"$WORKSPACE_KEY\"}"

Once data flows into Log Analytics, you write KQL queries against it exactly as you would for Azure SQL — the workspace abstraction normalizes the data regardless of origin:

// KQL: Find longest-running queries on Arc-connected SQL instances
// Run this in Log Analytics workspace
AzureDiagnostics
| where ResourceProvider == "MICROSOFT.AZUREARCDATA"
| where Category == "SQLQueryStoreRuntime"
| where TimeGenerated > ago(1h)
| extend ExecutionDurationMs = todouble(max_elapsed_time_d) / 1000
| where ExecutionDurationMs > 5000
| project 
    TimeGenerated,
    Resource,
    database_name_s,
    query_id_d,
    ExecutionDurationMs,
    total_worker_time_d,
    execution_count_d
| order by ExecutionDurationMs desc
| take 50

// KQL: Wait stats comparison across hybrid fleet
Perf
| where ObjectName == "SQLServer:Wait Statistics"
| where CounterName in ("Lock waits", "Log write waits", "Network IO waits")
| where TimeGenerated > ago(24h)
| summarize AvgWait = avg(CounterValue) by Computer, CounterName, bin(TimeGenerated, 1h)
| render timechart

// KQL: Identify Arc instances with high CPU over 80%
Perf
| where ObjectName == "Processor Information"
| where CounterName == "% Processor Time"
| where TimeGenerated > ago(1h)
| summarize AvgCPU = avg(CounterValue) by Computer, bin(TimeGenerated, 5m)
| where AvgCPU > 80
| join kind=inner (
    AzureDiagnostics
    | where ResourceProvider == "MICROSOFT.AZUREARCDATA"
    | distinct Computer = Resource
) on Computer
| project TimeGenerated, Computer, AvgCPU
| order by AvgCPU desc

Best Practices Assessment is an Arc-specific capability that runs scheduled SQL Server configuration assessments and reports findings to Log Analytics. It checks a broad set of rules covering security configuration, performance settings, availability configuration, and deprecated features — consult current Microsoft documentation for the exact rule count and categories, since these are added to over time. Unlike ad-hoc assessment tools, this runs on a schedule (weekly by default, configurable to daily) and trends results over time.

# Enable Best Practices Assessment on Arc SQL Server
az sql server-arc assessment create \
  --name SQLPROD01 \
  --resource-group rg-arc-sqlserver-prod \
  --workspace-id $WORKSPACE_ID \
  --schedule "0 2 * * 0"  # Weekly at 2 AM Sunday (cron format)

# View assessment results via CLI
az sql server-arc assessment show \
  --name SQLPROD01 \
  --resource-group rg-arc-sqlserver-prod

# Assessment findings appear in Log Analytics under SqlAssessment_CL table

Query assessment findings programmatically:

// KQL: Critical and High severity assessment findings
SqlAssessment_CL
| where TimeGenerated > ago(7d)
| where Severity_s in ("Critical", "High")
| where IsRuleInWarningState_b == true
| project
    TimeGenerated,
    Computer,
    RuleName_s,
    Severity_s,
    Category_s,
    Description_s,
    Recommendation_s
| order by Severity_s asc, TimeGenerated desc

Alert rules for Arc SQL Server instances use the same Azure Monitor alert framework as Azure SQL. The difference is that metric sources reference microsoft.azurearcdata/sqlserverinstances rather than microsoft.sql/servers. Some metrics available for Azure SQL (like DTU consumption) have no Arc equivalent since Arc instances aren't DTU-based.

# Create an alert rule for high CPU on Arc SQL instances
az monitor metrics alert create \
  --name "ArcSQL-HighCPU-Alert" \
  --resource-group rg-arc-sqlserver-prod \
  --scopes "/subscriptions/<sub-id>/resourceGroups/rg-arc-sqlserver-prod/providers/Microsoft.AzureArcData/sqlServerInstances/SQLPROD01" \
  --condition "avg Processor/PercentProcessorTime > 85" \
  --window-size 5m \
  --evaluation-frequency 1m \
  --action-group "/subscriptions/<sub-id>/resourceGroups/rg-arc-sqlserver-prod/actionGroups/dba-oncall" \
  --description "CPU exceeded 85% on Arc-connected SQL Server SQLPROD01" \
  --severity 2

18.4 Microsoft Defender for SQL via Arc

Microsoft Defender for SQL provides vulnerability assessment and advanced threat protection for SQL Server instances. Without Arc, Defender for SQL was limited to Azure SQL services. Arc extends it to on-premises and multicloud SQL Server instances under the same policy and billing framework.

Enable Defender for SQL on Arc instances:

# Enable Defender for SQL at subscription level
# This applies to all Arc SQL instances in the subscription
az security pricing create \
  --name SqlServerVirtualMachines \
  --tier Standard

# Verify Defender is active on specific Arc instance
az security sql-vulnerability-assessment list \
  --server-name SQLPROD01 \
  --resource-group rg-arc-sqlserver-prod

# Run an on-demand vulnerability assessment
az security sql-vulnerability-assessment scan \
  --server-name SQLPROD01 \
  --resource-group rg-arc-sqlserver-prod \
  --database-name HRDB

Defender for SQL performs two distinct functions. Vulnerability Assessment scans SQL Server configuration against a database of known misconfigurations — things like sa account enabled, CLR enabled without justification, xp_cmdshell exposed, databases with TRUSTWORTHY ON, weak password policies, and over-privileged logins. It produces a baseline on first run and flags deviations from that baseline on subsequent scans.

Advanced Threat Protection analyzes SQL Server audit logs for behavioral anomalies: SQL injection patterns, unusual data export volumes, logins from unexpected locations, and brute-force login patterns. This requires SQL Server Audit to be configured and shipping logs to a storage account or Log Analytics workspace.

-- Configure SQL Server Audit for Defender ATP integration
-- Run on the on-premises Arc-connected SQL Server instance

-- Create server audit pointing to Log Analytics
-- For Arc instances, use FILE audit and let Arc extension ship logs
USE master;
GO

CREATE SERVER AUDIT [ArcDefenderAudit]
TO FILE (
    FILEPATH = 'D:\SQLAudit\',
    MAXSIZE = 100 MB,
    MAX_ROLLOVER_FILES = 50,
    RESERVE_DISK_SPACE = OFF
)
WITH (
    QUEUE_DELAY = 1000,
    ON_FAILURE = CONTINUE
);
GO

ALTER SERVER AUDIT [ArcDefenderAudit] WITH (STATE = ON);
GO

-- Create audit specification for Defender-relevant events
CREATE SERVER AUDIT SPECIFICATION [ArcDefenderAuditSpec]
FOR SERVER AUDIT [ArcDefenderAudit]
ADD (FAILED_LOGIN_GROUP),
ADD (SUCCESSFUL_LOGIN_GROUP),
ADD (LOGOUT_GROUP),
ADD (DATABASE_PERMISSION_CHANGE_GROUP),
ADD (SERVER_PERMISSION_CHANGE_GROUP),
ADD (DATABASE_ROLE_MEMBER_CHANGE_GROUP),
ADD (SERVER_ROLE_MEMBER_CHANGE_GROUP),
ADD (USER_CHANGE_PASSWORD_GROUP),
ADD (SCHEMA_OBJECT_ACCESS_GROUP)
WITH (STATE = ON);
GO

-- Verify audit is active
SELECT 
    a.name AS audit_name,
    a.status_desc,
    a.type_desc,
    s.name AS spec_name,
    s.is_state_enabled
FROM sys.server_audits a
JOIN sys.server_audit_specifications s 
    ON a.audit_guid = s.audit_guid
WHERE a.name = 'ArcDefenderAudit';

Defender for SQL alerts surface in Azure Security Center (now Microsoft Defender for Cloud) under the same dashboard as Azure SQL alerts. A DBA managing 200 on-premises instances previously had no centralized security alert surface for SQL injection attempts. With Arc, a brute-force attack against an on-premises SQL Server in a Chicago data center triggers the same Defender for Cloud alert workflow as an attack against an Azure SQL Database in East US.

Gotcha: Defender for SQL is billed per protected instance per month — check current Azure pricing for your region and tier before enabling it broadly. For shops with large SQL Server estates, enabling Defender at subscription scope without an instance count audit first produces unexpected billing. Run the count before enabling:

# Count Arc SQL instances before enabling Defender
az sql server-arc list \
  --subscription <subscription-id> \
  --query "length(@)" \
  --output tsv

# List instances with vCore count to estimate Defender cost
az sql server-arc list \
  --subscription <subscription-id> \
  --query "[].{Name:name, Location:location, vCores:properties.vCores, Edition:properties.edition}" \
  --output table

18.5 Azure Policy for Hybrid SQL Server Governance

Azure Policy becomes your configuration enforcement mechanism across the hybrid fleet. Where you previously used SQL Server Policy-Based Management (PBM) for on-premises enforcement and separate tooling for Azure SQL, Arc unifies both under Azure Policy.

Built-in Arc SQL Server policies cover:

  • → SQL Server should have Azure Defender enabled
  • → SQL Server should have transparent data encryption enabled
  • → SQL Server should have the latest cumulative update installed
  • → SQL Server should not use the sa account
  • → Arc-enabled SQL Server instances should have Azure AD authentication configured

    • You assign these policies to management groups, subscriptions, or resource groups. Instances that drift from policy show as non-compliant in the Defender for Cloud compliance dashboard.

    # Assign built-in policy: Defender for SQL should be enabled on Arc instances
POLICY_DEFINITION_ID=$(az policy definition list \
  --query "[?displayName=='Microsoft Defender for SQL should be enabled for unprotected SQL Servers'].id" \
  --output tsv)

az policy assignment create \
  --name "require-defender-arcsql" \
  --display-name "Require Defender for Arc SQL Servers" \
  --policy $POLICY_DEFINITION_ID \
  --scope "/subscriptions/<subscription-id>/resourceGroups/rg-arc-sqlserver-prod" \
  --enforcement-mode Default

# Create custom policy: Ensure minimum SQL Server version
cat > custom-policy-sqlversion.json << 'EOF'
{
  "mode": "All",
  "policyRule": {
    "if": {
      "allOf": [
        {
          "field": "type",
          "equals": "Microsoft.AzureArcData/sqlServerInstances"
        },
        {
          "field": "Microsoft.AzureArcData/sqlServerInstances/version",
          "notIn": ["SQL Server 2019", "SQL Server 2022"]
        }
      ]
    },
    "then": {
      "effect": "audit"
    }
  },
  "parameters": {}
}
EOF

az policy definition create \
  --name "require-sql-2019-or-later" \
  --display-name "Arc SQL Server must be 2019 or later" \
  --description "Audits Arc-connected SQL Servers running versions prior to SQL Server 2019" \
  --rules custom-policy-sqlversion.json \
  --mode All

# Assign the custom policy
az policy assignment create \
  --name "enforce-sql-version" \
  --policy "require-sql-2019-or-later" \
  --scope "/subscriptions/<subscription-id>"

    Policy remediation tasks handle non-compliant resources automatically where possible. For example, a policy requiring TDE on all Arc SQLServer databases can include a deployIfNotExists effect that triggers a remediation task to enable TDE without manual DBA intervention:

    # Create remediation task for non-compliant Arc SQL instances
az policy remediation create \
  --name "remediate-defender-arcsql" \
  --policy-assignment "require-defender-arcsql" \
  --resource-group rg-arc-sqlserver-prod \
  --resource-discovery-mode ReEvaluateCompliance

# Monitor remediation task progress
az policy remediation show \
  --name "remediate-defender-arcsql" \
  --resource-group rg-arc-sqlserver-prod \
  --query "{Status:properties.provisioningState, Succeeded:properties.resourceCounts.compliant, Failed:properties.resourceCounts.noncompliant}"

# List all non-compliant Arc SQL resources across subscription
az policy state list \
  --subscription <subscription-id> \
  --filter "complianceState eq 'NonCompliant' and resourceType eq 'Microsoft.AzureArcData/sqlServerInstances'" \
  --query "[].{Resource:resourceId, Policy:policyDefinitionName, State:complianceState}" \
  --output table

    Guest Configuration policies extend enforcement into the OS and SQL Server configuration layer. Unlike standard Azure Policy which validates ARM resource properties, Guest Configuration runs inside the machine and can audit or enforce settings like SQL Server service account configuration, SQL Server error log retention, and SQL Agent job configurations. These policies deploy a Guest Configuration agent to the Arc-connected machine and run DSC-based configuration checks.

    # List available Guest Configuration policy definitions for SQL Server
az policy definition list \
  --query "[?contains(displayName, 'SQL') && policyType=='BuiltIn' && contains(metadata.category, 'Guest Configuration')].{Name:displayName, Id:name}" \
  --output table

# Assign Guest Configuration policy for SQL Server service account validation
az policy assignment create \
  --name "gc-sql-service-account" \
  --display-name "SQL Server services should not use SA account" \
  --policy "/providers/Microsoft.Authorization/policyDefinitions/<definition-id>" \
  --scope "/subscriptions/<subscription-id>/resourceGroups/rg-arc-sqlserver-prod" \
  --mi-system-assigned \
  --location eastus2

# Guest Configuration policies require a managed identity on the assignment
# Grant the assignment's managed identity the necessary role
ASSIGNMENT_PRINCIPAL=$(az policy assignment show \
  --name "gc-sql-service-account" \
  --scope "/subscriptions/<subscription-id>/resourceGroups/rg-arc-sqlserver-prod" \
  --query identity.principalId -o tsv)

az role assignment create \
  --assignee $ASSIGNMENT_PRINCIPAL \
  --role "Guest Configuration Resource Contributor" \
  --scope "/subscriptions/<subscription-id>/resourceGroups/rg-arc-sqlserver-prod"

    18.6 Arc as a Migration Bridge

    Arc is frequently positioned as a permanent hybrid management solution, but its most underappreciated use case is as a migration bridge — a way to bring Azure governance and tooling to an on-premises instance before migrating it to Azure SQL Managed Instance, Azure SQL Database, or SQL Server on Azure VMs. This section addresses that phased migration pattern.

    The migration bridge pattern works in three phases:

    Phase 1: Onboard           Phase 2: Assess            Phase 3: Migrate
─────────────────────      ─────────────────────      ─────────────────
Install Arc agent      →   Run BPA assessments    →   Execute migration
Connect to ARM             Evaluate Defender alerts    Decommission Arc resource
Establish monitoring       Size MI/DB targets          Retain audit history
Configure alerts           Address blockers            in Log Analytics
    graph LR
    A[Phase 1: Onboard
    Install Arc agent, connect to ARM,
    establish monitoring] --> B[Phase 2: Assess
    Run BPA, evaluate Defender alerts,
    size migration targets]
    B --> C[Phase 3: Migrate
    Execute migration,
    decommission Arc resource]
    C --> D[Log Analytics retains
    audit history post-migration]

    *Arc used as a migration bridge: governance and assessment tooling attach to the on-premises instance before it is retired in favor of a native Azure SQL target.*

    During Phase 2, Arc provides two migration-critical capabilities: Azure Migrate integration and the SQL Server assessment reports that identify migration blockers.

    # Create Azure Migrate project for hybrid SQL assessment
az migrate project create \
  --resource-group rg-arc-sqlserver-prod \
  --project-name migrate-sql-2024 \
  --location eastus2

# Arc-connected SQL Server instances appear automatically in Azure Migrate
# when the subscription and workspace are linked. View discovered instances:
az migrate machine list \
  --resource-group rg-arc-sqlserver-prod \
  --project-name migrate-sql-2024 \
  --output table

# The SQL Server migration extension provides target recommendation
az sql server-arc migration-assessment create \
  --name SQLPROD01 \
  --resource-group rg-arc-sqlserver-prod \
  --target-type ManagedInstance \
  --workspace-id $WORKSPACE_ID

    The migration assessment identifies blockers such as linked servers (not supported in Azure SQL Database), cross-database queries (requires Managed Instance or Elastic Pools), CLR assemblies using unsafe or external access, distributed transactions, SQL Server Agent jobs using unsupported subsystems, and Windows Authentication without Azure AD federation configured.

    Maintaining Arc connectivity during a rolling migration helps when you have multiple databases on a single instance and migrate them one at a time:

    -- SQL Server: Track database migration status across hybrid fleet
-- Create a tracking table in a DBA management database (on-prem)
CREATE TABLE dba.MigrationTracker (
    InstanceName        NVARCHAR(128) NOT NULL,
    DatabaseName        NVARCHAR(128) NOT NULL,
    ArcResourceId       NVARCHAR(500) NULL,
    MigrationTarget     NVARCHAR(200) NULL, -- e.g., 'mi-prod.database.windows.net'
    MigrationStatus     NVARCHAR(50)  NOT NULL DEFAULT 'Pending',
        -- Pending, Assessing, InProgress, Cutover, Complete
    AssessmentDate      DATETIME2 NULL,
    MigrationStartDate  DATETIME2 NULL,
    CutoverDate         DATETIME2 NULL,
    BlockerCount        INT NULL,
    Notes               NVARCHAR(MAX) NULL,
    ModifiedBy          NVARCHAR(128) NOT NULL DEFAULT SUSER_SNAME(),
    ModifiedDate        DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    CONSTRAINT PK_MigrationTracker PRIMARY KEY (InstanceName, DatabaseName)
);
GO

-- Populate with current databases
INSERT INTO dba.MigrationTracker (InstanceName, DatabaseName)
SELECT 
    @@SERVERNAME,
    name
FROM sys.databases
WHERE name NOT IN ('master', 'model', 'msdb', 'tempdb')
AND state_desc = 'ONLINE';
GO

-- Query migration status
SELECT 
    InstanceName,
    MigrationStatus,
    COUNT(*) AS DatabaseCount,
    MIN(AssessmentDate) AS EarliestAssessment,
    MAX(CutoverDate) AS LatestCutover
FROM dba.MigrationTracker
GROUP BY InstanceName, MigrationStatus
ORDER BY InstanceName, MigrationStatus;

    After migration, clean up Arc resources for instances that have been fully migrated:

    # Verify no remaining databases before disconnecting Arc
az sql db-arc list \
  --server-name SQLPROD01 \
  --resource-group rg-arc-sqlserver-prod \
  --output table

# Disconnect the Arc SQL Server extension first
az connectedmachine extension delete \
  --machine-name SQLPROD01 \
  --resource-group rg-arc-sqlserver-prod \
  --name WindowsAgent.SqlServer \
  --yes

# Disconnect the machine from Arc
# (Run this on the host itself OR remotely via ARM)
az connectedmachine delete \
  --name SQLPROD01 \
  --resource-group rg-arc-sqlserver-prod \
  --yes

# Or from the host, run the agent disconnect command:
# azcmagent disconnect --service-principal-id <id> --service-principal-secret <secret>

# Retain Log Analytics data per your retention policy
# The workspace data persists independently of Arc resource deletion

    Gotcha: Deleting the Arc connected machine resource in ARM does not uninstall the Arc agent from the host OS. The agent continues running but in a disconnected state. On decommissioned hosts this is harmless; on hosts that will be repurposed, uninstall the agent explicitly using Add/Remove Programs on Windows or the package manager on Linux before reprovisioning.

    18.7 Azure AD Authentication for Arc SQL Server

    One of the more transformative capabilities Arc enables for on-premises SQL Server is Azure Active Directory (Azure AD) authentication, which Microsoft now calls Microsoft Entra ID authentication. Traditionally, on-premises SQL Server relied on Windows Authentication against local Active Directory, or SQL authentication. Arc-enabled SQL Server 2022 can authenticate users directly against Azure AD without requiring Azure AD Connect or AD Federation Services — the Arc agent handles the token validation.

    This matters for hybrid environments where:

  • → Remote workers lack VPN access to on-premises AD but have Azure AD credentials
  • → Azure-native applications need to connect to on-premises SQL Server using managed identities
  • → You want unified audit trails across Azure SQL and on-premises SQL Server

    • Prerequisites for Azure AD auth on Arc SQL Server:

    1. SQL Server 2022 (Azure AD auth is not available for earlier versions via Arc)

    2. Arc Connected Machine Agent version 1.13 or later

    3. Azure AD admin assigned to the SQL Server instance

    4. Outbound connectivity to Azure AD endpoints

    # Set Azure AD admin for Arc SQL Server instance
az sql server-arc ad-admin create \
  --name SQLPROD01 \
  --resource-group rg-arc-sqlserver-prod \
  --display-name "SQL Arc Admins" \
  --object-id <azure-ad-group-object-id> \
  --type Group

# Verify AD admin assignment
az sql server-arc ad-admin show \
  --name SQLPROD01 \
  --resource-group rg-arc-sqlserver-prod

    Once configured, create Azure AD logins using T-SQL syntax:

    -- SQL Server 2022: Create Azure AD logins on Arc-connected instance
-- Connect as sysadmin first

-- Create login for an Azure AD user
CREATE LOGIN [dbadmin@contoso.com]
FROM EXTERNAL PROVIDER;
GO

-- Create login for an Azure AD group
CREATE LOGIN [SQL-DBAs@contoso.com]
FROM EXTERNAL PROVIDER;
GO

-- Create login for an Azure managed identity
-- Useful when Azure Functions or App Service needs to connect to on-prem SQL via Arc
CREATE LOGIN [my-azure-function-app]
FROM EXTERNAL PROVIDER;
GO

-- Grant server-level permissions
ALTER SERVER ROLE [sysadmin] ADD MEMBER [SQL-DBAs@contoso.com];
GO

-- Create database user mapped to the Azure AD login
USE [HRDB];
GO

CREATE USER [dbadmin@contoso.com] FROM LOGIN [dbadmin@contoso.com];
GO

ALTER ROLE [db_datareader] ADD MEMBER [dbadmin@contoso.com];
ALTER ROLE [db_datawriter] ADD MEMBER [dbadmin@contoso.com];
GO

-- Verify Azure AD logins
SELECT 
    name,
    type_desc,
    authentication_type_desc,
    create_date,
    is_disabled
FROM sys.server_principals
WHERE type IN ('E', 'X')  -- E = External User, X = External Group
ORDER BY create_date DESC;

    Connecting to Arc SQL Server using Azure AD authentication:

    # Python: Connect to Arc-enabled SQL Server using Azure AD token
# Uses azure-identity and pyodbc

import pyodbc
from azure.identity import DefaultAzureCredential
import struct

def get_azure_ad_token():
    """Acquire Azure AD token for SQL Server authentication."""
    credential = DefaultAzureCredential()
    # Resource ID for SQL Server
    token = credential.get_token("https://database.windows.net/.default")
    return token.token

def connect_arc_sql_server(server_name: str, database: str) -> pyodbc.Connection:
    """
    Connect to Arc-enabled SQL Server using Azure AD authentication.
    server_name: FQDN or IP of on-premises SQL Server
    database: Target database name
    """
    token = get_azure_ad_token()
    
    # Convert token to bytes for ODBC access token attribute
    token_bytes = token.encode('utf-16-le')
    token_struct = struct.pack(f'<I{len(token_bytes)}s', 
                               len(token_bytes), 
                               token_bytes)
    
    connection_string = (
        f"DRIVER={{ODBC Driver 18 for SQL Server}};"
        f"SERVER={server_name};"
        f"DATABASE={database};"
        f"Encrypt=yes;"
        f"TrustServerCertificate=no;"
    )
    
    conn = pyodbc.connect(
        connection_string,
        attrs_before={1256: token_struct}  # SQL_COPT_SS_ACCESS_TOKEN
    )
    return conn

# Usage
conn = connect_arc_sql_server("sqlprod01.corp.contoso.com", "HRDB")
cursor = conn.cursor()
cursor.execute("SELECT SYSTEM_USER, USER_NAME(), @@SERVERNAME")
row = cursor.fetchone()
print(f"Logged in as: {row[0]}, User: {row[1]}, Server: {row[2]}")
conn.close()

    Gotcha: Azure AD authentication on Arc SQL Server 2022 requires the SQL Server certificate to be trusted by clients. Self-signed certificates generated during SQL Server installation will cause connection failures with TrustServerCertificate=no. Either issue a certificate from an enterprise CA or update clients to trust the self-signed certificate during a transition period — but do not leave TrustServerCertificate=yes in production connection strings permanently.

    18.8 Operational Runbooks for Arc-Managed SQL Server

    Managing an Arc-connected SQL Server fleet requires operational procedures that account for both the Azure control plane and the on-premises SQL Server layer. This section documents runbook patterns for the most common operational scenarios.

    Runbook: Arc agent health check and remediation

    Arc agent connectivity issues are the most common operational problem. The agent can lose connectivity due to proxy changes, certificate expiration, service account password rotation, or network policy changes. Detect and remediate with this pattern:

    #!/bin/bash
# arc-agent-health-check.sh
# Run from Azure Cloud Shell or from a jumpbox with Azure CLI access

RESOURCE_GROUP="rg-arc-sqlserver-prod"
SUBSCRIPTION_ID="<subscription-id>"

echo "=== Arc Agent Health Check: $(date) ==="

# List all Arc machines and their connectivity status
az connectedmachine list \
  --resource-group $RESOURCE_GROUP \
  --query "[].{Name:name, Status:properties.status, LastHeartbeat:properties.lastStatusChange, AgentVersion:properties.agentVersion}" \
  --output table

# Find machines that haven't reported in over 30 minutes
STALE_THRESHOLD=$(date -u -d "30 minutes ago" '+%Y-%m-%dT%H:%M:%SZ')
echo ""
echo "=== Machines with stale heartbeat (> 30 min) ==="
az connectedmachine list \
  --resource-group $RESOURCE_GROUP \
  --query "[?properties.lastStatusChange < '$STALE_THRESHOLD'].{Name:name, LastHeartbeat:properties.lastStatusChange, Status:properties.status}" \
  --output table

# Check agent version - identify outdated agents
echo ""
echo "=== Agent versions in fleet ==="
az connectedmachine list \
  --resource-group $RESOURCE_GROUP \
  --query "[].{Name:name, AgentVersion:properties.agentVersion}" \
  --output table

    18.9 Limitations and When Not to Use Arc

    Arc solves real problems, but it is not the right tool in every scenario. Understanding the limitations prevents over-engineering.

    Arc does not provide real-time query performance insights equivalent to Query Store UI in SSMS. The data that flows to Log Analytics has ingestion latency — typically two to five minutes, sometimes longer under high telemetry load. For active performance troubleshooting of an in-flight incident, DBAs still connect directly to the SQL Server instance using SSMS, Azure Data Studio, or direct T-SQL queries against DMVs. Arc is a fleet management and governance layer, not a low-latency diagnostic tool.

    Arc agent overhead is minimal but not zero. The Connected Machine Agent and SQL Server extension consume approximately 200-400 MB of memory on the host and generate periodic CPU spikes during telemetry collection windows. On memory-constrained legacy servers (32 GB or less) running large SQL workloads, this overhead should be evaluated before mass rollout.

    Connectivity dependency is real. If an Arc-connected instance loses outbound internet access, it continues running SQL Server normally — Arc has no operational dependency on Azure connectivity. However, policy evaluations stop updating, Defender alerts stop flowing, monitoring gaps appear in Log Analytics, and BPA assessments fail silently. Design monitoring for Arc agent connectivity as a separate health signal.

    Arc is not a replication or high availability solution. It provides no data-layer capabilities. DBAs who encounter Arc for the first time sometimes conflate it with Azure SQL Managed Instance Link (which does provide replication). Arc manages metadata; Managed Instance Link synchronizes data. These are complementary, not competing.

    Sovereign cloud and regulatory constraints affect Arc deployments. Arc endpoints route through Azure's commercial cloud by default. Organizations subject to data sovereignty regulations in jurisdictions where Azure Government, Azure China, or Azure Germany regions apply must configure Arc to use the appropriate sovereign cloud endpoints — and some highly regulated industries prohibit any management-plane data leaving specific geographic boundaries, which Arc's current architecture does not accommodate.

    # Configure Arc for Azure Government cloud
# (Must be done before connecting the agent)
& "C:\Program Files\AzureConnectedMachineAgent\azcmagent.exe" config set cloud "AzureUSGovernment"

# Or for Azure China
& "C:\Program Files\AzureConnectedMachineAgent\azcmagent.exe" config set cloud "AzureChinaCloud"

# Verify cloud configuration
& "C:\Program Files\AzureConnectedMachineAgent\azcmagent.exe" config list

    Key Takeaways

  • → Arc projects on-premises SQL Server into Azure Resource Manager as a first-class resource, enabling unified RBAC, tagging, policy enforcement, and monitoring through the same Azure portal and API surface used for Azure SQL services — without moving any data or changing SQL Server's operational behavior.
  • → Onboarding uses an outbound-only HTTPS connection via the Connected Machine Agent; no inbound firewall rules are required. At-scale onboarding through configuration management tools (Ansible, SCCM, GPO) is the production approach, and license type configuration at onboarding time prevents billing discrepancies.
  • → Azure Monitor, Log Analytics KQL queries, Defender for SQL, and Best Practices Assessment all extend to Arc-connected instances under the same frameworks used for Azure SQL, eliminating parallel monitoring and security toolchains for hybrid fleets — though Arc telemetry has ingestion latency unsuitable for real-time incident diagnostics.
  • → Arc serves as a migration bridge, not just a permanent hybrid solution: its integration with Azure Migrate and SQL Server assessment reporting surfaces migration blockers, tracks per-database migration status, and preserves historical audit data in Log Analytics that persists after the Arc resource is decommissioned.
  • → Azure AD authentication for Arc SQL Server 2022 enables token-based authentication from Azure-native workloads and remote users without AD Federation Services or Azure AD Connect, but requires properly trusted certificates on the SQL Server host — self-signed certificates must be addressed before enabling this capability in production.
