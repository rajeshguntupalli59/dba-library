Chapter 26: Data Sovereignty and Residency Compliance

Data sovereignty — the principle that data is subject to the laws of the jurisdiction where it resides — has moved from legal theory to engineering constraint. GDPR, Schrems II, sectoral regulations, and an expanding set of national data-localization laws mean the DBA must now answer questions that used to belong to counsel: where does this database's data physically live, where do its backups live, who holds the encryption keys, and can you prove it? This chapter turns those questions into SQL Server engineering: region selection, replication boundaries, key custody, audit evidence, and the right-to-erasure problem.

26.1 Understanding the Regulatory Landscape for Cloud DBAs

You do not need a law degree, but you need the working vocabulary: data residency (data stored in a specific jurisdiction), data sovereignty (data subject to a jurisdiction's laws — residency is one mechanism, not the whole concept), data localization (laws requiring certain data to stay within borders), and transfer mechanisms (the legal basis for moving data across borders where allowed). The DBA's job is not to interpret the law — it is to implement the controls the business's interpretation requires, and to produce the evidence: region configurations, replication topologies, backup locations, key custody records, and access logs. When counsel asks "prove EU customer data never leaves the EU," the answer is architecture plus logs, not assurances.

26.2 AWS: Region, Replication, and Key Custody

On AWS, sovereignty is built from: region pinning (RDS instances, EC2, and S3 buckets in the required region — with SCPs/permission boundaries preventing deployment elsewhere); replication boundaries (no cross-region snapshot copies, no S3 cross-region replication to non-compliant regions — audit the automation, because a well-meaning DR setup is the most common sovereignty violation); and key custody (KMS keys in the same region, with key policies restricting use; for the strictest requirements, dedicated key stores or CloudHSM-backed keys where the customer holds exclusive key control). Document the backup chain end to end: automated RDS snapshots, manual snapshots, and S3 native backups each have their own region — verify all three.

26.3 Azure SQL: Geo-Replication, Paired Regions, and Data Boundary

Azure's sovereignty tooling is the most explicit: paired regions (each Azure region has a designated pair, usually in the same geography — failover groups default within the pair, which keeps DR inside the sovereignty boundary); the EU Data Boundary (Microsoft's commitment that EU customer data stays in the EU — understand exactly which services and data flows it covers); and customer-managed keys in Key Vault (preferably Managed HSM with customer-held key material for the strictest regimes). The traps: support telemetry and diagnostics — verify what leaves the region for monitoring and support (Azure Monitor, diagnostic settings destinations); and long-term retention backups — LTR stores in the paired region by default, which is usually compliant, but verify the pairing for your specific region rather than assuming.

26.4 Google Cloud: Residency Controls for SQL Server

On GCP: organization policies constraining resource locations (allowed regions for Cloud SQL, Compute Engine, and Cloud Storage — the GCP analog of AWS SCPs); Cloud KMS keys pinned to the compliant region with customer-managed encryption keys (CMEK) on Cloud SQL instances; and Access Transparency / Assured Workloads for the regimes that require personnel-access controls, not just data-location controls. The GCP-specific check: BigQuery and analytics exports — the sovereignty boundary most often breached is not the database but the pipeline that copies its data into an analytics project in another region (Chapter 22's offload pattern needs a residency review).

26.5 Audit Logging for Residency Compliance

Evidence is the product. The audit baseline: control-plane logs (CloudTrail, Azure Activity Log, GCP Audit Logs — proving where resources were created and what replication was configured); SQL Server audit (logins, data access to classified tables, DDL — proving who touched the data); and backup/restore logs (proving where copies went). Ship all three to immutable, retention-locked storage in the compliant region — audit logs that can be modified are not evidence. Run the "prove it" exercise annually: pick a regulated dataset and trace every copy (primary, replicas, backups, exports, analytics derivatives) to a compliant location, with logs. The gaps this finds are always surprising.

26.6 Data Classification and Residency-Aware Schema Design

Not all data carries the same obligations. Classify (public, internal, confidential, regulated/personal) using SQL Server's data classification labels or your governance tooling, then design residency around the classification: regulated columns isolated into dedicated tables or databases that can be pinned to compliant regions, while non-regulated data lives wherever is cheapest. The schema patterns: vertical partitioning by classification (personal data in its own tables with restricted access — also simplifies erasure, section 26.7); and tokenization/pseudonymization at the boundary (analytics and non-production environments get tokens, not real personal data — the sovereignty problem disappears when the data isn't personal). Classification is a living process: new columns get classified at migration-review time (Chapter 23's pipeline), not discovered during the audit.

26.7 Right to Erasure and the Database Engineering Challenge

The right to erasure ("delete my data") is a database engineering problem wearing a legal costume. The challenges: finding the data (personal data scattered across tables, replicas, backups, exports, and analytics derivatives — the classification from 26.6 is what makes this tractable); backups (you cannot surgically delete from a backup chain — the accepted practice is erasure from live systems plus backup expiration on the normal retention cycle, documented and defensible); and referential integrity (erasure must not corrupt the database — anonymize foreign-key-referenced rows rather than deleting them where history must be preserved). Build the erasure runbook before the first request arrives: the identified queries, the verification steps, and the evidence package. The 30-day clock starts when the request arrives, not when you're ready.

26.8 Operationalizing Sovereignty: Runbooks and Governance

Sovereignty fails operationally, not architecturally. The governance baseline: region allow-lists enforced by policy (not by convention — SCPs, Azure Policy, org policies that deny non-compliant deployments); the new-service review (every new cloud service or feature gets a residency check before production use — yesterday's compliant architecture plus today's new feature is tomorrow's finding); quarterly copy-mapping (the "prove it" exercise from 26.5, on a schedule); and incident runbooks for sovereignty breaches (a misconfigured replication caught by audit is an incident: stop the flow, assess exposure, notify per the breach plan). Assign ownership — sovereignty without an owner is a shared assumption, and shared assumptions are how data ends up in the wrong region.

Key Takeaways

  • → Sovereignty is architecture plus evidence. Region pinning, replication boundaries, and key custody — proven by control-plane logs, SQL Server audit, and backup records in immutable storage.
  • → Audit the automation, not just the architecture. DR copies, analytics exports, and new features are how data leaves the compliant region. Policy-enforced allow-lists beat conventions.
  • → Classify data, then design residency around classification. Isolate regulated data, tokenize at boundaries, classify new columns at migration-review time.
  • → Build the erasure runbook before the first request. Find-every-copy via classification, erasure from live systems, defensible backup expiration, anonymization where history must survive.
  • → Assign ownership and run the "prove it" exercise annually. Trace a regulated dataset to every copy with logs. The gaps are always surprising — that is the point.
