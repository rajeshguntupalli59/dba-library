Chapter 21: Policy-Driven Compliance Automation

Compliance frameworks — SOC 2, HIPAA, PCI-DSS, GDPR, ISO 27001 — share a common engineering problem: humans cannot reliably enforce policy at the speed and scale that modern database platforms demand. An autonomous compliance system doesn't wait for an audit cycle to discover that a staging database received production PII, that a service account accumulated excessive privileges over six months, or that an unencrypted backup landed in the wrong storage tier. It detects the drift, evaluates it against a machine-readable policy graph, and corrects or escalates the deviation without a ticket being opened. This chapter walks through how to build that system end-to-end — from encoding compliance rules as enforceable policy objects, to building the detection layer, to wiring autonomous remediation actions that leave a complete, auditor-readable record of every decision made.

From Compliance Checklists to Machine-Readable Policy Objects

The foundational shift in autonomous compliance is treating regulatory requirements not as PDF documents reviewed quarterly, but as versioned, structured objects that the platform can evaluate programmatically at any time. A policy object answers three questions: what condition must be true, what evidence proves it is true, and what action restores compliance when it is not.

The schema for a policy object should be stable enough to version in Git and expressive enough to generate both detection queries and remediation procedures from the same source.

# Policy object schema (Python dataclass, stored as YAML in Git)
from dataclasses import dataclass, field
from typing import List, Optional
from enum import Enum

class Severity(Enum):
    CRITICAL = "critical"
    HIGH     = "high"
    MEDIUM   = "medium"
    LOW      = "low"

class RemediationMode(Enum):
    AUTO     = "auto"        # system acts immediately
    APPROVE  = "approve"     # system proposes, human approves
    ALERT    = "alert"       # system only notifies

@dataclass
class CompliancePolicy:
    policy_id:          str
    framework:          str          # "PCI-DSS", "HIPAA", "SOC2", "GDPR"
    control_ref:        str          # e.g. "PCI-DSS 8.6.1"
    description:        str
    target_scope:       List[str]    # ["production", "staging-pii"]
    detection_query:    str          # SQL or PromQL
    detection_platform: str          # "sqlserver", "prometheus"
    severity:           Severity
    remediation_mode:   RemediationMode
    remediation_action: str          # function name in remediation registry
    evidence_query:     str          # query that produces audit evidence
    sla_minutes:        int          # time to remediate before escalation
    owner:              str
    tags:               List[str] = field(default_factory=list)

A YAML representation of a real policy under PCI-DSS 8.6.1 (system account password management) might look like this:

policy_id: pci-8-6-1-sqlserver-default-logins
framework: PCI-DSS
control_ref: "PCI-DSS 8.6.1"
description: "No SQL Server login may retain a default, blank, or common password in production"
target_scope: ["production"]
detection_query: |
  SELECT name FROM sys.sql_logins
  WHERE is_disabled = 0
    AND (is_policy_checked = 0
         OR PWDCOMPARE(N'Password123', password_hash) = 1
         OR PWDCOMPARE(N'sa', password_hash) = 1)
detection_platform: sqlserver
severity: critical
remediation_mode: auto
remediation_action: rotate_default_password
evidence_query: |
  SELECT name, is_policy_checked, is_expiration_checked,
         SYSUTCDATETIME() as checked_at
  FROM sys.sql_logins WHERE is_disabled = 0
sla_minutes: 15
owner: platform-security@company.com
tags: ["pci", "authentication", "credentials"]

This structure means every compliance check is a first-class, testable artifact. It can be linted for completeness, loaded into a policy engine at startup, and every evaluation is traceable back to a specific version in your policy repository. When the auditor asks "how do you enforce PCI-DSS 8.6.1?", the answer is a Git commit hash.

The policy registry itself should live in a table structure that supports efficient querying by framework, scope, and severity — the compliance loop pulls active policies from this registry on each evaluation cycle.

-- Policy registry table
CREATE TABLE compliance_policies (
    policy_id           NVARCHAR(200) PRIMARY KEY,
    framework           NVARCHAR(50)  NOT NULL,
    control_ref         NVARCHAR(100) NOT NULL,
    description         NVARCHAR(MAX) NOT NULL,
    target_scope        NVARCHAR(MAX) NOT NULL,  -- JSON array stored as string
    detection_query     NVARCHAR(MAX) NOT NULL,
    detection_platform  NVARCHAR(50)  NOT NULL
                        CHECK (detection_platform IN ('sqlserver','prometheus')),
    severity            NVARCHAR(20)  NOT NULL
                        CHECK (severity IN ('critical','high','medium','low')),
    remediation_mode    NVARCHAR(20)  NOT NULL
                        CHECK (remediation_mode IN ('auto','approve','alert')),
    remediation_action  NVARCHAR(200) NOT NULL,
    evidence_query      NVARCHAR(MAX) NOT NULL,
    sla_minutes         INT           NOT NULL DEFAULT 60,
    owner               NVARCHAR(200) NOT NULL,
    tags                NVARCHAR(MAX) NULL,      -- JSON array
    is_active           BIT           NOT NULL DEFAULT 1,
    version             INT           NOT NULL DEFAULT 1,
    last_modified       DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    modified_by         NVARCHAR(200) NOT NULL DEFAULT SYSTEM_USER
);

CREATE TABLE compliance_findings (
    finding_id          BIGINT IDENTITY(1,1) PRIMARY KEY,
    policy_id           NVARCHAR(200) NOT NULL
                        REFERENCES compliance_policies (policy_id),
    detected_at         DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    target_database     NVARCHAR(200)  NOT NULL,
    target_host         NVARCHAR(200)  NOT NULL,
    violation_detail    NVARCHAR(MAX)  NOT NULL,  -- JSON
    severity            NVARCHAR(20)   NOT NULL,
    status              NVARCHAR(30)   NOT NULL DEFAULT 'open'
                        CHECK (status IN ('open','remediating','resolved',
                                          'suppressed','escalated')),
    remediation_started DATETIMEOFFSET NULL,
    remediation_result  NVARCHAR(MAX)  NULL,      -- JSON
    resolved_at         DATETIMEOFFSET NULL,
    sla_deadline        AS (DATEADD(MINUTE, sla_minutes, detected_at)) PERSISTED,
    sla_minutes         INT            NOT NULL
);

CREATE INDEX IX_findings_status ON compliance_findings (status, detected_at DESC);
CREATE INDEX IX_findings_sla    ON compliance_findings (sla_deadline)
    WHERE status = 'open';

The separation of detection_query from evidence_query is intentional: the detection query is optimized for fast violation identification (it may return only violating rows), while the evidence query produces the full snapshot that goes into the audit report. Running the evidence query only at finding time and at resolution time keeps audit storage manageable without sacrificing completeness.

The Compliance Detection Loop: Continuous Evaluation Architecture

A compliance system that runs once per day is not autonomous — it is a scheduled report. An autonomous system evaluates policies on a cadence proportional to severity: critical policies scan every one to five minutes, high-severity policies every fifteen, medium and low every hour. The detection loop is the engine that makes this happen.

The loop architecture has four components: the policy scheduler (determines which policies are due for evaluation), the query executor (runs detection queries against each registered database), the finding processor (compares results against open findings to detect new violations and resolutions), and the action dispatcher (routes new findings to the remediation engine or approval workflow based on remediation mode).

graph LR
    A[Policy Registry] --> B[Policy Scheduler]
    B -->|due by cadence| C[Query Executor]
    C -->|violations| D[Finding Processor]
    D -->|new finding, fingerprinted| E[Action Dispatcher]
    D -->|no longer violating| F[Auto-resolve finding]
    E -->|mode: auto| G[Remediation Engine]
    E -->|mode: approve| H[Approval Workflow]
    E -->|mode: alert| I[Notify only]
    G --> J[Remediation Audit Log]
    H -->|approved or SLA breach| G

*The continuous compliance loop: cadence is severity-proportional, every finding is fingerprinted for idempotency, and remediation mode — not technical capability — decides whether the system acts, asks, or just informs.*

# compliance_loop.py — core detection loop
import asyncio
import asyncpg
import logging
from datetime import datetime, timezone
from typing import Dict, List, Any
from policy_registry import PolicyRegistry
from finding_processor import FindingProcessor
from action_dispatcher import ActionDispatcher

logger = logging.getLogger("compliance_loop")

CADENCE_MAP = {
    "critical": 60,      # seconds
    "high":     900,
    "medium":   3600,
    "low":      14400,
}

class ComplianceLoop:
    def __init__(self, registry: PolicyRegistry,
                 processor: FindingProcessor,
                 dispatcher: ActionDispatcher,
                 target_databases: List[Dict]):
        self.registry   = registry
        self.processor  = processor
        self.dispatcher = dispatcher
        self.targets    = target_databases
        self._last_run: Dict[str, datetime] = {}

    async def run_forever(self):
        logger.info("Compliance detection loop started")
        while True:
            policies = await self.registry.get_active_policies()
            now = datetime.now(timezone.utc)

            tasks = []
            for policy in policies:
                last = self._last_run.get(policy.policy_id)
                cadence = CADENCE_MAP[policy.severity]
                if last is None or (now - last).total_seconds() >= cadence:
                    for target in self.targets:
                        if self._scope_matches(policy.target_scope, target["env"]):
                            tasks.append(
                                self._evaluate_policy(policy, target, now)
                            )
                            self._last_run[policy.policy_id] = now

            if tasks:
                results = await asyncio.gather(*tasks, return_exceptions=True)
                for r in results:
                    if isinstance(r, Exception):
                        logger.error("Evaluation error: %s", r)

            await asyncio.sleep(10)  # tight loop; cadence enforcement is internal

    async def _evaluate_policy(self, policy, target: Dict, eval_time: datetime):
        try:
            violations = await self._run_detection_query(policy, target)
            await self.processor.process(
                policy=policy,
                target=target,
                violations=violations,
                eval_time=eval_time
            )
        except Exception as e:
            logger.error("Policy %s failed on %s: %s",
                         policy.policy_id, target["host"], e)
            raise

    async def _run_detection_query(self, policy, target: Dict) -> List[Any]:
        if policy.detection_platform == "sqlserver":
            # pyodbc path, called synchronously in executor
            return await asyncio.get_event_loop().run_in_executor(
                None, self._run_sqlserver_query,
                policy.detection_query, target
            )
        return []

    @staticmethod
    def _scope_matches(scope_list: List[str], env: str) -> bool:
        return env in scope_list or "all" in scope_list

The finding processor is the component responsible for idempotency — it must not create duplicate findings for a violation that is already open, and it must automatically resolve findings when the detection query no longer returns the violating rows.

-- Finding processor upsert — SQL Server equivalent
-- Insert new finding if not already open
INSERT INTO compliance_findings
    (policy_id, target_database, target_host,
     violation_detail, severity, status, sla_minutes)
SELECT
    @policy_id, @target_db, @target_host,
    @violation_detail, @severity, 'open', @sla_minutes
WHERE NOT EXISTS (
    SELECT 1 FROM compliance_findings
    WHERE policy_id       = @policy_id
      AND target_database = @target_db
      AND target_host     = @target_host
      AND JSON_VALUE(violation_detail, '$.fingerprint')
            = JSON_VALUE(@violation_detail, '$.fingerprint')
      AND status IN ('open', 'remediating')
);

-- Auto-resolve cleared findings
UPDATE compliance_findings
SET    status      = 'resolved',
       resolved_at = SYSDATETIMEOFFSET(),
       remediation_result = JSON_MODIFY('{}', '$.resolution', 'auto_resolved')
WHERE  policy_id       = @policy_id
  AND  target_database = @target_db
  AND  target_host     = @target_host
  AND  status IN ('open', 'remediating')
  AND  JSON_VALUE(violation_detail, '$.fingerprint')
         NOT IN (SELECT value FROM OPENJSON(@current_fingerprints));

The fingerprint approach deserves emphasis. Each violation row produced by a detection query must be reduced to a stable string key (typically a hash of the identifying fields — a username, a table name, a setting name) before comparison. Without fingerprinting, every evaluation cycle would generate spurious new findings for violations already in flight, and auto-resolution logic would fire incorrectly. The fingerprint is computed in the finding processor before writing to the database, not inside the SQL.

SLA enforcement runs as a separate, lightweight background coroutine that wakes every sixty seconds and promotes any open finding past its sla_deadline to escalated, then fires the escalation webhook:

async def sla_watchdog(pool, escalation_webhook: str):
    """Promote overdue open findings to escalated and notify."""
    import aiohttp, json
    async with pool.acquire() as conn:
        overdue = await conn.fetch("""
            UPDATE compliance_findings
            SET    status = 'escalated'
            WHERE  status = 'open'
              AND  sla_deadline < NOW()
            RETURNING finding_id, policy_id, target_host,
                      severity, violation_detail, detected_at, sla_deadline
        """)
    if overdue:
        payload = {
            "alert": "compliance_sla_breach",
            "count": len(overdue),
            "findings": [dict(r) for r in overdue]
        }
        async with aiohttp.ClientSession() as session:
            await session.post(escalation_webhook,
                               json=payload,
                               timeout=aiohttp.ClientTimeout(total=10))
        logger.warning("Escalated %d overdue compliance findings", len(overdue))

Autonomous Remediation: What Gets Auto-Fixed and What Doesn't

Not all compliance violations should be autonomously remediated. The remediation mode embedded in each policy object encodes the decision: auto means the system corrects the violation immediately and records what it did; approve means it opens an approval request and waits up to the SLA deadline before either escalating or self-approving based on risk tier; alert means it only notifies.

The remediation registry maps action names to Python callables. Each callable receives the finding, the target database connection parameters, and the full policy object. It must return a RemediationResult that includes success/failure, the SQL or commands executed, and enough context that an auditor could reconstruct the action from the result alone.

The set of actions that are safe to automate fully (auto mode) across production systems is narrower than intuition suggests. Good candidates for full automation:

  • → Revoking excessive privileges added to service accounts outside the change window
  • → Disabling login for accounts inactive beyond the policy threshold
  • → Forcing TLS requirement at the session level for connections detected without encryption
  • → Rotating credentials that match default or empty password patterns
  • → Re-enabling audit logging extensions that have been dropped or disabled
  • → Reclassifying data sensitivity labels on newly discovered columns containing PII patterns

    • Actions that warrant approve mode even when technically automatable:

  • → Dropping database objects (even temp tables containing unmasked PII)
  • → Changing authentication configuration at the cluster level
  • → Modifying role membership for roles used by application service accounts
  • → Encryption-at-rest changes that require restart or key rotation

    • The following shows a full remediation action for one of the highest-frequency PCI-DSS violations: an account with excessive login privileges that was provisioned outside the IAM workflow.

    -- Remediation: disable unauthorized login — SQL Server equivalent
BEGIN TRANSACTION;

    -- Capture current state
    INSERT INTO compliance_remediation_audit
        (action, login_name, old_state, new_state, executed_at, policy_id)
    SELECT
        'DISABLE_LOGIN',
        @login_name,
        (SELECT is_disabled, create_date, modify_date
         FROM sys.server_principals
         WHERE name = @login_name
         FOR JSON PATH, WITHOUT_ARRAY_WRAPPER),
        '{"is_disabled": true}',
        SYSDATETIMEOFFSET(),
        @policy_id
    FROM sys.server_principals
    WHERE name = @login_name;

    -- Execute remediation
    DECLARE @sql NVARCHAR(500) =
        N'ALTER LOGIN ' + QUOTENAME(@login_name) + N' DISABLE';
    EXEC sp_executesql @sql;

    -- Kill active sessions for this login
    DECLARE @session_id INT;
    DECLARE session_cursor CURSOR FOR
        SELECT session_id FROM sys.dm_exec_sessions
        WHERE login_name = @login_name;

    OPEN session_cursor;
    FETCH NEXT FROM session_cursor INTO @session_id;
    WHILE @@FETCH_STATUS = 0
    BEGIN
        DECLARE @kill_sql NVARCHAR(50) = N'KILL ' + CAST(@session_id AS NVARCHAR);
        EXEC sp_executesql @kill_sql;
        FETCH NEXT FROM session_cursor INTO @session_id;
    END;
    CLOSE session_cursor;
    DEALLOCATE session_cursor;

COMMIT TRANSACTION;

    Notice that both remediation scripts write to a compliance_remediation_audit table before executing the change. This is non-negotiable for autonomous systems: the audit record must exist even if the remediation command partially fails. The finding's remediation_result column then receives the full result including the audit record ID, so any auditor can trace a finding through its detection, approval, remediation, and evidence chain as a linked set of records rather than isolated log lines.

    The compliance_remediation_audit table schema supports this linkage:

    CREATE TABLE compliance_remediation_audit (
    audit_id        BIGINT IDENTITY(1,1) PRIMARY KEY,
    finding_id      BIGINT REFERENCES compliance_findings (finding_id),
    policy_id       NVARCHAR(200) NOT NULL
                    REFERENCES compliance_policies (policy_id),
    action          NVARCHAR(100) NOT NULL,
    login_name      NVARCHAR(200) NULL,
    old_state       NVARCHAR(MAX) NULL,   -- JSON
    new_state       NVARCHAR(MAX) NULL,   -- JSON
    executed_at     DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    executed_by     NVARCHAR(200) NOT NULL DEFAULT SYSTEM_USER,

CREATE INDEX IX_remediation_audit_policy
    ON compliance_remediation_audit (policy_id, executed_at DESC);

    PII Detection and Classification as a Continuous Policy

    Data classification — knowing which columns contain personally identifiable information — is not a one-time labeling exercise. Schemas evolve, new tables appear during feature deployments, and developers occasionally copy a production column into a reporting view without triggering any security review. Autonomous compliance treats classification as a standing policy that runs on every schema change event and on a periodic sweep of all unlabeled columns.

    The detection approach combines two techniques: pattern matching on column names and statistical sampling of column contents. Name-based detection is fast and catches the obvious cases (email, ssn, dob, credit_card_number). Content-based detection using regex sampling catches columns with opaque names (col_7, field_b, attr_value) that happen to hold PII.

    PII column name detection query:

    -- Detection query for compliance policy: pii-unlabeled-columns
SELECT
    SCHEMA_NAME(t.schema_id)        AS schema_name,
    t.name                          AS table_name,
    c.name                          AS column_name,
    tp.name                         AS data_type,
    CONVERT(NVARCHAR(64),
        HASHBYTES('MD5',
            SCHEMA_NAME(t.schema_id) + '.' + t.name + '.' + c.name),
        2)                          AS fingerprint
FROM sys.columns c
JOIN sys.tables  t  ON t.object_id  = c.object_id
JOIN sys.types   tp ON tp.user_type_id = c.user_type_id
WHERE
    -- Name-pattern match
    c.name LIKE '%email%'
    OR c.name LIKE '%phone%'
    OR c.name LIKE '%mobile%'
    OR c.name LIKE '%ssn%'
    OR c.name LIKE '%social%'
    OR c.name LIKE '%tax_id%'
    OR c.name LIKE '%passport%'
    OR c.name LIKE '%dob%'
    OR c.name LIKE '%birth%'
    OR c.name LIKE '%credit_card%'
    OR c.name LIKE '%card_number%'
    OR c.name LIKE '%cvv%'
    OR c.name LIKE '%first_name%'
    OR c.name LIKE '%last_name%'
    OR c.name LIKE '%full_name%'
    OR c.name LIKE '%salary%'
    OR c.name LIKE '%account_num%'
    OR c.name LIKE '%iban%'
-- Not already labeled via SQL Server Data Classification
AND NOT EXISTS (
    SELECT 1 FROM sys.sensitivity_classifications sc
    WHERE sc.object_id  = c.object_id
      AND sc.column_id  = c.column_id
);

    Content-based sampling runs as a Python callable in the remediation registry rather than as a pure SQL query, because it needs to issue per-table sample queries dynamically and apply regex matching in Python where the regex library is significantly more capable:

    # pii_content_sampler.py
import re
import asyncpg
from typing import List, Dict, Any

PII_PATTERNS = {
    "email":       re.compile(r'\b[A-Za-z0-9._%+\-]+@[A-Za-z0-9.\-]+\.[A-Z]{2,}\b', re.I),
    "ssn":         re.compile(r'\b\d{3}-\d{2}-\d{4}\b'),
    "credit_card": re.compile(r'\b(?:4\d{12}(?:\d{3})?|5[1-5]\d{14}|3[47]\d{13})\b'),
    "ip_address":  re.compile(r'\b(?:\d{1,3}\.){3}\d{1,3}\b'),
    "phone_us":    re.compile(r'\b(?:\+1[-.\s]?)?\(?\d{3}\)?[-.\s]?\d{3}[-.\s]?\d{4}\b'),
    "iban":        re.compile(r'\b[A-Z]{2}\d{2}[A-Z0-9]{4}\d{7}([A-Z0-9]?){0,16}\b'),
}

async def sample_column_for_pii(
    conn: asyncpg.Connection,
    schema: str,
    table: str,
    column: str,
    sample_size: int = 200
) -> List[str]:
    """
    Return list of PII type names detected in a random column sample.
    Returns empty list if no PII patterns found.
    """
    try:
        rows = await conn.fetch(
            f'SELECT {column}::TEXT FROM {schema}.{table} '
            f'TABLESAMPLE SYSTEM(5) LIMIT $1',
            sample_size
        )
    except Exception:
        # Column may not be castable to TEXT or table may be empty
        return []

    values = [r[0] for r in rows if r[0] is not None]
    if not values:
        return []

    detected = []
    for pii_type, pattern in PII_PATTERNS.items():
        match_count = sum(1 for v in values if pattern.search(v))
        # Require at least 3% match rate to avoid false positives on
        # columns that happen to contain one incidental matching string
        if match_count / len(values) >= 0.03:
            detected.append(pii_type)
    return detected

    When the classification policy finds an unlabeled PII column, the remediation action (in approve mode for schema-level changes) applies the appropriate sensitivity label and writes a classification record:

    -- Apply sensitivity label via built-in Data Classification
ADD SENSITIVITY CLASSIFICATION TO
    [schema_name].[table_name].[column_name]
WITH (
    LABEL        = 'Highly Confidential',
    INFORMATION_TYPE = 'Personal',
    RANK         = HIGH
);

-- Write to classification registry
MERGE data_classification_registry AS tgt
USING (VALUES (@schema_name, @table_name, @column_name,
               @pii_type, 'high', @detection_method, SYSDATETIMEOFFSET(), @policy_id))
    AS src (schema_name, table_name, column_name,
            pii_type, sensitivity, detection_method, classified_at, policy_id)
ON  tgt.schema_name = src.schema_name
AND tgt.table_name  = src.table_name
AND tgt.column_name = src.column_name
WHEN MATCHED THEN
    UPDATE SET pii_type         = src.pii_type,
               sensitivity      = src.sensitivity,
               detection_method = src.detection_method,
               classified_at    = src.classified_at
WHEN NOT MATCHED THEN
    INSERT (schema_name, table_name, column_name,
            pii_type, sensitivity, detection_method, classified_at, policy_id)
    VALUES (src.schema_name, src.table_name, src.column_name,
            src.pii_type, src.sensitivity, src.detection_method,
            src.classified_at, src.policy_id);

    Privilege Drift Detection and the Least-Privilege Enforcement Loop

    Privilege accumulation is among the most common compliance findings in real database environments. Service accounts gain SELECT on a new table for a one-time migration and the grant is never revoked. A developer is given temporary DBA access to investigate an incident and the elevated role persists for months. The autonomous privilege drift engine maintains a desired-state model of every role and periodically compares it against actual state, generating findings for every deviation.

    The desired state model is encoded in a privilege baseline table: the set of grants that are explicitly authorized for each role on each database object, with the authorization event that approved them.

    CREATE TABLE privilege_baseline (
    baseline_id     BIGINT IDENTITY(1,1) PRIMARY KEY,
    role_name       NVARCHAR(200) NOT NULL,
    object_schema   NVARCHAR(200) NOT NULL,
    object_name     NVARCHAR(200) NOT NULL,
    object_type     NVARCHAR(50)  NOT NULL CHECK (object_type IN
                    ('table','view','procedure','function','schema','database')),
    privilege_type  NVARCHAR(50)  NOT NULL,
    granted_by      NVARCHAR(200) NOT NULL,
    approved_by     NVARCHAR(200) NOT NULL,
    valid_from      DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    valid_until     DATETIMEOFFSET NULL,
    is_active       BIT NOT NULL DEFAULT 1,
    UNIQUE (role_name, object_schema, object_name, privilege_type)
);

-- Drift detection: object permissions present in sys.database_permissions
-- but absent from the baseline
CREATE OR ALTER VIEW privilege_drift AS
SELECT
    dp.grantee_principal_id,
    USER_NAME(dp.grantee_principal_id)  AS role_name,
    OBJECT_SCHEMA_NAME(dp.major_id)     AS object_schema,
    OBJECT_NAME(dp.major_id)            AS object_name,
    dp.type_desc                         AS privilege_type,
    CONVERT(NVARCHAR(64),
        HASHBYTES('MD5',
            USER_NAME(dp.grantee_principal_id)
            + ISNULL(OBJECT_SCHEMA_NAME(dp.major_id), '')
            + ISNULL(OBJECT_NAME(dp.major_id), '')
            + dp.type_desc), 2)          AS fingerprint
FROM sys.database_permissions dp
WHERE dp.state IN ('G', 'W')   -- GRANT or GRANT WITH GRANT OPTION
  AND NOT EXISTS (
        SELECT 1 FROM privilege_baseline pb
        WHERE pb.role_name      = USER_NAME(dp.grantee_principal_id)
          AND pb.object_schema  = ISNULL(OBJECT_SCHEMA_NAME(dp.major_id), '')
          AND pb.object_name    = ISNULL(OBJECT_NAME(dp.major_id), '')
          AND pb.privilege_type = dp.type_desc
          AND pb.is_active      = 1
          AND (pb.valid_until IS NULL OR pb.valid_until > SYSDATETIMEOFFSET())
  );

    The remediation action for privilege drift in auto mode revokes the unauthorized grant and records the pre-remediation state. For approve mode, the system writes a pending approval record and the remediation is held until a human approves or the SLA deadline triggers escalation.

    One practical detail: the revocation must be idempotent. If the detection query finds a privilege, the remediation revokes it, but the next evaluation cycle runs before the revocation propagates fully (rare but possible in federated environments), the remediation must not error on a double-revoke. SQL Server's REVOKE statement is safe to run when the privilege does not exist — it simply has no effect.

    Generating Audit Evidence Packages

    Compliance auditors do not inspect your findings table directly. They expect evidence packages: timestamped, signed collections of queries and their outputs that demonstrate a control was operating continuously during the audit period. The autonomous system must be able to generate these on demand.

    An evidence package for a single control contains:

    1. The policy definition as it existed during the audit period (from the policy registry with version history)

    2. A timeline of every evaluation: timestamp, query executed, rows returned, evaluation duration

    3. All findings raised during the period with their status progression

    4. All remediation actions taken with pre- and post-state

    5. Any SLA breaches and their escalation records

    6. The evidence query output at the time of each finding

    The evaluation log table supports items 2 and 6:

    CREATE TABLE compliance_evaluation_log (
    log_id          BIGINT IDENTITY(1,1) PRIMARY KEY,
    policy_id       NVARCHAR(200) NOT NULL
                    REFERENCES compliance_policies (policy_id),
    evaluated_at    DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    target_database NVARCHAR(200) NOT NULL,
    target_host     NVARCHAR(200) NOT NULL,
    rows_returned   INT NOT NULL,
    violation_count INT NOT NULL,
    duration_ms     INT NOT NULL,
    evidence_snapshot NVARCHAR(MAX) NULL,  -- JSON
    error_detail    NVARCHAR(MAX) NULL
);

CREATE INDEX IX_eval_log_policy_time
    ON compliance_evaluation_log (policy_id, evaluated_at DESC);

    The evidence package generator queries these tables and assembles a structured report. For a typical SOC 2 audit covering a ninety-day period, this function produces a JSON document that maps directly onto the auditor's control testing worksheet:

    # evidence_package_generator.py
import asyncpg
import json
from datetime import datetime, timezone
from typing import Dict, Any

async def generate_evidence_package(
    pool: asyncpg.Pool,
    policy_id: str,
    period_start: datetime,
    period_end: datetime
) -> Dict[str, Any]:
    async with pool.acquire() as conn:
        # 1. Policy definition (latest version in effect during period)
        policy = await conn.fetchrow("""
            SELECT * FROM compliance_policies WHERE policy_id = $1
        """, policy_id)

        # 2. Evaluation timeline
        evaluations = await conn.fetch("""
            SELECT evaluated_at, target_host, rows_returned,
                   violation_count, duration_ms, evidence_snapshot, error_detail
            FROM compliance_evaluation_log
            WHERE policy_id   = $1
              AND evaluated_at BETWEEN $2 AND $3
            ORDER BY evaluated_at
        """, policy_id, period_start, period_end)

        # 3. Findings during the period
        findings = await conn.fetch("""
            SELECT finding_id, detected_at, target_host, violation_detail,
                   status, remediation_started, resolved_at,
                   sla_deadline, remediation_result
            FROM compliance_findings
            WHERE policy_id   = $1
              AND detected_at BETWEEN $2 AND $3
            ORDER BY detected_at
        """, policy_id, period_start, period_end)

        # 4. Remediation actions
        remediations = await conn.fetch("""
            SELECT ra.audit_id, ra.finding_id, ra.action,
                   ra.old_state, ra.new_state, ra.executed_at,
                   ra.executed_by, ra.success, ra.error_detail
            FROM compliance_remediation_audit ra
            JOIN compliance_findings f ON f.finding_id = ra.finding_id
            WHERE f.policy_id   = $1
              AND ra.executed_at BETWEEN $2 AND $3
            ORDER BY ra.executed_at
        """, policy_id, period_start, period_end)

        # 5. SLA summary
        sla_stats = await conn.fetchrow("""
            SELECT
                COUNT(*)                                        AS total_findings,
                SUM(CASE WHEN status = 'resolved' THEN 1 END)  AS resolved,
                SUM(CASE WHEN status = 'escalated' THEN 1 END) AS escalated,
                AVG(EXTRACT(EPOCH FROM (resolved_at - detected_at))/60)
                                                               AS avg_resolution_minutes,
                MAX(EXTRACT(EPOCH FROM (resolved_at - detected_at))/60)
                                                               AS max_resolution_minutes
            FROM compliance_findings
            WHERE policy_id   = $1
              AND detected_at BETWEEN $2 AND $3
        """, policy_id, period_start, period_end)

    return {
        "package_generated_at": datetime.now(timezone.utc).isoformat(),
        "audit_period": {
            "start": period_start.isoformat(),
            "end":   period_end.isoformat()
        },
        "policy": dict(policy) if policy else None,
        "evaluation_summary": {
            "total_evaluations": len(evaluations),
            "evaluations_with_violations": sum(
                1 for e in evaluations if e["violation_count"] > 0
            ),
            "evaluation_errors": sum(
                1 for e in evaluations if e["error_detail"]
            ),
        },
        "evaluations":   [dict(e) for e in evaluations],
        "findings":      [dict(f) for f in findings],
        "remediations":  [dict(r) for r in remediations],
        "sla_summary":   dict(sla_stats) if sla_stats else {},
    }

    The output of generate_evidence_package can be signed with a platform key and stored in immutable object storage (S3 Object Lock, Azure Blob immutability policies) the moment it is generated. This produces a tamper-evident audit trail that can be presented to auditors without involving any engineer in the evidence collection process — which itself satisfies an independence requirement in several audit frameworks.

    Cross-Framework Policy Inheritance and Deduplication

    A mature compliance program covers multiple frameworks simultaneously. PCI-DSS, HIPAA, and SOC 2 all require activity logging, encryption in transit, and access control reviews, but they phrase the requirement differently and assign different SLA expectations. Maintaining separate policy objects for each framework's version of "enable TLS" leads to three detection queries running against the same target, generating three findings for the same violation, and creating confusion in the remediation workflow.

    The policy inheritance model resolves this by distinguishing between the canonical technical control and the framework citations that reference it. A single canonical policy handles detection and remediation; framework mappings record which controls satisfy which framework requirements.

    CREATE TABLE policy_framework_mappings (
    mapping_id      BIGINT IDENTITY(1,1) PRIMARY KEY,
    policy_id       NVARCHAR(200) NOT NULL
                    REFERENCES compliance_policies (policy_id),
    framework       NVARCHAR(50)  NOT NULL,
    control_ref     NVARCHAR(100) NOT NULL,
    requirement_text NVARCHAR(MAX) NOT NULL,
    UNIQUE (policy_id, framework, control_ref)
);

INSERT INTO policy_framework_mappings
    (policy_id, framework, control_ref, requirement_text)
VALUES
    ('tls-required-ss', 'PCI-DSS', 'PCI-DSS 4.2.1',
     'Strong cryptography used to safeguard PAN during transmission'),
    ('tls-required-ss', 'HIPAA',   'HIPAA 164.312(e)(1)',
     'Technical security measures to guard against unauthorized access'),
    ('tls-required-ss', 'SOC2',    'CC6.7',
     'Transmits data using encryption and authenticated protocols'),
    ('tls-required-ss', 'ISO27001','ISO27001 A.10.1',
     'Cryptographic controls applied to protect information in transit');

    When the evidence package generator runs for a specific framework, it queries the mapping table to find all canonical policies that contribute to that framework, then assembles evidence across all of them. A single finding on tls-required-pg surfaces in the PCI-DSS, HIPAA, SOC 2, and ISO 27001 evidence packages simultaneously, because the mapping table links them. Engineers receive one finding, one remediation task, and one resolution event — the multi-framework coverage is a reporting-layer concern, not a detection-layer concern.

    Change Window Enforcement as a Policy Class

    Compliance frameworks that require change management (SOC 2 CC8.1, ITIL-aligned controls, certain PCI-DSS requirements) impose restrictions on when schema and configuration changes may occur. The autonomous system enforces change windows not only by blocking out-of-window DDL (covered in Chapter 28), but by detecting DDL that did execute outside an approved window and raising it as a compliance finding.

    The DDL audit detection query requires that DDL event logging is already active:

    -- Detection query: DDL executed outside approved change windows
-- Assumes SQL Server Audit or an event trigger writes to ddl_audit_log
SELECT
    event_time,
    user_name,
    object_type,
    object_name,
    statement,
    CONVERT(NVARCHAR(64),
        HASHBYTES('MD5',
            CONVERT(NVARCHAR(50), event_time, 126)
            + user_name + object_name), 2)  AS fingerprint
FROM ddl_audit_log
WHERE event_time >= DATEADD(HOUR, -1, SYSDATETIMEOFFSET())
  AND NOT (
    -- Approved change windows: weekdays 22:00–02:00 UTC
    DATEPART(WEEKDAY, event_time AT TIME ZONE 'UTC') BETWEEN 2 AND 6
    AND (
        DATEPART(HOUR, event_time AT TIME ZONE 'UTC') >= 22
        OR DATEPART(HOUR, event_time AT TIME ZONE 'UTC') < 2
    )
  )
  AND user_name NOT IN (
        SELECT service_account FROM approved_automation_accounts
        WHERE ddl_allowed_anytime = 1
  );

    Because DDL outside change windows cannot typically be undone (the schema change already happened), the remediation mode for this policy class is almost always alert or approve, with the remediation action being a forced review ticket rather than a database operation. The compliance finding serves as the immutable record that the deviation occurred, regardless of whether the resulting schema state is ultimately accepted or rolled back.

    Key Takeaways

  • → Policy objects are the unit of compliance work. Encoding each regulatory requirement as a versioned, machine-readable object with a detection query, evidence query, remediation action, and SLA creates a complete, auditable compliance control that can be tested, deployed, and updated through standard engineering workflows rather than manual procedures.
  • → Idempotent fingerprinting prevents finding noise. Every violation row produced by a detection query must be reduced to a stable fingerprint before writing to the findings table. Without fingerprinting, repeated evaluation cycles generate duplicate findings for active violations and misfire auto-resolution logic, destroying the reliability of the detection layer.
  • → Remediation mode is a risk classification, not a technical limitation. The distinction between auto, approve, and alert is a deliberate risk decision encoded in the policy object — not a reflection of what the system is technically capable of doing. Privilege revocations and credential rotations can be automated safely; object drops and cluster-level configuration changes warrant human review even when they are technically straightforward to script.
  • → Cross-framework deduplication belongs in the mapping layer, not the detection layer. A single canonical policy detecting one technical condition satisfies multiple regulatory frameworks simultaneously. Maintaining separate detection queries per framework multiplies operational noise without adding control coverage. The evidence package generator, not the detection loop, is responsible for rendering a finding against each applicable framework.
  • → Evidence packages must be generated autonomously and stored immutably at the moment of collection. An audit evidence system that requires an engineer to manually gather query outputs, sign them, and submit them introduces both latency and integrity risk. Evidence generated programmatically from the evaluation log, signed with a platform key, and committed to immutable object storage the moment it is produced satisfies the independence and tamper-evidence requirements that modern compliance auditors expect from automated control systems.
