Chapter 20: Autonomous Threat Detection

Security in a self-managing database platform cannot depend on a human analyst reviewing logs at the end of a shift. By the time an intrusion is confirmed, a privilege escalation has propagated, or an exfiltration query has run to completion, the damage is already bounded only by how long the attack went undetected. This chapter builds the architecture for a database system that detects, classifies, and responds to threats autonomously — closing the gap between signal and action from hours to seconds. The patterns here cover behavioral baselining, anomaly scoring, automated containment, and integration with broader security pipelines, all grounded in what SQL Server actually exposes at the engine level.

20.1 The Threat Surface at the Engine Layer: What Autonomous Systems Must Monitor

Most security tooling lives above the database — WAF rules, network ACLs, SIEM ingestion of application logs. These are necessary but insufficient. An autonomous threat detection system must instrument the database engine itself because the most dangerous attacks succeed after the perimeter has already been crossed: stolen credentials, compromised application accounts, malicious insiders, or injected queries that bypass all upstream filtering.

The threat surface that matters for autonomous detection divides into four observable planes:

Authentication and session plane. Who is connecting, from where, at what time, using which authentication method. SQL Server surfaces this through Extended Events and the sys.dm_exec_sessions DMV. An autonomous system tracks not just raw connection counts but behavioral fingerprints: which application users connect from which hosts, at what hour distribution, with what typical session duration.

Query execution plane. What SQL is running. This is where SQL injection, data exfiltration, and reconnaissance manifest. SQL Server Query Store captures normalized query text with execution statistics. The autonomous system must detect structural anomalies — queries with unusual UNION counts, bulk SELECT * against sensitive tables, absence of WHERE clauses on large tables, and EXECUTE/xp_cmdshell patterns.

Privilege and schema mutation plane. DDL changes, role grants, ownership transfers. These are low-frequency operations in production that almost never happen outside of planned change windows. Any CREATE USER, GRANT, ALTER TABLE, DROP operation occurring outside of a sanctioned window is a high-confidence threat signal.

Data volume plane. Row counts and byte volumes returned by queries. A support engineer querying a customer table and returning 50 rows is normal. The same query returning 2 million rows is not. SQL Server does not expose per-query row return counts in a single DMV, so this plane requires instrumentation at the connection pooler or proxy layer — SQL Server Audit, or an eBPF-based collector at the network layer.

The autonomous threat detection system must monitor all four planes simultaneously, correlate signals across them, and produce a threat score that triggers graduated responses. A single anomalous signal is noise. The same session showing unusual connection time, a novel query pattern, and a high row-return volume simultaneously is an incident.

20.2 Behavioral Baselining: Building the Normal Model Autonomously

Detection requires a model of normal. Static rule systems — blacklists of bad query patterns, IP allowlists — fail against sophisticated attackers who operate within the envelope of legitimate access. Behavioral baselining builds a statistical model of normal operation that evolves continuously as the workload changes.

The baseline must be per-identity, not aggregate. The behavior of app_user is not the behavior of reporting_user. The autonomous system maintains a profile per database principal covering:

  • → Typical connection hour distribution (histogram by hour-of-day)
  • → Source host/IP distribution
  • → Average and 99th-percentile query execution time
  • → Query template frequency (normalized Query Store query hash)
  • → Tables accessed per session
  • → Average rows examined and returned

-- Refresh from Query Store
MERGE SecurityBaseline.QueryProfile AS tgt
USING (
    SELECT
        es.login_name,
        qs.query_hash,
        qt.query_sql_text,
        AVG(CAST(rs.avg_rowcount AS FLOAT))        AS avg_rows,
        STDEV(CAST(rs.avg_rowcount AS FLOAT))      AS stddev_rows,
        AVG(rs.avg_duration / 1000.0)              AS avg_duration_ms,
        STDEV(rs.avg_duration / 1000.0)            AS stddev_duration_ms,
        COUNT(*) * 1.0 /
            NULLIF(DATEDIFF(HOUR,
                MIN(rs.last_execution_time),
                MAX(rs.last_execution_time)), 0)   AS calls_per_hour
    FROM sys.query_store_query          qs
    JOIN sys.query_store_query_text     qt ON qt.query_text_id = qs.query_text_id
    JOIN sys.query_store_plan           qp ON qp.query_id      = qs.query_id
    JOIN sys.query_store_runtime_stats  rs ON rs.plan_id       = qp.plan_id
    -- join to current sessions is best-effort; use audit log for persistent mapping
    CROSS JOIN sys.dm_exec_sessions     es
    WHERE es.is_user_process = 1
    GROUP BY es.login_name, qs.query_hash, qt.query_sql_text
) AS src
ON tgt.LoginName = src.login_name
   AND tgt.QueryHash = src.query_hash
WHEN MATCHED THEN UPDATE SET
    AvgRowsReturned  = src.avg_rows,
    StdDevRows       = src.stddev_rows,
    AvgDurationMs    = src.avg_duration_ms,
    StdDevDurationMs = src.stddev_duration_ms,
    CallsPerHour     = src.calls_per_hour,
    LastUpdated      = SYSUTCDATETIME()
WHEN NOT MATCHED THEN INSERT (
    LoginName, QueryHash, QueryText, AvgRowsReturned,
    StdDevRows, AvgDurationMs, StdDevDurationMs,
    CallsPerHour, FirstSeen, LastUpdated
) VALUES (
    src.login_name, src.query_hash, src.query_sql_text,
    src.avg_rows, src.stddev_rows,
    src.avg_duration_ms, src.stddev_duration_ms,
    src.calls_per_hour, SYSUTCDATETIME(), SYSUTCDATETIME()
);

    The baseline refresh runs on a scheduled job — every 6 hours during stable periods, paused during incident response so the attack behavior does not contaminate the model. The autonomous system tracks first_seen to exclude newly observed query templates from scoring until they have accumulated at least 7 days of data; new templates are flagged as novel but not scored as threats until a minimum observation window passes.

    Connection-hour histograms are stored separately as JSON arrays — one cell per hour of the week (168 cells) — with exponential decay weighting so that recent behavior has higher influence than patterns from 90 days ago. The decay parameter (α = 0.05 per day) means the effective half-life is about 14 days, which tracks seasonal workload changes without being so volatile that a week of unusual traffic permanently distorts the model.

    20.3 Real-Time Anomaly Scoring at the Session Level

    With a behavioral baseline in place, the scoring engine evaluates every active session continuously. Scoring runs as a Python process that polls both engines every 30 seconds, computes Z-scores for observed session behavior against the baseline, and produces a composite threat score per session.

    The scoring formula weights four dimensions:

  • → Z_time: How far outside the normal hour distribution this connection falls
  • → Z_rows: Standard deviations above mean row return for the query being executed
  • → Z_query_novelty: Binary flag (0/1) — is this query template absent from the baseline?
  • → Z_volume: Aggregate data scanned in this session vs. the user's historical session average

def z_score(value: float, mean: float, stddev: float) -> float:
    """Return Z-score clamped to [0, 10]; negative deviations are not threats."""
    if stddev is None or stddev < 1e-9:
        return 0.0 if abs(value - mean) < 1e-9 else 5.0  # no variance → novel
    return max(0.0, (value - mean) / stddev)

def hour_distribution_score(hour: int, histogram: list[float]) -> float:
    """
    Score how anomalous this hour is relative to the user's historical distribution.
    Returns 0 (normal) to 10 (never seen at this hour).
    """
    if not histogram or len(histogram) != 168:
        return 2.0   # no data: mildly suspicious
    freq = histogram[hour]
    total = sum(histogram)
    if total < 1e-9:
        return 2.0
    expected = freq / total
    if expected < 0.001:   # less than 0.1% of sessions at this hour
        return 8.0
    if expected < 0.01:
        return 4.0
    return 0.0

def score_session(session: SessionProfile, baseline_row: Optional[dict]) -> ThreatScore:
    components = {}

    if baseline_row is None:
        # Novel user or query — no baseline to compare against
        components["novelty"]  = 6.0
        components["rows"]     = 0.0
        components["exec_ms"]  = 0.0
        components["time"]     = 0.0
    else:
        histogram = json.loads(baseline_row["hour_histogram"] or "[]")
        components["time"]    = hour_distribution_score(session.hour_of_week, histogram)
        components["rows"]    = z_score(
            session.rows_returned,
            baseline_row["avg_rows"]    or 0,
            baseline_row["stddev_rows"] or 0
        )
        components["exec_ms"] = z_score(
            session.exec_ms,
            baseline_row["avg_exec_ms"]    or 0,
            baseline_row["stddev_exec_ms"] or 0
        )
        components["novelty"] = 0.0

    # Weighted composite
    composite = (
        components.get("rows",    0) * 0.40 +
        components.get("time",    0) * 0.25 +
        components.get("exec_ms", 0) * 0.20 +
        components.get("novelty", 0) * 0.15
    )

    return ThreatScore(
        session_id=session.session_id,
        username=session.username,
        composite_score=round(composite, 3),
        components=components
    )

def poll_and_score_mssql(conn, baseline_cache: dict) -> list[ThreatScore]:
    scores = []
    now_dow  = datetime.now(timezone.utc).weekday()    # 0=Mon
    now_hour = datetime.now(timezone.utc).hour
    hour_of_week = now_dow * 24 + now_hour

    with conn.cursor() as cur:
        cur.execute("""
            SELECT
                CAST(r.session_id AS VARCHAR(20)) AS session_id,
                s.login_name                      AS username,
                s.client_net_address              AS client_addr,
                qs.query_hash                     AS query_id,
                0                                 AS rows_returned,   -- enriched separately
                DATEDIFF(MILLISECOND, r.start_time, SYSUTCDATETIME())
                                                  AS exec_ms
            FROM sys.dm_exec_requests r
            JOIN sys.dm_exec_sessions s
              ON s.session_id = r.session_id
            LEFT JOIN sys.dm_exec_query_stats qs
              ON qs.sql_handle = r.sql_handle
            WHERE s.is_user_process = 1
              AND r.session_id > 50
              AND s.login_name NOT IN ('sa', '##MS_PolicyEventProcessingLogin##')
        """)
        cols = [d[0] for d in cur.description]
        rows = cur.fetchall()

    for row in rows:
        r = dict(zip(cols, row))
        session = SessionProfile(
            session_id   = r["session_id"],
            username     = r["username"],
            client_addr  = r["client_addr"] or "unknown",
            query_id     = r["query_id"],
            rows_returned= r["rows_returned"],
            exec_ms      = r["exec_ms"] or 0.0,
            hour_of_week = hour_of_week
        )
        baseline = baseline_cache.get((r["username"], r["query_id"]))
        scores.append(score_session(session, baseline))

    return scores

if __name__ == "__main__":

                dispatch_threat_response(s, "ACT")
            elif s.composite_score >= THREAT_THRESHOLD_WARN:
                dispatch_threat_response(s, "WARN")
        time.sleep(30)

    The scoring loop runs every 30 seconds. It pulls from sys.dm_exec_requests and sys.dm_exec_sessions. The composite score crosses two thresholds: WARN (2.5) triggers alerting to the SIEM and on-call channel; ACT (4.0) triggers autonomous containment actions described in the next section.

    Threshold calibration matters. In the first 30 days after deployment on a new cluster, the system operates in shadow mode — it scores and logs but does not act. The false positive rate is measured as alerts that an operator manually classifies as non-threats. The ACT threshold is tuned upward until the false positive rate drops below 1 per week on steady-state workloads, then autonomous action is enabled.

    20.4 Autonomous Containment: From Detection to Response Without Human Intervention

    Detection without response is just expensive logging. The autonomous containment layer closes the loop: when a threat score crosses the ACT threshold, the system takes a graduated sequence of actions proportional to confidence and risk. The escalation ladder has four levels:

    Level 1 — Rate-limit the session. For scores between 4.0 and 5.5, the system does not terminate the session but reduces its resource access. In SQL Server, this means placing the login in a Resource Governor pool capped at 10% CPU and a low memory grant ratio.

    Level 2 — Terminate the active query. For scores between 5.5 and 7.0, the specific query is killed. The session remains active; the system monitors for recurrence. Two Level-2 terminations within a 5-minute window auto-escalate to Level 3.

    Level 3 — Terminate the session. For scores above 7.0, or after Level-2 escalation, the session is forcibly terminated and the user's ability to establish new connections is suspended for a configurable quarantine window (default: 15 minutes).

    Level 4 — Revoke and isolate. For the highest-confidence threats — novel query + off-hours connection + bulk data access simultaneously — the system revokes the role's login privilege entirely and creates a forensic snapshot of what was accessed.

    The autonomous containment logic integrates with the scoring engine through a simple state machine. Each session has a containment state (CLEAR, MONITORING, RATE_LIMITED, TERMINATED, QUARANTINED). State transitions are append-only to an audit table; no state is silently overwritten. This creates an immutable incident timeline that satisfies SOC-2 and ISO 27001 audit requirements — the autonomous system's every action is traceable.

    Two safety mechanisms prevent the autonomous system from taking catastrophic actions:

    1. Protected principals list. The accounts used by the monitoring agent itself, replication users, backup agents, and named DBA accounts are permanently excluded from autonomous containment. A compromised monitoring credential is still dangerous, but it should trigger a manual escalation path, not a self-terminating loop where the security agent kills itself.

    2. Quorum check before Level 3 and Level 4 actions. Before terminating a session or revoking a login, the containment engine queries how many other sessions from the same application are currently active and healthy. If the target session represents more than 60% of an application's connection pool, autonomous termination is suppressed and the action is escalated to a human-approved queue instead. This prevents a miscalibrated score from causing an application outage by killing the majority of its connections.

    def can_act_autonomously(
    username: str,
    session_id: str,
    level: int,
    conn
) -> bool:
    """
    Returns True if autonomous action at the given level is safe.
    Level 3+ requires quorum check.
    """
    PROTECTED = {"monitor", "backup_agent", "dba_monitor", "sa"}
    if username in PROTECTED:
        logger.warning("Skipping autonomous action: protected principal %s", username)
        return False

    if level < 3:
        return True

    # Quorum check: how many sessions does this user account for?
    cur = conn.cursor()
    cur.execute("""
        SELECT
            SUM(CASE WHEN login_name = ? THEN 1 ELSE 0 END) AS user_sessions,
            COUNT(*)                                          AS total_sessions
        FROM sys.dm_exec_sessions
        WHERE is_user_process = 1
    """, username)
    user_sessions, total_sessions = cur.fetchone()

    if total_sessions == 0:
        return True

    ratio = user_sessions / total_sessions
    if ratio > 0.60:
        logger.warning(
            "Quorum check failed for %s: %.0f%% of active sessions — "
            "escalating to human queue instead of autonomous Level %d action",
            username, ratio * 100, level
        )
        return False

    return True

    The containment actions are idempotent by design. Each KILL runs inside a TRY/CATCH that treats an already-disconnected session as a no-op, and ALTER LOGIN ... DISABLE on an already-disabled login is a no-op. This means the system can retry actions on the 30-second polling loop without accumulating side effects.

    20.5 DDL and Privilege Escalation Detection

    Schema mutations and privilege changes are categorically different from query anomalies. They do not require statistical modeling — any GRANT, CREATE USER, ALTER TABLE, or DROP operation that occurs outside a defined change window is an unconditional high-severity signal. The autonomous system treats them with a separate detection path that bypasses the scoring model entirely.

    In SQL Server, the same out-of-band delivery is achieved with a Service Broker conversation or an Event Notification that fires the alerting pipeline within milliseconds of the DDL completing — meaningfully faster than waiting for the next 30-second polling cycle.

    20.6 Integration with External Security Pipelines

    An autonomous detection system that operates entirely within the database perimeter is incomplete. Threats that originate at the application layer, succeed in part through the database, and then pivot to other infrastructure require correlation across multiple signal sources. The database-layer detection system must emit structured events that SIEM platforms, SOAR orchestrators, and zero-trust policy engines can consume.

    The canonical output format is structured JSON over a reliable transport. The scoring engine pushes events to three destinations simultaneously:

    1. Prometheus Alertmanager for operational on-call routing (low latency, fire-and-forget)

    2. An append-only event log table in the database itself (durable, queryable for forensics)

    3. A message queue (Kafka topic or AWS SQS queue) for SIEM ingestion (ordered, replayable)

    The event schema follows the OCSF (Open Cybersecurity Schema Framework) database/datastore activity category to maximize compatibility with Splunk, Microsoft Sentinel, and Elastic SIEM without requiring custom parsers. The exact class_uid and category_uid values are versioned by the OCSF schema itself, so confirm them against the schema release you target before wiring up production ingestion — the values below are illustrative:

    producer.poll(0)   # non-blocking flush

def emit_to_alert_table(event: dict, conn) -> None:
    with conn.cursor() as cur:
        cur.execute("""
            INSERT INTO security.ocsf_event_log
                (class_uid, severity_id, event_time, actor_user, raw_json)
            VALUES (%s, %s, to_timestamp(%s / 1000.0), %s, %s)
        """, (
            event["class_uid"],
            event["severity_id"],
            event["time"],
            event["actor"]["user"]["name"],
            json.dumps(event)
        ))
        conn.commit()

    The SOAR integration layer consumes from the Kafka topic and applies playbook logic. Playbooks at this layer handle tasks the database engine itself cannot: creating a security incident ticket, notifying the user's manager, coordinating with network teams to geo-block the source IP, or triggering an AWS GuardDuty finding. The database-layer autonomous system handles only what it can do with certainty and speed — query termination, session disconnect, login suspension — and delegates everything requiring broader organizational context to the SOAR.

    One integration pattern worth implementing explicitly is the feedback loop: when a SOAR playbook resolves an incident as a false positive, it sends a callback to the database security system's API endpoint. That callback marks the incident in the event log as a false positive and triggers a baseline recalibration for the affected user — slightly widening the anomaly thresholds to account for legitimate-but-unusual behavior. Without this feedback loop, an analyst who regularly runs large batch queries off-hours will generate persistent noise until the baseline naturally absorbs their behavior over 14 days. The feedback loop collapses that to seconds.

    20.7 Forensic Preservation and Post-Incident Analysis

    When autonomous containment fires, forensic preservation must happen simultaneously — not afterward. Evidence that might survive in memory or in SQL Server's plan cache is volatile and can be lost as soon as the session ends and cache entries age out.

    The containment engine triggers forensic capture as part of every Level 3 and Level 4 action:

    Comprehensive session forensic capture:

    -- Capture all available evidence before terminating the session
CREATE OR ALTER PROCEDURE security.usp_capture_session_forensics
    @incident_id  UNIQUEIDENTIFIER,
    @target_sid   INT,
    @target_user  SYSNAME
AS
BEGIN
    SET NOCOUNT ON;

    -- 1. Snapshot of current session state
    INSERT INTO security.forensic_sessions (
        incident_id, session_id, login_name, host_name,
        program_name, client_net_address, login_time,
        last_request_start_time, status, captured_at
    )
    SELECT
        @incident_id, s.session_id, s.login_name, s.host_name,
        s.program_name, s.client_net_address, s.login_time,
        r.start_time, s.status, SYSUTCDATETIME()
    FROM sys.dm_exec_sessions s
    LEFT JOIN sys.dm_exec_requests r
        ON r.session_id = s.session_id
    WHERE s.session_id = @target_sid;

    -- 2. Currently executing statement text
    INSERT INTO security.forensic_query_history (
        incident_id, login_name, session_id, query_text,
        captured_at
    )
    SELECT
        @incident_id, s.login_name, r.session_id,
        SUBSTRING(
            qt.text,
            (r.statement_start_offset / 2) + 1,
            (CASE r.statement_end_offset
                 WHEN -1 THEN DATALENGTH(qt.text)
                 ELSE r.statement_end_offset
             END - r.statement_start_offset) / 2 + 1
        ),
        SYSUTCDATETIME()
    FROM sys.dm_exec_requests r
    JOIN sys.dm_exec_sessions s ON s.session_id = r.session_id
    CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) qt
    WHERE r.session_id = @target_sid;

    -- 3. Any locks held by this session
    INSERT INTO security.forensic_locks (
        incident_id, session_id, resource_type, resource_database,
        request_mode, request_status, captured_at
    )
    SELECT
        @incident_id, l.request_session_id, l.resource_type,
        DB_NAME(l.resource_database_id), l.request_mode,
        l.request_status, SYSUTCDATETIME()
    FROM sys.dm_tran_locks l
    WHERE l.request_session_id = @target_sid;

    -- 4. Record the containment action
    INSERT INTO security.containment_actions (
        incident_id, action_type, target_user,
        target_session_id, executed_at, executed_by
    )
    VALUES (
        @incident_id, 'LEVEL3_TERMINATE', @target_user,
        @target_sid, SYSUTCDATETIME(), SYSTEM_USER
    );
END;

    After forensic capture, the post-incident analysis pipeline runs automatically within 2 minutes using the preserved evidence. It generates a structured incident report covering: timeline of the session, all queries executed during the incident window, tables accessed, data volume estimates, and the sequence of anomaly signals that triggered the response. This report goes directly to the SIEM as an OCSF Finding event and into a dedicated incident tracking table.

    The post-incident analysis also feeds a longer-horizon threat hunting query that examines whether the same anomaly pattern appeared in other sessions in the preceding 30 days — potentially revealing earlier reconnaissance that did not individually cross the detection threshold:

    -- Threat hunt: find sessions with similar anomaly fingerprint
-- within 30-day lookback window
DECLARE @confirmed_threat_user SYSNAME = N'compromised_svc';

SELECT
    el.actor_user,
    el.event_time,
    el.severity_id,
    JSON_VALUE(el.raw_json, '$.unmapped.score_components') AS components,
    JSON_VALUE(el.raw_json, '$.unmapped.composite_score')  AS score
FROM security.ocsf_event_log el
WHERE el.event_time > DATEADD(DAY, -30, SYSUTCDATETIME())
  AND el.class_uid = 5001
  AND TRY_CAST(
          JSON_VALUE(el.raw_json, '$.unmapped.score_components.rows')
          AS FLOAT) > 2.0     -- similar row-volume anomaly
  AND el.actor_user <> @confirmed_threat_user
ORDER BY el.event_time DESC;

    This pattern surfaces related actors that may be part of the same campaign — for instance, multiple application accounts compromised in a credential stuffing attack, each operating below the individual detection threshold but showing the same behavioral fingerprint.

    Key Takeaways

  • → Autonomous threat detection requires simultaneous instrumentation of all four observable planes — authentication, query execution, schema mutation, and data volume — because attackers who have already passed the perimeter leave signals that only become conclusive when correlated across multiple dimensions. A single-plane monitoring approach produces both excessive noise and dangerous blind spots.
  • → Behavioral baselining must be per-identity and decay-weighted, not aggregate. A baseline that treats all users as a single population will miss insider threats and account compromise entirely. Exponential decay weighting ensures the model tracks genuine workload evolution without permanently absorbing attack behavior into the normal profile.
  • → The scoring-to-action pipeline must be graduated and reversible. A binary detect-or-ignore system either generates too many false positives to remain credible or sets thresholds so high that real threats pass unimpeded. The four-level containment ladder — rate-limit, query kill, session terminate, login revoke — proportions the response to confidence, and protected principal lists with quorum checks prevent autonomous actions from causing application outages worse than the attack itself.
  • → DDL and privilege escalation events bypass the statistical scoring model entirely. Schema changes and role grants in production outside of defined change windows are unconditional high-severity signals. Event triggers and server-scoped DDL triggers fire synchronously within the transaction, providing sub-second detection latency that polling-based approaches cannot match.
  • → Forensic preservation and SIEM emission must be atomic with the containment action, not deferred. Evidence in plan caches, session state, and lock tables is volatile. Capturing it after termination means capturing nothing. Integrating forensics into the containment procedure, combined with OCSF-formatted event emission to a durable message queue, ensures that autonomous speed does not come at the cost of the post-incident visibility needed to understand the full scope of a threat.
