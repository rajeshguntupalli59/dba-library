Chapter 22: Autonomous Patch Management

Patch management sits at the intersection of security posture, availability guarantees, and operational risk — and in most organizations, it remains the most stubbornly manual process in the DBA's portfolio. Security advisories arrive unpredictably, maintenance windows are negotiated weeks in advance, and the gap between a CVE publication and a patched production cluster is measured in weeks or months. An autonomous patch management system collapses that gap by treating patching as a pipeline: continuous vulnerability ingestion, automated risk scoring, staged rollout with self-validation, and rollback triggered without human escalation. This chapter builds that pipeline end to end for SQL Server environments, with the goal of reducing the human decision surface to policy definition rather than per-patch approval.

22.1 Vulnerability Intelligence Pipelines: From CVE Feed to Patch Priority Score

The first obligation of an autonomous patch system is awareness — knowing what patches exist, what vulnerabilities they address, and how urgently each matters in your specific environment. Manual monitoring of vendor security pages does not scale. An ADE-level system subscribes to structured vulnerability feeds and enriches them with local context automatically.

SQL Server security advisories arrive through the Microsoft Security Response Center (MSRC) API at https://api.msrc.microsoft.com/cvrf/v2.0/, and the Microsoft SQL Server release notes track every Cumulative Update with its fixed KBs. The MSRC feed is machine-consumable and should be polled daily by an ingestion service that stores results in a patch intelligence table. Cross-referencing advisories with the installed build of each instance tells the system exactly which machines are exposed.

import httpx
import json
from datetime import datetime, timedelta
import pyodbc

MSRC_BASE = "https://api.msrc.microsoft.com/cvrf/v2.0/updates"

def fetch_msrc_sqlserver_updates(days_back: int = 1) -> list[dict]:
    """Fetch MSRC security updates mentioning SQL Server products."""
    resp = httpx.get(MSRC_BASE, timeout=30,
                     params={"$filter": "cvrfID ge '2026-Jan'"})
    resp.raise_for_status()
    updates = resp.json().get("value", [])
    # Keep only updates whose product tree includes SQL Server
    return [u for u in updates
            if "SQL Server" in json.dumps(u.get("ProductTree", {}))]

def compute_priority_score(update: dict) -> float:
    """
    Weighted score combining CVSS base score, exploit availability,
    and local asset exposure. Returns 0.0–100.0.
    """
    cvss_score = 0.0
    for metric in update.get("cvss", []):
        if metric.get("cvssSource") in ("NVD", "MSRC"):
            cvss_score = max(cvss_score, metric.get("baseScore", 0.0))

    # Exploit maturity multiplier — check EPSS score from api.first.org
    epss_score = fetch_epss_score(update["DocumentTracking"]["ID"])  # returns 0.0–1.0

    # Asset exposure: how many instances run the affected build?
    affected_instances = count_affected_instances(update)

    exposure_multiplier = min(1.5, 1.0 + (affected_instances / 10.0))
    raw = (cvss_score * 10) * (1 + epss_score) * exposure_multiplier
    return min(100.0, raw)

def ingest_updates_to_catalog(conn, updates: list[dict]):
    cur = conn.cursor()
    for update in updates:
        update_id = update["DocumentTracking"]["ID"]
        score = compute_priority_score(update)
        cur.execute("""
            MERGE patch_catalog AS target
            USING (SELECT ? AS update_id) AS src
            ON target.update_id = src.update_id
            WHEN MATCHED THEN
                UPDATE SET priority_score = ?, ingested_at = SYSUTCDATETIME()
            WHEN NOT MATCHED THEN
                INSERT (update_id, db_engine, priority_score,
                        published_at, raw_payload, ingested_at)
                VALUES (?, 'sqlserver', ?, ?, ?, SYSUTCDATETIME());
        """, (update_id, score, update_id, score,
              update.get("DocumentTracking", {}).get("CurrentReleaseDate"),
              json.dumps(update)))
    conn.commit()

The priority_score formula is intentional — it does not treat all CVEs equally. A CVSS 9.8 with no known exploit and zero affected clusters scores lower than a CVSS 7.5 with active exploitation and fifty clusters on the vulnerable version. The Exploit Prediction Scoring System (EPSS) from FIRST.org provides daily updated exploit probability scores that feed this calculation.

Once scores are assigned, the system classifies patches into three tiers that drive downstream automation behavior:

  • → Tier 1 (score ≥ 80): Deploy within 24 hours, bypass standard change freeze
  • → Tier 2 (score 50–79): Deploy within next scheduled maintenance window (≤ 7 days)
  • → Tier 3 (score < 50): Batch with next planned minor version upgrade

    • This tiering is stored alongside the CVE record and queried by the patch orchestrator to determine rollout timing without human input.

    22.2 Version Inventory and Drift Detection Across Fleet Clusters

    Autonomous patching requires authoritative, real-time knowledge of what version every cluster is running. Version drift — where different clusters diverge from the approved baseline — is itself a risk signal and a scheduling input. Without automated inventory, the patch pipeline cannot know which clusters need action.

    -- Central inventory table in a dedicated management database
CREATE TABLE dbo.SqlInstanceInventory (
    InstanceId          NVARCHAR(200)  NOT NULL PRIMARY KEY,
    Environment         NVARCHAR(50)   NOT NULL,
    Region              NVARCHAR(100),
    SqlVersion          NVARCHAR(50)   NOT NULL,
    BuildNumber         NVARCHAR(50)   NOT NULL,
    PatchLevel          NVARCHAR(50),   -- CU or SP designation
    ApprovedBaseline    NVARCHAR(50),
    DriftDetected       AS CAST(CASE WHEN BuildNumber != ApprovedBaseline
                                     THEN 1 ELSE 0 END AS BIT) PERSISTED,
    LastSeen            DATETIME2      NOT NULL DEFAULT SYSUTCDATETIME()
);

-- Surfaces instances behind the approved Cumulative Update
SELECT
    InstanceId,
    Environment,
    BuildNumber         AS CurrentBuild,
    ApprovedBaseline,
    PatchLevel,
    DATEDIFF(DAY, LastSeen, SYSUTCDATETIME()) AS DaysSinceCheckin
FROM dbo.SqlInstanceInventory
WHERE DriftDetected = 1
ORDER BY Environment DESC, DaysSinceCheckin DESC;

    On Kubernetes-hosted SQL Server (StatefulSets or Azure Arc-enabled SQL Server), the same inventory function is expressed as a CronJob that connects to the instance over the service DNS name and writes results to the central catalog. The autonomous patch system subscribes to instance lifecycle events rather than implementing its own polling.

    Drift detection feeds into the patch scheduler: clusters with minor_versions_behind >= 3 are escalated to Tier 2 regardless of the CVE score, because version gaps introduce an operational complexity cost beyond security risk alone. The system auto-generates a patch work order for these clusters and assigns them to the next available maintenance window.

    22.3 Staged Rollout Architecture: Canary, Ring, and Fleet Propagation

    The single most important property of autonomous patching is that it must never apply a patch to all clusters simultaneously. Fleet-wide simultaneous patching is how autonomous systems cause outages at scale. The rollout architecture implements concentric rings of trust, where each ring provides validation evidence for the next.

    The ring model for a typical enterprise fleet:

    | Ring | Scope | Dwell Time | Pass Criteria |

    |------|-------|------------|---------------|

    | 0 | Dev/test clusters | 2 hours | Zero crash loop, schema migrations pass |

    | 1 | Staging clusters (10% of traffic) | 24 hours | Error rate < baseline P95, query latency ≤ +5% |

    | 2 | Production canary (1 cluster) | 48 hours | All Ring 1 metrics + replication lag < 500ms |

    | 3 | Production batch (25% per wave) | 72 hours per wave | SLA metrics within tolerance |

    graph LR
    R0[Ring 0: Dev/test
    2h dwell] -->|pass| R1[Ring 1: Staging 10%
    24h dwell]
    R1 -->|pass| R2[Ring 2: Prod canary
    48h dwell]
    R2 -->|pass| R3[Ring 3: Prod batch 25%/wave
    72h per wave]
    R3 -->|pass| Done[Fully deployed]
    R0 -->|fail| RB0[Rollback ring 0 + escalate]
    R1 -->|fail| RB1[Rollback ring 1 + escalate]
    R2 -->|fail| RB2[Rollback ring 2 + escalate]
    R3 -->|fail| RB3[Rollback ring 3 + escalate]

    *A failing ring halts propagation entirely — later rings never see a patch that hasn't earned trust from every ring before it.*

    The orchestrator is responsible for advancing or halting rings. It does not ask for human confirmation to advance; it only escalates when a ring fails validation. The core orchestration loop:

    from enum import Enum
from dataclasses import dataclass
from datetime import datetime, timedelta
import time
import logging

class RingStatus(Enum):
    PENDING    = "pending"
    IN_FLIGHT  = "in_flight"
    VALIDATING = "validating"
    PASSED     = "passed"
    FAILED     = "failed"
    ROLLED_BACK = "rolled_back"

@dataclass
class PatchRing:
    ring_id: int
    clusters: list[str]
    dwell_hours: int
    status: RingStatus = RingStatus.PENDING
    started_at: datetime = None
    completed_at: datetime = None

class PatchOrchestrator:
    def __init__(self, patch_id: str, rings: list[PatchRing],
                 validator, patcher, notifier):
        self.patch_id  = patch_id
        self.rings     = rings
        self.validator = validator
        self.patcher   = patcher
        self.notifier  = notifier

    def run(self):
        for ring in self.rings:
            logging.info(f"Patch {self.patch_id}: starting ring {ring.ring_id}")
            self._apply_ring(ring)

            dwell_deadline = ring.started_at + timedelta(hours=ring.dwell_hours)
            while datetime.utcnow() < dwell_deadline:
                time.sleep(300)  # Check every 5 minutes during dwell
                result = self.validator.evaluate(ring.clusters)
                if result.status == "failing":
                    self._halt_and_rollback(ring, result.reason)
                    return  # Stop propagation entirely

            # Final gate check after full dwell period
            final = self.validator.evaluate(ring.clusters)
            if final.status != "healthy":
                self._halt_and_rollback(ring, final.reason)
                return

            ring.status = RingStatus.PASSED
            ring.completed_at = datetime.utcnow()
            logging.info(f"Ring {ring.ring_id} passed. Advancing.")

        self.notifier.send(f"Patch {self.patch_id} fully deployed across all rings.")

    def _apply_ring(self, ring: PatchRing):
        ring.status = RingStatus.IN_FLIGHT
        ring.started_at = datetime.utcnow()
        for cluster in ring.clusters:
            self.patcher.apply(cluster, self.patch_id)
        ring.status = RingStatus.VALIDATING

    def _halt_and_rollback(self, ring: PatchRing, reason: str):
        ring.status = RingStatus.FAILED
        logging.error(f"Ring {ring.ring_id} failed: {reason}. Initiating rollback.")
        for cluster in ring.clusters:
            self.patcher.rollback(cluster, self.patch_id)
        ring.status = RingStatus.ROLLED_BACK
        self.notifier.escalate(
            f"PATCH HALTED: {self.patch_id} at ring {ring.ring_id}. "
            f"Reason: {reason}. Rollback complete. Human review required."
        )

    The validator.evaluate() call queries Prometheus for a set of pre-defined SLIs: connection error rate, query latency P99, AG synchronization health, and active connection count. For SQL Server Always On Availability Groups, the validator checks the DMV sys.dm_hadr_database_replica_states for synchronization health and redo queue depth.

    -- Validation query run by the patch orchestrator against each SQL Server AG replica
SELECT
    ag.name                                                AS availability_group,
    drs.database_id,
    DB_NAME(drs.database_id)                              AS db_name,
    drs.synchronization_state_desc,
    drs.synchronization_health_desc,
    drs.redo_queue_size                                   AS redo_queue_kb,
    drs.log_send_queue_size                               AS send_queue_kb,
    drs.secondary_lag_seconds,
    CASE WHEN drs.redo_queue_size   > 51200 THEN 'WARN'
         WHEN drs.secondary_lag_seconds > 30    THEN 'WARN'
         WHEN drs.synchronization_health_desc != 'HEALTHY' THEN 'FAIL'
         ELSE 'OK'
    END                                                   AS patch_gate_status
FROM sys.dm_hadr_database_replica_states drs
JOIN sys.availability_groups ag
    ON drs.group_id = ag.group_id
WHERE drs.is_local = 0;  -- secondary replicas only

    When patch_gate_status returns any FAIL row, the orchestrator halts the ring immediately. A WARN during the dwell window triggers increased monitoring frequency (60-second checks instead of 5-minute) but does not by itself halt propagation — it must persist for 30 consecutive minutes before triggering a halt. This hysteresis prevents transient load spikes from stopping legitimate patch rollouts.

    22.4 Zero-Downtime Patch Execution for SQL Server Always On

    Applying a patch to a production database cluster without downtime requires understanding the AG topology and executing the patch sequence in the right order: patch secondary replicas first, verify they re-synchronize, then move the primary role to a patched replica, and finally patch the former primary.

    AG patch sequencer: The safest sequence is replica-first, then controlled primary failover. The autonomous patcher queries the AG topology from the DMVs and drives failover itself:

    import pyodbc
import time

def get_ag_topology(conn) -> tuple[str, list[str]]:
    """Return (primary_replica, secondary_replicas) for the production AG."""
    cur = conn.cursor()
    cur.execute("""
        SELECT ar.replica_server_name, ars.role_desc
        FROM sys.availability_groups ag
        JOIN sys.availability_replicas ar
            ON ag.group_id = ar.group_id
        JOIN sys.dm_hadr_availability_replica_states ars
            ON ar.replica_id = ars.replica_id
        WHERE ag.name = 'AG_Production'
    """)
    primary, secondaries = None, []
    for replica_name, role in cur.fetchall():
        if role == 'PRIMARY':
            primary = replica_name
        else:
            secondaries.append(replica_name)
    return primary, secondaries

def wait_for_sync(conn, timeout_seconds: int = 600):
    deadline = time.time() + timeout_seconds
    while time.time() < deadline:
        cur = conn.cursor()
        cur.execute("""
            SELECT COUNT(*)
            FROM sys.dm_hadr_database_replica_states
            WHERE is_local = 0
              AND synchronization_health_desc != 'HEALTHY'
        """)
        if cur.fetchone()[0] == 0:
            return
        time.sleep(15)
    raise RuntimeError("AG did not return to HEALTHY within timeout")

def patch_ag_cluster(admin_conn_str: str, patch_fn):
    """
    patch_fn: callable that accepts a hostname and performs the OS-level
    Cumulative Update install (e.g., via Azure Update Manager or
    AWS Systems Manager) and restarts the SQL Server service.
    """
    conn = pyodbc.connect(admin_conn_str, autocommit=True)

    # Step 1: Identify topology
    primary, secondaries = get_ag_topology(conn)

    # Step 2: Patch secondary replicas first (no traffic disruption)
    for replica in secondaries:
        patch_fn(replica)
        time.sleep(30)  # Brief settle period
        wait_for_sync(conn)  # Verify replica rejoined and re-synchronized

    # Step 3: Move primary role to a now-patched replica
    cur = conn.cursor()
    cur.execute("ALTER AVAILABILITY GROUP [AG_Production] FAILOVER")
    time.sleep(15)  # Allow role transition to complete

    # Step 4: Verify the new primary is the patched replica
    new_primary, _ = get_ag_topology(conn)
    assert new_primary != primary, "Failover did not complete successfully"

    # Step 5: Patch the old primary (now a secondary)
    patch_fn(primary)
    wait_for_sync(conn)

    The actual patch_fn submits the Cumulative Update through the platform's update orchestration — Azure Update Manager, AWS Systems Manager Patch Manager, or an Ansible playbook — and restarts the SQL Server service on the target host. The restart is coordinated so the AG role is already off the node being patched, which keeps the WSFC quorum intact throughout.

    Pre-patch gate: Before any patch sequence begins, the autonomous patcher verifies the AG is fully synchronized.

FAILOVER → patch the former primary. The Windows Update orchestration can be handled through Azure Update Manager, AWS Systems Manager Patch Manager, or a Terraform-driven Ansible playbook — the autonomous patcher generates and submits the job rather than executing it inline.

    22.5 Autonomous Rollback: Decision Logic, Trigger Conditions, and Recovery Verification

    Rollback is where autonomous systems either earn trust or destroy it. A system that patches but cannot reliably roll back is more dangerous than no automation at all. The rollback subsystem must be opinionated, fast, and verifiable.

    Rollback triggers fall into three categories:

    Hard triggers — immediate rollback, no dwell, no override:

  • → SQL Server service exits within 60 seconds of service restart (crash loop)
  • → AG secondary redo queue growing monotonically for 10 minutes post-patch
  • → Connection rejection rate exceeds 5% over a 2-minute window
  • → SQL Server AG replica enters NOT_SYNCHRONIZING state post-patch

    • Soft triggers — rollback if condition persists beyond hysteresis window (30 minutes):

  • → Query latency P99 elevated > 20% above pre-patch baseline
  • → Lock wait events per second > 2×pre-patch baseline
  • → Buffer hit ratio drops > 5 percentage points below pre-patch baseline
  • → TempDB allocation failures per minute > 0 (SQL Server specific)

    • Informational triggers — logged, escalated to human, no automatic rollback:

  • → New query plan regressions detected (via Query Store)
  • → Checkpoint duration increase > 50%
  • → Index fragmentation increase in tracked tables

    • The distinction between hard and soft triggers is intentional. Hard triggers represent conditions where continued operation is objectively unsafe — the database is either crashing, disconnecting clients, or losing replication. Soft triggers represent degradation that could be transient (a batch job, a sudden traffic spike) and need the hysteresis window to distinguish noise from signal.

    The rollback state machine tracks which tier of trigger fired and records it in the patch audit log:

    from dataclasses import dataclass, field
from datetime import datetime
from enum import Enum
from typing import Optional

class TriggerType(Enum):
    HARD  = "hard"
    SOFT  = "soft"
    NONE  = "none"

@dataclass
class RollbackDecision:
    trigger_type:   TriggerType
    trigger_reason: str
    fired_at:       datetime
    should_rollback: bool
    escalate_human: bool

@dataclass
class SoftTriggerState:
    condition:    str
    first_seen:   datetime
    last_seen:    datetime
    breach_count: int = 0
    HYSTERESIS_MINUTES: int = 30

    def is_sustained(self) -> bool:
        duration = (self.last_seen - self.first_seen).total_seconds() / 60
        return duration >= self.HYSTERESIS_MINUTES

class RollbackEvaluator:
    def __init__(self, metrics_client, baseline: dict):
        self.metrics  = metrics_client
        self.baseline = baseline
        self._soft_states: dict[str, SoftTriggerState] = {}

    def evaluate(self, cluster_id: str) -> RollbackDecision:
        m = self.metrics.fetch(cluster_id)

        # --- Hard trigger evaluation ---
        if m.get("process_crash_detected"):
            return RollbackDecision(
                trigger_type    = TriggerType.HARD,
                trigger_reason  = "SQL Server service crash detected",
                fired_at        = datetime.utcnow(),
                should_rollback = True,
                escalate_human  = True,
            )

        if m.get("connection_rejection_rate", 0) > 0.05:
            return RollbackDecision(
                trigger_type    = TriggerType.HARD,
                trigger_reason  = f"Connection rejection rate {m['connection_rejection_rate']:.1%}",
                fired_at        = datetime.utcnow(),
                should_rollback = True,
                escalate_human  = True,
            )

        replication_lag_growth = m.get("replication_lag_growth_rate_seconds_per_minute", 0)
        if replication_lag_growth > 0 and m.get("minutes_since_patch", 0) > 10:
            return RollbackDecision(
                trigger_type    = TriggerType.HARD,
                trigger_reason  = "Replication lag growing monotonically post-patch",
                fired_at        = datetime.utcnow(),
                should_rollback = True,
                escalate_human  = True,
            )

        # --- Soft trigger evaluation ---
        latency_baseline = self.baseline.get("p99_latency_ms", 0)
        current_latency  = m.get("p99_latency_ms", 0)
        if latency_baseline > 0 and current_latency > latency_baseline * 1.20:
            decision = self._evaluate_soft(
                "latency_elevation",
                f"P99 latency {current_latency:.0f}ms vs baseline {latency_baseline:.0f}ms"
            )
            if decision:
                return decision

        lock_baseline = self.baseline.get("lock_waits_per_second", 0)
        current_locks = m.get("lock_waits_per_second", 0)
        if lock_baseline > 0 and current_locks > lock_baseline * 2:
            decision = self._evaluate_soft(
                "lock_wait_elevation",
                f"Lock waits {current_locks:.1f}/s vs baseline {lock_baseline:.1f}/s"
            )
            if decision:
                return decision

        # Clear any soft states that have recovered
        self._clear_recovered_states(m)

        return RollbackDecision(
            trigger_type    = TriggerType.NONE,
            trigger_reason  = "All metrics within tolerance",
            fired_at        = datetime.utcnow(),
            should_rollback = False,
            escalate_human  = False,
        )

    def _evaluate_soft(self, condition_key: str, reason: str) -> Optional[RollbackDecision]:
        now = datetime.utcnow()
        if condition_key not in self._soft_states:
            self._soft_states[condition_key] = SoftTriggerState(
                condition  = reason,
                first_seen = now,
                last_seen  = now,
            )
        else:
            state = self._soft_states[condition_key]
            state.last_seen   = now
            state.breach_count += 1
            if state.is_sustained():
                return RollbackDecision(
                    trigger_type    = TriggerType.SOFT,
                    trigger_reason  = f"Sustained 30m: {reason}",
                    fired_at        = now,
                    should_rollback = True,
                    escalate_human  = True,
                )
        return None

    def _clear_recovered_states(self, metrics: dict):
        """Remove soft trigger states for conditions that have self-resolved."""
        latency_ok = (
            metrics.get("p99_latency_ms", 0)
            <= self.baseline.get("p99_latency_ms", 0) * 1.20
        )
        if latency_ok and "latency_elevation" in self._soft_states:
            del self._soft_states["latency_elevation"]

    Once a rollback decision is made, the rollback executor must verify its own success. A rollback that silently fails is indistinguishable from a patch that was never rolled back. The verification sequence:

    def execute_rollback_with_verification(cluster_id: str, patch_id: str,
                                       patcher, metrics_client,
                                       baseline: dict) -> bool:
    """
    Returns True if rollback succeeded and cluster returned to healthy baseline.
    Returns False if rollback itself failed — escalates immediately.
    """
    import logging, time

    logging.warning(f"Initiating rollback: cluster={cluster_id}, patch={patch_id}")

    try:
        patcher.rollback(cluster_id, patch_id)
    except Exception as exc:
        logging.error(f"Rollback execution error on {cluster_id}: {exc}")
        # Escalate immediately — this is a tier-1 incident
        escalate_incident(
            cluster_id = cluster_id,
            severity   = "P1",
            message    = f"Patch rollback FAILED on {cluster_id}: {exc}",
        )
        return False

    # Wait for service to stabilize after rollback
    time.sleep(60)

    # Verify the binary actually reverted
    current_version = patcher.get_version(cluster_id)
    expected_version = patcher.pre_patch_version(cluster_id, patch_id)
    if current_version != expected_version:
        logging.error(
            f"Version mismatch post-rollback: got {current_version}, "
            f"expected {expected_version}"
        )
        escalate_incident(
            cluster_id = cluster_id,
            severity   = "P1",
            message    = (
                f"Rollback version verification failed: {cluster_id} "
                f"still running {current_version}"
            ),
        )
        return False

    # Verify metric recovery — wait up to 10 minutes
    for attempt in range(20):
        m = metrics_client.fetch(cluster_id)
        latency_ok = (
            m.get("p99_latency_ms", 0)
            <= baseline.get("p99_latency_ms", 0) * 1.10
        )
        error_rate_ok = m.get("connection_rejection_rate", 0) < 0.01
        replication_ok = m.get("replication_lag_growth_rate_seconds_per_minute", 0) <= 0

        if latency_ok and error_rate_ok and replication_ok:
            logging.info(f"Rollback verified successfully for {cluster_id}")
            return True

        time.sleep(30)

    # Metrics did not recover in 10 minutes even after rollback
    escalate_incident(
        cluster_id = cluster_id,
        severity   = "P1",
        message    = (
            f"Post-rollback metric recovery failed on {cluster_id}. "
            f"Manual intervention required."
        ),
    )
    return False

    The distinction between a failed rollback and a slow recovery is time-bounded: ten minutes is sufficient for an AG to re-establish synchronization and drain in-flight queries after a binary revert. If the AG is still degraded at that point, the issue is not the patch reversal but something deeper — possibly a corrupted page, a config inconsistency, or an infrastructure-layer failure — and human judgment is genuinely needed.

    22.6 Patch Audit Trails and Compliance Reporting

    Autonomous systems that operate without human approval at each step face a higher evidentiary standard than manual processes. When an auditor asks "who approved patching this cluster at 2 AM?" the answer "the policy authorized it and the orchestrator executed autonomously" must be substantiated by a complete, tamper-evident record of every decision, every trigger condition evaluated, and every action taken.

    The patch audit log is append-only by design. In SQL Server this is enforced using a ledger table (SQL Server 2022+) or an INSERT-only permission structure where the patch agent role is granted INSERT but never UPDATE or DELETE on the audit tables.

    CREATE TABLE dbo.PatchAuditLog (
    LogId            BIGINT IDENTITY(1,1) PRIMARY KEY,
    EventTime        DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    PatchId          NVARCHAR(100) NOT NULL,

    RingId           INT,

    TriggerType      NVARCHAR(50),
    TriggerReason    NVARCHAR(MAX),
    Actor            NVARCHAR(200) NOT NULL DEFAULT SYSTEM_USER,
    MetricsSnapshot  NVARCHAR(MAX),  -- JSON stored as NVARCHAR for SQL Server 2016 compat
    Outcome          NVARCHAR(100),

);

-- Deny UPDATE and DELETE to the patch agent login
DENY UPDATE ON dbo.PatchAuditLog TO patch_agent_login;
DENY DELETE ON dbo.PatchAuditLog TO patch_agent_login;

CREATE TRIGGER PreventAuditTableAlter

AS
BEGIN
    DECLARE @EventData XML = EVENTDATA();

    Compliance reports query the audit log to produce evidence artifacts. A typical SOC 2 or PCI-DSS audit requires demonstrating that patches were applied within the required timeframe of CVE publication and that a complete approval chain exists. The autonomous model satisfies this by making the policy itself the auditable artifact:

    -- Patch SLA compliance report
-- Shows MSRC updates published in the last quarter and whether they were patched within tier SLA
SELECT
    pc.update_id,
    pc.priority_score,
    CASE
        WHEN pc.priority_score >= 80 THEN 'Tier 1 (24h)'
        WHEN pc.priority_score >= 50 THEN 'Tier 2 (7d)'
        ELSE                              'Tier 3 (next upgrade)'
    END                                                   AS tier,
    pc.published_at,
    MIN(CASE WHEN pal.event_type = 'patch_applied'
             THEN pal.event_time END)                     AS first_applied_at,
    DATEDIFF(HOUR, pc.published_at,
        MIN(CASE WHEN pal.event_type = 'patch_applied'
                 THEN pal.event_time END))                AS hours_to_first_patch,
    CASE
        WHEN pc.priority_score >= 80
         AND DATEDIFF(HOUR, pc.published_at,
               MIN(CASE WHEN pal.event_type = 'patch_applied'
                        THEN pal.event_time END)) <= 24
         THEN 'COMPLIANT'
        WHEN pc.priority_score >= 50
         AND DATEDIFF(HOUR, pc.published_at,
               MIN(CASE WHEN pal.event_type = 'patch_applied'
                        THEN pal.event_time END)) <= 168
         THEN 'COMPLIANT'
        WHEN pc.priority_score < 50
         THEN 'TIER3_DEFERRED'
        ELSE 'NON_COMPLIANT'
    END                                                   AS sla_status
FROM patch_catalog pc
LEFT JOIN patch_audit_log pal
       ON pal.patch_id = pc.update_id
GROUP BY pc.update_id, pc.priority_score, pc.published_at
ORDER BY pc.published_at DESC;

    Beyond the compliance report, the audit log surfaces operational metrics that feed continuous improvement of the patch policy itself. Rollback rates per patch tier, average dwell time before ring advancement, frequency of soft-trigger false positives — all of these are computable from the log and should be reviewed quarterly to tighten or relax thresholds as the fleet matures.

    22.7 Integrating with Change Management Systems: Autonomous Tickets Without Human Approval

    The autonomous patch pipeline does not operate in a vacuum. Most regulated environments require that every production change be associated with a change record — a ticket in ServiceNow, Jira, or a similar system. The key architectural decision is whether a human must approve that ticket before the patch executes, or whether the ticket is created and auto-approved by policy for patches that meet defined criteria.

    For Tier 1 patches (CVSS-equivalent score ≥ 80, 24-hour SLA), requiring human approval before patching begins is incompatible with the SLA. The system must be authorized to auto-approve via policy and to create the change record as an artifact of what it did, not as a gate to get permission. This requires a formal "pre-authorized change" category in the change management system — a concept that most ITSM platforms support but that must be explicitly negotiated with the change advisory board.

    The integration with ServiceNow's REST API demonstrates the pattern:

    import httpx
import json
from datetime import datetime

SNOW_BASE = "https://your-instance.service-now.com/api/now"
SNOW_AUTH = ("automation_user", "secret")

def create_patch_change_record(
    patch_id: str,
    cve_ids: list[str],
    tier: int,
    affected_clusters: list[str],
    planned_start: datetime,
    planned_end: datetime,
) -> str:
    """
    Creates a ServiceNow change request.
    Tier 1 patches are submitted as pre-authorized (change_type=standard).
    Tier 2 and 3 submit as normal changes and await CAB approval.
    Returns the change request sys_id.
    """
    change_type = "standard" if tier == 1 else "normal"
    approval    = "pre_approved" if tier == 1 else "requested"

    payload = {
        "short_description": f"Autonomous DB Patch: {', '.join(cve_ids)}",
        "description": (
            f"Automated patch deployment initiated by ADE patch orchestrator.\n"
            f"Patch ID: {patch_id}\n"
            f"CVEs addressed: {', '.join(cve_ids)}\n"
            f"Tier: {tier}\n"
            f"Affected clusters: {', '.join(affected_clusters)}\n"
            f"Planned window: {planned_start.isoformat()} – {planned_end.isoformat()}"
        ),
        "type":             change_type,
        "approval":         approval,
        "category":         "Database",
        "risk":             "low" if tier == 1 else "moderate",
        "impact":           "2",   # Medium impact
        "planned_start_date": planned_start.isoformat(),
        "planned_end_date":   planned_end.isoformat(),
        "u_automation_driven": "true",   # Custom field for audit filtering
    }

    resp = httpx.post(
        f"{SNOW_BASE}/table/change_request",
        auth   = SNOW_AUTH,
        json   = payload,
        headers = {"Content-Type": "application/json"},
    )
    resp.raise_for_status()
    sys_id = resp.json()["result"]["sys_id"]
    return sys_id

def close_patch_change_record(sys_id: str, outcome: str, notes: str):
    """Closes the change record with actual outcome after patch completes."""
    close_code = "successful" if outcome == "completed" else "unsuccessful"
    httpx.patch(
        f"{SNOW_BASE}/table/change_request/{sys_id}",
        auth  = SNOW_AUTH,
        json  = {
            "state":      "closed",
            "close_code": close_code,
            "close_notes": notes,
        },
        headers = {"Content-Type": "application/json"},
    )

    The u_automation_driven custom field is load-bearing for compliance: it allows auditors to filter all autonomously-executed changes and review them as a category, rather than having to distinguish them from manually-executed changes by description text. The change management team gets a clean report of every autonomous action, and the CAB can tune the pre-authorized change criteria based on observed outcomes.

    For Tier 2 changes that do require CAB approval, the orchestrator submits the ticket and then polls for approval state before proceeding:

    def wait_for_cab_approval(sys_id: str, timeout_hours: int = 72) -> bool:
    """
    Polls the change record until approved or timeout.
    Returns True if approved, False if rejected or timed out.
    """
    import time
    deadline = time.time() + (timeout_hours * 3600)

    while time.time() < deadline:
        resp = httpx.get(
            f"{SNOW_BASE}/table/change_request/{sys_id}"
            "?sysparm_fields=approval,state",
            auth = SNOW_AUTH,
        )
        record = resp.json()["result"]
        if record["approval"] == "approved":
            return True
        if record["approval"] in ("rejected", "cancelled"):
            return False
        time.sleep(300)  # Poll every 5 minutes

    return False  # Timed out — treat as blocked, not rejected

    A timeout is treated differently from a rejection: a timed-out approval means the CAB did not act within the window, which may itself be an SLA violation on the ITSM side. The orchestrator logs this separately and notifies both the DBA team and the ITSM administrators, rather than silently dropping the patch.

    22.8 Testing the Patch Pipeline: Chaos Injection and Dry-Run Mode

    An autonomous patch pipeline that has never been exercised under failure conditions will fail unpredictably when it encounters one in production. The patch pipeline requires its own test regime: scheduled dry runs that walk the full orchestration path without applying any package changes, and chaos injection tests that deliberately trigger rollback conditions to verify the rollback path executes correctly.

    Dry-run mode is toggled by a single flag threaded through the orchestrator. In dry-run mode, every action that would cause a side effect is replaced by a logged simulation:

    class DryRunPatcher:
    """Drop-in replacement for the real patcher during dry-run execution."""

    def __init__(self, real_patcher):
        self._real = real_patcher

    def apply(self, cluster_id: str, patch_id: str):
        import logging
        version_before = self._real.get_version(cluster_id)
        logging.info(
            f"[DRY-RUN] Would apply {patch_id} to {cluster_id} "
            f"(currently {version_before})"
        )

    def rollback(self, cluster_id: str, patch_id: str):
        import logging
        logging.info(f"[DRY-RUN] Would rollback {patch_id} on {cluster_id}")

    def get_version(self, cluster_id: str) -> str:
        return self._real.get_version(cluster_id)

    def pre_patch_version(self, cluster_id: str, patch_id: str) -> str:
        return self._real.pre_patch_version(cluster_id, patch_id)

    Dry-run mode exercises the full decision logic, the ServiceNow ticket creation (in a non-production SNOW instance), the metrics evaluation, and the ring advancement logic — but touches no database binaries. It should be run weekly in a staging environment against the current patch backlog to verify the pipeline remains functional.

    Chaos injection goes further: it deliberately injects failing conditions into the metrics stream to verify that the rollback evaluator fires correctly and that rollback execution completes within the expected time budget. A chaos test scenario for the hard-trigger path:

    class ChaosMetricsClient:
    """
    Wraps a real metrics client and injects synthetic failures
    at a specified time offset after patch application.
    """
    def __init__(self, real_client, chaos_scenario: dict):
        self._real    = real_client
        self._scenario = chaos_scenario
        self._patch_applied_at = None

    def mark_patch_applied(self):
        from datetime import datetime
        self._patch_applied_at = datetime.utcnow()

    def fetch(self, cluster_id: str) -> dict:
        from datetime import datetime
        real_metrics = self._real.fetch(cluster_id)

        if self._patch_applied_at is None:
            return real_metrics

        elapsed = (datetime.utcnow() - self._patch_applied_at).total_seconds()
        inject_after = self._scenario.get("inject_after_seconds", 120)

        if elapsed >= inject_after:
            for key, value in self._scenario.get("inject_metrics", {}).items():
                real_metrics[key] = value

        return real_metrics

# Example chaos scenario: inject a crash-loop signal 2 minutes after patch
crash_loop_scenario = {
    "inject_after_seconds": 120,
    "inject_metrics": {
        "process_crash_detected": True,
    },
}

# Example chaos scenario: inject sustained latency elevation
latency_scenario = {
    "inject_after_seconds": 60,
    "inject_metrics": {
        "p99_latency_ms": 4500,  # Well above any reasonable baseline
    },
}

    Chaos tests run in a dedicated test environment on a monthly cadence and their results are recorded in the audit log under event_type = 'chaos_test'. A chaos test that does not trigger the expected rollback within the specified time budget is treated as a pipeline defect and blocks the next production patch cycle until resolved. This is the test-as-gate model: the autonomous system must continuously prove its own safety mechanisms work before it is trusted to act autonomously in production.

    Key Takeaways

  • → Patch priority scoring combines CVSS base score, exploit probability (EPSS), and local fleet exposure — treating all CVEs as equal severity leads to alert fatigue and delays action on genuinely dangerous vulnerabilities while wasting resources on theoretical ones.
  • → The ring rollout model gates fleet-wide propagation on dwell-time validation — no ring advances until the previous ring has operated within defined SLI tolerances for the full dwell period, converting patch deployment from a single high-risk event into a series of validated, low-radius steps.
  • → Rollback triggers are stratified into hard triggers (immediate, no override) and soft triggers (hysteresis-gated) — this distinction prevents transient load spikes from causing unnecessary rollbacks while ensuring genuinely dangerous post-patch conditions receive an immediate response without waiting for human review.
  • → Append-only audit logs with privilege-enforced write restrictions provide the evidentiary foundation for autonomous operation in regulated environments — the policy itself becomes the auditable approval artifact, replacing per-change human sign-off with documented, machine-verifiable policy adherence.
  • → Dry-run mode and monthly chaos injection tests verify the rollback path remains functional — an untested autonomous rollback is operationally equivalent to no rollback at all, and the patch pipeline must treat its own safety mechanisms as first-class test subjects with gate conditions that block production use when tests fail.
