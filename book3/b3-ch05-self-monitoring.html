Chapter 5: Self-Monitoring Database Architectures

A database that cannot accurately observe itself cannot govern itself. Before any autonomous system can tune indexes, reroute traffic, or initiate a failover, it must first possess a complete, real-time model of its own operational state — not a snapshot delivered by a human running a query, but a continuous, structured stream of telemetry that flows into decision engines without manual intervention. This chapter builds the architectural foundation for that capability: how to instrument SQL Server for autonomous observability, how to design metric pipelines that survive the failures they are meant to detect, and how to move from passive dashboards to systems that interpret their own signals and act on them.

Instrumentation Architecture: What Autonomous Systems Must Observe

The gap between a monitored database and a self-monitoring one is not a matter of how many metrics you collect — it is a matter of what those metrics are connected to. Passive monitoring tells a human that something is wrong. Autonomous instrumentation provides structured signals to a decision layer that determines what to do without human involvement.

For autonomous operation, database telemetry must satisfy four properties:

1. Completeness — every failure mode the system might encounter has a measurable precursor signal.

2. Timeliness — signals arrive at the decision engine before the failure window closes.

3. Structure — metrics are labeled with enough context (database, instance, workload class, query fingerprint) that automated logic can act on them without ambiguity.

4. Self-referential integrity — the monitoring pipeline itself is monitored; a dead metrics agent must not leave the autonomous engine flying blind.

SQL Server exposes its internal state through a rich set of system catalog views and Dynamic Management Views (DMVs). The critical surfaces for autonomous instrumentation are sys.dm_exec_requests, sys.dm_exec_sessions, sys.dm_os_wait_stats, sys.dm_db_index_usage_stats, sys.dm_exec_query_stats, sys.dm_hadr_availability_replica_states, and the Query Store.

SQL Server does not surface all operationally relevant signals by default. The following query illustrates a foundation metric pull that an autonomous agent executes on a scheduled interval — producing a structured record suitable for ingestion into a time-series store like Prometheus, InfluxDB, or a columnstore staging database.

-- Autonomous baseline telemetry snapshot: connection pressure, blocking, AG lag,
-- and buffer cache efficiency
SELECT
    GETUTCDATE()                                                 AS collected_at,
    (SELECT COUNT(*) FROM sys.dm_exec_requests
     WHERE status = 'running')                                   AS active_requests,
    (SELECT COUNT(*) FROM sys.dm_exec_requests
     WHERE blocking_session_id > 0)                             AS blocked_requests,
    (SELECT COUNT(*) FROM sys.dm_exec_sessions
     WHERE is_user_process = 1
       AND status = 'sleeping'
       AND DATEDIFF(SECOND, last_request_end_time, GETUTCDATE()) > 30) AS idle_sessions_over_30s,
    (SELECT MAX(secondary_lag_seconds)
     FROM sys.dm_hadr_database_replica_states
     WHERE is_primary_replica = 0)                              AS ag_replication_lag_seconds,
    (SELECT CAST(
        (SUM(CASE WHEN physical_reads = 0 THEN 1.0 ELSE 0.0 END) /
         COUNT(*)) * 100 AS DECIMAL(5,2))
     FROM sys.dm_exec_requests
     WHERE status = 'running')                                   AS buffer_hit_proxy_pct,
    (SELECT SUM(cntr_value)
     FROM sys.dm_os_performance_counters
     WHERE counter_name = 'Number of Deadlocks/sec'
       AND instance_name = '_Total')                            AS deadlocks_per_sec;

These snapshots are insufficient on their own. Autonomous systems require delta calculations, moving averages, and anomaly baselines computed over rolling windows — which is why raw metric collection must be paired with a time-series backend. The instrumentation queries provide the raw material; the architecture around them determines whether that material becomes autonomous intelligence.

Building Metric Pipelines That Survive the Failures They Detect

The most dangerous design flaw in any autonomous monitoring architecture is a single-path metric pipeline. If the agent that collects replication lag data runs on the primary node, and the primary node crashes, the autonomous engine loses its replication signal at exactly the moment it is most needed. Every metric pipeline in an autonomous database architecture must be designed with failure-mode independence as a first-order constraint.

The production pattern is a sidecar-plus-external-aggregator topology:

  • → A lightweight collector (Prometheus sql_exporter or a custom PowerShell/Python agent) runs as a sidecar process co-located with each database node — not inside it — and pushes metrics to a remote aggregator.
  • → The aggregator (Prometheus with remote write, VictoriaMetrics, or a columnstore staging database) lives on independent infrastructure with no database dependency.
  • → The decision engine (Alertmanager rules, a custom Python daemon, or a Kubernetes operator) reads from the aggregator and never talks directly to the database node for telemetry.

    *Sidecar-plus-external-aggregator topology: the collector runs alongside each node but the aggregator and decision engine live on independent infrastructure, so a failed primary is still observable.*

    This topology means a failed primary is still observable from the external aggregator, because the replica's sidecar continues emitting. The decision engine sees the primary's metrics go silent at T+30s (scrape interval expiry), which is itself a signal that triggers the autonomous failover evaluation path.

    For SQL Server Always On Availability Groups, this pattern maps onto a distributed collector that queries sys.dm_hadr_availability_replica_states from every replica — not just the primary — so the system maintains a consistent view of the AG topology even during role transitions.

    The following Python agent demonstrates a resilient collection loop with self-healing behavior: if the database connection is lost, the agent emits a db_unreachable metric rather than silently dying.

    import pyodbc
import time
import prometheus_client as prom
from prometheus_client import Gauge, Counter

# --- Metric definitions ---
DB_ACTIVE_CONNECTIONS = Gauge('mssql_active_connections', 'Active user sessions',
                               ['host', 'database'])
DB_AG_SEND_QUEUE      = Gauge('mssql_ag_send_queue_kb', 'Max AG log send queue in KB',
                               ['host'])
DB_UNREACHABLE        = Gauge('mssql_unreachable', '1 if database is unreachable, 0 if healthy',
                               ['host'])
COLLECTION_ERRORS     = Counter('mssql_collection_errors_total', 'Total metric collection failures',
                                ['host'])

COLLECTION_QUERY = """
SELECT
    (SELECT count(*) FROM sys.dm_exec_sessions
      WHERE is_user_process = 1 AND status = 'running') AS active_conn,
    COALESCE(
        (SELECT MAX(log_send_queue_size)
         FROM sys.dm_hadr_database_replica_states), 0
    ) AS send_queue_kb
"""

def collect(host: str, conn_string: str, interval: int = 15):
    """Resilient metric collection loop. Emits mssql_unreachable on failure."""
    prom.start_http_server(9187)
    conn = None

    while True:
        try:
            if conn is None:
                conn = pyodbc.connect(conn_string, timeout=5)
                DB_UNREACHABLE.labels(host=host).set(0)

            with conn.cursor() as cur:
                cur.execute(COLLECTION_QUERY)
                row = cur.fetchone()
                DB_ACTIVE_CONNECTIONS.labels(host=host,
                    database=conn.getinfo(pyodbc.SQL_DATABASE_NAME)).set(row[0])
                DB_AG_SEND_QUEUE.labels(host=host).set(row[1])
                DB_UNREACHABLE.labels(host=host).set(0)

        except pyodbc.Error:
            # Connection lost — mark unreachable so decision engine can act
            DB_UNREACHABLE.labels(host=host).set(1)
            COLLECTION_ERRORS.labels(host=host).inc()
            try:
                conn.close()
            except Exception:
                pass
            conn = None  # Force reconnect on next cycle

        except Exception:
            COLLECTION_ERRORS.labels(host=host).inc()

        time.sleep(interval)

    The mssql_unreachable gauge is not decorative. The autonomous decision engine subscribes to it via Alertmanager and uses it as a trigger condition for failover evaluation — but only after correlating it with replica health signals to distinguish a true primary failure from a network partition affecting only the collector.

    On Windows clusters or Kubernetes, the same pattern uses the community sql_exporter with a job_name: sqlserver target configuration, with separate scrape endpoints per replica in the AG set. The key architectural rule is identical: the metric pipeline must be independent of the components it monitors.

    Autonomous Alerting Logic: From Thresholds to Conditional Decision Trees

    Static thresholds are the lowest form of monitoring intelligence. Setting alert when connections > 200 works until the day you provision a larger instance, add a connection pooler, or change application behavior — at which point the threshold is wrong and nobody updates it. Autonomous systems replace static thresholds with dynamic baselines and conditional decision trees that route different signals to different response actions.

    The architecture has three tiers:

    Tier 1 — Absolute violation alerts (respond immediately, no learning required): AG replica reporting as disconnected, log send queue stalled, disk at > 95% capacity, database engine down. These have no legitimate normal state and the autonomous response is always the same action.

    Tier 2 — Baseline deviation alerts (respond based on deviation from a rolling average): query latency at P99 exceeds 2× the 7-day baseline, connection count exceeds the rolling mean by 3 standard deviations, lock wait time rising at > 20% per minute. The response depends on the magnitude and direction of deviation.

    Tier 3 — Trend projection alerts (act before a threshold is hit): at the current rate of transaction log growth, the log send queue will exceed 10GB in 45 minutes; at the current growth rate, the data volume will exhaust disk in 6 hours. These fire before anything is broken, giving the autonomous system time to act gracefully.

    The following Prometheus alerting rules implement all three tiers for a SQL Server deployment:

    # prometheus/alerts/mssql_autonomous.yml
groups:
  - name: mssql_autonomous_tier1
    rules:
      - alert: MSSQLReplicaDisconnected
        expr: mssql_ag_send_queue_kb > 10485760
              OR absent(mssql_ag_send_queue_kb)
        for: 30s
        labels:
          severity: critical
          autonomous_action: evaluate_failover
        annotations:
          summary: "AG send queue critical or lag signal lost on {{ $labels.host }}"
          action: "Trigger autonomous failover evaluation pipeline"

  - name: mssql_autonomous_tier2
    rules:
      - alert: ConnectionSurgeAboveBaseline
        expr: >
          mssql_active_connections
          > (avg_over_time(mssql_active_connections[7d]) +
             3 * stddev_over_time(mssql_active_connections[7d]))
        for: 2m
        labels:
          severity: warning
          autonomous_action: scale_connection_pool
        annotations:
          summary: "Connection count {{ $value }} exceeds 3σ baseline on {{ $labels.host }}"

  - name: mssql_autonomous_tier3
    rules:
      - alert: AGLogSendQueueTrendCritical
        expr: >
          predict_linear(mssql_ag_send_queue_kb[30m], 2700) > 10737418240
        for: 0s
        labels:
          severity: warning
          autonomous_action: evaluate_replica_health
        annotations:
          summary: >
            "AG send queue on {{ $labels.host }} projected to exceed 10GB
             in 45 minutes"

    The autonomous_action label is not a documentation field — it is read by the Alertmanager webhook receiver and used to route the firing alert to the correct autonomous action handler. When ConnectionSurgeAboveBaseline fires, the webhook calls the connection-pool scaling function. When AGLogSendQueueTrendCritical fires, the handler queries sys.dm_hadr_database_replica_states to identify the lagging replica and evaluates failover or replica removal.

    This label-driven routing means the alert definition and the action it triggers are coupled in a structured, auditable way — which matters enormously when a CTO asks why the system dropped a replication slot at 3am.

    For SQL Server, the equivalent conditional logic lives in SQL Server Agent jobs triggered by WMI alerts, or — in more modern architectures — in Azure Monitor alert action groups that call Azure Automation runbooks. The autonomous action label pattern translates directly: an action group tag autonomous_action: rebuild_fragmented_indexes routes to a runbook that evaluates fragmentation levels and executes ALTER INDEX ... REBUILD with ONLINE = ON during the next maintenance window.

    Columnstore History and SQL Server Temporal Tables as the Autonomous Memory Layer

    Prometheus and Alertmanager handle real-time signal processing well, but they are poor historians. The autonomous decision engine needs more than a 15-second snapshot — it needs to ask: *was this exact query pattern responsible for a similar latency spike six weeks ago, and what resolved it?* That requires a queryable, relational history of database state, and the production solution pairs a columnstore metric-history table with SQL Server temporal tables.

    SQL Server columnstore indexes provide segment elimination and high compression ratios that make multi-month telemetry analytics practical. By routing metric snapshots into a time-partitioned columnstore staging table, the autonomous engine gains the ability to run arbitrary SQL analytics over months of telemetry — and to do so on the same database engine it already operates.

    SQL Server (columnstore table for metric storage):

    -- Schema for autonomous metric history (columnstore, partitioned by time)
CREATE TABLE dbo.db_metrics (
    collected_at          DATETIME2     NOT NULL,
    host                  NVARCHAR(128) NOT NULL,
    database_name         NVARCHAR(128) NOT NULL,
    active_connections    INT,
    ag_send_queue_kb      BIGINT,
    deadlocks             BIGINT,
    idle_session_count    INT,
    p99_query_latency_ms  NUMERIC(10, 3),
    INDEX CCI_db_metrics CLUSTERED COLUMNSTORE
);

-- Hourly P99 latency baseline per host (maintained by a scheduled aggregate job)
CREATE TABLE dbo.db_metrics_hourly (
    bucket               DATETIME2     NOT NULL,
    host                 NVARCHAR(128) NOT NULL,
    avg_connections      FLOAT,
    p99_latency_ms       NUMERIC(10, 3),
    max_send_queue_kb    BIGINT,
    CONSTRAINT PK_db_metrics_hourly PRIMARY KEY (bucket, host)
);

-- Populate hourly baselines from the columnstore history
INSERT INTO dbo.db_metrics_hourly (bucket, host, avg_connections, p99_latency_ms, max_send_queue_kb)
SELECT DATEADD(HOUR, DATEDIFF(HOUR, 0, collected_at), 0),
       host,
       AVG(CAST(active_connections AS FLOAT)),
       PERCENTILE_CONT(0.99) WITHIN GROUP (ORDER BY p99_query_latency_ms),
       MAX(ag_send_queue_kb)
FROM dbo.db_metrics
WHERE collected_at >= DATEADD(HOUR, -1, SYSDATETIME())
GROUP BY DATEADD(HOUR, DATEDIFF(HOUR, 0, collected_at), 0), host;

    For SQL Server, temporal tables provide system-versioned history of any row-level state change. The autonomous engine uses this to maintain a versioned record of configuration decisions — every time an index is rebuilt, a query plan is forced, or a connection pool limit is adjusted, the change is recorded in a temporal table with a valid_from / valid_to timestamp pair. This creates a complete audit trail and enables the system to compare "current configuration" against "configuration at last healthy state."

    -- Temporal table for autonomous configuration change history
CREATE TABLE dbo.AutonomousConfigHistory
(
    config_id         INT             NOT NULL PRIMARY KEY,
    host_name         NVARCHAR(128)   NOT NULL,
    database_name     NVARCHAR(128)   NOT NULL,
    config_key        NVARCHAR(256)   NOT NULL,
    config_value      NVARCHAR(MAX)   NOT NULL,
    changed_by        NVARCHAR(128)   NOT NULL DEFAULT 'autonomous_engine',
    change_reason     NVARCHAR(512),
    valid_from        DATETIME2 GENERATED ALWAYS AS ROW START NOT NULL,
    valid_to          DATETIME2 GENERATED ALWAYS AS ROW END   NOT NULL,
    PERIOD FOR SYSTEM_TIME (valid_from, valid_to)
)
WITH (SYSTEM_VERSIONING = ON (
    HISTORY_TABLE = dbo.AutonomousConfigHistory_History
));

-- Query: what was the max_worker_threads setting during the last major latency incident?
SELECT
    config_key,
    config_value,
    valid_from,
    valid_to,
    change_reason
FROM dbo.AutonomousConfigHistory
FOR SYSTEM_TIME BETWEEN '2024-09-15 02:00:00' AND '2024-09-15 04:00:00'
WHERE host_name = 'sqlprod-01'
  AND config_key = 'max_worker_threads'
ORDER BY valid_from;

    The combination of a columnstore metric-history table and SQL Server temporal tables (for configuration change history) gives the autonomous engine both dimensions of memory it requires: what was the system doing, and what was the system configured to do. Without both, the engine cannot distinguish between a recurring problem and a newly introduced configuration error.

    Closing the Loop: Autonomous Health Scoring and Self-Assessment

    All the instrumentation, pipeline resilience, and alert routing described so far feeds into what is, architecturally, the most important component: the autonomous health score — a single, composite number that the decision engine uses to determine whether the database is in a state where autonomous action is safe to take.

    This is not a vanity dashboard metric. It is the gate that controls whether the autonomous engine operates in observe mode (collect data, take no action), recommend mode (propose actions for human approval), or act mode (execute changes without human sign-off). Getting this wrong in either direction is costly: too conservative and the system never acts; too aggressive and it takes destructive action during a degraded state.

    The health score is computed as a weighted sum of normalized sub-scores across five dimensions:

    | Dimension | Weight | SQL Server Signal |

    |---|---|---|

    | Availability | 30% | AG sync state, sys.dm_hadr_availability_replica_states |

    | Replication health | 25% | AG log send queue, redo queue, synchronization_health_desc |

    | Resource pressure | 20% | Connection utilization, wait stats, CPU pressure, sys.dm_os_ring_buffers |

    | Query performance | 15% | P99 from sys.dm_exec_query_stats vs. 7-day baseline |

    | Configuration drift | 10% | sys.configurations vs. desired-state manifest |

    Each sub-score is a value between 0 and 1. A sub-score of 1.0 means that dimension is operating within its autonomous action bounds. A sub-score below 0.5 suppresses autonomous action for the affected class of operations. A composite score below 0.6 puts the engine in recommend mode. Below 0.4 it alerts a human and halts all autonomous action except safety-critical responses (emergency failover, disk pressure mitigation).

    The following Python function implements this scoring model against a running SQL Server instance:

    import pyodbc
from dataclasses import dataclass
from typing import Dict

@dataclass
class HealthScore:
    composite: float
    sub_scores: Dict[str, float]
    autonomous_mode: str  # 'act', 'recommend', or 'observe'

def compute_mssql_health_score(conn_string: str, baseline: Dict) -> HealthScore:
    """
    Compute a weighted autonomous health score for a SQL Server instance.
    baseline: dict of 7-day rolling averages {
        'p99_latency_ms': float, 'avg_connections': float,
        'connection_budget': float
    }
    """
    scores = {}

    with pyodbc.connect(conn_string) as conn:
        cur = conn.cursor()

        # --- Availability (30%) ---
        cur.execute("""
            SELECT COUNT(*)
            FROM sys.dm_hadr_availability_replica_states
            WHERE role_desc = 'SECONDARY'
              AND synchronization_health_desc = 'HEALTHY'
        """)
        healthy_replicas = cur.fetchone()[0]
        scores['availability'] = min(1.0, healthy_replicas / 1.0)  # Expect >=1

        # --- Replication health (25%) ---
        cur.execute("""
            SELECT COALESCE(MAX(log_send_queue_size + redo_queue_size), 0)
            FROM sys.dm_hadr_database_replica_states
        """)
        lag_kb = cur.fetchone()[0] or 0
        # Score: 1.0 at 0 KB queued, decays linearly to 0 at 10 GB queued
        scores['replication'] = max(0.0, 1.0 - (lag_kb / 10485760.0))

        # --- Resource pressure (20%) ---
        cur.execute("""
            SELECT COUNT(*) FROM sys.dm_exec_sessions
            WHERE is_user_process = 1 AND status = 'running'
        """)
        active = cur.fetchone()[0]
        budget = baseline.get('connection_budget', 500)
        scores['resource_pressure'] = max(0.0, 1.0 - (active / budget))

        # --- Query performance (15%) ---
        cur.execute("""
            SELECT COALESCE(
                MAX(total_elapsed_time * 1.0 / NULLIF(execution_count, 0)) / 1000.0, 0
            )
            FROM sys.dm_exec_query_stats
        """)
        p99 = cur.fetchone()[0] or 0.0
        baseline_p99 = baseline.get('p99_latency_ms', p99 or 1.0)
        ratio = p99 / baseline_p99 if baseline_p99 > 0 else 1.0
        # Score: 1.0 at or below baseline, decays linearly to 0 at 2x baseline
        scores['query_performance'] = max(0.0, min(1.0, 1.0 - (ratio - 1.0)))

        # --- Configuration drift (10%) ---
        cur.execute("""
            SELECT COUNT(*) FROM sys.configurations
            WHERE value <> value_in_use
        """)
        drift_count = cur.fetchone()[0]
        scores['configuration_drift'] = max(0.0, 1.0 - (drift_count / 10.0))

    weights = {
        'availability': 0.30,
        'replication': 0.25,
        'resource_pressure': 0.20,
        'query_performance': 0.15,
        'configuration_drift': 0.10,
    }
    composite = sum(scores[k] * weights[k] for k in weights)

    if composite >= 0.6:
        mode = 'act'
    elif composite >= 0.4:
        mode = 'recommend'
    else:
        mode = 'observe'

    return HealthScore(composite=composite, sub_scores=scores, autonomous_mode=mode)

    The scoring thresholds above (0.6 for act mode, 0.4 for recommend mode) are starting points, not fixed constants — they must be tuned against a specific environment's actual incident history. A team adopting this model should treat the initial thresholds as a hypothesis and validate them against months of historical health-score-versus-incident data before trusting the gate in production.

    The health score's real value is not the number itself but what it gates: it is the single decision point that separates "the system is confident enough to act" from "the system should defer to a human." Every autonomous action described elsewhere in this book should, in a mature implementation, check this gate — or an equivalent one — before executing.

    Key Takeaways

  • → Self-monitoring is not more metrics — it is metrics with structure, timeliness, and self-referential integrity, so a dead collector doesn't leave the autonomous engine reasoning from stale or absent data.
  • → Metric pipelines must be architecturally independent of the components they observe: a sidecar-plus-external-aggregator topology ensures a failed primary is still visible to the decision engine, because the signal path doesn't run through the primary itself.
  • → Static thresholds degrade as workloads change; dynamic baselines (rolling averages, standard deviation bands) and trend-projection alerts (predict_linear) let the system detect both current violations and problems that haven't happened yet.
  • → Columnstore metric history and SQL Server temporal tables give the autonomous engine two distinct kinds of memory — what the system was doing, and what it was configured to do — and both are necessary to distinguish a recurring problem from a newly introduced misconfiguration.
  • → A composite, weighted health score is the gate that determines whether the system operates in observe, recommend, or act mode; the weights and thresholds must be tuned to the specific environment rather than treated as universal defaults.
