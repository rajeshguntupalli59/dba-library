Chapter 4: Telemetry, Metrics, and Data Required for Autonomy

An autonomous database system is only as intelligent as the data it can see about itself. Before any self-healing loop executes, before any workload gets rerouted, before any index gets dropped or any connection pool gets resized — the system must first observe its own state with enough fidelity to make a sound decision. This chapter is about building that observational foundation: the telemetry pipelines, metric taxonomies, and contextual data structures that transform a passively monitored database into a fully aware autonomous engine. Getting this layer right is the prerequisite for everything else in this book. Getting it wrong means your autonomous actions will be based on incomplete or misleading signals — and autonomous actions taken on bad data are worse than no action at all.

4.1 The Telemetry Taxonomy: What Autonomous Systems Actually Need to See

Most monitoring stacks are built for humans — dashboards, alerts, on-call pages. Autonomous systems need something different: structured, timestamped, low-latency signal feeds that can be ingested by decision engines without human interpretation. Before touching a single query or Prometheus scrape config, the autonomous database architect needs a taxonomy of what categories of data actually drive autonomous decisions.

The four layers of database telemetry are:

1. Resource telemetry — CPU, memory, disk I/O, network throughput, and storage capacity at both the OS and database engine level. These are necessary but not sufficient. An autonomous system that reacts only to CPU spikes is a basic autoscaler, not an autonomous database.

2. Engine-internal metrics — buffer cache hit ratios, lock wait chains, transaction throughput, index maintenance progress, checkpoint frequency, transaction log flush throughput, query plan cache hit rates, and replication lag. These metrics describe what the database engine itself is experiencing, independent of what the hardware is doing.

3. Workload telemetry — query-level execution data: individual query durations, I/O reads per query, wait events, plan changes over time, and parameter distributions. This is the layer most monitoring systems underinvest in, and it's where the highest-value autonomous decisions live.

4. State and topology telemetry — cluster membership, replica health, failover readiness, connection pool saturation, and schema version state. Autonomous systems cannot safely act without understanding the current topology — promoting a standby without knowing whether it's actually current is a path to split-brain.

Each layer feeds different decision classes. Resource telemetry drives scaling and capacity decisions. Engine-internal metrics drive tuning and maintenance scheduling. Workload telemetry drives query optimization and plan pinning. State telemetry drives failover and topology management. A production autonomous system maintains all four layers simultaneously, with different collection frequencies appropriate to each.

The engine-internal layer lives in Dynamic Management Views (DMVs), the sys catalog views, the Query Store, and the Extended Events system — plus the transaction log subsystem for durability telemetry. These are your primary observational surfaces — everything else is derived from them.

4.2 Instrumenting SQL Server for Machine-Readable Metric Collection

The distinction between a monitoring-friendly database and an autonomy-ready database comes down to whether your metric collection is designed for human dashboards or for programmatic consumption. Autonomous systems need metrics that are timestamped precisely, labeled with enough dimensional context to drive decisions, and collected at frequencies that match the dynamics of the phenomena they describe.

#### SQL Server: Core Metric Surfaces

The sys.dm_exec_requests and sys.dm_exec_sessions DMVs are the primary source for real-time workload visibility. For autonomous systems, the critical fields are wait_type, wait_time, status, start_time, and query_hash. Querying these DMVs every 5–10 seconds and persisting the results gives your decision engine a timeline of what the database was doing at any moment.

-- Equivalent workload snapshot using DMVs
-- Designed for programmatic collection; include in a scheduled job or monitoring agent
SELECT
    GETUTCDATE()                                              AS collected_at,
    r.session_id,
    s.login_name,
    s.program_name,
    s.host_name,
    r.status,
    r.wait_type,
    r.wait_time / 1000.0                                     AS wait_time_seconds,
    r.total_elapsed_time / 1000.0                            AS elapsed_seconds,
    r.logical_reads,
    r.writes,
    r.cpu_time / 1000.0                                      AS cpu_seconds,
    qt.text                                                  AS query_text,
    qp.query_plan
FROM sys.dm_exec_requests r
JOIN sys.dm_exec_sessions s ON r.session_id = s.session_id
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle)  qt
CROSS APPLY sys.dm_exec_query_plan(r.plan_handle) qp
WHERE r.session_id != @@SPID
  AND s.is_user_process = 1
ORDER BY r.total_elapsed_time DESC;

These snapshots are the raw feed. They become useful to an autonomous system only when they're persisted with timestamps and queryable across time. A clustered columnstore table in SQL Server is appropriate for storing these at scale. The autonomous decision engine then queries the history, not just the present-moment snapshot.

#### Structured Metric Emission with DMVs and Query Store

For workload telemetry at the query level, sys.dm_exec_query_stats and the Query Store are the authoritative sources. These surfaces aggregate execution statistics per normalized query, giving you mean execution time, standard deviation, total I/O, and call count — exactly the inputs needed to identify regression candidates for autonomous tuning.

-- Query Store equivalent for regression detection
-- Surfaces queries with high average duration and significant variability
SELECT TOP 50
    GETUTCDATE()                                              AS collected_at,
    qs.query_id,
    qt.query_sql_text,
    qp.plan_id,
    rs.count_executions,
    ROUND(rs.avg_duration / 1000.0, 3)                       AS avg_duration_ms,
    ROUND(rs.stdev_duration / 1000.0, 3)                     AS stdev_duration_ms,
    ROUND(rs.avg_logical_io_reads, 0)                        AS avg_logical_reads,
    ROUND(rs.avg_cpu_time / 1000.0, 3)                       AS avg_cpu_ms,
    rs.last_execution_time
FROM sys.query_store_query qs
JOIN sys.query_store_query_text qt ON qs.query_text_id = qt.query_text_id
JOIN sys.query_store_plan qp       ON qs.query_id = qp.query_id
JOIN sys.query_store_runtime_stats rs ON qp.plan_id = rs.plan_id
WHERE rs.last_execution_time > DATEADD(MINUTE, -10, GETUTCDATE())
  AND rs.count_executions > 5
ORDER BY rs.avg_duration DESC;

The delta pattern is important here: you capture a snapshot, store it, capture the next snapshot 60 seconds later, and compute the difference in calls, total_exec_time, and I/O. This gives you per-interval throughput rates rather than cumulative totals, which is what decision logic actually needs. A query whose avg_ms jumps from 12ms to 340ms between two consecutive snapshots is a regression event — and that event should trigger autonomous investigation without waiting for a human to notice a dashboard spike.

4.3 Building a Real-Time Telemetry Pipeline with Prometheus, OpenTelemetry, and SQL Server Columnstore

Raw metric collection from database views is only half the architecture. Those metrics need to flow into a storage and query layer that the autonomous decision engine can interrogate in real time. The canonical stack is Prometheus + sql_exporter for scraping, combined with a SQL Server columnstore staging database for long-retention analytical queries and Alertmanager as a trigger surface for autonomous actions.

#### Prometheus Exporter Configuration

The sql_exporter from the Prometheus community exposes DMV output as Prometheus metrics. Its custom query capability is what makes it useful for autonomous systems — you can expose any DMV query you need, not just the defaults.

# custom_queries.yaml — extend sql_exporter for autonomy-relevant metrics
mssql_ag_lag:
  query: |
    SELECT ag.name AS ag_name,
           ar.replica_server_name,
           ISNULL(drs.log_send_queue_size, 0) AS send_queue_kb,
           ISNULL(drs.redo_queue_size, 0)     AS redo_queue_kb
    FROM sys.availability_groups ag
    JOIN sys.availability_replicas ar
      ON ag.group_id = ar.group_id
    LEFT JOIN sys.dm_hadr_database_replica_states drs
      ON ar.replica_id = drs.replica_id
  metrics:
    - ag_name:
        usage: "LABEL"
    - replica_server_name:
        usage: "LABEL"
    - send_queue_kb:
        usage: "GAUGE"
        description: "Log send queue in KB"
    - redo_queue_kb:
        usage: "GAUGE"
        description: "Redo queue in KB"

mssql_long_running_queries:
  query: |
    SELECT COUNT(*) AS count
    FROM sys.dm_exec_requests
    WHERE session_id > 50
      AND total_elapsed_time > 30000
  metrics:
    - count:
        usage: "GAUGE"
        description: "Number of queries running longer than 30 seconds"

mssql_index_fragmentation:
  query: |
    SELECT DB_NAME(ips.database_id) AS database_name,
           OBJECT_NAME(ips.object_id, ips.database_id) AS table_name,
           MAX(ips.avg_fragmentation_in_percent) AS max_fragmentation_pct
    FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') ips
    WHERE ips.page_count > 10000
    GROUP BY ips.database_id, ips.object_id
  metrics:
    - database_name:
        usage: "LABEL"
    - table_name:
        usage: "LABEL"
    - max_fragmentation_pct:
        usage: "GAUGE"
        description: "Worst index fragmentation; trigger autonomous maintenance at threshold"

This YAML feeds directly into the sql_exporter collector configuration. The index fragmentation metric is particularly important: when max_fragmentation_pct exceeds 30% on an index with more than 10,000 pages, the autonomous maintenance engine should schedule a targeted ALTER INDEX ... REORGANIZE or REBUILD for that specific index — not a database-wide rebuild, and not an alert to a human. This is what machine-readable telemetry enables: surgical, targeted autonomous action.

#### Alertmanager as an Autonomous Trigger Surface

Most teams use Alertmanager to page engineers. In an autonomous architecture, Alertmanager fires webhooks that trigger autonomous action scripts, not pagers. The alert becomes an event in the autonomous decision pipeline, not a notification.

# alertmanager.yml — route database alerts to autonomous action endpoint
route:
  group_by: ['alertname', 'database', 'instance']
  group_wait: 10s
  group_interval: 30s
  repeat_interval: 5m
  receiver: 'autonomous-action-handler'
  routes:
    - match:
        alertname: MSSQLAGLagHigh
      receiver: 'autonomous-failover-handler'
      continue: false
    - match:
        alertname: MSSQLLongRunningQueryDetected
      receiver: 'autonomous-query-killer'
      continue: false
    - match:
        alertname: MSSQLIndexFragmentationHigh
      receiver: 'autonomous-index-maintenance'
      continue: false

receivers:
  - name: 'autonomous-action-handler'
    webhook_configs:
      - url: 'http://ade-controller:8080/api/v1/action'
        send_resolved: true
        http_config:
          bearer_token: "${ADE_WEBHOOK_TOKEN}"

  - name: 'autonomous-failover-handler'
    webhook_configs:
      - url: 'http://ade-controller:8080/api/v1/failover'
        send_resolved: false

  - name: 'autonomous-query-killer'
    webhook_configs:
      - url: 'http://ade-controller:8080/api/v1/terminate-query'
        send_resolved: false

  - name: 'autonomous-index-maintenance'
    webhook_configs:
      - url: 'http://ade-controller:8080/api/v1/schedule-index-maintenance'
        send_resolved: true
graph LR
    T[Resource / Engine / Workload / State Telemetry] --> E[sql_exporter]
    E --> P[Prometheus TSDB]
    P --> AM[Alertmanager]
    AM -->|MSSQLAGLagHigh| F[autonomous-failover-handler]
    AM -->|MSSQLLongRunningQueryDetected| K[autonomous-query-killer]
    AM -->|MSSQLIndexFragmentationHigh| V[autonomous-index-maintenance]
    F --> C[ADE Controller]
    K --> C
    V --> C

*The telemetry pipeline: four layers of raw signal flow through exporters into Prometheus, where Alertmanager routes classified alerts to webhook handlers instead of a pager.*

The ADE controller at http://ade-controller:8080 is the autonomous decision engine — a service (covered in detail in Chapter 7) that receives webhook payloads from Alertmanager, validates the trigger conditions against a second source of truth, and executes the appropriate action. The double-check against a second source is non-negotiable: acting on a single metric signal without validation is how autonomous systems cause outages.

4.4 Wait Event Analysis: The Highest-Signal Metric Category for Autonomous Diagnosis

Wait events are the most information-dense signal category in any relational database engine. A CPU spike tells you that something is consuming CPU. A wait event tells you why the database is blocked — whether it's waiting for a lock held by another transaction, waiting for a buffer to be read from disk, waiting for network I/O to complete, or waiting for a transaction log write to harden. This distinction is what separates a monitoring system from an autonomous diagnostic system.

In SQL Server, wait events are surfaced in sys.dm_exec_requests.wait_type and aggregated in sys.dm_os_wait_stats. The taxonomy includes LCK_M_* (locking), PAGEIOLATCH_* (data file I/O), CXPACKET / CXCONSUMER (parallelism), SOS_SCHEDULER_YIELD (CPU pressure), WRITELOG (transaction log throughput), and HADR_* (availability replica sync) categories. Each category implies a different autonomous response.

The autonomous decision tree for SQL Server wait events looks like this:

  • → **LCK_M_* (locks): Sessions are blocked on locks. Autonomous action: identify the blocker via blocking_session_id in sys.dm_exec_requests, evaluate its age and importance, and if it exceeds the threshold (e.g., >120 seconds with >5 blocked waiters), kill the blocking session.
  • → PAGEIOLATCH_* / PAGEIO_* (I/O): Sessions are waiting for data to be read from disk. Autonomous action: warm the buffer pool for the hot table, evaluate max server memory headroom, and flag for capacity review if sustained.
  • → WRITELOG: High transaction log write contention. Autonomous action: verify the log file sits on dedicated low-latency storage, check for autogrowth stalls, and consider delayed durability for workloads that tolerate it — without compromising durability for committed transactions.
  • → THREADPOOL / worker starvation**: Worker threads are exhausted. Autonomous action: check max worker threads against current utilization and hunt the blocking chains consuming workers before raising any ceiling.
    • -- Wait type aggregation with autonomous action classification
-- Run on a schedule; compare delta between snapshots for rate-of-change analysis
WITH wait_stats AS (
    SELECT
        wait_type,
        waiting_tasks_count,
        wait_time_ms,
        max_wait_time_ms,
        signal_wait_time_ms,
        wait_time_ms - signal_wait_time_ms                  AS resource_wait_time_ms
    FROM sys.dm_os_wait_stats
    WHERE wait_type NOT IN (
        -- Exclude benign background waits
        'SLEEP_TASK', 'BROKER_TO_FLUSH', 'BROKER_TASK_STOP',
        'CLR_AUTO_EVENT', 'DISPATCHER_QUEUE_SEMAPHORE',
        'FT_IFTS_SCHEDULER_IDLE_WAIT', 'HADR_WORK_QUEUE',
        'HADR_FILESTREAM_IOMGR_IOCOMPLETION', 'ONDEMAND_TASK_QUEUE',
        'REQUEST_FOR_DEADLOCK_SEARCH', 'RESOURCE_QUEUE',
        'SERVER_IDLE_CHECK', 'SLEEP_DBSTARTUP', 'SLEEP_DBRECOVER',
        'SLEEP_MASTERDBREADY', 'SLEEP_MASTERMDREADY',
        'SLEEP_MASTERUPGRADED', 'SLEEP_MSDBSTARTUP',
        'SLEEP_SYSTEMTASK', 'SLEEP_TEMPDBSTARTUP',
        'SNI_HTTP_ACCEPT', 'SP_SERVER_DIAGNOSTICS_SLEEP',
        'SQLTRACE_BUFFER_FLUSH', 'WAITFOR', 'XE_DISPATCHER_WAIT',
        'XE_TIMER_EVENT', 'BROKER_EVENTHANDLER', 'CHECKPOINT_QUEUE',
        'DBMIRROR_EVENTS_QUEUE', 'SQLTRACE_INCREMENTAL_FLUSH_SLEEP',
        'WAIT_XTP_OFFLINE_CKPT_NEW_LOG'
    )
)
SELECT TOP 20
    wait_type,
    waiting_tasks_count,
    ROUND(wait_time_ms / 1000.0, 2)                         AS wait_time_seconds,
    ROUND(resource_wait_time_ms / 1000.0, 2)                AS resource_wait_seconds,
    ROUND(
        CASE WHEN waiting_tasks_count > 0
             THEN wait_time_ms * 1.0 / waiting_tasks_count
             ELSE 0 END, 2)                                  AS avg_wait_ms_per_task,
    CASE
        WHEN wait_type LIKE 'LCK_%'
             AND waiting_tasks_count > 20                   THEN 'INVESTIGATE_LOCK_CHAIN'
        WHEN wait_type = 'PAGEIOLATCH_SH'
             AND wait_time_ms > 30000                       THEN 'REVIEW_BUFFER_POOL_AND_IO'
        WHEN wait_type = 'WRITELOG'
             AND wait_time_ms > 10000                       THEN 'REVIEW_LOG_IO_SUBSYSTEM'
        WHEN wait_type = 'RESOURCE_SEMAPHORE'               THEN 'EVALUATE_MEMORY_GRANT'
        WHEN wait_type = 'THREADPOOL'                       THEN 'EVALUATE_MAX_WORKER_THREADS'
        WHEN wait_type LIKE 'HADR_%'
             AND wait_time_ms > 5000                        THEN 'CHECK_AG_REPLICA_HEALTH'
        ELSE 'MONITOR'
    END                                                     AS recommended_action
FROM wait_stats
ORDER BY wait_time_ms DESC;

    The recommended_action column in these queries is the bridge between metric and decision. An autonomous system ingests this output, reads the action class, and dispatches to the appropriate handler. This pattern — embedding decision logic directly in metric queries — is a valid approach for low-complexity decision rules, and it keeps the logic close to the data where it belongs.

    4.5 Contextual State Data: Topology, Schema, and Configuration Telemetry

    Metrics about query performance and wait events are meaningless without context about the system's current topology and configuration state. An autonomous action that's perfectly correct for a primary with three healthy replicas may be catastrophically wrong during a failover event. The autonomous system must always know the current state of the world before acting — and that state includes cluster topology, current role (primary or replica), schema version, and the effective value of every configuration parameter the decision logic depends on.

    -- Availability Group role and replica-count snapshot
SELECT
    ars.role_desc,
    (SELECT COUNT(*) FROM sys.dm_hadr_availability_replica_states) AS replica_state_rows,
    SERVERPROPERTY('ProductVersion')              AS product_version
FROM sys.dm_hadr_availability_replica_states ars
WHERE ars.is_local = 1;

    Configuration state — the effective, running values of options like max server memory, max degree of parallelism, or cost threshold for parallelism — must be polled from sys.configurations rather than assumed from a baseline document, because a pending RECONFIGURE or a Resource Governor override can make the baseline and the running state diverge. An autonomous system that reads its configuration baseline instead of sys.configurations is reasoning about a state that may no longer be true.

    Schema version telemetry — tracking which migration has been applied, via a migrations table or a tool like Flyway or Sqitch — matters because an autonomous system evaluating whether to create an index or adjust a query plan needs to know it's looking at the schema it thinks it's looking at, not a version mid-migration. Combining topology, configuration, and schema-version telemetry with the performance and wait-event data from earlier sections gives the decision engine the complete picture it needs before it acts.

    Key Takeaways

  • → Autonomous systems need telemetry across four layers — resource, engine-internal, workload, and state/topology — and each layer feeds a different class of decision; a system missing any one layer has a blind spot in its corresponding decision class.
  • → sys.dm_exec_requests, sys.dm_exec_query_stats, and Query Store are the primary machine-readable surfaces; snapshotting them on a schedule and computing deltas between snapshots is what turns cumulative counters into actionable rate-of-change signals.
  • → Wait event data is the highest-signal category for autonomous diagnosis because it explains why a session is blocked, not just that resource utilization is elevated — and it maps directly to a bounded set of recommended actions per wait category.
  • → Prometheus with custom exporter queries, and Alertmanager routed to webhook-driven action handlers rather than pagers, form a practical reference pipeline for turning raw telemetry into autonomous triggers — with a second-source validation step before any action executes.
  • → No metric is safe to act on in isolation from topology and configuration context; the same signal can call for opposite actions depending on whether the target is a primary or a replica, or whether a schema migration is in flight.
