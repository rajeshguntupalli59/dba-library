Chapter 31: Multi-Cloud Autonomous Database Operations

Operating a database fleet across AWS, Azure, and GCP simultaneously is not a distribution problem — it is a control problem. When your PostgreSQL clusters run on RDS in us-east-1 while your SQL Server Always On groups span Azure East US and West Europe, and your analytical replicas live in BigQuery-adjacent AlloyDB on GCP, the question is never "can these systems communicate?" It is "who decides, and how fast?" This chapter addresses the architecture of autonomous control planes that span cloud providers, treating each cloud as an execution zone rather than a decision-maker. An ADE operating in multi-cloud must detect cross-cloud latency degradation, reroute workloads, failover replicas, and rebalance connection pools — all without waiting for a human to open a console.

---

Topology Modeling: Representing Multi-Cloud Database Fleets as a Control Graph

Before any autonomous action is possible, the system must have a precise, machine-readable model of its own topology. A database fleet is not a list of hostnames — it is a directed graph where nodes are database instances and edges carry properties: replication lag in milliseconds, network RTT, cost-per-GB of data transfer, and current health state.

The autonomous control plane maintains this graph in a metadata store — typically a strongly consistent key-value system like etcd or Consul — with updates pushed by health agents running as sidecars to every database node. Each agent emits a heartbeat every five seconds carrying latency samples, replication offset, and a local cluster state hash. The control plane ingests these events and continuously recomputes the topology graph.

-- Topology registry in the control plane SQL Server database
CREATE TABLE dbo.db_topology (
    node_id               UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWSEQUENTIALID(),
    cloud_provider        NVARCHAR(10) NOT NULL
                          CHECK (cloud_provider IN ('aws','azure','gcp')),
    region                NVARCHAR(64) NOT NULL,
    availability_zone     NVARCHAR(64) NULL,
    role                  NVARCHAR(20) NOT NULL
                          CHECK (role IN ('primary','replica','arbiter')),
    cluster_id            UNIQUEIDENTIFIER NOT NULL,
    replication_lag_ms    DECIMAL(10,3) NULL,
    network_rtt_ms        DECIMAL(10,3) NULL,
    data_transfer_cost_per_gb DECIMAL(10,6) NULL,
    health_state          NVARCHAR(20) NOT NULL DEFAULT 'healthy'
                          CHECK (health_state IN ('healthy','degraded','failed','unknown')),
    last_seen             DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    metadata              NVARCHAR(MAX) NULL  -- JSON payload
);

-- Filtered index for failover candidate selection
CREATE INDEX IX_topology_failover_candidates
    ON dbo.db_topology (cluster_id, replication_lag_ms)
    INCLUDE (region, cloud_provider, node_id)
    WHERE health_state = 'healthy' AND role = 'replica';

-- Cross-cloud health summary
SELECT
    c.cluster_name,
    n.cloud_provider,
    SUM(CASE WHEN n.health_state = 'healthy'  THEN 1 ELSE 0 END) AS healthy_nodes,
    SUM(CASE WHEN n.health_state = 'degraded' THEN 1 ELSE 0 END) AS degraded_nodes,
    SUM(CASE WHEN n.health_state = 'failed'   THEN 1 ELSE 0 END) AS failed_nodes,
    MAX(n.replication_lag_ms)                                     AS max_lag_ms,
    AVG(n.network_rtt_ms)                                         AS avg_rtt_ms
FROM dbo.db_topology n
JOIN dbo.db_clusters c ON c.cluster_id = n.cluster_id
GROUP BY c.cluster_name, n.cloud_provider;

The graph model must encode cross-cloud edge costs. AWS us-east-1 to Azure East US carries roughly 30–50 ms RTT under normal conditions, but that number degrades predictably during specific BGP routing events. The autonomous system does not treat RTT as a static constant — it maintains a rolling 95th-percentile window of observed RTT per edge, updated every 60 seconds. When the p95 RTT on a replication channel exceeds 200 ms for three consecutive windows, the system classifies that edge as degraded and begins pre-positioning a promotion candidate in the lower-latency cloud zone.

The topology graph also feeds cost-awareness into autonomous decisions. Transferring 1 TB of WAL from AWS to GCP costs real money. The control plane embeds egress cost coefficients per provider pair and incorporates them into promotion scoring. A replica in Azure West Europe that is 20 ms slower than a GCP replica but saves $0.09/GB in egress cost will be preferred for promotion in non-latency-sensitive workloads — but only if RPO targets are still satisfiable.

Cross-Cloud Replication Architecture: pglogical, SQL Server AG, and the Async Bridge

Synchronous replication across clouds is architecturally problematic. A commit that must be acknowledged by a replica in a different cloud introduces 30–150 ms of forced write latency on every transaction. For most production workloads this is unacceptable. The autonomous multi-cloud architecture instead relies on asynchronous replication with continuous lag monitoring and dynamic RPO enforcement.

For PostgreSQL, pglogical provides logical replication that operates across version boundaries and cloud providers without requiring the shared WAL assumptions of physical streaming replication. The autonomous system deploys pglogical subscriptions from each cloud's regional primary to the others, treating each cloud as a logical subscriber set.

A critical architectural point: the control plane must distinguish between replication lag caused by network congestion versus lag caused by transaction volume. Both look identical in pg_stat_replication lag readings, but they demand different responses. Network-induced lag requires rerouting; volume-induced lag requires subscriber scaling or workload throttling. The autonomous system classifies lag cause by cross-correlating replication lag rate-of-change against the primary's WAL generation rate:

import psycopg2
import time
from dataclasses import dataclass
from typing import Optional

@dataclass
class LagDiagnosis:
    lag_ms: float
    wal_generation_rate_bytes_per_sec: float
    cause: str  # 'network' | 'volume' | 'subscriber_overload' | 'unknown'
    recommended_action: str

def diagnose_replication_lag(
    primary_dsn: str,
    subscriber_node_id: str,
    sample_interval_sec: int = 30
) -> LagDiagnosis:
    conn = psycopg2.connect(primary_dsn)
    cur = conn.cursor()

    def sample():
        cur.execute("""
            SELECT
                EXTRACT(EPOCH FROM write_lag) * 1000  AS lag_ms,
                pg_wal_lsn_diff(pg_current_wal_lsn(), sent_lsn) AS unsent_bytes,
                pg_wal_lsn_diff(sent_lsn, replay_lsn)           AS unacked_bytes
            FROM pg_stat_replication
            WHERE application_name = %s
        """, (subscriber_node_id,))
        return cur.fetchone()

    s1 = sample()
    time.sleep(sample_interval_sec)
    s2 = sample()

    if s1 is None or s2 is None:
        return LagDiagnosis(0, 0, 'unknown', 'verify_subscriber_connection')

    lag_ms         = s2[0] or 0
    wal_rate       = (s2[1] - s1[1]) / sample_interval_sec  # bytes/sec growth
    unacked_delta  = s2[2] - s1[2]  # growing means subscriber can't keep up

    if lag_ms < 100:
        cause  = 'acceptable'
        action = 'none'
    elif wal_rate > 50_000_000 and unacked_delta > 0:
        # Primary generating >50 MB/s WAL and unacked queue growing
        cause  = 'volume'
        action = 'throttle_writes_or_scale_subscriber'
    elif wal_rate < 5_000_000 and lag_ms > 500:
        # Low WAL generation but high lag → network is the bottleneck
        cause  = 'network'
        action = 'reroute_replication_channel_or_promote_closer_replica'
    else:
        cause  = 'subscriber_overload'
        action = 'restart_logical_worker_or_increase_wal_receiver_timeout'

    conn.close()
    return LagDiagnosis(lag_ms, wal_rate, cause, action)

For SQL Server, Always On Availability Groups spanning Azure regions use the asynchronous commit mode for cross-region replicas — a requirement, not an option. The autonomous control plane monitors sys.dm_hadr_database_replica_states continuously and enforces a lag SLO: if the secondary's redo_queue_size exceeds 512 MB for more than 90 seconds, the system triggers a workload throttle on the primary, reducing batch sizes in flight from application connection pools.

-- Autonomous lag monitoring query executed by the control plane every 30s
SELECT
    ag.name                                              AS ag_name,
    ar.replica_server_name,
    ar.availability_mode_desc,
    drs.database_id,
    DB_NAME(drs.database_id)                             AS database_name,
    drs.synchronization_state_desc,
    drs.redo_queue_size / 1024.0                         AS redo_queue_mb,
    drs.log_send_queue_size / 1024.0                     AS send_queue_mb,
    drs.secondary_lag_seconds,
    -- Compute breach: redo queue > 512 MB for enforcement threshold
    CASE
        WHEN drs.redo_queue_size > 524288 THEN 'BREACH_THROTTLE'
        WHEN drs.redo_queue_size > 262144 THEN 'WARNING'
        ELSE 'OK'
    END AS lag_policy_state
FROM sys.dm_hadr_availability_replica_states drs
JOIN sys.availability_replicas ar
    ON ar.replica_id = drs.replica_id
JOIN sys.availability_groups ag
    ON ag.group_id = ar.group_id
WHERE drs.is_local = 0  -- remote replicas only
ORDER BY drs.redo_queue_size DESC;

The autonomous bridge between PostgreSQL and SQL Server heterogeneous environments often uses Debezium as a CDC layer, with the control plane consuming change events from Kafka topics to maintain derived read replicas on the opposite engine. This pattern supports read-only cross-engine analytics without requiring synchronous writes to cross over the network boundary.

Autonomous Failover Orchestration Across Cloud Boundaries

A multi-cloud failover is categorically different from a single-cloud failover. In a single-cloud promotion, the control plane promotes a replica, updates DNS or load balancer routing rules, and reconfigures surviving replicas to follow the new primary — all within the same API surface. In a multi-cloud failover, the promotion itself may need to cross API boundaries: promoting an RDS read replica to a standalone instance requires AWS RDS API calls, while simultaneously updating an Azure Traffic Manager endpoint and reconfiguring a GCP Cloud DNS weighted record.

The autonomous orchestrator handles this through a cloud-agnostic action abstraction layer. Each cloud provider exposes a driver implementing a common interface: promote_replica(), update_routing_endpoint(), scale_connection_pool(), notify_health_check(). The orchestrator composes these across providers without hardcoding provider-specific logic into the decision engine.

The failover decision itself follows a deterministic scoring algorithm. When the primary becomes unreachable (confirmed by three independent health probers across different networks to avoid split-brain), the orchestrator evaluates all healthy replicas against the following scoring function:

promotion_score = (1 / replication_lag_ms) * 0.45
                + (1 / network_rtt_to_app_tier_ms) * 0.30
                + (1 / data_transfer_cost_per_gb) * 0.15
                + (disaster_zone_diversity_score) * 0.10

Weights are tunable per cluster profile. A cluster serving a latency-sensitive payment API weights RTT at 0.50 and cost at 0.05. A batch analytics cluster inverts those weights. The profile is stored in the topology metadata and loaded at orchestrator startup.

import boto3
import requests
from typing import List, Dict, Any
import logging

logger = logging.getLogger("failover_orchestrator")

PROVIDER_DRIVERS = {
    "aws":   __import__("drivers.aws_driver",   fromlist=["AWSDriver"]).AWSDriver,
    "azure": __import__("drivers.azure_driver", fromlist=["AzureDriver"]).AzureDriver,
    "gcp":   __import__("drivers.gcp_driver",   fromlist=["GCPDriver"]).GCPDriver,
}

def score_candidate(replica: Dict[str, Any], profile: Dict[str, float]) -> float:
    lag    = max(replica["replication_lag_ms"], 0.1)      # avoid division by zero
    rtt    = max(replica["network_rtt_to_app_ms"], 0.1)
    cost   = max(replica["data_transfer_cost_per_gb"], 0.001)
    divers = replica.get("disaster_zone_diversity_score", 0.5)

    return (
        (1 / lag)    * profile.get("lag_weight",   0.45) +
        (1 / rtt)    * profile.get("rtt_weight",   0.30) +
        (1 / cost)   * profile.get("cost_weight",  0.15) +
        divers       * profile.get("diversity_weight", 0.10)
    )

def execute_cross_cloud_failover(
    failed_primary: Dict[str, Any],
    candidates: List[Dict[str, Any]],
    profile: Dict[str, float],
    routing_config: Dict[str, Any]
) -> Dict[str, Any]:
    # Score and rank candidates
    ranked = sorted(
        candidates,
        key=lambda r: score_candidate(r, profile),
        reverse=True
    )
    winner = ranked[0]
    logger.info(
        f"Selected promotion candidate: {winner['node_id']} "
        f"in {winner['cloud_provider']}/{winner['region']} "
        f"with score {score_candidate(winner, profile):.4f}"
    )

    # Invoke cloud-specific promotion
    driver_cls = PROVIDER_DRIVERS[winner["cloud_provider"]]
    driver     = driver_cls(region=winner["region"])
    driver.promote_replica(replica_id=winner["node_id"])

    # Update routing layer in parallel across all clouds
    for cloud, endpoint_config in routing_config["endpoints"].items():
        rd = PROVIDER_DRIVERS[cloud](region=endpoint_config["region"])
        rd.update_routing_endpoint(
            endpoint_id=endpoint_config["id"],
            target_host=winner["hostname"],
            target_port=winner["port"]
        )
        logger.info(f"Routing updated in {cloud}: {endpoint_config['id']} → {winner['hostname']}")

    # Reconfigure surviving replicas to follow new primary
    survivors = [r for r in candidates if r["node_id"] != winner["node_id"]]
    for replica in survivors:
        rd = PROVIDER_DRIVERS[replica["cloud_provider"]](region=replica["region"])
        rd.reconfigure_replica(
            replica_id=replica["node_id"],
            new_primary_host=winner["hostname"],
            new_primary_port=winner["port"]
        )

    return {
        "status":       "completed",
        "new_primary":  winner["node_id"],
        "cloud":        winner["cloud_provider"],
        "region":       winner["region"],
        "failed_nodes": [failed_primary["node_id"]],
    }

A non-obvious failure mode in cross-cloud failover is DNS propagation lag. Even with a TTL of 30 seconds, resolvers across cloud providers cache aggressively. The autonomous system mitigates this by using connection string rewriting at the pgBouncer or SQL Server connection proxy layer rather than relying solely on DNS. When the orchestrator promotes a new primary, it pushes an updated pgbouncer.ini to all regional PgBouncer pools via its configuration API within seconds of the promotion completing, bypassing DNS entirely for in-flight connections.

graph TD

    Z[Azure Node] -->|heartbeat + lag| CP

*The cross-cloud failover path: topology telemetry feeds a scoring function, residency constraints act as a hard pre-filter, and only then does the orchestrator acquire a lease and promote.*

Autonomous Cost Governance and Workload Placement Across Clouds

Multi-cloud autonomy without cost governance is infrastructure debt on autopilot. An autonomous system that can freely promote replicas, spin up read nodes, or reroute traffic across cloud providers must also evaluate the cost consequence of every action it takes and every state it creates.

The ADE implements continuous cost attribution at the workload level, not the infrastructure level. This distinction matters: knowing that an EC2 instance costs $0.48/hour is infrastructure billing. Knowing that the nightly ETL job running on that instance generates 2.3 TB of cross-cloud egress at $0.09/GB — $207 per run — is workload attribution. The autonomous system optimizes the latter.

The autonomous workload placement engine runs a nightly optimization pass over these cost logs and proposes — or directly applies, depending on governance mode — workload migrations. A query pattern generating heavy cross-cloud egress is a candidate for read replica promotion in the destination cloud, eliminating the egress path entirely.

Governance mode determines whether the system applies changes autonomously or generates a change proposal requiring human approval. This is configured per cluster tier:

  • → **Tier 0 (critical)**: Failover is autonomous, cost optimizations require approval within 4 hours or auto-apply
  • → **Tier 1 (standard)**: All autonomous actions except schema changes apply immediately
  • → **Tier 2 (batch/analytics)**: Fully autonomous including workload rescheduling and replica scaling

    • Terraform is the enforcement layer for infrastructure-level decisions. When the autonomous system determines that a GCP read replica should be promoted to serve a workload currently pulling data from AWS, it generates a Terraform plan, validates it against a policy library (using OPA — Open Policy Agent), and applies it if no policy violations exist.

    #!/usr/bin/env bash
# Autonomous Terraform apply with OPA policy gate
# Called by control plane when workload placement change is decided

set -euo pipefail

PLAN_FILE="$1"         # Path to terraform plan JSON
POLICY_DIR="$2"        # OPA policy bundle path
TF_DIR="$3"            # Terraform working directory
APPROVAL_REQUIRED="$4" # 'yes' for Tier 0, 'no' for Tier 1+

echo "[$(date -u +%Y-%m-%dT%H:%M:%SZ)] Evaluating plan: ${PLAN_FILE}"

# Convert Terraform plan to JSON for OPA evaluation
terraform -chdir="${TF_DIR}" show -json "${PLAN_FILE}" > /tmp/tf_plan.json

# OPA policy evaluation
OPA_RESULT=$(opa eval \
    --data "${POLICY_DIR}" \
    --input /tmp/tf_plan.json \
    "data.database.placement.allow" \
    --format raw)

if [ "${OPA_RESULT}" != "true" ]; then
    echo "[BLOCKED] OPA policy denied this placement change."
    opa eval \
        --data "${POLICY_DIR}" \
        --input /tmp/tf_plan.json \
        "data.database.placement.deny_reasons" \
        --format pretty
    exit 1
fi

echo "[APPROVED] OPA policy passed."

if [ "${APPROVAL_REQUIRED}" == "yes" ]; then
    echo "[PENDING] Tier 0 cluster — queuing for human review within 4 hours."
    # Post to approval queue (Slack webhook, PagerDuty, or internal API)
    curl -s -X POST "${APPROVAL_WEBHOOK_URL}" \
         -H "Content-Type: application/json" \
         -d "{\"plan_file\": \"${PLAN_FILE}\", \"expires_in\": 14400}"
    exit 0
fi

echo "[APPLYING] Autonomous apply in progress..."
terraform -chdir="${TF_DIR}" apply -auto-approve "${PLAN_FILE}"
echo "[DONE] Infrastructure change applied autonomously."

    Observability Unification: A Single Pane Across AWS CloudWatch, Azure Monitor, and GCP Operations

    Autonomous systems cannot act on signals they cannot see. When your database fleet spans three clouds, each cloud's native observability stack captures a partial truth: CloudWatch knows about RDS instance metrics, Azure Monitor knows about SQL MI wait stats, and GCP Cloud Monitoring knows about AlloyDB storage I/O. None of them knows about the others, and none of them can correlate a cascading latency event that starts as a BGP hiccup in AWS, manifests as replication lag in Azure, and surfaces as query timeout spikes in GCP thirty seconds later.

    The autonomous observability layer solves this by pulling metrics from all three provider APIs into a unified time-series store — typically Prometheus with remote write, Victoria Metrics for long-term retention, or a self-managed InfluxDB cluster — and tagging every metric with a common schema: cloud_provider, region, cluster_id, node_id, role. Every alert rule and every autonomous decision operates against this unified schema, never against provider-native metric names.

    PostgreSQL (metrics ingestion tracking table):

    -- Unified metrics ingestion log: track staleness per provider
CREATE TABLE metrics_ingestion_status (
    provider       TEXT NOT NULL,
    region         TEXT NOT NULL,
    metric_family  TEXT NOT NULL,  -- e.g. 'replication_lag', 'query_latency'
    last_ingested  TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (provider, region, metric_family)
);

-- Alert view: staleness is computed at query time, not stored — now() is not
-- IMMUTABLE, so it cannot appear in a GENERATED ALWAYS AS ... STORED expression
CREATE VIEW stale_metric_sources AS
SELECT
    provider, region, metric_family,
    EXTRACT(EPOCH FROM (now() - last_ingested)) AS ingestion_lag_sec
FROM metrics_ingestion_status
WHERE EXTRACT(EPOCH FROM (now() - last_ingested)) > 120
ORDER BY ingestion_lag_sec DESC;
    -- Equivalent ingestion tracking for SQL Server control plane
CREATE TABLE dbo.metrics_ingestion_status (
    provider        NVARCHAR(16) NOT NULL,
    region          NVARCHAR(64) NOT NULL,
    metric_family   NVARCHAR(64) NOT NULL,
    last_ingested   DATETIMEOFFSET NOT NULL,
    -- Not PERSISTED: SYSDATETIMEOFFSET() is non-deterministic, and SQL Server
    -- only allows PERSISTED on deterministic computed column expressions.
    ingestion_lag_sec AS DATEDIFF(SECOND, last_ingested, SYSDATETIMEOFFSET()),
    is_stale        AS CAST(
                        CASE WHEN DATEDIFF(SECOND, last_ingested, SYSDATETIMEOFFSET()) > 120
                             THEN 1 ELSE 0 END AS BIT),
    CONSTRAINT PK_metrics_ingestion PRIMARY KEY (provider, region, metric_family)
);

-- Stale source alert query
SELECT provider, region, metric_family, ingestion_lag_sec
FROM dbo.metrics_ingestion_status
WHERE is_stale = 1
ORDER BY ingestion_lag_sec DESC;

    The ingestion agents for each provider run as lightweight Go services — one per cloud account — using the provider's native SDK to pull metrics on a 30-second cadence and write them to the central Prometheus remote-write endpoint. When an ingestion agent detects that it has not received a successful response from CloudWatch for more than 90 seconds, it emits a synthetic metric: metrics_source_reachable{provider="aws", region="us-east-1"} 0. The autonomous control plane treats a source-unreachable condition as elevated uncertainty — it does not make failover decisions based on the last known stale state of an unreachable node. Instead, it pauses autonomous promotion of nodes in that cloud until independent health probers — running from the other two clouds — confirm the situation.

    This is the multi-cloud version of the quorum problem: you need at least two independent observers to agree on a node's state before acting on it. The control plane enforces this by requiring confirmation from probers in at least two distinct cloud providers before classifying any node as failed rather than unknown.

    from enum import Enum
from typing import Dict, List
import logging

logger = logging.getLogger("health_classifier")

class NodeState(str, Enum):
    HEALTHY  = "healthy"
    DEGRADED = "degraded"
    UNKNOWN  = "unknown"
    FAILED   = "failed"

def classify_node_state(
    probe_results: Dict[str, bool],   # {"aws": True, "azure": False, "gcp": False}
    current_state: NodeState,
    consecutive_failure_count: int
) -> NodeState:
    """
    Require confirmation from at least two independent cloud probers before
    declaring FAILED. This prevents split-brain promotion during network partitions
    that isolate a single prober cloud.
    """
    reporting_failed = [cloud for cloud, reachable in probe_results.items()
                        if not reachable]
    reporting_healthy = [cloud for cloud, reachable in probe_results.items()
                         if reachable]

    if len(reporting_healthy) >= 2:
        # Majority of independent probers see the node as reachable
        return NodeState.HEALTHY

    if len(reporting_failed) >= 2 and consecutive_failure_count >= 3:
        # Two or more independent clouds cannot reach it, across three check cycles
        logger.warning(
            f"Node classified FAILED: failed from {reporting_failed}, "
            f"consecutive_count={consecutive_failure_count}"
        )
        return NodeState.FAILED

    if len(reporting_failed) >= 1:
        # Only one cloud sees it failing — could be prober-side partition
        logger.info(
            f"Node classified UNKNOWN: single-cloud failure from {reporting_failed}"
        )
        return NodeState.UNKNOWN

    return NodeState.DEGRADED

    For dashboarding, the unified observability layer exposes a single Grafana datasource pointing at the central time-series store. The dashboard hierarchy mirrors the topology graph: fleet view → cluster view → node view → query view. At the fleet level, the primary KPIs are cross-cloud replication health, inter-cloud RTT percentiles, and cost-per-query by cloud pair. Autonomous system actions — failovers, workload migrations, replica scaling events — are annotated directly onto the timeline panels using Grafana's annotation API, called by the orchestrator immediately after each action completes. This makes the history of autonomous decisions visible at exactly the time coordinates where they occurred, allowing retrospective analysis without log correlation.

    Conflict Resolution in Distributed Autonomous Systems

    When autonomous agents in multiple clouds can each initiate actions independently, the risk is not inaction — it is concurrent conflicting action. Two agents simultaneously deciding that the same replica should be promoted, one from the AWS control plane instance and one from the GCP instance, can result in a split-brain topology: two nodes both believing themselves to be primary, both accepting writes, with no replication relationship between them.

    The solution is a distributed lease system. Before any autonomous agent initiates a topology-changing action, it must acquire a lease on the target cluster's control record. Leases are stored in a strongly consistent, distributed key-value store — etcd is the standard choice — with a TTL of 30 seconds. If the agent fails or becomes partitioned mid-action, the lease expires and another agent can safely take over.

    import etcd3
import uuid
import time
from contextlib import contextmanager

etcd_client = etcd3.client(host="etcd-control-plane.internal", port=2379)

@contextmanager
def acquire_cluster_lease(cluster_id: str, agent_id: str, ttl_sec: int = 30):
    """
    Distributed lease for cluster-level topology operations.
    Raises RuntimeError if lease cannot be acquired (another agent holds it).
    """
    lease_key  = f"/ade/cluster_lease/{cluster_id}"
    lease_val  = agent_id.encode()

    # Attempt atomic put-if-not-exists
    lease   = etcd_client.lease(ttl_sec)
    success, _ = etcd_client.transaction(
        compare=[etcd_client.transactions.version(lease_key) == 0],
        success=[etcd_client.transactions.put(lease_key, lease_val, lease)],
        failure=[]
    )

    if not success:
        existing, _ = etcd_client.get(lease_key)
        holder = existing.decode() if existing else "unknown"
        raise RuntimeError(
            f"Cannot acquire lease for cluster {cluster_id}: held by agent {holder}"
        )

    logger.info(f"Lease acquired: cluster={cluster_id} agent={agent_id} ttl={ttl_sec}s")
    try:
        yield lease
    finally:
        etcd_client.revoke_lease(lease.id)
        logger.info(f"Lease released: cluster={cluster_id} agent={agent_id}")

    Beyond lease management, the autonomous system maintains a global action log — an append-only record of every decision made, the state at the time of the decision, the expected outcome, and the observed outcome after a verification window. This log serves three purposes: it provides an audit trail for compliance review, it feeds the reinforcement-learning layer that adjusts decision weights over time, and it enables rollback analysis when an autonomous action produces an unexpected state.

    CREATE TABLE dbo.autonomous_action_log (
    action_id           UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWSEQUENTIALID(),
    initiated_at        DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    agent_id            NVARCHAR(128) NOT NULL,
    cloud_provider      NVARCHAR(16)  NOT NULL,
    cluster_id          UNIQUEIDENTIFIER NOT NULL,
    action_type         NVARCHAR(64)  NOT NULL,
    target_node_id      UNIQUEIDENTIFIER NULL,
    decision_inputs     NVARCHAR(MAX) NULL,  -- JSON
    expected_outcome    NVARCHAR(MAX) NULL,  -- JSON
    observed_outcome    NVARCHAR(MAX) NULL,  -- JSON, populated post-verification
    outcome_verified_at DATETIMEOFFSET NULL,
    status              NVARCHAR(20) NOT NULL DEFAULT 'in_progress'
                        CHECK (status IN ('in_progress','completed','failed','rolled_back')),
    rollback_action_id  UNIQUEIDENTIFIER NULL
                        REFERENCES dbo.autonomous_action_log(action_id)
);

-- Filtered index for learning pipeline queries
CREATE INDEX IX_action_log_learning
    ON dbo.autonomous_action_log (action_type, initiated_at)
    INCLUDE (cluster_id, decision_inputs, observed_outcome)
    WHERE status = 'completed' AND observed_outcome IS NOT NULL;

    The verification window — typically five minutes after an action completes — is when the control plane re-samples the affected cluster's health metrics and compares them against the expected outcome recorded at decision time. If the observed state diverges from expected by more than a configurable threshold (for example, post-promotion replication lag remains above 1,000 ms when the expected outcome was below 200 ms), the system escalates: either triggering a rollback procedure or, if rollback is not safe, paging an on-call engineer with the full decision trace attached.

    Regulatory Compliance and Data Residency in Autonomous Cross-Cloud Operations

    Autonomous systems that can freely move data and reroute workloads across cloud regions run directly into data residency regulations: GDPR constrains EU personal data from leaving the EU economic area, certain financial regulators require transaction logs to remain within national borders, and healthcare data in some jurisdictions cannot traverse public cloud infrastructure without explicit sovereign cloud designation.

    The autonomous system must encode these constraints as hard guardrails — not soft preferences — that override any cost or latency optimization. A constraint violation is not a sub-optimal outcome; it is a compliance failure with legal consequences. This means residency constraints must be evaluated before the scoring function runs, not as an additional term within it.

    CREATE TABLE dbo.residency_policies (
    policy_id           UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWSEQUENTIALID(),
    cluster_id          UNIQUEIDENTIFIER NOT NULL,
    data_classification NVARCHAR(64) NOT NULL,
    allowed_regions     NVARCHAR(MAX) NOT NULL,  -- JSON array
    allowed_providers   NVARCHAR(MAX) NOT NULL,  -- JSON array
    enforce_at_write    BIT NOT NULL DEFAULT 1,
    enforce_at_read     BIT NOT NULL DEFAULT 1,
    regulation_ref      NVARCHAR(128) NULL,
    created_at          DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET()
);

-- Inline compliance check in failover candidate query
SELECT
    n.node_id,
    n.cloud_provider,
    n.region,
    n.replication_lag_ms,
    CASE
        WHEN JSON_VALUE(rp.allowed_providers, '$[0]') IS NULL THEN 1
        -- Simplified: full evaluation uses OPENJSON for array membership
        WHEN n.cloud_provider IN (
            SELECT value FROM OPENJSON(rp.allowed_providers)
        )
        AND n.region IN (
            SELECT value FROM OPENJSON(rp.allowed_regions)
        ) THEN 1
        ELSE 0
    END AS is_residency_compliant
FROM dbo.db_topology n
LEFT JOIN dbo.residency_policies rp
    ON rp.cluster_id = n.cluster_id
WHERE n.health_state = 'healthy'
  AND n.role = 'replica';

    The autonomous orchestrator applies residency filtering as a hard pre-filter: any candidate node that fails is_node_residency_compliant() is removed from the candidate set before scoring begins. If the pre-filter eliminates all candidates — that is, no compliant replica exists — the orchestrator does not fall back to a non-compliant node. It instead escalates to a human operator with a clear incident description: the cluster cannot autonomously recover without violating data residency constraints, and human intervention is required to either provision a compliant replica or authorize a temporary exception through a documented override workflow.

    This design reflects a principle that underlies all autonomous database engineering in regulated environments: the system's autonomy stops at the boundary of legal constraint. Autonomy is an operational property, not a compliance bypass.

    Key Takeaways

  • → **Topology modeling as a control graph is the foundation of multi-cloud autonomy.** Without a continuously updated, strongly consistent graph of nodes, edges, replication lag, and cost properties, every autonomous decision is based on stale or incomplete state. The graph is not a dashboard artifact — it is the primary data structure the control plane operates against.
  • → **Cross-cloud replication lag has two distinct causes that require different autonomous responses.** Volume-induced lag demands write throttling or subscriber scaling; network-induced lag demands replication channel rerouting or replica promotion to a lower-latency zone. Conflating the two leads to interventions that worsen the situation rather than resolving it.
  • → **Multi-cloud failover requires a cloud-agnostic action abstraction layer and distributed lease management.** Provider-specific promotion APIs must be hidden behind a uniform driver interface, and every topology-changing action must be gated on a distributed lease to prevent concurrent conflicting promotions from independent agents running in different clouds.
  • → **Unified observability across CloudWatch, Azure Monitor, and GCP Operations requires a common tagging schema and source-reachability tracking.** Metrics ingestion staleness is itself a signal: when a cloud's metrics source becomes unreachable, the autonomous system must treat affected nodes as `unknown` rather than acting on last-known state, and must require independent confirmation from probers in at least two cloud providers before classifying any node as `failed`.
  • → **Data residency constraints are hard guardrails that override all cost and latency optimization.** The autonomous orchestrator must evaluate regulatory policy compliance as a pre-filter that eliminates non-compliant candidates before the scoring function runs, and must escalate to human operators — rather than falling back to a non-compliant replica — when no compliant failover target exists.
