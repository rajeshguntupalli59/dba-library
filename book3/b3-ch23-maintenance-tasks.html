Chapter 23: Self-Managing Maintenance Tasks

Maintenance is where autonomous systems prove their worth most visibly. Index rebuild and reorganize cycles, statistics refreshes, log archival, partition management — these are tasks that senior DBAs have spent decades scheduling manually, tuning reactively, and debugging at 2 a.m. when they collide with peak workload. An autonomous maintenance engine eliminates that pattern entirely: it observes the state of every object in the catalog, models the cost of action against the cost of inaction, and executes maintenance at the optimal moment with zero human scheduling overhead. This chapter builds that engine — from the feedback loops that drive autonomous statistics and index management, to the partition lifecycle systems that provision and retire data without operator involvement, to the production-grade governance layer that keeps autonomous actions auditable and reversible.

23.1 The Maintenance Decision Loop: Observation, Costing, and Scheduling

Before any autonomous system can manage maintenance, it needs a principled model for when maintenance is worth doing — not just whether it is overdue. Scheduled maintenance (weekly index rebuilds, manual statistics updates) fails in high-throughput environments because it ignores current workload, lock contention probability, and the actual degradation rate of the objects it targets. The autonomous alternative is a continuous decision loop: measure object health, estimate the cost of immediate action, compare it against projected degradation cost, and schedule or defer accordingly.

The loop runs on a tight polling cycle (typically 60–300 seconds) and feeds a priority queue. Each candidate maintenance action carries three attributes: urgency score (how degraded is the object now), execution cost (estimated I/O, lock wait, duration), and opportunity window (how clear is the current workload). The system acts when urgency × opportunity exceeds execution cost. This is not metaphor — it translates directly into evaluable expressions over catalog metrics.

Maintenance candidate scoring — using index fragmentation and page density:

-- SQL Server: maintenance candidate scoring
-- Combines index fragmentation, page density, and recent rebuild history
SELECT
    OBJECT_SCHEMA_NAME(i.object_id)    AS schema_name,
    OBJECT_NAME(i.object_id)           AS table_name,
    i.name                             AS index_name,
    ips.avg_fragmentation_in_percent,
    ips.avg_page_space_used_in_percent,
    ips.page_count,
    -- Urgency score: fragmentation weighted by page count
    ROUND(
        ips.avg_fragmentation_in_percent
        * ips.page_count / 1000.0, 2
    )                                  AS urgency_score,
    -- Last maintenance from job history proxy
    maint.last_run_datetime            AS last_rebuilt
FROM sys.indexes i
CROSS APPLY sys.dm_db_index_physical_stats(
    DB_ID(), i.object_id, i.index_id, NULL, 'LIMITED'
) ips
LEFT JOIN (
    SELECT
        j.name,
        MAX(CAST(h.run_date AS CHAR(8)) + ' ' +
            STUFF(STUFF(RIGHT('000000' + CAST(h.run_time AS VARCHAR), 6),
            5, 0, ':'), 3, 0, ':')) AS last_run_datetime
    FROM msdb.dbo.sysjobs j
    JOIN msdb.dbo.sysjobhistory h ON j.job_id = h.job_id
    WHERE h.step_id = 0 AND h.run_status = 1
    GROUP BY j.name
) maint ON maint.name LIKE '%' + OBJECT_NAME(i.object_id) + '%'
WHERE i.type > 0
  AND ips.page_count > 500
  AND ips.avg_fragmentation_in_percent > 5
ORDER BY urgency_score DESC;

The output from these views feeds a Python scheduler that maintains the priority queue. The scheduler enforces two constraints before acting: a workload gate (active sessions below threshold, no long-running transactions older than N minutes) and a maintenance budget (maximum concurrent maintenance operations, rolling I/O ceiling). When both constraints pass and the top-priority candidate clears the cost threshold, the action fires.

23.2 Autonomous Statistics Management in SQL Server

SQL Server's automatic statistics update is often mistaken for autonomous maintenance — it is actually a reactive threshold mechanism that fires when roughly 20% of rows (plus 500) have changed since the last update. On a billion-row table, that means 200 million modifications before statistics refresh; on high-velocity OLTP tables the threshold perpetually lags behind the workload. A truly autonomous statistics engine replaces the static threshold with modification-velocity tracking driven by real-time catalog state.

The architecture has two layers. The first layer is a catalog monitor that tracks per-table modification velocity: the rate at which modification_counter grows per minute of wall clock time, read from sys.dm_db_stats_properties. Tables with high velocity need more frequent updates than stable reference tables. The second layer is a statistics dispatcher that issues targeted UPDATE STATISTICS ... WITH FULLSCAN (or a calibrated sample) on a computed schedule, ahead of the automatic threshold — effectively making auto-update statistics the fallback rather than the primary mechanism.

Statistics staleness detection — identifying statistics whose modification ratio has crossed the velocity-adjusted threshold:

-- Autonomous statistics staleness detection
-- Run by the maintenance engine; feeds the dispatch priority queue
SELECT
    OBJECT_SCHEMA_NAME(o.object_id)        AS schema_name,
    OBJECT_NAME(o.object_id)               AS table_name,
    s.name                                 AS stats_name,
    sp.last_updated,
    sp.rows,
    sp.modification_counter,
    ROUND(sp.modification_counter * 1.0
          / NULLIF(sp.rows, 0) * 100, 2)    AS modification_pct,
    -- Velocity-adjusted threshold: large tables get a tighter band
    CASE
        WHEN sp.rows > 100000000 THEN 2.0    -- 100M+ rows: 2%
        WHEN sp.rows > 10000000  THEN 5.0    -- 10M+ rows: 5%
        ELSE 10.0                             -- smaller: 10%
    END                                      AS stale_threshold_pct,
    CASE
        WHEN sp.modification_counter * 1.0 / NULLIF(sp.rows, 0) * 100 >
             CASE
                 WHEN sp.rows > 100000000 THEN 2.0
                 WHEN sp.rows > 10000000  THEN 5.0
                 ELSE 10.0
             END THEN 'UPDATE_REQUIRED'
        ELSE 'OK'
    END                                      AS dispatch_decision
FROM sys.stats s
JOIN sys.objects o ON o.object_id = s.object_id
CROSS APPLY sys.dm_db_stats_properties(s.object_id, s.stats_id) sp
WHERE o.type = 'U'
  AND s.auto_created = 0
  AND sp.modification_counter > 1000
ORDER BY sp.modification_counter * 1.0 / NULLIF(sp.rows, 0) DESC;

Beyond scheduled refreshes, the autonomous engine must also decide when to escalate from an online REORGANIZE to an offline-capable REBUILD — the most consequential maintenance decision in SQL Server. An offline rebuild holds a schema-modification lock that blocks all access to the table. The rule is: never escalate to a non-online rebuild during business hours, never on indexes serving queries averaging more than 100 concurrent sessions, and only when fragmentation exceeds a threshold that makes reorganization economically unjustified (typically >30% fragmentation with >1 GB of affected pages).

The Python component that implements this escalation gate queries active session counts before firing:

# Autonomous rebuild escalation engine
# Checks the workload gate before issuing REBUILD on high-fragmentation indexes

import pyodbc
from datetime import datetime, time as dt_time

CONN_STR = ("DRIVER={ODBC Driver 18 for SQL Server};SERVER=sqlprimary;"
            "DATABASE=AppDB;UID=maintenance_role;PWD=*******;")
FRAG_PCT_THRESHOLD  = 30.0
PAGE_COUNT_MIN      = 131072   # ~1 GB in 8 KB pages
MAX_ACTIVE_SESSIONS = 20
MAINTENANCE_WINDOW  = (dt_time(1, 0), dt_time(5, 0))  # 01:00–05:00 UTC

def within_maintenance_window():
    now = datetime.utcnow().time()
    return MAINTENANCE_WINDOW[0] <= now <= MAINTENANCE_WINDOW[1]

def get_active_session_count(conn):
    cur = conn.cursor()
    cur.execute("""
        SELECT COUNT(*)
        FROM sys.dm_exec_sessions
        WHERE is_user_process = 1 AND status = 'running'
    """)
    return cur.fetchone()[0]

def get_rebuild_candidates(conn):
    cur = conn.cursor()
    cur.execute("""
        SELECT OBJECT_SCHEMA_NAME(ips.object_id) AS schema_name,
               OBJECT_NAME(ips.object_id)        AS table_name,
               i.name                            AS index_name,
               ips.avg_fragmentation_in_percent,
               ips.page_count
        FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') ips
        JOIN sys.indexes i
          ON ips.object_id = i.object_id AND ips.index_id = i.index_id
        WHERE ips.avg_fragmentation_in_percent > ?
          AND ips.page_count > ?
          AND i.type > 0
        ORDER BY ips.page_count DESC
    """, FRAG_PCT_THRESHOLD, PAGE_COUNT_MIN)
    return cur.fetchall()

def run_resumable_rebuild(conn, schema, table, index):
    stmt = (f"ALTER INDEX [{index}] ON [{schema}].[{table}] "
            "REBUILD WITH (ONLINE = ON, RESUMABLE = ON, MAX_DURATION = 120 MINUTES)")
    conn.execute(stmt)
    print(f"[{datetime.utcnow().isoformat()}] Rebuild issued: {schema}.{table}.{index}")

def main():
    if not within_maintenance_window():
        print("Outside maintenance window — skipping escalation check.")
        return

    conn = pyodbc.connect(CONN_STR, autocommit=True)
    active = get_active_session_count(conn)
    if active > MAX_ACTIVE_SESSIONS:
        print(f"Active sessions={active} exceeds gate={MAX_ACTIVE_SESSIONS} — deferring.")
        return

    for schema, table, index, frag, pages in get_rebuild_candidates(conn):
        print(f"Escalating to REBUILD: {schema}.{table}.{index} "
              f"({frag:.1f}% fragmented, {pages // 128} MB)")
        run_resumable_rebuild(conn, schema, table, index)

    conn.close()

if __name__ == "__main__":
    main()

The same autonomous statistics management pattern applies to plan regressions. High-throughput OLTP tables should receive statistics updates independently from index maintenance — particularly when Query Store detects a plan regression. A spike in mean execution time on a query that previously was stable indicates stale statistics before any system alert fires. The maintenance engine monitors the Query Store regression signal and issues targeted UPDATE STATISTICS on the tables involved in those queries.

23.3 Autonomous Index Lifecycle Management

Index management is the maintenance task most likely to accumulate technical debt in manual operations. DBAs add indexes reactively (fixing a slow query), never audit whether the index is still used, and rarely rebuild fragmented ones on a principled schedule. The autonomous index lifecycle engine handles all three phases — creation, fragmentation remediation, and retirement — without human initiation.

Index creation is covered in detail in the query optimization chapter, but the maintenance layer adds a constraint: any autonomously created index must be tracked in a dba_autonomous_indexes registry table, stamped with the query pattern that justified it, and subject to a 30-day usage review. If sys.dm_db_index_usage_stats shows zero user seeks or scans in 30 days, the index is a retirement candidate.

Fragmentation remediation is where the maintenance engine makes daily decisions. The threshold logic is explicit:

  • → Fragmentation < 10%: no action
  • → Fragmentation 10–30%: REORGANIZE on a background schedule
  • → Fragmentation > 30%: REBUILD, subject to the workload gate

    • Autonomous index remediation — REORGANIZE vs REBUILD decision:

    -- SQL Server: autonomous index maintenance decision
-- Emits the correct action (REORGANIZE vs REBUILD) per fragmentation band
SELECT
    OBJECT_SCHEMA_NAME(ips.object_id)           AS schema_name,
    OBJECT_NAME(ips.object_id)                  AS table_name,
    i.name                                      AS index_name,
    ips.avg_fragmentation_in_percent,
    ips.page_count,
    CASE
        WHEN ips.avg_fragmentation_in_percent BETWEEN 10 AND 30
            THEN
                'ALTER INDEX ' + QUOTENAME(i.name)
                + ' ON ' + QUOTENAME(OBJECT_SCHEMA_NAME(ips.object_id))
                + '.' + QUOTENAME(OBJECT_NAME(ips.object_id))
                + ' REORGANIZE;'
        WHEN ips.avg_fragmentation_in_percent > 30
            THEN
                'ALTER INDEX ' + QUOTENAME(i.name)
                + ' ON ' + QUOTENAME(OBJECT_SCHEMA_NAME(ips.object_id))
                + '.' + QUOTENAME(OBJECT_NAME(ips.object_id))
                + ' REBUILD WITH (ONLINE = ON, RESUMABLE = ON,'
                + ' MAX_DURATION = 120 MINUTES);'
        ELSE 'No action required.'
    END                                         AS maintenance_action
FROM sys.dm_db_index_physical_stats(
    DB_ID(), NULL, NULL, NULL, 'LIMITED'
) ips
JOIN sys.indexes i
    ON ips.object_id = i.object_id
   AND ips.index_id  = i.index_id
WHERE i.type > 0
  AND ips.page_count > 200
  AND ips.avg_fragmentation_in_percent > 10
ORDER BY ips.avg_fragmentation_in_percent DESC;

    The RESUMABLE = ON clause on SQL Server rebuilds is a requirement, not a nicety, in autonomous systems. A resumable rebuild that gets interrupted by a workload spike or failover does not lose its progress — it pauses and resumes at next opportunity. The autonomous scheduler checks sys.index_resumable_operations on each maintenance cycle and resumes any paused operations if the workload gate passes.

    Index retirement follows a conservative pattern: the engine marks unused indexes as DEFERRED_DROP in the registry, disables (rather than drops) them for a 14-day observation window, verifies no plan regressions appear (via plan cache monitoring), and only then executes the drop. This staged approach means no autonomously managed index drop can produce an irreversible performance regression.

    23.4 Automated Partition Lifecycle: Provisioning, Migrating, and Retiring Partitions

    Partition management is one of the most operationally demanding maintenance tasks in large-scale databases — and one of the most amenable to full automation. A time-partitioned table growing at 50 GB/day needs new partitions created before the current period ends, old partitions detached and archived on retention schedule, and tablespace placement managed as storage tiers change. Done manually across dozens of tables, this is a multi-hour weekly DBA task. Done autonomously, it is a background process that requires no human attention until an exception condition fires.

    The autonomous partition manager has four responsibilities:

    1. Provisioning: Create future partitions ahead of the current period (typically 3–7 days ahead for daily partitions, 2 months ahead for monthly).

    2. Attachment validation: Verify new partitions pass constraint checks before the period goes live.

    3. Archival offload: Detach expired partitions, back up and export them to cold storage, and verify integrity before dropping.

    4. Filegroup migration: Move warm partitions to compressed or lower-cost filegroups based on age rules.

    *The four partition-manager responsibilities form one continuous lifecycle per table — every stage writes to dba_maintenance_log so a crashed run resumes from the last unconfirmed action.*

    Autonomous monthly partition provisioning — for a time-series table on a monthly partition scheme. Idempotent: safe to call on every maintenance cycle:

    -- Provision the next 2 monthly partitions ahead of the current period
-- Partition function: pf_monthly_events (RANGE RIGHT on DATE)
DECLARE @i INT = 0;
DECLARE @boundary DATE;
DECLARE @existing_boundaries TABLE (value DATE);

INSERT INTO @existing_boundaries
SELECT CAST(value AS DATE)
FROM sys.partition_range_values prv
WHERE prv.function_id = (
    SELECT pf.function_id
    FROM sys.partition_functions pf
    WHERE pf.name = 'pf_monthly_events'
);

WHILE @i < 2
BEGIN
    -- First day of the month, @i months ahead of next month
    SET @boundary = DATEADD(MONTH, DATEDIFF(MONTH, 0, GETDATE()) + @i + 1, 0);

    IF NOT EXISTS (SELECT 1 FROM @existing_boundaries WHERE value = @boundary)
    BEGIN
        ALTER PARTITION SCHEME ps_monthly_events NEXT USED [PRIMARY];
        ALTER PARTITION FUNCTION pf_monthly_events() SPLIT RANGE (@boundary);

        INSERT INTO dba_maintenance_log
            (action, object_name, executed_at, details)
        VALUES
            ('PARTITION_SPLIT', 'pf_monthly_events', GETUTCDATE(),
             'Split boundary ' + CAST(@boundary AS NVARCHAR(20)));
    END;

    SET @i = @i + 1;
END

    For partition archival on SQL Server, the autonomous engine uses partition switching — a metadata-only operation that detaches a partition into a staging table without data movement, then exports and drops the staging table. This is the correct production pattern because ALTER TABLE ... SWITCH is near-instantaneous and does not hold locks on the main table during export:

    SQL Server — Autonomous partition archival via partition switching:

    -- SQL Server: autonomous partition archival for a monthly partitioned table
-- Step 1: identify the oldest partition eligible for archival
DECLARE @oldest_boundary  DATE;
DECLARE @partition_number INT;
DECLARE @staging_table    NVARCHAR(128);
DECLARE @sql              NVARCHAR(MAX);

-- Find the oldest partition boundary older than retention threshold (24 months)
SELECT TOP 1
    @oldest_boundary  = CAST(prv.value AS DATE),
    @partition_number = p.partition_number
FROM sys.partitions p
JOIN sys.partition_range_values prv
    ON prv.function_id = (
        SELECT pf.function_id
        FROM sys.partition_functions pf
        WHERE pf.name = 'pf_monthly_events'
    )
   AND prv.boundary_id = p.partition_number - 1
WHERE p.object_id = OBJECT_ID('dbo.event_log')
  AND CAST(prv.value AS DATE) < DATEADD(MONTH, -24, GETDATE())
ORDER BY prv.value ASC;

IF @oldest_boundary IS NOT NULL
BEGIN
    SET @staging_table = 'dbo.event_log_archive_'
        + FORMAT(@oldest_boundary, 'yyyyMM');

    -- Create staging table with same schema
    SET @sql = '
        SELECT TOP 0 * INTO ' + @staging_table + '
        FROM dbo.event_log;
    ';
    EXEC sp_executesql @sql;

    -- Switch partition to staging table (metadata-only, instant)
    SET @sql = '
        ALTER TABLE dbo.event_log
        SWITCH PARTITION ' + CAST(@partition_number AS NVARCHAR)
        + ' TO ' + @staging_table + ';
    ';
    EXEC sp_executesql @sql;

    -- Log the archival event
    INSERT INTO dba_maintenance_log
        (action, object_name, executed_at, details)
    VALUES
        ('PARTITION_SWITCH', @staging_table, GETUTCDATE(),
         'Switched partition ' + CAST(@partition_number AS NVARCHAR)
         + ' boundary ' + CAST(@oldest_boundary AS NVARCHAR(20)));

    -- At this point, the staging table is handed off to the
    -- async export job (bcp/BACPAC/Azure Blob) before DROP
    PRINT 'Partition switched to staging: ' + @staging_table;
END

    The async export job that follows the partition switch is a separate process that reads dba_maintenance_log for PARTITION_SWITCH events not yet marked ARCHIVED, exports the staging table to cold storage (Azure Blob, S3, or NFS depending on deployment), verifies the row count against the pre-switch snapshot, and only then issues DROP TABLE. This separation of concerns is deliberate: the partition switch itself cannot fail the main table, and the drop can be retried independently if the export job is interrupted.

    Filegroup migration completes the partition lifecycle. As partitions age from hot to warm to cold, the autonomous engine moves them across filegroups defined on progressively lower-cost storage. The migration uses an online index rebuild with DROP_EXISTING = ON onto the target filegroup — the autonomous engine operates on one partition at a time rather than the whole table: each move is brief and scoped, and the workload gate still governs when it is allowed to run:

    -- Autonomous filegroup migration for aged partitions
-- Moves partitions older than 90 days to the WARM_DATA filegroup
-- using online index rebuilds (one partition at a time)
DECLARE @partition_number INT;
DECLARE @sql NVARCHAR(MAX);

DECLARE part_cursor CURSOR FOR
SELECT p.partition_number
FROM sys.partitions p
JOIN sys.partition_range_values prv
    ON prv.function_id = (
        SELECT pf.function_id
        FROM sys.partition_functions pf
        WHERE pf.name = 'pf_monthly_events'
    )
   AND prv.boundary_id = p.partition_number - 1
JOIN sys.indexes i
    ON i.object_id = p.object_id AND i.index_id = p.index_id
WHERE p.object_id = OBJECT_ID('dbo.event_log')
  AND p.index_id = 1
  AND CAST(prv.value AS DATE) < DATEADD(DAY, -90, GETDATE())
  AND p.data_compression_desc = 'NONE';

OPEN part_cursor;
FETCH NEXT FROM part_cursor INTO @partition_number;

WHILE @@FETCH_STATUS = 0
BEGIN
    -- Online rebuild of this partition onto the WARM_DATA filegroup
    SET @sql = 'ALTER INDEX PK_event_log ON dbo.event_log '
             + 'REBUILD PARTITION = ' + CAST(@partition_number AS NVARCHAR)
             + ' WITH (ONLINE = ON, DATA_COMPRESSION = PAGE) ON [WARM_DATA];';
    EXEC sp_executesql @sql;

    INSERT INTO dba_maintenance_log
        (action, object_name, executed_at, details)
    VALUES
        ('FILEGROUP_MIGRATE', 'dbo.event_log', GETUTCDATE(),
         'Moved partition ' + CAST(@partition_number AS NVARCHAR)
         + ' to WARM_DATA filegroup');

    FETCH NEXT FROM part_cursor INTO @partition_number;
END

CLOSE part_cursor;
DEALLOCATE part_cursor;

    A complete partition lifecycle manager combines all four responsibilities into a single orchestration loop, typically implemented as a Python daemon with individual method calls for provision, validate, archive, and migrate. Each method is idempotent and logs every action to dba_maintenance_log, so a crashed run simply resumes from the last unconfirmed action on the next cycle.

    23.5 Log and Audit File Management

    Database engines generate maintenance overhead of their own: transaction log files, slow query logs, audit logs, and trace files. An autonomous maintenance engine that manages tables but ignores file-level growth creates a different class of 2 a.m. incident — disk exhaustion from an unmanaged audit log directory.

    The log management layer of the autonomous engine handles three concerns: Transaction log retention policy enforcement, log file rotation and compression, and alert escalation when growth rate suggests impending exhaustion.

    SQL Server transaction log management in autonomous systems centers on ensuring log backups run frequently enough under the FULL recovery model to prevent log file expansion. The autonomous engine monitors log space usage via sys.dm_db_log_space_usage and triggers an unscheduled log backup when used log space crosses a threshold, rather than waiting for the next scheduled backup window:

    -- SQL Server: reactive log backup trigger
-- Fires an ad-hoc log backup when log space utilization exceeds threshold
DECLARE @log_used_pct  FLOAT;
DECLARE @db_name       SYSNAME = DB_NAME();
DECLARE @backup_path   NVARCHAR(512);
DECLARE @sql           NVARCHAR(1024);

SELECT @log_used_pct =
    used_log_space_in_percent
FROM sys.dm_db_log_space_usage;

IF @log_used_pct > 70.0
BEGIN
    SET @backup_path =
        N'\\backup-share\logs\'
        + @db_name + N'_log_'
        + FORMAT(GETUTCDATE(), N'yyyyMMdd_HHmmss')
        + N'.bak';

    SET @sql = N'BACKUP LOG ' + QUOTENAME(@db_name)
        + N' TO DISK = ' + QUOTENAME(@backup_path, '''')
        + N' WITH COMPRESSION, STATS = 10;';

    EXEC sp_executesql @sql;

    INSERT INTO dba_maintenance_log
        (action, object_name, executed_at, details)
    VALUES
        ('LOG_BACKUP_REACTIVE', @db_name, GETUTCDATE(),
         'Log used ' + CAST(ROUND(@log_used_pct, 1) AS VARCHAR)
         + '% triggered unscheduled backup to ' + @backup_path);
END

    Log file compression and rotation for operating-system-level logs (SQL Server ERRORLOG files) is handled by the Python maintenance daemon, which calls standard OS rotation utilities or implements rotation logic directly. The key autonomous behavior is that the daemon models disk consumption rate and projects time-to-full, alerting when the projection falls below a configurable horizon (for example, fewer than 48 hours to disk exhaustion at current growth rate) before the threshold is actually breached.

    23.6 Governance, Auditing, and the Human Override Layer

    Autonomous maintenance at production scale requires a governance layer that answers three questions at any moment: what did the system do, why did it do it, and how can a human stop it or reverse it? Without complete answers to all three, the autonomous engine is operationally dangerous — not because of what it does in normal operation, but because of what happens the first time it does something unexpected.

    The governance layer has four components: the maintenance audit log, the action registry with justification capture, the circuit breaker, and the dry-run mode.

    The Maintenance Audit Log

    Every autonomous action — every index rebuild, every statistics refresh, every partition create or drop, every partition split — writes a structured record to dba_maintenance_log. This table was referenced throughout the preceding sections; here is its complete definition:

    -- Autonomous maintenance audit log (SQL Server)
CREATE TABLE dbo.dba_maintenance_log (
    log_id          BIGINT IDENTITY(1,1) PRIMARY KEY,
    action          VARCHAR(64)     NOT NULL,   -- e.g. 'INDEX_REBUILD', 'PARTITION_SPLIT'
    object_schema   VARCHAR(128),
    object_name     VARCHAR(256)    NOT NULL,
    executed_at     DATETIME2       NOT NULL DEFAULT SYSUTCDATETIME(),
    duration_ms     INT,                        -- populated on completion
    rows_affected   BIGINT,
    status          VARCHAR(16)     NOT NULL DEFAULT 'RUNNING',
                                                -- RUNNING, COMPLETE, FAILED, SKIPPED
    justification   NVARCHAR(MAX),              -- why the engine chose this action
    initiated_by    VARCHAR(64)     NOT NULL DEFAULT 'autonomous_engine',
    dry_run         BIT             NOT NULL DEFAULT 0,
    details         NVARCHAR(MAX),
    error_message   NVARCHAR(MAX)
);

CREATE INDEX idx_maint_log_action_ts
    ON dbo.dba_maintenance_log (action, executed_at DESC);

CREATE INDEX idx_maint_log_object
    ON dbo.dba_maintenance_log (object_name, executed_at DESC);

    The justification column is what separates a governance-grade audit log from a simple activity log. Every action written by the autonomous engine includes a human-readable explanation of the metric values that triggered it: "frag_pct=42.1, pages=260000, last_rebuild=9d ago, active_sessions=3". A DBA reviewing the log the next morning can reconstruct exactly what the engine observed and why it acted, without needing to query historical catalog snapshots.

    The Circuit Breaker

    The circuit breaker is a single-table, single-row control record that the maintenance engine checks at the start of every decision loop iteration. If the breaker is tripped — either by the engine itself in response to an anomalous condition, or by a human operator — all autonomous actions halt immediately:

    -- Circuit breaker control table
CREATE TABLE dbo.dba_maintenance_circuit_breaker (
    id              INT PRIMARY KEY DEFAULT 1,
    enabled         BIT NOT NULL DEFAULT 1,
    tripped_at      DATETIME2,
    tripped_by      VARCHAR(128),
    reason          NVARCHAR(MAX),
    CONSTRAINT single_row CHECK (id = 1)
);

INSERT INTO dbo.dba_maintenance_circuit_breaker (id, enabled)
VALUES (1, 1);

-- Human operator trips the breaker:
-- UPDATE dbo.dba_maintenance_circuit_breaker
-- SET enabled = 0, tripped_at = SYSUTCDATETIME(),
--     tripped_by = 'dba_oncall', reason = 'Pre-release freeze';

-- Engine checks at loop start:
-- SELECT enabled FROM dbo.dba_maintenance_circuit_breaker WHERE id = 1;

    The Python maintenance daemon checks this record before every action dispatch. If enabled = 0, the daemon logs a CIRCUIT_BREAKER_HALT event and sleeps until the next cycle, at which point it checks again. This means a DBA can halt all autonomous maintenance with a single UPDATE statement from any SQL client — no SSH required, no process kill needed.

    The engine also trips its own breaker under two self-protection conditions: if it detects that a previous autonomous action is still running beyond its expected duration (suggesting a lock wait or runaway operation), and if it encounters three consecutive failures on any single object (suggesting a systemic problem requiring human diagnosis).

    Dry-Run Mode

    Dry-run mode is the development and validation interface for the autonomous engine. When dry_run = TRUE is passed to any action method, the engine performs all analysis, writes the full justification record to dba_maintenance_log with dry_run = TRUE and status = 'SKIPPED', but does not execute the maintenance statement. This mode is used during initial deployment to validate that the engine's decisions match operator intuitions, and during change-freeze periods when the circuit breaker would otherwise need to be tripped entirely.

    The Python dispatcher implements dry-run as a flag threaded through all action methods:

    # Maintenance dispatcher with dry-run and circuit breaker integration

import pyodbc
import logging
from datetime import datetime

logger = logging.getLogger("autonomous_maintenance")

CONN_STR = ("DRIVER={ODBC Driver 18 for SQL Server};SERVER=sqlprimary;"
            "DATABASE=AppDB;UID=maintenance_role;PWD=*******;")

class MaintenanceDispatcher:

    def __init__(self, dry_run: bool = False):
        self.dry_run = dry_run
        self.conn    = pyodbc.connect(CONN_STR, autocommit=True)

    def _circuit_breaker_enabled(self) -> bool:
        cur = self.conn.cursor()
        cur.execute(
            "SELECT enabled FROM dbo.dba_maintenance_circuit_breaker WHERE id = 1"
        )
        row = cur.fetchone()
        return bool(row[0]) if row else False

    def _log_action(self, action: str, object_name: str,
                    justification: str, status: str = "RUNNING",
                    duration_ms: int = None, error: str = None) -> int:
        cur = self.conn.cursor()
        cur.execute("""
            INSERT INTO dbo.dba_maintenance_log
                (action, object_name, executed_at, status,
                 justification, initiated_by, dry_run, error_message,
                 duration_ms)
            OUTPUT INSERTED.log_id
            VALUES (?, ?, SYSUTCDATETIME(), ?, ?, ?, ?, ?, ?)
        """, (action, object_name, status, justification,
              "autonomous_engine", int(self.dry_run), error, duration_ms))
        return cur.fetchone()[0]

    def _update_log(self, log_id: int, status: str,
                    duration_ms: int = None, error: str = None):
        cur = self.conn.cursor()
        cur.execute("""
            UPDATE dbo.dba_maintenance_log
            SET status = ?, duration_ms = ?, error_message = ?
            WHERE log_id = ?
        """, (status, duration_ms, error, log_id))

    def dispatch_stats_update(self, schema: str, table: str,
                              justification: str, fullscan: bool = False):
        if not self._circuit_breaker_enabled():
            logger.warning("Circuit breaker tripped — skipping UPDATE STATISTICS on %s.%s",
                           schema, table)
            return

        action = "STATS_FULLSCAN" if fullscan else "STATS_SAMPLED"
        scan   = "WITH FULLSCAN" if fullscan else ""
        stmt   = f"UPDATE STATISTICS [{schema}].[{table}] {scan}".strip()
        log_id = self._log_action(action, f"{schema}.{table}", justification)

        if self.dry_run:
            logger.info("[DRY RUN] Would execute: %s", stmt)
            self._update_log(log_id, "SKIPPED")
            return

        start = datetime.utcnow()
        try:
            self.conn.execute(stmt)
            elapsed = int((datetime.utcnow() - start).total_seconds() * 1000)
            self._update_log(log_id, "COMPLETE", duration_ms=elapsed)
            logger.info("Completed %s on %s.%s in %dms",
                        action, schema, table, elapsed)
        except Exception as exc:
            elapsed = int((datetime.utcnow() - start).total_seconds() * 1000)
            self._update_log(log_id, "FAILED",
                             duration_ms=elapsed, error=str(exc))
            logger.error("FAILED %s on %s.%s: %s", action, schema, table, exc)
            raise

    This pattern — circuit breaker check, pre-action log entry, dry-run branch, execution with timing, completion update — is applied uniformly to every action type in the dispatcher. A DBA can query dba_maintenance_log at any time and see the full history with justifications, durations, and outcomes for every autonomous decision the engine has ever made.

    Operator Dashboard Query

    The operational health of the autonomous maintenance engine is summarized by a single dashboard query that DBAs can pin to their monitoring interface:

    Operational summary (last 24 hours):

    -- Autonomous maintenance engine summary
SELECT
    action,
    status,
    COUNT(*)                                         AS event_count,
    AVG(duration_ms)                                 AS avg_duration_ms,
    MAX(duration_ms)                                 AS max_duration_ms,
    SUM(CASE WHEN dry_run = 1 THEN 1 ELSE 0 END)    AS dry_run_count,
    MIN(executed_at)                                 AS first_event,
    MAX(executed_at)                                 AS last_event
FROM dba_maintenance_log
WHERE executed_at > DATEADD(HOUR, -24, GETUTCDATE())
GROUP BY action, status
ORDER BY action, status;

    The circuit breaker state, the count of FAILED status events, and the presence of any escalation entries in the last 24 hours are the three signals a DBA monitors for autonomous maintenance health. Everything else runs without human attention.

    Key Takeaways

  • → The maintenance decision loop replaces static cron schedules with a continuous urgency-cost-opportunity model: maintenance fires when object degradation cost exceeds execution cost and the workload gate is open, not because a clock expired.
  • → Autonomous statistics management treats automatic statistics updates as a fallback, not the primary mechanism — using velocity-adjusted staleness thresholds and targeted UPDATE STATISTICS dispatch to keep the optimizer fed with fresh cardinality estimates without manual scheduling.
  • → Index lifecycle automation covers all three phases — creation, fragmentation remediation (REORGANIZE vs. REBUILD based on fragmentation band), and staged retirement through a deferred-drop registry — eliminating index technical debt accumulation over time.
  • → Partition lifecycle management handles provisioning, attachment validation, archival via metadata-only partition switching, and filegroup migration in a single idempotent orchestration loop, reducing multi-hour weekly DBA effort to a background process requiring no human attention during normal operation.
  • → The governance layer — audit log, justification capture, circuit breaker, and dry-run mode — is not optional scaffolding: it is what makes autonomous maintenance safe to deploy in production, giving operators complete visibility into every decision, a single-statement halt mechanism, and a validation path for new environments before live execution begins.
