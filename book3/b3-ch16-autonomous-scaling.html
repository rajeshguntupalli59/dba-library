Chapter 16: Autonomous Scaling in Cloud Databases

Scaling decisions made by humans are slow, reactive, and constrained by organizational bandwidth. A senior DBA wakes up to an on-call alert, interprets a spike, provisions additional capacity, and reruns workloads — by which time the damage is done. Autonomous scaling flips this model entirely: the system observes its own resource consumption, predicts demand trajectories, and executes capacity changes without human approval. This chapter covers the architecture and implementation of autonomous vertical and horizontal scaling for both PostgreSQL and SQL Server in cloud environments, including the signal pipelines that drive decisions, the execution layers that implement them, and the guardrails that prevent runaway automation from causing worse problems than it solves.

---

The Signal Pipeline: From Metric Collection to Scaling Decisions

Autonomous scaling begins not with the scaling action itself but with the quality of the signals feeding the decision engine. A system that scales on raw CPU percentage will thrash. A system that scales on composite signals — query latency percentiles, buffer hit ratios, replication lag, active connection depth, and queue depth simultaneously — makes durable decisions.

The canonical metric stack for autonomous scaling uses Prometheus for collection, a time-series anomaly model (ARIMA, Prophet, or a lightweight LSTM) for prediction, and a rule engine that translates predictions into scaling intents.

For PostgreSQL, the baseline signals come from pg_stat_activity, pg_stat_bgwriter, pg_stat_replication, and the pg_buffercache extension. For SQL Server, equivalent depth comes from Dynamic Management Views: sys.dm_exec_requests, sys.dm_os_wait_stats, sys.dm_os_ring_buffers, and sys.dm_db_resource_stats on Azure SQL.

-- Composite health signal query for the scaling decision engine
SELECT
    (SELECT COUNT(*) FROM sys.dm_exec_requests
     WHERE blocking_session_id <> 0) AS blocked_queries,
    (SELECT COUNT(*) FROM sys.dm_exec_requests
     WHERE status = 'running') AS active_queries,
    (SELECT
        CAST(100.0 * SUM(CASE WHEN physical_reads = 0 THEN 1 ELSE 0 END)
            / NULLIF(COUNT(*), 0) AS DECIMAL(5,2))
     FROM sys.dm_exec_requests
     WHERE status = 'running') AS logical_read_ratio,
    (SELECT TOP 1 DATEDIFF(SECOND, last_commit_time,
        secondary_last_commit_time)
     FROM sys.dm_hadr_database_replica_states
     WHERE is_local = 0) AS replica_lag_seconds,
    (SELECT MAX(DATEDIFF(SECOND, start_time, GETDATE()))
     FROM sys.dm_exec_requests
     WHERE status IN ('running','suspended')) AS max_query_duration_sec;

These two queries form the heartbeat of the scaling signal pipeline. A Python collector runs them on a 15-second cadence, pushes results to Prometheus via the prometheus_client library, and feeds a sliding window evaluator that determines whether observed values represent a transient spike or a sustained load pattern requiring a scaling response.

The distinction between a spike and a trend is the most important judgment the scaling engine must make. Spikes warrant connection pool adjustments or query prioritization changes. Sustained trends warrant compute scaling. The window evaluator applies a simple rule: if the composite score (a weighted average of the normalized metric deviations) exceeds 0.75 for three consecutive five-minute evaluation windows, a scaling intent is raised. A single window breach does not trigger scaling; it resets a cooldown timer and increases monitoring frequency.

Vertical Scaling Automation: Compute Resize Without Downtime

Vertical scaling — adding vCPUs or memory to an existing instance — is the first lever most cloud database architectures pull because it requires no application topology changes. The challenge is executing it with zero or near-zero downtime while maintaining ACID guarantees throughout the resize window.

On Azure SQL Database and Azure Database for PostgreSQL Flexible Server, compute tier changes are API-driven and can be automated via Terraform or direct REST calls. On AWS RDS, instance class modifications support the apply-immediately flag for minor version changes but require a maintenance window for major compute class changes unless using RDS Multi-AZ, where the standby is upgraded first and a failover is executed transparently.

The autonomous scaling controller must understand these platform-specific behaviors. A platform-agnostic abstraction layer is dangerous here; the controller needs to know whether the target platform supports online resize before issuing the command.

# Autonomous vertical scaling controller
# Handles both Azure Database for PostgreSQL and AWS RDS

import boto3
import requests
import json
import time
import logging
from dataclasses import dataclass
from enum import Enum

logger = logging.getLogger("autonomous_scaler")

class Platform(Enum):
    AWS_RDS = "aws_rds"
    AZURE_PG_FLEXIBLE = "azure_pg_flexible"
    AZURE_SQL = "azure_sql"

@dataclass
class ScalingIntent:
    platform: Platform
    resource_id: str
    current_sku: str
    target_sku: str
    trigger_metric: str
    trigger_value: float
    threshold: float
    cooldown_minutes: int = 30

class VerticalScalingController:
    def __init__(self, azure_token: str, aws_region: str):
        self.azure_token = azure_token
        self.rds_client = boto3.client('rds', region_name=aws_region)
        self.last_scale_time = {}

    def _is_in_cooldown(self, resource_id: str, cooldown_minutes: int) -> bool:
        if resource_id not in self.last_scale_time:
            return False
        elapsed = (time.time() - self.last_scale_time[resource_id]) / 60
        return elapsed < cooldown_minutes

    def execute_scaling(self, intent: ScalingIntent) -> dict:
        if self._is_in_cooldown(intent.resource_id, intent.cooldown_minutes):
            logger.info(f"Resource {intent.resource_id} in cooldown. Skipping.")
            return {"status": "skipped", "reason": "cooldown"}

        logger.warning(
            f"Scaling {intent.resource_id}: {intent.current_sku} -> {intent.target_sku} "
            f"[trigger: {intent.trigger_metric}={intent.trigger_value:.2f}, "
            f"threshold={intent.threshold}]"
        )

        if intent.platform == Platform.AWS_RDS:
            return self._scale_rds(intent)
        elif intent.platform in (Platform.AZURE_PG_FLEXIBLE, Platform.AZURE_SQL):
            return self._scale_azure(intent)

    def _scale_rds(self, intent: ScalingIntent) -> dict:
        try:
            response = self.rds_client.modify_db_instance(
                DBInstanceIdentifier=intent.resource_id,
                DBInstanceClass=intent.target_sku,
                ApplyImmediately=True  # safe for Multi-AZ; failover handles HA
            )
            self.last_scale_time[intent.resource_id] = time.time()
            return {
                "status": "initiated",
                "db_instance_status": response['DBInstance']['DBInstanceStatus']
            }
        except Exception as e:
            logger.error(f"RDS scaling failed: {e}")
            return {"status": "failed", "error": str(e)}

    def _scale_azure(self, intent: ScalingIntent) -> dict:
        # Azure Database for PostgreSQL Flexible Server SKU update
        parts = intent.resource_id.split("/")
        subscription_id = parts[2]
        resource_group = parts[4]
        server_name = parts[-1]

        url = (
            f"https://management.azure.com/subscriptions/{subscription_id}"
            f"/resourceGroups/{resource_group}"
            f"/providers/Microsoft.DBforPostgreSQL/flexibleServers/{server_name}"
            f"?api-version=2022-12-01"
        )
        payload = {"sku": {"name": intent.target_sku, "tier": "GeneralPurpose"}}
        headers = {
            "Authorization": f"Bearer {self.azure_token}",
            "Content-Type": "application/json"
        }
        response = requests.patch(url, headers=headers, data=json.dumps(payload))
        if response.status_code in (200, 202):
            self.last_scale_time[intent.resource_id] = time.time()
            return {"status": "initiated", "http_status": response.status_code}
        return {"status": "failed", "http_status": response.status_code,
                "body": response.text}

The cooldown mechanism is non-negotiable. Without it, a scaling controller can enter a feedback loop: scale up triggers a brief latency increase during the resize, which looks like continued stress, which triggers another scale-up, until the instance reaches the maximum available SKU. Thirty minutes is a sensible default; production systems may tune this based on the platform's typical resize completion time plus a safety buffer.

For SQL Server on RDS or Azure SQL Managed Instance, vertical scaling follows identical API patterns but operates on different SKU nomenclature. Azure SQL Elastic Pools support dynamic DTU or vCore allocation within a pool without instance restarts — making pool-level scaling the preferred lever when multiple databases share infrastructure.

Horizontal Scaling: Read Replica Automation and Sharding Orchestration

Vertical scaling has a ceiling. When the workload outgrows the largest available instance class, or when write latency targets require distributing read traffic, horizontal scaling becomes the operative architecture. Autonomous horizontal scaling for PostgreSQL and SQL Server takes two distinct forms: replica fleet management and, for write scalability, shard orchestration.

Autonomous Read Replica Management

The replica fleet should grow and shrink based on read queue depth and replica lag. When replica lag exceeds a defined threshold — say, 5 seconds — adding another replica reduces the per-replica replication fan-out, indirectly reducing lag on existing replicas while absorbing additional read traffic. When replica lag returns to acceptable levels and the replica connection utilization drops below 30% for two consecutive evaluation windows, the controller decommissions the youngest replica.

On Kubernetes, this is expressed through a custom operator pattern. The operator watches a DatabaseScalingPolicy custom resource and controls the replica count of a PostgresCluster (via CrunchyData PGO or Zalando postgres-operator).

For pgBouncer, horizontal scaling of the connection proxy layer accompanies every replica addition. Each new replica gets its own pgBouncer sidecar in transaction pooling mode, and the application-layer load balancer (HAProxy or Envoy) is updated to include the new replica endpoint with read-only routing tags.

-- Replica health for Availability Group autoscaler
SELECT
    ar.replica_server_name,
    drs.database_name,
    drs.synchronization_state_desc,
    drs.synchronization_health_desc,
    drs.log_send_queue_size AS log_send_queue_kb,
    drs.redo_queue_size AS redo_queue_kb,
    drs.log_send_rate AS log_send_rate_kb_sec,
    drs.redo_rate AS redo_rate_kb_sec,
    CASE
        WHEN drs.log_send_rate > 0
        THEN CAST(drs.log_send_queue_size * 1.0
                  / drs.log_send_rate AS DECIMAL(10,2))
        ELSE NULL
    END AS estimated_lag_seconds
FROM sys.dm_hadr_database_replica_states drs
JOIN sys.availability_replicas ar
    ON drs.replica_id = ar.replica_id
WHERE drs.is_local = 0
ORDER BY estimated_lag_seconds DESC NULLS LAST;

Write Scalability and Shard Orchestration

For write-bound workloads, Citus (now part of Azure Cosmos DB for PostgreSQL) provides shard-level horizontal scaling for PostgreSQL. The autonomous layer here orchestrates shard rebalancing in response to per-shard row count skew and per-shard query latency divergence. When a shard's query p99 exceeds 2× the fleet median for two evaluation periods, the rebalancer moves that shard to a less-loaded worker node — transparently to the application.

# Autonomous shard rebalancer for Citus / Azure Cosmos DB for PostgreSQL
# Triggers rebalancing when shard p99 latency diverges beyond threshold

import psycopg2
import logging

logger = logging.getLogger("shard_rebalancer")

COORDINATOR_DSN = "host=coordinator port=5432 dbname=app user=citus_admin"
P99_DIVERGENCE_THRESHOLD = 2.0  # target shard p99 must not exceed 2x fleet median
MIN_SHARD_SIZE_REBALANCE_MB = 500  # avoid rebalancing tiny shards

def get_shard_latency_profile(conn):
    with conn.cursor() as cur:
        cur.execute("""
            SELECT
                s.shardid,
                s.logicalrelid::text AS table_name,
                sp.nodename,
                sp.nodeport,
                pg_size_pretty(citus_shard_sizes.size) AS shard_size,
                citus_shard_sizes.size AS size_bytes
            FROM pg_dist_shard s
            JOIN pg_dist_shard_placement sp ON s.shardid = sp.shardid
            JOIN citus_shard_sizes() AS citus_shard_sizes(shardid, size)
                ON s.shardid = citus_shard_sizes.shardid
            WHERE sp.shardstate = 1
            ORDER BY size_bytes DESC
        """)
        return cur.fetchall()

def trigger_rebalance_if_needed(conn, shard_profile):
    sizes = [row[5] for row in shard_profile]
    if not sizes:
        return

    median_size = sorted(sizes)[len(sizes) // 2]
    oversized_shards = [
        row for row in shard_profile
        if row[5] > median_size * P99_DIVERGENCE_THRESHOLD
        and row[5] > MIN_SHARD_SIZE_REBALANCE_MB * 1024 * 1024
    ]

    if oversized_shards:
        logger.warning(
            f"Triggering shard rebalance: {len(oversized_shards)} oversized shards "
            f"detected (median={median_size / 1024 / 1024:.1f}MB)"
        )
        with conn.cursor() as cur:
            # Citus rebalancer runs asynchronously
            cur.execute("SELECT rebalance_table_shards(rebalance_strategy := 'by_shard_count');")
        conn.commit()
        logger.info("Shard rebalance initiated successfully.")
    else:
        logger.debug("Shard distribution within acceptable bounds. No action required.")

if __name__ == "__main__":
    conn = psycopg2.connect(COORDINATOR_DSN)
    profile = get_shard_latency_profile(conn)
    trigger_rebalance_if_needed(conn, profile)
    conn.close()

SQL Server's horizontal scaling story differs architecturally. Availability Groups with readable secondaries are the standard mechanism, but for write scale, Distributed Availability Groups and Stretch Database (deprecated in SQL Server 2022) have been largely superseded by application-layer sharding with elastic pools on Azure SQL. The autonomous controller for SQL Server targets pool elasticity — dynamically moving databases between pool service tiers based on DTU consumption patterns observed over rolling 24-hour windows.

Kubernetes-Native Scaling: Operators, HPA, and KEDA Integration

When PostgreSQL or SQL Server (via containers) runs on Kubernetes, the scaling surface expands to include Kubernetes-native primitives: Horizontal Pod Autoscaler (HPA), Vertical Pod Autoscaler (VPA), and KEDA (Kubernetes Event-Driven Autoscaling). The challenge is that databases are stateful workloads — naive HPA configurations that treat database pods like stateless microservices will corrupt data. Autonomous scaling on Kubernetes requires an operator-aware approach that understands the difference between scaling the connection proxy layer (always safe to scale horizontally) and scaling the database server layer (requires careful leader election and persistent volume management).

The recommended architecture separates three independently scalable layers:

1. Connection Proxy (pgBouncer / ProxySQL) — scaled horizontally via standard HPA on CPU and connection queue depth metrics from Prometheus. Safe to scale aggressively.

2. Read Replicas — scaled via the Postgres Operator's replica count field, gated by the replication health checks described in the previous section.

3. Primary Compute — scaled vertically via VPA (for PostgreSQL pods) or via cloud API calls for managed services. Never scaled horizontally without sharding.

KEDA enables event-driven scaling triggers that go beyond the metrics available natively to Kubernetes. A KEDA ScaledObject targeting the pgBouncer deployment can use a Prometheus query as its scaling trigger — for example, scaling pgBouncer replicas when the active connection count as a fraction of max_connections exceeds 0.70.

# KEDA ScaledObject for pgBouncer — scales proxy tier on connection pressure
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: pgbouncer-connection-scaler
  namespace: database
spec:
  scaleTargetRef:
    name: pgbouncer-deployment
  pollingInterval: 15
  cooldownPeriod: 120
  minReplicaCount: 2
  maxReplicaCount: 12
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring.svc.cluster.local:9090
        metricName: pgbouncer_active_connections_ratio
        query: |
          sum(pgbouncer_pools_cl_active) /
          sum(pgbouncer_config_max_client_conn)
        threshold: "0.70"
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring.svc.cluster.local:9090
        metricName: pgbouncer_wait_time_p95
        query: |
          histogram_quantile(0.95,
            rate(pgbouncer_pool_wait_seconds_bucket[2m]))
        threshold: "0.5"

For the Zalando postgres-operator, replica scaling is expressed as a patch to the Postgresql custom resource. The autonomous controller generates and applies this patch programmatically:

# Kubernetes operator patch to scale PostgreSQL read replicas
# Uses the Zalando postgres-operator CRD

from kubernetes import client, config
import json
import logging

logger = logging.getLogger("k8s_pg_scaler")

def scale_postgres_replicas(
    namespace: str,
    cluster_name: str,
    target_replica_count: int,
    current_replica_count: int
):
    config.load_incluster_config()  # use in-cluster ServiceAccount
    custom_api = client.CustomObjectsApi()

    patch_body = {
        "spec": {
            "numberOfInstances": target_replica_count + 1  # +1 for primary
        }
    }

    logger.info(
        f"Patching {cluster_name}: replicas {current_replica_count} "
        f"-> {target_replica_count} "
        f"(total instances: {target_replica_count + 1})"
    )

    try:
        custom_api.patch_namespaced_custom_object(
            group="acid.zalan.do",
            version="v1",
            namespace=namespace,
            plural="postgresqls",
            name=cluster_name,
            body=patch_body,
            content_type="application/merge-patch+json"
        )
        logger.info(f"Replica scale operation accepted by operator for {cluster_name}")
    except client.ApiException as e:
        logger.error(f"Kubernetes API error during replica scaling: {e.status} {e.reason}")
        raise

The controller invokes scale_postgres_replicas only after passing the replication health gate (lag under threshold, no pending base backup, WAL archiver not in error state). These preconditions are checked synchronously before the patch is applied; if any fail, the scale-up is deferred by one evaluation cycle with an alert raised so the operator can investigate if the gate remains blocked beyond the defined timeout.

Scale-Down Safety: Draining, Guardrails, and Reversibility

Scale-up is operationally simple compared to scale-down. Scaling down a database tier risks connection drops, in-flight transaction loss, and replication topology instability. Autonomous scale-down requires a disciplined drain-before-terminate sequence and a set of hard guardrails that prevent the controller from scaling below the minimum viable topology for the current workload.

The drain sequence for a PostgreSQL replica before decommissioning:

1. Remove the replica endpoint from the pgBouncer databases.ini and signal pgBouncer to reload. New connections stop routing to this replica.

2. Wait for the replica's active connection count (from pg_stat_activity) to reach zero or the drain timeout (120 seconds default) to expire.

3. If the drain timeout expires with active connections remaining, force-disconnect using pg_terminate_backend() for idle connections only. Running queries are allowed to complete.

4. Verify replication lag on remaining replicas has not increased beyond the acceptable threshold before proceeding.

5. Issue the Kubernetes delete or cloud API decommission.

-- Check active sessions on an AG secondary being drained
-- Run on the secondary instance
SELECT
    s.session_id,
    s.login_name,
    s.host_name,
    s.program_name,
    s.status,
    r.blocking_session_id,
    r.wait_type,
    r.wait_time / 1000.0 AS wait_seconds,
    DATEDIFF(SECOND, s.last_request_start_time, GETDATE()) AS seconds_since_request,
    LEFT(t.text, 80) AS query_preview
FROM sys.dm_exec_sessions s
LEFT JOIN sys.dm_exec_requests r ON s.session_id = r.session_id
OUTER APPLY sys.dm_exec_sql_text(r.sql_handle) t
WHERE s.is_user_process = 1
  AND s.session_id <> @@SPID
ORDER BY seconds_since_request DESC;

-- Force-disconnect idle sessions after drain timeout
-- Uses a cursor to terminate sessions one at a time with audit logging
DECLARE @session_id INT;
DECLARE @kill_cmd NVARCHAR(20);

DECLARE drain_cursor CURSOR FOR
    SELECT session_id
    FROM sys.dm_exec_sessions
    WHERE is_user_process = 1
      AND session_id <> @@SPID
      AND status = 'sleeping'
      AND program_name NOT LIKE '%replication%'
      AND program_name NOT LIKE '%hadr%';

OPEN drain_cursor;
FETCH NEXT FROM drain_cursor INTO @session_id;
WHILE @@FETCH_STATUS = 0
BEGIN
    SET @kill_cmd = N'KILL ' + CAST(@session_id AS NVARCHAR(10));
    EXEC sp_executesql @kill_cmd;
    FETCH NEXT FROM drain_cursor INTO @session_id;
END;
CLOSE drain_cursor;
DEALLOCATE drain_cursor;

Beyond the drain sequence, the scale-down controller enforces a set of hard guardrails that cannot be overridden by the evaluation engine — only by a human operator with explicit override authorization:

Minimum replica floor. The cluster must retain at least two replicas at all times if the primary is a single-AZ deployment, or at least one replica if the primary is Multi-AZ. Scaling below the floor is blocked unconditionally.

Replication lag gate. If aggregate replica lag across the surviving replicas exceeds the defined SLA threshold at the time the scale-down is proposed, the action is deferred. Removing a replica while surviving replicas are already lagging compounds the problem.

Active backup exclusion. If a pg_basebackup or equivalent RDS snapshot is in progress against any instance in the cluster, scale-down is deferred until the backup completes. Terminating a replica mid-backup produces an incomplete backup that may be silently useless.

Recent failover exclusion. If a primary failover occurred within the preceding 60 minutes, the scaling controller enters a mandatory observation window and takes no scale-down action. Failovers transiently inflate replica lag metrics and can make the cluster appear under-utilized when it is in fact recovering.

These guardrails are implemented as precondition checks in the scaling decision function, evaluated before any decommissioning API call is issued:

# Scale-down guardrail evaluator

from dataclasses import dataclass
from typing import List, Optional
import time

@dataclass
class ClusterState:
    replica_count: int
    primary_is_multi_az: bool
    max_replica_lag_seconds: float
    lag_sla_seconds: float
    backup_in_progress: bool
    last_failover_epoch: Optional[float]
    failover_observation_window_minutes: int = 60

class ScaleDownGuardrails:

    def evaluate(self, state: ClusterState) -> tuple[bool, str]:
        """
        Returns (allowed: bool, reason: str).
        Scale-down proceeds only if allowed is True.
        """
        min_replicas = 1 if state.primary_is_multi_az else 2
        if state.replica_count <= min_replicas:
            return False, (
                f"Replica count ({state.replica_count}) at or below minimum "
                f"floor ({min_replicas}) for this topology."
            )

        if state.max_replica_lag_seconds > state.lag_sla_seconds:
            return False, (
                f"Replica lag ({state.max_replica_lag_seconds:.1f}s) exceeds "
                f"SLA ({state.lag_sla_seconds:.1f}s). Deferring scale-down."
            )

        if state.backup_in_progress:
            return False, "Backup in progress. Scale-down deferred until completion."

        if state.last_failover_epoch is not None:
            elapsed_minutes = (time.time() - state.last_failover_epoch) / 60.0
            if elapsed_minutes < state.failover_observation_window_minutes:
                remaining = state.failover_observation_window_minutes - elapsed_minutes
                return False, (
                    f"Recent failover detected ({elapsed_minutes:.1f} minutes ago). "
                    f"Observation window active for {remaining:.1f} more minutes."
                )

        return True, "All guardrails passed. Scale-down approved."

The evaluate method returns a structured reason alongside the boolean decision so that every blocked scale-down is logged with full context. This audit trail becomes the primary diagnostic tool when the scaling system appears to be stuck — engineers can read the log and understand exactly which guardrail is holding the action.

Predictive Scaling: Demand Forecasting Ahead of Load Events

Reactive scaling — responding to observed degradation — introduces an unavoidable lag between demand onset and capacity availability. For predictable load patterns, predictive scaling closes this gap by provisioning capacity before demand materializes. The most common patterns amenable to prediction are: daily business-hour load cycles, weekly batch processing windows, end-of-month reporting runs, and marketing campaign spikes with known start times.

The predictive layer uses a lightweight Prophet model trained on the historical composite signal from the Prometheus time series. Prophet handles weekly and daily seasonality natively and tolerates missing data, making it practical for production environments where the signal pipeline occasionally has gaps.

# Predictive scaling using Facebook Prophet
# Trains on rolling 30-day history from Prometheus and generates 4-hour lookahead

import pandas as pd
from prophet import Prophet
from prometheus_api_client import PrometheusConnect
import logging
from datetime import datetime, timedelta

logger = logging.getLogger("predictive_scaler")

PROMETHEUS_URL = "http://prometheus.monitoring.svc.cluster.local:9090"
LOOKAHEAD_HOURS = 4
SCALE_UP_THRESHOLD = 0.75  # predicted composite score that triggers preemptive scale
TRAINING_DAYS = 30

def fetch_composite_signal(prom: PrometheusConnect) -> pd.DataFrame:
    end = datetime.utcnow()
    start = end - timedelta(days=TRAINING_DAYS)

    result = prom.get_metric_range_data(
        metric_name='db_composite_load_score',
        start_time=start,
        end_time=end,
        chunk_size=timedelta(hours=6)
    )

    if not result:
        raise ValueError("No data returned from Prometheus for composite load score.")

    records = []
    for series in result:
        for ts, val in series['values']:
            records.append({'ds': pd.to_datetime(ts, unit='s', utc=True), 'y': float(val)})

    df = pd.DataFrame(records).sort_values('ds').drop_duplicates('ds')
    df['ds'] = df['ds'].dt.tz_localize(None)  # Prophet requires tz-naive timestamps
    return df

def generate_scaling_forecast(df: pd.DataFrame) -> pd.DataFrame:
    model = Prophet(
        changepoint_prior_scale=0.05,   # conservative — avoid overfitting spikes
        seasonality_mode='multiplicative',
        daily_seasonality=True,
        weekly_seasonality=True,
        yearly_seasonality=False        # 30 days insufficient for annual patterns
    )
    model.fit(df)

    future = model.make_future_dataframe(
        periods=LOOKAHEAD_HOURS * 4,  # 15-minute granularity
        freq='15min',
        include_history=False
    )
    forecast = model.predict(future)
    return forecast[['ds', 'yhat', 'yhat_lower', 'yhat_upper']]

def evaluate_predictive_intent(forecast: pd.DataFrame) -> dict:
    upcoming_peak = forecast['yhat'].max()
    peak_time = forecast.loc[forecast['yhat'].idxmax(), 'ds']
    minutes_until_peak = (peak_time - datetime.utcnow()).total_seconds() / 60.0

    if upcoming_peak >= SCALE_UP_THRESHOLD and minutes_until_peak > 0:
        logger.warning(
            f"Predictive scale-up intent: peak score {upcoming_peak:.3f} "
            f"predicted at {peak_time} ({minutes_until_peak:.0f} minutes from now)"
        )
        return {
            "action": "preemptive_scale_up",
            "predicted_peak": upcoming_peak,
            "peak_time": str(peak_time),
            "minutes_until_peak": round(minutes_until_peak, 1)
        }

    return {"action": "none", "predicted_peak": upcoming_peak}

if __name__ == "__main__":
    prom = PrometheusConnect(url=PROMETHEUS_URL, disable_ssl=True)
    df = fetch_composite_signal(prom)
    forecast = generate_scaling_forecast(df)
    intent = evaluate_predictive_intent(forecast)
    logger.info(f"Predictive scaling evaluation complete: {intent}")

The predictive controller runs on a 15-minute cron schedule, separate from the reactive controller. Its outputs are intents — structured JSON records written to a shared intent queue — not direct API calls. The execution controller consumes intents from both reactive and predictive paths, applies deduplication (so a predictive scale-up and a reactive scale-up targeting the same resource within the same cooldown window result in a single operation), and issues the actual cloud API call.

This separation of intent generation from execution is architecturally important. It allows the predictive and reactive paths to be tuned, disabled, and audited independently. A runaway predictive model (one that has drifted from reality after a business pattern change) can be disabled without affecting reactive scaling behavior.

Cost Guardrails: Preventing Runaway Scaling Expenditure

Autonomous scaling that operates without cost visibility is a liability. A misconfigured threshold or a model that drifts after an unusual traffic event can scale an instance to the maximum available SKU and hold it there through the cooldown period, generating significant unplanned expenditure. Cost guardrails are the final layer of the autonomous scaling architecture.

The cost guardrail system maintains a per-resource monthly budget cap expressed in cloud provider currency units, a rolling expenditure estimate updated from cloud billing APIs, and a maximum SKU ceiling that the scaler is permitted to target regardless of the scaling intent's recommendation.

# Cost guardrail enforcer for the autonomous scaling controller

from dataclasses import dataclass
from typing import Dict
import logging

logger = logging.getLogger("cost_guardrail")

# SKU cost map — populated from cloud provider price list API at startup
# Values are approximate hourly costs in USD; replace with live API data
SKU_HOURLY_COST_USD: Dict[str, float] = {
    # AWS RDS PostgreSQL (example tier names)
    "db.t3.medium":   0.068,
    "db.r6g.large":   0.240,
    "db.r6g.xlarge":  0.480,
    "db.r6g.2xlarge": 0.960,
    "db.r6g.4xlarge": 1.920,
    # Azure PostgreSQL Flexible Server (example SKU names)
    "Standard_D2ds_v4":  0.181,
    "Standard_D4ds_v4":  0.362,
    "Standard_D8ds_v4":  0.724,
    "Standard_D16ds_v4": 1.448,
}

@dataclass
class ResourceBudget:
    resource_id: str
    monthly_budget_usd: float
    current_month_spend_usd: float
    max_sku_ceiling: str           # controller may never exceed this SKU

class CostGuardrailEnforcer:

    def __init__(self, budgets: Dict[str, ResourceBudget]):
        self.budgets = budgets

    def _hours_remaining_in_month(self) -> float:
        from datetime import datetime, timezone
        import calendar
        now = datetime.now(timezone.utc)
        days_in_month = calendar.monthrange(now.year, now.month)[1]
        end_of_month = datetime(now.year, now.month, days_in_month, 23, 59, 59,
                                tzinfo=timezone.utc)
        return (end_of_month - now).total_seconds() / 3600.0

    def approve_scaling_intent(
        self,
        resource_id: str,
        current_sku: str,
        target_sku: str
    ) -> tuple[bool, str]:

        budget = self.budgets.get(resource_id)
        if budget is None:
            # No budget defined — allow scaling but log warning
            logger.warning(f"No budget configured for {resource_id}. Allowing scaling.")
            return True, "No budget constraint configured."

        # SKU ceiling check
        current_cost = SKU_HOURLY_COST_USD.get(current_sku, 0.0)
        target_cost = SKU_HOURLY_COST_USD.get(target_sku, 0.0)
        ceiling_cost = SKU_HOURLY_COST_USD.get(budget.max_sku_ceiling, float('inf'))

        if target_cost > ceiling_cost:
            return False, (
                f"Target SKU {target_sku} (${target_cost:.3f}/hr) exceeds "
                f"configured ceiling {budget.max_sku_ceiling} "
                f"(${ceiling_cost:.3f}/hr) for {resource_id}."
            )

        # Projected spend check
        hours_remaining = self._hours_remaining_in_month()
        incremental_hourly = target_cost - current_cost
        projected_additional_spend = incremental_hourly * hours_remaining
        projected_total = budget.current_month_spend_usd + projected_additional_spend

        if projected_total > budget.monthly_budget_usd:
            return False, (
                f"Projected month-end spend ${projected_total:.2f} would exceed "
                f"budget ${budget.monthly_budget_usd:.2f} for {resource_id}. "
                f"Scaling from {current_sku} to {target_sku} blocked."
            )

        return True, (
            f"Cost guardrail approved. Projected month-end spend: "
            f"${projected_total:.2f} of ${budget.monthly_budget_usd:.2f} budget."
        )

When a scaling intent is blocked by the cost guardrail, the controller raises a COST_GUARDRAIL_BLOCKED alert to the on-call channel. This alert carries the full context: resource ID, blocked target SKU, projected overspend amount, and remaining budget. The human operator can choose to approve a one-time budget override, raise the monthly cap, or accept the degraded performance. The system does not silently absorb blocked scale-up events — each one is surfaced as an operational signal requiring a human judgment call on the cost-performance trade-off.

End-to-End Autonomous Scaling Workflow

Bringing together all the components described in this chapter, the end-to-end autonomous scaling workflow operates as a continuous loop with clearly separated phases:

Phase 1 — Observe (15-second cadence): The metric collector queries pg_stat_activity, pg_stat_replication, and related views (or DMVs for SQL Server) and pushes results to Prometheus. The composite load score is computed and stored as a time series.

Phase 2 — Evaluate (5-minute windows): The reactive evaluator computes the sliding-window composite score. If the score exceeds the scale-up threshold for three consecutive windows, a reactive scale-up intent is generated. If the score is below the scale-down threshold for six consecutive windows and all guardrails pass, a scale-down intent is generated.

Phase 3 — Predict (15-minute cadence): The Prophet-based predictive evaluator loads 30 days of composite score history, generates a 4-hour forecast, and produces a predictive scale-up intent if the forecast predicts a peak above threshold within the lookahead window.

Phase 4 — Gate (per intent): Each intent — reactive or predictive — passes through the guardrail stack: cooldown check, topology floor check, replication lag gate, backup exclusion, recent failover exclusion, and cost guardrail. Any failed gate defers the intent and generates an audit log entry.

Phase 5 — Execute (per approved intent): The execution controller calls the appropriate cloud API (RDS modify_db_instance, Azure REST PATCH, Kubernetes CRD patch) and records the scale event with full metadata to the audit log.

Phase 6 — Verify (5-minute post-scale window): After execution, the controller enters a heightened monitoring mode, sampling at 30-second intervals. If the composite score does not improve within 10 minutes of a scale-up completing, a SCALING_INEFFECTIVE alert is raised, prompting investigation of non-resource bottlenecks (lock contention, schema design, query plan regression) that scaling alone cannot resolve.

This six-phase loop runs continuously in production. The phases are independent processes connected through the shared intent queue and Prometheus metric store, so any individual phase can be paused, reconfigured, or replaced without affecting the others.

Key Takeaways

  • → Autonomous scaling requires composite signal pipelines — weighted combinations of query latency percentiles, buffer hit ratios, replication lag, and connection depth — rather than single-metric triggers like raw CPU percentage, which produce thrashing and false positive scale events.
  • → Vertical and horizontal scaling require platform-specific execution paths: AWS RDS Multi-AZ, Azure Flexible Server PATCH APIs, and Kubernetes CRD patches each carry distinct availability semantics that a platform-agnostic abstraction layer will obscure to the point of causing outages.
  • → Scale-down is categorically more dangerous than scale-up; a disciplined drain-before-terminate sequence combined with hard guardrails — replica floor, replication lag gate, active backup exclusion, and post-failover observation window — must be enforced unconditionally and cannot be overridden by the automated evaluation engine without a human approval path.
  • → Separating intent generation from execution — with reactive and predictive controllers both writing to a shared intent queue consumed by a single execution controller — allows each path to be tuned, disabled, and audited independently, preventing a drifted forecasting model from affecting reactive scaling behavior and vice versa.
  • → Cost guardrails are a structural requirement, not an optional add-on: every blocked scaling intent must surface as an explicit operational alert with projected overspend context, forcing a human judgment call on the cost-performance trade-off rather than allowing the system to either silently overspend or silently degrade under load.
