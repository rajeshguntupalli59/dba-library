Chapter 13: Self-Optimizing Storage and I/O

Storage is where autonomous database engineering gets physical. Query optimizers, connection poolers, and caching layers all operate in memory and CPU — but eventually, every read and write touches a storage medium, and the behavior of that medium under load determines whether your system survives a crisis or collapses under it. The systems examined in this chapter don't wait for a storage bottleneck to appear on a dashboard. They continuously monitor I/O saturation, file system layout, tablespace utilization, buffer hit ratios, and write amplification — then act. They move hot data closer to compute, tier cold data to cheaper media, rebalance writes across devices, and restructure on-disk layout without a human ever opening a terminal. This is autonomous storage management: a discipline that sits at the intersection of operating system I/O scheduling, database internals, and feedback-driven automation.

Instrumentation Architecture: Building the I/O Observability Layer

No autonomous action is sound without high-fidelity data. Before a system can self-optimize storage, it must build a complete picture of where I/O time is actually going — across SQL Server's I/O completion ports, VDI subsystem, and filegroup allocation patterns.

The observability layer must collect at three levels simultaneously: the OS block device level, the database engine level, and the logical object level. Conflating these three creates misleading signals. A table with poor sequential scan performance might be fine at the block device level but suffering from heap fragmentation. A WAL device might show 95% utilization while the data device sits idle — indicating checkpoint tuning as the correct intervention, not storage provisioning.

-- Capture I/O stall distribution per file to identify hot files vs. idle files
SELECT
    DB_NAME(vfs.database_id)         AS database_name,
    mf.physical_name,
    mf.type_desc,
    vfs.io_stall_read_ms,
    vfs.io_stall_write_ms,
    vfs.io_stall,
    vfs.num_of_reads,
    vfs.num_of_writes,
    CASE
        WHEN vfs.num_of_reads = 0 THEN 0
        ELSE ROUND(vfs.io_stall_read_ms * 1.0 / vfs.num_of_reads, 2)
    END AS avg_read_ms,
    CASE
        WHEN vfs.num_of_writes = 0 THEN 0
        ELSE ROUND(vfs.io_stall_write_ms * 1.0 / vfs.num_of_writes, 2)
    END AS avg_write_ms
FROM sys.dm_io_virtual_file_stats(NULL, NULL) vfs
JOIN sys.master_files mf
    ON vfs.database_id = mf.database_id
    AND vfs.file_id = mf.file_id
ORDER BY vfs.io_stall DESC;

These queries feed a time-series collection loop. In production, a Python agent runs on each database host at 15-second intervals, writing delta values (not cumulative totals) to a Prometheus Pushgateway. The delta calculation is important — raw cumulative counters are useless for detecting transient I/O spikes that resolve within a scrape window.

import pyodbc
import time
import requests

PUSHGATEWAY_URL = "http://prometheus-pushgateway:9091"
SCRAPE_INTERVAL = 15  # seconds
MSSQL_DSN = (
    "DRIVER={ODBC Driver 18 for SQL Server};"
    "SERVER=sql-primary;DATABASE=master;Trusted_Connection=yes;"
)

def collect_io_deltas(conn, prev_snapshot):
    cursor = conn.cursor()
    cursor.execute("""
        SELECT
            DB_NAME(vfs.database_id) AS database_name,
            mf.physical_name,
            vfs.num_of_reads,
            vfs.num_of_writes,
            vfs.num_of_bytes_read,
            vfs.num_of_bytes_written,
            vfs.io_stall_read_ms,
            vfs.io_stall_write_ms
        FROM sys.dm_io_virtual_file_stats(NULL, NULL) vfs
        JOIN sys.master_files mf
            ON vfs.database_id = mf.database_id
           AND vfs.file_id     = mf.file_id
    """)
    current = {(row[0], row[1]): row for row in cursor.fetchall()}

    metrics = []
    for key, row in current.items():
        if key in prev_snapshot:
            prev = prev_snapshot[key]
            delta_reads  = row[2] - prev[2]
            delta_writes = row[3] - prev[3]
            delta_stall  = (row[6] + row[7]) - (prev[6] + prev[7])
            total_io = delta_reads + delta_writes
            if total_io > 0:
                db, phys = key
                avg_stall = delta_stall / total_io
                metrics.append(
                    f'sqlserver_file_io_ops{{database="{db}",file="{phys}"}} {total_io}'
                )
                metrics.append(
                    f'sqlserver_file_io_stall_ms{{database="{db}",file="{phys}"}} {delta_stall:.0f}'
                )
                metrics.append(
                    f'sqlserver_file_avg_stall_ms{{database="{db}",file="{phys}"}} {avg_stall:.2f}'
                )

    push_metrics(metrics)
    return current

def push_metrics(metrics):
    payload = "
".join(metrics) + "
"
    requests.post(
        f"{PUSHGATEWAY_URL}/metrics/job/sqlserver_io_agent",
        data=payload,
        headers={"Content-Type": "text/plain"}
    )

def run_collector():
    conn = pyodbc.connect(MSSQL_DSN)
    snapshot = {}
    while True:
        snapshot = collect_io_deltas(conn, snapshot)
        time.sleep(SCRAPE_INTERVAL)

if __name__ == "__main__":
    run_collector()

At the OS level, iostat -x, blktrace, and nvme smart-log provide device-level saturation metrics. These are collected separately and joined to database-level metrics in Grafana using host labels. The full picture — object-level, engine-level, and device-level — is what allows the autonomous decision engine to distinguish between a bad query plan, a full checkpoint storm, and a failing NVMe drive.

Autonomous Filegroup Rebalancing

Once instrumentation is in place, the first class of autonomous action involves routing data to the right storage tier. Production environments routinely have heterogeneous storage: a fast NVMe tier for active working data, a mid-tier SAS or network-attached volume for warm data, and object storage or compressed block storage for cold or archival data. Manual tiering policies degrade over time because access patterns shift — yesterday's cold archive becomes today's compliance reporting target. Autonomous tiering systems react to this drift continuously.

In SQL Server, filegroup-based tiering is the mechanism. Each filegroup maps to one or more files on specific mount points. Tables and indexes can be moved between filegroups online using CREATE INDEX ... WITH (DROP_EXISTING = ON) ON [ColdFilegroup] for clustered indexes, or partition switching for partitioned tables — operations the autonomous system schedules during low-traffic windows when they would contend with active workloads.

The tiering decision logic follows a straightforward heat score model. For each relation, the system computes a heat score based on recent access frequency, write volume, and age of last modification:

heat_score = (reads_per_hour * 0.4) + (writes_per_hour * 0.5) + (1 / days_since_modified * 0.1)

Relations scoring below a configured cold threshold for seven consecutive measurement periods become candidates for demotion. Relations scoring above a hot threshold that currently reside on a slower tablespace become candidates for promotion.

-- Identify filegroups with disproportionate I/O load relative to data volume
SELECT
    fg.name                          AS filegroup_name,
    fg.type_desc,
    SUM(mf.size) * 8 / 1024         AS total_size_mb,
    SUM(vfs.num_of_reads)            AS total_reads,
    SUM(vfs.num_of_writes)           AS total_writes,
    SUM(vfs.io_stall)                AS total_stall_ms,
    ROUND(
        SUM(vfs.io_stall) * 1.0 /
        NULLIF(SUM(vfs.num_of_reads + vfs.num_of_writes), 0),
    2)                               AS avg_stall_ms_per_op
FROM sys.filegroups fg
JOIN sys.database_files mf ON mf.data_space_id = fg.data_space_id
JOIN sys.dm_io_virtual_file_stats(DB_ID(), NULL) vfs
    ON vfs.file_id = mf.file_id
GROUP BY fg.name, fg.type_desc
ORDER BY avg_stall_ms_per_op DESC;

In SQL Server, the equivalent of tablespace tiering is filegroup migration. Tables can be moved between filegroups by rebuilding their clustered index on the target filegroup: CREATE CLUSTERED INDEX ... ON table(col) WITH (DROP_EXISTING = ON) ON new_filegroup. This operation can be performed online in Enterprise Edition, making it appropriate for autonomous execution during low-traffic windows. The autonomous agent identifies candidate objects, schedules the rebuild during a detected low-traffic window (typically identified by a rolling average of @@CPU_BUSY and dm_os_wait_stats for PAGEIOLATCH_* waits), and executes the move.

The rebalancing agent runs as a Kubernetes CronJob with a configurable schedule. It pulls the heat score analysis from the metrics database, generates a list of recommended moves, applies a safety budget (maximum N GB of data movement per execution window), and issues the appropriate DDL. Completion is logged to an audit table, and the metrics pipeline recalculates heat scores in the next collection cycle.

Checkpoint and Write Amplification Control in SQL Server

SQL Server's write path is dominated by the checkpoint process and the lazy writer. Checkpoints flush dirty pages to disk; under automatic checkpoints their frequency is driven by log activity since the last checkpoint, while indirect checkpoints bound recovery time through the per-database target recovery time setting. When checkpoints fire too aggressively, they produce write amplification — the same data being written to disk multiple times unnecessarily — or checkpoint storms: sudden bursts of dirty page flushes that saturate the I/O subsystem and spike latency for every concurrent query.

An autonomous checkpoint controller observes sys.dm_os_performance_counters (checkpoint pages/sec) and per-database recovery settings continuously, and tunes TARGET_RECOVERY_TIME based on current write load and observed checkpoint duration. The key signal is checkpoint write volume versus I/O stall time from sys.dm_io_virtual_file_stats. When checkpoint I/O dominates total write I/O during burst windows, the I/O subsystem is being asked to flush dirty buffers faster than it comfortably can. The correct autonomous response is to raise TARGET_RECOVERY_TIME — spreading dirty-page flushes over a longer interval and trading a bounded increase in recovery time for smoother I/O.

When dirty pages accumulate faster than checkpoints drain them — visible as a rising checkpoint pages/sec rate alongside growing lazy-writes pressure — the buffer pool is holding too many modified pages between checkpoints. The correct response is to lower TARGET_RECOVERY_TIME so checkpoints fire more frequently and keep the dirty-page backlog bounded.

import pyodbc
import logging

THRESHOLDS = {
    "checkpoint_io_share":     0.60,  # checkpoint writes / total writes during burst
    "checkpoint_stall_ms":     20.0,  # avg write stall ms that signals I/O pressure
}

# target_recovery_time bounds, in seconds (SQL Server default is 60)
RECOVERY_TIME_BOUNDS = {"min": 30, "max": 600, "step": 30}

def analyze_checkpoints(conn):
    cur = conn.cursor()
    cur.execute("""
        SELECT DB_NAME(vfs.database_id) AS database_name,
               SUM(vfs.num_of_bytes_written) AS bytes_written,
               SUM(vfs.io_stall_write_ms)    AS write_stall_ms,
               SUM(vfs.num_of_writes)        AS writes
        FROM sys.dm_io_virtual_file_stats(NULL, NULL) vfs
        GROUP BY vfs.database_id
    """)
    io_by_db = {row[0]: row for row in cur.fetchall()}

    cur.execute("""
        SELECT name, target_recovery_time_in_seconds
        FROM sys.databases
        WHERE database_id > 4
    """)
    recovery_targets = {row[0]: row[1] for row in cur.fetchall()}
    return io_by_db, recovery_targets

def recommend_adjustments(io_by_db, recovery_targets, prev_io_by_db):
    recommendations = []
    for db, row in io_by_db.items():
        if db not in prev_io_by_db:
            continue
        prev = prev_io_by_db[db]
        delta_writes = row[3] - prev[3]
        delta_stall  = row[2] - prev[2]
        if delta_writes == 0:
            continue
        avg_stall = delta_stall / delta_writes
        current_target = recovery_targets.get(db, 60)
        # High average write stall during a write burst = checkpoint pressure.
        # Raising target_recovery_time spreads checkpoint flushes out.
        if (avg_stall > THRESHOLDS["checkpoint_stall_ms"]
                and current_target < RECOVERY_TIME_BOUNDS["max"]):
            recommendations.append({
                "database": db,
                "parameter": "target_recovery_time",
                "direction": "increase",
                "reason": f"avg_write_stall={avg_stall:.1f}ms exceeds threshold",
            })
    return recommendations

def apply_adjustment(conn, database, direction):
    cur = conn.cursor()
    cur.execute(
        "SELECT target_recovery_time_in_seconds FROM sys.databases WHERE name = ?",
        (database,),
    )
    current = cur.fetchone()[0]
    step = RECOVERY_TIME_BOUNDS["step"]
    new_value = current + step if direction == "increase" else current - step
    new_value = max(RECOVERY_TIME_BOUNDS["min"],
                    min(RECOVERY_TIME_BOUNDS["max"], new_value))
    logging.info(f"Adjusting {database}: target_recovery_time {current}s -> {new_value}s")
    # In production: ALTER DATABASE [db] SET TARGET_RECOVERY_TIME = new_value SECONDS
    # Omitted here for brevity — see the configuration management module.

The autonomous controller does not apply all recommendations simultaneously. It implements a one-parameter-per-cycle rule: change one variable, wait two checkpoint cycles, observe the new checkpoint pages/sec rate and I/O stall trend, and decide whether to apply the next recommendation. This is a primitive form of causal isolation — changing one parameter at a time and waiting for the system to reach steady state before making another change. Violating this principle produces configuration drift where the cause of a performance improvement or regression is impossible to identify.

Autonomous Index Storage Reorganization and Bloat Remediation

Index and table bloat is one of the most predictable sources of I/O waste in long-running SQL Server deployments. Deleted rows leave ghost records in pages. Index entries accumulate for rows that no longer exist. Over time, a table that logically contains 10 million rows may span pages sized for far more — and a large share of every I/O operation retrieves ghost records that the cleanup task has not yet reclaimed.

Autonomous bloat remediation differs from a fixed maintenance schedule in a critical way: it is reactive to measured waste, not a calendar. The system continuously estimates waste using the sys.dm_db_index_physical_stats DMV, and it acts when waste crosses a defined threshold relative to the cost of remediation.

-- Identify indexes with significant fragmentation eligible for autonomous rebuild or reorganize
SELECT
    OBJECT_NAME(ips.object_id)           AS table_name,
    i.name                               AS index_name,
    ips.index_type_desc,
    ips.avg_fragmentation_in_percent,
    ips.page_count,
    ips.avg_page_space_used_in_percent,
    ips.record_count,
    ips.ghost_record_count,
    CASE
        WHEN ips.avg_fragmentation_in_percent > 30 THEN 'REBUILD'
        WHEN ips.avg_fragmentation_in_percent > 10 THEN 'REORGANIZE'
        ELSE 'NONE'
    END AS recommended_action
FROM sys.dm_db_index_physical_stats(
    DB_ID(), NULL, NULL, NULL, 'SAMPLED'
) ips
JOIN sys.indexes i
    ON i.object_id = ips.object_id
    AND i.index_id = ips.index_id
WHERE ips.page_count > 1000
  AND ips.avg_fragmentation_in_percent > 10
ORDER BY ips.avg_fragmentation_in_percent DESC;

The remediation decision tree is more nuanced than fragmentation percentage alone. ALTER INDEX ... REORGANIZE is the first-line response — it compacts pages and reclaims ghost records without requiring an offline window. ALTER INDEX ... REBUILD WITH (ONLINE = ON) is the second-line response, reserved for cases where fragmentation has grown so severe that page count has expanded significantly beyond the logical data size. The autonomous agent calculates a waste ratio: (page_count * 8KB) / (record_count * avg_record_size_in_bytes). When this ratio exceeds 2.0 and REORGANIZE has not reduced it within a configured window, an online REBUILD is scheduled.

For SQL Server, the REORGANIZE vs REBUILD decision is made per-index based on fragmentation percentage and whether the index supports online rebuild. The autonomous agent constructs and executes the appropriate DDL, wrapped in a resource governor classification that limits I/O to a configurable percentage of device throughput during execution, preventing remediation from becoming its own source of I/O saturation.

A safety interlock prevents the autonomous bloat remediation system from executing during periods of high I/O utilization. The agent checks iostat device utilization and waits if any data device exceeds 70% utilization — using an exponential backoff with a maximum wait of 4 hours before escalating to an alert.

Partition-Based I/O Shaping and Autonomous Data Lifecycle Management

Partitioning is the most powerful tool available for shaping I/O patterns at the schema level. When a time-series table is partitioned by date, queries that filter on recent dates touch only the most recent partitions — the working set fits in buffer pool, sequential scan performance is predictable, and I/O pressure on older partitions drops to zero unless explicitly accessed. Autonomous data lifecycle management takes this further: it creates new partitions before they are needed, migrates aging partitions to cold storage, compresses or archives them on a schedule derived from observed access patterns, and detaches them from the parent table when they become permanently dormant.

The lifecycle engine manages five partition states: active (receiving writes and serving reads), warm (serving reads, no writes), cold (rarely accessed, eligible for compression), archived (moved to cold tablespace or object storage), and detached (removed from the partition tree, accessible only via direct query).

Autonomous partition creation is the most time-sensitive operation. A system that allows a partition to be missing during a high-write period will fail with partition scheme exhaustion. The creation agent runs hourly and ensures partitions exist for the current period plus two future periods.

-- Extend a partition scheme to accommodate future periods
-- Assumes partition function pfn_daily_range already exists
DECLARE @next_boundary DATE = CAST(DATEADD(DAY, 7, GETDATE()) AS DATE);

-- Add boundary points for each missing future day
DECLARE @d DATE = CAST(DATEADD(DAY, 1, GETDATE()) AS DATE);
WHILE @d <= @next_boundary
BEGIN
    -- Only add if boundary does not already exist
    IF NOT EXISTS (
        SELECT 1 FROM sys.partition_range_values prv
        JOIN sys.partition_functions pf ON pf.function_id = prv.function_id
        WHERE pf.name = 'pfn_daily_range'
          AND CAST(prv.value AS DATE) = @d
    )
    BEGIN
        -- Partition scheme must have NEXT USED filegroup designated
        ALTER PARTITION SCHEME psc_daily_range NEXT USED [warm_filegroup];
        ALTER PARTITION FUNCTION pfn_daily_range() SPLIT RANGE (@d);
        RAISERROR('Added partition boundary: %s', 0, 1, @d) WITH NOWAIT;
    END
    SET @d = DATEADD(DAY, 1, @d);
END

The partition lifecycle agent also handles the opposite end of the spectrum: identifying partitions that have transitioned from warm to cold based on observed access counts, and triggering compression or tablespace migration. This means switching the partition out to a staging table on the cold filegroup and applying DATA_COMPRESSION = PAGE before switching it back in.

import pyodbc
from datetime import datetime, timedelta
import logging

COLD_THRESHOLD_DAYS = 30       # partitions older than this are candidates for cold tier
ACCESS_THRESHOLD = 10          # avg reads per collection interval below which = cold
COLD_FILEGROUP = "ColdFG"
HOT_FILEGROUP  = "HotFG"

def get_partition_access_stats(conn, partitioned_table: str, schema: str = "dbo"):
    """Return recent I/O stats for each partition of a partitioned table."""
    cur = conn.cursor()
    cur.execute("""
        SELECT
            p.partition_number,
            fg.name AS current_filegroup,
            COALESCE(AVG(m.reads_delta), 0) AS avg_reads,
            MAX(m.collected_at)             AS last_access
        FROM sys.partitions p
        JOIN sys.indexes i
            ON i.object_id = p.object_id AND i.index_id = p.index_id
        JOIN sys.partition_schemes ps
            ON ps.data_space_id = i.data_space_id
        JOIN sys.destination_data_spaces dds
            ON dds.partition_scheme_id = ps.data_space_id
           AND dds.destination_id = p.partition_number
        JOIN sys.filegroups fg
            ON fg.data_space_id = dds.data_space_id
        JOIN sys.tables t ON t.object_id = p.object_id
        JOIN sys.schemas s ON s.schema_id = t.schema_id
        LEFT JOIN io_metrics_history m
            ON m.partition_number = p.partition_number
           AND m.collected_at >= DATEADD(DAY, -7, SYSUTCDATETIME())
        WHERE t.name = ? AND s.name = ?
          AND i.index_id IN (0, 1)
        GROUP BY p.partition_number, fg.name
    """, (partitioned_table, schema))
    return cur.fetchall()

def demote_cold_partitions(conn, partitioned_table: str, schema: str = "dbo",
                           dry_run: bool = True):
    rows = get_partition_access_stats(conn, partitioned_table, schema)
    cur = conn.cursor()

    for partition_number, current_fg, avg_reads, last_access in rows:
        # Partition age is derived from the boundary values of the partition function
        cur.execute("""
            SELECT CAST(rv.value AS DATE)
            FROM sys.partition_range_values rv
            JOIN sys.partition_functions pf ON pf.function_id = rv.function_id
            JOIN sys.indexes i ON i.data_space_id IN (
                SELECT ps.data_space_id FROM sys.partition_schemes ps
            )
            WHERE i.object_id = OBJECT_ID(?, 'U')
              AND rv.boundary_id = ?
        """, (f"{schema}.{partitioned_table}", partition_number))
        brow = cur.fetchone()
        if not brow:
            continue
        age_days = (datetime.utcnow().date() - brow[0]).days

        if age_days >= COLD_THRESHOLD_DAYS and avg_reads < ACCESS_THRESHOLD:
            if current_fg == HOT_FILEGROUP:
                logging.info(
                    f"Demoting partition {partition_number}: "
                    f"age={age_days}d, avg_reads={avg_reads:.1f}"
                )
                if not dry_run:
                    # SWITCH out to a staging table on the cold filegroup,
                    # apply PAGE compression, SWITCH back in.
                    cur.execute(
                        f"ALTER TABLE {schema}.{partitioned_table} "
                        f"SWITCH PARTITION {partition_number} "
                        f"TO {schema}.{partitioned_table}_cold_stage "
                        f"PARTITION {partition_number}"
                    )
                    cur.execute(
                        f"ALTER INDEX ALL ON {schema}.{partitioned_table}_cold_stage "
                        "REBUILD PARTITION = ALL "
                        f"WITH (DATA_COMPRESSION = PAGE) ON [{COLD_FILEGROUP}]"
                    )
                    conn.commit()
                    logging.info(f"Moved partition {partition_number} to {COLD_FILEGROUP}")
            else:
                logging.debug(f"Partition {partition_number} already on {current_fg}")
        else:
            logging.debug(
                f"Partition {partition_number}: age={age_days}d, "
                f"avg_reads={avg_reads:.1f} — no action"
            )

The combination of forward partition creation and backward partition demotion forms a complete data lifecycle pipeline. The system maintains a predictable working set on fast storage, prevents partition exhaustion failures, and continuously reclaims expensive NVMe capacity by moving dormant data to cheaper tiers — all without human scheduling.

Autonomous Buffer Pool Management and Prefetch Tuning

The database buffer pool is the primary mechanism for keeping frequently accessed pages in memory and avoiding physical I/O. SQL Server's buffer pool operates on an LRU-K-variant eviction policy. The engine already resizes the buffer pool dynamically within the max server memory bound, so autonomous buffer pool management focuses on shaping what competes for that memory. Autonomous buffer pool management bridges this gap.

In SQL Server, the buffer pool is managed dynamically by SQLOS within the max server memory bound. The autonomous layer adjusts max server memory within guardrails in response to page life expectancy trends and memory grant pressure, configures Buffer Pool Extension on fast SSD tiers as a second-level cache, and uses Resource Governor memory limits to keep runaway workloads from monopolizing the buffer pool.

-- SQL Server: warm the buffer pool after a partition migration by scanning
-- the newly promoted partition into memory ahead of the workload
SELECT COUNT_BIG(*)
FROM dbo.Orders_2024_11_15 WITH (INDEX(1));  -- clustered scan pulls pages into the buffer pool

In SQL Server, the buffer pool is managed dynamically by the memory manager (SQLOS), and the autonomous layer can influence it through Resource Governor memory limits, max server memory adjustments, and Buffer Pool Extension (BPE) configuration on systems with fast SSD tiers. The more powerful lever in SQL Server is identifying which buffer pages are being evicted and why, using sys.dm_os_buffer_descriptors.

-- Identify the distribution of buffer pool pages by database and object
-- to understand what is consuming the working set
SELECT
    DB_NAME(bd.database_id)             AS database_name,
    OBJECT_NAME(p.object_id, bd.database_id) AS object_name,
    i.name                              AS index_name,
    COUNT(*)                            AS pages_in_buffer,
    COUNT(*) * 8 / 1024                 AS size_in_buffer_mb,
    SUM(CAST(bd.is_modified AS INT))    AS dirty_pages
FROM sys.dm_os_buffer_descriptors bd
JOIN sys.allocation_units au
    ON bd.allocation_unit_id = au.allocation_unit_id
JOIN sys.partitions p
    ON au.container_id = CASE
        WHEN au.type IN (1, 3) THEN p.hobt_id
        WHEN au.type = 2       THEN p.partition_id
    END
JOIN sys.indexes i
    ON i.object_id = p.object_id
    AND i.index_id = p.index_id
WHERE bd.database_id NOT IN (1, 2, 3, 4)  -- exclude system databases
  AND bd.page_type = 'DATA_PAGE'
GROUP BY bd.database_id, p.object_id, i.name
HAVING COUNT(*) > 100
ORDER BY pages_in_buffer DESC;

The autonomous prefetch tuner operates at a different level. Rather than reacting to buffer pool contents, it predicts which pages will be needed and initiates reads before the query arrives. This is useful for scheduled workloads with known access patterns — nightly reporting jobs that always scan the same partition ranges, or ETL pipelines that process data in a known order.

The prefetch system maintains a workload schedule: a table of recurring queries with their historical execution start times, observed I/O patterns (which table and partition ranges they read), and typical page counts. Before a scheduled job runs, the prefetch agent issues covering scans over the expected partition ranges ahead of the job, pulling pages into the buffer pool before the workload arrives.

from datetime import datetime, timedelta
import pyodbc
import schedule
import time
import logging

PREWARM_LEAD_TIME_MINUTES = 10
MSSQL_DSN = (
    "DRIVER={ODBC Driver 18 for SQL Server};"
    "SERVER=sql-primary;DATABASE=Sales;Trusted_Connection=yes;"
)

WORKLOAD_SCHEDULE = [
    {
        "name": "nightly_revenue_report",
        "cron_time": "02:00",
        "tables_to_prewarm": [
            "dbo.Orders_2024_11_14",
            "dbo.Orders_2024_11_15",
            "dbo.Orders_2024_11_16",
        ],
    },
    {
        "name": "weekly_churn_analysis",
        "cron_time": "03:30",
        "tables_to_prewarm": [
            "dbo.CustomerEvents_2024_10",
            "dbo.CustomerEvents_2024_11",
        ],
    },
]

def prewarm_tables(conn, tables):
    cur = conn.cursor()
    for table in tables:
        try:
            # Covering scan pulls the table's pages into the buffer pool
            cur.execute(f"SELECT COUNT_BIG(*) FROM {table} WITH (INDEX(1))")
            pages = cur.fetchone()[0]
            conn.commit()
            logging.info(f"Prewarmed {table}: scan touched {pages} rows")
        except Exception as e:
            conn.rollback()
            logging.error(f"Failed to prewarm {table}: {e}")

def schedule_prewarm_jobs(conn):
    for job in WORKLOAD_SCHEDULE:
        job_hour, job_minute = map(int, job["cron_time"].split(":"))
        prewarm_dt = datetime.now().replace(
            hour=job_hour, minute=job_minute, second=0
        ) - timedelta(minutes=PREWARM_LEAD_TIME_MINUTES)
        prewarm_time_str = prewarm_dt.strftime("%H:%M")

        schedule.every().day.at(prewarm_time_str).do(
            prewarm_tables, conn=conn, tables=job["tables_to_prewarm"]
        )
        logging.info(
            f"Scheduled prewarm for '{job['name']}' at {prewarm_time_str}"
        )

def run():
    conn = pyodbc.connect(MSSQL_DSN)
    schedule_prewarm_jobs(conn)
    while True:
        schedule.run_pending()
        time.sleep(30)

if __name__ == "__main__":
    run()

This predictive prefetch approach reduces the latency spike that occurs when a large reporting job starts cold. Instead of spending the first several minutes of execution time loading pages from disk, the job finds its data already resident in the buffer pool and begins processing at full speed.

Transaction Log I/O Optimization

The transaction log is the highest-priority I/O path in SQL Server. Every committed transaction must have its log record durably written before the commit acknowledgment is returned to the client. Any contention, latency spike, or device saturation on the log device directly increases transaction commit latency for every session simultaneously.

Autonomous log optimization has three concerns: device placement, write batching behavior, and log size management.

Device placement is handled at the infrastructure level: The log should live on a dedicated device separate from data files, ideally one optimized for sequential write throughput rather than random read IOPS. The autonomous agent validates this configuration by checking the mount point of the log files via sys.master_files against the list of known device paths and their I/O characteristics. When log and data share a device, an alert is raised and, if a suitable dedicated device is available in the device inventory, an automated migration is initiated.

Write batching in SQL Server is controlled by delayed durability. The DELAYED_DURABILITY = ALLOWED database option lets transactions return before their log records are flushed — a group-commit pattern that batches multiple commits into a single log flush. The autonomous controller enables delayed durability selectively for non-critical workloads based on observed WRITELOG wait time in sys.dm_os_wait_stats and the ratio of active sessions to commits per second.

-- SQL Server: transaction log I/O telemetry per database
SELECT
    DB_NAME(vfs.database_id)              AS database_name,
    vfs.num_of_bytes_written              AS log_bytes_written,
    vfs.io_stall_write_ms                 AS log_write_stall_ms,
    CASE WHEN vfs.num_of_writes = 0 THEN 0
         ELSE vfs.io_stall_write_ms * 1.0 / vfs.num_of_writes END AS avg_write_stall_ms,
    lu.used_log_space_pct                 AS used_log_space_pct
FROM sys.dm_io_virtual_file_stats(NULL, NULL) vfs
JOIN sys.master_files mf
    ON vfs.database_id = mf.database_id AND vfs.file_id = mf.file_id
JOIN sys.dm_db_log_space_usage lu ON lu.database_id = vfs.database_id
WHERE mf.type_desc = 'LOG';

When WRITELOG waits dominate sys.dm_os_wait_stats and average log write stall climbs, the underlying device cannot sustain the flush rate — the correct intervention is either device upgrade or, as a temporary measure, enabling delayed durability for non-critical workloads. The autonomous system never sets DELAYED_DURABILITY = FORCED without explicit operator permission, since this sacrifices crash safety. The decision is encoded as a policy flag:

DELAYED_DURABILITY_POLICY = {
    "allow_delayed": True,   # may enable delayed durability for non-critical workloads
    "allow_forced":  False,  # never force delayed durability without human approval
}

In SQL Server, the transaction log is managed through VLF (virtual log file) architecture. A log file that has been grown many times in small increments accumulates hundreds of small VLFs, which degrades log scan performance during recovery. The autonomous agent monitors VLF count using DBCC LOGINFO and proactively grows the log in larger increments to consolidate VLFs when the count exceeds a configurable threshold.

-- SQL Server: Count VLFs per database log file
CREATE TABLE #vlf_info (
    RecoveryUnitId  INT,
    FileId          INT,
    FileSize        BIGINT,
    StartOffset     BIGINT,
    FSeqNo          BIGINT,
    Status          INT,
    Parity          INT,
    CreateLSN       NUMERIC(25,0)
);

EXEC sp_MSforeachdb '
    USE [?];
    INSERT INTO #vlf_info
    EXEC(''DBCC LOGINFO WITH NO_INFOMSGS'');
';

SELECT
    DB_NAME()     AS database_name,
    COUNT(*)      AS vlf_count,
    SUM(FileSize) / 1024 / 1024 AS total_log_mb,
    SUM(CASE WHEN Status = 2 THEN 1 ELSE 0 END) AS active_vlfs
FROM #vlf_info;

DROP TABLE #vlf_info;

When VLF count exceeds the threshold (commonly set to 200 for databases under 100GB), the remediation path is to shrink the log file to minimum size (which forces VLF consolidation), then immediately grow it in a single large allocation. This is a brief operation that causes no data loss but does require the log to not be actively written — the agent schedules it during the low-traffic window identified by the I/O utilization monitor.

Integrating Storage Autonomy with the Broader Control Loop

Each of the subsystems described in this chapter — I/O instrumentation, tablespace tiering, checkpoint control, bloat remediation, partition lifecycle management, buffer pool prefetch, and WAL optimization — can function independently. But maximum effectiveness comes from integration: a shared signal bus where each subsystem both reads from and writes to a common state model.

The integration point is the storage control plane: a lightweight service that aggregates signals from all subsystems and arbitrates competing actions. Without arbitration, subsystems can conflict. An index rebuild and a filegroup migration might both attempt to take conflicting locks on the same table simultaneously. A checkpoint control adjustment that increases TARGET_RECOVERY_TIME might interact adversely with a log device migration in progress. A partition prewarm job might run during peak I/O utilization and compete with active queries.

graph TD
    A[Filegroup Tiering] -->|register intent| G[Storage Control Plane]
    B[Bloat Remediation] -->|register intent| G
    C[Checkpoint Control] -->|register intent| G
    D[Partition Lifecycle] -->|register intent| G
    E[Buffer Pool / Prefetch] -->|register intent| G
    F[Log Optimization] -->|register intent| G
    G -->|conflict check + I/O budget check| H{Grant or Defer}
    H -->|granted| I[Action Executes]
    H -->|denied: object locked or budget exceeded| J[Deferred / Retried Next Cycle]
    G --> K[Audit Log]

*Every autonomous storage subsystem registers its intent with the storage control plane before acting; the plane grants or defers based on object-level conflicts and the global I/O budget.*

The control plane maintains a global I/O budget: a maximum number of concurrent I/O-intensive operations, a ceiling on MB/s consumed by background tasks, and an exclusion list of objects currently undergoing any autonomous action. Before any subsystem initiates an action, it registers an intent with the control plane, which checks for conflicts and grants or denies the action based on current system state.

import threading
import time
from dataclasses import dataclass, field
from typing import Dict, Optional
from enum import Enum

class ActionType(Enum):
    FILEGROUP_MOVE    = "filegroup_move"
    BLOAT_REMEDIATION = "bloat_remediation"
    PARTITION_CREATE  = "partition_create"
    PARTITION_DEMOTE  = "partition_demote"
    CHECKPOINT_TUNE   = "checkpoint_tune"
    LOG_TUNE          = "log_tune"
    PREWARM           = "prewarm"

@dataclass
class ActionIntent:
    action_type:   ActionType
    target_object: str              # schema.table or partition name
    estimated_io_mb: float
    requester:     str
    granted:       bool = False
    started_at:    Optional[float] = None

class StorageControlPlane:
    MAX_CONCURRENT_IO_OPS   = 2
    MAX_BACKGROUND_IO_MBS   = 200.0

    def __init__(self):
        self._lock          = threading.Lock()
        self._active: Dict[str, ActionIntent] = {}
        self._io_budget_used = 0.0

    def request_action(self, intent: ActionIntent) -> bool:
        with self._lock:
            # Check object-level conflict
            if intent.target_object in self._active:
                existing = self._active[intent.target_object]
                print(
                    f"CONFLICT: {intent.action_type.value} on {intent.target_object} "
                    f"blocked by {existing.action_type.value} from {existing.requester}"
                )
                return False

            # Check global I/O concurrency
            if len(self._active) >= self.MAX_CONCURRENT_IO_OPS:
                print(f"IO_BUDGET: max concurrent ops reached, deferring {intent.action_type.value}")
                return False

            # Check I/O bandwidth budget
            if self._io_budget_used + intent.estimated_io_mb > self.MAX_BACKGROUND_IO_MBS:
                print(f"IO_BUDGET: bandwidth ceiling reached, deferring {intent.action_type.value}")
                return False

            intent.granted   = True
            intent.started_at = time.time()
            self._active[intent.target_object] = intent
            self._io_budget_used += intent.estimated_io_mb
            return True

    def release_action(self, target_object: str):
        with self._lock:
            if target_object in self._active:
                released = self._active.pop(target_object)
                self._io_budget_used = max(0.0, self._io_budget_used - released.estimated_io_mb)

    def active_actions(self):
        with self._lock:
            return dict(self._active)

This control plane is deliberately simple — a threading lock over an in-memory dictionary. In production deployments across multiple database hosts, it would be backed by a distributed coordination service (etcd, Redis with Lua transactions, or a purpose-built sidecar). But the core contract is the same regardless of implementation: every background storage action must declare its intent, every execution is gated by a conflict check and a budget check, and every completion releases the held resources.

The control plane also serves as the audit log entry point. Every granted and denied action is written to a structured log that the observability layer reads for post-hoc analysis. When storage performance degrades unexpectedly, the audit log shows precisely which autonomous operations were active at the time, making root cause analysis tractable rather than speculative.

Key Takeaways

  • → Observability at three levels is non-negotiable: object-level, engine-level, and block-device-level I/O metrics must be collected simultaneously and at sub-minute granularity. Conflating these three levels produces misleading signals that drive incorrect autonomous actions.
  • → Tiering decisions must be based on measured heat scores, not age alone: access frequency, write volume, and recency of modification together determine whether a relation belongs on fast NVMe or cold-tier storage. Age-based policies fail when access patterns shift and yesterday's archive becomes today's active dataset.
  • → Checkpoint and log tuning must follow a one-parameter-per-cycle discipline: changing TARGET_RECOVERY_TIME and related settings simultaneously makes causal attribution impossible. Autonomous controllers must change one variable, observe two full checkpoint cycles, and evaluate before proceeding.
  • → Partition lifecycle automation closes the gap between theoretical tiering policy and operational reality: forward partition creation prevents exhaustion failures; backward partition demotion continuously reclaims fast-tier capacity. Neither is sufficient without the other, and both must integrate with the broader I/O control plane to avoid lock conflicts and bandwidth saturation.
  • → A storage control plane with I/O budgeting and object-level conflict detection is required before deploying multiple autonomous storage subsystems concurrently: without arbitration, independent subsystems will schedule conflicting operations, exhaust I/O bandwidth, and create the exact instability they were designed to prevent.
