Chapter 18: Autonomous Disaster Recovery

Disaster recovery has always been the discipline where human judgment mattered most — the 3 a.m. call, the war-room decision, the tense minutes choosing between data loss and extended downtime. Autonomous systems change that contract entirely. When your DR pipeline self-monitors replication health, self-diagnoses failure mode, self-selects a recovery path, and self-executes a tested runbook without waiting for a human to wake up, your RTO shrinks from hours to seconds and your RPO approaches zero. This chapter covers the architecture and implementation of fully autonomous DR systems for PostgreSQL and SQL Server — systems that observe failure signals at the infrastructure layer, reason about failure type and blast radius, execute tiered recovery actions with circuit breakers, and validate recovery integrity before re-admitting traffic, all without manual intervention.

---

Failure Taxonomy and Autonomous Signal Acquisition

Before an autonomous system can recover from a disaster, it must correctly classify what it is recovering from. Treating a network partition the same as a storage corruption or an application-level connection flood produces wrong recovery actions and can worsen the situation. A taxonomy-first architecture forces the system to gate all recovery paths through a classification layer before execution.

The five failure classes that autonomous DR must handle independently are:

1. Primary node loss — the database process or host becomes unreachable

2. Replication lag breach — standby is alive but diverging beyond RPO threshold

3. Split-brain ambiguity — multiple nodes believe they are primary

4. Data corruption — block-level, page-level, or logical corruption on disk or in transit

5. Region/AZ failure — an entire failure domain becomes unavailable

Signal acquisition for each class requires distinct sensor types. For node loss, TCP health checks and PostgreSQL pg_isready / SQL Server @@SERVERNAME reachability form the first layer. For replication lag, you instrument the replication stream directly.

-- Replication lag sensor for Always On AG
SELECT
    ag.name AS ag_name,
    ar.replica_server_name,
    drs.database_name,
    drs.synchronization_state_desc,
    drs.synchronization_health_desc,
    drs.log_send_queue_size,
    drs.redo_queue_size,
    drs.last_commit_time,
    DATEDIFF(SECOND, drs.last_commit_time, GETUTCDATE()) AS lag_seconds
FROM sys.dm_hadr_database_replica_states drs
JOIN sys.availability_replicas ar
    ON drs.replica_id = ar.replica_id
JOIN sys.availability_groups ag
    ON ar.group_id = ag.group_id
WHERE drs.is_local = 0;

These queries run on a 5-second scrape interval from a Prometheus exporter. When replication_lag_bytes exceeds your RPO threshold (converted to bytes using average WAL generation rate) or heartbeat_age_seconds exceeds 15 seconds, the signal is emitted to the classification engine.

The classification engine is a Python process that aggregates signals across layers — network, OS, database process, replication, and application — before assigning a failure class. It deliberately waits 10–30 seconds before acting, using a voting window to distinguish transient blips from real events:

import time
import collections
from dataclasses import dataclass, field
from enum import Enum
from typing import Optional

class FailureClass(Enum):
    NODE_LOSS = "node_loss"
    REPLICATION_LAG = "replication_lag"
    SPLIT_BRAIN = "split_brain"
    DATA_CORRUPTION = "data_corruption"
    AZ_FAILURE = "az_failure"
    UNKNOWN = "unknown"

@dataclass
class FailureSignal:
    source: str
    signal_type: str
    severity: float          # 0.0 to 1.0
    timestamp: float = field(default_factory=time.time)

class FailureClassifier:
    VOTE_WINDOW_SECONDS = 20
    CONFIDENCE_THRESHOLD = 0.70

    def __init__(self):
        self.signal_buffer: list[FailureSignal] = []

    def ingest(self, signal: FailureSignal):
        self.signal_buffer.append(signal)
        self._evict_stale()

    def classify(self) -> tuple[FailureClass, float]:
        if not self.signal_buffer:
            return FailureClass.UNKNOWN, 0.0

        votes: dict[FailureClass, float] = collections.defaultdict(float)

        for sig in self.signal_buffer:
            if sig.signal_type == "tcp_unreachable" and sig.severity > 0.8:
                votes[FailureClass.NODE_LOSS] += sig.severity
            elif sig.signal_type == "replication_lag_bytes" and sig.severity > 0.6:
                votes[FailureClass.REPLICATION_LAG] += sig.severity
            elif sig.signal_type == "dual_primary_detected":
                votes[FailureClass.SPLIT_BRAIN] += sig.severity * 2  # escalate weight
            elif sig.signal_type == "checksum_failure":
                votes[FailureClass.DATA_CORRUPTION] += sig.severity
            elif sig.signal_type == "az_health_degraded" and sig.severity > 0.9:
                votes[FailureClass.AZ_FAILURE] += sig.severity

        if not votes:
            return FailureClass.UNKNOWN, 0.0

        top_class = max(votes, key=votes.__getitem__)
        total = sum(votes.values())
        confidence = votes[top_class] / total if total > 0 else 0.0

        if confidence >= self.CONFIDENCE_THRESHOLD:
            return top_class, confidence
        return FailureClass.UNKNOWN, confidence

    def _evict_stale(self):
        cutoff = time.time() - self.VOTE_WINDOW_SECONDS
        self.signal_buffer = [s for s in self.signal_buffer if s.timestamp >= cutoff]

The classifier only fires a recovery action when confidence exceeds 70% within the vote window. This is not a soft threshold — it is a hard gate. Below 70%, the system escalates to a human via PagerDuty while continuing to collect signals. Above 70%, the recovery pipeline fires autonomously.

Autonomous Failover Architecture: Patroni, pg_auto_failover, and SQL Server Always On

Once failure is classified and confidence is sufficient, the autonomous system hands off to the failover execution layer. For PostgreSQL, two production-grade tools represent distinct architectural philosophies: Patroni (consensus-based, etcd/Consul/ZooKeeper-backed) and pg_auto_failover (coordinator-based, simpler operationally). For SQL Server, Always On Availability Groups with the Windows Server Failover Cluster or a Pacemaker equivalent on Linux provide the failover substrate.

#### Patroni: Consensus-Driven Autonomous Failover

Patroni uses a distributed configuration store (etcd by default) as its consensus layer. The leader key in etcd has a TTL; when the primary fails to renew it, a candidate replica wins the election and promotes itself. For fully autonomous operation, the key configuration parameters are:

# patroni.yml — production autonomous configuration
name: pg-primary-az1

restapi:
  listen: 0.0.0.0:8008
  connect_address: 10.0.1.10:8008

etcd3:
  hosts: 10.0.0.1:2379,10.0.0.2:2379,10.0.0.3:2379

bootstrap:
  dcs:
    ttl: 30
    loop_wait: 10
    retry_timeout: 30
    maximum_lag_on_failover: 1048576      # 1 MB — RPO gate
    master_start_timeout: 300
    synchronous_mode: true                # enforce sync replication
    synchronous_mode_strict: false        # allow async fallback if sync replica lost
    postgresql:
      use_pg_rewind: true
      use_slots: true
      parameters:
        wal_level: replica
        hot_standby: "on"
        max_wal_senders: 10
        max_replication_slots: 10
        wal_log_hints: "on"

postgresql:
  listen: 0.0.0.0:5432
  connect_address: 10.0.1.10:5432
  data_dir: /data/postgresql/14/main
  pgpass: /tmp/pgpass0
  authentication:
    replication:
      username: replicator
      password: "${REPLICATION_PASSWORD}"
    superuser:
      username: postgres
      password: "${POSTGRES_PASSWORD}"

tags:
  nofailover: false
  noloadbalance: false
  clonefrom: false
  nosync: false

The maximum_lag_on_failover: 1048576 parameter is your RPO gate. If a candidate replica is more than 1 MB behind the last known primary LSN, Patroni will not promote it — preventing an autonomous failover that would lose unacceptable data. Combined with synchronous_mode: true, Patroni ensures at least one replica is always synchronous, making the 1 MB threshold meaningful primarily for asynchronous replicas in multi-replica topologies.

#### pg_auto_failover: Coordinator-Based Simplicity

For teams running smaller topologies (2–3 nodes), pg_auto_failover provides a monitor-based approach with less operational overhead than Patroni's etcd dependency:

#### SQL Server Always On with Automatic Failover

SQL Server AG automatic failover requires WSFC quorum on Windows or Pacemaker on Linux. The key autonomous configuration is the FAILOVER_MODE = AUTOMATIC clause combined with health check thresholds:

-- Create AG with autonomous failover configuration
CREATE AVAILABILITY GROUP [AG_Production]
WITH (
    AUTOMATED_BACKUP_PREFERENCE = SECONDARY,
    HEALTH_CHECK_TIMEOUT = 30000,          -- 30 seconds before declaring unhealthy
    DB_FAILOVER = ON,                       -- fail over on database-level health issues
    DTC_SUPPORT = NONE,
    REQUIRED_SYNCHRONIZED_SECONDARIES_TO_COMMIT = 1  -- synchronous commit gate
)
FOR DATABASE [AppDB], [ReportDB]
REPLICA ON
    N'sql-primary' WITH (
        ENDPOINT_URL = N'TCP://sql-primary.internal:5022',
        AVAILABILITY_MODE = SYNCHRONOUS_COMMIT,
        FAILOVER_MODE = AUTOMATIC,
        SEEDING_MODE = AUTOMATIC,
        SECONDARY_ROLE (ALLOW_CONNECTIONS = READ_ONLY)
    ),
    N'sql-secondary' WITH (
        ENDPOINT_URL = N'TCP://sql-secondary.internal:5022',
        AVAILABILITY_MODE = SYNCHRONOUS_COMMIT,
        FAILOVER_MODE = AUTOMATIC,
        SEEDING_MODE = AUTOMATIC,
        SECONDARY_ROLE (ALLOW_CONNECTIONS = READ_ONLY)
    );

-- Set flexible failover policy (SQL Server 2019+)
ALTER AVAILABILITY GROUP [AG_Production]
    MODIFY REPLICA ON N'sql-primary'
    WITH (FAILURE_CONDITION_LEVEL = 3);
-- Level 3: fail on critical SQL Server errors, not just process crashes

FAILURE_CONDITION_LEVEL = 3 is the recommended production setting. Level 1 triggers on server-down only; Level 3 adds SQL Server internal critical errors and orphaned spinlocks. Level 5 (any qualified failure condition) produces too many false positives in multi-tenant environments.

Connection string design matters enormously for autonomous failover. Applications must use the AG listener, not the instance name, and must set MultiSubnetFailover=True and ConnectRetryCount=3 to survive the ~15–30 second WSFC transition window without returning errors to the application layer.

RPO-Aware Autonomous Recovery Decision Engine

Automatic failover tools (Patroni, AG automatic failover) handle the happy path — clean primary failure, healthy synchronous replica, quorum intact. Production disasters rarely follow this path. Your autonomous system needs a decision engine that reasons about recovery options when conditions are degraded: the synchronous replica is also down, the lag breach is severe, the DCS is unreachable, or you face a true split-brain.

The recovery decision engine is a state machine that maps (failure class, current topology state) → recovery action. The topology state is pulled from the cluster's own metadata store:

import psycopg2
import pyodbc
import subprocess
import logging
from enum import Enum
from typing import NamedTuple

logger = logging.getLogger("autonomous_dr")

class RecoveryAction(Enum):
    PROMOTE_SYNC_REPLICA   = "promote_sync_replica"
    PROMOTE_ASYNC_REPLICA  = "promote_async_replica_with_data_loss_ack"
    RESTORE_FROM_BACKUP    = "restore_from_backup"
    WAIT_FOR_PRIMARY       = "wait_for_primary_recovery"
    ESCALATE_TO_HUMAN      = "escalate_to_human"
    FENCE_OLD_PRIMARY      = "fence_old_primary"

class TopologyState(NamedTuple):
    sync_replica_available: bool
    sync_replica_lag_bytes: int
    async_replica_available: bool
    async_replica_lag_bytes: int
    dcs_quorum_healthy: bool
    old_primary_network_reachable: bool
    rpo_bytes: int    # configured RPO converted to bytes

class RecoveryDecisionEngine:

    def decide(self, failure_class, topo: TopologyState) -> RecoveryAction:
        # Split-brain: fence before anything else
        if failure_class == "split_brain":
            if topo.old_primary_network_reachable:
                return RecoveryAction.FENCE_OLD_PRIMARY
            return RecoveryAction.ESCALATE_TO_HUMAN

        # Primary lost, DCS unhealthy — can't safely elect
        if not topo.dcs_quorum_healthy:
            logger.warning("DCS quorum unhealthy — cannot safely elect new primary")
            return RecoveryAction.ESCALATE_TO_HUMAN

        # Primary lost, sync replica available and within RPO
        if (failure_class == "node_loss"
                and topo.sync_replica_available
                and topo.sync_replica_lag_bytes <= topo.rpo_bytes):
            return RecoveryAction.PROMOTE_SYNC_REPLICA

        # Primary lost, sync replica down or lagging, async within RPO
        if (failure_class == "node_loss"
                and not topo.sync_replica_available
                and topo.async_replica_available
                and topo.async_replica_lag_bytes <= topo.rpo_bytes):
            logger.warning(
                "Promoting async replica — lag=%d bytes within RPO=%d bytes",
                topo.async_replica_lag_bytes, topo.rpo_bytes
            )
            return RecoveryAction.PROMOTE_ASYNC_REPLICA

        # Primary lost, all replicas beyond RPO
        if failure_class == "node_loss" and not topo.sync_replica_available:
            logger.error("All replicas exceed RPO — data loss promotion requires human sign-off")
            return RecoveryAction.ESCALATE_TO_HUMAN

        # Replication lag breach on running primary — don't failover, investigate
        if failure_class == "replication_lag":
            return RecoveryAction.WAIT_FOR_PRIMARY  # triggers lag remediation pipeline

        # Data corruption detected
        if failure_class == "data_corruption":
            return RecoveryAction.RESTORE_FROM_BACKUP

        return RecoveryAction.ESCALATE_TO_HUMAN

*The recovery decision engine's mapping from failure class and topology state to action — every path that would exceed RPO without pre-authorization terminates in human escalation, never a silent promotion.*

Notice the deliberate conservatism: the engine escalates to a human whenever data loss would exceed the RPO and a human sign-off was not pre-authorized. This reflects a core ADE principle — autonomous systems must have explicit permission to cause data loss, not implicit permission by default. In practice, you can configure a data_loss_authorized: true flag per environment (acceptable in a dev/staging cluster, never in production without an SLA change).

The fencing action deserves special attention. Promoting a replica while the original primary is still reachable and accepting writes produces split-brain. The fence step must shoot the old primary in the head (STONITH — Shoot The Other Node In The Head) before completing promotion. On bare metal or VM infrastructure this is a power fence via IPMI/BMC. On cloud infrastructure it is an API call:

import boto3

def fence_ec2_instance(instance_id: str, region: str) -> bool:
    """
    Hard fence an EC2 instance by stopping it via AWS API.
    Returns True if fence succeeded, False if API call failed.
    The caller must verify instance state before proceeding with promotion.
    """
    ec2 = boto3.client("ec2", region_name=region)
    try:
        response = ec2.stop_instances(
            InstanceIds=[instance_id],
            Force=True   # equivalent to power cut — no graceful shutdown
        )
        state = response["StoppingInstances"][0]["CurrentState"]["Name"]
        logger.info("Fence initiated for %s — current state: %s", instance_id, state)

        # Poll for stopped state — max 60 seconds
        waiter = ec2.get_waiter("instance_stopped")
        waiter.wait(
            InstanceIds=[instance_id],
            WaiterConfig={"Delay": 5, "MaxAttempts": 12}
        )
        logger.info("Fence confirmed for %s", instance_id)
        return True
    except Exception as exc:
        logger.error("Fence failed for %s: %s", instance_id, exc)
        return False

If the fence fails, promotion must not proceed. A failed fence is an escalation event.

Automated Backup Validation and Point-in-Time Recovery Pipelines

Autonomous DR is only as strong as the backups it can restore from. Most organizations discover their backups are corrupted or incomplete during the actual disaster, not before. The autonomous pattern inverts this: restores are executed continuously in a shadow environment, and any failure in shadow restoration is treated as a current-severity alert.

The continuous restore pipeline operates on a schedule (typically every 4–8 hours for production databases) and validates three properties: restore completeness, data integrity, and RPO alignment.

For PostgreSQL with pgBackRest, the autonomous validation pipeline looks like:

#!/bin/bash
# Autonomous backup validation script — runs on isolated restore host
# Triggered by cron or Kubernetes CronJob every 6 hours

set -euo pipefail

RESTORE_TARGET_HOST="restore-validator.internal"
RESTORE_DATA_DIR="/data/restore-validate"
STANZA="pg-production"
ALERT_WEBHOOK="${PAGERDUTY_WEBHOOK_URL}"
SLACK_WEBHOOK="${SLACK_OPS_WEBHOOK}"

log() { echo "$(date -u +%Y-%m-%dT%H:%M:%SZ) $*"; }

# Step 1: Clean restore target
log "Clearing previous restore at ${RESTORE_DATA_DIR}"
rm -rf "${RESTORE_DATA_DIR}"
mkdir -p "${RESTORE_DATA_DIR}"

# Step 2: Restore latest backup
log "Starting pgBackRest restore for stanza ${STANZA}"
RESTORE_START=$(date +%s)

pgbackrest restore \
  --stanza="${STANZA}" \
  --pg1-path="${RESTORE_DATA_DIR}" \
  --type=default \
  --log-level-console=info \
  --process-max=4 \
  --recovery-option="recovery_target_action=promote"

RESTORE_END=$(date +%s)
RESTORE_DURATION=$((RESTORE_END - RESTORE_START))
log "Restore completed in ${RESTORE_DURATION} seconds"

# Step 3: Start PostgreSQL on restore host (non-production port)
pg_ctl -D "${RESTORE_DATA_DIR}" -o "-p 5433" start
sleep 10   # allow startup

# Step 4: Validate integrity
PSQL="psql -h localhost -p 5433 -U postgres"

CHECKSUM_RESULT=$($PSQL -c "SELECT pg_catalog.pg_verify_checksums('${RESTORE_DATA_DIR}');" -t 2>&1 || echo "FAILED")
TABLE_COUNT=$($PSQL -c "SELECT count(*) FROM information_schema.tables WHERE table_schema='public';" -t 2>&1)

# Step 5: Validate RPO — how old is the restored data?
LATEST_LSN=$($PSQL -c "SELECT pg_current_wal_lsn();" -t)
DB_TIME=$($PSQL -c "SELECT now();" -t)
CURRENT_TIME=$(date -u +%s)
DB_EPOCH=$($PSQL -c "SELECT EXTRACT(EPOCH FROM now())::bigint;" -t)
RPO_SECONDS=$((CURRENT_TIME - DB_EPOCH))

log "Restore validation: checksum=${CHECKSUM_RESULT}, tables=${TABLE_COUNT}, RPO_seconds=${RPO_SECONDS}"

# Step 6: Emit metrics to Prometheus pushgateway
cat <<EOF | curl --data-binary @- http://pushgateway.internal:9091/metrics/job/backup_validation
# TYPE backup_restore_duration_seconds gauge
backup_restore_duration_seconds{stanza="${STANZA}"} ${RESTORE_DURATION}
# TYPE backup_rpo_seconds gauge
backup_rpo_seconds{stanza="${STANZA}"} ${RPO_SECONDS}
# TYPE backup_validation_success gauge
backup_validation_success{stanza="${STANZA}"} $([ "$CHECKSUM_RESULT" != "FAILED" ] && echo 1 || echo 0)
EOF

# Step 7: Alert if validation failed
if [ "$CHECKSUM_RESULT" = "FAILED" ] || [ "$RPO_SECONDS" -gt 28800 ]; then
    log "VALIDATION FAILED — alerting ops"
    curl -s -X POST "${ALERT_WEBHOOK}" \
      -H "Content-Type: application/json" \
      -d "{\"severity\": \"critical\", \"summary\": \"Backup validation failed for stanza ${STANZA}\", \"rpo_seconds\": ${RPO_SECONDS}, \"checksum\": \"${CHECKSUM_RESULT}\"}"
fi

# Step 8: Shut down restore instance
pg_ctl -D "${RESTORE_DATA_DIR}" stop -m fast
log "Restore validation complete"

The SQL Server equivalent uses T-SQL's RESTORE VERIFYONLY for rapid validation before committing to a full restore, then moves to a full shadow restore on a scheduled basis:

-- Rapid backup file verification (run every backup cycle)
RESTORE VERIFYONLY
FROM DISK = N'\\backup-share\AppDB\AppDB_FULL_20240115.bak'
WITH
    CHECKSUM,
    STATS = 10;

-- Full shadow restore to validation instance (scheduled, separate from production)
RESTORE DATABASE [AppDB_Validate]
FROM DISK = N'\\backup-share\AppDB\AppDB_FULL_20240115.bak'
WITH
    MOVE N'AppDB_data' TO N'D:\ValidateData\AppDB_validate.mdf',
    MOVE N'AppDB_log'  TO N'D:\ValidateData\AppDB_validate.ldf',
    NORECOVERY,
    STATS = 5;

-- Apply latest differential
RESTORE DATABASE [AppDB_Validate]
FROM DISK = N'\\backup-share\AppDB\AppDB_DIFF_20240115.bak'
WITH
    NORECOVERY,
    STATS = 5;

-- Apply log chain to bring within RPO
RESTORE DATABASE [AppDB_Validate]
FROM DISK = N'\\backup-share\AppDB\AppDB_LOG_20240115_2300.trn'
WITH
    RECOVERY,
    STOPAT = '2024-01-15T23:59:59',
    STATS = 5;

-- Validate table counts and row counts post-restore
USE [AppDB_Validate];
SELECT
    t.name AS table_name,
    p.rows AS estimated_row_count
FROM sys.tables t
JOIN sys.partitions p
    ON t.object_id = p.object_id
WHERE p.index_id IN (0, 1)
ORDER BY p.rows DESC;

The shadow restore must run on a separate isolated instance — not a test schema on the production server. Restoring to the same instance risks corrupting production configuration, and the performance overhead of a large restore can degrade production query throughput.

Point-in-Time Recovery Automation

When data corruption or logical error is detected, the recovery action from the decision engine is RESTORE_FROM_BACKUP. Autonomous PITR must select the correct recovery target — not simply "restore the latest backup" but "restore to the point immediately before the corruption event was first detected."

The autonomous PITR pipeline needs three inputs:

1. The corruption detection timestamp (from the monitoring system)

2. The backup catalog (pgBackRest info or SQL Server msdb history)

3. The WAL/log archive to replay forward from the backup

PostgreSQL — Autonomous PITR selection:

import subprocess
import json
import datetime
import logging

logger = logging.getLogger("autonomous_pitr")

def select_pitr_target(corruption_detected_at: datetime.datetime, stanza: str) -> dict:
    """
    Select the appropriate backup and PITR target for autonomous restoration.
    Returns a dict with backup_label, recovery_target_time, and estimated_restore_minutes.
    corruption_detected_at: timezone-aware datetime of first corruption signal
    """
    # Add safety margin — restore to 5 minutes before detection
    # to avoid restoring to a point that might already contain corruption
    target_time = corruption_detected_at - datetime.timedelta(minutes=5)

    # Query pgBackRest backup catalog
    result = subprocess.run(
        ["pgbackrest", "--stanza", stanza, "--output", "json", "info"],
        capture_output=True, text=True, check=True
    )
    catalog = json.loads(result.stdout)

    # Find the most recent full or differential backup before target_time
    best_backup = None
    for stanza_info in catalog:
        if stanza_info["name"] != stanza:
            continue
        for backup in reversed(stanza_info.get("backup", [])):
            backup_stop_time = datetime.datetime.fromisoformat(
                backup["timestamp"]["stop"].replace("Z", "+00:00")
            )
            if backup_stop_time <= target_time:
                best_backup = backup
                break

    if best_backup is None:
        raise RuntimeError(
            f"No backup found before corruption target {target_time.isoformat()} "
            f"in stanza {stanza}"
        )

    backup_size_gb = best_backup["info"]["size"] / (1024 ** 3)
    # Estimate using a restore-throughput constant calibrated against your own
    # storage tier — measure it during a real restore rather than assuming a figure
    RESTORE_THROUGHPUT_MB_PER_SEC = 200
    estimated_restore_minutes = (backup_size_gb * 1024) / (RESTORE_THROUGHPUT_MB_PER_SEC * 60)

    logger.info(
        "Selected backup %s (stopped at %s) for PITR target %s; "
        "estimated restore time: %.1f minutes",
        best_backup["label"],
        best_backup["timestamp"]["stop"],
        target_time.isoformat(),
        estimated_restore_minutes
    )

    return {
        "backup_label": best_backup["label"],
        "recovery_target_time": target_time.isoformat(),
        "estimated_restore_minutes": estimated_restore_minutes,
        "backup_size_gb": round(backup_size_gb, 2)
    }


def execute_pitr(stanza: str, restore_data_dir: str, recovery_target_time: str) -> bool:
    """
    Execute pgBackRest PITR to a specific target time.
    Returns True on success, False on failure.
    """
    logger.info("Executing PITR to %s", recovery_target_time)
    try:
        subprocess.run(
            [
                "pgbackrest", "restore",
                "--stanza", stanza,
                "--pg1-path", restore_data_dir,
                "--type", "time",
                "--target", recovery_target_time,
                "--target-action", "promote",
                "--recovery-option", "recovery_target_inclusive=false",
                "--process-max", "4",
                "--log-level-console", "info"
            ],
            check=True
        )
        logger.info("PITR restore completed successfully")
        return True
    except subprocess.CalledProcessError as exc:
        logger.error("PITR restore failed: %s", exc)
        return False

SQL Server — Autonomous PITR via msdb backup history:

-- Identify the correct backup set for autonomous PITR
-- @corruption_time: the timestamp of first detected corruption
DECLARE @corruption_time DATETIME2 = '2024-01-15T22:47:00';
DECLARE @pitr_target     DATETIME2 = DATEADD(MINUTE, -5, @corruption_time);
DECLARE @database_name   NVARCHAR(128) = N'AppDB';

-- Find most recent full backup before PITR target
SELECT TOP 1
    bs.backup_set_id,
    bs.backup_start_date,
    bs.backup_finish_date,
    bs.backup_size,
    bs.compressed_backup_size,
    bmf.physical_device_name,
    bs.first_lsn,
    bs.last_lsn,
    bs.database_backup_lsn,
    'FULL' AS backup_type
FROM msdb.dbo.backupset bs
JOIN msdb.dbo.backupmediafamily bmf
    ON bs.media_set_id = bmf.media_set_id
WHERE bs.database_name = @database_name
  AND bs.type = 'D'                         -- Full backup
  AND bs.backup_finish_date <= @pitr_target
ORDER BY bs.backup_finish_date DESC;

-- Then find the differential and log chain to bring to PITR target
SELECT
    bs.backup_set_id,
    bs.type AS backup_type,
    bs.backup_start_date,
    bs.backup_finish_date,
    bmf.physical_device_name,
    bs.first_lsn,
    bs.last_lsn
FROM msdb.dbo.backupset bs
JOIN msdb.dbo.backupmediafamily bmf
    ON bs.media_set_id = bmf.media_set_id
WHERE bs.database_name = @database_name
  AND bs.type IN ('I', 'L')                 -- Differential and Log
  AND bs.backup_finish_date > (
        SELECT TOP 1 backup_finish_date
        FROM msdb.dbo.backupset
        WHERE database_name = @database_name
          AND type = 'D'
          AND backup_finish_date <= @pitr_target
        ORDER BY backup_finish_date DESC
      )
  AND bs.backup_start_date <= @pitr_target
ORDER BY bs.backup_start_date;

Once the backup chain is identified, the automated restore script iterates through the results, issuing RESTORE DATABASE ... WITH NORECOVERY for each backup in the chain and a final RESTORE DATABASE ... WITH RECOVERY, STOPAT = @pitr_target for the last log backup.

Circuit Breakers and Recovery Runbook Orchestration

Autonomous DR without circuit breakers is dangerous. An incorrectly classified failure can trigger a chain of recovery actions that deepens the incident — for example, repeatedly promoting replicas in a loop, or initiating PITR on a database that was actually only experiencing a network hiccup. Circuit breakers impose a hard limit on autonomous action frequency and allow the system to pause and escalate rather than spiral.

The circuit breaker pattern for DR has three states: Closed (normal operation, recovery actions allowed), Open (recovery actions suspended, human required), and Half-Open (a limited test action is permitted to probe whether conditions have normalized).

import time
import threading
from enum import Enum

class CBState(Enum):
    CLOSED    = "closed"
    OPEN      = "open"
    HALF_OPEN = "half_open"

class DRCircuitBreaker:
    """
    Circuit breaker for autonomous DR action execution.
    
    failure_threshold: number of failed recovery attempts within window to open
    recovery_timeout:  seconds in OPEN state before moving to HALF_OPEN
    action_window:     rolling window in seconds for counting failures
    """

    def __init__(
        self,
        failure_threshold: int = 3,
        recovery_timeout: int = 300,
        action_window: int = 600
    ):
        self.failure_threshold = failure_threshold
        self.recovery_timeout  = recovery_timeout
        self.action_window     = action_window

        self._state            = CBState.CLOSED
        self._failure_times: list[float] = []
        self._opened_at: float = 0.0
        self._lock             = threading.Lock()

    @property
    def state(self) -> CBState:
        with self._lock:
            if self._state == CBState.OPEN:
                if time.time() - self._opened_at >= self.recovery_timeout:
                    self._state = CBState.HALF_OPEN
                    return CBState.HALF_OPEN
            return self._state

    def allow_action(self) -> bool:
        """Returns True if an autonomous recovery action is permitted."""
        s = self.state
        return s in (CBState.CLOSED, CBState.HALF_OPEN)

    def record_success(self):
        with self._lock:
            self._state = CBState.CLOSED
            self._failure_times.clear()

    def record_failure(self):
        now = time.time()
        with self._lock:
            # Evict old failures outside the window
            cutoff = now - self.action_window
            self._failure_times = [t for t in self._failure_times if t >= cutoff]
            self._failure_times.append(now)

            if (self._state == CBState.HALF_OPEN
                    or len(self._failure_times) >= self.failure_threshold):
                self._state    = CBState.OPEN
                self._opened_at = now

    def status_dict(self) -> dict:
        return {
            "state": self.state.value,
            "failure_count_in_window": len(self._failure_times),
            "opened_at": self._opened_at if self._opened_at else None,
        }

The runbook orchestrator wraps every recovery action in the circuit breaker and emits the result to both the metrics pipeline and the incident management system:

import asyncio
import logging
from typing import Callable, Awaitable

logger = logging.getLogger("runbook_orchestrator")

class RunbookOrchestrator:

    def __init__(self, circuit_breaker: DRCircuitBreaker, alert_client):
        self.cb           = circuit_breaker
        self.alert_client = alert_client

    async def execute(
        self,
        action_name: str,
        action_fn: Callable[[], Awaitable[bool]],
        context: dict
    ) -> bool:
        """
        Execute a DR recovery action with circuit breaker protection.
        action_fn must return True on success, False on failure.
        """
        if not self.cb.allow_action():
            logger.error(
                "Circuit breaker OPEN — autonomous action %s blocked. "
                "State: %s", action_name, self.cb.status_dict()
            )
            await self.alert_client.page(
                severity="critical",
                summary=f"DR circuit breaker open — {action_name} requires human execution",
                context=context
            )
            return False

        logger.info("Executing autonomous DR action: %s | context: %s", action_name, context)
        try:
            success = await action_fn()
            if success:
                self.cb.record_success()
                logger.info("Action %s succeeded", action_name)
                await self.alert_client.notify(
                    severity="info",
                    summary=f"Autonomous DR action completed: {action_name}",
                    context=context
                )
            else:
                self.cb.record_failure()
                logger.error("Action %s returned failure", action_name)
                await self.alert_client.page(
                    severity="high",
                    summary=f"Autonomous DR action failed: {action_name}",
                    context=context
                )
            return success
        except Exception as exc:
            self.cb.record_failure()
            logger.exception("Action %s raised exception: %s", action_name, exc)
            await self.alert_client.page(
                severity="critical",
                summary=f"Autonomous DR action raised exception: {action_name}",
                context={**context, "exception": str(exc)}
            )
            return False

Three failures within a 10-minute window opens the circuit breaker for 5 minutes. During that open window, the orchestrator blocks all autonomous actions and pages a human. This prevents the system from executing six failed promotions in a row while the on-call engineer is being woken up. Once the circuit re-enters Half-Open after 5 minutes, it permits one probe action; if that succeeds, the circuit closes and autonomous operation resumes.

Post-Recovery Integrity Validation

Completing a failover or restore is not recovery — validated recovery is recovery. Autonomous DR systems must execute a post-recovery validation suite before re-admitting application traffic. Traffic re-admission is gated on validation passing, not simply on the database process being reachable.

The validation suite checks four categories: connectivity, data integrity, replication topology restoration, and application-level smoke tests.

PostgreSQL — Post-recovery validation:

-- 1. Connectivity and role check — confirms this is now the primary
SELECT
    pg_is_in_recovery()          AS is_standby,
    pg_postmaster_start_time()   AS postmaster_start,
    current_setting('cluster_name') AS cluster_name,
    pg_current_wal_lsn()         AS current_lsn;
-- is_standby must be FALSE after promotion

-- 2. Replication topology check — confirm new standby is connecting
SELECT
    application_name,
    client_addr,
    state,
    sync_state,
    (sent_lsn - replay_lsn) AS lag_bytes
FROM pg_stat_replication;
-- Expect at least one row with state='streaming' within 60 seconds of promotion

-- 3. Data integrity spot check — verify critical tables accessible
SELECT
    schemaname,
    tablename,
    n_live_tup,
    n_dead_tup,
    last_autovacuum,
    last_autoanalyze
FROM pg_stat_user_tables
WHERE schemaname = 'public'
ORDER BY n_live_tup DESC
LIMIT 20;

-- 4. Extension and sequence integrity
SELECT
    sequence_name,
    last_value,
    increment_by
FROM information_schema.sequences
WHERE sequence_schema = 'public'
ORDER BY sequence_name;

SQL Server — Post-recovery validation:

-- 1. AG health check after failover
SELECT
    ag.name AS ag_name,
    ar.replica_server_name,
    ars.role_desc,
    ars.operational_state_desc,
    ars.connected_state_desc,
    ars.synchronization_health_desc,
    drs.synchronization_state_desc,
    drs.log_send_queue_size,
    drs.redo_queue_size
FROM sys.availability_groups ag
JOIN sys.availability_replicas ar
    ON ag.group_id = ar.group_id
JOIN sys.dm_hadr_availability_replica_states ars
    ON ar.replica_id = ars.replica_id
JOIN sys.dm_hadr_database_replica_states drs
    ON ar.replica_id = drs.replica_id
ORDER BY ars.role_desc, ar.replica_server_name;

-- 2. Database consistency check on newly promoted primary
-- Run after promotion, before re-admitting traffic
DBCC CHECKDB (N'AppDB') WITH NO_INFOMSGS, ALL_ERRORMSGS;

-- 3. Identity and sequence object integrity
SELECT
    OBJECT_SCHEMA_NAME(object_id) AS schema_name,
    OBJECT_NAME(object_id) AS table_name,
    last_value,
    increment_by,
    is_exhausted
FROM sys.sequences
ORDER BY schema_name, table_name;

-- 4. Agent jobs re-enabled check (SQL Agent jobs are disabled on AG secondary)
SELECT
    job_id,
    name,
    enabled,
    date_modified
FROM msdb.dbo.sysjobs
WHERE enabled = 0
  AND name NOT LIKE '%_DO_NOT_ENABLE%'
ORDER BY name;
-- Jobs that were disabled on secondary must be re-enabled on new primary

The SQL Agent job re-enablement check is one of the most commonly missed post-failover steps in manual DR processes. When a SQL Server AG secondary becomes primary, SQL Agent jobs that were suppressed to prevent double-execution must be automatically re-enabled. This is typically handled by a post-failover alert policy or an automated script that watches for AG role change events and triggers the re-enablement:

-- Autonomous job re-enablement after AG promotion
-- Triggered by SQL Agent alert on AG role change event (event ID 1480)
DECLARE @new_role NVARCHAR(60);
SET @new_role = (
    SELECT TOP 1 role_desc
    FROM sys.dm_hadr_availability_replica_states
    WHERE is_local = 1
);

IF @new_role = N'PRIMARY'
BEGIN
    -- Re-enable all jobs that carry the auto-manage tag in their description
    UPDATE msdb.dbo.sysjobs
    SET enabled = 1
    WHERE enabled = 0
      AND description LIKE '%AG_AUTO_MANAGE%';

    -- Log the re-enablement
    EXEC msdb.dbo.sp_add_jobhistory
        @job_id = NULL,
        @step_id = 0,
        @sql_message_id = 0,
        @sql_severity = 0,
        @message = 'Autonomous AG failover: re-enabled tagged SQL Agent jobs on new primary',
        @run_status = 1,
        @run_date = CONVERT(INT, CONVERT(VARCHAR, GETDATE(), 112)),
        @run_time = 0;
END

The traffic admission gate is a separate component — typically a load balancer health check endpoint or a DNS TTL expiry — that the validation suite controls. Only when all four validation categories pass does the suite signal the load balancer to re-route connections to the new primary. In Kubernetes environments this is a readiness probe endpoint implemented in the database sidecar container; in traditional environments it is a script that updates a HAProxy backend weight or a Route 53 health check status.

Geo-Redundant and Multi-Region Autonomous DR

Single-region autonomous DR handles the majority of failure scenarios. Region-level failures — AZ outages, cloud region degradation, network backbone events — require a distinct architecture: geo-redundant replication with an autonomous cross-region election mechanism.

The fundamental challenge with cross-region autonomous failover is network latency. Synchronous replication across regions introduces write latency equal to the round-trip time between regions. For most regions this is 20–80 ms, which is unacceptable for OLTP workloads with tight SLAs. The production pattern is therefore:

  • → **Intra-region:** synchronous replication, automatic failover, RPO = 0
  • → **Cross-region:** asynchronous replication, autonomous failover with explicit data-loss acknowledgment, RPO = replication lag at time of failure

    • This asymmetric replication design requires the recovery decision engine to know which tier it is operating in. A cross-region failover is always a data-loss event and must be logged as such in the audit trail.

    PostgreSQL cross-region replication configuration:

    -- On primary: create a cascading replication slot for the DR region
SELECT pg_create_physical_replication_slot('dr_region_us_west_2', true, false);

-- Verify slot state before relying on it
SELECT
    slot_name,
    plugin,
    slot_type,
    active,
    confirmed_flush_lsn,
    (pg_current_wal_lsn() - confirmed_flush_lsn) AS lag_bytes,
    pg_size_pretty(pg_current_wal_lsn() - confirmed_flush_lsn) AS lag_pretty
FROM pg_replication_slots
WHERE slot_name = 'dr_region_us_west_2';

    One critical operational detail: replication slots retain WAL segments on the primary until the replica confirms receipt. In a cross-region scenario, if the DR region becomes unreachable for an extended period, WAL accumulates on the primary and can exhaust disk space. Autonomous DR systems must monitor slot lag and automatically drop inactive slots that exceed a WAL accumulation threshold:

    -- Autonomous slot health monitor
-- Run every 5 minutes; drop slots exceeding the WAL accumulation limit
DO $$
DECLARE
    slot_rec RECORD;
    max_lag_bytes BIGINT := 10737418240;  -- 10 GB WAL accumulation limit
    lag BIGINT;
BEGIN
    FOR slot_rec IN
        SELECT slot_name, active,
               (pg_current_wal_lsn() - confirmed_flush_lsn) AS lag_bytes
        FROM pg_replication_slots
        WHERE slot_type = 'physical'
    LOOP
        IF NOT slot_rec.active AND slot_rec.lag_bytes > max_lag_bytes THEN
            RAISE WARNING 'Dropping inactive slot % with lag % bytes exceeding threshold',
                slot_rec.slot_name, slot_rec.lag_bytes;
            PERFORM pg_drop_replication_slot(slot_rec.slot_name);
        END IF;
    END LOOP;
END $$;

    SQL Server — Cross-region AG with asynchronous DR replica:

    -- Add async DR replica to existing synchronous AG
ALTER AVAILABILITY GROUP [AG_Production]
ADD REPLICA ON N'sql-dr-west' WITH (
    ENDPOINT_URL = N'TCP://sql-dr-west.us-west-2.internal:5022',
    AVAILABILITY_MODE = ASYNCHRONOUS_COMMIT,     -- async — no latency impact on primary
    FAILOVER_MODE = MANUAL,                       -- cross-region failover requires human or explicit script
    SEEDING_MODE = AUTOMATIC,
    SECONDARY_ROLE (ALLOW_CONNECTIONS = READ_ONLY)
);

-- Monitor cross-region replica lag
SELECT
    ar.replica_server_name,
    drs.database_name,
    drs.synchronization_state_desc,
    drs.log_send_queue_size          AS unsent_log_kb,
    drs.redo_queue_size              AS unredone_log_kb,
    drs.log_send_rate                AS send_rate_kb_per_sec,
    drs.redo_rate                    AS redo_rate_kb_per_sec,
    DATEDIFF(SECOND, drs.last_commit_time, GETUTCDATE()) AS estimated_lag_seconds
FROM sys.dm_hadr_database_replica_states drs
JOIN sys.availability_replicas ar
    ON drs.replica_id = ar.replica_id
WHERE ar.replica_server_name = N'sql-dr-west'
  AND drs.is_local = 0;

    For cross-region autonomous failover in SQL Server, FAILOVER_MODE = MANUAL means the failover cluster will not automatically trigger the role change. The autonomous DR script must explicitly issue the failover command after passing the decision engine's data-loss acknowledgment gate:

    -- Autonomous cross-region failover script (executed on DR replica)
-- Requires prior data-loss acknowledgment from decision engine

-- Step 1: Verify this is the DR replica and it is secondary
IF (SELECT role_desc FROM sys.dm_hadr_availability_replica_states WHERE is_local = 1) != 'SECONDARY'
BEGIN
    RAISERROR('This script must run on the secondary DR replica', 16, 1);
    RETURN;
END

-- Step 2: Record pre-failover state for audit
INSERT INTO dbo.dr_audit_log (
    event_time, event_type, ag_name, replica_name,
    lag_seconds_at_failover, initiated_by
)
SELECT
    GETUTCDATE(), 'CROSS_REGION_FAILOVER_INITIATED',
    ag.name, ar.replica_server_name,
    DATEDIFF(SECOND, drs.last_commit_time, GETUTCDATE()),
    SYSTEM_USER
FROM sys.availability_groups ag
JOIN sys.availability_replicas ar ON ag.group_id = ar.group_id
JOIN sys.dm_hadr_database_replica_states drs ON ar.replica_id = drs.replica_id
WHERE drs.is_local = 1;

-- Step 3: Execute forced failover with data loss (explicit acknowledgment)
ALTER AVAILABILITY GROUP [AG_Production] FORCE_FAILOVER_ALLOW_DATA_LOSS;

-- Step 4: Update listener DNS to point to new primary (via external script call)
-- xp_cmdshell to route53-update.ps1 or equivalent
EXEC xp_cmdshell 'powershell.exe -File C:\DR\update-dns-listener.ps1 -AgName AG_Production';

    The DNS update step after cross-region failover is frequently overlooked. AG listeners are cluster-aware within a WSFC; across regions they require a separate DNS entry or global load balancer update. The autonomous pipeline must handle this as part of the runbook, not as an afterthought.

    Observability and the DR Simulation Framework

    An autonomous DR system that has never been tested is a liability. The simulation framework executes DR scenarios against the production topology on a schedule — not against a separate test environment — but with application traffic isolated to a shadow copy. This is analogous to chaos engineering but with a specific DR focus.

    The DR simulation framework maintains a catalog of scenarios and their expected outcomes:

    from dataclasses import dataclass
from typing import Callable, Awaitable

@dataclass
class DRScenario:
    name: str
    description: str
    inject_fn: Callable[[], Awaitable[None]]    # fault injection
    expected_recovery_action: str               # from RecoveryAction enum
    max_recovery_seconds: int                   # SLO for autonomous recovery
    validation_fn: Callable[[], Awaitable[bool]] # post-recovery check

DR_SCENARIOS = [
    DRScenario(
        name="primary_process_kill",
        description="Kill PostgreSQL process on primary — expect sync replica promotion within 30s",
        inject_fn=kill_primary_process,
        expected_recovery_action="promote_sync_replica",
        max_recovery_seconds=30,
        validation_fn=validate_new_primary_accepting_writes
    ),
    DRScenario(
        name="network_partition_primary",
        description="Block all network traffic to/from primary — expect fencing and promotion",
        inject_fn=apply_iptables_blackhole_to_primary,
        expected_recovery_action="fence_old_primary",
        max_recovery_seconds=60,
        validation_fn=validate_new_primary_accepting_writes
    ),
    DRScenario(
        name="backup_restore_integrity",
        description="Execute full PITR to 1 hour ago — validate data matches expected state",
        inject_fn=no_injection_required,
        expected_recovery_action="restore_from_backup",
        max_recovery_seconds=1800,
        validation_fn=validate_pitr_data_integrity
    ),
    DRScenario(
        name="replication_slot_bloat",
        description="Pause DR replica for 30 minutes — expect slot drop at WAL accumulation limit",
        inject_fn=pause_dr_replica_replication,
        expected_recovery_action="slot_auto_drop",
        max_recovery_seconds=300,
        validation_fn=validate_slot_dropped_and_wal_space_recovered
    ),
]

    Each simulation run produces a DR readiness report: which scenarios passed, which failed, what the actual recovery time was versus the SLO, and whether any circuit breakers opened during the run. This report feeds directly into the incident management system's DR readiness dashboard.

    The observability layer for autonomous DR should expose the following metrics as a minimum:

    | Metric | Type | Purpose |

    |---|---|---|

    | dr_failover_total | Counter | Count of autonomous failovers by type |

    | dr_failover_duration_seconds | Histogram | Time from failure detection to traffic restored |

    | dr_classification_confidence | Gauge | Current classifier confidence on active signal |

    | dr_circuit_breaker_state | Gauge | 0=closed, 1=half-open, 2=open |

    | dr_backup_rpo_seconds | Gauge | Age of most recently validated backup restore |

    | dr_replication_lag_bytes | Gauge | Current replication lag per replica |

    | dr_simulation_last_pass_timestamp | Gauge | Unix timestamp of last passing simulation run |

    When dr_simulation_last_pass_timestamp has not updated in more than 7 days, the system automatically files an incident. A DR system that hasn't been validated recently is not a DR system you can trust for autonomous execution.

    Key Takeaways

  • → **Failure classification precedes recovery action.** Treating all failures as "failover" produces wrong recovery paths; a voting-window classifier that waits 10–30 seconds for signal convergence prevents false positives and wrong-class recoveries while keeping RTO within SLO.
  • → **RPO is an explicit gate in the decision engine, not an aspiration.** The recovery decision engine must compare actual replication lag bytes against the configured RPO threshold and refuse to promote replicas that exceed it without an explicit pre-authorized data-loss acknowledgment. This transforms RPO from a metric you measure after a disaster into a constraint you enforce before one occurs.
  • → **Circuit breakers prevent autonomous systems from deepening incidents.** Three failed recovery attempts within a rolling window should open the circuit breaker, block further autonomous action, and escalate to a human — stopping the system from executing a cascade of failed promotions while the on-call engineer is responding.
  • → **Continuous shadow restores are the only reliable backup validation.** Verifying backup files with checksums is necessary but not sufficient; only a full autonomous restore to an isolated instance, followed by integrity checks and RPO age measurement, can confirm that your backup chain is actually recoverable when the decision engine selects `RESTORE_FROM_BACKUP`.
  • → **Post-recovery validation gates traffic re-admission.** The database process being reachable is not recovery; validated recovery requires confirming primary role, replication topology restoration, data integrity spot checks, and application-level smoke tests — and only after all four pass should the load balancer or DNS be updated to re-admit production traffic.
