Chapter 15: Intelligent Workload Classification

Autonomous database systems can only act intelligently when they understand what they're running. Query tuning, resource allocation, connection routing, and scheduling decisions all depend on knowing whether a given workload is OLTP, analytical, batch, ETL, or something in between — and that classification must happen continuously, at runtime, without human annotation. This chapter builds the full stack of intelligent workload classification: from raw signal extraction through feature engineering, model-based classification, and the downstream control loops that consume those labels to make autonomous decisions. The architecture described here runs in production today, using SQL Server's Query Store and DMV telemetry as primary data sources, augmented by custom instrumentation and ML inference layers that operate with sub-second latency for hot decisions and background model refresh cycles for drift correction.

15.1 Signal Extraction: Reading Workload DNA from Native Instrumentation

Classification begins with signals. SQL Server exposes rich runtime telemetry, but the signals that matter for workload classification are not the obvious ones like CPU or memory — they are behavioral fingerprints embedded in execution statistics, wait profiles, and access patterns.

The core features for workload classification fall into four categories:

  • → Execution profile: rows examined vs. rows returned ratio, execution frequency, plan stability
  • → Resource signature: buffer hits vs. disk reads, temp space usage, parallelism degree
  • → Wait topology: the distribution of wait types encountered during execution
  • → Temporal pattern: time-of-day clustering, burst coefficient, inter-arrival time variance

    • SQL Server exposes this through sys.query_store_runtime_stats, sys.dm_exec_query_stats, and sys.dm_exec_sessions. The challenge is that Query Store normalizes query text and loses some instance-level variance. Augmenting it with lightweight Extended Events sampling (sql_batch_completed) and a collector that snapshots sys.dm_exec_requests at 1-second intervals gives you the full picture.

    -- Extract equivalent workload signals from Query Store
-- Maps to the same feature vector schema used for classification
SELECT
    qsq.query_id,
    qsqt.query_sql_text,
    SUM(qsrs.count_executions)                                          AS total_calls,
    AVG(qsrs.avg_duration / 1000.0)                                     AS avg_exec_ms,
    STDEV(qsrs.avg_duration) / NULLIF(AVG(qsrs.avg_duration), 0)       AS exec_time_cv,
    AVG(qsrs.avg_rowcount)                                              AS avg_rows_returned,
    AVG(qsrs.avg_logical_io_reads)                                      AS avg_logical_reads,
    AVG(qsrs.avg_physical_io_reads)                                     AS avg_physical_reads,
    AVG(qsrs.avg_tempdb_space_used)                                     AS avg_temp_writes,
    AVG(qsrs.avg_log_bytes_used)                                        AS avg_log_bytes,
    SUM(qsrs.count_executions) /
        NULLIF(DATEDIFF(HOUR,
            MIN(qsrs.first_execution_time),
            MAX(qsrs.last_execution_time)), 0)                          AS calls_per_hour,
    AVG(qsrs.avg_dop)                                                   AS avg_parallelism
FROM sys.query_store_query             qsq
JOIN sys.query_store_query_text        qsqt ON qsq.query_text_id = qsqt.query_text_id
JOIN sys.query_store_plan              qspp ON qsq.query_id       = qspp.query_id
JOIN sys.query_store_runtime_stats     qsrs ON qspp.plan_id       = qsrs.plan_id
WHERE qsrs.count_executions > 10
GROUP BY qsq.query_id, qsqt.query_sql_text
ORDER BY SUM(qsrs.avg_duration * qsrs.count_executions) DESC;

    Wait profiles require a separate collection path. sys.dm_os_wait_stats gives cumulative waits; per-query waits come from sys.dm_exec_query_stats joined with sys.dm_exec_query_plan for per-plan wait attribution. A 1-second polling collector that snapshots sys.dm_exec_requests builds a wait histogram per query pattern over time.

    The wait topology feature is then encoded as a distribution vector: what fraction of total wait time falls into Lock, LWLock/Buffer, IO, CPU, Network, and Idle categories. OLTP workloads show high Lock and short CPU spikes. Analytical workloads show sustained CPU with sequential IO. Batch ETL workloads show high IO and Log write waits with low Lock contention.

    15.2 Feature Engineering for Runtime Classification

    Raw telemetry numbers are not directly usable by a classifier. The feature engineering layer transforms them into scale-invariant, semantically meaningful representations that generalize across databases of different sizes and query volumes.

    The derived features that carry the most discriminative signal are:

    | Feature | Formula | Interpretation |

    |---|---|---|

    | scan_dominance | seq_scan_rows / total_rows_examined | High = analytical |

    | write_amplification | log_bytes / (rows_modified + 1) | High = batch/ETL |

    | result_compression | rows_returned / rows_examined | Low = aggregation-heavy |

    | temporal_burst_coef | calls_p99 / calls_median over 5-min windows | High = bursty OLTP |

    | plan_instability | distinct_plans / total_calls | High = parameter sensitivity |

    | parallelism_affinity | avg_dop / max_dop | High = analytical intent |

    The following Python feature engineering pipeline runs as a scheduled collector — pulling from both databases, computing derived features, and publishing to a Redis time-series store that feeds the classification inference layer.

    import pyodbc
import redis
import json
import time
from dataclasses import dataclass, asdict
from typing import Optional
import numpy as np

@dataclass
class WorkloadFeatureVector:
    query_id: str
    avg_exec_ms: float
    exec_time_cv: float           # coefficient of variation
    avg_rows_returned: float
    buffer_hit_ratio: float
    avg_physical_reads: float
    avg_temp_writes: float
    avg_log_bytes: float
    calls_per_hour: float
    avg_parallelism: float
    # Derived features
    result_compression: float     # rows_returned / rows_examined
    temporal_burst_coef: float
    plan_instability: float
    write_amplification: float

def compute_derived_features(raw: dict, burst_history: list[float]) -> dict:
    """
    Compute scale-invariant derived features from raw telemetry.
    burst_history: list of calls_per_hour values from last 12 x 5-min windows
    """
    rows_examined = raw['avg_rows_returned'] / max(raw['buffer_hit_ratio'], 0.001)

    result_compression = raw['avg_rows_returned'] / max(rows_examined, 1)

    # Burst coefficient: ratio of 95th percentile to median over recent windows
    if len(burst_history) >= 4:
        p95 = float(np.percentile(burst_history, 95))
        median = float(np.median(burst_history))
        burst_coef = p95 / max(median, 0.1)
    else:
        burst_coef = 1.0

    write_amplification = raw['avg_log_bytes'] / max(raw['avg_rows_returned'], 1)

    return {
        'result_compression': result_compression,
        'temporal_burst_coef': burst_coef,
        'write_amplification': write_amplification,
    }

class FeatureCollector:
    def __init__(self, mssql_dsn: str, redis_url: str):
        self.mssql_conn = pyodbc.connect(mssql_dsn)
        self.redis = redis.from_url(redis_url)
        self.burst_cache: dict[str, list[float]] = {}

    def collect_and_publish(self):
        ms_features = self._collect_sqlserver()

        for fv in ms_features:
            key = f"wl:features:sqlserver:{fv.query_id}"
            self.redis.setex(key, 3600, json.dumps(asdict(fv)))
            # Append to time-series for burst calculation
            ts_key = f"wl:timeseries:sqlserver:{fv.query_id}"
            self.redis.lpush(ts_key, fv.calls_per_hour)
            self.redis.ltrim(ts_key, 0, 11)  # keep 12 windows = 60 minutes

    def _collect_sqlserver(self) -> list[WorkloadFeatureVector]:
        cur = self.mssql_conn.cursor()
        cur.execute("""
            SELECT
                CAST(qsq.query_id AS VARCHAR(20)) AS query_id,
                AVG(qsrs.avg_duration / 1000.0)   AS avg_exec_ms,
                STDEV(qsrs.avg_duration) / NULLIF(AVG(qsrs.avg_duration),0) AS exec_time_cv,
                AVG(qsrs.avg_rowcount)             AS avg_rows,
                AVG(qsrs.avg_logical_io_reads)     AS avg_logical,
                AVG(qsrs.avg_physical_io_reads)    AS avg_physical,
                AVG(qsrs.avg_tempdb_space_used)    AS avg_temp,
                AVG(qsrs.avg_log_bytes_used)       AS avg_log,
                SUM(qsrs.count_executions) /
                    NULLIF(DATEDIFF(HOUR,
                        MIN(qsrs.first_execution_time),
                        GETUTCDATE()), 0)           AS calls_per_hour,
                AVG(qsrs.avg_dop)                  AS avg_dop,
                COUNT(DISTINCT qspp.plan_id) * 1.0 /
                    NULLIF(SUM(qsrs.count_executions), 0) AS plan_instability
            FROM sys.query_store_query         qsq
            JOIN sys.query_store_plan          qspp ON qsq.query_id   = qspp.query_id
            JOIN sys.query_store_runtime_stats qsrs ON qspp.plan_id   = qsrs.plan_id
            WHERE qsrs.count_executions > 10
              AND qsrs.last_execution_time > DATEADD(MINUTE, -60, GETUTCDATE())
            GROUP BY qsq.query_id
        """)
        results = []
        for row in cur.fetchall():
            burst_key = f"wl:timeseries:sqlserver:{row.query_id}"
            history = [float(v) for v in self.redis.lrange(burst_key, 0, 11)]
            derived = compute_derived_features({
                'avg_rows_returned': row.avg_rows or 0,
                'buffer_hit_ratio': (row.avg_logical - (row.avg_physical or 0)) /
                                    max(row.avg_logical or 1, 1),
                'avg_log_bytes': row.avg_log or 0,
            }, history)
            fv = WorkloadFeatureVector(
                query_id=row.query_id,
                database_type='sqlserver',
                avg_exec_ms=row.avg_exec_ms or 0,
                exec_time_cv=row.exec_time_cv or 0,
                avg_rows_returned=row.avg_rows or 0,
                buffer_hit_ratio=(row.avg_logical - (row.avg_physical or 0)) /
                                  max(row.avg_logical or 1, 1),
                avg_physical_reads=row.avg_physical or 0,
                avg_temp_writes=row.avg_temp or 0,
                avg_log_bytes=row.avg_log or 0,
                calls_per_hour=row.calls_per_hour or 0,
                avg_parallelism=row.avg_dop or 1,
                plan_instability=row.plan_instability or 0,
                **derived
            )
            results.append(fv)
        return results

    15.3 The Classification Model: Architecture and Label Taxonomy

    The classification model sits at the core of the autonomous control loop. It receives feature vectors and produces workload labels that drive downstream decisions. The label taxonomy needs to be precise enough to guide action but stable enough to avoid thrashing.

    A five-class taxonomy works well across all production scenarios:

  • → OLTP_POINT: Short-duration, high-frequency, index-bound, single-digit row access. Classic transactional. Action: prioritize in connection pools, protect from query plan regression.
  • → OLTP_MODERATE: Slightly wider queries — small range scans, multi-table joins, under 100ms. Action: standard SLA tier.
  • → ANALYTICAL: Long-running, high-row-count aggregations, sequential scans, parallel execution. Action: route to read replica, assign lower CPU priority, allow longer lock waits.
  • → BATCH_ETL: High write amplification, sequential access, predictable schedule, large tempdb usage. Action: schedule during maintenance window, pre-warm buffers, expand the index maintenance budget post-run.
  • → MAINTENANCE: index rebuilds and reorganizations, statistics updates, DBCC operations. Action: track separately, do not apply SLA enforcement, use as calibration signal.

    • The classifier itself is a gradient-boosted tree model (XGBoost or LightGBM) trained on labeled historical data from Query Store. The labeling phase is the only place human judgment enters: a DBA manually labels 500–1000 representative query patterns once, and the model generalizes from there. Semi-supervised bootstrapping can extend coverage to new query patterns by treating high-confidence predictions as pseudo-labels for retraining.

    In production, the classifier runs as a FastAPI microservice with a 5ms SLA for batch classification of up to 200 feature vectors per request. The model is loaded into memory and refreshed weekly via a background retraining pipeline triggered by concept drift detection.

    import lightgbm as lgb
import numpy as np
import joblib
from fastapi import FastAPI
from pydantic import BaseModel
from typing import List
from enum import Enum

class WorkloadClass(str, Enum):
    OLTP_POINT    = "OLTP_POINT"
    OLTP_MODERATE = "OLTP_MODERATE"
    ANALYTICAL    = "ANALYTICAL"
    BATCH_ETL     = "BATCH_ETL"
    MAINTENANCE   = "MAINTENANCE"

FEATURE_COLUMNS = [
    'avg_exec_ms', 'exec_time_cv', 'avg_rows_returned',
    'buffer_hit_ratio', 'avg_physical_reads', 'avg_temp_writes',
    'avg_log_bytes', 'calls_per_hour', 'avg_parallelism',
    'result_compression', 'temporal_burst_coef',
    'plan_instability', 'write_amplification'
]

LABEL_MAP = {0: WorkloadClass.OLTP_POINT,
             1: WorkloadClass.OLTP_MODERATE,
             2: WorkloadClass.ANALYTICAL,
             3: WorkloadClass.BATCH_ETL,
             4: WorkloadClass.MAINTENANCE}

class ClassificationRequest(BaseModel):
    query_id: str
    features: dict

class ClassificationResponse(BaseModel):
    query_id: str
    workload_class: WorkloadClass
    confidence: float
    probabilities: dict

app = FastAPI()
model: lgb.Booster = joblib.load("/models/workload_classifier_v3.pkl")

@app.post("/classify", response_model=List[ClassificationResponse])
def classify_batch(requests: List[ClassificationRequest]):
    if not requests:
        return []

    feature_matrix = np.array([
        [r.features.get(col, 0.0) for col in FEATURE_COLUMNS]
        for r in requests
    ])

    # LightGBM returns probability matrix (n_samples x n_classes)
    proba_matrix = model.predict(feature_matrix)

    results = []
    for req, probas in zip(requests, proba_matrix):
        predicted_idx = int(np.argmax(probas))
        predicted_class = LABEL_MAP[predicted_idx]
        confidence = float(probas[predicted_idx])

        # Refuse to classify if confidence is below threshold —
        # route to human review queue instead
        if confidence < 0.65:
            predicted_class = WorkloadClass.OLTP_MODERATE  # safe default
            confidence = 0.0  # signals uncertainty to downstream consumers

        results.append(ClassificationResponse(
            query_id=req.query_id,
            workload_class=predicted_class,
            confidence=confidence,
            probabilities={LABEL_MAP[i].value: float(p)
                           for i, p in enumerate(probas)}
        ))
    return results

    The confidence threshold of 0.65 is not arbitrary. Below this level, empirical testing shows that misclassifications cause more harm (wrong resource allocation, incorrect routing) than the safe default of OLTP_MODERATE. Queries below threshold are published to a review queue consumed weekly by the DBA for manual labeling — feeding the retraining loop.

    15.4 Real-Time Classification Routing and Resource Policy Enforcement

    Classification labels are only valuable when they drive action at runtime. The downstream control loop connects workload labels to three enforcement mechanisms: connection pool routing, resource group assignment, and query timeout policies.

    Connection Routing via Resource Governor Classification

    SQL Server has no external pooler tier to reconfigure — routing happens in the Resource Governor classifier function and the AG read-only routing list. When the classification service reclassifies a query pattern (e.g., a formerly OLTP query has migrated to ANALYTICAL due to data growth), the orchestration agent updates the dbo.workload_routing_rules table below; the classifier function picks up the new routing at the next connection without any restart.

    -- SQL Server: Resource Governor workload group assignment
-- Classification function called by Resource Governor at connection time
-- Updated dynamically based on classification service output

-- Create/update the classifier function
CREATE OR ALTER FUNCTION dbo.fn_workload_classifier()
RETURNS SYSNAME
WITH SCHEMABINDING
AS
BEGIN
    DECLARE @workload_group SYSNAME;
    DECLARE @app_name       NVARCHAR(256) = APP_NAME();
    DECLARE @host_name      NVARCHAR(128) = HOST_NAME();
    DECLARE @login_name     SYSNAME       = SUSER_SNAME();

    -- Dynamic routing table updated by classification agent
    SELECT @workload_group = resource_group_name
    FROM dbo.workload_routing_rules
    WHERE (app_name_pattern IS NULL OR @app_name LIKE app_name_pattern)
      AND (login_pattern    IS NULL OR @login_name LIKE login_pattern)
      AND is_active = 1
    ORDER BY priority ASC;

    -- Fall back to default if no rule matches
    IF @workload_group IS NULL
        SET @workload_group = N'WG_OLTP_MODERATE';

    RETURN @workload_group;
END;
GO

-- Supporting routing rules table (populated by classification agent)
CREATE TABLE IF NOT EXISTS dbo.workload_routing_rules (
    rule_id             INT IDENTITY PRIMARY KEY,
    app_name_pattern    NVARCHAR(256) NULL,
    login_pattern       SYSNAME       NULL,
    resource_group_name SYSNAME       NOT NULL,
    priority            INT           NOT NULL DEFAULT 100,
    is_active           BIT           NOT NULL DEFAULT 1,
    updated_at          DATETIME2     NOT NULL DEFAULT SYSUTCDATETIME()
);

-- Resource Governor groups matching the five-class taxonomy
ALTER RESOURCE POOL RP_OLTP
    WITH (MIN_CPU_PERCENT = 20, MAX_CPU_PERCENT = 80,
          MIN_MEMORY_PERCENT = 10, MAX_MEMORY_PERCENT = 40);

ALTER RESOURCE POOL RP_ANALYTICAL
    WITH (MIN_CPU_PERCENT = 0,  MAX_CPU_PERCENT = 60,
          MIN_MEMORY_PERCENT = 20, MAX_MEMORY_PERCENT = 60);

ALTER RESOURCE POOL RP_BATCH
    WITH (MIN_CPU_PERCENT = 0,  MAX_CPU_PERCENT = 40,
          MIN_MEMORY_PERCENT = 5,  MAX_MEMORY_PERCENT = 30);

ALTER WORKLOAD GROUP WG_OLTP_POINT
    WITH (IMPORTANCE = HIGH, REQUEST_MAX_CPU_TIME_SEC = 5,
          REQUEST_MAX_MEMORY_GRANT_PERCENT = 5,
          GROUP_MAX_REQUESTS = 500)
    USING RP_OLTP;

ALTER WORKLOAD GROUP WG_OLTP_MODERATE
    WITH (IMPORTANCE = MEDIUM, REQUEST_MAX_CPU_TIME_SEC = 30,
          REQUEST_MAX_MEMORY_GRANT_PERCENT = 10,
          GROUP_MAX_REQUESTS = 200)
    USING RP_OLTP;

ALTER WORKLOAD GROUP WG_ANALYTICAL
    WITH (IMPORTANCE = LOW, REQUEST_MAX_CPU_TIME_SEC = 300,
          REQUEST_MAX_MEMORY_GRANT_PERCENT = 25,
          GROUP_MAX_REQUESTS = 20)
    USING RP_ANALYTICAL;

ALTER WORKLOAD GROUP WG_BATCH_ETL
    WITH (IMPORTANCE = LOW, REQUEST_MAX_CPU_TIME_SEC = 3600,
          REQUEST_MAX_MEMORY_GRANT_PERCENT = 20,
          GROUP_MAX_REQUESTS = 10)
    USING RP_BATCH;

ALTER RESOURCE GOVERNOR
    WITH (CLASSIFIER_FUNCTION = dbo.fn_workload_classifier);

ALTER RESOURCE GOVERNOR RECONFIGURE;

    The key design tension here is that Resource Governor applies its classification at connection time, not at query execution time. A connection from a reporting application that also issues occasional OLTP point lookups will be assigned the ANALYTICAL group for the entire session. The mitigation is to route clients through application-layer connection proxies that maintain separate connection pools per workload class, so the Resource Governor classifier function sees clean, purpose-specific connections rather than mixed-use sessions.

    Dynamic Reclassification and Hysteresis

    Reclassification events — when a query pattern transitions from one workload class to another — can cause resource thrashing if acted upon immediately. A query experiencing a temporary data skew might look ANALYTICAL for a few minutes before settling back to OLTP. Acting on every reclassification signal wastes reconfiguration cycles and destabilizes steady state.

    The solution is a hysteresis filter. A reclassification is only committed to the routing table when the new classification has been stable for a configurable number of consecutive scoring intervals. The following agent implements this pattern:

    import time
import collections
from dataclasses import dataclass, field
from typing import Optional

@dataclass
class ClassificationState:
    current_class: str
    candidate_class: str
    candidate_streak: int
    last_changed: float  # epoch seconds

    def should_reclassify(self, new_class: str,
                          hysteresis_periods: int = 3) -> bool:
        """
        Return True only when the new class has been consistently
        observed for `hysteresis_periods` consecutive scoring intervals.
        """
        if new_class == self.current_class:
            self.candidate_class = new_class
            self.candidate_streak = 0
            return False

        if new_class == self.candidate_class:
            self.candidate_streak += 1
        else:
            self.candidate_class = new_class
            self.candidate_streak = 1

        return self.candidate_streak >= hysteresis_periods

class ReclassificationAgent:
    def __init__(self, classifier_url: str, mssql_dsn: str,
                 scoring_interval_sec: int = 60,
                 hysteresis_periods: int = 3):
        self.classifier_url  = classifier_url
        self.mssql_dsn       = mssql_dsn
        self.interval        = scoring_interval_sec
        self.hysteresis      = hysteresis_periods
        self.states: dict[str, ClassificationState] = {}

    def run(self):
        import requests, pyodbc
        conn = pyodbc.connect(self.mssql_dsn)
        while True:
            features = self._fetch_features(conn)
            if not features:
                time.sleep(self.interval)
                continue

            response = requests.post(
                f"{self.classifier_url}/classify",
                json=features,
                timeout=10
            )
            classifications = response.json()

            for result in classifications:
                qid        = result['query_id']
                new_class  = result['workload_class']
                confidence = result['confidence']

                # Skip uncertain predictions entirely
                if confidence == 0.0:
                    continue

                if qid not in self.states:
                    self.states[qid] = ClassificationState(
                        current_class=new_class,
                        candidate_class=new_class,
                        candidate_streak=0,
                        last_changed=time.time()
                    )
                    self._apply_routing(conn, qid, new_class)
                    continue

                state = self.states[qid]
                if state.should_reclassify(new_class, self.hysteresis):
                    old_class = state.current_class
                    state.current_class = new_class
                    state.candidate_streak = 0
                    state.last_changed = time.time()
                    self._apply_routing(conn, qid, new_class)
                    self._emit_reclassification_event(
                        conn, qid, old_class, new_class
                    )

            time.sleep(self.interval)

    def _apply_routing(self, conn, query_id: str, workload_class: str):
        with conn.cursor() as cur:
            cur.execute(
                "EXEC dbo.assign_workload_resource_group @query_id = ?, @workload_class = ?",
                int(query_id), workload_class
            )
        conn.commit()

    def _emit_reclassification_event(self, conn, query_id: str,
                                     old_class: str, new_class: str):
        with conn.cursor() as cur:
            cur.execute("""
                INSERT INTO dbo.workload_reclassification_log
                    (query_id, old_class, new_class, event_time)
                VALUES (?, ?, ?, SYSUTCDATETIME())
            """, int(query_id), old_class, new_class)
        conn.commit()

    def _fetch_features(self, conn) -> list:
        # Fetch from Redis or directly from Query Store
        # Returns list of {query_id, features: {...}} dicts
        pass

    Three consecutive scoring intervals — with a 60-second default interval — means a reclassification event must persist for three minutes before action is taken. This eliminates transient noise while still responding to genuine workload character changes within a few minutes.

    15.5 Concept Drift Detection and Model Refresh

    Workload classifiers degrade over time. Schema changes, new application releases, data volume growth, and seasonal patterns all shift the underlying feature distributions. A model trained on last quarter's telemetry may produce subtly wrong classifications on today's workload without any obvious failure signal — queries are still classified, resource policies are still applied, but the assignments are increasingly misaligned with actual behavior.

    Detecting this drift without ground-truth labels requires statistical process control applied to the model's own output distribution. Three signals are monitored continuously:

    1. Class distribution drift: The proportion of queries assigned to each class should be stable over time. A sudden shift — say, ANALYTICAL rising from 15% to 35% without a known schema or application change — indicates either a genuine workload shift or model degradation.

    2. Confidence distribution collapse: If the average confidence score across all classifications drops below a threshold, the model is encountering feature vectors that it has not seen before. The distribution of max_proba values should be stable; a leftward shift signals drift.

    3. Feature distribution shift: The input feature distributions themselves can be monitored using a Population Stability Index (PSI) computed between the current 7-day window and the training baseline. PSI > 0.2 on any feature is a trigger for retraining.

    import numpy as np
from scipy import stats
from dataclasses import dataclass
from typing import Optional

@dataclass
class DriftReport:
    feature_name: str
    psi_score: float
    ks_statistic: float
    ks_pvalue: float
    drift_detected: bool

def compute_psi(baseline: np.ndarray, current: np.ndarray,
                n_bins: int = 10) -> float:
    """
    Population Stability Index.
    PSI < 0.1  : no significant drift
    PSI 0.1–0.2: moderate drift, monitor
    PSI > 0.2  : significant drift, retrain
    """
    baseline = baseline[np.isfinite(baseline)]
    current  = current[np.isfinite(current)]
    if len(baseline) == 0 or len(current) == 0:
        return 0.0

    # Build bins from baseline distribution
    bin_edges = np.percentile(baseline, np.linspace(0, 100, n_bins + 1))
    bin_edges = np.unique(bin_edges)  # dedup if percentiles collapse
    if len(bin_edges) < 2:
        return 0.0

    baseline_counts, _ = np.histogram(baseline, bins=bin_edges)
    current_counts,  _ = np.histogram(current,  bins=bin_edges)

    # Avoid division by zero with Laplace smoothing
    baseline_pct = (baseline_counts + 0.5) / (len(baseline) + 0.5 * n_bins)
    current_pct  = (current_counts  + 0.5) / (len(current)  + 0.5 * n_bins)

    psi = np.sum((current_pct - baseline_pct) * np.log(current_pct / baseline_pct))
    return float(psi)

def detect_feature_drift(baseline_features: dict[str, np.ndarray],
                         current_features:  dict[str, np.ndarray],
                         psi_threshold: float = 0.2) -> list[DriftReport]:
    reports = []
    for feature_name in baseline_features:
        if feature_name not in current_features:
            continue
        baseline = baseline_features[feature_name]
        current  = current_features[feature_name]

        psi = compute_psi(baseline, current)
        ks_stat, ks_pval = stats.ks_2samp(baseline, current)

        # Drift declared when PSI exceeds threshold OR KS test rejects at 1%
        drift = psi > psi_threshold or ks_pval < 0.01

        reports.append(DriftReport(
            feature_name=feature_name,
            psi_score=psi,
            ks_statistic=ks_stat,
            ks_pvalue=ks_pval,
            drift_detected=drift
        ))
    return reports

class DriftMonitor:
    def __init__(self, redis_client, retraining_trigger_callback):
        self.redis    = redis_client
        self.trigger  = retraining_trigger_callback
        self.baseline: Optional[dict[str, np.ndarray]] = None

    def load_baseline(self, model_version: str):
        """Load feature statistics captured at training time."""
        raw = self.redis.get(f"model:baseline_features:{model_version}")
        if raw:
            import json
            data = json.loads(raw)
            self.baseline = {k: np.array(v) for k, v in data.items()}

    def check(self, current_features: dict[str, np.ndarray],
              model_version: str):
        if self.baseline is None:
            self.load_baseline(model_version)
        if self.baseline is None:
            return  # no baseline to compare against

        reports = detect_feature_drift(self.baseline, current_features)
        drifted = [r for r in reports if r.drift_detected]

        if drifted:
            # Publish drift report for observability
            import json
            drift_summary = {
                r.feature_name: {'psi': r.psi_score, 'ks_p': r.ks_pvalue}
                for r in drifted
            }
            self.redis.setex(
                f"model:drift_report:{model_version}",
                86400,
                json.dumps(drift_summary)
            )
            # Fire retraining if any feature shows significant drift
            self.trigger(reason="feature_drift", drifted_features=drifted)

    Retraining Pipeline

    When drift is detected, the retraining pipeline executes in four stages:

    1. Data extraction: Pull the last 90 days of feature vectors from the time-series store, filtered to queries with at least 50 executions for statistical reliability.

    2. Pseudo-label generation: High-confidence predictions from the current model (confidence ≥ 0.85) on the new data become training labels. This is the semi-supervised step — it allows the model to adapt to new query patterns without requiring fresh human annotation.

    3. Model training and validation: The new model is trained on the combined dataset (original labeled data + pseudo-labeled new data) with a held-out validation set from the most recent 14 days. The new model must exceed the current model's F1 score on the validation set by at least 0.01 before it is promoted.

    4. Shadow deployment: The new model runs in parallel with the existing model for 24 hours, its classifications logged but not applied. If the classification agreement rate between old and new model drops below 80% on OLTP_POINT queries — the highest-stakes class — the deployment is halted and the divergence is flagged for human review.

    import lightgbm as lgb
import numpy as np
from sklearn.model_selection import train_test_split
from sklearn.metrics import f1_score
import joblib

def retrain_classifier(
    labeled_X: np.ndarray,
    labeled_y: np.ndarray,
    unlabeled_X: np.ndarray,
    current_model: lgb.Booster,
    pseudo_label_threshold: float = 0.85,
    min_f1_improvement: float = 0.01
) -> Optional[lgb.Booster]:

    # Stage 2: generate pseudo-labels from current model
    if len(unlabeled_X) > 0:
        proba = current_model.predict(unlabeled_X)
        max_proba = proba.max(axis=1)
        pseudo_labels = proba.argmax(axis=1)

        high_conf_mask = max_proba >= pseudo_label_threshold
        pseudo_X = unlabeled_X[high_conf_mask]
        pseudo_y = pseudo_labels[high_conf_mask]

        combined_X = np.vstack([labeled_X, pseudo_X])
        combined_y = np.concatenate([labeled_y, pseudo_y])
    else:
        combined_X = labeled_X
        combined_y = labeled_y

    # Stage 3: train and validate
    X_train, X_val, y_train, y_val = train_test_split(
        combined_X, combined_y, test_size=0.2,
        stratify=combined_y, random_state=42
    )

    params = {
        'objective':      'multiclass',
        'num_class':      5,
        'learning_rate':  0.05,
        'num_leaves':     63,
        'min_child_samples': 30,
        'feature_fraction':  0.8,
        'bagging_fraction':  0.8,
        'bagging_freq':      5,
        'verbose':        -1
    }

    dtrain = lgb.Dataset(X_train, label=y_train)
    dval   = lgb.Dataset(X_val,   label=y_val, reference=dtrain)

    new_model = lgb.train(
        params,
        dtrain,
        num_boost_round=500,
        valid_sets=[dval],
        callbacks=[lgb.early_stopping(50), lgb.log_evaluation(100)]
    )

    # Evaluate both models on validation set
    new_preds     = new_model.predict(X_val).argmax(axis=1)
    current_preds = current_model.predict(X_val).argmax(axis=1)

    new_f1     = f1_score(y_val, new_preds,     average='weighted')
    current_f1 = f1_score(y_val, current_preds, average='weighted')

    if new_f1 < current_f1 + min_f1_improvement:
        return None  # not good enough — keep existing model

    return new_model

    15.6 Workload Fingerprinting for Query Plan Stability

    Classification labels serve a second purpose beyond resource allocation: they anchor query plan stability enforcement. A query classified as OLTP_POINT should never suddenly acquire a parallel plan or a hash join it did not have before — such changes are almost always regressions for this workload type. An ANALYTICAL query, conversely, should be allowed — encouraged — to use new parallel strategies as the optimizer sees them.

    This insight leads to class-specific plan enforcement policies:

    Workload ClassPlan Enforcement Policy
    OLTP_POINTFreeze plan on first stable execution; force via SQL Server plan guide or Query Store plan forcing
    OLTP_MODERATESoft lock: alert on plan change, auto-test new plan before promoting
    ANALYTICALNo plan locking; allow optimizer freedom; monitor regression by execution time
    BATCH_ETLLock to validated plan for each ETL step; rebuild plan on schema changes
    MAINTENANCENo plan management; use default optimizer behavior

    SQL Server: Plan Fingerprinting and Stability Monitoring

    -- Track plan stability per query class
CREATE TABLE dbo.query_plan_registry (
    query_id        INT            NOT NULL,
    workload_class  NVARCHAR(32)   NOT NULL,
    plan_hash       BINARY(8)      NOT NULL,  -- query_plan_hash from Query Store
    first_seen      DATETIME2      NOT NULL DEFAULT SYSUTCDATETIME(),
    last_seen       DATETIME2      NOT NULL DEFAULT SYSUTCDATETIME(),
    execution_count BIGINT         NOT NULL DEFAULT 1,
    avg_exec_ms     FLOAT          NOT NULL,
    is_locked       BIT            NOT NULL DEFAULT 0,
    CONSTRAINT PK_query_plan_registry PRIMARY KEY (query_id, plan_hash)
);
GO

-- Called by the classification agent when a new plan hash
-- is observed for a locked query
CREATE OR ALTER PROCEDURE dbo.handle_plan_change
    @query_id       INT,
    @new_plan_hash  BINARY(8),
    @avg_exec_ms    FLOAT
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @class NVARCHAR(32), @locked_plan BINARY(8),
            @locked_exec_ms FLOAT, @regression_pct FLOAT;

    SELECT @class = workload_class, @locked_plan = plan_hash,
           @locked_exec_ms = avg_exec_ms
    FROM dbo.query_plan_registry
    WHERE query_id = @query_id AND is_locked = 1;

    IF @@ROWCOUNT = 0
    BEGIN
        -- No locked plan yet; record this as baseline
        INSERT INTO dbo.query_plan_registry
            (query_id, workload_class, plan_hash, avg_exec_ms, is_locked)
        SELECT @query_id, workload_class, @new_plan_hash, @avg_exec_ms,
               CASE WHEN workload_class IN (N'OLTP_POINT', N'BATCH_ETL')
                    THEN 1 ELSE 0 END
        FROM dbo.workload_routing_map
        WHERE query_id = @query_id;
        RETURN;
    END;

    -- If the plan changed on a locked class, evaluate the regression
    IF @locked_plan <> @new_plan_hash
    BEGIN
        SET @regression_pct = (@avg_exec_ms - @locked_exec_ms)
                              / NULLIF(@locked_exec_ms, 0) * 100;

        INSERT INTO dbo.plan_change_alerts
            (query_id, workload_class, old_plan_hash, new_plan_hash,
             old_exec_ms, new_exec_ms, regression_pct, detected_at)
        VALUES
            (@query_id, @class, @locked_plan, @new_plan_hash,
             @locked_exec_ms, @avg_exec_ms, @regression_pct, SYSUTCDATETIME());

        -- For OLTP_POINT: flag for plan forcing via the locked plan hash.
        -- The orchestration layer forces the known-good plan through
        -- sys.sp_query_store_force_plan.
        IF @class = N'OLTP_POINT' AND @regression_pct > 10
        BEGIN
            UPDATE dbo.query_plan_registry
            SET last_seen = SYSUTCDATETIME()
            WHERE query_id = @query_id AND plan_hash = @locked_plan;

            INSERT INTO dbo.autonomous_actions_log
                (action_type, query_id, detail, performed_at)
            VALUES
                ('PLAN_FORCE_REQUESTED', @query_id,
                 'Force locked plan hash for regressed OLTP_POINT query',
                 SYSUTCDATETIME());
        END;
    END;
END;
GO

    SQL Server: Plan Guide Automation

    -- Create or refresh a plan guide for a regressed OLTP_POINT query
-- Called by the autonomous agent when a plan regression is detected
CREATE OR ALTER PROCEDURE dbo.enforce_plan_guide
    @query_id       INT,
    @statement_text NVARCHAR(MAX),
    @plan_handle    VARBINARY(64)   -- handle of the known-good plan
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @guide_name NVARCHAR(256) = N'ADE_AUTO_' + CAST(@query_id AS NVARCHAR);
    DECLARE @hints      NVARCHAR(MAX);

    -- Extract USE PLAN hint XML from the plan handle
    SELECT @hints = N'OPTION (USE PLAN N'''
                  + CAST(query_plan AS NVARCHAR(MAX))
                  + N''')'
    FROM sys.dm_exec_query_plan(@plan_handle);

    -- Drop existing guide if present
    IF EXISTS (SELECT 1 FROM sys.plan_guides WHERE name = @guide_name)
        EXEC sp_control_plan_guide N'DROP', @guide_name;

    -- Create new guide forcing the known-good plan
    EXEC sp_create_plan_guide
        @name        = @guide_name,
        @stmt        = @statement_text,
        @type        = N'SQL',
        @module_or_batch = NULL,
        @params      = NULL,
        @hints       = @hints;

    -- Record the enforcement action
    INSERT INTO dbo.autonomous_actions_log
        (action_type, query_id, detail, performed_at)
    VALUES
        ('PLAN_GUIDE_ENFORCED', @query_id,
         N'Guide: ' + @guide_name, SYSUTCDATETIME());
END;
GO

    The plan guide enforcement path completes the feedback loop: the classifier identifies a query's workload class, the plan registry tracks its execution plan history, and when a regression is detected on a locked class, the autonomous agent restores the known-good plan without waiting for DBA intervention.

    15.7 Observability: Making the Classification System Legible

    An autonomous classification system that operates as a black box will not survive contact with production operations teams. DBAs and on-call engineers need to understand why a query was assigned to a particular class, what resource policy is being applied, and what recent reclassification events have occurred. Without this visibility, the system will be disabled at the first sign of unexpected behavior.

    Three observability surfaces are required:

    Classification explanation table — a human-readable record of the dominant features that drove each classification decision.

    -- Dashboard view: current classification state for all active queries
CREATE OR ALTER VIEW dbo.vw_workload_classification_dashboard AS
SELECT
    qsq.query_id,
    LEFT(qsqt.query_sql_text, 120)              AS query_preview,
    wrm.workload_class,
    wrm.target_pool,
    wrm.statement_timeout_ms,
    wrm.work_mem,
    wrm.updated_at                               AS last_classified,
    ce.confidence,
    ce.explanation_text,
    -- Recent performance context
    AVG(qsrs.avg_duration / 1000.0)             AS avg_exec_ms_recent,
    SUM(qsrs.count_executions)                  AS executions_last_hour,
    MAX(qsrs.last_execution_time)               AS last_execution
FROM dbo.workload_routing_map              wrm
JOIN sys.query_store_query                 qsq  ON wrm.query_id      = qsq.query_id
JOIN sys.query_store_query_text            qsqt ON qsq.query_text_id = qsqt.query_text_id
JOIN sys.query_store_plan                  qspp ON qsq.query_id      = qspp.query_id
JOIN sys.query_store_runtime_stats         qsrs ON qspp.plan_id      = qsrs.plan_id
LEFT JOIN dbo.classification_explanations  ce   ON wrm.query_id      = ce.query_id
WHERE qsrs.last_execution_time > DATEADD(HOUR, -1, SYSUTCDATETIME())
GROUP BY
    qsq.query_id, qsqt.query_sql_text, wrm.workload_class,
    wrm.target_pool, wrm.statement_timeout_ms, wrm.work_mem,
    wrm.updated_at, ce.confidence, ce.explanation_text;

    Reclassification history and audit trail — DBAs need to see the timeline of classification changes for any query and the reason each change was made. This is both an operational tool and an audit record for compliance environments where resource policy decisions must be explainable.

    -- Reclassification history with feature deltas
CREATE OR ALTER VIEW dbo.workload_reclassification_history AS
SELECT
    rl.query_id,
    rl.old_class,
    rl.new_class,
    rl.event_time,
    -- Feature snapshot at time of reclassification
    ce_new.top_features                              AS features_at_change,
    ce_new.confidence                                AS confidence_at_change,
    -- Time in previous class
    DATEDIFF(SECOND,
        LAG(rl.event_time) OVER
            (PARTITION BY rl.query_id ORDER BY rl.event_time),
        rl.event_time)                               AS seconds_in_prior_class
FROM dbo.workload_reclassification_log rl
LEFT JOIN dbo.classification_explanations ce_new
    ON rl.query_id = ce_new.query_id

    The three observability layers — current classification state, feature explanations, and reclassification history — together provide the operational transparency required for DBAs to trust the autonomous system. When something unexpected occurs, the first question — "why did this query get classified as ANALYTICAL?" — has an immediate, data-backed answer in classification_explanations. The second question — "when did that change, and what triggered it?" — is answered by workload_reclassification_history.

    Key Takeaways

  • → Workload classification requires behavioral fingerprints, not just resource metrics. Features like result compression ratio, temporal burst coefficient, write amplification, and plan instability carry far more discriminative signal than raw CPU or memory consumption figures. Extracting these features from Query Store requires derived computation, not direct column reads.
  • → A five-class taxonomy — OLTP_POINT, OLTP_MODERATE, ANALYTICAL, BATCH_ETL, MAINTENANCE — is sufficient to drive all meaningful autonomous control decisions, including connection pool routing, resource group assignment, query timeout policy, and plan stability enforcement. Finer-grained taxonomies introduce instability without corresponding control benefit.
  • → Hysteresis filtering is non-negotiable in reclassification pipelines. Acting on every classification signal change causes resource thrashing that is more harmful than a slightly stale classification. Requiring three consecutive scoring intervals of agreement before committing a reclassification balances responsiveness against stability.
  • → Concept drift degrades classifiers silently. Monitoring the Population Stability Index across all input features and the confidence score distribution of model outputs provides early warning of drift before misclassifications accumulate to operational impact. Semi-supervised pseudo-labeling with a high confidence gate (≥ 0.85) allows continuous model adaptation without requiring ongoing human annotation effort.
  • → Autonomous classification systems require layered observability to earn operational trust. The classification decision itself, the feature contributions that drove it, and the full reclassification history for each query must all be queryable in real time. Without this transparency, operations teams will override or disable the system at the first unexpected outcome, defeating the purpose of autonomy.
