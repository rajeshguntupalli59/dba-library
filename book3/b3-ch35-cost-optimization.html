Chapter 35: Autonomous Cost Optimization

Cost is the boundary condition that shapes every other autonomous decision. A system that auto-scales without cost awareness will optimize itself into a cloud bill that ends careers. A system that freezes capacity to control spend will fail SLAs under load. Autonomous cost optimization is the discipline of building control loops that balance performance, availability, and expenditure continuously — without a human approving each tradeoff. This chapter covers the full architecture: how autonomous systems model infrastructure cost in real time, how they make provisioning and rightsizing decisions without human intervention, how query-level spend attribution works at scale, and how to implement feedback loops that keep cost within envelope while preserving SLA guarantees.

---

35.1 Cost Modeling as a First-Class Metric: Tagging, Attribution, and Real-Time Spend Signals

Before any autonomous system can optimize cost, it needs a continuously updated model of what things cost and who is responsible for that cost. Most teams treat cost as a billing artifact — something discovered monthly when the cloud invoice arrives. Autonomous systems treat cost as a runtime metric, sampled at the same frequency as CPU and I/O.

The foundation is dimensional cost attribution: every resource consumption event (query execution, storage write, network egress, index maintenance job) is tagged with an ownership dimension before it hits the billing system. In practice, this means building a cost metadata layer that maps database objects to cost centers.

-- Cost attribution registry
CREATE TABLE CostAttribution.Ownership (
    OwnershipID        INT IDENTITY(1,1) PRIMARY KEY,
    SchemaName         NVARCHAR(128)  NOT NULL,
    ApplicationTag     NVARCHAR(256),
    CostCenter         NVARCHAR(128)  NOT NULL,
    TeamName           NVARCHAR(128)  NOT NULL,
    MonthlyBudgetUSD   DECIMAL(12,2),
    AlertThresholdPct  DECIMAL(5,2)   DEFAULT 80.0,
    CreatedAt          DATETIME2      DEFAULT SYSUTCDATETIME(),
    UpdatedAt          DATETIME2      DEFAULT SYSUTCDATETIME()
);

-- Real-time query cost estimate from Query Store
CREATE OR REPLACE VIEW CostAttribution.QueryCostEstimate AS
SELECT
    qsq.query_id,
    qsq.query_hash,
    SUBSTRING(qt.query_sql_text, 1, 500)   AS query_sample,
    ca.CostCenter,
    ca.TeamName,
    qsrs.count_executions,
    qsrs.avg_duration / 1000.0             AS avg_duration_ms,
    qsrs.avg_cpu_time / 1000.0             AS avg_cpu_ms,
    -- Compute cost estimate: $0.048/vCPU-hour
    ROUND(
        (qsrs.avg_cpu_time / 1e6 / 3600.0) -- microseconds → hours
        * qsrs.count_executions
        * 0.048
    , 6)                                   AS estimated_compute_cost_usd,
    qsrs.avg_logical_io_reads,
    -- I/O cost estimate
    ROUND(
        (qsrs.avg_logical_io_reads * 8192.0 / 1e9)
        * qsrs.count_executions
        * 0.10
    , 6)                                   AS estimated_io_cost_usd
FROM sys.query_store_query          qsq
JOIN sys.query_store_query_text     qt   ON qt.query_text_id = qsq.last_query_text_id
JOIN sys.query_store_runtime_stats  qsrs ON qsrs.plan_id IN (
    SELECT plan_id FROM sys.query_store_plan WHERE query_id = qsq.query_id
)
LEFT JOIN CostAttribution.Ownership ca
    ON qsq.object_id IN (
        SELECT object_id FROM sys.objects WHERE schema_id = SCHEMA_ID(ca.SchemaName)
    )
WHERE qsrs.last_execution_time >= DATEADD(HOUR, -1, SYSUTCDATETIME());

The real-time signal layer pulls from cloud pricing APIs — AWS Cost Explorer, Azure Cost Management, or GCP Billing — and correlates resource-level line items with database-level metrics. The autonomous system needs this correlation to know that a spike in shared_blks_read on a PostgreSQL replica translates into a measurable EBS cost increase, not just a performance concern.

The Python daemon below polls cloud cost APIs every 15 minutes and writes normalized cost signals into a time-series store (Prometheus pushgateway or InfluxDB) alongside database metrics:

import boto3
import psycopg2
import requests
import json
from datetime import datetime, timedelta
from prometheus_client import CollectorRegistry, Gauge, push_to_gateway

PUSHGATEWAY_URL = "http://prometheus-pushgateway:9091"
DB_CONN = "host=localhost dbname=platform user=cost_agent password=secret"

def fetch_rds_cost(account_id: str, cluster_id: str) -> float:
    """Pull last 24h spend for a specific RDS cluster from Cost Explorer."""
    client = boto3.client("ce", region_name="us-east-1")
    end = datetime.utcnow().date()
    start = end - timedelta(days=1)
    response = client.get_cost_and_usage(
        TimePeriod={"Start": str(start), "End": str(end)},
        Granularity="DAILY",
        Filter={
            "And": [
                {"Dimensions": {"Key": "SERVICE", "Values": ["Amazon Relational Database Service"]}},
                {"Tags": {"Key": "ClusterID", "Values": [cluster_id]}}
            ]
        },
        Metrics=["UnblendedCost"],
        GroupBy=[{"Type": "TAG", "Key": "CostCenter"}]
    )
    total = 0.0
    for result in response.get("ResultsByTime", []):
        for group in result.get("Groups", []):
            total += float(group["Metrics"]["UnblendedCost"]["Amount"])
    return total

def push_cost_metrics(cluster_id: str, cost_usd: float, cost_center: str):
    registry = CollectorRegistry()
    g = Gauge(
        "db_cluster_daily_cost_usd",
        "Estimated daily cost for database cluster",
        ["cluster_id", "cost_center"],
        registry=registry
    )
    g.labels(cluster_id=cluster_id, cost_center=cost_center).set(cost_usd)
    push_to_gateway(PUSHGATEWAY_URL, job="cost_optimizer", registry=registry)

def record_cost_signal(cluster_id: str, cost_usd: float, cost_center: str):
    """Write cost signal to local PostgreSQL cost tracking table."""
    conn = psycopg2.connect(DB_CONN)
    with conn.cursor() as cur:
        cur.execute("""
            INSERT INTO cost_attribution.daily_spend
                (cluster_id, cost_center, spend_date, cost_usd, recorded_at)
            VALUES (%s, %s, CURRENT_DATE, %s, NOW())
            ON CONFLICT (cluster_id, cost_center, spend_date)
            DO UPDATE SET cost_usd = EXCLUDED.cost_usd, recorded_at = NOW()
        """, (cluster_id, cost_center, cost_usd))
    conn.commit()
    conn.close()

if __name__ == "__main__":
    clusters = [
        {"id": "prod-pg-cluster-01", "cost_center": "platform-eng"},
        {"id": "prod-pg-cluster-02", "cost_center": "data-science"},
    ]
    for c in clusters:
        cost = fetch_rds_cost("123456789012", c["id"])
        push_cost_metrics(c["id"], cost, c["cost_center"])
        record_cost_signal(c["id"], cost, c["cost_center"])
        print(f"Recorded ${cost:.4f} for {c['id']} ({c['cost_center']})")

With cost flowing as a real-time metric, the system now has the signal quality needed to make autonomous decisions — not just report on what was spent.

35.2 Autonomous Rightsizing: Instance, Storage, and Replica Count Control Loops

Rightsizing without autonomy is a quarterly meeting. Rightsizing with autonomy is a continuous control loop that evaluates provisioned capacity against actual utilization and executes changes within pre-approved envelopes. The key architectural distinction is between reactive rightsizing (respond to a threshold breach) and predictive rightsizing (anticipate tomorrow's workload shape and pre-position capacity at the right tier before the cost is incurred).

The control loop for autonomous rightsizing operates on three independent axes:

1. Compute tier — instance size (vCPU/RAM). Scale up when P95 CPU exceeds 75% for 30 consecutive minutes during business hours. Scale down when P95 CPU stays below 20% for 4 consecutive hours outside a peak window.

2. Storage tier — provisioned IOPS versus actual IOPS. On AWS RDS, gp3 volumes allow independent IOPS and throughput provisioning. When consumed IOPS consistently runs below 40% of provisioned, the system reduces provisioned IOPS to the next tier down.

3. Replica count — read replicas are the largest cost lever in most PostgreSQL and SQL Server architectures. Each read replica is a full instance cost. The system tracks replica load in 5-minute windows and decommissions idle replicas using a golden signal model: if a replica's active connections drop below 5 and its CPU stays under 10% for 20 consecutive minutes, it is a candidate for removal.

-- Autonomous rightsizing evaluation for Always On secondaries
CREATE OR REPLACE PROCEDURE CostOptimization.EvaluateReplicaRightsizing
AS
BEGIN
    SET NOCOUNT ON;

    SELECT
        rm.ReplicaHost,
        CASE
            WHEN rm.AvgActiveConnections < 5
             AND rm.AvgCPUPct < 10
             AND rm.ConsecutiveIdleWindows >= 4
            THEN 'DECOMMISSION'
            WHEN rm.AvgActiveConnections < 10
             AND rm.AvgCPUPct < 25
             AND rm.ConsecutiveIdleWindows >= 12
            THEN 'SCALE_DOWN_TIER'
            ELSE 'NO_ACTION'
        END                                    AS ActionRecommended,
        rm.AvgActiveConnections,
        rm.AvgCPUPct,
        rm.ConsecutiveIdleWindows * 5          AS IdleDurationMin,
        -- SQL Server Business Critical: ~$0.55/vCore-hour × 8 vCores × 730hr
        CASE
            WHEN rm.ConsecutiveIdleWindows >= 4
            THEN CAST(0.55 * 8 * 730 AS DECIMAL(10,2))
            ELSE 0.00
        END                                    AS EstimatedSavingsUSDMonth
    FROM CostOptimization.ReplicaMetricsRollup rm
    WHERE rm.WindowEnd >= DATEADD(HOUR, -1, SYSUTCDATETIME())
    ORDER BY EstimatedSavingsUSDMonth DESC;
END;

The action layer for autonomous decommissioning requires three safeguards: a change freeze window (no decommissions during peak hours 08:00–22:00 local business timezone), a quorum check (never drop below minimum replica count defined in the DR policy, typically 2), and a cost approval gate — actions with savings above a threshold require an async approval signal from a human or a CI/CD pipeline before execution. Below the threshold, they execute immediately.

The Python controller that acts on these recommendations connects the evaluation SQL above to the cloud provider API:

import boto3
import psycopg2
from datetime import datetime, time
import pytz

RDS_CLIENT = boto3.client("rds", region_name="us-east-1")
DB_CONN = "host=localhost dbname=platform user=cost_agent"
MIN_REPLICA_COUNT = 2
AUTO_APPROVE_SAVINGS_THRESHOLD = 50.0   # USD/month
PEAK_HOURS_TZ = pytz.timezone("America/New_York")
PEAK_START = time(8, 0)
PEAK_END   = time(22, 0)

def is_peak_window() -> bool:
    now_local = datetime.now(PEAK_HOURS_TZ).time()
    return PEAK_START <= now_local <= PEAK_END

def get_current_replica_count(cluster_id: str) -> int:
    resp = RDS_CLIENT.describe_db_clusters(DBClusterIdentifier=cluster_id)
    return len(resp["DBClusters"][0]["DBClusterMembers"]) - 1  # subtract writer

def execute_rightsizing_actions(cluster_id: str):
    if is_peak_window():
        print("In peak window — skipping autonomous rightsizing.")
        return

    conn = psycopg2.connect(DB_CONN)
    with conn.cursor() as cur:
        cur.execute("""
            SELECT replica_host, action_recommended, estimated_savings_usd_mo
            FROM cost_optimization.evaluate_replica_rightsizing()
            WHERE action_recommended != 'NO_ACTION'
        """)
        actions = cur.fetchall()
    conn.close()

    current_replicas = get_current_replica_count(cluster_id)

    for replica_host, action, savings in actions:
        if action == "DECOMMISSION":
            if current_replicas <= MIN_REPLICA_COUNT:
                print(f"Skipping {replica_host} — at minimum replica floor.")
                continue
            if savings >= AUTO_APPROVE_SAVINGS_THRESHOLD:
                # Auto-approve: execute immediately
                print(f"Auto-decommissioning {replica_host} (saves ${savings:.2f}/mo)")
                RDS_CLIENT.delete_db_instance(
                    DBInstanceIdentifier=replica_host,
                    SkipFinalSnapshot=True
                )
                current_replicas -= 1
            else:
                # Queue for async human approval
                queue_for_approval(replica_host, action, savings)

def queue_for_approval(replica_host: str, action: str, savings: float):
    """Write to approval queue — picked up by async approval service."""
    conn = psycopg2.connect(DB_CONN)
    with conn.cursor() as cur:
        cur.execute("""
            INSERT INTO cost_optimization.pending_approvals
                (resource_id, action, estimated_savings_usd_mo, requested_at, status)
            VALUES (%s, %s, %s, NOW(), 'PENDING')
        """, (replica_host, action, savings))
    conn.commit()
    conn.close()

if __name__ == "__main__":
    execute_rightsizing_actions("prod-aurora-cluster-01")

Storage rightsizing follows a similar pattern but operates on provisioned IOPS metrics from CloudWatch or Azure Monitor rather than connection counts. The signal is: when VolumeReadIOPs + VolumeWriteIOPs averaged over a 7-day rolling window is below 40% of ProvisionedIOPS, reduce provisioned IOPS by one step (typically 1000 IOPS increments on gp3). Each reduction step saves approximately $0.10/hour on AWS.

35.3 Query-Level Cost Governance: Spend Limits, Query Killing, and Workload Shaping

Compute infrastructure rightsizing addresses the supply side of cost. Query-level governance addresses the demand side — it ensures that individual queries or workloads do not consume disproportionate resources relative to their business value. This is where autonomous cost optimization becomes genuinely operational rather than just architectural.

The discipline has three tiers:

Tier 1 — Statement Timeout Enforcement by Cost Center. Each cost center gets a configurable statement timeout. Data science workloads doing exploratory analysis against production replicas are limited to 30-second queries by default. OLTP application roles get 5-second timeouts. The mapping is maintained in the cost attribution registry and applied dynamically via connection pooler configuration (PgBouncer) or resource governor (SQL Server).

-- Resource Governor workload group mapping for cost governance
-- Each cost center maps to a resource pool with CPU/memory limits
CREATE RESOURCE POOL DataSciencePool
WITH (
    MIN_CPU_PERCENT        = 0,
    MAX_CPU_PERCENT        = 25,    -- Cap at 25% CPU for exploratory workloads
    MIN_MEMORY_PERCENT     = 0,
    MAX_MEMORY_PERCENT     = 20,
    MIN_IOPS_PER_VOLUME    = 0,
    MAX_IOPS_PER_VOLUME    = 500
);

CREATE RESOURCE POOL OLTPPool
WITH (
    MIN_CPU_PERCENT        = 20,
    MAX_CPU_PERCENT        = 80,
    MIN_MEMORY_PERCENT     = 20,
    MAX_MEMORY_PERCENT     = 70
);

-- Classifier function: route connections to pools based on login
CREATE FUNCTION CostOptimization.ClassifyWorkload()
RETURNS SYSNAME
WITH SCHEMABINDING AS
BEGIN
    DECLARE @PoolName SYSNAME = 'default';

    SELECT @PoolName = rcp.ResourcePoolName
    FROM CostOptimization.RoleCostPolicy rcp
    WHERE rcp.LoginName = SUSER_SNAME()
      AND rcp.IsActive = 1;

    RETURN @PoolName;
END;

ALTER RESOURCE GOVERNOR WITH (CLASSIFIER_FUNCTION = CostOptimization.ClassifyWorkload);
ALTER RESOURCE GOVERNOR RECONFIGURE;

-- Autonomous kill of queries exceeding cost-based time limits
-- Executed by SQL Agent job every 60 seconds
CREATE OR REPLACE PROCEDURE CostOptimization.KillOverbudgetQueries
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @SessionID   INT;
    DECLARE @LoginName   NVARCHAR(128);
    DECLARE @DurationSec INT;
    DECLARE @KillSQL     NVARCHAR(64);

    DECLARE kill_cursor CURSOR LOCAL FAST_FORWARD FOR
        SELECT
            r.session_id,
            s.login_name,
            DATEDIFF(SECOND, r.start_time, SYSUTCDATETIME()) AS duration_sec
        FROM sys.dm_exec_requests r
        JOIN sys.dm_exec_sessions  s ON s.session_id = r.session_id
        JOIN CostOptimization.RoleCostPolicy rcp
            ON rcp.LoginName = s.login_name
           AND rcp.IsActive   = 1
        WHERE DATEDIFF(SECOND, r.start_time, SYSUTCDATETIME())
              > rcp.HardKillTimeoutSec
          AND r.session_id <> @@SPID;

    OPEN kill_cursor;
    FETCH NEXT FROM kill_cursor INTO @SessionID, @LoginName, @DurationSec;

    WHILE @@FETCH_STATUS = 0
    BEGIN
        SET @KillSQL = N'KILL ' + CAST(@SessionID AS NVARCHAR(10));

        INSERT INTO CostOptimization.KillLog
            (SessionID, LoginName, DurationSec, KilledAt)
        VALUES (@SessionID, @LoginName, @DurationSec, SYSUTCDATETIME());

        EXEC sp_executesql @KillSQL;

        FETCH NEXT FROM kill_cursor INTO @SessionID, @LoginName, @DurationSec;
    END;

    CLOSE kill_cursor;
    DEALLOCATE kill_cursor;
END;

Tier 2 — Workload Shaping via Queue Depth Control. Rather than killing queries outright, a more sophisticated approach throttles arrival rate at the connection pooler. When the autonomous system detects that aggregate query cost (estimated compute + I/O) in a rolling 5-minute window is approaching the cost center's budget threshold, it instructs PgBouncer (PostgreSQL) or the application-tier connection pool (SQL Server) to reduce max_client_conn for the offending pool. This creates natural back-pressure without hard terminations — callers queue rather than fail, and the system bleeds off the overload gradually.

The key metrics that drive queue depth control are:

  • → `active_query_cost_rate_usd_per_min` — sum of estimated cost per minute across all currently running queries for a cost center
  • → `budget_burn_rate_pct` — how fast the monthly budget is being consumed versus expected linear burn
  • → `queue_depth_ratio` — ratio of waiting connections to active connections; above 3.0 indicates a pooler bottleneck that amplifies cost

    • PostgreSQL — budget burn rate monitor:

    CREATE OR REPLACE VIEW cost_optimization.budget_burn_rate AS
WITH daily_spend AS (
    SELECT
        cost_center,
        SUM(cost_usd) AS mtd_spend_usd
    FROM cost_attribution.daily_spend
    WHERE spend_date >= DATE_TRUNC('month', CURRENT_DATE)
    GROUP BY cost_center
),
expected_linear AS (
    SELECT
        o.cost_center,
        o.monthly_budget_usd,
        -- Days elapsed in current month as fraction
        EXTRACT(DAY FROM NOW()) / EXTRACT(DAY FROM
            (DATE_TRUNC('month', NOW()) + INTERVAL '1 month - 1 day')
        ) AS month_fraction
    FROM cost_attribution.ownership o
)
SELECT
    el.cost_center,
    el.monthly_budget_usd,
    COALESCE(ds.mtd_spend_usd, 0)                          AS mtd_spend_usd,
    el.monthly_budget_usd * el.month_fraction               AS expected_spend_usd,
    ROUND(
        COALESCE(ds.mtd_spend_usd, 0)
        / NULLIF(el.monthly_budget_usd * el.month_fraction, 0)
        * 100
    , 2)                                                    AS burn_rate_pct,
    CASE
        WHEN COALESCE(ds.mtd_spend_usd, 0)
             > el.monthly_budget_usd * el.month_fraction * 1.20
        THEN 'THROTTLE'
        WHEN COALESCE(ds.mtd_spend_usd, 0)
             > el.monthly_budget_usd * el.month_fraction * 1.10
        THEN 'WARN'
        ELSE 'NORMAL'
    END                                                     AS budget_status
FROM expected_linear el
LEFT JOIN daily_spend ds USING (cost_center);

    SQL Server — equivalent burn rate view:

    CREATE OR REPLACE VIEW CostOptimization.BudgetBurnRate AS
WITH DailySpend AS (
    SELECT
        CostCenter,
        SUM(CostUSD) AS MTDSpendUSD
    FROM CostAttribution.DailySpend
    WHERE SpendDate >= DATEFROMPARTS(YEAR(SYSUTCDATETIME()), MONTH(SYSUTCDATETIME()), 1)
    GROUP BY CostCenter
),
ExpectedLinear AS (
    SELECT
        o.CostCenter,
        o.MonthlyBudgetUSD,
        -- Fraction of month elapsed
        CAST(DAY(SYSUTCDATETIME()) AS FLOAT)
        / CAST(DAY(EOMONTH(SYSUTCDATETIME())) AS FLOAT)  AS MonthFraction
    FROM CostAttribution.Ownership o
)
SELECT
    el.CostCenter,
    el.MonthlyBudgetUSD,
    ISNULL(ds.MTDSpendUSD, 0)                              AS MTDSpendUSD,
    el.MonthlyBudgetUSD * el.MonthFraction                 AS ExpectedSpendUSD,
    ROUND(
        ISNULL(ds.MTDSpendUSD, 0)
        / NULLIF(el.MonthlyBudgetUSD * el.MonthFraction, 0)
        * 100
    , 2)                                                   AS BurnRatePct,
    CASE
        WHEN ISNULL(ds.MTDSpendUSD, 0)
             > el.MonthlyBudgetUSD * el.MonthFraction * 1.20
        THEN 'THROTTLE'
        WHEN ISNULL(ds.MTDSpendUSD, 0)
             > el.MonthlyBudgetUSD * el.MonthFraction * 1.10
        THEN 'WARN'
        ELSE 'NORMAL'
    END                                                    AS BudgetStatus
FROM ExpectedLinear el
LEFT JOIN DailySpend ds ON ds.CostCenter = el.CostCenter;

    Tier 3 — Query Rewrite and Index Suggestion as a Cost Reduction Path. Before a query is killed or a workload is throttled, the system checks whether the expensive query matches a known rewrite pattern or is missing an index that would reduce its resource footprint by more than 50%. This is cost-aware query optimization: the autonomous planner asks not just "is this query slow?" but "is this query consuming more budget than its value warrants, and can we fix it without killing it?"

    This closes the loop between cost governance and the query optimization subsystems covered in earlier chapters. The cost signal from pg_stat_statements or Query Store feeds back into the index advisor, which prioritizes index candidates by estimated cost reduction rather than purely by execution time improvement.

    35.4 Predictive Cost Forecasting: Time-Series Models for Budget Protection

    Reactive cost control — responding after a threshold is crossed — is inherently too slow for monthly budget protection. By the time a cost center is 20% over its expected burn rate, the spend has already occurred. Predictive cost forecasting shifts the control point upstream: the autonomous system builds a rolling forecast of end-of-month spend and takes throttling action when the forecast, not the current spend, exceeds the budget.

    The forecasting model does not need to be sophisticated. A linear extrapolation with a 7-day trailing average captures most of the signal in workloads that have weekly seasonality (which is the majority of business database workloads). More complex workloads — those with end-of-quarter spikes, monthly batch runs, or irregular marketing campaigns — benefit from a simple additive decomposition: trend + weekly seasonal component + a one-time event flag populated from an engineering calendar.

    PostgreSQL — rolling cost forecast with linear extrapolation:

    CREATE OR REPLACE FUNCTION cost_optimization.forecast_month_end_spend(
    p_cost_center TEXT
)
RETURNS TABLE (
    cost_center           TEXT,
    current_mtd_spend     NUMERIC,
    forecast_month_end    NUMERIC,
    monthly_budget        NUMERIC,
    forecast_over_budget  BOOLEAN,
    days_until_breach     INT
) AS $$
DECLARE
    v_days_in_month   INT;
    v_days_elapsed    INT;
    v_mtd_spend       NUMERIC;
    v_daily_avg_7d    NUMERIC;
    v_days_remaining  INT;
    v_forecast        NUMERIC;
    v_budget          NUMERIC;
BEGIN
    v_days_in_month  := EXTRACT(DAY FROM
        DATE_TRUNC('month', NOW()) + INTERVAL '1 month' - INTERVAL '1 day'
    )::INT;
    v_days_elapsed   := EXTRACT(DAY FROM NOW())::INT;
    v_days_remaining := v_days_in_month - v_days_elapsed;

    -- MTD actual spend
    SELECT COALESCE(SUM(ds.cost_usd), 0)
    INTO   v_mtd_spend
    FROM   cost_attribution.daily_spend ds
    WHERE  ds.cost_center = p_cost_center
      AND  ds.spend_date >= DATE_TRUNC('month', CURRENT_DATE);

    -- 7-day trailing daily average (excludes today to avoid partial day bias)
    SELECT COALESCE(AVG(ds.cost_usd), 0)
    INTO   v_daily_avg_7d
    FROM   cost_attribution.daily_spend ds
    WHERE  ds.cost_center = p_cost_center
      AND  ds.spend_date  >= CURRENT_DATE - 7
      AND  ds.spend_date  <  CURRENT_DATE;

    -- Simple linear forecast: MTD + (7d daily avg × remaining days)
    v_forecast := v_mtd_spend + (v_daily_avg_7d * v_days_remaining);

    SELECT COALESCE(o.monthly_budget_usd, 0)
    INTO   v_budget
    FROM   cost_attribution.ownership o
    WHERE  o.cost_center = p_cost_center
    LIMIT  1;

    RETURN QUERY SELECT
        p_cost_center,
        v_mtd_spend,
        v_forecast,
        v_budget,
        v_forecast > v_budget,
        CASE
            WHEN v_daily_avg_7d > 0
            THEN GREATEST(0, FLOOR(
                    (v_budget - v_mtd_spend) / v_daily_avg_7d
                 )::INT)
            ELSE v_days_remaining
        END;
END;
$$ LANGUAGE plpgsql;
    CREATE OR REPLACE PROCEDURE CostOptimization.ForecastMonthEndSpend
    @CostCenter NVARCHAR(128)
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE
        @DaysInMonth    INT,
        @DaysElapsed    INT,
        @DaysRemaining  INT,
        @MTDSpend       DECIMAL(12,2),
        @DailyAvg7D     DECIMAL(12,2),
        @Forecast       DECIMAL(12,2),
        @Budget         DECIMAL(12,2),
        @DaysToBreach   INT;

    SET @DaysInMonth   = DAY(EOMONTH(SYSUTCDATETIME()));
    SET @DaysElapsed   = DAY(SYSUTCDATETIME());
    SET @DaysRemaining = @DaysInMonth - @DaysElapsed;

    SELECT @MTDSpend = ISNULL(SUM(CostUSD), 0)
    FROM   CostAttribution.DailySpend
    WHERE  CostCenter = @CostCenter
      AND  SpendDate  >= DATEFROMPARTS(YEAR(SYSUTCDATETIME()),
                                       MONTH(SYSUTCDATETIME()), 1);

    SELECT @DailyAvg7D = ISNULL(AVG(CostUSD), 0)
    FROM   CostAttribution.DailySpend
    WHERE  CostCenter = @CostCenter
      AND  SpendDate  >= CAST(DATEADD(DAY, -7, SYSUTCDATETIME()) AS DATE)
      AND  SpendDate  <  CAST(SYSUTCDATETIME() AS DATE);

    SET @Forecast = @MTDSpend + (@DailyAvg7D * @DaysRemaining);

    SELECT @Budget = ISNULL(MonthlyBudgetUSD, 0)
    FROM   CostAttribution.Ownership
    WHERE  CostCenter = @CostCenter;

    SET @DaysToBreach =
        CASE
            WHEN @DailyAvg7D > 0
            THEN CAST(FLOOR((@Budget - @MTDSpend) / @DailyAvg7D) AS INT)
            ELSE @DaysRemaining
        END;

    SELECT
        @CostCenter                         AS CostCenter,
        @MTDSpend                           AS CurrentMTDSpend,
        @Forecast                           AS ForecastMonthEnd,
        @Budget                             AS MonthlyBudget,
        CASE WHEN @Forecast > @Budget
             THEN CAST(1 AS BIT) ELSE CAST(0 AS BIT) END AS ForecastOverBudget,
        GREATEST(0, @DaysToBreach)          AS DaysUntilBreach;
END;

    The forecast output feeds a graduated response ladder. When days_until_breach is more than 14, the system logs a warning. When it drops below 7, the system automatically tightens statement timeouts by 20% for non-critical roles. When it drops below 3, the system activates hard throttling — reducing max_connections for the offending cost center's pool and rejecting new batch workload submissions. This graduated ladder prevents both false alarms (which erode trust in the autonomous system) and budget overruns (which erode organizational confidence in autonomous operation).

    The forecast can be enhanced with an event calendar overlay — a simple table that records known high-cost events (end-of-quarter reporting runs, data migration windows, marketing campaign activations) with an estimated cost multiplier. On days adjacent to a calendar event, the system widens the forecast confidence band rather than triggering throttling prematurely.

    35.5 Multi-Dimensional Cost Tradeoff Engine: Balancing SLA, Availability, and Spend

    The hardest problem in autonomous cost optimization is not identifying waste — it is making the correct tradeoff when cost reduction and SLA preservation are in direct conflict. A replica that is idle 90% of the time costs money to run. But that same replica may be the one that absorbs a burst read query from a monthly finance report that arrives at an unpredictable time. Removing it saves cost; keeping it preserves latency headroom. The autonomous system needs a principled framework for resolving this tension without defaulting to the human-in-the-loop.

    The framework used here is a multi-objective scoring function that assigns a composite score to each potential cost action. The score has three components:

    1. Cost savings weight (W_cost) — normalized USD saved per month, scaled 0–1 against the maximum potential saving in the action set.

    2. SLA risk weight (W_sla) — estimated probability that this action causes an SLA breach in the next 30 days, scaled 0–1 (higher is riskier).

    3. Availability risk weight (W_avail) — estimated probability that removing this resource increases RTO if a primary failure occurs simultaneously, scaled 0–1.

    The composite action score is:

    Action_Score = W_cost × α  −  W_sla × β  −  W_avail × γ

    where α, β, and γ are organizational preference weights that encode risk tolerance. A cost-aggressive organization (a startup in growth phase) might set α=0.7, β=0.2, γ=0.1. A risk-averse organization (financial services) might set α=0.3, β=0.4, γ=0.3. Actions with positive composite scores are candidates for autonomous execution; negative-scoring actions require human approval regardless of the savings magnitude.

    PostgreSQL — multi-objective scoring implementation:

    CREATE OR REPLACE FUNCTION cost_optimization.score_cost_actions(
    p_alpha NUMERIC DEFAULT 0.5,   -- cost savings weight
    p_beta  NUMERIC DEFAULT 0.3,   -- SLA risk weight
    p_gamma NUMERIC DEFAULT 0.2    -- availability risk weight
)
RETURNS TABLE (
    action_id           INT,
    resource_id         TEXT,
    action_type         TEXT,
    savings_usd_mo      NUMERIC,
    sla_risk_score      NUMERIC,
    availability_risk   NUMERIC,
    composite_score     NUMERIC,
    recommended         BOOLEAN
) AS $$
DECLARE
    v_max_savings NUMERIC;
BEGIN
    -- Normalize savings against the maximum in the candidate set
    SELECT MAX(ca.estimated_savings_usd_mo)
    INTO   v_max_savings
    FROM   cost_optimization.action_candidates ca
    WHERE  ca.status = 'PENDING';

    RETURN QUERY
    SELECT
        ca.action_id,
        ca.resource_id,
        ca.action_type,
        ca.estimated_savings_usd_mo,
        ca.sla_risk_score,
        ca.availability_risk_score,
        ROUND(
            (ca.estimated_savings_usd_mo / NULLIF(v_max_savings, 0)) * p_alpha
            - ca.sla_risk_score   * p_beta
            - ca.availability_risk_score * p_gamma
        , 4)                                        AS composite_score,
        (
            (ca.estimated_savings_usd_mo / NULLIF(v_max_savings, 0)) * p_alpha
            - ca.sla_risk_score   * p_beta
            - ca.availability_risk_score * p_gamma
        ) > 0                                       AS recommended
    FROM cost_optimization.action_candidates ca
    WHERE ca.status = 'PENDING'
    ORDER BY composite_score DESC;
END;
$$ LANGUAGE plpgsql;
    CREATE OR REPLACE PROCEDURE CostOptimization.ScoreCostActions
    @Alpha DECIMAL(4,2) = 0.5,
    @Beta  DECIMAL(4,2) = 0.3,
    @Gamma DECIMAL(4,2) = 0.2
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @MaxSavings DECIMAL(12,2);

    SELECT @MaxSavings = MAX(EstimatedSavingsUSDMonth)
    FROM   CostOptimization.ActionCandidates
    WHERE  Status = 'PENDING';

    SELECT
        ca.ActionID,
        ca.ResourceID,
        ca.ActionType,
        ca.EstimatedSavingsUSDMonth,
        ca.SLARiskScore,
        ca.AvailabilityRiskScore,
        ROUND(
            (ca.EstimatedSavingsUSDMonth / NULLIF(@MaxSavings, 0)) * @Alpha
            - ca.SLARiskScore            * @Beta
            - ca.AvailabilityRiskScore   * @Gamma
        , 4)                                            AS CompositeScore,
        CASE
            WHEN (
                (ca.EstimatedSavingsUSDMonth / NULLIF(@MaxSavings, 0)) * @Alpha
                - ca.SLARiskScore            * @Beta
                - ca.AvailabilityRiskScore   * @Gamma
            ) > 0 THEN CAST(1 AS BIT)
            ELSE CAST(0 AS BIT)
        END                                             AS Recommended
    FROM   CostOptimization.ActionCandidates ca
    WHERE  ca.Status = 'PENDING'
    ORDER  BY CompositeScore DESC;
END;

    The SLA risk score and availability risk score are not static — they are populated by the system's monitoring layer based on recent behavior. A replica that has served read traffic in the last 48 hours gets a higher SLA risk score for decommissioning than one that has been idle for two weeks. A replica in a region where the primary has shown elevated error rates gets a higher availability risk score for decommissioning than one in a region with a perfect health record.

    This self-updating risk model means the scoring function adapts to changing operational context rather than operating on fixed parameters. The weights (α, β, γ) are the only parameters that require human judgment; the input scores are data-driven and continuously refreshed.

    35.6 Feedback Loops and Continuous Calibration: Closing the Cost Optimization Cycle

    An autonomous cost optimization system that acts without measuring the effect of its actions will drift. Replicas are decommissioned, timeouts are tightened, IOPS are reduced — but without a feedback loop that measures whether these actions achieved their intended savings without degrading performance, the system has no mechanism to learn whether its models are calibrated or whether its thresholds are set appropriately.

    The feedback loop operates on a 30-day cycle aligned with the billing period:

    Step 1 — Action logging. Every autonomous action is written to an immutable audit log with the predicted outcome (expected savings, estimated SLA impact) recorded at decision time.

    Step 2 — Outcome measurement. 7 days after an action, the system queries actual spend and SLA metrics for the affected cost center and compares them against the predictions made at decision time.

    Step 3 — Calibration adjustment. If predictions consistently overestimate savings by more than 20%, the cost model's unit cost coefficients ($/vCPU-hour, $/GB-IO) are recalibrated using the measured actuals. If SLA risk predictions consistently underestimate breach probability, the β weight in the scoring function is increased automatically by 0.05 per miscalibration event, up to a maximum of 0.6.

    PostgreSQL — feedback calibration table and adjustment function:

    CREATE TABLE cost_optimization.action_outcomes (
    outcome_id          SERIAL PRIMARY KEY,
    action_id           INT NOT NULL REFERENCES cost_optimization.action_candidates(action_id),
    action_taken_at     TIMESTAMPTZ NOT NULL,
    predicted_savings   NUMERIC(12,2),
    actual_savings_7d   NUMERIC(12,2),
    predicted_sla_risk  NUMERIC(5,4),
    sla_breach_occurred BOOLEAN DEFAULT FALSE,
    measured_at         TIMESTAMPTZ DEFAULT NOW(),
    calibration_applied BOOLEAN DEFAULT FALSE
);

CREATE OR REPLACE FUNCTION cost_optimization.calibrate_cost_model()
RETURNS TEXT AS $$
DECLARE
    v_avg_savings_error   NUMERIC;
    v_sla_mismatch_count  INT;
    v_calibration_msg     TEXT := '';
BEGIN
    -- Check savings prediction accuracy over last 30 days
    SELECT AVG(
        (actual_savings_7d - predicted_savings)
        / NULLIF(predicted_savings, 0) * 100
    )
    INTO v_avg_savings_error
    FROM cost_optimization.action_outcomes
    WHERE measured_at >= NOW() - INTERVAL '30 days'
      AND calibration_applied = FALSE;

    IF ABS(v_avg_savings_error) > 20 THEN
        -- Adjust cost coefficients by the error fraction
        UPDATE cost_optimization.cost_model_parameters
        SET coefficient_value = coefficient_value * (1 + v_avg_savings_error / 100.0),
            last_calibrated_at = NOW()
        WHERE parameter_name IN ('cpu_cost_per_vcpu_hour', 'io_cost_per_gb');

        v_calibration_msg := v_calibration_msg
            || format('Cost model recalibrated: avg error was %s%%. ', ROUND(v_avg_savings_error, 2));
    END IF;

    -- Check SLA risk prediction accuracy
    SELECT COUNT(*)
    INTO v_sla_mismatch_count
    FROM cost_optimization.action_outcomes
    WHERE measured_at        >= NOW() - INTERVAL '30 days'
      AND sla_breach_occurred = TRUE
      AND predicted_sla_risk  < 0.2    -- predicted low risk but breach occurred
      AND calibration_applied = FALSE;

    IF v_sla_mismatch_count >= 3 THEN
        UPDATE cost_optimization.scoring_weights
        SET weight_value = LEAST(weight_value + 0.05, 0.6),
            last_adjusted_at = NOW()
        WHERE weight_name = 'beta_sla_risk';

        v_calibration_msg := v_calibration_msg
            || format('SLA risk weight increased: %s under-predicted breaches. ',
                      v_sla_mismatch_count);
    END IF;

    -- Mark these outcomes as processed
    UPDATE cost_optimization.action_outcomes
    SET calibration_applied = TRUE
    WHERE measured_at >= NOW() - INTERVAL '30 days'
      AND calibration_applied = FALSE;

    RETURN COALESCE(NULLIF(v_calibration_msg, ''), 'No calibration required.');
END;
$$ LANGUAGE plpgsql;
    CREATE OR REPLACE PROCEDURE CostOptimization.CalibrateCostModel
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE
        @AvgSavingsError   DECIMAL(8,4),
        @SLAMismatchCount  INT,
        @CalibrationMsg    NVARCHAR(1000) = N'';

    -- Savings prediction accuracy
    SELECT @AvgSavingsError = AVG(
        (ActualSavings7D - PredictedSavings)
        / NULLIF(PredictedSavings, 0) * 100
    )
    FROM CostOptimization.ActionOutcomes
    WHERE MeasuredAt          >= DATEADD(DAY, -30, SYSUTCDATETIME())
      AND CalibrationApplied  = 0;

    IF ABS(@AvgSavingsError) > 20
    BEGIN
        UPDATE CostOptimization.CostModelParameters
        SET    CoefficientValue  = CoefficientValue * (1 + @AvgSavingsError / 100.0),
               LastCalibratedAt = SYSUTCDATETIME()
        WHERE  ParameterName IN (N'cpu_cost_per_vcpu_hour', N'io_cost_per_gb');

        SET @CalibrationMsg = @CalibrationMsg
            + N'Cost model recalibrated: avg error was '
            + CAST(ROUND(@AvgSavingsError, 2) AS NVARCHAR(20)) + N'%. ';
    END;

    -- SLA risk underestimation check
    SELECT @SLAMismatchCount = COUNT(*)
    FROM CostOptimization.ActionOutcomes
    WHERE MeasuredAt          >= DATEADD(DAY, -30, SYSUTCDATETIME())
      AND SLABreachOccurred   = 1
      AND PredictedSLARisk    < 0.2
      AND CalibrationApplied  = 0;

    IF @SLAMismatchCount >= 3
    BEGIN
        UPDATE CostOptimization.ScoringWeights
        SET    WeightValue     = CASE
                                     WHEN WeightValue + 0.05 > 0.6 THEN 0.6
                                     ELSE WeightValue + 0.05
                                 END,
               LastAdjustedAt = SYSUTCDATETIME()
        WHERE  WeightName = N'beta_sla_risk';

        SET @CalibrationMsg = @CalibrationMsg
            + N'SLA risk weight increased: '
            + CAST(@SLAMismatchCount AS NVARCHAR(10))
            + N' under-predicted breaches. ';
    END;

    -- Mark outcomes processed
    UPDATE CostOptimization.ActionOutcomes
    SET    CalibrationApplied = 1
    WHERE  MeasuredAt        >= DATEADD(DAY, -30, SYSUTCDATETIME())
      AND  CalibrationApplied = 0;

    SELECT ISNULL(NULLIF(@CalibrationMsg, N''), N'No calibration required.') AS CalibrationResult;
END;

    The calibration function is scheduled to run on the first day of each billing month, immediately after month-end actuals are available from the cloud provider. Over several billing cycles, the cost model converges toward accurate unit cost estimates for the specific instance family and region in use, and the scoring weights stabilize at values that reflect the organization's actual risk tolerance as revealed by operational history rather than aspirational policy documents.

    A reasonable target for a well-calibrated system after six months of operation is predicted savings within 10% of actual savings and an SLA breach false-negative rate in the low single digits — figures that will vary with workload volatility and forecasting horizon. Track the actual numbers in the action_outcomes table and report them in a monthly cost optimization review rather than assuming convergence.

    Key Takeaways

  • → **Cost must be a runtime metric, not a billing artifact.** Autonomous cost optimization starts with dimensional attribution — tagging every query, index maintenance event, and storage write to a cost center at collection time, then flowing that signal into the same monitoring stack as CPU and I/O. Without real-time cost visibility, the control loops have nothing to act on.
  • → **Rightsizing operates on three independent axes — compute tier, storage IOPS, and replica count — each with its own control loop cadence and safeguards.** Replica decommissioning is gated by minimum quorum floors, change freeze windows, and cost approval thresholds to prevent the autonomous system from undermining DR guarantees in pursuit of savings.
  • → **Query-level cost governance addresses the demand side of spend through a three-tier model: statement timeout enforcement by cost center, workload shaping via connection pool queue depth control, and cost-aware index suggestion that prioritizes candidates by budget impact rather than raw execution time improvement.**
  • → **Predictive forecasting shifts the control point upstream of threshold breaches.** A linear extrapolation on a 7-day trailing daily average, overlaid with a calendar of known high-cost events, gives the system enough lead time to apply graduated throttling before a cost center's budget is exhausted — rather than after.
  • → **The multi-objective scoring function (W_cost × α − W_sla × β − W_avail × γ) provides a principled, auditable basis for resolving cost-versus-SLA tradeoffs autonomously.** The organizational risk preference is encoded in the α/β/γ weights, while the input scores are continuously refreshed from operational data. The feedback calibration loop closes the cycle by adjusting both the cost model coefficients and the β weight when predictions diverge from measured outcomes across billing periods.
