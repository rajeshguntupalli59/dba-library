Chapter 34: Observability for Autonomous Databases

Autonomous systems that act without human intervention are only as trustworthy as the signals they observe. A self-managing database can tune indexes, reroute connections, and promote replicas — but if its perception of system state is incomplete, delayed, or structurally wrong, every downstream decision compounds the error. This chapter is not about dashboards or alerting thresholds for on-call engineers. It is about building an observability layer that feeds autonomous decision engines: a nervous system that the database uses to know itself, reason about causality, and act with confidence. The architecture here draws from production patterns in cloud-native databases and translates them into SQL Server deployments that can be built today.

Signal Architecture: What Autonomous Databases Must See

Most observability stacks are built for humans — colorful dashboards, Slack notifications, runbook links in alert bodies. Autonomous systems need something architecturally different: a structured, machine-readable signal layer where every metric carries enough context for a decision engine to act without asking a human what it means.

The distinction matters immediately at the signal taxonomy level. Autonomous observability requires three categories of signals, each serving a different function in the decision loop:

State signals describe what is true right now — active sessions, lock counts, replication lag, buffer hit ratios, index bloat percentages. These are point-in-time facts.

Trend signals describe rate of change — query latency increasing at 12ms/minute, index fragmentation growth exceeding the rebuild threshold velocity, connection pool saturation trending toward hard limits. These enable predictive action before a threshold is breached.

Causal signals describe why something is happening — a lock wait chain rooted in a long-running transaction, a bloat spike correlated with a batch job that started at 02:00, a replication lag spike coinciding with a transaction log backup that contains a large DDL operation. These enable targeted remediation rather than blunt interventions.

A decision engine fed only state signals will be reactive and frequently wrong. Fed trend and causal signals, it can act preemptively and precisely.

-- Structured blocking signal for autonomous consumption
CREATE OR ALTER VIEW autonomous.blocking_signal AS
SELECT
    r.session_id                            AS blocked_session,
    r.blocking_session_id                   AS blocking_session,
    r.wait_type,
    r.wait_time / 1000                      AS wait_seconds,
    r.cpu_time,
    r.logical_reads,
    s_blocked.login_name                    AS blocked_login,
    s_blocked.program_name                  AS blocked_app,
    s_blocking.login_name                   AS blocking_login,
    s_blocking.program_name                 AS blocking_app,
    s_blocking.status                       AS blocking_status,
    DATEDIFF(SECOND, s_blocking.last_request_start_time, GETDATE()) AS blocker_age_seconds,
    t_blocked.text                          AS blocked_query,
    t_blocking.text                         AS blocking_query
FROM sys.dm_exec_requests r
JOIN sys.dm_exec_sessions s_blocked  ON r.session_id = s_blocked.session_id
JOIN sys.dm_exec_sessions s_blocking ON r.blocking_session_id = s_blocking.session_id
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) t_blocked
CROSS APPLY sys.dm_exec_sql_text(
    (SELECT sql_handle FROM sys.dm_exec_requests
     WHERE session_id = r.blocking_session_id)) t_blocking
WHERE r.blocking_session_id > 0;

-- Connection trend signal
CREATE OR ALTER VIEW autonomous.connection_trend AS
SELECT
    GETDATE()                                                    AS ts,
    COUNT(*)                                                     AS active_sessions,
    SUM(CASE WHEN status = 'running' THEN 1 ELSE 0 END)         AS running,
    SUM(CASE WHEN status = 'sleeping'
             AND open_transaction_count > 0 THEN 1 ELSE 0 END)  AS idle_in_txn,
    SUM(CASE WHEN wait_type LIKE 'LCK%' THEN 1 ELSE 0 END)      AS lock_waiters
FROM sys.dm_exec_sessions
WHERE is_user_process = 1;

The structural requirement for autonomous consumption is that these views must be queryable by a decision engine on a fixed polling interval — typically 15 to 30 seconds — and each row must carry enough information for a rule engine or ML model to classify the situation and select a response action without joining additional tables at decision time.

Signal freshness is non-negotiable. A decision engine that acts on 10-minute-old data in a system experiencing a lock cascade or connection storm will always act too late. The observability pipeline must guarantee that the latency from event occurrence to signal availability does not exceed two polling cycles.

Telemetry Pipeline Architecture: From Database to Decision Engine

Raw signals in database views are the beginning of the observability pipeline, not the end. The autonomous decision engine needs a structured telemetry pipeline that ingests signals, normalizes them, stores them for trend analysis, and exposes them to the reasoning layer. Building this pipeline requires deliberate architectural choices about collection frequency, storage granularity, and the interface between the telemetry store and the decision engine.

The reference architecture pairs a collector agent — a lightweight Python service polling DMVs and extended events, or a Prometheus SQL Server exporter — with a time-series backend (Prometheus, InfluxDB, or Azure Monitor) and a rule engine that subscribes to derived metrics. For SQL Server on Azure, Azure Monitor with custom metrics and Log Analytics workspaces serve the same function, though with higher latency that must be accounted for in decision logic.

# Autonomous telemetry collector — SQL Server
# Runs as a scheduled task or container sidecar every 15 seconds
# Pushes structured signals to the decision engine API

import pyodbc
import requests
import time
from datetime import datetime, timezone
from dataclasses import dataclass, asdict
from typing import Optional

@dataclass
class DatabaseSignalPacket:
    """Structured signal packet consumed by the decision engine."""
    timestamp: str
    instance_id: str
    signal_class: str          # 'state' | 'trend' | 'causal'
    signal_name: str
    value: float
    severity: str              # 'nominal' | 'warning' | 'critical' | 'emergency'
    context: dict              # causal metadata — blocking spids, query hashes, etc.
    suggested_action: Optional[str] = None  # pre-classified by collector

THRESHOLDS = {
    "connection_pct": {"warning": 70, "critical": 85, "emergency": 95},
    "replication_lag_bytes": {"warning": 50_000_000, "critical": 200_000_000, "emergency": 1_000_000_000},
    "blocking_chain_depth": {"warning": 2, "critical": 4, "emergency": 8},
    "sleeping_txn_seconds": {"warning": 60, "critical": 300, "emergency": 900},
}

def classify_severity(signal_name: str, value: float) -> str:
    thresholds = THRESHOLDS.get(signal_name)
    if not thresholds:
        return "nominal"
    if value >= thresholds["emergency"]:
        return "emergency"
    elif value >= thresholds["critical"]:
        return "critical"
    elif value >= thresholds["warning"]:
        return "warning"
    return "nominal"

def collect_signals(conn, instance_id: str, max_user_connections: int) -> list[DatabaseSignalPacket]:
    packets = []
    ts = datetime.now(timezone.utc).isoformat()
    cur = conn.cursor()

    # Connection saturation
    cur.execute("""
        SELECT COUNT(*) FROM sys.dm_exec_connections
    """)
    conn_count = cur.fetchone()[0]
    conn_pct = conn_count * 100.0 / max_user_connections

    cur.execute("""
        SELECT COUNT(*)
        FROM sys.dm_exec_sessions s
        JOIN sys.dm_tran_session_transactions t
          ON s.session_id = t.session_id
        WHERE s.status = 'sleeping'
          AND s.is_user_process = 1
    """)
    sleeping_txn = cur.fetchone()[0]

    cur.execute("""
        WITH chain AS (
            SELECT session_id, blocking_session_id, 1 AS blocking_depth
            FROM sys.dm_exec_requests
            WHERE blocking_session_id > 0
            UNION ALL
            SELECT r.session_id, r.blocking_session_id, c.blocking_depth + 1
            FROM sys.dm_exec_requests r
            JOIN chain c ON r.session_id = c.blocking_session_id
        )
        SELECT MAX(blocking_depth) FROM chain
    """)
    row = cur.fetchone()
    block_depth = row[0] if row and row[0] else 0

    packets.append(DatabaseSignalPacket(
        timestamp=ts,
        instance_id=instance_id,
        signal_class="state",
        signal_name="connection_pct",
        value=float(conn_pct),
        severity=classify_severity("connection_pct", float(conn_pct)),
        context={"sleeping_txn": sleeping_txn, "blocking_chain_depth": block_depth},
        suggested_action="scale_connection_pool" if conn_pct > 85 else None
    ))

    # AG redo queue lag — primary only
    try:
        cur.execute("""
            SELECT ar.replica_server_name,
                   SUM(drs.redo_queue_size) AS redo_lag_bytes
            FROM sys.dm_hadr_database_replica_states drs
            JOIN sys.availability_replicas ar
              ON drs.replica_id = ar.replica_id
            GROUP BY ar.replica_server_name
        """)
        for replica, redo_lag in cur.fetchall():
            if redo_lag is not None:
                packets.append(DatabaseSignalPacket(
                    timestamp=ts,
                    instance_id=instance_id,
                    signal_class="state",
                    signal_name="replication_lag_bytes",
                    value=float(redo_lag),
                    severity=classify_severity("replication_lag_bytes", float(redo_lag)),
                    context={"replica": replica},
                    suggested_action="investigate_replica_throughput" if redo_lag > 200_000_000 else None
                ))
    except pyodbc.Error:
        pass  # not in an AG — skip

    # Sleeping sessions holding open transactions — causal signal
    cur.execute("""
        SELECT TOP 20 s.session_id, s.login_name, s.program_name,
               DATEDIFF(SECOND, t.transaction_begin_time, SYSUTCDATETIME()) AS txn_age_sec,
               SUBSTRING(st.text, 1, 200)
        FROM sys.dm_exec_sessions s
        JOIN sys.dm_tran_session_transactions t
          ON s.session_id = t.session_id
        LEFT JOIN sys.dm_exec_requests r ON s.session_id = r.session_id
        OUTER APPLY sys.dm_exec_sql_text(r.sql_handle) st
        WHERE s.status = 'sleeping'
          AND s.is_user_process = 1
        ORDER BY txn_age_sec DESC
    """)
    for row in cur.fetchall():
        spid, login, app, seconds, sql_text = row
        packets.append(DatabaseSignalPacket(
            timestamp=ts,
            instance_id=instance_id,
            signal_class="causal",
            signal_name="sleeping_txn_seconds",
            value=float(seconds),
            severity=classify_severity("sleeping_txn_seconds", float(seconds)),
            context={"spid": spid, "login": login, "app": app,
                     "sql": (sql_text or "")[:500]},
            suggested_action="kill_sleeping_transaction" if seconds > 120 else None
        ))

    return packets

def push_to_decision_engine(packets: list[DatabaseSignalPacket], endpoint: str):
    payload = [asdict(p) for p in packets]
    response = requests.post(
        f"{endpoint}/api/v1/signals",
        json=payload,
        headers={"Content-Type": "application/json"},
        timeout=5
    )
    response.raise_for_status()

def run_collector(conn_str: str, instance_id: str, decision_engine_url: str,
                 max_user_connections: int, interval_seconds: int = 15):
    conn = pyodbc.connect(conn_str, autocommit=True)
    print(f"[collector] started for instance={instance_id}, interval={interval_seconds}s")

    while True:
        try:
            packets = collect_signals(conn, instance_id, max_user_connections)
            critical = [p for p in packets if p.severity in ("critical", "emergency")]
            push_to_decision_engine(packets, decision_engine_url)
            if critical:
                print(f"[collector] {len(critical)} critical signals pushed at {datetime.now().isoformat()}")
        except pyodbc.Error:
            conn = pyodbc.connect(conn_str, autocommit=True)  # reconnect on connection loss
        except Exception as e:
            print(f"[collector] error: {e}")
        time.sleep(interval_seconds)

This collector runs as a Kubernetes sidecar alongside the database pod. The suggested_action field is pre-populated by the collector based on simple threshold logic, but the decision engine is not obligated to follow it — it cross-references the suggestion against the full signal history, current system load, active maintenance windows, and operator-defined constraint policies before acting.

The telemetry pipeline must handle backpressure gracefully. If the decision engine endpoint is temporarily unavailable, the collector must buffer locally — typically in a SQLite file or local Redis instance — rather than drop signals. Dropping signals during an incident is precisely when the autonomous system most needs complete data.

For Azure-hosted environments, the same collector can additionally publish to Azure Monitor via its REST API or to an Event Hub that the decision engine consumes as a stream, giving the decision engine both the low-latency local path and the durable cloud path.

Distributed Tracing and Query Fingerprinting for Autonomous Root Cause Analysis

State metrics tell the decision engine that something is wrong. Distributed tracing and query fingerprinting tell it what caused the problem and whether a similar pattern has been seen before. This is the layer that transforms an autonomous system from a reactive threshold responder into a system capable of true root-cause-driven remediation.

Query fingerprinting normalizes SQL text by replacing literals with placeholders, producing a stable identifier that survives parameter changes. SQL Server's Query Store does this natively via query_hash and query_plan_hash. The fingerprint becomes the key for correlating current symptoms with historical remediation outcomes — if fingerprint 0x8f3a2c caused a sequential scan storm last Tuesday and the fix was to create an index on (tenant_id, created_at), the decision engine should recognize that fingerprint immediately the next time it surfaces.

-- Query regression detection against stored baselines using Query Store
WITH current_stats AS (
    SELECT
        q.query_id,
        qt.query_sql_text,
        rs.count_executions,
        rs.avg_duration / 1000.0                         AS avg_ms,
        rs.avg_logical_io_reads,
        rs.avg_query_max_used_memory,
        p.plan_id,
        p.query_plan_hash
    FROM sys.query_store_query q
    JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
    JOIN sys.query_store_plan p        ON q.query_id = p.query_id
    JOIN sys.query_store_runtime_stats rs ON p.plan_id = rs.plan_id
    JOIN sys.query_store_runtime_stats_interval rsi
        ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
    WHERE rsi.start_time > DATEADD(MINUTE, -30, GETDATE())
      AND rs.count_executions > 50
),
baseline AS (
    SELECT query_id, baseline_avg_ms, baseline_avg_logical_reads
    FROM autonomous.query_baselines  -- custom table, populated during stable window
)
SELECT
    c.query_id,
    LEFT(c.query_sql_text, 120)                          AS query_sample,
    c.count_executions,
    ROUND(c.avg_ms, 2)                                   AS avg_ms,
    ROUND(b.baseline_avg_ms, 2)                          AS baseline_ms,
    ROUND((c.avg_ms - b.baseline_avg_ms)
        / NULLIF(b.baseline_avg_ms, 0) * 100, 1)         AS pct_regression,
    c.avg_logical_io_reads,
    b.baseline_avg_logical_reads,
    c.plan_id,
    c.query_plan_hash,
    CASE
        WHEN c.avg_ms > b.baseline_avg_ms * 3   THEN 'critical_regression'
        WHEN c.avg_ms > b.baseline_avg_ms * 1.5 THEN 'moderate_regression'
        WHEN c.avg_logical_io_reads >
             b.baseline_avg_logical_reads * 2   THEN 'io_regression'
        ELSE 'nominal'
    END                                                  AS classification
FROM current_stats c
JOIN baseline b ON c.query_id = b.query_id
WHERE c.avg_ms > b.baseline_avg_ms * 1.3
ORDER BY pct_regression DESC;

Beyond query fingerprinting, distributed tracing at the application layer — using OpenTelemetry with a SQL Server instrumented driver — provides the call chain context that database-layer metrics cannot. When the autonomous system sees that a specific microservice (identified by its service name in the trace span) is responsible for 80% of the slow query load, it can route the remediation not at the database level but at the connection pool level: reducing the maximum connections allocated to that service in the application connection pool, or applying a Resource Governor workload group timeout.

This is the architectural distinction between observability for humans and observability for autonomous systems. A human reads the trace and decides what to do. The autonomous system is designed so that the trace span metadata is already structured as an input feature to the decision classifier — service_name, query_fingerprint, p99_latency, error_rate, calls_per_second — and the classifier outputs an action label with a confidence score.

Prometheus, InfluxDB, and the Autonomous Metrics Store

The choice of metrics backend is an architectural decision with significant downstream consequences for the autonomous decision engine. The engine needs to answer questions like: "Has replication lag been increasing monotonically for the past 20 minutes?" and "What was the p99 query latency for fingerprint 0x9a3c during the last three high-traffic windows?" These are time-series range queries, not point-in-time lookups, and the backend must serve them efficiently at sub-second latency because the decision loop runs on a tight cycle.

Prometheus with remote_write to InfluxDB is the standard architecture for autonomous SQL Server deployments at scale. Prometheus scrapes the SQL Server exporter every 15 seconds and handles the collection and alerting layer. InfluxDB stores the long-term history with downsampling tasks that pre-compute the trend metrics the decision engine needs. The alerting layer — Prometheus Alertmanager — serves a different purpose here than in human-operated systems: rather than notifying on-call engineers, it fires webhooks directly to the autonomous decision engine's action API.

# prometheus/rules/autonomous_db.yml
# These rules feed the autonomous decision engine, not human pagers
groups:
  - name: autonomous_sqlserver
    interval: 15s
    rules:
      # Trend rule: AG redo queue increasing monotonically
      - alert: ReplicationLagIncreasing
        expr: |
          deriv(mssql_redo_queue_bytes[5m]) > 0
          AND mssql_redo_queue_bytes > 10000000
        for: 3m
        labels:
          severity: warning
          action_target: decision_engine
        annotations:
          summary: "Redo queue trending upward on {{ $labels.instance }}"
          replica: "{{ $labels.replica_server_name }}"
          current_lag_bytes: "{{ $value }}"
          signal_class: trend

      # State rule: connection saturation
      - alert: ConnectionPoolNearCapacity
        expr: |
          (mssql_connections_user / mssql_config_max_user_connections) * 100 > 85
        for: 1m
        labels:
          severity: critical
          action_target: decision_engine
        annotations:
          summary: "Connection count above 85% on {{ $labels.instance }}"
          signal_class: state

      # Causal rule: sleeping transactions with open tran accumulating
      - alert: SleepingTransactionsAccumulating
        expr: |
          increase(mssql_sleeping_open_transactions_count[5m]) > 5
        for: 2m
        labels:
          severity: warning
          action_target: decision_engine
        annotations:
          summary: "Sleeping sessions with open transactions accumulating on {{ $labels.instance }}"
          signal_class: causal

      # Trend rule: index fragmentation rising above maintenance threshold
      - alert: IndexFragmentationRising
        expr: |
          mssql_index_fragmentation_pct > 30
          AND mssql_index_page_count > 1000
        for: 10m
        labels:
          severity: warning
          action_target: decision_engine
        annotations:
          summary: "Fragmentation above 30% on {{ $labels.instance }}.{{ $labels.index_name }}"
          signal_class: trend

For the metrics store, a downsampling layer is what makes sub-second trend queries feasible. Rather than scanning millions of raw data points, the decision engine reads pre-aggregated five-minute windows:

-- SQL Server: downsampled trend table for the decision engine
-- A SQL Agent job runs this every 5 minutes; the engine reads metrics_5min,
-- never the raw signal store.
CREATE TABLE autonomous.metrics_5min (
    bucket       DATETIME2(0)  NOT NULL,
    instance_id  NVARCHAR(128) NOT NULL,
    signal_name  NVARCHAR(128) NOT NULL,
    avg_value    FLOAT         NOT NULL,
    max_value    FLOAT         NOT NULL,
    min_value    FLOAT         NOT NULL,
    p95_value    FLOAT         NOT NULL,
    sample_count INT           NOT NULL,
    CONSTRAINT PK_metrics_5min PRIMARY KEY (bucket, instance_id, signal_name)
);

-- Downsampling procedure (scheduled every 5 minutes)
CREATE OR ALTER PROCEDURE autonomous.usp_rollup_signals_5min
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @bucket DATETIME2(0) =
        DATEADD(MINUTE, -(DATEPART(MINUTE, SYSUTCDATETIME()) % 5), SYSUTCDATETIME());

    WITH ranked AS (
        SELECT
            instance_id,
            signal_name,
            value,
            PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY value)
                OVER (PARTITION BY instance_id, signal_name) AS p95_value
        FROM autonomous.signal_store
        WHERE ts >= DATEADD(MINUTE, -5, @bucket)
          AND ts < @bucket
    )
    INSERT INTO autonomous.metrics_5min
        (bucket, instance_id, signal_name, avg_value, max_value,
         min_value, p95_value, sample_count)
    SELECT
        @bucket,
        instance_id,
        signal_name,
        AVG(value),
        MAX(value),
        MIN(value),
        MAX(p95_value),
        COUNT(*)
    FROM ranked
    GROUP BY instance_id, signal_name;
END;

The is_trending_up function illustrates the architectural principle: the decision engine must not re-implement statistical reasoning inline every time it needs to answer a trend question. That logic lives in the observability layer and is callable as a function. The decision engine calls autonomous.is_trending_up('prod-sql-01', 'redo_queue_kb') and receives a boolean with supporting evidence. This keeps the decision engine's logic clean and testable.

For Azure-hosted environments, the same architecture uses Azure Monitor Metrics with a custom metrics namespace, supplemented by a local InfluxDB instance for low-latency trend queries that cannot tolerate the latency of a remote Azure Monitor API call in the middle of a decision loop. The DMV polling agent writes to both stores: Azure Monitor for durable long-term history and compliance, and InfluxDB for the sub-second trend queries the autonomous engine needs.

Anomaly Detection: Teaching the System to Recognize Its Own Normal

Threshold-based alerting is insufficient for autonomous systems for a fundamental reason: it cannot distinguish between a metric value that is genuinely anomalous and one that is expected given current context. A connection count of 950 out of 1000 is an emergency at 02:00 on a Tuesday but may be normal during a scheduled end-of-month batch run. An autonomous system that pages itself every month-end will either stop acting on that alert or will thrash through unnecessary remediation steps.

The solution is contextual anomaly detection — building a model of what normal looks like for each signal conditioned on time of day, day of week, and covarying signals (like active batch jobs or deployment flags). The simplest production-viable approach is a seasonal decomposition model per signal per instance, updated incrementally as new data arrives.

# Seasonal anomaly detection for autonomous database observability
# Uses additive decomposition: observed = trend + seasonal + residual
# Residual z-score triggers anomaly classification

import numpy as np
from dataclasses import dataclass
from typing import Optional

@dataclass
class AnomalyResult:
    signal_name: str
    instance_id: str
    observed_value: float
    expected_value: float
    residual_z_score: float
    is_anomaly: bool
    anomaly_direction: Optional[str]   # 'high' | 'low' | None
    context_window: str                # e.g. 'weekday_morning_peak'


class SeasonalAnomalyDetector:
    """
    Lightweight seasonal anomaly detector suitable for embedding
    in the observability pipeline. Maintains per-signal, per-context-window
    running statistics (mean + variance) updated with Welford's online algorithm.
    No external ML library dependency.
    """

    def __init__(self, z_threshold: float = 3.0):
        self.z_threshold = z_threshold
        # Keyed by (instance_id, signal_name, context_window)
        # Value: {'n': int, 'mean': float, 'M2': float}
        self._stats: dict[tuple, dict] = {}

    @staticmethod
    def _context_window(ts_hour: int, ts_weekday: int) -> str:
        """Map timestamp to a context window label."""
        if ts_weekday >= 5:
            period = "weekend"
        elif 7 <= ts_hour < 10:
            period = "morning_peak"
        elif 10 <= ts_hour < 18:
            period = "business_hours"
        elif 18 <= ts_hour < 22:
            period = "evening"
        else:
            period = "overnight"
        day_type = "weekend" if ts_weekday >= 5 else "weekday"
        return f"{day_type}_{period}"

    def _update(self, key: tuple, value: float):
        """Welford's online algorithm for running mean and variance."""
        if key not in self._stats:
            self._stats[key] = {'n': 0, 'mean': 0.0, 'M2': 0.0}
        s = self._stats[key]
        s['n'] += 1
        delta = value - s['mean']
        s['mean'] += delta / s['n']
        delta2 = value - s['mean']
        s['M2'] += delta * delta2

    def _z_score(self, key: tuple, value: float) -> tuple[float, float]:
        """Returns (z_score, expected_value). Returns (0, value) if insufficient data."""
        s = self._stats.get(key)
        if s is None or s['n'] < 30:   # need at least 30 samples per context window
            return 0.0, value
        variance = s['M2'] / (s['n'] - 1)
        stddev = np.sqrt(variance) if variance > 0 else 1e-9
        z = (value - s['mean']) / stddev
        return float(z), float(s['mean'])

    def observe(
        self,
        instance_id: str,
        signal_name: str,
        value: float,
        ts_hour: int,
        ts_weekday: int
    ) -> AnomalyResult:
        window = self._context_window(ts_hour, ts_weekday)
        key = (instance_id, signal_name, window)

        z, expected = self._z_score(key, value)
        self._update(key, value)

        is_anomaly = abs(z) > self.z_threshold
        direction = None
        if is_anomaly:
            direction = "high" if z > 0 else "low"

        return AnomalyResult(
            signal_name=signal_name,
            instance_id=instance_id,
            observed_value=value,
            expected_value=round(expected, 4),
            residual_z_score=round(z, 3),
            is_anomaly=is_anomaly,
            anomaly_direction=direction,
            context_window=window
        )

    def load_state(self, state: dict):
        """Restore detector state from persistent store (e.g. Redis or pickle)."""
        self._stats = {tuple(k.split('|')): v for k, v in state.items()}

    def dump_state(self) -> dict:
        """Serialize state for persistence across collector restarts."""
        return {'|'.join(k): v for k, v in self._stats.items()}

The detector is stateful: it accumulates running statistics per context window and must survive collector restarts without losing its learned baselines. The dump_state / load_state pattern serializes to Redis or a local file, with the decision engine periodically snapshotting the detector state to the autonomous metadata store.

A signal that crosses a static threshold but is not anomalous in its context window is downgraded from critical to informational in the signal packet before it reaches the decision engine. Conversely, a signal that has not crossed any static threshold but has a z-score above 3.0 within its context window is elevated to warning regardless of absolute value. This means the decision engine acts more on deviation from expected behavior than on absolute thresholds — which is precisely the right behavior for a system managing databases with widely varying load profiles.

Observability for Autonomous Actions: Closing the Loop

The most commonly overlooked dimension of autonomous database observability is observing the autonomous system itself. Every action the system takes — terminating a session, adjusting MAXDOP settings, promoting a replica, draining a connection pool — must be recorded with enough context to answer the forensic questions that will inevitably be asked: What triggered that action? What signals did the system see? What was the state before and after? Was the action effective?

This action audit log is not optional. Without it, the autonomous system is a black box that operators cannot trust or improve. Every action taken by the decision engine must be written to a structured audit store before the action is executed.

-- Autonomous action audit store
CREATE TABLE autonomous.action_log (
    action_id        BIGINT IDENTITY(1,1) PRIMARY KEY,
    executed_at      DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    instance_id      NVARCHAR(128)  NOT NULL,
    action_type      NVARCHAR(64)   NOT NULL,
    action_params    NVARCHAR(MAX)  NOT NULL,   -- JSON
    trigger_signals  NVARCHAR(MAX)  NOT NULL,   -- JSON
    pre_state        NVARCHAR(MAX),             -- JSON
    post_state       NVARCHAR(MAX),             -- JSON
    outcome          NVARCHAR(32),
    outcome_detail   NVARCHAR(MAX),
    confidence_score FLOAT,
    operator_review  NVARCHAR(32),
    rollback_sql     NVARCHAR(MAX)
);

CREATE INDEX IX_action_log_instance_time
    ON autonomous.action_log (instance_id, executed_at DESC);
CREATE INDEX IX_action_log_type_time
    ON autonomous.action_log (action_type, executed_at DESC);

The post_state column is populated by a deferred job — typically 60 seconds after the action — that re-runs the same state queries used to populate pre_state and records whether the condition that triggered the action has resolved. This before-and-after comparison is the feedback signal that the decision engine uses to evaluate its own effectiveness over time. If a particular action type consistently produces outcome = 'no_effect' for a particular signal pattern, the decision engine's rule weights for that combination are downgraded.

The rollback_sql column deserves emphasis. For every action that modifies database configuration or session state, the decision engine must generate and store the SQL to reverse that action at the time of execution. This is not primarily for automated rollback — though that is supported — but for operator trust. An engineer investigating an incident must be able to look at the action log, see exactly what the autonomous system did, understand why, and if necessary undo it with a single SQL statement. Autonomous systems that cannot be cleanly overridden by operators will not remain in production.

The action log is also the training data set for improving the decision engine. Periodically — typically weekly — the autonomous system runs a retrospective analysis comparing trigger signals, actions taken, and outcomes. Signal patterns that consistently preceded successful outcomes reinforce the corresponding decision rules. Patterns that preceded no_effect or failed outcomes trigger a review flag in the operator dashboard. Over months of operation, this retrospective loop produces a decision engine that is observably better calibrated to the specific workload patterns of the database it manages.

Key Takeaways

  • → Autonomous observability requires three structurally distinct signal classes — state, trend, and causal — because a decision engine acting on state signals alone will be consistently reactive and late, while trend and causal signals enable preemptive, targeted action before conditions become critical.
  • → The telemetry pipeline must guarantee signal freshness within two polling cycles and handle backpressure by buffering locally rather than dropping signals; data loss during an incident is precisely when the autonomous decision engine is most dependent on a complete and continuous signal stream.
  • → Query fingerprinting paired with stored baselines enables regression detection that survives parameter changes, plan changes, and schema evolution — connecting current query performance anomalies to historical remediation outcomes so the decision engine can recognize recurrent patterns and apply proven fixes rather than re-deriving solutions from scratch.
  • → Contextual anomaly detection using per-signal, per-context-window running statistics separates genuinely anomalous behavior from expected load variations, preventing the decision engine from acting on high absolute values that are normal given the time of day or concurrent batch activity, and ensuring it does respond to subtle deviations that fall below static thresholds but are statistically significant within their context.
  • → Every autonomous action must be written to a structured audit log with pre-state, post-state, trigger signals, confidence score, and rollback SQL before execution; this log is simultaneously the trust mechanism for operators, the safety net for overrides, and the training dataset that closes the feedback loop enabling the decision engine to improve its calibration over time.
