Chapter 25: AI-Driven Change Management

Autonomous systems that can observe and decide are only as valuable as their ability to act — and acting on a production database system means managing change. Change management has historically been the domain of human judgment, CAB meetings, deployment windows, and rollback plans drafted at midnight. At the ADE level, the goal is to replace that human-in-the-loop bottleneck with a system that classifies risk, selects strategy, executes with precision, and rolls back autonomously when signals deteriorate. This chapter covers the full architecture: how an autonomous change management system ingests proposed changes, scores their risk against live telemetry, selects an execution strategy, instruments the rollout, and either completes or self-heals — without paging anyone at 2 AM.

---

Risk Scoring Engines: Classifying Change Before Execution

Every autonomous change pipeline begins with a classification gate. Before a DDL statement, configuration push, or schema migration touches a production instance, it must pass through a risk scoring engine that combines static analysis of the change itself with dynamic analysis of the current system state.

Static analysis examines the change in isolation. A CREATE INDEX CONCURRENTLY on a 50-million-row table is categorically different from the same operation on a 50-thousand-row table. An ALTER TABLE ... ADD COLUMN DEFAULT in PostgreSQL 11+ is trivially safe; the same statement on PostgreSQL 10 rewrites the table. A SQL Server ALTER TABLE ... ALTER COLUMN on a column with dependent indexed views is a blocking operation regardless of row count. The static analyzer must know these rules and apply them without human instruction.

Dynamic analysis examines what the system is doing right now. A change that scores "medium risk" at 3 AM may score "critical risk" at 2 PM when the instance is processing 40,000 transactions per second with 85% buffer cache utilization. The scoring engine must pull live metrics at decision time, not at submission time.

-- Equivalent live risk context for SQL Server change scoring
CREATE OR ALTER VIEW autonomous_change.live_risk_context AS
SELECT
    (SELECT COUNT(*) FROM sys.dm_exec_requests WHERE blocking_session_id <> 0) AS active_blocked_sessions,
    (SELECT COUNT(*) FROM sys.dm_exec_sessions WHERE is_user_process = 1) AS active_connections,
    (SELECT CAST(cntr_value AS FLOAT)
     FROM sys.dm_os_performance_counters
     WHERE counter_name = 'Buffer cache hit ratio'
       AND object_name LIKE '%Buffer Manager%') AS buffer_cache_hit_ratio,
    (SELECT MAX(DATEDIFF(SECOND, transaction_begin_time, GETDATE()))
     FROM sys.dm_tran_active_transactions
     WHERE transaction_type = 1) AS oldest_txn_seconds,
    (SELECT MAX(secondary_lag_seconds)
     FROM sys.dm_hadr_database_replica_states
     WHERE is_local = 0) AS max_replica_lag_seconds,
    (SELECT COUNT(*) FROM sys.dm_exec_requests WHERE wait_type LIKE 'LCK%') AS lock_wait_count;

The scoring engine combines static weights with dynamic multipliers. A Python-based scorer might represent this as:

import psycopg2
import json
from dataclasses import dataclass
from enum import Enum
from typing import Optional

class RiskTier(Enum):
    LOW = "low"
    MEDIUM = "medium"
    HIGH = "high"
    CRITICAL = "critical"

@dataclass
class ChangeProposal:
    change_id: str
    change_type: str          # ddl, config, data_migration, index
    target_table: str
    estimated_row_count: int
    statement: str
    requires_lock: bool
    lock_level: str           # row, page, table, exclusive

def score_change_risk(proposal: ChangeProposal, db_conn) -> dict:
    # Static base score
    static_score = 0
    
    static_rules = {
        ("ddl", "exclusive"): 40,
        ("ddl", "table"): 30,
        ("index", "table"): 20,
        ("index", "row"): 5,
        ("config", "none"): 10,
        ("data_migration", "row"): 15,
    }
    static_score += static_rules.get((proposal.change_type, proposal.lock_level), 10)
    
    # Row count multiplier
    if proposal.estimated_row_count > 100_000_000:
        static_score *= 2.5
    elif proposal.estimated_row_count > 10_000_000:
        static_score *= 1.8
    elif proposal.estimated_row_count > 1_000_000:
        static_score *= 1.3
    
    # Dynamic context multipliers
    with db_conn.cursor() as cur:
        cur.execute("SELECT * FROM autonomous_change.live_risk_context")
        row = cur.fetchone()
        cols = [desc[0] for desc in cur.description]
        context = dict(zip(cols, row))
    
    dynamic_multiplier = 1.0
    
    if context["active_lock_waiters"] > 5:
        dynamic_multiplier += 0.4
    if context["buffer_cache_hit_ratio"] and context["buffer_cache_hit_ratio"] < 0.90:
        dynamic_multiplier += 0.3
    if context["oldest_txn_seconds"] and context["oldest_txn_seconds"] > 30:
        dynamic_multiplier += 0.5
    if context["max_replica_lag_bytes"] and context["max_replica_lag_bytes"] > 50_000_000:
        dynamic_multiplier += 0.6
    if context["inactive_repl_slots"] and context["inactive_repl_slots"] > 0:
        dynamic_multiplier += 0.8  # Inactive slots mean WAL accumulation risk
    
    final_score = static_score * dynamic_multiplier
    
    if final_score < 20:
        tier = RiskTier.LOW
    elif final_score < 45:
        tier = RiskTier.MEDIUM
    elif final_score < 75:
        tier = RiskTier.HIGH
    else:
        tier = RiskTier.CRITICAL
    
    return {
        "change_id": proposal.change_id,
        "static_score": static_score,
        "dynamic_multiplier": dynamic_multiplier,
        "final_score": final_score,
        "risk_tier": tier.value,
        "context_snapshot": context,
        "autonomous_action": _select_autonomous_action(tier, context)
    }

def _select_autonomous_action(tier: RiskTier, context: dict) -> str:
    if tier == RiskTier.LOW:
        return "execute_immediately"
    elif tier == RiskTier.MEDIUM:
        return "execute_with_monitoring"
    elif tier == RiskTier.HIGH:
        return "defer_to_maintenance_window"
    else:  # CRITICAL
        if context.get("active_lock_waiters", 0) > 10:
            return "block_and_escalate"
        return "block_and_defer_72h"

This scoring system is the gatekeeper. Every change proposal — whether generated by a CI/CD pipeline, a human DBA via a migration tool, or by the autonomous system itself as part of an optimization cycle — passes through this gate before touching production.

Autonomous Migration Execution: Online Schema Changes Without Human Oversight

Once a change clears the risk gate at an acceptable tier, the execution layer takes over. The most dangerous class of database change is DDL on large tables, and the autonomous execution layer must have first-class support for online schema change strategies — not as a fallback, but as the default path.

For PostgreSQL, the primary tools are pg_repack for table rewrites and CREATE INDEX CONCURRENTLY for index operations. Both can run without holding an exclusive lock for the full duration, but both require careful orchestration. CREATE INDEX CONCURRENTLY can fail partway through, leaving an invalid index that must be detected and cleaned up. pg_repack requires the pgstattuple extension and sufficient disk space.

For SQL Server, online index operations (WITH (ONLINE = ON)) and online column operations (WITH (ONLINE = ON) in SQL Server 2017+) serve similar purposes. The SQL Server Agent or an external orchestrator manages the execution, with Always On Availability Group lag monitoring integrated into the execution loop.

The autonomous execution controller wraps these operations in an instrumented harness:

    @snapshot NVARCHAR(MAX) OUTPUT
AS
BEGIN
    SET NOCOUNT ON;
    SELECT @snapshot = (
        SELECT
            SYSDATETIMEOFFSET() AS timestamp,
            (SELECT SUM(cntr_value) FROM sys.dm_os_performance_counters
             WHERE counter_name = 'Batch Requests/sec') AS batch_requests_sec,
            (SELECT COUNT(*) FROM sys.dm_exec_sessions WHERE is_user_process = 1) AS active_connections,
            (SELECT MAX(secondary_lag_seconds) FROM sys.dm_hadr_database_replica_states WHERE is_local = 0) AS max_ag_lag_seconds,

        FOR JSON PATH, WITHOUT_ARRAY_WRAPPER
    );
END;

The execution harness runs the change inside a monitoring loop. Every 10 seconds during a long-running operation, it samples progress, checks replica lag, checks for lock accumulation, and compares against pre-execution baselines. If any metric degrades beyond a configured threshold, the operation is aborted and the abort reason is logged.

For batched data migrations — moving data in chunks, backfilling columns, or archiving records — the autonomous executor uses a self-throttling loop that adjusts batch size based on observed write latency:

import time
import psycopg2
from typing import Callable

def autonomous_batched_migration(
    conn_string: str,
    batch_query: str,          # Must accept %(batch_size)s and %(last_id)s
    count_query: str,
    max_lag_bytes: int = 100_000_000,
    target_batch_duration_ms: int = 500,
    initial_batch_size: int = 1000,
    max_batch_size: int = 50_000,
    min_batch_size: int = 100,
    execution_id: str = None
):
    """
    Self-throttling batched migration executor.
    Adjusts batch size dynamically based on actual execution duration
    and replica lag, ensuring the migration stays within safe thresholds.
    """
    conn = psycopg2.connect(conn_string)
    conn.autocommit = True
    
    batch_size = initial_batch_size
    last_id = 0
    total_rows = 0
    consecutive_lag_violations = 0
    
    with conn.cursor() as cur:
        cur.execute(count_query)
        total_estimated = cur.fetchone()[0]
    
    print(f"[{execution_id}] Starting migration. Estimated rows: {total_estimated}")
    
    while True:
        # Check replica lag before each batch
        with conn.cursor() as cur:
            cur.execute("""
                SELECT COALESCE(max(pg_wal_lsn_diff(sent_lsn, replay_lsn)), 0)
                FROM pg_stat_replication
            """)
            current_lag = cur.fetchone()[0]
        
        if current_lag > max_lag_bytes:
            consecutive_lag_violations += 1
            wait_seconds = min(2 ** consecutive_lag_violations, 60)
            print(f"[{execution_id}] Replica lag {current_lag:,} bytes exceeds threshold. "
                  f"Backing off {wait_seconds}s (violation #{consecutive_lag_violations})")
            time.sleep(wait_seconds)
            # Shrink batch size aggressively when lag builds
            batch_size = max(min_batch_size, batch_size // 2)
            continue
        else:
            consecutive_lag_violations = 0
        
        # Execute batch and measure duration
        batch_start = time.monotonic()
        with conn.cursor() as cur:
            cur.execute(batch_query, {"batch_size": batch_size, "last_id": last_id})
            rows_processed = cur.rowcount
        batch_duration_ms = (time.monotonic() - batch_start) * 1000
        
        if rows_processed == 0:
            print(f"[{execution_id}] Migration complete. Total rows processed: {total_rows}")
            break
        
        total_rows += rows_processed
        last_id += rows_processed  # Assumes sequential ID or adjust per schema
        
        # Self-tuning batch size based on duration feedback
        if batch_duration_ms > 0:
            adjustment_ratio = target_batch_duration_ms / batch_duration_ms
            new_batch_size = int(batch_size * adjustment_ratio)
            batch_size = max(min_batch_size, min(max_batch_size, new_batch_size))
        
        progress_pct = round(total_rows / total_estimated * 100, 1) if total_estimated > 0 else 0
        print(f"[{execution_id}] Batch complete: {rows_processed} rows in {batch_duration_ms:.0f}ms. "
              f"New batch size: {batch_size}. Progress: {progress_pct}%")
        
        # Brief yield between batches to reduce contention
        time.sleep(0.05)
    
    conn.close()

This pattern means that a 500-million-row backfill migration runs without any human watching it. If the replica falls behind, the system slows down. If the replica catches up and the database is underloaded, the system speeds up. The batch size converges on the fastest rate that keeps lag within bounds.

AI-Assisted Change Plan Generation: From Intent to Executable Strategy

Risk scoring and execution harnesses handle the mechanics. But in a fully autonomous system, the change plan itself should not always originate from a human writing SQL. The system needs the ability to translate high-level intents — "this query is slow because it lacks an appropriate index" or "this table is bloated by 60% and needs a repack" — into concrete, sequenced, risk-scored change plans.

This is where large language model integration moves from a developer convenience into production infrastructure. The autonomous optimizer identifies a problem, describes it in structured natural language, and queries an LLM API to generate a candidate change plan. That plan is then parsed, statically analyzed by the risk scorer, and submitted through the same execution pipeline as any human-authored migration.

The integration requires strict guardrails. The LLM output is never executed directly. Every generated statement is passed through a SQL parser, validated against schema, compared against a catalog of known-dangerous patterns, and scored. Only then does it enter the execution queue.

import openai
import sqlglot
import re
from typing import Optional

DANGEROUS_PATTERNS = [
    r'\bDROP\s+TABLE\b',
    r'\bTRUNCATE\b',
    r'\bDELETE\s+FROM\b(?!.*\bWHERE\b)',  # DELETE without WHERE
    r'\bUPDATE\b(?!.*\bWHERE\b)',          # UPDATE without WHERE
    r'\bDROP\s+DATABASE\b',
    r'\bDROP\s+SCHEMA\b',
]

def generate_change_plan_from_intent(
    intent: str,
    schema_context: str,
    db_platform: str,  # "postgresql" or "sqlserver"
    model: str = "gpt-4o"
) -> Optional[dict]:
    """
    Generates a structured change plan from a natural-language optimization intent.
    Output is a JSON object with statements, sequencing, and reversibility metadata.
    All output is validated before entering the execution pipeline.
    """
    
    system_prompt = f"""You are a database change plan generator for {db_platform}.
    
    Given an optimization intent and schema context, produce a JSON change plan with this exact structure:
    {{
      "intent_summary": "...",
      "statements": [
        {{
          "sequence": 1,
          "statement": "...",
          "change_type": "ddl|index|config|data_migration",
          "lock_level": "none|row|page|table|exclusive",
          "reversible": true|false,
          "reversal_statement": "..." or null,
          "online_safe": true|false,
          "estimated_duration_hint": "seconds|minutes|hours"
        }}
      ],
      "requires_maintenance_window": true|false,
      "dependencies": []
    }}
    
    Rules:
    - Prefer CONCURRENT or ONLINE operations wherever the platform supports them
    - Always include reversal_statement for DDL that has a clean inverse
    - Never generate DROP TABLE, TRUNCATE, or DELETE without WHERE
    - For {db_platform}, use correct syntax precisely
    - Output ONLY valid JSON, no explanation text"""
    
    response = openai.chat.completions.create(
        model=model,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": f"Intent: {intent}\n\nSchema context:\n{schema_context}"}
        ],
        temperature=0.1,  # Low temperature for deterministic, precise SQL output
        response_format={"type": "json_object"}
    )
    
    raw_plan = response.choices[0].message.content
    
    try:
        import json
        plan = json.loads(raw_plan)
    except json.JSONDecodeError as e:
        print(f"LLM returned unparseable JSON: {e}")
        return None
    
    # Validate every statement before returning
    validated_statements = []
    for stmt_obj in plan.get("statements", []):
        statement = stmt_obj.get("statement", "")
        
        # Pattern-based safety check
        for pattern in DANGEROUS_PATTERNS:
            if re.search(pattern, statement, re.IGNORECASE):
                print(f"BLOCKED: Dangerous pattern detected in generated statement: {statement[:100]}")
                return None
        
        # Syntax validation via sqlglot
        try:
            dialect = "postgres" if db_platform == "postgresql" else "tsql"
            parsed = sqlglot.parse(statement, dialect=dialect)
            if not parsed:
                print(f"BLOCKED: Statement failed SQL parsing: {statement[:100]}")
                return None
        except sqlglot.errors.ParseError as e:
            print(f"BLOCKED: SQL parse error in generated statement: {e}")
            return None
        
        validated_statements.append(stmt_obj)
    
    plan["statements"] = validated_statements
    plan["generated_by"] = "llm"
    plan["validated"] = True
    
    return plan

The schema context passed to this function is not a raw dump of all DDL. It is a curated, minimal representation: the target table's column definitions, existing indexes, approximate row count, and the specific query or metric that triggered the optimization intent. Sending a full schema dump to an LLM API is both expensive and produces worse results than targeted context.

Rollback Orchestration: Autonomous Recovery When Deployments Go Wrong

A change management system without autonomous rollback is not autonomous — it is merely automated. The difference is consequential. Automation runs a script. Autonomy decides when the script has produced a bad outcome and reverses it without being told to.

Autonomous rollback requires three things: a pre-execution baseline, continuous signal monitoring during execution, and a reversibility map that knows how to undo every change type the system can apply.

Some changes are trivially reversible: creating an index can be reversed by dropping it; adding a column with a default can be reversed by dropping the column; changing a configuration parameter can be reversed by restoring the previous value. Other changes are not reversible in-place: once a table rewrite via pg_repack completes, there is no "un-repack." For those, the rollback strategy is not reversal but rather pre-execution snapshot validation — ensuring a point-in-time restore target exists before the operation begins.

CREATE TABLE autonomous_change.rollback_registry (

    PRIMARY KEY (change_type, lock_level)
);

    tps_baseline             DECIMAL(18,2),
    p99_latency_ms           DECIMAL(18,2),

The rollback decision engine runs as a background monitor during every active execution. It samples current metrics on a short interval and compares them against the baseline using configurable degradation thresholds:

import time
import psycopg2
from dataclasses import dataclass
from typing import Optional

@dataclass
class RollbackSignal:
    triggered: bool
    reason: str
    severity: str   # warning, abort
    metric_name: str
    baseline_value: float
    current_value: float
    threshold_pct: float

def evaluate_rollback_signals(
    execution_id: str,
    conn_string: str,
    thresholds: dict = None
) -> Optional[RollbackSignal]:
    """
    Compares current system metrics against pre-execution baseline.
    Returns a RollbackSignal if any metric has degraded beyond threshold.
    """
    if thresholds is None:
        thresholds = {
            "tps_drop_pct": 30.0,           # Abort if TPS drops more than 30%
            "p99_latency_increase_pct": 50.0, # Abort if P99 latency grows more than 50%
            "cache_hit_ratio_drop_pct": 5.0,  # Abort if cache hit ratio falls more than 5 points
            "replication_lag_bytes_max": 200_000_000,  # Abort if lag exceeds 200MB
            "error_rate_multiplier": 3.0,     # Abort if error rate triples
        }

    conn = psycopg2.connect(conn_string)
    try:
        with conn.cursor() as cur:
            # Fetch baseline
            cur.execute("""
                SELECT tps_baseline, p99_latency_ms, error_rate_per_min,
                       cache_hit_ratio, replication_lag_bytes
                FROM autonomous_change.execution_baselines
                WHERE execution_id = %s
            """, (execution_id,))
            baseline_row = cur.fetchone()
            if not baseline_row:
                return None
            tps_base, p99_base, err_base, cache_base, lag_base = baseline_row

            # Sample current metrics
            cur.execute("""
                SELECT
                    (SELECT sum(xact_commit + xact_rollback)
                     FROM pg_stat_database WHERE datname = current_database()) AS current_tps,
                    (SELECT round((sum(blks_hit)::numeric /
                     nullif(sum(blks_hit) + sum(blks_read), 0)) * 100, 2)
                     FROM pg_stat_database) AS current_cache_hit,
                    (SELECT COALESCE(max(pg_wal_lsn_diff(sent_lsn, replay_lsn)), 0)
                     FROM pg_stat_replication) AS current_lag
            """)
            current = cur.fetchone()
            current_tps, current_cache, current_lag = current

        # Evaluate each signal
        if tps_base and tps_base > 0 and current_tps is not None:
            drop_pct = ((tps_base - current_tps) / tps_base) * 100
            if drop_pct > thresholds["tps_drop_pct"]:
                return RollbackSignal(
                    triggered=True,
                    reason=f"TPS dropped {drop_pct:.1f}% from baseline ({tps_base:.0f} → {current_tps:.0f})",
                    severity="abort",
                    metric_name="tps",
                    baseline_value=float(tps_base),
                    current_value=float(current_tps),
                    threshold_pct=thresholds["tps_drop_pct"]
                )

        if current_lag is not None and current_lag > thresholds["replication_lag_bytes_max"]:
            return RollbackSignal(
                triggered=True,
                reason=f"Replica lag {current_lag:,} bytes exceeds abort threshold",
                severity="abort",
                metric_name="replication_lag_bytes",
                baseline_value=float(lag_base or 0),
                current_value=float(current_lag),
                threshold_pct=0.0
            )

        if cache_base and current_cache is not None:
            cache_drop = float(cache_base) - float(current_cache)
            if cache_drop > thresholds["cache_hit_ratio_drop_pct"]:
                return RollbackSignal(
                    triggered=True,
                    reason=f"Buffer cache hit ratio dropped {cache_drop:.1f} points from baseline",
                    severity="abort",
                    metric_name="cache_hit_ratio",
                    baseline_value=float(cache_base),
                    current_value=float(current_cache),
                    threshold_pct=thresholds["cache_hit_ratio_drop_pct"]
                )

        return None  # No rollback signal triggered

    finally:
        conn.close()


def execute_rollback(
    execution_id: str,
    reversal_statement: str,
    conn_string: str,
    signal: RollbackSignal
) -> bool:
    """
    Executes the reversal statement for a triggered rollback signal,
    updates the execution log, and emits a structured audit record.
    """
    conn = psycopg2.connect(conn_string)
    conn.autocommit = True
    try:
        with conn.cursor() as cur:
            # Execute the reversal
            cur.execute(reversal_statement)

            # Update execution log
            cur.execute("""
                UPDATE autonomous_change.execution_log
                SET status = 'rolled_back',
                    completed_at = now(),
                    abort_reason = %s
                WHERE execution_id = %s
            """, (signal.reason, execution_id))

        print(f"[ROLLBACK] execution_id={execution_id} | reason={signal.reason} | "
              f"metric={signal.metric_name} | "
              f"baseline={signal.baseline_value} | current={signal.current_value}")
        return True

    except Exception as e:
        print(f"[ROLLBACK FAILED] execution_id={execution_id} | error={e}")
        return False
    finally:
        conn.close()

The monitoring loop that drives this engine runs at the orchestrator level, calling evaluate_rollback_signals every few seconds for any in-flight execution. The moment a signal is returned, the loop calls execute_rollback with the pre-stored reversal statement. For operations with no clean reversal — such as a completed table repack — the abort path instead halts any remaining follow-on steps and flags the execution for human review, since the principal change cannot be undone by SQL alone.

Canary Deployment Patterns for Schema Changes

Not all schema changes are single-shot. In distributed application environments where application code and database schema evolve together, the autonomous change system must support the database side of a canary deployment — where a schema change is applied in a way that remains backward-compatible with both the current and next version of the application simultaneously.

This is the expand-contract (also called parallel change) pattern formalized into the execution engine. Rather than applying a breaking schema change in one step, the autonomous system sequences it across three phases:

Phase 1 – Expand: Add new structures (columns, tables, indexes) without removing or altering existing ones. The old application version continues to function; the new version can begin writing to the new structures.

Phase 2 – Migrate: Backfill existing data into the new structures using the self-throttling batched executor. Both application versions operate concurrently during this phase.

Phase 3 – Contract: Once the canary application deployment has stabilized and telemetry confirms correctness, remove the old structures.

graph LR

    G3 -->|failed| RB3[Rollback phase 3]

*Expand-contract turns one breaking change into three reversible steps, each gated on live telemetry rather than a fixed calendar slot — the contract phase gets the tightest thresholds because it's the hardest to undo.*

The autonomous system tracks canary deployments as multi-phase change plans with explicit phase gates:

The canary phase gate runs on a schedule — every five minutes once a phase has been active for the minimum observation window. If the gate returns passed, the orchestrator advances to the next phase automatically. If it returns failed, the system executes the rollback plan for the current phase and emits an alert. The contract phase is held to a stricter standard than the expand phase: removing old columns or tables is harder to reverse than adding new ones, so the gate thresholds for Phase 3 are intentionally tighter.

Integrating with CI/CD Pipelines: The Autonomous Change API

For the autonomous change management system to function at scale, it cannot operate as a standalone silo. It must integrate with the same CI/CD pipelines that development teams already use. The integration point is a change submission API that accepts a migration from a deployment pipeline — a Flyway migration file, a Django migration, a Liquibase changeset — scores it, and either approves it for autonomous execution or returns a structured rejection with the exact reason.

The API contract is simple but consequential: any change that returns approved will be executed by the autonomous system with no further human confirmation. Any change that returns deferred or blocked is held in queue or returned to the submitter with a reasoning payload. This means the API must be trustworthy enough that teams are willing to submit migrations to it rather than running them manually.

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
from typing import Optional, List
import uuid

app = FastAPI(title="Autonomous Change Management API")

class MigrationSubmission(BaseModel):
    pipeline_id: str
    change_type: str
    target_schema: str
    target_table: Optional[str]
    statements: List[str]
    estimated_row_count: Optional[int] = 0
    requires_lock: bool = False
    lock_level: str = "row"
    submitter: str
    urgency: str = "normal"  # normal, urgent, maintenance_only

class ChangeDecision(BaseModel):
    submission_id: str
    decision: str        # approved, deferred, blocked
    risk_tier: str
    risk_score: float
    scheduled_for: Optional[str]
    rejection_reasons: List[str]
    execution_strategy: str

@app.post("/v1/changes/submit", response_model=ChangeDecision)
async def submit_change(submission: MigrationSubmission):
    submission_id = str(uuid.uuid4())
    rejection_reasons = []

    # Build ChangeProposal from submission
    proposal = ChangeProposal(
        change_id=submission_id,
        change_type=submission.change_type,
        target_table=submission.target_table or "",
        estimated_row_count=submission.estimated_row_count or 0,
        statement="\n".join(submission.statements),
        requires_lock=submission.requires_lock,
        lock_level=submission.lock_level
    )

    # Score against live system state
    db_conn = get_db_connection()  # connection pool, not shown
    score_result = score_change_risk(proposal, db_conn)
    risk_tier = score_result["risk_tier"]
    autonomous_action = score_result["autonomous_action"]

    # Map action to decision
    if autonomous_action == "execute_immediately":
        decision = "approved"
        execution_strategy = "immediate"
        scheduled_for = "now"
    elif autonomous_action == "execute_with_monitoring":
        decision = "approved"
        execution_strategy = "monitored"
        scheduled_for = "now"
    elif autonomous_action == "defer_to_maintenance_window":
        if submission.urgency == "urgent":
            decision = "approved"
            execution_strategy = "monitored_urgent"
            scheduled_for = "now"
        else:
            decision = "deferred"
            execution_strategy = "maintenance_window"
            scheduled_for = next_maintenance_window()
            rejection_reasons.append(
                f"Risk score {score_result['final_score']:.1f} requires maintenance window execution"
            )
    else:  # block_and_escalate / block_and_defer_72h
        decision = "blocked"
        execution_strategy = "none"
        scheduled_for = None
        rejection_reasons.append(
            f"Risk tier CRITICAL: {score_result['autonomous_action']}"
        )
        rejection_reasons.append(
            f"Dynamic risk multiplier: {score_result['dynamic_multiplier']:.2f}x "
            f"(live system conditions are unfavorable)"
        )

    return ChangeDecision(
        submission_id=submission_id,
        decision=decision,
        risk_tier=risk_tier,
        risk_score=score_result["final_score"],
        scheduled_for=scheduled_for,
        rejection_reasons=rejection_reasons,
        execution_strategy=execution_strategy
    )

Teams configure their CI/CD pipelines to call this endpoint before any migration step. A blocked response fails the pipeline stage with a structured error that includes the exact metrics that caused the block — making it trivially clear whether the issue is the change itself (static risk) or the current system state (dynamic risk). If it is the current system state, the same migration may be resubmitted an hour later and receive an approved decision.

This feedback loop is itself an educational mechanism. Engineers learn quickly which change patterns trigger which risk tiers, and over time they author migrations that are less likely to conflict with production conditions — writing CREATE INDEX CONCURRENTLY rather than CREATE INDEX, partitioning large deletes into batches, and including reversal statements as standard practice.

Key Takeaways

  • → **Risk scoring must be both static and dynamic.** A change's inherent danger — derived from its type, lock level, and affected row count — is only half the picture. The live system state at execution time determines the final risk tier and the appropriate autonomous action, and those two inputs must be combined at decision time, not at submission time.
  • → **Online and concurrent execution strategies are not optional for autonomous systems.** When no human is watching, a blocking DDL operation that escalates lock contention has no one to cancel it. The autonomous execution layer must default to `CONCURRENT`, `ONLINE`, or batched strategies for every operation class that supports them, treating blocking operations as a last resort reserved for explicit maintenance windows.
  • → **LLM-generated change plans require deterministic validation gates before execution.** Language model output is generative and can contain syntactically valid but semantically dangerous SQL. Every generated statement must pass pattern-based safety checks, a SQL parser, and the same risk scoring pipeline as any human-authored migration before it is eligible for execution.
  • → **Autonomous rollback requires pre-execution baselines, not just post-execution comparisons.** Without capturing TPS, latency, cache hit ratio, and replica lag immediately before a change begins, the system has no meaningful reference point against which to evaluate degradation. A rollback signal is only as reliable as the baseline it compares against.
  • → **The expand-contract pattern and canary phase gates make schema changes safe to automate fully.** By breaking breaking changes into backward-compatible phases with automated telemetry gates between them, the autonomous system can advance — or retreat — through a schema migration without any human decision point, while maintaining compatibility with both old and new application versions throughout the entire deployment window.
