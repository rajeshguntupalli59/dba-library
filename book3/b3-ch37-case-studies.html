Chapter 37: Real-World Autonomous DBA Case Studies

The gap between autonomous database theory and production reality is where most platform engineering teams lose momentum. Architectural patterns that look elegant in whiteboards collapse against the friction of legacy schemas, bursty traffic, compliance requirements, and on-call engineers who override automation at the first sign of unfamiliarity. This chapter closes that gap by examining five real-world autonomous DBA deployments — drawn from high-scale SaaS platforms, financial institutions, healthcare data pipelines, and multi-cloud e-commerce systems — each built on PostgreSQL, SQL Server, or both. Every case study follows the same structure: the operational problem, the autonomous architecture chosen, the specific tooling and decision logic wired together, and the lessons that only surface in production. These are not success stories scrubbed clean for a conference talk. They include rollbacks, missed thresholds, and architectural pivots that led to better designs.

---

Case Study 1: Autonomous Failover and Connection Rerouting at a High-Frequency Trading Firm

A mid-sized proprietary trading firm running PostgreSQL 15 on bare metal needed sub-30-second failover with zero manual intervention. Their previous setup used Patroni with a manual promotion script triggered by on-call engineers — a process that averaged 4.5 minutes from detection to connection rerouting due to human latency and shift handoff ambiguity. The requirement from the trading desk: automated failover with automatic client rerouting in under 25 seconds, with a hard constraint that no transaction could be silently lost.

The architecture replaced manual triggers with a fully autonomous stack. Patroni remained the cluster manager, backed by etcd for distributed consensus. The critical addition was a custom Python daemon called trade-sentinel that consumed Patroni's REST API, pg_stat_replication, and a business-level heartbeat table written by the trading application. HAProxy sat in front of all database connections, with its backend configuration dynamically rewritten by trade-sentinel whenever Patroni reported a leader change.

The decision logic was explicit and layered:

1. Detection: If the Patroni leader endpoint returns HTTP 503 for three consecutive 2-second polls, or if the heartbeat table (trading.heartbeat) has not been updated within 8 seconds, enter failover evaluation mode.

2. Validation: Confirm the standby's replication lag is under 512KB and that etcd quorum is healthy. If either condition fails, escalate to PagerDuty and hold without promoting.

3. Promotion: Issue patronictl switchover via REST with --force, capture the new leader hostname, and rewrite HAProxy's backend stanza.

4. Connection rerouting: Reload HAProxy without dropping existing long-lived connections using haproxy -sf $(cat /var/run/haproxy.pid).

5. Verification: Run a synthetic write/read probe transaction against the new primary. If it fails within 10 seconds, re-escalate to human.

The trade-sentinel daemon managed promotion and HAProxy rewrite atomically:

import requests
import subprocess
import time
import logging
from datetime import datetime, timezone

PATRONI_API = "http://localhost:8008"
HAPROXY_CFG = "/etc/haproxy/haproxy.cfg"
HAPROXY_PID = "/var/run/haproxy.pid"
HEARTBEAT_THRESHOLD_SECONDS = 8
POLL_INTERVAL = 2
FAILURE_THRESHOLD = 3

logger = logging.getLogger("trade-sentinel")

def get_patroni_leader() -> str | None:
    try:
        resp = requests.get(f"{PATRONI_API}/master", timeout=3)
        if resp.status_code == 200:
            return resp.json().get("host")
    except requests.RequestException:
        return None
    return None

def trigger_patroni_switchover(candidate: str) -> bool:
    payload = {"leader": candidate, "force": True}
    try:
        resp = requests.post(
            f"{PATRONI_API}/switchover",
            json=payload,
            timeout=15
        )
        return resp.status_code == 200
    except requests.RequestException as e:
        logger.error(f"Switchover API call failed: {e}")
        return False

def rewrite_haproxy_backend(new_primary_host: str) -> None:
    with open(HAPROXY_CFG, "r") as f:
        cfg = f.read()
    # Replace the primary backend server line
    import re
    cfg = re.sub(
        r"(server primary\s+)\S+(:5432)",
        rf"\g<1>{new_primary_host}\g<2>",
        cfg
    )
    with open(HAPROXY_CFG, "w") as f:
        f.write(cfg)
    with open(HAPROXY_PID, "r") as f:
        old_pid = f.read().strip()
    subprocess.run(
        ["haproxy", "-f", HAPROXY_CFG, "-sf", old_pid],
        check=True
    )
    logger.info(f"HAProxy reloaded with new primary: {new_primary_host}")

def run_sentinel():
    consecutive_failures = 0
    while True:
        leader = get_patroni_leader()
        if leader is None:
            consecutive_failures += 1
            logger.warning(
                f"Patroni leader unreachable — failure count: {consecutive_failures}"
            )
        else:
            consecutive_failures = 0

        if consecutive_failures >= FAILURE_THRESHOLD:
            logger.critical("Threshold exceeded — initiating autonomous failover")
            # In production: query etcd for best replica before choosing candidate
            success = trigger_patroni_switchover("replica-01")
            if success:
                time.sleep(5)
                new_leader = get_patroni_leader()
                if new_leader:
                    rewrite_haproxy_backend(new_leader)
                else:
                    logger.error("Failover succeeded but new leader undetectable — escalating")
            consecutive_failures = 0
        time.sleep(POLL_INTERVAL)

if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO)
    run_sentinel()

The first production failover completed in 18.4 seconds. The second, triggered six weeks later by a kernel panic on the primary host, completed in 21.1 seconds — within specification despite higher system load. The lessons were two-fold: the heartbeat table proved far more reliable as a detection signal than Patroni's own API, which exhibited a 3–4 second delay in reporting leader loss during network partitions; and HAProxy's graceful reload was safe only because the trading application used persistent connections with application-level retry — without that, the reload would have dropped in-flight orders.

Case Study 2: Self-Healing Index Management for a SaaS Analytics Platform (SQL Server)

A B2B analytics SaaS company ran SQL Server 2022 on Azure VMs (Standard_D32s_v5 instances) serving 400+ tenant databases within a single instance via schema-per-tenant isolation. Index fragmentation was causing query degradation across tenants at different rates — a scheduled maintenance window applied the same REBUILD/REORGANIZE policy to all tenants, causing unpredictable latency spikes during business hours for tenants in different time zones. The solution: a fully autonomous index management loop that evaluated each tenant schema independently and acted without scheduling.

The autonomous index agent ran as a SQL Server Agent job on a 15-minute cycle. Its logic tree:

  • → If `avg_fragmentation_in_percent > 30` AND `page_count > 1000`: REBUILD ONLINE
  • → If `avg_fragmentation_in_percent > 10` AND `page_count > 500`: REORGANIZE
  • → If `page_count <= 500`: skip (small table overhead not worth it)
  • → If estimated rebuild duration (based on historical stats) would exceed 4 minutes: defer to off-peak window specific to tenant's primary geography
    • -- Autonomous index maintenance procedure per tenant schema
CREATE OR ALTER PROCEDURE dbo.usp_AutoIndexMaintenance
    @TenantSchema  NVARCHAR(128),
    @DryRun        BIT = 0
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @SQL           NVARCHAR(MAX);
    DECLARE @TableName     NVARCHAR(256);
    DECLARE @IndexName     NVARCHAR(256);
    DECLARE @Fragmentation FLOAT;
    DECLARE @PageCount     BIGINT;
    DECLARE @Action        NVARCHAR(50);

    DECLARE index_cursor CURSOR LOCAL FAST_FORWARD FOR
        SELECT
            QUOTENAME(s.name) + '.' + QUOTENAME(t.name)    AS full_table_name,
            QUOTENAME(i.name)                               AS index_name,
            ips.avg_fragmentation_in_percent,
            ips.page_count,
            CASE
                WHEN ips.avg_fragmentation_in_percent > 30
                     AND ips.page_count > 1000              THEN 'REBUILD'
                WHEN ips.avg_fragmentation_in_percent > 10
                     AND ips.page_count > 500               THEN 'REORGANIZE'
                ELSE 'SKIP'
            END AS recommended_action
        FROM sys.dm_db_index_physical_stats(
                 DB_ID(), NULL, NULL, NULL, 'LIMITED') ips
        JOIN sys.indexes i
            ON ips.object_id = i.object_id
            AND ips.index_id = i.index_id
        JOIN sys.tables t
            ON i.object_id = t.object_id
        JOIN sys.schemas s
            ON t.schema_id = s.schema_id
        WHERE s.name     = @TenantSchema
          AND i.name     IS NOT NULL
          AND ips.page_count > 500;

    OPEN index_cursor;
    FETCH NEXT FROM index_cursor
        INTO @TableName, @IndexName, @Fragmentation, @PageCount, @Action;

    WHILE @@FETCH_STATUS = 0
    BEGIN
        IF @Action = 'REBUILD'
        BEGIN
            SET @SQL = N'ALTER INDEX ' + @IndexName
                     + N' ON ' + @TableName
                     + N' REBUILD WITH (ONLINE = ON, MAXDOP = 4);';
        END
        ELSE IF @Action = 'REORGANIZE'
        BEGIN
            SET @SQL = N'ALTER INDEX ' + @IndexName
                     + N' ON ' + @TableName
                     + N' REORGANIZE;';
        END

        IF @Action <> 'SKIP'
        BEGIN
            -- Audit the decision before acting
            INSERT INTO dbo.autonomous_index_log
                (tenant_schema, table_name, index_name,
                 fragmentation_pct, page_count, action_taken,
                 executed_sql, log_time)
            VALUES
                (@TenantSchema, @TableName, @IndexName,
                 @Fragmentation, @PageCount, @Action,
                 @SQL, SYSUTCDATETIME());

            IF @DryRun = 0
                EXEC sp_executesql @SQL;
        END

        FETCH NEXT FROM index_cursor
            INTO @TableName, @IndexName, @Fragmentation, @PageCount, @Action;
    END

    CLOSE index_cursor;
    DEALLOCATE index_cursor;
END;
GO

-- Master orchestrator job iterates all tenant schemas
DECLARE @TenantSchema NVARCHAR(128);
DECLARE tenant_cursor CURSOR LOCAL FAST_FORWARD FOR
    SELECT schema_name
    FROM   dbo.tenant_registry
    WHERE  maintenance_enabled = 1
      AND  GETUTCDATE() BETWEEN maintenance_window_start
                             AND maintenance_window_end;

OPEN tenant_cursor;
FETCH NEXT FROM tenant_cursor INTO @TenantSchema;
WHILE @@FETCH_STATUS = 0
BEGIN
    EXEC dbo.usp_AutoIndexMaintenance
        @TenantSchema = @TenantSchema,
        @DryRun       = 0;
    FETCH NEXT FROM tenant_cursor INTO @TenantSchema;
END
CLOSE tenant_cursor;
DEALLOCATE tenant_cursor;

    The tenant_registry table stored each tenant's primary geography and the associated UTC maintenance window — a 4-hour block during their 2–6 AM local time. The autonomous agent queried maintenance_window_start and maintenance_window_end before acting, ensuring a tenant headquartered in Tokyo received index rebuilds during Tokyo's off-hours, not London's. This was the architectural insight that the previous global maintenance window lacked entirely.

    After 90 days in production, average query duration across tenants dropped 31% during peak hours, and index-related blocking incidents — previously averaging 4 per week — dropped to zero. The autonomous_index_log table became the team's primary evidence artifact in customer SLA reviews.

    Case Study 3: Autonomous Query Plan Stabilization in a Healthcare Data Warehouse

    A regional healthcare network operated a PostgreSQL 16 data warehouse — approximately 12TB across 60 tables — that fed clinical dashboards consumed by 300+ concurrent analysts. The platform team faced a recurring problem: after statistics updates (triggered by autovacuum), query plans for 8–12 critical reporting queries would regress. A plan that previously used an index scan would switch to a sequential scan on a 900M-row fact table, spiking query time from 4 seconds to 3.5 minutes. The on-call response was manual: a DBA would run EXPLAIN ANALYZE, identify the regression, and inject SET enable_seqscan = off at the session level or create a pg_hint_plan override. This manual process averaged 45 minutes of analyst impact.

    The autonomous plan stabilization system worked in three tiers:

    Tier 1 — Continuous baseline capture: A background process recorded query fingerprints and their execution plans using pg_stat_statements and auto_explain, storing normalized plan JSON in a monitoring schema.

    Tier 2 — Regression detection: Every 5 minutes, a Python process compared recent execution time (90th percentile over the last 15 minutes) against the rolling 7-day baseline for each fingerprint. If the ratio exceeded 2.5x, it flagged a potential regression.

    Tier 3 — Autonomous remediation: The system retrieved the last known good plan, extracted the join type and scan method differences, and automatically injected a pg_hint_plan comment into the affected query's scheduled invocation wrapper.

    The Python remediation agent retrieved the baseline plan, parsed the scan node types from the JSONB, and synthesized a pg_hint_plan directive:

    import psycopg2
import json
import logging
from typing import Optional

logger = logging.getLogger("plan-stabilizer")

def extract_hint_from_plan(plan_json: dict) -> Optional[str]:
    """
    Walk the plan tree and extract scan/join hints.
    Returns a pg_hint_plan directive string or None.
    """
    hints = []

    def walk(node: dict):
        node_type = node.get("Node Type", "")
        relation = node.get("Relation Name", "")

        if node_type == "Index Scan" and relation:
            idx = node.get("Index Name", "")
            if idx:
                hints.append(f"IndexScan({relation} {idx})")
        elif node_type == "Seq Scan" and relation:
            # Baseline used index — force it back
            pass
        elif "Hash Join" in node_type:
            inner = node.get("Plans", [{}])[1].get("Relation Name", "")
            outer = node.get("Plans", [{}])[0].get("Relation Name", "")
            if inner and outer:
                hints.append(f"HashJoin({outer} {inner})")

        for child in node.get("Plans", []):
            walk(child)

    walk(plan_json.get("Plan", {}))
    return "/*+ " + " ".join(hints) + " */" if hints else None

def apply_plan_stabilization(conn_str: str, fingerprint: int) -> None:
    conn = psycopg2.connect(conn_str)
    cur = conn.cursor()

    # Retrieve last known good baseline plan
    cur.execute("""
        SELECT plan_json, query_sample
        FROM monitoring.query_plan_history
        WHERE fingerprint = %s
          AND is_baseline = TRUE
        ORDER BY captured_at DESC
        LIMIT 1
    """, (fingerprint,))
    row = cur.fetchone()

    if not row:
        logger.warning(f"No baseline plan found for fingerprint {fingerprint}")
        return

    plan_json, query_sample = row
    hint = extract_hint_from_plan(plan_json)

    if hint:
        # Store hint in the plan override registry — applications
        # read this table to prepend hints at query construction time
        cur.execute("""
            INSERT INTO monitoring.plan_override_registry
                (fingerprint, hint_directive, applied_at, source)
            VALUES (%s, %s, now(), 'autonomous-plan-stabilizer')
            ON CONFLICT (fingerprint) DO UPDATE
                SET hint_directive = EXCLUDED.hint_directive,
                    applied_at     = EXCLUDED.applied_at
        """, (fingerprint, hint))
        conn.commit()
        logger.info(
            f"Plan hint applied for fingerprint {fingerprint}: {hint}"
        )
    else:
        logger.warning(
            f"Could not synthesize hint for fingerprint {fingerprint} — escalating"
        )

    cur.close()
    conn.close()

    The production deployment stabilized 11 of the 12 identified regression fingerprints autonomously. The twelfth required manual intervention — the regression was caused by a schema change (a new partial index that changed cardinality estimates) rather than statistics drift, and the baseline plan was genuinely suboptimal for the new schema. This distinction — regression caused by data drift versus regression caused by schema change — became a classification dimension added to the detection layer in the next iteration.

    Case Study 4: Autonomous Capacity Scaling in a Multi-Tenant E-Commerce Platform (PostgreSQL on Kubernetes)

    A direct-to-consumer e-commerce company ran PostgreSQL 16 via the CloudNativePG operator on a Kubernetes cluster (AWS EKS) spanning three availability zones. Their traffic profile was violently bursty: normal load was 800 TPS, but flash sales and influencer-driven traffic spikes routinely hit 12,000–15,000 TPS within 90 seconds of an event trigger. Vertical scaling was too slow (node provisioning took 7–12 minutes); the autonomous solution was horizontal read scaling through automated replica addition and pgBouncer pool expansion, combined with query routing logic that redirected read queries based on real-time lag monitoring.

    The scaling loop was implemented as a Kubernetes controller (using the kopf framework in Python) that watched a custom resource PostgreSQLScalePolicy and acted on Prometheus metrics fed through the Prometheus Adapter for Kubernetes:

  • → When `pg_stat_activity_count{state="active"} / max_connections > 0.75` for 60 seconds: scale pgBouncer pool size up by 20%, add one read replica via CloudNativePG's `instances` field patch.
  • → When replica lag on any standby exceeds 30MB: do not add more replicas; instead reduce connection pressure by throttling non-critical background jobs via a priority queue table.
  • → When `pg_stat_activity_count{state="active"} / max_connections < 0.35` for 300 seconds: scale down one replica if replica count > 2.

    • The Kubernetes controller patched CloudNativePG's Cluster resource to add replicas dynamically:

    import kopf
import kubernetes
import logging
import time
from prometheus_api_client import PrometheusConnect

PROMETHEUS_URL   = "http://prometheus.monitoring.svc.cluster.local:9090"
CNPG_GROUP       = "postgresql.cnpg.io"
CNPG_VERSION     = "v1"
CNPG_PLURAL      = "clusters"
NAMESPACE        = "databases"
CLUSTER_NAME     = "ecommerce-pg"
MIN_REPLICAS     = 2
MAX_REPLICAS     = 8
SCALE_UP_RATIO   = 0.75
SCALE_DOWN_RATIO = 0.35
SCALE_COOLDOWN   = 180  # seconds between scale events

prom  = PrometheusConnect(url=PROMETHEUS_URL, disable_ssl=True)
k8s   = kubernetes.client.CustomObjectsApi()
last_scale_time = 0

def get_connection_utilization() -> float:
    result = prom.custom_query(
        'sum(pg_stat_activity_count{state="active",cluster="ecommerce-pg"}) '
        '/ sum(pg_settings_max_connections{cluster="ecommerce-pg"})'
    )
    if result:
        return float(result[0]["value"][1])
    return 0.0

def get_current_replica_count() -> int:
    cluster = k8s.get_namespaced_custom_object(
        group=CNPG_GROUP, version=CNPG_VERSION,
        namespace=NAMESPACE, plural=CNPG_PLURAL,
        name=CLUSTER_NAME
    )
    return cluster["spec"]["instances"]

def patch_replica_count(new_count: int) -> None:
    patch = {"spec": {"instances": new_count}}
    k8s.patch_namespaced_custom_object(
        group=CNPG_GROUP, version=CNPG_VERSION,
        namespace=NAMESPACE, plural=CNPG_PLURAL,
        name=CLUSTER_NAME, body=patch
    )
    logging.info(f"Patched CloudNativePG cluster to {new_count} instances")

def get_max_replication_lag_bytes() -> int:
    result = prom.custom_query(
        'max(pg_replication_lag_bytes{cluster="ecommerce-pg"})'
    )
    if result:
        return int(float(result[0]["value"][1]))
    return 0

@kopf.timer("postgresql.cnpg.io", "v1", "clusters", interval=60.0)
def autoscale_loop(spec, name, namespace, **kwargs):
    global last_scale_time
    if name != CLUSTER_NAME or namespace != NAMESPACE:
        return

    now = time.time()
    if (now - last_scale_time) < SCALE_COOLDOWN:
        logging.debug("Inside cooldown window — skipping scale evaluation")
        return

    utilization  = get_connection_utilization()
    current_reps = get_current_replica_count()
    lag_bytes    = get_max_replication_lag_bytes()

    logging.info(
        f"Utilization={utilization:.2f}, replicas={current_reps}, "
        f"max_lag_bytes={lag_bytes}"
    )

    LAG_CEILING = 30 * 1024 * 1024  # 30 MB

    if utilization > SCALE_UP_RATIO:
        if lag_bytes > LAG_CEILING:
            logging.warning(
                "High connection pressure but replication lag exceeds 30MB — "
                "holding replica count, throttling background jobs instead"
            )
            throttle_background_jobs()
        elif current_reps < MAX_REPLICAS:
            patch_replica_count(current_reps + 1)
            last_scale_time = now
    elif utilization < SCALE_DOWN_RATIO and current_reps > MIN_REPLICAS:
        patch_replica_count(current_reps - 1)
        last_scale_time = now

def throttle_background_jobs() -> None:
    """
    Signals the job priority queue to pause non-critical batch work
    by setting a cluster-wide throttle flag in the coordination table.
    """
    import psycopg2
    import os
    conn = psycopg2.connect(os.environ["PG_CONN_STR"])
    cur = conn.cursor()
    cur.execute("""
        INSERT INTO ops.scaling_signals (signal_key, signal_value, updated_at)
        VALUES ('background_throttle', 'true', now())
        ON CONFLICT (signal_key) DO UPDATE
            SET signal_value = 'true',
                updated_at   = now()
    """)
    conn.commit()
    cur.close()
    conn.close()
    logging.info("Background job throttle signal set")

    The most significant lesson from this deployment was the interaction between replica provisioning latency and connection pool saturation. CloudNativePG required approximately 45–90 seconds to bring a new replica online and fully sync. During that window, if the spike was sharp enough, pgBouncer's pool would saturate and begin queuing connections. The mitigation was to trigger pool expansion (pgBouncer's pool_size via its admin interface) immediately — before the replica was ready — so that queued connections had somewhere to land as soon as the replica joined the pool. The sequence mattered: pool first, then replica.

    The second lesson was that the SCALE_COOLDOWN window needed to be asymmetric: 60 seconds for scale-up (to react quickly), 300 seconds for scale-down (to avoid thrashing when traffic declines slowly). A symmetric cooldown caused premature scale-down during the trailing edge of flash sales, requiring an immediate re-scale that itself triggered the cooldown again.

    Case Study 5: Autonomous Compliance Auditing and Remediation in a Financial Services PostgreSQL Deployment

    A regional bank's data engineering team operated PostgreSQL 15 databases containing customer PII, transaction records, and loan origination data, subject to audit requirements from both their internal compliance framework and external regulatory guidance. Their pain point was not detection — they had extensive logging — but remediation latency: when a compliance violation was identified (a column without row-level security, an unencrypted backup path, a role with excessive GRANT permissions), the ticket-to-fix cycle averaged 11 business days due to approval workflows and DBA bandwidth.

    The autonomous compliance agent shortened this cycle by classifying violations into three tiers:

  • → **Tier 1 (Auto-Remediate)**: Violations where the corrective action is reversible, low-risk, and pre-approved by the security team (e.g., revoking a PUBLIC schema execute permission, adding a column-level `SECURITY LABEL`).
  • → **Tier 2 (Auto-Draft + Human Approve)**: Violations where the fix is known but the blast radius requires sign-off (e.g., modifying RLS policies on tables with active sessions, revoking a role with 50+ dependent objects).
  • → **Tier 3 (Alert Only)**: Violations requiring architectural judgment (e.g., an entire schema missing encryption at rest, a cross-database link to an unapproved external system).

    • The autonomous remediation function for Tier 1 violations:

    -- Tier 1 auto-remediation: revoke PUBLIC schema DML permissions
CREATE OR REPLACE PROCEDURE compliance.auto_remediate_public_exposure()
LANGUAGE plpgsql
AS $$
DECLARE
    v_schema  TEXT;
    v_table   TEXT;
    v_priv    TEXT;
    v_sql     TEXT;
BEGIN
    FOR v_schema, v_table, v_priv IN
        SELECT table_schema, table_name, privilege_type
        FROM compliance.public_schema_overexposure
    LOOP
        v_sql := format(
            'REVOKE %I ON %I.%I FROM PUBLIC',
            v_priv, v_schema, v_table
        );

        -- Audit before execution
        INSERT INTO compliance.remediation_log
            (violation_type, object_identifier, action_sql,
             tier, remediated_at, initiated_by)
        VALUES
            ('public_schema_overexposure',
             v_schema || '.' || v_table,
             v_sql, 1, now(), 'autonomous-compliance-agent');

        EXECUTE v_sql;
    END LOOP;
END;
$$;

-- Enable RLS on regulated tables (Tier 1 where no active sessions on table)
CREATE OR REPLACE PROCEDURE compliance.auto_enable_rls_safe()
LANGUAGE plpgsql
AS $$
DECLARE
    v_schema  TEXT;
    v_table   TEXT;
    v_active  INT;
    v_sql     TEXT;
BEGIN
    FOR v_schema, v_table IN
        SELECT schema_name, table_name
        FROM compliance.tables_missing_rls
    LOOP
        -- Only auto-enable RLS if no active queries are currently touching this table
        SELECT COUNT(*) INTO v_active
        FROM pg_stat_activity psa
        JOIN pg_locks pl ON psa.pid = pl.pid
        JOIN pg_class pc ON pl.relation = pc.oid
        JOIN pg_namespace pn ON pc.relnamespace = pn.oid
        WHERE pn.nspname = v_schema
          AND pc.relname = v_table
          AND psa.state  = 'active';

        IF v_active = 0 THEN
            v_sql := format(
                'ALTER TABLE %I.%I ENABLE ROW LEVEL SECURITY',
                v_schema, v_table
            );

            INSERT INTO compliance.remediation_log
                (violation_type, object_identifier, action_sql,
                 tier, remediated_at, initiated_by)
            VALUES
                ('missing_rls', v_schema || '.' || v_table,
                 v_sql, 1, now(), 'autonomous-compliance-agent');

            EXECUTE v_sql;
        ELSE
            -- Escalate to Tier 2: table is active, needs human approval
            INSERT INTO compliance.remediation_queue
                (violation_type, object_identifier, recommended_sql,
                 tier, queued_at, approval_status)
            VALUES
                ('missing_rls', v_schema || '.' || v_table,
                 format('ALTER TABLE %I.%I ENABLE ROW LEVEL SECURITY',
                        v_schema, v_table),
                 2, now(), 'pending');
        END IF;
    END LOOP;
END;
$$;

    The Tier 2 workflow connected to the bank's internal approval platform via a webhook: once a record appeared in compliance.remediation_queue with approval_status = 'pending', a notification triggered a Slack approval message with a one-click approval button. Approved records updated approval_status = 'approved' and triggered the agent to execute the stored recommended_sql. The average Tier 2 remediation time dropped from 11 business days to 6.2 hours — driven almost entirely by the pre-drafted SQL that security reviewers could read, approve, or reject without any DBA ticket creation or back-and-forth.

    The most important architectural lesson from this case study was the value of the remediation_log table as a compliance artifact. External auditors could query the log to verify that violations were detected and remediated within specific SLA windows, with full SQL provenance. The autonomous system was not just faster — it was more auditable than the manual process, which relied on ticket comments and email threads that were difficult to correlate with actual database state changes.

    A secondary lesson was the necessity of scoping Tier 1 carefully. On the third week of deployment, the agent auto-revoked an EXECUTE permission on a stored procedure that a batch job had relied on for 4 years — a procedure that was not documented anywhere except a comment in the source code of a decommissioned internal tool. The batch job failed silently overnight. This prompted a refinement: Tier 1 actions now require the affected object to appear in a pre-approved object registry (compliance.tier1_eligible_objects) before autonomous action can proceed. The registry is maintained by DBAs and reviewed quarterly.

    Synthesis: Patterns Across All Five Deployments

    Examining the five case studies together, several design patterns appear consistently in autonomous DBA systems that survive production contact:

    1. Layered decision gates, not binary triggers

    Every deployment used a multi-stage decision process before acting. Detection triggered evaluation; evaluation triggered either autonomous action or escalation; action triggered verification. No deployment allowed a single metric threshold to directly trigger a destructive or irreversible change. The trading firm's three-poll failure threshold, the healthcare platform's 2.5x regression ratio, and the compliance agent's Tier 1/2/3 classification all embody this principle.

    2. Audit-first, act-second

    In every case, the system wrote an audit record before executing a change — not after. This ordering matters: if the execution fails mid-operation, the audit record still exists and contains the intended action, enabling forensic reconstruction. The SQL Server index agent, the compliance remediation procedure, and the plan stabilizer all follow this pattern.

    3. Asymmetric conservatism

    Autonomous systems consistently applied different thresholds for action versus inaction. The Kubernetes autoscaler used a 60-second cooldown for scale-up and a 300-second cooldown for scale-down. The compliance agent applied stricter preconditions to Tier 1 than to Tier 2 escalations (because Tier 1 executes without human review). Systems that used symmetric thresholds oscillated or over-acted.

    4. Human override surfaces, not human override requirements

    All five systems provided mechanisms for humans to override or inspect autonomous decisions without requiring humans to be in the critical path of every decision. The plan_override_registry, the remediation_queue, the tier1_eligible_objects registry, and the Slack approval workflow all represent designed override surfaces — places where human judgment can inject itself without breaking the automation loop.

    5. Production failure as design input

    The silent batch job failure from the compliance case, the replica provisioning lag from the Kubernetes autoscaler, and the schema-change-versus-data-drift distinction from the healthcare platform all led to architectural refinements that would not have been discoverable through any amount of upfront design. Each case study team built a feedback loop from production incidents back into the autonomous system's decision logic — not just into runbooks.

    ---

    Key Takeaways

  • → **Autonomous systems earn trust through auditability, not just performance**: every production deployment in this chapter succeeded in gaining organizational acceptance partly because the system's decisions were fully logged with provenance, enabling retrospective review by both engineers and external auditors.
  • → **Detection signal quality determines autonomous system reliability more than remediation sophistication**: the trading firm's heartbeat table outperformed Patroni's own API as a failure signal; the healthcare platform's regression ratio proved more stable than raw execution time comparisons; signal design deserves as much engineering attention as the remediation logic.
  • → **The boundary between Tier 1 (auto-act) and Tier 2 (human-approve) actions must be defined by blast radius and reversibility, not by technical complexity**: some technically simple actions (revoking a permission) have large blast radii; some technically complex actions (online index rebuild) are easily reversible. Conflating complexity with risk leads to either under-automation or over-automation.
  • → **Cooldown windows and lag guards are not optional safety theater — they are architectural requirements**: every case study that skipped or underestimated these guards experienced oscillation, thrashing, or a preventable failure before adding them back; asymmetric cooldowns (faster to engage protective action, slower to disengage it) consistently outperformed symmetric ones.
  • → **The object registry pattern — maintaining a pre-approved list of objects eligible for autonomous action — is the practical solution to the scope creep problem in autonomous remediation systems**: without it, autonomous agents inevitably encounter edge cases (undocumented dependencies, legacy objects, objects shared across teams) that cause silent failures; with it, the blast radius of any autonomous action is bounded and reviewable before deployment.
