Chapter 37: Real-World Autonomous DBA Case Studies

The gap between autonomous database theory and production reality is where most platform engineering teams lose momentum. Architectural patterns that look elegant in whiteboards collapse against the friction of legacy schemas, bursty traffic, compliance requirements, and on-call engineers who override automation at the first sign of unfamiliarity. This chapter closes that gap by examining five real-world autonomous DBA deployments — drawn from high-scale SaaS platforms, financial institutions, healthcare data pipelines, and multi-cloud e-commerce systems — each built on SQL Server across on-premises, Azure, and hybrid deployments. Every case study follows the same structure: the operational problem, the autonomous architecture chosen, the specific tooling and decision logic wired together, and the lessons that only surface in production. These are not success stories scrubbed clean for a conference talk. They include rollbacks, missed thresholds, and architectural pivots that led to better designs.

Case Study 1: Autonomous Failover and Connection Rerouting at a High-Frequency Trading Firm

A mid-sized proprietary trading firm running SQL Server 2022 on bare metal needed sub-30-second failover with zero manual intervention. Their previous setup used an Always On availability group with a manual failover script triggered by on-call engineers — a process that averaged 4.5 minutes from detection to connection rerouting due to human latency and shift handoff ambiguity. The requirement from the trading desk: automated failover with automatic client rerouting in under 25 seconds, with a hard constraint that no transaction could be silently lost.

The architecture replaced manual triggers with a fully autonomous stack. An Always On availability group in synchronous-commit mode with automatic failover remained the core, backed by a Windows Server Failover Cluster for quorum. The critical addition was a custom Python daemon called trade-sentinel that consumed the AG DMVs (sys.dm_hadr_availability_replica_states, sys.dm_hadr_database_replica_states) and a business-level heartbeat table written by the trading application. The AG listener sat in front of all database connections, so client rerouting after a failover was a DNS-level flip to the new primary — no connection-string changes, no proxy rewrites.

The decision logic was explicit and layered:

1. Detection: If the primary replica's role state in sys.dm_hadr_availability_replica_states is unhealthy for three consecutive 2-second polls, or if the heartbeat table (trading.heartbeat) has not been updated within 8 seconds, enter failover evaluation mode.

2. Validation: Confirm the synchronous secondary is in SYNCHRONIZED state with a redo queue under 512KB and that cluster quorum is healthy. If either condition fails, escalate to PagerDuty and hold without failing over.

3. Failover: Issue ALTER AVAILABILITY GROUP [TradingAG] FAILOVER from the target secondary, then verify the new primary role via the DMVs.

4. Connection rerouting: The AG listener DNS record follows the primary automatically; the daemon forces a DNS cache flush on the application tier and validates that new connections land on the new primary.

5. Verification: Run a synthetic write/read probe transaction against the new primary through the listener. If it fails within 10 seconds, re-escalate to human.

The trade-sentinel daemon managed detection, failover, and listener verification atomically:

import pyodbc
import subprocess
import time
import logging
from datetime import datetime, timezone

PRIMARY_CONN   = "DRIVER={ODBC Driver 18 for SQL Server};SERVER=sql-primary;DATABASE=master;Trusted_Connection=yes;"
SECONDARY_CONN = "DRIVER={ODBC Driver 18 for SQL Server};SERVER=sql-secondary;DATABASE=master;Trusted_Connection=yes;"
AG_NAME        = "TradingAG"
LISTENER       = "trading-ag-listener"
HEARTBEAT_THRESHOLD_SECONDS = 8
POLL_INTERVAL  = 2
FAILURE_THRESHOLD = 3

logger = logging.getLogger("trade-sentinel")

def query(conn_str: str, sql: str):
    with pyodbc.connect(conn_str, timeout=5) as conn:
        cur = conn.cursor()
        cur.execute(sql)
        return cur.fetchall()

def primary_role_state() -> str | None:
    try:
        rows = query(PRIMARY_CONN, """
            SELECT role_desc
            FROM sys.dm_hadr_availability_replica_states
            WHERE replica_server_name = @@SERVERNAME
        """)
        return rows[0][0] if rows else None
    except pyodbc.Error:
        return None

def secondary_sync_state() -> tuple:
    rows = query(SECONDARY_CONN, """
        SELECT synchronization_state_desc,
               ISNULL(redo_queue_size, 0)
        FROM sys.dm_hadr_database_replica_states
        WHERE database_id = DB_ID('TradingDB')
    """)
    return (rows[0][0], rows[0][1]) if rows else ("UNKNOWN", -1)

def heartbeat_age_seconds() -> float:
    try:
        rows = query(PRIMARY_CONN, """
            SELECT DATEDIFF(SECOND, MAX(updated_at), SYSUTCDATETIME())
            FROM trading.heartbeat
        """)
        return float(rows[0][0]) if rows and rows[0][0] is not None else 9999.0
    except pyodbc.Error:
        return 9999.0

def trigger_failover() -> bool:
    # Planned failover executes from the TARGET secondary
    with pyodbc.connect(SECONDARY_CONN, autocommit=True) as conn:
        cur = conn.cursor()
        cur.execute(f"ALTER AVAILABILITY GROUP [{AG_NAME}] FAILOVER")
    logger.info("Failover command issued from secondary")
    time.sleep(5)
    return primary_role_state() == "PRIMARY"

def flush_app_dns() -> None:
    subprocess.run(["powershell", "-Command", "Clear-DnsClientCache"],
                   check=False)
    logger.info("Application-tier DNS cache flushed")

def run_sentinel():
    consecutive_failures = 0
    while True:
        role = primary_role_state()
        hb_age = heartbeat_age_seconds()
        if role != "PRIMARY" or hb_age > HEARTBEAT_THRESHOLD_SECONDS:
            consecutive_failures += 1
            logger.warning(
                f"Primary unhealthy (role={role}, hb_age={hb_age:.1f}s) — "
                f"failure count: {consecutive_failures}"
            )
        else:
            consecutive_failures = 0

        if consecutive_failures >= FAILURE_THRESHOLD:
            logger.critical("Threshold exceeded — initiating autonomous failover")
            sync_state, redo_kb = secondary_sync_state()
            if sync_state != "SYNCHRONIZED" or redo_kb > 512:
                logger.error(
                    f"Secondary not ready (state={sync_state}, "
                    f"redo={redo_kb}KB) — escalating to human"
                )
            elif trigger_failover():
                flush_app_dns()
                logger.info("Failover complete — listener now on new primary")
            else:
                logger.error("Failover failed — escalating to human")
            consecutive_failures = 0
        time.sleep(POLL_INTERVAL)

if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO)
    run_sentinel()

The first production failover completed in 18.4 seconds. The second, triggered six weeks later by a kernel panic on the primary host, completed in 21.1 seconds — within specification despite higher system load. The lessons were two-fold: the heartbeat table proved far more reliable as a detection signal than the replica-state DMVs alone, which exhibited a 3–4 second delay in reporting role loss during network partitions; and the AG listener flip was safe only because the trading application used persistent connections with application-level retry — without that, in-flight orders on the failed primary would still have been lost at the TCP layer.

Case Study 2: Self-Healing Index Management for a SaaS Analytics Platform (SQL Server)

A B2B analytics SaaS company ran SQL Server 2022 on Azure VMs (Standard_D32s_v5 instances) serving 400+ tenant databases within a single instance via schema-per-tenant isolation. Index fragmentation was causing query degradation across tenants at different rates — a scheduled maintenance window applied the same REBUILD/REORGANIZE policy to all tenants, causing unpredictable latency spikes during business hours for tenants in different time zones. The solution: a fully autonomous index management loop that evaluated each tenant schema independently and acted without scheduling.

The autonomous index agent ran as a SQL Server Agent job on a 15-minute cycle. Its logic tree:

  • → If avg_fragmentation_in_percent > 30 AND page_count > 1000: REBUILD ONLINE
  • → If avg_fragmentation_in_percent > 10 AND page_count > 500: REORGANIZE
  • → If page_count <= 500: skip (small table overhead not worth it)
  • → If estimated rebuild duration (based on historical stats) would exceed 4 minutes: defer to off-peak window specific to tenant's primary geography
    • -- Autonomous index maintenance procedure per tenant schema
CREATE OR ALTER PROCEDURE dbo.usp_AutoIndexMaintenance
    @TenantSchema  NVARCHAR(128),
    @DryRun        BIT = 0
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @SQL           NVARCHAR(MAX);
    DECLARE @TableName     NVARCHAR(256);
    DECLARE @IndexName     NVARCHAR(256);
    DECLARE @Fragmentation FLOAT;
    DECLARE @PageCount     BIGINT;
    DECLARE @Action        NVARCHAR(50);

    DECLARE index_cursor CURSOR LOCAL FAST_FORWARD FOR
        SELECT
            QUOTENAME(s.name) + '.' + QUOTENAME(t.name)    AS full_table_name,
            QUOTENAME(i.name)                               AS index_name,
            ips.avg_fragmentation_in_percent,
            ips.page_count,
            CASE
                WHEN ips.avg_fragmentation_in_percent > 30
                     AND ips.page_count > 1000              THEN 'REBUILD'
                WHEN ips.avg_fragmentation_in_percent > 10
                     AND ips.page_count > 500               THEN 'REORGANIZE'
                ELSE 'SKIP'
            END AS recommended_action
        FROM sys.dm_db_index_physical_stats(
                 DB_ID(), NULL, NULL, NULL, 'LIMITED') ips
        JOIN sys.indexes i
            ON ips.object_id = i.object_id
            AND ips.index_id = i.index_id
        JOIN sys.tables t
            ON i.object_id = t.object_id
        JOIN sys.schemas s
            ON t.schema_id = s.schema_id
        WHERE s.name     = @TenantSchema
          AND i.name     IS NOT NULL
          AND ips.page_count > 500;

    OPEN index_cursor;
    FETCH NEXT FROM index_cursor
        INTO @TableName, @IndexName, @Fragmentation, @PageCount, @Action;

    WHILE @@FETCH_STATUS = 0
    BEGIN
        IF @Action = 'REBUILD'
        BEGIN
            SET @SQL = N'ALTER INDEX ' + @IndexName
                     + N' ON ' + @TableName
                     + N' REBUILD WITH (ONLINE = ON, MAXDOP = 4);';
        END
        ELSE IF @Action = 'REORGANIZE'
        BEGIN
            SET @SQL = N'ALTER INDEX ' + @IndexName
                     + N' ON ' + @TableName
                     + N' REORGANIZE;';
        END

        IF @Action <> 'SKIP'
        BEGIN
            -- Audit the decision before acting
            INSERT INTO dbo.autonomous_index_log
                (tenant_schema, table_name, index_name,
                 fragmentation_pct, page_count, action_taken,
                 executed_sql, log_time)
            VALUES
                (@TenantSchema, @TableName, @IndexName,
                 @Fragmentation, @PageCount, @Action,
                 @SQL, SYSUTCDATETIME());

            IF @DryRun = 0
                EXEC sp_executesql @SQL;
        END

        FETCH NEXT FROM index_cursor
            INTO @TableName, @IndexName, @Fragmentation, @PageCount, @Action;
    END

    CLOSE index_cursor;
    DEALLOCATE index_cursor;
END;
GO

-- Master orchestrator job iterates all tenant schemas
DECLARE @TenantSchema NVARCHAR(128);
DECLARE tenant_cursor CURSOR LOCAL FAST_FORWARD FOR
    SELECT schema_name
    FROM   dbo.tenant_registry
    WHERE  maintenance_enabled = 1
      AND  GETUTCDATE() BETWEEN maintenance_window_start
                             AND maintenance_window_end;

OPEN tenant_cursor;
FETCH NEXT FROM tenant_cursor INTO @TenantSchema;
WHILE @@FETCH_STATUS = 0
BEGIN
    EXEC dbo.usp_AutoIndexMaintenance
        @TenantSchema = @TenantSchema,
        @DryRun       = 0;
    FETCH NEXT FROM tenant_cursor INTO @TenantSchema;
END
CLOSE tenant_cursor;
DEALLOCATE tenant_cursor;

    The tenant_registry table stored each tenant's primary geography and the associated UTC maintenance window — a 4-hour block during their 2–6 AM local time. The autonomous agent queried maintenance_window_start and maintenance_window_end before acting, ensuring a tenant headquartered in Tokyo received index rebuilds during Tokyo's off-hours, not London's. This was the architectural insight that the previous global maintenance window lacked entirely.

    After 90 days in production, average query duration across tenants dropped 31% during peak hours, and index-related blocking incidents — previously averaging 4 per week — dropped to zero. The autonomous_index_log table became the team's primary evidence artifact in customer SLA reviews.

    Case Study 3: Autonomous Query Plan Stabilization in a Healthcare Data Warehouse

    A regional healthcare network operated a SQL Server 2022 data warehouse — approximately 12TB across 60 tables — that fed clinical dashboards consumed by 300+ concurrent analysts. The platform team faced a recurring problem: after automatic statistics updates, query plans for 8–12 critical reporting queries would regress. A plan that previously used an index seek would switch to a clustered index scan on a 900M-row fact table, spiking query time from 4 seconds to 3.5 minutes. The on-call response was manual: a DBA would capture the actual execution plan, identify the regression, and force the good plan via Query Store with sp_query_store_force_plan. This manual process averaged 45 minutes of analyst impact.

    The autonomous plan stabilization system worked in three tiers:

    Tier 1 — Continuous baseline capture: Query Store captured query fingerprints (query_hash), their plans (query_plan_hash), and runtime statistics automatically, with forced-plan history providing the known-good baseline.

    Tier 2 — Regression detection: Every 5 minutes, a SQL Server Agent job compared recent average duration against the rolling 7-day baseline for each tracked query. If the ratio exceeded 2.5x, it flagged a potential regression.

    Tier 3 — Autonomous remediation: The system retrieved the last known good plan from Query Store and forced it with sp_query_store_force_plan, then validated that the forced plan was being used on subsequent executions.

    The regression detection and auto-forcing procedure:

    CREATE OR ALTER PROCEDURE Monitoring.AutoForceRegressedPlans
AS
BEGIN
    SET NOCOUNT ON;

    -- Candidates: queries whose recent avg duration exceeds 2.5x baseline
    DECLARE @QueryId BIGINT, @GoodPlanId BIGINT, @RecentMs FLOAT, @BaselineMs FLOAT;

    DECLARE cur CURSOR LOCAL FAST_FORWARD FOR
    WITH Recent AS (
        SELECT q.query_id,
               AVG(rs.avg_duration / 1000.0) AS recent_avg_ms
        FROM sys.query_store_query q
        JOIN sys.query_store_plan p
          ON p.query_id = q.query_id
        JOIN sys.query_store_runtime_stats rs
          ON rs.plan_id = p.plan_id
        WHERE rs.last_execution_time > DATEADD(MINUTE, -15, SYSUTCDATETIME())
        GROUP BY q.query_id
    ),
    Baseline AS (
        SELECT q.query_id,
               AVG(rs.avg_duration / 1000.0) AS baseline_avg_ms
        FROM sys.query_store_query q
        JOIN sys.query_store_plan p
          ON p.query_id = q.query_id
        JOIN sys.query_store_runtime_stats rs
          ON rs.plan_id = p.plan_id
        WHERE rs.last_execution_time > DATEADD(DAY, -7, SYSUTCDATETIME())
          AND rs.last_execution_time < DATEADD(MINUTE, -15, SYSUTCDATETIME())
        GROUP BY q.query_id
    )
    SELECT r.query_id,
           (SELECT TOP 1 p.plan_id
            FROM sys.query_store_plan p
            JOIN sys.query_store_runtime_stats rs ON rs.plan_id = p.plan_id
            WHERE p.query_id = r.query_id
              AND rs.last_execution_time < DATEADD(MINUTE, -15, SYSUTCDATETIME())
            ORDER BY rs.avg_duration ASC) AS good_plan_id,
           r.recent_avg_ms,
           b.baseline_avg_ms
    FROM Recent r
    JOIN Baseline b ON b.query_id = r.query_id
    WHERE r.recent_avg_ms > b.baseline_avg_ms * 2.5
      AND b.baseline_avg_ms > 1000   -- ignore sub-second noise
      AND NOT EXISTS (                  -- not already forced
            SELECT 1 FROM sys.query_store_plan fp
            WHERE fp.query_id = r.query_id AND fp.force_failure_count = 0
              AND fp.plan_id IN (
                  SELECT plan_id FROM sys.query_store_query_hints
                  WHERE query_id = r.query_id));

    OPEN cur;
    FETCH NEXT FROM cur INTO @QueryId, @GoodPlanId, @RecentMs, @BaselineMs;
    WHILE @@FETCH_STATUS = 0
    BEGIN
        IF @GoodPlanId IS NOT NULL
        BEGIN
            EXEC sp_query_store_force_plan @QueryId, @GoodPlanId;

            INSERT INTO Monitoring.PlanStabilizationLog
                (QueryId, ForcedPlanId, RecentAvgMs, BaselineAvgMs,
                 ForcedAt, InitiatedBy)
            VALUES
                (@QueryId, @GoodPlanId, @RecentMs, @BaselineMs,
                 SYSUTCDATETIME(), 'autonomous-plan-stabilizer');
        END
        ELSE
        BEGIN
            -- No known-good plan: escalate for human review
            INSERT INTO Monitoring.PlanRegressionQueue
                (QueryId, RecentAvgMs, BaselineAvgMs,
                 DetectedAt, Status)
            VALUES
                (@QueryId, @RecentMs, @BaselineMs,
                 SYSUTCDATETIME(), 'pending_review');
        END
        FETCH NEXT FROM cur INTO @QueryId, @GoodPlanId, @RecentMs, @BaselineMs;
    END
    CLOSE cur;
    DEALLOCATE cur;
END;

    A companion un-force job ran hourly: if a forced plan's force_failure_count climbed or its recent performance no longer beat the unforced baseline, the system called sp_query_store_unforce_plan and logged the outcome. This prevented stale forced plans from fossilizing into the workload — the most common failure mode the team had seen with manual plan forcing.

    After 60 days in production, plan-regression incidents on the 12 tracked reporting queries dropped from an average of 3 per week to zero analyst-visible events. The Monitoring.PlanStabilizationLog table became the team's primary evidence artifact in incident reviews.

    Case Study 4: Autonomous Capacity Scaling in a Multi-Tenant E-Commerce Platform (SQL Server on Azure)

    A direct-to-consumer e-commerce company ran SQL Server on Azure SQL Database Hyperscale across three regions. Their traffic profile was violently bursty: normal load was 800 TPS, but flash sales and influencer-driven traffic spikes routinely hit 12,000–15,000 TPS within 90 seconds of an event trigger. Manual scaling was too slow (tier changes took several minutes and required change approval); the autonomous solution was a control loop that scaled vCores up and down via the Azure control plane and expanded Hyperscale named replicas for read offload, driven by real-time resource utilization signals.

    The scaling loop was implemented as a Python daemon (running as an Azure Container Instance on a 60-second timer) that read resource signals from sys.dm_db_resource_stats and acted through the Azure CLI:

  • → When average CPU over the last 5 minutes exceeds 75% for 60 seconds: scale vCores up one tier via az sql db update, and add one Hyperscale named replica for read offload.
  • → When log write or data I/O waits dominate and replica count is already at the cap: do not add more replicas; instead throttle non-critical background jobs via a priority queue table.
  • → When average CPU stays below 35% for 300 seconds: scale down one tier if vCores are above the floor.

    • The daemon adjusted the database service tier directly through the Azure control plane:

    import pyodbc
import subprocess
import logging
import time
import json

DB_CONN      = "DRIVER={ODBC Driver 18 for SQL Server};SERVER=ecommerce-sql.database.windows.net;DATABASE=ShopDB;Authentication=ActiveDirectoryMsi;"
RESOURCE_GROUP = "rg-ecommerce-prod"
SERVER         = "ecommerce-sql"
DATABASE       = "ShopDB"
MIN_VCORES     = 4
MAX_VCORES     = 80
SCALE_UP_CPU   = 75.0
SCALE_DOWN_CPU = 35.0
SCALE_COOLDOWN = 180  # seconds between scale events

TIERS = [4, 8, 16, 24, 32, 40, 48, 64, 80]
last_scale_time = 0

def query(sql: str):
    with pyodbc.connect(DB_CONN, timeout=10) as conn:
        cur = conn.cursor()
        cur.execute(sql)
        return cur.fetchall()

def avg_cpu_pct_5min() -> float:
    rows = query("""
        SELECT AVG(avg_cpu_percent)
        FROM sys.dm_db_resource_stats
        WHERE end_time > DATEADD(MINUTE, -5, GETUTCDATE())
    """)
    return float(rows[0][0]) if rows and rows[0][0] is not None else 0.0

def current_vcores() -> int:
    out = subprocess.run(
        ["az", "sql", "db", "show", "--resource-group", RESOURCE_GROUP,
         "--server", SERVER, "--name", DATABASE,
         "--query", "currentServiceObjectiveName", "-o", "tsv"],
        capture_output=True, text=True, check=True
    )
    name = out.stdout.strip()  # e.g. "HS_Gen5_16"
    return int(name.rsplit("_", 1)[1])

def scale_to_vcores(vcores: int) -> None:
    tier = f"HS_Gen5_{vcores}"
    subprocess.run(
        ["az", "sql", "db", "update", "--resource-group", RESOURCE_GROUP,
         "--server", SERVER, "--name", DATABASE,
         "--service-objective", tier],
        check=True
    )
    logging.info(f"Scaled {DATABASE} to {tier}")

def throttle_background_jobs() -> None:
    """Pause non-critical batch work via a coordination table."""
    with pyodbc.connect(DB_CONN) as conn:
        cur = conn.cursor()
        cur.execute("""
            MERGE ops.scaling_signals AS tgt
            USING (SELECT 'background_throttle' AS signal_key) AS src
              ON tgt.signal_key = src.signal_key
            WHEN MATCHED THEN
                UPDATE SET signal_value = 'true',
                           updated_at = SYSUTCDATETIME()
            WHEN NOT MATCHED THEN
                INSERT (signal_key, signal_value, updated_at)
                VALUES ('background_throttle', 'true', SYSUTCDATETIME());
        """)
        conn.commit()
    logging.info("Background job throttle signal set")

def avg_log_write_pct_5min() -> float:
    rows = query("""
        SELECT AVG(avg_log_write_percent)
        FROM sys.dm_db_resource_stats
        WHERE end_time > DATEADD(MINUTE, -5, GETUTCDATE())
    """)
    return float(rows[0][0]) if rows and rows[0][0] is not None else 0.0

def autoscale_loop():
    global last_scale_time
    now = time.time()
    if (now - last_scale_time) < SCALE_COOLDOWN:
        logging.debug("Inside cooldown window — skipping scale evaluation")
        return

    cpu       = avg_cpu_pct_5min()
    log_write = avg_log_write_pct_5min()
    current   = current_vcores()
    idx       = TIERS.index(current)
    logging.info(f"CPU={cpu:.1f}%, log_write={log_write:.1f}%, vcores={current}")

    if cpu > SCALE_UP_CPU:
        if log_write > 90.0:
            # Log throughput is the bottleneck — more vCores will not help;
            # shed background load instead
            logging.warning(
                "High CPU but log write saturated — throttling background jobs"
            )
            throttle_background_jobs()
        elif idx < len(TIERS) - 1:
            scale_to_vcores(TIERS[idx + 1])
            last_scale_time = now
    elif cpu < SCALE_DOWN_CPU and idx > 0 and current > MIN_VCORES:
        scale_to_vcores(TIERS[idx - 1])
        last_scale_time = now

if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO)
    while True:
        autoscale_loop()
        time.sleep(60)

    The most significant lesson from this deployment was the interaction between tier-change latency and connection pool saturation. A vCore scale-up on Hyperscale required approximately 45–90 seconds to complete. During that window, if the spike was sharp enough, the application's connection pool would saturate and begin queuing. The mitigation was to throttle non-critical background jobs immediately — before the scale completed — so that queued connections had somewhere to land as soon as capacity arrived. The sequence mattered: shed load first, then scale.

    The second lesson was that the SCALE_COOLDOWN window needed to be asymmetric: 60 seconds for scale-up (to react quickly), 300 seconds for scale-down (to avoid thrashing when traffic declines slowly). A symmetric cooldown caused premature scale-down during the trailing edge of flash sales, requiring an immediate re-scale that itself triggered the cooldown again.

    Case Study 5: Autonomous Compliance Auditing and Remediation in a Financial Services SQL Server Deployment

    A regional bank's data engineering team operated SQL Server 2022 databases containing customer PII, transaction records, and loan origination data, subject to audit requirements from both their internal compliance framework and external regulatory guidance. Their pain point was not detection — they had extensive logging — but remediation latency: when a compliance violation was identified (a table without row-level security, an unencrypted backup path, a login with excessive GRANT permissions), the ticket-to-fix cycle averaged 11 business days due to approval workflows and DBA bandwidth.

    The autonomous compliance agent shortened this cycle by classifying violations into three tiers:

  • → Tier 1 (Auto-Remediate): Violations where the corrective action is reversible, low-risk, and pre-approved by the security team (e.g., revoking a PUBLIC schema execute permission, adding a column-level data mask).
  • → Tier 2 (Auto-Draft + Human Approve): Violations where the fix is known but the blast radius requires sign-off (e.g., adding a row-level security policy on tables with active sessions, revoking a role with 50+ dependent objects).
  • → Tier 3 (Alert Only): Violations requiring architectural judgment (e.g., an entire database missing TDE, a linked server to an unapproved external system).

    • The autonomous remediation procedures for Tier 1 violations:

    -- Tier 1 auto-remediation: revoke PUBLIC schema permissions
CREATE OR ALTER PROCEDURE Compliance.AutoRemediatePublicExposure
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @SchemaName SYSNAME, @TableName SYSNAME, @PrivName SYSNAME, @Sql NVARCHAR(MAX);

    DECLARE cur CURSOR LOCAL FAST_FORWARD FOR
        SELECT SchemaName, TableName, PrivilegeName
        FROM Compliance.PublicSchemaOverexposure;

    OPEN cur;
    FETCH NEXT FROM cur INTO @SchemaName, @TableName, @PrivName;
    WHILE @@FETCH_STATUS = 0
    BEGIN
        SET @Sql = N'REVOKE ' + QUOTENAME(@PrivName)
                 + N' ON ' + QUOTENAME(@SchemaName) + N'.' + QUOTENAME(@TableName)
                 + N' FROM PUBLIC';

        -- Audit before execution
        INSERT INTO Compliance.RemediationLog
            (ViolationType, ObjectIdentifier, ActionSql,
             Tier, RemediatedAt, InitiatedBy)
        VALUES
            ('public_schema_overexposure',
             @SchemaName + N'.' + @TableName,
             @Sql, 1, SYSUTCDATETIME(), 'autonomous-compliance-agent');

        EXEC sp_executesql @Sql;
        FETCH NEXT FROM cur INTO @SchemaName, @TableName, @PrivName;
    END
    CLOSE cur;
    DEALLOCATE cur;
END;

-- Enable row-level security on regulated tables
-- (Tier 1 only when no active sessions are touching the table)
CREATE OR ALTER PROCEDURE Compliance.AutoEnableRLSSafe
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @SchemaName SYSNAME, @TableName SYSNAME, @Active INT, @Sql NVARCHAR(MAX);

    DECLARE cur CURSOR LOCAL FAST_FORWARD FOR
        SELECT SchemaName, TableName
        FROM Compliance.TablesMissingRLS;

    OPEN cur;
    FETCH NEXT FROM cur INTO @SchemaName, @TableName;
    WHILE @@FETCH_STATUS = 0
    BEGIN
        -- Only auto-enable RLS if no active requests are touching this table
        SELECT @Active = COUNT(*)
        FROM sys.dm_exec_requests r
        JOIN sys.dm_tran_locks l
          ON l.request_session_id = r.session_id
        JOIN sys.partitions p
          ON p.hobt_id = l.resource_associated_entity_id
        JOIN sys.objects o
          ON o.object_id = p.object_id
        JOIN sys.schemas s
          ON s.schema_id = o.schema_id
        WHERE s.name = @SchemaName
          AND o.name = @TableName
          AND r.status = 'running';

        IF @Active = 0
        BEGIN
            SET @Sql = N'ALTER SECURITY POLICY '
                     + QUOTENAME(@SchemaName + N'_rls_policy')
                     + N' ADD FILTER PREDICATE Compliance.fn_SecurityPredicate(UserName)'
                     + N' ON ' + QUOTENAME(@SchemaName) + N'.' + QUOTENAME(@TableName);

            INSERT INTO Compliance.RemediationLog
                (ViolationType, ObjectIdentifier, ActionSql,
                 Tier, RemediatedAt, InitiatedBy)
            VALUES
                ('missing_rls', @SchemaName + N'.' + @TableName,
                 @Sql, 1, SYSUTCDATETIME(), 'autonomous-compliance-agent');

            EXEC sp_executesql @Sql;
        END
        ELSE
        BEGIN
            -- Escalate to Tier 2: table is active, needs human approval
            INSERT INTO Compliance.RemediationQueue
                (ViolationType, ObjectIdentifier, RecommendedSql,
                 Tier, QueuedAt, ApprovalStatus)
            VALUES
                ('missing_rls', @SchemaName + N'.' + @TableName,
                 N'ALTER SECURITY POLICY '
                 + QUOTENAME(@SchemaName + N'_rls_policy')
                 + N' ADD FILTER PREDICATE Compliance.fn_SecurityPredicate(UserName)'
                 + N' ON ' + QUOTENAME(@SchemaName) + N'.' + QUOTENAME(@TableName),
                 2, SYSUTCDATETIME(), 'pending');
        END
        FETCH NEXT FROM cur INTO @SchemaName, @TableName;
    END
    CLOSE cur;
    DEALLOCATE cur;
END;

    The Tier 2 workflow connected to the bank's internal approval platform via a webhook: once a record appeared in Compliance.RemediationQueue with ApprovalStatus = 'pending', a notification triggered a Teams approval message with a one-click approval button. Approved records updated ApprovalStatus = 'approved' and triggered the agent to execute the stored RecommendedSql. The average Tier 2 remediation time dropped from 11 business days to 6.2 hours — driven almost entirely by the pre-drafted SQL that security reviewers could read, approve, or reject without any DBA ticket creation or back-and-forth.

    The most important architectural lesson from this case study was the value of the RemediationLog table as a compliance artifact. External auditors could query the log to verify that violations were detected and remediated within specific SLA windows, with full SQL provenance. The autonomous system was not just faster — it was more auditable than the manual process, which relied on ticket comments and email threads that were difficult to correlate with actual database state changes.

    A secondary lesson was the necessity of scoping Tier 1 carefully. On the third week of deployment, the agent auto-revoked an EXECUTE permission on a stored procedure that a batch job had relied on for 4 years — a procedure that was not documented anywhere except a comment in the source code of a decommissioned internal tool. The batch job failed silently overnight. This prompted a refinement: Tier 1 actions now require the affected object to appear in a pre-approved object registry (Compliance.Tier1EligibleObjects) before autonomous action can proceed. The registry is maintained by DBAs and reviewed quarterly.

    Synthesis: Patterns Across All Five Deployments

    Examining the five case studies together, several design patterns appear consistently in autonomous DBA systems that survive production contact:

    1. Layered decision gates, not binary triggers

    Every deployment used a multi-stage decision process before acting. Detection triggered evaluation; evaluation triggered either autonomous action or escalation; action triggered verification. No deployment allowed a single metric threshold to directly trigger a destructive or irreversible change. The trading firm's three-poll failure threshold, the healthcare platform's 2.5x regression ratio, and the compliance agent's Tier 1/2/3 classification all embody this principle.

    2. Audit-first, act-second

    In every case, the system wrote an audit record before executing a change — not after. This ordering matters: if the execution fails mid-operation, the audit record still exists and contains the intended action, enabling forensic reconstruction. The SQL Server index agent, the compliance remediation procedure, and the plan stabilizer all follow this pattern.

    3. Asymmetric conservatism

    Autonomous systems consistently applied different thresholds for action versus inaction. The Kubernetes autoscaler used a 60-second cooldown for scale-up and a 300-second cooldown for scale-down. The compliance agent applied stricter preconditions to Tier 1 than to Tier 2 escalations (because Tier 1 executes without human review). Systems that used symmetric thresholds oscillated or over-acted.

    4. Human override surfaces, not human override requirements

    All five systems provided mechanisms for humans to override or inspect autonomous decisions without requiring humans to be in the critical path of every decision. The plan_override_registry, the remediation_queue, the tier1_eligible_objects registry, and the Slack approval workflow all represent designed override surfaces — places where human judgment can inject itself without breaking the automation loop.

    5. Production failure as design input

    The silent batch job failure from the compliance case, the replica provisioning lag from the Kubernetes autoscaler, and the schema-change-versus-data-drift distinction from the healthcare platform all led to architectural refinements that would not have been discoverable through any amount of upfront design. Each case study team built a feedback loop from production incidents back into the autonomous system's decision logic — not just into runbooks.

    Key Takeaways

  • → Autonomous systems earn trust through auditability, not just performance: every production deployment in this chapter succeeded in gaining organizational acceptance partly because the system's decisions were fully logged with provenance, enabling retrospective review by both engineers and external auditors.
  • → Detection signal quality determines autonomous system reliability more than remediation sophistication: the trading firm's heartbeat table outperformed the AG replica-state DMVs as a failure signal; the healthcare platform's regression ratio proved more stable than raw execution time comparisons; signal design deserves as much engineering attention as the remediation logic.
  • → The boundary between Tier 1 (auto-act) and Tier 2 (human-approve) actions must be defined by blast radius and reversibility, not by technical complexity: some technically simple actions (revoking a permission) have large blast radii; some technically complex actions (online index rebuild) are easily reversible. Conflating complexity with risk leads to either under-automation or over-automation.
  • → Cooldown windows and lag guards are not optional safety theater — they are architectural requirements: every case study that skipped or underestimated these guards experienced oscillation, thrashing, or a preventable failure before adding them back; asymmetric cooldowns (faster to engage protective action, slower to disengage it) consistently outperformed symmetric ones.
  • → The object registry pattern — maintaining a pre-approved list of objects eligible for autonomous action — is the practical solution to the scope creep problem in autonomous remediation systems: without it, autonomous agents inevitably encounter edge cases (undocumented dependencies, legacy objects, objects shared across teams) that cause silent failures; with it, the blast radius of any autonomous action is bounded and reviewable before deployment.
