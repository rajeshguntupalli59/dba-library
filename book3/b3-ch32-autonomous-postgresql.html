Chapter 32: Autonomous PostgreSQL Systems

PostgreSQL was never designed to manage itself — but the ecosystem that has grown around it over the past decade has quietly assembled every component necessary to build a fully autonomous system. Patroni handles HA decisions. pg_auto_failover handles topology changes. pgBouncer manages connection routing. Prometheus and Alertmanager observe and react. Kubernetes operators orchestrate lifecycle events. What most teams lack is not the tooling but the architecture that ties these components into a coherent decision-making system: one that observes its own state, reasons about degradation, and takes corrective action without a human in the loop. This chapter builds that architecture from the ground up, covering autonomous topology management, self-tuning memory and parallelism, automated vacuum and bloat remediation, connection intelligence, and the control-plane patterns that make human intervention the exception rather than the rule.

---

Autonomous Topology Management with Patroni and pg_auto_failover

The first requirement of any autonomous PostgreSQL system is that it knows, at all times, exactly what its topology looks like — and can reshape that topology without human involvement when conditions demand it. Two tools dominate this space: Patroni, which uses a distributed consensus store (etcd, Consul, or ZooKeeper) to manage leader election and replication state, and pg_auto_failover, which embeds topology logic directly into a monitor process that coordinates a simpler two- or three-node architecture. Each has its place.

Patroni is appropriate for clusters where topology complexity is high: multiple standbys, cascading replication, geographic distribution across availability zones, or integration with Kubernetes operators like the Zalando postgres-operator or CloudNativePG. pg_auto_failover is better suited for smaller, high-velocity deployments where simplicity and determinism matter more than flexibility.

The autonomous pattern requires not just failover capability but *policy-driven* failover — the system must decide when to fail over based on observable signals, not just a timeout. A naive timeout-based failover system will promote a standby that has fallen behind due to network partition, producing a split-brain scenario or data loss. An autonomous system checks replication lag, WAL streaming state, and synchronous commit configuration before making a promotion decision.

In a Patroni-managed cluster, the DCS (distributed configuration store) is the source of truth. The following illustrates how to query the current cluster state programmatically, which forms the basis for any autonomous control plane decision:

import requests
import json

PATRONI_API = "http://patroni-primary:8008"

def get_cluster_state():
    response = requests.get(f"{PATRONI_API}/cluster", timeout=5)
    state = response.json()
    members = state.get("members", [])
    topology = {}
    for member in members:
        topology[member["name"]] = {
            "role": member["role"],
            "state": member["state"],
            "lag": member.get("lag", 0),
            "timeline": member.get("timeline"),
            "host": member["host"],
        }
    return topology

def evaluate_failover_eligibility(topology):
    eligible = []
    for name, info in topology.items():
        if info["role"] == "replica" and info["state"] == "running":
            if info["lag"] is not None and info["lag"] < 10485760:  # 10 MB lag threshold
                eligible.append((name, info["lag"]))
    return sorted(eligible, key=lambda x: x[1])

topology = get_cluster_state()
candidates = evaluate_failover_eligibility(topology)
print(f"Failover candidates by lag: {candidates}")

This decision logic — promote the replica with the lowest lag that is below an acceptable threshold — replaces the human judgment call that most teams make manually during an incident. The autonomous system runs this evaluation continuously and can trigger a patronictl switchover or patronictl failover via the REST API when the primary health check fails.

For clusters using pg_auto_failover, the monitor node exposes its own state machine. The autonomous controller subscribes to state transitions and enforces policy constraints before allowing promotion to proceed:

-- Equivalent: query AG replica status for autonomous evaluation
SELECT
    ag.name AS ag_name,
    ar.replica_server_name,
    ars.role_desc,
    ars.operational_state_desc,
    ars.connected_state_desc,
    ars.synchronization_health_desc,
    ars.last_commit_time,
    drs.synchronization_state_desc,
    drs.log_send_queue_size,
    drs.redo_queue_size
FROM sys.availability_groups ag
JOIN sys.availability_replicas ar ON ag.group_id = ar.group_id
JOIN sys.dm_hadr_availability_replica_states ars ON ar.replica_id = ars.replica_id
LEFT JOIN sys.dm_hadr_database_replica_states drs ON ar.replica_id = drs.replica_id
ORDER BY ag.name, ars.role_desc;

A mature autonomous topology system also enforces a *failover budget* — a maximum number of automated failovers permitted within a rolling time window. This prevents cascading failures caused by a flapping primary from triggering repeated promotions, each of which carries its own risk. The control plane should record every topology change in an immutable audit log, decrement from the budget, and escalate to human on-call if the budget is exhausted. Autonomy does not mean recklessness; it means that routine, well-understood failures are resolved without human latency.

Self-Tuning Memory, Parallelism, and Configuration Drift Correction

PostgreSQL's performance is governed by a relatively small set of configuration parameters — shared_buffers, work_mem, effective_cache_size, max_parallel_workers_per_gather, wal_buffers, checkpoint_completion_target — but the optimal values for these parameters shift as workloads change. A database serving an OLTP workload at 09:00 may be processing large analytical aggregations by 23:00. A static postgresql.conf will be wrong for both.

Autonomous configuration management addresses this through *workload fingerprinting* and *parameter policy enforcement*. The system continuously profiles the running workload, classifies it against known archetypes, and adjusts parameters within defined safety bounds using ALTER SYSTEM — which writes to postgresql.auto.conf and survives restarts without touching the managed configuration baseline.

The workload fingerprinting logic queries pg_stat_statements and derives a workload signature:

-- Equivalent workload classification from DMVs
SELECT
    SUM(user_seeks + user_scans + user_lookups) AS total_reads,
    SUM(user_scans) AS full_scans,
    SUM(user_seeks) AS index_seeks,
    ROUND(100.0 * SUM(user_scans) /
        NULLIF(SUM(user_seeks + user_scans + user_lookups), 0), 2) AS pct_full_scans,
    SUM(range_scan_count) AS range_scans,
    SUM(singleton_lookup_count) AS point_lookups
FROM sys.dm_db_index_usage_stats
WHERE database_id = DB_ID();

When pct_seq_scan exceeds 60 percent combined with a buffer hit ratio below 85 percent, the system classifies the workload as analytically dominated and triggers a parameter adjustment pass. The automation increases effective_cache_size to reflect available OS page cache, raises work_mem for sort-heavy operations, and increases max_parallel_workers_per_gather toward the defined ceiling.

The critical discipline here is *bounded autonomy*: the system may never set shared_buffers above 40 percent of total system RAM, work_mem beyond a per-session ceiling that would exhaust memory under maximum connection count, or max_parallel_workers beyond the number of available CPU cores minus two (reserved for maintenance tasks). These bounds are encoded as policy, not as hardcoded values, so they can be updated through the configuration management plane without touching the automation code.

Configuration drift — the condition where postgresql.conf, postgresql.auto.conf, and runtime SHOW values have diverged from the declared policy baseline — must be detected and remediated automatically. The following illustrates an autonomous drift detection pass:

import subprocess
import psycopg2

POLICY_BASELINE = {
    "shared_buffers": "4GB",
    "work_mem": "64MB",
    "checkpoint_completion_target": "0.9",
    "wal_compression": "on",
    "max_parallel_workers_per_gather": "4",
}

def check_config_drift(conn_str: str) -> dict:
    conn = psycopg2.connect(conn_str)
    cur = conn.cursor()
    drift = {}
    for param, expected in POLICY_BASELINE.items():
        cur.execute("SHOW %s" % param)
        actual = cur.fetchone()[0]
        if actual != expected:
            drift[param] = {"expected": expected, "actual": actual}
    cur.close()
    conn.close()
    return drift

def remediate_drift(conn_str: str, drift: dict):
    conn = psycopg2.connect(conn_str)
    cur = conn.cursor()
    for param, values in drift.items():
        print(f"Correcting {param}: {values['actual']} -> {values['expected']}")
        cur.execute(f"ALTER SYSTEM SET {param} = %s", (values["expected"],))
    conn.commit()
    cur.execute("SELECT pg_reload_conf()")
    conn.commit()
    cur.close()
    conn.close()

drift = check_config_drift("host=pg-primary dbname=postgres user=automation")
if drift:
    remediate_drift("host=pg-primary dbname=postgres user=automation", drift)

This pattern runs as a scheduled job — every 15 minutes in production environments — and reports any remediations to the audit log with before/after values and timestamps. Parameters that require a restart rather than a reload are flagged but not automatically applied; they are queued for execution during the next maintenance window, which the autonomous scheduler determines based on traffic patterns derived from connection pool metrics.

Autonomous Vacuum Management and Bloat Remediation

Autovacuum is PostgreSQL's built-in mechanism for reclaiming dead tuples and maintaining planner statistics, but its default configuration is conservative. Left unmanaged, high-write OLTP tables will accumulate dead tuple bloat that degrades query performance, inflates table sizes, and — in the most severe case involving transaction ID wraparound — causes the database to enter read-only mode and refuse new connections. An autonomous system cannot tolerate any of these outcomes.

The autonomous vacuum controller operates on two tiers: reactive (responding to tables that have already exceeded bloat or dead tuple thresholds) and proactive (adjusting autovacuum parameters per-table based on observed write velocity before problems develop). Most teams only implement the reactive tier. The proactive tier is what distinguishes a truly autonomous system.

The foundation is a continuous dead tuple monitor that queries pg_stat_user_tables and cross-references with actual table sizes to compute a dead tuple ratio and an estimated bloat percentage:

-- SQL Server equivalent: index fragmentation as the analog to dead tuple bloat
SELECT
    OBJECT_SCHEMA_NAME(ips.object_id) AS schema_name,
    OBJECT_NAME(ips.object_id) AS table_name,
    i.name AS index_name,
    ips.index_type_desc,
    ROUND(ips.avg_fragmentation_in_percent, 2) AS fragmentation_pct,
    ips.page_count,
    ips.record_count,
    CASE
        WHEN ips.avg_fragmentation_in_percent > 30 THEN 'REBUILD'
        WHEN ips.avg_fragmentation_in_percent > 10 THEN 'REORGANIZE'
        ELSE 'OK'
    END AS recommended_action
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') ips
JOIN sys.indexes i ON ips.object_id = i.object_id AND ips.index_id = i.index_id
WHERE ips.page_count > 1000
ORDER BY ips.avg_fragmentation_in_percent DESC;

When a table enters CRITICAL status, the autonomous controller evaluates whether to issue a manual VACUUM (non-blocking, reclaims dead tuples), VACUUM ANALYZE (reclaim plus statistics refresh), or VACUUM FULL (full rewrite, takes an exclusive lock — almost never appropriate in a live system). For tables where bloat has reached a structural level — the actual physical size has diverged significantly from the expected live-data size — the system invokes pg_repack via a background job, which performs the equivalent of VACUUM FULL without taking an exclusive lock.

The proactive tier is more subtle. For each high-write table, the system sets storage parameters directly to override autovacuum defaults:

-- Autonomous per-table autovacuum tuning for a high-write events table
ALTER TABLE events SET (
    autovacuum_vacuum_scale_factor = 0.01,    -- vacuum at 1% dead tuples (vs default 20%)
    autovacuum_analyze_scale_factor = 0.005,  -- analyze at 0.5% changes
    autovacuum_vacuum_cost_delay = 2,         -- ms; more aggressive than default 20ms
    autovacuum_vacuum_insert_scale_factor = 0.05
);

The automation derives these values dynamically: for a table receiving more than 50,000 writes per hour, autovacuum_vacuum_scale_factor is set to 0.01; above 500,000 writes per hour, it is set to 0.001. The autovacuum_vacuum_cost_delay is inversely proportional to available I/O headroom as measured from the storage layer metrics. If the system is under I/O pressure, cost delay increases to reduce autovacuum's I/O footprint; when I/O is available, it decreases to allow faster cleanup.

Transaction ID wraparound — where a database approaches the 2-billion transaction ID limit and PostgreSQL begins emitting "database is not accepting commands" errors — is a failure that should never reach production in an autonomous system. The controller monitors age(datfrozenxid) against a tiered alert schedule: at 500 million transactions of age, it increases autovacuum aggressiveness; at 1 billion, it triggers a forced VACUUM FREEZE on the affected tables; at 1.5 billion, it pages the on-call team regardless of the failover budget because this condition requires human decision-making about maintenance windows.

Connection Intelligence: pgBouncer Autonomous Routing and Pool Sizing

Connection management is one of the most visible failure modes in PostgreSQL under load. Each PostgreSQL backend is an OS process consuming memory; at hundreds or thousands of direct connections, the overhead of context switching and memory pressure degrades performance for everyone. pgBouncer sits in front of PostgreSQL and multiplexes application connections onto a smaller pool of actual database connections — but a static pgBouncer configuration becomes a bottleneck as workloads evolve.

An autonomous connection management layer continuously monitors pool utilization, client wait times, and backend saturation, and adjusts pgBouncer configuration dynamically. pgBouncer exposes a management interface via a pseudo-database called pgbouncer that accepts control commands at runtime:

The autonomous pool controller interprets these metrics and applies the following decision logic: if cl_waiting exceeds 5 percent of cl_active for more than 30 consecutive seconds, pool_size is incremented by 10 percent, subject to a maximum that is calculated from max_connections minus reserved connections for administrative access and autovacuum workers. If sv_idle exceeds 40 percent of pool_size for more than 5 minutes, the pool is shrunk by 10 percent to reclaim backend resources. This hysteresis — requiring a sustained condition before acting, and acting conservatively in both directions — prevents the pool from oscillating continuously.

Autonomous routing adds another dimension: the connection layer should direct read-only queries to standby replicas when replication lag is below an acceptable threshold, and fall back to the primary when standbys are lagging or unavailable. HAProxy or Nginx can perform this routing based on health check endpoints exposed by Patroni (/master and /replica), but a more intelligent implementation uses a connection proxy that is aware of the query intent and the current replication state:

import psycopg2
import requests

PATRONI_PRIMARY = "http://pg-node-1:8008"
PATRONI_REPLICA_1 = "http://pg-node-2:8008"

PRIMARY_DSN = "host=pg-node-1 port=5432 dbname=app user=app_user"
REPLICA_DSN = "host=pg-node-2 port=5432 dbname=app user=app_user options=-c default_transaction_read_only=on"
MAX_ACCEPTABLE_LAG_BYTES = 5 * 1024 * 1024  # 5 MB

def get_replica_lag_bytes(patroni_url: str) -> int:
    try:
        resp = requests.get(f"{patroni_url}/patroni", timeout=2)
        data = resp.json()
        return data.get("replication", [{}])[0].get("sent_lsn", 0)
    except Exception:
        return float("inf")

def get_connection(read_only: bool = False) -> psycopg2.extensions.connection:
    if read_only:
        lag = get_replica_lag_bytes(PATRONI_REPLICA_1)
        if lag < MAX_ACCEPTABLE_LAG_BYTES:
            try:
                return psycopg2.connect(REPLICA_DSN)
            except Exception:
                pass  # fall through to primary
    return psycopg2.connect(PRIMARY_DSN)

This routing logic is the foundation of a connection intelligence layer. In production, it runs inside a pgBouncer-adjacent sidecar or a lightweight connection routing service, and the lag threshold itself is tunable per application tier: analytics applications can tolerate 60 seconds of replica lag; payment processing applications must use the primary exclusively.

Autonomous Index Management: Creation, Elimination, and Consolidation

Index sprawl is one of the most common performance debt patterns in mature PostgreSQL installations. Tables accumulate indexes added reactively during incidents, never revisited afterward. Write performance degrades as every index must be maintained on INSERT and UPDATE. Query plans become unpredictable as the optimizer weighs an expanding set of options. An autonomous index management system approaches this problem from both ends: identifying missing indexes that would improve query performance, and identifying existing indexes that are unused, duplicated, or partially redundant.

The missing index signal comes primarily from pg_stat_statements combined with EXPLAIN plan analysis. When a query with high total_time shows sequential scans on large tables, the autonomous system generates a candidate index, validates it on a standby using EXPLAIN (not EXPLAIN ANALYZE — we never run the query again just to test), and scores it against the existing index set for redundancy:

-- Missing index recommendations from Query Store and DMVs
SELECT TOP 20
    migs.avg_total_user_cost * migs.avg_user_impact * (migs.user_seeks + migs.user_scans)
        AS improvement_measure,
    mid.statement AS table_name,
    mid.equality_columns,
    mid.inequality_columns,
    mid.included_columns,
    migs.user_seeks,
    migs.user_scans,
    migs.last_user_seek,
    ROUND(migs.avg_total_user_cost, 2) AS avg_query_cost,
    ROUND(migs.avg_user_impact, 2) AS avg_impact_pct,
    'CREATE INDEX IX_auto_' +
        REPLACE(REPLACE(mid.statement, '[', ''), ']', '') +
        '_' + CONVERT(varchar, mig.index_handle) AS suggested_index_ddl
FROM sys.dm_db_missing_index_groups mig
JOIN sys.dm_db_missing_index_group_stats migs ON mig.index_group_handle = migs.group_handle
JOIN sys.dm_db_missing_index_details mid ON mig.index_handle = mid.index_handle
WHERE migs.avg_total_user_cost * migs.avg_user_impact * (migs.user_seeks + migs.user_scans) > 1000
ORDER BY improvement_measure DESC;

Unused index detection is more straightforward — PostgreSQL tracks index scans, tuple reads, and tuple fetches per index since the last statistics reset. Any index with zero scans since the last reset (which should cover at least one full week of representative workload) is a candidate for elimination:

-- Unused indexes in SQL Server
SELECT
    OBJECT_SCHEMA_NAME(i.object_id) AS schema_name,
    OBJECT_NAME(i.object_id) AS table_name,
    i.name AS index_name,
    i.type_desc,
    ISNULL(us.user_seeks, 0) AS user_seeks,
    ISNULL(us.user_scans, 0) AS user_scans,
    ISNULL(us.user_lookups, 0) AS user_lookups,
    ISNULL(us.user_seeks + us.user_scans + us.user_lookups, 0) AS total_reads,
    ISNULL(us.user_updates, 0) AS user_updates,
    ps.used_page_count * 8 / 1024 AS index_size_mb
FROM sys.indexes i
LEFT JOIN sys.dm_db_index_usage_stats us
    ON i.object_id = us.object_id
    AND i.index_id = us.index_id
    AND us.database_id = DB_ID()
JOIN sys.dm_db_partition_stats ps
    ON i.object_id = ps.object_id
    AND i.index_id = ps.index_id
WHERE i.type_desc NOT IN ('HEAP', 'CLUSTERED')
  AND i.is_primary_key = 0
  AND i.is_unique_constraint = 0
  AND ISNULL(us.user_seeks + us.user_scans + us.user_lookups, 0) < 10
  AND ps.used_page_count * 8 / 1024 > 10
ORDER BY user_updates DESC, index_size_mb DESC;

The autonomous index manager never drops an index immediately. The workflow follows a three-phase safety protocol:

Phase 1 — Marking. The index is renamed with an _autonomous_drop_candidate_YYYYMMDD suffix. This change is visible to the DBA team, is logged, and does not affect query execution.

Phase 2 — Observation. The system waits for a configurable dwell period — typically 7 to 14 days — while monitoring whether any query plan in pg_stat_statements shows a regression in mean_exec_time or total_exec_time. If a regression is detected that correlates temporally with the marking, the index is automatically unmarked and restored to its original name, and the incident is recorded.

Phase 3 — Removal. After the dwell period with no regression, the index is dropped during a low-traffic window. The DDL is preserved in the audit log so it can be recreated manually if needed.

For duplicate index detection — where two indexes cover the same leading columns — the system queries pg_index and pg_attribute to compare column lists:

-- Detect duplicate and prefix-duplicate indexes in PostgreSQL
WITH index_columns AS (
    SELECT
        i.indrelid::regclass AS table_name,
        c.relname AS index_name,
        i.indisunique,
        i.indisprimary,
        array_agg(a.attname ORDER BY pos.ord) AS columns
    FROM pg_index i
    JOIN pg_class c ON c.oid = i.indexrelid
    JOIN pg_class t ON t.oid = i.indrelid
    JOIN LATERAL unnest(i.indkey) WITH ORDINALITY AS pos(attnum, ord) ON TRUE
    JOIN pg_attribute a ON a.attrelid = i.indrelid AND a.attnum = pos.attnum
    WHERE t.relkind = 'r'
      AND NOT i.indisprimary
    GROUP BY i.indrelid, c.relname, i.indisunique, i.indisprimary
),
duplicates AS (
    SELECT
        a.table_name,
        a.index_name AS index_a,
        b.index_name AS index_b,
        a.columns AS columns_a,
        b.columns AS columns_b
    FROM index_columns a
    JOIN index_columns b
        ON a.table_name = b.table_name
        AND a.index_name < b.index_name
        AND (
            a.columns = b.columns
            OR a.columns[1:array_length(b.columns, 1)] = b.columns
            OR b.columns[1:array_length(a.columns, 1)] = a.columns
        )
)
SELECT * FROM duplicates ORDER BY table_name;

When duplicates are found, the system keeps the more selective index (or the one with more recent scan activity) and queues the other for the three-phase elimination workflow described above.

Query Plan Stability and Autonomous Plan Management

Query plan regression is one of the most disruptive events in a production PostgreSQL environment. A statistics refresh, a new index, an autovacuum run on a recently modified table, or a PostgreSQL minor version upgrade can all cause the planner to choose a different execution plan — one that may be dramatically slower than the previous one. An autonomous system needs to detect plan regressions as they occur and respond before they cascade into user-visible latency.

PostgreSQL does not natively support plan freezing (SQL Server's Query Store plan forcing is the closest analog), but pg_hint_plan provides a mechanism to inject planner hints at query execution time, effectively overriding the optimizer's decisions. The autonomous plan manager uses this as a corrective tool, not a permanent configuration: when a regression is detected, a hint is applied; when the underlying statistics issue is resolved (by a targeted ANALYZE), the hint is removed and the system verifies the planner chooses the correct plan natively.

The regression detection logic operates on pg_stat_statements, comparing rolling average execution times against a historical baseline:

from dataclasses import dataclass
from datetime import datetime, timedelta
from typing import Optional
import psycopg2

@dataclass
class QueryBaseline:
    queryid: int
    query_fingerprint: str
    baseline_mean_ms: float
    baseline_stddev_ms: float
    recorded_at: datetime

REGRESSION_THRESHOLD_MULTIPLIER = 3.0  # flag if mean > 3x baseline

def detect_plan_regressions(conn_str: str, baselines: list[QueryBaseline]) -> list[dict]:
    conn = psycopg2.connect(conn_str)
    cur = conn.cursor()
    regressions = []

    for baseline in baselines:
        cur.execute("""
            SELECT
                mean_exec_time,
                stddev_exec_time,
                calls
            FROM pg_stat_statements
            WHERE queryid = %s
        """, (baseline.queryid,))
        row = cur.fetchone()
        if row is None:
            continue
        current_mean, current_stddev, calls = row
        if calls < 50:
            continue  # insufficient sample
        threshold = baseline.baseline_mean_ms * REGRESSION_THRESHOLD_MULTIPLIER
        if current_mean > threshold:
            regressions.append({
                "queryid": baseline.queryid,
                "baseline_mean_ms": baseline.baseline_mean_ms,
                "current_mean_ms": current_mean,
                "degradation_factor": round(current_mean / baseline.baseline_mean_ms, 2),
                "calls": calls,
            })

    cur.close()
    conn.close()
    return regressions

When a regression is detected, the autonomous system performs three immediate actions:

1. Targeted ANALYZE. Run ANALYZE on the tables involved in the regressed query's most recently observed plan. Fresh statistics frequently resolve planner regressions caused by stale row-count estimates.

2. Plan capture. Use EXPLAIN (FORMAT JSON) to capture the current plan and compare it structurally to the last known good plan stored in the baseline catalog. If the plan structure has changed (for example, a nested loop replaced a hash join), the change is recorded as the probable cause.

3. Hint injection. If the targeted ANALYZE does not resolve the regression within two evaluation cycles (typically 10 minutes), pg_hint_plan is used to enforce the last-known-good join order and scan method. The hint is stored in the hint_plan.hints management table that the pg_hint_plan extension reads at parse time.

PostgreSQL (pg_hint_plan table insertion):

-- Inject a stabilizing hint for a regressed query
INSERT INTO hint_plan.hints (norm_query_string, application_name, hints)
VALUES (
    'SELECT * FROM orders o JOIN customers c ON o.customer_id = c.id WHERE o.status = $1',
    '',  -- apply to all application connections
    'HashJoin(o c) SeqScan(o) IndexScan(c)'
);

SQL Server (Query Store plan forcing — native capability):

-- Force a specific plan in SQL Server Query Store
USE app_database;

-- Find the last known good plan for a query
SELECT
    qsq.query_id,
    qsp.plan_id,
    qsp.last_execution_time,
    qsp.avg_duration / 1000.0 AS avg_duration_ms,
    qsp.count_executions
FROM sys.query_store_query qsq
JOIN sys.query_store_plan qsp ON qsq.query_id = qsp.query_id
JOIN sys.query_store_runtime_stats qsrs ON qsp.plan_id = qsrs.plan_id
WHERE qsq.query_hash = 0x <your_query_hash>
ORDER BY qsp.last_execution_time DESC;

-- Force the last known good plan
EXEC sys.sp_query_store_force_plan
    @query_id = <query_id>,
    @plan_id = <last_known_good_plan_id>;

The autonomous plan manager maintains a plan stability catalog — a table recording every queryid, its baseline execution profile, the last forced hint (if any), and the timestamp of the last regression event. This catalog is the input to a weekly plan health report that surfaces queries that have required intervention, allowing the DBA team to address root causes (missing statistics targets, poor histogram column coverage, correlation statistics) rather than relying on hints indefinitely.

The Autonomous Control Plane: Event Loop, Audit, and Human Escalation

All of the autonomous behaviors described in the preceding sections — topology management, configuration tuning, vacuum remediation, connection routing, index management, plan stability enforcement — must be coordinated through a unified control plane. Without coordination, autonomous subsystems can conflict: the connection pool scaler may increase pool size at the same moment the configuration tuner is reducing max_connections, for example. The control plane is the arbitration layer that prevents such conflicts, enforces action budgets, and determines when autonomy must give way to human judgment.

The control plane architecture has five components:

1. The Observation Bus. A continuous stream of metric events ingested from Prometheus, pg_stat_* views, Patroni API, pgBouncer admin, and OS-level metrics (CPU, memory, I/O wait). Events are normalized into a common schema and written to a time-series buffer.

2. The Rule Engine. A set of declarative rules — encoded as YAML or in a domain-specific policy language — that map observation patterns to candidate actions. Rules are versioned and auditable.

3. The Action Queue. A prioritized queue of candidate actions. Before any action is dequeued and executed, it is evaluated for conflicts against currently executing actions, checked against the relevant budget (failover budget, vacuum budget, DDL budget), and logged with a pre-execution fingerprint.

4. The Executor. The component that actually runs actions: calling Patroni APIs, issuing ALTER SYSTEM, invoking pg_repack, updating pgBouncer configuration, inserting into hint_plan.hints. The executor is the only component with write access to the database infrastructure.

5. The Escalation Manager. When budgets are exhausted, when actions fail, when contradictory signals make autonomous decision-making unsafe, or when a pre-defined confidence threshold is not met, the escalation manager creates an incident in the team's alerting system (PagerDuty, Opsgenie, or equivalent) with a structured context payload that tells the on-call engineer exactly what the system observed, what it tried, and why it stopped.

*The five-component control plane: every candidate action passes through budget and conflict checks before execution, and the inhibit table can halt the executor at any time regardless of what the rule engine proposes.*

The audit log is equally critical. Every action taken by the autonomous system — whether successful or not — is written to an append-only audit table:

-- Autonomous action audit log schema
CREATE TABLE autonomous_actions (
    action_id       BIGSERIAL PRIMARY KEY,
    action_time     TIMESTAMPTZ NOT NULL DEFAULT now(),
    component       TEXT NOT NULL,
    cluster_name    TEXT NOT NULL,
    action_type     TEXT NOT NULL,
    target_object   TEXT,
    parameters      JSONB,
    pre_state       JSONB,
    post_state      JSONB,
    result          TEXT NOT NULL CHECK (result IN ('success', 'failed', 'skipped', 'escalated')),
    error_detail    TEXT,
    triggered_by    TEXT NOT NULL  -- 'rule:vacuum_critical', 'rule:config_drift', etc.
);

CREATE INDEX ON autonomous_actions (action_time DESC);
CREATE INDEX ON autonomous_actions (component, action_time DESC);
CREATE INDEX ON autonomous_actions (cluster_name, result, action_time DESC);

This table serves two purposes beyond auditability: it is the input to the budget enforcement calculation (counting actions of each type within a rolling window), and it feeds the weekly operational review that should be part of every team running an autonomous system. That review asks not only "what did the system fix?" but "what should the system have fixed but didn't, and why?"

The question of human override is non-negotiable. Every autonomous action type must have a corresponding inhibit mechanism: a flag in a control table, a Patroni tag, a pgBouncer PAUSE command, or an environment variable read at action evaluation time. When an operator sets an inhibit flag, the relevant subsystem stops acting autonomously and escalates all decisions immediately. This is the emergency brake, and it must be reliable, fast, and well-documented.

-- Autonomous control inhibit table
CREATE TABLE autonomous_inhibits (
    inhibit_id      SERIAL PRIMARY KEY,
    component       TEXT NOT NULL,   -- 'vacuum_controller', 'topology_manager', 'ALL'
    cluster_name    TEXT NOT NULL,
    inhibited_by    TEXT NOT NULL,
    inhibit_reason  TEXT NOT NULL,
    inhibit_start   TIMESTAMPTZ NOT NULL DEFAULT now(),
    inhibit_until   TIMESTAMPTZ,     -- NULL means indefinite
    released_at     TIMESTAMPTZ
);

-- Check function used by all autonomous components before taking action
CREATE OR REPLACE FUNCTION is_autonomous_action_inhibited(
    p_component TEXT,
    p_cluster   TEXT
) RETURNS BOOLEAN AS $$
    SELECT EXISTS (
        SELECT 1 FROM autonomous_inhibits
        WHERE (component = p_component OR component = 'ALL')
          AND cluster_name = p_cluster
          AND released_at IS NULL
          AND (inhibit_until IS NULL OR inhibit_until > now())
    );
$$ LANGUAGE sql STABLE;

Every autonomous component calls is_autonomous_action_inhibited() before executing any action. If it returns true, the action is logged with result skipped and the escalation manager is notified. This single check is the integration point between human judgment and automated execution — simple, auditable, and reliable under all conditions.

---

Key Takeaways

  • → **Autonomous topology management requires policy-driven failover**, not timeout-based failover. Evaluating replication lag, synchronous commit state, and WAL streaming continuity before promoting a replica prevents the data loss and split-brain scenarios that naive automation produces. Failover budgets — maximum automated promotions within a rolling window — prevent cascading failures from spiraling beyond recovery.
  • → **Self-tuning configuration requires bounded autonomy with workload fingerprinting.** `ALTER SYSTEM` allows parameter changes that survive restart without touching managed configuration baselines, but every parameter must be bounded by policy — memory fractions, CPU counts, and connection limits — that the automation enforces without exception. Configuration drift detection closes the loop, ensuring that actual runtime values converge on declared policy rather than drifting silently.
  • → **Vacuum management operates on two tiers: reactive remediation and proactive per-table tuning.** The reactive tier responds to accumulated dead tuples and bloat; the proactive tier adjusts `autovacuum_vacuum_scale_factor` and cost delay parameters per table based on observed write velocity, preventing problems before they require intervention. Transaction ID wraparound monitoring with tiered alert thresholds ensures this failure mode is addressed with days of runway rather than minutes.
  • → **Index management in an autonomous system follows a three-phase safety protocol**: mark, observe, remove. Immediate index drops — even for provably unused indexes — carry operational risk. The dwell period with regression monitoring converts a high-risk manual operation into a low-risk automated one. Duplicate index detection and the missing index signal from `pg_stat_statements` combined with execution plan analysis complete the index lifecycle management loop.
  • → **The autonomous control plane is the architecture that makes individual autonomous subsystems safe to operate together.** The observation bus, rule engine, action queue, executor, and escalation manager form a coherent decision-making system. The audit log and inhibit mechanism are not optional add-ons — they are the foundation of operator trust in the system. Autonomy earns its place in production by making human intervention the exception and by being completely transparent about every decision it makes.
