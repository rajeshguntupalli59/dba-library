Chapter 32: Azure SQL Autonomous Services: Serverless, Managed Instance, and Control-Plane Operations

Every autonomous system you build on SQL Server operates inside a platform that is already making autonomous decisions. Azure SQL Database pauses compute when it is idle, scales vCores up and down under load, applies automatic plan corrections when regressions appear, and creates or drops indexes on its own authority. Azure SQL Managed Instance moves your database between service tiers, patches the underlying host without your involvement, and fails over to a secondary when hardware degrades. If your autonomous database engine does not understand what the platform is doing — and, more importantly, does not coordinate with it — the two layers will fight. This chapter maps the autonomous services Azure SQL provides, shows how to observe and configure each one, and builds the coordination layer that lets your ADE and the platform's control plane share responsibility without conflicting.

The distinction matters because the previous chapters built autonomy from scratch: agents, policy engines, DMV-driven sensors. That model fits SQL Server running on virtual machines or on-premises, where you own every decision. On Azure SQL, roughly half of those decisions are already handled by the control plane. The DBA's job shifts from building every autonomous behavior to curating the platform's autonomous behaviors — enabling what helps, bounding what risks, and filling the gaps the platform deliberately leaves open.

The Platform Autonomy Layer: What Azure SQL Decides for You

Before coordinating with the platform, you need an accurate inventory of what it does autonomously. The Azure SQL control plane operates at a different layer than your database engine agents: it manages the compute, storage, and availability substrate. Your agents manage the workload inside the database. The boundary between the two is the service tier contract — and every conflict between your ADE and the platform can be traced to an action that crossed that boundary in the wrong direction.

The platform's autonomous decisions fall into five categories:

1. Compute lifecycle: serverless auto-pause and auto-resume, automatic vCore scaling in the serverless and Hyperscale tiers, and elastic pool resource balancing across member databases.

2. Performance tuning: automatic plan correction (plan forcing through the Query Store interface), automatic index management (create and drop), and adaptive query processing features that are enabled by default.

3. Availability: automatic failover within the availability zone or region, failover groups with automatic geo-failover policies, and zone-redundant configurations that the control plane maintains without operator input.

4. Maintenance: patching of the underlying host and SQL Server build, driven by maintenance window policies you configure but do not execute.

5. Backup and retention: automated full, differential, and log backups on a platform schedule, with long-term retention policies that run as background control-plane operations.

Your ADE owns everything inside the database that the platform explicitly does not: workload classification, custom index strategies beyond the platform's conservative heuristics, query governance, capacity forecasting tied to business events, and any decision that requires knowledge of your application's intent. The coordination rule is simple to state and difficult to enforce: never let both layers tune the same knob. If automatic index management is enabled, your index-creation agent must not create indexes on the same tables. If the platform owns plan forcing, your plan-forcing agent must defer. The rest of this chapter builds the mechanisms that enforce that rule.

Serverless: Auto-Pause, Auto-Scaling, and the DBA's New Job

The serverless compute tier is the most visibly autonomous surface in Azure SQL. A serverless database pauses itself after a configurable period of inactivity — typically one hour — and resumes automatically when a new connection arrives. While running, it scales compute between a configured minimum and maximum vCore count based on demand. The DBA configures the envelope; the platform makes every decision inside it.

For the ADE, serverless introduces a new operational reality: the database can be absent. Any agent that polls DMVs on a schedule must handle the paused state gracefully — a connection attempt to a paused database triggers auto-resume, which takes 30–60 seconds, and a naive health check will report the database as down during that window. The correct pattern is to query the control plane's view of database state before attempting a data-plane connection:

-- Check whether a serverless database is paused before connecting
-- Runs against the master database of the logical server
SELECT
    d.name                                AS database_name,
    d.state_desc,
    DATABASEPROPERTYEX(d.name, 'Status')   AS detailed_status
FROM sys.databases d
WHERE d.name = N'OrdersDB';

The auto-pause delay itself is an autonomous policy decision the DBA configures. Setting it too short means frequent pause/resume cycles — each resume incurs latency and the first queries after resume face a cold buffer pool. Setting it too long wastes the cost advantage that justifies serverless. The ADE can manage this setting as a control-plane action, adjusting the pause delay based on observed connection patterns:

# Adjust serverless auto-pause delay from observed idle patterns
import pyodbc
import subprocess

def recommend_pause_delay(conn_str: str, database: str) -> int:
    """Analyze connection gaps; return recommended auto-pause delay in minutes."""
    with pyodbc.connect(conn_str) as conn:
        cur = conn.cursor()
        cur.execute("""
            SELECT DATEDIFF(MINUTE, MAX(login_time), SYSUTCDATETIME())
            FROM sys.dm_exec_sessions
            WHERE database_id = DB_ID(?)
              AND is_user_process = 1
        """, (database,))
        row = cur.fetchone()
        longest_recent_idle_min = row[0] if row and row[0] else 0

    # If the longest recent idle gap is well under the current delay,
    # the delay can be shortened without causing resume storms.
    if longest_recent_idle_min < 30:
        return 60     # keep default: workload is bursty, avoid resume latency
    elif longest_recent_idle_min > 240:
        return 120    # long idle stretches: pause sooner, save cost
    return 60

def apply_pause_delay(server: str, resource_group: str, database: str, delay_min: int):
    subprocess.run([
        "az", "sql", "db", "update",
        "--resource-group", resource_group,
        "--server", server,
        "--name", database,
        "--auto-pause-delay", str(delay_min),
    ], check=True)

The deeper lesson of serverless is that the DBA's autonomous agents must become state-aware of the platform. Every agent in your ADE should check database state before acting, back off during resume, and distinguish "database is paused" from "database is down." That check is a few lines of code, but without it, the autonomous system will page you at 3 AM because a dev database did exactly what you configured it to do.

Elastic Pools: Autonomous Resource Sharing Across Databases

Elastic pools are the platform's answer to the multi-tenant resource problem: instead of provisioning peak capacity for every database, you provision a shared pool of eDTUs or vCores and let the platform distribute them. The pool's resource governor is itself an autonomous system — it throttles individual databases that exceed their per-database max, borrows idle capacity for databases under load, and enforces the pool's aggregate limits.

The coordination question for the ADE is placement: which databases belong in which pool, and when should a database graduate from a pool to a single database (or vice versa)? The platform will never make that decision for you — it manages resources within the pool, not membership of the pool. Your ADE fills the gap by monitoring per-database resource consumption against pool limits:

-- Elastic pool pressure: which databases are consistently consuming
-- a disproportionate share of the pool?
SELECT
    DB_NAME(r.database_id)                       AS database_name,
    AVG(r.avg_cpu_percent)                       AS avg_cpu_pct,
    MAX(r.avg_cpu_percent)                       AS max_cpu_pct,
    AVG(r.avg_data_io_percent)                   AS avg_data_io_pct,
    AVG(r.avg_log_write_percent)                 AS avg_log_write_pct,
    COUNT(*)                                     AS samples
FROM sys.elastic_pool_resource_stats r
WHERE r.end_time >= DATEADD(DAY, -7, GETUTCDATE())
GROUP BY r.database_id
HAVING AVG(r.avg_cpu_percent) > 40
ORDER BY avg_cpu_pct DESC;

The policy that consumes this data is straightforward: a database that averages above 40% of the pool's CPU for a week is a candidate for graduation to a single database, because it is both paying for capacity it could use alone and starving its pool neighbors of burst headroom. Conversely, a single database averaging under 10% CPU is a candidate for pool membership. These are control-plane actions — executed through the Azure CLI or ARM templates, not through T-SQL — which is exactly why they belong in your ADE's control-plane action layer rather than in any database-internal agent.

Automatic Tuning: The Platform's Query Governor

Automatic tuning is where platform autonomy most directly overlaps with the agents built in earlier chapters — and where the "never tune the same knob twice" rule is most important. Azure SQL offers three automatic tuning options: automatic plan correction, automatic index management (create and drop), and the legacy automatic plan-choice correction. Each can be enabled independently per database.

-- Inspect and configure automatic tuning per database
SELECT
    name,
    desired_state_desc   AS plan_correction,
    actual_state_desc    AS actual_state,
    reason_desc
FROM sys.database_automatic_tuning_options;

-- Enable plan correction only; leave index management to the ADE
ALTER DATABASE [OrdersDB]
    SET AUTOMATIC_TUNING (
        FORCE_LAST_GOOD_PLAN = ON,
        CREATE_INDEX = OFF,
        DROP_INDEX = OFF
    );

The recommended division of labor: let the platform own automatic plan correction and let your ADE own index management, or vice versa — but document the choice and enforce it. The platform's plan correction is conservative, well-tested, and operates through the same Query Store plan-forcing mechanism your agents would use. There is no value in duplicating it. The platform's index management is similarly conservative — it creates indexes only for clear-cut missing-index cases and drops only indexes it created itself after a dwell period. If your ADE has a richer index strategy (workload-aware consolidation, columnstore evaluation, partitioning-aware placement), disable the platform's and let yours own the knob.

Whatever the division, your ADE must observe what the platform did. The tuning recommendations DMV is the observation surface:

-- What has automatic tuning done lately? Feed this into the ADE audit log.
SELECT
    r.reason,
    r.score,
    JSON_VALUE(CAST(r.details AS NVARCHAR(MAX)), '$.implementationDetails.script')
        AS implementation_script,
    r.state                                 AS recommendation_state,
    r.created                               AS recommended_at,
    r.last_refresh                          AS last_evaluated
FROM sys.dm_db_tuning_recommendations r
ORDER BY r.last_refresh DESC;

Ingesting the platform's tuning history into your ADE's action log closes the loop: when your index agent proposes a new index, it can check whether the platform already created, evaluated, and dropped a similar index — and learn from that outcome instead of repeating the experiment. Platform actions are not noise in your telemetry. They are the most authoritative signal available about what has already been tried.

Managed Instance: Service Tiers and Control-Plane Operations

Azure SQL Managed Instance is the platform surface closest to the self-managed SQL Server of the earlier chapters — you get SQL Agent, cross-database queries, CLR, and Service Broker — but the control plane still owns the host. Patching, failover, storage management, and high-availability topology are platform decisions. The DBA's autonomous agents run inside the instance exactly as they would on a VM, with two critical differences: some DMVs and configuration options are restricted, and the instance can be stopped and started as a control-plane operation.

The stop/start capability is the Managed Instance equivalent of serverless auto-pause, and it creates the same state-awareness requirement for your agents. A stopped instance refuses connections with a control-plane error, not a database error — your ADE's health checks must distinguish the two, because "stopped by policy" is not an incident.

The more strategically interesting autonomy in Managed Instance is the service tier update: scaling vCores, moving between General Purpose and Business Critical, or enabling zone redundancy. These are online operations in most cases, but they are not free — a tier change restarts the SQL Server process, dropping the buffer pool and plan cache. Your ADE should treat a tier change the way it treats a failover: schedule it in a maintenance window, warm the cache afterward, and verify query performance against baseline before declaring success:

# Coordinated Managed Instance tier change with post-change verification
import subprocess
import pyodbc
import time

def scale_managed_instance(server: str, resource_group: str,
                           vcore: int, tier: str, conn_str: str):
    # 1. Capture pre-change baseline
    with pyodbc.connect(conn_str) as conn:
        cur = conn.cursor()
        cur.execute("""
            SELECT AVG(avg_cpu_percent) FROM sys.dm_db_resource_stats
            WHERE end_time >= DATEADD(HOUR, -1, GETUTCDATE())
        """)
        baseline_cpu = cur.fetchone()[0]

    # 2. Execute the control-plane scaling operation
    subprocess.run([
        "az", "sql", "mi", "update",
        "--resource-group", resource_group,
        "--name", server,
        "--vcore", str(vcore),
        "--tier", tier,
    ], check=True)

    # 3. Wait for the instance to come back online
    for _ in range(60):
        try:
            with pyodbc.connect(conn_str, timeout=10) as conn:
                conn.cursor().execute("SELECT 1")
            break
        except Exception:
            time.sleep(30)

    # 4. Warm the buffer pool and plan cache with the top workload queries
    with pyodbc.connect(conn_str) as conn:
        cur = conn.cursor()
        cur.execute("""
            SELECT TOP 20 query_sql_text
            FROM sys.query_store_query
            ORDER BY last_execution_time DESC
        """)
        for (sql_text,) in cur.fetchall():
            try:
                cur.execute("SET ROWCOUNT 1")
                cur.execute(sql_text)
                cur.execute("SET ROWCOUNT 0")
            except Exception:
                pass  # best-effort warming; individual failures are fine

Note what this script does not do: it does not decide whether to scale. That decision belongs to the capacity-planning policy from Chapter 14, running in your ADE. The script is the execution arm — the control-plane action that the policy invokes. Keeping the decision layer (your ADE) separate from the execution layer (platform APIs) is what makes the system auditable: every scaling event traces back to a policy evaluation with a recorded rationale.

Failover Groups: Autonomous Geo-Failover Policy

Failover groups are the clearest example of platform autonomy done well. You define a primary and a secondary in different regions, configure a failover policy — automatic or manual — and a grace period. If the primary becomes unreachable, the control plane evaluates the outage against the grace period and fails over automatically. Read-write and read-only listeners follow the role change without application reconfiguration.

The grace period is the autonomy knob, and it deserves the same policy treatment as any threshold in your ADE. The default of one hour is conservative: it prevents flapping during transient outages but accepts up to an hour of downtime before failing over. For a payment database, that is far too long; for a dev database, it is appropriately cautious. Your ADE can manage grace periods as policy, tightening them for databases whose RTO demands it:

# Set failover group policy from RTO requirements
import subprocess

def configure_failover_group(server: str, resource_group: str,
                             group_name: str, rto_minutes: int):
    # Grace period must cover transient blips but respect the RTO.
    # Policy: grace = RTO minus expected failover time, capped at 60 min.
    grace_minutes = max(60, min(3600, (rto_minutes - 5) * 60))
    grace_hours = max(1, grace_minutes // 60)
    mode = "Automatic" if rto_minutes <= 30 else "Manual"

    subprocess.run([
        "az", "sql", "failover-group", "update",
        "--resource-group", resource_group,
        "--server", server,
        "--name", group_name,
        "--failover-policy", mode,
        "--grace-period", str(grace_hours),
    ], check=True)
    print(f"{group_name}: policy={mode}, grace-period={grace_hours}h for RTO {rto_minutes}min")

The critical coordination point: your ADE's own failover agents must be disabled for any database in an automatic failover group. Two failover authorities — your agent and the platform — will eventually disagree about whether a failover is warranted, and the result is a failover war: the platform fails over to the secondary, your agent detects the old primary as "unhealthy primary" and tries to fail back, and the database ping-pongs between regions. The ADE's topology inventory must mark failover-group members as platform-managed for availability, and the failover policy engine must refuse to evaluate them. This is the single most important coordination rule in the chapter, and it is worth enforcing in code rather than in documentation.

The platform-owned failover path: the control plane evaluates the outage against the grace period and fails over without ADE involvement. Your agents observe and log; they do not act.

Maintenance Windows and Update Policies

Platform patching is autonomous by design — you cannot log into the host and run Windows Update — but the schedule is yours to configure. Maintenance windows let you declare when the platform is allowed to patch: a day of the week and a time range, aligned with your own maintenance windows from Chapter 23. The coordination value is obvious: if your ADE schedules index rebuilds for Saturday 02:00 and the platform patches at Saturday 02:00, the two will contend for I/O and the rebuild will run against a cold cache after the host restarts.

# Align platform maintenance windows with the ADE's own maintenance schedule
import subprocess

WEEKDAYS = ["", "Monday", "Tuesday", "Wednesday",
            "Thursday", "Friday", "Saturday", "Sunday"]

def set_maintenance_window(server: str, resource_group: str,
                           db_name: str, day: int, start_hour: int):
    # day: 1=Monday .. 7=Sunday; start_hour: 0-23
    # Keep the platform window OUTSIDE the ADE's Saturday 02:00 rebuild window
    subprocess.run([
        "az", "sql", "db", "update",
        "--resource-group", resource_group,
        "--server", server,
        "--name", db_name,
        "--maint-config-id",
        "SQL_{}_{}".format(WEEKDAYS[day], start_hour),
    ], check=True)

The update policy for Managed Instance deserves separate attention: instances can be pinned to a specific SQL Server build or follow the platform's rolling update train. For production instances under ADE management, the policy should be explicit and version-controlled — the ADE's change-management integration from Chapter 25 should record every platform build change the way it records every schema change, because a build change can alter query plans just as surely as a statistics update can.

Azure Arc: Extending Control-Plane Autonomy to Your Own Infrastructure

Azure Arc-enabled SQL Server brings a subset of the platform's control-plane autonomy to SQL Server running on your own VMs or on-premises: centralized inventory, automated patch assessment, and policy-driven configuration through Azure Policy. For the ADE, Arc is the bridge that lets one autonomous system manage a hybrid fleet with one set of policies.

The practical value is inventory and compliance rather than deep autonomy: Arc tells your ADE which instances exist, what versions they run, and whether they comply with the policies you declare — password rotation, TLS configuration, audit enablement. Your ADE's agents then enforce the database-internal state, while Arc enforces the host-level state. The division mirrors the cloud division: platform owns the substrate, ADE owns the workload.

-- Arc-enabled instances report into the same inventory the ADE already uses.
-- Reconcile Arc inventory against the ADE's known fleet weekly:
-- any instance in Arc but missing from the ADE is unmanaged autonomy debt.
SELECT
    arc.instance_name,
    arc.version,
    arc.last_seen_utc,
    ade.last_checkin_utc,
    CASE
        WHEN ade.instance_name IS NULL THEN 'UNMANAGED_BY_ADE'
        WHEN arc.last_seen_utc < DATEADD(DAY, -1, SYSUTCDATETIME()) THEN 'STALE_ARC_DATA'
        ELSE 'COVERED'
    END AS coverage_state
FROM arc_inventory arc
LEFT JOIN ade_fleet_inventory ade
    ON ade.instance_name = arc.instance_name;

The Shared-Responsibility Contract: Encoding It in Policy

Every coordination rule in this chapter — who owns plan forcing, who owns failover, who owns index management — is a candidate for encoding in the ADE's policy engine rather than living in runbooks. The shared-responsibility contract is a policy document that the ADE loads at startup and enforces on every action:

# shared_responsibility.yaml — who owns what, enforced by the ADE policy engine
platform_managed:
  availability:
    - "databases in automatic failover groups"
    - "zone-redundant Business Critical databases"
  performance:
    - "automatic plan correction (FORCE_LAST_GOOD_PLAN = ON)"
  compute:
    - "serverless auto-pause and auto-scale"
    - "elastic pool resource distribution"
  maintenance:
    - "host patching within configured maintenance windows"

ade_managed:
  availability:
    - "AG failover for self-managed SQL Server (VMs, on-premises)"
    - "failover-group grace period and policy configuration"
  performance:
    - "index lifecycle management (platform CREATE_INDEX = OFF)"
    - "statistics maintenance and custom plan forcing"
  compute:
    - "elastic pool membership and graduation decisions"
    - "serverless auto-pause delay tuning"
  maintenance:
    - "maintenance window alignment and build-change tracking"

conflict_rules:
  - rule: "If platform owns plan correction, ADE plan-forcing agent is disabled for that database."
  - rule: "If database is in an automatic failover group, ADE failover evaluation is refused."
  - rule: "Platform tuning recommendations are ingested into the ADE action log before any ADE index action on the same table."

The enforcement mechanism is a pre-action check in the ADE's action dispatcher — the same pattern as the deployment-window guard from Chapter 28. Before any autonomous action executes, the dispatcher evaluates it against the shared-responsibility contract. An index-creation action on a database where the platform owns index management is refused with a structured log entry, not executed and hoped for the best.

This contract is also the document you show an auditor. When the auditor asks "who decided to drop that index," the answer is either a platform tuning record with a timestamp and a score, or an ADE action log entry with a policy evaluation and a human approval — never "we don't know, both layers can do that." Shared responsibility without a written contract is just shared blame.

Key Takeaways

  • → Never let both layers tune the same knob. The platform's autonomous services and your ADE must have a written, policy-enforced division of labor. Every overlap — plan forcing, index management, failover, compute scaling — is a future incident. Encode the division in the shared-responsibility contract and enforce it in the action dispatcher.
  • → Your agents must be platform-state-aware. Serverless pause, Managed Instance stop/start, and failover-group transitions are not failures. Agents that treat them as failures will page you for correct platform behavior. Check database state through the control plane's view before acting through the data plane.
  • → Ingest platform actions into your action log. Automatic tuning recommendations, tier changes, and failover events are the most authoritative signal available about what has already been tried. An ADE that ignores the platform's history will repeat its experiments and contradict its decisions.
  • → Availability in a failover group is platform-managed — keep your failover agents idle. Two failover authorities will eventually disagree, and the result is a failover war between regions. Mark platform-managed databases in the topology inventory and refuse failover evaluation for them in code, not just in documentation.
  • → Align maintenance windows across both layers. Platform patching and ADE maintenance contend for the same I/O and the same cold caches. Configure the platform's maintenance windows to avoid your ADE's maintenance windows, and track platform build changes with the same rigor as schema changes.
