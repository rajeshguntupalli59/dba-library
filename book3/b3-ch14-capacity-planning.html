Chapter 14: Autonomous Capacity Planning

Capacity planning in traditional database operations is a quarterly ritual — a DBA pulls growth trends, builds a spreadsheet, presents a forecast, and waits for procurement. By the time new hardware arrives, the situation has already changed. Autonomous capacity planning replaces this cycle with a continuously running feedback system that observes resource consumption, projects future demand using statistical and ML-based models, triggers provisioning actions through infrastructure APIs, and validates outcomes — all without a human in the scheduling loop. This chapter walks through building that system end-to-end: the signal collection layer, the forecasting engine, the decision rules that translate forecasts into actions, and the integration with Kubernetes, Terraform, and cloud-native scaling APIs that make those actions real.

14.1 Measuring What Actually Constrains Your Database

Before any forecasting model is worth building, the signal collection layer must be honest about which resources are actually binding constraints. Storage exhaustion is obvious and easy to measure. What kills production systems more often is a subtler constellation of pressures: buffer pool saturation, transaction log write amplification, connection exhaustion at the proxy layer, I/O queue depth at the block device level, and CPU contention during checkpoint storms. An autonomous system that only watches disk is dangerous — it will declare the environment healthy while the query engine is thrashing.

The baseline metrics collection strategy needs to capture five resource dimensions at short intervals (30 seconds to 2 minutes depending on the resource): storage, memory, compute, I/O, and connection throughput. These are not server-level metrics; they must be captured at the database instance level, correlated with workload identity.

-- Equivalent resource pressure snapshot for SQL Server
-- Designed to be executed by a SQL Agent job every 60 seconds

SELECT
    GETUTCDATE()                                                AS captured_at,
    (SELECT SUM(size) * 8192 FROM sys.master_files
     WHERE database_id = DB_ID())                              AS db_size_bytes,
    (SELECT COUNT(*) FROM sys.dm_exec_sessions
     WHERE is_user_process = 1 AND status = 'running')         AS active_connections,
    (SELECT COUNT(*) FROM sys.dm_os_waiting_tasks
     WHERE wait_type LIKE 'LCK%')                              AS lock_waiters,
    (SELECT cntr_value FROM sys.dm_os_performance_counters
     WHERE counter_name = 'Buffer cache hit ratio'
     AND object_name LIKE '%Buffer Manager%')                  AS buffer_hit_ratio,
    (SELECT physical_memory_in_use_kb * 1024
     FROM sys.dm_os_process_memory)                            AS memory_in_use_bytes,
    (SELECT cntr_value FROM sys.dm_os_performance_counters
     WHERE counter_name = 'Log Bytes Flushed/sec'
     AND instance_name = DB_NAME())                            AS log_flush_rate,
    (SELECT SUM(log_send_queue_size) FROM sys.dm_hadr_database_replica_states
     WHERE is_local = 0)                                       AS max_replication_lag_bytes,
    (SELECT physical_memory_kb * 1024
     FROM sys.dm_os_sys_info)                                  AS total_host_memory_bytes;

Store these snapshots in a dedicated metrics database — not in the production instance you are monitoring. Use a dedicated SQL Server instance as the metrics database, or push to Prometheus with a scrape interval of 30 seconds and long-term retention via Thanos or Cortex. The key architectural decision here is separation of the observer from the observed: if your capacity system depends on the health of the system it monitors, you lose visibility exactly when you need it most.

For I/O, do not rely on database-layer counters alone. Instrument at the OS level using node_exporter for Linux hosts (or the Windows Exporter for SQL Server on Windows), and correlate diskstats metrics — specifically io_time_ms and await — with the database-layer write rates. A rising await with stable write volume signals block device saturation before any database-level metric reflects it.

Connection pressure is particularly insidious. SQL Server exposes live connection counts through sys.dm_exec_connections and the User Connections performance counter. When the connection count approaches the configured user connections limit — or when the rate of new connections spikes without a matching rise in active requests — the system is already degraded: a capacity event has effectively started. Capture this metric explicitly:

-- SQL Server connection pressure — run every 30s, export to Prometheus via sql_exporter
SELECT
    COUNT(*)                                              AS total_connections,
    SUM(CASE WHEN s.status = 'running' THEN 1 ELSE 0 END) AS active_requests,
    SUM(CASE WHEN DATEDIFF(MINUTE, c.connect_time, GETUTCDATE()) > 60
              AND s.status = 'sleeping' THEN 1 ELSE 0 END) AS idle_over_60min,
    -- Connections waiting on a worker = pressure signal
    SUM(CASE WHEN w.wait_type IS NOT NULL THEN 1 ELSE 0 END) AS waiting_connections
FROM sys.dm_exec_connections c
LEFT JOIN sys.dm_exec_sessions s ON s.session_id = c.session_id
LEFT JOIN sys.dm_os_waiting_tasks w
    ON w.session_id = c.session_id AND w.wait_type LIKE 'THREADPOOL%';

Push these metrics into the same time-series store as your database-level snapshots. The forecasting engine needs a unified view.

14.2 Forecasting Models Calibrated for Database Workload Patterns

Database resource consumption has properties that make naive forecasting models perform poorly. Storage growth is often smooth but punctuated by bulk loads, schema migrations, and index rebuilds. Connection counts show strong diurnal seasonality — business applications spike at 9 AM and taper off overnight — but also carry irregular spikes from batch jobs, reporting windows, and end-of-month processing. Memory pressure follows query complexity, not time. A good forecasting layer handles all three patterns: smooth trends, seasonal cycles, and irregular spikes.

The practical forecasting stack for an autonomous system combines three approaches depending on the resource dimension:

  • → Linear regression with drift detection for storage (growth is mostly monotonic; the anomaly is when it isn't)
  • → Prophet or SARIMA for connection counts and CPU (strong seasonality, predictable cycles)
  • → Percentile-based headroom analysis for buffer pool and memory (you care about P95/P99, not mean)

    • The following Python script implements the forecasting engine. It pulls raw metrics from Prometheus, applies Prophet for connection forecasting, and emits a structured capacity recommendation. This runs as a Kubernetes CronJob every four hours.

    #!/usr/bin/env python3
"""
autonomous_capacity_forecast.py
Pulls metrics from Prometheus, applies statistical forecasting,
and emits capacity recommendations to a Redis-backed action queue.
"""

import json
import logging
from datetime import datetime, timedelta

import pandas as pd
import redis
import requests
from prophet import Prophet

logging.basicConfig(level=logging.INFO,
                    format="%(asctime)s %(levelname)s %(message)s")
log = logging.getLogger("capacity_forecast")

PROMETHEUS_URL = "http://prometheus:9090"
REDIS_URL = "redis://redis:6379"
FORECAST_HORIZON_HOURS = 72
RECOMMENDATION_THRESHOLD_PCT = 0.85  # trigger if forecast hits 85% of limit

RESOURCE_LIMITS = {
    "connections": 500,        # user connections for this instance class
    "storage_bytes": 1_099_511_627_776,  # 1 TB provisioned
    "memory_bytes": 68_719_476_736,      # 64 GB RAM
}


def query_prometheus_range(metric: str, hours_back: int = 168) -> pd.DataFrame:
    end = datetime.utcnow()
    start = end - timedelta(hours=hours_back)
    params = {
        "query": metric,
        "start": start.isoformat() + "Z",
        "end": end.isoformat() + "Z",
        "step": "300",  # 5-minute resolution
    }
    response = requests.get(f"{PROMETHEUS_URL}/api/v1/query_range",
                            params=params, timeout=30)
    response.raise_for_status()
    results = response.json()["data"]["result"]
    if not results:
        return pd.DataFrame()

    values = results[0]["values"]
    df = pd.DataFrame(values, columns=["timestamp", "value"])
    df["ds"] = pd.to_datetime(df["timestamp"], unit="s", utc=True)
    df["y"] = df["value"].astype(float)
    return df[["ds", "y"]]


def run_prophet_forecast(df: pd.DataFrame,
                         horizon_hours: int) -> pd.DataFrame:
    model = Prophet(
        yearly_seasonality=False,
        weekly_seasonality=True,
        daily_seasonality=True,
        changepoint_prior_scale=0.05,
        interval_width=0.95,
    )
    df_local = df.copy()
    df_local["ds"] = df_local["ds"].dt.tz_localize(None)
    model.fit(df_local)

    future = model.make_future_dataframe(
        periods=horizon_hours * 12,  # 5-min intervals
        freq="5min"
    )
    forecast = model.predict(future)
    return forecast[["ds", "yhat", "yhat_lower", "yhat_upper"]].tail(
        horizon_hours * 12
    )


def evaluate_capacity(resource: str,
                       forecast: pd.DataFrame,
                       limit: float) -> dict:
    peak_forecast = forecast["yhat_upper"].max()
    peak_at = forecast.loc[forecast["yhat_upper"].idxmax(), "ds"]
    utilization = peak_forecast / limit

    return {
        "resource": resource,
        "forecast_peak_value": round(peak_forecast, 2),
        "forecast_peak_at": peak_at.isoformat(),
        "limit": limit,
        "forecast_utilization_pct": round(utilization * 100, 2),
        "action_required": utilization >= RECOMMENDATION_THRESHOLD_PCT,
        "evaluated_at": datetime.utcnow().isoformat(),
    }


def push_recommendation(client: redis.Redis, recommendation: dict):
    if recommendation["action_required"]:
        client.lpush("capacity:actions:pending",
                     json.dumps(recommendation))
        log.info("Pushed capacity action: %s utilization %.1f%%",
                 recommendation["resource"],
                 recommendation["forecast_utilization_pct"])
    else:
        log.info("Resource %s within bounds: %.1f%%",
                 recommendation["resource"],
                 recommendation["forecast_utilization_pct"])


def main():
    r = redis.from_url(REDIS_URL)

    # Metric names depend on the sql_exporter collectors enabled;
    # adjust to match your deployment's collector configuration.
    metric_map = {
        "connections": 'sqlserver_performance{counter="User Connections"}',
        "storage_bytes": "sqlserver_database_size_bytes",
        "memory_bytes": 'sqlserver_performance{counter="Total Server Memory (KB)"} * 1024',
    }

    for resource, prometheus_metric in metric_map.items():
        log.info("Forecasting: %s", resource)
        df = query_prometheus_range(prometheus_metric)
        if df.empty or len(df) < 50:
            log.warning("Insufficient data for %s, skipping", resource)
            continue

        forecast = run_prophet_forecast(df, FORECAST_HORIZON_HOURS)
        rec = evaluate_capacity(resource, forecast,
                                RESOURCE_LIMITS[resource])
        push_recommendation(r, rec)


if __name__ == "__main__":
    main()

    For storage specifically, augment Prophet with a simple linear regression over the trailing 30-day trend. Storage growth rates rarely change suddenly, and Prophet's seasonality machinery adds noise where none exists. When the linear model and Prophet disagree by more than 20%, escalate to human review rather than acting autonomously — forecast disagreement is itself a signal that something unusual is happening in the workload.

    Calibrate RECOMMENDATION_THRESHOLD_PCT per resource type. Connections should trigger at 80% because connection exhaustion is instantaneous — there is no graceful degradation. Storage can trigger at 85% because growth is observable and provisioning has lead time. Memory should trigger at 75% because you need buffer to absorb a reporting query spike before the OOM killer becomes involved.

    14.3 Translating Forecasts into Provisioning Actions via Infrastructure APIs

    A capacity forecast that produces a report is still manual capacity planning. The autonomous layer converts forecast outputs into concrete provisioning actions executed against infrastructure APIs without waiting for human approval, subject to safety guardrails that define the action envelope. The architecture here follows the same observe-decide-act loop described in earlier chapters, but the decision layer is more conservative than in performance tuning because provisioning actions are typically irreversible or expensive to reverse.

    The action hierarchy for capacity events, in ascending order of impact and required confidence:

    1. Rebalance connection governance — tighten Resource Governor workload group caps (MAX_DOP, REQUEST_MAX_MEMORY_GRANT_PERCENT) for reporting workloads and raise the application connection pool ceiling via config reload. Zero risk, zero cost, immediate effect.

    2. Expand vertical resources — increase instance size via cloud provider API (RDS ModifyDBInstance, Azure SQL service tier change). Requires maintenance window awareness.

    3. Add read replicas — provision a new read replica via Terraform or cloud API to offload read workload. Increases cost, takes 15–30 minutes for large databases.

    4. Expand storage — increase allocated storage or tablespace via cloud API. Usually non-disruptive on modern cloud platforms; can be disruptive on self-managed storage.

    5. Trigger archival pipelines — move cold data to object storage or a separate archive instance to reclaim space. Complex; requires data classification to be pre-configured.

    graph LR
    A[Forecast Engine] -->|utilization >= threshold| B[Redis Recommendation Queue]
    B --> C{Action Hierarchy}
    C -->|Tier 1| D[Rebalance Connection Pools]
    C -->|Tier 2| E[Expand Vertical Resources]
    C -->|Tier 3| F[Add Read Replicas]
    C -->|Tier 4| G[Expand Storage]
    C -->|Tier 5| H[Trigger Archival Pipeline]
    D --> I[Validate Outcome]
    E --> I
    F --> I
    G --> I
    H --> I
    I -->|failed| J[Escalate to Human]
    I -->|succeeded| K[Feed Back to Forecast Model]

    *Forecasts drive a ranked action hierarchy, from low-risk connection pool rebalancing to high-impact archival pipelines; every executed action is validated and fed back into the forecasting loop.*

    The decision engine reads from the Redis recommendation queue and routes actions through the appropriate handler:

    #!/usr/bin/env python3
"""
capacity_action_executor.py
Reads capacity recommendations from the action queue and executes
the appropriate provisioning response through the correct API.
"""

import json
import logging
import os
import time

import boto3
import redis

log = logging.getLogger("capacity_executor")
logging.basicConfig(level=logging.INFO,
                    format="%(asctime)s %(levelname)s %(message)s")

REDIS_URL = os.environ["REDIS_URL"]
RDS_INSTANCE_ID = os.environ["RDS_INSTANCE_ID"]
AWS_REGION = os.environ.get("AWS_REGION", "us-east-1")

# Action cooldown: don't act on the same resource more than once per window
COOLDOWN_SECONDS = {
    "connections": 1800,     # 30 minutes
    "storage_bytes": 14400,  # 4 hours
    "memory_bytes": 7200,    # 2 hours
}

rds = boto3.client("rds", region_name=AWS_REGION)
r = redis.from_url(REDIS_URL)


def is_in_cooldown(resource: str) -> bool:
    key = f"capacity:cooldown:{resource}"
    return r.exists(key) == 1


def set_cooldown(resource: str):
    key = f"capacity:cooldown:{resource}"
    r.setex(key, COOLDOWN_SECONDS[resource], "1")


def expand_rds_storage(current_gb: int, increment_pct: float = 0.30) -> dict:
    new_size = int(current_gb * (1 + increment_pct))
    new_size = max(new_size, current_gb + 50)  # minimum 50 GB increment

    log.info("Expanding RDS storage: %d GB -> %d GB", current_gb, new_size)
    response = rds.modify_db_instance(
        DBInstanceIdentifier=RDS_INSTANCE_ID,
        AllocatedStorage=new_size,
        ApplyImmediately=True,
    )
    return {
        "action": "storage_expansion",
        "old_size_gb": current_gb,
        "new_size_gb": new_size,
        "rds_status": response["DBInstance"]["DBInstanceStatus"],
    }


MSSQL_DSN = (
    "DRIVER={ODBC Driver 18 for SQL Server};"
    "SERVER=sql-primary;DATABASE=master;Trusted_Connection=yes;"
)


def scale_connection_governance(utilization_pct: float) -> dict:
    """
    Shed load under connection pressure by tightening Resource Governor
    limits on the reporting workload group, protecting the OLTP group.
    """
    import pyodbc

    if utilization_pct >= 90:
        new_max_dop, new_grant_pct = 2, 10
    elif utilization_pct >= 85:
        new_max_dop, new_grant_pct = 4, 15
    else:
        return {"action": "governor_noop"}

    conn = pyodbc.connect(MSSQL_DSN, autocommit=True)
    cur = conn.cursor()
    cur.execute(
        "ALTER WORKLOAD GROUP reporting_group WITH "
        f"(MAX_DOP = {new_max_dop}, "
        f"REQUEST_MAX_MEMORY_GRANT_PERCENT = {new_grant_pct});"
    )
    cur.execute("ALTER RESOURCE GOVERNOR RECONFIGURE;")
    conn.close()
    log.info("Resource Governor tightened: MAX_DOP=%d grant_pct=%d",
             new_max_dop, new_grant_pct)

    return {
        "action": "governor_adjustment",
        "max_dop": new_max_dop,
        "grant_pct": new_grant_pct,
    }


def handle_recommendation(rec: dict) -> dict | None:
    resource = rec["resource"]
    utilization = rec["forecast_utilization_pct"]

    if is_in_cooldown(resource):
        log.info("Resource %s is in cooldown, skipping", resource)
        return None

    result = None

    if resource == "connections":
        result = scale_connection_governance(utilization)

    elif resource == "storage_bytes":
        current_gb = int(rec["limit"] / (1024 ** 3))
        result = expand_rds_storage(current_gb)

    elif resource == "memory_bytes":
        # Memory scaling requires instance resize — emit for human approval
        # above a certain threshold; auto-act only for minor adjustments
        log.warning("Memory pressure at %.1f%% — emitting for orchestrator review",
                    utilization)
        r.lpush("capacity:escalations", json.dumps(rec))
        return {"action": "escalated_to_orchestrator", "resource": resource}

    if result:
        set_cooldown(resource)
        r.lpush("capacity:actions:completed",
                json.dumps({**rec, "result": result,
                            "executed_at": time.time()}))

    return result


def main():
    log.info("Capacity action executor starting")
    while True:
        item = r.brpop("capacity:actions:pending", timeout=30)
        if item is None:
            continue
        _, payload = item
        try:
            rec = json.loads(payload)
            handle_recommendation(rec)
        except Exception as e:
            log.error("Failed to handle recommendation: %s", e)
            r.lpush("capacity:actions:failed", payload)


if __name__ == "__main__":
    main()

    The memory escalation path in this executor is intentional. Vertical scaling of an RDS instance or an Azure SQL tier is not instantaneous and carries a brief failover window (typically 30–60 seconds on modern multi-AZ deployments, but still observable). The autonomous system acts immediately on soft resources (connection pool limits, storage expansion) and escalates hard resource decisions — instance resizes — to the orchestrator layer, which can apply maintenance window awareness and rollback logic. This is not a limitation of the autonomous design; it is the appropriate confidence boundary.

    For SQL Server on Azure SQL, the equivalent scaling action uses the Azure SDK:

from azure.identity import DefaultAzureCredential

        }

    14.4 Kubernetes-Native Capacity Scaling for Database Workloads

    When databases run inside Kubernetes — whether as StatefulSets managed by the CloudNativePG operator, CrunchyData PGO, or the SQL Server on Kubernetes operator — capacity planning integrates with the Kubernetes resource model. This introduces both tighter feedback loops and new failure modes. PersistentVolumeClaims can be expanded online (on supporting storage classes) by patching the PVC spec. CPU and memory requests can be adjusted by updating the StatefulSet, which triggers a rolling pod restart. Connection scaling is handled by the operator's pooler abstraction.

    CloudNativePG exposes a Cluster CRD that the autonomous system can patch directly when capacity thresholds are breached. The following shows a Kubernetes operator-style patch applied by the capacity executor:

    #!/usr/bin/env python3
"""
k8s_capacity_patch.py
Applies capacity changes to CloudNativePG Cluster CRDs via the Kubernetes API.
"""

from kubernetes import client, config
import json
import logging

log = logging.getLogger("k8s_capacity")
config.load_incluster_config()  # running inside the cluster

custom_api = client.CustomObjectsApi()
core_api = client.CoreV1Api()

NAMESPACE = "databases"
STATEFULSET_NAME = "mssql-primary"
PVC_NAME = "mssql-data-mssql-primary-0"


def expand_pvc_storage(new_size_gi: int):
    """
    Patch the data PVC — the CSI driver handles online volume expansion.
    Requires the storage class to allow volume expansion.
    """
    patch = {"spec": {"resources": {"requests": {"storage": f"{new_size_gi}Gi"}}}}
    core_api.patch_namespaced_persistent_volume_claim(
        name=PVC_NAME,
        namespace=NAMESPACE,
        body=patch,
    )
    log.info("Patched PVC %s storage to %dGi", PVC_NAME, new_size_gi)


def scale_read_replicas(new_replicas: int):
    """
    Scale the AG secondary StatefulSet. The operator's reconcile loop
    joins new pods to the availability group automatically.
    """
    apps_api = client.AppsV1Api()
    apps_api.patch_namespaced_stateful_set_scale(
        name="mssql-secondary",
        namespace=NAMESPACE,
        body={"spec": {"replicas": new_replicas}},
    )
    log.info("Scaled AG secondary StatefulSet to %d replicas", new_replicas)


def update_resource_requests(cpu_request: str,
                              memory_request: str,
                              cpu_limit: str,
                              memory_limit: str):
    """
    Update CPU and memory resource requests on the primary StatefulSet.
    This triggers a rolling restart — use with care.
    """
    apps_api = client.AppsV1Api()
    sts = apps_api.read_namespaced_stateful_set(
        name=STATEFULSET_NAME, namespace=NAMESPACE)
    container = sts.spec.template.spec.containers[0]
    container.resources.requests = {"cpu": cpu_request, "memory": memory_request}
    container.resources.limits = {"cpu": cpu_limit, "memory": memory_limit}
    apps_api.patch_namespaced_stateful_set(
        name=STATEFULSET_NAME,
        namespace=NAMESPACE,
        body={"spec": {"template": {"spec": {"containers": [
            {"name": container.name, "resources": container.resources.to_dict()}
        ]}}}},
    )
    log.info("Patched StatefulSet resources: cpu=%s mem=%s",
             cpu_request, memory_request)


def get_current_statefulset_spec() -> dict:
    apps_api = client.AppsV1Api()
    sts = apps_api.read_namespaced_stateful_set(
        name=STATEFULSET_NAME, namespace=NAMESPACE)
    container = sts.spec.template.spec.containers[0]
    return {
        "replicas": sts.spec.replicas,
        "resources": {
            "requests": dict(container.resources.requests or {}),
            "limits": dict(container.resources.limits or {}),
        },
    }


def autonomous_scale_decision(recommendation: dict) -> None:
    spec = get_current_statefulset_spec()
    resource = recommendation["resource"]
    utilization = recommendation["forecast_utilization_pct"]

    if resource == "storage_bytes":
        # PVC size is tracked separately from the pod spec
        pvc = core_api.read_namespaced_persistent_volume_claim(
            name=PVC_NAME, namespace=NAMESPACE)
        current_size_str = pvc.spec.resources.requests["storage"]  # e.g. "500Gi"
        current_gi = int(current_size_str.replace("Gi", ""))
        new_gi = int(current_gi * 1.35)  # 35% expansion
        new_gi = max(new_gi, current_gi + 100)  # floor increment
        expand_pvc_storage(new_gi)

    elif resource == "connections":
        current_replicas = spec.get("replicas", 1)
        if utilization >= 90 and current_replicas < 5:
            scale_read_replicas(current_replicas + 1)
            log.info("Added read replica: %d -> %d replicas",
                     current_replicas, current_replicas + 1)

    elif resource == "memory_bytes":
        # Only auto-scale memory if headroom is extremely tight
        # and the cluster is running below the node's available capacity.
        # Otherwise escalate.
        if utilization >= 95:
            current_mem = spec.get("resources", {}).get(
                "requests", {}).get("memory", "8Gi")
            current_gi = int(current_mem.replace("Gi", ""))
            new_gi = current_gi + 8
            update_resource_requests(
                cpu_request=spec.get("resources", {}).get(
                    "requests", {}).get("cpu", "2"),
                memory_request=f"{new_gi}Gi",
                cpu_limit=spec.get("resources", {}).get(
                    "limits", {}).get("cpu", "4"),
                memory_limit=f"{int(new_gi * 1.25)}Gi",
            )
        else:
            log.info("Memory at %.1f%% — below auto-scale threshold, "
                     "escalating", utilization)

    The key behavioral rule embedded in autonomous_scale_decision is that storage and read-replica counts are scaled automatically, while memory resource updates are gated at a higher utilization threshold because they force a pod restart (and an AG failover sequence). This asymmetry reflects the actual cost profile of each operation: PVC expansion is non-disruptive on most CSI drivers (Ceph RBD, EBS, GCE PD), but pod restarts always carry a brief promotion or failover sequence, even with proper readiness probes.

    The functions above use the operator-agnostic approach: patch the StatefulSet for memory and CPU, patch the PVC for storage, and manage secondary replicas through the availability group configuration — no operator-specific CRD required.

    Horizontal Pod Autoscaler integration for connection proxies:

    The database itself cannot be HPA-scaled (it is stateful), but the connection proxy layer in front of it can be. The following HPA manifest scales the proxy deployment based on connection wait pressure as a custom metric:

    apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: sqlproxy-hpa
  namespace: databases
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: sqlproxy
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: External
    external:
      metric:
        name: sqlserver_proxy_connection_waits
        selector:
          matchLabels:
            database: mssql-primary
      target:
        type: AverageValue
        averageValue: "0"   # any nonzero waiting clients triggers scale-out
  - type: External
    external:
      metric:
        name: sqlserver_proxy_idle_connections
        selector:
          matchLabels:
            database: mssql-primary
      target:
        type: AverageValue
        averageValue: "5"   # scale in when avg idle > 5 per pod
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60
      policies:
      - type: Pods
        value: 2
        periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 600   # 10 minutes before scaling in
      policies:
      - type: Pods
        value: 1
        periodSeconds: 120

    The cl_waiting metric is binary in intent — any sustained nonzero value means clients are being throttled. Setting the target to zero means any waiting client detected above the stabilization window triggers scale-out. The scale-in stabilization window of ten minutes prevents oscillation after a burst subsides.

    14.5 Terraform-Driven Capacity Automation with State Drift Detection

    For environments managed through Terraform, the autonomous capacity system must interact with Terraform state rather than calling APIs directly. Calling the AWS or Azure SDK directly from the executor bypasses Terraform's state model, which creates drift: Terraform state says the instance is db.r6g.2xlarge but the API has moved it to db.r6g.4xlarge. The next terraform apply will revert the autonomous change and potentially cause an unplanned resize mid-day.

    The correct integration pattern is to update the Terraform variable store (an S3-backed variable file, Terraform Cloud workspace variables, or a Vault-backed Terraform input) and trigger a controlled terraform apply rather than calling the infrastructure API directly. The autonomous system becomes a variable writer, not an API caller.

    #!/usr/bin/env python3
"""
terraform_capacity_updater.py
Updates Terraform variables in S3 and triggers a Terraform Cloud run
in response to capacity recommendations. Terraform performs the actual
API call, keeping state consistent.
"""

import json
import logging
import os

import boto3
import requests

log = logging.getLogger("terraform_capacity")

S3_BUCKET = os.environ["CAPACITY_VARS_BUCKET"]
S3_KEY = "capacity/rds_variables.json"
TFC_TOKEN = os.environ["TFC_TOKEN"]
TFC_WORKSPACE_ID = os.environ["TFC_WORKSPACE_ID"]

s3 = boto3.client("s3")


def read_current_vars() -> dict:
    try:
        obj = s3.get_object(Bucket=S3_BUCKET, Key=S3_KEY)
        return json.loads(obj["Body"].read())
    except s3.exceptions.NoSuchKey:
        return {}


def write_updated_vars(vars_dict: dict):
    s3.put_object(
        Bucket=S3_BUCKET,
        Key=S3_KEY,
        Body=json.dumps(vars_dict, indent=2),
        ContentType="application/json",
    )
    log.info("Updated capacity variables in S3: %s", vars_dict)


def trigger_tfc_run(message: str):
    """
    Trigger a Terraform Cloud plan+apply run for the capacity workspace.
    """
    url = f"https://app.terraform.io/api/v2/runs"
    headers = {
        "Authorization": f"Bearer {TFC_TOKEN}",
        "Content-Type": "application/vnd.api+json",
    }
    payload = {
        "data": {
            "attributes": {
                "message": message,
                "auto-apply": True,
                "refresh": True,
            },
            "type": "runs",
            "relationships": {
                "workspace": {
                    "data": {
                        "type": "workspaces",
                        "id": TFC_WORKSPACE_ID
                    }
                }
            }
        }
    }
    response = requests.post(url, headers=headers,
                             json=payload, timeout=30)
    response.raise_for_status()
    run_id = response.json()["data"]["id"]
    log.info("Triggered Terraform Cloud run: %s", run_id)
    return run_id


INSTANCE_CLASS_LADDER = [
    "db.t4g.medium",
    "db.t4g.large",
    "db.r6g.large",
    "db.r6g.xlarge",
    "db.r6g.2xlarge",
    "db.r6g.4xlarge",
    "db.r6g.8xlarge",
    "db.r6g.16xlarge",
]


def next_instance_class(current: str) -> str | None:
    try:
        idx = INSTANCE_CLASS_LADDER.index(current)
        if idx + 1 < len(INSTANCE_CLASS_LADDER):
            return INSTANCE_CLASS_LADDER[idx + 1]
    except ValueError:
        pass
    return None


def apply_capacity_recommendation(recommendation: dict):
    resource = recommendation["resource"]
    current_vars = read_current_vars()

    if resource == "storage_bytes":
        current_gb = current_vars.get("rds_allocated_storage_gb", 500)
        new_gb = max(int(current_gb * 1.35), current_gb + 100)
        current_vars["rds_allocated_storage_gb"] = new_gb
        write_updated_vars(current_vars)
        trigger_tfc_run(
            f"Autonomous capacity: storage {current_gb}GB -> {new_gb}GB "
            f"(forecast {recommendation['forecast_utilization_pct']:.1f}%)"
        )

    elif resource == "memory_bytes":
        current_class = current_vars.get("rds_instance_class", "db.r6g.large")
        new_class = next_instance_class(current_class)
        if new_class:
            current_vars["rds_instance_class"] = new_class
            write_updated_vars(current_vars)
            trigger_tfc_run(
                f"Autonomous capacity: instance {current_class} -> {new_class} "
                f"(memory forecast {recommendation['forecast_utilization_pct']:.1f}%)"
            )
        else:
            log.error("Already at maximum instance class: %s", current_class)
            # Escalate to human — no more ladder rungs available

    log.info("Capacity recommendation applied via Terraform: resource=%s",
             resource)

    This pattern ensures that terraform plan outputs remain auditable and predictable. Every autonomous capacity change is a Terraform run with a message string that identifies the triggering recommendation and the forecast percentage that drove it. The run log becomes the capacity audit trail.

    Drift detection runs as a separate process that periodically compares the live infrastructure state against Terraform state and alerts when they diverge by more than a defined tolerance:

    def detect_capacity_drift():
    """
    Compare actual RDS instance class against Terraform state.
    Flags if they diverge, indicating an out-of-band change.
    """
    current_vars = read_current_vars()
    tf_instance_class = current_vars.get("rds_instance_class")

    rds = boto3.client("rds")
    instance = rds.describe_db_instances(
        DBInstanceIdentifier=os.environ["RDS_INSTANCE_ID"]
    )["DBInstances"][0]
    actual_class = instance["DBInstanceClass"]

    if tf_instance_class and actual_class != tf_instance_class:
        log.warning(
            "DRIFT DETECTED: Terraform expects %s, actual is %s. "
            "An out-of-band change may have occurred.",
            tf_instance_class, actual_class
        )
        # Push drift alert to monitoring channel
        return {"drift": True,
                "expected": tf_instance_class,
                "actual": actual_class}

    return {"drift": False, "instance_class": actual_class}

    14.6 Validating That Capacity Actions Worked

    Executing a provisioning action is not the end of the loop. The autonomous system must validate that the action achieved its intended effect and that the validated outcome is fed back into the forecasting model as a signal. Without this feedback, the system will re-forecast against stale assumptions and potentially trigger redundant or contradictory actions.

    The validation cycle runs after a resource-specific settlement period (storage: 15 minutes for the cloud API to reflect the new size; connection governance: 5 minutes for the Resource Governor reconfigure to take effect; instance resize: 30 minutes including failover and warm-up).

    Post-action storage validation:

    -- Verify storage expansion outcome in SQL Server environment
-- Run after the settlement window following Azure SQL storage tier update

SELECT
    GETUTCDATE()                                           AS validated_at,
    DB_NAME()                                              AS database_name,
    SUM(size * 8192)                                       AS actual_db_size_bytes,
    SUM(size * 8192) / 1073741824.0                        AS actual_db_size_gb,
    (
        SELECT max_size * 8192
        FROM sys.master_files
        WHERE database_id = DB_ID()
        AND type = 0  -- data files only
    )                                                      AS max_allocated_bytes,
    (
        (SELECT max_size * 8192
         FROM sys.master_files
         WHERE database_id = DB_ID() AND type = 0)
        - SUM(size * 8192)
    )                                                      AS remaining_headroom_bytes
FROM
    sys.master_files
WHERE
    database_id = DB_ID();

    The Python validation loop reads the completed action record from Redis, waits the settlement period, queries the database, and compares the outcome against the expected post-action state:

    def validate_action_outcome(completed_action: dict) -> dict:
    resource = completed_action["resource"]
    result = completed_action["result"]
    executed_at = completed_action["executed_at"]

    settlement_seconds = {
        "storage_bytes": 900,     # 15 minutes
        "connections": 300,       # 5 minutes
        "memory_bytes": 1800,     # 30 minutes
    }

    # Wait for settlement if needed
    elapsed = time.time() - executed_at
    remaining_wait = settlement_seconds[resource] - elapsed
    if remaining_wait > 0:
        log.info("Waiting %.0fs for %s action to settle",
                 remaining_wait, resource)
        time.sleep(remaining_wait)

    # Query actual current state
    if resource == "storage_bytes":
        actual = query_current_db_size_bytes()   # sqlserver
        expected = result.get("new_size_gb", 0) * (1024 ** 3)
        # Storage expansion is validated if actual db_size < 85% of new limit
        success = actual < (expected * 0.85)

    elif resource == "connections":
        actual_waiting = query_sqlserver_waiting_connections()
        success = actual_waiting == 0

    elif resource == "memory_bytes":
        actual_mem_pct = query_current_memory_utilization_pct()
        success = actual_mem_pct < 75.0

    else:
        success = None  # unknown resource type

    validation_record = {
        "resource": resource,
        "action_result": result,
        "validation_success": success,
        "validated_at": time.time(),
        "actual_state": actual if resource == "storage_bytes" else None,
    }

    if not success:
        log.warning("Action validation FAILED for %s — pushing to escalation queue",
                    resource)
        r.lpush("capacity:validations:failed", json.dumps(validation_record))
    else:
        log.info("Action validation SUCCEEDED for %s", resource)
        r.lpush("capacity:validations:succeeded", json.dumps(validation_record))

    return validation_record

    Failed validations are escalated, not retried automatically. Automatic retry of a failed provisioning action risks compounding the error — if an RDS storage expansion failed because the instance was in a modifying state, retrying immediately will fail again and potentially leave the instance in a confused state. Human review of failed validations is the correct response. The autonomous system has done its job by detecting the failure and escalating it with full context.

    14.7 Capacity Planning for Multi-Tenant Database Architectures

    Multi-tenant architectures add a layer of complexity: resources are shared across tenants, but tenant growth rates are independent and often uncorrelated. A single large tenant onboarding a new product line can exhaust storage allocated to dozens of smaller tenants. The autonomous capacity system must track resource consumption per tenant and forecast at the tenant level, not just the aggregate.

    In a shared-schema multi-tenant SQL Server deployment, tenant isolation typically uses Row-Level Security with a tenant_id column. Resource attribution requires estimating storage per tenant from row counts and average record size:

    -- Per-tenant storage consumption (shared schema) — run nightly and store in
-- the capacity metrics database. Assumes a tenant_table_registry mapping
-- table names to tenant_id.
SELECT
    t.tenant_id,
    COUNT(DISTINCT st.name)                              AS table_count,
    SUM(CAST(p.rows AS BIGINT) * ips.avg_record_size_in_bytes) AS estimated_bytes,
    GETUTCDATE()                                         AS measured_at
FROM sys.tables st
JOIN sys.partitions p
    ON st.object_id = p.object_id
JOIN sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'SAMPLED') ips
    ON ips.object_id = st.object_id AND ips.index_id = p.index_id
JOIN tenant_table_registry t
    ON st.name = t.table_name
WHERE p.index_id IN (0, 1)   -- heap or clustered index only
GROUP BY t.tenant_id
ORDER BY estimated_bytes DESC;

    For a schema-per-tenant deployment, attribution is simpler — the schema size is directly attributable:

    -- Schema-per-tenant storage attribution
SELECT
    s.name                                AS tenant_schema,
    SUM(pa.used_pages * 8192)             AS used_bytes,
    GETUTCDATE()                          AS measured_at
FROM sys.schemas s
JOIN sys.tables st
    ON st.schema_id = s.schema_id
JOIN sys.partitions p
    ON p.object_id = st.object_id
JOIN sys.allocation_units pa
    ON pa.container_id = p.partition_id
WHERE s.name NOT IN ('dbo', 'sys', 'information_schema', 'guest')
  AND p.index_id IN (0, 1)   -- heap or clustered index only
GROUP BY s.name
ORDER BY used_bytes DESC;

    SQL Server — per-tenant storage in a shared database:

    -- Per-tenant table size attribution in shared SQL Server database
-- Assumes tenant_id-prefixed tables or a tenant_id column mapped in a registry

SELECT
    t.tenant_id,
    COUNT(DISTINCT st.name)                               AS table_count,
    SUM(pa.used_pages * 8192)                             AS used_bytes,
    SUM(pa.total_pages * 8192)                            AS allocated_bytes,
    GETUTCDATE()                                          AS measured_at
FROM
    sys.tables st
    JOIN sys.partitions p
        ON st.object_id = p.object_id
    JOIN sys.allocation_units pa
        ON p.partition_id = pa.container_id
    JOIN tenant_table_registry t          -- your mapping table
        ON st.name = t.table_name
WHERE
    p.index_id IN (0, 1)                  -- heap or clustered index only
GROUP BY
    t.tenant_id
ORDER BY
    used_bytes DESC;

    The per-tenant forecast then runs Prophet independently per tenant, and the aggregate forecast is built by summing tenant forecasts. This prevents the "average is fine but one tenant is exploding" failure mode. When a single tenant's forecast exceeds a per-tenant quota threshold, the action is tenant-specific: notify the tenant, apply storage limits if the architecture supports them, or accelerate the migration of that tenant to a dedicated instance.

    The tenant-level capacity data also feeds churn modeling. A tenant whose storage growth rate is decelerating sharply and whose connection count is falling is showing pre-churn signal. That is not a capacity problem — it is a business problem. The capacity system surfaces it; the business system acts on it. Keeping these concerns separated at the data layer but unified at the metrics layer is what makes the autonomous system genuinely useful beyond pure infrastructure management.

    14.8 Failure Modes and Safety Boundaries

    Every autonomous provisioning system will eventually act on a bad forecast. The question is not whether it will happen but what the blast radius looks like when it does. The safety architecture has three layers: pre-action validation, action envelopes, and a circuit breaker.

    Pre-action validation checks that the action is coherent before execution:

  • → The new storage size is larger than the current size (never shrink autonomously)
  • → The new instance class exists in the approved ladder and is available in the target AZ
  • → The action does not conflict with a maintenance window defined in the operations calendar
  • → The recommendation is not older than the cooldown period (stale recommendations can be hazardous)

    • Action envelopes bound what the system can do autonomously:

  • → Maximum single-step storage increase: 50% of current size
  • → Maximum single-step instance class change: one rung on the ladder
  • → Maximum read replicas per autonomous decision: one
  • → No autonomous action between 08:00–09:30 or 17:00–18:00 local business time (peak risk windows)

    • The maintenance window check deserves its own implementation because it must be reliable even when the capacity system's dependencies are partially degraded:

    from datetime import datetime, time as dtime
import pytz

BUSINESS_TZ = pytz.timezone("America/New_York")
BLACKOUT_WINDOWS = [
    (dtime(8, 0), dtime(9, 30)),    # morning ramp-up
    (dtime(17, 0), dtime(18, 0)),   # evening peak
    (dtime(23, 30), dtime(0, 30)),  # midnight batch jobs -- wraps midnight
]


def is_in_blackout_window() -> bool:
    now_local = datetime.now(BUSINESS_TZ).time()
    for start, end in BLACKOUT_WINDOWS:
        if start <= end:
            if start <= now_local <= end:
                return True
        else:
            # Window wraps midnight
            if now_local >= start or now_local <= end:
                return True
    return False

    Circuit breaker: If three consecutive capacity actions within a 24-hour window result in validation failures, the circuit opens and the system stops acting autonomously. It continues to forecast and queue recommendations but routes them all to the escalation queue instead of executing. The circuit resets only when a human operator explicitly closes it after reviewing the failure history. This pattern borrows from distributed systems resilience design — the circuit breaker prevents a malfunctioning autonomous component from repeatedly hammering infrastructure in a degraded state.

    CIRCUIT_BREAKER_KEY = "capacity:circuit_breaker:open"
FAILURE_COUNTER_KEY = "capacity:circuit_breaker:failure_count"
FAILURE_THRESHOLD = 3
FAILURE_WINDOW_SECONDS = 86400  # 24 hours


def record_action_failure(r: redis.Redis):
    count = r.incr(FAILURE_COUNTER_KEY)
    r.expire(FAILURE_COUNTER_KEY, FAILURE_WINDOW_SECONDS)
    if count >= FAILURE_THRESHOLD:
        r.set(CIRCUIT_BREAKER_KEY, "open")
        log.error("CIRCUIT BREAKER OPENED: %d consecutive failures. "
                  "All capacity actions paused pending human review.", count)


def is_circuit_open(r: redis.Redis) -> bool:
    return r.exists(CIRCUIT_BREAKER_KEY) == 1


def close_circuit(r: redis.Redis):
    """Called by human operator after reviewing failure history."""
    r.delete(CIRCUIT_BREAKER_KEY)
    r.delete(FAILURE_COUNTER_KEY)
    log.info("Circuit breaker closed by operator.")

    The combination of pre-action validation, bounded envelopes, blackout windows, and a circuit breaker gives the autonomous system a defined safety surface. It will not fix every problem perfectly, but it will not make a bad situation dramatically worse through unbounded autonomous action.

    Key Takeaways

  • → Signal honesty before forecasting accuracy: An autonomous capacity system is only as reliable as its observability layer. Measure all five resource dimensions — storage, memory, compute, I/O, and connection throughput — at the database instance level, separated from the systems being monitored, before investing in forecasting sophistication.
  • → Match the forecasting model to the resource pattern: Use linear regression for monotonic resources like storage, seasonal models such as Prophet or SARIMA for cyclical resources like connection counts and CPU, and percentile-based headroom analysis for memory pressure. Applying a single model across all resource types produces forecasts that are right on average and wrong at the moments that matter.
  • → Preserve Terraform state integrity: When Terraform manages your infrastructure, the autonomous system must write to the variable layer and trigger controlled Terraform runs rather than calling cloud APIs directly. Out-of-band API calls create state drift that the next planned terraform apply will silently revert, potentially causing unplanned changes at the worst possible moment.
  • → Calibrate the action hierarchy to reversibility: Not all capacity actions carry the same risk. Connection pool adjustments are immediate and costless to reverse; instance resizes force failover windows; storage contractions are irreversible on most platforms. The autonomous system should act freely at the low-risk end of the hierarchy and escalate — not act autonomously — as the cost and irreversibility of an action increase.
  • → Close the loop with validated outcomes and a circuit breaker: Executing a provisioning action and moving on is incomplete automation. The system must validate that each action achieved its intended effect after a resource-specific settlement period, feed validated outcomes back into the forecasting model, and trip a circuit breaker after a defined number of consecutive validation failures to prevent a malfunctioning component from compounding infrastructure problems through repeated unchecked action.
