Chapter 17: Zero-Touch High Availability

High availability in autonomous systems is not a feature you configure once and monitor manually — it is a continuous, self-executing contract between your infrastructure and your uptime SLA. The moment a human must intervene to restore service, you have failed the ADE standard. This chapter covers the architecture and implementation of HA systems that detect failure, make promotion decisions, reroute traffic, reintegrate replicas, and validate their own health — all without a pager going off at 2 a.m. The patterns here apply across SQL Server Always On Availability Groups on WSFC, AGs orchestrated by Kubernetes operators, and hybrid topologies that span on-premises and cloud. The goal is not just fast failover — it is correct, reversible, and observable failover that a system can execute and explain without human involvement.

17.1 The Anatomy of a Zero-Touch Failover Event

Before automating failover, you must model every failure mode precisely. Autonomous systems do not fail over on a hunch — they fail over when a constellation of signals crosses a decision threshold. The difference between autonomous HA and naive auto-failover is the difference between a surgeon and a reflex: one evaluates context, the other reacts to a single stimulus.

The canonical failure taxonomy for HA systems has three tiers:

Tier 1 — Node failure. The primary database process is unreachable. This is unambiguous at the OS level: no TCP response on the database port, no heartbeat from the HA agent, process not running.

Tier 2 — Network partition. The primary is alive but cannot be reached by replicas or the load balancer. This is the most dangerous case for autonomous systems — a false positive here causes a split-brain condition where two nodes believe they are primary.

Tier 3 — Performance degradation masquerading as failure. The primary is responding, but query latency is so high that applications are timing out. Connections are queuing. Replication lag is climbing. This is not a hard failure — it is a soft failure that an autonomous system must distinguish from a real outage.

A production autonomous HA system evaluates signals across all three tiers before acting. The decision matrix looks like this:

SignalSourceThresholdWeight
TCP connectivityAG listener / load balancer health check3 consecutive failuresHigh
Replication lagsys.dm_hadr_database_replica_states redo queue> 30 secondsMedium
Replica quorumWSFC quorum votesMajority unreachableHigh
Transaction throughputPrometheus sql_exporter batch requests/secDrop > 80% in 60sMedium
OS-level processWSFC resource monitor / Kubernetes liveness probeProcess absentHigh

An autonomous system acts only when the aggregate signal exceeds a confidence threshold — typically, a combination of at least two High-weight signals or one High plus two Medium signals. This prevents failover storms triggered by transient network blips.

SELECT

    ar.replica_server_name,

    ars.synchronization_health_desc,

    ars.operational_state_desc,
    drs.synchronization_state_desc,

These queries are not run interactively — they are ingested every 10 seconds by the HA orchestration layer, stored as time-series metrics, and evaluated against the decision matrix. The HA agent is a consumer of this data, not a human.

17.2 WSFC Quorum and the Lease Contract: Autonomous Promotion Architecture

Windows Server Failover Cluster (WSFC) quorum is the autonomous HA framework for SQL Server at scale. Its architecture is worth studying not just as a tool but as a design pattern: it externalizes consensus to a vote-based quorum model, making the cluster's leadership state a shared, durable, observable fact rather than an assumption held by individual nodes.

The WSFC architecture for zero-touch HA rests on three contracts:

The Quorum Vote. Every node (and optional witness) holds votes. A cluster can only bring resources online — including the availability group — while it holds a majority of votes. If a partition splits the cluster, the side without majority stops rather than risking split-brain. No external signal is needed — the absence of quorum is itself the trigger that halts the minority side.

The Candidate Election. When the primary replica fails, automatic failover requires both SYNCHRONOUS_COMMIT availability mode and AUTOMATIC failover mode on the target secondary. The AG promotes the synchronous secondary with the most hardened log sequence, minimizing data loss. With REQUIRED_SYNCHRONIZED_SECONDARIES_TO_COMMIT set, a transaction cannot commit until the required number of secondaries has hardened it — giving a zero-data-loss guarantee under automatic failover.

The Health Lease. SQL Server reports instance health to the cluster through sp_server_diagnostics, which runs on a repeating interval (by default one third of the lease timeout). If diagnostics report unhealthy — or stop reporting before the lease timeout (default 20 seconds) expires — the cluster initiates failover. This prevents a scenario where a frozen SQL Server holds cluster resources while being unable to serve writes — a subtle split-brain vector.

The AG configuration for autonomous failover behavior is dense with tunable parameters that directly affect the decision logic:

-- AG-level health and timeout tuning for autonomous failover
ALTER AVAILABILITY GROUP [ProductionAG]
    SET (HEALTH_CHECK_TIMEOUT = 30000);   -- ms before cluster declares replica unhealthy

-- Per-replica session timeout controls how long the primary waits
-- for a secondary's ping before marking it disconnected
ALTER AVAILABILITY GROUP [ProductionAG]
    MODIFY REPLICA ON N'sqlag-replica1'
    WITH (SESSION_TIMEOUT = 10);          -- seconds

-- Lease timeout lives in the cluster resource, not in T-SQL:
-- Get-ClusterResource "ProductionAG" | Set-ClusterParameter LeaseTimeout 20000

The HEALTH_CHECK_TIMEOUT parameter is critical for autonomous operation. It bounds how long the cluster waits for sp_server_diagnostics to return before declaring the replica unhealthy and triggering failover. Too short, and transient diagnostic stalls cause failover storms; too long, and real outages go unremediated.

When a synchronous secondary falls behind or disconnects, the primary's REQUIRED_SYNCHRONIZED_SECONDARIES_TO_COMMIT setting determines whether writes block or continue. An autonomous HA controller watches the count of synchronized secondaries and can dynamically relax this setting during a degraded window — trading a bounded RPO increase for continued write availability — then restore it when the secondary recovers.

Python — AG DMV integration for autonomous monitoring:

import pyodbc
import time
import logging
from dataclasses import dataclass
from typing import Optional

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger("ag_monitor")

@dataclass
class AGClusterState:
    primary: str
    members: list
    failover_in_progress: bool
    sync_secondaries: list

AG_ENDPOINTS = [
    "DRIVER={ODBC Driver 18 for SQL Server};SERVER=sqlag-primary;Trusted_Connection=yes;",
    "DRIVER={ODBC Driver 18 for SQL Server};SERVER=sqlag-replica1;Trusted_Connection=yes;",
    "DRIVER={ODBC Driver 18 for SQL Server};SERVER=sqlag-replica2;Trusted_Connection=yes;",
]

CLUSTER_QUERY = """
SELECT
    ar.replica_server_name,
    ars.role_desc,
    ar.availability_mode_desc,
    ar.failover_mode_desc,
    ars.synchronization_health_desc,
    drs.redo_queue_size
FROM sys.availability_replicas ar
JOIN sys.dm_hadr_availability_replica_states ars
    ON ar.replica_id = ars.replica_id
LEFT JOIN sys.dm_hadr_database_replica_states drs
    ON ar.replica_id = drs.replica_id AND drs.is_local = 1
"""

def fetch_cluster_state() -> Optional[AGClusterState]:
    """
    Query each replica until one responds.
    In a real split-brain scenario, replicas may disagree on role —
    the quorum-holding side is authoritative, not any single node.
    """
    for dsn in AG_ENDPOINTS:
        try:
            conn = pyodbc.connect(dsn, timeout=5)
            cur = conn.cursor()
            cur.execute(CLUSTER_QUERY)
            members = [
                {
                    "name": row[0], "role": row[1], "avail_mode": row[2],
                    "failover_mode": row[3], "health": row[4],
                    "redo_queue_kb": row[5] or 0,
                }
                for row in cur.fetchall()
            ]
            conn.close()
            primary = next(
                (m["name"] for m in members if m["role"] == "PRIMARY"), None
            )
            sync = [
                m["name"] for m in members
                if m["role"] == "SECONDARY"
                and m["avail_mode"] == "SYNCHRONOUS_COMMIT"
            ]
            return AGClusterState(
                primary=primary,
                members=members,
                failover_in_progress=primary is None,
                sync_secondaries=sync,
            )
        except pyodbc.Error as e:
            logger.warning(f"Could not reach endpoint: {e}")
    return None

def evaluate_and_alert(state: AGClusterState):
    lagging = [
        m for m in state.members
        if m["redo_queue_kb"] > 1024 and m["role"] != "PRIMARY"
    ]
    if lagging:
        logger.warning(
            f"Secondaries exceeding redo-queue threshold: "
            f"{[m['name'] for m in lagging]}"
        )
    if not state.sync_secondaries:
        logger.error(
            "No synchronous secondary present — cluster is operating in async mode. "
            "RPO guarantee is degraded."
        )

if __name__ == "__main__":
    while True:
        state = fetch_cluster_state()
        if state:
            evaluate_and_alert(state)
        time.sleep(15)

This script is not a replacement for WSFC's own decision-making — it is a secondary observer that feeds into an alerting and audit trail, allowing the autonomous system to record why it made a failover decision in language that a post-incident review can parse.

17.3 SQL Server Always On and the Kubernetes Operator Model

SQL Server's Always On Availability Groups provide quorum-based leadership-election semantics through the cluster service. In Windows Server Failover Cluster (WSFC) deployments, quorum is managed by a cluster quorum resource — a vote-based lease that makes leadership a shared, observable fact. In containerized deployments (SQL Server on Kubernetes), the SQL Server Operator from the mssql-operator or community sql-server-k8s-operator replaces WSFC entirely.

The Kubernetes operator model is significant because it brings SQL Server HA into the same orchestration plane as the rest of the application stack. An operator is a custom Kubernetes controller that watches a Custom Resource Definition (CRD) representing the AG's desired state and continuously reconciles actual state to match it. When a primary pod dies, Kubernetes detects the pod failure, the operator observes the AG state change via the DMVs, elects a new primary from the healthy replicas, and updates the Service object that application connections point to — all within the reconciliation loop.

The AG CRD for an autonomous deployment looks conceptually like this in YAML:

apiVersion: sql.microsoft.com/v1
kind: SqlServer
metadata:
  name: sqlag-primary
spec:
  saPassword: "$(SA_PASSWORD)"
  edition: Developer
---
apiVersion: sql.microsoft.com/v1
kind: AvailabilityGroup
metadata:
  name: production-ag
spec:
  name: ProductionAG
  databases:
    - orders
    - inventory
  replicas:
    - server: sqlag-primary
      availabilityMode: SYNCHRONOUS_COMMIT
      failoverMode: AUTOMATIC
    - server: sqlag-replica1
      availabilityMode: SYNCHRONOUS_COMMIT
      failoverMode: AUTOMATIC
    - server: sqlag-replica2
      availabilityMode: ASYNCHRONOUS_COMMIT
      failoverMode: MANUAL
  listenerPort: 1433

The AUTOMATIC failover mode on synchronous replicas is what enables zero-touch behavior. When the operator detects that the primary replica is in a NOT_SYNCHRONIZING or DISCONNECTED state for longer than the configured health check threshold, it executes the equivalent of ALTER AVAILABILITY GROUP ... FORCE_FAILOVER_ALLOW_DATA_LOSS or a clean automatic failover depending on whether data loss is acceptable.

For the operator to make this decision autonomously, it must have clear policy guidance baked into the CRD:

SQL Server — verifying AG readiness for automatic failover:

-- Validates that both synchronous replicas are healthy and within failover policy
SELECT
    ag.name                             AS availability_group,
    ar.replica_server_name,
    ar.availability_mode_desc,
    ar.failover_mode_desc,
    ars.synchronization_health_desc,
    ars.is_local,
    ars.role_desc,
    CASE
        WHEN ar.failover_mode_desc = 'AUTOMATIC'
         AND ars.synchronization_health_desc = 'HEALTHY'
        THEN 'ELIGIBLE_FOR_AUTO_FAILOVER'
        ELSE 'NOT_ELIGIBLE'
    END                                 AS failover_eligibility
FROM sys.availability_groups ag
JOIN sys.availability_replicas ar
    ON ag.group_id = ar.group_id
JOIN sys.dm_hadr_availability_replica_states ars
    ON ar.replica_id = ars.replica_id
WHERE ag.name = 'ProductionAG';

A critical architectural consideration in zero-touch SQL Server HA is the handling of the AG listener after failover. The listener is a virtual network name (VNN) that clients connect to. In WSFC, the cluster updates DNS automatically. In Kubernetes, the operator updates the ClusterIP Service. In both cases, the connection rerouting is transparent to application code — but only if applications are using the AG listener or Service name, never the direct node IP. Autonomous HA systems enforce this at the infrastructure layer: direct-node connection strings are blocked by network policy, forcing all traffic through the abstraction layer that the operator controls.

17.4 Traffic Rerouting Without Human Intervention: AG Listeners and Read-Only Routing

Promoting a replica to primary is half the problem. The other half is getting client connections to the new primary before application-level timeouts cascade into a service outage. In autonomous systems, connection rerouting must happen in under 5 seconds in most SLA frameworks — which rules out DNS TTL-based approaches for latency-sensitive workloads.

The standard architecture for zero-touch traffic rerouting in SQL Server uses a layered approach:

Application → AG Listener (virtual network name) → Primary replica / Read-only routing list

The availability group listener is a virtual network name (VNN) with its own IP that always points at the current primary. On failover, the cluster moves the listener to the new primary and updates DNS. Applications connect to the listener name — never to a node IP — so rerouting is transparent. Read-only routing extends this: connections specifying ApplicationIntent=ReadOnly are redirected by the primary to a readable secondary from the routing list, offloading reporting traffic automatically:

-- Read-only routing list: reporting connections land on secondaries automatically
ALTER AVAILABILITY GROUP [ProductionAG]
    MODIFY REPLICA ON N'sqlag-primary'
    WITH (SECONDARY_ROLE (READ_ONLY_ROUTING_LIST = (N'sqlag-replica1', N'sqlag-replica2')));

ALTER AVAILABILITY GROUP [ProductionAG]
    MODIFY REPLICA ON N'sqlag-replica1'
    WITH (SECONDARY_ROLE (READ_ONLY_ROUTING_LIST = (N'sqlag-replica2', N'sqlag-primary')));

In Kubernetes, the operator updates the ClusterIP Service that application connections point to, achieving the same effect as the WSFC listener move. In both cases, autonomous HA systems enforce listener-based connectivity at the infrastructure layer: direct-node connection strings are blocked by network policy, forcing all traffic through the abstraction layer that the operator controls.

Where an extra TCP proxy tier is required in front of the listener, HAProxy performs active port health checks against each replica and routes write traffic only to the node currently holding the primary role:

# haproxy.cfg — relevant sections for autonomous primary routing
frontend sql_write
    bind *:1433
    mode tcp
    default_backend sql_primary

backend sql_primary
    mode tcp
    option tcp-check
    default-server inter 2s fall 3 rise 2 on-marked-down shutdown-sessions
    server sqlag-primary  10.0.1.1:1433 check
    server sqlag-replica1 10.0.1.2:1433 check backup
    server sqlag-replica2 10.0.1.3:1433 check backup

The key directive here is on-marked-down shutdown-sessions. When HAProxy's health check marks the current primary as down, it immediately tears down all existing connections to that node. This forces the application's connection pool to re-establish connections, which then hit the backend pool and land on the new primary. The total rerouting time is bounded by: HAProxy check interval (2s) × fall threshold (3) = 6 seconds worst case.

For workloads that cannot tolerate even 6 seconds of connection disruption, a service mesh approach using Envoy or Istio reduces this to sub-second. An Envoy TCP health check against port 1433 runs at 500ms intervals, and active request draining ensures in-flight transactions are completed before the connection is terminated. The trade-off is operational complexity — service mesh HA configuration is significantly more involved than HAProxy.

The application's connection string is the other half of failover resilience. SqlClient's ConnectRetryCount and ConnectRetryInterval parameters absorb the reconnection burst that follows a failover, so the application retries internally instead of surfacing errors:

-- Connection string parameters relevant to failover resilience
Server=ag-listener;Database=orders;Trusted_Connection=True;
ConnectRetryCount=3;          -- retry the open attempt 3 times
ConnectRetryInterval=10;      -- wait 10s between retries
ApplicationIntent=ReadWrite;  -- route to the primary replica
MultiSubnetFailover=True      -- parallel connection attempts across listener IPs

The ConnectRetryCount = 3 setting is particularly important: it means that during the 6-second HAProxy switchover window, client connection attempts are retried by the driver rather than failing with connection errors. From the application's perspective, queries slow down for a few seconds rather than returning errors. This is the correct behavior for a zero-touch system — transient slowness is acceptable; connection errors are not.

Verifying connection routing post-failover:

-- Run against the new primary after promotion
-- Confirms that application traffic has successfully rerouted
SELECT
    c.client_net_address,
    s.program_name,
    s.status,
    COUNT(*) AS connection_count,
    MAX(DATEDIFF(SECOND, s.last_request_start_time, GETUTCDATE()))
        AS max_seconds_since_request
FROM sys.dm_exec_connections c
JOIN sys.dm_exec_sessions s
    ON c.session_id = s.session_id
WHERE s.is_user_process = 1
  AND s.status <> 'sleeping'
GROUP BY c.client_net_address, s.program_name, s.status
ORDER BY connection_count DESC;

This query is executed by the post-failover validation routine — not a human — to confirm that application connections have landed on the new primary and are in running rather than suspended state, which would indicate stuck requests from the failed primary.

17.5 Self-Healing Replica Reintegration After Failover

Failover is a one-way event unless the system also handles replica reintegration autonomously. After a primary fails and is promoted away, the former primary — once recovered — must rejoin the cluster as a secondary. The AG automatically re-synchronizes a rejoined replica through log shipping catch-up: the former primary rolls back any uncommitted work from its divergent tail and applies the new primary's log stream until it is synchronized.

The AG rejoin flow works as follows: when the former primary comes back online, it contacts the new primary and negotiates the common log sequence. If the divergence is within the available log on the primary, the secondary rolls back and catches up automatically. If the divergence exceeds the available log — because the primary has already truncated past the divergence point — the replica must be reseeded: the autonomous system removes it from the AG, restores a fresh backup with NORECOVERY, and rejoins it.

Monitoring the reintegration process autonomously requires tracking data movement state and redo queue from the moment the former primary reconnects:

The autonomous reintegration policy is: if estimated_seconds_to_sync keeps growing over three consecutive evaluations during reintegration, suspend and resume data movement on the replica once and retry. If three resume attempts fail, quarantine the node — remove it from the read-only routing list, suspend its AG data movement, and generate a human-escalation alert. This is the one scenario where zero-touch fails gracefully into a managed-intervention state: the system has exhausted its automated recovery options and is explicitly communicating that human attention is required.

Replica reintegration after an AG failover is observable through the DMV layer:

Monitoring replica reintegration and data movement:

-- Tracks the progress of a replica rejoining the AG after primary failure
SELECT
    db_name(drs.database_id)            AS database_name,
    ar.replica_server_name,
    drs.synchronization_state_desc,
    drs.is_suspended,
    drs.suspend_reason_desc,
    drs.log_send_queue_size             AS pending_send_kb,
    drs.redo_queue_size                 AS pending_redo_kb,
    drs.log_send_rate                   AS send_rate_kb_per_sec,
    drs.redo_rate                       AS redo_rate_kb_per_sec,
    CASE
        WHEN drs.redo_rate > 0
        THEN (drs.redo_queue_size / drs.redo_rate)
        ELSE NULL
    END                                 AS estimated_seconds_to_sync
FROM sys.dm_hadr_database_replica_states drs
JOIN sys.availability_replicas ar
    ON drs.replica_id = ar.replica_id
WHERE drs.is_local = 0
ORDER BY drs.log_send_queue_size DESC;

The estimated_seconds_to_sync calculated column is what the autonomous system uses to decide whether to mark the rejoining replica as pending (expected to finish within SLA) or degraded (reintegration is taking longer than expected, possibly indicating storage or network issues on the rejoining node). This metric feeds into the cluster health dashboard and the replica promotion eligibility gate.

17.6 Autonomous Runbook Execution and Post-Failover Validation

The final layer of zero-touch HA is not the failover itself — it is the automated validation that follows. A failover that succeeds technically but leaves the system in a degraded or undiscovered state is a failure in the autonomous contract. Post-failover validation is the system's self-assessment: it must confirm that the new primary is healthy, that replication has resumed, that connections are routed correctly, that any dependent services have reconnected, and that the cluster is in a state where a second failover — if required — could succeed.

Autonomous runbook execution treats the post-failover sequence as a directed acyclic graph of checks, each with a pass/fail condition, a timeout, and an escalation policy:

[1] New primary responds on port 1433 and reports PRIMARY role in DMVs
    → PASS: continue
    → FAIL after 10s: re-evaluate candidate replicas, attempt second promotion

[2] sys.dm_hadr_database_replica_states shows at least one synchronizing secondary
    → PASS: continue
    → FAIL after 60s: alert, degrade RPO guarantee flag in cluster metadata

[3] Application connection count matches pre-failover baseline (±20%)
    → PASS: continue
    → FAIL after 30s: check AG listener DNS, force connection pool recycle

[4] Write throughput returns to baseline (±30%)
    → PASS: mark failover complete
    → FAIL after 120s: escalate to on-call — performance anomaly on new primary

[5] Former primary rejoins as secondary
    → PASS within 300s: full cluster health restored
    → FAIL after 300s: quarantine former primary, alert for manual inspection

This runbook is implemented as an orchestration script that reads cluster state at each step rather than assuming the previous step's side effects persist:

import pyodbc
import time
import logging
from enum import Enum
from typing import Callable, Optional

logger = logging.getLogger("failover_validator")

class CheckResult(Enum):
    PASS = "PASS"
    FAIL = "FAIL"
    TIMEOUT = "TIMEOUT"

def run_check_with_timeout(
    check_fn: Callable[[], bool],
    timeout_seconds: int,
    poll_interval: int = 5,
    name: str = "check",
) -> CheckResult:
    deadline = time.monotonic() + timeout_seconds
    while time.monotonic() < deadline:
        try:
            if check_fn():
                logger.info(f"[{name}] PASS")
                return CheckResult.PASS
        except Exception as e:
            logger.warning(f"[{name}] exception during check: {e}")
        time.sleep(poll_interval)
    logger.error(f"[{name}] TIMEOUT after {timeout_seconds}s")
    return CheckResult.TIMEOUT

def check_primary_reachable(dsn: str) -> bool:
    conn = pyodbc.connect(dsn, timeout=5)
    cur = conn.cursor()
    cur.execute("""
        SELECT ars.role_desc
        FROM sys.dm_hadr_availability_replica_states ars
        WHERE ars.is_local = 1
    """)
    role = cur.fetchone()[0]
    conn.close()
    return role == "PRIMARY"  # True only if this node believes it is primary

def check_replication_active(dsn: str, min_replicas: int = 1) -> bool:
    conn = pyodbc.connect(dsn, timeout=5)
    cur = conn.cursor()
    cur.execute("""
        SELECT COUNT(*)
        FROM sys.dm_hadr_database_replica_states
        WHERE synchronization_state_desc IN ('SYNCHRONIZED', 'SYNCHRONIZING')
          AND is_local = 0
    """)
    count = cur.fetchone()[0]
    conn.close()
    return count >= min_replicas

def check_cluster_complete(dsn: str, expected_members: int) -> bool:
    conn = pyodbc.connect(dsn, timeout=5)
    cur = conn.cursor()
    cur.execute("""
        SELECT COUNT(*)
        FROM sys.dm_hadr_availability_replica_states
        WHERE connected_state_desc = 'CONNECTED'
    """)
    count = cur.fetchone()[0]
    conn.close()
    return count >= expected_members

def execute_post_failover_runbook(
    new_primary_dsn: str,
    expected_cluster_size: int,
    escalation_fn: Callable[[str], None],
):
    steps = [
        (
            "primary_reachable",
            lambda: check_primary_reachable(new_primary_dsn),
            10,
            True,   # fatal if fails — cannot continue without primary
        ),
        (
            "replication_active",
            lambda: check_replication_active(new_primary_dsn),
            60,
            False,  # non-fatal — alert but continue
        ),
        (
            "cluster_complete",
            lambda: check_cluster_complete(new_primary_dsn, expected_cluster_size),
            300,
            False,
        ),
    ]

    for name, fn, timeout, is_fatal in steps:
        result = run_check_with_timeout(fn, timeout_seconds=timeout, name=name)
        if result != CheckResult.PASS:
            escalation_fn(
                f"Post-failover check '{name}' returned {result.value}. "
                f"Manual inspection required."
            )
            if is_fatal:
                logger.critical(
                    f"Fatal check '{name}' failed — halting runbook. "
                    f"Cluster may be in unsafe state."
                )
                return

    logger.info("Post-failover runbook complete. Cluster health validated.")

The escalation function passed into execute_post_failover_runbook is deliberately abstract — in practice it dispatches to a PagerDuty API, a Slack webhook, or an incident management system. The point is that escalation is the last resort in the autonomous contract: the runbook exhausts every automated recovery option before producing a human-visible alert.

A companion post-failover validation script runs T-SQL checks against the DMVs and posts results to a centralized monitoring table that the operator controller reads:

-- Post-failover health summary for autonomous AG validation
-- Insert into a shared audit table read by the orchestration layer
INSERT INTO dba.ag_failover_audit (
    failover_time,
    new_primary,
    ag_name,
    replica_count_healthy,
    max_redo_queue_kb,
    validation_status
)
SELECT
    SYSDATETIMEOFFSET()                                        AS failover_time,
    SERVERNAME                                                 AS new_primary,
    ag.name                                                    AS ag_name,
    SUM(CASE WHEN ars.synchronization_health_desc = 'HEALTHY'
             THEN 1 ELSE 0 END)                                AS replica_count_healthy,
    MAX(drs.redo_queue_size)                                   AS max_redo_queue_kb,
    CASE
        WHEN SUM(CASE WHEN ars.synchronization_health_desc = 'HEALTHY'
                      THEN 1 ELSE 0 END) >= 2
         AND MAX(drs.redo_queue_size) < 102400   -- under 100MB redo backlog
        THEN 'VALIDATED'
        ELSE 'DEGRADED'
    END                                                        AS validation_status
FROM sys.availability_groups ag
JOIN sys.availability_replicas ar
    ON ag.group_id = ar.group_id
JOIN sys.dm_hadr_availability_replica_states ars
    ON ar.replica_id = ars.replica_id
JOIN sys.dm_hadr_database_replica_states drs
    ON ar.replica_id = drs.replica_id
WHERE ag.name = 'ProductionAG'
GROUP BY ag.name;

The dba.ag_failover_audit table becomes the authoritative record of every failover event: what triggered it, when it occurred, who became primary, how long reintegration took, and whether post-failover validation passed. This table is read by the automated reporting layer to produce post-incident summaries without human authorship — the system describes what happened to itself.

17.7 Split-Brain Prevention: Fencing, STONITH, and Consensus Guarantees

Every automated HA system faces one adversarial scenario that cannot be resolved by checking metrics: the network partition where both the primary and a promoted replica believe they are the authoritative write endpoint. This is split-brain, and it is the failure mode that turns an HA system into a data consistency catastrophe.

Zero-touch HA does not just detect split-brain — it prevents it architecturally. The prevention mechanisms operate at three levels.

Level 1: Quorum-enforced primary exclusivity. In WSFC, the cluster can only bring the availability group online on the side holding a majority of quorum votes. A replica cannot become primary without quorum. A primary that loses quorum connectivity is taken offline rather than continuing to serve writes without a valid majority. The quorum vote is the arbiter — no quorum, no primary designation.

Level 2: STONITH (Shoot The Other Node In The Head). When a replica is promoted, it must ensure the former primary cannot continue accepting writes. STONITH accomplishes this by issuing a fencing command — typically a power cycle or network isolation command — through an out-of-band management interface (IPMI, AWS EC2 stop-instance API, Azure VM deallocate). The promotion is not considered complete until the fencing operation confirms the former primary is offline.

In cloud environments, STONITH is implemented through the provider's control plane API:

import boto3
import logging

logger = logging.getLogger("stonith")

def fence_instance(instance_id: str, region: str) -> bool:
    """
    Hard fence an EC2 instance by stopping it via the AWS API.
    Called by the HA orchestrator when a replica is promoted
    and the former primary's cluster membership has not been gracefully released.
    Used as a STONITH mechanism to guarantee the former primary cannot write.
    """
    ec2 = boto3.client("ec2", region_name=region)
    try:
        response = ec2.stop_instances(
            InstanceIds=[instance_id],
            Force=True   # Force=True bypasses graceful shutdown
        )
        state = response["StoppingInstances"][0]["CurrentState"]["Name"]
        logger.info(f"Fencing {instance_id}: instance state is now '{state}'")
        return state in ("stopping", "stopped")
    except Exception as e:
        logger.critical(
            f"STONITH FAILED for {instance_id}: {e}. "
            f"Human intervention required — potential split-brain."
        )
        return False

If STONITH fails — if the fencing operation cannot reach the management API, or the API returns an error — the autonomous system must not complete the promotion. Instead, it must halt the election and generate a critical alert. A failed fence is worse than a failed failover: a failed failover leaves you with no primary; a failed fence with a completed promotion leaves you with two primaries.

Level 3: Forced-failover sequencing. When the orchestrator issues the promotion command, it does so only after confirming the fencing operation succeeded and quorum majority is held. The sequencing is:

1. Confirm quorum majority on the surviving side
2. Confirm fencing of former primary (API acknowledgment)
3. Execute ALTER AVAILABILITY GROUP ... FORCE_FAILOVER_ALLOW_DATA_LOSS on the winning replica
4. Move the AG listener to the new primary and update DNS
5. Confirm sp_server_diagnostics reports healthy before opening client traffic

Step 2 must complete before step 3. This is not a best-effort sequence — it is enforced in the orchestrator's promotion code path. Any HA framework that promotes first and fences second is architecturally unsafe.

sequenceDiagram
    participant Quorum as WSFC Quorum
    participant Replica as Candidate Replica
    participant Fence as Fencing API (IPMI/Cloud)
    participant OldPrimary as Former Primary
    participant Listener as AG Listener

    Replica->>Quorum: Confirm majority held
    Quorum-->>Replica: Majority confirmed
    Replica->>Fence: Fence former primary
    Fence->>OldPrimary: Power cycle / network isolate
    Fence-->>Replica: Fence confirmed
    Replica->>Replica: ALTER AVAILABILITY GROUP ... FORCE_FAILOVER
    Replica->>Listener: Move listener to new primary
    Listener->>Replica: Route write traffic

*Promotion only proceeds after the fence is confirmed — a failed fence halts the sequence rather than risking dual primaries.*

The quorum configuration itself deserves periodic autonomous review — Node Majority for odd-node clusters, Node and File Share Majority for even-node clusters, plus dynamic quorum and dynamic witness behavior. An autonomous controller validates that the effective vote count still yields a strict majority after every topology change, because misconfigured quorum is the most common cause of split-brain in production WSFC environments.

17.8 Observable Failover: The Audit Trail That Explains Itself

An autonomous system that cannot explain its own decisions is unauditable and, in regulated environments, non-compliant. Zero-touch HA must generate a structured, timestamped, causal audit trail for every failover event: what signals triggered the decision, what threshold was crossed, what actions were taken in what sequence, and what the outcome of each action was.

The audit trail is not a log file — it is a structured database record that can be queried, compared across failover events, and used to improve the decision logic over time. Each failover event is a first-class entity:

-- Failover audit schema for autonomous HA
CREATE TABLE dba.failover_events (
    event_id            BIGINT IDENTITY(1,1) PRIMARY KEY,
    event_time          DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    ag_name             NVARCHAR(128) NOT NULL,
    trigger_signal      NVARCHAR(256) NOT NULL,  -- e.g., 'TCP_HEALTH_CHECK_FAILED'
    trigger_details     NVARCHAR(MAX),           -- raw signal data at decision time (JSON)
    former_primary      NVARCHAR(128) NOT NULL,
    new_primary         NVARCHAR(128) NOT NULL,
    candidate_set       NVARCHAR(MAX),           -- all replicas evaluated, with hardened LSN
    winning_candidate   NVARCHAR(128) NOT NULL,
    fence_attempted     BIT NOT NULL,
    fence_succeeded     BIT,
    promotion_time      DATETIMEOFFSET,
    listener_switch_time DATETIMEOFFSET,
    first_client_conn   DATETIMEOFFSET,
    replication_resumed DATETIMEOFFSET,
    total_downtime_ms   INT,
    validation_status   NVARCHAR(32),
    escalated           BIT NOT NULL DEFAULT 0,
    escalation_reason   NVARCHAR(MAX)
);

-- Indexes for post-incident analysis
CREATE INDEX IX_failover_events_time ON dba.failover_events (event_time DESC);
CREATE INDEX IX_failover_events_primary ON dba.failover_events (former_primary, event_time DESC);
GO

-- View for SLA reporting: downtime per calendar month
CREATE OR ALTER VIEW dba.monthly_ha_summary AS
SELECT
    DATEFROMPARTS(YEAR(event_time), MONTH(event_time), 1) AS month,
    COUNT(*)                                              AS failover_count,
    AVG(CAST(total_downtime_ms AS FLOAT))                 AS avg_downtime_ms,
    MAX(total_downtime_ms)                                AS max_downtime_ms,
    SUM(CAST(total_downtime_ms AS BIGINT)) / 1000.0        AS total_downtime_seconds,
    SUM(CASE WHEN escalated = 1 THEN 1 ELSE 0 END)         AS escalated_count,
    SUM(CASE WHEN validation_status = N'VALIDATED' THEN 1 ELSE 0 END) AS clean_failovers
FROM dba.failover_events
GROUP BY DATEFROMPARTS(YEAR(event_time), MONTH(event_time), 1);

The trigger_details JSON column stores the raw signal values at the moment the decision was made — the redo queue in KB, the seconds since the last sp_server_diagnostics heartbeat, the load balancer health check failure count. This is the evidence record that answers the post-incident question: "Why did the system fail over at 03:47?" The answer is not "because the cluster said so" — it is a structured document showing that the redo queue was 2.3 GB, the last diagnostics heartbeat was 38 seconds ago (above the 20-second lease timeout), and TCP connectivity had failed three consecutive checks in the preceding 6 seconds.

The equivalent SQL Server audit table captures the same causal chain but reads from DMV snapshots captured at the time of the operator's reconciliation loop:

-- SQL Server: failover audit schema in the DBA utility database
CREATE TABLE dba.ag_failover_events (
    event_id              BIGINT IDENTITY(1,1) PRIMARY KEY,
    event_time            DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    ag_name               NVARCHAR(128)  NOT NULL,
    former_primary        NVARCHAR(128)  NOT NULL,
    new_primary           NVARCHAR(128)  NOT NULL,
    trigger_signal        NVARCHAR(256)  NOT NULL,
    send_queue_at_trigger BIGINT,        -- log_send_queue_size KB at trigger time
    redo_queue_at_trigger BIGINT,        -- redo_queue_size KB at trigger time
    failover_type         NVARCHAR(64),  -- 'AUTOMATIC' or 'FORCED'
    data_loss_detected    BIT            NOT NULL DEFAULT 0,
    validation_status     NVARCHAR(32),
    total_downtime_ms     INT,
    operator_version      NVARCHAR(64),  -- operator image version that performed failover
    notes                 NVARCHAR(MAX)
);

The operator_version column is subtle but important: it records which version of the Kubernetes operator or cluster service executed the failover. When a failover behaves unexpectedly — too slow, incorrect candidate selection, fence failure — the operator version is the first variable to investigate. Autonomous systems evolve, and their audit trails must capture the version of the autonomous agent that made each decision, not just the decision itself.

Key Takeaways

  • → Zero-touch failover requires a multi-signal decision matrix, not a single trip-wire. Autonomous HA systems act on the aggregate of TCP connectivity, replication lag, replica quorum, and process health signals — preventing failover storms from transient network events while catching real outages with high confidence.
  • → WSFC quorum serves a single architectural role: it externalizes leadership state into a shared, durable medium so that no individual node can unilaterally claim primary status. Any HA framework that does not anchor leadership in external consensus is architecturally unsafe for autonomous operation.
  • → Traffic rerouting speed is determined by the health-check stack, not DNS. The combination of the AG listener move, HAProxy's interval-based TCP health checks with on-marked-down shutdown-sessions, and the driver's ConnectRetryCount delivers sub-10-second connection rerouting without application code changes or DNS TTL dependency.
  • → Split-brain prevention is non-negotiable and must be enforced by sequencing: acquire consensus key, confirm fencing, then promote. An HA system that promotes first and fences later — or that treats fencing as optional — exposes the cluster to dual-primary data corruption. Failed fencing must halt the promotion, not ignore the error.
  • → The failover audit trail is as important as the failover itself. A structured, queryable record of every trigger signal, candidate evaluation, fencing outcome, and validation result turns an autonomous HA system from a black box into an accountable agent — one that can explain its decisions to post-incident reviews, compliance auditors, and the next iteration of its own decision logic.
