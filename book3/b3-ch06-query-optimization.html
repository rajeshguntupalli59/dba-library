Chapter 6: Autonomous Query Optimization

Query performance is the most visible surface area of database operations — slow queries surface as customer complaints, SLA breaches, and on-call pages. Yet in most organizations, query tuning remains a manual, reactive, expert-dependent process: a DBA receives an alert, opens a query plan, adds an index, and deploys a fix hours later. Autonomous query optimization replaces this loop entirely. The system continuously observes execution plans, detects regressions and anti-patterns, tests optimization candidates, and deploys changes — without waiting for a human to notice something is wrong. This chapter covers the full architecture of an autonomous query optimization layer: how queries are captured and classified, how the system reasons about plan stability and index opportunities, how candidate optimizations are validated safely before deployment, and how a feedback loop ensures that changes persist only when they demonstrably improve production workloads.

Continuous Query Telemetry: Building the Observation Layer

Autonomous optimization is only as good as its observability. Before any decision can be made, the system needs a continuous, structured feed of query behavior — not sampled logs, not manual EXPLAIN runs, but a persistent, queryable record of every workload pattern the database encounters.

SQL Server provides Query Store as the foundation. It captures query text, plans, and runtime statistics per query, normalizing parameterized variants into a single query entry — so SELECT * FROM orders WHERE id = 42 and SELECT * FROM orders WHERE id = 99 collapse into one entry. This normalization is essential for pattern-level analysis. Query Store must be enabled on each database, with capture mode and retention tuned for high-volume systems.

SQL Server ships Query Store — a far richer structure that persists plan history, resource consumption over time, and supports plan forcing directly from T-SQL. It must be enabled per database and configured for appropriate retention.

-- Enable Query Store with production-appropriate settings
ALTER DATABASE [YourDatabase] SET QUERY_STORE = ON;
ALTER DATABASE [YourDatabase] SET QUERY_STORE (
    OPERATION_MODE           = READ_WRITE,
    CLEANUP_POLICY           = (STALE_QUERY_THRESHOLD_DAYS = 30),
    DATA_FLUSH_INTERVAL_SECONDS = 60,
    MAX_STORAGE_SIZE_MB      = 4096,
    INTERVAL_LENGTH_MINUTES  = 15,       -- granularity of runtime stats
    SIZE_BASED_CLEANUP_MODE  = AUTO,
    QUERY_CAPTURE_MODE       = AUTO,     -- filters low-impact noise
    MAX_PLANS_PER_QUERY      = 200,
    WAIT_STATS_CAPTURE_MODE  = ON        -- SQL Server 2017+
);

-- Find regressing queries: recent runtime 50%+ worse than historical baseline
SELECT TOP 50
    qt.query_sql_text,
    q.query_id,
    rs_recent.avg_duration   / 1000.0  AS recent_avg_ms,
    rs_hist.avg_duration     / 1000.0  AS hist_avg_ms,
    ROUND(
        100.0 * (rs_recent.avg_duration - rs_hist.avg_duration)
              / NULLIF(rs_hist.avg_duration, 0), 2
    )                                  AS pct_regression,
    rs_recent.count_executions         AS recent_executions,
    p_recent.plan_id                   AS recent_plan_id,
    p_hist.plan_id                     AS historical_plan_id
FROM sys.query_store_query q
JOIN sys.query_store_query_text  qt   ON q.query_text_id     = qt.query_text_id
JOIN sys.query_store_plan        p_recent ON p_recent.query_id = q.query_id
JOIN sys.query_store_runtime_stats rs_recent
    ON rs_recent.plan_id = p_recent.plan_id
JOIN sys.query_store_plan        p_hist   ON p_hist.query_id   = q.query_id
    AND p_hist.plan_id <> p_recent.plan_id
JOIN sys.query_store_runtime_stats rs_hist
    ON rs_hist.plan_id = p_hist.plan_id
WHERE rs_recent.last_execution_time > DATEADD(HOUR, -1, GETUTCDATE())
  AND rs_hist.last_execution_time   < DATEADD(HOUR, -2, GETUTCDATE())
  AND rs_hist.avg_duration          > 0
  AND rs_recent.avg_duration > rs_hist.avg_duration * 1.5
ORDER BY pct_regression DESC;

Beyond these built-in views, the autonomous system needs a time-series telemetry store — not just a point-in-time snapshot. The practical architecture uses a Prometheus scraper that exports Query Store and DMV metrics on a 30-second interval and writes them to a time-series database (Victoria Metrics, Thanos, or Prometheus itself with long retention). A Python collector handles the normalization and emission.

import pyodbc
import time
import requests
from datetime import datetime

PUSHGATEWAY_URL = "http://prometheus-pushgateway:9091"
DB_CONN = ("DRIVER={ODBC Driver 18 for SQL Server};"
           "SERVER=sql-prod-01;DATABASE=appdb;UID=monitor;PWD=secret")

def collect_query_stats():
    conn = pyodbc.connect(DB_CONN)
    cur  = conn.cursor()
    cur.execute("""
        SELECT TOP 500
            CONVERT(VARCHAR(64), qs.query_hash, 1) AS query_hash,
            LEFT(qt.text, 200)    AS query_preview,
            qs.execution_count    AS calls,
            qs.total_elapsed_time / 1000.0 / NULLIF(qs.execution_count, 0)
                                  AS mean_exec_ms,
            qs.total_logical_reads  AS logical_reads,
            qs.total_logical_writes AS logical_writes,
            qs.total_worker_time / 1000.0 AS total_cpu_ms
        FROM sys.dm_exec_query_stats qs
        CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) qt
        WHERE qs.execution_count > 10
        ORDER BY mean_exec_ms DESC
    """)
    rows = cur.fetchall()
    cols = [d[0] for d in cur.description]
    cur.close()
    conn.close()

    metrics = []
    ts = int(time.time() * 1000)

    for row in rows:
        record = dict(zip(cols, row))
        qid    = record["query_hash"]
        label  = f'query_hash="{qid}"'
        for metric in ["mean_exec_ms", "calls",
                       "logical_reads", "logical_writes", "total_cpu_ms"]:
            val = record.get(metric) or 0
            metrics.append(
                f'mssql_query_{metric}{{{label}}} {val} {ts}'
            )

    payload = "\n".join(metrics) + "\n"
    resp = requests.post(
        f"{PUSHGATEWAY_URL}/metrics/job/query_telemetry",
        data=payload,
        headers={"Content-Type": "text/plain"}
    )
    resp.raise_for_status()
    print(f"[{datetime.utcnow().isoformat()}] Pushed {len(rows)} query records")

if __name__ == "__main__":
    while True:
        try:
            collect_query_stats()
        except Exception as e:
            print(f"Error: {e}")
        time.sleep(30)

With this telemetry layer operational, the system has the raw material it needs to make decisions. The next step is classifying what kind of problem each query signature represents.

Plan Regression Detection and Automatic Plan Stabilization

Plan regression is one of the most insidious database failure modes. A query that ran in 12 ms for months suddenly takes 4.2 seconds — not because the query changed, but because a statistics update, a new index, or an automatic statistics update shifted the optimizer's cost estimates enough to select a different join strategy or access path. In a manually operated system, this surfaces as a P2 incident. In an autonomous system, it is detected within one collection interval and remediated before most users notice.

The detection model is straightforward: for each normalized query ID, maintain a rolling baseline of mean_exec_time and stddev_exec_time. When the observed mean exceeds baseline_mean + N * baseline_stddev (where N is a tunable sensitivity, typically 3), flag the query as a regression candidate. But raw statistical deviation is not sufficient — call volume matters. A query called twice is not a meaningful regression signal. The autonomous rule is:

> When calls_in_window >= 20 AND mean_exec_time > baseline_mean + 3 * baseline_stddev AND the trend is sustained for at least two consecutive collection intervals, classify the query as a confirmed regression and trigger the remediation pipeline.

SQL Server remediation is the cleaner case because Query Store supports plan forcing — pinning a query to a known-good historical plan with a single T-SQL statement.

-- Autonomous plan stabilization: force the last known-good plan
-- Called by the remediation engine when a regression is confirmed

DECLARE @query_id   BIGINT = 1042;       -- detected regressing query
DECLARE @good_plan_id BIGINT;

-- Find the plan with lowest avg_duration in the prior stable window
SELECT TOP 1
    @good_plan_id = p.plan_id
FROM sys.query_store_plan p
JOIN sys.query_store_runtime_stats rs ON rs.plan_id = p.plan_id
WHERE p.query_id = @query_id
  AND rs.last_execution_time BETWEEN
        DATEADD(DAY, -7, GETUTCDATE()) AND
        DATEADD(HOUR, -2, GETUTCDATE())   -- exclude the regression window
ORDER BY rs.avg_duration ASC;

-- Force the good plan
IF @good_plan_id IS NOT NULL
BEGIN
    EXEC sys.sp_query_store_force_plan
        @query_id   = @query_id,
        @plan_id    = @good_plan_id;

    -- Log the action for the autonomous audit trail
    INSERT INTO dba_autonomous_actions
        (action_type, target_id, target_plan_id, reason, acted_at)
    VALUES
        ('PLAN_FORCE', @query_id, @good_plan_id,
         'Regression detected: mean_exec_time exceeded 3-sigma baseline',
         GETUTCDATE());
END

SQL Server provides native plan forcing through Query Store (sp_query_store_force_plan) and plan guides. For the autonomous layer, Query Store plan forcing is the practical choice: the system identifies the last known good plan from Query Store history and forces it without touching application code — the same mechanism behind Automatic Tuning's automatic plan correction.

For SQL Server, once a plan is forced, the autonomous system must monitor whether the forced plan is still the correct choice after conditions change — for example, after a major data load that legitimately shifts the optimal join order. The system schedules a re-evaluation every 24 hours: it temporarily unforces the plan, observes runtime for one collection window, and forces again if the regression persists, or permanently unforces if the new plan is now stable and comparable in performance. This feedback loop prevents the system from accumulating stale plan forces indefinitely.

Autonomous Index Management: Discovery, Validation, and Lifecycle

Indexes are the highest-leverage knob in query optimization, and they are also the easiest source of configuration drift — redundant indexes consuming write overhead, missing indexes causing sequential scans at scale, and bloated indexes that were once useful but now serve dead workloads. An autonomous index management system handles all three dimensions continuously.

Discovery starts with execution plan analysis. SQL Server exposes whether a query performed a full table scan in a context where an index could have served it through sys.dm_db_index_usage_stats (user_scans against heaps and clustered indexes), actual execution plans, and sys.dm_db_missing_index_details.

-- Surface high-impact missing index recommendations from DMVs
-- The autonomous engine queries this on every 15-minute cycle
SELECT TOP 30
    ROUND(migs.avg_total_user_cost
          * migs.avg_user_impact
          * (migs.user_seeks + migs.user_scans), 0)  AS estimated_improvement_score,
    migs.user_seeks,
    migs.user_scans,
    ROUND(migs.avg_user_impact, 1)                   AS avg_pct_benefit,
    mid.statement                                     AS table_name,
    mid.equality_columns,
    mid.inequality_columns,
    mid.included_columns,
    -- Construct the index DDL automatically
    'CREATE INDEX [ADE_IDX_' +
        REPLACE(REPLACE(mid.statement, '[', ''), ']', '') + '_' +
        CAST(migs.group_handle AS VARCHAR) + ']'
    + ' ON ' + mid.statement
    + ' (' + ISNULL(mid.equality_columns, '')
    + CASE WHEN mid.equality_columns IS NOT NULL
            AND mid.inequality_columns IS NOT NULL THEN ', ' ELSE '' END
    + ISNULL(mid.inequality_columns, '') + ')'
    + ISNULL(' INCLUDE (' + mid.included_columns + ')', '')
    + ' WITH (ONLINE = ON, FILLFACTOR = 90)'     AS proposed_ddl,
    migs.last_user_seek
FROM sys.dm_db_missing_index_groups   mig
JOIN sys.dm_db_missing_index_group_stats migs ON migs.group_handle = mig.index_group_handle
JOIN sys.dm_db_missing_index_details   mid   ON mid.index_handle   = mig.index_handle
WHERE migs.avg_total_user_cost * migs.avg_user_impact
      * (migs.user_seeks + migs.user_scans)         > 10000  -- impact threshold
  AND migs.last_user_seek                           > DATEADD(HOUR, -4, GETUTCDATE())
ORDER BY estimated_improvement_score DESC;

For SQL Server, the autonomous system uses a combination of sys.dm_db_index_usage_stats, sys.dm_db_missing_index_details, and hypothetical index analysis via AUTOPILOT. AUTOPILOT lets the optimizer reason about an index that does not yet exist — the system defines a hypothetical index, requests the estimated plan (the query is never executed), checks whether the optimizer would use it, then rolls back the hypothesis without any write to disk.

Validation before deployment is non-negotiable. The autonomous system must not create indexes on production tables without a safety gate. The gate checks:

  • → Table size: if the table exceeds a configured threshold (e.g., 100 GB), the index build is scheduled during the maintenance window with WITH (ONLINE = ON) in SQL Server.
  • → Write amplification: the system estimates the additional write cost by querying DML rates from sys.dm_db_index_operational_stats. If the table sustains more than a configured number of inserts/updates per second, the estimated overhead is computed against available I/O headroom.
  • → Redundancy check: before any new index is created, the engine checks whether an existing index already covers the proposed columns, possibly with a superset of keys.

    • Lifecycle management closes the loop. An index that was useful during a past workload pattern becomes a pure write tax when that pattern disappears. The autonomous system tracks user_seeks and user_scans counts from sys.dm_db_index_usage_stats. When an index has recorded zero scans over a rolling 30-day window and the database has been active throughout that window, it is classified as a dead index and queued for removal — first disabled (SQL Server supports disabling without dropping), then dropped in the next maintenance window after a configurable hold period.

    Workload-Aware Statistics Management and Cardinality Feedback

    The SQL Server query optimizer is cost-based — it relies on statistics that describe the distribution of values in each column to estimate the number of rows a predicate will match. When those statistics are stale or insufficiently granular for the actual workload, the planner produces bad cardinality estimates, which cascade into bad plan choices. Autonomous statistics management means the system continuously monitors cardinality error rates and triggers targeted statistics updates rather than waiting for the auto-update statistics threshold to fire.

    The core signal is the cardinality error ratio: the ratio of estimated rows in the plan vs. actual rows returned at runtime. SQL Server exposes this after execution through Query Store's estimated vs. actual row counts and the last_rows / avg_rows columns in sys.dm_exec_query_stats.

    When cardinality error ratio exceeds a threshold (typically > 10x under-estimate or > 5x over-estimate on a high-frequency query), the autonomous system triggers targeted statistics refresh:

    -- Targeted statistics update with full scan for high-variance columns
-- SQL Server by default samples; FULLSCAN is expensive but accurate

UPDATE STATISTICS [dbo].[orders] [stat_orders_customer_segment]
WITH FULLSCAN, NORECOMPUTE;   -- NORECOMPUTE: we manage the schedule autonomously

-- For new multi-column statistics where none exist
IF NOT EXISTS (
    SELECT 1 FROM sys.stats s
    JOIN sys.stats_columns sc ON sc.object_id = s.object_id AND sc.stats_id = s.stats_id
    JOIN sys.columns c ON c.object_id = sc.object_id AND c.column_id = sc.column_id
    WHERE s.object_id = OBJECT_ID('dbo.orders')
      AND c.name = 'customer_segment'
      AND (SELECT COUNT(*) FROM sys.stats_columns sc2 WHERE sc2.stats_id = s.stats_id) > 1
)
BEGIN
    CREATE STATISTICS [stat_orders_status_segment]
        ON [dbo].[orders] ([status], [customer_segment])
        WITH FULLSCAN;
END

-- Record action
INSERT INTO dba_autonomous_actions
    (action_type, object_name, reason, acted_at)
VALUES (
    'STATISTICS_FULLSCAN',
    'dbo.orders(status, customer_segment)',
    'Cardinality error ratio 15x detected on QueryID 1042, plan switched to nested loop',
    GETUTCDATE()
);

    Beyond reactive statistics refresh, the autonomous system must also manage statistics for skewed distributions — columns where a small number of values dominate (e.g., an order_status column where 95% of rows have status completed). Standard histogram statistics handle these poorly. The pattern is to identify high-skew columns from sys.dm_db_stats_histogram (SQL Server 2016+), and increase the statistics target or create filtered indexes that serve the minority predicate values where skew causes plan failures.

    The Autonomous Validation and Rollback Feedback Loop

    None of the remediation actions described above — plan forcing, hint injection, index creation, statistics refresh — are safe to leave unverified. An autonomous optimization system is not a fire-and-forget script; it is a closed loop that measures whether its own actions produced the intended effect, and reverses them when they did not.

    The validation pattern is consistent across action types:

    1. Record a pre-action baseline. Before executing any change, snapshot the current mean_exec_time, calls, and I/O counters for the affected query or queries, alongside the exact action being taken and its rationale.

    2. Apply the change. Execute the plan force, index creation, hint injection, or statistics refresh, and log it in the dba_autonomous_actions audit table with a unique action ID.

    3. Observe the post-action window. Wait for a defined evaluation window (typically two to three collection intervals) to accumulate enough calls to be statistically meaningful, then re-measure the same metrics.

    4. Compare and decide. If the post-action metrics show sustained improvement relative to the pre-action baseline, the action is marked confirmed and left in place. If the metrics are unchanged or worse, the action is automatically reverted — the index is dropped, the plan is unforced, the hint is removed, or the statistics target is rolled back — and the audit record is updated with the outcome.

    *The autonomous validation and rollback loop applied consistently across every remediation type in this chapter.*

    This loop is what prevents an autonomous optimizer from accumulating stale or counterproductive changes over time. An index created in response to a transient reporting workload that never recurs, or a plan force that was correct at the time but has since become suboptimal as data distributions shifted, both get cleaned up automatically rather than persisting as silent technical debt that only a human audit would eventually catch.

    The evaluation window and improvement threshold are the two parameters that most determine how conservative or aggressive the loop behaves. A short window with a low improvement bar creates noisy, thrashing behavior — the system reverting and reapplying changes as normal variance crosses the threshold. A long window with a high bar makes the system slow to correct clearly bad decisions. Tuning these parameters against the specific workload's variance characteristics, rather than adopting a fixed industry default, is part of operating this system responsibly.

    Key Takeaways

  • → Autonomous query optimization depends on continuous, structured telemetry — Query Store and sys.dm_exec_query_stats — where Query Store provides native time windows through its runtime stats intervals, while DMV-based collectors need external snapshot-and-diff tooling to compute windowed rates from cumulative counters.
  • → Plan regression detection should combine statistical deviation (mean exceeding a multiple of baseline standard deviation) with a minimum call-volume threshold, so the system does not react to noise from low-frequency queries.
  • → SQL Server's Query Store supports native plan forcing via sp_query_store_force_plan, and Automatic Tuning can apply it autonomously — giving the autonomous layer an engine-native plan-pinning mechanism.
  • → Autonomous index management must validate candidates with a hypothetical-index tool (missing-index DMVs and AUTOPILOT hypothetical indexes on SQL Server) before committing to a real CREATE INDEX, and must track index usage over time to retire indexes that no longer serve live workloads.
  • → Every autonomous optimization action needs a validation and rollback loop: a recorded pre-action baseline, a defined observation window, and an automatic reversal path when the action does not produce the expected improvement — without this loop, the system accumulates unverified changes as technical debt.
