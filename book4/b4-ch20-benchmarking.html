Chapter 20: Benchmarking Vector Databases: Throughput, Latency, Recall

Choosing a vector database without benchmarking it is the equivalent of selecting a relational engine based on marketing collateral alone — you will eventually regret it. The vector database ecosystem is young, vendor claims are aggressive, and the gap between synthetic benchmark numbers and production behavior is wide enough to cause real incidents at scale. This chapter builds a rigorous framework for measuring what actually matters in vector search systems: query throughput, tail latency, and recall accuracy. You will learn how these three metrics interact (improving one often degrades another), how to construct benchmarks that reflect your actual workload rather than a vendor's best-case scenario, and how to interpret results from the most common tools in the ecosystem — SQL Server native vectors, Pinecone, Weaviate, Qdrant, and Milvus. By the end, you will have runnable harnesses, concrete thresholds to target, and a vocabulary for communicating vector database performance the same way you already communicate IOPS, latency percentiles, and cache hit ratios.

---

The Three Metrics That Define Vector Search Performance

Every vector database benchmark ultimately reduces to three numbers: throughput, latency, and recall. Understanding what each measures — and where the bodies are buried — is the prerequisite to designing any useful test.

Throughput is queries per second (QPS). It measures how many similarity searches the system can complete in a unit of time under sustained load. Like any throughput metric, it is meaningless without specifying concurrency. A system that delivers 500 QPS at 1 concurrent client and 480 QPS at 50 concurrent clients is a fundamentally different beast from one that delivers 500 QPS at 1 client and 12,000 QPS at 50 clients. Always measure throughput under the concurrency your application actually generates.

Latency is the time to complete a single query. In production systems, what matters is not mean latency but tail latency — specifically p95 and p99. A vector database with a 5ms mean and a 2,000ms p99 will make your application feel broken during load spikes. Most vector workloads are in the critical path of user-facing requests, which makes p99 the governing metric.

Recall is the fraction of true nearest neighbors that a query actually returns. It is the metric unique to approximate nearest neighbor (ANN) systems, and it has no direct analogue in traditional databases. If you ask for the 10 most similar vectors to a query, and the system returns 10 results but only 7 of them are genuinely in the true top-10, your recall@10 is 0.7. Recall is what separates ANN search from exact k-NN search — and it is what makes benchmarking vector databases harder than benchmarking relational systems.

The fundamental tension is this: recall, throughput, and latency form a triangle where you can optimize any two by sacrificing the third. Tightening recall requires searching more of the index graph, which increases latency and reduces throughput. Reducing latency requires searching less, which damages recall. This is not an implementation deficiency — it is the mathematical reality of ANN algorithms, and any honest benchmark must measure all three simultaneously.

The recall-latency curve is the most important diagnostic tool in vector database performance analysis. It plots recall (x-axis) against query latency (y-axis) at fixed concurrency, with each point representing a different index parameter setting. The database with the curve closest to the lower-right corner of the plot — high recall at low latency — wins that workload.

Practical thresholds for production systems:

| Metric | Acceptable | Good | Excellent |

|---|---|---|---|

| Recall@10 | > 0.90 | > 0.95 | > 0.99 |

| p99 latency (single node) | < 100ms | < 20ms | < 5ms |

| QPS (per node, 768-dim) | > 500 | > 2,000 | > 10,000 |

These numbers are for 768-dimensional embeddings (a common size from models like text-embedding-3-small and all-MiniLM-L6-v2) on a dataset of 1–10 million vectors. Dimensionality, dataset size, and filter complexity all shift these thresholds dramatically.

Constructing a Realistic Benchmark Dataset

Vendor benchmarks almost always use ANN-benchmarks datasets — SIFT1M, GIST1M, or GloVe — because they are public, reproducible, and make their systems look good. Your workload is probably none of those. Building a benchmark that predicts production behavior requires matching four properties of your real dataset: dimensionality, distribution, dataset size, and filter selectivity.

Dimensionality directly determines index build time, memory consumption, and query latency. OpenAI's text-embedding-3-large produces 3072-dimensional vectors. Cohere's embed-english-v3.0 produces 1024-dimensional vectors. Most open-source models produce 384–768 dimensions. Do not benchmark at 128 dimensions if you are going to deploy at 1536.

Distribution matters more than most engineers expect. ANN index structures (HNSW, IVF, ScaNN) exploit clustering in the vector space to skip regions during search. Randomly generated vectors are uniformly distributed in high-dimensional space and do not cluster — they are the worst case for ANN indices and the best case for demonstrating that an index provides no benefit. Real embedding vectors cluster by semantic topic. If your documents are all from a single domain (medical literature, legal contracts, software documentation), your vectors will cluster differently than a general-purpose corpus, and your recall numbers will differ from published benchmarks.

Filtered search is the single biggest gap between published benchmarks and production behavior. Most real applications combine vector similarity with metadata filters: "find the 10 most similar documents to this query, but only from this tenant's data, written after 2023-01-01, tagged as 'approved'." Pre-filtering (apply metadata filter first, then search remaining vectors) destroys recall when the filter is selective. Post-filtering (search vectors first, then apply filter) destroys recall when the filter eliminates most results. How a database handles this tradeoff — Qdrant's filterable HNSW, Weaviate's inverted-index integration, Pinecone's metadata filtering — is one of its most important production characteristics.

The following script generates a synthetic benchmark dataset that mirrors real embedding distributions by using actual sentence-transformers embeddings on sampled text:

# Python
# benchmark_dataset_generator.py
# Generates a realistic benchmark dataset using real embedding models
# Requires: sentence-transformers, numpy, h5py, datasets

import numpy as np
import h5py
import time
from sentence_transformers import SentenceTransformer
from datasets import load_dataset

def generate_benchmark_dataset(
    n_corpus: int = 100_000,
    n_queries: int = 1_000,
    model_name: str = "sentence-transformers/all-MiniLM-L6-v2",
    output_path: str = "benchmark_dataset.h5",
    batch_size: int = 512
):
    """
    Generates an HDF5 benchmark dataset in the ANN-benchmarks format.
    Uses real text embeddings for realistic vector distributions.
    
    HDF5 schema:
      /train   (n_corpus, dim)   float32  - corpus vectors
      /test    (n_queries, dim)  float32  - query vectors
      /neighbors (n_queries, 100) int32   - ground truth (computed exactly)
      /distances (n_queries, 100) float32 - ground truth distances
    """
    print(f"Loading model: {model_name}")
    model = SentenceTransformer(model_name)
    dim = model.get_sentence_embedding_dimension()
    print(f"Embedding dimension: {dim}")

    # Load a real text corpus for realistic distributions
    print("Loading corpus text from Wikipedia sample...")
    dataset = load_dataset(
        "wikipedia", "20220301.en",
        split="train",
        streaming=True,
        trust_remote_code=True
    )
    
    texts = []
    for item in dataset:
        # Extract first 256 characters of each article as a passage
        texts.append(item["text"][:256])
        if len(texts) >= n_corpus + n_queries:
            break
    
    corpus_texts = texts[:n_corpus]
    query_texts = texts[n_corpus:n_corpus + n_queries]
    
    print(f"Encoding {n_corpus} corpus documents...")
    t0 = time.time()
    corpus_vectors = model.encode(
        corpus_texts,
        batch_size=batch_size,
        show_progress_bar=True,
        normalize_embeddings=True  # Cosine similarity -> dot product
    ).astype(np.float32)
    encode_time = time.time() - t0
    print(f"Corpus encoding: {encode_time:.1f}s ({n_corpus/encode_time:.0f} docs/sec)")
    
    print(f"Encoding {n_queries} query vectors...")
    query_vectors = model.encode(
        query_texts,
        batch_size=batch_size,
        show_progress_bar=True,
        normalize_embeddings=True
    ).astype(np.float32)
    
    # Compute exact ground truth using brute-force cosine similarity
    # For normalized vectors, cosine similarity = dot product
    print("Computing exact ground truth (brute-force)...")
    k_gt = 100  # Store top-100 ground truth for evaluating recall@1 through @100
    
    neighbors = np.zeros((n_queries, k_gt), dtype=np.int32)
    distances = np.zeros((n_queries, k_gt), dtype=np.float32)
    
    # Process in batches to avoid OOM on large datasets
    query_batch_size = 100
    for i in range(0, n_queries, query_batch_size):
        batch = query_vectors[i:i + query_batch_size]
        # Matrix multiply: (batch_size, dim) x (dim, n_corpus) -> (batch_size, n_corpus)
        sims = np.dot(batch, corpus_vectors.T)
        # Get top-k indices (descending similarity)
        top_k_idx = np.argpartition(sims, -k_gt, axis=1)[:, -k_gt:]
        for j, row_idx in enumerate(range(i, min(i + query_batch_size, n_queries))):
            top_k_sorted = top_k_idx[j][np.argsort(sims[j, top_k_idx[j]])[::-1]]
            neighbors[row_idx] = top_k_sorted
            distances[row_idx] = sims[j, top_k_sorted]
        
        if i % 1000 == 0:
            print(f"  Ground truth: {i}/{n_queries} queries")
    
    # Write HDF5 compatible with ann-benchmarks tooling
    print(f"Writing dataset to {output_path}...")
    with h5py.File(output_path, "w") as f:
        f.create_dataset("train", data=corpus_vectors, compression="gzip")
        f.create_dataset("test", data=query_vectors, compression="gzip")
        f.create_dataset("neighbors", data=neighbors, compression="gzip")
        f.create_dataset("distances", data=distances, compression="gzip")
        f.attrs["dimension"] = dim
        f.attrs["n_corpus"] = n_corpus
        f.attrs["n_queries"] = n_queries
        f.attrs["model"] = model_name
        f.attrs["metric"] = "cosine"
    
    print(f"Dataset written: {corpus_vectors.nbytes / 1e6:.1f} MB corpus, "
          f"{query_vectors.nbytes / 1e6:.1f} MB queries")
    return output_path


if __name__ == "__main__":
    generate_benchmark_dataset(
        n_corpus=100_000,
        n_queries=1_000,
        model_name="sentence-transformers/all-MiniLM-L6-v2",
        output_path="minilm_100k_benchmark.h5"
    )

This produces an HDF5 file in the same format as ANN-benchmarks, so you can drop it into standard tooling or write your own evaluation loop. The critical design choice here is using real embeddings on real text: your benchmark dataset should come from the same distribution as your production data, or your recall numbers will be wrong by 5–15 percentage points.

Building a Multi-Database Benchmark Harness

With a dataset in hand, the next step is a consistent measurement harness that runs the same queries against multiple databases and captures the metrics that matter. The harness must be fair: each database should be given its best-case index configuration, not a default one. Default configurations almost always favor index build time over query performance, which is the opposite of production priorities.

@dataclass
class BenchmarkResult:
    database: str
    index_config: dict
    n_corpus: int
    n_queries: int
    concurrency: int
    k: int                          # Number of results requested
    # Throughput
    total_queries: int = 0
    total_time_sec: float = 0.0
    qps: float = 0.0
    # Latency (milliseconds)
    latencies_ms: List[float] = field(default_factory=list)
    p50_ms: float = 0.0
    p95_ms: float = 0.0
    p99_ms: float = 0.0
    # Recall
    recall_at_k: float = 0.0
    # Index build
    index_build_sec: float = 0.0
    index_size_mb: float = 0.0


def compute_recall(
    returned_ids: List[List[int]],
    ground_truth: np.ndarray,
    k: int
) -> float:
    """
    Computes recall@k: fraction of true top-k neighbors found in returned results.
    ground_truth shape: (n_queries, k_gt) — rows are sorted by similarity descending.
    """
    n_queries = len(returned_ids)
    recall_sum = 0.0
    for i in range(n_queries):
        true_top_k = set(ground_truth[i, :k].tolist())
        returned = set(returned_ids[i][:k])
        if len(true_top_k) > 0:
            recall_sum += len(true_top_k & returned) / len(true_top_k)
    return recall_sum / n_queries

class SqlServerBenchmark:
    """
    SQL Server 2025 native vector benchmark adapter.
    Compares exact VECTOR_DISTANCE search (ground truth, 100% recall)
    against approximate VECTOR_SEARCH over a DiskANN index.
    """

    def __init__(self, connection_string: str, table_name: str = "benchmark_vectors"):
        self.connection_string = connection_string
        self.table = table_name
        self.dim = 0

    @contextmanager
    def _conn(self):
        conn = pyodbc.connect(self.connection_string)
        try:
            yield conn
        finally:
            conn.close()

    def load_data(self, vectors: np.ndarray) -> float:
        """Loads corpus vectors and returns seconds elapsed."""
        n, dim = vectors.shape
        self.dim = dim
        t0 = time.time()
        with self._conn() as conn:
            cur = conn.cursor()
            cur.execute(f"IF OBJECT_ID('{self.table}', 'U') IS NOT NULL DROP TABLE {self.table}")
            cur.execute(f"""
                CREATE TABLE {self.table} (
                    id        INT NOT NULL CONSTRAINT PK_{self.table} PRIMARY KEY,
                    embedding VECTOR({dim}) NOT NULL
                )
            """)
            # Bulk insert: fast_executemany batches the parameter arrays
            cur.fast_executemany = True
            rows = [
                (i, "[" + ",".join(f"{v:.6f}" for v in vec) + "]")
                for i, vec in enumerate(vectors)
            ]
            cur.executemany(
                f"INSERT INTO {self.table} (id, embedding) "
                f"VALUES (?, CAST(? AS VECTOR({dim})))",
                rows
            )
            conn.commit()
        return time.time() - t0

    def build_diskann_index(self, maxdop: int = 4) -> float:
        """Builds the DiskANN vector index, returns build time in seconds."""
        t0 = time.time()
        with self._conn() as conn:
            cur = conn.cursor()
            cur.execute(
                f"IF EXISTS (SELECT 1 FROM sys.indexes "
                f"WHERE name = '{self.table}_diskann_idx') "
                f"DROP INDEX {self.table}_diskann_idx ON {self.table}"
            )
            cur.execute(f"""
                CREATE VECTOR INDEX {self.table}_diskann_idx
                ON {self.table} (embedding)
                WITH (METRIC = 'cosine', TYPE = 'DiskANN', MAXDOP = {maxdop})
            """)
            conn.commit()
        return time.time() - t0

    def run_queries(
        self,
        query_vectors: np.ndarray,
        k: int = 10,
        concurrency: int = 1,
        mode: str = "ann",
        top_n: int = 50
    ) -> tuple:
        """
        Returns (latencies_ms, all_returned_ids).
        mode='exact': VECTOR_DISTANCE ORDER BY — ground truth, 100% recall.
        mode='ann':   VECTOR_SEARCH over the DiskANN index with TOP_N over-fetch.
        """
        n_queries = len(query_vectors)
        latencies = []
        all_ids = []

        def single_query(i: int):
            vec = query_vectors[i]
            vec_lit = "[" + ",".join(f"{v:.6f}" for v in vec) + "]"
            conn = pyodbc.connect(self.connection_string)
            try:
                cur = conn.cursor()
                t0 = time.perf_counter()
                if mode == "exact":
                    cur.execute(f"""
                        SELECT TOP ({k}) id
                        FROM {self.table}
                        WHERE embedding IS NOT NULL
                        ORDER BY VECTOR_DISTANCE('cosine', embedding,
                                                 CAST(? AS VECTOR({self.dim})))
                    """, (vec_lit,))
                else:
                    # Join back to the table: VECTOR_SEARCH returns the key
                    # columns plus s.distance (see Chapter 2)
                    cur.execute(f"""
                        SELECT TOP ({k}) t2.id
                        FROM VECTOR_SEARCH(
                                 TABLE = {self.table} AS t,
                                 COLUMN = embedding,
                                 SIMILAR_TO = CAST(? AS VECTOR({self.dim})),
                                 METRIC = 'cosine',
                                 TOP_N = ?
                             ) AS s
                        JOIN {self.table} AS t2 ON t2.id = s.id
                        ORDER BY s.distance
                    """, (vec_lit, top_n))
                ids = [row[0] for row in cur.fetchall()]
                elapsed = (time.perf_counter() - t0) * 1000
                return elapsed, ids
            finally:
                conn.close()

        with concurrent.futures.ThreadPoolExecutor(max_workers=concurrency) as executor:
            futures = [executor.submit(single_query, i) for i in range(n_queries)]
            for future in concurrent.futures.as_completed(futures):
                lat, ids = future.result()
                latencies.append(lat)
                all_ids.append(ids)

        return latencies, all_ids


class QdrantBenchmark:
    """
    Qdrant benchmark adapter.
    Qdrant is particularly strong at filtered ANN — test with and without filters.
    """
    
    def __init__(
        self,
        url: str = "http://localhost:6333",
        collection_name: str = "benchmark"
    ):
        self.client = QdrantClient(url=url, timeout=60)
        self.collection = collection_name
    
    def load_data(self, vectors: np.ndarray, m: int = 16, ef_construction: int = 100) -> float:
        """Loads corpus and builds HNSW index simultaneously."""
        n, dim = vectors.shape
        
        # Delete existing collection
        try:
            self.client.delete_collection(self.collection)
        except Exception:
            pass
        
        t0 = time.time()
        self.client.create_collection(
            collection_name=self.collection,
            vectors_config=VectorParams(
                size=dim,
                distance=Distance.COSINE
            ),
            hnsw_config=HnswConfigDiff(
                m=m,
                ef_construct=ef_construction,
                full_scan_threshold=10_000  # Use HNSW for collections > 10k vectors
            ),
            optimizers_config=OptimizersConfigDiff(
                indexing_threshold=0  # Index immediately, don't batch
            )
        )
        
        # Batch upload
        batch_size = 1000
        for start in range(0, n, batch_size):
            end = min(start + batch_size, n)
            batch = vectors[start:end]
            points = [
                PointStruct(
                    id=start + i,
                    vector=batch[i].tolist()
                )
                for i in range(len(batch))
            ]
            self.client.upsert(collection_name=self.collection, points=points)
        
        # Wait for indexing to complete
        while True:
            info = self.client.get_collection(self.collection)
            if info.status.value == "green":
                break
            time.sleep(1.0)
        
        return time.time() - t0
    
    def run_queries(
        self,
        query_vectors: np.ndarray,
        k: int = 10,
        concurrency: int = 1,
        ef_search: int = 128
    ) -> tuple:
        latencies = []
        all_ids = []
        
        def single_query(i: int):
            vec = query_vectors[i].tolist()
            t0 = time.perf_counter()
            results = self.client.search(
                collection_name=self.collection,
                query_vector=vec,
                limit=k,
                search_params={"hnsw_ef": ef_search}
            )
            elapsed = (time.perf_counter() - t0) * 1000
            ids = [int(r.id) for r in results]
            return elapsed, ids
        
        with concurrent.futures.ThreadPoolExecutor(max_workers=concurrency) as executor:
            futures = [executor.submit(single_query, i) for i in range(len(query_vectors))]
            for future in concurrent.futures.as_completed(futures):
                lat, ids = future.result()
                latencies.append(lat)
                all_ids.append(ids)
        
        return latencies, all_ids

# Benchmark runner

def run_benchmark(
    dataset_path: str,
    sqlserver_conn: Optional[str] = None,
    qdrant_url: Optional[str] = None,
    concurrencies: List[int] = [1, 4, 16, 32],
    k: int = 10,
    top_n_values: List[int] = [10, 50, 100]
) -> List[BenchmarkResult]:
    """
    Runs the full benchmark suite against all configured databases.
    Returns a list of BenchmarkResult objects, one per (database, concurrency, TOP_N) combination.
    """
    # Load dataset
    print(f"Loading dataset from {dataset_path}...")
    with h5py.File(dataset_path, "r") as f:
        corpus = f["train"][:]
        queries = f["test"][:]
        ground_truth = f["neighbors"][:]
    
    n_corpus, dim = corpus.shape
    n_queries = len(queries)
    print(f"Dataset: {n_corpus:,} corpus vectors, {n_queries:,} queries, dim={dim}")
    
    results = []
    
    # ── SQL Server native vectors ─────────────────────────────────────────
    if sqlserver_conn:
        print("\n=== SQL Server native vectors benchmark ===")
        mssql = SqlServerBenchmark(sqlserver_conn)

        print("Loading data...")
        load_time = mssql.load_data(corpus)
        print(f"  Data load: {load_time:.1f}s")

        print("Building DiskANN index (MAXDOP=4)...")
        build_time = mssql.build_diskann_index(maxdop=4)
        print(f"  Index build: {build_time:.1f}s")

        # Exact search gives the ground truth for recall measurement
        print("Measuring exact-search baseline (ground truth)...")
        _, exact_ids = mssql.run_queries(queries, k=k, concurrency=4, mode="exact")
        exact_recall = compute_recall(exact_ids, ground_truth, k)
        print(f"  Exact baseline recall: {exact_recall:.4f} (should be 1.0000)")

        for top_n in top_n_values:
            for concurrency in concurrencies:
                print(f"  Querying: TOP_N={top_n}, concurrency={concurrency}")
                latencies, returned_ids = mssql.run_queries(
                    queries, k=k,
                    concurrency=concurrency,
                    mode="ann",
                    top_n=top_n
                )
                recall = compute_recall(returned_ids, ground_truth, k)
                latencies_sorted = sorted(latencies)

                result = BenchmarkResult(
                    database="sqlserver",
                    index_config={"type": "DiskANN", "metric": "cosine", "top_n": top_n},
                    n_corpus=n_corpus,
                    n_queries=n_queries,
                    concurrency=concurrency,
                    k=k,
                    total_queries=n_queries,
                    total_time_sec=sum(latencies) / 1000 / concurrency,
                    qps=n_queries / (sum(latencies) / 1000 / concurrency),
                    latencies_ms=latencies,
                    p50_ms=latencies_sorted[int(0.50 * len(latencies_sorted))],
                    p95_ms=latencies_sorted[int(0.95 * len(latencies_sorted))],
                    p99_ms=latencies_sorted[int(0.99 * len(latencies_sorted))],
                    recall_at_k=recall,
                    index_build_sec=build_time
                )
                results.append(result)
                print(f"    QPS={result.qps:.0f}  p99={result.p99_ms:.1f}ms  recall={recall:.4f}")

    # ── Qdrant ────────────────────────────────────────────────────────────────
    if qdrant_url:
        print("\n=== Qdrant benchmark ===")
        qd = QdrantBenchmark(qdrant_url)
        
        for m, ef_c in [(16, 100), (32, 128)]:
            print(f"  Loading data and building HNSW (m={m}, ef_construction={ef_c})...")
            build_time = qd.load_data(corpus, m=m, ef_construction=ef_c)
            print(f"  Index build+load: {build_time:.1f}s")
            
            for ef_s in ef_search_values:
                for concurrency in concurrencies:
                    print(f"  Querying: ef_search={ef_s}, concurrency={concurrency}")
                    latencies, returned_ids = qd.run_queries(
                        queries, k=k,
                        concurrency=concurrency,
                        ef_search=ef_s
                    )
                    recall = compute_recall(returned_ids, ground_truth, k)
                    latencies_sorted = sorted(latencies)
                    
                    result = BenchmarkResult(
                        database="qdrant",
                        index_config={"m": m, "ef_construction": ef_c, "ef_search": ef_s},
                        n_corpus=n_corpus,
                        n_queries=n_queries,
                        concurrency=concurrency,
                        k=k,
                        total_queries=n_queries,
                        total_time_sec=sum(latencies) / 1000 / concurrency,
                        qps=n_queries / (sum(latencies) / 1000 / concurrency),
                        latencies_ms=latencies,
                        p50_ms=latencies_sorted[int(0.50 * len(latencies_sorted))],
                        p95_ms=latencies_sorted[int(0.95 * len(latencies_sorted))],
                        p99_ms=latencies_sorted[int(0.99 * len(latencies_sorted))],
                        recall_at_k=recall,
                        index_build_sec=build_time
                    )
                    results.append(result)
                    print(f"    QPS={result.qps:.0f}  p99={result.p99_ms:.1f}ms  recall={recall:.4f}")
    
    return results


def print_summary_table(results: List[BenchmarkResult]):
    """Prints a formatted comparison table sorted by recall descending."""
    print("\n" + "=" * 90)
    print(f"{'Database':<12} {'Config':<30} {'Conc':>5} {'QPS':>8} {'p50ms':>7} "
          f"{'p99ms':>7} {'Recall':>8}")
    print("-" * 90)
    for r in sorted(results, key=lambda x: (-x.recall_at_k, x.p99_ms)):
        cfg = f"top_n={r.index_config.get('top_n','-')}"
        print(f"{r.database:<12} {cfg:<30} {r.concurrency:>5} {r.qps:>8.0f} "
              f"{r.p50_ms:>7.1f} {r.p99_ms:>7.1f} {r.recall_at_k:>8.4f}")
    print("=" * 90)


if __name__ == "__main__":
    import argparse
    parser = argparse.ArgumentParser()
    parser.add_argument("--dataset", default="minilm_100k_benchmark.h5")
    parser.add_argument("--sqlserver-conn", default=None)
    parser.add_argument("--qdrant-url", default=None)
    parser.add_argument("--concurrencies", nargs="+", type=int, default=[1, 4, 16, 32])
    parser.add_argument("--k", type=int, default=10)
    args = parser.parse_args()
    
    results = run_benchmark(
        dataset_path=args.dataset,
        sqlserver_conn=args.sqlserver_conn,
        qdrant_url=args.qdrant_url,
        concurrencies=args.concurrencies,
        k=args.k
    )
    print_summary_table(results)

This harness is intentionally modular. Adding a Weaviate or Milvus adapter means implementing load_data() and run_queries() following the same contract, then registering the adapter in run_benchmark(). The key design choice is measuring latency from the client's perspective — including network round-trip and serialization — not from inside the database engine. That is the number your users experience.

SQL Server Native Vectors: Index Tuning for Production Throughput

SQL Server 2025 native vectors are the most common starting point for teams already on the Microsoft stack, which means you inherit connection pooling via SqlClient, availability groups, ACID transactions, and decades of operational tooling. They are not the fastest vector option in pure QPS terms, but they are frequently the right answer when your dataset fits on your existing instances and your team already operates SQL Server.

Two access paths govern SQL Server vector performance: exact search with VECTOR_DISTANCE (a scan, 100% recall) and approximate search through the DiskANN index with VECTOR_SEARCH. The levers that matter most:

  • → **Index metric match.** The METRIC in CREATE VECTOR INDEX must equal the metric argument in every VECTOR_DISTANCE / VECTOR_SEARCH call. A mismatch silently disables the index and drops you to a full scan.
  • → **TOP_N over-fetch in VECTOR_SEARCH.** Higher TOP_N → better recall, higher latency. This is the recall-latency knob you sweep, analogous to ef_search in HNSW engines.
  • → **MAXDOP at index build time.** DiskANN builds are CPU-intensive; set MAXDOP in the WITH clause to use multiple cores, then schedule builds in maintenance windows.
  • → **Plan choice under filters.** With selective WHERE clauses the optimizer may choose a scan over the DiskANN index. Inspect actual execution plans and treat unexpected plan flips as the vector equivalent of a parameter-sniffing incident.

    • The relationship between TOP_N and the recall-latency tradeoff is the most important control knob during production tuning. The following T-SQL sweeps it against the exact-search baseline:

    -- SQL Server 2025: sweep TOP_N to find the recall-latency knee point
DECLARE @q VECTOR(1536) = '[0.1, 0.2, ...]';

-- TOP_N = 10: fast but lower recall
SELECT t2.id, s.distance
FROM VECTOR_SEARCH(
         TABLE = dbo.benchmark_vectors AS t,
         COLUMN = embedding,
         SIMILAR_TO = @q,
         METRIC = 'cosine',
         TOP_N = 10
     ) AS s
JOIN dbo.benchmark_vectors AS t2 ON t2.id = s.id
ORDER BY s.distance;

-- TOP_N = 50: balanced
SELECT t2.id, s.distance
FROM VECTOR_SEARCH(
         TABLE = dbo.benchmark_vectors AS t,
         COLUMN = embedding,
         SIMILAR_TO = @q,
         METRIC = 'cosine',
         TOP_N = 50
     ) AS s
JOIN dbo.benchmark_vectors AS t2 ON t2.id = s.id
ORDER BY s.distance;

-- TOP_N = 200: high recall, slower
SELECT t2.id, s.distance
FROM VECTOR_SEARCH(
         TABLE = dbo.benchmark_vectors AS t,
         COLUMN = embedding,
         SIMILAR_TO = @q,
         METRIC = 'cosine',
         TOP_N = 200
     ) AS s
JOIN dbo.benchmark_vectors AS t2 ON t2.id = s.id
ORDER BY s.distance;

-- Compare each run's result set against the exact ground truth:
SELECT TOP (10) id
FROM dbo.benchmark_vectors
WHERE embedding IS NOT NULL
ORDER BY VECTOR_DISTANCE('cosine', embedding, @q);

    One SQL Server behavior that surprises engineers coming from pure vector databases: the query optimizer can choose not to use the vector index. If your query includes a highly selective WHERE clause, the optimizer may decide a scan is cheaper than an index seek followed by a filter. This is generally correct behavior for small result sets, but it means your p99 latency can spike when a predicate causes plan flips. The remedy is to examine actual execution plans for queries that combine vector ranking with metadata filters, and to compare plans in a controlled test (the benchmark harness above makes this repeatable) to find the index-vs-scan crossover point.

    Parallelism is another SQL Server lever that most engineers do not configure for vector workloads. DiskANN index builds accept MAXDOP directly, so a build can use multiple CPU cores:

    -- SQL Server 2025: parallel DiskANN index build
CREATE VECTOR INDEX IX_benchmark_vectors_embedding
ON dbo.benchmark_vectors (embedding)
WITH (METRIC = 'cosine', TYPE = 'DiskANN', MAXDOP = 8);

-- Verify build parallelism and timing via the actual plan / Query Store
-- (Chapter 14 covers vector-specific wait and plan analysis)

    The tradeoff with build parallelism is predictable: it shortens the maintenance window at the cost of CPU pressure on the instance. Schedule builds off-hours, and at high query concurrency prefer letting concurrency itself saturate CPU cores rather than over-parallelizing individual operations.

    Weaviate and Milvus: Distributed Vector Search Benchmarking

    When your dataset exceeds single-node capacity — typically above 50–100 million vectors at 768 dimensions on a well-provisioned machine — you need a distributed vector database. Weaviate and Milvus both offer horizontal scaling, but with different architectural philosophies that produce different benchmark characteristics.

    Weaviate stores vectors alongside a rich object store and a built-in GraphQL/REST API. Its HNSW index is built per-shard, with shards distributed across nodes. The benchmarking implication is that inter-shard query fan-out adds latency that does not appear in single-node tests. When benchmarking Weaviate in a multi-node configuration, always include the scatter-gather latency by targeting the coordinator endpoint, not an individual shard node directly.

    Milvus separates compute and storage more aggressively. Its architecture includes query nodes (which hold loaded segments in memory), data nodes (which manage write-ahead logs and compaction), and an S3-compatible object store for persistence. The benchmarking implication is that Milvus latency is bimodal: queries against loaded segments are fast (all data in DRAM), but queries that trigger segment loading from object storage are dramatically slower. Always warm the query nodes before recording benchmark numbers.

    A minimal Weaviate benchmark query using the Python client:

    # Python — Weaviate v4 client benchmark query
import weaviate
import time
import numpy as np

def benchmark_weaviate(
    host: str,
    collection_name: str,
    query_vectors: np.ndarray,
    k: int = 10,
    ef_search: int = 128
) -> tuple:
    """
    Returns (latencies_ms, all_returned_ids) for a Weaviate collection.
    ef parameter controls HNSW search depth at query time.
    """
    client = weaviate.connect_to_local(host=host)
    collection = client.collections.get(collection_name)
    
    latencies = []
    all_ids = []
    
    try:
        for vec in query_vectors:
            t0 = time.perf_counter()
            results = collection.query.near_vector(
                near_vector=vec.tolist(),
                limit=k,
                return_properties=[],          # Only need the ID for recall computation
                additional_properties=["id"],
                query_properties=None,
                # ef is set at collection level via schema, not per-query in v4
            )
            elapsed_ms = (time.perf_counter() - t0) * 1000
            latencies.append(elapsed_ms)
            all_ids.append([obj.uuid for obj in results.objects])
    finally:
        client.close()
    
    return latencies, all_ids

    One Weaviate-specific tuning parameter deserves explicit attention: the ef parameter in the collection's HNSW configuration controls search depth at query time, similar to the TOP_N over-fetch in SQL Server's VECTOR_SEARCH. Unlike SQL Server, where TOP_N is a per-query argument, Weaviate requires updating the collection's efConfig via the schema API to change it without restarting. This makes dynamic ef sweeping more cumbersome in Weaviate — plan your benchmark parameter grid before starting rather than adjusting on the fly.

    Filtered Search Benchmarking: The Production Reality Check

    The scenario that breaks most vendor benchmark claims is filtered search. A realistic e-commerce or SaaS application rarely searches all vectors — it searches vectors belonging to a specific user, product category, date range, or tenant. The interaction between the vector index and the metadata filter is where architectural differences between databases become most visible.

    To measure filtered search performance, extend the benchmark dataset with synthetic metadata and test at several selectivity levels:

    # Python
# filtered_benchmark.py
# Tests recall and latency under metadata filtering at multiple selectivity levels

import numpy as np
import time
from qdrant_client import QdrantClient
from qdrant_client.models import (
    FieldCondition, Filter, MatchValue,
    Range, PointStruct, PayloadSchemaType
)


def load_qdrant_with_metadata(
    client: QdrantClient,
    collection_name: str,
    vectors: np.ndarray,
    n_categories: int = 100
):
    """
    Assigns each vector a random category_id (0..n_categories-1).
    Creates a payload index for fast filtered search.
    """
    n = len(vectors)
    categories = np.random.randint(0, n_categories, size=n)
    
    batch_size = 1000
    for start in range(0, n, batch_size):
        end = min(start + batch_size, n)
        points = [
            PointStruct(
                id=start + i,
                vector=vectors[start + i].tolist(),
                payload={"category_id": int(categories[start + i])}
            )
            for i in range(end - start)
        ]
        client.upsert(collection_name=collection_name, points=points)
    
    # Create payload index so Qdrant can use filterable HNSW
    client.create_payload_index(
        collection_name=collection_name,
        field_name="category_id",
        field_schema=PayloadSchemaType.INTEGER
    )
    
    return categories


def benchmark_filtered_query(
    client: QdrantClient,
    collection_name: str,
    query_vector: np.ndarray,
    category_id: int,
    k: int = 10,
    ef_search: int = 128
) -> tuple:
    """
    Returns (latency_ms, result_ids) for a filtered query.
    """
    query_filter = Filter(
        must=[
            FieldCondition(
                key="category_id",
                match=MatchValue(value=category_id)
            )
        ]
    )
    t0 = time.perf_counter()
    results = client.search(
        collection_name=collection_name,
        query_vector=query_vector.tolist(),
        query_filter=query_filter,
        limit=k,
        search_params={"hnsw_ef": ef_search}
    )
    elapsed_ms = (time.perf_counter() - t0) * 1000
    ids = [int(r.id) for r in results]
    return elapsed_ms, ids


def run_filtered_benchmark(
    client: QdrantClient,
    collection_name: str,
    query_vectors: np.ndarray,
    categories: np.ndarray,
    n_categories_list: list = [10, 100, 1000],
    k: int = 10
):
    """
    Tests how latency and result count vary with filter selectivity.
    With 100k vectors and n_categories=10, each bucket has ~10k vectors (low selectivity).
    With n_categories=1000, each bucket has ~100 vectors (high selectivity — hard case).
    """
    print(f"\n{'Selectivity':<20} {'n_categories':<15} {'Avg Latency':>12} "
          f"{'p99 Latency':>12} {'Avg Results':>12}")
    print("-" * 75)
    
    for n_cat in n_categories_list:
        # Re-assign categories at this granularity
        n_vectors = len(categories)
        cat_ids = categories % n_cat  # Map existing categories to smaller range
        
        latencies = []
        result_counts = []
        
        for i, qvec in enumerate(query_vectors):
            target_cat = int(cat_ids[i % n_vectors])
            lat, ids = benchmark_filtered_query(
                client, collection_name, qvec, target_cat, k=k
            )
            latencies.append(lat)
            result_counts.append(len(ids))
        
        selectivity = f"~{n_vectors // n_cat:,} vectors/cat"
        p99 = sorted(latencies)[int(0.99 * len(latencies))]
        avg_lat = sum(latencies) / len(latencies)
        avg_results = sum(result_counts) / len(result_counts)
        
        print(f"{selectivity:<20} {n_cat:<15} {avg_lat:>11.1f}ms "
              f"{p99:>11.1f}ms {avg_results:>12.1f}")

    When you run this across databases, the output reveals something that synthetic benchmarks hide entirely: highly selective filters (small buckets) cause different failure modes in different databases. In SQL Server, a highly selective filter may cause the optimizer to skip the DiskANN index in favor of a scan — which is slow but returns perfect recall. In Weaviate, the ef parameter drives how aggressively the system oversamples before filtering, so high selectivity requires increasing ef dramatically to maintain recall, which increases latency. In Qdrant, the filterable HNSW implementation tracks which vectors satisfy payload predicates inside the graph structure itself, which generally maintains recall at lower latency penalty — but requires the payload index to be created before ingest, not after.

    These are the kinds of behavioral differences that do not appear in any vendor benchmark and that will determine which database actually fits your production query pattern.

    Interpreting Benchmark Results: Common Traps

    Running a benchmark is easier than interpreting one. There are several systematic traps that cause engineers to make wrong decisions from correct data.

    The warm-cache trap. Most vector databases cache recently accessed graph nodes or segments in memory. Running your benchmark query set repeatedly will produce increasingly optimistic latency numbers as the cache warms. Always measure latency on a cold or realistically warm cache, which means either clearing the OS page cache before each run (echo 3 > /proc/sys/vm/drop_caches on Linux) or pre-warming with a separate query set that does not overlap your test queries.

    The single-client trap. If your application generates concurrent queries — and production applications almost always do — measuring at concurrency=1 gives you latency numbers that are optimistic by a factor of 2–5x for CPU-bound workloads. Measure at concurrency levels matching your peak application concurrency, not your baseline.

    The index-not-built trap. Some databases defer index construction until a threshold of writes is reached, or until a compaction job runs. Milvus, for example, will serve queries from growing segments using brute-force until a segment reaches a size threshold and gets indexed. If you run your benchmark immediately after loading, you may be benchmarking brute-force search, not ANN. Always verify index status before measuring. For Milvus, call utility.index_building_progress(). For Qdrant, check that collection_info.status == "green". For SQL Server, confirm the vector index exists in sys.indexes and that row counts match the expected corpus size before measuring.

    The metric distance trap. Cosine similarity and Euclidean distance produce different nearest neighbor orderings, and recall numbers computed against ground truth using the wrong metric will be meaningless. Always confirm that your ground truth was computed with the same distance metric as your index. The benchmark harness above uses cosine similarity (dot product on normalized vectors) throughout — verify this is consistent if you adapt it.

    The dimensionality compression trap. Some databases support scalar quantization (SQ8, SQ4) or product quantization (PQ) to compress vectors and reduce memory usage. These techniques trade recall for memory efficiency, sometimes dramatically. When comparing a quantized Milvus index against an unquantized SQL Server DiskANN index, you are not comparing like for like — you are comparing a memory-efficient approximate index against a full-precision one. Measure both the quantized and unquantized configurations if your target system uses quantization.

    Continuous Benchmarking in CI/CD

    A benchmark run before database selection is necessary but insufficient. Vector database performance degrades as data grows, as index parameters drift, and as query distributions shift when your application evolves. Embedding continuous benchmarks in your CI/CD pipeline catches regressions before they reach production.

    The practical approach is a lightweight nightly benchmark job that runs a fixed 1,000-query set against your staging database and emits three metrics to your observability platform: recall@10, p99 latency, and QPS at your standard concurrency. When any of these crosses a threshold — recall drops below 0.95, p99 exceeds 50ms, QPS falls below 1,000 — the pipeline fires an alert.

    # Python
# ci_benchmark.py
# Lightweight benchmark for CI integration — exits non-zero on regression

import sys
import h5py
import numpy as np
import pyodbc
import time

RECALL_THRESHOLD = 0.95
P99_LATENCY_THRESHOLD_MS = 50.0
MIN_QPS = 500.0

def run_ci_benchmark(dsn: str, dataset_path: str, k: int = 10) -> bool:
    """
    Returns True if all thresholds pass, False on regression.
    """
    with h5py.File(dataset_path, "r") as f:
        queries = f["test"][:100]   # Use 100 queries for speed in CI
        ground_truth = f["neighbors"][:]
    
    latencies = []
    returned_ids = []
    
    DIM = 1536  # must match benchmark_vectors.embedding
    conn = pyodbc.connect(dsn)
    cur = conn.cursor()
    for vec in queries:
        vec_str = "[" + ",".join(f"{v:.6f}" for v in vec) + "]"
        t0 = time.perf_counter()
        cur.execute(
            f"SELECT TOP ({k}) t2.id "
            f"FROM VECTOR_SEARCH( "
            f"         TABLE = benchmark_vectors AS t, "
            f"         COLUMN = embedding, "
            f"         SIMILAR_TO = CAST(? AS VECTOR({DIM})), "
            f"         METRIC = 'cosine', TOP_N = 50) AS s "
            f"JOIN benchmark_vectors AS t2 ON t2.id = s.id "
            f"ORDER BY s.distance",
            (vec_str,)
        )
        ids = [row[0] for row in cur.fetchall()]
        latencies.append((time.perf_counter() - t0) * 1000)
        returned_ids.append(ids)
    conn.close()
    
    # Compute metrics
    n = len(queries)
    recall = sum(
        len(set(ground_truth[i, :k]) & set(returned_ids[i][:k])) / k
        for i in range(n)
    ) / n
    latencies_sorted = sorted(latencies)
    p99 = latencies_sorted[int(0.99 * n)]
    qps = n / (sum(latencies) / 1000)
    
    print(f"Recall@{k}: {recall:.4f} (threshold: {RECALL_THRESHOLD})")
    print(f"p99 latency: {p99:.1f}ms (threshold: {P99_LATENCY_THRESHOLD_MS}ms)")
    print(f"QPS: {qps:.0f} (threshold: {MIN_QPS})")
    
    passed = True
    if recall < RECALL_THRESHOLD:
        print(f"FAIL: recall {recall:.4f} below threshold {RECALL_THRESHOLD}")
        passed = False
    if p99 > P99_LATENCY_THRESHOLD_MS:
        print(f"FAIL: p99 {p99:.1f}ms exceeds threshold {P99_LATENCY_THRESHOLD_MS}ms")
        passed = False
    if qps < MIN_QPS:
        print(f"FAIL: QPS {qps:.0f} below threshold {MIN_QPS}")
        passed = False
    
    return passed


if __name__ == "__main__":
    import argparse
    parser = argparse.ArgumentParser()
    parser.add_argument("--dsn", required=True)
    parser.add_argument("--dataset", required=True)
    args = parser.parse_args()
    
    passed = run_ci_benchmark(args.dsn, args.dataset)
    sys.exit(0 if passed else 1)

    Embed this in your CI pipeline as a step that runs after migrations and before promotion to staging. The dataset file is committed to artifact storage (not to the repository, as it can be hundreds of megabytes) and fetched at CI runtime. The thresholds are checked into source control alongside your application code, which means recall regressions are treated with the same severity as functional test failures.

    Choosing Between Databases: A Decision Framework

    After running benchmarks across SQL Server native vectors, Pinecone, Weaviate, Qdrant, and Milvus, most teams face the same question: given similar recall numbers at similar latency, how do I choose? Pure throughput numbers rarely decide the question. The decision rests on four operational dimensions that benchmarks illuminate but do not automatically answer.

    Dataset size and growth trajectory. If your dataset is under 5 million vectors today and is expected to grow slowly, SQL Server native vectors on a well-provisioned instance handle the workload with no additional infrastructure. The operational simplicity of a single system is worth significant throughput headroom. If your dataset is already in the tens of millions and growing at a rate that will require horizontal scaling within twelve months, start with a distributed system (Qdrant cluster, Weaviate with multiple shards, or Milvus) even if a single node would technically suffice today. Migration from single-node to distributed is painful; choosing the right architecture at 20M vectors is far cheaper than migrating at 80M.

    Filter complexity. If your queries are predominantly unfiltered — similarity search against the full corpus — most databases perform comparably at equivalent hardware spend. If your queries are predominantly filtered by high-cardinality metadata (per-user, per-tenant, per-category with thousands of categories), Qdrant's filterable HNSW is worth measuring carefully, because the recall-under-filter numbers differ meaningfully from unfiltered recall at the same ef parameter values.

    Operational maturity of your team. Milvus is architecturally sophisticated — it has separate query nodes, index nodes, data nodes, and a message queue — and running it reliably requires understanding all of those components. If your team has not operated distributed systems with complex topology before, the operational surface area is a real risk. Pinecone eliminates that risk entirely by being a managed service at the cost of query customization and egress pricing. There is no architecture decision that is universally correct; the right choice accounts for the humans who will be on call when it fails at 2am.

    Latency budget and tail behavior. Managed services like Pinecone have network round-trips to their API endpoints that add fixed latency regardless of index parameters. If your application requires sub-10ms p99 and it is co-located in the same cloud region as the vector database, self-hosted Qdrant or SQL Server native vectors will consistently outperform managed Pinecone on raw latency, because you eliminate the inter-service network hop. If your latency budget is 100ms and reliability is more important than raw speed, the managed operational model wins on total cost of ownership.

    Key Takeaways

  • → **Recall, latency, and throughput form an inseparable triangle:** you can optimize any two by sacrificing the third. Every benchmark must measure all three simultaneously at the same index configuration, or the results are misleading. The recall-latency curve — not a single headline QPS number — is the authoritative diagnostic.
  • → **Benchmark datasets must match production distributions:** vectors generated by real embedding models on domain-relevant text cluster differently from synthetic random vectors, and recall numbers differ by 5–15 percentage points between synthetic and realistic datasets. Always build benchmarks from actual embeddings of actual text.
  • → **Filtered search is where vendor benchmarks diverge most from production behavior:** the interaction between vector ANN indices and metadata filters produces dramatically different recall and latency outcomes across databases. Measure filtered recall at multiple selectivity levels before trusting any performance claim for a workload that combines similarity search with attribute filtering.
  • → **Index state validation is a prerequisite for valid measurements:** systems like Milvus, Qdrant, and SQL Server can serve queries without using the ANN index (exact-scan fallback), producing benchmark numbers that reflect brute-force search rather than ANN search. Always confirm index build completion and warm query caches with a separate, non-overlapping query set before recording measurements.
  • → **Continuous benchmarking in CI/CD converts a one-time evaluation into an ongoing regression signal:** committing recall thresholds, p99 latency limits, and minimum QPS values alongside application code ensures that schema migrations, index parameter changes, data growth, and dependency upgrades are caught before they degrade production search quality.
