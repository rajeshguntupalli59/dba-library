Chapter 22: Chunking Strategies for RAG

22.1 Why Chunking Is a Database Design Problem

Embedding models have context windows, but the reason you chunk documents goes deeper than model limits: a chunk is the unit of retrieval, and retrieval quality is dominated by chunk granularity. A 5,000-token document embedded as a single vector averages its meaning into mush — the vector for a runbook chapter says "this is vaguely about failover" instead of pointing at the exact step the user needs. A 20-token fragment, on the other hand, may be so context-free ("click OK to continue") that it matches everything and explains nothing.

Chunking is also a storage design problem, and you should think of it like page layout. Chunk size determines row count; row width (chunk text plus a 1,536-dimension vector is roughly 6 KB before overhead) determines page density; overlap determines how much of your storage is redundant by design; and chunk metadata columns determine what you can filter on at query time. Every decision in this chapter shows up in the table definition, the index size, and the retrieval latency.

The performance characteristics are well-understood: for a corpus of one million documents averaging 2,000 tokens, 512-token chunks with 64-token overlap produce approximately 4.3 million chunks. At 1,536 dimensions, that is roughly 25 GB of raw vector data before indexing overhead. These numbers matter when sizing your SQL Server vector table and planning the DiskANN index build.

---

22.2 Fixed-Size Chunking: Mechanics and Limits

Fixed-size chunking splits text every N tokens — typically 256 or 512 — regardless of content boundaries. It is the simplest strategy, the easiest to reason about for capacity planning, and the correct default when you are standing up your first RAG pipeline. Its weakness is that it cuts mid-sentence and mid-thought: a procedure split across a chunk boundary becomes two vectors that each half-answer the question.

# Python — fixed-size chunking by token count (tiktoken)
import tiktoken
enc = tiktoken.get_encoding("cl100k_base")

def fixed_chunks(text, size=512, overlap=64):
    toks = enc.encode(text)
    step = size - overlap
    return [enc.decode(toks[i:i + size])
            for i in range(0, len(toks), step)
            if toks[i:i + size]]

Size the chunks to your retrieval budget, not your model's context window. The retrieved chunks must fit in the LLM prompt alongside the question — five 512-token chunks consume ~2,500 tokens of context before the model writes a word. If your answers need tight precision (error codes, configuration values), prefer 256-token chunks and retrieve more of them; if your answers need narrative context (runbook procedures, design docs), prefer 512.

---

22.3 Overlap Design: What Gets Repeated and Why

Overlap exists for one reason: boundary sentences. Without overlap, the sentence straddling a chunk boundary belongs fully to neither chunk's vector, and a question about exactly that sentence retrieves two mediocre matches instead of one good one. A 10–15% overlap (50–64 tokens on a 512-token chunk) captures boundary context at a modest storage cost.

Overlap is redundant storage by design — budget for it. A 512-token chunk with 64-token overlap stores ~12.5% more vectors than the non-overlapping equivalent, and the DiskANN index grows with it. That is a fair price for retrieval quality, but do not let overlap creep to 50%: at that point you are paying for an index that is half duplicate, and the near-duplicate vectors distort the similarity ranking by crowding out genuinely different content.

---

22.4 Structural and Semantic Splitting

When your documents have structure, use it. Markdown headers, HTML sections, PDF outline levels, and code function boundaries are natural chunk edges — a chunk that starts at a heading and ends before the next heading is a self-contained unit of meaning, which is exactly what you want a vector to represent. Recursive character splitting (split on double newline, then single newline, then sentence, then word) approximates this without a real parser and is a solid middle ground.

Semantic splitting goes one step further: embed sentences individually, then group consecutive sentences whose embeddings are similar, cutting where the topic shifts. It produces chunks that respect meaning rather than formatting, at the cost of an extra embedding pass per document. Reserve it for high-value corpora where retrieval quality is the product — support knowledge bases, legal documents — not for bulk log ingestion where fixed-size chunking is fine.

Whichever strategy you choose, store the strategy as metadata. A ChunkStrategy column ('fixed-512', 'recursive-md', 'semantic') lets you A/B chunking strategies in production — serve 90% of traffic from one strategy, 10% from another, and measure which retrieves better answers. You cannot run that experiment if the strategy is only in your ETL script's git history.

22.5 Ingesting Chunks into SQL Server and Pinecone

The following pipeline chunks a document, embeds each chunk with OpenAI, and writes to SQL Server as the authoritative store — with the option to mirror vectors into Pinecone for pure-vector workloads at scale. SQL Server holds chunk text, metadata, and vectors in one transaction; Pinecone, when used, holds vectors plus a chunk ID foreign key.

-- SQL Server: chunk table with strategy metadata and versioning
CREATE TABLE dbo.DocumentChunks (
    ChunkId       BIGINT IDENTITY(1,1) NOT NULL
        CONSTRAINT PK_DocumentChunks PRIMARY KEY,
    DocId         NVARCHAR(100) NOT NULL,
    DocVersion    INT NOT NULL CONSTRAINT DF_DocumentChunks_Version DEFAULT (1),
    ChunkIndex    INT NOT NULL,
    ChunkStrategy NVARCHAR(40) NOT NULL,      -- 'fixed-512', 'recursive-md', ...
    ChunkSize     INT NOT NULL,                -- tokens, for sizing analysis
    OverlapTokens INT NOT NULL,
    ChunkText     NVARCHAR(MAX) NOT NULL,
    Embedding     VECTOR(1536) NOT NULL,
    ModelName     NVARCHAR(100) NOT NULL,
    TenantId      INT NOT NULL,
    CreatedAt     DATETIME2(0) NOT NULL
        CONSTRAINT DF_DocumentChunks_Created DEFAULT SYSUTCDATETIME(),
    CONSTRAINT UQ_DocumentChunks_DocVer_Chunk
        UNIQUE (DocId, DocVersion, ChunkIndex)
);
CREATE INDEX IX_DocumentChunks_Tenant_Doc
    ON dbo.DocumentChunks (TenantId, DocId, DocVersion);
-- Build the DiskANN index AFTER the bulk ingest, not before
-- (preview write constraints favor index-after-load):
CREATE VECTOR INDEX IX_DocumentChunks_Embedding
    ON dbo.DocumentChunks (Embedding)
    WITH (METRIC = 'cosine', TYPE = 'DiskANN', MAXDOP = 8);

# Python — chunk, embed, upsert to SQL Server (pyodbc), mirror to Pinecone
import openai, pyodbc, tiktoken
from pinecone import Pinecone   # optional: only if you mirror vectors

openai_client = openai.OpenAI()
pc = Pinecone(api_key="...") if MIRROR_TO_PINECONE else None
conn = pyodbc.connect("DRIVER={ODBC Driver 18 for SQL Server};"
                      "SERVER=localhost;DATABASE=ragdb;Trusted_Connection=yes;"
                      "Encrypt=yes;TrustServerCertificate=yes")

def vec_lit(emb): return "[" + ",".join(str(v) for v in emb) + "]"

def ingest(doc_id, version, text, tenant_id,
           strategy="fixed-512", size=512, overlap=64,
           model="text-embedding-3-small"):
    enc = tiktoken.get_encoding("cl100k_base")
    toks, step = enc.encode(text), size - overlap
    chunks = [enc.decode(toks[i:i + size])
              for i in range(0, len(toks), step) if toks[i:i + size]]
    embs = [e.embedding for e in
            openai_client.embeddings.create(input=chunks, model=model).data]
    cur = conn.cursor()
    for idx, (chunk, emb) in enumerate(zip(chunks, embs)):
        cur.execute("""MERGE dbo.DocumentChunks AS t
            USING (SELECT ? AS DocId, ? AS DocVersion, ? AS ChunkIndex,
                          ? AS ChunkStrategy, ? AS ChunkSize, ? AS OverlapTokens,
                          ? AS ChunkText, CAST(? AS VECTOR(1536)) AS Embedding,
                          ? AS ModelName, ? AS TenantId) AS s
            ON t.DocId = s.DocId AND t.DocVersion = s.DocVersion
               AND t.ChunkIndex = s.ChunkIndex
            WHEN MATCHED THEN UPDATE SET ChunkText = s.ChunkText,
                Embedding = s.Embedding, ModelName = s.ModelName
            WHEN NOT MATCHED THEN INSERT (DocId, DocVersion, ChunkIndex,
                ChunkStrategy, ChunkSize, OverlapTokens, ChunkText,
                Embedding, ModelName, TenantId)
                VALUES (s.DocId, s.DocVersion, s.ChunkIndex, s.ChunkStrategy,
                        s.ChunkSize, s.OverlapTokens, s.ChunkText,
                        s.Embedding, s.ModelName, s.TenantId);""",
            (doc_id, version, idx, strategy, size, overlap,
             chunk, vec_lit(emb), model, tenant_id))
        if pc:  # mirror: vector + metadata only, text stays in SQL Server
            pc.Index("rag-vectors").upsert([{
                "id": f"{doc_id}:v{version}:{idx}",
                "values": emb,
                "metadata": {"tenant": tenant_id, "chunk_id_hint": idx}}])
    conn.commit()
    return len(chunks)

One Pinecone-specific concern worth flagging: metadata stored alongside vectors is not free — each vector's metadata counts toward index size. Storing full chunk text in Pinecone metadata avoids a round-trip to SQL Server but inflates costs for large corpora. The pattern above keeps authoritative text in SQL Server and only a chunk ID hint in Pinecone metadata, so retrieval does one key lookup back to the database for the rows it actually uses.

22.6 Querying Across Chunk Strategies: Parent-Child Retrieval

Small chunks retrieve precisely; large chunks provide context. Parent-child retrieval gets both: index small child chunks (128–256 tokens) for the similarity search, but return their larger parent chunks (1,024+ tokens) to the LLM. The retrieval is precise, the context is rich.

-- SQL Server: parent-child retrieval
-- ChildChunks(ChunkId, ParentId, Embedding VECTOR(1536), ...)
-- ParentChunks(ParentId PK, ParentText NVARCHAR(MAX), ...)
DECLARE @q VECTOR(1536) = '[0.12, 0.87, ...]';  -- embedded question

SELECT DISTINCT p.ParentId, p.ParentText
FROM (
    SELECT TOP (20) c.ParentId
    FROM dbo.ChildChunks AS c
    WHERE c.TenantId = @tenant
      AND VECTOR_DISTANCE('cosine', c.Embedding, @q) < @maxDistance
    ORDER BY VECTOR_DISTANCE('cosine', c.Embedding, @q)
) AS hits
JOIN dbo.ParentChunks AS p ON p.ParentId = hits.ParentId;
-- DISTINCT collapses multiple child hits under the same parent

Chunk-level filtering: the metadata columns you attach at ingestion become filter dimensions at query time. In SQL Server this is a standard T-SQL WHERE clause combined with the vector similarity predicate:

-- SQL Server: retrieve chunks from a specific document version,
-- tenant-scoped, with similarity ranking
DECLARE @q VECTOR(1536) = '[0.12, 0.87, ...]';

SELECT TOP (10) ChunkId, ChunkText,
       VECTOR_DISTANCE('cosine', Embedding, @q) AS Distance
FROM dbo.DocumentChunks
WHERE TenantId = @tenant
  AND DocId = @doc
  AND DocVersion = (SELECT MAX(DocVersion)
                    FROM dbo.DocumentChunks WHERE DocId = @doc)
ORDER BY Distance;

Pre-filtering on metadata before the vector similarity scan is an important performance decision. With a DiskANN index, a filtered ANN search that is highly selective can be inefficient — for high-selectivity filters (eliminating more than ~90% of rows), an exact scan over the filtered subset via VECTOR_DISTANCE with ORDER BY often outperforms the ANN path. Measure both on your data (Chapter 20) rather than assuming the index always wins.

22.7 Choosing a Chunking Strategy by Document Type

  • → Runbooks and procedures: structural splitting on headings. Steps must stay together; a boundary cut inside a procedure is the most damaging failure mode.
  • → Q&A and support articles: one chunk per question-answer pair. The natural unit of the content is the natural unit of retrieval.
  • → Long narrative docs and design records: fixed 512-token chunks with 64-token overlap, or parent-child with 256-token children for precision.
  • → Code: split on function/class boundaries, keep signatures with bodies, and store the file path and symbol name as metadata columns. Never split mid-function.
  • → Tables and structured data: one chunk per row-group with the column headers repeated in each chunk's text — a vector of bare numbers without headers retrieves on noise.

    • Match chunk granularity to query granularity. If your users ask narrow factual questions ("What is the default max server memory for this workload?"), small precise chunks (128–256 tokens) will outperform large ones. If your users ask synthesis questions ("Summarize the tradeoffs between rowstore and columnstore for this workload"), larger chunks (512+ tokens) serve better. When one application serves both, the parent-child pattern from Section 22.6 is the production-grade solution.

    22.8 Measuring Chunking Quality

    Chunking quality is measured the same way retrieval quality is measured: with a labeled evaluation set of questions and the chunks that should answer them. Build 50–100 representative questions against your corpus, record the expected answer fragment for each, then score strategies by the fraction of questions whose expected fragment appears in the top-k retrieved chunks.

    -- SQL Server: evaluation samples live next to the chunks
CREATE TABLE dbo.ChunkEvalSamples (
    SampleId INT IDENTITY(1,1) NOT NULL CONSTRAINT PK_ChunkEvalSamples PRIMARY KEY,
    Question NVARCHAR(1000) NOT NULL,
    QuestionEmbedding VECTOR(1536) NOT NULL,  -- embedded with the same model
    ExpectedFragment NVARCHAR(500) NOT NULL,  -- must appear in a top-k chunk
    StrategyUnderTest NVARCHAR(40) NOT NULL
);
-- Score: for each sample, retrieve top-5 chunks of that strategy and check
-- whether ExpectedFragment appears; aggregate the hit rate per strategy.

    Run the evaluation per strategy using the ChunkStrategy column to partition, and re-run it whenever you change chunk size, overlap, or the embedding model. A strategy change that improves one query type often degrades another — the eval set is how you see the tradeoff before your users do.

    22.9 Operational Considerations: Re-Chunking and Schema Evolution

    Chunking strategies evolve: you start with fixed-512, discover your runbooks need structural splitting, and now half your corpus uses the old strategy. The DocVersion column in the schema above makes this manageable — re-chunk a document as a new version, backfill in batches, and switch the retrieval query to MAX(DocVersion) only when the new version is complete. Old versions stay queryable during the cutover and provide an instant rollback.

    The practical response to a model upgrade is the same pattern one level up: store the model name and version alongside each chunk and treat model upgrades as full re-ingestion events. Pinecone's approach is to create a new index for the upgraded model and switch query traffic only after full re-ingestion, using a feature flag. In SQL Server, add a second vector column for the new model and backfill it in batches before switching the query path:

    -- SQL Server: side-by-side model migration
ALTER TABLE dbo.DocumentChunks ADD Embedding_v2 VECTOR(3072) NULL;
-- Backfill in batches (online, throttled):
-- UPDATE TOP (10000) dbo.DocumentChunks
-- SET Embedding_v2 = ... WHERE Embedding_v2 IS NULL;
CREATE VECTOR INDEX IX_DocumentChunks_Embedding_v2
    ON dbo.DocumentChunks (Embedding_v2)
    WITH (METRIC = 'cosine', TYPE = 'DiskANN', MAXDOP = 8);
-- Switch retrieval to Embedding_v2, then:
-- ALTER TABLE dbo.DocumentChunks DROP COLUMN Embedding;
-- DROP INDEX IX_DocumentChunks_Embedding ON dbo.DocumentChunks;

    Key Takeaways

  • → Chunking is a database design decision: chunk size sets row counts, row width sets page density, overlap is redundant storage by design, and metadata columns become query-time filters.
  • → Start with fixed-size chunking (256–512 tokens, 10–15% overlap); graduate to structural splitting where documents have headings, and semantic splitting where retrieval quality is the product.
  • → Store chunking strategy, size, overlap, model name, and document version as columns — they are the dimensions you will filter, evaluate, and migrate on.
  • → Use parent-child retrieval when one application serves both precise factual questions and synthesis questions: small children for ranking, large parents for context.
  • → For highly selective metadata filters, an exact VECTOR_DISTANCE scan over the filtered subset can beat the DiskANN path — measure both (Chapter 20).
  • → Re-chunk as new document versions and migrate embedding models side-by-side with a second vector column; never mix models or strategies in one query path without a version predicate.
