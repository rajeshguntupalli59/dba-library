Chapter 31: Multi-Modal Search: Text and Image Together

Most production search systems today handle one modality at a time — a text query searches text, an image query searches images. But users do not experience information in those silos. A retail customer uploads a photo of shoes and types "like these but in red." A medical researcher searches with an MRI scan and a clinical note simultaneously. A news archive needs to find articles where the image and headline tell contradictory stories. These compound queries require a database layer that understands both text and images as first-class embedding types and can combine them during retrieval. This chapter covers the embedding models that bridge the modality gap, the storage and indexing strategies for mixed-type vectors, the query architectures that fuse signals from both dimensions, and the production patterns that make multi-modal search scale reliably.

---

The Embedding Bridge: How Text and Images Share a Vector Space

The foundational insight behind multi-modal search is that text and images can be embedded into the *same* vector space — a shared coordinate system where semantic proximity means the same thing regardless of modality. A vector for the text "golden retriever playing fetch" and a vector for an actual photograph of that scene should land close together in this space. This is not obvious from first principles; it required learning a joint embedding model from hundreds of millions of image-caption pairs.

CLIP and Its Descendants

OpenAI's CLIP (Contrastive Language-Image Pre-training, 2021) established the practical template. CLIP trains a text encoder and an image encoder jointly using contrastive loss — during training, the model pulls matching image-text pairs together while pushing non-matching pairs apart. The result is two encoders that produce vectors in the same 512- or 768-dimensional space.

*Text and image encoders trained jointly land vectors in the same coordinate system — this is what makes cross-modal retrieval possible.*

For production use, the relevant CLIP derivatives include:

| Model | Dimensions | Notes |

|---|---|---|

| openai/clip-vit-base-patch32 | 512 | Baseline; widely benchmarked |

| openai/clip-vit-large-patch14 | 768 | Better quality, higher latency |

| laion/CLIP-ViT-H-14-laion2B-s32B-b79K | 1024 | Trained on LAION-2B; strong zero-shot |

| sentence-transformers/clip-ViT-B-32 | 512 | HuggingFace wrapper; easier pipeline |

| Google's SigLIP | 1152 | Sigmoid loss variant; better recall at scale |

| OpenAI text-embedding-3-large | 3072 | Text only; not image-capable |

The practical implication for database architects: you are storing vectors from the *same* model family in the same table or collection. If you embed images with clip-vit-large-patch14, you must embed all query text with that same model's text encoder. Mixing encoders from different CLIP checkpoints produces meaningless distance comparisons — equivalent to storing lengths in meters in one column and feet in another and comparing them without conversion.

Dimensionality and Distance Metrics

CLIP vectors use cosine similarity as the natural distance metric because the encoders produce unit-normalized vectors by default. In SQL Server terms, that means the VECTOR type with VECTOR_DISTANCE('cosine', ...) rather than 'euclidean'. Pinecone, Weaviate, and Qdrant all support cosine similarity natively and it should be your default for CLIP-family embeddings.

One architectural decision that often surprises DBAs: you can store text embeddings and image embeddings in the *same* column when they share the same model and dimensionality. There is no type system distinction between "image vector" and "text vector" at the database level. The distinction is carried by your application logic and metadata columns. This is similar to storing both customer and product records in a single entities table — possible, but you need a type discriminator column to avoid joining apples with oranges in business queries.

Storage Architecture for Mixed-Modal Data

Before writing any queries, you need a schema that accommodates multiple modalities without creating a maintenance nightmare. There are three patterns worth knowing, each with different tradeoffs.

Pattern 1: Single Table, Shared Vector Column

All embeddings live in one table. A modality column distinguishes text from image. This works well when text and image documents are genuinely interchangeable from a business perspective — a product catalog where each item has both a description text and one or more product images.

-- SQL Server 2025
-- Single-table multi-modal schema for a product catalog
CREATE TABLE dbo.ProductEmbeddings (
    Id          BIGINT IDENTITY(1,1) NOT NULL
        CONSTRAINT PK_ProductEmbeddings PRIMARY KEY,
    ProductId   BIGINT NOT NULL
        CONSTRAINT FK_ProductEmbeddings_Products
        REFERENCES dbo.Products (Id),
    Modality    NVARCHAR(10) NOT NULL
        CONSTRAINT CK_ProductEmbeddings_Modality
        CHECK (Modality IN ('text', 'image')),
    SourceRef   NVARCHAR(500) NOT NULL,   -- field name or image URL/path
    Embedding   VECTOR(512) NOT NULL,     -- CLIP ViT-B/32 dimensions
    CreatedAt   DATETIME2(0) NOT NULL
        CONSTRAINT DF_ProductEmbeddings_Created DEFAULT SYSUTCDATETIME(),
    MetadataJson NVARCHAR(MAX) NULL
        CONSTRAINT CK_ProductEmbeddings_Json CHECK (ISJSON(MetadataJson) = 1)
);
-- One DiskANN index over the shared column; modality is a query-time filter
CREATE VECTOR INDEX IX_ProductEmbeddings_Embedding
    ON dbo.ProductEmbeddings (Embedding)
    WITH (METRIC = 'cosine', TYPE = 'DiskANN', MAXDOP = 8);
-- Composite index for filtered product lookups
CREATE INDEX IX_ProductEmbeddings_Product_Modality
    ON dbo.ProductEmbeddings (ProductId, Modality);

On the single-table pattern, keep one DiskANN index over the shared Embedding column and pass Modality = 'text' as a query-time predicate (SQL Server has no partial vector indexes). The modality filter narrows candidates before the similarity ranking is applied; the composite index on (ProductId, Modality) covers the filtered product lookups. If text and image pipelines diverge in update rate or dimensionality, prefer Pattern 2 instead of fighting one shared index.

Pattern 2: Separate Tables per Modality

More explicit and easier to maintain independently. Use this when text and image pipelines have very different update rates or when the embedding models differ in dimensionality.

-- SQL Server 2025
-- Separate tables for text and image embeddings
CREATE TABLE dbo.DocumentTextEmbeddings (
    Id         BIGINT IDENTITY(1,1) NOT NULL
        CONSTRAINT PK_DocumentTextEmbeddings PRIMARY KEY,
    DocId      BIGINT NOT NULL,
    ChunkIndex INT NOT NULL CONSTRAINT DF_DTE_ChunkIndex DEFAULT (0),
    Content    NVARCHAR(MAX) NOT NULL,
    Embedding  VECTOR(1536) NOT NULL,   -- OpenAI text-embedding-3-small
    MetadataJson NVARCHAR(MAX) NULL,
    CONSTRAINT UQ_DTE_Doc_Chunk UNIQUE (DocId, ChunkIndex)
);
CREATE TABLE dbo.DocumentImageEmbeddings (
    Id         BIGINT IDENTITY(1,1) NOT NULL
        CONSTRAINT PK_DocumentImageEmbeddings PRIMARY KEY,
    DocId      BIGINT NOT NULL,
    ImageIndex INT NOT NULL CONSTRAINT DF_DIE_ImageIndex DEFAULT (0),
    ImagePath  NVARCHAR(500) NOT NULL,
    Embedding  VECTOR(512) NOT NULL,    -- CLIP ViT-B/32
    MetadataJson NVARCHAR(MAX) NULL,
    CONSTRAINT UQ_DIE_Doc_Image UNIQUE (DocId, ImageIndex)
);
CREATE VECTOR INDEX IX_DTE_Embedding
    ON dbo.DocumentTextEmbeddings (Embedding)
    WITH (METRIC = 'cosine', TYPE = 'DiskANN', MAXDOP = 8);
CREATE VECTOR INDEX IX_DIE_Embedding
    ON dbo.DocumentImageEmbeddings (Embedding)
    WITH (METRIC = 'cosine', TYPE = 'DiskANN', MAXDOP = 8);

The tradeoff: two tables means two search queries per multi-modal lookup, and you need an application-layer fusion step. The benefit is that you can update the image embedding model without touching the text pipeline, and each table gets its own DiskANN index tuned (via MAXDOP and build scheduling) to its vector space's geometry and update rate.

Pattern 3: Weaviate Multi-Modal Collections

Weaviate has native multi-modal support via its multi2vec-clip vectorizer module, which handles both text and image fields in a single collection and produces a single fused vector. This shifts the fusion problem from your application layer to the database layer.

# Python
import weaviate
from weaviate.classes.config import Configure, Property, DataType
import base64
from pathlib import Path

client = weaviate.connect_to_local()  # or weaviate.connect_to_weaviate_cloud()

# Create a multi-modal collection
client.collections.create(
    name="ProductCatalog",
    vectorizer_config=Configure.Vectorizer.multi2vec_clip(
        image_fields=["product_image"],
        text_fields=["name", "description"],
        # Weight the contribution of each field to the combined vector
        weights={
            "product_image": [0.6],   # 60% image signal
            "name": [0.2],
            "description": [0.2],
        }
    ),
    properties=[
        Property(name="name", data_type=DataType.TEXT),
        Property(name="description", data_type=DataType.TEXT),
        Property(name="product_image", data_type=DataType.BLOB),  # base64 image
        Property(name="sku", data_type=DataType.TEXT),
        Property(name="price", data_type=DataType.NUMBER),
        Property(name="category", data_type=DataType.TEXT),
    ]
)

# Ingest a product with both text and image
def encode_image(image_path: str) -> str:
    with open(image_path, "rb") as f:
        return base64.b64encode(f.read()).decode("utf-8")

collection = client.collections.get("ProductCatalog")

collection.data.insert({
    "name": "Running Shoe X500",
    "description": "Lightweight mesh upper with cushioned midsole, ideal for road running",
    "product_image": encode_image("./images/shoe_x500.jpg"),
    "sku": "SHOE-X500-BLK-10",
    "price": 129.99,
    "category": "footwear"
})

client.close()

The Weaviate multi2vec-clip module uses field weights to combine sub-embeddings into one vector before indexing. This is architecturally different from the two-query-and-fuse pattern — you get a single HNSW index, lower query latency, and simpler application code. The cost is that you cannot independently update image weights without re-embedding the entire collection.

Ingestion Pipelines: Embedding at Scale

Getting data into a multi-modal store efficiently requires a pipeline that handles image preprocessing, batching, and error recovery. Raw images rarely arrive in a form suitable for CLIP: they need resizing, normalization, and format validation before the model sees them.

# Python
# Production-grade multi-modal ingestion pipeline
# Using sentence-transformers (CLIP wrapper), Qdrant, and async batching

import asyncio
import logging
from dataclasses import dataclass
from pathlib import Path
from typing import Optional
import numpy as np
from PIL import Image
from sentence_transformers import SentenceTransformer
from qdrant_client import QdrantClient, AsyncQdrantClient
from qdrant_client.models import (
    Distance, VectorParams, PointStruct,
    NamedVector, VectorsConfig
)

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)

# CLIP ViT-B/32 via sentence-transformers wrapper
# Note: This model produces BOTH text and image vectors in the same 512-d space
MODEL_NAME = "clip-ViT-B-32"
VECTOR_DIM = 512
BATCH_SIZE = 64
MAX_IMAGE_SIZE = (336, 336)  # CLIP ViT-B/32 optimal input resolution

@dataclass
class ProductRecord:
    product_id: str
    name: str
    description: str
    image_path: Optional[str]
    category: str
    price: float

def load_and_preprocess_image(image_path: str) -> Optional[Image.Image]:
    """Load image with validation and normalization."""
    try:
        img = Image.open(image_path).convert("RGB")
        # Preserve aspect ratio while bounding to MAX_IMAGE_SIZE
        img.thumbnail(MAX_IMAGE_SIZE, Image.LANCZOS)
        return img
    except Exception as e:
        logger.warning(f"Failed to load image {image_path}: {e}")
        return None

def embed_batch(
    model: SentenceTransformer,
    records: list[ProductRecord]
) -> tuple[list[np.ndarray], list[np.ndarray]]:
    """
    Embed a batch of records.
    Returns (text_embeddings, image_embeddings).
    image_embeddings[i] is None if the image failed to load.
    """
    # Text: concatenate name + description for richer signal
    texts = [f"{r.name}. {r.description}" for r in records]
    text_embeddings = model.encode(
        texts,
        batch_size=BATCH_SIZE,
        normalize_embeddings=True,
        show_progress_bar=False
    )

    images = []
    image_mask = []  # Track which records have valid images
    for r in records:
        if r.image_path:
            img = load_and_preprocess_image(r.image_path)
            if img:
                images.append(img)
                image_mask.append(True)
            else:
                image_mask.append(False)
        else:
            image_mask.append(False)

    image_embeddings_raw = []
    if images:
        image_embeddings_raw = model.encode(
            images,
            batch_size=BATCH_SIZE,
            normalize_embeddings=True,
            show_progress_bar=False
        )

    # Reconstruct image_embeddings list aligned with records
    img_iter = iter(image_embeddings_raw)
    image_embeddings = []
    for has_image in image_mask:
        if has_image:
            image_embeddings.append(next(img_iter))
        else:
            image_embeddings.append(None)

    return text_embeddings, image_embeddings

def build_qdrant_points(
    records: list[ProductRecord],
    text_embeddings: list[np.ndarray],
    image_embeddings: list[Optional[np.ndarray]]
) -> list[PointStruct]:
    """
    Build Qdrant points using named vectors.
    Qdrant supports multiple named vector spaces per collection.
    """
    points = []
    for i, record in enumerate(records):
        vectors = {
            "text": text_embeddings[i].tolist()
        }
        if image_embeddings[i] is not None:
            vectors["image"] = image_embeddings[i].tolist()

        points.append(PointStruct(
            id=abs(hash(record.product_id)) % (2**63),  # Qdrant needs uint64
            vector=vectors,
            payload={
                "product_id": record.product_id,
                "name": record.name,
                "description": record.description,
                "category": record.category,
                "price": record.price,
                "has_image": image_embeddings[i] is not None
            }
        ))
    return points

async def setup_collection(client: AsyncQdrantClient, collection_name: str):
    """Create collection with named vector spaces for text and image."""
    collections = await client.get_collections()
    existing = [c.name for c in collections.collections]

    if collection_name not in existing:
        await client.create_collection(
            collection_name=collection_name,
            vectors_config={
                "text": VectorParams(size=VECTOR_DIM, distance=Distance.COSINE),
                "image": VectorParams(size=VECTOR_DIM, distance=Distance.COSINE),
            }
        )
        logger.info(f"Created collection: {collection_name}")
    else:
        logger.info(f"Collection {collection_name} already exists, skipping creation")

async def ingest_products(
    records: list[ProductRecord],
    collection_name: str = "products_multimodal",
    qdrant_url: str = "http://localhost:6333"
):
    model = SentenceTransformer(MODEL_NAME)
    client = AsyncQdrantClient(url=qdrant_url)

    await setup_collection(client, collection_name)

    total_ingested = 0
    for batch_start in range(0, len(records), BATCH_SIZE):
        batch = records[batch_start:batch_start + BATCH_SIZE]

        text_embs, image_embs = embed_batch(model, batch)
        points = build_qdrant_points(batch, text_embs, image_embs)

        await client.upsert(
            collection_name=collection_name,
            points=points,
            wait=True
        )
        total_ingested += len(points)
        logger.info(
            f"Ingested batch {batch_start}–{batch_start + len(batch)}, "
            f"total: {total_ingested}"
        )

    await client.close()
    logger.info(f"Ingestion complete. Total records: {total_ingested}")

A few production details worth noting in this pipeline:

Qdrant named vectors allow multiple vector spaces per document in a single collection. This is superior to storing separate collections per modality because a single upsert keeps both vectors atomic — you cannot have a text vector without its corresponding image vector falling out of sync.

Image failure handling: Real product images fail to load regularly — corrupted files, unsupported formats, network-mounted paths that go stale. The pipeline tracks has_image in the payload so queries can filter to image-capable records when needed.

Normalization at embed time: CLIP vectors should be L2-normalized before storage. normalize_embeddings=True in sentence-transformers handles this. Pre-normalizing means the database computes cosine similarity as a dot product — numerically cheaper and avoids re-normalization overhead on the query path.

Query Patterns: Fusing Text and Image Signals

With data ingested, the interesting engineering happens at query time. Multi-modal search exposes four distinct query patterns, each appropriate to different use cases.

Pattern 1: Text Query Against Image Index

The simplest multi-modal query: a user types text, you retrieve images whose CLIP image embeddings are closest to the CLIP text embedding of the query. The entire "magic" is that the CLIP encoder maps both to the same space.

# Python
# Multi-modal query patterns using Qdrant named vectors

from qdrant_client import QdrantClient
from qdrant_client.models import (
    SearchRequest, NamedVector, Filter,
    FieldCondition, MatchValue, MatchAny
)
from sentence_transformers import SentenceTransformer
from PIL import Image
import base64
import io
from typing import Optional

model = SentenceTransformer("clip-ViT-B-32")
client = QdrantClient(url="http://localhost:6333")
COLLECTION = "products_multimodal"

def text_to_image_search(
    query_text: str,
    category_filter: Optional[str] = None,
    top_k: int = 20
) -> list[dict]:
    """
    Query: text string → retrieve closest images.
    Classic cross-modal retrieval.
    """
    query_vector = model.encode(
        query_text,
        normalize_embeddings=True
    ).tolist()

    search_filter = None
    if category_filter:
        search_filter = Filter(
            must=[
                FieldCondition(key="category", match=MatchValue(value=category_filter)),
                FieldCondition(key="has_image", match=MatchValue(value=True))
            ]
        )

    results = client.search(
        collection_name=COLLECTION,
        query_vector=NamedVector(name="image", vector=query_vector),  # text → image space
        query_filter=search_filter,
        limit=top_k,
        with_payload=True,
        score_threshold=0.25  # CLIP cosine scores below 0.25 are typically noise
    )

    return [
        {
            "product_id": r.payload["product_id"],
            "name": r.payload["name"],
            "score": r.score,
            "has_image": r.payload.get("has_image", False)
        }
        for r in results
    ]

def image_to_image_search(
    query_image_path: str,
    top_k: int = 20,
    exclude_product_id: Optional[str] = None
) -> list[dict]:
    """
    Query: image → retrieve visually similar items.
    'Shop the look' / visual similarity pattern.
    """
    img = Image.open(query_image_path).convert("RGB")
    query_vector = model.encode(img, normalize_embeddings=True).tolist()

    search_filter = None
    if exclude_product_id:
        # Exclude the query item itself from results
        search_filter = Filter(
            must_not=[
                FieldCondition(key="product_id", match=MatchValue(value=exclude_product_id))
            ]
        )

    results = client.search(
        collection_name=COLLECTION,
        query_vector=NamedVector(name="image", vector=query_vector),
        query_filter=search_filter,
        limit=top_k,
        with_payload=True
    )
    return [{"product_id": r.payload["product_id"], "name": r.payload["name"], "score": r.score}
            for r in results]

def combined_text_image_search(
    query_text: str,
    query_image_path: str,
    text_weight: float = 0.4,
    image_weight: float = 0.6,
    top_k: int = 20
) -> list[dict]:
    """
    Fused query: BOTH a text query AND a reference image.
    Use case: 'Find shoes like [image] but with [text description]'.

    Fusion strategy: weighted average of text and image query vectors.
    This works because both live in the same CLIP space.
    """
    import numpy as np

    text_vector = model.encode(query_text, normalize_embeddings=True)

    img = Image.open(query_image_path).convert("RGB")
    image_vector = model.encode(img, normalize_embeddings=True)

    # Weighted combination — still in the shared CLIP space
    fused_vector = text_weight * text_vector + image_weight * image_vector

    # Re-normalize after combination
    fused_norm = np.linalg.norm(fused_vector)
    if fused_norm > 0:
        fused_vector = fused_vector / fused_norm

    # Query the image index with the fused vector
    # (could also query the text index — depends on what you indexed)
    results = client.search(
        collection_name=COLLECTION,
        query_vector=NamedVector(name="image", vector=fused_vector.tolist()),
        limit=top_k,
        with_payload=True,
        score_threshold=0.20
    )

    return [
        {
            "product_id": r.payload["product_id"],
            "name": r.payload["name"],
            "score": r.score,
            "query_mode": "fused_text_image"
        }
        for r in results
    ]

def late_fusion_search(
    query_text: str,
    query_image_path: str,
    text_weight: float = 0.5,
    image_weight: float = 0.5,
    candidate_pool: int = 100,
    top_k: int = 20
) -> list[dict]:
    """
    Late fusion: run two separate searches, then combine scores.
    More expensive but allows independent index tuning per modality.
    Use when text and image are in DIFFERENT embedding spaces.
    """
    import numpy as np

    # Search 1: text vector → text index
    text_vector = model.encode(query_text,normalize_embeddings=True).tolist()

    text_results = client.search(
        collection_name=COLLECTION,
        query_vector=NamedVector(name="text", vector=text_vector),
        limit=candidate_pool,
        with_payload=True,
        score_threshold=0.15
    )

    # Search 2: image vector → image index
    img = Image.open(query_image_path).convert("RGB")
    image_vector = model.encode(img, normalize_embeddings=True).tolist()

    image_results = client.search(
        collection_name=COLLECTION,
        query_vector=NamedVector(name="image", vector=image_vector),
        limit=candidate_pool,
        with_payload=True,
        score_threshold=0.15
    )

    # Merge scores by product_id
    score_map: dict[str, dict] = {}
    for r in text_results:
        pid = r.payload["product_id"]
        score_map[pid] = {
            "product_id": pid,
            "name": r.payload["name"],
            "text_score": r.score,
            "image_score": 0.0,
            "payload": r.payload
        }

    for r in image_results:
        pid = r.payload["product_id"]
        if pid in score_map:
            score_map[pid]["image_score"] = r.score
        else:
            score_map[pid] = {
                "product_id": pid,
                "name": r.payload["name"],
                "text_score": 0.0,
                "image_score": r.score,
                "payload": r.payload
            }

    # Weighted combined score
    fused = []
    for pid, data in score_map.items():
        combined = text_weight * data["text_score"] + image_weight * data["image_score"]
        fused.append({
            "product_id": pid,
            "name": data["name"],
            "combined_score": combined,
            "text_score": data["text_score"],
            "image_score": data["image_score"]
        })

    fused.sort(key=lambda x: x["combined_score"], reverse=True)
    return fused[@top_k]

The late fusion pattern deserves a closer look, because it is the right choice whenever text and image embeddings come from *different* models with *different* dimensionalities. When you have a 1536-dimension OpenAI text embedding alongside a 512-dimension CLIP image embedding, you cannot average them — the vector spaces are unrelated. Late fusion avoids that requirement: each modality gets its own search against its own index, and scores are combined numerically after the fact. The cost is two round-trips to the database and a merge step in application memory.

Early fusion (the weighted average in combined_text_image_search) only works when both modalities are encoded by the same model family into the same shared space. CLIP's design makes this possible; most other combinations do not.

Multi-Modal Search in SQL Server: The T-SQL Perspective

For teams operating on SQL Server 2025, the fusion logic moves into T-SQL rather than application code. This has advantages for teams that want to keep retrieval logic auditable and version-controlled as migrations.

-- SQL Server 2025: late fusion multi-modal search using two CTEs
-- Assumes:
--   dbo.ProductTextEmbeddings (ProductId, Embedding VECTOR(1536))
--   dbo.ProductImageEmbeddings (ProductId, Embedding VECTOR(512))
-- Each has its own DiskANN index.
-- Parameters (DECLAREd or passed by the application):
--   @text_query_vector  VECTOR(1536) — OpenAI embedding of the query string
--   @image_query_vector VECTOR(512)  — CLIP embedding of the reference image
--   @text_weight, @image_weight      — e.g. 0.5 / 0.5
--   @candidate_k, @top_k             — e.g. 100 / 20
WITH text_candidates AS (
    SELECT TOP (@candidate_k)
        product_id,
        1.0 - VECTOR_DISTANCE('cosine', embedding, CAST(@text_query_vector AS VECTOR(1536)))
            AS text_score
    FROM product_text_embeddings
    ORDER BY VECTOR_DISTANCE('cosine', embedding, CAST(@text_query_vector AS VECTOR(1536)))
),
image_candidates AS (
    SELECT TOP (@candidate_k)
        product_id,
        1.0 - VECTOR_DISTANCE('cosine', embedding, CAST(@image_query_vector AS VECTOR(512)))
            AS image_score
    FROM product_image_embeddings
    ORDER BY VECTOR_DISTANCE('cosine', embedding, CAST(@image_query_vector AS VECTOR(512)))
),
fused AS (
    SELECT
        COALESCE(t.product_id, i.product_id) AS product_id,
        COALESCE(t.text_score, 0.0) * @text_weight
            + COALESCE(i.image_score, 0.0) * @image_weight  AS combined_score,
        COALESCE(t.text_score, 0.0)  AS text_score,
        COALESCE(i.image_score, 0.0) AS image_score
    FROM text_candidates t
    FULL OUTER JOIN image_candidates i ON t.product_id = i.product_id
)
SELECT TOP (@top_k)
    f.product_id,
    p.name,
    p.category,
    p.price,
    f.combined_score,
    f.text_score,
    f.image_score
FROM fused f
JOIN products p ON p.id = f.product_id
ORDER BY f.combined_score DESC;

A subtlety in both queries: the FULL OUTER JOIN between text_candidates and image_candidates is deliberate. Products that appear in only one result set still participate in the final ranking, with a zero score contribution from the missing modality. This prevents the fusion from arbitrarily excluding products that have strong text relevance but weak image relevance or vice versa. Whether that behavior is correct depends on your use case — if you require *both* modalities to have non-trivial signal, replace the FULL OUTER JOIN with an INNER JOIN.

Score Normalization Before Fusion

A common mistake in late fusion implementations is combining raw cosine similarity scores across modalities without considering their distributions. Different models produce scores with different statistical properties: a cosine similarity of 0.7 in a text embedding space does not mean the same "closeness" as 0.7 in a CLIP image space. CLIP image-to-image similarities tend to cluster in a narrower range than text-to-text similarities because image features are more visually concrete.

The solution is score normalization within each modality's result set before combining. The two standard approaches:

Min-Max normalization: Scale each modality's scores to [0, 1] relative to the candidate pool.

# Python
def normalize_scores_minmax(scores: list[float]) -> list[float]:
    if not scores:
        return scores
    min_s, max_s = min(scores), max(scores)
    if max_s == min_s:
        return [1.0] * len(scores)
    return [(s - min_s) / (max_s - min_s) for s in scores]

def late_fusion_with_normalization(
    text_results: list,  # [(product_id, name, score), ...]
    image_results: list,
    text_weight: float = 0.5,
    image_weight: float = 0.5,
    top_k: int = 20
) -> list[dict]:
    import numpy as np

    text_scores_raw  = [r.score for r in text_results]
    image_scores_raw = [r.score for r in image_results]

    text_scores_norm  = normalize_scores_minmax(text_scores_raw)
    image_scores_norm = normalize_scores_minmax(image_scores_raw)

    score_map: dict[str, dict] = {}
    for r, norm_score in zip(text_results, text_scores_norm):
        pid = r.payload["product_id"]
        score_map[pid] = {"name": r.payload["name"], "text_score": norm_score, "image_score": 0.0}

    for r, norm_score in zip(image_results, image_scores_norm):
        pid = r.payload["product_id"]
        if pid in score_map:
            score_map[pid]["image_score"] = norm_score
        else:
            score_map[pid] = {"name": r.payload["name"], "text_score": 0.0, "image_score": norm_score}

    fused = [
        {
            "product_id": pid,
            "name": data["name"],
            "combined_score": text_weight * data["text_score"] + image_weight * data["image_score"],
            "text_score": data["text_score"],
            "image_score": data["image_score"]
        }
        for pid, data in score_map.items()
    ]
    fused.sort(key=lambda x: x["combined_score"], reverse=True)
    return fused[@top_k]

Reciprocal Rank Fusion (RRF): An alternative that is rank-based rather than score-based, and therefore inherently distribution-agnostic.

# Python
def reciprocal_rank_fusion(
    text_results: list,
    image_results: list,
    k: int = 60,  # RRF smoothing constant; 60 is the standard default
    top_n: int = 20
) -> list[dict]:
    """
    Combine two ranked lists using RRF.
    RRF score = sum over each list of: 1 / (rank_in_list + k)
    """
    rrf_scores: dict[str, float] = {}
    payload_store: dict[str, dict] = {}

    for rank, r in enumerate(text_results, start=1):
        pid = r.payload["product_id"]
        rrf_scores[pid] = rrf_scores.get(pid, 0.0) + 1.0 / (rank + k)
        payload_store[pid] = r.payload

    for rank, r in enumerate(image_results, start=1):
        pid = r.payload["product_id"]
        rrf_scores[pid] = rrf_scores.get(pid, 0.0) + 1.0 / (rank + k)
        if pid not in payload_store:
            payload_store[pid] = r.payload

    ranked = sorted(rrf_scores.items(), key=lambda x: x[1], reverse=True)[:top_n]

    return [
        {
            "product_id": pid,
            "name": payload_store[pid]["name"],
            "rrf_score": score
        }
        for pid, score in ranked
    ]

RRF has a practical advantage in production: it is robust to outlier scores and does not require you to tune normalization ranges as your corpus grows. The tradeoff is that you lose the interpretable per-modality score breakdown — you cannot easily tell whether a result ranked highly because of text signal, image signal, or both.

Handling Queries Without an Image

In real deployments, most users will provide text queries most of the time. The multi-modal system must degrade gracefully when only one modality is present, rather than treating a missing image as an error.

# Python
from enum import Enum
from dataclasses import dataclass
from typing import Optional

class QueryModality(Enum):
    TEXT_ONLY   = "text_only"
    IMAGE_ONLY  = "image_only"
    BOTH        = "both"

@dataclass
class MultiModalQuery:
    text: Optional[str]
    image_path: Optional[str]
    category_filter: Optional[str] = None
    text_weight: float = 0.5
    image_weight: float = 0.5
    top_k: int = 20

    @property
    def modality(self) -> QueryModality:
        if self.text and self.image_path:
            return QueryModality.BOTH
        elif self.text:
            return QueryModality.TEXT_ONLY
        elif self.image_path:
            return QueryModality.IMAGE_ONLY
        raise ValueError("Query must have at least one of text or image_path")

def route_multimodal_query(
    query: MultiModalQuery,
    model: SentenceTransformer,
    client: QdrantClient
) -> list[dict]:
    """
    Route query to the appropriate search strategy based on what inputs are available.
    """
    modality = query.modality

    if modality == QueryModality.TEXT_ONLY:
        # Standard vector search on text index; optionally also hit image index
        # for cross-modal retrieval (user typed, wants images back)
        return text_to_image_search(
            query_text=query.text,
            category_filter=query.category_filter,
            top_k=query.top_k
        )

    elif modality == QueryModality.IMAGE_ONLY:
        return image_to_image_search(
            query_image_path=query.image_path,
            top_k=query.top_k
        )

    else:  # BOTH
        # Decide between early fusion and late fusion based on modality compatibility
        # (For CLIP, early fusion is fine; generalize with late fusion if needed)
        text_results = client.search(
            collection_name=COLLECTION,
            query_vector=NamedVector(
                name="text",
                vector=model.encode(query.text, normalize_embeddings=True).tolist()
            ),
            limit=query.top_k * 3,
            with_payload=True
        )
        from PIL import Image as PILImage
        img = PILImage.open(query.image_path).convert("RGB")
        image_results = client.search(
            collection_name=COLLECTION,
            query_vector=NamedVector(
                name="image",
                vector=model.encode(img, normalize_embeddings=True).tolist()
            ),
            limit=query.top_k * 3,
            with_payload=True
        )

        return reciprocal_rank_fusion(
            text_results=text_results,
            image_results=image_results,
            top_n=query.top_k
        )

The routing logic here is deliberately simple — three branches, no machine learning. In a production system you might introduce a fourth branch: a zero-shot re-ranker that scores the top-K candidates from the fused list against the original text query using a cross-encoder model. That adds latency (typically 50–150 ms for a list of 100 candidates on CPU) but improves precision significantly, especially for ambiguous queries where the bi-encoder CLIP search is unreliable.

Pinecone: Multi-Modal with Namespaces and Metadata Filtering

Pinecone's architecture does not have native named vector support in the same way Qdrant does. The production pattern for multi-modal search in Pinecone uses namespaces to separate modalities within a single index, combined with metadata filtering.

# Python
# Multi-modal pattern in Pinecone using namespaces
# Pinecone indexes are fixed-dimension; CLIP ViT-B/32 = 512

from pinecone import Pinecone, ServerlessSpec
from sentence_transformers import SentenceTransformer
from PIL import Image
import numpy as np
from typing import Optional

pc = Pinecone(api_key="YOUR_PINECONE_API_KEY")
model = SentenceTransformer("clip-ViT-B-32")

INDEX_NAME   = "products-multimodal"
TEXT_NS      = "text"   # namespace for text embeddings
IMAGE_NS     = "image"  # namespace for image embeddings
VECTOR_DIM   = 512

def create_pinecone_index():
    if INDEX_NAME not in [i.name for i in pc.list_indexes()]:
        pc.create_index(
            name=INDEX_NAME,
            dimension=VECTOR_DIM,
            metric="cosine",
            spec=ServerlessSpec(cloud="aws", region="us-east-1")
        )

def upsert_product(
    product_id: str,
    name: str,
    description: str,
    category: str,
    price: float,
    image_path: Optional[str] = None
):
    index = pc.Index(INDEX_NAME)

    # Upsert text embedding
    text_vector = model.encode(
        f"{name}. {description}", normalize_embeddings=True
    ).tolist()

    index.upsert(
        vectors=[{
            "id": f"{product_id}",
            "values": text_vector,
            "metadata": {
                "product_id": product_id,
                "name": name,
                "category": category,
                "price": price,
                "modality": "text"
            }
        }],
        namespace=TEXT_NS
    )

    # Upsert image embedding if image is available
    if image_path:
        img = Image.open(image_path).convert("RGB")
        image_vector = model.encode(img, normalize_embeddings=True).tolist()

        index.upsert(
            vectors=[{
                "id": f"{product_id}",
                "values": image_vector,
                "metadata": {
                    "product_id": product_id,
                    "name": name,
                    "category": category,
                    "price": price,
                    "modality": "image"
                }
            }],
            namespace=IMAGE_NS
        )

def multimodal_query_pinecone(
    query_text: Optional[str],
    query_image_path: Optional[str],
    category_filter: Optional[str] = None,
    top_k: int = 20,
    text_weight: float = 0.5,
    image_weight: float = 0.5
) -> list[dict]:
    index = pc.Index(INDEX_NAME)

    metadata_filter = {}
    if category_filter:
        metadata_filter = {"category": {"$eq": category_filter}}

    results_text   = []
    results_image  = []

    if query_text:
        text_vector = model.encode(query_text, normalize_embeddings=True).tolist()
        resp = index.query(
            namespace=IMAGE_NS,           # text query → image namespace (cross-modal)
            vector=text_vector,
            top_k=top_k * 3,
            filter=metadata_filter if metadata_filter else None,
            include_metadata=True
        )
        results_text = resp.matches

    if query_image_path:
        img = Image.open(query_image_path).convert("RGB")
        image_vector = model.encode(img, normalize_embeddings=True).tolist()
        resp = index.query(
            namespace=IMAGE_NS,
            vector=image_vector,
            top_k=top_k * 3,
            filter=metadata_filter if metadata_filter else None,
            include_metadata=True
        )
        results_image = resp.matches

    if results_text and results_image:
        return reciprocal_rank_fusion_pinecone(results_text, results_image, top_n=top_k)
    elif results_text:
        return [{"product_id": m.metadata["product_id"], "name": m.metadata["name"], "score": m.score}
                for m in results_text[@top_k]]
    elif results_image:
        return [{"product_id": m.metadata["product_id"], "name": m.metadata["name"], "score": m.score}
                for m in results_image[@top_k]]
    return []

def reciprocal_rank_fusion_pinecone(
    text_matches,
    image_matches,
    k: int = 60,
    top_n: int = 20
) -> list[dict]:
    rrf: dict[str, float] = {}
    meta: dict[str, dict]  = {}

    for rank, m in enumerate(text_matches, start=1):
        pid = m.metadata["product_id"]
        rrf[pid] = rrf.get(pid, 0.0) + 1.0 / (rank + k)
        meta[pid] = m.metadata

    for rank, m in enumerate(image_matches, start=1):
        pid = m.metadata["product_id"]
        rrf[pid] = rrf.get(pid, 0.0) + 1.0 / (rank + k)
        if pid not in meta:
            meta[pid] = m.metadata

    ranked = sorted(rrf.items(), key=lambda x: x[1], reverse=True)[:top_n]
    return [{"product_id": pid, "name": meta[pid]["name"], "rrf_score": score}
            for pid, score in ranked]

One limitation of the Pinecone namespace approach: namespaces share the same dimension. Since CLIP text and image encoders produce the same dimension by design, this is not a constraint for CLIP-based systems. If your architecture mixes CLIP images (512-d) with a different text embedding model (1536-d), you would need two separate Pinecone indexes rather than two namespaces.

Production Considerations: Latency, Cost, and Quality Tradeoffs

Multi-modal search introduces compound latency: you are now encoding queries with a vision model in addition to a text model, and potentially issuing two database queries instead of one. Understanding where time is spent guides optimization.

Embedding latency is typically the largest contributor. CLIP ViT-B/32 runs at roughly 5–15 ms per image on a modern CPU with batch size 1, and under 2 ms per text query. On GPU, image embedding drops below 2 ms. If your deployment is CPU-only, consider:

  • → Caching embeddings for repeated reference images (user uploads the same product photo repeatedly)
  • → Quantizing the CLIP model with INT8 to reduce inference time at marginal quality cost
  • → Using a lighter CLIP variant (ViT-S/32) for latency-critical paths and a heavier model for offline indexing

    • Index scan latency scales with collection size and HNSW parameters. A practical rule: keep ef (the HNSW search parameter at query time) at 2–4× your top_k. For top_k=20, ef=64 is a reasonable starting point. Increasing ef improves recall at the cost of latency — profile this against your SLA.

    Quality measurement for multi-modal search requires a labeled evaluation set with both modalities. The standard metric is Recall@K: for a set of known-relevant items, what fraction appear in the top-K results? Building this dataset means collecting (query text, reference image, known-relevant product IDs) triples — time-consuming but necessary before tuning fusion weights.

    Cost management in cloud-hosted vector databases (Pinecone, Weaviate Cloud) is driven by stored vector count and query volume. Multi-modal doubles your vector count per document when storing separate text and image embeddings. If cost is a constraint, consider:

  • → Storing only image embeddings and using the CLIP text encoder at query time for cross-modal retrieval (text query → image index). This halves storage at the cost of losing text-to-text retrieval as a fallback.
  • → Tiering: use a smaller vector dimension (256-d via PCA projection of CLIP) for the first-pass ANN search, then re-score top candidates with the full 512-d embedding.

    A Complete End-to-End Example: Fashion Visual Search

    To bring the patterns together, consider a fashion retail application that supports three query types: "type a description," "upload a photo," and "type a description while holding a photo." The following shows the complete server-side handler.

    # Python
# Fashion visual search: end-to-end query handler
# FastAPI endpoint integrating all multi-modal patterns

from fastapi import FastAPI, File, Form, UploadFile, HTTPException
from fastapi.responses import JSONResponse
import tempfile, os, shutil
from typing import Optional
from sentence_transformers import SentenceTransformer
from qdrant_client import QdrantClient
from qdrant_client.models import NamedVector, Filter, FieldCondition, MatchValue

app = FastAPI(title="Fashion Visual Search API")

# Initialize at startup — avoid re-loading per request
_model: Optional[SentenceTransformer] = None
_qdrant: Optional[QdrantClient] = None

@app.on_event("startup")
async def startup():
    global _model, _qdrant
    _model  = SentenceTransformer("clip-ViT-B-32")
    _qdrant = QdrantClient(url=os.getenv("QDRANT_URL", "http://localhost:6333"))

@app.post("/search")
async def search(
    query_text: Optional[str]       = Form(None),
    category:   Optional[str]       = Form(None),
    top_k:      int                 = Form(20),
    text_weight: float              = Form(0.4),
    image_weight: float             = Form(0.6),
    image:      Optional[UploadFile] = File(None)
):
    if not query_text and not image:
        raise HTTPException(status_code=400, detail="Provide at least query_text or an image.")

    # Persist uploaded image to temp file for PIL
    tmp_image_path = None
    if image:
        suffix = os.path.splitext(image.filename)[-1] or ".jpg"
        with tempfile.NamedTemporaryFile(delete=False, suffix=suffix) as tmp:
            shutil.copyfileobj(image.file, tmp)
            tmp_image_path = tmp.name

    try:
        q = MultiModalQuery(
            text=query_text,
            image_path=tmp_image_path,
            category_filter=category,
            text_weight=text_weight,
            image_weight=image_weight,
            top_k=top_k
        )
        results = route_multimodal_query(q, _model, _qdrant)
        return JSONResponse(content={"results": results, "modality": q.modality.value})

    finally:
        if tmp_image_path and os.path.exists(tmp_image_path):
            os.unlink(tmp_image_path)  # always clean up temp files

@app.get("/health")
async def health():
    return {"status": "ok", "model": "clip-ViT-B-32"}

    The FastAPI handler deliberately isolates temp-file cleanup in a finally block — a failure during embedding or Qdrant search must not leave orphaned image files filling the server's /tmp directory. In a container environment, /tmp is often an in-memory tmpfs with limited capacity.

    Key Takeaways

  • → **Shared embedding spaces** are the foundation of multi-modal search. CLIP-family models encode text and images into the same vector space, enabling cross-modal queries where a text string can retrieve images and vice versa without any additional translation layer.
  • → **Storage architecture choices** — single table with modality column, separate tables per modality, or database-native multi-modal collections (Weaviate) — each carry different tradeoffs for indexing flexibility, update independence, and operational complexity. Choose based on whether text and image pipelines change at the same rate.
  • → **Early fusion** (averaging query vectors) works only when text and image embeddings share the same model and dimensionality. **Late fusion** (two searches, score combination) is the safe default when embedding models differ, and RRF is the most robust score combination method because it is rank-based and distribution-agnostic.
  • → **Score normalization before combining modality scores** is not optional in production. Raw cosine similarities from different models have different statistical distributions; combining them without normalization biases fusion toward whichever modality happens to produce larger raw values.
  • → **Graceful degradation** — routing single-modality queries through the appropriate index without treating a missing image or text as an error — is required for any system that faces real user traffic. Wrap modality detection in an explicit routing layer so that adding new query types later does not require restructuring the retrieval core.
