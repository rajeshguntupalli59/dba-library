Chapter 36: Backing Up Embedding Data

The Three-Artifact Problem

Embedding data presents a deceptively familiar backup challenge. The vectors themselves are just floating-point arrays — and any experienced DBA knows how to back up a table of floats. What makes embedding backups genuinely different is the relationship between three distinct artifacts that must remain in sync: the raw source data, the embeddings derived from that data, and the model that produced those embeddings. Back up only two of the three and you have a restoration problem that won't reveal itself until you're already in a production incident. This chapter covers the full backup and recovery strategy for vector workloads on SQL Server — from native snapshots to managed exports, from model versioning to the operational patterns that keep RAG pipelines recoverable at scale.

Consider a document chunk stored in SQL Server:

-- SQL Server 2025: the three artifacts live in one database
-- Artifact 1: source data
CREATE TABLE dbo.SourceDocuments (
    DocId        INT IDENTITY(1,1) NOT NULL
        CONSTRAINT PK_SourceDocuments PRIMARY KEY,
    Title        NVARCHAR(400) NOT NULL,
    Body         NVARCHAR(MAX) NOT NULL,
    LastModified DATETIME2(0) NOT NULL
);
-- Artifact 2: embeddings derived from it (note the provenance columns)
CREATE TABLE dbo.DocumentChunks (
    ChunkId    BIGINT IDENTITY(1,1) NOT NULL
        CONSTRAINT PK_DocumentChunks PRIMARY KEY,
    DocId      INT NOT NULL
        CONSTRAINT FK_Chunks_Docs REFERENCES dbo.SourceDocuments (DocId),
    ChunkText  NVARCHAR(MAX) NOT NULL,
    Embedding  VECTOR(1536) NOT NULL,
    ModelId    NVARCHAR(100) NOT NULL,  -- Artifact 3: which model made this
    ModelDims  SMALLINT NOT NULL,
    EmbeddedAt DATETIME2(0) NOT NULL
        CONSTRAINT DF_Chunks_Embedded DEFAULT SYSUTCDATETIME()
);
-- Artifact 3: the model registry (what each ModelId means)
CREATE TABLE dbo.EmbeddingModels (
    ModelId      NVARCHAR(100) NOT NULL
        CONSTRAINT PK_EmbeddingModels PRIMARY KEY,
    Provider     NVARCHAR(60) NOT NULL,
    ModelName    NVARCHAR(120) NOT NULL,
    Dimensions   SMALLINT NOT NULL,
    RetiredAt    DATETIME2(0) NULL
);
-- A backup that captures DocumentChunks but not SourceDocuments or
-- EmbeddingModels restores vectors you cannot regenerate or interpret.
-- Back up all three, or back up none.
  • → Source data — the documents. Without these, embeddings cannot be regenerated.
  • → Embeddings — the vector arrays plus model provenance (ModelId, ModelDims). Without provenance, restored vectors are uninterpretable numbers.
  • → Model registry — which model version produced each vector. Without it, re-embedding silently mixes geometries (Chapter 30).

    Backup Strategies for SQL Server Vector Tables

    SQL Server treats a table with a VECTOR column like any other table for backup purposes. The difference is scale: 10 million document chunks at 1536 dimensions (4 bytes per dimension in the native vector type) hold roughly 58 GB of vector data before indexes. The DiskANN index adds further storage for the navigational graph. Plan backup windows and storage accordingly — and test restore throughput, not just backup throughput.

    -- SQL Server: tiered backup schedule for the vector database
-- Weekly FULL (Sunday 02:00)
BACKUP DATABASE VectorRagDb
TO URL = 'https://vecbackups.blob.core.windows.net/sqlbackups/full.bak'
WITH COMPRESSION, CHECKSUM, STATS = 10;
-- Daily DIFFERENTIAL (02:00) — vector tables change mostly by INSERT,
-- so differentials stay small relative to the base
BACKUP DATABASE VectorRagDb
TO URL = 'https://vecbackups.blob.core.windows.net/sqlbackups/diff.bak'
WITH DIFFERENTIAL, COMPRESSION, CHECKSUM;
-- LOG every 15 minutes — keeps RPO tight for the source + chunk tables
BACKUP LOG VectorRagDb
TO URL = 'https://vecbackups.blob.core.windows.net/sqlbackups/log.trn'
WITH COMPRESSION, CHECKSUM;
-- Native backups capture the DiskANN index *definition*; the index
-- contents rebuild from vector data during recovery. Budget the rebuild
-- into RTO (Chapter 35) — it is not part of the restore timer.

    For very large vector tables, add a bulk-export tier: periodically export DocId, ChunkId, Embedding to Parquet in object storage via bcp or Azure Data Factory. The export is platform-independent — it rebuilds the vector tables on any SQL Server instance without replaying the backup chain, and it doubles as the seed for a second vector platform if you ever migrate.

    -- SQL Server Agent job: weekly vector export to Parquet-adjacent CSV
-- (bcp native format preserves the VECTOR column; CSV via a view that
--  renders the vector as text for portability)
CREATE VIEW dbo.vw_ChunkExport AS
SELECT ChunkId, DocId, ModelId, ModelDims,
       CAST(Embedding AS NVARCHAR(MAX)) AS EmbeddingText, EmbeddedAt
FROM dbo.DocumentChunks;
GO

    Exporting from Managed Vector Databases

    If part of your estate lives in Pinecone, Weaviate, or Qdrant Cloud, their export story is an API, not a backup file. Schedule weekly full exports of (id, vector, metadata) to object storage you control — the export is your only defense against a managed-service incident, a billing dispute that locks the account, or a migration you didn't plan.

    The operational rule: keep authoritative source data in SQL Server or object storage you control, so a managed export failure degrades into a re-embedding event rather than data loss. The managed store is a cache with an SLA; the source of truth is yours.

    -- SQL Server: track managed-service exports alongside native backups
CREATE TABLE dbo.BackupAudit (
    BackupId     BIGINT IDENTITY(1,1) NOT NULL
        CONSTRAINT PK_BackupAudit PRIMARY KEY,
    BackupType   NVARCHAR(20) NOT NULL,   -- 'full','diff','log','export'
    TargetSystem NVARCHAR(50) NOT NULL,   -- 'sqlserver','pinecone','weaviate'
    StartedAt    DATETIME2(0) NOT NULL,
    FinishedAt   DATETIME2(0) NULL,
    RowCount     BIGINT NULL,
    Location     NVARCHAR(500) NOT NULL,  -- URL or path
    ChecksumOk   BIT NULL
);
-- One audit table for every backup and export across every system.
-- During an incident, "what was the consistent state of our entire
-- data layer at 03:00 on June 15?" is answered here — not by
-- reconstructing it from three different consoles.

    Model Versioning as a Backup Dependency

    A backup of embeddings without the model registry is a backup of uninterpretable numbers. The dbo.EmbeddingModels table from Section 36.1 must be backed up on the same schedule as the vector tables — it lives in the same database, so native backups already capture it. The failure mode this prevents: restoring vectors, then re-embedding new documents with a different model version because nobody recorded which version produced the restored ones. Distances between old and new vectors become meaningless, and retrieval quality collapses without a single error in the log.

  • → Pin the model version in the pipeline configuration, and store the pin in the database — not just in a deployment script.
  • → On restore, verify every ModelId in DocumentChunks has a row in EmbeddingModels before serving traffic.
  • → Retired models stay in the registry forever — a retired row is documentation, not dead weight (Chapter 30).

    Recovery Procedures and RTO Planning

    Recovery has three phases, each with its own timer:

  • → Restore — replay the backup chain to the target point in time. Standard SQL Server restore sequence: full, latest differential, log chain with NORECOVERY until the last log.
  • → Index rebuild — the DiskANN index reconstructs from the restored vector data. This is the hidden RTO multiplier (Chapter 35): hours at tens of millions of rows.
  • → Catch-up — re-embed documents newer than the restore point from the watermark, then run the recall canary before returning traffic.
    • -- SQL Server: point-in-time restore sequence for the vector database
-- (run on the recovery instance)
RESTORE DATABASE VectorRagDb
FROM URL = 'https://vecbackups.blob.core.windows.net/sqlbackups/full.bak'
WITH NORECOVERY, REPLACE, STATS = 10;
RESTORE DATABASE VectorRagDb
FROM URL = 'https://vecbackups.blob.core.windows.net/sqlbackups/diff.bak'
WITH NORECOVERY;
RESTORE LOG VectorRagDb
FROM URL = 'https://vecbackups.blob.core.windows.net/sqlbackups/log.trn'
WITH RECOVERY, STOPAT = '2026-09-26T14:30:00';
-- Then: allow the DiskANN index to rebuild (monitor via error log /
-- extended events), verify model registry completeness, re-embed the
-- post-STOPAT delta from the watermark, run the recall canary.

    Backup Schedules and Retention Policies

  • → Full weekly, differential daily, log every 15 minutes. Vector tables are insert-heavy, so differentials stay proportionally small — but verify this monthly; a re-embedding backfill turns the differential into a near-full.
  • → Retain 4 weekly fulls + 30 days of logs as the baseline; extend for regulated data (the vector store inherits the source corpus's retention policy — Chapter 34).
  • → Export weekly to object storage independently of native backups — different failure domain, different restore path.
  • → Test-restore monthly to an isolated instance and record all three phase timers. A backup you've never restored is a backup you don't have.

    Key Takeaways

  • → Back up three artifacts, not one: source documents, embeddings with model provenance, and the model registry — restore any two and you have a silent corruption incident.
  • → Native SQL Server backups work unchanged on vector tables — but the DiskANN index rebuilds from data during recovery, so budget the rebuild into RTO.
  • → Export weekly to object storage as a platform-independent tier — different failure domain, different restore path, migration seed.
  • → Managed-service exports are the minimum viable posture where you can't run native backups — and the authoritative source stays in systems you control.
  • → Audit every backup and export in one table so incident response can answer "what was our consistent state at 03:00?" in one query.
  • → Test-restore monthly and time all three phases — restore, index rebuild, catch-up. Untested backups are hopes, not plans.
