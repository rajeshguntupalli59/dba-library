Chapter 33: Semantic Caching

33.1 How Semantic Caching Differs from Conventional Caching

LLM API calls are expensive, slow, and deterministic enough that many questions asked of a system are semantically equivalent even when worded differently. A user asking "What's the refund policy?" and another asking "How do I get my money back?" want the same answer. Conventional caching based on exact string matching would treat these as cache misses. Semantic caching uses vector similarity to recognize that two queries mean roughly the same thing and return a cached response — cutting latency from seconds to milliseconds and reducing token costs by 40–80% in production workloads with high query repetition. This chapter covers how semantic caches work, how to build one on SQL Server 2025 native vectors with a Redis tier, how to integrate caching into LangChain and LlamaIndex pipelines, and how to operate a semantic cache in production without sacrificing answer quality.

The core operation is a nearest-neighbor lookup over cached questions: embed the incoming question, find the most similar previously asked question, and if the distance is below a strict threshold, return its cached answer. The threshold is the entire safety story — too loose and paraphrased-but-different questions get wrong answers; too tight and the cache never hits.

33.2 Building a Semantic Cache on SQL Server

SQL Server 2025 with native VECTOR is a natural fit for a semantic cache if your application already runs on SQL Server. You avoid introducing a new infrastructure component, benefit from transactional consistency, and can use standard T-SQL for cache management queries.

-- SQL Server 2025: semantic answer cache
CREATE TABLE dbo.SemanticAnswerCache (
    EntryId      BIGINT IDENTITY(1,1) NOT NULL
        CONSTRAINT PK_SemanticAnswerCache PRIMARY KEY,
    Namespace    NVARCHAR(60) NOT NULL,     -- 'support', 'sales', 'codegen'
    TenantId     INT NOT NULL,              -- never share answers across tenants
    QuestionText NVARCHAR(1000) NOT NULL,
    QuestionEmb  VECTOR(1536) NOT NULL,
    AnswerText   NVARCHAR(MAX) NOT NULL,
    ModelId      NVARCHAR(100) NOT NULL,
    HitCount     BIGINT NOT NULL CONSTRAINT DF_SAC_Hits DEFAULT (0),
    CreatedAt    DATETIME2(0) NOT NULL
        CONSTRAINT DF_SAC_Created DEFAULT SYSUTCDATETIME(),
    LastHitAt    DATETIME2(0) NULL
);
CREATE INDEX IX_SAC_Namespace_Tenant
    ON dbo.SemanticAnswerCache (Namespace, TenantId);
CREATE VECTOR INDEX IX_SAC_QuestionEmb
    ON dbo.SemanticAnswerCache (QuestionEmb)
    WITH (METRIC = 'cosine', TYPE = 'DiskANN', MAXDOP = 4);

Python client wrapping the SQL Server cache

# Python — semantic cache backed by SQL Server native VECTOR
import pyodbc, openai

class SqlServerSemanticCache:
    """Semantic cache backed by SQL Server native VECTOR."""

    def __init__(self, conn_str, model="text-embedding-3-small",
                 threshold=0.08):
        self.conn = pyodbc.connect(conn_str)
        self.client = openai.OpenAI()
        self.model = model
        self.threshold = threshold   # cosine distance: lower = stricter

    def _embed(self, text):
        return self.client.embeddings.create(
            input=[text], model=self.model).data[0].embedding

    def lookup(self, question, namespace="support", tenant_id=1):
        q = "[" + ",".join(str(v) for v in self._embed(question)) + "]"
        cur = self.conn.cursor()
        row = cur.execute("""SELECT TOP (1) EntryId, AnswerText,
                VECTOR_DISTANCE('cosine', QuestionEmb,
                    CAST(? AS VECTOR(1536))) AS Distance
            FROM dbo.SemanticAnswerCache
            WHERE Namespace = ? AND TenantId = ? AND ModelId = ?
              AND VECTOR_DISTANCE('cosine', QuestionEmb,
                      CAST(? AS VECTOR(1536))) < ?
            ORDER BY Distance""",
            (q, namespace, tenant_id, self.model, q, self.threshold)
        ).fetchone()
        if row is None:
            return None
        cur.execute("""UPDATE dbo.SemanticAnswerCache
                       SET HitCount = HitCount + 1,
                           LastHitAt = SYSUTCDATETIME()
                       WHERE EntryId = ?""", (row[0],))
        self.conn.commit()
        return {"answer": row[1], "distance": row[2],
                "cached": True}

    def store(self, question, answer, namespace="support", tenant_id=1):
        q = "[" + ",".join(str(v) for v in self._embed(question)) + "]"
        cur = self.conn.cursor()
        cur.execute("""INSERT INTO dbo.SemanticAnswerCache
                           (Namespace, TenantId, QuestionText, QuestionEmb,
                            AnswerText, ModelId)
                       VALUES (?, ?, ?, CAST(? AS VECTOR(1536)), ?, ?)""",
                    (namespace, tenant_id, question, q, answer, self.model))
        self.conn.commit()

Two non-negotiable predicates in the lookup: TenantId (cached answers must never leak across tenants — Chapter 34) and ModelId (an answer generated from one embedding model's geometry must not be served for another's). The threshold of 0.08 cosine distance is a starting point — tune it on your eval set, measuring false-hit rate, not just hit rate.

33.3 Semantic Caching with Redis and a Dedicated Vector Store

For applications that need sub-5ms cache lookups and cannot afford a full SQL Server query round-trip, Redis with the RediSearch module (or Redis Stack) provides an in-memory vector cache. The tradeoff is that Redis is bounded by available memory; entries must be kept small or the cache must be tiered.

The production pattern is a tiered cache: Redis holds the hottest question/answer pairs as exact-match entries keyed by question hash (sub-millisecond, no vector math), while SQL Server holds the full semantic cache for near-duplicate lookup. The request path checks Redis first, then SQL Server semantic lookup, then the full RAG pipeline — each tier an order of magnitude cheaper than the next to miss.

# Python — tiered lookup: Redis exact-match -> SQL Server semantic -> RAG
import hashlib, json
import redis

r = redis.Redis(host="localhost", port=6379, decode_responses=True)
sem_cache = SqlServerSemanticCache(conn_str="...")  # Section 33.2

def answer_question(question, namespace="support", tenant_id=1):
    # Tier 1: Redis exact match on normalized question text
    norm = " ".join(question.lower().split())
    key = f"semcache:{namespace}:{tenant_id}:" \
          f"{hashlib.sha256(norm.encode()).hexdigest()}"
    hit = r.get(key)
    if hit:
        return {"answer": json.loads(hit)["a"], "tier": "redis"}
    # Tier 2: SQL Server semantic (near-duplicate) lookup
    sem = sem_cache.lookup(question, namespace, tenant_id)
    if sem:
        r.setex(key, 3600, json.dumps({"a": sem["answer"]}))
        return {"answer": sem["answer"], "tier": "semantic"}
    # Tier 3: full RAG pipeline, then populate both tiers
    result = rag_answer(question, tenant_id)   # Chapters 21/25 pipeline
    sem_cache.store(question, result["answer"], namespace, tenant_id)
    r.setex(key, 3600, json.dumps({"a": result["answer"]}))
    return {"answer": result["answer"], "tier": "rag"}

33.4 LangChain and LlamaIndex Integration

LangChain with GPTCache and a SQL Server backend. GPTCache supports custom storage backends — implement its storage interface over dbo.SemanticAnswerCache and LangChain's set_llm_cache() picks it up with no pipeline changes. The key detail is the similarity evaluation function: GPTCache's default is exact-match-friendly, so configure its cosine-distance threshold to match the 0.08 starting point from Section 33.2 and tune from there.

LlamaIndex. Wrap the query engine: check SqlServerSemanticCache.lookup() before calling query_engine.query(), and store() after. For LlamaIndex's agent workloads, cache at the tool-result level rather than the final-answer level (Section 33.7) — tool calls repeat far more often than full agent trajectories.

In production, keep the framework integration thin: the cache class from Section 33.2 owns storage, thresholds, and tenant isolation; the framework glue is a few lines that call it. When you tune the threshold or change the schema, you change one place.

33.5 Cache Hit Rate Optimization

Hit rate is driven by question repetition, which you can engineer:

  • → Normalize before hashing. Lowercase, collapse whitespace, strip punctuation for the Redis exact-match tier — "What's the refund policy?" and "what's the refund policy" are the same question.
  • → Segment by namespace. A single cache namespace mixing product questions, support queries, and code generation requests produces false positive hits — code questions semantically overlapping with English descriptions. Segmenting by namespace (which maps to the Namespace column predicate in SQL Server) keeps the search space focused and reduces false positives.
  • → Tune the threshold per namespace. Support FAQs tolerate a looser threshold (answers are stable, paraphrases are common); code generation needs a strict one (small wording changes alter the correct answer).
  • → Seed from history. Pre-populate the cache from query logs: take the top-N frequent questions, run them through the RAG pipeline once, and store the pairs. Day-one hit rate jumps from zero to the steady-state value.
    • -- SQL Server: hit-rate and false-hit analysis
SELECT Namespace,
       COUNT(*) AS Entries,
       SUM(HitCount) AS TotalHits,
       CAST(SUM(HitCount) AS FLOAT) / NULLIF(COUNT(*), 0) AS AvgHitsPerEntry
FROM dbo.SemanticAnswerCache
GROUP BY Namespace
ORDER BY AvgHitsPerEntry DESC;
-- Namespaces with high entries but ~0 hits are mis-tuned:
-- threshold too strict, or questions that never repeat.
-- Namespaces with rising user complaints need threshold tightening,
-- not hit-rate celebration.

    33.6 Production Operations: Monitoring, Eviction, and Invalidation

    Unlike memory-bounded caches like Redis, a SQL Server-backed semantic cache grows without bound unless you actively evict entries. Three practical eviction strategies:

    -- SQL Server: eviction strategies for the semantic cache
-- 1. Age-based: drop entries never hit in 90 days
DELETE FROM dbo.SemanticAnswerCache
WHERE LastHitAt < DATEADD(day, -90, SYSUTCDATETIME())
  AND CreatedAt < DATEADD(day, -90, SYSUTCDATETIME());
-- 2. Hit-count-based: keep only entries earning their storage
-- DELETE FROM dbo.SemanticAnswerCache
-- WHERE HitCount = 0 AND CreatedAt < DATEADD(day, -30, SYSUTCDATETIME());
-- 3. Capacity-based: keep the top-N per namespace by hits
-- WITH ranked AS (
--     SELECT EntryId, ROW_NUMBER() OVER (
--         PARTITION BY Namespace ORDER BY HitCount DESC) AS rn
--     FROM dbo.SemanticAnswerCache)
-- DELETE FROM ranked WHERE rn > 100000;

    Invalidation is event-driven: when a source document changes, flush cache entries whose answers derived from it. Track provenance — store the source DocId list alongside each cached answer — so a document update can DELETE exactly the affected entries instead of flushing the namespace.

    # Python — event-driven invalidation
def handle_document_updated_event(event, cache):
    """Flush cached answers derived from the changed document."""
    doc_id = event["doc_id"]
    cur = cache.conn.cursor()
    cur.execute("""DELETE FROM dbo.SemanticAnswerCache
                   WHERE EntryId IN (
                       SELECT EntryId FROM dbo.SemanticAnswerProvenance
                       WHERE DocId = ?)""", (doc_id,))
    deleted = cur.rowcount
    cache.conn.commit()
    return deleted

def handle_namespace_flush_event(event, cache):
    """Nuclear option: flush a whole namespace (e.g., policy rewrite)."""
    cur = cache.conn.cursor()
    cur.execute("DELETE FROM dbo.SemanticAnswerCache WHERE Namespace = ?",
                (event["namespace"],))
    cache.conn.commit()

    Monitor hit rate, false-hit complaints, and p99 lookup latency per tier. A semantic cache whose hit rate climbs while user complaints climb is a threshold problem — tighten it. A cache whose latency approaches the RAG pipeline's latency has lost its purpose — check the DiskANN index health and the Redis tier.

    33.7 Semantic Caching for Agentic and Multi-Turn Workloads

    Agents break the single-question assumption: a multi-turn conversation has context, tool calls, and intermediate reasoning. Cache at the right granularity:

  • → Tool-result caching. Agent tool calls (database lookups, API fetches) repeat across conversations far more than full trajectories. Cache tool results keyed by (tool name, normalized arguments) in the Redis exact-match tier — deterministic, high hit rate, trivially safe.
  • → Turn-level caching with conversation context. For follow-up questions ("and what about the enterprise plan?"), embed the question plus a summary of the conversation so far. The cache key captures the context the answer depends on; without it, follow-ups collide with unrelated same-text questions.
  • → Never cache across different tool states. An answer that depended on a tool result must be invalidated when the underlying data changes — extend the provenance pattern from Section 33.6 to tool outputs.

    33.8 Failure Modes and Mitigations

  • → False hits (wrong answer served confidently). The catastrophic mode. Mitigate with strict per-namespace thresholds, user feedback signals that auto-tighten the threshold, and a "report wrong answer" path that deletes the offending entry immediately.
  • → Stale answers. The source changed; the cache didn't hear about it. Mitigate with provenance-tracked invalidation (Section 33.6), not TTLs — TTLs either flush too aggressively (killing hit rate) or too lazily (serving stale answers).
  • → Tenant leakage. A cached answer from tenant A served to tenant B. Mitigate by making TenantId a mandatory predicate in every lookup — enforced in the cache class, not left to callers.
  • → Threshold drift. What was strict enough at 10K entries may be too loose at 10M, as denser space means closer near-duplicates. Re-tune the threshold quarterly against the eval set.

    • ---

    Key Takeaways

  • → Semantic caching trades LLM calls for vector lookups: embed the question, near-duplicate-match against cached questions in SQL Server, and skip the pipeline on a hit.
  • → The similarity threshold is the entire safety story — tune it per namespace on evals, measuring false-hit rate, not just hit rate.
  • → TenantId and ModelId are mandatory lookup predicates — tenant leakage and cross-model reads are silent corruption.
  • → Tier the cache: Redis exact-match for sub-millisecond hot hits, SQL Server semantic for near-duplicates, RAG pipeline as the fallback that repopulates both.
  • → Invalidate by provenance (document → affected entries), evict by age/hits/capacity, and never rely on TTLs for correctness.
