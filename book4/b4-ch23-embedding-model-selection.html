Chapter 23: Embedding Model Selection

What an Embedding Model Actually Does (and Why It Matters to a DBA)

An embedding model is a function from text to a fixed-length array of floats. Everything downstream — your VECTOR(n) column width, your storage footprint, your index build time, your retrieval quality — is determined by two properties of that function: its output dimension and its semantic quality on your domain. The model is chosen once per corpus and lives in your schema as a column width and a ModelName value, which makes model selection a schema decision with the permanence of a data type choice. Get it wrong and you face cascading problems: mismatched dimensions between stored and query vectors, poor retrieval quality on domain-specific content, unnecessary API costs at query time, or latency profiles that make the application unusable.

This chapter walks through the three major embedding ecosystems — OpenAI, Cohere, and Sentence Transformers — examining their output dimensions, quality characteristics, cost structures, and operational tradeoffs. You will leave with a framework for matching model to workload and production-ready integration code for each provider against SQL Server.

---

OpenAI Embeddings: Production Workhorse

OpenAI's text-embedding-3-small (1,536 dimensions) and text-embedding-3-large (3,072 dimensions) are the default choice for most production RAG systems: strong general quality, simple API, and per-token pricing that is cheap at ingest scale. The 3-series supports dimension truncation — you can request fewer dimensions than the native output (e.g., 512 from the large model) with modest quality loss, which lets you trade storage and index size against retrieval quality without changing models.

# Python — batch-embed documents and store in SQL Server
import openai, pyodbc

openai_client = openai.OpenAI()
conn = pyodbc.connect("DRIVER={ODBC Driver 18 for SQL Server};"
                      "SERVER=localhost;DATABASE=ragdb;Trusted_Connection=yes;"
                      "Encrypt=yes;TrustServerCertificate=yes")

def load_documents_to_sqlserver(docs, model="text-embedding-3-small",
                                dimensions=None):
    """Batch-embed documents and store in SQL Server native VECTOR."""
    kwargs = {"model": model}
    if dimensions:                       # 3-series supports truncation
        kwargs["dimensions"] = dimensions
    resp = openai_client.embeddings.create(input=[d["text"] for d in docs],
                                           **kwargs)
    dim = dimensions or (3072 if "large" in model else 1536)
    cur = conn.cursor()
    for doc, e in zip(docs, resp.data):
        vec = "[" + ",".join(str(v) for v in e.embedding) + "]"
        cur.execute("""INSERT INTO dbo.Documents
                           (DocId, Title, BodyText, Embedding, ModelName)
                       VALUES (?, ?, ?, CAST(? AS VECTOR(%d)), ?)""" % dim,
                    (doc["id"], doc["title"], doc["text"], vec, model))
    conn.commit()
    return len(docs)

The SQL Server schema for this setup:

-- SQL Server 2025
CREATE TABLE dbo.Documents (
    DocKey    BIGINT IDENTITY(1,1) NOT NULL
        CONSTRAINT PK_Documents PRIMARY KEY,
    DocId     NVARCHAR(100) NOT NULL,
    Title     NVARCHAR(300) NULL,
    BodyText  NVARCHAR(MAX) NOT NULL,
    Embedding VECTOR(1536) NOT NULL,          -- matches text-embedding-3-small
    ModelName NVARCHAR(100) NOT NULL
        CONSTRAINT DF_Documents_Model DEFAULT ('text-embedding-3-small'),
    CreatedAt DATETIME2(0) NOT NULL
        CONSTRAINT DF_Documents_Created DEFAULT SYSUTCDATETIME()
);
-- DiskANN index for ANN search (exact VECTOR_DISTANCE for smaller corpora):
CREATE VECTOR INDEX IX_Documents_Embedding
    ON dbo.Documents (Embedding)
    WITH (METRIC = 'cosine', TYPE = 'DiskANN', MAXDOP = 4);
-- To drop and rebuild after a model change:
-- DROP INDEX IX_Documents_Embedding ON dbo.Documents;

Operational notes: OpenAI is an external API dependency on your ingest path — batch aggressively (the API accepts large input arrays), retry with backoff, and checkpoint progress so a failed batch does not restart a million-document ingest. At query time, embedding the question adds one API round-trip to retrieval latency; for latency-sensitive paths, cache question embeddings or use a local model for the query side while keeping OpenAI vectors for the corpus — never mixing the two in one query.

Cohere Embeddings: Retrieval-Optimized with Input Type Awareness

Cohere's embed-v4 family is purpose-built for retrieval: it accepts an input_type parameter (search_document vs search_query) that tunes the embedding for its role, which measurably improves retrieval on asymmetric tasks — short question against long document — where generic embeddings underperform. It also offers native quantized outputs, reducing storage and memory without a separate compression step.

# Python — Cohere embeddings with input-type awareness into SQL Server
import cohere, pyodbc

co = cohere.ClientV2(api_key="...")
conn = pyodbc.connect("DRIVER={ODBC Driver 18 for SQL Server};"
                      "SERVER=localhost;DATABASE=ragdb;Trusted_Connection=yes;"
                      "Encrypt=yes;TrustServerCertificate=yes")

def load_with_cohere(docs, model="embed-v4.0", dim=1536):
    resp = co.embed(texts=[d["text"] for d in docs], model=model,
                    input_type="search_document",
                    embedding_types=["float"])
    cur = conn.cursor()
    for doc, emb in zip(docs, resp.embeddings.float_):
        vec = "[" + ",".join(str(v) for v in emb[:dim]) + "]"
        cur.execute("""INSERT INTO dbo.Documents
                           (DocId, Title, BodyText, Embedding, ModelName)
                       VALUES (?, ?, ?, CAST(? AS VECTOR(1536)), ?)""",
                    (doc["id"], doc["title"], doc["text"], vec, model))
    conn.commit()

# Query side uses the matching input type:
# co.embed(texts=[question], model=model,
#          input_type="search_query", embedding_types=["float"])

The input-type distinction is a contract you must honor in both directions: documents embedded as search_document must be queried with search_query vectors. Enforce it with the ModelName column plus an input-type column if you serve both roles from one table.

Sentence Transformers: Local Embeddings for Privacy and Cost Control

Sentence Transformers (e.g., all-MiniLM-L6-v2 at 384 dimensions, bge-large-en-v1.5 at 1,024) run on your own infrastructure — no API dependency, no per-token cost, no data leaving your network. For regulated industries and air-gapped environments, that settles the decision by itself. The tradeoff is quality on general-domain queries (top commercial models still lead on broad benchmarks) and the operational burden of GPU inference at ingest scale.

# Python — local Sentence Transformers embeddings into SQL Server
from sentence_transformers import SentenceTransformer
import pyodbc

st_model = SentenceTransformer("BAAI/bge-large-en-v1.5")  # 1024 dims
conn = pyodbc.connect("DRIVER={ODBC Driver 18 for SQL Server};"
                      "SERVER=localhost;DATABASE=ragdb;Trusted_Connection=yes;"
                      "Encrypt=yes;TrustServerCertificate=yes")

def load_with_st(docs, batch_size=256):
    cur = conn.cursor()
    for i in range(0, len(docs), batch_size):
        batch = docs[i:i + batch_size]
        embs = st_model.encode([d["text"] for d in batch],
                               normalize_embeddings=True)  # cosine-ready
        for doc, emb in zip(batch, embs):
            vec = "[" + ",".join(str(v) for v in emb) + "]"
            cur.execute("""INSERT INTO dbo.Documents
                               (DocId, Title, BodyText, Embedding, ModelName)
                           VALUES (?, ?, ?, CAST(? AS VECTOR(1024)), ?)""",
                        (doc["id"], doc["title"], doc["text"], vec,
                         "bge-large-en-v1.5"))
        conn.commit()   # checkpoint per batch: resumable ingest

Note the column width changes with the model: 384-dimension MiniLM needs VECTOR(384), 1,024-dimension BGE needs VECTOR(1024). The dimension is part of the schema, so a model change is a schema migration — plan for the side-by-side pattern in the versioning section below rather than an in-place ALTER.

Comparing Models: Quality, Cost, and Latency at Production Scale

Compare on three axes, in this order:

  • → Quality on your data. Public benchmarks (MTEB) rank models on generic corpora; your corpus is not generic. Build the evaluation harness from Chapter 22.8 — 50–100 questions with expected fragments — and score candidate models on it. A smaller model that understands your domain vocabulary (medical, legal, industrial) routinely beats a larger general model.
  • → Total cost. API models charge per token at ingest and per question at query time; local models charge GPU-hours once plus engineering time. At 100M documents, API ingest cost dominates; at 10K questions per second, API query cost and latency dominate. Model the full three-year cost, not the per-1K-token price.
  • → Latency profile. API embedding adds a network round-trip to every retrieval; local inference adds GPU scheduling latency but no network. Measure p99 end-to-end (embed question + vector search + LLM), not embedding latency in isolation.

    • Query to estimate current vector storage in a SQL Server table:

    -- SQL Server: estimate vector storage per model dimension
SELECT ModelName,
       COUNT(*) AS Vectors,
       COUNT(*) * 1536 * 4 / 1024 / 1024 AS ApproxVectorMB_1536d,
       COUNT(*) * 1024 * 4 / 1024 / 1024 AS ApproxVectorMB_1024d
FROM dbo.Documents
GROUP BY ModelName;
-- float32 = 4 bytes/dimension; refine with actual dimension per model.
-- Add sys.dm_db_partition_stats reserved pages for the full picture
-- including row overhead, indexes, and allocation.

    If storage is the binding constraint, consider quantization: Cohere provides native quantized outputs, and Sentence Transformers float32 outputs can be post-processed into lower-precision representations before storage. Quantization trades recall for memory — measure both configurations on your eval set (Chapter 20) before committing the schema to a narrower representation.

    Model Versioning and Migration Strategy

    Embedding models get updated — vendors release new versions, and your own fine-tunes evolve. Because vectors from different models are mutually meaningless, a model change is a full re-ingestion event, not an in-place update. The production pattern is side-by-side: add a second vector column, backfill in batches, switch the query path, then drop the old column.

    -- SQL Server: side-by-side embedding model migration
ALTER TABLE dbo.Documents ADD Embedding_v2 VECTOR(3072) NULL;
-- Backfill in throttled batches during off-peak:
-- UPDATE TOP (50000) dbo.Documents
-- SET Embedding_v2 = ...  -- computed by the re-embedding job
-- WHERE Embedding_v2 IS NULL;
CREATE VECTOR INDEX IX_Documents_Embedding_v2
    ON dbo.Documents (Embedding_v2)
    WITH (METRIC = 'cosine', TYPE = 'DiskANN', MAXDOP = 8);
-- Point retrieval at Embedding_v2 + ModelName = 'text-embedding-3-large',
-- verify eval scores, then:
-- DROP INDEX IX_Documents_Embedding ON dbo.Documents;
-- ALTER TABLE dbo.Documents DROP COLUMN Embedding;
-- EXEC sp_rename 'dbo.Documents.Embedding_v2', 'Embedding', 'COLUMN';

    During the backfill, the ModelName predicate in the retrieval query guarantees old and new vectors never mix in one result set. Size the backfill batches to your maintenance window and monitor transaction log growth — re-embedding a large corpus is one of the heaviest write workloads the table will ever see.

    ---

    Choosing the Right Model: A Decision Framework

  • → Starting out, general domain? OpenAI text-embedding-3-small at 1,536 dimensions. Best quality-per-dollar, simplest operations, and the dimension truncation option gives you a storage escape hatch.
  • → Asymmetric retrieval (short queries, long documents)? Cohere with search_document/search_query input types. The role-aware embeddings earn their keep on Q&A workloads.
  • → Regulated data or no external APIs? Sentence Transformers on your own GPUs. Accept the quality gap on generic queries or close it with domain fine-tuning.
  • → Massive scale, cost-dominated? Truncated OpenAI dimensions (512) or quantized Cohere outputs; validate recall on your eval set before committing.
  • → Sub-50ms retrieval SLA? Local model for the query path (no API round-trip) regardless of which model embedded the corpus — as long as query and corpus models match.

    End-to-End Example: Evaluating Two Models Side by Side

    The decision framework narrows the field; the eval set makes the call. Embed your Chapter 22.8 evaluation questions with both candidate models, retrieve top-5 chunks per model from side-by-side columns, and score hit rate plus p99 retrieval latency:

    -- SQL Server: A/B retrieval quality between two embedding models
-- EvalQuestions(QuestionId, QuestionText, ExpectedFragment,
--               QSmall VECTOR(1536), QLarge VECTOR(3072))
-- Documents has Embedding (small model) and Embedding_v2 (large model)
DECLARE @qid INT = 42;

SELECT 'small' AS Model,
       (SELECT COUNT(*) FROM (
            SELECT TOP (5) d.BodyText
            FROM dbo.Documents AS d
            WHERE d.ModelName = 'text-embedding-3-small'
            ORDER BY VECTOR_DISTANCE('cosine', d.Embedding, q.QSmall)
        ) AS r WHERE r.BodyText LIKE '%' + q.ExpectedFragment + '%') AS Hit
FROM dbo.EvalQuestions AS q WHERE q.QuestionId = @qid
UNION ALL
SELECT 'large',
       (SELECT COUNT(*) FROM (
            SELECT TOP (5) d.BodyText
            FROM dbo.Documents AS d
            WHERE d.ModelName = 'text-embedding-3-large'
            ORDER BY VECTOR_DISTANCE('cosine', d.Embedding_v2, q.QLarge)
        ) AS r WHERE r.BodyText LIKE '%' + q.ExpectedFragment + '%')
FROM dbo.EvalQuestions AS q WHERE q.QuestionId = @qid;
-- Aggregate Hit over all questions per model: higher hit rate wins,
-- with p99 latency from Chapter 20's harness as the tiebreaker.

    Run this over the full eval set, not a handful of samples — model differences that are invisible at n=10 become decisive at n=100. Keep the eval set versioned alongside the schema: when the vendor ships the next model version, you re-run the same harness instead of re-litigating the decision from scratch.

    ---

    Key Takeaways

  • → Model selection is a schema decision: dimension becomes the VECTOR(n) column width, and the model name belongs in a column, not a comment.
  • → OpenAI is the default for general workloads, Cohere earns its keep on asymmetric Q&A retrieval with input-type awareness, and Sentence Transformers win wherever data cannot leave your network.
  • → Never mix models in one query path: enforce the same-model rule with a ModelName predicate, and honor input-type contracts (Cohere) in both directions.
  • → Decide on your data, not public benchmarks: score candidates on a versioned eval set of your own questions, with p99 latency as the tiebreaker.
  • → Migrate models side-by-side — second vector column, throttled backfill, new DiskANN index, verified eval scores, then drop the old column. A model change is a re-ingestion event, never an in-place update.
