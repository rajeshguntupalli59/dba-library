Chapter 9: DiskANN Indexing in SQL Server 2025: Performance Tradeoffs

Vector search at scale lives or dies by its index structure. When you move beyond brute-force exact search — the vector equivalent of a full table scan — you enter the world of Approximate Nearest Neighbor (ANN) algorithms. SQL Server 2025 made its choice for you: the native vector index is built on DiskANN, a graph-based ANN algorithm designed at Microsoft Research for billion-scale search on SSD-backed storage. This chapter unpacks how DiskANN works, where it sits relative to the exact search you already know, what the index costs to build and maintain, and how to reason about the recall-versus-latency tradeoff that defines every ANN system. If B-tree fill-factor and fragmentation tradeoffs feel natural to you, this chapter will feel like home.

---

The ANN Problem: Why Exact Search Stops Scaling

Exact nearest-neighbor search with VECTOR_DISTANCE computes the distance from the query vector to every stored vector. At 1 million vectors of 1536 dimensions, that is roughly 1.5 billion floating-point operations per query — hundreds of milliseconds even with SIMD acceleration, before any I/O. It is perfectly accurate (100% recall by definition) and perfectly acceptable up to about 50,000 vectors. Past that, latency grows linearly with table size, and no amount of hardware generosity changes the math.

ANN algorithms trade a small, measurable amount of recall for dramatic speed improvements. Recall is the fraction of the true top-k nearest neighbors that the approximate search actually returns: 0.97 recall means 97 of the 100 true nearest neighbors were found. The core insight is identical to why you do not read every page of a book to find a topic — you use an index that organizes content so you can skip most of it. For most production AI workloads, 97% recall at 10 milliseconds is far more valuable than 100% recall at 1,500 milliseconds — and embeddings are already approximate representations of meaning, so the last few percent of geometric precision rarely changes what the user experiences.

---

How DiskANN Works: Graphs Instead of Trees

DiskANN builds a navigable graph over the vector collection: each vector becomes a node connected to a bounded set of its nearest neighbors. A query starts at a fixed entry point and greedily walks the graph — at each step moving to the neighbor closest to the query vector — until no unvisited neighbor is closer than the current best candidates. Because the graph is constructed so that greedy routing converges quickly, search touches only a tiny fraction of the collection: query time grows logarithmically with data size rather than linearly.

What distinguishes DiskANN from earlier graph indexes (notably HNSW, which powers several dedicated vector databases covered in Chapters 15–19) is its storage design. HNSW keeps the entire graph in RAM, which makes it fast but memory-hungry at billion-vector scale. DiskANN was designed for SSDs: it stores the full-precision vectors and most of the graph on disk, keeps only a compressed or sampled representation in memory, and issues a small, bounded number of random SSD reads per query. The result is an index that serves billion-scale collections from a single machine without requiring terabytes of RAM — a design that maps naturally onto SQL Server's buffer-pool-and-storage architecture.

For the DBA, the useful mental model is: a DiskANN vector index is a specialized access path for ORDER BY VECTOR_DISTANCE queries, analogous to how a B-tree is a specialized access path for range predicates. The query optimizer chooses between the exact scan path and the approximate index path the same way it chooses between a table scan and an index seek — based on cost, with the added dimension that the approximate path deliberately sacrifices a few percent of recall for orders of magnitude less work.

Creating and Querying the Vector Index

The DDL is deliberately minimal — one statement, with the distance metric as the key decision:

-- DiskANN approximate vector index (preview in SQL Server 2025)
CREATE VECTOR INDEX IX_RagChunks_Embedding
ON dbo.RagChunks (Embedding)
WITH (
    METRIC = 'cosine',     -- must match the metric your queries use
    TYPE   = 'DiskANN',
    MAXDOP = 4             -- parallelism for the index build
);

-- Approximate k-NN through the index
DECLARE @q VECTOR(1536) = '[0.012, -0.043, 0.071, ...]';

SELECT t.ChunkId, t.ChunkText, s.distance
FROM VECTOR_SEARCH(
    TABLE      = dbo.RagChunks AS t,
    COLUMN     = Embedding,
    SIMILAR_TO = @q,
    METRIC     = 'cosine',
    TOP_N      = 10
) AS s
ORDER BY s.distance;

The METRIC choice is the single most consequential parameter: it must match both your embedding model's normalization characteristics and the metric your queries specify. Cosine is the right default for normalized text embeddings (OpenAI, most sentence-transformer models). Euclidean suits unnormalized embeddings where magnitude carries meaning. Dot product matches models trained with inner-product objectives. An index built with the wrong metric does not error — it silently returns poorly ranked results, which is worse.

Note the current preview constraints, because they shape real designs: the table must have a single-column integer clustered primary key; the table becomes read-only while the vector index exists in SQL Server 2025; incorporating new data means dropping and recreating the index; and partitioned tables, views, and temporary tables are not supported. These constraints are why Chapter 8's schema patterns keep embeddings in ordinary tables with ordinary keys — the vector index stays a droppable performance layer, never a structural dependency.

The Tradeoff Table: Exact vs. DiskANN

Every ANN decision is a position on three axes — recall, latency, and build/maintenance cost. Here is where the two SQL Server search paths land:

| | Exact (VECTOR_DISTANCE) | Approximate (DiskANN) |

|---|---|---|

| Recall | 100% by definition | Typically 95–99%, tunable |

| Query cost | O(n): full scan per query | O(log n): graph walk |

| Latency at 1M vectors | Hundreds of ms | Single-digit to tens of ms |

| Build cost | None | Minutes to hours for large collections |

| Write path | Normal DML | Drop index → load → rebuild (preview) |

| Memory pressure | Buffer pool for scanned pages | Graph + vectors compete for buffer pool |

| Suitable for | Under ~50K vectors; 100% recall required | 50K+ vectors; interactive latency SLAs |

The crossover point deserves emphasis because teams routinely misjudge it in both directions. Below roughly 50,000 vectors, exact search is so fast that the DiskANN index buys you almost nothing while adding build time and write-path friction — skip it. Above that, latency divergence becomes impossible to ignore, and the index pays for itself immediately. Between 50K and a few hundred thousand vectors, either path works; choose based on whether your latency SLA has headroom.

Tuning Recall: What to Measure

"Approximate" is only acceptable when you can measure how approximate. The standard methodology: sample a few hundred representative query vectors, run each through both the exact path (VECTOR_DISTANCE with ORDER BY) and the approximate path (VECTOR_SEARCH), and compute recall@k — the fraction of the exact top-k present in the approximate top-k. Automate this as a scheduled job; recall is the canary for index health, degrading when the data distribution drifts away from what the index was built on.

-- Recall spot-check pattern: compare exact vs approximate top-10
-- Run for a sample of query vectors; recall@10 = |intersection| / 10
DECLARE @q VECTOR(1536) = '[0.012, -0.043, 0.071, ...]';

-- Exact ground truth
SELECT TOP (10) ChunkId
INTO #exact
FROM dbo.RagChunks
WHERE Embedding IS NOT NULL
ORDER BY VECTOR_DISTANCE('cosine', Embedding, @q);

-- Approximate candidates
SELECT TOP (10) ChunkId
INTO #approx
FROM VECTOR_SEARCH(
    TABLE = dbo.RagChunks AS t, COLUMN = Embedding,
    SIMILAR_TO = @q, METRIC = 'cosine', TOP_N = 10
) AS s;

-- Overlap = recall@10 for this query
SELECT COUNT(*) * 1.0 / 10 AS recall_at_10
FROM #exact AS e JOIN #approx AS a ON a.ChunkId = e.ChunkId;

DROP TABLE #exact, #approx;

If recall slips below your target (0.95 is a common floor for RAG retrieval), the remedies in order of cost: increase TOP_N and rerank the surplus with exact VECTOR_DISTANCE (cheap, often sufficient); rebuild the index after significant data churn (moderate); reconsider chunking or the embedding model (expensive, but sometimes the real problem is upstream of the index).

Key Takeaways

  • → SQL Server 2025's native vector index uses DiskANN — a graph-based ANN algorithm designed for SSD-backed, billion-scale search — created with CREATE VECTOR INDEX ... WITH (TYPE = 'DiskANN') and queried via the VECTOR_SEARCH table-valued function.
  • → Exact search (VECTOR_DISTANCE) gives 100% recall with O(n) cost per query and needs no index — it is the right choice under roughly 50,000 vectors. DiskANN gives 95–99% recall with O(log n) cost and is the right choice above that.
  • → The METRIC parameter must match your embedding model and your queries; a mismatched metric silently degrades ranking quality instead of erroring.
  • → Preview constraints shape the design: single-column integer clustered key required, table read-only while the index exists, drop-and-recreate to ingest new data — keep the vector index a droppable performance layer, not a structural dependency.
  • → Measure recall@k by comparing VECTOR_SEARCH against exact VECTOR_DISTANCE on a query sample, on a schedule. When recall slips, over-fetch with larger TOP_N and rerank exactly before rebuilding anything.
