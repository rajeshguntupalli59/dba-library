Chapter 12: Multi-Tenant Vector Storage in SQL Server

Multi-tenancy turns every vector decision up a notch. One tenant's support tickets must never surface in another tenant's RAG answers; a noisy tenant's indexing burst must not starve everyone else's retrieval latency; onboarding tenant number ten thousand should be a row insert, not a migration project. SQL Server's tenancy toolkit — shared tables with tenant keys, row-level security, separate schemas, separate databases, elastic pools — maps cleanly onto vector workloads, with one vector-specific wrinkle: the approximate vector index does not understand tenants, so filtered search quality needs deliberate design. This chapter walks through the four tenancy patterns, their vector implications, and how to keep retrieval both isolated and fast.

---

Pattern 1: Shared Tables with tenant_id (Pooled Tenancy)

The default pattern: every vector row carries a TenantId, every query filters on it, and tenants share tables, indexes, and the buffer pool. It is the cheapest to operate and the fastest to onboard — a new tenant is an INSERT into a tenants table, not a provisioning event.

-- Pooled tenancy: TenantId on every vector row, filtered at query time
CREATE TABLE dbo.TenantChunks (
    ChunkId     INT IDENTITY(1,1) NOT NULL CONSTRAINT PK_TenantChunks PRIMARY KEY,
    TenantId    INT NOT NULL,
    DocumentId  INT NOT NULL,
    ChunkText   NVARCHAR(MAX) NOT NULL,
    Embedding   VECTOR(1536) NULL,
    CONSTRAINT FK_TenantChunks_Tenants FOREIGN KEY (TenantId)
        REFERENCES dbo.Tenants (TenantId)
);
-- Tenant-keyed access path: every retrieval seeks here first
CREATE INDEX IX_TenantChunks_Tenant ON dbo.TenantChunks (TenantId, ChunkId);

-- Tenant-scoped exact retrieval
DECLARE @tenantId INT = 101, @q VECTOR(1536) = '...';
SELECT TOP (10) ChunkId, ChunkText,
       VECTOR_DISTANCE('cosine', Embedding, @q) AS Distance
FROM dbo.TenantChunks
WHERE TenantId = @tenantId AND Embedding IS NOT NULL
ORDER BY Distance;

For exact search this pattern is flawless: the TenantId predicate seeks the tenant's slice and ranks only within it — perfect isolation, perfect recall. For DiskANN approximate search, the wrinkle appears: the vector index is built over all tenants' vectors together, and a tenant-scoped query is a filtered ANN search. With moderate tenant counts and reasonably balanced data volumes this works well — the relational filter narrows candidates and the graph walk stays efficient. It degrades when one tenant dominates the corpus (their vectors saturate the graph neighborhoods) or when a tenant's data is a tiny fraction of a huge shared index (the walk wastes effort on other tenants' vectors). Mitigations: over-fetch TOP_N aggressively for small tenants, and monitor per-tenant recall with the Chapter 9 spot-check pattern parameterized by tenant.

---

Enforcing Isolation: Row-Level Security

A WHERE TenantId = @tenantId clause is a convention; row-level security (RLS) makes it a guarantee. With RLS, the database itself filters every query — including ad-hoc queries, reporting tools, and that one stored procedure someone wrote at 2 AM without the tenant predicate:

-- RLS: the database enforces tenant isolation, not application discipline
CREATE SCHEMA Security;
GO
CREATE FUNCTION Security.fn_TenantAccessPredicate(@TenantId INT)
RETURNS TABLE
WITH SCHEMABINDING
AS RETURN SELECT 1 AS AccessResult
           WHERE @TenantId = CAST(SESSION_CONTEXT(N'TenantId') AS INT)
              OR IS_MEMBER('db_owner') = 1;
GO
CREATE SECURITY POLICY Security.TenantFilter
ADD FILTER PREDICATE Security.fn_TenantAccessPredicate(TenantId)
    ON dbo.TenantChunks,
ADD BLOCK PREDICATE Security.fn_TenantAccessPredicate(TenantId)
    ON dbo.TenantChunks AFTER INSERT;
GO
-- Application sets the tenant once per session/pooled connection reset
EXEC sp_set_session_context @key = N'TenantId', @value = 101;

Two operational notes. First, SESSION_CONTEXT must be set whenever a pooled connection is reused for a different tenant — reset it on connection checkout or set it at the start of every retrieval procedure; a stale tenant context is a data leak. Second, the security predicate composes with vector queries transparently: the optimizer applies it as part of the plan, so VECTOR_SEARCH results joined back to the secured table are filtered before they reach the caller. Test this explicitly — write a test that sets a tenant context and asserts zero rows from other tenants leak through the full retrieval procedure, not just the base table.

Pattern 2: Schema per Tenant

When tenants need stronger isolation — per-tenant backup/restore, per-tenant index maintenance windows, or regulatory boundaries that shared tables cannot satisfy — schema-per-tenant gives each tenant their own set of tables (tenant_101.RagChunks, tenant_102.RagChunks) inside one database. Each tenant gets their own DiskANN vector index, which eliminates the filtered-ANN recall concern entirely: every index is single-tenant by construction.

The cost is operational multiplicity: schema migrations must roll across every tenant schema (script it — never hand-apply), and the preview vector index's drop-and-recreate refresh cycle now runs per tenant. This pattern fits tens to low hundreds of tenants with meaningful per-tenant data volumes. Past that, the migration fan-out becomes the dominant operational burden.

---

Pattern 3: Database per Tenant (with Elastic Pools)

Database-per-tenant is the strongest isolation SQL Server offers short of separate instances: per-tenant backups, per-tenant restores, per-tenant performance tuning, and a blast radius limited to one tenant when something goes wrong. Each database holds its own vector tables and its own DiskANN index — the cleanest possible vector story, since every index is single-tenant and sized to that tenant's corpus.

On Azure SQL Database, elastic pools make this economically sane: hundreds of tenant databases share a pool of DTUs or vCores, with per-database min/max limits preventing noisy-neighbor starvation. The tradeoff is management surface — provisioning, connection routing (a tenant-to-database catalog), and cross-tenant schema upgrades across hundreds of databases demand automation from day one. This is the pattern for SaaS products where tenants pay enough to justify per-tenant infrastructure and where compliance requires hard boundaries.

---

Pattern 4: Separate Instances (Rare, and Usually Wrong)

Instance-per-tenant — separate SQL Server instances or separate managed servers per tenant — appears in RFP responses more often than in sensible architectures. It gives absolute noisy-neighbor isolation at the cost of multiplying every operational burden by the tenant count: patching, monitoring, backups, and licensing. Reserve it for the handful of tenants whose contracts genuinely demand dedicated infrastructure, and run everyone else on one of the first three patterns.

Noisy Neighbors and Resource Governance

In pooled and schema-per-tenant patterns, tenants share compute, and vector workloads are disproportionately capable of hogging it — a single tenant's million-vector backfill or a burst of concurrent similarity searches can saturate CPU and evict other tenants' hot pages from the buffer pool. Two controls keep the peace. On-premises, Resource Governor with per-tenant workload groups (classified by login or session context) caps CPU and memory grants per tenant. On Azure SQL Database elastic pools, per-database max vCore/DTU settings provide the same isolation with less configuration. Either way, the principle is the same: decide the noisy-neighbor policy before the first incident, not during it.

Monitor per-tenant vector health with the same queries you use globally, parameterized by tenant: un-embedded backlog per tenant (Chapter 8's query with a TenantId group-by), recall spot-checks per tenant for filtered ANN search, and query-store wait statistics broken out by tenant context. Tenancy problems announce themselves in per-tenant metrics long before they show up in global ones.

---

Key Takeaways

  • → Pooled tenancy (TenantId on every vector row) is the default: cheapest to operate, instant onboarding, perfect for exact search — but watch filtered-ANN recall for tiny tenants in huge shared indexes and over-fetch TOP_N to compensate.
  • → Row-level security turns tenant filtering from application convention into database guarantee — set SESSION_CONTEXT on every pooled connection checkout and test the full retrieval procedure for cross-tenant leaks, not just the base table.
  • → Schema-per-tenant gives each tenant their own DiskANN index (no filtered-search recall concerns) at the cost of migration fan-out; database-per-tenant on elastic pools gives hard boundaries and per-tenant backup/restore for SaaS scale.
  • → Govern the noisy neighbor before the first incident: Resource Governor workload groups on-premises, per-database caps in elastic pools — vector workloads are disproportionately capable of hogging shared CPU and buffer pool.
  • → Monitor tenancy in per-tenant metrics — embedding backlog, recall spot-checks, and Query Store waits broken out by tenant — because tenancy problems show up there long before they move global dashboards.
