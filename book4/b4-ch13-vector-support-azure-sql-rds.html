Chapter 13: Vector Support on Azure SQL and RDS for SQL Server

Native vectors are not just an on-premises story. The same VECTOR type and VECTOR_DISTANCE function run on Azure SQL Database and Azure SQL Managed Instance — generally available, in all regions — and on Amazon RDS for SQL Server wherever the 17.x engine is deployed. The T-SQL you write is identical across all of them, which is the real headline: develop once, deploy wherever your data lives. What differs is everything around the T-SQL — provisioning, scaling, backups, network integration with embedding APIs, and the managed-service constraints that shape production designs. This chapter maps vector support across the three major managed platforms and gives you a deployment checklist for each.

---

Azure SQL Database: Vectors Without an Upgrade Project

Azure SQL Database is the fastest path to production vectors for most teams: native vector type and functions are generally available, so there is no upgrade project, no patching window, and no capacity planning for the engine itself. Provision a database, create your tables, and the Chapter 7 through 12 patterns work unchanged.

Three Azure-specific considerations shape the design. First, service tier sizing is memory sizing. Vector workloads are memory-hungry (~6 KB per 1536-dimension vector plus DiskANN graph overhead), and in Azure SQL Database memory scales with the service tier. A General Purpose database that comfortably serves an OLTP workload can feel cramped once a few million vectors land in the buffer pool. Start on Hyperscale or a generously sized General Purpose tier for vector workloads, and watch buffer-pool residency before blaming query plans for slow retrieval.

Second, elastic pools are the multi-tenant answer. The database-per-tenant pattern from Chapter 12 maps directly onto elastic pools: hundreds of tenant databases share pooled vCores with per-database min/max caps for noisy-neighbor control. Each tenant database holds its own vector tables and DiskANN index — single-tenant indexes with no filtered-search recall concerns, at a cost structure that makes sense per tenant.

Third, embedding generation integrates natively. Azure SQL Database can call Azure OpenAI directly through sp_invoke_external_rest_endpoint, keeping the embedding pipeline inside the data platform for backfills and low-volume ingestion. For production scale, pair the database with Azure Functions or Container Apps that batch embedding requests and bulk-load vectors — the same staged pattern from Chapter 8, with the staging table living in the same logical server.

The approximate vector index and VECTOR_SEARCH are in preview on Azure SQL Database, same as on-premises — design with the drop-and-recreate refresh cycle in mind, and keep exact VECTOR_DISTANCE search as the production path until the preview graduates.

---

Azure SQL Managed Instance: Near-Parity with On-Premises

Azure SQL Managed Instance gives you native vector support (GA for the type and functions) inside an instance-scoped managed service — the closest cloud analog to the on-premises SQL Server this book assumes elsewhere. If your vector architecture uses instance-level features — SQL Server Agent jobs for embedding backfills, cross-database queries, linked servers to data sources — Managed Instance preserves them, where single-database Azure SQL Database would force a redesign.

The practical guidance: choose Managed Instance when you are lifting an existing on-premises vector workload (or an on-premises estate that will grow vectors) with minimal refactoring. Choose single-database Azure SQL Database when you are building cloud-native from scratch and want the simplest operational surface. The vector T-SQL is identical; the decision is about everything around it.

---

Amazon RDS for SQL Server: Vectors Follow the Engine

Amazon RDS for SQL Server supports SQL Server 2025 (17.x), and native vector capabilities follow the engine version — where the 17.x engine runs, the VECTOR type and VECTOR_DISTANCE function are available. The T-SQL from earlier chapters ports directly. What changes are the RDS operational realities that every RDS DBA already knows:

  • → No sysadmin, no SQL Agent in the traditional sense. Embedding backfill jobs run through RDS's managed job mechanisms or — more commonly — through external schedulers (EventBridge + Lambda, or an EC2-hosted scheduler) that connect over the RDS endpoint. Design the ingestion pipeline as an external process from the start rather than assuming in-engine scheduling.
  • → Backups are RDS snapshots. Automated RDS backups capture the whole instance via storage snapshots — your vector columns ride along with everything else, which is exactly the single-system backup story that makes native vectors attractive. Point-in-time restore works the same for vector tables as for OLTP tables. Test restore of a vector database specifically: restore time scales with total data size, and multi-GB vector columns make databases bigger than their row counts suggest.
  • → Instance sizing is fixed at provisioning. Unlike Azure SQL Database's fluid scaling, RDS instance classes are chosen up front (with modification downtime for changes). Size for the vector working set — memory for hot vectors plus DiskANN overhead — at provisioning time, not after the first slow Monday morning.
  • → Multi-AZ for availability. RDS Multi-AZ deployments (via Always On availability groups) replicate vector tables like any other data — no special handling needed, but failover testing should include a vector retrieval workload to confirm the secondary serves similarity queries at expected latency after failover.
  • → Embedding API calls go through your VPC. Whether you generate embeddings from an external pipeline or via in-engine REST calls, the traffic to OpenAI or Bedrock-hosted models traverses your VPC networking — plan security groups, NAT, and PrivateLink the way you would for any external dependency, and keep API keys in Secrets Manager, never in stored procedures.

    Deployment Checklist: Same T-SQL, Different Surroundings

    Whichever managed platform you choose, run through this checklist before declaring the vector workload production-ready:

  • → Confirm engine version and feature maturity. Verify 17.x (or the Azure SQL equivalent) and decide explicitly which features are GA-backed versus preview-backed in your architecture. Document the decision — preview features need a re-evaluation trigger, not just hope.
  • → Size memory for vectors, not just rows. Estimate total vector bytes (dimensions × 4 bytes × row count × 1.3 for overhead), add the working-set fraction you need resident, and provision the tier/instance class accordingly. Revisit after the first month of production telemetry.
  • → Wire up the embedding pipeline's identity. Managed identity (Azure) or IAM roles (AWS) for the pipeline's access to both the database and the embedding API — no connection strings with passwords in application config, no API keys in source control.
  • → Test backup and restore with vectors. Measure restore time for the actual data volume, verify vector queries return correct results post-restore, and confirm the restore SLA still holds with vector columns included.
  • → Enable Query Store from day one. Managed platforms give you less access to the OS-level telemetry you might lean on premises-side; Query Store plus the platform's monitoring (Azure Monitor, CloudWatch/RDS Performance Insights) is your performance record. Vector plan regressions are exactly what you want caught automatically.
  • → Load-test the refresh cycle. If you use the DiskANN preview index, rehearse the drop-rebuild-swap cycle at production data volume in a non-production environment first — build duration, not just query latency, is part of the SLA.

    Key Takeaways

  • → The vector T-SQL is identical across SQL Server 2025, Azure SQL Database, Azure SQL Managed Instance, and RDS for SQL Server 17.x — native VECTOR type and VECTOR_DISTANCE are GA on Azure SQL; the DiskANN index and VECTOR_SEARCH remain preview everywhere.
  • → On Azure SQL Database, size the service tier for vector memory, use elastic pools for database-per-tenant architectures, and prefer external batched pipelines (Functions/Container Apps) over row-by-row in-engine embedding calls at scale.
  • → On RDS for SQL Server, vectors follow the 17.x engine: plan for external job scheduling, snapshot-based backups (test restore time with vector data volumes), up-front instance sizing for the vector working set, and VPC-plumbed embedding API access with Secrets Manager.
  • → Run the deployment checklist on every platform: confirm feature maturity explicitly, size memory for vectors, wire managed identities, test backup/restore with real vector volumes, enable Query Store day one, and rehearse the preview index refresh cycle at production scale.
