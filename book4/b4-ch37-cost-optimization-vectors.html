Chapter 37: Cost Optimization: Dimensionality Reduction and Quantization

Storage and query costs in vector databases grow linearly with two variables: the number of vectors and the size of each vector. A production RAG system ingesting documents at scale can easily accumulate tens of millions of 1536-dimensional float32 vectors — roughly 90 GB of raw embedding data before any indexing overhead. This chapter covers the two primary techniques for controlling that growth without sacrificing retrieval quality: dimensionality reduction, which shrinks the number of dimensions per vector, and quantization, which shrinks the number of bits per dimension. Both approaches trade a small, measurable amount of recall for significant savings in storage, memory, and query latency. Understanding exactly where those tradeoffs land — and how to measure them — is the engineering work this chapter addresses.

---

The Cost Structure of Vector Storage

Before optimizing anything, understand what you're paying for. Vector databases carry costs along four axes that compound each other.

Raw storage is the floor. A float32 value occupies 4 bytes. A 1536-dimensional OpenAI text-embedding-3-small vector is 6,144 bytes (6 KB) per document. At 10 million documents, that's 58 GB before indexes. Switch to text-embedding-3-large at 3072 dimensions and you're at 117 GB. Pinecone, Weaviate, and Qdrant all charge for storage either directly or through node sizing, so this matters immediately.

Index memory multiplies the base storage. HNSW indexes — the most common structure across all major vector databases — maintain neighbor graphs that consume roughly 1.5× to 4× the raw vector memory depending on the M parameter (graph connectivity). A 58 GB float32 dataset can easily require 200+ GB of RAM to serve with HNSW at reasonable recall.

Query throughput cost ties to memory pressure. When working sets don't fit in RAM, queries hit disk, and latency spikes from single-digit milliseconds to hundreds. Cloud providers size instances to fit vector indexes in memory, so every unnecessary byte in your vectors translates directly to a larger, more expensive instance.

Embedding API costs sit upstream. OpenAI charges per token for embedding generation. If you're re-embedding during pipeline changes or re-indexing after dimension changes, those API calls add up fast.

The table below shows approximate storage requirements for common embedding models at 10 million vectors:

| Model | Dimensions | float32 Storage | int8 Storage | Binary Storage |

|---|---|---|---|---|

| text-embedding-3-small | 1536 | 58 GB | 14.6 GB | 1.8 GB |

| text-embedding-3-large | 3072 | 117 GB | 29.3 GB | 3.7 GB |

| text-embedding-ada-002 | 1536 | 58 GB | 14.6 GB | 1.8 GB |

| all-MiniLM-L6-v2 | 384 | 14.6 GB | 3.7 GB | 0.46 GB |

| Cohere embed-english-v3.0 | 1024 | 39 GB | 9.8 GB | 1.2 GB |

The binary column is not a typo. That's the endgame of quantization: 1 bit per dimension instead of 32.

Dimensionality Reduction: PCA, Matryoshka, and Native Truncation

Dimensionality reduction eliminates dimensions from vectors, either by training a projection (PCA) or by using embedding models designed to work well at reduced sizes.

PCA-based reduction is the classical approach. You collect a representative sample of your vectors, fit a PCA transformation matrix, and project all vectors into a lower-dimensional space that preserves maximum variance. The projection matrix must be stored and applied to every new query vector at search time — this is the runtime cost of PCA.

# Python
import numpy as np
from sklearn.decomposition import PCA
from sklearn.preprocessing import normalize
import pickle

def fit_pca_reducer(sample_vectors: np.ndarray, target_dims: int) -> PCA:
    """
    Fit a PCA reducer on a sample of your corpus vectors.
    sample_vectors: shape (n_samples, original_dims)
    target_dims: number of dimensions to keep
    """
    pca = PCA(n_components=target_dims, random_state=42)
    pca.fit(sample_vectors)
    
    explained = pca.explained_variance_ratio_.sum()
    print(f"Explained variance with {target_dims} dims: {explained:.3f}")
    
    return pca

def reduce_and_normalize(vectors: np.ndarray, pca: PCA) -> np.ndarray:
    """
    Project and L2-normalize. Normalization is required after PCA
    if you use cosine similarity for search.
    """
    reduced = pca.transform(vectors)
    return normalize(reduced, norm='l2')

# Workflow: sample 100k vectors from your corpus
# (representative spread — don't use only recent documents)
sample = np.load("corpus_sample_100k.npy")   # shape (100000, 1536)

pca = fit_pca_reducer(sample, target_dims=512)

# Save projection matrix for query-time use
with open("pca_reducer_1536_to_512.pkl", "wb") as f:
    pickle.dump(pca, f)

# Process your full corpus in batches
def process_batch(raw_batch: np.ndarray, pca: PCA) -> np.ndarray:
    return reduce_and_normalize(raw_batch, pca)

# Check how many dimensions you actually need
for dims in [128, 256, 512, 768, 1024]:
    test_pca = PCA(n_components=dims, random_state=42)
    test_pca.fit(sample)
    variance = test_pca.explained_variance_ratio_.sum()
    print(f"  {dims} dims → {variance:.4f} explained variance ({variance*100:.1f}%)")

Running this on text-embedding-3-small vectors typically yields 95%+ explained variance at 512 dimensions. The problem is that explained variance doesn't directly map to recall — you need to measure recall separately, which means running benchmark queries before committing to a target dimension count.

Matryoshka Representation Learning (MRL) changes the game. OpenAI's newer models (text-embedding-3-small, text-embedding-3-large) and Cohere's v3 models are trained with MRL, meaning the first N dimensions of the full vector are themselves a valid, high-quality embedding. You can truncate rather than project. No projection matrix required, no transformation at query time, and the quality at reduced dimensions is better than PCA because the model was explicitly trained for it.

# Python
from openai import OpenAI
import numpy as np

client = OpenAI()

def embed_with_truncation(
    texts: list[str],
    model: str = "text-embedding-3-small",
    dimensions: int = 512   # native truncation — MRL models only
) -> np.ndarray:
    """
    OpenAI supports native dimension truncation via the `dimensions` parameter.
    Valid only for text-embedding-3-* models.
    """
    response = client.embeddings.create(
        model=model,
        input=texts,
        dimensions=dimensions   # API truncates and re-normalizes for you
    )
    return np.array([item.embedding for item in response.data])

# Compare quality across dimension counts
test_queries = [
    "database indexing strategies",
    "vector similarity search performance",
    "cost optimization for embeddings"
]

for dims in [256, 512, 768, 1536]:
    embeddings = embed_with_truncation(test_queries, dimensions=dims)
    print(f"dims={dims}: shape={embeddings.shape}, "
          f"norm={np.linalg.norm(embeddings[0]):.4f}")

# For text-embedding-3-large: max 3072, usable at 256, 512, 1024, 3072
# OpenAI's benchmarks show 512-dim 3-small outperforms 1536-dim ada-002
# on MTEB — smaller is sometimes better when MRL-trained

The operational advantage here is significant: you can change your target dimension count by updating the API parameter and re-indexing, with no separate transformation pipeline to maintain.

Choosing a target dimension is an empirical question. The practical process:

1. Generate embeddings at your target dimension and at full dimension for a held-out query set (minimum 500 queries with known relevant documents).

2. Run nearest-neighbor retrieval at both sizes with identical HNSW parameters.

3. Compute Recall@10 at both sizes.

4. Accept the reduction if recall drop is under 3–5% for your use case.

For most RAG applications using MRL-trained models, 512 dimensions achieves recall within 2% of 1536 while cutting storage and index memory by two thirds.

Scalar Quantization: float32 to int8

Quantization reduces the number of bits per dimension. Scalar quantization maps each float32 value to an integer within a fixed range — typically int8 (256 levels) or even uint8. The loss in precision is real but bounded, and the memory savings are immediate: 4 bytes becomes 1 byte per dimension, a 4× reduction.

The math is straightforward. For a vector where values span [-1.0, 1.0], each float32 is mapped to an int8 using:

quantized = round(float_value × 127)
dequantized = quantized / 127

Most vector databases handle this transparently. Qdrant's scalar quantization is production-grade and simple to configure:

# Python
from qdrant_client import QdrantClient
from qdrant_client.models import (
    VectorParams, Distance,
    ScalarQuantizationConfig, ScalarType,
    QuantizationSearchParams
)

client = QdrantClient(url="http://localhost:6333")

# Create collection with int8 scalar quantization
client.create_collection(
    collection_name="documents_sq",
    vectors_config=VectorParams(
        size=1536,
        distance=Distance.COSINE
    ),
    quantization_config=ScalarQuantizationConfig(
        type=ScalarType.INT8,
        quantile=0.99,      # clip outliers: 99th percentile maps to max int8
        always_ram=True     # keep quantized index in RAM, fetch originals from disk
    )
)

# always_ram=True is the key production setting:
# - Search uses quantized (1-byte) vectors for fast candidate selection
# - Top candidates are re-scored with original float32 vectors
# - Original vectors can live on disk (SSD), quantized in RAM
# This is "quantization with rescoring" — near full recall at fraction of memory

# Search with rescoring enabled (default when quantization is configured)
results = client.search(
    collection_name="documents_sq",
    query_vector=[0.1] * 1536,   # your actual query embedding here
    limit=10,
    search_params=QuantizationSearchParams(
        ignore=False,           # use quantization for initial search
        rescore=True,           # rescore top candidates with originals
        oversampling=2.0        # fetch 20 candidates, rescore to return 10
    )
)

# oversampling controls the recall/speed tradeoff:
# 1.0 → fastest, lowest recall
# 3.0 → slower, highest recall (approaches float32 quality)
# 2.0 is the practical default for most production use cases

print(f"Retrieved {len(results)} results")
for r in results:
    print(f"  id={r.id}, score={r.score:.4f}")

Quantization on SQL Server. The native VECTOR type in SQL Server 2025 stores float32 — there is no built-in float16 or binary-quantized column type. Your compression levers are (a) storing fewer dimensions via MRL truncation (Section 37.2), (b) quantizing at the application layer before insert, and (c) the two-phase pattern: a compact representation for candidate selection, full float32 for rescoring.

-- SQL Server 2025: two-phase pattern — compact candidates, exact rescore
-- Phase 1 storage: truncated 512-dim vectors in a smaller VECTOR column
CREATE TABLE dbo.DocumentsCompact (
    ChunkId   BIGINT IDENTITY(1,1) NOT NULL
        CONSTRAINT PK_DocumentsCompact PRIMARY KEY,
    ChunkText NVARCHAR(MAX) NOT NULL,
    Emb512    VECTOR(512) NOT NULL   -- 512 x 4 bytes = 2 KB vs 6 KB for 1536
);
CREATE VECTOR INDEX IX_DocCompact_Emb512
    ON dbo.DocumentsCompact (Emb512)
    WITH (METRIC = 'cosine', TYPE = 'DiskANN', MAXDOP = 4);
-- Phase 2: full 1536-dim vectors for exact rescoring of the candidates
CREATE TABLE dbo.DocumentsFull (
    ChunkId   BIGINT NOT NULL
        CONSTRAINT PK_DocumentsFull PRIMARY KEY,
    EmbFull   VECTOR(1536) NOT NULL
);
GO
-- Two-phase search: DiskANN over compact vectors, exact rescore over full
DECLARE @q512  VECTOR(512)  = '[0.1, ...]';   -- truncated query embedding
DECLARE @qfull VECTOR(1536) = '[0.1, ...]';   -- full query embedding
WITH CompactCandidates AS (
    SELECT TOP (100) ChunkId,
           VECTOR_DISTANCE('cosine', Emb512, @q512) AS approx_dist
    FROM dbo.DocumentsCompact
    ORDER BY approx_dist
)
SELECT TOP (10) c.ChunkId,
       VECTOR_DISTANCE('cosine', f.EmbFull, @qfull) AS exact_dist
FROM CompactCandidates AS c
JOIN dbo.DocumentsFull AS f ON f.ChunkId = c.ChunkId
ORDER BY exact_dist;
-- 3x storage reduction on the indexed column, recall within 1-3% of full
-- float32 search when validated on your eval set (Section 37.5).

The two-phase pattern — coarse binary search, exact float32 reranking — is the same pattern Qdrant calls "rescoring." It's the standard production approach for binary quantization and delivers recall within 1–3% of full float32 search at a fraction of the memory cost.

Product Quantization and Vector Database Native Support

Product quantization (PQ) goes further than scalar quantization by dividing each high-dimensional vector into subvectors and quantizing each subvector against a learned codebook. The result is a compact code — often 8–32 bytes for a 1536-dimensional vector — that approximates the original with reasonable accuracy.

PQ is more complex than scalar quantization: it requires a training phase to build codebooks, and the codebooks must be stored and used at query time. The payoff is compression ratios of 32× to 96× with recall that holds up better than naive binary quantization for unoptimized models.

Faiss, the underlying library in many vector databases, exposes PQ directly. Weaviate and Milvus expose it through their configuration APIs:

# Python — Milvus PQ configuration via pymilvus
from pymilvus import (
    connections, FieldSchema, CollectionSchema,
    DataType, Collection, utility
)

connections.connect(host="localhost", port="19530")

fields = [
    FieldSchema(name="id", dtype=DataType.INT64, is_primary=True, auto_id=True),
    FieldSchema(name="text", dtype=DataType.VARCHAR, max_length=4096),
    FieldSchema(name="embedding", dtype=DataType.FLOAT_VECTOR, dim=1536)
]

schema = CollectionSchema(fields=fields, description="PQ quantized documents")
collection = Collection(name="documents_pq", schema=schema)

# IVF_PQ index: inverted file + product quantization
# This is the standard high-compression option in Milvus/Faiss
index_params = {
    "metric_type": "IP",          # inner product (use normalized vectors for cosine)
    "index_type": "IVF_PQ",
    "params": {
        "nlist": 1024,            # number of IVF clusters (scale with sqrt(n_vectors))
        "m": 16,                  # number of subvectors (must divide dim evenly: 1536/16=96)
        "nbits": 8                # bits per subvector code (8 = 256 centroids per subquantizer)
    }
}
# Memory per vector: m * (nbits/8) bytes = 16 * 1 = 16 bytes vs 6144 bytes float32
# Compression ratio: 384x

collection.create_index(field_name="embedding", index_params=index_params)
collection.load()

# Search — nprobe controls how many IVF clusters to check
# More clusters → higher recall, higher latency
search_params = {
    "metric_type": "IP",
    "params": {"nprobe": 64}    # check 64 of 1024 clusters; 6.25% of index
}

results = collection.search(
    data=[[0.1] * 1536],        # query embedding (normalized)
    anns_field="embedding",
    param=search_params,
    limit=10,
    output_fields=["text"]
)

for hits in results:
    for hit in hits:
        print(f"id={hit.id}, score={hit.score:.4f}, text={hit.entity.get('text')[:80]}")

# PQ recall benchmarking guide:
# nprobe=10  → ~85% recall@10, fastest
# nprobe=64  → ~93% recall@10, good default
# nprobe=256 → ~97% recall@10, slowest (approaching brute force)
# Tune nprobe to hit your latency SLA, then evaluate recall

Weaviate exposes its own PQ interface through its schema configuration, which is worth knowing if you're running Weaviate in production:

# Python — Weaviate PQ configuration via weaviate-client v4
import weaviate
from weaviate.classes.config import (
    Configure, Property, DataType, VectorDistances
)

client = weaviate.connect_to_local()

# Create collection with PQ enabled
client.collections.create(
    name="DocumentsPQ",
    vectorizer_config=Configure.Vectorizer.none(),   # bring your own vectors
    vector_index_config=Configure.VectorIndex.hnsw(
        distance_metric=VectorDistances.COSINE,
        quantizer=Configure.VectorIndex.Quantizer.pq(
            training_limit=100_000,   # vectors needed before PQ kicks in
            segments=96,              # 1536 dims / 96 segments = 16 dims per segment
            centroids=256             # 2^8 centroids (8-bit codes)
        )
    ),
    properties=[
        Property(name="content", data_type=DataType.TEXT),
        Property(name="source", data_type=DataType.TEXT)
    ]
)

# Weaviate trains PQ automatically once training_limit vectors are loaded
# Before training_limit: stores float32 flat (temporary, high memory)
# After training_limit: compresses existing vectors + new vectors

# For production: pre-populate with training_limit vectors before going live
# Or set a lower training_limit if your corpus starts small

client.close()

The practical PQ tradeoff: you're trading recall and query-time CPU for memory. PQ requires decoding compact codes during distance computation, which is CPU-intensive. On modern hardware with SIMD support, Faiss makes this fast — but it's not free. Benchmark both latency and recall before committing.

Measuring the Tradeoffs: A Recall Benchmarking Framework

Every compression decision requires recall validation. "Recall@K" measures what fraction of the true top-K nearest neighbors you retrieve when using an approximate or compressed index. This is your primary metric.

# Python
import numpy as np
from typing import Callable
import time

def compute_recall_at_k(
    queries: np.ndarray,
    corpus: np.ndarray,
    search_fn: Callable,    # function: query_vector -> list of retrieved IDs
    k: int = 10,
    batch_size: int = 100
) -> dict:
    """
    Computes Recall@K by comparing approximate search results
    against brute-force exact neighbors.
    
    queries:    shape (n_queries, dims)
    corpus:     shape (n_corpus, dims) — the indexed vectors
    search_fn:  your vector DB search call, returns list of IDs
    """
    
    # Ground truth: exact brute-force neighbors
    # For large corpora, compute this once and cache it
    print("Computing ground truth (brute force)...")
    ground_truth = []
    
    # Batch to avoid OOM on large corpora
    for q_start in range(0, len(queries), batch_size):
        q_batch = queries[q_start:q_start + batch_size]
        
        # Cosine similarity via dot product (assumes normalized vectors)
        similarities = q_batch @ corpus.T         # (batch, n_corpus)
        top_k_indices = np.argsort(-similarities, axis=1)[:, :k]
        ground_truth.extend(top_k_indices.tolist())
    
    # Approximate search with the system under test
    print("Running approximate search...")
    retrieved = []
    latencies = []
    
    for i, query in enumerate(queries):
        start = time.perf_counter()
        result_ids = search_fn(query)
        elapsed = time.perf_counter() - start
        latencies.append(elapsed * 1000)   # ms
        retrieved.append(result_ids[:k])
    
    # Recall@K: what fraction of ground truth top-K did we find?
    recall_scores = []
    for true_ids, ret_ids in zip(ground_truth, retrieved):
        true_set = set(true_ids)
        ret_set = set(ret_ids)
        recall = len(true_set & ret_set) / len(true_set)
        recall_scores.append(recall)
    
    return {
        "recall_at_k": np.mean(recall_scores),
        "recall_p50": np.percentile(recall_scores, 50),
        "recall_p10": np.percentile(recall_scores, 10),   # worst queries
        "latency_p50_ms": np.percentile(latencies, 50),
        "latency_p95_ms": np.percentile(latencies, 95),
        "latency_p99_ms": np.percentile(latencies, 99),
        "k": k
    }

# Example: compare float32 vs int8 quantized search in Qdrant

The P10 recall column — the 10th percentile recall across your query set — is more informative than the mean. A mean recall of 0.95 can hide specific query categories that consistently miss. Those outliers often correspond to semantically sparse topics, short queries, or domain-specific vocabulary your embedding model handles poorly. Investigate them.

What to do when recall is too low:

  • → Increase `oversampling` (Qdrant) or `nprobe` (Milvus/Faiss) — the fastest fix
  • → Increase `ef` at query time on HNSW indexes — trades latency for recall
  • → Switch from binary to int8 quantization — better recall at more memory cost
  • → Use a higher-quality embedding model — more information preserved at same dimensions
  • → Increase target dimensions if using MRL truncation — recall usually improves monotonically

    Combining Both Techniques: Dimension Reduction + Quantization

    The highest compression ratios come from stacking both techniques: reduce dimensions first, then quantize. The order matters — quantize the reduced vectors, not the original ones.

    Follow the numbers down: the Full Vector (blue, 1,536-dim float32, 6,144 bytes) is Truncated to 512 dimensions (teal, 2,048 bytes — Matryoshka truncation keeps the important dimensions), then Quantized to int8 (green, 512 bytes in RAM). That tiny int8 copy is what the ANN Search (purple) actually scans — twelve times less memory per vector. The full-precision vectors stay on disk for Disk Rescore (gray): ANN proposes candidates cheaply, rescoring orders them accurately, and the merged result is the final Top-K Results (green). The pattern: search cheap, rescore dear.

    *Dimension reduction happens first, then quantization compresses the already-reduced vector — reducing the original would discard information the truncation already preserved.*

    # Python — Combined pipeline: MRL truncation + int8 in Qdrant

from openai import OpenAI
from qdrant_client import QdrantClient
from qdrant_client.models import (
    VectorParams, Distance,
    ScalarQuantizationConfig, ScalarType,
    QuantizationSearchParams, PointStruct
)
import numpy as np
import uuid

openai_client = OpenAI()
qdrant = QdrantClient(url="http://localhost:6333")

TARGET_DIMS = 512    # MRL truncation: 1536 → 512 (3.3× smaller)
# Combined with int8: 512 × 1 byte = 512 bytes vs 1536 × 4 = 6144 bytes → 12× smaller

# Create the collection: 512-dim vectors with int8 quantization
qdrant.recreate_collection(
    collection_name="documents_optimized",
    vectors_config=VectorParams(
        size=TARGET_DIMS,
        distance=Distance.COSINE
    ),
    quantization_config=ScalarQuantizationConfig(
        type=ScalarType.INT8,
        quantile=0.99,
        always_ram=True
    )
)

def embed_documents(texts: list[str]) -> np.ndarray:
    """Embed at target dimensions using MRL truncation."""
    response = openai_client.embeddings.create(
        model="text-embedding-3-small",
        input=texts,
        dimensions=TARGET_DIMS
    )
    return np.array([item.embedding for item in response.data])

def ingest_batch(texts: list[str], ids: list[str] = None):
    """Embed and upsert a batch of documents."""
    embeddings = embed_documents(texts)
    
    if ids is None:
        ids = [str(uuid.uuid4()) for _ in texts]
    
    points = [
        PointStruct(
            id=id_,
            vector=embedding.tolist(),
            payload={"text": text}
        )
        for id_, text, embedding in zip(ids, texts, embeddings)
    ]
    
    qdrant.upsert(collection_name="documents_optimized", points=points)
    return ids

def search_optimized(query_text: str, top_k: int = 10) -> list[dict]:
    """
    Embed query at same truncated dimension, search with rescoring.
    """
    query_embedding = embed_documents([query_text])[0]
    
    results = qdrant.search(
        collection_name="documents_optimized",
        query_vector=query_embedding.tolist(),
        limit=top_k,
        search_params=QuantizationSearchParams(
            rescore=True,
            oversampling=2.0
        ),
        with_payload=True
    )
    
    return [
        {"id": r.id, "score": r.score, "text": r.payload.get("text", "")}
        for r in results
    ]

# Storage math for this configuration:
# Original: 1536 dims × 4 bytes = 6,144 bytes per vector
# Optimized: 512 dims × 1 byte  =   512 bytes per vector (quantized in RAM)
# + 512 dims × 4 bytes = 2,048 bytes on disk for rescoring originals
# RAM savings: 12× for the hot index; disk holds originals at 3×

    A practical comparison across compression strategies for 10 million vectors:

    | Strategy | RAM (index only) | Disk | Recall@10 | Query Latency |

    |---|---|---|---|---|

    | float32, 1536 dims | ~200 GB | 58 GB | 0.99 | baseline |

    | float32, 512 dims (MRL) | ~67 GB | 19 GB | 0.97 | faster |

    | int8, 1536 dims + rescore | ~50 GB | 58 GB | 0.97 | similar |

    | int8, 512 dims + rescore | ~17 GB | 19 GB | 0.95 | faster |

    | binary, 1536 dims + rescore | ~6 GB | 58 GB | 0.93 | fastest search |

    | binary, 512 dims + rescore | ~2 GB | 19 GB | 0.90 | fastest overall |

    The int8 + 512 dims row represents the practical optimum for most production RAG systems: it cuts RAM by more than 10× versus full float32 HNSW, preserves 95% recall with rescoring, and keeps query latency low. Binary quantization pushes further but requires more careful recall validation — acceptable for some use cases, not for others.

    SQL Server Optimization Workflow

    For teams running vector search inside SQL Server 2025 via native VECTOR and DiskANN, the optimization path uses the same principles as managed vector databases but expressed in T-SQL and DMVs.

    -- SQL Server 2025 — full optimization workflow

-- Step 1: Baseline — full float32, DiskANN
CREATE TABLE dbo.Documents (
    DocId     INT IDENTITY(1,1) NOT NULL
        CONSTRAINT PK_Documents PRIMARY KEY,
    Content   NVARCHAR(MAX) NOT NULL,
    Source    NVARCHAR(200) NOT NULL,
    Embedding VECTOR(1536) NOT NULL
);
CREATE VECTOR INDEX IX_Documents_Embedding
    ON dbo.Documents (Embedding)
    WITH (METRIC = 'cosine', TYPE = 'DiskANN', MAXDOP = 4);

-- Step 2: Add a truncated-dimension column for 3x storage savings
-- (populate from the application with MRL-truncated 512-dim embeddings)
ALTER TABLE dbo.Documents ADD Embedding512 VECTOR(512) NULL;
GO
-- Backfill in batches in production (UPDATE TOP ... in a loop);
-- single statement shown for clarity:
-- UPDATE dbo.Documents SET Embedding512 = ;
CREATE VECTOR INDEX IX_Documents_Embedding512
    ON dbo.Documents (Embedding512)
    WITH (METRIC = 'cosine', TYPE = 'DiskANN', MAXDOP = 4);
-- Storage: 512 x 4 bytes = 2 KB vs 1536 x 4 = 6 KB per row -> 3x reduction

-- Step 3: Validate recall parity between full and truncated columns
DECLARE @q VECTOR(1536) = '[0.1, ...]';
DECLARE @q512 VECTOR(512) = '[0.1, ...]';
WITH FullResults AS (
    SELECT TOP (20) DocId,
           VECTOR_DISTANCE('cosine', Embedding, @q) AS dist_full
    FROM dbo.Documents ORDER BY dist_full
),
HalfResults AS (
    SELECT TOP (20) DocId,
           VECTOR_DISTANCE('cosine', Embedding512, @q512) AS dist_half
    FROM dbo.Documents ORDER BY dist_half
)
SELECT COALESCE(f.DocId, h.DocId) AS DocId,
       f.dist_full, h.dist_half,
       CASE WHEN f.DocId IS NULL THEN 'only in truncated'
            WHEN h.DocId IS NULL THEN 'only in full'
            ELSE 'in both' END AS status
FROM FullResults AS f
FULL OUTER JOIN HalfResults AS h ON h.DocId = f.DocId
ORDER BY COALESCE(f.dist_full, h.dist_half);

-- Step 4: Measure index sizes via DMVs
SELECT i.name AS IndexName,
       SUM(s.used_page_count) * 8 / 1024 AS IndexMB
FROM sys.indexes AS i
JOIN sys.dm_db_partition_stats AS s
  ON s.object_id = i.object_id AND s.index_id = i.index_id
WHERE i.object_id = OBJECT_ID(N'dbo.Documents')
GROUP BY i.name
ORDER BY IndexMB DESC;

-- Step 5: Tune query-time recall via TOP_N over-fetch
-- DiskANN has no session-level ef_search equivalent; control the
-- recall/latency tradeoff by over-fetching candidates and rescoring:
DECLARE @q2 VECTOR(512) = '[0.1, ...]';
SELECT TOP (10) DocId, exact_dist
FROM (
    SELECT TOP (100) DocId,                     -- over-fetch 10x
           VECTOR_DISTANCE('cosine', Embedding512, @q2) AS exact_dist
    FROM dbo.Documents
) AS candidates
ORDER BY exact_dist;
-- Increase the inner TOP_N for better recall, decrease for lower latency.

    SQL Server 2025 includes a production-grade vector story natively: the VECTOR type, VECTOR_DISTANCE, and DiskANN indexes ship in the engine. For teams standardized on SQL Server, that means vector search lives in the same database as the operational data — one backup story, one security model, one monitoring stack — with Azure AI Search or a sidecar vector database (Qdrant, Weaviate) as the option when you need quantization or scale the in-engine index doesn't cover.

    Operational Checklist: Before You Compress

    Compression decisions are difficult to reverse once data is in production. Run through this checklist before changing your vector storage strategy:

    1. Benchmark with your actual queries, not synthetic ones.

    Random query vectors don't represent the distribution of queries your users send. Use a sample of real production queries or, at minimum, queries from your domain.

    2. Establish a recall floor, not just a recall target.

    Decide in advance: what is the minimum acceptable Recall@10 for your application? If your RAG system fails to retrieve the right context, downstream LLM quality degrades. Set the floor before seeing the numbers, or you'll be tempted to rationalize whatever the benchmark shows.

    3. Test re-indexing time.

    Changing dimensions or quantization type requires re-embedding and re-indexing. For 10 million vectors, this can take hours. Know your re-indexing window before committing to a strategy that might need to change.

    4. Keep originals if you use binary quantization.

    Binary quantization without rescoring loses too much recall for most applications. Rescoring requires access to original float32 vectors. If you compress and discard originals, you lose the ability to rescore.

    5. Stage changes through a shadow index.

    Build the new compressed index in parallel, run your recall benchmark against both indexes simultaneously, and cut over only after validating recall. Never optimize directly on the production index.

    6. Monitor recall in production, not just at launch.

    Query distributions shift over time. A compression strategy that meets your recall floor at launch may degrade as users ask questions about topics not well-represented in your corpus sample. Build a production recall monitor using human-labeled query-document pairs sampled weekly.

    Key Takeaways

  • → **Storage and memory costs scale with both vector count and vector size**: the two primary levers for controlling cost are dimensionality reduction (fewer dimensions) and quantization (fewer bits per dimension), and they can be stacked for compounding savings.
  • → **MRL-trained models (OpenAI text-embedding-3-*, Cohere v3) enable native truncation**: you can reduce from 1536 to 512 dimensions by setting a single API parameter, with better quality than PCA projection because the model was explicitly trained for it.
  • → **Scalar quantization (int8) with rescoring is the lowest-risk compression step**: it delivers 4× memory reduction with recall loss typically under 3%, using the original float32 vectors stored on disk for rescoring top candidates identified by the compressed index.
  • → **The practical production optimum for most RAG systems is 512-dim MRL + int8 quantization**: this combination achieves roughly 12× memory reduction versus full float32 HNSW while preserving approximately 95% Recall@10, and it is straightforward to implement with SQL Server DiskANN (MRL-truncated columns) and Qdrant (native quantization).
  • → **Recall benchmarking must use real queries and must track the P10 recall, not just the mean**: a high average recall can hide systematically poor retrieval on specific query categories, and those failures are the ones that degrade downstream LLM response quality in production.
