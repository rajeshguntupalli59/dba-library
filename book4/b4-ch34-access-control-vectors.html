Chapter 34: Access Control for Vector Data

Why Vector Access Control Is Different

Vector databases introduce a category of access control problems that traditional RBAC models weren't designed to solve. A row in a relational table is discrete and bounded — you can grant SELECT on a specific table, filter rows by tenant ID, and call it done. A vector embedding is a compressed semantic fingerprint of content that may span topics, contain implicit references to sensitive material, or be retrievable through queries that have no obvious surface-level connection to the underlying data. When a similarity search returns the top-k nearest neighbors, you cannot predict at query time which documents will surface. This chapter covers how to apply SQL Server Row-Level Security, namespace isolation, API key scoping, and query-time filtering to vector data across SQL Server native vectors, Pinecone, Weaviate, and Qdrant — and how to build a unified authorization layer that treats vector search as a first-class security boundary.

---

Row-Level Security on SQL Server Vector Tables

SQL Server's Row-Level Security (RLS) applies directly to vector tables: a security policy with a predicate function filters rows before the similarity ranking ever sees them. Every security primitive SQL Server exposes — roles, schemas, column-level grants, views — applies to vector data exactly as it does to relational data.

-- SQL Server 2025: RLS on a vector chunk table
-- 1. Predicate function: which tenant is calling?
CREATE FUNCTION dbo.fn_TenantPredicate(@TenantId INT)
RETURNS TABLE
WITH SCHEMABINDING
AS RETURN SELECT 1 AS AccessGranted
WHERE @TenantId = CAST(SESSION_CONTEXT(N'TenantId') AS INT)
   OR CAST(SESSION_CONTEXT(N'TenantId') AS INT) = 0;  -- 0 = service admin
GO
-- 2. Security policy binding the predicate to the vector table
CREATE SECURITY POLICY dbo.TenantFilterPolicy
ADD FILTER PREDICATE dbo.fn_TenantPredicate(TenantId)
    ON dbo.DocumentChunks,
ADD BLOCK PREDICATE dbo.fn_TenantPredicate(TenantId)
    ON dbo.DocumentChunks AFTER INSERT;
GO
-- 3. Application sets context once per session:
-- EXEC sp_set_session_context 'TenantId', @tenantId;
-- Every vector query below now silently filters to the tenant:
DECLARE @q VECTOR(1536) = '[0.12, 0.87, ...]';
SELECT TOP (10) ChunkId, ChunkText,
       VECTOR_DISTANCE('cosine', Embedding, @q) AS Distance
FROM dbo.DocumentChunks
ORDER BY Distance;
-- No WHERE TenantId needed: the policy injects it. Forget the
-- sp_set_session_context call and the query returns zero rows —
-- fail-closed by design.

A frequent performance pitfall: when RLS adds a TenantId = X predicate to a DiskANN scan, the filter applies after the ANN index returns candidates, not before. If the index returns 200 candidates but only 3 belong to the current tenant, effective recall collapses and you waste I/O on irrelevant rows.

The solution is tenant-aware physical design: partition the chunk table by tenant (partitioned table with one DiskANN index per partition is not supported in preview — so instead maintain separate chunk tables per tenant tier, or over-fetch aggressively with TOP_N and filter in the outer query):

-- SQL Server: tenant-safe ANN retrieval with over-fetch + filter
-- RLS narrows to the tenant; TOP_N over-fetch compensates for
-- post-index filtering so recall survives.
DECLARE @q VECTOR(1536) = '[0.12, 0.87, ...]';
EXEC sp_set_session_context 'TenantId', @tenantId;

SELECT TOP (10) s.ChunkId, c.ChunkText, s.Distance
FROM (
    SELECT TOP (200) ChunkId,
           VECTOR_DISTANCE('cosine', Embedding, @q) AS Distance
    FROM dbo.DocumentChunks          -- RLS predicate applies here
    ORDER BY Distance
) AS s
JOIN dbo.DocumentChunks AS c ON c.ChunkId = s.ChunkId
ORDER BY s.Distance;
-- Rule of thumb: over-fetch 10–20x the final k when a tenant filter
-- follows the ANN scan; measure recall@k per tenant (Chapter 20).

For Azure SQL Database, the same RLS pattern works identically — set the session context from your API's authenticated claims (Microsoft Entra ID) so the tenant flows from login to predicate without application code in between.

Namespace Isolation in Pinecone and Weaviate

Pinecone namespaces partition one index into isolated vector spaces: queries against namespace tenant-42 can never return vectors from tenant-43, because the namespace is part of the storage key. Map one tenant to one namespace and the isolation is structural, not predicate-based — there is no filter to forget.

Weaviate offers the same shape via tenant-aware collections (multi-tenancy feature): each tenant gets isolated shards within a collection, with per-tenant activation so cold tenants consume no memory. Qdrant's payload filtering achieves tenant isolation with a mandatory tenant_id payload filter — effective, but predicate-based, so enforce it in a wrapper client rather than trusting every caller.

The hierarchy of assurance, strongest first: separate indexes per tenant → namespaces/tenant-shards → mandatory metadata filters → RLS predicates. Choose based on tenant count and isolation requirements; a hundred tenants with strict data residency get separate indexes, ten thousand SaaS tenants get namespaces or RLS.

Metadata Filtering as a Security Predicate

Beyond tenant isolation, document-level permissions (this user may see these documents) belong in the retrieval query as metadata predicates. Store the access control list as columns — AllowedRoles, OwnerId, Classification — and apply them in the same query as the similarity ranking:

-- SQL Server: document-level permission predicate in the retrieval query
DECLARE @q VECTOR(1536) = '[0.12, 0.87, ...]';
DECLARE @userRoles NVARCHAR(400) = '|analyst|auditor|';  -- from auth context

SELECT TOP (10) ChunkId, ChunkText,
       VECTOR_DISTANCE('cosine', Embedding, @q) AS Distance
FROM dbo.DocumentChunks
WHERE TenantId = CAST(SESSION_CONTEXT(N'TenantId') AS INT)
  AND (Classification <> 'Restricted'
       OR OwnerId = CAST(SESSION_CONTEXT(N'UserId') AS INT)
       OR EXISTS (SELECT 1 FROM STRING_SPLIT(AllowedRoles, ',') AS r
                  WHERE @userRoles LIKE '%|' + LTRIM(RTRIM(r.value)) + '|%'))
ORDER BY Distance;
-- Permission logic lives in the query, not in post-retrieval application
-- code: a chunk the user may not see is never returned, never embedded
-- in a prompt, never summarized by the LLM.

The critical rule: enforce permissions before retrieval, never after. Filtering the top-k in application code is both a security hole (the LLM already saw the text if you re-rank first) and a quality bug (you return fewer than k results). The predicate belongs in the database query.

API Key Management and Least-Privilege Design

  • → Separate keys per trust boundary. Ingest workers get write-only credentials; the retrieval API gets read-only; humans get nothing — they authenticate through the application. A leaked read-only key cannot poison the index.
  • → Scope managed-service keys. Pinecone API keys should be scoped to the project and rotated on a schedule; store them in Azure Key Vault, not in application configuration.
  • → SQL Server: use contained database users or Entra ID. The retrieval service connects as a low-privilege database user with SELECT on the chunk tables and nothing else — no DDL, no access to the embedding queue or eval tables.
  • → Rotate on a schedule, not on incident. Quarterly rotation with dual-key support (accept N and N+1 during rollover) turns rotation into a routine instead of a fire drill.

    Audit Logging for Vector Queries

    Vector queries need auditing like any data access — which tenant asked what, which chunks were returned, and whether permission predicates were active. Log at the retrieval-procedure boundary, not in the application:

    -- SQL Server: audit log table for vector retrieval
CREATE TABLE dbo.VectorQueryAudit (
    AuditId    BIGINT IDENTITY(1,1) NOT NULL
        CONSTRAINT PK_VectorQueryAudit PRIMARY KEY,
    OccurredAt DATETIME2(0) NOT NULL
        CONSTRAINT DF_VQA_Occurred DEFAULT SYSUTCDATETIME(),
    TenantId   INT NOT NULL,
    UserId     INT NULL,
    Namespace  NVARCHAR(60) NOT NULL,
    TopK       INT NOT NULL,
    ReturnedIds NVARCHAR(MAX) NOT NULL,  -- JSON array of ChunkIds served
    MinDistance FLOAT NULL,              -- top-1 distance: quality signal
    ClientIp   NVARCHAR(45) NULL
);
CREATE INDEX IX_VQA_Tenant_Time ON dbo.VectorQueryAudit (TenantId, OccurredAt);
-- Write one row per retrieval call from the stored procedure that serves
-- vector search. Partition by month; retention per compliance policy.
-- The ReturnedIds JSON lets incident response answer "who saw chunk X?"
-- with a single query.
    # Python — audited retrieval wrapper (pyodbc)
import json, pyodbc

conn = pyodbc.connect("DRIVER={ODBC Driver 18 for SQL Server};"
                      "SERVER=localhost;DATABASE=ragdb;Trusted_Connection=yes;"
                      "Encrypt=yes;TrustServerCertificate=yes")

def audited_retrieve(question_emb, tenant_id, user_id, namespace, top_k=10):
    vec = "[" + ",".join(str(v) for v in question_emb) + "]"
    cur = conn.cursor()
    cur.execute("EXEC sp_set_session_context 'TenantId', ?",
                (tenant_id,))   # RLS context: fail-closed per Section 34.2
    rows = cur.execute("""SELECT TOP (?) ChunkId, ChunkText,
                VECTOR_DISTANCE('cosine', Embedding,
                    CAST(? AS VECTOR(1536))) AS Distance
            FROM dbo.DocumentChunks
            ORDER BY Distance""", (top_k, vec)).fetchall()
    cur.execute("""INSERT INTO dbo.VectorQueryAudit
                       (TenantId, UserId, Namespace, TopK, ReturnedIds,
                        MinDistance)
                   VALUES (?, ?, ?, ?, ?, ?)""",
                (tenant_id, user_id, namespace, top_k,
                 json.dumps([r[0] for r in rows]),
                 rows[0][2] if rows else None))
    conn.commit()
    return rows

    Handling Sensitive Data in Embedding Pipelines

    Embeddings are not anonymized data. A vector preserves enough semantic content that sensitive text can be partially reconstructed, and the chunk text stored alongside it is the original sensitive content in full. Treat the vector store with the same classification as the source documents:

  • → Encrypt at rest and in transit. TDE for the database, TLS for every connection — including the embedding API calls that carry raw text off-network.
  • → Redact before embedding. PII scrubbing belongs in the ingest pipeline, before the embedding call — once PII is embedded and stored, every copy (cache, backup, replica) carries it.
  • → Prefer local embedding models for regulated data. Sentence Transformers on your own infrastructure keeps text in-network; API embedding sends it to a third party under their retention policy.
  • → Backups inherit classification. A backup of the vector database is a backup of the sensitive corpus — same encryption, same access controls, same retention policy (Chapter 36).

    A Unified Authorization Layer

    Production systems rarely use a single vector database. A typical architecture might use SQL Server native vectors for low-latency operational queries, Pinecone for high-scale semantic search, and Weaviate for knowledge graph traversal with vector similarity. Each database has its own access control model. Building authorization logic independently for each creates inconsistency and maintenance burden.

    The unified layer is a policy decision point in front of all of them: one function that maps (user, tenant, roles) to (allowed namespaces, filters, top-k limits), called by every retrieval path regardless of backend:

    # Python — unified authorization layer across vector backends
from dataclasses import dataclass

@dataclass
class AuthzDecision:
    tenant_id: int
    namespace: str        # Pinecone namespace / Weaviate tenant / SQL predicate
    max_top_k: int
    classification_ceiling: str   # highest classification the user may see
    sql_tenant_filter: str        # fragment for SQL Server queries

def authorize(user, backend_name: str) -> AuthzDecision:
    """Single policy decision point. backend_name: "sqlserver" | "pinecone"
    | "qdrant" | "weaviate". Every retrieval path calls this first."""
    tenant_id = user.tenant_id
    roles = set(user.roles)
    ceiling = "Restricted" if "auditor" in roles else "Internal"
    max_k = 50 if "analyst" in roles else 10
    namespace = f"tenant-{tenant_id}" if backend_name == "pinecone" \
        else "default"
    return AuthzDecision(
        tenant_id=tenant_id, namespace=namespace, max_top_k=max_k,
        classification_ceiling=ceiling,
        sql_tenant_filter=f"TenantId = {tenant_id}")
# SQL Server path: sp_set_session_context + RLS (Section 34.2)
# Pinecone path:   namespace=decision.namespace, top_k=min(k, decision.max_top_k)
# Weaviate path:   tenant filter + top_k cap
# One policy, every backend — audit once, at this layer.

    Key Takeaways

  • → SQL Server RLS integrates directly with vector tables via security policies and SESSION_CONTEXT — but ANN index performance degrades when tenant predicates apply post-scan, so over-fetch 10–20x and measure recall@k per tenant.
  • → Enforce permissions before retrieval, never after. Predicates belong in the database query; post-retrieval filtering is a security hole and a quality bug.
  • → Choose isolation strength by tenant reality: separate indexes for strict residency, namespaces/tenant-shards for SaaS scale, RLS predicates where the database is SQL Server.
  • → Audit at the retrieval boundary — tenant, user, returned chunk IDs, top-1 distance — so incident response can answer "who saw chunk X?" with one query.
  • → Treat embeddings as sensitive as source text: redact before embedding, prefer local models for regulated data, and give backups the corpus's classification.
  • → Unify authorization in one policy decision point across backends — one function mapping user to namespaces, filters, and limits, audited once.
