Chapter 26: Caching Embeddings

Why Embeddings Are Unusually Cacheable

Embedding inference is expensive — an API call costs money and 100–300ms, a local model costs GPU time — and it is also perfectly deterministic: the same text through the same model always produces the same vector. Deterministic plus expensive is the textbook definition of cacheable. Unlike most application caches, an embedding cache never goes stale on its own: the vector for a text does not change unless the model changes, so invalidation is a model-versioning problem, not a TTL problem.

Not all text is equally cacheable. Query strings from users cluster heavily around common questions — support tickets, product searches, FAQ lookups. Document chunks in a RAG corpus are almost always worth caching because they are embedded once during ingestion and compared repeatedly at query time. If you are already storing document embeddings in SQL Server native vectors or Pinecone, the document side of the cache is essentially already solved. The query side is where the additional caching layer pays off.

---

Cache Architecture: Where Embeddings Live

Layer 1: In-process LRU cache

Lives in the application process, holds the hottest few thousand question embeddings. Sub-microsecond lookup, zero network. Lost on restart — acceptable, because it refills in minutes under production traffic.

Layer 2: Redis (shared, fast)

Shared across application instances, sub-millisecond latency, survives individual app restarts. The workhorse layer: every question embedding check hits Redis before it hits an API or GPU.

Layer 3: Persistent database cache (SQL Server)

Survives server restarts and infrastructure events. Slower than Redis but queryable. Useful when you need to audit which embeddings have been generated, track model versions, or join embedding cache data with other relational data. SQL Server native VECTOR is a natural fit here because the cache table can double as a lightweight vector store.

Implementing a Redis Embedding Cache

# Python — Redis L2 embedding cache with model-versioned keys
import hashlib, struct
import redis

r = redis.Redis(host="localhost", port=6379, decode_responses=False)
MODEL_ID = "text-embedding-3-small"
DIM = 1536

def cache_key(text):
    digest = hashlib.sha256(text.encode("utf-8")).hexdigest()
    return f"emb:{MODEL_ID}:{digest}".encode()

def get_cached(text):
    raw = r.get(cache_key(text))
    if raw is None:
        return None
    return list(struct.unpack(f"<{DIM}f", raw))  # float32 little-endian

def set_cached(text, embedding):
    raw = struct.pack(f"<{DIM}f", *embedding)
    r.set(cache_key(text), raw)   # no TTL: vectors don't decay

def get_or_embed(text, embed_fn):
    vec = get_cached(text)
    if vec is None:
        vec = embed_fn(text)
        set_cached(text, vec)
    return vec

Two design decisions matter here. The model ID is part of the key — a model upgrade must never read another model's vectors, and key namespacing makes that impossible by construction. And there is no TTL: embedding vectors do not decay, so expiry would only cause pointless recomputation. Eviction, if Redis memory pressure demands it, should use an allkeys-lru policy rather than time-based expiry.

SQL Server as a Persistent Embedding Cache

When you need durability, auditability, or the ability to query cache contents alongside relational data, SQL Server with native VECTOR is a natural fit. The same table that stores cached embeddings can participate in vector similarity queries, making it a dual-purpose structure — cache and lightweight vector store in one.

-- SQL Server 2025: persistent embedding cache table
CREATE TABLE dbo.EmbeddingCache (
    CacheKey    CHAR(64) NOT NULL          -- SHA-256 of the text
        CONSTRAINT PK_EmbeddingCache PRIMARY KEY,
    ModelId     NVARCHAR(100) NOT NULL,    -- part of the logical key
    DimCount    INT NOT NULL,
    Embedding   VECTOR(1536) NOT NULL,
    TextPreview NVARCHAR(200) NULL,        -- for auditing, not retrieval
    HitCount    BIGINT NOT NULL CONSTRAINT DF_EmbeddingCache_Hits DEFAULT (0),
    CreatedAt   DATETIME2(0) NOT NULL
        CONSTRAINT DF_EmbeddingCache_Created DEFAULT SYSUTCDATETIME(),
    LastHitAt   DATETIME2(0) NULL
);
CREATE INDEX IX_EmbeddingCache_Model_Hits
    ON dbo.EmbeddingCache (ModelId, HitCount DESC);

-- SQL Server: cache read (with hit accounting) and write
DECLARE @key CHAR(64) = '...sha256...';
DECLARE @model NVARCHAR(100) = 'text-embedding-3-small';

UPDATE dbo.EmbeddingCache
SET HitCount = HitCount + 1, LastHitAt = SYSUTCDATETIME()
WHERE CacheKey = @key AND ModelId = @model;

SELECT Embedding FROM dbo.EmbeddingCache
WHERE CacheKey = @key AND ModelId = @model;

Here is a Python integration layer that uses the SQL Server cache with a Redis L2 in front of it:

# Python — two-tier embedding cache: Redis (fast) -> SQL Server (persistent)
import hashlib, os, struct
import pyodbc, redis

r = redis.Redis(host="localhost", port=6379, decode_responses=False)
conn = pyodbc.connect(os.environ["SQLSERVER_CONN"])
MODEL_ID = "text-embedding-3-small"
DIM = 1536

def _key(text):
    return hashlib.sha256(text.encode()).hexdigest()

def get_or_embed_tiered(text, embed_fn):
    """Two-tier embedding cache: Redis (fast) -> SQL Server (persistent)."""
    digest = _key(text)
    rkey = f"emb:{MODEL_ID}:{digest}".encode()
    # L2: Redis check
    raw = r.get(rkey)
    if raw:
        return list(struct.unpack(f"<{DIM}f", raw))
    # L3: SQL Server check
    cur = conn.cursor()
    cur.execute("""UPDATE dbo.EmbeddingCache
                   SET HitCount = HitCount + 1, LastHitAt = SYSUTCDATETIME()
                   WHERE CacheKey = ? AND ModelId = ?""", (digest, MODEL_ID))
    row = cur.execute("""SELECT CAST(Embedding AS NVARCHAR(MAX))
                         FROM dbo.EmbeddingCache
                         WHERE CacheKey = ? AND ModelId = ?""",
                      (digest, MODEL_ID)).fetchone()
    if row:
        vec = [float(x) for x in row[0].strip("[]").split(",")]
        r.set(rkey, struct.pack(f"<{DIM}f", *vec))  # backfill Redis
        conn.commit()
        return vec
    # Miss everywhere: embed and write through both layers
    vec = embed_fn(text)
    vec_lit = "[" + ",".join(str(v) for v in vec) + "]"
    cur.execute("""INSERT INTO dbo.EmbeddingCache
                       (CacheKey, ModelId, DimCount, Embedding, TextPreview)
                   VALUES (?, ?, ?, CAST(? AS VECTOR(1536)), ?)""",
                (digest, MODEL_ID, DIM, vec_lit, text[:200]))
    conn.commit()
    r.set(rkey, struct.pack(f"<{DIM}f", *vec))
    return vec

The HitCount column is more useful than it looks: it tells you which cached embeddings earn their storage, which questions dominate your traffic, and — when joined against retrieval logs — whether your cache is actually covering the expensive calls.

Cache Invalidation: The Hard Part

Model version tagging is the primary defense. Every cache entry must include the model identifier as part of the cache key and as a stored attribute. The examples above use MODEL_ID in both the Redis key and the SQL Server row. A model migration procedure looks like this:

-- SQL Server: model migration for the embedding cache
-- 1. New rows are written under the new ModelId automatically
--    (the application passes the new MODEL_ID).
-- 2. Retire the old model's rows after the cutover + grace period:
DELETE FROM dbo.EmbeddingCache
WHERE ModelId = 'text-embedding-3-small'
  AND LastHitAt < DATEADD(day, -30, SYSUTCDATETIME());
-- 3. In Redis, either FLUSHDB the emb: namespace or let allkeys-lru
--    evict old keys naturally; they are namespaced by model and harmless.

Never reuse a cache key across models, never "migrate" vectors from one model to another by copying rows, and never let a query path read a vector whose ModelId does not match the model that will consume it. Cross-model vector reads are silent corruption — the query runs, the numbers look plausible, and retrieval quality degrades without an error.

---

LangChain and LlamaIndex Cache Integration

If you use LangChain, its CacheBackedEmbeddings wraps any embedding model with a byte-store cache — point it at Redis and you get the L2 layer with no custom code. For LlamaIndex, the ingestion pipeline's IngestionCache deduplicates document embeddings across pipeline runs, which covers the document side. Neither replaces the SQL Server L3 layer: framework caches are key-value conveniences, while the database cache gives you auditability, hit analytics, and joins against your retrieval logs.

Semantic Cache: A Step Beyond Exact Match

Exact-match caching only helps when the same question text repeats. A semantic cache goes further: embed the incoming question, search the cache for a similar previously answered question, and reuse its answer when similarity is high enough. This turns the cache from a key-value lookup into a vector search problem — and SQL Server can serve it directly:

-- SQL Server 2025: semantic answer cache
CREATE TABLE dbo.SemanticAnswerCache (
    EntryId      BIGINT IDENTITY(1,1) NOT NULL
        CONSTRAINT PK_SemanticAnswerCache PRIMARY KEY,
    QuestionText NVARCHAR(1000) NOT NULL,
    QuestionEmb  VECTOR(1536) NOT NULL,
    AnswerText   NVARCHAR(MAX) NOT NULL,
    ModelId      NVARCHAR(100) NOT NULL,
    HitCount     BIGINT NOT NULL CONSTRAINT DF_SemCache_Hits DEFAULT (0),
    CreatedAt    DATETIME2(0) NOT NULL
        CONSTRAINT DF_SemCache_Created DEFAULT SYSUTCDATETIME()
);
CREATE VECTOR INDEX IX_SemanticAnswerCache_Q
    ON dbo.SemanticAnswerCache (QuestionEmb)
    WITH (METRIC = 'cosine', TYPE = 'DiskANN');

-- Lookup: reuse an answer when a near-duplicate question was seen before
DECLARE @q VECTOR(1536) = '[0.12, 0.87, ...]';  -- embedded incoming question
SELECT TOP (1) EntryId, AnswerText,
       VECTOR_DISTANCE('cosine', QuestionEmb, @q) AS Distance
FROM dbo.SemanticAnswerCache
WHERE ModelId = 'text-embedding-3-small'
  AND VECTOR_DISTANCE('cosine', QuestionEmb, @q) < 0.08  -- near-duplicate only
ORDER BY Distance;
-- On hit: UPDATE HitCount, return AnswerText, skip the LLM entirely.
-- On miss: run the full RAG pipeline, then INSERT the Q/A pair.

The threshold is everything: too loose and paraphrased-but-different questions get wrong answers; too tight and the cache never hits. Start at 0.08 cosine distance, measure the false-hit rate on your eval set, and only widen it with evidence. Chapter 33 covers semantic caching patterns in full, including multi-tenant isolation of cached answers.

Monitoring Cache Performance

-- SQL Server: embedding cache effectiveness dashboard query
SELECT ModelId,
       COUNT(*) AS CachedVectors,
       SUM(HitCount) AS TotalHits,
       CAST(SUM(HitCount) AS FLOAT) / NULLIF(COUNT(*), 0) AS AvgHitsPerVector,
       SUM(CASE WHEN LastHitAt > DATEADD(day, -7, SYSUTCDATETIME())
                THEN 1 ELSE 0 END) AS ActiveLast7d
FROM dbo.EmbeddingCache
GROUP BY ModelId;
-- Healthy cache: AvgHitsPerVector well above 1, ActiveLast7d a large
-- share of CachedVectors. A cache where most rows have HitCount = 0
-- is just an expensive log table — shrink what you cache.

Track hit rate per layer (L1/L2/L3) in your application metrics, not just in the database. A healthy deployment shows L1 absorbing the hottest questions, L2 absorbing the long tail of repeats, and L3 catching cold starts after deploys. If L3 hit rate is near zero, your Redis sizing is fine and the database layer is pure insurance — which is a legitimate architecture, as long as it is a conscious one.

---

Cache Warming Strategies

A cold cache after a deploy means every question pays full embedding latency until the cache refills. Warm it from history: take the top-N most frequent questions from your query logs, embed them in a background job at deploy time, and write through all three layers. For the document side, the ingest pipeline already warms the cache — every embedded chunk is a cache entry if you route ingestion through get_or_embed_tiered.

Schedule warming as part of the deploy pipeline, not as a manual step. A deploy that finishes with a warm cache behaves like the old version from the first request; a deploy that finishes cold creates a latency spike that your dashboards will attribute to the new code.

---

Key Takeaways

  • → Layer your caches: in-process LRU for the hottest queries, Redis for cross-instance sharing with sub-millisecond latency, SQL Server native VECTOR for durability and auditability, and the vector store itself for document embeddings already indexed during ingestion.
  • → Namespace every cache key by model ID and never set a TTL on embedding vectors — they do not decay. Invalidation is a model-versioning problem.
  • → Use the HitCount column to prove the cache earns its storage; a cache where most rows are never hit is an expensive log table.
  • → A semantic answer cache in SQL Server — near-duplicate question lookup via DiskANN — can skip the LLM entirely for repeated questions, but the similarity threshold must be tuned on evals, not guessed.
  • → Warm the cache from query-log history at deploy time so the first request after a release behaves like the last request before it.
