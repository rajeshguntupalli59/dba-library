Chapter 2: How Vector Search Works: ANN vs Exact Search

Every vector query in SQL Server 2025 takes one of two paths: exact search, which measures the distance from your query vector to every stored vector and returns the true nearest neighbors, or approximate search, which navigates a DiskANN graph index to find nearly-the-nearest neighbors at a fraction of the cost. The two paths differ in guarantees, scaling behavior, operational overhead, and the T-SQL you write — and choosing the wrong one is the single most common performance mistake in production vector workloads. This chapter builds your intuition for both, with the numbers that determine where each one wins.

---

Exact Search: VECTOR_DISTANCE and the Full Scan

Exact search is the honest baseline: compute VECTOR_DISTANCE between the query vector and every row, sort, take the top k. No index to build, no parameters to tune, and — by construction — 100% recall. The true nearest neighbors are always returned because every candidate was measured.

-- SQL Server 2025: exact k-NN search, 100% recall, no index required
DECLARE @q VECTOR(1536) = '[0.12, 0.87, 0.34, ...]';  -- query embedding

-- Cosine distance ranking
SELECT TOP (10)
       DocumentId, Title,
       VECTOR_DISTANCE('cosine', Embedding, @q) AS Distance
FROM dbo.RagChunks
WHERE Embedding IS NOT NULL
ORDER BY Distance;

-- Euclidean variant: change only the metric argument
SELECT TOP (10) DocumentId,
       VECTOR_DISTANCE('euclidean', Embedding, @q) AS L2Distance
FROM dbo.RagChunks
WHERE Embedding IS NOT NULL
ORDER BY L2Distance;

-- Dot product variant (negative dot product: smaller = more similar)
SELECT TOP (10) DocumentId,
       VECTOR_DISTANCE('dot', Embedding, @q) AS NegDotProduct
FROM dbo.RagChunks
WHERE Embedding IS NOT NULL
ORDER BY NegDotProduct;

When exact search is the right choice:

  • → Small to medium collections. Under roughly 50,000 vectors of 1536 dimensions, exact search on modern hardware typically completes in tens of milliseconds — fast enough for interactive use with zero index maintenance.
  • → Recall is non-negotiable. Compliance search, legal discovery, and any workload where a missed neighbor has consequences beyond a slightly worse recommendation.
  • → Ground-truth measurement. Exact search is how you compute recall for the approximate path — it is the ruler everything else is measured against (Chapter 9).
  • → Prototypes and new tables. Start every new vector table on exact search. Add the DiskANN index when measurements — not anxiety — say you need it.

    The Scaling Wall: Why Exact Search Stops Working

    The performance ceiling of exact search is arithmetic, not engineering. Each query computes distance to every vector: for 1 million vectors of 1536 dimensions, that is about 1.5 billion floating-point multiply-add operations. With SIMD acceleration that runs in the low hundreds of milliseconds on a modern CPU — acceptable for a batch job, too slow for a user-facing search box. At 10 million vectors you are past a second per query before I/O, and the cost grows linearly with every row you add. No index trick short of approximation changes this; the math is the math.

    This is also a CPU story, not just a latency story. Ten concurrent exact-search queries over a million-vector table each burn a core computing distances. Under load, exact search does not degrade gracefully — it saturates CPU and everything on the instance feels it. When sys.dm_exec_query_stats shows your retrieval procedure dominated by worker time rather than waits, and the corpus keeps growing, you have found the wall. The way through it is approximation.

    ---

    Approximate Search: The DiskANN Graph Index

    Approximate nearest neighbor (ANN) search trades a small, measurable amount of recall for dramatic speed. SQL Server 2025's approximate path is a DiskANN index — a navigable graph built over the vector collection where each vector is a node connected to its nearest neighbors. A query enters at a fixed entry point and greedily walks toward the query vector, touching only a tiny fraction of the collection. Query cost grows logarithmically with data size instead of linearly: going from 1 million to 10 million vectors barely moves latency.

    -- SQL Server 2025: DiskANN approximate index (preview) + VECTOR_SEARCH
CREATE VECTOR INDEX IX_RagChunks_Embedding
ON dbo.RagChunks (Embedding)
WITH (METRIC = 'cosine', TYPE = 'DiskANN', MAXDOP = 4);

DECLARE @q VECTOR(1536) = '[0.12, 0.87, 0.34, ...]';

-- Approximate k-NN: graph walk instead of full scan
SELECT t.DocumentId, t.Title, s.distance
FROM VECTOR_SEARCH(
         TABLE = dbo.RagChunks AS t,
         COLUMN = Embedding,
         SIMILAR_TO = @q,
         METRIC = 'cosine',
         TOP_N = 10
     ) AS s
ORDER BY s.distance;

    Recall is the metric that makes "approximate" respectable: the fraction of the true top-k neighbors the index actually returns. A DiskANN index delivering 0.97 recall@10 finds 97 of the 100 true nearest neighbors in milliseconds instead of finding all 100 in over a second. Since embeddings are themselves approximate representations of meaning, that last few percent of geometric precision almost never changes what the user experiences — but you must measure it (Chapter 9 gives the spot-check pattern, Chapter 14 makes it a scheduled SLI).

    What DiskANN costs you: build time (minutes to hours for very large collections, scheduled in maintenance windows), the preview write-path constraint (drop and recreate the index to ingest new data — Chapter 10's staging-swap pattern), and memory competition between the graph and the buffer pool. What it buys you: flat latency into the millions of vectors.

    HNSW in Dedicated Engines: The Same Idea, Different Home

    You will encounter a second graph algorithm constantly in this book's later chapters: HNSW (Hierarchical Navigable Small World), the index inside Qdrant, Weaviate, Milvus, and Pinecone's serving layer. HNSW builds a layered graph — sparse long-range connections at the top, dense short-range connections at the bottom — and descends from coarse to fine. It delivers the same O(log n) search with 95–99% recall as DiskANN.

    The practical difference is memory architecture. HNSW keeps its entire graph in RAM, which makes it extremely fast and extremely memory-hungry at billion-vector scale. DiskANN was designed for SSDs: most of the graph and the full-precision vectors live on disk, with only a working set in memory, issuing a small bounded number of random reads per query. That design maps naturally onto SQL Server's buffer-pool-and-storage architecture — which is why Microsoft chose it for the in-engine index. When you read vendor benchmarks comparing HNSW engines against SQL Server's vector index, remember you are comparing two legitimate answers to the same problem, optimized for different resource profiles.

    Filtered Search: Combining Predicates with Similarity

    Real queries are rarely pure similarity — they combine "similar to this" with "and in this category, published, visible to this tenant." SQL Server's answer is the ordinary relational engine: predicates and vector ranking compose in one query, planned by the regular optimizer.

    -- Filtered vector search: relational predicate + similarity in one plan
DECLARE @q VECTOR(1536) = '[0.12, 0.87, 0.34, ...]';
DECLARE @tenantId INT = 42;

-- Exact path: the predicate narrows the scan before ranking
SELECT TOP (10) ChunkId, ChunkText,
       VECTOR_DISTANCE('cosine', Embedding, @q) AS Distance
FROM dbo.TenantChunks
WHERE TenantId = @tenantId
  AND Embedding IS NOT NULL
ORDER BY Distance;

-- Approximate path: over-fetch, because filters consume candidates
SELECT TOP (10) c.ChunkId, c.ChunkText, s.distance
FROM VECTOR_SEARCH(
         TABLE = dbo.TenantChunks AS t,
         COLUMN = Embedding,
         SIMILAR_TO = @q,
         METRIC = 'cosine',
         TOP_N = 50              -- over-fetch 5x, then filter down
     ) AS s
JOIN dbo.TenantChunks AS c ON c.ChunkId = s.ChunkId
WHERE c.TenantId = @tenantId
ORDER BY s.distance;

    The over-fetch pattern in the approximate query deserves emphasis because it is the most common recall bug in production: if you ask the index for exactly 10 candidates and the tenant filter discards 6, you return 4 results — not because only 4 were relevant, but because the filter ate your candidate budget. Ask for 50, filter, then trim to 10. For highly selective filters over huge shared indexes, consider the tenancy patterns in Chapter 12 (schema-per-tenant gives each tenant a dedicated DiskANN index with no filtering penalty at all).

    ---

    Putting It Together: The Decision You Revisit

    Start every vector table on exact search. It is correct, simple, and fast enough until it isn't. Promote to the DiskANN index when production measurements show the corpus crossing ~50K vectors with latency pressure — or when sys.dm_exec_query_stats shows retrieval CPU dominating the instance. When you promote, measure recall@k against exact ground truth before and after, and keep measuring it on a schedule (Chapter 14). The decision is not permanent and not precious: the embedding model, the chunking strategy, and the retrieval procedure shape stay the same — only the access path changes, exactly like adding a B-tree index to a table that outgrew its scan.

    ---

    Key Takeaways

  • → Exact search (VECTOR_DISTANCE with ORDER BY) computes distance to every vector: 100% recall, no index, O(n) cost per query — the right default under roughly 50,000 vectors and the ground truth everything else is measured against.
  • → Approximate search (DiskANN index via CREATE VECTOR INDEX, queried with VECTOR_SEARCH) walks a navigable graph for O(log n) queries at 95–99% recall — the answer when exact search hits its arithmetic scaling wall.
  • → DiskANN is designed for SSD-backed operation (small memory working set, bounded random reads); HNSW, used by Qdrant, Weaviate, and Milvus, keeps its graph in RAM. Same problem, different resource profiles — compare them on your workload, not on marketing.
  • → Filtered vector search composes relational predicates with similarity ranking in one T-SQL statement; on the approximate path, over-fetch TOP_N well above your display count so filters do not eat your candidate budget.
  • → Promote from exact to approximate based on production measurements (corpus size, retrieval CPU in sys.dm_exec_query_stats), measure recall@k before and after, and keep measuring it — the access path is allowed to change as the data grows.
