Chapter 27: Evaluating RAG Systems

The RAG Quality Problem: Why "It Feels Right" Doesn't Scale

Every RAG demo looks brilliant on the five questions its builder tried. Production is the other 50,000 questions, and the failure mode is not dramatic — it is a slow bleed of almost-right answers, missing citations, and confident hallucinations that erode trust one ticket at a time. "It feels right" does not scale; measured quality does. Evaluation is the discipline of turning answer quality into numbers you can trend, alert on, and gate deployments with.

A RAG system has two halves that fail independently: retrieval (did we fetch the right chunks?) and generation (did the LLM use them faithfully?). Measure them separately. A faithful answer built on wrong chunks is a retrieval failure; a hallucinated answer built on right chunks is a generation failure. Conflating them sends you tuning the wrong half.

---

Retrieval Metrics: Measuring What the Vector Search Returns

Build a labeled eval set: 100+ representative questions, each with the chunk IDs that should answer it (Chapter 22.8). Then score retrieval with the standard information-retrieval metrics:

  • → Recall@k: fraction of questions where at least one gold chunk appears in the top-k retrieved. The headline retrieval metric.
  • → Precision@k / MRR: how high the gold chunks rank, not just whether they appear. MRR (mean reciprocal rank) rewards putting the best chunk first.
  • → Context precision: of the retrieved chunks, how many are actually relevant — the metric that tells you whether the LLM prompt is mostly signal or mostly noise.
    • # Python — retrieval evaluation harness on SQL Server
# Uses SQL Server native VECTOR for retrieval and a simple eval harness
import pyodbc, openai

openai_client = openai.OpenAI()
conn = pyodbc.connect("DRIVER={ODBC Driver 18 for SQL Server};"
                      "SERVER=localhost;DATABASE=ragdb;Trusted_Connection=yes;"
                      "Encrypt=yes;TrustServerCertificate=yes")

def retrieve_chunk_ids(question_emb, k=10, tenant_id=1):
    """Returns ordered list of chunk IDs from SQL Server vector search."""
    vec = "[" + ",".join(str(v) for v in question_emb) + "]"
    cur = conn.cursor()
    cur.execute("""SELECT TOP (?) ChunkId
                   FROM dbo.DocumentChunks
                   WHERE TenantId = ?
                   ORDER BY VECTOR_DISTANCE('cosine', Embedding,
                       CAST(? AS VECTOR(1536)))""",
                (k, tenant_id, vec))
    return [r[0] for r in cur.fetchall()]

def recall_at_k(eval_set, k=10):
    hits = 0
    for q in eval_set:
        q_emb = openai_client.embeddings.create(
            input=[q["question"]],
            model="text-embedding-3-small").data[0].embedding
        retrieved = set(retrieve_chunk_ids(q_emb, k=k))
        if retrieved & set(q["gold_chunk_ids"]):
            hits += 1
    return hits / len(eval_set)

# eval_set entries: {"question": ..., "gold_chunk_ids": [...]}
# e.g. question="How does log shipping differ from mirroring?",
#      gold chunks from the HA/DR runbook chapter
print("Recall@10:", recall_at_k(eval_set, k=10))

    When retrieval scores are low, the diagnostic path mirrors index tuning: check embedding model alignment with your query distribution, examine chunk size and overlap, verify that the DiskANN index's TOP_N over-fetch and distance thresholds match your recall target, and consider hybrid search (vector + full-text, Chapter 11) for queries with strong keyword signals.

    Generation Metrics: Faithfulness, Relevance, and Hallucination Detection

    Retrieval metrics stop at the chunk list; generation metrics judge the answer. The three that matter:

  • → Faithfulness: is every claim in the answer supported by the retrieved context? Decompose the answer into atomic claims and verify each against the chunks. A single unsupported claim is a hallucination.
  • → Answer relevance: does the answer actually address the question, or does it summarize related-but-irrelevant context fluently?
  • → Context utilization: did the answer use the retrieved chunks, or did the model answer from its own parametric knowledge while ignoring the context you paid to retrieve?

    • The RAGAS framework implements these as LLM-judged metrics. Here is a RAGAS evaluation pipeline for a RAG system on SQL Server:

    # Python — RAGAS evaluation pipeline for SQL Server-backed RAG
# pip install ragas langchain-openai datasets
import pyodbc, openai
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision
from datasets import Dataset

openai_client = openai.OpenAI()
conn = pyodbc.connect("DRIVER={ODBC Driver 18 for SQL Server};"
                      "SERVER=localhost;DATABASE=ragdb;Trusted_Connection=yes;"
                      "Encrypt=yes;TrustServerCertificate=yes")

def rag_pipeline(question):
    """Your RAG pipeline: returns (answer, retrieved contexts)."""
    q_emb = openai_client.embeddings.create(
        input=[question], model="text-embedding-3-small").data[0].embedding
    vec = "[" + ",".join(str(v) for v in q_emb) + "]"
    cur = conn.cursor()
    rows = cur.execute("""SELECT TOP (5) ChunkText
                          FROM dbo.DocumentChunks
                          WHERE TenantId = 1
                          ORDER BY VECTOR_DISTANCE('cosine', Embedding,
                              CAST(? AS VECTOR(1536)))""", (vec,)).fetchall()
    contexts = [r[0] for r in rows]
    completion = openai_client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "system",
                   "content": "Answer using only the provided context."},
                  {"role": "user",
                   "content": f"Context:\n{chr(10).join(contexts)}\n\n"
                              f"Question: {question}"}])
    return completion.choices[0].message.content, contexts

questions = [
    "What are the ACID properties and how does SQL Server enforce them?",
    "What is the difference between REORGANIZE and REBUILD?",
    # ... 100+ questions with ground-truth answers
]
records = {"question": [], "answer": [], "contexts": [],
           "ground_truth": []}
for q, gt in zip(questions, ground_truths):
    answer, contexts = rag_pipeline(q)
    records["question"].append(q); records["answer"].append(answer)
    records["contexts"].append(contexts); records["ground_truth"].append(gt)

results = evaluate(Dataset.from_dict(records),
                   metrics=[faithfulness, answer_relevancy,
                            context_precision])
print(results)

    LLM-judged metrics cost money and have their own variance — run each eval three times and average, and spot-check a sample by hand. An eval harness nobody trusts is worse than no harness, because it produces confident wrong conclusions.

    End-to-End Correctness: Answer Quality at Scale

    Retrieval metrics and generation metrics diagnose components; end-to-end correctness measures the system your users experience. The practical approach: a golden set of question/answer pairs graded by an LLM judge against rubrics (correct, partially correct, incorrect, refused), run nightly against production data snapshots.

    Grade on a rubric, not a vibe. "Correct" means the answer contains the expected facts with no contradictions; "partially correct" means the key fact is present but a detail is wrong or missing; "refused" is a valid outcome when the context genuinely lacks the answer — and should be scored as correct behavior, not failure, or your metrics will punish honesty and reward hallucination.

    ---

    Storing and Trending Evaluation Results in SQL Server

    Eval results are time-series data. Store every run in SQL Server — same database, same backup, joinable against deployment history and corpus version metadata:

    -- SQL Server 2025: evaluation results warehouse
CREATE TABLE dbo.EvalRuns (
    RunId        BIGINT IDENTITY(1,1) NOT NULL
        CONSTRAINT PK_EvalRuns PRIMARY KEY,
    RunAt        DATETIME2(0) NOT NULL
        CONSTRAINT DF_EvalRuns_RunAt DEFAULT SYSUTCDATETIME(),
    EvalDataset  NVARCHAR(100) NOT NULL,   -- 'support-v3', 'dba-runbooks-v1'
    CorpusVersion INT NOT NULL,
    EmbeddingModel NVARCHAR(100) NOT NULL,
    ChunkStrategy NVARCHAR(40) NOT NULL,
    IndexType    NVARCHAR(40) NOT NULL,     -- 'DiskANN', 'exact', 'hybrid'
    GitSha       CHAR(40) NULL,             -- pipeline code version
    Notes        NVARCHAR(500) NULL
);
CREATE TABLE dbo.EvalScores (
    ScoreId  BIGINT IDENTITY(1,1) NOT NULL
        CONSTRAINT PK_EvalScores PRIMARY KEY,
    RunId    BIGINT NOT NULL CONSTRAINT FK_EvalScores_Run
        REFERENCES dbo.EvalRuns (RunId),
    Metric   NVARCHAR(60) NOT NULL,         -- 'recall@10', 'faithfulness', ...
    Score    FLOAT NOT NULL,
    SampleN  INT NOT NULL
);
CREATE INDEX IX_EvalScores_Run_Metric ON dbo.EvalScores (RunId, Metric);

    -- SQL Server: trend faithfulness across runs for one dataset
SELECT r.RunAt, r.GitSha, r.EmbeddingModel, s.Score AS Faithfulness
FROM dbo.EvalRuns AS r
JOIN dbo.EvalScores AS s ON s.RunId = r.RunId AND s.Metric = 'faithfulness'
WHERE r.EvalDataset = 'support-v3'
ORDER BY r.RunAt;
-- A drop here after a deploy is your rollback signal.

    -- SQL Server: did the chunking change help? Compare two runs metric by metric
DECLARE @before BIGINT = 41, @after BIGINT = 42;
SELECT COALESCE(b.Metric, a.Metric) AS Metric,
       b.Score AS BeforeScore, a.Score AS AfterScore,
       a.Score - b.Score AS Delta
FROM (SELECT Metric, Score FROM dbo.EvalScores WHERE RunId = @before) AS b
FULL OUTER JOIN
     (SELECT Metric, Score FROM dbo.EvalScores WHERE RunId = @after) AS a
  ON a.Metric = b.Metric
ORDER BY Metric;

    Production Monitoring: Online Metrics and Feedback Loops

    Offline evals gate deployments; online metrics catch what evals miss. Instrument the production RAG path:

  • → Retrieval telemetry: log top-1 distance per query. A rising median distance means the corpus is drifting away from the questions — new topics, new vocabulary, stale chunks.
  • → Refusal rate: how often the pipeline answers "I don't have information about that." A spike means a corpus gap or a threshold misconfiguration, not a model failure.
  • → User feedback: thumbs up/down on answers, joined to the retrieval log. The highest-value eval data you will ever get — feed confirmed-bad answers back into the golden set.
  • → Latency per stage: embed, retrieve, rerank, generate (Chapter 25.8). Regressions here are operational, not quality — but users experience them as quality.

    • Run the golden-set eval as a scheduled job (a SQL Server Agent job or an external scheduler invoking the Python harness) and write results into dbo.EvalRuns/dbo.EvalScores. Alert when faithfulness or recall@k drops more than a threshold below the rolling baseline — that alert is the production equivalent of a failed unit test.

    ---

    Building an Evaluation-Driven Development Loop

    The loop: change one thing (chunk size, reranker threshold, embedding model) → run the eval harness → compare dbo.EvalScores before/after → keep or revert. One variable at a time, like any experiment. The teams that improve RAG quality fastest are not the ones with the best models — they are the ones with the tightest loop between idea and measured result.

    Gate deployments on it: a CI step that runs the golden set and fails the build when faithfulness drops below the baseline turns quality regressions into build failures — visible, attributable, and reversible before users ever see them (Chapter 20 covers the CI benchmarking pattern this plugs into).

    ---

    A Note on Evaluation Dataset Maintenance

    Eval sets rot. Questions go stale as the product changes, gold chunks get re-chunked out of existence, and the set silently stops representing production traffic. Refresh it quarterly: sample real user questions from the retrieval logs, label a fresh batch, and retire questions the corpus can no longer answer. Version the dataset (EvalDataset = 'support-v4') and never compare scores across versions — compare within a version, and re-baseline when you cut a new one.

    ---

    Key Takeaways

  • → Measure retrieval (recall@k, MRR, context precision) and generation (faithfulness, answer relevance) separately — they fail independently and are fixed independently.
  • → Store every eval run in SQL Server (dbo.EvalRuns / dbo.EvalScores) with corpus version, model, chunk strategy, and code SHA — quality trends are time-series data.
  • → Score refusals as correct when the context genuinely lacks the answer, or your metrics will punish honesty and reward hallucination.
  • → Run the golden set nightly as a scheduled job, alert on drops below the rolling baseline, and gate deployments on faithfulness like a unit test.
  • → Feed production feedback (thumbs down, rising top-1 distances, refusal spikes) back into the golden set — the loop between idea and measured result is what compounds.
