Chapter 6: Data Types in Vector Storage: Text, Images, Audio, Code

Vector databases are, at their core, indifferent to the original form of your data. Whether you hand them a paragraph from a legal document, a spectrogram of a customer service call, a JPEG thumbnail, or a Python function, the storage layer sees only a sequence of floating-point numbers. But the path from raw data to those numbers — the embedding pipeline — varies dramatically by modality, and the choices you make there determine search quality, index behavior, and infrastructure cost more than almost anything else. This chapter walks through the four modalities that drive the majority of production vector workloads: text, images, audio, and code. For each, you will see how embeddings are generated, what dimensionality and distance metrics apply, and how to wire it into real storage systems with runnable examples.

---

6.1 Text Embeddings: The Dominant Workload

Text is where most teams start, and for good reason. The tooling is mature, the models are well-benchmarked, and the use cases — semantic search, RAG pipelines, document classification, duplicate detection — map directly onto problems DBAs already understand. If you have maintained a full-text search index in SQL Server (CONTAINS/FREETEXT) or Elasticsearch, you already understand the tension text embeddings are meant to resolve: keyword search finds documents that share vocabulary, but not necessarily meaning. A query for "myocardial infarction" will miss documents that only use "heart attack." Embedding-based search collapses that gap.

How text embeddings work

A text embedding model takes a string and outputs a dense vector. The vector encodes semantic meaning in a high-dimensional space: documents about similar topics land near each other under cosine similarity or dot product distance. The dimensionality ranges widely — 384 dimensions for fast models like all-MiniLM-L6-v2, 1536 for OpenAI's text-embedding-3-small, 3072 for text-embedding-3-large. Higher dimension is not always better; it increases storage cost and slows index construction, and for many retrieval tasks a 768-dimensional model is indistinguishable in quality from a 3072-dimensional one.

Chunking is a database partitioning problem

Before you embed a document, you must decide how to cut it up. Embedding models have token limits: text-embedding-3-small supports 8,191 tokens, sentence-transformers models typically support 512 tokens. Feeding a 200-page PDF as a single string is not an option. Chunking strategies include fixed-size windows, sentence boundaries, paragraph boundaries, and semantic chunking. The right choice depends on your retrieval pattern — the same tradeoff you make when deciding between row-level and block-level access in a traditional DBMS.

A practical baseline: 512-token chunks with 50-token overlap. The overlap prevents semantic content from being split across chunk boundaries the way a page boundary in a B-tree splits a row.

# Python
# Text embedding pipeline using OpenAI + SQL Server
# Requirements: openai>=1.0, pyodbc, tiktoken

import openai
import pyodbc
import tiktoken
from typing import List, Tuple

client = openai.OpenAI()  # reads OPENAI_API_KEY from environment

conn = pyodbc.connect(
    "DRIVER={ODBC Driver 18 for SQL Server};SERVER=localhost;"
    "DATABASE=vectordb;Trusted_Connection=yes;Encrypt=yes;"
    "TrustServerCertificate=yes"
)

def chunk_text(text: str, model: str = "text-embedding-3-small",
               chunk_tokens: int = 512, overlap_tokens: int = 50) -> List[str]:
    """Split text into overlapping token-bounded chunks."""
    enc = tiktoken.encoding_for_model(model)
    tokens = enc.encode(text)
    chunks = []
    start = 0
    while start < len(tokens):
        end = min(start + chunk_tokens, len(tokens))
        chunk_tokens_slice = tokens[start:end]
        chunks.append(enc.decode(chunk_tokens_slice))
        if end == len(tokens):
            break
        start += chunk_tokens - overlap_tokens
    return chunks

def embed_texts(texts: List[str], model: str = "text-embedding-3-small") -> List[List[float]]:
    """Batch embed up to 2048 strings per API call."""
    response = client.embeddings.create(input=texts, model=model)
    return [item.embedding for item in response.data]

def to_vector_literal(embedding: List[float]) -> str:
    """Format an embedding as a VECTOR literal SQL Server can CAST."""
    return "[" + ",".join(str(v) for v in embedding) + "]"

def ingest_document(cursor, doc_id: str, title: str, body: str) -> int:
    """Chunk, embed, and store a document. Returns number of chunks inserted."""
    chunks = chunk_text(body)
    embeddings = embed_texts(chunks)
    for i, (chunk, emb) in enumerate(zip(chunks, embeddings)):
        cursor.execute(
            "INSERT INTO document_chunks (doc_id, title, chunk_index, chunk_text, embedding) "
            "VALUES (?, ?, ?, ?, CAST(? AS VECTOR(1536)))",
            (doc_id, title, i, chunk, to_vector_literal(emb))
        )
    cursor.commit()
    return len(chunks)

# ── Schema (run once) ─────────────────────────────────────────────────────────
SCHEMA_SQL = """
CREATE TABLE document_chunks (
    id          BIGINT IDENTITY(1,1) NOT NULL CONSTRAINT PK_document_chunks PRIMARY KEY,
    doc_id      NVARCHAR(100) NOT NULL,
    title       NVARCHAR(200) NULL,
    chunk_index INT NOT NULL,
    chunk_text  NVARCHAR(MAX) NOT NULL,
    embedding   VECTOR(1536) NOT NULL,
    created_at  DATETIME2(0) NOT NULL CONSTRAINT DF_document_chunks_created
                    DEFAULT SYSUTCDATETIME()
);

CREATE VECTOR INDEX document_chunks_embedding_idx
    ON document_chunks (embedding)
    WITH (METRIC = 'cosine', TYPE = 'DiskANN', MAXDOP = 4);
"""

# ── Query ─────────────────────────────────────────────────────────────────────
def semantic_search(cursor, query: str, top_k: int = 5) -> List[Tuple]:
    query_embedding = embed_texts([query])[0]
    cursor.execute(
        """
        SELECT TOP (?) doc_id, title, chunk_index, chunk_text,
               1 - VECTOR_DISTANCE('cosine', embedding, CAST(? AS VECTOR(1536)))
                   AS cosine_similarity
        FROM   document_chunks
        WHERE  embedding IS NOT NULL
        ORDER  BY VECTOR_DISTANCE('cosine', embedding, CAST(? AS VECTOR(1536)))
        """,
        (top_k, to_vector_literal(query_embedding), to_vector_literal(query_embedding))
    )
    return cursor.fetchall()

VECTOR_DISTANCE('cosine', embedding, @query) is SQL Server's cosine distance. One minus that value gives you cosine similarity, which is more intuitive when you need to filter by a quality threshold (e.g., WHERE 1 - VECTOR_DISTANCE('cosine', embedding, @query) > 0.75).

6.2 Image Embeddings: Visual Similarity at Database Scale

Image search appears exotic, but the database framing is familiar: you are building an index over a feature space, and the features happen to come from a convolutional or transformer-based vision model rather than a B-tree key. The use cases span e-commerce (find visually similar products), content moderation (detect near-duplicate or policy-violating images), medical imaging (retrieve histology slides similar to a reference), and manufacturing (surface defect matching).

How image embeddings are generated

Vision models map an image to a dense vector by passing it through a neural network and extracting the activations at a specific layer — typically the penultimate layer before the classification head. CLIP (Contrastive Language-Image Pretraining) models are especially useful because they embed images and text into the same vector space, which allows cross-modal queries: you can retrieve images using a text string as the query.

Common models and their output dimensions:

  • → **OpenAI CLIP (ViT-B/32):** 512 dimensions
  • → **OpenAI CLIP (ViT-L/14):** 768 dimensions
  • → **Google's ViT-G via Vertex AI:** 1408 dimensions
  • → **ResNet-50 (ImageNet features):** 2048 dimensions (older, rarely used for search)

    • CLIP at ViT-L/14 is the standard starting point for production image search. It handles both similarity search within images and text-to-image retrieval, which reduces the number of specialized indexes you need to maintain.

    # Python
# Image embedding pipeline using CLIP + Weaviate
# Requirements: weaviate-client>=4.0, open-clip-torch, Pillow, torch

import weaviate
import open_clip
import torch
from PIL import Image
from pathlib import Path
import base64, io, json

# ── Load CLIP model (CPU or GPU depending on hardware) ──────────────────────
model, _, preprocess = open_clip.create_model_and_transforms(
    "ViT-L-14", pretrained="openai"
)
model.eval()
tokenizer = open_clip.get_tokenizer("ViT-L-14")

def embed_image(image_path: str) -> list[float]:
    """Return a 768-dim CLIP vector for an image file."""
    img = preprocess(Image.open(image_path).convert("RGB")).unsqueeze(0)
    with torch.no_grad():
        features = model.encode_image(img)
        features /= features.norm(dim=-1, keepdim=True)  # L2 normalize
    return features.squeeze().tolist()

def embed_text_for_image_search(text: str) -> list[float]:
    """Embed a text query into the same CLIP space as images."""
    tokens = tokenizer([text])
    with torch.no_grad():
        features = model.encode_text(tokens)
        features /= features.norm(dim=-1, keepdim=True)
    return features.squeeze().tolist()

# ── Weaviate schema ──────────────────────────────────────────────────────────
client = weaviate.connect_to_local()  # or weaviate.connect_to_weaviate_cloud(...)

from weaviate.classes.config import Configure, Property, DataType, VectorDistances

if not client.collections.exists("ProductImage"):
    client.collections.create(
        name="ProductImage",
        vectorizer_config=Configure.Vectorizer.none(),  # we supply our own vectors
        vector_index_config=Configure.VectorIndex.hnsw(
            distance_metric=VectorDistances.COSINE,
            ef_construction=128,
            max_connections=32,
        ),
        properties=[
            Property(name="product_id",   data_type=DataType.TEXT),
            Property(name="file_path",    data_type=DataType.TEXT),
            Property(name="description",  data_type=DataType.TEXT),
        ],
    )

# ── Ingest images ─────────────────────────────────────────────────────────────
def ingest_product_images(image_dir: str):
    collection = client.collections.get("ProductImage")
    with collection.batch.dynamic() as batch:
        for path in Path(image_dir).glob("*.jpg"):
            product_id = path.stem
            vector = embed_image(str(path))
            batch.add_object(
                properties={
                    "product_id":  product_id,
                    "file_path":   str(path),
                    "description": f"Product image {product_id}",
                },
                vector=vector,
            )

# ── Text-to-image search ──────────────────────────────────────────────────────
def search_images_by_text(query: str, top_k: int = 10):
    query_vector = embed_text_for_image_search(query)
    collection = client.collections.get("ProductImage")
    results = collection.query.near_vector(
        near_vector=query_vector,
        limit=top_k,
        return_metadata=["distance"],
    )
    for obj in results.objects:
        print(f"{obj.properties['product_id']} | "
              f"distance={obj.metadata.distance:.4f} | "
              f"path={obj.properties['file_path']}")

# Example: search_images_by_text("red running shoes with white sole")

    Storage considerations for images

    A 768-dimensional float32 vector consumes 3,072 bytes — about 3 KB per image. At one million images, that is 3 GB of vector data before indexing overhead. The HNSW index typically adds 1.5–2× the raw vector size, putting you at roughly 6–9 GB for the index alone. That fits comfortably in the memory of a cloud instance sized for this workload. The images themselves should not go into the vector database; store them in object storage (S3, GCS) and keep only the path or a content-addressed hash in the metadata fields.

    Preprocessing matters

    Unlike text, images require explicit preprocessing before embedding: resize to the model's expected input resolution (224×224 for ViT-B/32, 336×336 for ViT-L/14@336), normalize pixel values, and handle color mode. Feeding a grayscale medical image directly to a model expecting three-channel RGB input without conversion will produce silently incorrect embeddings — the query will return results, they just will not be meaningful. Always validate your preprocessing pipeline with a small labeled set before bulk ingestion.

    6.3 Audio Embeddings: Time-Series Signals as Vectors

    Audio is the least common modality in general-purpose vector workloads, but it is heavily used in specific verticals: call center analytics, music recommendation, speaker verification, podcast search, and environmental sound classification. The embedding pipeline is more involved than text or images because audio must be converted from a raw waveform to a fixed-length vector in a way that captures the relevant signal while discarding noise.

    Representations and models

    There are two main approaches to audio embedding:

    1. Spectrogram-based: Convert the waveform to a mel-spectrogram (a 2D time-frequency representation), then pass it through a CNN or transformer. Models: OpenL3, PANNs (Pretrained Audio Neural Networks), CLAP (Contrastive Language-Audio Pretraining).

    2. Waveform-based: Feed raw audio samples directly to a transformer. Models: wav2vec 2.0, Whisper encoder features, EnCodec.

    For semantic audio search — finding recordings similar in content or speaker — CLAP is the current standard because it supports cross-modal text-to-audio queries, the same pattern that makes CLIP useful for images.

    For speaker identification, models like speechbrain/spkrec-ecapa-voxceleb produce 192-dimensional speaker embeddings optimized for cosine similarity between the same speaker across recordings.

    # Python
# Audio embedding pipeline using CLAP + Qdrant
# Requirements: qdrant-client, msclap, librosa, numpy

import librosa
import numpy as np
from qdrant_client import QdrantClient
from qdrant_client.models import (
    Distance, VectorParams, PointStruct, SearchRequest
)
from msclap import CLAP  # Microsoft CLAP implementation

# ── Initialize CLAP and Qdrant ────────────────────────────────────────────────
clap_model = CLAP(version="2023", use_cuda=False)
qdrant = QdrantClient(url="http://localhost:6333")

COLLECTION_NAME = "audio_clips"
VECTOR_DIM = 512  # CLAP 2023 audio embedding dimension

# ── Create collection ─────────────────────────────────────────────────────────
qdrant.recreate_collection(
    collection_name=COLLECTION_NAME,
    vectors_config=VectorParams(size=VECTOR_DIM, distance=Distance.COSINE),
)

def embed_audio_file(file_path: str) -> np.ndarray:
    """
    Load an audio file and return a CLAP embedding.
    CLAP internally resamples to 44.1 kHz and expects mono or stereo.
    """
    embeddings = clap_model.get_audio_embeddings(
        [file_path], resample=True
    )
    vec = embeddings[0]
    # L2 normalize for cosine similarity
    return (vec / np.linalg.norm(vec)).tolist()

def embed_audio_text_query(text: str) -> list[float]:
    """Embed a text query into the CLAP audio space."""
    embeddings = clap_model.get_text_embeddings([text])
    vec = embeddings[0]
    return (vec / np.linalg.norm(vec)).tolist()

def ingest_audio_clips(clips: list[dict]):
    """
    clips: list of {"id": int, "file_path": str, "label": str, "duration_s": float}
    """
    points = []
    for clip in clips:
        vector = embed_audio_file(clip["file_path"])
        points.append(
            PointStruct(
                id=clip["id"],
                vector=vector,
                payload={
                    "file_path":  clip["file_path"],
                    "label":      clip["label"],
                    "duration_s": clip["duration_s"],
                },
            )
        )
    qdrant.upsert(collection_name=COLLECTION_NAME, points=points)

def search_audio_by_text(query: str, top_k: int = 5):
    """Find audio clips matching a natural language description."""
    query_vector = embed_audio_text_query(query)
    results = qdrant.search(
        collection_name=COLLECTION_NAME,
        query_vector=query_vector,
        limit=top_k,
        with_payload=True,
    )
    for hit in results:
        print(f"Score: {hit.score:.4f} | "
              f"Label: {hit.payload['label']} | "
              f"File: {hit.payload['file_path']}")

# Example: search_audio_by_text("dogs barking outdoors")
# Example: search_audio_by_text("angry customer complaining about billing")

    Segmentation and temporal alignment

    Long audio recordings — interviews, conference calls, podcasts — require segmentation before embedding, similar to text chunking. A common strategy is to use voice activity detection (VAD) to find speech segments, then embed each segment of 5–30 seconds independently. This gives finer retrieval granularity: instead of finding "the episode that discusses refund policies," you can surface the 20-second clip where refund policies are explicitly mentioned.

    The metadata schema for audio should carry temporal anchors: start_time_s and end_time_s for each embedded segment. These allow the retrieval result to play back or link to the exact moment in a recording, which is the audio equivalent of returning a document chunk rather than a full document.

    Sampling rate and codec normalization

    Audio from different sources arrives at different sample rates (8 kHz telephony, 44.1 kHz music, 16 kHz podcast) and codecs (MP3, AAC, FLAC, OGG). Most embedding models expect a specific input: wav2vec 2.0 requires 16 kHz mono PCM. Feeding 8 kHz telephone audio without upsampling, or stereo audio without downmixing, degrades embedding quality. Build a normalization step (librosa's resample, ffmpeg via subprocess) at the front of your ingestion pipeline and enforce it — treat it the same way you would enforce data type coercion in an ETL pipeline.

    6.4 Code Embeddings: Semantic Search Across Source Files

    Code is a modality that most vector database introductions skip, but it is one of the most commercially valuable. Developers search for how a function was used across a codebase, how a specific API was called, or what code handles a particular edge case. Traditional regex-based code search (grep, ripgrep) is syntactically exact; embedding-based search finds code that does the same thing expressed differently.

    How code embeddings differ from text embeddings

    Code has structure that plain text does not: function signatures, indentation scope, docstrings, variable names, and control flow. Models trained specifically on code — microsoft/codebert-base, Salesforce/codet5-base, OpenAI's text-embedding-3-small with code content, and voyage-code-2 from Voyage AI — outperform generic text models on code retrieval tasks because they understand that def add(a, b): return a + b and func sum(x int, y int) int { return x + y } are semantically equivalent even across languages.

    voyage-code-2 from Voyage AI currently leads benchmarks for code retrieval, producing 1536-dimensional embeddings. For teams already on the OpenAI stack, text-embedding-3-small performs well enough on code and avoids introducing a second embedding provider.

    Chunking strategies for code

    File-level embedding loses too much precision; function-level or class-level chunking is the practical standard. Parse the AST of each source file and extract functions, methods, and classes as individual embedding units. Include the docstring, signature, and body as the text passed to the embedding model. For Python, the ast module handles this natively; for multi-language codebases, tree-sitter provides a consistent AST interface across languages.

    # Python
# Code embedding pipeline using tree-sitter + Pinecone + Voyage AI
# Requirements: pinecone-client>=3.0, voyageai, tree-sitter, tree-sitter-python

import ast
import textwrap
from pathlib import Path
import voyageai
from pinecone import Pinecone, ServerlessSpec

voyage = voyageai.Client()  # reads VOYAGE_API_KEY from environment
pc = Pinecone()             # reads PINECONE_API_KEY from environment

INDEX_NAME = "codebase-search"
DIMENSION  = 1536           # voyage-code-2 output dimension

# ── Create Pinecone index (serverless, cosine) ─────────────────────────────
if INDEX_NAME not in [idx.name for idx in pc.list_indexes()]:
    pc.create_index(
        name=INDEX_NAME,
        dimension=DIMENSION,
        metric="cosine",
        spec=ServerlessSpec(cloud="aws", region="us-east-1"),
    )

index = pc.Index(INDEX_NAME)

# ── Extract Python functions from source ──────────────────────────────────
def extract_python_functions(source_path: str) -> list[dict]:
    """
    Parse a Python file and return one dict per function/method,
    containing the name, source text, and file path.
    """
    source = Path(source_path).read_text(encoding="utf-8")
    tree   = ast.parse(source)
    units  = []

    for node in ast.walk(tree):
        if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef)):
            func_lines = source.splitlines()[
                node.lineno - 1 : node.end_lineno
            ]
            func_text = textwrap.dedent("\n".join(func_lines))
            units.append({
                "name":       node.name,
                "file_path":  source_path,
                "start_line": node.lineno,
                "end_line":   node.end_lineno,
                "source":     func_text,
            })

    return units

def embed_code_units(units: list[dict]) -> list[list[float]]:
    """Embed a list of code units using voyage-code-2."""
    texts = [u["source"] for u in units]
    response = voyage.embed(texts, model="voyage-code-2", input_type="document")
    return response.embeddings

def ingest_python_file(file_path: str, namespace: str = ""):
    """Parse, embed, and upsert all functions from a Python file."""
    units = extract_python_functions(file_path)
    if not units:
        return

    embeddings = embed_code_units(units)

    vectors = []
    for unit, embedding in zip(units, embeddings):
        # Pinecone IDs must be strings; use file+line as a stable key
        vec_id = f"{unit['file_path']}::{unit['name']}::{unit['start_line']}"
        vectors.append({
            "id":     vec_id,
            "values": embedding,
            "metadata": {
                "name":       unit["name"],
                "file_path":  unit["file_path"],
                "start_line": unit["start_line"],
                "end_line":   unit["end_line"],
                "source":     unit["source"][:1000],  # Pinecone metadata is size-limited
            },
        })

    # Pinecone recommends upsert batches of 100 or fewer
    batch_size = 100
    for i in range(0, len(vectors), batch_size):
        index.upsert(vectors=vectors[i : i + batch_size], namespace=namespace)

def ingest_directory(root_dir: str, namespace: str = ""):
    """Walk a directory tree and ingest all .py files."""
    for path in Path(root_dir).rglob("*.py"):
        print(f"Ingesting {path}")
        ingest_python_file(str(path), namespace=namespace)

# ── Search ────────────────────────────────────────────────────────────────────
def search_code(query: str, top_k: int = 5, namespace: str = "") -> list[dict]:
    """
    Embed a natural language or code query and retrieve matching functions.
    """
    response = voyage.embed([query], model="voyage-code-2", input_type="query")
    query_vector = response.embeddings[0]

    results = index.query(
        vector=query_vector,
        top_k=top_k,
        include_metadata=True,
        namespace=namespace,
    )

    matches = []
    for match in results.matches:
        matches.append({
            "score":      match.score,
            "name":       match.metadata["name"],
            "file_path":  match.metadata["file_path"],
            "start_line": match.metadata["start_line"],
            "source":     match.metadata["source"],
        })
    return matches

    Multi-language codebases

    When your codebase spans multiple languages — Go services, Python scripts, TypeScript frontends, SQL stored procedures — you have two practical options:

    1. Single shared index: Embed all code regardless of language into the same Pinecone index or SQL Server vector table. This works well when queries are natural language ("find the function that handles payment retries"), because the model maps both the query and code across languages into a shared semantic space. Include language as a metadata field and filter when needed.

    2. Per-language indexes: Maintain separate indexes or namespaces per language. This is useful when queries are themselves code ("find Go functions similar to this Python function") because it lets you tune chunking, model selection, and distance thresholds per language without cross-contamination.

    For most teams, the single shared index is simpler to operate and surprisingly effective.

    SQL and database code

    SQL stored procedures, views, and migration scripts are a special case worth calling out. Developers routinely need to find queries that JOIN a particular table, update a specific column, or implement a pattern like a slowly changing dimension. Embedding SQL is straightforward — feed the SQL text to the embedding model — but chunking differs: a SQL file may contain dozens of independent statements. Split on statement boundaries (semicolons, GO delimiters in SQL Server) and embed each statement independently.

    The metadata fields that pay off for SQL code search: database_name, schema_name, object_type (table, view, procedure, trigger), tables_referenced (extracted by parsing), and last_modified. This turns your vector database into a semantic catalog layer on top of your existing database assets.

    6.5 Multi-Modal Pipelines: Combining Modalities in One Index

    Real applications rarely deal with a single modality in isolation. A product catalog has a name (text), a description (text), images, and potentially a promotional audio clip. A customer support system has transcribed calls (text derived from audio), agent notes (text), and screenshots of error messages (images). Building a single search experience across all of these requires a decision: do you use a single unified embedding space, or do you maintain separate indexes and fuse results at query time?

    Unified embedding space with CLIP/CLAP

    CLIP and CLAP models are trained to project images and text (or audio and text) into a shared vector space using contrastive learning. A text query lands near matching images, and image queries land near matching captions. This makes it possible to maintain a single index and query it with any modality.

    The limitation is that these shared spaces are trained for specific modality pairs. CLIP handles image↔text; CLAP handles audio↔text; there is no single off-the-shelf model that embeds text, images, audio, and code into one coherent space. Unified multi-modal models exist (Google's Gemini, Meta's ImageBind) but they are not yet standardized in the same way that CLIP is for image-text tasks.

    Late fusion with per-modality indexes

    graph TD
    T[Text] --> ET[Text embedding model]
    I[Image] --> EI[CLIP image encoder]
    A[Audio] --> EA[CLAP audio encoder]
    C[Code] --> EC[Code embedding model]
    ET --> IDX1[(Text index)]
    EI --> IDX2[(Image index)]
    EA --> IDX3[(Audio index)]
    EC --> IDX4[(Code index)]
    IDX1 --> RRF[Reciprocal Rank Fusion]
    IDX2 --> RRF
    IDX3 --> RRF
    IDX4 --> RRF
    RRF --> R[Fused results]

    *Each modality gets its own embedding model and index; results are merged at query time via Reciprocal Rank Fusion rather than forced into one shared vector space.*

    The alternative is to maintain separate indexes per modality and fuse results at query time. A search query is embedded by each relevant model, each index returns its top-K results, and a fusion layer combines the ranked lists. Reciprocal Rank Fusion (RRF) is the standard algorithm for this:

    # Python
# Reciprocal Rank Fusion for multi-modal result merging
from collections import defaultdict
from typing import Any

def reciprocal_rank_fusion(
    ranked_lists: list[list[Any]],
    id_key: str = "id",
    k: int = 60,
) -> list[dict]:
    """
    Merge multiple ranked result lists using RRF.
    Each item in a ranked_list must be a dict with a unique id_key.
    k=60 is the standard constant that dampens the influence of high ranks.
    """
    scores: dict[Any, float] = defaultdict(float)
    items:  dict[Any, dict]  = {}

    for ranked_list in ranked_lists:
        for rank, item in enumerate(ranked_list, start=1):
            item_id = item[id_key]
            scores[item_id] += 1.0 / (k + rank)
            items[item_id]   = item  # keep the last-seen metadata

    fused = sorted(
        [{"rrf_score": score, **items[item_id]} for item_id, score in scores.items()],
        key=lambda x: x["rrf_score"],
        reverse=True,
    )
    return fused

# Example: fuse text search and image search results for a product catalog
# text_results  = [{"id": "prod_001", "name": "Red Sneaker", ...}, ...]
# image_results = [{"id": "prod_003", "name": "Trail Runner", ...}, ...]
# fused = reciprocal_rank_fusion([text_results, image_results])

    RRF does not require score normalization across modalities, which is a significant practical advantage: cosine similarity scores from a text index are not directly comparable to distance scores from an image index, but rank positions are comparable.

    Metadata alignment across modalities

    When operating a multi-modal pipeline, the metadata schema becomes the spine that connects records across indexes. A product_id field that exists in both the text chunk table and the image vector collection is what makes post-retrieval joining possible. Design your metadata schema before you build the ingestion pipelines, or you will find yourself with three indexes that cannot be joined without a full table scan.

    A practical metadata pattern for a product catalog:

    -- SQL Server: unified metadata table that all modality indexes reference
CREATE TABLE dbo.product_assets (
    asset_id      UNIQUEIDENTIFIER NOT NULL CONSTRAINT DF_product_assets_id DEFAULT NEWID(),
    product_id    NVARCHAR(100) NOT NULL,
    modality      NVARCHAR(20) NOT NULL
                  CONSTRAINT CK_product_assets_modality
                  CHECK (modality IN ('text', 'image', 'audio', 'code')),
    source_ref    NVARCHAR(500) NOT NULL,   -- chunk text, S3 path, git SHA, etc.
    embedding_dim INT NOT NULL,
    index_name    SYSNAME NOT NULL,         -- which index/table holds the vector
    external_id   NVARCHAR(100) NOT NULL,   -- the vector's ID in that index
    created_at    DATETIME2(0) NOT NULL CONSTRAINT DF_product_assets_created
                    DEFAULT SYSUTCDATETIME(),
    CONSTRAINT PK_product_assets PRIMARY KEY (asset_id)
);

CREATE INDEX IX_product_assets_product ON dbo.product_assets (product_id);
CREATE INDEX IX_product_assets_modality ON dbo.product_assets (modality, index_name);

    This table acts as a reverse-lookup registry: given a vector ID returned by Pinecone or Weaviate, you can join back to the canonical product_id and fetch any other modality's vectors or metadata.

    6.6 Distance Metrics by Modality

    Not all vector spaces are created equal, and the choice of distance metric affects both retrieval quality and index performance. The table below summarizes the practical defaults by modality:

    | Modality | Typical Model Family | Recommended Metric | Notes |

    |---|---|---|---|

    | Text | Sentence-transformers, OpenAI | Cosine similarity | Vectors are L2-normalized by most models |

    | Text (dot product tuned) | Matryoshka / OpenAI v3 | Dot product | Only if model is trained with dot product objective |

    | Images | CLIP variants | Cosine similarity | L2-normalize outputs before storage |

    | Audio (semantic) | CLAP | Cosine similarity | Same contrastive training as CLIP |

    | Audio (speaker ID) | ECAPA-TDNN, x-vectors | Cosine similarity | Speaker embeddings respond well to cosine |

    | Code | voyage-code-2, CodeBERT | Cosine similarity | Normalize outputs |

    | Binary / hash | SimHash, MinHash | Hamming distance | Store hashes in VARBINARY(MAX) in SQL Server |

    The near-universal answer is cosine similarity, which is why most production systems normalize vectors to unit length at ingestion time and then use dot product as a fast approximation (dot product on unit vectors equals cosine similarity). SQL Server's VECTOR_DISTANCE takes the metric as an argument ('cosine' vs 'dot'), so you can switch metrics without changing the schema.

    Euclidean (L2) distance is appropriate when the magnitude of the vector carries semantic information, which is rare in embedding models designed for retrieval — those models are typically trained with normalization objectives. Hamming distance is useful for binary fingerprinting and near-duplicate detection in image or document deduplication pipelines.

    6.7 Storage Sizing and Cost Modeling

    Before committing to a database architecture, teams need to estimate how much vector data they are actually dealing with. The arithmetic is simple but frequently underestimated.

    Per-vector storage

    A single float32 (4-byte) vector of dimension *d* consumes *4d* bytes on disk. The HNSW index — the dominant index type in production vector stores — adds roughly 1.5–2× the raw vector size in graph structure overhead. A 1536-dimensional OpenAI embedding therefore consumes:

  • → Raw vector: 4 × 1536 = 6,144 bytes (≈ 6 KB)
  • → With HNSW overhead: ≈ 12–15 KB per vector

    • At one million documents with five chunks each (five million vectors):

  • → Raw data: 5M × 6 KB = 30 GB
  • → Index: 5M × 15 KB = 75 GB total on-disk

    • That is a meaningful infrastructure commitment. Dimensionality reduction strategies — Matryoshka representation learning (MRL), PCA post-processing, or switching to a smaller model — can cut that by 50–75% at a modest quality cost.

    Quantization

    Scalar quantization (SQ8) and binary quantization (BQ) reduce vector storage at the cost of some retrieval precision. SQL Server stores vectors as float32 in the native VECTOR type; application-side float16 arrays or binary hashes in VARBINARY trade retrieval precision for storage when you need it. Pinecone offers built-in int8 quantization. Weaviate supports both scalar and product quantization natively.

    A common production pattern:

    1. Store the full-precision vectors on disk for re-ranking.

    2. Use a quantized version for the HNSW index to reduce memory footprint.

    3. After ANN retrieval returns top-100 candidates, re-rank with exact dot product on the full-precision vectors.

    This two-stage pattern maintains high recall while reducing the memory needed to serve the HNSW index, which must fit in RAM for low-latency queries.

    Cost across platforms

    Managed vector databases price on stored vectors, queries per second, and sometimes on the hosting tier (pod-based vs. serverless). Self-hosted SQL Server on a VM with adequate RAM is often the most cost-effective option at moderate scale — tens of millions of vectors — because you pay only for compute and storage, not a per-vector premium. Beyond a few hundred million vectors, the operational overhead of running a purpose-built system like Qdrant or Weaviate at scale often justifies the higher unit cost.

    Key Takeaways

  • → **Modality determines the embedding pipeline, not the storage layer.** SQL Server native vectors, Pinecone, Weaviate, and Qdrant are all modality-agnostic; what changes is the model you call before writing a vector to the index. Design your ingestion pipeline first, then select the database that fits your operational constraints.
  • → **Chunking and segmentation are first-class engineering problems.** Whether you are splitting a legal document into 512-token windows, extracting Python functions from an AST, or segmenting a call recording by voice activity, how you divide data before embedding determines retrieval granularity more than model choice does.
  • → **CLIP and CLAP enable cross-modal text-to-X queries without a separate query path.** By embedding images or audio into the same vector space as text, you avoid maintaining a specialized query interface for each modality — a single near-vector query handles both image similarity and text-to-image retrieval.
  • → **Cosine similarity with L2-normalized vectors is the safe default across all modalities.** Euclidean distance is rarely appropriate for embedding-based retrieval; Hamming distance applies only to binary fingerprinting. When in doubt, normalize at ingestion and use cosine.
  • → **Size your infrastructure before you build.** A 1536-dimensional embedding model applied to five million vectors produces roughly 75 GB of indexed data. Factor in HNSW overhead, quantization trade-offs, and the distinction between disk storage and RAM residency before selecting a hosting tier — vector indexes must fit in memory to serve low-latency queries.
