Chapter 32: Graph and Vector: Combining Relationship and Semantic Search

Semantic search answers the question *what does this mean?* Graph traversal answers the question *how are these things connected?* Neither question alone is sufficient for many real-world AI applications. A knowledge graph without semantic understanding forces exact string matches and brittle schema design. A vector index without relationship awareness loses the structural context that determines whether two semantically similar documents are actually related, authored by the same person, part of the same regulatory framework, or connected through a chain of citations. This chapter explores how to combine graph and vector capabilities into a unified retrieval layer — covering the architectural patterns, the specific tools that support native graph-vector hybrid search, and the practical tradeoffs that determine when you need both versus when one is sufficient.

---

Why Graph Structure and Vector Similarity Serve Different Retrieval Needs

Start with a concrete example: a pharmaceutical knowledge base containing drug compounds, clinical trials, regulatory approvals, adverse event reports, and the researchers who authored each document. Pure vector search can find documents semantically similar to "cardiovascular side effects in elderly patients." But it cannot tell you that two apparently similar adverse event reports refer to different formulations of the same drug, or that the most semantically relevant paper was authored by a researcher whose institution's data has been retracted. That structural context lives in the graph.

Graph databases model entities and relationships as first-class citizens. In property graph terms, nodes hold attributes and edges hold typed, directional relationships with their own properties. Neo4j's Cypher, Amazon Neptune's Gremlin and SPARQL, and Weaviate's cross-references all express this structure. The query planner traverses the graph using index-free adjacency — following pointers directly from one node to its neighbors rather than performing joins across tables. This gives graph databases their characteristic performance on multi-hop traversal queries: O(depth × branching_factor) rather than O(n log n) for a join-based equivalent.

Vector databases answer a different kind of query. Given a query embedding, find the k nearest vectors in high-dimensional space. The performance envelope is defined by approximate nearest neighbor (ANN) algorithms — HNSW, IVF, ScaNN — that trade recall for speed. A well-tuned HNSW index on a 1536-dimensional embedding space with 10 million vectors returns 10 nearest neighbors in under 10ms at 99% recall. No graph traversal is involved; the structure being searched is a proximity graph of embeddings, not an entity-relationship graph of domain objects.

The architectural question is where these two search modes intersect. Three patterns emerge in production:

Pre-filter by graph, rank by vector. Traverse the graph to identify a candidate set of entity IDs, then perform vector similarity search over that restricted set. This uses graph traversal to answer structural questions ("all drugs approved by the FDA in the last three years") and vector search to rank within that set.

Post-filter by graph, retrieve by vector. Retrieve top-k semantically similar documents, then apply graph traversal to expand, filter, or re-rank based on structural relationships. A recommendation system might retrieve 50 semantically similar items, then use the user's purchase graph to remove already-purchased items and boost items purchased by structurally similar users.

Graph-guided vector traversal. Use graph relationships to guide which regions of the vector space to explore. This is the approach taken by graph-aware RAG systems that follow citation or entity linkage graphs to gather context before embedding retrieval.

Pattern 1: Pre-Filter (teal) runs Graph Traversal first to carve out candidate entities, then searches vectors only within that set — best when the graph is selective. Pattern 2: Post-Filter (purple) runs Vector Search first for top-k similarity, then applies the Graph Filter to prune or expand — best when similarity dominates. Pattern 3: Guided (amber) lets the Entity Graph Select Regions of vector space before Vector Retrieval — best for citation graphs and hierarchies. Choose by selectivity: whichever side prunes harder goes first.

*The three ways graph structure and vector similarity combine in production retrieval systems.*

Native Graph-Vector Databases: Weaviate, Neo4j Vector, and Amazon Neptune Analytics

Several databases now offer native support for both paradigms within a single query engine, eliminating the need for application-level orchestration between separate systems.

Weaviate was designed from the start around the idea that objects have both vector representations and references to other objects. Its schema system defines cross-references between classes, and its GraphQL query layer lets you traverse those references while filtering by vector similarity in the same request.

# Python
import weaviate
import weaviate.classes as wvc

client = weaviate.connect_to_local()

# Schema: Drug nodes reference ClinicalTrial nodes
# This query retrieves trials semantically similar to a query
# that are linked to a specific drug compound
query_text = "cardiovascular adverse events in elderly patients"

response = (
    client.collections.get("ClinicalTrial")
    .query.near_text(
        query=query_text,
        limit=10,
        return_metadata=wvc.query.MetadataQuery(distance=True),
        filters=wvc.query.Filter.by_ref("hasDrug").by_property("name").equal("Atorvastatin"),
    )
)

for obj in response.objects:
    print(f"Trial ID: {obj.properties['trial_id']}")
    print(f"Title: {obj.properties['title']}")
    print(f"Distance: {obj.metadata.distance:.4f}")
    print()

client.close()

The Filter.by_ref() call translates to a graph traversal: follow the hasDrug reference edge and filter by the target node's property. Weaviate executes this as a pre-filter before the vector search, meaning the ANN index is queried only over the subset of trials linked to Atorvastatin. At scale this matters: if 10% of your 10M trial documents are linked to the target drug, you are running ANN over 1M vectors rather than 10M, which is roughly a 10x improvement in query latency with no change in recall.

Neo4j added native vector indexing in version 5.11, allowing a CALL db.index.vector.queryNodes() procedure alongside standard Cypher graph traversal. This enables a query that first does vector retrieval and then traverses the graph from the results.

# Python - Neo4j combined graph + vector query
from neo4j import GraphDatabase
from openai import OpenAI

openai_client = OpenAI()
driver = GraphDatabase.driver("bolt://localhost:7687", auth=("neo4j", "password"))

def get_embedding(text: str) -> list[float]:
    response = openai_client.embeddings.create(
        input=text,
        model="text-embedding-3-small"
    )
    return response.data[0].embedding

def graph_vector_search(query: str, hop_depth: int = 2, top_k: int = 5):
    embedding = get_embedding(query)

    cypher = """
    // Step 1: Vector similarity search to find seed nodes
    CALL db.index.vector.queryNodes('document_embeddings', $top_k, $embedding)
    YIELD node AS doc, score AS similarity_score

    // Step 2: Traverse the graph from each seed node
    // Follow AUTHORED_BY and CITES relationships up to hop_depth
    CALL apoc.path.subgraphNodes(doc, {
        relationshipFilter: 'AUTHORED_BY>|CITES>',
        maxLevel: $hop_depth
    })
    YIELD node AS related

    // Step 3: Collect and return with structural context
    WITH doc, similarity_score,
         collect(DISTINCT related) AS graph_neighbors
    RETURN
        doc.title AS title,
        doc.document_id AS doc_id,
        similarity_score,
        [n IN graph_neighbors WHERE n:Author | n.name] AS authors,
        [n IN graph_neighbors WHERE n:Document | n.title] AS cited_docs,
        size(graph_neighbors) AS graph_connectivity
    ORDER BY similarity_score DESC
    """

    with driver.session() as session:
        result = session.run(
            cypher,
            embedding=embedding,
            top_k=top_k,
            hop_depth=hop_depth
        )
        return [record.data() for record in result]

results = graph_vector_search(
    "machine learning approaches for drug interaction prediction",
    hop_depth=2,
    top_k=5
)

for r in results:
    print(f"Title: {r['title']}")
    print(f"Similarity: {r['similarity_score']:.4f}")
    print(f"Authors: {', '.join(r['authors'])}")
    print(f"Cites: {len(r['cited_docs'])} documents")
    print(f"Graph Connectivity: {r['graph_connectivity']} related nodes")
    print()

driver.close()

The graph_connectivity metric here is not just informational. Documents with high graph connectivity in a citation network are generally more influential and more likely to represent canonical sources rather than derivative work. This is a structural signal that pure vector similarity cannot capture.

Amazon Neptune Analytics (not Neptune Database) introduced vector similarity search in 2024, enabling openCypher queries that combine graph traversal with approximate nearest neighbor search over stored embeddings. The design pattern follows the same logic: use Neptune's property graph for structural filtering, Neptune Analytics' vector index for semantic ranking.

SQL Server Graph Tables Meet VECTOR: Graph-Vector Hybrid in T-SQL

If your stack is already on SQL Server, you may not need a dedicated graph database for moderate-complexity relationship modeling. SQL Server's native graph tables (CREATE TABLE AS NODE / AS EDGE, since 2017) handle traversal via MATCH predicates, and the 2025 VECTOR type handles the similarity layer. The combination is not as expressive as Cypher for deep traversal, but for depth-limited graph queries it is entirely production-viable and keeps your stack consolidated.

-- SQL Server 2025
-- Schema: documents with embeddings, plus a relationship graph
CREATE TABLE dbo.Documents (
    DocId     UNIQUEIDENTIFIER NOT NULL
        CONSTRAINT PK_Documents PRIMARY KEY
        DEFAULT NEWSEQUENTIALID(),
    Title     NVARCHAR(300) NOT NULL,
    Content   NVARCHAR(MAX) NULL,
    Embedding VECTOR(1536) NULL,
    CreatedAt DATETIME2(0) NOT NULL
        CONSTRAINT DF_Documents_Created DEFAULT SYSUTCDATETIME()
);
CREATE TABLE dbo.DocRelationships (
    SourceId UNIQUEIDENTIFIER NOT NULL
        CONSTRAINT FK_DR_Source REFERENCES dbo.Documents (DocId),
    TargetId UNIQUEIDENTIFIER NOT NULL
        CONSTRAINT FK_DR_Target REFERENCES dbo.Documents (DocId),
    RelType  NVARCHAR(40) NOT NULL,  -- 'CITES', 'AUTHORED_BY_SAME', 'PART_OF_SERIES'
    Weight   FLOAT NOT NULL CONSTRAINT DF_DR_Weight DEFAULT (1.0),
    CONSTRAINT PK_DocRelationships PRIMARY KEY (SourceId, TargetId, RelType)
);
CREATE VECTOR INDEX IX_Documents_Embedding
    ON dbo.Documents (Embedding)
    WITH (METRIC = 'cosine', TYPE = 'DiskANN', MAXDOP = 8);
CREATE INDEX IX_DocRelationships_Source ON dbo.DocRelationships (SourceId);
CREATE INDEX IX_DocRelationships_Target ON dbo.DocRelationships (TargetId);

-- Graph-vector hybrid query:
-- 1. Find top-10 semantically similar documents (vector layer)
-- 2. Traverse 2 hops of the citation graph from those seeds (graph layer)
-- 3. Re-rank the expanded set by a combined score
DECLARE @q VECTOR(1536) = '[0.1, 0.2, ...]';  -- embedded query

WITH
-- Step 1: Vector similarity search - seed nodes
VectorSeeds AS (
    SELECT TOP (10) d.DocId, d.Title,
        1 - VECTOR_DISTANCE('cosine', d.Embedding, @q) AS CosineSimilarity
    FROM dbo.Documents AS d
    WHERE d.Embedding IS NOT NULL
    ORDER BY VECTOR_DISTANCE('cosine', d.Embedding, @q)
),
-- Step 2: Graph traversal from seed nodes (up to 2 hops)
GraphExpansion AS (
    SELECT DocId, DocId AS OriginId, 0 AS Hops FROM VectorSeeds
    UNION ALL
    SELECT dr.TargetId AS DocId, ge.OriginId, ge.Hops + 1
    FROM GraphExpansion AS ge
    JOIN dbo.DocRelationships AS dr
      ON dr.SourceId = ge.DocId AND dr.RelType = 'CITES'
    WHERE ge.Hops < 2
),
ExpandedCandidates AS (
    SELECT DocId, MIN(Hops) AS MinHops
    FROM GraphExpansion
    GROUP BY DocId
),
FinalRanking AS (
    SELECT d.DocId, d.Title,
        1 - VECTOR_DISTANCE('cosine', d.Embedding, @q) AS CosineSimilarity,
        ec.MinHops,
        -- Graph proximity penalty: seeds (hop=0) get full score;
        -- each hop reduces score by 15%
        (1 - VECTOR_DISTANCE('cosine', d.Embedding, @q))
            * POWER(0.85, ec.MinHops) AS CombinedScore,
        CASE WHEN vs.DocId IS NOT NULL THEN 1 ELSE 0 END AS IsSeedNode
    FROM ExpandedCandidates AS ec
    JOIN dbo.Documents AS d ON d.DocId = ec.DocId
    LEFT JOIN VectorSeeds AS vs ON vs.DocId = ec.DocId
    WHERE d.Embedding IS NOT NULL
)
SELECT TOP (20) DocId, Title,
    ROUND(CAST(CosineSimilarity AS FLOAT), 4) AS SemanticScore,
    MinHops AS GraphHops,
    ROUND(CAST(CombinedScore AS FLOAT), 4) AS CombinedScore,
    IsSeedNode
FROM FinalRanking
ORDER BY CombinedScore DESC
OPTION (MAXRECURSION 10);

The hop penalty (0.85 per hop) is a tunable parameter. In citation networks where relevance decays sharply with distance, values between 0.75 and 0.85 work well. In social graphs where second-degree connections are highly relevant, you might use 0.95 or no penalty at all. Benchmark this against your human-labeled relevance set before deploying.

Performance characteristics to expect: with 1M documents and a DiskANN index, the vector seed retrieval runs in ~5ms. The recursive CTE traversal over 10 seeds at depth 2 with average branching factor 5 will generate ~250 candidate nodes, and the secondary embedding lookups add ~1ms. Total query time is typically 10–30ms for this pattern at this scale — well within interactive response time budgets.

Graph-Aware RAG: Using Relationship Context in LLM Pipelines

Retrieval-Augmented Generation pipelines typically operate in a flat retrieval model: embed the query, retrieve top-k chunks, stuff them into the context window. This loses structural information. Graph-aware RAG incorporates relationship traversal into the retrieval step so the context passed to the LLM includes not just semantically similar content but contextually connected content.

Microsoft Research published GraphRAG in 2024, which builds a community detection graph over extracted entities and uses that graph to enable global queries (summarizing broad themes across a corpus) that flat RAG cannot handle. The architecture is more complex than simple hybrid search but the principle is the same: use graph structure to decide what to retrieve.

A more immediately deployable pattern is entity-linked RAG: extract named entities from the query, look up those entities in a knowledge graph to gather structured context, then combine that structured context with vector-retrieved chunks.

# Python
# Entity-linked Graph-aware RAG with Neo4j + SQL Server + OpenAI

from neo4j import GraphDatabase
from openai import OpenAI
import pyodbc
import json
from typing import Optional

openai_client = OpenAI()
neo4j_driver = GraphDatabase.driver("bolt://localhost:7687", auth=("neo4j", "password"))
sql_conn = pyodbc.connect("DRIVER={ODBC Driver 18 for SQL Server};"
                         "SERVER=localhost;DATABASE=knowledge_db;"
                         "Trusted_Connection=yes;Encrypt=yes;"
                         "TrustServerCertificate=yes")

def extract_entities_from_query(query: str) -> list[str]:
    """Use LLM to extract named entities from the query."""
    response = openai_client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {
                "role": "system",
                "content": "Extract named entities (people, organizations, drugs, diseases, locations) "
                           "from the query. Return a JSON array of entity names only."
            },
            {"role": "user", "content": query}
        ],
        response_format={"type": "json_object"}
    )
    result = json.loads(response.choices[0].message.content)
    return result.get("entities", [])

def get_graph_context(entities: list[str]) -> dict:
    """Traverse knowledge graph for entity context."""
    if not entities:
        return {}

    cypher = """
    UNWIND $entity_names AS name
    MATCH (e:Entity)
    WHERE e.name =~ ('(?i)' + name)

    // Get direct relationships (1 hop)
    OPTIONAL MATCH (e)-[r1]->(neighbor1:Entity)
    OPTIONAL MATCH (e)<-[r2]-(neighbor2:Entity)

    RETURN
        e.name AS entity_name,
        e.type AS entity_type,
        e.description AS entity_description,
        collect(DISTINCT {
            name: neighbor1.name,
            type: neighbor1.type,
            relationship: type(r1),
            direction: 'outgoing'
        }) AS outgoing_relations,
        collect(DISTINCT {
            name: neighbor2.name,
            type: neighbor2.type,
            relationship: type(r2),
            direction: 'incoming'
        }) AS incoming_relations
    """

    with neo4j_driver.session() as session:
        result = session.run(cypher, entity_names=entities)
        graph_context = {}
        for record in result:
            entity = record["entity_name"]
            graph_context[entity] = {
                "type": record["entity_type"],
                "description": record["entity_description"],
                "relations": record["outgoing_relations"] + record["incoming_relations"]
            }
        return graph_context

def vector_search_with_graph_filter(
    query: str,
    entity_ids: Optional[list[str]] = None,
    top_k: int = 5
) -> list[dict]:
    """Vector similarity search in SQL Server, optionally filtered by entity graph."""
    embedding = openai_client.embeddings.create(
        input=query,
        model="text-embedding-3-small"
    ).data[0].embedding

    embedding_str = "[" + ",".join(str(x) for x in embedding) + "]"

    vec_param = "[" + ",".join(str(x) for x in embedding) + "]"
    cur = sql_conn.cursor()
    if entity_ids:
        placeholders = ",".join("?" for _ in entity_ids)
        rows = cur.execute(f"""
            SELECT TOP (?) c.ChunkId, c.Content, c.SourceDoc, c.SectionTitle,
                1 - VECTOR_DISTANCE('cosine', c.Embedding,
                        CAST(? AS VECTOR(1536))) AS Similarity
            FROM dbo.DocumentChunks AS c
            JOIN dbo.ChunkEntities AS ce ON ce.ChunkId = c.ChunkId
            WHERE ce.EntityId IN ({placeholders})
            ORDER BY VECTOR_DISTANCE('cosine', c.Embedding,
                         CAST(? AS VECTOR(1536)))
        """, (top_k, vec_param, *entity_ids, vec_param)).fetchall()
    else:
        rows = cur.execute("""
            SELECT TOP (?) ChunkId, Content, SourceDoc, SectionTitle,
                1 - VECTOR_DISTANCE('cosine', Embedding,
                        CAST(? AS VECTOR(1536))) AS Similarity
            FROM dbo.DocumentChunks
            ORDER BY VECTOR_DISTANCE('cosine', Embedding,
                         CAST(? AS VECTOR(1536)))
        """, (top_k, vec_param, vec_param)).fetchall()

        return [
            {
                "chunk_id": r[0],
                "content": r[1],
                "source_doc": r[2],
                "section_title": r[3],
                "similarity": float(r[4])
            }
            for r in rows
        ]

def graph_aware_rag(query: str) -> str:
    """Full graph-aware RAG pipeline."""

    # Step 1: Extract entities from query
    entities = extract_entities_from_query(query)
    print(f"Extracted entities: {entities}")

    # Step 2: Get structured graph context for those entities
    graph_context = get_graph_context(entities)
    print(f"Graph context retrieved for {len(graph_context)} entities")

    # Step 3: Vector search (filtered if we have entity context)
    # In production, translate entity names to IDs via a lookup table
    retrieved_chunks = vector_search_with_graph_filter(query, top_k=5)
    print(f"Retrieved {len(retrieved_chunks)} chunks via vector search")

    # Step 4: Construct enriched context for LLM
    graph_context_text = ""
    for entity, ctx in graph_context.items():
        graph_context_text += f"\n[Entity: {entity} ({ctx['type']})]\n"
        if ctx["description"]:
            graph_context_text += f"Description: {ctx['description']}\n"
        if ctx["relations"]:
            relations_summary = [
                f"  - {rel['relationship']} -> {rel['name']}"
                for rel in ctx["relations"][:5]  # Limit to top 5 relations
            ]
            graph_context_text += "Relationships:\n" + "\n".join(relations_summary) + "\n"

    chunks_text = "\n\n".join([
        f"[Source: {c['source_doc']} | Section: {c['section_title']} | Similarity: {c['similarity']:.3f}]\n{c['content']}"
        for c in retrieved_chunks
    ])

    # Step 5: LLM generation with structured + semantic context
    prompt = f"""Answer the following question using the provided context.

KNOWLEDGE GRAPH CONTEXT (Structured relationships):
{graph_context_text if graph_context_text else "No graph context available."}

DOCUMENT CONTEXT (Semantically similar passages):
{chunks_text}

QUESTION: {query}

Provide a comprehensive answer grounded in the provided context."""

    response = openai_client.chat.completions.create(
        model="gpt-4o",
        messages=[
            {"role": "system", "content": "You are a precise research assistant. Ground your answers in the provided context."},
            {"role": "user", "content": prompt}
        ],
        temperature=0.1
    )

    return response.choices[0].message.content

# Example usage
answer = graph_aware_rag(
    "What are the known drug interactions between statins and blood thinners in elderly patients?"
)
print(answer)

The separation of graph context (structured, relational facts) from vector context (semantically similar text passages) in the prompt is intentional. LLMs attend differently to structured relational facts than to free-text passages, and keeping them visually distinct in the prompt tends to improve attribution accuracy in the generated answer.

Choosing Between Graph-Vector Integration Strategies

The decision tree for graph-vector architecture is driven by three factors: relationship depth, data volume, and team operational capacity.

Relationship depth is the primary driver. If your graph queries require more than three hops to answer meaningful questions, T-SQL recursive CTEs become slow and operationally awkward. Neo4j, Amazon Neptune, or ArangoDB handle this naturally. At one to two hops, SQL Server with a well-indexed adjacency table performs comparably to a dedicated graph database and eliminates operational complexity.

Data volume determines whether you can afford native hybrid query engines or need to separate the systems. Weaviate performs well at 50M+ vectors with cross-references, but its graph capabilities are limited to direct object references — it is not a property graph database. Neo4j's vector index, as of version 5.x, handles tens of millions of vectors with HNSW but is not optimized for the billion-vector scale that Pinecone or Milvus serve. If you need billion-scale vectors with complex multi-hop graph traversal, you are building a hybrid architecture with two separate systems communicating at the application layer.

Team operational capacity is the factor that gets underweighted in architecture decisions. Running two production database systems — a graph database and a vector database — means two monitoring setups, two backup procedures, two capacity planning models, and two teams who need to understand both. Unless the retrieval quality improvement from the native graph-vector approach is significant and measurable, the simpler architecture wins.

A practical decision matrix:

| Scenario | Recommended Architecture |

|---|---|

| <10M vectors, shallow relationships (≤2 hops) | SQL Server native graph tables + VECTOR + recursive CTEs |

| <50M vectors, moderate relationship complexity | Weaviate with cross-references |

| Any scale, deep graph traversal (>3 hops) | Neo4j 5.x or Amazon Neptune Analytics |

| >500M vectors + complex graphs |Separate vector DB (Pinecone/Milvus) + graph DB (Neo4j/Neptune), application-layer orchestration |

| Regulated environment, single-vendor preference | Amazon Neptune Analytics (unified) |

Implementing the Application-Layer Orchestration Pattern

When you cannot fit both concerns into a single database, the application layer becomes the join engine. The pattern requires careful attention to consistency, latency, and the ordering of operations.

# Python
# Application-layer orchestration: Pinecone (vector) + Neo4j (graph)

from pinecone import Pinecone
from neo4j import GraphDatabase
from openai import OpenAI
from dataclasses import dataclass
from typing import Optional
import asyncio

@dataclass
class HybridSearchResult:
    doc_id: str
    title: str
    vector_score: float
    graph_score: float
    combined_score: float
    graph_hops: int
    structural_context: dict

class HybridSearchOrchestrator:
    def __init__(
        self,
        pinecone_api_key: str,
        pinecone_index_name: str,
        neo4j_uri: str,
        neo4j_auth: tuple,
    ):
        self.pc = Pinecone(api_key=pinecone_api_key)
        self.index = self.pc.Index(pinecone_index_name)
        self.neo4j_driver = GraphDatabase.driver(neo4j_uri, auth=neo4j_auth)
        self.openai_client = OpenAI()

    def _get_embedding(self, text: str) -> list[float]:
        return self.openai_client.embeddings.create(
            input=text,
            model="text-embedding-3-small"
        ).data[0].embedding

    def _vector_search(
        self,
        embedding: list[float],
        top_k: int = 20,
        namespace: str = "",
        filter_dict: Optional[dict] = None
    ) -> list[dict]:
        """Pinecone vector search returning candidate IDs and scores."""
        response = self.index.query(
            vector=embedding,
            top_k=top_k,
            namespace=namespace,
            filter=filter_dict,
            include_metadata=True
        )
        return [
            {
                "doc_id": match.id,
                "vector_score": match.score,
                "metadata": match.metadata
            }
            for match in response.matches
        ]

    def _graph_score_and_expand(
        self,
        seed_doc_ids: list[str],
        expansion_depth: int = 2
    ) -> dict[str, dict]:
        """
        For each seed document, compute a graph centrality score and
        expand to neighboring nodes. Returns a dict keyed by doc_id.
        """
        cypher = """
        UNWIND $seed_ids AS seed_id
        MATCH (d:Document {doc_id: seed_id})

        // Compute in-degree as a structural importance proxy
        OPTIONAL MATCH (d)<-[:CITES]-(citing:Document)
        WITH d, seed_id, count(citing) AS citation_count

        // Expand neighbors up to expansion_depth
        CALL apoc.path.subgraphNodes(d, {
            relationshipFilter: 'CITES>|RELATED_TO>',
            maxLevel: $depth,
            limit: 50
        })
        YIELD node AS neighbor

        WITH
            seed_id,
            d.title AS title,
            citation_count,
            collect(DISTINCT {
                doc_id: neighbor.doc_id,
                title: neighbor.title,
                hops: 1
            }) AS neighbors

        RETURN
            seed_id,
            title,
            citation_count,
            neighbors,
            // Normalize citation count to [0, 1] range using log scale
            // We use a soft normalization; tune the divisor for your corpus
            (1.0 - exp(-citation_count / 10.0)) AS graph_score
        """

        with self.neo4j_driver.session() as session:
            result = session.run(
                cypher,
                seed_ids=seed_doc_ids,
                depth=expansion_depth
            )
            graph_data = {}
            for record in result:
                graph_data[record["seed_id"]] = {
                    "title": record["title"],
                    "citation_count": record["citation_count"],
                    "graph_score": record["graph_score"],
                    "neighbors": record["neighbors"]
                }
            return graph_data

    def _fetch_neighbor_vectors(
        self,
        neighbor_ids: list[str],
        query_embedding: list[float]
    ) -> list[dict]:
        """Fetch vector scores for graph-expanded nodes not in original results."""
        if not neighbor_ids:
            return []

        # Fetch by ID from Pinecone
        fetch_response = self.index.fetch(ids=neighbor_ids)
        neighbor_results = []
        for doc_id, vector_data in fetch_response.vectors.items():
            if vector_data.values:
                # Compute cosine similarity manually
                import numpy as np
                qv = np.array(query_embedding)
                dv = np.array(vector_data.values)
                similarity = float(np.dot(qv, dv) / (np.linalg.norm(qv) * np.linalg.norm(dv)))
                neighbor_results.append({
                    "doc_id": doc_id,
                    "vector_score": similarity,
                    "metadata": vector_data.metadata or {}
                })
        return neighbor_results

    def search(
        self,
        query: str,
        top_k_vector: int = 20,
        expansion_depth: int = 2,
        vector_weight: float = 0.6,
        graph_weight: float = 0.4,
        final_top_k: int = 10
    ) -> list[HybridSearchResult]:
        """
        Full hybrid search:
        1. Vector search for seed candidates
        2. Graph scoring and expansion
        3. Fetch vector scores for expanded nodes
        4. Combined scoring and final ranking
        """
        # Step 1: Vector search
        embedding = self._get_embedding(query)
        vector_results = self._vector_search(embedding, top_k=top_k_vector)
        seed_ids = [r["doc_id"] for r in vector_results]
        vector_score_map = {r["doc_id"]: r["vector_score"] for r in vector_results}

        # Step 2: Graph scoring and expansion
        graph_data = self._graph_score_and_expand(seed_ids, expansion_depth)

        # Collect all neighbor IDs not already in vector results
        all_neighbor_ids = set()
        for seed_id, data in graph_data.items():
            for neighbor in data.get("neighbors", []):
                n_id = neighbor.get("doc_id")
                if n_id and n_id not in vector_score_map:
                    all_neighbor_ids.add(n_id)

        # Step 3: Fetch vector scores for expanded nodes
        expanded_vector_results = self._fetch_neighbor_vectors(
            list(all_neighbor_ids), embedding
        )
        for r in expanded_vector_results:
            vector_score_map[r["doc_id"]] = r["vector_score"]

        # Build graph score map from all known nodes
        graph_score_map: dict[str, float] = {}
        for seed_id, data in graph_data.items():
            graph_score_map[seed_id] = data["graph_score"]

        # Step 4: Combined scoring
        all_candidate_ids = set(vector_score_map.keys())
        results = []

        for doc_id in all_candidate_ids:
            v_score = vector_score_map.get(doc_id, 0.0)
            g_score = graph_score_map.get(doc_id, 0.0)
            combined = (vector_weight * v_score) + (graph_weight * g_score)

            # Determine graph hops (0 = seed, 1+ = expanded)
            hops = 0 if doc_id in {r["doc_id"] for r in vector_results} else 1

            g_data = graph_data.get(doc_id, {})
            results.append(HybridSearchResult(
                doc_id=doc_id,
                title=g_data.get("title", "Unknown"),
                vector_score=v_score,
                graph_score=g_score,
                combined_score=combined,
                graph_hops=hops,
                structural_context={
                    "citation_count": g_data.get("citation_count", 0),
                    "neighbor_count": len(g_data.get("neighbors", []))
                }
            ))

        results.sort(key=lambda x: x.combined_score, reverse=True)
        return results[:final_top_k]

    def close(self):
        self.neo4j_driver.close()

orchestrator = HybridSearchOrchestrator(

    neo4j_auth=("neo4j", "password")

    print(f"  Citations: {r.structural_context['citation_count']}")

Two implementation details here deserve attention. First, the graph score uses a log-normalized citation count rather than raw citation count. Raw citation count creates a rich-get-richer dynamic where the most-cited papers dominate regardless of semantic relevance. The formula 1.0 - exp(-citation_count / 10.0) maps zero citations to a graph score of 0 and asymptotically approaches 1 as citations grow, with a reasonable inflection point around 10 citations for most academic corpora. Adjust the divisor based on the citation distribution of your specific dataset.

Second, the _fetch_neighbor_vectors step introduces a latency cost: a Pinecone fetch call for potentially hundreds of IDs. Whether this is acceptable depends on your latency budget. If the latency budget is tight, consider capping expansion to 1 hop, limiting neighbors per seed to the top 5 by graph edge weight, or pre-materializing graph-neighbor embeddings into a secondary index.

SQL Server Compatibility: Graph Tables and Vector Search

SQL Server 2017 introduced native graph table support (CREATE TABLE AS NODE and CREATE TABLE AS EDGE), and SQL Server 2025 (and Azure SQL Database's preview features) added vector similarity functions. This combination allows graph-vector hybrid queries within a single SQL Server instance, following the same graph-plus-vector pattern, expressed entirely in T-SQL.

-- SQL Server
-- Graph tables combined with vector similarity search

-- Node tables
CREATE TABLE dbo.Documents (
    doc_id      UNIQUEIDENTIFIER DEFAULT NEWSEQUENTIALID() PRIMARY KEY,
    title       NVARCHAR(500) NOT NULL,
    content     NVARCHAR(MAX),
    embedding   VARBINARY(MAX),   -- stored as binary; cast for similarity functions
    created_at  DATETIME2 DEFAULT SYSUTCDATETIME(),
    $node_id    -- implicit SQL Server graph node column
) AS NODE;

CREATE TABLE dbo.Authors (
    author_id   UNIQUEIDENTIFIER DEFAULT NEWSEQUENTIALID() PRIMARY KEY,
    name        NVARCHAR(200),
    institution NVARCHAR(200),
    $node_id
) AS NODE;

-- Edge tables
CREATE TABLE dbo.Cites (
    citation_date   DATE,
    $edge_id,       -- implicit edge columns
    $from_id,
    $to_id
) AS EDGE;

CREATE TABLE dbo.AuthoredBy (
    $edge_id,
    $from_id,
    $to_id
) AS EDGE;

-- Graph-vector hybrid query using MATCH syntax (SQL Server graph)
-- and VECTOR_DISTANCE (available in SQL Server 2025 / Azure SQL)

-- Step 1: Find semantically similar documents using vector search
-- Step 2: Use MATCH to traverse citation graph from those seeds
-- Step 3: Re-rank by combined score

DECLARE @query_embedding VARBINARY(MAX) = <your_embedding_binary>;
DECLARE @hop_depth INT = 2;
DECLARE @top_k INT = 10;

WITH VectorSeeds AS (
    SELECT TOP (@top_k)
        doc_id,
        title,
        embedding,
        VECTOR_DISTANCE('cosine', embedding, @query_embedding) AS cosine_distance
    FROM dbo.Documents
    ORDER BY VECTOR_DISTANCE('cosine', embedding, @query_embedding) ASC
),

-- One-hop expansion via SQL Server MATCH clause
OneHopExpansion AS (
    SELECT DISTINCT
        cited.doc_id        AS expanded_doc_id,
        seed.doc_id         AS origin_doc_id,
        1                   AS hop_count
    FROM VectorSeeds seed
    JOIN dbo.Documents AS citing
        ON seed.doc_id = citing.doc_id
    JOIN dbo.Cites AS c
        ON TRUE
    JOIN dbo.Documents AS cited
        ON TRUE
    WHERE MATCH(citing-(c)->cited)
),

-- Two-hop expansion
TwoHopExpansion AS (
    SELECT DISTINCT
        cited2.doc_id       AS expanded_doc_id,
        one.origin_doc_id,
        2                   AS hop_count
    FROM OneHopExpansion one
    JOIN dbo.Documents AS intermediate
        ON one.expanded_doc_id = intermediate.doc_id
    JOIN dbo.Cites AS c2
        ON TRUE
    JOIN dbo.Documents AS cited2
        ON TRUE
    WHERE MATCH(intermediate-(c2)->cited2)
),

AllCandidates AS (
    SELECT doc_id AS candidate_id, 0 AS min_hops
    FROM VectorSeeds
    UNION ALL
    SELECT expanded_doc_id, 1 FROM OneHopExpansion
    UNION ALL
    SELECT expanded_doc_id, 2 FROM TwoHopExpansion
),

Deduped AS (
    SELECT candidate_id, MIN(min_hops) AS min_hops
    FROM AllCandidates
    GROUP BY candidate_id
)

SELECT TOP 20
    d.doc_id,
    d.title,
    ROUND(1.0 - VECTOR_DISTANCE('cosine', d.embedding, @query_embedding), 4) AS semantic_score,
    dj.min_hops                                                                AS graph_hops,
    ROUND(
        (1.0 - VECTOR_DISTANCE('cosine', d.embedding, @query_embedding))
        * POWER(0.85, CAST(dj.min_hops AS FLOAT)),
        4
    )                                                                          AS combined_score
FROM Deduped dj
JOIN dbo.Documents d ON d.doc_id = dj.candidate_id
ORDER BY combined_score DESC;

The SQL Server MATCH clause follows the ASCII-art arrow syntax (from_node-(edge)->to_node), which is unique to SQL Server's graph implementation. Unlike Cypher, it cannot express variable-length path traversal in a single clause — hence the explicit one-hop and two-hop CTE expansion above. For deeper traversal, this approach becomes repetitive. SQL Server 2022 introduced SHORTEST_PATH which handles variable-length traversal more cleanly:

-- SQL Server 2022+: Variable-length path with SHORTEST_PATH

SELECT
    source.doc_id       AS source_doc_id,
    target.doc_id       AS target_doc_id,
    COUNT(edge.$edge_id) AS path_length
FROM dbo.Documents AS source,
     dbo.Cites FOR PATH AS edge,
     dbo.Documents FOR PATH AS target
WHERE MATCH(SHORTEST_PATH(source(-(edge)->target)+))
  AND source.doc_id IN (SELECT doc_id FROM VectorSeeds)
HAVING COUNT(edge.$edge_id) <= 3

SHORTEST_PATH finds the minimum hop count between source and target, which is preferable to the manual CTE expansion when you want the true graph distance rather than a fixed-depth expansion.

Evaluating Hybrid Retrieval Quality

Adding graph traversal to a vector search pipeline should be justified by measurable retrieval quality improvement. The standard evaluation framework applies: build a test set of queries with human-labeled relevant documents, compute Precision@k and NDCG@k for pure vector search, then recompute after adding graph expansion.

A useful heuristic to check before running a full evaluation: compute the overlap between your graph-expanded candidate set and the human-labeled relevant set. If the graph expansion surfaces relevant documents that vector search missed, the architecture is earning its complexity. If the overlap is near zero — graph expansion consistently surfaces documents that human raters do not find relevant — your graph edges may not encode the right relationships for the retrieval task.

The graph connectivity metric from the Neo4j example earlier (graph_connectivity) can serve as a proxy relevance signal during development. Documents with zero graph connectivity in a well-constructed knowledge graph are either orphans (data quality problem) or highly specialized documents with narrow applicability. High-connectivity documents are structurally central and tend to be more broadly relevant. Track this distribution in your test set before tuning score weights.

# Python
# Offline evaluation: compare pure vector vs. graph-vector hybrid retrieval

from sklearn.metrics import ndcg_score
import numpy as np

def evaluate_retrieval(
    test_queries: list[dict],  # [{"query": str, "relevant_ids": list[str]}]
    searcher_fn,               # callable(query) -> list[str] of doc_ids
    k: int = 10
) -> dict:
    """
    Compute Precision@k and NDCG@k over a labeled test set.

    test_queries: list of dicts with 'query' and 'relevant_ids' keys
    searcher_fn: function that takes a query string and returns ordered list of doc_ids
    k: cutoff rank
    """
    precisions = []
    ndcg_scores = []

    for item in test_queries:
        query = item["query"]
        relevant = set(item["relevant_ids"])

        retrieved = searcher_fn(query)[:k]

        # Precision@k
        hits = sum(1 for doc_id in retrieved if doc_id in relevant)
        precisions.append(hits / k)

        # NDCG@k: binary relevance
        relevance_true = np.array([[1 if doc_id in relevant else 0
                                    for doc_id in retrieved]])
        # Ideal ranking: all relevant docs at top
        ideal = np.array([[1] * min(len(relevant), k) +
                          [0] * max(0, k - len(relevant))])
        if relevance_true.sum() > 0:
            ndcg_scores.append(ndcg_score(ideal, relevance_true, k=k))
        else:
            ndcg_scores.append(0.0)

    return {
        f"precision_at_{k}": np.mean(precisions),
        f"ndcg_at_{k}": np.mean(ndcg_scores),
        "n_queries": len(test_queries)
    }

Key Takeaways

  • → **Graph and vector search solve orthogonal retrieval problems.** Vector similarity finds semantically proximate content; graph traversal finds structurally related content. Many production AI applications require both, and the combination surfaces results that neither approach finds alone.
  • → **Three integration patterns cover most production needs:** pre-filter by graph then rank by vector, post-retrieve by vector then expand by graph, and graph-guided RAG where entity relationships shape what context the LLM receives. Choose the pattern based on whether structural constraints are known before or after the semantic query.
  • → **SQL Server native graph tables + VECTOR + recursive CTEs is a viable graph-vector stack** for shallow relationship graphs (one to two hops) and data volumes below the tens of millions. It eliminates operational complexity at the cost of expressiveness for deep traversal queries.
  • → **Native graph-vector engines (Neo4j 5.x, Weaviate, Amazon Neptune Analytics) reduce application-layer complexity** but impose scale ceilings and operational learning curves. Evaluate them when your graph queries exceed two hops or when application-layer orchestration between two separate systems creates unacceptable latency or consistency challenges.
  • → **Measure before you build.** Graph expansion should be justified by Precision@k and NDCG@k improvements on a labeled test set. If the graph structure of your data does not encode relationships that are semantically meaningful for your retrieval task, adding a graph layer adds latency and operational burden without improving answer quality.
