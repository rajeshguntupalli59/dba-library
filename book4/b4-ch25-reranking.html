Chapter 25: Reranking — Improving Retrieval Quality

25.1 Why Vector Search Alone Is Not Enough

Vector search is a recall machine: it finds candidates fast across millions of rows, but its ranking is coarse. A bi-encoder embedding compresses a 512-token document into a single 1,536-dimensional point, and that compression loses information. Two documents with different specific claims can land at nearly identical distances from a query vector because their general topics match.

Embedding compression loss. A question about "SQL Server index fragmentation thresholds" may return documents about "SQL Server index performance" ranked higher than a document that actually explains when to REORGANIZE vs REBUILD — because "index performance" is a broader, more common phrase in the embedding model's training data. The vector distance says "topically close"; the user's question needed "specifically answering."

Reranking fixes this with a two-stage retrieval: Stage 1 (the vector index) retrieves 50–200 candidates cheaply for recall; Stage 2 (the reranker) scores each candidate against the query precisely and re-orders them for precision. You pay the expensive scoring only on the candidates, not the corpus — which is why reranking routinely delivers the biggest quality-per-millisecond improvement in a RAG pipeline.

---

25.2 Cross-Encoder Architecture and Why It Works Better

A bi-encoder embeds the query and each document independently, then compares vectors. A cross-encoder takes the query and one document together as input and outputs a relevance score directly — the model sees the actual words of both, so it can reward exact answer matches, penalize topic-only overlap, and understand negation ("this does NOT apply to Standard Edition"). That joint attention is why cross-encoders outrank bi-encoders on precision, and why they are too slow to run over a whole corpus: each query-document pair is a full model forward pass.

# Python — cross-encoder reranking (ms-marco-MiniLM-L-6-v2)
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

def rerank(query, candidates, top_n=5):
    """candidates: list of dicts with 'text'. Returns top_n, re-ordered."""
    pairs = [[query, c["text"]] for c in candidates]
    scores = reranker.predict(pairs)
    ranked = sorted(zip(candidates, scores),
                    key=lambda x: x[1], reverse=True)
    return [{"text": c["text"], "rerank_score": float(s),
             "vector_distance": c.get("distance")}
            for c, s in ranked[:top_n]]

The canonical example: a SQL Server DBA knowledge base where the query is "How do I reduce index fragmentation on a high-write table?"

query = "How do I reduce index fragmentation on a high-write table?"
# Candidate documents from ANN retrieval (top-20 from SQL Server)
candidates = [
    {"id": "doc_001", "text":
     "sys.dm_db_index_physical_stats reports fragmentation. Query it regularly "
     "to monitor avg_fragmentation_in_percent across your indexes."},
    {"id": "doc_002", "text":
     "Use ALTER INDEX ... REORGANIZE for fragmentation between 5 and 30 "
     "percent, and ALTER INDEX ... REBUILD for fragmentation above 30 percent. "
     "On high-write tables, schedule rebuilds during maintenance windows."},
    {"id": "doc_003", "text":
     "Fill factor reserves free space on index pages. Setting FILLFACTOR to 80 "
     "on high-write tables reduces page splits and slows fragmentation growth."},
    {"id": "doc_004", "text":
     "Index performance in SQL Server depends on statistics. Running UPDATE "
     "STATISTICS after bulk loads ensures the optimizer uses indexes correctly."},
    {"id": "doc_005", "text":
     "Partitioning a large table lets you rebuild individual partitions. For "
     "high-write partitioned tables, rebuild only the hot partitions nightly."},
]
ranked = rerank(query, candidates, top_n=3)
for r in ranked:
    print(f"{r['rerank_score']:.3f}  {r['text'][:80]}...")
# Expected: doc_002 (REORGANIZE vs REBUILD thresholds) rises to rank 1,
# doc_003 (fill factor) to rank 2 — both directly answering fragmentation
# mitigation — while doc_001 (monitoring) and doc_004 (statistics) fall.

25.3 Re-ranking with Cohere and Production API Integration

Running a cross-encoder locally costs you GPU inference infrastructure on the query path. Cohere Rerank is the managed alternative: send the query and up to hundreds of candidate texts, get relevance scores back. Fifty documents through Cohere Rerank typically completes in 80–150ms round-trip from a co-located cloud instance — often faster than local CPU inference, with no model to host.

# Python — Cohere Rerank over SQL Server retrieval candidates
import cohere, pyodbc

co = cohere.ClientV2(api_key="...")
conn = pyodbc.connect("DRIVER={ODBC Driver 18 for SQL Server};"
                      "SERVER=localhost;DATABASE=ragdb;Trusted_Connection=yes;"
                      "Encrypt=yes;TrustServerCertificate=yes")

def sqlserver_retrieve(question_emb, top_k=50, tenant_id=1):
    vec = "[" + ",".join(str(v) for v in question_emb) + "]"
    cur = conn.cursor()
    cur.execute("""SELECT TOP (?) ChunkId, ChunkText,
                          VECTOR_DISTANCE('cosine', Embedding,
                              CAST(? AS VECTOR(1536))) AS Distance
                   FROM dbo.DocumentChunks
                   WHERE TenantId = ? AND Embedding IS NOT NULL
                   ORDER BY Distance""", (top_k, vec, tenant_id))
    return [{"id": r[0], "text": r[1], "distance": r[2]}
            for r in cur.fetchall()]

def retrieve_and_rerank(question, question_emb, top_n=5, tenant_id=1):
    candidates = sqlserver_retrieve(question_emb, top_k=50,
                                    tenant_id=tenant_id)
    rr = co.rerank(model="rerank-v3.5", query=question,
                   documents=[c["text"] for c in candidates],
                   top_n=top_n, return_documents=False)
    return [{"id": candidates[r.index]["id"],
             "text": candidates[r.index]["text"],
             "rerank_score": r.relevance_score,
             "vector_distance": candidates[r.index]["distance"]}
            for r in rr.results]

For latency budgets: retrieving 50 rows from SQL Server takes 5–15ms on typical hardware. The ms-marco-MiniLM-L-6-v2 cross-encoder scores 50 pairs on CPU in approximately 120–200ms; Cohere Rerank does it in 80–150ms over the network. Either way, total two-stage retrieval stays under 300ms — well within a 500ms SLA for interactive search.

25.4 Implementing Re-ranking in SQL Server Pipelines

When your vector store is SQL Server, the re-ranking step happens in the application layer after the T-SQL retrieval. The database returns candidate rows with their distance values; Python applies the cross-encoder and returns the re-ordered set. Keep the boundary clean: SQL Server owns recall (top-50 candidates, tenant filtering, distance thresholding), the reranker owns precision (final top-5 order).

-- SQL Server: candidate retrieval tuned for reranking
-- Over-fetch (TOP 50) because the reranker re-orders; the final cut is top-5.
-- The distance threshold keeps obvious non-matches out of paid rerank calls.
DECLARE @q VECTOR(1536) = '[0.12, 0.87, ...]';  -- embedded question

SELECT TOP (50) ChunkId, ChunkText,
       VECTOR_DISTANCE('cosine', Embedding, @q) AS Distance
FROM dbo.DocumentChunks
WHERE TenantId = @tenant
  AND ModelName = 'text-embedding-3-small'
  AND VECTOR_DISTANCE('cosine', Embedding, @q) < 0.45  -- threshold: tune on evals
ORDER BY Distance;

# Python — SQL Server retrieve + local cross-encoder rerank
import pyodbc
from sentence_transformers import CrossEncoder

conn = pyodbc.connect("DRIVER={ODBC Driver 18 for SQL Server};"
                      "SERVER=localhost;DATABASE=ragdb;Trusted_Connection=yes;"
                      "Encrypt=yes;TrustServerCertificate=yes")
reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

def sqlserver_retrieve_and_rerank(question, question_emb,
                                  candidate_k=50, top_n=5,
                                  max_distance=0.45, tenant_id=1):
    vec = "[" + ",".join(str(v) for v in question_emb) + "]"
    cur = conn.cursor()
    cur.execute("""SELECT TOP (?) ChunkId, ChunkText,
                          VECTOR_DISTANCE('cosine', Embedding,
                              CAST(? AS VECTOR(1536))) AS Distance
                   FROM dbo.DocumentChunks
                   WHERE TenantId = ? AND ModelName = 'text-embedding-3-small'
                     AND VECTOR_DISTANCE('cosine', Embedding,
                             CAST(? AS VECTOR(1536))) < ?
                   ORDER BY Distance""",
                (candidate_k, vec, tenant_id, vec, max_distance))
    candidates = [{"id": r[0], "text": r[1], "distance": r[2]}
                  for r in cur.fetchall()]
    if not candidates:
        return []   # threshold refused: better no answer than a bad one
    scores = reranker.predict([[question, c["text"]] for c in candidates])
    ranked = sorted(zip(candidates, scores),
                    key=lambda x: x[1], reverse=True)[:top_n]
    return [{"id": c["id"], "text": c["text"],
             "rerank_score": float(s), "vector_distance": c["distance"]}
            for c, s in ranked]

The distance threshold deserves emphasis: it is your cheapest quality control. Candidates beyond the threshold are so dissimilar that reranking them wastes inference budget and risks promoting a fluent-but-irrelevant chunk. Tune the threshold on your eval set (Chapter 22.8) — it is the one number that most directly trades "answered questions" against "answer quality."

25.5 LLM-Based Re-ranking and Reciprocal Rank Fusion

A cross-encoder scores query-document pairs; an LLM reranker goes further and judges them. Prompt the LLM with the query plus numbered candidates and ask it to return the best ordering with brief justifications. Quality is excellent — the LLM understands nuance no cross-encoder captures — but cost and latency are an order of magnitude higher, so reserve LLM reranking for the final ordering of an already-reranked top-10, or for offline eval-set grading.

Reciprocal Rank Fusion (RRF) solves a different problem: combining rankings from multiple retrieval paths. Your hybrid search (Chapter 11) produces a vector ranking and a full-text ranking that disagree; RRF merges them without needing comparable scores:

-- SQL Server: Reciprocal Rank Fusion over vector + full-text rankings
-- Each CTE ranks the same candidate pool by a different signal (1 = best).
-- RRF score = SUM(1 / (k + rank)); k = 60 is the standard constant.
DECLARE @q VECTOR(1536) = '[0.12, 0.87, ...]';

WITH VectorRank AS (
    SELECT ChunkId, ROW_NUMBER() OVER (
        ORDER BY VECTOR_DISTANCE('cosine', Embedding, @q)) AS rnk
    FROM dbo.DocumentChunks WHERE TenantId = @tenant
),
TextRank AS (
    SELECT ChunkId, ROW_NUMBER() OVER (
        ORDER BY RANK DESC) AS rnk
    FROM CONTAINSTABLE(dbo.DocumentChunks, ChunkText, @keywords)
)
SELECT COALESCE(v.ChunkId, t.ChunkId) AS ChunkId,
       1.0 / (60 + COALESCE(v.rnk, 1000))
       + 1.0 / (60 + COALESCE(t.rnk, 1000)) AS RrfScore
FROM VectorRank AS v
FULL OUTER JOIN TextRank AS t ON t.ChunkId = v.ChunkId
ORDER BY RrfScore DESC;
-- Feed the top RRF results into the cross-encoder for final ordering.

The pipeline order that works in production: hybrid retrieval → RRF fusion → cross-encoder rerank of the fused top-50 → top-5 to the LLM. Each stage narrows the candidate set while increasing the scoring precision, so total latency stays bounded.

25.6 Production Patterns: Latency, Caching, and Model Selection

  • → Budget the stages. Retrieval 5–15ms, rerank 80–200ms, generation seconds. Reranking is never the bottleneck — but cap candidate count (50, not 200) so a slow reranker cannot blow the SLA.
  • → Cache rerank decisions. Frequent questions rerank the same candidates identically. Cache the final top-5 per (question hash, corpus version) — Chapter 33 covers semantic caching, which extends this to paraphrased questions.
  • → Choose the reranker by volume. Under ~100 QPS, local cross-encoder on CPU is cheapest. Above that, compare GPU inference cost against Cohere Rerank API pricing at your actual candidate counts — the crossover surprises most teams.
  • → Version the reranker with the corpus. A reranker upgrade changes ordering; a corpus re-chunk changes candidates. Deploy them behind the same feature flag and measure the eval set before and after.

    25.7 Evaluating Re-ranking Quality

    Measure reranking with the same eval set you use for chunking (Chapter 22.8), scored at two cutoffs: hit rate at top-5 before reranking (vector retrieval alone) and after (reranked order). The delta is the reranker's contribution. Track it per query type — rerankers help most on ambiguous queries where the vector ranking is flat, and least on exact-match queries where the vector ranking is already correct.

    # Python — measure reranker lift on an eval set
def evaluate_reranker(eval_set, embed_fn, top_n=5):
    pre_hits = post_hits = 0
    for q in eval_set:
        q_emb = embed_fn(q["question"])
        cands = sqlserver_retrieve(q_emb, top_k=50)          # Stage 1
        pre_hits += any(q["expected"] in c["text"] for c in cands[:top_n])
        ranked = rerank(q["question"], cands, top_n=top_n)   # Stage 2
        post_hits += any(q["expected"] in r["text"] for r in ranked)
    n = len(eval_set)
    return {"vector_only": pre_hits / n, "reranked": post_hits / n,
            "lift": (post_hits - pre_hits) / n}

# Typical result: vector_only=0.62, reranked=0.78, lift=+0.16
# If lift < 0.05, your reranker is not earning its latency: check the
# candidate count, the distance threshold, and whether the eval questions
# match production query distribution.

    25.8 End-to-End Pipeline: SQL Server + Cross-Encoder + RAG Generation

    Putting it together — a complete RAG query path with per-stage latency instrumentation:

    # Python — full RAG pipeline: SQL Server retrieval, cross-encoder
# rerank, LLM generation, with per-stage timing
import time, pyodbc, openai
from sentence_transformers import CrossEncoder

openai_client = openai.OpenAI()
conn = pyodbc.connect("DRIVER={ODBC Driver 18 for SQL Server};"
                      "SERVER=localhost;DATABASE=ragdb;Trusted_Connection=yes;"
                      "Encrypt=yes;TrustServerCertificate=yes")
reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

def rag_answer(question, tenant_id=1, top_n=5):
    stages = {}
    # --- Stage 1: embed the question ---
    t0 = time.perf_counter()
    q_emb = openai_client.embeddings.create(
        input=[question], model="text-embedding-3-small").data[0].embedding
    stages["embed_ms"] = (time.perf_counter() - t0) * 1000
    # --- Stage 2: ANN retrieval from SQL Server ---
    t0 = time.perf_counter()
    candidates = sqlserver_retrieve_and_rerank(
        question, q_emb, candidate_k=50, top_n=top_n, tenant_id=tenant_id)
    stages["retrieve_rerank_ms"] = (time.perf_counter() - t0) * 1000
    if not candidates:
        return {"answer": "I don't have information about that.",
                "stages": stages, "sources": []}
    # --- Stage 3: generate with retrieved context ---
    context = "\n\n".join(f"[{c['id']}] {c['text']}" for c in candidates)
    t0 = time.perf_counter()
    completion = openai_client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {"role": "system",
             "content": "Answer using only the provided context. "
                        "Cite sources as [id]. If the context does not "
                        "contain the answer, say so."},
            {"role": "user",
             "content": f"Context:\n{context}\n\nQuestion: {question}"}])
    stages["generate_ms"] = (time.perf_counter() - t0) * 1000
    return {"answer": completion.choices[0].message.content,
            "stages": stages,
            "sources": [c["id"] for c in candidates]}

result = rag_answer(
    "What is the difference between REORGANIZE and REBUILD for index maintenance?",
    tenant_id=7)
print(result["stages"])   # e.g. embed_ms=180, retrieve_rerank_ms=210, ...
print(result["answer"])

    This pipeline produces an answer with cited sources, full latency instrumentation per stage, and a clean separation between retrieval, re-ranking, and generation that allows each component to be swapped independently — for example, replacing the local cross-encoder with Cohere Rerank, or replacing SQL Server with a dedicated vector engine, without touching the generation layer.

    ---

    Key Takeaways

  • → Reranking is a two-stage retrieval: the vector index optimizes recall over the corpus, the reranker optimizes precision over 50–200 candidates. It is the highest quality-per-millisecond improvement in most RAG pipelines.
  • → SQL Server owns recall (tenant-filtered top-50 with a distance threshold); the cross-encoder or Cohere Rerank owns the final ordering. Keep that boundary clean.
  • → Fuse hybrid rankings with Reciprocal Rank Fusion in T-SQL before reranking: RRF merges vector and full-text orderings without comparable scores.
  • → Tune the distance threshold on your eval set — it is the cheapest quality control you have, and it keeps irrelevant candidates out of paid rerank calls.
  • → Measure reranker lift (hit rate before vs after) per query type; if lift is under ~5 points, fix candidate count, threshold, or eval distribution before blaming the model.
