Chapter 18: Chroma: Local-First Vector DB for Development

Chroma occupies a unique position in the vector database landscape: it is the tool developers reach for first, the one that runs in a Python process with zero infrastructure, and the one that disappears from the conversation the moment a team decides to move to production. That reputation is both earned and slightly unfair. Chroma is a genuinely capable vector store that handles millions of embeddings, supports persistent disk-backed storage, and can run as a standalone server with a client/server split that mirrors how teams actually work. What it lacks is the operational maturity of Pinecone or Weaviate — but for local development, rapid prototyping, and small-to-medium deployments where you control the machine, it is often the most productive choice. This chapter covers Chroma's architecture, its embedding and collection model, persistent versus in-memory operation, querying patterns that transfer directly to production systems, and the specific scenarios where Chroma remains the right answer even after your application ships.

---

18.1 Chroma's Architecture: An Embedded Database Perspective

Database professionals will recognize Chroma's design immediately once you map it to familiar concepts. Chroma is, at its core, an embedded vector database in the same lineage as SQLite — it runs inside your process, writes to a local directory, and requires no separate daemon. This is its defining characteristic and the source of both its appeal and its limitations.

The storage model

Chroma uses a layered storage architecture. The vector index is backed by HNSW (Hierarchical Navigable Small World), the same algorithm used internally by Weaviate, Qdrant, and Milvus. Metadata and document text are stored in DuckDB in versions prior to 0.4, and in Chroma's own embedded SQLite-based system in the 0.4+ architecture. This separation — vectors in an HNSW structure, metadata in a columnar or relational store — mirrors what you see in every production vector database. Chroma just makes the layers visible in a single local directory.

The chroma directory after initialization looks like this:

# shell
ls -la ./chroma_data/
# chroma.sqlite3          <- metadata, collections, embeddings catalog
# <uuid>/                 <- one directory per collection
#   data_level0.bin       <- HNSW graph (bottom layer, all nodes)
#   header.bin            <- index parameters
#   length.bin            <- node count
#   link_lists.bin        <- HNSW upper-layer links

If you have managed SQL Server databases, think of chroma.sqlite3 as the system catalog and the HNSW binary files as a specialized index tablespace. The collection UUID directory is analogous to a table's data files — the collection is the primary organizing unit in Chroma, equivalent to a table with a mandatory vector column and optional metadata columns.

Collections as tables

A Chroma collection holds:

  • → **IDs** — string primary keys (you supply these, no auto-increment)
  • → **embeddings** — float arrays of fixed dimension (dimensionality is inferred from the first insert)
  • → **documents** — optional raw text (the source that was embedded)
  • → **metadatas** — optional key/value dictionaries (analogous to non-indexed columns)

    • The dimension constraint works like a typed column: once you insert a 1536-dimensional embedding, every subsequent insert must match. Mixing models is a schema violation Chroma enforces at insert time.

    Client modes

    Chroma supports three operational modes that map to a deployment progression:

    | Mode | Use Case | Analogy |

    |------|----------|---------|

    | Ephemeral (in-memory) | Unit tests, notebooks | :memory: SQLite |

    | Persistent (embedded) | Local dev, single-process apps | File-based SQLite |

    | Client/Server (HTTP) | Multi-process, shared dev environment | Separate DB server |

    Most tutorials show only the ephemeral mode. Production-adjacent usage requires understanding the persistent and client/server modes, which this chapter covers in detail.

    18.2 Getting Started: Collections, Embeddings, and Basic Queries

    Install Chroma with its default dependencies, which include the HNSW library and sentence-transformers for local embedding generation:

    # shell
pip install chromadb sentence-transformers openai
# For the server mode:
pip install "chromadb[server]"

    Ephemeral client (testing and notebooks)

    # Python
import chromadb

# In-memory client — resets on process exit
client = chromadb.EphemeralClient()

# Create a collection with cosine similarity (default is L2)
collection = client.create_collection(
    name="product_docs",
    metadata={"hnsw:space": "cosine"}
)

# Add documents — Chroma uses its default embedding function if you don't specify one
# Default is all-MiniLM-L6-v2 via sentence-transformers (384 dimensions)
collection.add(
    documents=[
        "SQL Server supports JSON in NVARCHAR columns for semi-structured data",
        "SQL Server 2025 adds native vector similarity search",
        "Chroma is an open-source embedding database",
        "HNSW indexing provides approximate nearest neighbor search",
        "RAG pipelines combine retrieval with language model generation",
    ],
    ids=["doc_001", "doc_002", "doc_003", "doc_004", "doc_005"],
    metadatas=[
        {"source": "db_docs", "category": "database"},
        {"source": "db_docs", "category": "vector"},
        {"source": "chroma_docs", "category": "vector"},
        {"source": "research", "category": "algorithms"},
        {"source": "ml_docs", "category": "architecture"},
    ]
)

# Query — Chroma embeds the query text automatically using the same function
results = collection.query(
    query_texts=["how does vector similarity search work?"],
    n_results=3,
    include=["documents", "metadatas", "distances"]
)

for i, (doc, meta, dist) in enumerate(zip(
    results["documents"][0],
    results["metadatas"][0],
    results["distances"][0]
)):
    print(f"Rank {i+1} | Distance: {dist:.4f} | Source: {meta['source']}")
    print(f"  {doc}\n")

    The include parameter controls what Chroma returns — omit "embeddings" unless you need the raw vectors, since returning full embedding arrays for large result sets is expensive.

    Persistent client with metadata filtering

    # Python
import chromadb
from chromadb.utils import embedding_functions

# Persistent client — survives process restart
client = chromadb.PersistentClient(path="./chroma_data")

# Use OpenAI embeddings instead of the default local model
openai_ef = embedding_functions.OpenAIEmbeddingFunction(
    api_key="sk-...",          # or read from env: os.environ["OPENAI_API_KEY"]
    model_name="text-embedding-3-small"  # 1536 dimensions
)

# get_or_create is idempotent — safe to call on restart
collection = client.get_or_create_collection(
    name="engineering_kb",
    embedding_function=openai_ef,
    metadata={"hnsw:space": "cosine"}
)

# Batch insert — Chroma handles the embedding calls internally
documents = [
    "Connection pooling reduces database overhead by reusing connections",
    "Read replicas distribute query load across multiple database instances",
    "Partitioning splits large tables into smaller, manageable segments",
    "Index rebuild reclaims space from fragmented indexes in SQL Server",
    "The transaction log ensures durability and enables replication",
]
ids = [f"kb_{i:04d}" for i in range(len(documents))]
metadatas = [
    {"topic": "performance", "db": "general"},
    {"topic": "scaling", "db": "general"},
    {"topic": "storage", "db": "general"},
    {"topic": "maintenance", "db": "sqlserver"},
    {"topic": "reliability", "db": "sqlserver"},
]

collection.add(documents=documents, ids=ids, metadatas=metadatas)

# Query with metadata filter — equivalent to WHERE clause
results = collection.query(
    query_texts=["how to improve query performance?"],
    n_results=3,
    where={"db": "sqlserver"},          # metadata filter
    include=["documents", "metadatas", "distances"]
)

print(f"Found {len(results['ids'][0])} results filtered to SQL Server topics:")
for doc, meta, dist in zip(
    results["documents"][0],
    results["metadatas"][0],
    results["distances"][0]
):
    print(f"  [{meta['topic']}] dist={dist:.4f}: {doc[:60]}...")

    The where clause supports operators that map directly to SQL predicates:

    # Python
# Single condition
where={"category": "vector"}

# AND condition
where={"$and": [{"category": "vector"}, {"source": "db_docs"}]}

# OR condition
where={"$or": [{"db": "sqlserver"}, {"db": "general"}]}

# Comparison operators
where={"score": {"$gte": 0.8}}          # score >= 0.8
where={"year": {"$in": [2023, 2024]}}   # year IN (2023, 2024)
where={"status": {"$ne": "archived"}}   # status != 'archived'

    For DBA readers: these operators compile down to SQLite predicates against the metadata store before the HNSW search executes. Pre-filtering on metadata is more efficient than post-filtering large result sets, particularly when the metadata column has high cardinality.

    18.3 Embedding Functions: Wiring Chroma to Your Model Layer

    Chroma's embedding function abstraction is one of its more thoughtful design decisions. Rather than requiring you to compute embeddings externally and pass float arrays, Chroma lets you attach an embedding function to a collection and then work exclusively with text. The function is called transparently during add() and query().

    Built-in embedding functions

    # Python
from chromadb.utils import embedding_functions

# 1. Default: all-MiniLM-L6-v2 (384-dim, runs locally, no API key needed)
default_ef = embedding_functions.DefaultEmbeddingFunction()

# 2. OpenAI — text-embedding-3-small (1536-dim) or text-embedding-3-large (3072-dim)
openai_ef = embedding_functions.OpenAIEmbeddingFunction(
    api_key="sk-...",
    model_name="text-embedding-3-small"
)

# 3. Cohere — good multilingual support
cohere_ef = embedding_functions.CohereEmbeddingFunction(
    api_key="...",
    model_name="embed-english-v3.0"
)

# 4. Sentence Transformers — local, no API costs, many model choices
st_ef = embedding_functions.SentenceTransformerEmbeddingFunction(
    model_name="BAAI/bge-large-en-v1.5"  # 1024-dim, strong retrieval performance
)

# 5. HuggingFace Inference API — cloud-hosted open models
hf_ef = embedding_functions.HuggingFaceEmbeddingFunction(
    api_key="hf_...",
    model_name="sentence-transformers/all-mpnet-base-v2"
)

    Custom embedding function for Azure OpenAI or AWS Bedrock

    When your organization's models are hosted on enterprise AI platforms, you write a custom embedding function by subclassing EmbeddingFunction:

    # Python
import numpy as np
from chromadb import EmbeddingFunction, Documents, Embeddings
import boto3
import json

class BedrockEmbeddingFunction(EmbeddingFunction):
    """Chroma embedding function backed by Amazon Bedrock Titan Embeddings."""

    def __init__(self, region_name: str = "us-east-1"):
        self.client = boto3.client("bedrock-runtime", region_name=region_name)
        self.model_id = "amazon.titan-embed-text-v1"

    def __call__(self, input: Documents) -> Embeddings:
        embeddings = []
        for text in input:
            body = json.dumps({"inputText": text})
            response = self.client.invoke_model(
                modelId=self.model_id,
                body=body,
                contentType="application/json",
                accept="application/json"
            )
            result = json.loads(response["body"].read())
            embeddings.append(result["embedding"])
        return embeddings


class AzureOpenAIEmbeddingFunction(EmbeddingFunction):
    """Chroma embedding function backed by Azure OpenAI."""

    def __init__(
        self,
        azure_endpoint: str,
        api_key: str,
        deployment_name: str,
        api_version: str = "2024-02-01"
    ):
        from openai import AzureOpenAI
        self.client = AzureOpenAI(
            azure_endpoint=azure_endpoint,
            api_key=api_key,
            api_version=api_version
        )
        self.deployment_name = deployment_name

    def __call__(self, input: Documents) -> Embeddings:
        # Azure OpenAI supports batch embedding — send all texts at once
        response = self.client.embeddings.create(
            input=input,
            model=self.deployment_name
        )
        # Sort by index to preserve order
        sorted_data = sorted(response.data, key=lambda x: x.index)
        return [item.embedding for item in sorted_data]


# Usage
bedrock_ef = BedrockEmbeddingFunction(region_name="us-west-2")
azure_ef = AzureOpenAIEmbeddingFunction(
    azure_endpoint="https://your-resource.openai.azure.com",
    api_key="...",
    deployment_name="text-embedding-3-small"
)

client = chromadb.PersistentClient(path="./chroma_data")
collection = client.get_or_create_collection(
    name="enterprise_docs",
    embedding_function=azure_ef,
    metadata={"hnsw:space": "cosine"}
)

    A dimension mismatch is a hard schema error. If you create a collection with text-embedding-3-small (1536 dimensions) and later try to query it with a custom function that returns 768-dimensional vectors, Chroma raises a ValueError at query time. There is no silent dimension reduction. Treat the embedding function attached to a collection as a schema constraint — document it alongside your collection metadata.

    18.4 Client/Server Mode and LangChain Integration

    Running Chroma as a server unlocks multi-process access, which is the minimum viable architecture for any application with a web server, background workers, and a database — they cannot all share an embedded client safely. The server exposes a FastAPI HTTP interface, and the Python client speaks to it over HTTP.

    Starting the Chroma server

    # shell
# Install with server dependencies
pip install "chromadb[server]"

# Start server on default port 8000
chroma run --path ./chroma_data --host 0.0.0.0 --port 8000

# Or with Docker — useful for CI and team shared environments
docker run -d \
  --name chroma \
  -p 8000:8000 \
  -v $(pwd)/chroma_data:/chroma/chroma \
  -e IS_PERSISTENT=TRUE \
  chromadb/chroma:latest

# Verify the server is running
curl http://localhost:8000/api/v1/heartbeat
# {"nanosecond heartbeat": 1234567890}

curl http://localhost:8000/api/v1/collections
# Returns list of existing collections as JSON

    Connecting from Python (client/server mode)

    # Python
import chromadb

# HTTP client — connects to running Chroma server
client = chromadb.HttpClient(
    host="localhost",
    port=8000,
    # Optional: add auth headers if you've configured Chroma with token auth
    # settings=chromadb.Settings(chroma_client_auth_provider="token",
    #                            chroma_client_auth_credentials="secret-token")
)

# Everything else is identical to the embedded client API
collection = client.get_or_create_collection(
    name="shared_collection",
    metadata={"hnsw:space": "cosine"}
)

# Test round-trip
collection.add(
    documents=["Server mode enables multi-process access to Chroma"],
    ids=["server_test_001"]
)

count = collection.count()
print(f"Collection contains {count} documents")

results = collection.query(
    query_texts=["multi-process database access"],
    n_results=1
)
print(results["documents"][0])

    LangChain integration

    LangChain treats Chroma as a VectorStore, which means you can swap it for Pinecone or Weaviate by changing two lines. This is exactly the abstraction you want during development — build against Chroma, promote to a production vector database without rewriting retrieval logic.

    # Python
from langchain_community.vectorstores import Chroma
from langchain_openai import OpenAIEmbeddings
from langchain_core.documents import Document
import chromadb

# Option 1: Let LangChain manage the Chroma client (simple case)
embedding_function = OpenAIEmbeddings(model="text-embedding-3-small")

vectorstore = Chroma(
    collection_name="langchain_demo",
    embedding_function=embedding_function,
    persist_directory="./chroma_langchain_data"
)

# Add LangChain Document objects (they carry page_content and metadata)
docs = [
    Document(
        page_content="Indexes in SQL Server speed up query execution by reducing full table scans",
        metadata={"source": "mssql_manual", "chapter": "11", "topic": "indexing"}
    ),
    Document(
        page_content="B-tree indexes are the default index type in SQL Server",
        metadata={"source": "mssql_manual", "chapter": "11", "topic": "indexing"}
    ),
    Document(
        page_content="Full-text indexes are optimal for CONTAINS and FREETEXT queries on text columns",
        metadata={"source": "mssql_manual", "chapter": "11", "topic": "indexing"}
    ),
    Document(
        page_content="Filtered indexes include only rows matching a WHERE condition",
        metadata={"source": "mssql_manual", "chapter": "11", "topic": "indexing"}
    ),
]

vectorstore.add_documents(docs)

# Similarity search — returns Documents ranked by relevance
query = "what index type should I use for text search?"
similar_docs = vectorstore.similarity_search(query, k=2)
for doc in similar_docs:
    print(f"[{doc.metadata['topic']}] {doc.page_content}")

# Similarity search with scores
docs_with_scores = vectorstore.similarity_search_with_score(query, k=2)
for doc, score in docs_with_scores:
    print(f"Score: {score:.4f} | {doc.page_content[:60]}...")

# Option 2: Connect LangChain to a running Chroma server
http_client = chromadb.HttpClient(host="localhost", port=8000)

server_vectorstore = Chroma(
    client=http_client,
    collection_name="langchain_server_collection",
    embedding_function=embedding_function
)

# Use as a retriever in a RAG chain
retriever = server_vectorstore.as_retriever(
    search_type="similarity",
    search_kwargs={"k": 4, "filter": {"topic": "indexing"}}
)

# The retriever works with any LangChain chain
retrieved = retriever.invoke("how do partial indexes work?")
for doc in retrieved:
    print(doc.page_content)

    The as_retriever() call is the bridge to the full LangChain ecosystem — you can pass this retriever directly to RetrievalQA, ConversationalRetrievalChain, or LangGraph nodes without modification.

    18.5 HNSW Tuning, Scaling Limits, and When to Graduate

    Chroma exposes HNSW parameters through collection metadata. Understanding these parameters gives you control over the precision/performance tradeoff that every vector index presents — the same tradeoff exists in SQL Server's DiskANN configuration and Weaviate's HNSW configuration.

    HNSW parameters exposed by Chroma

    # Python
import chromadb

client = chromadb.PersistentClient(path="./chroma_data")

# Create collection with explicit HNSW tuning
collection = client.get_or_create_collection(
    name="tuned_collection",
    metadata={
        "hnsw:space": "cosine",        # Distance metric: cosine, l2, ip (inner product)
        "hnsw:construction_ef": 200,   # Candidates examined during index build (default: 100)
        "hnsw:search_ef": 100,         # Candidates examined during search (default: 10)
        "hnsw:M": 32,                  # Connections per node in graph (default: 16)
        "hnsw:num_threads": 4,         # Parallel threads for index operations
        "hnsw:resize_factor": 1.2,     # Growth factor when index needs to expand
        "hnsw:batch_size": 100,        # Vectors per batch during construction
        "hnsw:sync_threshold": 1000,   # Flush to disk after N mutations
    }
)

    Parameter guidance from database operations experience:

    | Parameter | Default | When to Increase | Memory Impact |

    |-----------|---------|-----------------|---------------|

    | hnsw:M | 16 | Recall < 0.90, dataset > 100K | ~2x at M=32 |

    | hnsw:construction_ef | 100 | Recall < 0.95 at query time | Index build time only |

    | hnsw:search_ef | 10 | Recall < 0.90 in production | Per-query CPU |

    | hnsw:num_threads | 1 | Batch ingestion too slow | None (CPU only) |

    The key insight: hnsw:construction_ef affects index quality permanently. hnsw:search_ef can be tuned per-query without rebuilding the index. If you index with construction_ef=100 and find recall is poor, you must rebuild — there is no online reindex in Chroma.

    Measuring recall and query performance

    # Python
import chromadb
import time
import numpy as np
from chromadb.utils import embedding_functions

def benchmark_chroma_collection(
    collection,
    query_texts: list[str],
    n_results: int = 10
) -> dict:
    """
    Basic benchmark for Chroma query latency and result consistency.
    In production you'd compare against brute-force results for recall measurement.
    """
    latencies = []

    for query in query_texts:
        start = time.perf_counter()
        results = collection.query(
            query_texts=[query],
            n_results=n_results,
            include=["distances"]
        )
        elapsed_ms = (time.perf_counter() - start) * 1000
        latencies.append(elapsed_ms)

    latency_array = np.array(latencies)
    return {
        "n_queries": len(query_texts),
        "p50_ms": np.percentile(latency_array, 50),
        "p95_ms": np.percentile(latency_array, 95),
        "p99_ms": np.percentile(latency_array, 99),
        "mean_ms": latency_array.mean(),
        "collection_size": collection.count(),
    }


# Example usage
client = chromadb.PersistentClient(path="./chroma_data")
col = client.get_collection("tuned_collection")

test_queries = [
    "vector similarity search algorithms",
    "SQL Server index optimization",
    "RAG pipeline architecture",
    "distributed database scaling",
    "embedding model selection",
]

stats = benchmark_chroma_collection(col, test_queries)
print(f"Collection size: {stats['collection_size']:,}")
print(f"P50 latency:  {stats['p50_ms']:.1f} ms")
print(f"P95 latency:  {stats['p95_ms']:.1f} ms")
print(f"P99 latency:  {stats['p99_ms']:.1f} ms")

    Scaling limits and the graduation decision

    Chroma does not publish hard row limits, but practical experience with HNSW implementations establishes soft boundaries that matter for planning:

  • → **Under 500K vectors:** Chroma is indistinguishable from production vector databases in most workloads. Latency stays in single-digit milliseconds on commodity hardware with tuned `hnsw:search_ef`.
  • → **500K to 2M vectors:** Performance degrades predictably — HNSW memory footprint grows, and single-node Chroma cannot distribute the index across machines. Query latency at P99 becomes notable.
  • → **Above 2M vectors:** Chroma is a wrong-size tool. The HNSW index lives entirely in RAM; a 2M vector collection at 1536 dimensions requires roughly 12 GB of RAM for the index alone (float32 × 1536 × 2M ≈ 12 GB), before the graph structure overhead.

    • The other signals that indicate it is time to graduate from Chroma:

    1. Multiple services need concurrent read/write access — Chroma's server mode works, but it has no connection pooling, no query planner, and no replication.

    2. You need filtered search at scale — Chroma's pre-filtering approach works well when the metadata filter is highly selective; it degrades when filters are loose and the HNSW graph still needs to scan large subgraphs.

    3. SLA requirements exist — Chroma has no built-in monitoring, no replication lag metrics, and no managed backup. Operationalizing it requires wrapping it with infrastructure you build yourself.

    4. You need multi-tenancy — Chroma's collection-per-tenant model works at small tenant counts; at hundreds of tenants, the collection overhead becomes unwieldy.

    5. Your team needs audit logs or access control — Chroma has no row-level security, no audit trail, and only token-level authentication in server mode.

    None of these limitations are criticisms of Chroma's design philosophy. It is an embedded database, and embedded databases are not wrong tools — they are differently scoped tools.

    18.6 Real RAG Pipeline with Chroma: End-to-End Example

    This section assembles the concepts from earlier in the chapter into a complete, runnable RAG pipeline. The pattern here — document loading, chunking, embedding, storage, retrieval, generation — is identical regardless of which vector database backs the retrieval step.

    graph LR
    subgraph "Ingestion"
        A[Load documents] --> B[Chunk text]
        B --> C[Embed chunks]
        C --> D[(Chroma collection)]
    end
    subgraph "Query time"
        E[User question] --> F[Embed question]
        F --> G[Query Chroma]
        D -.-> G
        G --> H[Retrieved chunks]
        H --> I[Assemble prompt]
        I --> J[LLM generation]
        J --> K[Answer + sources]
    end

    *Ingestion (top) populates the Chroma collection once per document set; query time (bottom) embeds the question, retrieves the nearest chunks, and passes them to the LLM as grounding context.*

    # Python
import chromadb
from chromadb.utils import embedding_functions
from openai import OpenAI
import hashlib
import textwrap
from typing import Optional

# ── Configuration ────────────────────────────────────────────────────────────
CHROMA_PATH = "./rag_chroma_data"
COLLECTION_NAME = "technical_kb"
EMBEDDING_MODEL = "text-embedding-3-small"
GENERATION_MODEL = "gpt-4o-mini"
CHUNK_SIZE = 400          # characters per chunk
CHUNK_OVERLAP = 80        # overlap between consecutive chunks
TOP_K = 4                 # number of chunks to retrieve


# ── Chunking ─────────────────────────────────────────────────────────────────
def chunk_text(text: str, chunk_size: int, overlap: int) -> list[str]:
    """
    Naive fixed-size chunking with overlap.
    In production, prefer semantic chunking or recursive character splitting.
    """
    chunks = []
    start = 0
    while start < len(text):
        end = start + chunk_size
        chunks.append(text[start:end].strip())
        start += chunk_size - overlap
    return [c for c in chunks if len(c) > 50]  # drop tiny tail chunks


def doc_id(source: str, chunk_index: int) -> str:
    """Deterministic ID so re-ingestion is idempotent via upsert."""
    raw = f"{source}::{chunk_index}"
    return hashlib.md5(raw.encode()).hexdigest()


# ── Ingestion ─────────────────────────────────────────────────────────────────
def ingest_documents(
    collection: chromadb.Collection,
    documents: list[dict],   # each: {"text": str, "source": str, "category": str}
    chunk_size: int = CHUNK_SIZE,
    overlap: int = CHUNK_OVERLAP
) -> int:
    """
    Chunk and upsert documents into a Chroma collection.
    Returns total chunks ingested.
    """
    all_ids, all_docs, all_metas = [], [], []

    for doc in documents:
        chunks = chunk_text(doc["text"], chunk_size, overlap)
        for i, chunk in enumerate(chunks):
            all_ids.append(doc_id(doc["source"], i))
            all_docs.append(chunk)
            all_metas.append({
                "source": doc["source"],
                "category": doc["category"],
                "chunk_index": i,
                "total_chunks": len(chunks),
            })

    # Upsert is idempotent — safe to call on re-ingestion
    collection.upsert(
        documents=all_docs,
        ids=all_ids,
        metadatas=all_metas
    )
    return len(all_ids)


# ── Retrieval ─────────────────────────────────────────────────────────────────
def retrieve(
    collection: chromadb.Collection,
    query: str,
    k: int = TOP_K,
    category_filter: Optional[str] = None
) -> list[dict]:
    """
    Retrieve top-k chunks relevant to the query, with optional category filter.
    Returns list of dicts with keys: text, source, distance.
    """
    where = {"category": category_filter} if category_filter else None

    results = collection.query(
        query_texts=[query],
        n_results=k,
        where=where,
        include=["documents", "metadatas", "distances"]
    )

    chunks = []
    for doc, meta, dist in zip(
        results["documents"][0],
        results["metadatas"][0],
        results["distances"][0]
    ):
        chunks.append({
            "text": doc,
            "source": meta["source"],
            "category": meta["category"],
            "distance": dist,
        })
    return chunks


# ── Generation ────────────────────────────────────────────────────────────────
def generate_answer(
    openai_client: OpenAI,
    query: str,
    context_chunks: list[dict],
    model: str = GENERATION_MODEL
) -> str:
    """
    Generate a grounded answer using retrieved context.
    """
    context_text = "\n\n---\n\n".join(
        f"[Source: {c['source']}]\n{c['text']}"
        for c in context_chunks
    )

    system_prompt = textwrap.dedent("""
        You are a technical assistant answering questions about databases and AI systems.
        Answer using only the information in the provided context.
        If the context does not contain enough information, say so explicitly.
        Cite the source document for each claim you make.
    """).strip()

    user_message = f"""Context:
{context_text}

Question: {query}

Answer:"""

    response = openai_client.chat.completions.create(
        model=model,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_message},
        ],
        temperature=0.1,   # low temperature for factual retrieval tasks
        max_tokens=512,
    )
    return response.choices[0].message.content


# ── Pipeline assembly ─────────────────────────────────────────────────────────
def build_rag_pipeline():
    """Wire up the Chroma collection and OpenAI clients."""
    openai_client = OpenAI()  # reads OPENAI_API_KEY from environment

    openai_ef = embedding_functions.OpenAIEmbeddingFunction(
        model_name=EMBEDDING_MODEL
    )

    chroma_client = chromadb.PersistentClient(path=CHROMA_PATH)
    collection = chroma_client.get_or_create_collection(
        name=COLLECTION_NAME,
        embedding_function=openai_ef,
        metadata={"hnsw:space": "cosine"}
    )

    return openai_client, collection

    18.7 Migrating from Chroma to a Production Vector Database

    When the graduation signals from Section 18.5 appear, the migration path is straightforward because Chroma's API surface maps cleanly onto Pinecone, Weaviate, and SQL Server native vectors. The core operation is: read vectors and metadata from Chroma, write them to the target database.

    Exporting from Chroma

    # Python
import chromadb
import json

def export_chroma_collection(
    chroma_path: str,
    collection_name: str,
    output_path: str,
    batch_size: int = 500
) -> int:
    """
    Export all vectors, documents, and metadata from a Chroma collection
    to a newline-delimited JSON file for migration.
    """
    client = chromadb.PersistentClient(path=chroma_path)
    collection = client.get_collection(collection_name)

    total = collection.count()
    print(f"Exporting {total:,} documents from '{collection_name}'...")

    exported = 0
    with open(output_path, "w") as f:
        # Chroma does not support cursor-based pagination natively;
        # use offset/limit via get() for batch export
        offset = 0
        while offset < total:
            batch = collection.get(
                limit=batch_size,
                offset=offset,
                include=["embeddings", "documents", "metadatas"]
            )

            for record_id, embedding, document, metadata in zip(
                batch["ids"],
                batch["embeddings"],
                batch["documents"],
                batch["metadatas"]
            ):
                record = {
                    "id": record_id,
                    "embedding": embedding,
                    "document": document,
                    "metadata": metadata,
                }
                f.write(json.dumps(record) + "\n")
                exported += 1

            offset += batch_size
            print(f"  Exported {min(offset, total):,} / {total:,}", end="\r")

    print(f"\nExport complete: {exported:,} records written to {output_path}")
    return exported


# Export

    collection_name="engineering_kb",
    output_path="./migration_export.jsonl"

    Importing to SQL Server

    # Python
import json
import pyodbc

def to_vector_literal(embedding) -> str:
    return "[" + ",".join(str(v) for v in embedding) + "]"

def import_to_sqlserver(
    jsonl_path: str,
    connection_string: str,
    table_name: str,
    batch_size: int = 500
) -> int:
    """
    Load Chroma export into a SQL Server table with a native VECTOR column.
    Creates the table and a DiskANN index if they do not exist.
    """
    conn = pyodbc.connect(connection_string)
    cur = conn.cursor()

    # Inspect the first record to get the dimension
    with open(jsonl_path) as f:
        first = json.loads(f.readline())
    dim = len(first["embedding"])

    # Create table if it does not exist
    cur.execute(f"""
        IF OBJECT_ID('{table_name}', 'U') IS NULL
        CREATE TABLE {table_name} (
            id        NVARCHAR(100) NOT NULL CONSTRAINT PK_{table_name} PRIMARY KEY,
            embedding VECTOR({dim}) NOT NULL,
            document  NVARCHAR(MAX) NULL,
            metadata  NVARCHAR(MAX) NULL   -- JSON payload
        )
    """)
    cur.execute(f"""
        IF NOT EXISTS (SELECT 1 FROM sys.indexes WHERE name = '{table_name}_diskann_idx')
        CREATE VECTOR INDEX {table_name}_diskann_idx
            ON {table_name} (embedding)
            WITH (METRIC = 'cosine', TYPE = 'DiskANN', MAXDOP = 4)
    """)
    conn.commit()

    total_inserted = 0
    batch = []

    def flush(rows):
        # MERGE gives idempotent upserts: re-running the import updates rows
        cur.executemany(f"""
            MERGE {table_name} AS t
            USING (SELECT ? AS id, CAST(? AS VECTOR({dim})) AS embedding,
                          ? AS document, ? AS metadata) AS s
            ON t.id = s.id
            WHEN MATCHED THEN
                UPDATE SET embedding = s.embedding, document = s.document,
                           metadata = s.metadata
            WHEN NOT MATCHED THEN
                INSERT (id, embedding, document, metadata)
                VALUES (s.id, s.embedding, s.document, s.metadata);
        """, rows)
        conn.commit()

    with open(jsonl_path) as f:
        for line in f:
            record = json.loads(line)
            batch.append((
                record["id"],
                to_vector_literal(record["embedding"]),
                record["document"],
                json.dumps(record["metadata"])
            ))
            if len(batch) >= batch_size:
                flush(batch)
                total_inserted += len(batch)
                batch = []

    # Final batch
    if batch:
        flush(batch)
        total_inserted += len(batch)

    cur.close()
    conn.close()
    print(f"Imported {total_inserted:,} records into {table_name}")
    return total_inserted

    Importing to Pinecone

    # Python
import json
from pinecone import Pinecone, ServerlessSpec

def import_to_pinecone(
    jsonl_path: str,
    api_key: str,
    index_name: str,
    batch_size: int = 100
) -> int:
    """
    Load Chroma export into a Pinecone serverless index.
    """
    pc = Pinecone(api_key=api_key)

    # Infer dimension from first record
    with open(jsonl_path) as f:
        first = json.loads(f.readline())
    dim = len(first["embedding"])

    # Create index if it does not exist
    if index_name not in [idx.name for idx in pc.list_indexes()]:
        pc.create_index(
            name=index_name,
            dimension=dim,
            metric="cosine",
            spec=ServerlessSpec(cloud="aws", region="us-east-1")
        )

    index = pc.Index(index_name)
    total_upserted = 0
    batch = []

    with open(jsonl_path) as f:
        for line in f:
            record = json.loads(line)
            # Pinecone metadata values must be strings, numbers, booleans, or lists
            flat_metadata = {
                k: v for k, v in record["metadata"].items()
                if isinstance(v, (str, int, float, bool, list))
            }
            flat_metadata["document"] = record["document"]  # store text in metadata

            batch.append({
                "id": record["id"],
                "values": record["embedding"],
                "metadata": flat_metadata
            })

            if len(batch) >= batch_size:
                index.upsert(vectors=batch)
                total_upserted += len(batch)
                batch = []
                print(f"  Upserted {total_upserted:,} vectors", end="\r")

    if batch:
        index.upsert(vectors=batch)
        total_upserted += len(batch)

    print(f"\nImported {total_upserted:,} vectors into Pinecone index '{index_name}'")
    return total_upserted


# Import
import_to_pinecone(
    jsonl_path="./migration_export.jsonl",
    api_key="pcsk_...",
    index_name="engineering-kb"
)

    The migration scripts above re-use the embeddings stored in Chroma rather than re-embedding from scratch — a significant cost saving when the collection contains hundreds of thousands of documents. Re-embedding is only necessary when you switch to a different embedding model as part of the migration, which is a natural time to do so if you are upgrading from a local model to a higher-quality API model.

    18.8 Chroma in CI/CD: Testing Vector Features Without a Server

    One of Chroma's most underrated capabilities is its role in automated testing. Every team that builds RAG features eventually needs to test retrieval quality, embedding consistency, and metadata filtering logic without spinning up a full vector database service in CI. Chroma's ephemeral client makes this possible in a single pytest fixture.

    # Python — conftest.py
import pytest
import chromadb
from chromadb.utils import embedding_functions
import numpy as np


@pytest.fixture(scope="session")
def chroma_client():
    """Session-scoped in-memory Chroma client — no disk I/O, resets between test runs."""
    return chromadb.EphemeralClient()


@pytest.fixture(scope="function")
def empty_collection(chroma_client):
    """Function-scoped collection — isolated between individual tests."""
    col = chroma_client.get_or_create_collection(
        name=f"test_collection_{id(object())}",
        metadata={"hnsw:space": "cosine"}
    )
    yield col
    chroma_client.delete_collection(col.name)


@pytest.fixture(scope="session")
def deterministic_ef():
    """
    Deterministic embedding function for testing.
    Produces consistent embeddings so test results are reproducible.
    Uses a simple hash-based approach rather than a real model.
    """
    class HashEmbeddingFunction:
        def __call__(self, input):
            embeddings = []
            for text in input:
                # Seed numpy RNG with hash of text for reproducibility
                rng = np.random.default_rng(abs(hash(text)) % (2**32))
                emb = rng.standard_normal(384).astype(np.float32)
                emb = emb / np.linalg.norm(emb)   # normalize to unit sphere
                embeddings.append(emb.tolist())
            return embeddings

    return HashEmbeddingFunction()


@pytest.fixture(scope="session")

    These tests run in milliseconds — no network calls, no model inference (using the deterministic hash embedder), no external dependencies. They test the logic of your collection schema, filtering predicates, and upsert behavior. The deterministic embedding function is a deliberate choice: real embedding models are non-deterministic under different runtime environments (GPU vs. CPU, model version updates), so pinning embedding behavior for unit tests produces stable CI pipelines.

    For integration tests that actually exercise the embedding model, use a separate fixture that marks the tests with @pytest.mark.integration and skip them in standard CI runs:

    # Python

    Key Takeaways

  • → **Chroma is an embedded database first.** Its default operating mode — in-process, single-file, no daemon — makes it the fastest path from idea to working vector search, following the same philosophy as SQLite for relational data. Client/server mode extends this to multi-process deployments without changing the API surface.
  • → **The embedding function is a schema constraint.** Attaching an embedding function to a collection fixes both the dimensionality and the semantic space of that collection. Changing the model requires rebuilding the collection. Treat the embedding function choice with the same deliberateness you would apply to choosing a column type.
  • → **HNSW parameters set at construction time are permanent.** `hnsw:construction_ef` and `hnsw:M` cannot be changed without rebuilding the index. Set them based on your target recall before ingesting production data; `hnsw:search_ef` can be tuned at query time without rebuilding.
  • → **Graduation from Chroma is a data volume and operational maturity decision, not a capability gap.** The filtering, embedding, and retrieval patterns you build against Chroma are directly portable to SQL Server native vectors, Pinecone, and Weaviate. The migration scripts in this chapter preserve stored embeddings so you do not pay re-embedding costs at migration time.
  • → **Chroma's ephemeral client makes vector search testable in CI without infrastructure.** A deterministic embedding function combined with `EphemeralClient` produces fast, stable unit tests for collection schema, metadata filtering, and upsert logic. Reserve real embedding model calls for integration tests that run in pre-deployment stages.
