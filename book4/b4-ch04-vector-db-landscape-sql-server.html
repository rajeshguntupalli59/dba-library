Chapter 4 of 40 Vector Databases & AI

Chapter 4: The Vector Database Landscape: SQL Server Vectors, Pinecone, Weaviate, Qdrant, Chroma

The vector database market has grown from a niche corner of machine-learning infrastructure into a crowded field of managed services, open-source engines, and — most importantly for this book — native support inside the relational databases you already operate. That last development changed the selection calculus more than any single product launch. For years the default advice was: keep your operational data in SQL Server, ship embeddings to a specialized vector store, and synchronize the two. SQL Server 2025 makes "keep everything in one engine" a legitimate architecture for a large share of workloads, and the rest of this chapter maps the landscape with that option as the center of gravity.

The naming in this market is not always consistent. Some products are databases built specifically for vectors. Others are cloud services that abstract away the infrastructure entirely. And one — SQL Server 2025 — is the database you already know, with vectors added as a first-class data type. A practical map of the landscape will ground every infrastructure decision in the rest of this book.

---

SQL Server 2025 Native Vectors: The Relational Anchor

SQL Server 2025 introduced a native VECTOR(n) data type — a first-class column type supporting 1 to 1998 dimensions, stored in an optimized binary format and exposed as JSON. There is no extension to install, no separate process to run, and no new operational model to learn. If you can create a table and an index, you can store and search vectors.

Similarity search comes in two flavors. For exact nearest-neighbor search, the built-in VECTOR_DISTANCE function computes cosine, Euclidean, or dot-product distance between two vectors directly in T-SQL:

-- SQL Server 2025: native VECTOR type and exact similarity search
CREATE TABLE dbo.Products (
    ProductId   INT NOT NULL CONSTRAINT PK_Products PRIMARY KEY,
    Sku         NVARCHAR(50) NOT NULL UNIQUE,
    Name        NVARCHAR(200) NOT NULL,
    Category    NVARCHAR(50) NULL,
    Embedding   VECTOR(1536) NULL   -- OpenAI text-embedding-3-small dimensions
);

DECLARE @q VECTOR(1536) = '[0.012, -0.043, 0.071, ...]';  -- query embedding

-- Exact k-NN: computes distance to every row, 100% recall
SELECT TOP (10)
    ProductId, Sku, Name,
    VECTOR_DISTANCE('cosine', Embedding, @q) AS Distance
FROM dbo.Products
WHERE Category = 'running'          -- relational pre-filter, same query
ORDER BY Distance;

For larger collections, CREATE VECTOR INDEX builds an approximate nearest-neighbor index using the DiskANN algorithm — a graph-based index designed for SSD-backed, billion-scale vector search — and the VECTOR_SEARCH table-valued function queries it:

-- SQL Server 2025: DiskANN approximate index + VECTOR_SEARCH
CREATE VECTOR INDEX IX_Products_Embedding
ON dbo.Products (Embedding)
WITH (METRIC = 'cosine', TYPE = 'DiskANN');

DECLARE @q VECTOR(1536) = '[0.012, -0.043, 0.071, ...]';

-- Approximate k-NN through the vector index
SELECT t.ProductId, t.Name, s.distance
FROM VECTOR_SEARCH(
    TABLE     = dbo.Products AS t,
    COLUMN    = Embedding,
    SIMILAR_TO = @q,
    METRIC    = 'cosine',
    TOP_N     = 10
) AS s
ORDER BY s.distance;

The killer feature is the hybrid query in the first example: a relational predicate (WHERE Category = 'running') combined with vector ranking in a single T-SQL statement, planned by the same query optimizer that handles the rest of your workload. No synchronization pipeline between two systems, no second set of credentials, no separate backup story. Native vector support is also generally available in Azure SQL Database and Azure SQL Managed Instance, so the same code runs in the cloud with no changes.

Best for: teams already running SQL Server who want semantic search, recommendations, or RAG retrieval alongside their operational data; workloads up to millions of vectors; anyone who values transactions, joins, row-level security, and a single backup story over squeezing the last millisecond of ANN latency.

Pinecone: The Fully Managed Option

Pinecone is a fully managed, cloud-native vector database — no infrastructure to operate, no indexes to tune. You create an index, upsert vectors with metadata, and query. It supports hybrid dense-plus-sparse search, namespace-based multi-tenancy (each tenant gets a logical partition inside one index), and serverless tiers that scale to zero. Filtering on metadata is a true pre-filter against the index, which matters for selective predicates at scale.

The tradeoff is the classic SaaS bargain: you trade operational burden for pricing that scales with usage and data-residency constraints you do not control. There is also an architectural cost that teams underestimate — your embeddings now live in a second system. Every product row in SQL Server needs a corresponding vector in Pinecone, and the synchronization between the two (on insert, update, delete) is your code to write, monitor, and repair when it drifts.

# Python example — semantic search with Pinecone
from pinecone import Pinecone
from openai import OpenAI

openai_client = OpenAI()
pc = Pinecone(api_key="YOUR_PINECONE_API_KEY")
index = pc.Index("products-index")  # must already exist

query_vector = openai_client.embeddings.create(
    input="comfortable sneakers for long runs",
    model="text-embedding-3-small"
).data[0].embedding

results = index.query(
    vector=query_vector,
    top_k=10,
    filter={"category": {"$eq": "running"}},  # true pre-filter on metadata
    include_metadata=True
)
for match in results["matches"]:
    print(f"Score: {match['score']:.4f} | SKU: {match['metadata']['sku']}")

Best for: teams that want production-grade vector search with zero operational overhead, can accept SaaS pricing and data-residency constraints, and have the engineering discipline to keep two systems synchronized.

Weaviate: The Open-Source Object Store

Weaviate is an open-source vector database with GraphQL and REST APIs that stores full objects — not just vectors — alongside their embeddings. It has built-in support for multiple modalities (text, image, audio) through its module system and can generate vectors itself via integrated inference modules, so your application can send raw text and let Weaviate handle the embedding call. Its hybrid search combines BM25 keyword scoring with vector similarity in a single query.

Weaviate runs on-premises or in the cloud, including a managed cloud offering. It is the right shape when you need a document store with vectorization baked in rather than an index bolted onto another database. The operational surface is real, though: you are running a JVM-based distributed system with its own backup, monitoring, and upgrade story — separate from your SQL Server estate.

Best for: teams needing a full object store with built-in vectorization and multi-modal support, who are comfortable operating (or paying for) a second database platform.

---

Qdrant: Performance-Per-Dollar, Self-Hosted

Qdrant is an open-source vector database written in Rust with an excellent performance-per-dollar profile. Its standout feature is payload filtering: scalar metadata indexes that interact correctly with the underlying HNSW graph, so filtered vector queries maintain high recall without the post-filter degradation that plagues naive implementations. It also supports quantization (scalar, product, and binary) to shrink memory footprint with modest recall cost, and offers both self-hosted and managed cloud deployments.

For a SQL Server shop, Qdrant is the strongest "dedicated engine, self-hosted" candidate: a single static binary, a straightforward HTTP API, and honest, well-documented performance characteristics. You still own the synchronization problem with your relational data, but the operational burden is lighter than JVM-based alternatives.

Best for: self-hosted deployments where filtered vector search performance and operational simplicity matter more than managed-service convenience.

---

Chroma: The Embedded Prototyping Store

Chroma is a lightweight, embedded-first vector store that runs in-process with Python applications. It is the fastest path from zero to a working semantic-search prototype: pip install, add documents, query. It supports persistent local storage and a client-server mode for small teams, but it is not designed for high-throughput production workloads or multi-tenant isolation at scale.

Chroma's role in a SQL Server architecture is usually temporary — prototype the retrieval logic locally, then promote the schema and queries to SQL Server 2025 native vectors or a dedicated engine for production. Treat it as a sketchpad, not a foundation.

Best for: prototyping, local development, and single-process applications that do not need production durability or scale.

Reading the Map: A Selection Framework

With the pieces on the table, the decision reduces to a handful of questions. Answer them in order and the right system usually selects itself.

1. Where does the vector query need to join relational data? If your retrieval query naturally combines semantic ranking with relational predicates — tenant filters, category constraints, permission checks, joins to orders or inventory — SQL Server 2025 native vectors win on simplicity. Every dedicated engine can store metadata and filter on it, but none of them joins to your Orders table. Keeping vectors next to the data they describe eliminates an entire class of consistency bugs.

2. What scale are you actually at? Under roughly 50,000 vectors, SQL Server's exact VECTOR_DISTANCE search is fast enough that an index is optional. Into the millions, the DiskANN vector index keeps latency flat. Past tens of millions of vectors with high query-per-second demands and aggressive recall targets, the dedicated engines' specialized storage layers start to justify their operational cost. Be honest about which bracket you are in today versus in three years — most teams overestimate.

3. Who operates it? SQL Server native vectors are operated by the DBA team you already have, with the backup, monitoring, and security tooling you already own. Pinecone is operated by Pinecone. Weaviate, Qdrant, and Milvus are operated by whoever you assign — and "whoever" needs to learn a new system. Never underestimate the cost of a second operational model: on-call rotations, upgrade runbooks, and incident muscle memory all double.

4. What are the data-residency and compliance constraints? Embeddings derived from regulated data inherit its compliance requirements. Keeping vectors inside SQL Server means your existing TDE encryption, auditing, and row-level security policies apply unchanged. A SaaS vector database means a new data-processing agreement and a new entry in your compliance register. A self-hosted engine means you reimplement those controls yourself.

One more consideration that cuts across all of these: embedding model lock-in is independent of database choice. Vectors from one model cannot be compared with vectors from another, so switching models means re-embedding your corpus regardless of where the vectors live. Choose the model carefully (Chapter 23), because it is the hardest thing in this stack to change.

---

Key Takeaways

  • → SQL Server 2025 native vectors — the VECTOR(n) type, VECTOR_DISTANCE, DiskANN vector indexes, and VECTOR_SEARCH — make the relational engine itself a legitimate vector database for a large share of workloads, with hybrid relational-plus-vector queries as the killer feature.
  • → Pinecone trades operational burden for SaaS pricing and a synchronization pipeline you must build between your relational data and the vector store. Choose it when you want zero infrastructure to operate and can accept the constraints.
  • → Weaviate is an object store with vectorization baked in — the right shape when you need documents, multi-modal support, and built-in embedding generation rather than an index bolted onto another database.
  • → Qdrant is the strongest self-hosted dedicated option, with correct pre-filtering against its HNSW graph and a light operational footprint. Chroma is a prototyping sketchpad, not a production foundation.
  • → Select by answering four questions in order: does the query join relational data, what scale are you really at, who operates the system, and what do compliance constraints require. Most teams that answer honestly find SQL Server native vectors cover their needs.
