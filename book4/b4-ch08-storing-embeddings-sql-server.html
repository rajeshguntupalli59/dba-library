Chapter 8: Creating and Storing Embeddings in SQL Server

An embedding pipeline has two halves: generating vectors from content, and storing them where queries can reach them. Most teams overthink the first half and underthink the second. Generating an embedding is an API call; storing it well is a schema design, bulk-load, backfill, and lifecycle discipline that determines whether your vector search stays fast and correct for years. This chapter covers the full write path in SQL Server 2025: table patterns for documents and chunks, inserting vectors with proper type conversions, generating embeddings from inside the database with sp_invoke_external_rest_endpoint, bulk-loading millions of vectors efficiently, and backfilling the inevitable gaps.

---

Schema Patterns: Documents, Chunks, and Embeddings

Two schema shapes cover nearly every vector workload. The simple shape — one row per document with a VECTOR column — works when each document is embedded whole. The chunked shape — a parent document table plus a child chunk table carrying the embeddings — is what production RAG systems actually use, because retrieval quality depends on chunking (Chapter 22) and chunks are the unit of both embedding and ranking.

-- Production RAG schema: documents + chunks, embeddings on the chunks
CREATE TABLE dbo.RagDocuments (
    DocumentId  INT IDENTITY(1,1) NOT NULL CONSTRAINT PK_RagDocuments PRIMARY KEY,
    Title       NVARCHAR(300) NOT NULL,
    SourceUri   NVARCHAR(1000) NULL,
    DocHash     BINARY(32) NOT NULL,          -- SHA-256 of source: detects changes
    CreatedAt   DATETIME2(0) NOT NULL CONSTRAINT DF_RagDocuments_CreatedAt DEFAULT SYSUTCDATETIME()
);

CREATE TABLE dbo.RagChunks (
    ChunkId     INT IDENTITY(1,1) NOT NULL CONSTRAINT PK_RagChunks PRIMARY KEY,
    DocumentId  INT NOT NULL CONSTRAINT FK_RagChunks_Documents
                    REFERENCES dbo.RagDocuments (DocumentId) ON DELETE CASCADE,
    ChunkSeq    INT NOT NULL,                 -- order within the document
    ChunkText   NVARCHAR(MAX) NOT NULL,
    TokenCount  INT NOT NULL,
    Embedding   VECTOR(1536) NULL,            -- NULL until embedded
    ModelName   NVARCHAR(100) NULL,
    EmbeddedAt  DATETIME2(0) NULL,
    CONSTRAINT UQ_RagChunks_DocSeq UNIQUE (DocumentId, ChunkSeq)
);
CREATE INDEX IX_RagChunks_DocumentId ON dbo.RagChunks (DocumentId);
CREATE INDEX IX_RagChunks_NeedsEmbedding ON dbo.RagChunks (DocumentId)
    WHERE Embedding IS NULL;                 -- filtered index drives backfill

Several deliberate choices here. DocHash lets the indexing pipeline detect when source content changed and re-chunk only what moved (Chapter 28). The filtered index on Embedding IS NULL makes "find everything still needing embeddings" a trivial seek — the backfill query you will run most often. The single-column integer primary key on the chunk table keeps the door open for a DiskANN vector index later. And ModelName per chunk means a model migration never silently mixes coordinate spaces.

Inserting Vectors: Conversions That Keep You Honest

Application code almost always produces embeddings as JSON arrays of floats. SQL Server converts those strings to the native type with CAST — and the conversion is strict about dimensions, which is a guardrail worth keeping:

-- Strict conversion: wrong dimension count fails loudly (good)
UPDATE dbo.RagChunks
SET Embedding  = CAST('[0.012, -0.043, 0.071, ...]' AS VECTOR(1536)),
    ModelName  = 'text-embedding-3-small',
    EmbeddedAt = SYSUTCDATETIME()
WHERE ChunkId = 42;

-- Defensive pattern for pipeline code: TRY_CAST + explicit check
UPDATE dbo.RagChunks
SET Embedding  = TRY_CAST(@embeddingJson AS VECTOR(1536)),
    ModelName  = @modelName,
    EmbeddedAt = SYSUTCDATETIME()
WHERE ChunkId = @chunkId;

-- Catch rows where conversion failed instead of silently storing NULL
SELECT ChunkId, DocumentId
FROM dbo.RagChunks
WHERE EmbeddedAt IS NULL AND ChunkId IN (...);  -- investigate these

From .NET, the cleanest path is SqlClient with the vector passed as a string parameter converted in T-SQL, or EF Core 10+, whose SQL Server provider maps float[] properties to VECTOR(n) columns with LINQ support for VECTOR_DISTANCE. Python pipelines typically use pyodbc with the JSON-string-plus-CAST pattern. Whichever client you use, parameterize — never concatenate embedding JSON into dynamic SQL.

Generating Embeddings Inside the Database

SQL Server can call out to embedding APIs directly through sp_invoke_external_rest_endpoint, which invokes an HTTPS endpoint — such as Azure OpenAI's embeddings API — and returns the response as JSON. This is genuinely useful for backfills, prototypes, and low-volume workloads: the database that stores the vectors also orchestrates their creation, with no middle-tier service to build.

-- Generate an embedding via Azure OpenAI without leaving T-SQL
-- (Requires a database-scoped credential for the endpoint; see docs)
DECLARE @payload NVARCHAR(MAX) = JSON_OBJECT(
    'input': (SELECT ChunkText FROM dbo.RagChunks WHERE ChunkId = 42),
    'model': 'text-embedding-3-small'
);
DECLARE @response NVARCHAR(MAX);

EXEC sp_invoke_external_rest_endpoint
    @url     = 'https://YOUR-RESOURCE.openai.azure.com/openai/deployments/YOUR-DEPLOYMENT/embeddings?api-version=2024-10-21',
    @method  = 'POST',
    @payload = @payload,
    @response = @response OUTPUT;

-- Extract the embedding array and store it as a native VECTOR
UPDATE dbo.RagChunks
SET Embedding  = CAST(JSON_QUERY(@response, '$.data[0].embedding') AS VECTOR(1536)),
    ModelName  = 'text-embedding-3-small',
    EmbeddedAt = SYSUTCDATETIME()
WHERE ChunkId = 42;

Be clear-eyed about the limits of this pattern. It issues one HTTPS call per invocation, so embedding a million chunks row-by-row through the stored procedure is slow and expensive — and it couples your database to the latency and rate limits of an external API. The right mental model: sp_invoke_external_rest_endpoint is for backfills of modest size, administrative re-embedding, and prototypes. Production ingestion at scale belongs in an application pipeline (Azure Functions, a container job, ADF) that batches requests, honors rate limits, and writes vectors with bulk load — which is the next section.

---

Bulk Loading: Millions of Vectors Without the Pain

The initial load — and every model migration — is a bulk operation, and it should be treated like one. Row-by-row inserts of million-row embedding sets will take hours and generate transaction log pressure that affects the whole instance. The DBA playbook applies directly:

  • → Stage first, then merge. Bulk-load raw embedding JSON into a staging table (heap, no indexes), then INSERT ... SELECT with CAST(... AS VECTOR(n)) into the production table. Validation failures land in staging where they are cheap to inspect, not in production where they roll back a giant transaction.
  • → Batch the transaction. Commit every 5,000–10,000 rows. This bounds transaction log growth, keeps lock escalation from surprising you, and gives restartable checkpoints if the load fails halfway.
  • → Drop the vector index first. If a DiskANN vector index exists on the target table, drop it before the bulk load and rebuild after. Index maintenance during bulk insert is pure overhead, and the preview vector index requires drop-and-recreate to incorporate new data anyway.
  • → Use the fastest path available. bcp, BULK INSERT, or SqlBulkCopy into staging; set-based INSERT...SELECT for the typed load. TABLOCK on the staging insert enables minimal logging where the recovery model allows it.
  • → Validate dimensions in staging. A single malformed vector — wrong dimension count, NaN values, non-numeric tokens — aborts a batch. Check TRY_CAST results in staging and quarantine failures before they touch production.
    • -- Bulk pattern: stage raw JSON, validate, then typed insert in batches
CREATE TABLE dbo.StageEmbeddings (
    ChunkId       INT NOT NULL,
    EmbeddingJson NVARCHAR(MAX) NOT NULL,
    ModelName     NVARCHAR(100) NOT NULL
);  -- heap, no indexes: fastest possible load target

-- ... bcp / BULK INSERT the raw JSON here ...

-- Quarantine malformed rows before they poison the batch
SELECT ChunkId, LEFT(EmbeddingJson, 80) AS Sample
INTO dbo.QuarantineEmbeddings
FROM dbo.StageEmbeddings
WHERE TRY_CAST(EmbeddingJson AS VECTOR(1536)) IS NULL;

DELETE s FROM dbo.StageEmbeddings AS s
JOIN dbo.QuarantineEmbeddings AS q ON q.ChunkId = s.ChunkId;

-- Typed, batched insert into production
DECLARE @batch INT = 10000, @done INT = 0;
WHILE 1 = 1
BEGIN
    UPDATE TOP (@batch) c
    SET c.Embedding  = CAST(s.EmbeddingJson AS VECTOR(1536)),
        c.ModelName  = s.ModelName,
        c.EmbeddedAt = SYSUTCDATETIME()
    FROM dbo.RagChunks AS c
    JOIN dbo.StageEmbeddings AS s ON s.ChunkId = c.ChunkId
    WHERE c.Embedding IS NULL;

    IF @@ROWCOUNT = 0 BREAK;
    SET @done += @@ROWCOUNT;
    RAISERROR('Embedded %d chunks so far', 0, 1, @done) WITH NOWAIT;
END

    Backfill and Lifecycle: Vectors Are Never "Done"

    Embedding storage is a lifecycle, not a one-time load. Documents get added, edited, and deleted; models get upgraded; chunks get re-split. Design the write path for the steady state:

  • → New documents arrive with NULL embeddings; a scheduled job (SQL Agent or an external scheduler) picks them up via the filtered index and embeds them in batches. The application never blocks on embedding latency.
  • → Edited documents are detected by comparing DocHash; only changed documents are re-chunked and re-embedded. Deleting the old chunks first (or versioning them) prevents stale vectors from outranking fresh ones.
  • → Deleted documents cascade to chunks through the foreign key — no orphan vectors. If you soft-delete instead, add the delete flag to every retrieval query's filter.
  • → Model changes mean re-embedding everything into a new column (or table) and cutting over atomically — never mixing coordinate spaces in one column. Chapter 30 covers the migration playbook.

    • A simple monitoring query keeps the lifecycle honest — run it on a schedule and alert when the un-embedded backlog grows:

    -- Backlog health: how much content is waiting for embeddings?
SELECT
    COUNT(*) AS TotalChunks,
    SUM(CASE WHEN Embedding IS NULL THEN 1 ELSE 0 END) AS AwaitingEmbedding,
    MIN(CreatedAt) AS OldestUnembedded
FROM dbo.RagChunks AS c
JOIN dbo.RagDocuments AS d ON d.DocumentId = c.DocumentId;

    ---

    Key Takeaways

  • → Use the chunked schema — documents plus a child chunk table carrying the VECTOR(n) column — with a content hash for change detection, a filtered index on un-embedded rows, and the embedding model recorded per row.
  • → Convert embedding JSON with CAST(... AS VECTOR(n)) and let dimension mismatches fail loudly; use TRY_CAST plus quarantine tables in pipeline code so one malformed vector never aborts a batch.
  • → sp_invoke_external_rest_endpoint lets T-SQL call embedding APIs directly — ideal for backfills and prototypes, but production ingestion at scale belongs in a batched application pipeline.
  • → Bulk-load in three stages: raw JSON into an unindexed staging heap, validation with quarantine, then batched typed inserts — dropping any DiskANN vector index before the load and rebuilding after.
  • → Treat embeddings as a lifecycle: NULL-then-backfill for new documents, hash-based change detection for edits, cascade deletes for removals, and a monitored backlog query so the pipeline never silently stalls.
