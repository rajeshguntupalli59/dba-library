Chapter 17: Qdrant: Payload Filtering and Precision Tuning

Qdrant occupies a distinctive position in the vector database landscape: it was built from the ground up in Rust with a clear architectural opinion that vector search and structured metadata filtering should be first-class equals, not an afterthought. Where other systems treat payload filters as a post-processing step applied after ANN retrieval, Qdrant's filtered HNSW implementation weaves payload conditions directly into the graph traversal itself. The result is a system where adding filters often costs less than you expect, and where the gap between "give me the nearest vectors" and "give me the nearest vectors matching these exact business conditions" nearly disappears. This chapter walks through Qdrant's data model, its payload indexing system, the mechanics of filtered HNSW, and the production configuration knobs that separate a tuned deployment from one that simply runs.

---

17.1 Qdrant's Data Model: Collections, Points, and Payloads

Before touching query syntax, you need to understand how Qdrant organizes data. The mental model maps cleanly to relational concepts, which makes it approachable for DBAs.

A collection is Qdrant's equivalent of a table. It holds a set of points, where each point contains:

  • → A **unique ID** — either a 64-bit unsigned integer or a UUID string
  • → One or more **vectors** — dense, sparse, or multivector depending on configuration
  • → A **payload** — an arbitrary JSON document, roughly analogous to an NVARCHAR(MAX) column holding JSON in SQL Server

    • Unlike traditional databases where schema is enforced at write time, Qdrant's payload schema is flexible by default. You can insert points with completely different payload shapes into the same collection. However, the analogy to SQL Server's JSON support goes further than you might expect: just as SQL Server benefits from indexed computed columns over JSON paths before those paths become filter-efficient, Qdrant requires you to create payload indexes before payload fields become efficient filter predicates.

    This distinction matters. Without a payload index, Qdrant performs a full scan of all payload documents to evaluate a filter condition — effectively a sequential scan. With a payload index, filter evaluation happens in a purpose-built data structure before or during vector traversal.

    Supported payload types and their indexed forms:

    | Payload Type | Qdrant Index Type | Analogy |

    |---|---|---|

    | String/keyword | Keyword index | B-tree on VARCHAR |

    | Integer | Integer index | B-tree on BIGINT |

    | Float | Float index | B-tree on DOUBLE |

    | Boolean | — (inline, fast) | BIT column |

    | Geo coordinates | Geo index | PostGIS spatial index |

    | Full text | Text index (tokenized) | GIN index on tsvector |

    | UUID | UUID index | B-tree on UUID |

    The collection-level configuration also controls vector parameters, distance metrics, and the HNSW graph parameters that affect both search quality and resource consumption. Let's stand up a collection and populate it with something realistic.

    # Python
from qdrant_client import QdrantClient
from qdrant_client.models import (
    Distance,
    VectorParams,
    PointStruct,
    CreateCollection,
)
from sentence_transformers import SentenceTransformer
import uuid

# Connect to a local Qdrant instance (default port 6333)
client = QdrantClient(host="localhost", port=6333)

COLLECTION_NAME = "product_catalog"
VECTOR_DIM = 384  # all-MiniLM-L6-v2 output dimension

# Create collection with explicit HNSW configuration
client.create_collection(
    collection_name=COLLECTION_NAME,
    vectors_config=VectorParams(
        size=VECTOR_DIM,
        distance=Distance.COSINE,
        # HNSW index params — tunable per collection
        hnsw_config={
            "m": 16,               # edges per node; higher = better recall, more RAM
            "ef_construct": 100,   # build-time beam width
            "full_scan_threshold": 10_000,  # switch to brute force below this count
        },
    ),
)

# Create payload indexes BEFORE bulk insert (more efficient)
client.create_payload_index(
    collection_name=COLLECTION_NAME,
    field_name="category",
    field_schema="keyword",
)
client.create_payload_index(
    collection_name=COLLECTION_NAME,
    field_name="price",
    field_schema="float",
)
client.create_payload_index(
    collection_name=COLLECTION_NAME,
    field_name="in_stock",
    field_schema="bool",
)
client.create_payload_index(
    collection_name=COLLECTION_NAME,
    field_name="description",
    field_schema={
        "type": "text",
        "tokenizer": "word",
        "min_token_len": 2,
        "max_token_len": 20,
        "lowercase": True,
    },
)

# Encode some product descriptions
encoder = SentenceTransformer("all-MiniLM-L6-v2")

products = [
    {"id": str(uuid.uuid4()), "text": "Wireless noise-canceling over-ear headphones",
     "category": "electronics", "price": 149.99, "in_stock": True, "brand": "SoundPro"},
    {"id": str(uuid.uuid4()), "text": "Ergonomic mechanical keyboard with RGB backlight",
     "category": "electronics", "price": 89.99, "in_stock": True, "brand": "TypeMaster"},
    {"id": str(uuid.uuid4()), "text": "Standing desk converter, 36-inch wide surface",
     "category": "furniture", "price": 229.00, "in_stock": False, "brand": "DeskRise"},
    {"id": str(uuid.uuid4()), "text": "Portable USB-C hub with 4K HDMI output",
     "category": "electronics", "price": 59.99, "in_stock": True, "brand": "HubTech"},
    {"id": str(uuid.uuid4()), "text": "Adjustable lumbar support office chair",
     "category": "furniture", "price": 399.00, "in_stock": True, "brand": "ErgoSeat"},
]

vectors = encoder.encode([p["text"] for p in products]).tolist()

points = [
    PointStruct(
        id=p["id"],
        vector=v,
        payload={
            "category": p["category"],
            "price":    p["price"],
            "in_stock": p["in_stock"],
            "brand":    p["brand"],
            "description": p["text"],
        },
    )
    for p, v in zip(products, vectors)
]

# Upsert in a single batch
operation_info = client.upsert(
    collection_name=COLLECTION_NAME,
    wait=True,   # synchronous — waits for indexing to complete
    points=points,
)
print(f"Upsert status: {operation_info.status}")

# Verify collection info
info = client.get_collection(COLLECTION_NAME)
print(f"Points count: {info.points_count}")
print(f"Indexed vectors: {info.indexed_vectors_count}")

    The wait=True parameter deserves mention. Qdrant is eventually consistent by default — vectors are accepted into a write-ahead buffer before being incorporated into the HNSW graph. Setting wait=True blocks until the operation is confirmed durable, which is the correct choice for transactional writes. For bulk loading, omitting it (or setting wait=False) allows pipelining and can improve throughput by an order of magnitude, provided you validate completeness afterward.

    17.2 Payload Filtering: From Simple Conditions to Complex Predicates

    Qdrant's filter language uses a nested boolean structure that maps directly to SQL WHERE clauses. Once you see the correspondence, the API becomes predictable.

    The top-level filter is always one of: must (AND), should (OR), must_not (NOT), or their nested combinations. Each condition targets a specific payload field using a typed matcher.

    # Python
from qdrant_client.models import (
    Filter,
    FieldCondition,
    MatchValue,
    MatchAny,
    Range,
    SearchRequest,
)

encoder = SentenceTransformer("all-MiniLM-L6-v2")
query_text = "comfortable headphones for long work sessions"
query_vector = encoder.encode(query_text).tolist()

# -------------------------------------------------------------------
# Example 1: Simple AND filter
# SQL equivalent: WHERE category = 'electronics' AND in_stock = true
# -------------------------------------------------------------------
simple_filter = Filter(
    must=[
        FieldCondition(key="category", match=MatchValue(value="electronics")),
        FieldCondition(key="in_stock", match=MatchValue(value=True)),
    ]
)

results = client.search(
    collection_name=COLLECTION_NAME,
    query_vector=query_vector,
    query_filter=simple_filter,
    limit=5,
    with_payload=True,
    with_vectors=False,
)

for r in results:
    print(f"Score: {r.score:.4f} | {r.payload['description']} | ${r.payload['price']}")

# -------------------------------------------------------------------
# Example 2: Range filter on numeric field
# SQL equivalent: WHERE price BETWEEN 50.00 AND 200.00
# -------------------------------------------------------------------
price_filter = Filter(
    must=[
        FieldCondition(key="price", range=Range(gte=50.0, lte=200.0)),
        FieldCondition(key="in_stock", match=MatchValue(value=True)),
    ]
)

results_price = client.search(
    collection_name=COLLECTION_NAME,
    query_vector=query_vector,
    query_filter=price_filter,
    limit=10,
    with_payload=["description", "price", "brand"],
)

# -------------------------------------------------------------------
# Example 3: OR condition with MatchAny
# SQL equivalent: WHERE category IN ('electronics', 'accessories')
# -------------------------------------------------------------------
category_filter = Filter(
    must=[
        FieldCondition(
            key="category",
            match=MatchAny(any=["electronics", "accessories"]),
        ),
        FieldCondition(key="price", range=Range(lt=100.0)),
    ]
)

# -------------------------------------------------------------------
# Example 4: Nested boolean — (must AND) combined with (should OR)
# SQL equivalent:
#   WHERE in_stock = true
#     AND (category = 'electronics' OR price < 100.0)
# -------------------------------------------------------------------
nested_filter = Filter(
    must=[
        FieldCondition(key="in_stock", match=MatchValue(value=True)),
        Filter(
            should=[
                FieldCondition(key="category", match=MatchValue(value="electronics")),
                FieldCondition(key="price", range=Range(lt=100.0)),
            ]
        ),
    ]
)

results_nested = client.search(
    collection_name=COLLECTION_NAME,
    query_vector=query_vector,
    query_filter=nested_filter,
    limit=5,
    with_payload=True,
)

# -------------------------------------------------------------------
# Example 5: must_not exclusion
# SQL equivalent: WHERE brand != 'SoundPro' AND in_stock = true
# -------------------------------------------------------------------
exclusion_filter = Filter(
    must=[
        FieldCondition(key="in_stock", match=MatchValue(value=True)),
    ],
    must_not=[
        FieldCondition(key="brand", match=MatchValue(value="SoundPro")),
    ],
)

    One thing that trips up developers coming from SQL: Qdrant filters operate on the payload document as a whole, not on join results. There is no equivalent of a multi-table join at query time. If your data model requires join semantics — say, filtering products by a property that lives in a separate entity — you must denormalize that property into the point's payload before inserting. This is standard practice in vector databases and mirrors the document database pattern: write-time denormalization in exchange for read-time simplicity and speed.

    Nested payload fields are accessed with dot notation. If a payload contains {"metadata": {"region": "us-east-1"}}, the filter key is "metadata.region". Arrays are also supported: if a payload field contains ["tag1", "tag2", "tag3"], a MatchValue condition checks whether any element matches.

    17.3 Filtered HNSW: How Qdrant Avoids the Post-Filter Penalty

    To understand why Qdrant's filtered search is competitive with unfiltered search, you need to understand what most other systems do and why it's costly.

    The naive approach — post-filtering:

    1. Retrieve the top-K neighbors from the HNSW graph

    2. Apply payload filters to those K results

    3. Return however many survive the filter

    This works when the filter selectivity is low (most documents pass). When selectivity is high — say, only 0.1% of documents match the filter — you need to retrieve K/0.001 = 1000K candidates to expect K results. At that point, you have effectively done a full graph scan, and the ANN index provides no benefit.

    Qdrant's approach — filtered HNSW traversal:

    Qdrant maintains an additional data structure: a payload filter index for each indexed field, which maps field values to point IDs. During HNSW traversal, Qdrant uses this index to evaluate filter conditions per candidate node *before* computing distances or following graph edges. Nodes that fail the filter condition are skipped during graph traversal, not just discarded afterward.

    The practical effect is that the search explores the graph only through nodes that satisfy the filter. This is closer to how a SQL Server filtered index works: the index was built over a specific subset of data, and queries that match that predicate can use the index directly rather than filtering after retrieval.

    There is a tradeoff: HNSW graphs can become less connected when many nodes are excluded. Qdrant addresses this with an automatic fallback mechanism. When the expected number of matching points falls below full_scan_threshold (configured per collection), Qdrant switches to brute-force search over only the matching points. For small result sets, brute force over a tiny filtered subset is faster than graph traversal anyway.

    # Python
# Demonstrating the performance difference between filtered and unfiltered search,
# and verifying that Qdrant is using its index vs. brute force path.

import time
from qdrant_client.models import SearchParams

# For a larger dataset, create and populate a collection programmatically
import random
import numpy as np

LARGE_COLLECTION = "benchmark_collection"
N_POINTS = 100_000
DIM = 128

# Create collection
try:
    client.delete_collection(LARGE_COLLECTION)
except Exception:
    pass

client.create_collection(
    collection_name=LARGE_COLLECTION,
    vectors_config=VectorParams(
        size=DIM,
        distance=Distance.COSINE,
        hnsw_config={
            "m": 16,
            "ef_construct": 128,
            "full_scan_threshold": 10_000,
        },
    ),
)

# Create payload index before bulk insert
client.create_payload_index(
    collection_name=LARGE_COLLECTION,
    field_name="tenant_id",
    field_schema="keyword",
)
client.create_payload_index(
    collection_name=LARGE_COLLECTION,
    field_name="score",
    field_schema="float",
)

# Generate random points with tenant labels (100 tenants, ~1000 points each)
BATCH_SIZE = 1000
tenants = [f"tenant_{i:03d}" for i in range(100)]

for batch_start in range(0, N_POINTS, BATCH_SIZE):
    batch_ids = list(range(batch_start, min(batch_start + BATCH_SIZE, N_POINTS)))
    batch_vectors = np.random.rand(len(batch_ids), DIM).tolist()
    batch_points = [
        PointStruct(
            id=i,
            vector=v,
            payload={
                "tenant_id": random.choice(tenants),
                "score": random.uniform(0.0, 1.0),
            },
        )
        for i, v in zip(batch_ids, batch_vectors)
    ]
    client.upsert(
        collection_name=LARGE_COLLECTION,
        wait=False,   # async for bulk load throughput
        points=batch_points,
    )

# Wait for indexing to complete
import time
while True:
    info = client.get_collection(LARGE_COLLECTION)
    if info.status.value == "green":
        break
    time.sleep(1)

query_vector = np.random.rand(DIM).tolist()

# Benchmark 1: Unfiltered search
start = time.perf_counter()
for _ in range(50):
    client.search(
        collection_name=LARGE_COLLECTION,
        query_vector=query_vector,
        limit=10,
    )
unfiltered_ms = (time.perf_counter() - start) / 50 * 1000
print(f"Unfiltered search avg latency: {unfiltered_ms:.2f}ms")

# Benchmark 2: Filtered search — 1% selectivity (1 of 100 tenants)
tenant_filter = Filter(
    must=[FieldCondition(key="tenant_id", match=MatchValue(value="tenant_042"))]
)
start = time.perf_counter()
for _ in range(50):
    client.search(
        collection_name=LARGE_COLLECTION,
        query_vector=query_vector,
        query_filter=tenant_filter,
        limit=10,
        search_params=SearchParams(hnsw_ef=128),  # explicit ef at query time
    )
filtered_ms = (time.perf_counter() - start) / 50 * 1000
print(f"Filtered search (1% selectivity) avg latency: {filtered_ms:.2f}ms")

# Benchmark 3: High-selectivity filter — 0.1% with range condition
narrow_filter = Filter(
    must=[
        FieldCondition(key="tenant_id", match=MatchValue(value="tenant_042")),
        FieldCondition(key="score", range=Range(gte=0.95)),
    ]
)
start = time.perf_counter()
for _ in range(50):
    client.search(
        collection_name=LARGE_COLLECTION,
        query_vector=query_vector,
        query_filter=narrow_filter,
        limit=10,
    )
narrow_ms = (time.perf_counter() - start) / 50 * 1000
print(f"High-selectivity filtered search avg latency: {narrow_ms:.2f}ms")
# Note: at very high selectivity, Qdrant switches to brute-force over
# the matching subset, which is often faster than graph traversal

    Exact numbers depend heavily on hardware, dataset size, and dimensionality, so run this benchmark against your own deployment rather than trusting a printed figure — but the general shape holds: unfiltered and 1%-selectivity filtered search land in a similar low-millisecond range, and high-selectivity search (where brute-force kicks in) is often just as fast because the matching set is small. The filtered HNSW penalty is far smaller than the equivalent post-filter architecture.

    17.4 Precision Tuning: ef, Quantization, and Segment Configuration

    Qdrant exposes more precision knobs than most vector databases. Understanding them requires understanding the search accuracy vs. speed tradeoff in concrete terms.

    The ef parameter:

    In HNSW, ef (exploration factor) controls how many candidates the graph explorer keeps in its priority queue during traversal. Higher ef means more candidates explored, which increases recall at the cost of latency. Two separate ef values exist:

  • → `ef_construct`: Used during index build. Set this once at collection creation. Typical values: 100–400. Higher values produce better graph connectivity but slow down writes.
  • → `hnsw_ef` (or `ef` at search time): Used during query. Can be set per-query via `SearchParams`. Typical range: 64–512.

    • The m parameter controls the number of bidirectional edges each node maintains in the graph. Higher m increases RAM usage proportionally but improves recall, especially at lower ef values. For 100k–1M vectors, m=16 is a reasonable default. For datasets requiring very high recall (>99%) at large scale, m=32 or m=64 is warranted.

    Quantization:

    Qdrant supports three quantization strategies that trade accuracy for speed and memory reduction:

    | Strategy | Memory Reduction | Recall Impact | Typical Use |

    |---|---|---|---|

    | Scalar (int8) | ~4x | <1% at ef rescore | General purpose |

    | Product Quantization (PQ) | 8–32x | 2–5% without rescore | Memory-constrained |

    | Binary | ~32x | Significant without rescore | Pre-filtering, speed priority |

    All three support rescoring: after the initial quantized search narrows the candidate set, Qdrant fetches the original full-precision vectors for the top candidates and re-ranks them. This recovers most of the accuracy penalty. The tradeoff is I/O for the rescore step.

    # Python
from qdrant_client.models import (
    ScalarQuantizationConfig,
    ProductQuantizationConfig,
    BinaryQuantizationConfig,
    QuantizationConfig,
    ScalarType,
    CompressionRatio,
)

# ---------------------------------------------------------------
# Creating a collection with scalar quantization (recommended default)
# ---------------------------------------------------------------
client.create_collection(
    collection_name="quantized_products",
    vectors_config=VectorParams(
        size=1536,          # OpenAI text-embedding-3-small dimension
        distance=Distance.COSINE,
        hnsw_config={
            "m": 16,
            "ef_construct": 128,
            "full_scan_threshold": 10_000,
        },
    ),
    quantization_config=ScalarQuantizationConfig(
        type=ScalarType.INT8,
        quantile=0.99,      # clip outliers; 0.99 is conservative
        always_ram=True,    # keep quantized vectors in RAM, originals on disk
    ),
)

# ---------------------------------------------------------------
# Creating a collection with product quantization for memory-constrained environments
# 1536-dim OpenAI vectors compressed to ~192 bytes (8x reduction at m=256)
# ---------------------------------------------------------------
client.create_collection(
    collection_name="compressed_products",
    vectors_config=VectorParams(
        size=1536,
        distance=Distance.COSINE,
    ),
    quantization_config=ProductQuantizationConfig(
        compression=CompressionRatio.X16,  # 16x compression
        always_ram=True,
    ),
)

# ---------------------------------------------------------------
# Per-query control over quantization behavior
# ---------------------------------------------------------------
from qdrant_client.models import QuantizationSearchParams

results = client.search(
    collection_name="quantized_products",
    query_vector=query_vector,
    limit=10,
    search_params=SearchParams(
        hnsw_ef=256,           # higher ef compensates for quantization noise
        quantization=QuantizationSearchParams(
            ignore=False,       # use quantization
            rescore=True,       # rescore top candidates with original vectors
            oversampling=2.5,   # fetch 2.5x candidates for rescore pool
        ),
    ),
)

# ---------------------------------------------------------------
# Optimizer and segment configuration
# These control how Qdrant manages internal storage segments
# ---------------------------------------------------------------
from qdrant_client.models import OptimizersConfigDiff

client.update_collection(
    collection_name="quantized_products",
    optimizer_config=OptimizersConfigDiff(
        # Flush segments to disk when they exceed this size (in KB)
        max_segment_size=200_000,      # 200MB per segment
        # How many points trigger a segment merge
        memmap_threshold=50_000,
        # Minimum number of vectors before HNSW index is built
        # (below this, brute force is used instead)
        indexing_threshold=20_000,
        # Number of concurrent optimizer threads
        max_optimization_threads=2,
        # Flush interval in seconds
        flush_interval_sec=5,
        # Vacuum deleted vectors (tombstone cleanup)
        deleted_threshold=0.2,
        vacuum_min_vector_number=1000,
    ),
)

    Understanding segments:

    Qdrant partitions each collection into segments — immutable or appendable units of storage that each contain a subset of points. New points land in a mutable "appendable" segment. When that segment grows beyond memmap_threshold, the optimizer merges it into a larger immutable segment backed by a memory-mapped file. The immutable segment then gets an HNSW index built on it (once it exceeds indexing_threshold).

    This architecture means that very fresh data that hasn't been incorporated into a segment HNSW index yet is searched via brute force, while indexed segments use HNSW. If your collection receives a heavy write burst followed immediately by queries, you may see temporarily elevated latency or reduced recall until the optimizer catches up. Monitoring indexed_vectors_count vs. points_count from get_collection() gives you visibility into this lag.

    17.5 Named Vectors and Multivector Collections

    A practical scenario that arises frequently: you want to search the same items with multiple embeddings — perhaps a text embedding for semantic search and a separate image embedding for visual similarity. Qdrant handles this natively with named vectors.

    # Python
from qdrant_client.models import NamedVector, NamedSparseVector, SparseVector

# Create a collection with multiple named vector spaces
client.create_collection(
    collection_name="multimodal_products",
    vectors_config={
        "text": VectorParams(
            size=384,
            distance=Distance.COSINE,
        ),
        "image": VectorParams(
            size=512,
            distance=Distance.COSINE,
        ),
        "price_embedding": VectorParams(
            size=32,
            distance=Distance.EUCLID,
        ),
    },
)

# Insert a point with all three vector representations
client.upsert(
    collection_name="multimodal_products",
    points=[
        PointStruct(
            id=1,
            vector={
                "text":            [0.1, 0.2, 0.3] * 128,   # 384-dim placeholder
                "image":           [0.4, 0.5, 0.6] * (512 // 3) + [0.4] * (512 % 3),
                "price_embedding": [0.7] * 32,
            },
            payload={"name": "Wireless Headphones", "price": 149.99},
        )
    ],
    wait=True,
)

# Search using only one named vector
text_query = [0.15, 0.25, 0.35] * 128  # placeholder 384-dim query

results = client.search(
    collection_name="multimodal_products",
    query_vector=NamedVector(name="text", vector=text_query),
    limit=5,
    with_payload=True,
)

# Hybrid search: combine results from text and image vectors
# using Qdrant's query API (v1.7+)
from qdrant_client.models import (
    Prefetch,
    FusionQuery,
    Fusion,
)

image_query = [0.45, 0.55, 0.65] * (512 // 3) + [0.45] * (512 % 3)

# Reciprocal Rank Fusion across two vector spaces
hybrid_results = client.query_points(
    collection_name="multimodal_products",
    prefetch=[
        Prefetch(
            query=NamedVector(name="text", vector=text_query),
            limit=20,
        ),
        Prefetch(
            query=NamedVector(name="image", vector=image_query),
            limit=20,
        ),
    ],
    query=FusionQuery(fusion=Fusion.RRF),
    limit=10,
    with_payload=True,
)

    Named vectors let you avoid maintaining separate collections per modality, which simplifies payload management considerably — you only need one set of payload indexes rather than synchronized copies across multiple collections.

    Sparse vectors for hybrid dense+sparse search:

    Qdrant also supports sparse vectors natively, enabling BM25-style keyword search alongside dense semantic search within the same system.

    # Python
from qdrant_client.models import SparseVectorParams

# Collection with both dense and sparse vector slots
client.create_collection(
    collection_name="hybrid_search_products",
    vectors_config={
        "dense": VectorParams(size=384, distance=Distance.COSINE),
    },
    sparse_vectors_config={
        "sparse": SparseVectorParams(),
    },
)

# Simulate BM25 sparse weights (in production, use a sparse encoder like SPLADE)
def mock_sparse_vector(text: str) -> SparseVector:
    """Toy TF-weighted sparse representation."""
    tokens = text.lower().split()
    token_ids = [hash(t) % 30_000 for t in tokens]
    weights  = [1.0 / (tokens.count(t) ** 0.5) for t in tokens]
    # deduplicate by index
    combined = {}
    for idx, w in zip(token_ids, weights):
        combined[idx] = combined.get(idx, 0.0) + w
    indices = list(combined.keys())
    values  = list(combined.values())
    return SparseVector(indices=indices, values=values)

# Upsert a point with both dense and sparse vectors
import numpy as np

client.upsert(
    collection_name="hybrid_search_products",
    points=[
        PointStruct(
            id=1,
            vector={
                "dense":  np.random.rand(384).tolist(),
                "sparse": mock_sparse_vector("wireless noise canceling headphones"),
            },
            payload={"name": "Wireless Headphones"},
        )
    ],
    wait=True,
)

# Hybrid query: fuse dense semantic search with sparse keyword search
dense_query  = np.random.rand(384).tolist()
sparse_query = mock_sparse_vector("wireless headphones long battery")

hybrid_results = client.query_points(
    collection_name="hybrid_search_products",
    prefetch=[
        Prefetch(
            query=NamedVector(name="dense", vector=dense_query),
            limit=20,
        ),
        Prefetch(
            query=NamedSparseVector(name="sparse", vector=sparse_query),
            limit=20,
        ),
    ],
    query=FusionQuery(fusion=Fusion.RRF),
    limit=10,
    with_payload=True,
)

    17.6 Scroll, Recommendation, and Discovery APIs

    Qdrant exposes several query modes beyond the standard search() endpoint. Each addresses a different retrieval pattern.

    Scroll — paginated full collection scan with filters:

    When you need to iterate over all matching points (not just the nearest neighbors), scroll() provides cursor-based pagination. This is useful for bulk exports, backfill operations, and building recommendation candidate sets from structured criteria alone.

    # Python
from qdrant_client.models import ScrollRequest

# Retrieve all in-stock electronics, paginated
offset = None  # start from the beginning
all_electronics = []

while True:
    results, next_offset = client.scroll(
        collection_name=COLLECTION_NAME,
        scroll_filter=Filter(
            must=[
                FieldCondition(key="category", match=MatchValue(value="electronics")),
                FieldCondition(key="in_stock",  match=MatchValue(value=True)),
            ]
        ),
        limit=100,
        offset=offset,
        with_payload=True,
        with_vectors=False,
    )
    all_electronics.extend(results)
    if next_offset is None:
        break
    offset = next_offset

print(f"Total matching points: {len(all_electronics)}")

    Recommendation API — finding similar items without a query vector:

    The recommendation endpoint accepts one or more positive example point IDs and optional negative example IDs. Qdrant internally fetches those points' vectors, computes an average positive direction, and performs the search. This is the correct abstraction for "more like this" UI patterns without requiring the client to store or re-encode vectors.

    # Python
from qdrant_client.models import RecommendRequest

# "More like this product, but not like that one"
recommendations = client.recommend(
    collection_name=COLLECTION_NAME,
    positive=["product-id-1", "product-id-2"],   # IDs of liked items
    negative=["product-id-3"],                    # IDs of disliked items
    query_filter=Filter(
        must=[FieldCondition(key="in_stock", match=MatchValue(value=True))]
    ),
    limit=5,
    with_payload=True,
)

for rec in recommendations:
    print(f"Score: {rec.score:.4f} | {rec.payload['description']}")

    Discovery API — constrained exploration:

    The discovery endpoint extends the recommendation concept with context pairs — pairs of (positive, negative) examples that define a preference direction without requiring query vectors. It is useful when you want to explore a region of the vector space defined by relative preferences rather than absolute query proximity.

    # Python
from qdrant_client.models import DiscoverRequest, ContextExamplePair

discovery_results = client.discover(
    collection_name=COLLECTION_NAME,
    target="product-id-1",   # item to find neighbors of
    context=[
        ContextExamplePair(
            positive="product-id-4",
            negative="product-id-3",
        )
    ],
    query_filter=Filter(
        must=[FieldCondition(key="category", match=MatchValue(value="electronics"))]
    ),
    limit=5,
    with_payload=True,
)

    17.7 Production Deployment Patterns

    Running Qdrant in production involves decisions about persistence, sharding, replication, and access control. This section covers the patterns that matter most for teams moving from prototype to production.

    Persistence and snapshots:

    Qdrant stores its data in a configurable storage_path directory. The default on-disk format uses memory-mapped files for large segments, which means the OS page cache provides an implicit read buffer. For cloud deployments, map this path to a persistent volume — losing the storage directory means losing all data.

    Qdrant provides a snapshot API for point-in-time backups:

    # Python
# Create a snapshot of a collection
snapshot_info = client.create_snapshot(collection_name=COLLECTION_NAME)
print(f"Snapshot created: {snapshot_info.name}")

# List available snapshots
snapshots = client.list_snapshots(collection_name=COLLECTION_NAME)
for s in snapshots:
    print(f"  {s.name} — {s.size} bytes — created at {s.creation_time}")

# Restore from snapshot (via REST, since Python SDK uses the same endpoint)
# POST /collections/{collection_name}/snapshots/recover
# { "location": "file:///qdrant/snapshots/collection-name/snapshot-name.snapshot" }

    Distributed mode — shards and replication:

    Qdrant's distributed mode partitions a collection into shards, each of which is an independent HNSW index. Shards can be replicated across nodes for fault tolerance. The configuration happens at collection creation:

    # Python
# Create a distributed collection — requires Qdrant cluster mode
client.create_collection(
    collection_name="distributed_catalog",
    vectors_config=VectorParams(size=384, distance=Distance.COSINE),
    shard_number=4,           # 4 shards distributed across nodes
    replication_factor=2,     # each shard replicated to 2 nodes
    write_consistency_factor=1,  # 1 replica must confirm writes
)

    Queries in distributed mode are automatically broadcast to all shards, and results are merged. The write consistency factor controls the durability vs. latency tradeoff: requiring all replicas to confirm (write_consistency_factor=replication_factor) maximizes durability but adds write latency proportional to replica count.

    API key authentication and TLS:

    Qdrant supports simple API key authentication and TLS termination, configured via the config.yaml file rather than the client:

    # qdrant config.yaml (server-side)
service:
  api_key: "your-secret-api-key"
  enable_tls: true
  tls:
    cert: /path/to/server.crt
    key:  /path/to/server.key

storage:
  storage_path: /qdrant/storage
  snapshots_path: /qdrant/snapshots

# Distributed mode
cluster:
  enabled: true
  p2p:
    port: 6335
  consensus:
    tick_period_ms: 100

    On the client side, pass the API key at construction:

    # Python
client = QdrantClient(
    host="your-qdrant-host",
    port=6333,
    api_key="your-secret-api-key",
    https=True,               # enables TLS verification
    prefix="optional/prefix", # useful when behind a path-routing reverse proxy
)

    Monitoring collection health:

    # Python
def collection_health_report(client: QdrantClient, collection_name: str) -> dict:
    """
    Returns a structured health summary useful for alerting dashboards.
    """
    info = client.get_collection(collection_name)
    config = info.config

    total_points    = info.points_count
    indexed_vectors = info.indexed_vectors_count
    index_lag       = total_points - indexed_vectors

    segments = client.get_collection(collection_name).segments_count

    return {
        "collection":       collection_name,
        "status":           info.status.value,
        "total_points":     total_points,
        "indexed_vectors":  indexed_vectors,
        "index_lag":        index_lag,
        "index_lag_pct":    round(index_lag / max(total_points, 1) * 100, 2),
        "segments":         segments,
        "vector_size":      config.params.vectors.size,
        "distance":         config.params.vectors.distance.value,
        "m":                config.hnsw_config.m,
        "ef_construct":     config.hnsw_config.ef_construct,
    }

report = collection_health_report(client, COLLECTION_NAME)
for k, v in report.items():
    print(f"  {k:<22} {v}")

    Write-ahead log and crash recovery:

    Qdrant uses a write-ahead log (WAL) to ensure that accepted writes survive crashes even before segments are flushed. The WAL is replayed on startup. This means your data is safe after wait=True upserts, but a large WAL that hasn't been checkpointed will slow down restart time. The flush_interval_sec optimizer setting controls how frequently WAL entries are checkpointed to segments.

    17.8 Practical Integration Pattern: Tenant-Isolated Search

    A common production pattern when building multi-tenant SaaS applications on Qdrant is to use a single collection with a tenant_id payload field and a keyword index, rather than a separate collection per tenant. This avoids the overhead of managing thousands of collections while still delivering tenant-isolated results.

    # Python
import hashlib
from qdrant_client.models import (
    Filter, FieldCondition, MatchValue,
    PointStruct, VectorParams, Distance,
)
from sentence_transformers import SentenceTransformer
from qdrant_client import QdrantClient

client   = QdrantClient(host="localhost", port=6333)
encoder  = SentenceTransformer("all-MiniLM-L6-v2")

COLLECTION = "saas_documents"

# One-time setup
client.recreate_collection(
    collection_name=COLLECTION,
    vectors_config=VectorParams(size=384, distance=Distance.COSINE),
)
client.create_payload_index(
    collection_name=COLLECTION,
    field_name="tenant_id",
    field_schema="keyword",
)
client.create_payload_index(
    collection_name=COLLECTION,
    field_name="doc_type",
    field_schema="keyword",
)
client.create_payload_index(
    collection_name=COLLECTION,
    field_name="created_at",
    field_schema="integer",  # Unix timestamp — integer index supports range queries
)

def deterministic_point_id(tenant_id: str, doc_id: str) -> int:
    """
    Generate a stable integer point ID from tenant + document ID.
    Qdrant integer IDs must be uint64, so we truncate the hash.
    """
    h = hashlib.sha256(f"{tenant_id}:{doc_id}".encode()).digest()
    return int.from_bytes(h[:8], "big") >> 1  # shift to keep within signed range

def upsert_document(
    tenant_id: str,
    doc_id: str,
    text: str,
    doc_type: str,
    created_at: int,
) -> None:
    vector = encoder.encode(text).tolist()
    point_id = deterministic_point_id(tenant_id, doc_id)
    client.upsert(
        collection_name=COLLECTION,
        points=[
            PointStruct(
                id=point_id,
                vector=vector,
                payload={
                    "tenant_id":  tenant_id,
                    "doc_id":     doc_id,
                    "doc_type":   doc_type,
                    "created_at": created_at,
                    "text":       text,
                },
            )
        ],
        wait=True,
    )

def tenant_search(
    tenant_id: str,
    query: str,
    doc_type: str | None = None,
    min_created_at: int | None = None,
    limit: int = 10,
) -> list[dict]:
    """
    Vector search scoped strictly to a single tenant,
    with optional document type and recency filters.
    """
    must_conditions = [
        FieldCondition(key="tenant_id", match=MatchValue(value=tenant_id))
    ]
    if doc_type is not None:
        must_conditions.append(
            FieldCondition(key="doc_type", match=MatchValue(value=doc_type))
        )
    if min_created_at is not None:
        must_conditions.append(
            FieldCondition(key="created_at", range=Range(gte=min_created_at))
        )

    query_vector = encoder.encode(query).tolist()

    results = client.search(
        collection_name=COLLECTION,
        query_vector=query_vector,
        query_filter=Filter(must=must_conditions),
        limit=limit,
        with_payload=["doc_id", "doc_type", "text", "created_at"],
    )

    return [
        {
            "score":      r.score,
            "doc_id":     r.payload["doc_id"],
            "doc_type":   r.payload["doc_type"],
            "text":       r.payload["text"],
            "created_at": r.payload["created_at"],
        }
        for r in results
    ]

# Example usage
import time

upsert_document(
    tenant_id="acme_corp",
    doc_id="kb-001",
    text="How to reset your password using the account settings page",
    doc_type="knowledge_base",
    created_at=int(time.time()),
)

upsert_document(
    tenant_id="acme_corp",
    doc_id="ticket-0042",
    text="User reports login failure after password reset attempt",
    doc_type="support_ticket",
    created_at=int(time.time()),
)

results = tenant_search(
    tenant_id="acme_corp",
    query="login problems after changing password",
    limit=5,
)

for r in results:
    print(f"[{r['score']:.4f}] ({r['doc_type']}) {r['text'][:80]}")

    This pattern has one significant consideration: if a single tenant accounts for a very large fraction of all points (say, one tenant holds 80% of the data), that tenant's searches will traverse more nodes during HNSW graph construction and querying than a balanced distribution would imply. For severely skewed tenants, the dedicated-collection approach for that specific tenant is worth the operational complexity.

    Key Takeaways

  • → **Qdrant's filtered HNSW** integrates payload conditions directly into graph traversal rather than applying them as a post-filter step. This keeps filtered search latency close to unfiltered latency even at selectivities of 1% or lower, and automatically falls back to brute-force over the matching subset when the result set is very small.
  • → **Payload indexes must be created explicitly** before those fields become efficient filter predicates. The field type you choose — keyword, integer, float, geo, or text — determines which comparison operators are available and how the index is physically structured. Creating indexes before bulk insert is faster than creating them afterward.
  • → **Quantization (scalar, product, or binary) combined with rescoring** is the primary lever for reducing memory footprint without sacrificing meaningful recall. The `always_ram=True` option for quantized vectors keeps the compressed representation in memory for fast candidate retrieval while the full-precision originals can live on disk and are only read for the rescore step.
  • → **Named vectors and sparse vector support** allow a single collection to serve multiple retrieval modalities — dense semantic search, sparse keyword search, and cross-modal fusion — without synchronizing parallel collections. The `prefetch` + `FusionQuery(RRF)` pattern is the idiomatic way to implement hybrid search in Qdrant v1.7+.
  • → **Multi-tenant isolation via payload filtering** (single collection, `tenant_id` keyword index) is operationally simpler than per-tenant collections at moderate tenant counts. The pattern breaks down when tenant data is severely skewed, at which point dedicated collections for the largest tenants become preferable.
