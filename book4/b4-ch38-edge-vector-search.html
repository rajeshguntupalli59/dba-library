Chapter 38: Edge Deployment of Vector Search

The push to run vector search closer to the data source—on mobile devices, embedded hardware, IoT gateways, retail point-of-sale systems, and CDN edge nodes—represents the next frontier for AI-enabled applications. Latency budgets that tolerate 200ms round trips to a central cloud region become unacceptable when you're building real-time product recommendations in a store with spotty connectivity, or semantic search on a drone with no uplink at all. This chapter examines the architectural patterns, tooling choices, and operational tradeoffs of deploying vector search at the edge: what "edge" actually means in this context, which vector engines survive the constraints of limited RAM and CPU, how to synchronize edge indexes with a central store, and how to build applications that degrade gracefully when the edge goes offline.

---

What "Edge" Means for Vector Search

Edge is not a single topology. The term covers at least four distinct deployment tiers, each with different resource profiles and connectivity expectations:

Tier 1: Browser and mobile client. WebAssembly runtimes, React Native apps, and native iOS/Android applications. RAM is 256MB to 2GB usable, storage is flash, and the device may have no network connection for extended periods. The vector index must be embedded in the application bundle or downloaded on first run.

Tier 2: Edge server / CDN PoP. Cloudflare Workers, AWS Lambda@Edge, Fastly Compute@Edge. Memory is severely constrained (128MB to 512MB per worker isolate), and you cannot run a persistent process. Vector search here means either a very small in-memory index loaded at cold start, or a sidecar service running alongside the worker runtime.

Tier 3: On-premise gateway / industrial edge. A Raspberry Pi 4, NVIDIA Jetson, or Intel NUC sitting in a retail store, factory floor, or hospital wing. These have 4–16GB RAM, local NVMe storage, and intermittent WAN connectivity. This is the most capable edge tier and can run a full vector database instance.

Tier 4: Near-edge / regional. A small VM or bare-metal server in a regional co-location facility, 10–30ms from end users rather than 80–120ms to a central cloud region. Full database capabilities, but still subject to the deployment patterns that make edge useful.

The database analogy is familiar: this mirrors the read-replica topology DBAs have used for decades. The central write master holds the source of truth; edge replicas serve reads locally. Vector databases add one wrinkle—the index is not just a data structure but an expensive artifact that takes time and compute to build. You cannot simply stream WAL records and reconstruct an HNSW graph incrementally the way you replay row changes into a B-tree.

| Tier | RAM | Storage | Connectivity | Can run |

|---|---|---|---|---|

| Browser/mobile | 256MB–2GB | Flash | Intermittent | SQLite-vec, Chroma (tiny) |

| CDN edge worker | 128–512MB | None (ephemeral) | Always-on | Static index shard |

| On-premise gateway | 4–16GB | NVMe | Intermittent WAN | Qdrant, SQLite-vec, SQL Server Express |

| Regional near-edge | 32–256GB | NVMe/SAN | Reliable | Full Qdrant, Weaviate, SQL Server Standard |

Understanding which tier you're targeting determines almost every subsequent decision: which engine to use, how to handle index updates, and how to write application code that degrades gracefully.

---

Choosing a Vector Engine for Constrained Environments

The dominant cloud vector databases—Pinecone, Weaviate Cloud, Qdrant Cloud—are designed for servers with abundant RAM and assume reliable network access to their control planes. Deploying them at Tier 1 or Tier 2 is not viable. Even Tier 3 requires careful selection.

SQLite-vec is the most portable option. It is a SQLite extension written in C that adds a vec0 virtual table implementing flat KNN search and a quantized IVF-style index. The entire extension is a single shared library under 200KB. Because SQLite runs in-process, there is no network hop, no daemon to manage, and no port to expose. It is the right choice for mobile and browser-wasm deployments.

# Python
# SQLite-vec: embedded vector search for mobile/edge Python applications
# pip install sqlite-vec

import sqlite3
import sqlite_vec
import numpy as np
from sentence_transformers import SentenceTransformer

def build_local_index(documents: list[dict], db_path: str = "edge_search.db"):
    """
    Build a local vector index using SQLite-vec.
    Appropriate for Tier 3 edge gateways or bundled desktop applications.
    documents: list of {"id": str, "text": str, "metadata": dict}
    """
    model = SentenceTransformer("all-MiniLM-L6-v2")  # 80MB, runs CPU-only
    embeddings = model.encode([d["text"] for d in documents], normalize_embeddings=True)
    dim = embeddings.shape[1]  # 384 for MiniLM

    conn = sqlite3.connect(db_path)
    sqlite_vec.load(conn)  # register the extension

    conn.execute("DROP TABLE IF EXISTS vec_items")
    conn.execute("DROP TABLE IF EXISTS item_metadata")

    # Create the virtual vector table
    conn.execute(f"""
        CREATE VIRTUAL TABLE vec_items USING vec0(
            item_id INTEGER PRIMARY KEY,
            embedding FLOAT[{dim}]
        )
    """)

    # Store metadata in a regular SQLite table (join at query time)
    conn.execute("""
        CREATE TABLE item_metadata (
            item_id INTEGER PRIMARY KEY,
            doc_id  TEXT,
            text    TEXT,
            payload TEXT  -- JSON blob for arbitrary metadata
        )
    """)

    import json
    for i, (doc, emb) in enumerate(zip(documents, embeddings)):
        conn.execute(
            "INSERT INTO vec_items(item_id, embedding) VALUES (?, ?)",
            [i, emb.astype(np.float32).tobytes()]
        )
        conn.execute(
            "INSERT INTO item_metadata(item_id, doc_id, text, payload) VALUES (?, ?, ?, ?)",
            [i, doc["id"], doc["text"], json.dumps(doc.get("metadata", {}))]
        )

    conn.commit()
    print(f"Indexed {len(documents)} documents, dim={dim}, db_path={db_path}")
    print(f"DB size: {os.path.getsize(db_path) / 1024 / 1024:.1f} MB")
    conn.close()

def query_local_index(query_text: str, top_k: int = 5, db_path: str = "edge_search.db"):
    """
    Query the local SQLite-vec index. No network required.
    Typical latency: 2–15ms for 50K vectors on Raspberry Pi 4.
    """
    model = SentenceTransformer("all-MiniLM-L6-v2")
    query_vec = model.encode([query_text], normalize_embeddings=True)[0]

    conn = sqlite3.connect(db_path)
    sqlite_vec.load(conn)

    results = conn.execute("""
        SELECT
            m.doc_id,
            m.text,
            m.payload,
            v.distance
        FROM vec_items v
        JOIN item_metadata m ON m.item_id = v.item_id
        WHERE v.embedding MATCH ?
          AND k = ?
        ORDER BY v.distance
    """, [query_vec.astype(np.float32).tobytes(), top_k]).fetchall()

    conn.close()
    return [
        {"doc_id": r[0], "text": r[1], "metadata": r[2], "distance": r[3]}
        for r in results
    ]

Qdrant ships as a single statically linked binary (~50MB) and is the best choice for Tier 3 on-premise gateways. It supports HNSW indexing, scalar quantization (SQ8), and binary quantization—all of which reduce the RAM footprint dramatically. A collection of 500K 1536-dimensional vectors (OpenAI ada-002 size) uses approximately 3GB uncompressed but drops to under 800MB with binary quantization, making it viable on a device with 4GB total RAM.

SQL Server Express on a gateway box is viable for Tier 3 when you already run SQL Server in your application stack (common in retail and healthcare edge deployments). SQL Server 2025 Express supports the native VECTOR type, VECTOR_DISTANCE, and DiskANN indexes — you get full T-SQL expressivity and can join vector search with transactional data in the same engine, within Express's resource limits. The tradeoff is a larger baseline footprint than Qdrant, but a single engine for everything.

For Tier 1 (browser/mobile), the realistic options narrow further: Transformers.js (WebAssembly port of ONNX Runtime) handles embedding generation in-browser, and SQLite-vec compiled to WASM handles the search. Both fit in a browser tab with no server round-trip.

Index Synchronization: Keeping Edge in Sync with Central

The hardest operational problem in edge vector deployment is not the initial data load—it's keeping edge indexes current as the central store evolves. This is the vector equivalent of replication lag, but with a fundamentally different character: you cannot apply vector index changes as a log of row mutations. An HNSW graph rebuild is not decomposable into atomic operations.

graph TD
    A[Central vector store
canonical collection] -->|1: Snapshot-and-replace| B[Edge node:
hot-swap full index]
    A -->|2: Delta sync via changelog| C[Edge node:
incremental upserts]
    A -->|3: Versioned snapshot| D[Edge node:
immutable, symlink swap]
    B --> E[Local queries served
with no network hop]
    C --> E
    D --> E

*Three synchronization patterns for keeping an edge index current with the central store — the right choice depends on update frequency and acceptable staleness.*

The practical patterns are:

1. Snapshot-and-replace. Periodically export the full collection from the central store as a binary snapshot, ship it to edge nodes, and hot-swap the index. Qdrant supports snapshots natively via its REST API. This is appropriate when the dataset is stable (changes fewer than 5% of vectors per day) and the snapshot fits within your transfer window.

2. Delta sync with a changelog. Maintain a changelog table (or Kafka topic) of vectors inserted, updated, or deleted since the last sync. The edge node consumes the changelog and applies individual upserts. This works well with Qdrant's point upsert API and SQL Server's standard INSERT/UPDATE/DELETE against the vector table (rebuild or reorganize the DiskANN index after heavy delta application — quality remains acceptable until the index is 30–40% updated, at which point a rebuild improves recall by 3–8%).

3. Versioned read-only snapshots. Treat the edge index as immutable. Build a new snapshot for every major data version, push it to edge nodes, and switch a symlink atomically. No online mutation. This is operationally simple and eliminates index drift, at the cost of requiring full rebuilds for every update cycle.

# Python
# Edge synchronization manager: delta sync from central Qdrant to edge Qdrant
# Run this on the edge node as a periodic job (cron / systemd timer)

import time
import json
import hashlib
import sqlite3
import requests
from datetime import datetime, timezone
from qdrant_client import QdrantClient
from qdrant_client.models import PointStruct, UpdateStatus

CENTRAL_URL   = "https://central-qdrant.internal:6333"
CENTRAL_API_KEY = "central-api-key"
EDGE_URL      = "http://localhost:6333"
COLLECTION    = "products"
SYNC_STATE_DB = "/data/sync_state.db"
BATCH_SIZE    = 256

def init_sync_state():
    """Track the last-synced offset per collection in local SQLite."""
    conn = sqlite3.connect(SYNC_STATE_DB)
    conn.execute("""
        CREATE TABLE IF NOT EXISTS sync_state (
            collection  TEXT PRIMARY KEY,
            last_offset TEXT,    -- opaque cursor from central store
            last_sync   TEXT,
            vectors_synced INTEGER DEFAULT 0
        )
    """)
    conn.commit()
    return conn

def get_last_offset(conn, collection: str) -> str | None:
    row = conn.execute(
        "SELECT last_offset FROM sync_state WHERE collection = ?",
        [collection]
    ).fetchone()
    return row[0] if row else None

def save_offset(conn, collection: str, offset: str, count: int):
    conn.execute("""
        INSERT INTO sync_state(collection, last_offset, last_sync, vectors_synced)
        VALUES (?, ?, ?, ?)
        ON CONFLICT(collection) DO UPDATE SET
            last_offset = excluded.last_offset,
            last_sync   = excluded.last_sync,
            vectors_synced = sync_state.vectors_synced + excluded.vectors_synced
    """, [collection, offset, datetime.now(timezone.utc).isoformat(), count])
    conn.commit()

def fetch_delta_from_central(last_offset: str | None, batch_size: int = BATCH_SIZE):
    """
    Scroll through the central Qdrant collection from a given offset.
    Returns (points, next_offset). next_offset is None when fully caught up.
    """
    central = QdrantClient(url=CENTRAL_URL, api_key=CENTRAL_API_KEY)

    scroll_result = central.scroll(
        collection_name=COLLECTION,
        offset=last_offset,          # None = start from beginning
        limit=batch_size,
        with_payload=True,
        with_vectors=True,
    )
    points, next_offset = scroll_result
    return points, next_offset

def apply_delta_to_edge(points):
    """Upsert a batch of points into the local edge Qdrant instance."""
    if not points:
        return 0

    edge = QdrantClient(url=EDGE_URL)
    upsert_points = [
        PointStruct(
            id=p.id,
            vector=p.vector,
            payload=p.payload,
        )
        for p in points
    ]

    result = edge.upsert(
        collection_name=COLLECTION,
        points=upsert_points,
        wait=True,
    )

    if result.status != UpdateStatus.COMPLETED:
        raise RuntimeError(f"Edge upsert failed: {result.status}")

    return len(points)

def run_delta_sync():
    conn = init_sync_state()
    last_offset = get_last_offset(conn, COLLECTION)
    total_synced = 0
    start_time = time.monotonic()

    print(f"[{datetime.now().isoformat()}] Starting delta sync for '{COLLECTION}', offset={last_offset}")

    while True:
        try:
            points, next_offset = fetch_delta_from_central(last_offset)
        except Exception as e:
            print(f"ERROR fetching from central: {e}")
            break

        if not points:
            print(f"Sync complete. Synced {total_synced} vectors in {time.monotonic()-start_time:.1f}s")
            break

        count = apply_delta_to_edge(points)
        total_synced += count
        last_offset = next_offset
        save_offset(conn, COLLECTION, str(next_offset) if next_offset else "COMPLETE", count)

        print(f"  Batch: +{count} vectors | total={total_synced} | next_offset={next_offset}")

        if next_offset is None:
            print("Reached end of collection.")
            break

        time.sleep(0.05)  # Brief pause — don't saturate edge IO

    conn.close()
    return total_synced

if __name__ == "__main__":
    synced = run_delta_sync()
    print(f"Delta sync finished. {synced} vectors applied to edge.")

A critical operational detail: on low-power flash storage (eMMC, SD card), the HNSW index build is IO-intensive enough to wear out the storage over months of frequent rebuilds. Profile the write amplification of your sync strategy. On a Raspberry Pi 4 with an SD card, a full rebuild of 100K vectors writes approximately 2–4GB to disk. At one rebuild per day, that is 60–120GB of writes per month—within the endurance budget of most industrial SD cards (10,000+ program/erase cycles at 8–32GB), but worth tracking.

Offline-First Application Architecture

An edge deployment that assumes continuous connectivity is not truly an edge deployment—it's a remote client. The application must be designed to function when the WAN link is down, when the central vector store is unreachable, and when the local index is days behind the central store. This is the same discipline as offline-first mobile databases, applied to vector search.

The pattern has three states:

  • → **Online with sync.** The edge index is current. Queries run locally. Writes are forwarded to the central store and reflected in the next delta sync.
  • → **Offline with stale index.** The edge index serves queries from its last-known-good state. Results may be incomplete (new vectors not yet synced) but are never wrong (no hallucinated data). The application should surface a freshness indicator to users: "Results reflect data as of 4 hours ago."
  • → **Offline with missing index.** The edge node has just been provisioned and the initial sync has not completed, or the index has been deleted due to a storage failure. The application must degrade gracefully—either surfacing a text search fallback, a curated static list, or a "search unavailable" state.
    • # Python
# Offline-first vector search wrapper with graceful degradation
# Appropriate for a retail kiosk or industrial mobile app

import os
import time
import sqlite3
import sqlite_vec
import numpy as np
import json
import logging
from enum import Enum
from dataclasses import dataclass
from typing import Optional
from sentence_transformers import SentenceTransformer

logger = logging.getLogger("edge_search")


class SearchMode(Enum):
    VECTOR_LOCAL   = "vector_local"    # Local vector index, fully operational
    TEXT_FALLBACK  = "text_fallback"   # FTS5 fulltext search, no vectors
    STATIC_CATALOG = "static_catalog"  # Pre-baked result list, last resort
    UNAVAILABLE    = "unavailable"     # All systems offline


@dataclass
class SearchResult:
    doc_id: str
    text: str
    score: float
    mode: SearchMode
    freshness_seconds: int   # How old is the index data?


class OfflineFirstVectorSearch:
    """
    Edge vector search with graceful degradation through multiple fallback modes.
    Designed for environments where connectivity is intermittent.
    """

    def __init__(
        self,
        vector_db_path: str = "/data/edge_search.db",
        static_catalog_path: str = "/data/static_catalog.json",
        max_acceptable_staleness_hours: float = 48.0,
    ):
        self.vector_db_path = vector_db_path
        self.static_catalog_path = static_catalog_path
        self.max_staleness_seconds = max_acceptable_staleness_hours * 3600
        self._model: Optional[SentenceTransformer] = None

    def _get_model(self) -> SentenceTransformer:
        if self._model is None:
            self._model = SentenceTransformer("all-MiniLM-L6-v2")
        return self._model

    def _check_index_health(self) -> tuple[bool, int]:
        """
        Returns (is_healthy, staleness_seconds).
        Reads a metadata row written by the sync process.
        """
        if not os.path.exists(self.vector_db_path):
            return False, -1

        try:
            conn = sqlite3.connect(self.vector_db_path)
            sqlite_vec.load(conn)

            # Check that the vector table exists and has rows
            row = conn.execute(
                "SELECT COUNT(*) FROM vec_items"
            ).fetchone()
            if row[0] == 0:
                conn.close()
                return False, -1

            # Check sync metadata written by the sync process
            meta = conn.execute("""
                SELECT last_sync_ts FROM sync_metadata
                ORDER BY last_sync_ts DESC LIMIT 1
            """).fetchone()
            conn.close()

            if meta is None:
                return True, 999999  # Index exists but no sync record

            last_sync_ts = meta[0]  # Unix timestamp written by sync job
            staleness = int(time.time() - last_sync_ts)
            return True, staleness

        except Exception as e:
            logger.warning(f"Index health check failed: {e}")
            return False, -1

    def _vector_search(self, query_text: str, top_k: int) -> list[SearchResult]:
        model = self._get_model()
        query_vec = model.encode([query_text], normalize_embeddings=True)[0]

        conn = sqlite3.connect(self.vector_db_path)
        sqlite_vec.load(conn)

        rows = conn.execute("""
            SELECT
                m.doc_id,
                m.text,
                m.payload,
                v.distance,
                s.last_sync_ts
            FROM vec_items v
            JOIN item_metadata m ON m.item_id = v.item_id
            CROSS JOIN (SELECT MAX(last_sync_ts) AS last_sync_ts FROM sync_metadata) s
            WHERE v.embedding MATCH ?
              AND k = ?
            ORDER BY v.distance
        """, [query_vec.astype(np.float32).tobytes(), top_k]).fetchall()
        conn.close()

        last_sync_ts = rows[0][4] if rows else time.time()
        staleness = int(time.time() - last_sync_ts)

        return [
            SearchResult(
                doc_id=r[0],
                text=r[1],
                score=float(r[3]),
                mode=SearchMode.VECTOR_LOCAL,
                freshness_seconds=staleness,
            )
            for r in rows
        ]

    def _fts_fallback(self, query_text: str, top_k: int) -> list[SearchResult]:
        """
        Full-text search using SQLite FTS5. Available even when vector index is broken.
        Lower precision than vector search but always returns something for keyword queries.
        """
        if not os.path.exists(self.vector_db_path):
            return []

        try:
            conn = sqlite3.connect(self.vector_db_path)
            rows = conn.execute("""
                SELECT
                    m.doc_id,
                    m.text,
                    bm25(fts_items) AS score
                FROM fts_items
                JOIN item_metadata m ON m.doc_id = fts_items.doc_id
                WHERE fts_items MATCH ?
                ORDER BY score
                LIMIT ?
            """, [query_text, top_k]).fetchall()
            conn.close()

            return [
                SearchResult(
                    doc_id=r[0],
                    text=r[1],
                    score=float(r[2]),
                    mode=SearchMode.TEXT_FALLBACK,
                    freshness_seconds=999999,
                )
                for r in rows
            ]
        except Exception as e:
            logger.warning(f"FTS fallback failed: {e}")
            return []

    def _static_catalog_fallback(self, top_k: int) -> list[SearchResult]:
        """
        Last-resort fallback: return top items from a pre-baked static catalog.
        The catalog is a JSON file bundled with the application, never stale.
        """
        if not os.path.exists(self.static_catalog_path):
            return []

        try:
            with open(self.static_catalog_path) as f:
                catalog = json.load(f)

            return [
                SearchResult(
                    doc_id=item["id"],
                    text=item["text"],
                    score=0.0,
                    mode=SearchMode.STATIC_CATALOG,
                    freshness_seconds=0,  # catalog is versioned, not time-based
                )
                for item in catalog[:top_k]
            ]
        except Exception as e:
            logger.warning(f"Static catalog fallback failed: {e}")
            return []

    def search(self, query_text: str, top_k: int = 5) -> tuple[list[SearchResult], SearchMode]:
        """
        Main search entry point. Returns results and the mode actually used.
        Callers should surface the mode to users when it is not VECTOR_LOCAL.
        """
        healthy, staleness = self._check_index_health()

        # Attempt vector search if index is healthy and not excessively stale
        if healthy and (staleness < self.max_staleness_seconds or staleness == -1):
            try:
                results = self._vector_search(query_text, top_k)
                if results:
                    return results, SearchMode.VECTOR_LOCAL
            except Exception as e:
                logger.error(f"Vector search failed: {e}")

        # Fall back to FTS
        logger.info("Falling back to FTS search")
        fts_results = self._fts_fallback(query_text, top_k)
        if fts_results:
            return fts_results, SearchMode.TEXT_FALLBACK

        # Fall back to static catalog
        logger.info("Falling back to static catalog")
        static_results = self._static_catalog_fallback(top_k)
        if static_results:
            return static_results, SearchMode.STATIC_CATALOG

        return [], SearchMode.UNAVAILABLE


# Example: retail kiosk application loop
def kiosk_search_demo():
    searcher = OfflineFirstVectorSearch(
        max_acceptable_staleness_hours=24.0
    )

    queries = [
        "wireless headphones under $300",
        "running shoes for flat feet",
        "gifts for coffee lovers",
    ]

    for query in queries:
        results, mode = searcher.search(query, top_k=3)

        freshness_msg = ""
        if results and mode == SearchMode.VECTOR_LOCAL:
            staleness_h = results[0].freshness_seconds / 3600
            if staleness_h > 1:
                freshness_msg = f" (index is {staleness_h:.1f}h old)"

        mode_warning = {
            SearchMode.VECTOR_LOCAL:   "",
            SearchMode.TEXT_FALLBACK:  " [keyword search — vector index unavailable]",
            SearchMode.STATIC_CATALOG: " [showing popular items — search offline]",
            SearchMode.UNAVAILABLE:    " [search unavailable]",
        }[mode]

        print(f"\nQuery: '{query}'{mode_warning}{freshness_msg}")
        for r in results:
            print(f"  {r.doc_id} | {r.text[:60]}")


if __name__ == "__main__":
    kiosk_search_demo()

    The key insight in this pattern is that the application never throws an exception to the user. Every failure mode produces a degraded-but-functional result. This matches the principle that search on a retail floor must always show *something*—a blank screen is worse than a list of popular items that ignores the query.

    WebAssembly: Bringing Vector Search to the Browser

    Tier 1 edge—browser and mobile—requires a different execution model entirely. JavaScript runtimes cannot load native binaries; everything must run in WebAssembly. The two components you need are an embedding model and a vector search engine, both compiled to WASM.

    Transformers.js provides ONNX-Runtime-compiled transformer models running in the browser via WebAssembly. Models are downloaded from Hugging Face and cached in the browser's Cache API. A quantized version of all-MiniLM-L6-v2 is approximately 23MB after quantization—reasonable for a first-run download, cacheable thereafter.

    SQLite-vec compiled to WASM is the search engine. The sqlite-vec project ships WASM builds. Combined with the sql.js or wa-sqlite SQLite WASM bindings, you get a fully in-browser vector index backed by the Origin Private File System (OPFS) for persistence.

    // JavaScript / browser (ES modules)
// In-browser vector search using Transformers.js + SQLite-vec WASM
// No server round-trip for either embedding generation or search

import { pipeline } from "@xenova/transformers";
import initSqlJs from "sql.js";
// sqlite-vec WASM build; load as an ArrayBuffer from your CDN/assets
import sqliteVecWasm from "./sqlite_vec.wasm?url";

let db = null;
let embedder = null;
const DIM = 384;  // all-MiniLM-L6-v2

/**
 * Initialize the embedding model and SQLite-vec database.
 * Call once at application startup.
 * Downloads ~23MB of model weights on first load (cached by browser thereafter).
 */
export async function initEdgeSearch() {
  // Load embedding model — runs entirely in WASM/WebWorker
  embedder = await pipeline(
    "feature-extraction",
    "Xenova/all-MiniLM-L6-v2",
    { quantized: true }   // INT8 quantized: ~23MB vs ~90MB for fp32
  );

  // Load SQLite with sqlite-vec extension
  const SQL = await initSqlJs({
    locateFile: () => sqliteVecWasm,
  });

  // Attempt to restore from OPFS (Origin Private File System) for persistence
  let dbData = null;
  try {
    const root = await navigator.storage.getDirectory();
    const fileHandle = await root.getFileHandle("edge_search.db");
    const file = await fileHandle.getFile();
    dbData = new Uint8Array(await file.arrayBuffer());
    console.log(`Restored index from OPFS (${(dbData.length / 1024 / 1024).toFixed(1)} MB)`);
  } catch {
    console.log("No existing OPFS index; starting fresh.");
  }

  db = dbData ? new SQL.Database(dbData) : new SQL.Database();

  // Create tables if first run
  db.run(`
    CREATE VIRTUAL TABLE IF NOT EXISTS vec_items USING vec0(
      item_id INTEGER PRIMARY KEY,
      embedding FLOAT[${DIM}]
    )
  `);
  db.run(`
    CREATE TABLE IF NOT EXISTS item_metadata (
      item_id INTEGER PRIMARY KEY,
      doc_id  TEXT,
      text    TEXT,
      payload TEXT
    )
  `);

  console.log("Edge search initialized.");
}

/**
 * Embed and index an array of documents into the in-browser SQLite-vec index.
 * @param {Array<{id: string, text: string, metadata?: object}>} documents
 */
export async function indexDocuments(documents) {
  if (!db || !embedder) throw new Error("Call initEdgeSearch() first");

  const texts = documents.map(d => d.text);

  // Generate embeddings in the browser via WASM
  const output = await embedder(texts, { pooling: "mean", normalize: true });
  const embeddings = output.tolist(); // float32[][]

  db.run("BEGIN TRANSACTION");
  try {
    const insertVec  = db.prepare(
      "INSERT OR REPLACE INTO vec_items(item_id, embedding) VALUES (?, ?)"
    );
    const insertMeta = db.prepare(
      "INSERT OR REPLACE INTO item_metadata(item_id, doc_id, text, payload) VALUES (?, ?, ?, ?)"
    );

    for (let i = 0; i < documents.length; i++) {
      const emb = new Float32Array(embeddings[i]);
      insertVec.run([i, emb]);
      insertMeta.run([i, documents[i].id, documents[i].text,
                      JSON.stringify(documents[i].metadata ?? {})]);
    }

    insertVec.free();
    insertMeta.free();
    db.run("COMMIT");
  } catch (e) {
    db.run("ROLLBACK");
    throw e;
  }

  // Persist to OPFS so the index survives page reload
  await persistToOPFS();
  console.log(`Indexed ${documents.length} documents in-browser.`);
}

/**
 * Search the in-browser vector index.
 * @param {string} queryText
 * @param {number} topK
 * @returns {Array<{docId, text, metadata, distance}>}
 */
export async function searchLocal(queryText, topK = 5) {
  if (!db || !embedder) throw new Error("Call initEdgeSearch() first");

  const output = await embedder([queryText], { pooling: "mean", normalize: true });
  const queryVec = new Float32Array(output.tolist()[0]);

  const stmt = db.prepare(`
    SELECT
      m.doc_id,
      m.text,
      m.payload,
      v.distance
    FROM vec_items v
    JOIN item_metadata m ON m.item_id = v.item_id
    WHERE v.embedding MATCH ?
      AND k = ?
    ORDER BY v.distance
  `);

  const rows = [];
  stmt.bind([queryVec, topK]);
  while (stmt.step()) {
    const [docId, text, payload, distance] = stmt.getAsObject(["doc_id","text","payload","distance"]);
    rows.push({ docId, text, metadata: JSON.parse(payload), distance });
  }
  stmt.free();

  return rows;
}

async function persistToOPFS() {
  try {
    const data = db.export();  // Uint8Array of the SQLite file
    const root = await navigator.storage.getDirectory();
    const fileHandle = await root.getFileHandle("edge_search.db", { create: true });
    const writable = await fileHandle.createWritable();
    await writable.write(data);
    await writable.close();
  } catch (e) {
    console.warn("OPFS persistence failed (may not be supported in this browser):", e);
  }
}

    Browser-side vector search has concrete limits. A 50,000-vector index at 384 dimensions occupies roughly 75MB of memory as Float32 arrays, which is within the typical browser tab budget. At 768 dimensions (BERT-base), that doubles to 150MB and begins to compete with the rest of the page. For larger catalogs, apply scalar quantization to INT8 (4× reduction) before writing to the browser index, or shard the index across multiple OPFS files and use a routing layer to pick the relevant shard.

    Security Considerations at the Edge

    Edge deployments surface a threat model distinct from cloud deployments. A Qdrant instance running on a retail floor is physically accessible to an attacker in a way that a cloud database never is. The threat is not only network-based.

    Physical access controls. The edge device should boot from an encrypted disk (LUKS on Linux, BitLocker on Windows IoT). The vector index itself may contain sensitive embeddings—for example, embeddings of customer images in a facial recognition system encode biometric information indirectly. If an attacker extracts the raw float vectors, inversion attacks (reconstructing approximate inputs from embeddings) are plausible for some model architectures.

    Network segmentation. The Qdrant or SQLite-vec instance should not be reachable from the public network. Bind to 127.0.0.1 or a local VLAN interface. If the edge application is a web server that also serves customers, place the vector search on a separate internal interface and never proxy direct access to the vector DB port.

    API key rotation. If the edge node connects to a central Qdrant or Pinecone instance to pull sync data, the API key on the edge device is a credential that could be extracted from the filesystem. Rotate these keys on a schedule and use short-lived tokens (OAuth 2.0 client credentials) where supported. Store keys in the OS keychain or TPM-backed secure enclave, not in plain configuration files.

    Differential privacy for federated indexes. In cases where edge nodes generate embeddings from user behavior and those embeddings are sent back to the central store for model improvement, consider adding calibrated Laplace noise to embeddings before transmission. This prevents the central store from precisely reconstructing individual user interactions while preserving the aggregate signal for retraining.

    When evaluating edge hardware, the metric that most surprises engineers is not raw query latency—HNSW on modern ARM chips is fast—but embedding generation throughput. A MiniLM model running on a Raspberry Pi 4 CPU produces roughly 40–80 sentences per second. If your application must embed user queries at search time, that is imperceptible (one query = one embedding ≈ 12–25ms). If it must re-embed a 100K document catalog on every full sync, that is 20–40 minutes of CPU time. The right mitigation is to embed at the central store and ship float vectors in the sync payload rather than re-embedding on edge.

    Putting It Together: A Retail Edge Deployment

    To make the patterns concrete, consider a mid-size retailer deploying semantic product search on 800 point-of-sale kiosks in stores across a country. Each kiosk runs on an Intel NUC (16GB RAM, 512GB NVMe, intermittent WAN via store Wi-Fi). The product catalog has 250,000 SKUs, each embedded at 384 dimensions using all-MiniLM-L6-v2.

    Central infrastructure. A Qdrant Cloud instance holds the canonical collection. Product catalog updates—new SKUs, price changes, discontinuations—are pushed by the central ERP system via a Kafka topic consumed by an ingestion service that upserts into Qdrant.

    Edge provisioning. New kiosks run a provisioning script on first boot that pulls a full Qdrant snapshot from an S3-compatible store (pre-built nightly from the central collection), hydrates the local Qdrant instance, and writes a sync state record. Snapshot size for 250K × 384-dim vectors with binary quantization is approximately 125MB—a reasonable first-boot download even on slow store Wi-Fi.

    Ongoing sync. A systemd timer runs the delta sync script every 15 minutes. If the WAN is down, the job exits cleanly and retries on the next cycle. The local index stays at whatever state it last successfully synced to.

    Application layer. The kiosk application uses the OfflineFirstVectorSearch wrapper. If the local Qdrant instance is reachable and the index is less than 24 hours stale, queries go local (sub-10ms). If Qdrant is unhealthy (OOM-killed, disk full), the app falls back to an FTS5 index over product names maintained in SQLite. If the SQLite database is also missing, the app shows the store's top-50 bestsellers from a JSON file bundled with the application binary.

    Observability. Each kiosk pushes a lightweight heartbeat every 5 minutes to a central monitoring endpoint when WAN is available: sync lag, index size, p95 query latency, and current search mode. The ops team can see at a glance how many kiosks are in VECTOR_LOCAL vs TEXT_FALLBACK vs STATIC_CATALOG mode and dispatch store IT when a device drifts into persistent fallback.

    This architecture means a network outage or a Qdrant crash on a kiosk produces a degraded-but-functional experience—keyword search still works—rather than a broken one. A full store network outage still allows customers to find products. The catalog data, being relatively stable, makes stale vector results a minor quality concern rather than a correctness issue.

    Key Takeaways

  • → **Edge vector search spans four distinct tiers**—browser/mobile, CDN worker, on-premise gateway, and near-edge regional—each with different RAM budgets, storage media, and connectivity assumptions. Match the engine to the tier: SQLite-vec for embedded/browser use, Qdrant binary with quantization for on-premise gateways, full-featured engines for near-edge.
  • → **Index synchronization is the defining operational challenge.** Unlike row-based replication, HNSW graphs cannot be updated as a log of atomic mutations indefinitely without quality degradation. Design a sync strategy—snapshot-and-replace, delta upsert, or versioned immutable snapshots—that matches your update frequency and acceptable recall budget.
  • → **Offline-first architecture requires multiple fallback layers.** A production edge search system should gracefully degrade from local vector search → full-text search → static curated results rather than failing hard. Surface index freshness to users when results may be stale; never present stale data as current without disclosure.
  • → **Embedding generation throughput, not query latency, is the edge bottleneck.** Generating embeddings on low-power ARM hardware is 10–20× slower than querying an HNSW index. Push embedding computation to the central store and ship float vectors in sync payloads to avoid re-embedding large catalogs on constrained hardware.
  • → **Edge deployments introduce physical security concerns.** Vector indexes may encode sensitive biometric or behavioral signals indirectly. Encrypt edge storage at rest, bind database ports to localhost or internal interfaces only, use short-lived credentials for central sync, and add differential privacy noise to any embeddings transmitted back to central stores for model improvement.
